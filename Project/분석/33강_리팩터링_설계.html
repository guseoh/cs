33-1. 백로그 분류와 우선순위

들어가기 전

1강부터 32강까지 강의 끝마다 "발견 사항·리팩터링 백로그"를 남겼다. 13강 이후 항목만 세어도 결함·위험이 80개를 넘고, 코드 스타일 이탈이 30개 가까이 된다. 1~12강의 지적(도메인 경계, 동결된 아키텍처 위반 204개, 프로세스 메모리 세션 등)까지 합치면 더 많다.

이 목록을 위에서부터 차례로 고치면 실패한다. 이유는 세 가지다.

  • 항목끼리 의존한다. 결제 성공 처리를 한곳으로 모으려면, 먼저 상태 값을 enum으로 바꿔야 비교 코드가 깔끔해진다. 상태를 enum으로 바꾸려면, 먼저 "지금 상태 문자열이 어디서 어떻게 쓰이는지"를 테스트로 고정해야 안전하다. 순서를 거꾸로 하면 같은 코드를 두 번 고치게 된다.
  • 항목마다 필요한 일이 다르다. "정률 쿠폰에 100% 상한이 없다"는 한 줄 검증이면 끝난다. 반면 "결제 PROCESSING 고립"은 상태 기계와 복구 절차를 새로 설계해야 한다. 같은 목록에 섞어 두면 큰 일이 작은 일에 묻히거나, 작은 일이 큰 설계를 기다리며 방치된다.
  • 운영 중인 시스템이다. 31강에서 확인했듯 지금 app01은 실제로 서비스되고 있고, CD 타이머가 main을 자동 배포할 수 있다. 한 번에 크게 바꾸면 되돌릴 방법이 없다. DB 복원 연습도 한 번도 하지 않았다.

그래서 33-1의 목표는 목록을 고치는 순서와 묶음으로 바꾸는 것이다. 고치는 방법 자체는 33-2부터 다룬다.

1. 분류 기준: 항목의 "성격"으로 먼저 나눈다

항목을 위험도만으로 줄 세우면 "인증·결제처럼 무서운 것"이 위로 오고 "매직 문자열" 같은 구조 문제가 아래로 간다. 그런데 실제로는 구조 문제가 결제 재설계의 전제 조건이다. 그래서 먼저 성격으로 나누고, 그 안에서 위험과 의존으로 순서를 정한다.

성격 정의 필요한 일 예
A. 안전망 리팩터링을 시작하기 전에 갖춰야 하는 것. 없으면 "안 바뀌었다"를 증명할 수 없다 테스트·측정·연습을 먼저 만든다 성능 기준선 부재(BL-28-02), DB 복원 미검증(BL-31-03), 보호할 계약 목록 부재(BL-32-01)
B. 공통 기반 여러 영역에 반복되는 구조 문제. 한 번 정하면 모든 영역에 적용된다 규칙과 공용 타입을 설계한다 매직 문자열 상태, HTTP 예외 누수, *TimestampJdbcType 10개, new 로 만드는 협력 객체
C. 핵심 재설계 설계 판단이 결과를 바꾸는 동시성·실패 처리 백지 설계와 대안 비교 결제 PROCESSING 고립, 재고 경합과 잠금 순서, 정기 주문·청구
D. 국소 결함 영향 범위가 한 메서드·한 규칙 안에 있다 테스트 하나와 수정 하나 장바구니 수량 상한, 정률 쿠폰 상한, 찜 목록 공개 필터, 빈 catch
E. 운영 트랙 코드 밖(설정·인프라·절차)의 문제 코드 리팩터링과 별도로 진행 640MiB OOM 조건, 헬스체크 대상, CD 정책 만료, 정본 문서 갱신

이 분류에서 가장 중요한 판단은 A를 맨 앞에 둔 것이다. 점진적 리팩터링의 정의는 "동작을 바꾸지 않고 구조를 바꾸는 것"이다. 그런데 동작이 바뀌지 않았는지 확인할 수단이 없으면, 그것은 리팩터링이 아니라 그냥 재작성이다. 원리

3. 우선순위를 정하는 세 축

같은 성격 안에서는 세 축으로 순서를 정한다.

  1. 피해 크기: 돈·재고·개인정보·가용성에 직접 닿는가. 결제 이중 청구, 재고 음수, 빌링키 노출은 최상위다.
  2. 발생 가능성: 지금 구성(단일 인스턴스, 낮은 트래픽)에서 실제로 일어나는가. 다중 인스턴스 이중 청구는 피해는 크지만 지금은 일어나지 않는다. 반면 OOM은 250 RPS에서 실제로 일어났다.
  3. 선행 의존: 이 항목을 고쳐야 다른 항목을 고칠 수 있는가. 상태 enum은 피해가 직접 생기는 결함이 아니지만, 결제·재고·정기 재설계 모두가 기대는 기반이다.

이 축으로 보면 몇 가지 판단이 나온다.

  • 빌링키 평문 저장은 성격상 C(정기)지만, 피해가 크고 고치는 범위가 비교적 독립적이다. 정기 재설계를 기다리지 않고 공통 기반 단계와 함께 처리할 수 있다. 다만 기존 행을 암호화하는 데이터 이행이 필요하므로 33-8의 DB 변경 절차(expand → migrate → contract)를 따라야 한다.
  • 다중 인스턴스 이중 청구는 피해는 최상위지만, 지금 다중 인스턴스 계획이 없다. 대신 "다중 인스턴스로 가기 전에 반드시 해결" 조건으로 묶어 두고, 지금은 단일 실행을 강제하는 장치(예: 스케줄러 잠금)를 설계에 넣는다.
  • OOM 조건은 운영 트랙이지만 측정 없이 숫자만 바꾸면 안 된다. A(성능 기준선)가 먼저다.

33-2. 안전망 설계

들어가기 전

리팩터링의 정의는 "외부에서 보이는 동작을 바꾸지 않고 내부 구조를 바꾸는 것"이다. 원리 그러니 리팩터링의 첫 질문은 "무엇을 고칠까"가 아니라 "동작이 바뀌지 않았다는 것을 무엇으로 확인할까"다.

PawCycle에는 이미 테스트가 많다. 실제 MySQL로 도는 통합 테스트, 물리 잠금 테스트, 멱등 재생 테스트, ArchUnit 계층 규칙이 있다(29강). 그런데도 28강의 Redis 캐시 회귀는 모든 테스트를 통과했다. 기존 테스트는 "이 기능이 맞게 동작하는가"를 확인하도록 쓰였기 때문이다. 리팩터링에 필요한 것은 "이 기능이 어제와 똑같이 동작하는가"를 확인하는 테스트다. 둘은 비슷해 보이지만 단언하는 대상이 다르다.

이 절은 다섯 겹의 안전망을 설계한다.

1. 특성 테스트: 지금의 동작을 그대로 고정한다

무엇이 다른가

특성 테스트(characterization test)는 Michael Feathers가 『Working Effectively with Legacy Code』에서 정리한 기법이다. 코드가 "어떻게 동작해야 하는가"가 아니라 "지금 어떻게 동작하는가"를 기록한다. 기대값을 손으로 쓰지 않고 현재 구현의 출력을 관찰해서 그대로 단언한다. 그래서 이상해 보이는 동작도 일단 고정한다. 원리

참고 WikiDocs 특성화 테스트: 기존 코드의 행위를 보존하는 안전망 구축이 "버그처럼 보이는 동작도 그대로 고정한다"는 원칙과 작성 순서를 설명한다(검색 요약으로 확인). youngju.dev — 리팩터링 완전 가이드는 특성화 테스트 → 이음새(seam) 찾기 → 점진 교체 순서를 다룬다(검색 요약으로 확인).

"이상한 동작도 고정한다"가 중요하다. 예를 들어 21강에서 환불한 주문이 PAID로 남아 멤버십 결제액에 포함된다는 결함을 찾았다. 특성 테스트는 이 동작을 "현재 동작"으로 일단 고정한다. 그리고 테스트 이름에 결함임을 표시한다. 나중에 결함을 고칠 때 이 테스트를 의도적으로 바꾼다. 그러면 "리팩터링 중 실수로 바뀐 동작"과 "의도적으로 고친 결함"이 커밋에서 구분된다.

PawCycle에서 무엇을 단언하는가

이 시스템에서 "동작"은 HTTP 응답만이 아니다. 결제 하나가 끝나면 DB의 여러 테이블이 동시에 바뀐다. 그래서 특성 테스트는 요청 하나 → 응답 + DB 상태 스냅숏을 단위로 잡는다.

흐름 요청 고정할 DB 상태
체크아웃 POST /api/checkout (Idempotency-Key 포함) orders.status, payments(status, attempt_no), inventories(reserved_quantity, version), inventory_movements(type), member_coupons.status, checkout_idempotency 행
결제 승인 성공 POST /api/payments/confirm + 가짜 결제사 SUCCEEDED 위 + deliveries, notifications, cart_items 소비, member_memberships
결제 승인 실패 가짜 결제사 FAILED 재고 release movement, 쿠폰 원복, 주문 PAYMENT_FAILED
결제 승인 무응답 가짜 결제사 예외 payments.status = UNKNOWN, 재고·쿠폰 그대로
대사 UNKNOWN 결제에 대해 조회 SUCCEEDED 승인 성공과 같은 부가 효과(차이가 있으면 그 차이도 고정)
정기 회차 처리 스케줄러 1회 실행 subscription_orders, orders(source=SUBSCRIPTION), 재고 예약, subscription_schedules.status
정기결제 READY attempt 처리 attempt 상태, UNKNOWN 시 재청구 없음
멱등 재생 같은 키로 두 번 두 번째 응답이 첫 응답과 바이트 단위로 같음

"대사"의 둘째 칸에 주목해야 한다. 19강에서 성공 처리 코드가 승인·대사·정기결제 세 곳에 복제되어 있고 "조금씩 다르다"고 했다. 실제 코드로 비교하면 차이가 보인다. 확인

// PaymentApplicationService.finalizePayment (승인 경로)
payments.consumeCart(payments.findMemberId(payment.orderId()), payment.orderId());

// PaymentReconciliationService (대사 경로)
if ("ONE_TIME".equals(payment.source())) payments.consumeCart(payment.memberId(), payment.orderId());

// SubscriptionBillingProcessor (정기결제 경로) — consumeCart, useReservedCoupon 호출 없음

승인 경로는 주문 출처를 확인하지 않고 장바구니를 소비한다. 대사 경로는 ONE_TIME일 때만 소비한다. 정기결제 경로는 장바구니도 쿠폰도 건드리지 않는다. 특성 테스트는 이 세 가지 동작을 각각 그대로 고정해야 한다. 33-4에서 성공 처리를 하나로 합칠 때, 어느 차이가 의도였고 어느 차이가 결함인지를 이 테스트가 드러낸다.

작성 방식

DB 상태를 비교하는 특성 테스트는 손으로 단언을 쓰면 금방 지친다. 그래서 스냅숏 비교 방식을 쓴다. 관심 있는 테이블의 관심 있는 컬럼만 정렬해서 텍스트로 뽑고, 처음 한 번은 그 텍스트를 파일로 저장(골든 파일)한다. 그 뒤로는 저장된 파일과 비교한다.

// 저장소에 없는 예시 — 결제 승인 성공의 특성 테스트
@Test
void characterization_confirm_success_one_time_order() {
  long orderId = fixtures.checkoutOneTimeOrder(member, sku(2), coupon(FIXED_1000));
  fakeToss.willReturn(SUCCEEDED);

  var response = api.confirm(member, paymentKey, providerOrderId(orderId), amount(orderId));

  approver.verify(
      Snapshot.of(response)
          .table("orders", "id, status, payment_amount", "id = ?", orderId)
          .table("payments", "attempt_no, status, payment_key IS NOT NULL", "order_id = ?", orderId)
          .table("inventories", "sku_id, on_hand_quantity, reserved_quantity", "sku_id IN (?)", skuIds)
          .table("inventory_movements", "type, quantity, reserved_before, reserved_after", "payment_id = ?", paymentId)
          .table("member_coupons", "status", "id = ?", couponId)
          .table("deliveries", "status", "order_id = ?", orderId)
          .table("notifications", "type, target_type", "target_id = ?", orderId)
          .table("cart_items", "count(*)", "member_id = ?", member.id())
          .masking("created_at", "updated_at", "paid_at"));   // 시각은 가린다
}

핵심은 세 가지다.

  • 시각·랜덤 값은 가린다. created_at, UUID로 만드는 providerOrderId 같은 값은 실행마다 다르다. 그대로 비교하면 매번 실패한다. 테스트에서 Clock을 고정하고(이미 여러 서비스가 Clock을 주입받는다), 남는 값은 마스킹한다.
  • 실제 MySQL로 돌린다. 잠금과 생성 컬럼, CHECK 제약이 동작에 포함되기 때문이다. 이미 CI의 Backend lane이 실제 MySQL 8.4를 쓴다(29강).
  • 결제사는 가짜로 둔다. 응답 지연, 예외, 4xx, 5xx를 각각 주입할 수 있어야 한다. 이미 TossTestPaymentAdapter가 프로필별로 있으므로 이것을 시나리오 주입이 가능한 형태로 확장한다.

2. 보호할 계약 목록

특성 테스트는 "지금의 동작"을 지킨다. 그러나 동작 중에는 바뀌면 안 되는 것과 바뀌어도 되는 것이 섞여 있다. 리팩터링 과정에서 결함을 고치면 특성 테스트 일부는 의도적으로 바뀐다. 그때 "바뀌면 안 되는 것"까지 같이 바꾸지 않도록, 계약을 따로 목록으로 둔다.

33-3. 공통 기반 설계

들어가기 전

33-1에서 "공통 기반"으로 분류한 문제는 모두 같은 증상을 보인다. 같은 결정이 코드 여러 곳에 흩어져 있고, 컴파일러가 그 일관성을 지켜 주지 못한다.

  • 결제 상태가 "SUCCEEDED"인지 비교하는 코드가 23곳에 있다. 오타 하나("SUCCEDED")는 컴파일을 통과하고, 그 분기는 영원히 실행되지 않는다.
  • "이 상황은 409다"라는 결정이 서비스 코드 32곳에 숫자로 박혀 있다. 같은 도메인 예외를 배치 작업에서 던지면, HTTP와 상관없는 곳에서 HTTP 숫자를 들고 다니게 된다.
  • 시간을 DB에 쓰는 방법이 JdbcType 클래스 10개에 복제되어 있다.

이 절은 다섯 가지 공통 기반을 설계한다. 원칙은 하나다. 결정은 한 곳에 두고, 나머지는 그 결정을 참조하게 한다. 그리고 점진적 리팩터링이므로, 각 기반은 DB를 바꾸지 않고 도입할 수 있는 형태를 먼저 찾는다.

세 지식이 모두 문자열 비교로 표현되어 있다. 그래서 "결제는 어떤 상태에서 어떤 상태로 갈 수 있는가"를 알려면 코드 전체를 검색해야 한다. 그리고 실제 전이를 막는 것은 SQL의 조건이다. 21강에서 본 쿠폰, 20강에서 본 취소·반품처럼 UPDATE … WHERE status = 'X'가 진짜 문지기다. 확인

목표 구조

상태마다 enum을 만들고, 허용 전이를 enum 안에 표로 둔다.

// 저장소에 없는 예시
public enum PaymentStatus {
  READY, PROCESSING, SUCCEEDED, FAILED, UNKNOWN;     // DB CHECK 제약과 같은 다섯 값

  private static final Map<PaymentStatus, Set<PaymentStatus>> ALLOWED = Map.of(
      READY,      Set.of(PROCESSING, FAILED),        // FAILED: 체크아웃 만료 처리
      PROCESSING, Set.of(SUCCEEDED, FAILED, UNKNOWN),
      UNKNOWN,    Set.of(SUCCEEDED, FAILED),          // 조회로만 확정
      SUCCEEDED,  Set.of(),
      FAILED,     Set.of());

  public boolean canMoveTo(PaymentStatus next) {
    return ALLOWED.get(this).contains(next);
  }

  public PaymentStatus moveTo(PaymentStatus next) {
    if (!canMoveTo(next)) throw new IllegalStateTransition(this, next);
    return next;
  }
}

여기서 중요한 설계 판단이 두 가지 있다.

첫째, SQL의 조건부 UPDATE는 그대로 둔다. enum의 moveTo는 애플리케이션이 실수로 잘못된 전이를 시도하는 것을 막는다. 하지만 두 트랜잭션이 동시에 같은 결제를 바꾸려는 경쟁은 막지 못한다. 그것은 지금처럼 DB가 막아야 한다. 다만 SQL의 조건을 문자열로 다시 쓰지 않고, enum에서 만든다.

// 저장소에 없는 예시 — 전이 SQL을 표에서 만든다
int updated = jdbc.update(
    "UPDATE payments SET status = ?, updated_at = ? WHERE id = ? AND status = ?",
    next.name(), now, paymentId, expectedCurrent.name());
if (updated != 1) throw new ConcurrentTransition(paymentId, expectedCurrent, next);

둘째, enum 이름을 지금 DB에 저장된 문자열과 똑같이 짓는다. 그러면 이 리팩터링에는 migration이 필요 없다. JPA 엔티티는 @Enumerated(EnumType.STRING)으로 바꾸고, 네이티브 SQL은 .name()을 쓰면 된다. DB에 쓰이는 바이트가 한 글자도 바뀌지 않는다. 그래서 롤백도 안전하다. 코드만 되돌리면 된다. 해석

  • 같은 서비스를 HTTP 밖에서 부를 때 의미가 없다. 정기결제 프로세서가 이 예외를 잡을 때 "409"는 아무 의미가 없다. 24강에서 처리 루프가 CommerceException만 잡고 숫자로 분기하지 않는 것도 이 때문이다.
  • HTTP 의미를 바꾸려면 서비스를 고쳐야 한다. 예를 들어 "재고 부족"을 409에서 422로 바꾸려면 서비스 코드를 고쳐야 한다. 웹 계층의 결정이 아래로 새어 들어간 것이다.

4. 멱등성 공용 구조

지금의 모습

멱등 결과를 저장하는 테이블이 네 개다(1강). 체크아웃, 빠른 재주문, 구독 생성, 구독 명령이다. 네 곳 모두 같은 일을 한다.

  1. 요청 지문(fingerprint)을 계산한다(길이 접두사를 붙인 연결 + SHA-256, 15·17강).
  2. 같은 키로 저장된 결과가 있으면 지문을 비교해 재생하거나 409를 낸다.
  3. 없으면 처리하고 결과를 저장한다.

그런데 보관과 정리 정책이 서로 다르다.

테이블 보관 정책 정리 코드 런타임 트리거
구독 생성·명령 첫 성공 + 30일 있음 없음(테스트만 호출, 25강)
체크아웃 없음 없음 없음
빠른 재주문 없음 없음 없음

목표 구조

테이블은 그대로 두고(migration 없음), 코드를 하나의 절차로 모은다.

// 저장소에 없는 예시
public interface IdempotencyStore {
  Reservation reserve(IdempotencyScope scope, String key, Fingerprint fingerprint);
  void complete(Reservation reservation, StoredResponse response);
}

public sealed interface Reservation {
  record Fresh(long id) implements Reservation {}
  record Replay(StoredResponse response) implements Reservation {}
  record Conflict() implements Reservation {}            // 같은 키, 다른 지문
}

// 사용하는 쪽
switch (store.reserve(CHECKOUT, key, fingerprint)) {
  case Replay r   -> { return r.response().as(CheckoutResult.class); }
  case Conflict c -> throw new CommerceException(CommerceError.IDEMPOTENCY_KEY_REUSED);
  case Fresh f    -> { var result = doCheckout(…); store.complete(f, StoredResponse.of(result)); return result; }
}

IdempotencyScope가 테이블을 고르고, 보관 기간과 정리 배치를 함께 정의한다. 그러면 25강의 "정리 코드는 있는데 트리거가 없다"와 "체크아웃·재주문은 정책 자체가 없다"가 한 번에 정리된다. 정리 스케줄러는 하나만 두고, 범위마다 배치 크기를 정한다.

보호할 계약은 25강에서 정한 것을 그대로 따른다.

  • 보관 기간은 첫 성공 시각부터 계산하고, 재생으로 연장하지 않는다.
  • 재생과 정리가 경쟁해도 결과가 깨지지 않는다(25강에서 두 순서 모두 테스트).
  • 지문 계산 방식(길이 접두사)은 바꾸지 않는다. 바꾸면 이미 저장된 키가 모두 Conflict가 된다.

5. 모듈 경계와 외부 포트

지금의 모습

패키지는 도메인별로 나뉘어 있다(commerce/payment, commerce/inventory, …). 계층 규칙은 ArchUnit으로 검사한다. 그러나 도메인 사이의 경계는 강제되지 않는다. 체크아웃 저장소 어댑터 하나가 회원 주소, 장바구니, SKU, 주문, 결제, 쿠폰 저장소를 직접 쓴다. 확인CheckoutPersistenceAdapter 반대로 결제 승인은 배송·알림·멤버십·재고 서비스를 직접 부른다.

리팩터링 이후 새 기능과 AI 활용을 늘릴 계획이라면 이 경계가 가장 먼저 필요하다. 경계가 없으면 새 기능 하나가 여러 도메인의 테이블을 직접 건드리게 되고, 그 기능을 고칠 때 영향 범위를 예측할 수 없다.

33-4. 결제 재설계

들어가기 전

이 절부터 33-6까지는 같은 형식으로 진행한다.

  1. 요구사항만 적는다. 기존 코드를 잊고, 이 영역이 지켜야 할 것을 문장으로 쓴다.
  2. 백지 설계를 한다. 요구사항만 보고 구조를 정하고, 갈림길마다 대안을 비교한다.
  3. 실제 구현과 나란히 놓는다. 같은 판단, 다른 판단, 빠진 것을 구분한다.
  4. 목표 설계를 정한다. 실제 구현의 좋은 결정은 지키고, 빠진 것과 결함만 고친다.

백지에서 시작하는 이유는 "지금 코드가 왜 이렇게 생겼는지" 이미 알고 있으면 그 구조를 정답으로 받아들이기 쉽기 때문이다. 다만 목표 설계는 백지 설계를 그대로 쓰지 않는다. 점진적 리팩터링이므로 지금 구조에서 갈 수 있는 거리만큼만 간다.

1. 요구사항

2. 백지 설계

갈림길 1: 결제사 호출과 트랜잭션의 관계

R3 때문에 결제사 호출은 트랜잭션 밖에 있어야 한다. 그러면 결제 하나가 세 구간으로 나뉜다.

구간 하는 일 트랜잭션
① 선점 READY → PROCESSING. 결제 키를 기록하고 "언제까지 처리 중인가(리스)"를 남긴다 짧은 TX1
② 호출 결제사 승인 API 호출 없음
③ 확정 PROCESSING → SUCCEEDED / FAILED / UNKNOWN과 부가 효과 짧은 TX2

대안으로 "TX1 없이 바로 호출하고 나중에 기록"을 생각해 볼 수 있다. 그러나 이 방식에서는 호출 도중 죽으면 우리 DB에 흔적이 남지 않는다. 결제사에서는 돈이 나갔는데 우리는 그 사실을 모른다. 그래서 호출 전에 반드시 기록을 남긴다. 이것은 31강 A1 워커의 "생성 의도를 먼저 저장"과 같은 원리다. 원리

갈림길 2: 고립된 PROCESSING을 어떻게 찾는가

구간 ②에서 프로세스가 죽거나, ③의 TX2가 교착으로 실패하면 결제는 PROCESSING에 남는다. 이것을 찾아내는 방법은 세 가지다.

방법 내용 장점 단점
A. 시간 기준 updated_at < now - N분인 PROCESSING 컬럼 추가 없음 N을 짧게 잡으면 아직 처리 중인 결제를 건드린다
B. 리스 TX1에서 processing_until = now + N을 기록. 만료된 것만 복구 의도가 명확함. 처리 시간이 다른 경로마다 N을 다르게 컬럼 추가 필요
C. 하트비트 처리 중인 프로세스가 주기적으로 갱신 정확함 결제 한 건에 비해 과함

백지 설계라면 B(리스)를 고른다. 결제사 호출의 타임아웃이 정해져 있으면(예: 30초), 리스를 그보다 넉넉하게(예: 5분) 잡으면 된다. 리스가 만료됐다는 것은 "그 시간 안에 확정되지 않았다"는 뜻이므로, 복구 작업이 건드려도 안전하다.

갈림길 3: 복구는 어떻게 하는가

복구 작업은 두 단계로 나눈다. 이것이 18강에서 본 이슈 #417의 "2단계 확정"이다.

  1. 판정 단계: 리스가 만료된 PROCESSING을 하나 골라 결제사에 조회한다(승인 API를 다시 부르지 않는다, R1).
  2. 확정 단계: 조회 결과가 명확하면(성공 또는 확정 실패) 구간 ③과 같은 확정 로직으로 처리한다. 조회도 불확실하면 UNKNOWN으로 바꾸고 대사 대상에 넘긴다.

여기서 중요한 것은 "같은 확정 로직"이다. 복구가 별도의 성공 처리 코드를 가지면 R7이 깨진다.

갈림길 4: 성공 처리를 어디에 둘 것인가

R5와 R7을 함께 만족하려면 성공 처리는 한 곳에 있어야 한다. 그리고 경로마다 다른 부분은 데이터(주문 출처)로 결정해야 한다.

// 저장소에 없는 예시 — 백지 설계의 성공 처리 진입점
public final class PaymentCompletion {
  public CompletionResult complete(long paymentId, ProviderOutcome outcome) {
    // TX 안에서 호출된다(Propagation.MANDATORY)
    PaymentRow payment = payments.lockById(paymentId);
    if (payment.status().isTerminal()) return CompletionResult.alreadyDone(payment);

    return switch (outcome) {
      case Approved a   -> succeed(payment, a);
      case Declined d   -> fail(payment, d);
      case Indeterminate i -> markUnknown(payment, i);
    };
  }

  private CompletionResult succeed(PaymentRow payment, Approved approved) {
    OrderRow order = orders.lockById(payment.orderId());
    SourcePolicy policy = SourcePolicy.of(order.source());   // ONE_TIME / SUBSCRIPTION

    inventory.deductAll(order.items(), payment.id());         // SKU id 오름차순(33-5)
    payments.transition(payment.id(), PROCESSING_OR_UNKNOWN, SUCCEEDED, approved.key());
    orders.transition(order.id(), PAYMENT_PENDING, PAID);
    deliveries.createPreparing(order.id());
    if (policy.usesCoupon())  coupons.useReserved(order.id());
    if (policy.consumesCart()) carts.consume(order.memberId(), order.id());

    events.publish(new PaymentCompleted(payment.id(), order.id(), order.memberId()));  // 부가 효과
    return CompletionResult.succeeded(payment);
  }
}

SourcePolicy가 핵심이다. "일반 주문은 장바구니를 소비하고 쿠폰을 쓴다, 정기 주문은 둘 다 하지 않는다"는 규칙이 이름 있는 정책으로 한 곳에 있다. 지금처럼 if ("ONE_TIME".equals(payment.source()))가 경로마다 있거나 없는 상태가 아니다.

갈림길 5: 부가 효과를 어떻게 떼어 낼 것인가

R6을 만족하려면 알림과 멤버십 평가를 TX2 밖으로 빼야 한다. 방법은 세 가지다.

방법 동작 장애 시 복잡도
같은 TX(지금) TX2 안에서 직접 호출 부가 효과 실패 → 결제 확정 롤백 가장 낮음
커밋 후 이벤트 @TransactionalEventListener(AFTER_COMMIT) 커밋 직후 프로세스가 죽으면 부가 효과 유실 낮음
아웃박스 테이블 TX2에서 outbox 행을 함께 INSERT, 별도 작업이 읽어 처리 유실 없음(최소 한 번 처리) 중간: 테이블, 처리기, 중복 대비

참고 WikiDocs 트랜잭셔널 아웃박스 패턴: 이벤트 발행과 DB 트랜잭션 원자성 보장이 이중 쓰기 문제와 아웃박스의 동작을 설명한다(검색 요약으로 확인). Spring 쪽 구현 전략은 Spring 공식 블로그 — A Use Case for Transactions: Outbox Pattern Strategies에 있다(제목·요약만 확인).

백지 설계라면 부가 효과마다 따로 판단한다.

  • 멤버십 평가: 365일 결제액을 집계하고 멤버십 행을 잠근다(21강). 무겁고, 실패해도 다음 결제 때 다시 평가하면 결과가 같아진다(멱등). 그리고 하루 늦게 반영돼도 업무상 문제가 작다. → 커밋 후 이벤트 + 실패 시 재평가 배치로 충분하다.
  • 알림: notifications 테이블에 행 하나를 넣는 일이다. 실패할 이유가 거의 없고, 유실되면 고객이 결제 완료 알림을 못 받는다. 그런데 알림 INSERT는 이미 그 자체가 "DB에 기록되는 이벤트"다. → 같은 TX에 남겨도 된다. 다만 알림 생성이 실패해도 결제가 롤백되지 않도록, 알림 생성 코드가 예외를 던질 수 있는 경로(외부 발송 등)를 갖지 않게 한다.

이 판단에서 배울 점은 모든 부가 효과에 같은 도구를 쓰지 않는다는 것이다. 23강에서 Kafka·Outbox를 NOT SELECTED로 판정한 근거(유실이 문제 될 만큼의 비동기 처리 요구가 없음)가 여기서도 그대로 적용된다. 해석

갈림길 6: 결제사 응답을 어떻게 해석할 것인가

R9를 위해 결제사 응답을 세 범주로 나누는 규칙을 한 곳에 둔다.

범주 의미 예
Approved 돈이 나갔다 승인 성공 응답
Declined 돈이 나가지 않았음이 확실하다 카드 한도 초과, 잔액 부족처럼 결제사가 명시한 거절 코드
Indeterminate 모른다 타임아웃, 연결 끊김, 5xx, 해석할 수 없는 4xx

핵심은 4xx를 모두 Declined로 보지 않는 것이다. HTTP 4xx는 "요청이 잘못됐다"는 뜻이지 "결제가 일어나지 않았다"는 보증이 아니다. 예를 들어 이미 승인된 결제를 다시 승인하려 하면 결제사가 4xx(중복 요청)를 돌려줄 수 있는데, 이 경우 돈은 이미 나갔다. 그래서 Declined는 결제사가 문서로 보장한 거절 코드 목록에 있을 때만 쓰고, 나머지 4xx는 Indeterminate로 본다. 원리

3. 실제 구현과 비교

갈림길 백지 설계 실제 구현 판정
1. 구간 분리 선점 TX1 → 호출 → 확정 TX2 같다. confirm()이 transaction.execute로 READY→PROCESSING, 호출, 다시 transaction.execute로 확정 확인 유지
2. 고립 탐지 리스 컬럼 없음. UNKNOWN만 대사 대상이고, PROCESSING은 정기결제 경로에서만 대사(24강) 추가 필요
3. 2단계 복구 조회 → 같은 확정 로직 미구현(#417) 추가 필요
4. 성공 처리 한 진입점 + 출처 정책 승인·대사·정기결제 3곳에 복제, 장바구니 소비 조건이 서로 다름 확인 통합
5. 부가 효과 효과별로 분리 알림·멤버십이 TX2 안 직접 호출 확인 멤버십만 분리
6. 응답 해석 세 범주, 4xx 선별 승인 경로는 4xx를 FAILED로, 조회 경로는 UNKNOWN으로(18강) 통일
금액 검증(R2) 서버 금액과 비교 같다. payment.amount().compareTo(amount) != 0이면 409 확인 유지
멱등 재생(R1) 이미 성공이면 그 결과 반환 같다. SUCCEEDED+PAID+같은 금액+같은 키면 그대로 반환 확인 유지
환불 상태(R8) 주문에 환불 상태 없음. 환불돼도 PAID(21강) 추가 필요

표를 보면 실제 구현의 뼈대는 옳다. 구간 분리, 금액 검증, 멱등 재생은 백지 설계와 같은 결정이다. 문제는 뼈대 위에 쌓인 것들이다. 성공 처리가 복제되면서 조건이 어긋났고, 실패 경로(고립, 응답 해석)가 완성되지 않았다.

4. 목표 설계

단계 1: 응답 해석 통일 (DB 변경 없음)

ProviderOutcome 타입과 해석 규칙을 만들고, 승인·조회·정기결제 어댑터가 모두 이 타입을 돌려주게 한다. 이 단계에서 동작이 바뀌는 지점은 "승인 경로의 일부 4xx가 FAILED 대신 UNKNOWN이 된다"는 것이다. 이것은 의도적 변경이므로, 해당 특성 테스트를 이 PR에서 함께 바꾸고 PR 본문에 명시한다.

단계 2: 성공 처리 통합 (DB 변경 없음)

PaymentCompletion을 만들고 세 경로가 이것을 부르게 한다. 순서가 중요하다.

  1. 지금의 세 경로 동작을 특성 테스트로 고정한다(33-2). 장바구니 소비 조건 차이가 테스트에 드러난다.
  2. PaymentCompletion을 만들되, 처음에는 승인 경로만 이것을 쓰게 한다. 특성 테스트가 통과하는지 본다.
  3. 대사 경로를 옮긴다. 이때 "출처를 보고 장바구니 소비" 규칙이 승인 경로에도 적용되는지 결정한다. 승인 경로는 지금 출처를 보지 않는다. 그런데 승인 API(/api/payments/confirm)는 일반 주문에서만 불린다면 결과는 같다. 이것을 특성 테스트로 확인한 뒤 옮긴다.
  4. 정기결제 경로를 옮긴다.

한 PR에 한 경로씩 옮기면, 문제가 생겼을 때 어느 경로가 원인인지 바로 알 수 있다.

단계 3: 리스와 2단계 복구 (DB 변경 있음)

payments.processing_until 컬럼이 필요하다. 이것은 33-8의 expand → migrate → contract 절차를 따른다.

단계 내용 롤백 가능성
expand processing_until DATETIME NULL 추가. 코드는 아직 쓰지 않음 이전 코드가 이 컬럼을 무시하므로 안전
코드 1 TX1에서 processing_until을 기록 이전 코드로 돌아가도 컬럼은 남지만 무해
코드 2 복구 작업 추가(처음엔 판정만 하고 확정은 로그로만 = 그림자 모드) 끄면 그만
코드 3 복구 작업이 실제 확정 확정 로직은 단계 2의 PaymentCompletion 재사용

이미 있는 PROCESSING 행에는 processing_until이 NULL이다. 복구 작업은 NULL이면 updated_at + 리스 기본값으로 계산한다. 그래서 별도 데이터 이행(backfill)이 필요 없다.

복구 작업을 그림자 모드로 먼저 돌리는 이유는 다중 인스턴스·동시 실행을 아직 검증하지 않았기 때문이다(24강의 이중 청구 위험). 판정 결과만 로그와 지표로 남기고, 실제 확정 로직이 같은 결과를 냈을지 비교한 뒤 켠다.

단계 4: 멤버십 평가 분리 (DB 변경 없음)

PaymentCompleted 이벤트를 커밋 후에 처리하는 리스너로 멤버십 평가를 옮긴다. 실패하면 로그와 지표를 남기고, 매일 한 번 "최근 결제가 있었는데 평가가 갱신되지 않은 회원"을 다시 평가하는 배치를 둔다. 21강에서 "멤버십 재평가 배치가 없다"고 지적한 것이 함께 해결된다.

단계 5: 환불 상태 (DB 변경 있음)

주문 상태에 REFUNDED(필요하면 PARTIALLY_REFUNDED)를 추가한다. 이것도 expand가 먼저다.

  1. DB CHECK 제약에 새 값을 추가만 한다(CHECK (status IN (…, 'REFUNDED'))). 이전 코드는 이 값을 쓰지 않으므로 안전하다.
  2. OrderStatus enum에 값을 추가하고, 환불 완료 시 주문을 REFUNDED로 바꾼다.
  3. 멤버십 집계 쿼리가 status = 'PAID'만 세는지 확인한다(21강). 그러면 환불 주문이 자동으로 빠진다.
  4. 과거에 환불됐는데 PAID로 남은 주문을 고칠지 결정한다. 고친다면 별도 데이터 이행 PR로 분리하고, 복원 연습(33-2) 이후에 한다.

주의: 이전 버전 코드는 REFUNDED를 모른다. 단계 2를 배포한 뒤 롤백하면, 이전 코드가 REFUNDED 주문을 읽을 때 문자열 비교에서 어느 분기에도 걸리지 않는다. 그래서 단계 2 배포 전에 "이전 버전이 모르는 주문 상태를 만나면 어떻게 동작하는가"를 특성 테스트로 확인해 둔다. 해석

5. 남는 위험

위험 대응
다중 인스턴스에서 복구 작업이 같은 결제를 동시에 조회·확정 복구 대상 선택을 FOR UPDATE SKIP LOCKED로 하고, 확정은 조건부 UPDATE로 한 번만 성공하게 한다. 다중 인스턴스 전에 반드시 검증
결제사가 "조회" API에서도 불확실한 응답을 계속 돌려줌 UNKNOWN으로 두고 사람이 처리하는 운영 대시보드(이미 OperationsQueryRepository가 PAYMENT_ACTION_REQUIRED를 모은다)
커밋 후 이벤트 유실 멤버십은 재평가 배치로 보정. 유실되면 안 되는 효과가 생기면 그때 아웃박스 도입

정리

  • 실제 결제 구현의 뼈대(선점 → 호출 → 확정, 금액 검증, 멱등 재생)는 백지 설계와 같은 결정이다. 이 뼈대는 지킨다.
  • 고칠 것은 뼈대 위의 네 가지다. 성공 처리 통합, 응답 해석 통일, 고립 PROCESSING 복구, 부가 효과 분리.
  • 순서는 DB 변경이 없는 것부터다. 응답 해석 → 성공 처리 통합 → 리스·복구 → 멤버십 분리 → 환불 상태.

33-5. 재고 재설계

들어가기 전

재고는 숫자 하나다. 그런데 이 숫자를 바꾸는 경로가 많다. 체크아웃 예약, 결제 성공 차감, 결제 실패·만료 해제, 취소·반품 복원, 관리자 조정, 그리고 정기 주문의 자체 예약이다. 경로가 많을수록 "두 요청이 같은 SKU를 동시에 바꿀 때"의 경우의 수가 늘어난다.

17강에서 이 프로젝트가 재고 경합을 어떻게 다루는지 봤다. FOR UPDATE로 행을 잠그고, 그 위에 version CAS를 한 번 더 건다(#335·#336). 그리고 모든 변경을 inventory_movements 원장에 남기고, UNIQUE(payment_id, type, sku_id)로 같은 결제의 중복 차감을 막는다.

이 구조는 정합성 측면에서 단단하다. 이 절에서 다루는 문제는 정합성이 아니라 교착(deadlock)과 일관성 없는 진입점이다.

1. 요구사항

번호 요구사항
R1 가용 재고는 음수가 되지 않는다
R2 같은 결제가 같은 SKU를 두 번 예약·차감하지 않는다
R3 재고의 모든 변경은 원장(movement)에 남는다. 원장을 합산하면 현재 재고와 일치한다
R4 여러 SKU를 한 번에 바꾸는 요청끼리 교착에 빠지지 않는다
R5 재고 부족과 일시적 경합을 구분해 응답한다(부족은 사용자에게, 경합은 재시도)
R6 일반 주문과 정기 주문이 같은 규칙으로 재고를 다룬다
R7 인기 상품에 요청이 몰려도 처리량이 급격히 무너지지 않는다

2. 백지 설계: 세 가지 동시성 전략

재고를 줄이는 방법은 세 가지가 대표적이다.

전략 A: 비관적 잠금 (SELECT … FOR UPDATE)

SELECT available_quantity, reserved_quantity FROM inventories WHERE sku_id = ? FOR UPDATE;
-- 애플리케이션이 판단
UPDATE inventories SET available_quantity = available_quantity - ?, reserved_quantity = reserved_quantity + ? WHERE sku_id = ?;
  • 읽는 순간 행을 잠근다. 다른 트랜잭션은 커밋될 때까지 기다린다.
  • 판단 로직이 복잡해도 안전하다. 읽은 값이 바뀌지 않음이 보장되기 때문이다.
  • 대가: 잠금을 잡은 채로 다른 일을 하면 대기가 길어진다. 여러 행을 잠그면 순서에 따라 교착이 생긴다.

전략 B: 낙관적 잠금 (version CAS)

SELECT available_quantity, version FROM inventories WHERE sku_id = ?;
UPDATE inventories SET available_quantity = available_quantity - ?, version = version + 1
 WHERE sku_id = ? AND version = ?;   -- 영향 행 0이면 누군가 먼저 바꿨다
  • 읽을 때 잠그지 않는다. 쓸 때 "내가 읽은 뒤로 아무도 안 바꿨다"를 확인한다.
  • 대가: 경합이 잦으면 재시도가 폭증한다. 인기 상품에 100명이 몰리면 99명이 실패하고 다시 시도한다.

전략 C: 조건부 UPDATE (원자적 차감)

UPDATE inventories SET available_quantity = available_quantity - ?, reserved_quantity = reserved_quantity + ?
 WHERE sku_id = ? AND available_quantity >= ?;   -- 영향 행 0이면 재고 부족
  • 판단과 변경이 SQL 한 문장이다. DB가 그 행에 대해 짧게 배타 잠금을 잡고, 조건을 다시 평가한 뒤 바꾼다. 원리
  • 경합이 잦아도 재시도가 필요 없다. 두 번째 요청은 첫 번째가 커밋되기를 기다렸다가 바뀐 값으로 조건을 다시 본다.
  • 대가: 판단 로직이 SQL 조건으로 표현될 만큼 단순해야 한다. 그리고 "바뀌기 전 값"을 원장에 남기려면 변경 후에 다시 읽거나 계산해야 한다.

참고(검색 요약) velog 쇼핑몰 재고관리 — 동시성 문제 해결방법 탐구: 낙관락&비관락, 분산락과 「동시에 같은 데이터를 수정하면 어떻게 되나요?」가 세 방식을 비교한다. 공통 결론은 "단순 조건으로 끝나는 차감은 조건부 UPDATE, 복잡한 검증이 필요하면 FOR UPDATE, 충돌이 적은 편집은 version"이다.

백지 설계의 선택

재고 예약·차감의 판단은 "가용 수량이 요청 수량 이상인가" 하나다. 그래서 전략 C가 가장 자연스럽다.

기준 A. FOR UPDATE B. version CAS C. 조건부 UPDATE
R1 음수 방지 애플리케이션이 판단 애플리케이션이 판단 DB가 보장
R5 부족 vs 경합 구분 가능 경합이 "변경됨"으로 섞임 영향 행 0 = 부족
R7 몰림 시 처리량 대기 줄 재시도 폭증 대기 줄(짧음)
원장 이전 값 기록 읽은 값 그대로 읽은 값 그대로 변경 후 다시 읽거나 계산
교착 다중 행이면 순서 의존 없음(잠금 없음) 다중 행이면 순서 의존

C도 여러 SKU를 바꾸면 각 UPDATE가 행 잠금을 잡는다. 그래서 교착 문제(R4)는 전략과 상관없이 잠금 순서로 풀어야 한다.

3. 교착: 잠금 순서의 문제

교착은 어떻게 생기는가

교착은 두 트랜잭션이 서로 상대가 잡은 잠금을 기다릴 때 생긴다. 원리 트랜잭션 1이 X를 잡고 Y를 기다리고, 트랜잭션 2가 Y를 잡고 X를 기다리면 둘 다 영원히 진행하지 못한다. InnoDB는 이것을 감지해 한쪽을 롤백시킨다.

모든 트랜잭션이 같은 순서로 잠그면 교착은 생기지 않는다. X를 항상 Y보다 먼저 잠그면, 누군가 Y를 잡고 있다는 것은 이미 X를 잡았다는 뜻이다. 그래서 X를 기다리며 Y를 쥐고 있는 상황이 나올 수 없다.

PawCycle의 잠금 순서

17·18강에서 확인한 잠금 순서를 나란히 놓으면 다음과 같다.

경로 잠금 순서(확인)
체크아웃 회원 행(장바구니 잠금, lockForAdd) → 장바구니 항목 → 재고(장바구니 항목 순서대로) → 쿠폰
결제 확정 TX2 결제 → 재고(주문 항목 순서대로) → 주문 → … → 장바구니 소비
체크아웃 만료 결제 → 재고 해제 → 쿠폰 → 결제·주문
정기 주문 (잠금 없이) 재고 version CAS

두 가지 문제가 보인다.

  1. 장바구니와 재고의 순서가 반대다. 체크아웃은 장바구니 → 재고, 결제 확정은 재고 → 장바구니다. 같은 회원이 체크아웃 직후 이전 주문의 결제를 확정하는 상황이 겹치면 교착 후보가 된다(18강에서 해석으로 지적).
  2. 여러 SKU의 잠금 순서가 정해져 있지 않다. 장바구니 항목 순서, 주문 항목 순서는 ORDER BY 없이 PK 스캔 순서에 기댄다(17강). 두 주문이 같은 두 SKU를 서로 다른 순서로 담으면 교착 후보가 된다.

지금 교착이 실제로 보고되지 않은 이유는 트래픽이 낮기 때문이다. 단일 인스턴스, 낮은 동시성에서는 두 트랜잭션이 정확히 겹칠 확률이 작다. 하지만 정기배송 몰림(23강 1만 건)과 일반 주문이 겹치는 순간이 오면 이야기가 달라진다. 해석

전역 순서를 하나 정한다.

회원(장바구니) → 주문 → 결제 → 재고(SKU id 오름차순) → 쿠폰
  • 결제 확정 TX2는 재고보다 장바구니를 먼저 잠근다. 장바구니 소비는 TX2의 마지막에 하지만, 잠금은 처음에 잡는다(SELECT … FOR UPDATE로 회원 장바구니 행을 먼저). 소비 자체는 그대로 마지막에 한다.
  • 재고는 항상 sku_id 오름차순으로 다룬다. InventoryService에 단건 메서드 대신 reserveAll(List<Line>), deductAll(…)처럼 여러 줄을 받는 메서드를 두고, 메서드 안에서 정렬한다. 호출자가 순서를 신경 쓰지 않아도 되게 만드는 것이 핵심이다.
// 저장소에 없는 예시 — 순서를 서비스가 책임진다
public void reserveAll(long paymentId, List<StockLine> lines) {
  List<StockLine> merged = StockLine.mergeBySku(lines);           // 같은 SKU 합산
  merged.sort(Comparator.comparingLong(StockLine::skuId));       // 전역 순서
  for (StockLine line : merged) {
    int updated = inventories.reserveIfAvailable(line.skuId(), line.quantity());
    if (updated == 0) throw new CommerceException(CommerceError.INVENTORY_INSUFFICIENT);
    movements.recordReserve(paymentId, line);                    // UNIQUE(payment_id, type, sku_id)
  }
}

mergeBySku가 숨은 결함 하나를 막는다. 장바구니에 같은 SKU가 두 줄로 들어 있으면(옵션이 같은 상품을 따로 담은 경우 등), 지금 코드는 같은 결제로 같은 SKU를 두 번 예약하려다 UNIQUE(payment_id, type, sku_id)에 걸린다. 이 상황이 실제로 생길 수 있는지는 장바구니 담기 규칙(16강)에 달려 있으므로 특성 테스트로 확인한다. 미확인

FOR UPDATE + CAS는 왜 둘 다 있는가

실제 코드는 행을 FOR UPDATE로 잠근 뒤 version 조건까지 건 UPDATE를 한다. 잠금을 잡은 이상 그 행을 다른 트랜잭션이 바꿀 수 없으므로, version 조건은 이 경로에서는 항상 참이다.

17강에서 본 #335·#336의 맥락은 정기 주문 경로였다. 정기 주문은 잠금 없이 CAS만 쓴다. 그래서 체크아웃 경로와 정기 주문 경로가 같은 행을 동시에 바꿀 때, 정기 주문의 CAS가 체크아웃의 변경을 감지하려면 체크아웃도 version을 올려야 한다. 즉 체크아웃의 version 증가는 정기 주문 경로를 위한 것이다. 해석

진입점을 하나로 합치면 이 이중 방어는 필요 없어진다. 모든 경로가 같은 조건부 UPDATE를 쓰면, DB가 행 단위로 직렬화해 주기 때문이다. version 컬럼은 남겨 두되(관리자 화면의 동시 편집 감지 등에 쓸 수 있다), 재고 차감의 정합성은 가용 조건으로 지킨다.

원장의 "이전 값"은 어떻게 기록하나

조건부 UPDATE로 바꾸면 "UPDATE 전에 읽은 값"이 없다. 원장에는 available_before, available_after 같은 값이 있다(17강). 해결은 두 가지다.

  • UPDATE 뒤에 같은 TX에서 다시 읽는다. UPDATE가 행 잠금을 잡았으므로, 같은 TX의 다음 SELECT는 방금 바꾼 값을 본다. before는 after에 수량을 더해 계산한다.
  • MySQL 8의 UPDATE … ; SELECT ROW_COUNT()만으로는 이전 값을 얻을 수 없다. PostgreSQL의 RETURNING이 MySQL에는 없다. 그래서 첫 번째 방법을 쓴다.

6. 없는 행에 대한 FOR UPDATE

재고 영역 밖이지만 같은 잠금 문제라 함께 다룬다. 16·20·21·22강에서 "없는 행에 FOR UPDATE를 거는 곳"을 여러 번 지적했다. 빠른 재주문 멱등 조회, 취소·반품, 첫 멤버십 평가, 구독 명령 키 예약이다.

원리 InnoDB의 REPEATABLE READ에서 존재하지 않는 키를 FOR UPDATE로 찾으면, 그 키가 들어갈 틈(gap)에 잠금이 걸린다. 갭 락끼리는 서로 막지 않는다. 그래서 두 트랜잭션이 같은 틈에 갭 락을 잡을 수 있다. 그다음 둘 다 그 틈에 INSERT하려 하면, 각자 상대의 갭 락에 막혀 교착이 된다.

16강에서 이 프로젝트가 장바구니에 대해 이미 해법을 썼다. 부모 행(회원)을 먼저 잠근다. 부모 행은 반드시 존재하므로 갭 락이 아니라 레코드 락이 걸리고, 같은 회원의 요청은 거기서 줄을 선다. 같은 방법을 나머지 경로에 적용한다.

경로 지금 목표
빠른 재주문 멱등 없는 키에 FOR UPDATE 회원 행 먼저 잠금 → 키 조회
취소·반품 없는 요청에 FOR UPDATE 주문 행 먼저 잠금
첫 멤버십 평가 없는 멤버십 행에 FOR UPDATE 회원 행 먼저 잠금, 또는 INSERT … ON DUPLICATE KEY
구독 명령 키 예약 없는 키에 FOR UPDATE 구독 행 먼저 잠금(22강이 "의도적으로 보존"이라고 한 부분은 그 이유를 특성 테스트로 남긴 뒤 판단)

정리

  • 재고의 정합성 구조(원장 + UNIQUE + 트랜잭션 강제)는 이미 좋다. 지킨다.
  • 고칠 것은 진입점과 순서다. 모든 재고 변경을 InventoryService의 다건 메서드로 모으고, 그 안에서 SKU id 오름차순으로 다룬다.
  • 진입점이 하나가 되면 FOR UPDATE + CAS 이중 방어를 조건부 UPDATE 하나로 단순화할 수 있다.
  • 결제 확정 TX2는 장바구니 잠금을 맨 앞으로 옮겨 체크아웃과 순서를 맞춘다.

33-6. 정기배송 재설계

들어가기 전

정기배송은 이 시스템에서 사람 없이 돈이 움직이는 유일한 경로다. 일반 구매는 고객이 결제 버튼을 누르고 결과를 본다. 정기배송은 스케줄러가 회차를 찾아 주문을 만들고, 저장된 빌링키로 결제한다. 실패해도 고객은 그 순간 화면을 보고 있지 않다.

그래서 이 영역의 설계 질문은 대부분 "아무도 보고 있지 않을 때 어떻게 안전하게 실패하는가"다.

22~25강에서 이 영역을 깊게 봤다. 23강의 Phase 10 측정에서 배치 크기 500, 주기 15초로 1만 건을 정합성 손실 없이 처리했고, Kafka·Outbox 없이도 충분하다는 판정(NOT SELECTED)이 나왔다. 이 판정은 그대로 유지한다. 이 절에서 고칠 것은 처리 구조와 실패 정책이다.

갈림길 2: 동시 실행 방지

지금은 단일 인스턴스라 스케줄러가 하나만 돈다. 24강에서 "다중 인스턴스가 되면 PROCESSING 자동 대사가 이중 청구를 부를 수 있다"고 지적했다. 방법은 세 가지다.

방법 동작 장점 단점
작업 잠금(ShedLock 등) 스케줄 작업 하나를 한 인스턴스만 실행 단순, 기존 코드 그대로 한 인스턴스만 일함(확장 안 됨)
후보 선점(FOR UPDATE SKIP LOCKED) 각 인스턴스가 서로 다른 회차를 잠그고 가져감 여러 인스턴스가 나눠 처리 선택 쿼리 수정, MySQL 8 필요(이미 8.4)
상태 선점(조건부 UPDATE) UPDATE … SET status='CLAIMED' WHERE id=? AND status='READY' 성공한 쪽만 처리 DB만으로 보장 선점 후 죽으면 리스 필요(33-4와 같은 문제)

백지 설계라면 청구(④)는 상태 선점이다. 이미 READY→PROCESSING이 조건부 UPDATE로 되어 있으므로, 두 인스턴스가 같은 시도를 잡아도 한쪽만 성공한다. 주문 생성(②)은 UNIQUE(schedule_id)가 최종 방어선이고, 그 앞에서 SKIP LOCKED로 후보를 나누면 충돌 자체가 줄어든다.

문제는 PROCESSING 자동 대사다. 한 인스턴스가 청구 중(PROCESSING)인데 다른 인스턴스의 대사 작업이 그것을 "고립"으로 보고 조회하면, 아직 결제사 응답이 오기 전이라 조회 결과가 "없음"일 수 있다. 이것을 FAILED로 확정하면, 잠시 뒤 결제사가 승인한 돈은 주인을 잃는다. 이것이 33-4의 리스가 필요한 이유다. 대사 작업은 리스가 만료된 PROCESSING만 건드린다.

갈림길 3: 고칠 수 없는 회차의 격리

지금 코드는 주소 없음, 빌링 수단 없음, 재고 없음이면 회차를 HELD로 바꾼다. 확인hold(scheduleId, "MISSING_SHIPPING_ADDRESS") 등 이것은 좋은 격리다. 그런데 23강에서 지적한 것처럼 데이터 불변식 위반(예: 미래 회차가 둘 이상, 스냅숏 불일치)은 예외로 끝나서, 다음 실행에 같은 회차를 다시 집는다. 배치 크기 500 중 일부를 매번 같은 실패가 차지한다.

백지 설계라면 실패에 횟수를 세고, 같은 회차가 N번 연속 예외로 끝나면 HELD(사유: INVARIANT_VIOLATION)로 격리한다. 사람이 고친 뒤 다시 SCHEDULED로 돌린다. 그리고 HELD로 바뀔 때 고객 알림과 운영 지표를 함께 남긴다(R8).

// 저장소에 없는 예시
sealed interface CandidateOutcome {
  record Created(long orderId) implements CandidateOutcome {}
  record AlreadyOrdered() implements CandidateOutcome {}
  record Skipped(String reason) implements CandidateOutcome {}        // 구독 비활성 등
  record Held(HoldReason reason) implements CandidateOutcome {}       // 주소·빌링·재고·불변식
}

CandidateOutcome process(Candidate c, LocalDate today) {
  var context = loader.load(c);                       // 1·2: 조회와 사전 조건
  if (context.alreadyOrdered()) return new AlreadyOrdered();
  var readiness = readinessCheck.check(context);      // 3: 배송지·빌링
  if (readiness.blocked()) return holds.hold(c, readiness.reason());
  var plan = planResolver.resolve(context);           // 4: 스냅숏·플랜 변경
  var lines = pricing.lines(plan);                    // 5: 품목
  var order = orderFactory.create(context, plan, lines);   // 6: 주문 + InventoryService.reserveAll
  scheduleAdvancer.advance(context, plan);            // 7: 다음 회차·version
  return new Created(order.id());
}

각 단계가 따로 테스트 가능해지고, Held의 사유별로 지표를 남길 수 있다. 이 분해는 동작을 바꾸지 않으므로 특성 테스트(33-2)만 통과하면 된다.

5. 고객 경험 쪽 빈칸

R8(놓친 회차 알림)은 코드보다 정책 문제다. 23강에서 "놓친 회차는 따라잡지 않는다(no catch-up)"고 확인했다. 기술적으로 맞는 결정이지만, 고객 입장에서는 이번 달 사료가 오지 않는다. 그래서 다음을 함께 정한다.

  • 회차가 HELD가 되면 사유별 알림을 보낸다("배송지가 없어 이번 회차를 보류했습니다").
  • 정기결제가 영구 거절되면 결제 수단 재등록 안내를 보낸다(PAYMENT_ACTION_REQUIRED 알림은 이미 있다, 19강).
  • 재시도가 모두 실패하면 회차를 FAILED로 끝내고 알린다.

알림 문구와 시점은 제품 결정이므로 하네스 기준으로 사용자 승인이 필요하다(32강).

정리

  • 정기배송의 안전 구조(주문·청구 분리, 회차당 주문 하나, 회차별 독립 TX, UNKNOWN 재청구 금지)는 이미 맞다. 지킨다.
  • 고칠 것은 실패 정책이다. 재시도 간격, 영구 거절 구분, 불변식 위반 격리, 고객 알림.
  • 다중 인스턴스로 가기 전에 반드시 끝낼 것은 리스 기반 대사(33-4)와 후보 선점이다.
  • 빌링키 암호화는 expand → migrate → contract의 교과서적 사례다. 되돌릴 수 없는 단계(C1, C2)는 관찰과 복원 연습 뒤에만 간다.

2. AI 기능: 호출 경계를 공통 구조로

지금의 모습

15강에서 리뷰 요약·비교·추천 AI가 몇 가지 좋은 결정을 하고 있음을 봤다. 확인 기록

  • AI 호출을 DB 트랜잭션 밖에서 한다.
  • 입력의 지문(길이 접두사 + SHA-256)으로 결과를 캐시한다.
  • AI 출력을 검증한다(허용된 후보만, 금지어 검사).
  • AI는 구매 가능 상품을 결정하지 않고, 검증된 후보만 재정렬한다(PWC-0010).

그리고 결함도 봤다.

  • AI 클라이언트에 타임아웃이 없다. AI 서버가 응답하지 않으면 요청 스레드가 무한정 묶인다. 30강의 OOM 원인 중 하나가 "스레드 217개"였다는 것을 기억하면, 이것은 가용성 위험이다.
  • 익명 GET 요청이 유료 AI 호출과 DB 쓰기를 일으킨다. 캐시 미스가 동시에 몰리면 같은 입력에 대해 AI를 여러 번 부른다(스탬피드).
  • UNSAFE_TERMS의 "약"이 "약간", "예약" 같은 정상 문장까지 거부한다.

목표: AI 게이트웨이

새 AI 기능을 추가할 계획이라면, 기능마다 이 결정을 반복하게 두면 안 된다. 33-3의 "외부 포트" 원칙을 AI에 적용해 하나의 게이트웨이를 둔다.

게이트웨이 책임 내용 지금
타임아웃 연결·응답 타임아웃(예: 3초·20초), 초과 시 대체 응답 없음
중복 억제 같은 지문의 요청이 처리 중이면 결과를 기다림(single-flight) 없음(스탬피드)

익명 요청 정책이 이 중 가장 중요한 결정이다. 공개 상품 페이지의 "AI 리뷰 요약"은 익명 사용자도 봐야 한다. 그런데 익명 요청이 생성을 일으키면, 봇 하나가 AI 비용을 마음대로 쓸 수 있다. 그래서 생성은 리뷰가 바뀔 때 배치로 미리 하고, 익명 요청은 저장된 결과만 읽게 한다. 결과가 없으면 "요약 준비 중"을 보여 준다. 이것은 AI 응답을 요청 경로에서 빼는 결정이기도 해서, 타임아웃 문제도 함께 줄어든다. 해석

금지어 검사는 부분 문자열 비교 대신 단어 경계를 본다. 한국어는 조사가 붙어 단어 경계가 모호하므로, 금지 표현을 "약" 같은 한 글자가 아니라 "의약품", "처방" 같은 구체적인 표현으로 바꾸고, 판정 결과를 지표로 남겨 오탐을 추적한다. 이것은 AI 기능의 품질 문제라서 목록 자체는 제품 결정이다.

확장할 때의 규칙

리팩터링 뒤 AI 활용을 늘릴 때 지킬 규칙을 미리 정한다. 15강의 PWC-0010 원칙을 일반화한 것이다.

  1. AI는 결정하지 않고 제안한다. 가격, 재고, 결제, 구매 가능 여부는 AI가 정하지 않는다. AI의 출력은 검증된 후보 안에서 순서나 설명을 바꾸는 데만 쓴다.
  2. AI 호출은 요청 경로 밖에서 하는 것을 기본으로 한다. 꼭 요청 경로에 둬야 하면 게이트웨이의 타임아웃과 대체 응답을 반드시 쓴다.
  3. AI 출력은 저장하고 출처를 남긴다. 어떤 모델, 어떤 입력 지문으로 만든 결과인지 기록해야 문제가 생겼을 때 다시 만들 수 있다.
  4. 새 AI 기능은 평가 세트와 함께 들어온다. 15강의 금지어 오탐처럼, AI 기능의 실패는 예외가 아니라 "그럴듯한 오답"으로 나타난다. 대표 입력 수십 개와 기대 성질(금지 표현 없음, 후보 밖 상품 없음 등)을 테스트로 둔다.

  • 카탈로그는 캐시 복원 결정이 핵심이다. 측정으로 내린 KEEP 판정을 측정 없이 뒤집지 않는다.
  • AI는 게이트웨이 하나로 타임아웃·중복 억제·예산·익명 정책·검증을 모은다. 확장의 규칙 네 가지를 미리 정한다.
  • 세션 저장소는 다중 인스턴스의 전제다. CD가 켜진 지금은 배포마다 로그아웃되는 문제로 우선순위가 오른다.
  • 나머지는 공통 기반을 적용하면 정리되는 국소 수정이다.

33-8. 실행 로드맵

들어가기 전

33-1~33-7에서 "무엇을 어떤 모습으로 바꿀지"를 정했다. 이 절은 "어떤 순서로, 한 번에 얼마만큼, 어떻게 되돌릴 수 있게" 바꿀지를 정한다.

점진적 리팩터링의 성패는 설계보다 순서와 단위에서 갈린다. 아무리 좋은 목표 설계도, 한 PR에 너무 많이 담으면 리뷰가 불가능해지고 되돌리기도 어려워진다. 반대로 너무 잘게 나누면 중간 상태가 오래 남아 두 구조가 공존하는 기간이 길어진다.

이 저장소에는 순서를 정할 때 반드시 고려해야 할 운영 제약이 하나 있다. 31강에서 확인한 대로 CD 타이머가 켜져 있다. main에 병합된 앱 변경은 자동으로 운영에 배포될 수 있다. 그리고 29강에서 본 정책상 migration·SQL·운영 설정·Compose·nginx 변경은 자동 배포에서 제외되어 감독형 배포가 필요하다. 그래서 PR마다 "자동 배포되는가, 감독형인가"가 순서 설계의 입력이 된다.

1. 전체 단계

단계 작업 ID 예 포함 끝 조건 배포 방식
0. 안전망 REFACTOR-SAFETY-001~ 특성 테스트, 보호 계약 목록, 성능 기준선, 관측 보강, 복원 연습 33-2 정리 표의 다섯 항목 완료 테스트·관측은 자동, 복원 연습은 운영 실행
1. 공통 기반 REFACTOR-BASE-001~ 상태 enum, 도메인 예외, 시간 타입, 멱등 공용 구조, 모듈 규칙(동결), DI 정리 새 코드에서 매직 문자열·HTTP 숫자·모듈 위반이 빌드 실패 자동(DB 변경 없음)
2. 결제 REFACTOR-PAY-001~ 응답 해석, 성공 처리 통합, 리스·복구, 멤버십 분리, 환불 상태 성공 처리 진입점 1개, 고립 PROCESSING 자동 복구 리스·환불은 감독형(migration)

4. 정기 REFACTOR-SUB-001~ 분해, 불변식 격리, 재시도 정책, 빌링키 암호화, 정리 트리거 재시도 간격 정책 존재, 빌링키 평문 0 컬럼 추가·데이터 이행은 감독형
5. 나머지 REFACTOR-CAT/AI/FE/OPS-… 캐시 결정, AI 게이트웨이, 국소 결함, 프론트, 운영 백로그 D 비움 대부분 자동

병렬로 할 수 있는 것

단계는 순서대로지만 모든 작업이 직렬은 아니다.

  • 단계 0의 복원 연습은 운영 실행이라 승인과 일정이 필요하다. 그동안 단계 1을 진행할 수 있다. 단계 1은 DB를 바꾸지 않기 때문이다(33-3).
  • 단계 5의 국소 결함과 운영 항목은 대부분 다른 단계와 겹치지 않는다. 단계 0이 끝난 뒤라면 언제든 끼워 넣을 수 있다.
  • 단계 2와 3은 재고 잠금 순서에서 맞물린다. 결제 성공 처리 통합(단계 2의 두 번째 작업)이 끝나야 재고 순서 고정(단계 3)이 한 곳만 고치면 된다. 그래서 2 → 3 순서를 지킨다.

2. 한 PR의 크기

하네스의 원칙은 "하나의 사용자 목적을 같은 승인·검증·롤백 경계로 묶는다"다(32강). 리팩터링에 적용하면 다음과 같다.

원칙 적용
한 PR은 하나의 동작 변화 또는 동작 불변 구조 변경 중 하나만 성공 처리 통합(불변)과 4xx 해석 변경(변화)을 같은 PR에 넣지 않는다
동작 불변 PR은 특성 테스트가 한 줄도 바뀌지 않아야 한다 바뀌었다면 그 PR은 동작 변화 PR이다
동작 변화 PR은 바뀐 특성 테스트를 PR 본문에 나열한다 리뷰어가 의도된 변화만 있는지 확인
migration은 앱 코드와 다른 PR 감독형 배포 단위를 작게 유지
한 PR은 하루 안에 리뷰할 수 있는 크기 넘으면 단계를 더 나눈다

"특성 테스트가 한 줄도 바뀌지 않아야 한다"는 규칙이 이 로드맵의 가장 강력한 장치다. 구조 변경 PR의 리뷰어는 코드의 모든 줄을 이해할 필요가 없다. 특성 테스트가 그대로인지만 보면 된다. 32강에서 본 리뷰 면제 문제(고위험 PR에 리뷰가 몰리지 못함)를 줄이는 효과도 있다. 해석

3. DB 변경: expand → migrate → contract

왜 필요한가

이 저장소의 복구 원칙은 "코드는 되돌리고 DB는 되돌리지 않는다"다(29강 릴리스 엔진, 30강 AWS 시절부터). 그러면 모든 DB 변경은 다음 조건을 만족해야 한다.

새 스키마에서 이전 버전 코드가 정상 동작해야 한다.

이 조건을 만족하는 방법이 expand → migrate → contract(병렬 변경, parallel change)다. 원리 스키마를 한 번에 바꾸지 않고, 새 구조를 추가해 옛 구조와 나란히 두었다가(expand), 데이터와 코드를 옮기고(migrate), 모두 옮겨 간 뒤 옛 구조를 제거한다(contract).

참고(검색 요약) youngju.dev — Expand-Contract 무중단 스키마 변경이 컬럼 이름 변경을 "추가 → 백필 → 전환 → 삭제" 네 단계로 나누고 단계별 롤백 안전성을 설명한다. 같은 블로그의 무중단 스키마 변경 완전 가이드는 DDL이 잡는 잠금 등급을 다룬다. 이 기법은 Martin Fowler가 진화적 데이터베이스 설계에서 정리했다.

이번 리팩터링의 DB 변경 목록

변경 단계 expand migrate contract
payments.processing_until 2 컬럼 추가(NULL) 쓰기 시작, NULL은 계산 없음(유지)
주문 REFUNDED 상태 2 CHECK에 값 추가 환불 시 상태 변경, 과거 데이터 보정(선택) 없음
정기 회차 실패 횟수 4 컬럼 추가(기본 0) 쓰기 시작 없음
정기결제 next_attempt_at 4 컬럼 추가(NULL) 쓰기 시작, NULL은 즉시 없음
빌링키 암호화 4 암호문·키 버전 컬럼 추가 이중 쓰기 → 백필 → 읽기 전환 평문 쓰기 중단 → 평문 삭제
쿠폰 1인 1장 5 중복 데이터 조회·정리 — UNIQUE 추가(정책 확인 후)

대부분이 expand만으로 끝난다. contract가 필요한 것은 빌링키 암호화와 제약 추가뿐이다. 제약 추가는 "기존 데이터가 제약을 만족해야 추가된다"는 점에서 contract에 가깝다. 이전 코드가 제약을 위반하는 데이터를 쓸 수 있다면 롤백 후 쓰기가 실패하기 때문이다. 그래서 제약 추가 전에 이전 버전 코드가 그 제약을 위반할 경로가 없는지 특성 테스트로 확인한다.

MySQL DDL에서 조심할 것

25강에서 본 것처럼 MySQL의 DDL은 암묵적 커밋을 일으킨다. 그래서 이 저장소는 migration을 V4~V8처럼 여러 파일로 나눴다. 같은 원칙을 따른다.

  • DDL과 데이터 변경(DML)을 같은 migration 파일에 섞지 않는다.
  • 큰 테이블의 ALTER TABLE은 MySQL 8의 ALGORITHM=INSTANT(컬럼 끝에 NULL 허용 컬럼 추가 등)가 되는지 먼저 확인한다. 안 되면 테이블 복사가 일어나 잠금이 길어진다.
  • 백필은 migration이 아니라 배치 작업으로 한다. 25강의 정리 배치처럼 ORDER BY … LIMIT 단위로 나눠서, 잠금을 짧게 잡는다.

동작을 바꾸는 PR 중 위험한 것은 켜기 전에 관찰하는 단계를 둔다.

6. 각 단계의 되돌리기

단계 되돌리는 방법 되돌릴 수 없는 지점
0 테스트·관측 추가는 되돌릴 필요 없음 없음
1 revert PR(코드만, DB 변경 없음) 없음
2 응답 해석·통합: revert. 리스: 컬럼은 남기고 코드만 revert. 복구 작업: 스위치를 shadow로 환불 상태의 과거 데이터 보정(별도 PR, 복원 연습 후)
3 revert(DB 변경 없음) 없음
4 재시도·격리: 스위치. 빌링키: M2까지는 읽기만 되돌리면 됨 C1(평문 쓰기 중단), C2(평문 삭제)
5 대부분 revert 제약 추가(위반 데이터가 생기면 쓰기 실패)

되돌릴 수 없는 지점은 전체 로드맵에서 세 곳뿐이다. 빌링키 C1·C2, 그리고 제약 추가다. 이 세 곳은 다음 조건을 모두 만족할 때만 진행한다.

  1. 복원 연습(33-2)이 끝나 RTO가 기록되어 있다.
  2. 직전 단계를 운영에서 충분히 관찰했다(빌링키는 M2의 불일치 지표 0).
  3. 별도 운영 실행 승인을 받았다(하네스 기준 Operations Execution).

7. 리팩터링이 끝난 뒤

이 로드맵이 끝나면 다음 상태가 된다.

  • 결제·재고·정기의 핵심 규칙이 각각 한 곳에 있다.
  • 상태와 오류가 타입으로 표현되고, 새 코드의 일탈은 빌드가 막는다.
  • 모듈 경계와 외부 포트가 있어서, 새 기능은 정해진 자리(33-7의 확장 지점 표)로 들어온다.
  • 운영은 OOM 조건, 헬스체크, 알림, CD 정책 같은 빈칸이 메워져 있다.
  • 무엇보다 특성 테스트와 보호 계약 목록이 남는다. 이것은 리팩터링이 끝나도 계속 쓰인다. 새 기능을 추가할 때 기존 동작이 바뀌지 않았음을 확인하는 수단이기 때문이다.

마지막 항목이 이 로드맵의 진짜 산출물이다. 코드 구조는 언젠가 다시 바뀐다. 그러나 "바뀌어도 안전한지 확인하는 장치"는 다음 변화에도 그대로 쓰인다.
