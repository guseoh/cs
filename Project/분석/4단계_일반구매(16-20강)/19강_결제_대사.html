19강. 결제 대사: "모른다"를 "안다"로 바꾸는 절차

18강은 결제사 응답을 받지 못하면 결제를 UNKNOWN으로 남기고 끝났다. 이번 강의는 그 다음 이야기다. 우리 장부(DB)와 결제사 장부가 다를 때, 어느 쪽을 믿고 어떻게 맞추는가. 이 작업을 대사(對査, reconciliation)라고 부른다.

0. 대사란 무엇이고, PawCycle은 어느 것을 하는가

대사는 금융·결제 도메인의 용어로, "내 장부와 상대방 장부가 같은지 맞춰 보는 작업"이다. 보통 두 종류로 나눈다. 원리

실시간·단기 대사 정기·정산 대사
시점 결제 직후 ~ 수 분 다음 날(D+1) 등 주기적
방식 결제사 조회 API로 한 건씩 상태 확인 결제사가 주는 거래 내역 파일 전체와 비교
목적 미확정(PENDING·UNKNOWN) 건을 빨리 확정 전체 거래액과 정산금 검증

PawCycle이 구현한 것은 첫 번째뿐이다. 그것도 일반 결제는 관리자가 버튼을 눌러야 실행된다. 정산 파일 대사와 결제사 웹훅 수신은 코드에 없다. [확인: webhook 검색 결과 0건, 대사 호출자는 AdminPaymentController와 정기결제 처리기 두 곳]

같이 읽을 자료:

  • 4offoff, 거래대사(Transaction Reconciliation) (2026-04-07) — 열어서 본문을 읽었다. 위 표의 두 유형 구분이 이 글의 정리다. 그 밖에 타임아웃, 데이터 유실, "우리는 PENDING인데 결제사는 SUCCESS" 같은 상태 불일치가 왜 생기는지 설명한다. "PENDING·PROCESSING 건을 1분마다 조회 API로 확인하는 스케줄러"라는 실무 시나리오도 있다. PawCycle에 없는 부분(스케줄러)을 이 글이 보여 준다. 대표 그림은 제목 표지라 싣지 않았다.

1. 누가 어떤 상태를 맡는가 — 대사 지도

18강까지 나온 결제 상태와, 각 상태를 정리하는 주체를 한 장에 모아 보자.

대사의 입구 조건이 이 지도를 그대로 강제한다(PaymentReconciliationService.java).

boolean billingProcessing = "BILLING".equals(row.type()) && "PROCESSING".equals(row.status());
if (!billingProcessing && !"UNKNOWN".equals(row.status()))
  throw new CommerceException(409, "PAYMENT_RECONCILIATION_NOT_ALLOWED", "UNKNOWN 결제 또는 처리 중 Billing만 대사할 수 있습니다.");

일반 결제의 PROCESSING은 대사로 확정할 수 없다. 18강 5절에서 본 것처럼, 고립된 PROCESSING은 "승인 요청 전에 죽었는지 후에 죽었는지" 구분이 안 된다. 게다가 지금 이 순간 승인 요청이 진행 중일 수도 있다. 18강의 TX1과 TX2 사이에 있는 정상 요청을 대사가 가로채 FAILED로 만들면, 몇 초 뒤 결제사 승인이 성공해도 TX2는 "이미 PROCESSING이 아니다"를 보고 손을 뗀다. 돈은 빠졌는데 주문은 실패가 된다. 그래서 진행 중인 워커가 없다는 펜스(fence) 없이는 열지 않는다. 기록·해석 반면 UNKNOWN은 18강의 TX2가 "결과를 모른다"고 확정해서 기록한 상태다. 진행 중인 승인 요청이 없음이 보장되므로 대사가 안전하게 손댈 수 있다.

2. 세 단계 — 시도 횟수를 먼저 커밋한다

대사도 15·18강과 같은 3단 구조다. 다른 점은 첫 트랜잭션이 "시도 예산"을 차감한다는 것이다.

@Transactional(propagation = Propagation.NOT_SUPPORTED)          // ⓪ 호출자의 트랜잭션이 있어도 일시 중단
public PaymentReconciliationResult reconcile(long id, Long adminId) {
  ReconciliationWork work = transaction.execute(status -> {         // ① 시작 트랜잭션
    ReconciliationWork row = payments.findForStart(id);              //    SELECT ... FROM payments WHERE id=? FOR UPDATE
    ... 상태 게이트, 결제사 구성 확인 ...
    if (row.attempts() >= 10) throw new CommerceException(409, "PAYMENT_RECONCILIATION_EXHAUSTED", ...);
    payments.incrementAttempts(id, row.attempts() + 1);              //    시도 횟수 +1, last_reconciled_at 기록 → 커밋
    return row;
  });
  ProviderResult observed;
  try { observed = ... queryOnly(id) ... ; }                         // ② 트랜잭션 밖 조회
  catch (RuntimeException e) { observed = new ProviderResult("UNKNOWN", "NO_RESPONSE"); }
  boolean billingFailure = transaction.execute(status -> complete(id, adminId, observed));  // ③ 완료 트랜잭션
  ...
}
  • ⓪ Propagation.NOT_SUPPORTED: 정기결제 처리기처럼 이미 트랜잭션 안에서 이 메서드를 부르는 경우가 있다. 그대로 두면 결제사 조회가 호출자의 트랜잭션 안에서 실행되어 커넥션과 잠금을 붙잡는다. NOT_SUPPORTED는 호출자의 트랜잭션을 잠시 멈추고 트랜잭션 없이 실행한다. 그래서 안쪽 TransactionTemplate이 독립된 짧은 트랜잭션 두 개를 만든다. 5강의 전파 속성 중 거의 쓰지 않는 옵션이 실제로 쓰인 사례다. 확인·원리

  • ① 시도 횟수를 조회 전에 커밋하는 이유 해석:

    • 예산을 보장한다. 조회 중에 서버가 죽어도 횟수는 이미 소모되었다. 그래서 "최대 10회"가 재시작 후에도 지켜진다. 조회 후에 올리면, 죽을 때마다 횟수가 안 올라 무한 재시도가 가능하다.
    • 결제사를 과하게 두드리지 않는다. 장애 중인 결제사에 조회가 몰리면 상대의 상황이 더 나빠진다.
    • 관측성. last_reconciled_at이 "언제 마지막으로 확인했나"를 남긴다.

    billing 처리 쪽 결정 기록도 "대사 attempt commit 후 query"를 지켜야 할 순서로 명시한다. 기록 - ② 조회는 실패해도 예외로 끝나지 않는다. 어떤 예외든 UNKNOWN, NO_RESPONSE로 바꿔 ③에 넘긴다. 그래야 시도 횟수와 10회 소진 처리가 일관되게 돈다.

3. 조회는 "신원 확인"부터 — GET이라서 반복해도 안전하다

일반 결제의 조회(TossTestPaymentAdapter.queryPayment)는 GET /v1/payments/orders/{orderId}다.

if (!body.path("orderId").isTextual() || !body.path("paymentKey").isTextual()
    || !body.path("totalAmount").isNumber() || !body.path("status").isTextual()
    || !providerOrderId.equals(body.path("orderId").asText())             // 주문번호 일치
    || !paymentKey.equals(body.path("paymentKey").asText())               // 결제 키 일치
    || amount.compareTo(body.path("totalAmount").decimalValue()) != 0)    // 금액 일치
  return new ConfirmResult("UNKNOWN", "IDENTITY_MISMATCH");
return new ConfirmResult(switch (providerStatus) {
  case "DONE" -> "SUCCEEDED";
  case "ABORTED", "EXPIRED" -> "FAILED";
  default -> "UNKNOWN";                                                   // IN_PROGRESS, CANCELED 등
}, providerStatus);
  • 신원 3종 일치: 결제사 응답의 주문번호, 결제 키, 총액이 우리 기록과 모두 같을 때만 상태를 믿는다. 하나라도 다르면, 상태가 DONE이어도 UNKNOWN이다. 다른 결제의 DONE을 보고 이 결제를 성공 처리하는 사고를 막는다. 금액 비교에는 USE_BIG_DECIMAL_FOR_FLOATS로 JSON 숫자를 BigDecimal로 읽는다(17강의 부동소수점 이야기). 확인
  • CANCELED가 실패가 아니다. 18강의 승인 경로는 CANCELED를 FAILED로 본다. 조회 경로는 이를 UNKNOWN으로 남긴다. 조회 시점의 CANCELED는 "승인됐다가 취소됨"일 수 있어서, 단순 실패로 보고 재고를 풀면 환불·취소 흐름(20강)과 엇갈린다. 그래서 사람의 판단에 넘기는 보수적 선택으로 보인다. 해석
  • 비-2xx, 타임아웃, 신원 누락은 모두 UNKNOWN이다. "404는 결제가 없다는 뜻이니 실패"라고 단정하지 않는다. 결제사 쪽 반영 지연이나 잘못된 키일 수도 있기 때문이다. 기록

왜 조회는 몇 번이고 반복해도 되는가 원리. HTTP 메서드의 의미론을 보자.

  • 안전(safe): 서버 상태를 바꾸지 않는다. GET이 해당한다.
  • 멱등(idempotent): 여러 번 보내도 결과 상태가 한 번 보낸 것과 같다. GET, PUT, DELETE가 해당한다.
  • 승인 POST /confirm은 안전하지도 멱등하지도 않다. 그래서 18강은 승인을 절대 자동 재시도하지 않는다.
  • 조회 GET은 안전하다. 그래서 대사는 "모르면 다시 물어보면 된다"는 전략을 쓸 수 있다.

쓰기는 위험하니 한 번만 하고, 읽기를 반복해서 진실을 찾는다. 이것이 대사 설계의 핵심 원리다.

4. 완료 트랜잭션 — 다시 잠그고, 다시 확인하고, 반영한다

private boolean complete(long paymentId, Long adminId, ProviderResult observed) {
  ReconciliationTarget payment = payments.findForCompletion(paymentId);
  //   SELECT payment.*, orders.member_id, orders.source FROM payments JOIN orders ... WHERE payment.id=? FOR UPDATE
  if (!billingProcessing && !"UNKNOWN".equals(payment.status())) return false;    // 그사이 다른 대사가 확정했으면 손 떼기
  if ("SUCCEEDED".equals(observed.status())) {
    for (OrderItem item : payments.findOrderItems(payment.orderId()))             // sku_id 오름차순
      inventory.deduct(item.skuId(), item.quantity(), paymentId);
    payments.markSucceeded(...); payments.markOrderPaid(...);
    deliveries.createPreparing(...); payments.useReservedCoupon(...);
    if ("ONE_TIME".equals(payment.source())) payments.consumeCart(memberId, orderId);  // 일반 주문만 장바구니 소비
    membershipEvaluation.evaluate(memberId); notifications.create(memberId, "ORDER_PAID", ...);
  } else if ("FAILED".equals(observed.status())) {
    if ("BILLING".equals(payment.type())) { ...; return true; }                    // 정기결제 실패는 재시도 경로로
    for (...) inventory.release(...);                                              // 일반 결제 실패: 예약 해제
    payments.markFailed(paymentId, observed.providerStatus()); payments.markOrderPaymentFailed(...);
    payments.releaseReservedCoupon(...);
  } else if (payment.attempts() >= 10) {                                           // 여전히 모름 + 예산 소진
    payments.markOrderActionRequired(payment.orderId());                           //   주문 PAYMENT_ACTION_REQUIRED
    notifications.create(memberId, "PAYMENT_ACTION_REQUIRED", "PAYMENT", paymentId);  //   고객에게 "결제 확인 필요"
  }
  if (adminId != null) audits.append(adminId, "PAYMENT_RECONCILE", "PAYMENT", paymentId);  // 관리자 감사 로그, 같은 커밋
  return false;
}
  • 결과별 반영은 18강 TX2와 같은 효과를 같은 묶음으로 커밋한다. 성공 경로가 두 군데(승인 TX2, 대사 완료)에 있으므로, 효과 목록이 어긋나지 않게 유지하는 것이 이 코드의 숨은 비용이다. 실제로 둘은 조금 다르다. 확인
    • 대사는 주문 항목을 sku_id 오름차순으로 읽어 재고를 잠근다(items(orderId, ..., true) → orderBy(item.skuId.asc())). 승인 경로는 정렬하지 않는다(findAllByOrderId). 대사가 잠금 순서를 명시적으로 고정한 쪽이다.
    • 장바구니가 없을 때 승인 경로는 ensureExists로 만들고, 대사는 건너뛴다. 결정 기록은 "없는 장바구니 생성·cart version 정책을 승인 없이 바꾸는 것"을 제외 대상으로 적었다. 리팩터링하면서 기존 동작을 그대로 보존한 결과로 보인다. 기록·해석

  • 10회를 다 써도 모르면:

    • 주문을 PAYMENT_ACTION_REQUIRED로 바꾼다. 프론트엔드에서는 "결제 확인 필요"로 보인다.
    • 고객에게 알림을 보낸다.
    • 재고 예약은 여전히 유지한다. 돈이 빠졌을 가능성이 남아 있기 때문이다.

    자동화가 포기한 지점을 사람에게 명시적으로 넘기는 상태다. 확인 - 감사 로그를 같은 트랜잭션에: 관리자가 실행했다면 "누가 언제 어떤 결제를 대사했다"가 결제 상태 변경과 함께 커밋된다. 14강의 관리자 상품 수정과 같은 원칙이다. 확인

4-1. 장바구니 version — "정확히 한 번"을 지키는 코드

public void consumeCart(long memberId, long orderId) {
  Long cartId = locks.first("SELECT id FROM carts WHERE member_id=? FOR UPDATE", Long.class, memberId);
  if (cartId == null) return;
  boolean changed = false;
  for (OrderItem item : findOrderItems(orderId)) {
    Integer current = locks.first("SELECT quantity FROM cart_items WHERE cart_id=? AND sku_id=? FOR UPDATE", ...);
    if (current == null) continue;
    changed |= (current <= item.quantity() ? delete(...) : update(current - item.quantity())) > 0;   // 실제 영향 행 수로 판단
  }
  var update = queries.update(cart).set(cart.updatedAt, now);
  if (changed) update.set(cart.version, cart.version.add(1));                                         // 배치 전체에 +1 한 번
  writes.mutate(() -> update.where(cart.id.eq(cartId)).execute());
}

16강에서 예고한 #414·PR #415(2026-10-20 병합)의 수정이 바로 이 메서드다. 원래는 대사가 장바구니 수량을 차감·삭제하면서도 version을 올리지 않았다. 그러면 17강의 체크아웃이 "장바구니가 안 바뀌었다"고 잘못 판단하고, 재생 지문 비교가 실제 상태와 어긋난다. 기록

  • 실제로 바뀐 행이 있을 때만(> 0), 그것도 배치 전체에 한 번 +1 한다.
  • 실제 MySQL 8.4.11과 가짜 결제사로 다음을 검증했다.
    • 수량 5→3에서 version 7→8
    • 여러 항목이 바뀌어도 +1 한 번
    • 변경이 없으면 그대로
    • 동시·중복 대사
  • updated_at은 변경이 없어도 갱신한다. 이 "touch"는 별도 계약으로 보존했다. 기록·확인

4-2. mutate() — 벌크 쓰기 전후의 flush와 clear

public int mutate(LongSupplier update) {
  entities.flush();                                  // ① 대기 중인 엔티티 변경을 먼저 DB로
  int count = Math.toIntExact(update.getAsLong());   // ② QueryDSL 벌크 UPDATE/DELETE
  entities.clear();                                  // ③ 1차 캐시 비우기
  return count;
}

벌크 쿼리는 영속성 컨텍스트를 거치지 않고 DB에 직접 쓴다. 그래서 ① 앞서 엔티티로 바꾼 값이 아직 DB에 없으면 벌크 쿼리가 옛 값을 기준으로 실행된다. ③ 벌크로 바꾼 행이 1차 캐시에 옛 값으로 남아 있으면 같은 트랜잭션의 다음 조회가 옛 값을 본다. 17강의 @Modifying(flushAutomatically, clearAutomatically)와 같은 문제를 직접 처리한 것이다. 원리 시각은 jdbcTime()으로 예전 저장 방식(벽시계 값)과 맞춘다. 16강의 "UTC 결정은 필드별로 좁게 적용"이 여기서도 이어진다. 확인

5. 빠진 것과 트레이드오프

이 대사는 "틀리지 않는 것"을 "빨리 맞추는 것"보다 우선한다. 대가는 다음과 같다. 해석

  • 일반 UNKNOWN은 사람이 눌러야 풀린다. 결제사 장애로 UNKNOWN이 100건 쌓이면 관리자가 100번 눌러야 한다. 그동안 그 주문들의 재고는 예약된 채 팔리지 않는다.
  • 웹훅이 없다. 결제사가 "이 결제 DONE 됐어"라고 먼저 알려 주는 경로가 없다. 웹훅을 붙이더라도 웹훅 본문을 진실로 믿지 않고 "조회를 해 보라는 신호"로만 쓰는 것이 안전하다. 위조나 순서 뒤바뀜이 가능하기 때문이다. 이 프로젝트의 "조회 + 신원 3종 확인" 구조는 그 처리기를 그대로 받아 줄 수 있다.
  • D+1 정산 대사가 없다. 조회 대사는 우리가 아는 결제만 확인한다. "결제사에는 있는데 우리 DB에는 없는" 거래(예: TX1 전에 실패한 요청이 결제사에서는 처리된 경우)는 거래 내역 파일과 전수 비교해야만 찾는다.

운영 환경은 아직 결제를 받지 않으므로(18강 6절) 지금 당장의 위험은 아니다. 실제 오픈 전에 메워야 할 목록으로 정리해 둘 만하다. 가장 작은 다음 단계는 UNKNOWN 자동 대사 스케줄러다. 지금의 reconcile()이 이미 예산, 잠금, 재확인, 감사를 갖추고 있으므로 호출자만 추가하면 된다.

// 저장소에 없는 예시 — 일반 UNKNOWN을 지수 백오프로 자동 대사
@Scheduled(fixedDelayString = "${pawcycle.commerce.payment-reconcile.fixed-delay-ms:60000}")
public void reconcileUnknownPayments() {
  for (Long id : payments.findUnknownDue(now(), 50)) {   // last_reconciled_at + 2^attempts 분이 지난 UNKNOWN만
    try { reconciliation.reconcile(id); }                // adminId 없이: 감사 로그 대신 메트릭
    catch (CommerceException e) { metrics.reconcileSkipped(e.code()); }   // EXHAUSTED 등은 건너뛰기
  }
}

17강의 만료 스케줄러와 마찬가지로, 서버가 여러 대면 같은 결제를 동시에 집을 수 있다. 하지만 시작 트랜잭션의 FOR UPDATE와 상태 게이트 덕분에 시도 횟수만 두 번 오르고 결과는 하나로 수렴한다.

6. 면접에서 이렇게 말한다

  • "결제사 응답을 받지 못한 결제는 UNKNOWN으로 두고, 대사에서 조회 API로 반복 확인합니다. 승인 POST는 멱등하지 않아 재시도하지 않지만, 조회 GET은 안전하므로 몇 번이고 물어볼 수 있습니다."
  • "대사는 시도 횟수를 조회 전에 커밋해 최대 10회 예산을 보장합니다. 조회는 트랜잭션 밖에서 하고, 완료 트랜잭션에서 결제를 다시 잠그고 아직 UNKNOWN인지 재확인한 뒤 반영합니다."
  • "결제사 응답의 주문번호·결제 키·금액이 모두 일치할 때만 상태를 믿고, 하나라도 다르면 DONE이어도 UNKNOWN으로 둡니다. 10회를 써도 모르면 주문을 '결제 확인 필요'로 바꾸고 고객에게 알리며, 재고 예약은 유지합니다."
  • "일반 PROCESSING은 진행 중인 승인과 구분할 수 없어 대사 대상에서 뺐습니다."
  • 한계로 말할 것: 일반 결제의 자동 대사·웹훅·D+1 정산 대사는 아직 없습니다. 다음 단계로 백오프 스케줄러를 제안합니다.
