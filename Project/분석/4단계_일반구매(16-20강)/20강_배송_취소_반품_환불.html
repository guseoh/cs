20강. 배송·취소·반품·환불: 결제 이후의 "되돌리기"를 설계하기

결제가 성공하면 끝이 아니다. 상품은 배송되어야 하고, 고객은 마음을 바꾸고(취소), 받은 물건을 돌려보내며(반품), 그때마다 돈을 돌려줘야 한다(환불). 이 강의는 결제 이후의 네 가지 흐름을 다룬다.

이 영역에서 PawCycle이 내린 가장 큰 구조적 결정은 이것이다. 주문(orders)의 상태는 결제 이후 PAID에서 더 바뀌지 않는다. 대신 배송, 취소, 반품, 환불이 각자 자기 테이블과 상태 기계를 가진다. 각 테이블에는 주문당 하나라는 UNIQUE(order_id)가 붙는다(환불은 시도마다 한 행). 확인 주문 하나에 상태 값 하나를 두고 PAID → SHIPPED → CANCELLED → REFUNDED…처럼 계속 덮어쓰는 방식과 비교해 보자.

  • 덮어쓰는 방식은 "배송 중에 반품 요청 + 환불 실패" 같은 동시에 성립하는 사실을 표현하지 못한다.
  • 단계별 시각과 담당자를 담을 곳도 없다.

먼저 전체 지도를 보자.

두 가지가 그림의 핵심이다. 취소는 배송 준비 중(PREPARING)일 때만 할 수 있고, 반품은 배송 완료 후 7일 이내에만 할 수 있다. 출고된 뒤에는 취소가 막히고, 고객은 받은 다음 반품해야 한다. 어느 쪽이든 결국 환불 행 하나를 만들고, 실제 돈을 돌려주는 실행은 따로 일어난다.

1. 배송 — 상태와 시각의 조합을 DB가 강제한다

배송 생성은 18강 승인 TX2와 19강 대사 완료 안에서 deliveryService.createPreparing(orderId)로 일어난다. 주석은 "중복 콜백이 와도 배송은 하나만 남는다"이고, 이것을 UNIQUE(order_id)가 받쳐 준다. 확인

상태 전이는 DeliveryService(DeliveryService.java)가 전부 맡는다. 모두 관리자 API에서 호출된다.

전이 허용 시작 상태 부수 효과
ship PREPARING, FAILED 택배사·송장 기록, ORDER_SHIPPED 알림
complete SHIPPED DELIVERED, ORDER_DELIVERED 알림
fail SHIPPED FAILED, 사유 기록
(취소) PREPARING CANCELLED (2절)

모든 전이는 같은 틀을 따른다. 행을 FOR UPDATE로 잠그고, 시작 상태가 맞지 않으면 409 DELIVERY_STATE_CONFLICT를 낸다. 그다음 전이, 알림, 메트릭, 관리자 감사 로그를 한 트랜잭션에서 처리한다. 14강의 관리자 상품 수정과 같은 원칙이다. 확인

더 흥미로운 것은 DB 쪽 방어다(V16).

CONSTRAINT chk_deliveries_state CHECK (
    (status='PREPARING' AND shipped_at IS NULL     AND delivered_at IS NULL     AND failed_at IS NULL     AND cancelled_at IS NULL)
 OR (status='SHIPPED'   AND shipped_at IS NOT NULL AND delivered_at IS NULL     AND failed_at IS NULL     AND cancelled_at IS NULL)
 OR (status='DELIVERED' AND shipped_at IS NOT NULL AND delivered_at IS NOT NULL AND failed_at IS NULL     AND cancelled_at IS NULL)
 OR (status='FAILED'    AND shipped_at IS NOT NULL AND delivered_at IS NULL     AND failed_at IS NOT NULL AND cancelled_at IS NULL)
 OR (status='CANCELLED' AND shipped_at IS NULL     AND delivered_at IS NULL     AND failed_at IS NULL     AND cancelled_at IS NOT NULL))
  • 한 줄이 상태 하나다. "이 상태라면 이 시각들은 반드시 있고, 저 시각들은 반드시 없다"를 선언한다. 예를 들어 "배송 완료인데 출고 시각이 없다"나 "취소됐는데 출고 시각이 있다(출고 후 취소)" 같은 모순된 행은 저장 자체가 거부된다. 애플리케이션에 버그가 있어도 불가능한 상태가 DB에 들어가지 못한다. 원리
  • 재출고 경로가 이 제약과 맞물린다. FAILED에서 ship()을 하면 엔티티가 failedAt = null, failureReason = null로 지우고 shippedAt을 새 시각으로 덮는다. 그래야 SHIPPED 줄의 조건(failed_at IS NULL)을 통과한다. 확인 대신 "몇 번 실패했고 언제 실패했는지"라는 이력은 사라진다. 감사 로그(DELIVERY_FAIL, DELIVERY_SHIP)와 알림에만 흔적이 남는다. 이력이 중요해지면 delivery_events 같은 이벤트 테이블이 필요하다. 해석
  • MySQL은 8.0.16부터 CHECK 제약을 실제로 검사한다. 그 전에는 문법만 받고 무시했다. 이 프로젝트는 MySQL 8.4를 쓰므로 위 제약이 실제로 동작한다. 원리

2. 취소 — 한 트랜잭션에서 "되돌림의 의도"까지만 확정한다

CancellationService.request(CancellationService.java)는 고객이 호출한다(POST /api/orders/{orderId}/cancellations).

CancellationPersistenceAdapter.OrderLock order = cancellations.findOrderForUpdate(memberId, orderId);  // ① 내 주문, 잠금
if (order == null) throw ...404 ORDER_NOT_FOUND;
CancellationView existing = cancellations.findExisting(orderId);         // ② 이미 취소했으면 그 결과를 그대로(멱등)
if (existing != null) return response(existing);
DeliveryLock delivery = cancellations.findDeliveryForUpdate(orderId);    // ③ 배송 잠금
if (!"PAID".equals(order.status()) || delivery == null || !"PREPARING".equals(delivery.status())
    || !cancellations.hasSuccessfulPayment(orderId))                     //    PAID + 준비 중 + 성공한 결제
  throw ...409 CANCELLATION_NOT_ALLOWED;
if (cancellations.hasReturnForUpdate(orderId)) throw ...409;             // ④ 반품과 상호 배타
long cancellationId = cancellations.create(orderId, reason);             // ⑤ 취소 행 REFUND_PENDING
cancellations.cancelDelivery(delivery.deliveryId());                     //    배송 CANCELLED
for (OrderItem item : cancellations.findOrderItems(orderId))             //    sku_id 순서
  inventory.restoreCancellation(item.skuId(), item.quantity(), cancellationId);  // 재고 available +
cancellations.createRefund(orderId, cancellationId);                     // ⑥ 환불 READY, 금액 = 결제 금액 전액
  • ① 소유권 + 잠금: WHERE id=? AND member_id=? FOR UPDATE다. 이 주문 행 잠금이 같은 주문에 대한 취소·반품 요청을 줄 세운다. 반품 요청도 같은 주문 행을 먼저 잠그기 때문이다.
  • ② 멱등: 두 번 눌러도 두 번째는 첫 취소를 돌려준다. 동시에 들어와도 ①에서 줄을 서므로 같은 결과가 된다. 최후 방어선은 UNIQUE(order_id)다.
  • ③ 출고 전에만: 배송이 SHIPPED가 되면 취소가 막힌다. 이미 택배 트럭에 실린 상품은 "취소"가 아니라 "반품" 대상이라는 도메인 규칙이다.
  • ⑤ 재고는 available로 복원한다: 결제 성공 때 이미 DEDUCT(예약분이 출고분으로 빠짐)가 일어났다. 그래서 reserved가 아니라 판매 가능 수량을 다시 늘린다(17강 그림의 RESTORE). 원장에는 cancellationId를 근거로 남는다. 확인
  • ⑥ 환불은 "만들기만" 한다: 환불 행은 READY 상태이고, 금액은 orders.payment_amount 전액을 INSERT ... SELECT로 복사한다. 결제사 호출은 이 트랜잭션 안에서 하지 않는다. 15·18강과 같은 이유다. 대신 "돌려줘야 할 돈이 있다"는 의도가 취소와 같은 커밋으로 남는다. 그래서 환불 실행이 몇 번 실패해도 사라지지 않는다. Outbox 패턴의 핵심 아이디어("외부 작업을 DB에 먼저 기록")를 도메인 테이블로 구현한 셈이다. 해석

한계와 관찰 해석

  • 부분 취소가 없다. 3개를 산 주문에서 하나만 취소할 수 없고, 금액도 항상 전액이다. 주문 항목 단위 취소를 하려면 취소 항목 테이블, 부분 환불 금액 계산(쿠폰 할인을 항목에 어떻게 나눌지), 부분 재고 복원이 필요하다. 업계에서도 까다로운 문제다.
  • 없는 행 잠금: findExisting과 hasReturnForUpdate는 대부분 없는 행을 FOR UPDATE로 읽는다(order_cancellations, order_returns의 order_id 유니크 인덱스). 16·17강의 #331 교착과 같은 모양이다. 같은 주문은 ①이 줄 세우지만, 서로 다른 주문의 취소가 같은 갭을 공유하면 갭 락과 INSERT INTENTION이 엇갈릴 수 있다. 실제 재현 기록은 찾지 못했다. 주문 행 잠금이 이미 같은 주문을 직렬화하므로, 이 두 조회는 잠금 없이 읽어도 된다.

3. 반품 — 고객 요청, 관리자 승인, 관리자 수령

반품은 사람이 끼는 단계가 많다. 상태 기계로 먼저 보자.

ReturnService.java의 규칙이다. 확인

  • 요청 조건: 주문 PAID, 배송 DELIVERED, 그리고 deliveredAt + 7일이 현재보다 뒤여야 한다. 7일은 설정값(pawcycle.commerce.return-request-days)이다. 취소가 이미 있으면 409다. 취소와 반품은 상호 배타이며, 양쪽 모두 주문 행을 먼저 잠그고 상대 테이블을 확인한다.
  • 승인·거절은 REQUESTED에서만: 거절 사유와 결정한 관리자 ID, 결정 시각을 남긴다. DB의 chk_order_returns_decision은 REQUESTED면 decided_at이 NULL, 그 밖의 상태면 NOT NULL을 강제한다. 배송 CHECK와 같은 발상이다.
  • 수령은 APPROVED에서만, 그리고 재입고 여부(restock)를 관리자가 정한다. 돌아온 사료 포대가 뜯어졌거나 파손됐다면 다시 팔 수 없다. 그럴 때는 재고를 복원하지 않고 환불만 한다. restock=true일 때만 inventory.restoreReturn이 available을 늘린다. 재고 숫자가 "실제로 팔 수 있는 물건"을 뜻하도록 지키는 규칙이다. 확인·해석
  • 수령과 같은 커밋에서 반품은 REFUND_PENDING이 되고, 환불 행 READY가 생긴다(전액). 감사 로그도 함께 남는다.

4. 환불 — 결제 승인의 거울상

환불 실행(RefundService.process, RefundService.java)은 18강 결제 승인과 같은 3단 구조다.

  1. 선점: READY를 PROCESSING으로 바꿔 커밋한다.
  2. 결제사 호출: 트랜잭션 밖에서 취소(환불) API를 부른다. 금액이 0원이면 호출하지 않고 로컬 성공으로 처리한다(V19에서 amount > 0 제약을 완화).
  3. 완료 트랜잭션

같은 점보다 다른 점이 공부할 거리다. 확인

결제 승인(18·19강) 환불(이번 강의)
누가 시작하나 고객 브라우저(confirm) 관리자(/api/admin/refunds/{id})
불명 결과 상태를 UNKNOWN으로 바꿈 현재 상태 유지(PROCESSING이면 PROCESSING)

  • 불명이면 상태를 그대로 둔다: if ("UNKNOWN".equals(state)) state = row.status();. 첫 실행에서 응답을 못 받으면 환불은 PROCESSING에 머문다. 그래서 대사가 PROCESSING도 받아들인다. REFUND_ACTION_REQUIRED 알림은 이미 UNKNOWN인 행에서 다시 불명일 때만 나간다. 이 코드로는 UNKNOWN 상태로 들어가는 경로가 잘 보이지 않는다. 그래서 이 알림이 실제로 언제 나가는지는 다른 쓰기 경로까지 확인해야 한다. 확인·미확인
  • PROCESSING 대사의 위험 해석: 18·19강에서 결제는 진행 중일 수 있는 PROCESSING을 대사 대상에서 뺐다. 환불은 넣었다. 환불은 행마다 고유한 idempotency key로 결제사에 요청하고, 대사도 그 키로 조회한다. 그래서 "같은 환불이 두 번 실행되는" 위험은 결제사 쪽 멱등성에 기대어 줄였다고 볼 수 있다. 그래도 실행 중인 요청과 대사가 겹쳐 대사가 먼저 "실패"를 관측하면 판단이 엇갈릴 수 있다. 결제사의 멱등 키 동작은 문서로 확인하지 않았다 미확인.
  • 재시도는 "같은 행 재실행"이 아니라 "새 행"이다: FAILED 행에서만, attempt_no + 1 ≤ 3일 때, 같은 출처(취소 또는 반품)로 새 환불 행을 READY로 만든다. 새 idempotency key를 받는다. 이미 만들어 둔 같은 차수 행이 있으면 그것을 돌려준다(멱등). 실패한 시도의 기록이 덮이지 않고 행으로 남는다. 확인

  • 성공하면 한 커밋에서 다음을 처리한다.

    • 쿠폰 반환: USED를 AVAILABLE로 되돌린다.
    • 취소 또는 반품을 COMPLETED로 바꾼다.
    • 멤버십 등급을 재평가한다(21강).
    • 완료 알림을 보낸다.

    쿠폰을 돌려주는 것은 정책 결정이다. 전액 환불이니 쿠폰도 쓰지 않은 것으로 본다는 뜻이다. 확인·해석

4-1. "주문당 성공한 환불은 하나" — 생성 컬럼 + UNIQUE

환불은 한 주문에 여러 행이 생긴다(재시도). 그래서 UNIQUE(order_id)를 걸 수 없다. 그런데 "성공한 환불"은 주문당 하나여야 한다. 두 번 성공하면 돈을 두 번 돌려준 것이다. PostgreSQL이라면 부분 인덱스로 쉽게 해결한다.

-- PostgreSQL (저장소에 없는 비교용 예시)
CREATE UNIQUE INDEX uk_refunds_succeeded ON refunds(order_id) WHERE status = 'SUCCEEDED';

MySQL에는 부분 인덱스가 없다. 그래서 V16은 생성 컬럼(generated column)으로 같은 효과를 낸다.

succeeded_order_id BIGINT GENERATED ALWAYS AS
    (CASE WHEN status='SUCCEEDED' THEN order_id ELSE NULL END) STORED,
CONSTRAINT uk_refunds_succeeded_order UNIQUE (succeeded_order_id),
  • 성공 행에서만 order_id 값이 생기고, 나머지는 NULL이다.
  • MySQL의 UNIQUE는 NULL을 서로 다른 값으로 취급한다. 그래서 실패·대기 행은 몇 개든 공존하고, 성공 행만 주문당 하나로 제한된다. 원리
  • 18강의 payments 테이블에도 같은 장치(uk_payments_successful_order)가 있다. "주문당 성공한 결제도 하나"다. 승인 경로와 대사 경로가 동시에 같은 주문을 성공 처리하려 해도, 두 번째 쓰기는 DB가 거부한다. 확인

  • 그 밖의 제약도 상태 기계를 받쳐 준다.

    • UNIQUE(source, source_id, attempt_no): 같은 취소·반품의 같은 차수는 하나
    • UNIQUE(idempotency_key): 결제사 요청 키 중복 금지
    • CHECK: 출처가 취소면 cancellation_id만, 반품이면 return_id만 존재

    source_id도 COALESCE(cancellation_id, return_id)로 만든 생성 컬럼이다.

같이 읽을 자료:

  • 망태의 개발냄새(kimmangtae), MySQL 조건부 유니크 제약 조건 설정하기 (2025-04-21) — 열어서 본문 앞부분을 읽었다. "학생 계정끼리만 인증코드가 중복되면 안 된다"는 요구를, PostgreSQL 조건부 유니크 대신 MySQL의 생성 컬럼과 유니크 인덱스로 푼다. "MySQL UNIQUE는 NULL을 중복으로 보지 않는다"는 원리를 바로 활용한다. 위의 succeeded_order_id와 같은 기법이다. 그림은 없다.
  • 검색 결과에서 velog의 "[MySQL] Generated 컬럼 & 함수 기반 인덱스", tonylim.tistory.com "Generated 컬럼 및 함수 기반 인덱스"를 봤다. 제목만 확인했다.

5. 트레이드오프 정리

선택 얻은 것 대가
주문 상태는 PAID로 고정, 사후 처리는 별도 테이블 동시 사실 표현, 단계별 시각·담당자 기록 화면이 여러 테이블을 조합해 상태를 계산해야 함
상태·시각 조합을 CHECK로 강제 불가능한 상태가 저장되지 않음 재출고 시 실패 이력이 덮임
취소·반품 커밋 때 환불 행만 생성 외부 호출 없이 의도를 영속화 실제 환불은 관리자가 실행해야 함
환불 재시도는 새 행 시도 이력 보존, 결제사 키 분리 성공 하나를 보장하는 생성 컬럼 장치가 필요
전액 취소·환불만 쿠폰 배분·부분 재고 문제 회피 부분 취소 요구에 대응 불가

그리고 18강과 같은 사실을 다시 짚는다. 환불 어댑터도 운영에서는 503이고, 실제 결제사 취소 API 구현체는 저장소에 없다(로컬 샌드박스만 있음). 이 강의의 흐름은 저장소 기준 설계와 테스트로 검증된 것이다. 실제 돈을 돌려준 증거는 아니다. 확인
