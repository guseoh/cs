17강. 체크아웃: 결제 직전의 약속을 한 트랜잭션으로 만든다

체크아웃은 "결제하기" 버튼을 눌렀을 때 실행된다. 돈은 아직 오가지 않는다. 결제 승인은 18강에서 다룬다. 이 단계의 일은 결제창을 띄우기 전에 서버가 지킬 약속을 DB에 확정하는 것이다.

  • 이 가격과 이 배송지로 주문서(Order, PAYMENT_PENDING)를 만든다.
  • 결제 대기 건(Payment, READY, 30분 후 만료)을 만든다.
  • 그동안 남이 사 가지 못하도록 재고를 예약하고, 쿠폰을 예약한다.
  • 같은 요청이 다시 와도 하나만 생기도록 멱등성 결과를 남긴다.

이 모든 것이 CheckoutApplicationService.checkout(CheckoutApplicationService.java) 안의 TransactionTemplate 한 번으로 일어난다. 중간에 하나라도 실패하면 전부 없던 일이 된다. 먼저 전체 순서와, 각 단계가 무엇을 잠그는지 보자.

여기서 눈여겨볼 점이 하나 있다. 체크아웃은 장바구니를 비우지 않는다. 결제가 실패하거나 30분 안에 결제하지 않으면 사용자는 장바구니를 그대로 다시 써야 하기 때문이다. 장바구니는 결제 성공이 확정되는 대사 단계에서 주문 수량만큼 차감된다. 이때 16강에서 본 "version 정확히 +1" 규칙이 적용된다. 확인·기록

1. 멱등성: "재생"을 "변경 감지"보다 먼저 판정한다

2단계와 3단계의 순서가 이 강의의 첫 번째 핵심이다.

CartLock cartLock = cart.lockForAdd(memberId);
CheckoutReplay replay = checkout.findReplay(memberId, idempotencyKey);      // ② 먼저: 이 키로 이미 만든 주문이 있나
if (replay != null) {

      || !checkoutFingerprint(addressId, memberCouponId, replay.requestCartVersion())
          .equals(replay.requestFingerprint()))                               //   ⓒ 배송지·쿠폰이 처음과 다르면
    throw new CommerceException(409, "IDEMPOTENCY_KEY_CONFLICT", ...);
  return response(replay);                                                    //   같은 요청이면 첫 결과를 그대로

if (requestedCartVersion != null && requestedCartVersion != cartLock.version())  // ③ 그다음: 장바구니가 바뀌었나
  throw new CommerceException(409, "CART_CHANGED", "장바구니가 변경되었습니다.");

왜 이 순서인가 기록·해석. 첫 체크아웃이 성공하고 결제까지 끝났다고 하자. 그러면 대사 단계가 장바구니를 차감하고 version이 7에서 8로 오른다. 그런데 첫 응답이 네트워크에서 사라져서, 사용자가 같은 키로 다시 요청한다. 순서가 반대라면 ③에서 "7 ≠ 8 → CART_CHANGED"가 난다. 이미 성공한 주문을 두고 "장바구니가 바뀌었다"는 엉뚱한 오류를 받는 것이다. 그래서 "이 키로 만든 결과가 있는가?"를 먼저 묻는다. 결과가 있으면 현재 장바구니가 아니라 최초 요청의 정체성(identity)과 비교한다.

  • 지문: SHA-256(addressId | couponId 또는 "none" | 최초 cartVersion). 같은 키에 다른 배송지나 쿠폰을 실어 보내면 409다. 키는 같은데 내용이 다른 요청을 "같은 요청"으로 처리하면, 사용자가 바꾼 배송지가 조용히 무시된다.
  • ⓐ fail-closed: 지문이나 버전 컬럼이 생기기 전의 옛 결과에는 대조할 근거가 없다. 이때 "아마 같겠지"라고 추정해 재생하지 않고 거부한다. 기록
  • 조회에 잠금이 없다: findResult는 일반 SELECT다. 16강에서 본 #331의 교착(없는 행 FOR UPDATE → 다른 회원끼리 supremum 갭 경합)을 PR #332가 이렇게 고쳤다. 같은 회원의 동시 요청은 1단계 회원 잠금이 이미 줄 세우므로, 이 조회에는 잠금이 필요 없다. 원리
  • 저장이 두 번 나뉜 이유: saveIdempotency로 행을 만든 뒤, saveCartVersion이 UPDATE ... SET request_cart_version = ? WHERE ... AND request_cart_version IS NULL로 버전을 채운다. 갱신된 행이 1이 아니면 IllegalStateException으로 전체를 롤백한다. 버전 컬럼은 V23에서 NULL 허용으로 나중에 추가되었다. 옛 행과 같이 살아야 해서 생긴 모양으로 보인다. 확인·해석

2. 잠근 상태에서 다시 계산한다 — 클라이언트는 가격을 보내지 않는다

요청 본문은 addressId, memberCouponId, cartVersion 세 개뿐이다(CheckoutRequest). 금액과 수량은 하나도 보내지 않는다. 서버가 잠근 데이터로 전부 다시 계산한다. 확인

public List<CheckoutCartItem> findCartItems(long cartId) {
  List<CartItemEntity> lockedItems = cartItems.findAllByCartIdForUpdate(cartId);      // ① 장바구니 항목 잠금
  List<Long> skuIds = lockedItems.stream().map(item -> item.getId().skuId()).toList();
  for (Sku sku : skus.findAllByIdInForUpdate(skuIds)) lockedSkus.put(sku.getId(), sku); // ② SKU 행 잠금
  return lockedItems.stream().map(item -> new CheckoutCartItem(
      sku.getId(), item.getQuantity(), sku.getSkuCode(), sku.getName(),
      sku.getPrice(), sku.getProduct().getName())).toList();                          // ③ 잠근 가격·이름 사용
}
  • ① 장바구니 항목 잠금: 체크아웃 도중 다른 탭이 수량을 바꾸지 못하게 한다(3단계 버전 비교와 짝).
  • ② SKU 잠금: 관리자가 체크아웃 도중 가격이나 판매 상태를 바꾸면, 그 수정은 이 트랜잭션이 끝날 때까지 기다린다. 14강의 관리자 상품 PATCH가 같은 행을 잠그기 때문이다. "결제 금액을 계산한 가격"과 "주문에 기록된 가격"이 어긋날 수 없다. 원리·해석
  • ③ 스냅샷: createOrderItem이 SKU 코드, 상품명, SKU명, 단가를 order_items에 복사한다. 배송지도 orders에 복사한다(수령인, 전화번호, 주소). 확인
    • 왜 복사하나 원리: 주문은 "그때 그 조건의 계약서"다. 다음 달 가격이 오르거나 상품명이 바뀌어도, 지난 주문의 영수증이 바뀌면 안 된다. 그래서 FK로 참조만 하지 않고 값을 복제한다. 정규화를 의도적으로 깨는 것이다. 이력·감사·환불 금액 계산이 모두 이 스냅샷을 기준으로 한다.
    • 주소도 마찬가지다. 10강에서 본 "기본 배송지 변경"이 이미 만든 주문이나 정기배송에 자동으로 번지지 않는다. 기록

잠금 순서와 교착 회피 원리·해석: 두 체크아웃이 같은 SKU 두 개(A, B)를 사려 한다고 하자. 한쪽은 A→B 순서로, 다른 쪽은 B→A 순서로 잠그면 교착이 난다. 여기서는 cart_items를 PK (cart_id, sku_id) 순서로 읽고, 그 순서대로 재고를 예약한다. 그래서 두 회원 모두 SKU 오름차순으로 잠그게 된다. 다만 쿼리에 ORDER BY가 없으므로, 이 순서는 InnoDB가 PK 순서로 스캔한다는 구현 특성에 기대고 있다. 순서를 명시하는 ORDER BY item.id.skuId를 붙이는 것이 더 안전하다.

3. 쿠폰 할인 — BigDecimal과 내림

public static BigDecimal discount(BigDecimal original, BigDecimal minimum,
    String type, BigDecimal value, BigDecimal maximum) {
  if (original.compareTo(minimum) < 0)                              // 최소 주문 금액
    throw new CommerceException(409, "COUPON_MINIMUM_ORDER", ...);
  BigDecimal discount = "PERCENTAGE".equals(type)
      ? original.multiply(value).divide(BigDecimal.valueOf(100), 0, RoundingMode.DOWN)  // 원 단위 내림
      : value;                                                       // 정액
  if (maximum != null) discount = discount.min(maximum);            // 최대 할인 한도
  return discount.min(original);                                    // 결제 금액이 음수가 되지 않게
}
  • BigDecimal을 쓰는 이유 원리: double은 2진 부동소수점이라 0.1을 정확히 표현하지 못한다(0.1 + 0.2 = 0.30000000000000004). 돈 계산에서는 1원 오차도 정산 불일치다. DB 컬럼도 DECIMAL(18,2)다.
  • RoundingMode.DOWN: 15% 할인에서 12,345원 → 1,851.75원 → 1,851원이다. 할인을 내려 깎으므로 회사가 1원 덜 깎아 준다. 반올림 규칙은 정책이다. 그래서 이 메서드처럼 한곳에 모아야 화면과 주문, 환불이 같은 숫자를 낸다. 해석
  • 할인 후 금액이 100원 미만이면 409다(PAYMENT_AMOUNT_TOO_LOW). PG의 최소 결제 금액과 맞춘 값으로 보이지만, 근거 문서는 확인하지 못했다. 미확인
  • 쿠폰 잠금 순서는 member_coupons(내 쿠폰) FOR UPDATE → coupons(쿠폰 정의) FOR UPDATE다. 예약은 UPDATE ... SET status='RESERVED' WHERE status='AVAILABLE'처럼 상태 조건을 건 UPDATE로 한다. 결제가 성공하면 USED, 만료되면 AVAILABLE로 돌아간다. 확인 21강에서 다시 본다.
    • 사소한 관찰 해석: reserveCoupon은 reserveIfAvailable의 반환값(갱신된 행 수)을 확인하지 않는다. 바로 앞에서 잠그고 AVAILABLE을 확인했으니 실제로는 1이다. 하지만 재고 예약처럼 != 1이면 실패시키는 편이 방어적이다.

4. 재고 예약 — 비관적 잠금과 버전 CAS를 둘 다 쓴다

재고는 숫자 두 개로 관리한다(inventories).

  • available_quantity: 지금 팔 수 있는 수량
  • reserved_quantity: 결제를 기다리며 묶여 있는 수량
  • 둘 다 CHECK (>= 0)이고, version이 있다.

이 두 숫자가 사건마다 어떻게 움직이는지가 재고 모델의 전부다.

  • 예약 시점이 결제 전이다. 결제를 마친 뒤에 재고를 빼면, 마지막 1개를 두 사람이 동시에 결제했을 때 늦은 사람은 돈이 빠져나간 뒤에야 "재고 없음"을 듣는다. 그러면 자동 환불을 해야 한다. 결제 전에 예약하면 늦은 사람은 결제창을 띄우기 전에 409를 받는다. 대가는 "결제하지 않고 떠난 사람이 30분 동안 재고를 묶는다"는 점이고, 5절의 만료가 이를 푼다. 원리·해석
  • 모든 이동은 inventory_movements에 직전·직후 숫자와 함께 한 줄씩 남는다. 그리고 UNIQUE (payment_id, type, sku_id)가 있다. 같은 결제가 같은 SKU를 두 번 RESERVE하거나 두 번 DEDUCT하는 것을 DB가 막는다. 재고 숫자는 "결과"이고, movement는 그 결과를 설명하는 "원장(ledger)"이다. 확인

4-1. 예약 코드 한 줄씩

@Service
@Transactional(propagation = Propagation.MANDATORY)      // ① 혼자서는 실행 불가
public class InventoryService {
  public void reserve(long skuId, int quantity, long paymentId) {
    InventoryEntity inventory = inventories.findLockedBySkuId(skuId).orElse(null);   // ② FOR UPDATE
    if (inventory == null || inventory.availableQuantity() < quantity)
      throw new CommerceException(409, "INVENTORY_INSUFFICIENT", "재고가 부족합니다.");
    int changed = inventories.reserveIfVersionMatches(skuId, quantity, inventory.version());  // ③ CAS
    if (changed != 1) throw new CommerceException(409, "INVENTORY_CONFLICT", "재고가 변경되었습니다.");
    movements.save(InventoryMovementEntity.payment(skuId, paymentId, "RESERVE", ...));         // ④ 원장
  }
}

-- ③ reserveIfVersionMatches
UPDATE inventories
SET available_quantity = available_quantity - :quantity,
    reserved_quantity  = reserved_quantity  + :quantity,
    version = version + 1
WHERE sku_id = :skuId
  AND version = :expectedVersion          -- 내가 읽은 그 버전일 때만
  AND available_quantity >= :quantity     -- 그리고 여전히 충분할 때만
  • ① Propagation.MANDATORY: 바깥 트랜잭션이 없으면 예외를 던진다. 재고 변경은 반드시 주문·결제 생성과 같은 커밋에 묶여야 하기 때문이다. 재고만 따로 커밋되면 "주문은 롤백됐는데 재고는 빠진" 상태가 생긴다. 5강의 전파 속성을 "실수를 막는 계약"으로 쓴 사례다. 원리
  • ② 비관적 잠금: 같은 SKU를 사는 다른 체크아웃은 여기서 줄을 선다.
  • ③ 조건부 UPDATE(CAS, Compare-And-Swap): 이미 잠갔는데 왜 버전 조건까지 거나? 최종 방어막이다. 잠금이 누락된 경로가 생기거나 잠금 범위가 바뀌어도, 버전과 available >= quantity 조건이 음수 재고와 lost update를 막는다. DB의 CHECK (available_quantity >= 0)이 그 뒤의 세 번째 방어선이다. 해석
  • 이 UPDATE는 @Modifying(flushAutomatically = true, clearAutomatically = true)다. 실행 전에 대기 중인 변경을 flush하고, 실행 후 영속성 컨텍스트를 비운다. 벌크 UPDATE는 1차 캐시를 거치지 않으므로, 캐시에 남은 옛 InventoryEntity(옛 수량)를 다시 쓰지 않으려는 것이다. 그래서 이 호출 뒤에는 앞서 읽은 엔티티가 모두 준영속(detached)이 된다. 체크아웃이 그 뒤에 persist나 쿼리만 하는 이유이기도 하다. 원리·해석

4-2. 잠금이 원래부터 있었던 것은 아니다 — 측정이 찾아낸 버그

#335 PERF-COMMERCE-003은 로컬에서 120 VU로 부하를 건 실험이었다. 기록

  • 서로 다른 SKU를 사면 20 RPS에서 안정적이었다.
  • 여러 회원이 같은 재고 행을 사면 5 RPS까지는 안정적이었다. 하지만 10 RPS 워밍업 30초 동안 300건 중 INVENTORY_CONFLICT 409가 7건 나와 실험을 중단했다.
  • 원인: 당시 코드는 SKU 행만 FOR UPDATE로 잠그고, 재고 행의 버전은 일반 조회로 읽었다. RR의 일반 조회는 MVCC 스냅샷(과거)을 본다(15강 3-5). 그래서 앞 트랜잭션이 커밋한 새 버전 대신 옛 버전으로 CAS를 시도해 실패했다.
  • PR #336(2026-10-06)은 한 지점만 바꿨다. 재고 행을 잠금 조회(현재 읽기)로 읽은 뒤 CAS한다. 수정 후 정확한 후보 이미지로 10 RPS를 재측정했더니 1,201건, 오류·dropped·deadlock 0이었다.
  • 기각한 대안:
    • Hikari·스레드 증설: 커넥션 풀이 먼저 포화됐다는 근거가 없었다.
    • CAS 폐기 또는 잠금 전면 제거: 최종 방어막이 사라진다.
    • 스키마·인덱스·비동기를 한꺼번에 변경: 원인과 효과를 분리할 수 없다.
  • 한계: 15/20 RPS는 측정하지 않았다. 그래서 "선착순 한정판에서도 버틴다"는 주장은 할 수 없다. 첫 After 측정은 옛 이미지로 실행된 잘못된 측정이었다. 그래서 개선 근거에서 빼고 따로 보존했다. 기록

이 사례에서 꼭 가져갈 원리가 있다. "잠금 안에서 읽는다"는 "그 행을 잠금 읽기로 읽는다"여야 한다. 다른 행(SKU)을 잠갔다고 해서, 같은 트랜잭션의 일반 SELECT가 최신 값을 보지는 않는다.

5. 30분 만료 — 묶인 재고를 푸는 스케줄러

@Scheduled(fixedDelayString = "${pawcycle.commerce.checkout-expiration.fixed-delay-ms:60000}")
public void expireDueCheckouts() { service.expireDue(batchSize); }        // 기본 60초마다, 100건씩

public int expireDue(int batchSize) {
  for (Long paymentId : expirations.findDuePaymentIds(batchSize))         // READY이고 expires_at <= now인 NORMAL 결제
    if (processor.expire(paymentId)) expired++;                           // 결제 하나마다 별도 트랜잭션
}

@Transactional
public boolean expire(long paymentId) {
  var payment = expirations.findForUpdate(paymentId);                     // payment → order 순서로 잠금
  if (payment == null || !"READY".equals(payment.paymentStatus())
      || !"PAYMENT_PENDING".equals(payment.orderStatus())) return false;  // 잠근 뒤 상태 재확인
  for (var item : expirations.findOrderItems(payment.orderId()))
    inventory.release(item.skuId(), item.quantity(), paymentId);          // reserved → available
  expirations.releaseCoupon(payment.orderId());                           // RESERVED → AVAILABLE
  expirations.markExpired(paymentId, payment.orderId());
  return true;
}
  • 후보 조회는 잠금 없이, 처리는 잠금 후 재확인. 목록을 뽑은 뒤 처리하기까지 그 사이에 사용자가 결제를 시작해 상태가 바뀌었을 수 있다. 그래서 잠근 뒤 다시 READY·PAYMENT_PENDING인지 본다. 15강의 "확인 시점과 사용 시점(TOCTOU)" 방어가 여기서도 반복된다. 원리
  • 결제 하나당 트랜잭션 하나: 한 건이 실패해도 앞서 처리한 건은 커밋된 채로 남는다. 100건을 한 트랜잭션에 넣으면 잠금을 오래 쥐고, 하나만 실패해도 전부 롤백된다. 해석
  • PROCESSING·UNKNOWN은 건드리지 않는다. 결제사에 승인 요청을 이미 보냈는데 결과를 모르는 결제다. 이때 재고를 풀어 버리면, 실제로는 돈이 빠져나간 주문의 재고를 남에게 팔게 된다. 이 경우는 18·19강의 조회 중심 대사가 다룬다. 기록
  • 서버가 여러 대면 @Scheduled가 인스턴스마다 돈다. 같은 결제를 두 인스턴스가 동시에 처리하려 해도 행 잠금과 상태 재확인 덕분에 한쪽만 성공한다. 그래서 분산 락(ShedLock 등) 없이도 정합성은 지켜진다. 다만 같은 일을 중복해서 조회하는 비용은 남는다. 해석

개선점 해석

  • expireDue 루프는 processor.expire가 던진 예외를 잡지 않는다. 예를 들어 release의 "Reserved inventory is inconsistent" 같은 예외가 한 건에서 나면 그 배치의 나머지 건이 이번 회차에 처리되지 않는다. 다음 회차에 같은 건이 맨 앞(order by expiresAt, id)에 다시 오면 계속 막힐 수 있다. 건별로 예외를 잡아 기록하고 넘어가는 처리가 필요하다.
// 저장소에 없는 예시 — 독성 메시지(poison) 한 건이 배치 전체를 막지 않게
for (Long paymentId : expirations.findDuePaymentIds(batchSize)) {
  try { if (processor.expire(paymentId)) expired++; }
  catch (RuntimeException e) { metrics.expirationFailed(); log.warn("checkout expiry failed paymentId={}", paymentId); }
}

6. 트레이드오프 정리

선택 얻은 것 치른 대가
한 트랜잭션에 주문·결제·재고·쿠폰·멱등성 부분 성공이 없다 트랜잭션이 길고 잠금이 많다
회원 행으로 같은 회원 직렬화 중복 체크아웃·교착 방지 같은 회원의 동시 요청은 순차 처리
인기 SKU 재고 행 잠금 + CAS 음수 재고·lost update 없음 같은 SKU 구매가 줄을 선다(상한 미측정)
결제 전 예약 + 30분 만료 결제 후 재고 부족 환불 없음 이탈자가 최대 30분+ 재고를 묶음
클라이언트는 가격을 보내지 않음 가격 조작 불가 화면 금액과 다르면 다시 조회해야

선착순 대량 판매에서는 재고 행 하나에 잠금이 몰리는 것이 병목이 된다. 업계의 대안은 다음과 같다.

  • Redis DECR로 수량을 먼저 깎기
  • 재고를 여러 행으로 쪼개기(bucket)
  • 대기열 두기

PawCycle은 측정 근거 없이 이 복잡도를 들이지 않았다. 그래서 상한은 "미측정"으로 남겨 두었다. 기록·해석
