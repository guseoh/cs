18강. 결제 승인: 돈이 오가는 순간, 트랜잭션은 어디서 끊어야 하는가

17강의 체크아웃이 결제 대기 건(Payment READY)을 만들었다. 이번 강의는 사용자가 결제창에서 카드 인증을 마친 뒤, 서버가 결제사(PG, 여기서는 토스페이먼츠)에 "이 결제를 승인하라"고 요청하고 그 결과를 DB에 반영하는 과정을 다룬다.

이 단계가 어려운 이유는 하나다. 외부 결제사의 승인과 우리 DB의 커밋은 하나의 원자적 작업으로 묶을 수 없다. 결제사에 돈을 빼라고 요청한 뒤 우리 서버가 죽으면, "돈은 나갔는데 주문은 결제 대기"인 상태가 남는다. 이 강의의 모든 설계는 그 틈을 어떻게 다루는지에 대한 이야기다.

먼저 프론트엔드부터 DB까지의 전체 흐름을 보자.

15강의 리뷰 요약에서 본 "짧은 트랜잭션 → 트랜잭션 밖 외부 호출 → 짧은 트랜잭션" 구조가 여기서도 반복된다. 차이는 되돌릴 수 없는 것이 돈이라는 점이다.

1. 프론트엔드 — URL의 금액을 믿지 않는다

토스 결제창은 인증을 마치면 successUrl?paymentKey=...&orderId=...&amount=...로 돌아온다. 이 URL은 브라우저 주소창에 있으므로 사용자가 고칠 수 있다. app/checkout/success/page.tsx는 세 가지 방어를 한다. 확인

// ① URL에서 결제 정보를 읽자마자 주소창에서 지운다
window.history.replaceState({}, "", "/checkout/success");

// ② 체크아웃 때 저장해 둔 "서버가 정한 금액"과 대조하고, 승인 요청에는 그 서버 금액을 보낸다
const expected = readTossCheckoutContext();               // 체크아웃 응답의 providerOrderId·amount
const validationError = validateTossSuccess({ ...callback }, expected);
paymentApi.confirmToss(callback.paymentKey, callback.providerOrderId, expected.amount, csrf);

// ③ 같은 결제에 대한 승인 Promise를 ref에 하나만 보관한다
if (!confirmPromiseRef.current || confirmKeyRef.current !== confirmKey) {
  confirmPromiseRef.current = executeWithCsrf(...);       // React StrictMode가 effect를 두 번 돌려도 요청은 한 번
}
  • ① 주소 정리: 새로고침이나 방문 기록, 공유된 링크로 paymentKey가 다시 쓰이지 않게 한다. 결제 정보는 세션 저장소로 옮겨 새로고침 후에도 승인을 이어 간다. 확인·해석
  • ② 서버 금액이 권위다: "redirect의 amount보다 Backend Checkout amount를 권위로 삼는다"는 결정이다. 그래도 프론트엔드 검증은 편의일 뿐이다. 진짜 방어는 2절의 백엔드 금액 대조가 한다. 기록
  • ③ StrictMode 중복 실행 방지: 개발 모드의 React는 effect를 두 번 실행해 부작용을 드러낸다. 승인 요청이 두 번 나가면 서버가 409를 돌려준다. 그래서 같은 키의 Promise를 재사용해 요청 자체를 한 번만 보낸다. 확인·기록

2. TX1 — 상태를 "잠금"으로 쓰는 선점(claim)

PaymentApplicationService.confirm(PaymentApplicationService.java)의 첫 트랜잭션이다.

PaymentWork work = transaction.execute(status -> {
  PaymentWork payment = payments.findByProviderOrderIdForUpdate(providerOrderId, memberId);  // ① 내 결제만, 잠금
  if (payment == null) throw notFound();                                                    //    남의 것이면 404
  if ("SUCCEEDED".equals(payment.status()) && "PAID".equals(payment.orderStatus())
      && payment.amount().compareTo(amount) == 0 && paymentKey.equals(payment.paymentKey()))
    return payment;                                                                         // ② 이미 끝난 같은 승인 → 성공 재응답
  if (!"READY".equals(payment.status()) || !"PAYMENT_PENDING".equals(payment.orderStatus())
      || payment.amount().compareTo(amount) != 0)
    throw new CommerceException(409, "PAYMENT_CONFIRM_CONFLICT", ...);                      // ③ 상태·금액이 다르면 거절
  payments.markProcessing(payment.paymentId(), paymentKey);                                 // ④ READY → PROCESSING 커밋
  return payment;
});
  • ① 소유권: providerOrderId와 memberId를 함께 WHERE에 넣는다(12강). 남의 주문번호를 알아도 승인할 수 없다.
  • ② 멱등 재응답: 승인이 이미 끝난 결제에 같은 paymentKey와 금액으로 다시 요청하면 결제사를 부르지 않고 성공을 돌려준다. 응답을 잃은 클라이언트가 재시도해도 안전하다.
  • ③ 금액 대조: 클라이언트가 보낸 금액이 DB의 결제 금액(17강에서 서버가 계산한 값)과 한 푼이라도 다르면 409다. URL을 고쳐 100원으로 승인받으려는 시도가 여기서 막힌다. 결제사도 승인 요청의 금액과 인증된 금액을 대조하므로 이중 방어다. 확인·원리
  • ④ 선점이 핵심이다. PROCESSING으로 바꿔 커밋하면, 이후 같은 결제에 대한 두 번째 요청은 ③에서 409를 받는다. 결제사에 승인 요청이 두 번 나가는 일(이중 승인)을 막는다. DB 행 잠금은 트랜잭션이 끝나면 풀리지만, 상태 값은 트랜잭션을 넘어 살아남는 잠금이다. 이것을 "claim"이라 부른다. 원리
    • 17강의 만료 스케줄러는 READY만 만료시킨다. 그래서 선점된 결제는 결제사 호출 중에 만료로 풀리지 않는다.
    • 관찰 해석: 선점할 때 expires_at이 지났는지는 보지 않는다. 30분이 지났더라도 스케줄러가 아직 돌지 않았다면 승인이 진행된다. 예약 재고가 아직 남아 있으므로 정합성 문제는 없다. "30분"은 엄격한 마감이 아니라 정리 기준에 가깝다.

3. 결제사 호출 — "응답이 없다"는 "실패했다"가 아니다

TX1이 커밋된 뒤, DB 커넥션 없이 토스 승인 API를 부른다. 결과는 세 갈래로 나뉜다. 여기서 결제의 상태 기계를 먼저 그려 보자.

(그림 아래쪽 점선은 UNKNOWN에서 READY로 되돌아가 재승인하는 경로가 없다는 뜻이다.)

어댑터(TossTestPaymentAdapter, TossTestPaymentAdapter.java)가 응답을 이렇게 나눈다. 확인

결제사 응답 어댑터 결과 이유
2xx + status=DONE SUCCEEDED 승인 완료
2xx + CANCELED/ABORTED FAILED 확정 실패
2xx + 그 밖의 상태 UNKNOWN 진행 중일 수 있음
4xx FAILED (응답의 code 보관) 결제사가 요청을 거절함(카드 한도 등)
5xx, 타임아웃, I/O 오류, 인터럽트 예외 → 서비스가 UNKNOWN 처리 결과를 모름

왜 타임아웃이 실패가 아니라 "모름"인가 원리. 네트워크에서 응답을 못 받은 경우는 세 가지가 섞여 있다.

  1. 요청이 결제사에 도착하지 못했다.
  2. 도착해서 승인되었는데 응답이 돌아오다 끊겼다.
  3. 결제사가 아직 처리 중이다.

클라이언트는 이 셋을 구분할 수 없다. 분산 시스템의 "두 장군 문제"와 같은 구조다. 여기서 FAILED로 단정하고 재고를 풀면, 2번 경우 돈은 빠져나갔는데 재고는 남에게 팔리는 최악의 결과가 된다. 그렇다고 바로 승인을 다시 요청하면 이중 승인 위험이 있다. 그래서 UNKNOWN으로 표시하고 예약을 유지한 채, 조회 API로 결과를 확인하는 대사(19강)에 넘긴다.

  • 타임아웃 10초: HttpClient의 connectTimeout과 요청별 timeout이 모두 10초다. 15강의 AI 요약 클라이언트와 달리 타임아웃을 명시했다. 결제 응답을 무한정 기다리면 Tomcat 워커 스레드가 묶이기 때문이다. 확인·원리
  • InterruptedException 처리: Thread.currentThread().interrupt()로 인터럽트 플래그를 복원한 뒤 UNKNOWN 처리한다. 인터럽트를 삼키면 스레드를 종료하려는 상위 코드(서버 종료 등)가 신호를 잃는다. 자바 동시성의 기본 예절이다. 원리
  • 비밀키 보호: test_sk_로 시작하지 않는 키로는 빈 생성 자체가 실패한다. 실수로 라이브 키를 넣어도 기동하지 않는다. 키는 Authorization: Basic base64(secretKey + ":")로만 쓰이고 로그로 나가지 않는다. 확인

짚어 볼 지점: 4xx를 모두 확정 실패로 보는 매핑 해석. 승인 요청이 4xx를 받으면 대부분은 정말 거절이다(잔액 부족, 카드 정지 등). 하지만 19강에서 볼 조회 경로는 결정 기록상 "404 등 4xx, 5xx, timeout, 신원 불일치, 미발견을 일괄 FAILED로 간주하지 않는다"이고, 코드에서도 비-2xx를 UNKNOWN으로 처리한다. 즉 같은 결제사 응답 코드를 승인 경로는 확정 실패로, 조회 경로는 불명으로 다룬다. 승인에서 4xx가 나오는 상황 중 실제로는 이미 승인된 경우가 있는지(예: 같은 결제를 두 번 승인 요청했을 때)는 결제사 오류 코드 문서를 대조해야 한다. 나는 그 문서를 확인하지 않았다 미확인. 우리 서버는 2절의 선점 덕분에 같은 결제의 승인을 두 번 보내지 않는다. 그래서 위험은 작지만, 오류 코드별 허용 목록(allowlist)으로 좁히는 편이 일관된다.

4. TX2 — 결과를 한 번에 반영한다

private PaymentResult finalizePayment(long paymentId, String providerResult, String paymentKey) {
  PaymentState payment = payments.findForUpdate(paymentId);                 // 다시 잠근다
  if (!"PROCESSING".equals(payment.status()))                               // 그사이 누가 확정했으면
    return new PaymentResult(..., payment.status());                        //   손대지 않고 현재 상태만 응답
  if ("UNKNOWN".equals(providerResult)) { payments.markUnknown(paymentId); return ...; }
  if ("SUCCEEDED".equals(providerResult)) {
    for (OrderItem item : payments.findOrderItems(payment.orderId()))
      inventoryService.deduct(item.skuId(), item.quantity(), paymentId);    // reserved → 출고
    payments.markSucceeded(paymentId, paymentKey);
    payments.markOrderPaid(payment.orderId());                              // 주문 PAID
    deliveryService.createPreparing(payment.orderId());                     // 배송 준비(20강)
    payments.useReservedCoupon(payment.orderId());                          // 쿠폰 RESERVED → USED
    notificationService.create(memberId, "ORDER_PAID", "ORDER", orderId);    // 인앱 알림(21강)
    payments.consumeCart(memberId, payment.orderId());                      // 장바구니 차감, version +1 한 번
    membershipEvaluation.evaluate(memberId);                                // 멤버십 등급 재평가
    return ...SUCCEEDED;
  }
  for (...) inventoryService.release(item.skuId(), item.quantity(), paymentId);  // 실패: reserved → available
  payments.markFailed(paymentId); payments.markOrderPaymentFailed(orderId); payments.releaseReservedCoupon(orderId);
  return ...FAILED;
}
  • "PROCESSING이 아니면 손대지 않는다": 결제사 응답을 기다리는 동안 다른 경로가 이 결제를 먼저 확정했을 수 있다(예: 19강의 대사). 그럴 때 두 번째 반영이 재고를 또 차감하지 않도록, 잠근 뒤 상태를 다시 본다. 15·17강에서 반복된 "잠금 후 재확인" 패턴이다. 그래도 뚫리면 inventory_movements의 UNIQUE(payment_id, type, sku_id)가 같은 DEDUCT 두 번을 막는다. 확인·원리
  • 성공 효과 7가지를 한 트랜잭션에: 재고, 결제, 주문, 배송, 쿠폰, 알림, 장바구니, 멤버십이 함께 커밋되거나 함께 롤백된다. "주문은 PAID인데 배송 준비 행이 없다" 같은 반쪽 상태가 생기지 않는다. 메시지 큐나 Outbox 없이 모듈러 모놀리스의 로컬 트랜잭션 하나로 일관성을 얻은 것이다. 대가는 TX2가 길어지고, 알림이나 멤버십 평가 중 하나만 실패해도 결제 확정 전체가 롤백된다는 점이다. 해석
  • 장바구니 소비: consumeCart가 주문 수량만큼 장바구니 항목을 빼거나 지우고, 바뀐 것이 있으면 version을 정확히 한 번 올린다(16강, #414→PR #415). 장바구니가 없으면 INSERT ... ON DUPLICATE KEY UPDATE id=id(ensureExists)로 만든 뒤 잠근다. 회원 행 잠금 대신 중복 키 처리를 쓰는 다른 방식의 "없으면 만들기"다. 확인

4-1. 잠금 순서가 체크아웃과 반대다 [해석, 재현하지 않음]

경로 잠금 순서
체크아웃(17강) 회원 → 장바구니 → 장바구니 항목 → SKU → 쿠폰 → 재고
승인 TX2 결제 → 재고(deduct) → 주문·쿠폰 → 장바구니

같은 회원이 탭 A에서 주문 1의 결제 승인을 받는 순간, 탭 B에서 같은 SKU가 담긴 장바구니로 새 체크아웃을 시작했다고 하자. 그러면 이런 순서가 가능하다.

  1. TX2가 재고 X를 잠근다.
  2. 체크아웃이 장바구니를 잠근다.
  3. TX2가 장바구니를 기다린다.
  4. 체크아웃이 재고 X를 기다린다. → 교착

InnoDB는 한쪽을 롤백시킨다. TX2가 희생되면 결제사 승인은 끝났는데 DB는 PROCESSING으로 남는다. 바로 5절의 "고립된 PROCESSING"이다. 사용자 조작 두 개가 밀리초 단위로 겹쳐야 하므로 확률은 낮다. 하지만 결과가 무겁다. TX2에서 장바구니 소비를 재고보다 먼저 잠그거나, 장바구니 소비를 커밋 후 별도 트랜잭션으로 빼는 방안을 검토할 수 있다. 실제로 교착을 재현한 기록은 찾지 못했다.

5. 고립된 PROCESSING — 자동으로 고치지 않기로 한 결정

TX1과 TX2 사이에는 프로세스가 죽을 수 있는 구간이 있다.

#414·PR #415의 고장 주입 실험(일회용 MySQL과 가짜 결제사)은 두 틈을 모두 재현했다. 기록

  • 주문은 PAYMENT_PENDING, 결제는 PROCESSING, 재고 예약은 그대로 남았다.
  • 17강의 만료 스케줄러는 READY만 다룬다. 19강의 대사는 UNKNOWN만 다룬다. 그래서 어느 자동 경로도 이 결제를 집어 가지 않는다.
  • 이 실험은 실제 토스나 운영 장애가 아니다.

두 틈이 DB에서는 똑같이 보인다는 점이 문제의 본질이다. 틈 1이면 예약을 풀어도 되고, 틈 2면 결제를 완료 처리해야 한다. 경과 시간만 보고 "오래됐으니 실패"로 판정하면 틈 2에서 사고가 난다.

2026-10-22 승인된 정책(#417)은 다음과 같다. 기록

  • 1단계(구현됨, PR #450, 2026-10-23 병합): 관리자가 의심 결제를 직접 골라 결제사에 조회만 한다. 주문번호, 결제 키, 금액이 정확히 일치하는 DONE, 확정 실패, 진행 중, 모호하거나 조회 불가를 구분해서 보여 준다. 조회 결과로 상태를 바꾸지는 않는다.
  • 2단계(미구현, 이슈 Open): 확정 DONE이라도 바로 완료 처리하지 않는다. 다음 조건이 갖춰져야 로컬 확정 후보가 된다.
    • 지금 이 결제를 처리 중인 워커가 없다는 운영 펜스(fence)
    • 최신 DB 재검증과 잠금
    • 한 번만 완료되는 원자성
  • 기각한 대안:
    • 조회 오류를 즉시 FAILED로 보고 예약 해제: 실제로 승인됐을 가능성을 없애지 못한다.
    • 승인(POST confirm)을 자동 재시도하거나 재결제: 이중 승인 위험이 있다.
    • DB 행 잠금만으로 펜스 대체: 이미 진행 중인 외부 I/O는 DB 잠금으로 멈출 수 없다.

이 결정의 대가는 분명하다. 자동 복구 대신 운영자의 수동 조사가 남고, 예약 재고가 오래 묶일 수 있다. "추측으로 완료시키지 않는다"를 신뢰성보다 우선한 선택이다.

같이 읽을 자료:

  • It`s all your duck(dkswhdgur246), 결제 승인 요청(PG사 API 호출)과 DB 트랜잭션의 순서간의 장단점을 비교 해보기 (2024-10-20) — 열어서 본문 앞부분을 읽었다. 결제 승인 호출을 트랜잭션에서 분리하는 이유(undo 영역 정리 지연, 커넥션 재사용 불가, 잠금 대기)를 들고, 호출을 트랜잭션 앞에 둘지 뒤에 둘지 장단점을 비교한다. PawCycle은 그 둘의 절충이다. 앞에 짧은 TX1로 선점을 기록하고, 뒤에 TX2로 확정한다. "호출 전에 상태를 남긴다"는 점이 두 틈을 감지할 수 있게 만든다. 아래는 글쓴이가 그린 숙소 예약 결제 프로세스 그림이다.

6. 지금 이 코드가 실제 결제를 하는가 — 환경별 어댑터

TossPaymentAdapter 구현은 프로필과 설정으로 하나만 선택된다. 확인

조건 구현 동작
local-integration 프로필이 아님(운영 포함) TossUnavailablePaymentAdapter isConfigured()=false → 승인 요청 즉시 503
local-integration + test 플래그 꺼짐(기본) TossSandboxPaymentAdapter paymentKey 접두사로 결과 흉내: fail_→실패, unknown_→불명, 그 외 성공
local-integration + pawcycle.toss.test.enabled=true + test_sk_ 키 TossTestPaymentAdapter 토스 테스트 API 실제 호출

즉 현재 저장소 기준으로 운영 환경은 결제를 받지 않는다(fail-closed). 결제사가 구성되지 않았으면 "아마 성공"으로 넘어가지 않고 503으로 막는다. 7강의 "AI가 꺼져 있으면 Null Object"와 비교하면 의도적으로 반대다. AI는 없어도 기능이 동작해야 하지만, 결제는 없으면 멈춰야 한다. 해석 토스 테스트 결제도 "저장소 기준 준비 완료(YES) / 제품 완료(NO)"로 기록되어 있다. 실제 브라우저에서 결제창 → 성공·실패 → 승인 → 새로고침까지 이어지는 여정 검증은 보류 상태다. 기록

샌드박스 어댑터의 접두사 규칙은 테스트에서 세 갈래를 결정적으로 만들기 위한 장치다. 진짜 결제사는 "타임아웃"을 원할 때 만들어 주지 않기 때문이다.
