10강. 회원 배송지 CRUD: 가장 단순한 기능으로 모든 층을 꿰기

이번 강의의 목표

  • 1~9강에서 배운 층(요청 경로, 소유권, 트랜잭션, 엔티티, SQL, 테스트)이 가장 단순한 기능 하나에서 어떻게 맞물리는지 처음부터 끝까지 따라간다.
  • “기본 배송지는 하나만”이라는 규칙을 어디에 두느냐에 따라 설계가 어떻게 달라지는지 비교한다.
  • saveAndFlush가 꼭 필요했던 이유를 9강의 플러시 개념으로 설명한다.
  • 이 단순한 기능에도 남아 있는 동시성 빈틈과 테스트 빈틈을 찾는다.

1. 왜 배송지가 기준점인가

배송지는 회원이 자기 배송지를 만들고, 보고, 고치고, 지우고, 기본으로 지정하는 기능이다. 외부 결제사도, 재고도, 상태 전이도 없다. 그래서 지금까지 배운 층을 잡음 없이 볼 수 있다. 이후 강의에서 체크아웃이나 구독 명령이 복잡해 보일 때, “배송지에서는 이 층이 어떻게 생겼었지?”로 돌아오면 된다.

확인 API는 다섯 개, 구독 배송지까지 여섯 개다.

// member/address/api/MemberAddressController.java (요지)
@GetMapping("/addresses")                         → 200 목록
@PostMapping("/addresses")                        → 201 Created + Location: /api/addresses/{id}
@PatchMapping("/addresses/{addressId}")           → 204 No Content
@DeleteMapping("/addresses/{addressId}")          → 204 No Content
@PutMapping("/addresses/{addressId}/default")     → 204 No Content
@PutMapping("/subscriptions/{subscriptionId}/shipping-address") → 204 (구독 배송지 스냅샷)
  • 생성은 201 + Location 헤더, 본문 없는 성공은 204다. 3강에서 본 HTTP 계약 정리 결정이 여기서도 지켜진다.
  • 모든 메서드의 첫 인자는 @AuthenticationPrincipal AuthenticatedMemberPrincipal principal이다. 8강에서 본 대로 회원 ID는 세션 인증에서만 온다.

2. 물리 ERD: “기본 배송지”를 어디에 저장할까

확인 배송지 테이블은 V13에서 생겼다.

-- V13__add_commerce_supporting_domains.sql (발췌)
CREATE TABLE member_addresses (
    id BIGINT NOT NULL AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    name VARCHAR(100) NOT NULL,              -- "집", "회사" 같은 별칭
    recipient_name VARCHAR(100) NOT NULL,
    recipient_phone VARCHAR(30) NOT NULL,
    postal_code VARCHAR(20) NOT NULL,
    address_line1 VARCHAR(255) NOT NULL,
    address_line2 VARCHAR(255) NULL,
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL,
    CONSTRAINT pk_member_addresses PRIMARY KEY (id),
    CONSTRAINT fk_member_addresses_member FOREIGN KEY (member_id) REFERENCES members (id)
) ...;

ALTER TABLE members
    ADD COLUMN default_address_id BIGINT NULL,
    ADD CONSTRAINT fk_members_default_address
        FOREIGN KEY (default_address_id) REFERENCES member_addresses (id);

눈여겨볼 점은 member_addresses에 is_default 컬럼이 없다는 것이다. 대신 members 행이 기본 배송지를 가리킨다. 두 설계를 나란히 놓으면 차이가 보인다.

  • A의 강점: 규칙이 구조에 있다. 컬럼 하나에는 값이 하나만 들어간다. 그래서 “기본 배송지는 최대 하나”가 어떤 코드 버그로도 깨지지 않는다. 기본을 바꾸는 일도 members 한 행의 UPDATE 하나다. 4강의 PRIMARY KEY (subscription_id)로 pending을 최대 하나로 만든 것과 같은 발상이다. 개수 제약을 조건문이 아니라 스키마 모양으로 표현했다.
  • B의 약점. 플래그 방식은 직관적이지만, 두 요청이 동시에 서로 다른 주소를 기본으로 지정하면 두 행이 모두 1이 될 수 있다. 막으려면 5강에서 본 “생성 컬럼 + UNIQUE”(MySQL에는 부분 인덱스가 없으니)를 쓰거나, 회원 행을 잠가 직렬화해야 한다.
  • A의 약점 1: 같은 회원의 주소라는 보장이 없다. 해석 fk_members_default_address는 default_address_id가 어떤 배송지든 존재하기만 하면 통과시킨다. 회원 7의 기본 배송지로 회원 8의 주소를 가리키는 행도 DB는 막지 못한다.
    • 지금은 애플리케이션이 findByIdAndMemberId로 소유권을 확인한 주소만 지정하므로 실제로 일어나지 않는다(5절).
    • DB로 막으려면 4강의 복합 외래 키 기법을 쓰면 된다. member_addresses에 UNIQUE (id, member_id)를 두고, members의 (default_address_id, id)가 그것을 참조하게 한다. 플랜과 플랜 버전에서 이미 쓴 방법인데 여기서는 쓰지 않았다.
  • A의 약점 2: 순환 참조. member_addresses → members, members → member_addresses로 서로를 가리킨다. 6강에서 본 대로 테이블을 다 만든 뒤 ALTER TABLE로 FK를 나중에 붙였다. 삭제 순서도 신경 써야 한다(6절).

3. JPA 엔티티: 같은 컬럼을 두 번 매핑하는 이유

// member/domain/MemberAddress.java (발췌)
@Entity
@Table(name = "member_addresses")
@Getter
@NoArgsConstructor(access = lombok.AccessLevel.PROTECTED)
public class MemberAddress {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(name = "member_id", nullable = false)
  private Long memberId;                                    // ① 값으로 매핑

  @ManyToOne(fetch = FetchType.LAZY)
  @JoinColumn(name = "member_id", insertable = false, updatable = false)
  private Member member;                                    // ② 같은 컬럼을 연관관계로, 읽기 전용
  ...
}

// member/domain/Member.java (발췌)
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "default_address_id")
private MemberAddress defaultAddress;

public void assignDefaultAddress(MemberAddress address) { this.defaultAddress = address; }
public void clearDefaultAddress() { this.defaultAddress = null; }
  • ① 과 ② 가 같은 member_id 컬럼을 가리킨다. 원리 JPA는 한 컬럼을 두 필드가 동시에 쓰면 어느 값을 INSERT할지 정할 수 없어 시작 시 오류를 낸다. 그래서 ②에 insertable = false, updatable = false를 붙여 읽기 전용으로 만들었다. 쓰기는 ①의 Long memberId로만 한다.
    • 해석 이렇게 하면 배송지를 만들 때 Member 엔티티를 불러오지 않고 ID만으로 저장할 수 있다. 5강에서 본 “다른 애그리거트는 ID로 참조” 원칙을 지키면서, 필요하면 연관관계로 탐색할 길도 남긴 절충이다.
  • @NoArgsConstructor(access = PROTECTED). 원리 JPA(Hibernate)는 조회 결과로 객체를 만들 때와 지연 로딩 프록시를 만들 때 인자 없는 생성자가 필요하다. protected로 두면 JPA는 쓸 수 있지만, 다른 패키지의 코드가 빈 배송지를 함부로 만들 수는 없다.
  • IDENTITY 전략. MySQL의 AUTO_INCREMENT를 쓴다. 원리 ID는 INSERT를 해야 알 수 있으므로, Hibernate는 이 엔티티를 persist하는 즉시 INSERT를 실행한다. 트랜잭션 끝까지 모았다가 보내는 쓰기 지연이 이 엔티티의 INSERT에는 적용되지 않는다.
  • 기본 배송지는 @ManyToOne이다. 회원 한 명이 가리키는 주소는 하나지만, DB 모양은 단순한 외래 키 컬럼이다. @ManyToOne은 그 FK 컬럼을 가장 있는 그대로 매핑하는 방법이다.
  • 상태 변경 메서드가 있다. MemberAddress.update(...), Member.assignDefaultAddress(...). 5강의 구독 V2 엔티티(생성자뿐)와 달리, 여기는 엔티티 메서드 + 변경 감지(dirty checking) 로 수정하는 평범한 JPA 스타일이다. 9강에서 본 “엔티티 상태 전이 → JPA”의 전형이다.

4. HTTP 계약: 검증과 PATCH의 의미

// member/address/api/MemberAddressRequest.java
public record MemberAddressRequest(
    @NotBlank @Size(max = 100) String name,
    @NotBlank @Size(max = 100) String recipientName,
    @NotBlank @Size(max = 30)  String recipientPhone,
    @NotBlank @Size(max = 20)  String postalCode,
    @NotBlank @Size(max = 255) String addressLine1,
    @Size(max = 255)           String addressLine2) {}
  • 검증 길이가 DB 컬럼 길이와 같다. VARCHAR(100)이면 @Size(max = 100)이다. 길이 초과를 DB가 거절하면 SQL 오류(500)가 되지만, 여기서 막으면 필드별 400(VALIDATION_FAILED)이 된다. 8강에서 본 공통 검증 처리기가 이 오류를 필드 이름순으로 정렬해 돌려준다.
    • @Valid가 언제, 누구에 의해 실행되는지는 망나니개발자의 「@Valid와 @Validated를 이용한 유효성 검증의 동작 원리」가 자세히 설명한다. 컨트롤러 인자에 붙은 @Valid는 인자를 만드는 단계(ArgumentResolver)에서 검증되고, 실패하면 MethodArgumentNotValidException이 난다.
  • 해석 전화번호·우편번호 형식은 검사하지 않는다. 길이만 본다. recipientPhone = "아무 글자"도 통과한다. 배송사 연동을 하면 바로 문제가 될 부분이라, 개선 후보다(@Pattern 또는 값 객체).
  • addressLine2만 @NotBlank가 없다. 상세 주소는 비워도 되고, DB도 NULL 허용이다. 검증과 스키마가 서로 맞는다.

PATCH인데 사실은 PUT

수정 API는 @PatchMapping인데 요청은 생성과 같은 MemberAddressRequest다. 필수 필드 다섯 개를 다 보내야 하고, 서비스는 모든 필드를 덮어쓴다.

  • 원리 HTTP 의미로 보면 “리소스 전체를 보낸 값으로 바꾼다”는 PUT이다. PATCH는 “보낸 필드만 바꾼다”는 부분 수정이다.
  • 개발하는 곰돌이의 「실무에서의 PUT과 PATCH에 대한 개인적인 생각 정리」는 이 혼동이 실무에서 흔하다고 짚는다. 교과서 정의(PUT은 전체 대체, 빠진 속성은 null)와 달리, 실무에서는 일부만 수정하는 API도 PUT으로 부르는 경우가 많다는 것이다. 글은 결국 클라이언트 관점에서, 팀이 규칙을 정하고 협의해 쓰면 된다고 결론 낸다.

출처: 개발하는 곰돌이 · 실무에서의 PUT과 PATCH. tistory 그림이라 11월 30일 만료.

  • 해석 PawCycle 안에도 두 방식이 섞여 있다. 3강에서 본 쿠폰 관리 PATCH는 보낸 필드만 병합하고, 명시적 null과 생략을 구분한다(진짜 PATCH). 배송지 PATCH는 전체 대체다. 같은 동사가 다른 의미로 쓰이는 셈이다. 계약 문서에 “배송지 PATCH는 전체 필드 필수”라고 적혀 있는 한 동작에는 문제가 없지만, 일관성의 관점에서는 PUT이 더 정직하다.

5. 소유권: 남의 배송지는 “없다”

// MemberAddressApplicationService (발췌)
MemberAddress address = addresses
    .findByIdAndMemberId(addressId, memberId)                    // SELECT ... WHERE id=? AND member_id=?
    .orElseThrow(() -> notFound("ADDRESS_NOT_FOUND"));           // 404
  • 조회 조건에 회원 ID를 넣는다. “일단 ID로 찾고, 주인인지 검사”가 아니라 처음부터 내 것만 찾는다. 남의 주소는 조회 결과가 비어 있으니 “존재하지 않음”과 구별되지 않는다. 4강 MVP1부터 이어진 “타인 자원은 403이 아니라 404” 원칙이다.
  • 이 방식이 막는 공격을 IDOR(Insecure Direct Object Reference)라 한다. URL의 ID 숫자만 바꿔서 남의 자원에 접근하는 공격이다. 배움을 남기다의 「인증은 있는데 인가가 없었다: IDOR 허점 분석」은 제목 그대로 이 문제를 다룬다. 로그인(인증)은 확인했지만, 그 자원이 그 사람 것인지(인가) 는 확인하지 않은 상황이다.
  • 기록 다른 기능은 한 단계 더 나아갔다. 결제 승인, 리뷰·문의 수정, 회원 쿠폰은 ID와 회원 ID를 함께 PESSIMISTIC_WRITE(FOR UPDATE) 조건에 넣는다. 소유권 확인과 잠금을 한 번에 하는 것이다. 배송지는 소유권만 확인하고 잠그지는 않는다. 이 차이가 7절의 동시성 빈틈으로 이어진다. 인가 전체 구조는 12강에서 본다.

6. 트랜잭션과 플러시: saveAndFlush가 꼭 필요했던 이유

기본 배송지를 바꾸는 코드를 보자.

@Transactional
public void makeDefault(long memberId, long addressId) {
  Member member = requireMember(memberId);
  MemberAddress address = addresses.findByIdAndMemberId(addressId, memberId)
      .orElseThrow(() -> notFound("ADDRESS_NOT_FOUND"));
  member.assignDefaultAddress(address);
  members.saveAndFlush(member);                   // ← 왜 그냥 save가 아니라 saveAndFlush인가
  subscriptionShipping.releaseAddressHolds(memberId);
}

member는 이미 영속 상태라 변경 감지로 커밋 때 UPDATE가 나간다. 그런데도 saveAndFlush로 지금 당장 UPDATE를 보낸다. 이유는 바로 다음 줄에 있다.

// subscription/persistence/SubscriptionShippingPersistenceAdapter.java (발췌)
public void releaseAddressHolds(long memberId) {
  mutation("""
      UPDATE subscription_schedules schedule
      JOIN subscriptions subscription ON subscription.id=schedule.subscription_id
      JOIN members member ON member.id=subscription.member_id
      ...
      SET schedule.status='SCHEDULED', schedule.hold_reason=NULL
      WHERE subscription.member_id=:member
        AND member.default_address_id IS NOT NULL               -- ← DB에서 직접 읽는다
        AND subscription.status='ACTIVE' AND snapshot.subscription_id IS NULL
        AND schedule.status='HELD' AND schedule.hold_reason='MISSING_SHIPPING_ADDRESS'
        AND context.order_id IS NULL
      """).setParameter("member", memberId).executeUpdate();
}

private MutationQuery mutation(String sql) {
  // Preserve JDBC visibility: the address service owns its explicit saveAndFlush calls.
  return entities.unwrap(Session.class).createNativeMutationQuery(sql)
      .setHibernateFlushMode(FlushMode.COMMIT);
}
  • 이 SQL이 하는 일. 4강에서 정기배송 회차가 배송지가 없어 HELD / MISSING_SHIPPING_ADDRESS로 보류될 수 있다고 봤다. 회원이 기본 배송지를 만들거나 지정하면, 그 보류를 즉시 풀어 다음 자동 주문이 처리할 수 있게 한다.
  • 조건이 DB의 members.default_address_id를 직접 읽는다. 그런데 방금 바꾼 기본 배송지는 아직 영속성 컨텍스트(메모리)에만 있을 수 있다.
  • 이 네이티브 UPDATE는 자동 플러시를 하지 않는다. FlushMode.COMMIT은 “커밋 때만 플러시하라”는 뜻이다. 원리 9강에서 본 대로 Hibernate는 보통 JPQL이나 네이티브 쿼리 직전에 관련 변경을 자동으로 플러시한다(AUTO). 이 쿼리는 일부러 그것을 끄고, 플러시 책임을 호출하는 배송지 서비스에 넘겼다. 주석이 그 계약을 적는다. “배송지 서비스가 명시적 saveAndFlush 호출을 소유한다.”
  • saveAndFlush를 빼면? 메모리에서는 기본 배송지가 지정됐는데 DB에는 아직 NULL이다. 그러면 보류 해제 SQL이 default_address_id IS NOT NULL 조건에 걸려 아무것도 풀지 않는다. 사용자는 배송지를 등록했는데 정기배송은 계속 멈춰 있게 된다.
  • 확인 이 순서는 테스트가 지킨다. SubscriptionOrderAutomationServiceIntegrationTests.makeDefaultFlushesBeforeReleasingShippingHolds()가 이 시나리오를 검증한다.
    • 회원의 기본 배송지를 NULL로 만들고, 회차 세 개를 HELD로 둔다.
    • makeDefault를 호출한 뒤 자격이 있는 회차만 SCHEDULED로 풀렸는지 확인한다.
    • 이미 주문이 생긴 회차, 구독 배송지 스냅샷이 있는 회차는 풀리지 않아야 한다.
  • 영속성 컨텍스트와 플러시의 기본은 행복한 개발자의 「Spring jpa save(), saveAndFlush() 제대로 알고 쓰기」와 9강 참고 자료의 준현 · JPA 플러쉬가 설명한다. 두 글 모두 save는 영속성 컨텍스트에만 반영하고 커밋 때 SQL을 보내지만, saveAndFlush는 즉시 SQL을 보낸다는 차이를 다룬다.

설계 평가 해석 배송지 서비스가 정기배송의 회차 상태까지 바꾸는 것은 도메인 간 결합이다. 장점은 “배송지 등록 = 보류 해제”가 한 트랜잭션이라 어긋날 수 없다는 것이다. 단점은 배송지 코드가 정기배송의 보류 규칙을 알아야 하고, 플러시 순서라는 보이지 않는 계약이 생긴다는 것이다. 대안은 배송지 변경 이벤트를 발행하고 정기배송 쪽이 반응하게 하는 것이다(Spring @TransactionalEventListener 등). 그러면 결합은 줄지만 같은 트랜잭션 보장을 어떻게 유지할지 다시 설계해야 한다.

7. 동시성: 단순한 기능에도 빈틈은 있다

확인 배송지 서비스는 회원 행도, 배송지 행도 잠그지 않는다. requireMember는 members.findById(일반 조회)이고, 배송지도 findByIdAndMemberId(일반 조회)다. 동시 요청이 오면 어떻게 될까? 세 가지 상황을 따져 보자. 이 절의 분석은 모두 해석이며, 테스트로 재현된 것은 아니다.

상황 1. 첫 배송지를 두 개 동시에 만든다.

  • 두 트랜잭션 모두 “기본 배송지 없음”을 읽고, 각자 자기 주소를 기본으로 지정한다.
  • 같은 members 행을 UPDATE하므로 둘째는 첫째의 커밋을 기다렸다가 덮어쓴다. 결과적으로 나중에 커밋한 주소가 기본이 된다.
  • 그래도 기본은 여전히 하나다. 2절의 “부모가 가리키기” 설계가 바로 여기서 값을 한다. 플래그 방식이었다면 두 행이 모두 기본이 됐을 것이다.

상황 2. 같은 주소를 동시에 고친다.

  • 두 PATCH가 같은 주소를 읽고 각자 덮어쓴다. 나중 커밋이 먼저 커밋을 통째로 지운다.
  • 이것을 갱신 분실(lost update)이라 한다. @Version 같은 낙관적 잠금이 없어서 생긴다.
  • 배송지는 전체 대체 수정이라 “둘 중 마지막 사람의 의도”가 남는다. 업무적으로 큰 문제는 아닐 수 있다.

상황 3. 기본 배송지 A를 지우는 동시에 A를 다시 기본으로 지정한다. 이것이 가장 흥미롭다.

  • 데이터는 지켜진다. 외래 키가 “없는 주소를 기본으로 지정”하는 것을 DB에서 거절한다. 6강의 “제약은 마지막 방어선”이 여기서 일한다.
  • 사용자 경험은 지켜지지 않는다. 그 거절은 Spring에서 DataIntegrityViolationException이 되고, 배송지 예외 처리기의 catch-all에 걸려 500 MEMBER_ADDRESS_UNAVAILABLE 이 된다. 정상적인 경쟁 상황인데 서버 오류로 보인다.
    • 미확인 이 시나리오를 재현하는 테스트는 저장소에서 찾지 못했다. 위 흐름은 코드와 InnoDB 잠금 동작으로 추론한 것이다.

갱신 분실과 그 해결책은 개인 블로그 두 편이 그림과 함께 잘 설명한다.

  • 주니의 「갱신 분실(lost update) 문제를 어떻게 해결할 수 있을까」는 “매일 자정 재화 1개 지급”과 “사용자의 재화 사용”이 겹치는 실제 상황에서 출발한다. synchronized가 @Transactional과 왜 잘 맞지 않는지 검토하고, 최종적으로 balance = balance + 1 같은 원자적 UPDATE 쿼리를 택한 과정을 적는다. 9강에서 비교한 “읽지 않고 조건부 UPDATE 한 번” 방식과 같은 결론이다.

출처: 주니 · 갱신 분실(lost update) 문제를 어떻게 해결할 수 있을까. tistory 그림이라 11월 30일 만료.

  • 후디의 「JPA의 낙관적 락과 비관적 락을 통해 엔티티에 대한 동시성 제어하기」는 @Version(낙관적)과 @Lock(PESSIMISTIC_WRITE)(비관적)을 JPA 코드로 비교한다. 이 블로그의 그림은 자체 사이트에 있어 만료되지 않는다.

출처: 후디 · JPA의 낙관적 락과 비관적 락

개선 제안 해석 체크아웃이 이미 쓰는 방법(회원 행 잠금)을 배송지의 쓰기 메서드에만 적용하면 세 상황이 모두 정리된다.

java // 제안 예시 — 저장소에 없는 코드다 @Transactional public void makeDefault(long memberId, long addressId) { Member member = members.findByIdForUpdate(memberId) // SELECT ... FOR UPDATE .orElseThrow(() -> notFound("MEMBER_NOT_FOUND")); MemberAddress address = addresses.findByIdAndMemberId(addressId, memberId) .orElseThrow(() -> notFound("ADDRESS_NOT_FOUND")); // T1이 커밋한 뒤라 깨끗한 404 ... }

  • 같은 회원의 배송지 쓰기가 한 줄로 선다. 상황 3의 T2는 처음부터 기다렸다가, T1 커밋 후 주소가 없음을 보고 404를 받는다.
  • 상황 1에서는 둘째 요청이 첫째가 지정한 기본 배송지를 보고 그대로 둔다. “첫 주소가 기본”이라는 의도가 지켜진다.
  • 대가는 같은 회원의 배송지 요청이 동시에 처리되지 못한다는 것뿐이다. 한 사람이 배송지를 초당 여러 번 바꾸는 일은 드물다. 이 경우 비관적 잠금의 비용은 거의 없다.

8. 배송지를 지워도 과거 주문은 안전한가

배송지는 수정·삭제가 자유롭다. 그런데 이미 그 주소로 나간 주문은 어떻게 될까?

  • 확인 주문은 주소를 참조하지 않고 복사한다. 6강에서 본 orders 테이블에는 address_id 같은 FK가 없다. 대신 recipient_name, recipient_phone, postal_code, address_line1, address_line2를 주문 시점의 값으로 갖고 있다. 4강의 스냅샷 원칙이 주소에도 적용된 것이다.
    • 배송지를 고쳐도 과거 주문의 배송 주소는 바뀌지 않는다.
    • 배송지를 지워도 FK 충돌이 없다.
  • 확인 정기배송 배송지도 별도 스냅샷이다. subscription_shipping_snapshots가 구독마다 주소 사본을 갖는다. 계약 문서는 “회원 주소 변경은 기존 구독 스냅샷이나 생성된 주문을 변경하지 않는다”고 적는다. 그래서 6절의 보류 해제 SQL에도 snapshot.subscription_id IS NULL 조건이 있다. 구독 전용 주소가 이미 있는 구독은 회원 기본 주소와 무관하다.
  • 삭제 순서. 지우려는 주소가 기본이면 먼저 members.default_address_id를 NULL로 바꾸고 나서 주소를 지운다. 순서가 반대면 fk_members_default_address가 삭제를 막는다. 2절의 순환 참조가 여기서 순서를 강제한다.
  • 미확인 기본 주소를 지우면 다른 주소가 자동으로 기본이 되지 않는다. 코드는 기본을 비우기만 한다. 이것이 의도된 제품 결정인지는 기록을 찾지 못했다. 그 상태에서 정기결제 회차가 오면 HELD / MISSING_SHIPPING_ADDRESS가 될 수 있다(23강).

9. 테스트: 무엇이 지켜지고 있고, 무엇이 비어 있나

확인 배송지 관련 테스트는 세 곳에 있다.

테스트 지키는 것
MemberAddressApiIntegrationTests (4개) 빈 이름·긴 전화번호의 필드 오류 형식, 없는 주소의 404 계약, 구독 배송지의 옛 요청 형식(이름 없음) 허용
SubscriptionOrderAutomationServiceIntegrationTests 기본 배송지 지정·첫 배송지 생성 시 플러시 후 자격 있는 보류만 해제
SubscriptionShippingWriteProtocolIntegrationTests 등 다른 시나리오의 준비 단계로 배송지 생성·기본 지정을 사용

비어 있는 것도 분명하다.

  • “첫 배송지는 자동으로 기본이 된다”는 규칙을 직접 검증하는 테스트가 없다.
  • “기본 배송지를 지우면 기본이 비워진다”를 검증하는 테스트가 없다.
  • 다른 회원의 주소를 기본으로 지정하려 하면 404인지 검증하는 테스트가 없다. 2절에서 본 대로 DB가 이것을 막지 못하므로, 이 테스트가 사실상 유일한 방어선이어야 한다.
  • 7절의 동시성 시나리오 테스트가 없다.

해석 배송지는 “단순한 CRUD라 테스트할 게 없다”고 여기기 쉬운 기능이다. 하지만 이 기능에도 스키마가 보장하지 않는 규칙(같은 회원 소유)과 도메인 간 부수 효과(보류 해제)가 있다. 테스트는 정확히 그 두 곳에 가장 먼저 필요하다. 지금은 부수 효과 쪽만 지켜지고 있다.

  • 개발하는 곰돌이 · 실무에서의 PUT과 PATCH: 교과서 정의와 실무 관행의 차이
  • 배움을 남기다 · 인증은 있는데 인가가 없었다: IDOR 허점 분석: 소유권 검증이 빠졌을 때
  • 행복한 개발자 · Spring jpa save(), saveAndFlush() 제대로 알고 쓰기: 플러시 시점의 차이
  • 주니 · 갱신 분실 문제를 어떻게 해결할 수 있을까: 원자적 UPDATE로 푼 실제 사례

10강 정리

  • “기본 하나”를 스키마 모양으로 표현했다. members.default_address_id 포인터 하나라서 어떤 버그로도 기본이 둘이 될 수 없다. 대신 FK는 “같은 회원의 주소”까지는 보장하지 않는다. 4강의 복합 FK 기법으로 막을 수 있지만 적용하지 않았다.
  • JPA 매핑
    • 같은 member_id 컬럼을 값(쓰기)과 읽기 전용 연관관계로 두 번 매핑해, ID 참조와 탐색을 함께 얻었다.
    • IDENTITY라서 INSERT가 즉시 나간다.
  • HTTP 계약
    • 검증 길이와 DB 길이가 같다. 형식 검증(전화번호)은 없다.
    • PATCH인데 실제로는 전체 대체(PUT 의미)다. 쿠폰의 진짜 PATCH와 일관되지 않는다.
  • 소유권: 조회 조건에 회원 ID를 넣어 남의 주소는 404다(IDOR 방어). 다만 다른 기능처럼 잠금과 함께 쓰지는 않는다.
  • saveAndFlush의 이유: 바로 뒤의 네이티브 보류 해제 SQL이 FlushMode.COMMIT이라 자동 플러시를 하지 않는다. 기본 배송지 변경이 먼저 DB에 있어야 한다. 테스트가 이 순서를 지킨다.
  • 동시성 빈틈: 잠금이 없어서 다음 세 가지가 생길 수 있다. 회원 행 FOR UPDATE 하나로 정리된다.
    • 첫 기본 배송지가 뒤바뀜
    • 갱신 분실
    • 삭제와 기본 지정이 겹칠 때 FK 위반이 500으로 보임
  • 스냅샷: 주문과 구독은 주소를 복사해 갖는다. 그래서 배송지 수정·삭제가 과거를 바꾸지 않는다.
  • 테스트 빈틈: 기본 배송지 규칙, 타인 주소 기본 지정, 동시성 테스트가 없다.
