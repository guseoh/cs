7강. 시작과 Bean 구성: 애플리케이션은 어떻게 조립되는가

이번 강의의 목표

  • main()에서 SpringApplication.run()이 끝날 때까지 무엇이 어떤 순서로 일어나는지 이해한다.
  • PawCycle이 Spring을 띄우기 전에 유지보수 명령을 먼저 가르는 이유를 안다.
  • 프로필과 조건부 Bean으로 환경마다 다른 구현을 끼우는 방법을 본다. 대상은 토스 어댑터 3종, AI 클라이언트, Redis 캐시, 스케줄러다.
  • ArchUnit으로 패키지·계층 규칙을 테스트로 강제하고, 위반 기준선을 204개에서 5개로 줄여 간 과정을 읽는다.

1강 정정: 1강에서 “동결된 위반 204개(application→api 186개)”라고 했다. 이것은 10월 7일 시점의 숫자다. 확인 기준 커밋(f9ab9f87)의 기준선 파일에는 5개만 남아 있다. 4절에서 그 과정을 본다.

1. main()의 두 갈래

// PawcycleBackendApplication.java (전체)
@SpringBootApplication
public class PawcycleBackendApplication {
  public static void main(String[] args) {
    int catalogImportExitCode = ProductionDemoCatalogImportCommand.runIfRequested(args);
    if (catalogImportExitCode != ProductionDemoCatalogImportCommand.NOT_REQUESTED) {
      if (catalogImportExitCode != 0) System.exit(catalogImportExitCode);
      return;
    }
    int maintenanceExitCode = ProductionAuthSmokeMemberBootstrap.runIfRequested(args);
    if (maintenanceExitCode != ProductionAuthSmokeMemberBootstrap.NOT_REQUESTED) {
      if (maintenanceExitCode != 0) System.exit(maintenanceExitCode);
      return;
    }
    SpringApplication.run(PawcycleBackendApplication.class, args);
  }
}

보통의 Spring Boot 앱은 main에 SpringApplication.run 한 줄뿐이다. PawCycle은 그 앞에 두 개의 관문을 둔다. 운영 카탈로그 적재 명령과, 운영 인증 점검용 회원 생성 명령이다. 같은 jar, 같은 Docker 이미지를 웹 서버로도, 일회성 명령으로도 쓰기 위한 구조다.

왜 Spring을 띄운 뒤가 아니라 전에 가를까? 인증 점검 관문 코드가 답을 준다.

// member/maintenance/ProductionAuthSmokeMemberBootstrap.java (발췌)
private static final List<String> ENFORCED_ARGUMENTS = List.of(
    option("spring.main.web-application-type", "none"),   // 웹 서버를 띄우지 않는다
    option(ENABLED, "true"),
    option("spring.flyway.enabled", "false"),              // 마이그레이션을 돌리지 않는다
    option("spring.main.banner-mode", "off"),
    option("logging.level.root", "OFF"),                   // 로그를 전부 끈다
    option("debug", "false"), option("trace", "false"),
    option("spring.jpa.show-sql", "false"), ...);

static int runIfRequested(String[] args, ...) {
  ResolvedProperty webApplicationType = resolve(args, systemProperties, environment, WEB_APPLICATION_TYPE);
  if (!webApplicationType.present()) return NOT_REQUESTED;   // 지정 안 함 → 평소처럼 웹 서버
  if (webApplicationType.ambiguous()) { error.println(ERROR_MESSAGE); return FAILURE; }
  if ("servlet".equals(...)) return NOT_REQUESTED;
  if (!"none".equals(...)) { ...; return FAILURE; }
  ...
  return application.run(enforceArguments(args));            // 사용자 인자 위에 강제 인자를 덮어씀
}
  • 모드는 컨텍스트를 만들기 전에 정해야 한다. 원리 웹 서버를 띄울지, Flyway를 돌릴지, 로그를 얼마나 남길지는 ApplicationContext를 만드는 과정 자체를 바꾸는 설정이다. 컨텍스트가 이미 뜬 뒤에는 되돌릴 수 없다. 예를 들어 Flyway는 시작 중에 이미 마이그레이션을 실행한다.
  • 강제 인자로 사용자 입력을 덮어쓴다. enforceArguments는 사용자가 넘긴 같은 키(--debug 포함)를 지우고 강제 값을 뒤에 붙인다. 운영자가 실수로 --debug를 붙여도, 회원 생성 과정의 SQL이나 자격 증명이 로그에 찍히지 않는다. 3강의 “로그에 새는 개인정보”와 같은 방어다.
  • 애매하면 실패한다(fail-closed). 같은 키가 서로 다른 값으로 여러 번 오면(ambiguous) 일반 웹 서버로 넘어가지 않고 종료 코드 2로 끝난다. 스크립트는 종료 코드만 보고 성공 여부를 판단할 수 있다.
  • 출력은 PASS 한 줄. 실행 중에는 System.out과 System.err를 버리는 스트림으로 바꿨다가, 성공하면 정해진 PASS 메시지 한 줄만 출력한다.

관문이 보지 못하는 설정 경로

이 설계에는 리뷰에서 지적된 흥미로운 틈이 있었다. 기록 이 관문은 명령줄 인자, 시스템 속성, 일부 환경 변수만 읽는다. 그런데 Spring은 그보다 훨씬 많은 곳에서 설정을 읽는다. SPRING_APPLICATION_JSON, spring.config.additional-location, application.properties 같은 곳이다. 리뷰(PR #70)는 이 점을 짚었다.

  • 관문이 보지 못하는 경로로 “웹 아님 + 활성화”를 주면 관문은 NOT_REQUESTED로 판단한다.
  • 그러면 일반 SpringApplication.run이 실행되는데, Spring은 그 설정을 읽어 유지보수 러너를 켤 수 있다.
  • 결과적으로 관문의 강제 인자(Flyway 끄기, 출력 억제)를 우회할 수 있다는 지적이다.

미확인 이 지적에 대한 수정 커밋은 원본에서 확인하지 못했다. 실제로 재현해 보지도 않았다. 대신 현재 코드에는 두 번째 방어선이 있다.

// member/maintenance/ProductionAuthSmokeMemberMaintenanceConfiguration.java
@Configuration(proxyBeanMethods = false)
@ConditionalOnNotWebApplication                         // 웹 앱이면 아예 등록하지 않는다
@ConditionalOnProperty(prefix = "...", name = "enabled", havingValue = "true")
public class ProductionAuthSmokeMemberMaintenanceConfiguration { ... }

해석 관문을 우회해 일반 웹 서버로 뜨면 @ConditionalOnNotWebApplication이 막는다. 남는 위험은 하나다. 관문이 못 보는 경로로 none 모드가 설정되면, 강제 인자 없이 유지보수 설정이 켜질 수 있다. 교훈은 이렇다. 사전 검사는 프레임워크가 최종적으로 해석할 설정 표면과 같은 범위를 봐야 한다. 다르다면 프레임워크 안쪽에도 같은 조건을 한 번 더 둬야 한다.

2. SpringApplication.run() 안에서 일어나는 일 (깊게)

이제 평소의 웹 서버 경로다. run() 한 줄 안에서 일어나는 일을 PawCycle 설정에 맞춰 펼치면 다음과 같다.

단계마다 PawCycle에서 의미 있는 지점을 짚어 보자.

  • ① 설정 출처의 우선순위. 같은 키가 여러 곳에 있으면 위쪽이 이긴다. application.properties의 spring.datasource.url=${SPRING_DATASOURCE_URL}는 값 자체가 아니라 환경 변수를 가리키는 자리표시자다. 비밀 값은 파일에 두지 않고 컨테이너 환경 변수(2강 compose)로 주입한다.
    • ${PAWCYCLE_TOSS_TEST_ENABLED:false}처럼 : 뒤에 기본값을 둔 키가 많다. 외부 기능은 모두 기본이 꺼짐이라는 원칙(4강)이 여기서 구현된다.
    • 반대로 SPRING_DATASOURCE_URL처럼 기본값이 없는 키는 값이 없으면 시작이 실패한다. DB 없이 뜨는 서버는 의미가 없으니, 일찍 실패하는 편이 낫다.
  • ③ 등록 순서가 조건 평가를 바꾼다. 원리 Spring Boot는 우리 코드의 @Component를 먼저 스캔한다. DataSourceAutoConfiguration 같은 자동 구성은 그 뒤에 처리한다. 그래서 자동 구성은 “사용자가 이미 같은 타입의 Bean을 만들었으면 물러난다”(@ConditionalOnMissingBean)가 가능하다. 3절에서 이 순서가 실제로 중요해진다.
  • ④ 생성자 주입과 순환 참조. 원리 Spring Boot 2.6부터 순환 참조는 기본적으로 금지다. 생성자 주입만 쓰면 A가 B를, B가 A를 필요로 할 때 둘 다 만들 수 없어 시작이 실패한다. 이것은 결함이 아니라 설계 냄새를 시작 시점에 드러내는 장치다.
  • ⑤ Flyway가 JPA보다 먼저다. 원리 Spring Boot는 JPA의 EntityManagerFactory가 Flyway Bean에 의존하도록 순서를 잡아 준다. 그래서 마이그레이션이 끝난 스키마를 대상으로 ddl-auto=validate가 엔티티와 테이블을 대조한다. 6강의 “JPA는 검사만 한다”가 바로 이 지점이다. 마이그레이션을 빠뜨린 배포는 트래픽을 받기 전에 실패한다.
  • ⑥ 준비 완료. Tomcat이 8080을 연 뒤에야 2강의 헬스체크(/api/products)가 통과한다. compose의 depends_on: service_healthy가 proxy를 이때까지 기다리게 한다.

3. 프로필과 조건부 Bean: 환경마다 다른 구현 끼우기

토스 결제 어댑터 3종

5강까지 본 결제 흐름은 TossPaymentAdapter라는 인터페이스에만 의존한다. 실제 구현은 세 개이고, 환경에 따라 정확히 하나만 Bean으로 등록된다.

// commerce/payment/infrastructure/toss/
@Component @Profile("local-integration")
@ConditionalOnProperty(name = "pawcycle.toss.test.enabled", havingValue = "true")
class TossTestPaymentAdapter implements TossPaymentAdapter { ... }        // 토스 테스트 API를 실제로 호출

@Component @Profile("local-integration")
@ConditionalOnProperty(name = "pawcycle.toss.test.enabled", havingValue = "false", matchIfMissing = true)
class TossSandboxPaymentAdapter implements TossPaymentAdapter {           // 외부 호출 없는 가짜
  public ConfirmResult confirm(String paymentKey, ...) {
    if (paymentKey.startsWith("unknown_")) return new ConfirmResult("UNKNOWN", "NO_RESPONSE");
    if (paymentKey.startsWith("fail_"))    return new ConfirmResult("FAILED", "ABORTED");
    return new ConfirmResult("SUCCEEDED", "DONE");
  }
}

@Component @Profile("!local-integration")
class TossUnavailablePaymentAdapter implements TossPaymentAdapter {
  public boolean isConfigured() { return false; }
  public ConfirmResult confirm(...) {
    throw new CommerceException(503, "PAYMENT_PROVIDER_UNAVAILABLE", "...");
  }
}

두 조건을 표로 놓으면 빈칸이 없다.

프로필 pawcycle.toss.test.enabled 등록되는 Bean 동작
local-integration true Test 토스 테스트 API 호출(test_sk_ 키만, 라이브 키 거부)
local-integration false 또는 없음 Sandbox 결제 키 접두어로 성공·실패·미확정을 흉내
그 외 (운영 포함) 무엇이든 Unavailable 503으로 실패
  • 정확히 하나가 보장된다. 첫 두 행은 같은 속성의 true와 false/없음으로 배타적이다. 세 번째 행은 프로필 부정(!)으로 앞의 둘과 배타적이다. 어떤 조합에서도 Bean이 0개나 2개가 되지 않는다. 0개나 2개면 주입 지점에서 시작이 실패한다.
  • 운영에서는 속성을 켜도 소용없다. @Profile이 바깥 관문이기 때문이다. 운영 환경에 누가 PAWCYCLE_TOSS_TEST_ENABLED=true를 넣어도, local-integration 프로필이 아니면 Test·Sandbox 어댑터는 후보조차 되지 않는다. 두 조건을 겹쳐서 쓴 이유가 이것이다.
  • 기본값이 “실패”다. 아무것도 설정하지 않은 환경의 결제는 가짜 성공이 아니라 503이다. 4강의 “결제사가 없으면 가짜 결제 성공을 만들지 않는다”(fail-closed)가 Bean 구성으로 구현된 것이다.
  • 확인 정기결제(TossSandboxBillingAdapter / TossUnavailableBillingAdapter)와 환불(TossSandboxRefundAdapter / TossUnavailableRefundAdapter) 어댑터도 같은 구조다.
  • Sandbox의 설계가 영리하다. 결제 키 접두어(unknown_, fail_)만으로 UNKNOWN 같은 재현하기 어려운 상태를 만들 수 있다. 3강의 PROCESSING·UNKNOWN 처리를 로컬에서 시험할 수 있게 해 주는 테스트 더블이다.

AI 클라이언트: 진짜 Bean과 “아무것도 안 하는” Bean

AI 기능도 기본이 꺼짐이지만, 구현 방식이 다르다.

// catalog/product/application/ProductCommerceAiConfiguration.java (발췌)
@Configuration(proxyBeanMethods = false)
class ProductCommerceAiConfiguration {
  @Bean
  @ConditionalOnProperty(prefix = "pawcycle.ai.review-summary", name = "enabled", havingValue = "true")
  ReviewSummaryAiClient reviewSummaryClient(@Value("${spring.ai.openai.api-key:}") String key, ...) {
    ChatClient client = client(key, model);       // 키·모델이 비었으면 IllegalStateException
    return reviews -> client.prompt().system("...의료나 치료 주장을 하지 마세요.").user(...).call().content();
  }

  @Bean
  @ConditionalOnMissingBean(ReviewSummaryAiClient.class)
  ReviewSummaryAiClient disabledReviewSummaryClient() {
    return reviews -> null;                        // 꺼졌을 때: 요약 없음
  }
}
  • 널 객체 패턴. 꺼졌을 때도 ReviewSummaryAiClient Bean은 항상 존재한다. 다만 null을 돌려줄 뿐이다. 호출하는 쪽은 “Bean이 있는가”를 검사하지 않고, 결과가 없을 때의 처리만 하면 된다. 토스 어댑터의 Unavailable도 같은 계열의 패턴이다.
  • 켜졌는데 키가 없으면 시작이 실패한다. client()가 키나 모델이 비어 있으면 예외를 던진다. 해석 첫 요청이 올 때 터지는 것보다 배포 직후 시작 단계에서 터지는 편이 훨씬 빨리 발견된다.
  • 스타터를 쓰지 않았다. 확인 build.gradle은 spring-ai-openai와 spring-ai-client-chat 모듈만 쓴다. 자동 구성이 들어 있는 스타터는 쓰지 않는다. 해석 스타터를 쓰면 API 키가 있을 때 OpenAI 모델 Bean이 자동으로 만들어진다. PawCycle은 기능별 플래그로 명시적으로 켤 때만 모델 클라이언트를 직접 만드는 쪽을 택했다. 4강의 “AI는 기본 꺼짐, 비용 승인은 별도”와 같은 원칙이다.

그런데 여기에 짚을 점이 하나 있다. Spring Boot 공식 문서 「Creating Your Own Auto-configuration」은 이렇게 경고한다.

이 조건들은 지금까지 처리된 것을 기준으로 평가되므로 Bean 정의가 추가되는 순서에 매우 주의해야 한다. 그래서 @ConditionalOnBean과 @ConditionalOnMissingBean은 자동 구성 클래스에서만 쓰기를 권한다. (요지)

  • 해석 PawCycle의 AI 설정은 일반 @Configuration에서 @ConditionalOnMissingBean을 쓴다. 지금은 같은 클래스 안에서 활성 Bean이 먼저 선언되어 있어 의도대로 동작한다.
  • 하지만 누군가 메서드 순서를 바꾸거나, 다른 설정 클래스에 활성 Bean을 옮기면 조용히 두 Bean이 생기거나 비활성 Bean만 남을 수 있다. 정확히 어느 쪽이 될지는 처리 순서에 달려 있어서, 겉으로는 잘 드러나지 않는다.

개선 제안 해석 같은 프로젝트의 토스 Sandbox 어댑터가 이미 더 안전한 방법을 쓰고 있다. 비활성 Bean에도 속성 조건을 반대로 거는 것이다.

java // 제안 예시 — 저장소에 없는 코드다 @Bean @ConditionalOnProperty(prefix = "pawcycle.ai.review-summary", name = "enabled", havingValue = "false", matchIfMissing = true) ReviewSummaryAiClient disabledReviewSummaryClient() { return reviews -> null; }

두 Bean이 같은 속성의 true / false·없음으로 배타적이 되어 등록 순서와 무관해진다. 프로젝트 안에서 같은 문제를 두 방식으로 푸는 불일치도 사라진다.

Redis 캐시와 스케줄러: 조건부 Bean이 아닌 것과 맞는 것

  • Redis 캐시는 Bean이 아니라 값으로 끈다. 확인 ProductListCache는 항상 Bean으로 등록되고, @Value("${pawcycle.catalog.product-list-cache.enabled:false}") boolean enabled를 받아 실행 중에 분기한다.
    • Redis 스타터는 클래스패스에 있으므로 연결 팩토리는 자동 구성으로 만들어진다. 다만 Lettuce 클라이언트는 처음 쓸 때 연결하므로, 캐시가 꺼져 있으면 실제 연결은 일어나지 않는다. 원리
    • 헬스체크도 같은 플래그(management.health.redis.enabled=${PAWCYCLE_PRODUCT_LIST_CACHE_ENABLED:false})로 묶었다. Redis를 쓰지 않는 환경에서 Redis가 없다는 이유로 헬스체크가 실패하는 일을 막는다. 2강의 “헬스체크가 무엇을 증명하는가”와 같은 고민이다.
    • 해석 조건부 Bean으로 끄면 Bean이 아예 없으니 주입하는 쪽마다 분기가 필요하다. 값으로 끄면 캐시 클래스 한 곳에서만 분기하면 된다. 캐시처럼 “있으면 빠르고 없어도 맞는” 기능에는 값 플래그가 더 단순하다.
  • 스케줄러는 조건부 Bean이 맞다. SubscriptionOrderAutomationTrigger는 @ConditionalOnProperty로 켜질 때만 Bean이 된다. Bean이 없으면 @Scheduled 메서드도 등록되지 않는다. 운영 DB에 스스로 주문을 만드는 기능이니 존재 자체를 설정으로 통제하는 것이 맞다(4강).

4. 패키지·계층 규칙과 ArchUnit

규칙을 테스트로 강제한다

계층 구조(api → application → domain, persistence, infrastructure)는 문서로만 정하면 금방 무너진다. 급할 때 컨트롤러에서 저장소를 바로 부르는 한 줄이 쌓이기 때문이다. ArchUnit은 컴파일된 바이트코드를 읽어 클래스 사이의 의존을 그래프로 만들고, 규칙 위반을 테스트 실패로 만든다.

이 velog 글 「아키텍처 컨벤션 검증을 위해 ArchUnit을 활용한 아키텍처 테스트 작성하기」가 입문용으로 좋다. 글은 ArchUnit이 공식적으로 제공하는 일곱 가지 검사(패키지·클래스 종속성, 포함, 상속, 어노테이션, 레이어, 순환)를 소개한다. 그리고 한 사이드 프로젝트의 레이어 규칙을 실제 테스트로 옮겨 보인다.

출처: velog @langoustine · 아키텍처 컨벤션 검증을 위해 ArchUnit을 활용한 아키텍처 테스트 작성하기. 그림은 “아키텍처 구조를 살펴볼게요” 문장 바로 뒤에 있는 것으로 확인했고, 그림 내부를 확대해 읽지는 않았다.

PawCycle의 규칙은 테스트 안의 검증용 예제에서 한눈에 보인다.

// src/test/java/.../architecture/BackendArchitectureTests.java (발췌)
assertThat(rules(ROOT + "example.application.UseCase", "org.springframework.jdbc.core.JdbcTemplate", false))
    .containsExactly("application-sql");        // 애플리케이션 계층은 SQL 도구를 직접 쓰지 않는다
assertThat(rules(ROOT + "example.application.UseCase", ROOT + "example.api.Dto", false))
    .containsExactly("application-api");        // 애플리케이션은 HTTP DTO를 모른다
assertThat(rules(ROOT + "example.domain.Model", ROOT + "example.infrastructure.Provider", false))
    .containsExactly("domain-adapter");         // 도메인은 외부 어댑터를 모른다
assertThat(rules(ROOT + "example.api.Controller", ROOT + "example.persistence.Store", false))
    .containsExactly("api-persistence");        // 컨트롤러는 저장소를 직접 부르지 않는다
assertThat(rules(ROOT + "example.persistence.Store", ROOT + "example.api.Dto", false))
    .containsExactly("persistence-api");        // 저장소도 HTTP DTO를 모른다
assertThat(rules(ROOT + "example.api.Controller", ROOT + "example.domain.Entity", true))
    .containsExactly("api-storage");            // 컨트롤러가 JPA 엔티티를 응답으로 내보내지 않는다
assertThat(rules(ROOT + "example.application.UseCase", "com.querydsl.jpa.impl.JPAQueryFactory", false))
    .containsExactly("querydsl-boundary");      // Querydsl은 영속성 계층 안에서만
assertThat(rules(ROOT + "example.persistence.Store", "jakarta.persistence.EntityManager", false))
    .isEmpty();                                 // 저장소가 EntityManager를 쓰는 것은 허용
  • api-storage의 의미. 컨트롤러가 JPA 엔티티를 그대로 JSON으로 내보내면 위험이 셋 생긴다. 내부 컬럼이 API에 새고, 지연 로딩이 직렬화 중에 쿼리를 날리고, 엔티티를 바꾸면 API가 깨진다. 1강의 spring.jpa.open-in-view=false와 짝을 이루는 규칙이다. OSIV가 꺼져 있으면 트랜잭션 밖 지연 로딩은 예외로 끝난다(8·9강).
  • application-api의 의미. 애플리케이션 서비스가 CreateSubscriptionRequest 같은 HTTP DTO를 받으면, HTTP를 바꿀 때 업무 로직까지 바뀐다. 확인 그래서 HTTP 입력은 API 계층의 매퍼가 중립 커맨드로 바꾸고, 응답은 각 응답 DTO의 static from(View)가 완성된 View에서 만든다(PR #394 등). 별도의 거대한 공통 매퍼는 만들지 않았다.

기준선 래칫: 204개에서 5개로

기존 코드에 이미 위반이 수백 개 있다면 규칙을 어떻게 도입할까? 한 번에 다 고치면 거대한 위험한 PR이 된다. PawCycle은 기준선 동결을 택했다.

// BackendArchitectureTests.productionDependenciesMustNotAddLegacyViolations (발췌)
JavaClasses classes = new ClassFileImporter().importPath(Path.of("build/classes/java/main"));
Set<String> actual = violations(classes);
Set<String> baseline = ... readAllLines("src/test/resources/architecture/legacy-dependencies.txt");
Set<String> added = actual - baseline;      // 새로 생긴 위반
Set<String> removed = baseline - actual;    // 고쳐졌는데 기준선에 남은 항목
assertThat(added).as("New architecture violations; see %s", report).isEmpty();
assertThat(removed).as("Remove resolved entries from the baseline").isEmpty();
  • 양방향 비교가 핵심이다.
    • 새 위반이 생기면 실패한다. 빚이 늘지 않는다.
    • 고친 위반이 기준선에 남아 있어도 실패한다. 고쳤으면 기준선에서 지워야 하니, 기준선은 줄어들기만 한다.
    • 이렇게 한쪽으로만 움직이는 장치를 래칫(ratchet, 톱니바퀴 멈춤쇠)이라 한다.
  • 기준선은 자동으로 갱신하지 않는다. 주석이 못 박는다. “진단은 체크인된 기준선을 절대 갱신하지 않는다. CI에서도.” 현재 위반은 build/reports에 보고서로만 쓴다. 자동 갱신을 허용하면 새 위반이 슬쩍 기준선에 들어가 래칫이 무력해진다.
  • 운영 바이트코드만 본다. build/classes/java/main만 읽는다. 테스트 픽스처나 라이브러리는 규칙의 대상이 아니다.

확인 기준선 파일의 줄 수를 커밋마다 세어 보면, 이 래칫이 실제로 돌아간 기록이 남아 있다.

그래프에서 읽을 점이 세 가지다.

  • 처음에 늘어난 것은 빚이 늘어서가 아니다. 기록 131 → 145 → 204의 증가는 패키지 정규화 PR(#343, #345)에서 생겼다. 기능 최상위에 평평하게 놓여 있던 클래스를 api/application/persistence 같은 계층 패키지로 옮겼더니, 원래 있던 의존이 이제야 계층 위반으로 보이게 됐다.
    • 이 결정 기록은 이를 새 결합이 아니라 재분류(RECLASSIFIED)로 구분하고, “숫자가 늘어도 결합을 새로 만든 것과 같지 않다”고 적는다.
    • 반대로 “패키지 이동만으로 결합이 해결됐다고 하지 않는다”고도 적는다. 측정 도구의 숫자와 실제 품질을 구분하는 태도다.
  • 줄어든 것은 실제 경계 분리 작업이다. 10월 14–20일의 PR 15개가 HTTP DTO를 애플리케이션과 저장소에서 떼어 냈다. 영역별로 쿠폰, 카탈로그 관리, 장바구니, 주문, 구독, 체크아웃을 나눠 진행했다. 한 번에 204개를 고치는 대신, 응답 목적과 되돌리기 범위가 같은 단위로 나눴다.
  • 남은 5개는 모두 runtime-maintenance다.
runtime-maintenance | PawcycleBackendApplication -> catalog.maintenance.ProductionDemoCatalogImportCommand
runtime-maintenance | PawcycleBackendApplication -> member.maintenance.ProductionAuthSmokeMemberBootstrap
runtime-maintenance | catalog.application.CustomerCatalogImportService -> catalog.maintenance.persistence.(3개)

첫 두 줄은 **1절에서 본 `main()`의 두 관문** 그 자체다. 운영 코드가 유지보수 도구에 의존하면 안 된다는 규칙이 있는데, 진입점이 유지보수 명령을 부르니 위반으로 잡힌다.
- **[해석]** 이것은 “같은 jar를 웹 서버와 일회성 명령으로 쓴다”는 1절의 설계 결정이 **의도적으로 지불한 비용**이다. 남겨 둔 것이 실수가 아니라 선택이라는 점을 설명할 수 있어야 한다.
- 없애려면 유지보수 명령을 별도 진입점(다른 `main` 클래스나 별도 실행 모듈)으로 분리해야 한다. 대신 이미지나 실행 스크립트가 늘어난다.

ArchUnit의 한계. 기록 결정 기록은 이 가드가 “리플렉션, SQL 의미, 트랜잭션 정합성을 증명하지 않는다”고 명시한다. 문자열로 짠 SQL이 다른 테이블을 건드리거나, 리플렉션으로 클래스를 부르는 의존은 바이트코드 그래프에 나타나지 않는다. ArchUnit은 구조를 지키는 도구이지 동작을 증명하는 도구가 아니다. 동작은 3강에서 본 MySQL 통합 테스트들의 몫이다.

7강 정리

  • main()의 두 갈래: 같은 jar를 웹 서버와 일회성 명령으로 쓴다.
    • 모드(웹 여부, Flyway, 로그)는 컨텍스트를 만들기 전에 정해야 하므로 관문이 run() 앞에 있다.
    • 강제 인자로 사용자 입력을 덮어쓰고, 애매하면 종료 코드 2로 실패한다.
    • 관문이 보는 설정 범위와 Spring이 해석하는 범위가 다르면 틈이 생긴다. 그래서 설정 클래스에 두 번째 조건(@ConditionalOnNotWebApplication)을 뒀다.
  • run()의 순서: 환경(우선순위) → 컨텍스트 → Bean 정의·조건 평가(스캔 먼저, 자동 구성 나중) → 생성자 주입 → Flyway → JPA validate → Tomcat → 준비 완료.
  • 조건부 Bean
    • 토스 어댑터 3종: 프로필 × 속성으로 정확히 하나가 등록되고, 기본값은 503(fail-closed)이다.
    • AI: 널 객체 패턴을 쓰고, 켰는데 키가 없으면 시작 단계에서 실패한다. 스타터 대신 모듈만 쓴다.
    • 일반 @Configuration의 @ConditionalOnMissingBean은 등록 순서에 의존한다. 반대 조건 속성으로 바꾸는 것이 더 안전하다.
    • Redis 캐시는 값 플래그로, 스케줄러는 조건부 Bean으로 끈다.
  • ArchUnit 래칫
    • 새 위반도 실패, 고쳤는데 남은 기준선 항목도 실패라서 기준선은 줄기만 한다.
    • 131 → 204(재분류) → 5(10/20).
    • 남은 5개는 main()의 유지보수 관문이 의도적으로 지불한 비용이다.
