8강. 요청 하나의 처리 경로: Tomcat에서 트랜잭션까지

이번 강의의 목표

  • HTTP 요청 하나가 Tomcat 스레드 → 서블릿 필터 → Spring Security → DispatcherServlet → 컨트롤러 → 서비스(프록시·트랜잭션)로 가는 길을 그릴 수 있다.
  • 각 층에서 실패가 생기면 어디서 응답으로 바뀌는지 설명할 수 있다. 특히 보안 필터에서 생긴 실패가 @RestControllerAdvice에 잡히지 않는 이유를 이해한다.
  • thread-per-request 모델과 ThreadLocal, 프록시가 끼어드는 지점을 PawCycle 코드 위에서 확인한다.

표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 원리 일반 원리 · 미확인

1. 요청 하나가 지나가는 길

아래 그림은 브라우저 요청이 Nginx를 지나 Spring Boot 컨테이너에 들어온 뒤의 경로다. 위쪽 점선 상자는 서블릿 필터 영역(Spring MVC 바깥), 아래쪽 점선 상자는 DispatcherServlet 이후의 Spring MVC 영역이다.

그림의 핵심은 점선 상자 두 개의 경계다. 위쪽 상자에서 생긴 실패는 Spring MVC의 @RestControllerAdvice가 볼 수 없다. 그래서 PawCycle에는 오류 처리기가 두 계열로 나뉘어 있다. 3절과 6절에서 이유를 본다.

2. Tomcat: 요청 하나 = 스레드 하나 (깊게)

원리 Spring MVC는 요청당 스레드(thread-per-request) 모델이다.

  • Tomcat의 NIO 커넥터는 소수의 스레드로 소켓 연결을 받아(acceptor) 데이터가 도착했는지 감시한다(poller).
  • 요청이 완성되면 워커 스레드 풀(기본 최대 200개)에서 스레드 하나를 꺼내 맡긴다.
  • 그 스레드는 필터, 컨트롤러, 서비스, DB 대기까지 응답을 다 쓸 때까지 그 요청만 처리한다. DB가 느리면 스레드는 그동안 블록된 채 묶여 있다.
  • 3강에서 본 “커넥션 풀 대기 117개”와 2강의 pids_limit: 256(= 스레드 상한)이 모두 이 모델에서 나온다. 느린 요청이 많아지면 스레드가 고갈되고, 새 요청은 큐에서 기다린다.

이 모델에서 생기는 미묘한 함정이 ThreadLocal 이다. PawCycle의 첫 필터가 그것을 다룬다.

// common/web/RequestCorrelationFilter.java
@Component
public class RequestCorrelationFilter extends OncePerRequestFilter {
  static final String REQUEST_ID_HEADER = "X-Request-ID";
  private static final Pattern SAFE_REQUEST_ID = Pattern.compile("[A-Za-z0-9._-]{1,64}");

  protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) ... {
    MDC.put("requestId", requestId(request));
    try {
      filterChain.doFilter(request, response);
    } finally {
      MDC.remove("requestId");            // 반드시 지운다
    }
  }

  private String requestId(HttpServletRequest request) {
    String candidate = request.getHeader(REQUEST_ID_HEADER);
    if (candidate != null && SAFE_REQUEST_ID.matcher(candidate).matches()) return candidate;
    return UUID.randomUUID().toString();
  }
}
  • MDC는 ThreadLocal이다. 원리 MDC(Mapped Diagnostic Context)는 로그에 요청 ID 같은 값을 붙이려고 현재 스레드에 값을 저장한다. 그런데 Tomcat 스레드는 풀에서 재사용된다. finally에서 지우지 않으면 다음 요청이 같은 스레드를 받았을 때 이전 요청의 ID가 남아 로그가 엉뚱한 요청에 묶인다. try/finally는 예외가 나도 정리를 보장하는 관용구다.
  • 헤더 값을 검증한다. 클라이언트가 보낸 X-Request-ID를 그대로 로그에 넣으면, 줄바꿈 문자를 넣어 가짜 로그 줄을 끼워 넣는 공격(로그 인젝션)이 가능하다. 영숫자와 ._- 64자 이내만 받는 정규식이 이를 막는다.
  • OncePerRequestFilter. 서블릿은 내부 포워드나 오류 페이지 디스패치에서 같은 요청에 필터를 다시 태울 수 있다. 이 부모 클래스는 요청당 한 번만 실행되도록 보장한다.

그런데 이 필터를 실제 배치와 함께 보면 세 가지 빈틈이 보인다.

  • 확인 실행 순서를 지정하지 않았다. @Order도 FilterRegistrationBean도 없다.
    • 원리 Spring Boot는 순서 없는 Filter Bean을 가장 낮은 우선순위로 등록한다. Spring Security 필터 체인은 기본 순서 -100으로 그보다 앞에 선다.
    • 해석 따라서 인증 실패(401)나 CSRF 거절(403)처럼 Security가 직접 응답하는 경우, 요청 ID 필터는 실행되지도 않는다. 보안 거절이야말로 추적하고 싶은 요청인데, 거기에 ID가 없다.
  • 확인 로그 패턴에 requestId가 없다. application.properties와 리소스 어디에도 %X{requestId} 같은 로그 패턴이나 logback 설정이 없다.
    • 해석 Spring Boot 기본 로그 형식은 MDC 값을 출력하지 않으므로, 지금은 MDC에 넣은 ID가 로그에 찍히지 않을 가능성이 높다.
    • 미확인 다른 경로(구조화 로그 설정 등)로 출력되는지는 27강(관측)에서 실제 로그로 확인한다.
  • 확인 Nginx가 ID를 만들거나 넘기지 않는다. 2강의 Nginx 설정에는 X-Request-ID 관련 지시어가 없다. 그래서 백엔드가 매번 새 UUID를 만들고, Nginx 접근 로그와 백엔드 로그를 같은 요청으로 묶을 수 없다. 응답 헤더로 돌려주지도 않아서, 프론트나 사용자가 오류 문의 때 ID를 알려 줄 수도 없다.

개선 제안 해석 세 가지를 함께 고쳐야 효과가 난다. 1. Nginx에서 proxy_set_header X-Request-ID $request_id;로 입구에서 ID를 만들어 넘기고, 접근 로그에도 같은 값을 남긴다. 2. 필터에 @Order(Ordered.HIGHEST_PRECEDENCE)를 붙여 Security보다 먼저 실행한다. 응답 헤더에도 같은 ID를 쓴다. 3. 로그 패턴에 %X{requestId}를 넣는다.

3. Spring Security 필터 체인

구조: 서블릿 필터 하나가 Spring 안의 체인을 부른다

Tomcat은 Spring Bean을 모른다. 그런데 Security 필터들은 Spring Bean이다. 이 둘을 잇는 구조를 Spring Security 공식 문서의 그림으로 보자. 아래 그림은 Spring Security 공식 저장소의 원본 이미지다.

공식 문서 「Spring Security · Architecture」의 설명에 따라 그림을 읽으면 이렇다.

  • DelegatingFilterProxy: Tomcat에 등록되는 진짜 서블릿 필터다. 스스로는 아무것도 하지 않고, Spring 컨테이너에서 Bean을 찾아 일을 위임한다. 서블릿 컨테이너와 Spring 컨테이너 사이의 다리다.
  • FilterChainProxy: 위임받는 Spring Bean이다. 요청 URL에 맞는 SecurityFilterChain을 고른다. 체인이 여러 개일 수 있어서다.
    • 확인 PawCycle도 체인이 두 개다. 메인 체인과, 성능 측정용 SubscriptionBurstMeasurementSecurityConfiguration의 @Order(1) 체인이다.
  • SecurityFilterChain: 실제 보안 필터들의 목록이다. 1강에서 본 SecurityConfig의 http.csrf(...).authorizeHttpRequests(...)...build()가 바로 이 체인을 만든다.

우리 요청이 체인 안에서 겪는 일을 순서대로 보자.

  1. 세션에서 인증 복원. HttpSessionSecurityContextRepository가 JSESSIONID 쿠키로 서버 세션을 찾고, 거기 저장된 인증 정보(SecurityContext)를 꺼내 현재 스레드에 둔다. 이것도 ThreadLocal이고, 요청이 끝나면 Security가 비운다.
  2. CSRF 검사. POST이므로 X-CSRF-TOKEN 헤더 값이 세션에 저장된 토큰(HttpSessionCsrfTokenRepository)과 같아야 한다. 다르거나 없으면 403이다. 왜 쿠키가 아니라 헤더인지는 11강에서 깊게 본다.
  3. 인가 규칙. 규칙은 위에서부터 처음 맞는 하나가 적용된다.
// common/security/SecurityConfig.java (인가 규칙 발췌)
.requestMatchers(EndpointRequest.to("health", "prometheus")).permitAll()
.requestMatchers(HttpMethod.GET, "/api/products/*/reviews/me").authenticated()   // ①
.requestMatchers(HttpMethod.GET, "/api/products", "/api/products/**", ...).permitAll() // ②
...
.requestMatchers(HttpMethod.POST, "/api/auth/login").permitAll()
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/**").authenticated()                                       // 우리 요청
.anyRequest().denyAll()                                                           // ③
  • ①이 ②보다 위에 있어야 한다. /api/products/7/reviews/me(내 리뷰)는 /api/products/**(공개 상품)에도 맞는다. 순서가 바뀌면 내 리뷰 조회가 비로그인에게 열린다. 구체적인 규칙을 먼저, 넓은 규칙을 나중에 두는 것이 원칙이다.
  • ③ 기본 거부. 어느 규칙에도 맞지 않는 경로는 전부 거부한다. 새 엔드포인트를 만들고 규칙 추가를 잊으면, 열리는 대신 막힌다. 3강의 fail-closed다.
  • 우리 요청은 /api/**에 맞고 인증돼 있으니 통과한다.

실패하면: 컨트롤러 어드바이스는 여기까지 오지 못한다

인증이 없거나 CSRF가 틀리면 어떻게 될까? 공식 문서의 ExceptionTranslationFilter 그림이 그 흐름을 보여 준다.

  • 인증이 없어서 막히면 AuthenticationEntryPoint가, 인증은 됐는데 권한이 없거나 CSRF가 틀려 막히면 AccessDeniedHandler가 응답을 만든다.
  • 이 모든 일은 필터 안에서 끝난다. 요청은 DispatcherServlet에 도달하지 않는다.

망나니개발자의 「필터(Filter) vs 인터셉터(Interceptor) 차이 및 용도」가 이 차이를 정확히 짚는다. 필터는 디스패처 서블릿 앞의 서블릿 영역에서 관리되기 때문에, @ControllerAdvice·@ExceptionHandler 같은 스프링의 예외 처리를 받을 수 없다는 것이다. (원문의 흐름 그림은 서명된 임시 이미지 주소라 시간이 지나면 깨지므로 링크로만 둔다.)

그래서 PawCycle은 Security용 처리기를 따로 만들되, 응답 모양은 MVC 쪽과 똑같이 맞췄다.

// common/security/ApiAccessDeniedHandler.java
public void handle(HttpServletRequest request, HttpServletResponse response, AccessDeniedException e) ... {
  if (e instanceof CsrfException) {
    errorWriter.write(response, 403, "CSRF_INVALID", "CSRF 토큰이 유효하지 않습니다.");
    return;
  }
  errorWriter.write(response, 403, "ACCESS_DENIED", "접근 권한이 없습니다.");
}

// common/security/ApiErrorWriter.java
public void write(HttpServletResponse response, int status, String code, String message) ... {
  response.setStatus(status);
  response.setCharacterEncoding("UTF-8");
  response.setContentType("application/json");
  objectMapper.writeValue(response.getOutputStream(), ApiErrorResponse.withoutFieldErrors(code, message));
}
  • 같은 ApiErrorResponse(code, message, fieldErrors) 형태다. 프론트는 오류가 필터에서 났든 컨트롤러에서 났든 한 가지 방식으로 처리한다. 2강 Nginx의 로그인 속도 제한 429 응답({"code":"RATE_LIMITED",...})도 같은 모양이었다. Nginx, Security 필터, MVC 세 층이 같은 오류 계약을 지킨다.
  • CSRF 거절을 구분한다. 둘 다 403이지만 코드가 다르다. 프론트는 CSRF_INVALID를 받으면 토큰을 새로 받아 재시도할 수 있고, ACCESS_DENIED면 재시도하지 않는다. 상태 코드만으로는 이 구분이 안 된다.
  • Spring의 기본 로그아웃 필터를 껐다. .logout(logout -> logout.disable())로 끄고, 별도의 LogoutHandler Bean(CSRF 토큰 삭제, 컨텍스트 정리, 쿠키 삭제)을 직접 조립했다. 로그아웃 응답도 같은 JSON 계약을 따르게 하려는 것으로 보인다. 해석 로그인·로그아웃의 전체 흐름은 11강에서 본다.

4. DispatcherServlet에서 컨트롤러까지: 인자 변환

Security를 통과한 요청은 DispatcherServlet에 도착한다. DispatcherServlet은 @PostMapping 정보로 처리할 메서드를 찾고, 메서드 파라미터 하나하나를 채운다.

// subscription/api/SubscriptionController.java (발췌)
@PostMapping("/subscriptions/{subscriptionId}/commands/{command}")
ResponseEntity<SubscriptionDetailResponse> command(
    @AuthenticationPrincipal AuthenticatedMemberPrincipal principal,          // ① 세션 인증에서
    @PathVariable long subscriptionId,                                        // ② URL에서, long 변환
    @PathVariable String command,
    @RequestHeader(value = "Idempotency-Key", required = false) String key,   // ③ 선택 헤더
    @RequestHeader(value = "If-Match", required = false) String ifMatch,
    @RequestBody(required = false) SubscriptionCommandRequest request) {      // ④ JSON → 객체
  validateIfMatchSyntax(ifMatch);                                             // ⑤ 문법만 여기서
  return response(service.command(principal.memberId(), subscriptionId, command, key, ifMatch,
      (request == null ? SubscriptionCommandRequest.empty() : request).toCommand()));  // ⑥ 중립 커맨드
}
  • ① 회원 ID는 본문이 아니라 인증에서 온다. @AuthenticationPrincipal은 3절에서 세션으로 복원한 SecurityContext에서 꺼낸다. 4강의 MVP1 결정(“요청 본문의 memberId를 신뢰하지 않는다”)이 이렇게 구현된다. 클라이언트는 남의 ID를 보낼 통로 자체가 없다.
  • ② 타입 변환 실패는 400이다. /subscriptions/abc/...처럼 숫자가 아니면 MethodArgumentTypeMismatchException이 나고, 6절의 공통 처리기가 VALIDATION_FAILED로 바꾼다.
  • ③ 왜 required = false인가. 멱등 키와 If-Match는 이 API에 필수다. 그런데도 프레임워크에 필수 표시를 맡기지 않았다.
    • 해석 프레임워크가 막으면 일반적인 400이 된다. 서비스가 직접 검사하면 도메인 의미가 있는 오류를 줄 수 있다. 예를 들어 5강에서 본 SubscriptionFailure.Kind에는 PRECONDITION_REQUIRED(428)가 있다. “조건부 요청 헤더가 필요하다”는 HTTP 표준 상태 코드다.
  • ④ 본문도 선택이다. 일시정지처럼 추가 입력이 없는 명령은 본문 없이 보낼 수 있다. null이면 빈 요청으로 바꾼다.
  • ⑤ 문법 검사와 의미 검사를 나눈다. 기록 컨트롤러는 If-Match 값이 "5" 같은 형식인지만 본다. 실제 버전 비교는 서비스가 트랜잭션 안에서 한다. 구조 정리 결정 기록도 이 둘의 순서를 바꾸지 않는다고 명시한다. 6강에서 본 대로 “성공 재생 판정이 버전 검사보다 먼저”여야 하기 때문이다.
  • ⑥ HTTP DTO는 여기서 끝난다. request.toCommand()로 중립 커맨드를 만들어 넘긴다. 7강 ArchUnit의 application-api 규칙이 지키는 경계다.

5. 프록시와 트랜잭션: 보이지 않는 한 층

컨트롤러는 파사드 SubscriptionService.command(...)를 부르고, 파사드는 명령 서비스를 부른다. 실제 일은 여기서 일어난다.

// subscription/application/SubscriptionCommandApplicationService.java (발췌)
class SubscriptionCommandApplicationService {          // public이 아닌 패키지 전용 클래스

  @Transactional
  SubscriptionOperationResult command(long memberId, long subscriptionId, String command,
      String key, String ifMatch, SubscriptionCommand request) {      // 메서드도 패키지 전용
    SubscriptionCommandType commandType = SubscriptionCommandType.fromExternalValue(command);
    support.validateKey(key);                                         // 멱등 키 검사
    String fingerprint = support.fingerprint(request);                // 요청 지문
    SubscriptionProjection subscription = store.lockOwnedSubscription(memberId, subscriptionId); // 행 잠금
    if (!reservations.reserveCommand(memberId, subscriptionId, normalized, key, fingerprint))
      return replay(...);                                             // 이미 있는 키 → 재생 또는 충돌
    ... // 5강: If-Match 비교 → 전이 → CAS로 version 증가
  }
}
  • @Transactional은 프록시가 처리한다. 원리 Spring은 이 클래스를 감싼 프록시 객체를 Bean으로 등록한다. 파사드가 commands.command(...)를 부르면 실제로는 프록시가 먼저 받는다. 프록시는 다음 일을 대신 한다.
    • 커넥션 풀에서 커넥션을 꺼내 트랜잭션을 시작한다.
    • 진짜 메서드를 부른다.
    • 정상 종료면 커밋, 런타임 예외면 롤백한다.
    • 우리 코드에는 BEGIN도 COMMIT도 보이지 않는다. 이것이 AOP(관점 지향 프로그래밍)다.
  • 패키지 전용 메서드인데 동작하나? Spring 공식 문서 「Using @Transactional」은 이렇게 적는다. 6.0부터는 클래스 기반 프록시에서 protected나 패키지 전용 메서드도 기본으로 트랜잭션이 된다. 인터페이스 기반 프록시라면 여전히 public이어야 한다. 이 클래스는 인터페이스를 구현하지 않으므로 CGLIB 클래스 프록시가 쓰이고, 그래서 동작한다. 예전 Spring 지식(“public만 된다”)으로 읽으면 오해하기 쉬운 부분이다.
  • 자기 호출의 함정. 같은 문서는 이렇게 경고한다. 프록시 모드에서는 프록시를 통해 들어오는 외부 호출만 가로챈다. 같은 객체 안에서 다른 @Transactional 메서드를 부르는 자기 호출은 실제 트랜잭션을 만들지 않는다.
    • 여기서는 파사드라는 다른 Bean이 부르므로 안전하다.
    • 7강에서 본 “파사드에는 SQL도, 트랜잭션 어노테이션도 없다”는 구조 결정이 이 함정을 구조적으로 피하는 역할도 한다.
  • 잠금 → 예약 순서. 트랜잭션을 열자마자 구독 행을 먼저 잠근다(lockOwnedSubscription, FOR UPDATE). 같은 구독에 대한 동시 명령은 여기서 줄을 선다. 그다음 멱등 예약(6강의 subscription_command_idempotency_results)을 시도한다. 3강의 교착 사례처럼 잠금 순서가 정합성의 핵심이라, 이 순서는 22강에서 다시 깊게 본다.
  • 응답은 트랜잭션 밖에서 만든다. 1강의 spring.jpa.open-in-view=false 때문에, 트랜잭션이 끝나면 영속성 컨텍스트도 닫힌다.
    • 기록 그래서 서비스는 응답에 필요한 값을 다 채운 완성된 View를 돌려주고, 컨트롤러가 SubscriptionDetailResponse.from(view)로 DTO를 만든다.
    • 결정 기록은 이것을 “DTO 생성이 커밋 뒤로 옮겨지는 비용을 인정”했다고 적는다. 그 대신 응답을 만드는 동안 SQL이 0회임을 테스트로 지킨다.
    • 응답 조립 중 지연 로딩으로 쿼리가 날아가는 일이 원천적으로 없다. 커넥션도 커밋 직후 풀에 반납된다. 커넥션을 쥐고 JSON을 직렬화하지 않으니, 3강의 커넥션 풀 압박을 줄인다.

6. 예외는 어디서 응답이 되는가

이제 실패 경로를 한 표로 모을 수 있다.

어디서 실패하나 예 누가 응답을 만드나 응답
Nginx 로그인 속도 초과 Nginx @login_rate_limited 429 RATE_LIMITED
Security 필터 세션 없음 ApiAuthenticationEntryPoint 401 AUTH_REQUIRED
Security 필터 CSRF 불일치 ApiAccessDeniedHandler 403 CSRF_INVALID
Security 필터 USER가 /api/admin/** ApiAccessDeniedHandler 403 ACCESS_DENIED
인자 변환 ID가 숫자 아님, JSON 깨짐, @Valid 실패 CommonValidationExceptionHandler 400 VALIDATION_FAILED + fieldErrors
서비스 남의 구독, 버전 불일치, 상태 전이 불가 SubscriptionExceptionHandler 404 · 412 · 409 · 428
그 밖의 예상 못 한 예외 버그, DB 오류 SubscriptionExceptionHandler.unexpected 500 INTERNAL_ERROR + 서버 로그

코드에서 짚을 점이 세 가지다.

// common/api/CommonValidationExceptionHandler.java (발췌)
@Order(Ordered.HIGHEST_PRECEDENCE)
@RestControllerAdvice(basePackages = {
  "com.pawcycle.backend.commerce", "com.pawcycle.backend.catalog.admin.api", ...,
  "com.pawcycle.backend.recommendation.api", "com.pawcycle.backend.interaction.api",
  "com.pawcycle.backend.subscription"
})
public class CommonValidationExceptionHandler {
  @ExceptionHandler(MethodArgumentNotValidException.class)
  ResponseEntity<ApiErrorResponse> methodArgumentNotValid(MethodArgumentNotValidException exception) {
    List<FieldErrorResponse> fieldErrors = exception.getBindingResult().getFieldErrors().stream()
        .sorted(Comparator.comparing(FieldError::getField)
                          .thenComparing(error -> Objects.requireNonNullElse(error.getDefaultMessage(), "")))
        ...

// subscription/api/SubscriptionExceptionHandler.java (발췌)
@RestControllerAdvice(assignableTypes = {SubscriptionController.class, RepeatCommerceController.class})
public class SubscriptionExceptionHandler {
  @ExceptionHandler(SubscriptionFailure.class)
  ResponseEntity<ApiErrorResponse> handleSubscriptionFailure(SubscriptionFailure error) {
    int status = switch (error.kind()) {
      case BAD_REQUEST -> 400; case NOT_FOUND -> 404; case CONFLICT -> 409;
      case PRECONDITION_FAILED -> 412; case PRECONDITION_REQUIRED -> 428;
    };
    ...
  }
  @ExceptionHandler(Exception.class)
  ResponseEntity<ApiErrorResponse> unexpected(Exception exception) {
    log.error("Unexpected exception while processing subscription request", exception);
    return ResponseEntity.internalServerError().body(... "INTERNAL_ERROR", "요청을 처리할 수 없습니다.");
  }
}
  • HTTP 숫자는 API 계층만 안다. 서비스는 SubscriptionFailure.Kind.PRECONDITION_FAILED 같은 의미만 던지고, 숫자 412는 처리기가 정한다. 기록 이전에는 애플리케이션 7곳과 저장소 2곳이 HTTP 숫자를 가진 예외에 직접 의존했다. 그것을 41개 실패 지점에서 의미 기반으로 바꿨다(PR #391). 7강 그래프에서 기준선이 202 → 193으로 줄어든 지점이다.
  • 필드 오류를 정렬한다. 같은 잘못된 요청이면 언제나 같은 순서의 오류 목록이 나온다. Bean Validation은 필드 검사 순서를 보장하지 않기 때문이다. 프론트의 테스트와 화면 표시가 흔들리지 않는다.
  • 500은 숨기고 로그는 남긴다. 클라이언트에는 원인을 감춘 일반 메시지만 준다. 스택 트레이스와 SQL 오류는 서버 로그에만 남긴다. 2절의 요청 ID가 로그에 찍혔다면 이 로그와 사용자 문의를 묶을 수 있었을 것이다.

그리고 기록 이 구조가 실제로 구멍을 낸 사례가 있다. 공통 검증 처리기는 basePackages 목록으로 적용 범위를 정한다. 추천·상호작용·상품 API 패키지가 이 목록에서 빠져 있던 동안, 그 API들의 잘못된 입력(예: 숫자 자리에 문자)은 400이 아니라 catch-all 500으로 처리됐다. 패키지를 목록에 추가해 고쳤다(PR #424 계열, 결정 기록 PWC-0124).

  • 해석 문자열 패키지 목록은 새 패키지를 만들 때 잊기 쉽다. 7강의 보안 규칙(anyRequest().denyAll())처럼 “기본으로 적용되고 예외만 빼는” 방향이 더 안전하다. 예를 들어 basePackages = "com.pawcycle.backend" 전체에 적용하고, 다른 오류 형식을 쓰는 곳만 제외하는 식이다.
  • 해석 결정 기록은 이 사건의 교훈을 이렇게 남겼다. “mock으로 컨트롤러 메서드를 직접 호출한 테스트의 성공은 HTTP 바인딩의 성공을 대신하지 않는다.” 인자 변환과 예외 매핑은 DispatcherServlet을 거쳐야만 일어난다. 그래서 MockMvc나 실제 HTTP로 시험해야 이 층이 검증된다.

8강 정리

  • 요청 하나 = Tomcat 스레드 하나. 스레드는 응답을 다 쓸 때까지 묶인다. 스레드는 재사용되므로 ThreadLocal(MDC, SecurityContext)은 반드시 finally에서 비운다.
  • 두 영역의 경계. 서블릿 필터(Spring Security 포함)는 Spring MVC 바깥이라 @RestControllerAdvice가 닿지 않는다.
    • 그래서 Security용 EntryPoint·AccessDeniedHandler를 따로 두되, 같은 JSON 오류 계약을 지킨다.
    • Nginx의 429도 같은 모양이다.
  • Security 체인: 세션에서 인증 복원 → CSRF(헤더 토큰 = 세션 토큰) → 인가 규칙(처음 맞는 규칙, 구체적인 것이 먼저, 마지막은 denyAll).
  • 인자 변환
    • 회원 ID는 인증에서만 받는다.
    • 필수 헤더를 일부러 required = false로 두고 서비스가 428 같은 의미 있는 오류를 준다.
    • 컨트롤러는 문법만, 서비스는 의미를 검사한다.
  • 트랜잭션 프록시
    • Spring 6부터 패키지 전용 메서드도 CGLIB 프록시로 트랜잭션이 된다.
    • 자기 호출은 트랜잭션이 안 된다. 파사드가 다른 Bean이라 안전하다.
    • OSIV를 끄고 완성된 View → 커밋 후 DTO 순서로 응답을 만든다.
  • 발견한 빈틈
    • 요청 ID 필터가 Security 뒤에 실행되고, 로그 패턴에도 없고, Nginx와 이어지지 않는다.
    • 공통 검증 처리기의 패키지 목록은 새 패키지를 놓치기 쉽다. 실제로 500 사고가 났었다.

8강에서 남긴 미확인 항목

  • /api/subscriptions/...와 계약 문서의 /api/v2/subscriptions/... 경로 관계(22강)
  • 요청 ID가 실제 운영 로그에 찍히는지(27강)
  • 로그인·로그아웃 흐름과 세션 고정 방지의 실제 동작(11강)
