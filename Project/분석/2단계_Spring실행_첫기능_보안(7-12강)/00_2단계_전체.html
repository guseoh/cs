7강. 시작과 Bean 구성: 애플리케이션은 어떻게 조립되는가

이번 강의의 목표

  • main()에서 SpringApplication.run()이 끝날 때까지 무엇이 어떤 순서로 일어나는지 이해한다.
  • PawCycle이 Spring을 띄우기 전에 유지보수 명령을 먼저 가르는 이유를 안다.
  • 프로필과 조건부 Bean으로 환경마다 다른 구현을 끼우는 방법을 본다. 대상은 토스 어댑터 3종, AI 클라이언트, Redis 캐시, 스케줄러다.
  • ArchUnit으로 패키지·계층 규칙을 테스트로 강제하고, 위반 기준선을 204개에서 5개로 줄여 간 과정을 읽는다.

1강 정정: 1강에서 “동결된 위반 204개(application→api 186개)”라고 했다. 이것은 10월 7일 시점의 숫자다. 확인 기준 커밋(f9ab9f87)의 기준선 파일에는 5개만 남아 있다. 4절에서 그 과정을 본다.

1. main()의 두 갈래

// PawcycleBackendApplication.java (전체)
@SpringBootApplication
public class PawcycleBackendApplication {
  public static void main(String[] args) {
    int catalogImportExitCode = ProductionDemoCatalogImportCommand.runIfRequested(args);
    if (catalogImportExitCode != ProductionDemoCatalogImportCommand.NOT_REQUESTED) {
      if (catalogImportExitCode != 0) System.exit(catalogImportExitCode);
      return;
    }
    int maintenanceExitCode = ProductionAuthSmokeMemberBootstrap.runIfRequested(args);
    if (maintenanceExitCode != ProductionAuthSmokeMemberBootstrap.NOT_REQUESTED) {
      if (maintenanceExitCode != 0) System.exit(maintenanceExitCode);
      return;
    }
    SpringApplication.run(PawcycleBackendApplication.class, args);
  }
}

보통의 Spring Boot 앱은 main에 SpringApplication.run 한 줄뿐이다. PawCycle은 그 앞에 두 개의 관문을 둔다. 운영 카탈로그 적재 명령과, 운영 인증 점검용 회원 생성 명령이다. 같은 jar, 같은 Docker 이미지를 웹 서버로도, 일회성 명령으로도 쓰기 위한 구조다.

왜 Spring을 띄운 뒤가 아니라 전에 가를까? 인증 점검 관문 코드가 답을 준다.

// member/maintenance/ProductionAuthSmokeMemberBootstrap.java (발췌)
private static final List<String> ENFORCED_ARGUMENTS = List.of(
    option("spring.main.web-application-type", "none"),   // 웹 서버를 띄우지 않는다
    option(ENABLED, "true"),
    option("spring.flyway.enabled", "false"),              // 마이그레이션을 돌리지 않는다
    option("spring.main.banner-mode", "off"),
    option("logging.level.root", "OFF"),                   // 로그를 전부 끈다
    option("debug", "false"), option("trace", "false"),
    option("spring.jpa.show-sql", "false"), ...);

static int runIfRequested(String[] args, ...) {
  ResolvedProperty webApplicationType = resolve(args, systemProperties, environment, WEB_APPLICATION_TYPE);
  if (!webApplicationType.present()) return NOT_REQUESTED;   // 지정 안 함 → 평소처럼 웹 서버
  if (webApplicationType.ambiguous()) { error.println(ERROR_MESSAGE); return FAILURE; }
  if ("servlet".equals(...)) return NOT_REQUESTED;
  if (!"none".equals(...)) { ...; return FAILURE; }
  ...
  return application.run(enforceArguments(args));            // 사용자 인자 위에 강제 인자를 덮어씀
}
  • 모드는 컨텍스트를 만들기 전에 정해야 한다. 원리 웹 서버를 띄울지, Flyway를 돌릴지, 로그를 얼마나 남길지는 ApplicationContext를 만드는 과정 자체를 바꾸는 설정이다. 컨텍스트가 이미 뜬 뒤에는 되돌릴 수 없다. 예를 들어 Flyway는 시작 중에 이미 마이그레이션을 실행한다.
  • 강제 인자로 사용자 입력을 덮어쓴다. enforceArguments는 사용자가 넘긴 같은 키(--debug 포함)를 지우고 강제 값을 뒤에 붙인다. 운영자가 실수로 --debug를 붙여도, 회원 생성 과정의 SQL이나 자격 증명이 로그에 찍히지 않는다. 3강의 “로그에 새는 개인정보”와 같은 방어다.
  • 애매하면 실패한다(fail-closed). 같은 키가 서로 다른 값으로 여러 번 오면(ambiguous) 일반 웹 서버로 넘어가지 않고 종료 코드 2로 끝난다. 스크립트는 종료 코드만 보고 성공 여부를 판단할 수 있다.
  • 출력은 PASS 한 줄. 실행 중에는 System.out과 System.err를 버리는 스트림으로 바꿨다가, 성공하면 정해진 PASS 메시지 한 줄만 출력한다.

관문이 보지 못하는 설정 경로

이 설계에는 리뷰에서 지적된 흥미로운 틈이 있었다. 기록 이 관문은 명령줄 인자, 시스템 속성, 일부 환경 변수만 읽는다. 그런데 Spring은 그보다 훨씬 많은 곳에서 설정을 읽는다. SPRING_APPLICATION_JSON, spring.config.additional-location, application.properties 같은 곳이다. 리뷰(PR #70)는 이 점을 짚었다.

  • 관문이 보지 못하는 경로로 “웹 아님 + 활성화”를 주면 관문은 NOT_REQUESTED로 판단한다.
  • 그러면 일반 SpringApplication.run이 실행되는데, Spring은 그 설정을 읽어 유지보수 러너를 켤 수 있다.
  • 결과적으로 관문의 강제 인자(Flyway 끄기, 출력 억제)를 우회할 수 있다는 지적이다.

미확인 이 지적에 대한 수정 커밋은 원본에서 확인하지 못했다. 실제로 재현해 보지도 않았다. 대신 현재 코드에는 두 번째 방어선이 있다.

// member/maintenance/ProductionAuthSmokeMemberMaintenanceConfiguration.java
@Configuration(proxyBeanMethods = false)
@ConditionalOnNotWebApplication                         // 웹 앱이면 아예 등록하지 않는다
@ConditionalOnProperty(prefix = "...", name = "enabled", havingValue = "true")
public class ProductionAuthSmokeMemberMaintenanceConfiguration { ... }

해석 관문을 우회해 일반 웹 서버로 뜨면 @ConditionalOnNotWebApplication이 막는다. 남는 위험은 하나다. 관문이 못 보는 경로로 none 모드가 설정되면, 강제 인자 없이 유지보수 설정이 켜질 수 있다. 교훈은 이렇다. 사전 검사는 프레임워크가 최종적으로 해석할 설정 표면과 같은 범위를 봐야 한다. 다르다면 프레임워크 안쪽에도 같은 조건을 한 번 더 둬야 한다.

2. SpringApplication.run() 안에서 일어나는 일 (깊게)

이제 평소의 웹 서버 경로다. run() 한 줄 안에서 일어나는 일을 PawCycle 설정에 맞춰 펼치면 다음과 같다.

단계마다 PawCycle에서 의미 있는 지점을 짚어 보자.

  • ① 설정 출처의 우선순위. 같은 키가 여러 곳에 있으면 위쪽이 이긴다. application.properties의 spring.datasource.url=${SPRING_DATASOURCE_URL}는 값 자체가 아니라 환경 변수를 가리키는 자리표시자다. 비밀 값은 파일에 두지 않고 컨테이너 환경 변수(2강 compose)로 주입한다.
    • ${PAWCYCLE_TOSS_TEST_ENABLED:false}처럼 : 뒤에 기본값을 둔 키가 많다. 외부 기능은 모두 기본이 꺼짐이라는 원칙(4강)이 여기서 구현된다.
    • 반대로 SPRING_DATASOURCE_URL처럼 기본값이 없는 키는 값이 없으면 시작이 실패한다. DB 없이 뜨는 서버는 의미가 없으니, 일찍 실패하는 편이 낫다.
  • ③ 등록 순서가 조건 평가를 바꾼다. 원리 Spring Boot는 우리 코드의 @Component를 먼저 스캔한다. DataSourceAutoConfiguration 같은 자동 구성은 그 뒤에 처리한다. 그래서 자동 구성은 “사용자가 이미 같은 타입의 Bean을 만들었으면 물러난다”(@ConditionalOnMissingBean)가 가능하다. 3절에서 이 순서가 실제로 중요해진다.
  • ④ 생성자 주입과 순환 참조. 원리 Spring Boot 2.6부터 순환 참조는 기본적으로 금지다. 생성자 주입만 쓰면 A가 B를, B가 A를 필요로 할 때 둘 다 만들 수 없어 시작이 실패한다. 이것은 결함이 아니라 설계 냄새를 시작 시점에 드러내는 장치다.
  • ⑤ Flyway가 JPA보다 먼저다. 원리 Spring Boot는 JPA의 EntityManagerFactory가 Flyway Bean에 의존하도록 순서를 잡아 준다. 그래서 마이그레이션이 끝난 스키마를 대상으로 ddl-auto=validate가 엔티티와 테이블을 대조한다. 6강의 “JPA는 검사만 한다”가 바로 이 지점이다. 마이그레이션을 빠뜨린 배포는 트래픽을 받기 전에 실패한다.
  • ⑥ 준비 완료. Tomcat이 8080을 연 뒤에야 2강의 헬스체크(/api/products)가 통과한다. compose의 depends_on: service_healthy가 proxy를 이때까지 기다리게 한다.

3. 프로필과 조건부 Bean: 환경마다 다른 구현 끼우기

토스 결제 어댑터 3종

5강까지 본 결제 흐름은 TossPaymentAdapter라는 인터페이스에만 의존한다. 실제 구현은 세 개이고, 환경에 따라 정확히 하나만 Bean으로 등록된다.

// commerce/payment/infrastructure/toss/
@Component @Profile("local-integration")
@ConditionalOnProperty(name = "pawcycle.toss.test.enabled", havingValue = "true")
class TossTestPaymentAdapter implements TossPaymentAdapter { ... }        // 토스 테스트 API를 실제로 호출

@Component @Profile("local-integration")
@ConditionalOnProperty(name = "pawcycle.toss.test.enabled", havingValue = "false", matchIfMissing = true)
class TossSandboxPaymentAdapter implements TossPaymentAdapter {           // 외부 호출 없는 가짜
  public ConfirmResult confirm(String paymentKey, ...) {
    if (paymentKey.startsWith("unknown_")) return new ConfirmResult("UNKNOWN", "NO_RESPONSE");
    if (paymentKey.startsWith("fail_"))    return new ConfirmResult("FAILED", "ABORTED");
    return new ConfirmResult("SUCCEEDED", "DONE");
  }
}

@Component @Profile("!local-integration")
class TossUnavailablePaymentAdapter implements TossPaymentAdapter {
  public boolean isConfigured() { return false; }
  public ConfirmResult confirm(...) {
    throw new CommerceException(503, "PAYMENT_PROVIDER_UNAVAILABLE", "...");
  }
}

두 조건을 표로 놓으면 빈칸이 없다.

프로필 pawcycle.toss.test.enabled 등록되는 Bean 동작
local-integration true Test 토스 테스트 API 호출(test_sk_ 키만, 라이브 키 거부)
local-integration false 또는 없음 Sandbox 결제 키 접두어로 성공·실패·미확정을 흉내
그 외 (운영 포함) 무엇이든 Unavailable 503으로 실패
  • 정확히 하나가 보장된다. 첫 두 행은 같은 속성의 true와 false/없음으로 배타적이다. 세 번째 행은 프로필 부정(!)으로 앞의 둘과 배타적이다. 어떤 조합에서도 Bean이 0개나 2개가 되지 않는다. 0개나 2개면 주입 지점에서 시작이 실패한다.
  • 운영에서는 속성을 켜도 소용없다. @Profile이 바깥 관문이기 때문이다. 운영 환경에 누가 PAWCYCLE_TOSS_TEST_ENABLED=true를 넣어도, local-integration 프로필이 아니면 Test·Sandbox 어댑터는 후보조차 되지 않는다. 두 조건을 겹쳐서 쓴 이유가 이것이다.
  • 기본값이 “실패”다. 아무것도 설정하지 않은 환경의 결제는 가짜 성공이 아니라 503이다. 4강의 “결제사가 없으면 가짜 결제 성공을 만들지 않는다”(fail-closed)가 Bean 구성으로 구현된 것이다.
  • 확인 정기결제(TossSandboxBillingAdapter / TossUnavailableBillingAdapter)와 환불(TossSandboxRefundAdapter / TossUnavailableRefundAdapter) 어댑터도 같은 구조다.
  • Sandbox의 설계가 영리하다. 결제 키 접두어(unknown_, fail_)만으로 UNKNOWN 같은 재현하기 어려운 상태를 만들 수 있다. 3강의 PROCESSING·UNKNOWN 처리를 로컬에서 시험할 수 있게 해 주는 테스트 더블이다.

AI 클라이언트: 진짜 Bean과 “아무것도 안 하는” Bean

AI 기능도 기본이 꺼짐이지만, 구현 방식이 다르다.

// catalog/product/application/ProductCommerceAiConfiguration.java (발췌)
@Configuration(proxyBeanMethods = false)
class ProductCommerceAiConfiguration {
  @Bean
  @ConditionalOnProperty(prefix = "pawcycle.ai.review-summary", name = "enabled", havingValue = "true")
  ReviewSummaryAiClient reviewSummaryClient(@Value("${spring.ai.openai.api-key:}") String key, ...) {
    ChatClient client = client(key, model);       // 키·모델이 비었으면 IllegalStateException
    return reviews -> client.prompt().system("...의료나 치료 주장을 하지 마세요.").user(...).call().content();
  }

  @Bean
  @ConditionalOnMissingBean(ReviewSummaryAiClient.class)
  ReviewSummaryAiClient disabledReviewSummaryClient() {
    return reviews -> null;                        // 꺼졌을 때: 요약 없음
  }
}
  • 널 객체 패턴. 꺼졌을 때도 ReviewSummaryAiClient Bean은 항상 존재한다. 다만 null을 돌려줄 뿐이다. 호출하는 쪽은 “Bean이 있는가”를 검사하지 않고, 결과가 없을 때의 처리만 하면 된다. 토스 어댑터의 Unavailable도 같은 계열의 패턴이다.
  • 켜졌는데 키가 없으면 시작이 실패한다. client()가 키나 모델이 비어 있으면 예외를 던진다. 해석 첫 요청이 올 때 터지는 것보다 배포 직후 시작 단계에서 터지는 편이 훨씬 빨리 발견된다.
  • 스타터를 쓰지 않았다. 확인 build.gradle은 spring-ai-openai와 spring-ai-client-chat 모듈만 쓴다. 자동 구성이 들어 있는 스타터는 쓰지 않는다. 해석 스타터를 쓰면 API 키가 있을 때 OpenAI 모델 Bean이 자동으로 만들어진다. PawCycle은 기능별 플래그로 명시적으로 켤 때만 모델 클라이언트를 직접 만드는 쪽을 택했다. 4강의 “AI는 기본 꺼짐, 비용 승인은 별도”와 같은 원칙이다.

그런데 여기에 짚을 점이 하나 있다. Spring Boot 공식 문서 「Creating Your Own Auto-configuration」은 이렇게 경고한다.

이 조건들은 지금까지 처리된 것을 기준으로 평가되므로 Bean 정의가 추가되는 순서에 매우 주의해야 한다. 그래서 @ConditionalOnBean과 @ConditionalOnMissingBean은 자동 구성 클래스에서만 쓰기를 권한다. (요지)

  • 해석 PawCycle의 AI 설정은 일반 @Configuration에서 @ConditionalOnMissingBean을 쓴다. 지금은 같은 클래스 안에서 활성 Bean이 먼저 선언되어 있어 의도대로 동작한다.
  • 하지만 누군가 메서드 순서를 바꾸거나, 다른 설정 클래스에 활성 Bean을 옮기면 조용히 두 Bean이 생기거나 비활성 Bean만 남을 수 있다. 정확히 어느 쪽이 될지는 처리 순서에 달려 있어서, 겉으로는 잘 드러나지 않는다.

개선 제안 해석 같은 프로젝트의 토스 Sandbox 어댑터가 이미 더 안전한 방법을 쓰고 있다. 비활성 Bean에도 속성 조건을 반대로 거는 것이다.

java // 제안 예시 — 저장소에 없는 코드다 @Bean @ConditionalOnProperty(prefix = "pawcycle.ai.review-summary", name = "enabled", havingValue = "false", matchIfMissing = true) ReviewSummaryAiClient disabledReviewSummaryClient() { return reviews -> null; }

두 Bean이 같은 속성의 true / false·없음으로 배타적이 되어 등록 순서와 무관해진다. 프로젝트 안에서 같은 문제를 두 방식으로 푸는 불일치도 사라진다.

Redis 캐시와 스케줄러: 조건부 Bean이 아닌 것과 맞는 것

  • Redis 캐시는 Bean이 아니라 값으로 끈다. 확인 ProductListCache는 항상 Bean으로 등록되고, @Value("${pawcycle.catalog.product-list-cache.enabled:false}") boolean enabled를 받아 실행 중에 분기한다.
    • Redis 스타터는 클래스패스에 있으므로 연결 팩토리는 자동 구성으로 만들어진다. 다만 Lettuce 클라이언트는 처음 쓸 때 연결하므로, 캐시가 꺼져 있으면 실제 연결은 일어나지 않는다. 원리
    • 헬스체크도 같은 플래그(management.health.redis.enabled=${PAWCYCLE_PRODUCT_LIST_CACHE_ENABLED:false})로 묶었다. Redis를 쓰지 않는 환경에서 Redis가 없다는 이유로 헬스체크가 실패하는 일을 막는다. 2강의 “헬스체크가 무엇을 증명하는가”와 같은 고민이다.
    • 해석 조건부 Bean으로 끄면 Bean이 아예 없으니 주입하는 쪽마다 분기가 필요하다. 값으로 끄면 캐시 클래스 한 곳에서만 분기하면 된다. 캐시처럼 “있으면 빠르고 없어도 맞는” 기능에는 값 플래그가 더 단순하다.
  • 스케줄러는 조건부 Bean이 맞다. SubscriptionOrderAutomationTrigger는 @ConditionalOnProperty로 켜질 때만 Bean이 된다. Bean이 없으면 @Scheduled 메서드도 등록되지 않는다. 운영 DB에 스스로 주문을 만드는 기능이니 존재 자체를 설정으로 통제하는 것이 맞다(4강).

4. 패키지·계층 규칙과 ArchUnit

규칙을 테스트로 강제한다

계층 구조(api → application → domain, persistence, infrastructure)는 문서로만 정하면 금방 무너진다. 급할 때 컨트롤러에서 저장소를 바로 부르는 한 줄이 쌓이기 때문이다. ArchUnit은 컴파일된 바이트코드를 읽어 클래스 사이의 의존을 그래프로 만들고, 규칙 위반을 테스트 실패로 만든다.

이 velog 글 「아키텍처 컨벤션 검증을 위해 ArchUnit을 활용한 아키텍처 테스트 작성하기」가 입문용으로 좋다. 글은 ArchUnit이 공식적으로 제공하는 일곱 가지 검사(패키지·클래스 종속성, 포함, 상속, 어노테이션, 레이어, 순환)를 소개한다. 그리고 한 사이드 프로젝트의 레이어 규칙을 실제 테스트로 옮겨 보인다.

출처: velog @langoustine · 아키텍처 컨벤션 검증을 위해 ArchUnit을 활용한 아키텍처 테스트 작성하기. 그림은 “아키텍처 구조를 살펴볼게요” 문장 바로 뒤에 있는 것으로 확인했고, 그림 내부를 확대해 읽지는 않았다.

PawCycle의 규칙은 테스트 안의 검증용 예제에서 한눈에 보인다.

// src/test/java/.../architecture/BackendArchitectureTests.java (발췌)
assertThat(rules(ROOT + "example.application.UseCase", "org.springframework.jdbc.core.JdbcTemplate", false))

assertThat(rules(ROOT + "example.domain.Model", ROOT + "example.infrastructure.Provider", false))

    .containsExactly("persistence-api");        // 저장소도 HTTP DTO를 모른다

  • application-api의 의미. 애플리케이션 서비스가 CreateSubscriptionRequest 같은 HTTP DTO를 받으면, HTTP를 바꿀 때 업무 로직까지 바뀐다. 확인 그래서 HTTP 입력은 API 계층의 매퍼가 중립 커맨드로 바꾸고, 응답은 각 응답 DTO의 static from(View)가 완성된 View에서 만든다(PR #394 등). 별도의 거대한 공통 매퍼는 만들지 않았다.

기준선 래칫: 204개에서 5개로

기존 코드에 이미 위반이 수백 개 있다면 규칙을 어떻게 도입할까? 한 번에 다 고치면 거대한 위험한 PR이 된다. PawCycle은 기준선 동결을 택했다.

// BackendArchitectureTests.productionDependenciesMustNotAddLegacyViolations (발췌)
JavaClasses classes = new ClassFileImporter().importPath(Path.of("build/classes/java/main"));
Set<String> actual = violations(classes);
Set<String> baseline = ... readAllLines("src/test/resources/architecture/legacy-dependencies.txt");
Set<String> added = actual - baseline;      // 새로 생긴 위반
Set<String> removed = baseline - actual;    // 고쳐졌는데 기준선에 남은 항목
assertThat(added).as("New architecture violations; see %s", report).isEmpty();
assertThat(removed).as("Remove resolved entries from the baseline").isEmpty();
  • 양방향 비교가 핵심이다.
    • 새 위반이 생기면 실패한다. 빚이 늘지 않는다.
    • 고친 위반이 기준선에 남아 있어도 실패한다. 고쳤으면 기준선에서 지워야 하니, 기준선은 줄어들기만 한다.
    • 이렇게 한쪽으로만 움직이는 장치를 래칫(ratchet, 톱니바퀴 멈춤쇠)이라 한다.
  • 기준선은 자동으로 갱신하지 않는다. 주석이 못 박는다. “진단은 체크인된 기준선을 절대 갱신하지 않는다. CI에서도.” 현재 위반은 build/reports에 보고서로만 쓴다. 자동 갱신을 허용하면 새 위반이 슬쩍 기준선에 들어가 래칫이 무력해진다.
  • 운영 바이트코드만 본다. build/classes/java/main만 읽는다. 테스트 픽스처나 라이브러리는 규칙의 대상이 아니다.

확인 기준선 파일의 줄 수를 커밋마다 세어 보면, 이 래칫이 실제로 돌아간 기록이 남아 있다.

그래프에서 읽을 점이 세 가지다.

  • 처음에 늘어난 것은 빚이 늘어서가 아니다. 기록 131 → 145 → 204의 증가는 패키지 정규화 PR(#343, #345)에서 생겼다. 기능 최상위에 평평하게 놓여 있던 클래스를 api/application/persistence 같은 계층 패키지로 옮겼더니, 원래 있던 의존이 이제야 계층 위반으로 보이게 됐다.

첫 두 줄은 **1절에서 본 `main()`의 두 관문** 그 자체다. 운영 코드가 유지보수 도구에 의존하면 안 된다는 규칙이 있는데, 진입점이 유지보수 명령을 부르니 위반으로 잡힌다.
- **[해석]** 이것은 “같은 jar를 웹 서버와 일회성 명령으로 쓴다”는 1절의 설계 결정이 **의도적으로 지불한 비용**이다. 남겨 둔 것이 실수가 아니라 선택이라는 점을 설명할 수 있어야 한다.
- 없애려면 유지보수 명령을 별도 진입점(다른 `main` 클래스나 별도 실행 모듈)으로 분리해야 한다. 대신 이미지나 실행 스크립트가 늘어난다.

ArchUnit의 한계. 기록 결정 기록은 이 가드가 “리플렉션, SQL 의미, 트랜잭션 정합성을 증명하지 않는다”고 명시한다. 문자열로 짠 SQL이 다른 테이블을 건드리거나, 리플렉션으로 클래스를 부르는 의존은 바이트코드 그래프에 나타나지 않는다. ArchUnit은 구조를 지키는 도구이지 동작을 증명하는 도구가 아니다. 동작은 3강에서 본 MySQL 통합 테스트들의 몫이다.

8강. 요청 하나의 처리 경로: Tomcat에서 트랜잭션까지

이번 강의의 목표

  • HTTP 요청 하나가 Tomcat 스레드 → 서블릿 필터 → Spring Security → DispatcherServlet → 컨트롤러 → 서비스(프록시·트랜잭션)로 가는 길을 그릴 수 있다.
  • 각 층에서 실패가 생기면 어디서 응답으로 바뀌는지 설명할 수 있다. 특히 보안 필터에서 생긴 실패가 @RestControllerAdvice에 잡히지 않는 이유를 이해한다.
  • thread-per-request 모델과 ThreadLocal, 프록시가 끼어드는 지점을 PawCycle 코드 위에서 확인한다.

표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 원리 일반 원리 · 미확인

1. 요청 하나가 지나가는 길

아래 그림은 브라우저 요청이 Nginx를 지나 Spring Boot 컨테이너에 들어온 뒤의 경로다. 위쪽 점선 상자는 서블릿 필터 영역(Spring MVC 바깥), 아래쪽 점선 상자는 DispatcherServlet 이후의 Spring MVC 영역이다.

그림의 핵심은 점선 상자 두 개의 경계다. 위쪽 상자에서 생긴 실패는 Spring MVC의 @RestControllerAdvice가 볼 수 없다. 그래서 PawCycle에는 오류 처리기가 두 계열로 나뉘어 있다. 3절과 6절에서 이유를 본다.

2. Tomcat: 요청 하나 = 스레드 하나 (깊게)

원리 Spring MVC는 요청당 스레드(thread-per-request) 모델이다.

  • Tomcat의 NIO 커넥터는 소수의 스레드로 소켓 연결을 받아(acceptor) 데이터가 도착했는지 감시한다(poller).
  • 요청이 완성되면 워커 스레드 풀(기본 최대 200개)에서 스레드 하나를 꺼내 맡긴다.
  • 그 스레드는 필터, 컨트롤러, 서비스, DB 대기까지 응답을 다 쓸 때까지 그 요청만 처리한다. DB가 느리면 스레드는 그동안 블록된 채 묶여 있다.
  • 3강에서 본 “커넥션 풀 대기 117개”와 2강의 pids_limit: 256(= 스레드 상한)이 모두 이 모델에서 나온다. 느린 요청이 많아지면 스레드가 고갈되고, 새 요청은 큐에서 기다린다.

이 모델에서 생기는 미묘한 함정이 ThreadLocal 이다. PawCycle의 첫 필터가 그것을 다룬다.

// common/web/RequestCorrelationFilter.java
@Component
public class RequestCorrelationFilter extends OncePerRequestFilter {
  static final String REQUEST_ID_HEADER = "X-Request-ID";
  private static final Pattern SAFE_REQUEST_ID = Pattern.compile("[A-Za-z0-9._-]{1,64}");

  protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) ... {
    MDC.put("requestId", requestId(request));
    try {
      filterChain.doFilter(request, response);
    } finally {
      MDC.remove("requestId");            // 반드시 지운다
    }
  }

  private String requestId(HttpServletRequest request) {
    String candidate = request.getHeader(REQUEST_ID_HEADER);
    if (candidate != null && SAFE_REQUEST_ID.matcher(candidate).matches()) return candidate;
    return UUID.randomUUID().toString();
  }
}
  • MDC는 ThreadLocal이다. 원리 MDC(Mapped Diagnostic Context)는 로그에 요청 ID 같은 값을 붙이려고 현재 스레드에 값을 저장한다. 그런데 Tomcat 스레드는 풀에서 재사용된다. finally에서 지우지 않으면 다음 요청이 같은 스레드를 받았을 때 이전 요청의 ID가 남아 로그가 엉뚱한 요청에 묶인다. try/finally는 예외가 나도 정리를 보장하는 관용구다.
  • 헤더 값을 검증한다. 클라이언트가 보낸 X-Request-ID를 그대로 로그에 넣으면, 줄바꿈 문자를 넣어 가짜 로그 줄을 끼워 넣는 공격(로그 인젝션)이 가능하다. 영숫자와 ._- 64자 이내만 받는 정규식이 이를 막는다.
  • OncePerRequestFilter. 서블릿은 내부 포워드나 오류 페이지 디스패치에서 같은 요청에 필터를 다시 태울 수 있다. 이 부모 클래스는 요청당 한 번만 실행되도록 보장한다.

그런데 이 필터를 실제 배치와 함께 보면 세 가지 빈틈이 보인다.

  • 확인 실행 순서를 지정하지 않았다. @Order도 FilterRegistrationBean도 없다.
    • 원리 Spring Boot는 순서 없는 Filter Bean을 가장 낮은 우선순위로 등록한다. Spring Security 필터 체인은 기본 순서 -100으로 그보다 앞에 선다.
    • 해석 따라서 인증 실패(401)나 CSRF 거절(403)처럼 Security가 직접 응답하는 경우, 요청 ID 필터는 실행되지도 않는다. 보안 거절이야말로 추적하고 싶은 요청인데, 거기에 ID가 없다.
  • 확인 로그 패턴에 requestId가 없다. application.properties와 리소스 어디에도 %X{requestId} 같은 로그 패턴이나 logback 설정이 없다.
    • 해석 Spring Boot 기본 로그 형식은 MDC 값을 출력하지 않으므로, 지금은 MDC에 넣은 ID가 로그에 찍히지 않을 가능성이 높다.
    • 미확인 다른 경로(구조화 로그 설정 등)로 출력되는지는 27강(관측)에서 실제 로그로 확인한다.
  • 확인 Nginx가 ID를 만들거나 넘기지 않는다. 2강의 Nginx 설정에는 X-Request-ID 관련 지시어가 없다. 그래서 백엔드가 매번 새 UUID를 만들고, Nginx 접근 로그와 백엔드 로그를 같은 요청으로 묶을 수 없다. 응답 헤더로 돌려주지도 않아서, 프론트나 사용자가 오류 문의 때 ID를 알려 줄 수도 없다.

개선 제안 해석 세 가지를 함께 고쳐야 효과가 난다. 1. Nginx에서 proxy_set_header X-Request-ID $request_id;로 입구에서 ID를 만들어 넘기고, 접근 로그에도 같은 값을 남긴다. 2. 필터에 @Order(Ordered.HIGHEST_PRECEDENCE)를 붙여 Security보다 먼저 실행한다. 응답 헤더에도 같은 ID를 쓴다. 3. 로그 패턴에 %X{requestId}를 넣는다.

3. Spring Security 필터 체인

구조: 서블릿 필터 하나가 Spring 안의 체인을 부른다

Tomcat은 Spring Bean을 모른다. 그런데 Security 필터들은 Spring Bean이다. 이 둘을 잇는 구조를 Spring Security 공식 문서의 그림으로 보자. 아래 그림은 Spring Security 공식 저장소의 원본 이미지다.

공식 문서 「Spring Security · Architecture」의 설명에 따라 그림을 읽으면 이렇다.

  • DelegatingFilterProxy: Tomcat에 등록되는 진짜 서블릿 필터다. 스스로는 아무것도 하지 않고, Spring 컨테이너에서 Bean을 찾아 일을 위임한다. 서블릿 컨테이너와 Spring 컨테이너 사이의 다리다.
  • FilterChainProxy: 위임받는 Spring Bean이다. 요청 URL에 맞는 SecurityFilterChain을 고른다. 체인이 여러 개일 수 있어서다.
    • 확인 PawCycle도 체인이 두 개다. 메인 체인과, 성능 측정용 SubscriptionBurstMeasurementSecurityConfiguration의 @Order(1) 체인이다.
  • SecurityFilterChain: 실제 보안 필터들의 목록이다. 1강에서 본 SecurityConfig의 http.csrf(...).authorizeHttpRequests(...)...build()가 바로 이 체인을 만든다.

우리 요청이 체인 안에서 겪는 일을 순서대로 보자.

  1. 세션에서 인증 복원. HttpSessionSecurityContextRepository가 JSESSIONID 쿠키로 서버 세션을 찾고, 거기 저장된 인증 정보(SecurityContext)를 꺼내 현재 스레드에 둔다. 이것도 ThreadLocal이고, 요청이 끝나면 Security가 비운다.
  2. CSRF 검사. POST이므로 X-CSRF-TOKEN 헤더 값이 세션에 저장된 토큰(HttpSessionCsrfTokenRepository)과 같아야 한다. 다르거나 없으면 403이다. 왜 쿠키가 아니라 헤더인지는 11강에서 깊게 본다.
  3. 인가 규칙. 규칙은 위에서부터 처음 맞는 하나가 적용된다.
// common/security/SecurityConfig.java (인가 규칙 발췌)
.requestMatchers(EndpointRequest.to("health", "prometheus")).permitAll()
.requestMatchers(HttpMethod.GET, "/api/products/*/reviews/me").authenticated()   // ①
.requestMatchers(HttpMethod.GET, "/api/products", "/api/products/**", ...).permitAll() // ②
...
.requestMatchers(HttpMethod.POST, "/api/auth/login").permitAll()
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/**").authenticated()                                       // 우리 요청
.anyRequest().denyAll()                                                           // ③
  • ①이 ②보다 위에 있어야 한다. /api/products/7/reviews/me(내 리뷰)는 /api/products/**(공개 상품)에도 맞는다. 순서가 바뀌면 내 리뷰 조회가 비로그인에게 열린다. 구체적인 규칙을 먼저, 넓은 규칙을 나중에 두는 것이 원칙이다.
  • ③ 기본 거부. 어느 규칙에도 맞지 않는 경로는 전부 거부한다. 새 엔드포인트를 만들고 규칙 추가를 잊으면, 열리는 대신 막힌다. 3강의 fail-closed다.
  • 우리 요청은 /api/**에 맞고 인증돼 있으니 통과한다.

실패하면: 컨트롤러 어드바이스는 여기까지 오지 못한다

인증이 없거나 CSRF가 틀리면 어떻게 될까? 공식 문서의 ExceptionTranslationFilter 그림이 그 흐름을 보여 준다.

  • 인증이 없어서 막히면 AuthenticationEntryPoint가, 인증은 됐는데 권한이 없거나 CSRF가 틀려 막히면 AccessDeniedHandler가 응답을 만든다.
  • 이 모든 일은 필터 안에서 끝난다. 요청은 DispatcherServlet에 도달하지 않는다.

망나니개발자의 「필터(Filter) vs 인터셉터(Interceptor) 차이 및 용도」가 이 차이를 정확히 짚는다. 필터는 디스패처 서블릿 앞의 서블릿 영역에서 관리되기 때문에, @ControllerAdvice·@ExceptionHandler 같은 스프링의 예외 처리를 받을 수 없다는 것이다. (원문의 흐름 그림은 서명된 임시 이미지 주소라 시간이 지나면 깨지므로 링크로만 둔다.)

그래서 PawCycle은 Security용 처리기를 따로 만들되, 응답 모양은 MVC 쪽과 똑같이 맞췄다.

// common/security/ApiAccessDeniedHandler.java
public void handle(HttpServletRequest request, HttpServletResponse response, AccessDeniedException e) ... {
  if (e instanceof CsrfException) {
    errorWriter.write(response, 403, "CSRF_INVALID", "CSRF 토큰이 유효하지 않습니다.");
    return;
  }
  errorWriter.write(response, 403, "ACCESS_DENIED", "접근 권한이 없습니다.");
}

// common/security/ApiErrorWriter.java
public void write(HttpServletResponse response, int status, String code, String message) ... {
  response.setStatus(status);
  response.setCharacterEncoding("UTF-8");
  response.setContentType("application/json");
  objectMapper.writeValue(response.getOutputStream(), ApiErrorResponse.withoutFieldErrors(code, message));
}
  • 같은 ApiErrorResponse(code, message, fieldErrors) 형태다. 프론트는 오류가 필터에서 났든 컨트롤러에서 났든 한 가지 방식으로 처리한다. 2강 Nginx의 로그인 속도 제한 429 응답({"code":"RATE_LIMITED",...})도 같은 모양이었다. Nginx, Security 필터, MVC 세 층이 같은 오류 계약을 지킨다.
  • CSRF 거절을 구분한다. 둘 다 403이지만 코드가 다르다. 프론트는 CSRF_INVALID를 받으면 토큰을 새로 받아 재시도할 수 있고, ACCESS_DENIED면 재시도하지 않는다. 상태 코드만으로는 이 구분이 안 된다.
  • Spring의 기본 로그아웃 필터를 껐다. .logout(logout -> logout.disable())로 끄고, 별도의 LogoutHandler Bean(CSRF 토큰 삭제, 컨텍스트 정리, 쿠키 삭제)을 직접 조립했다. 로그아웃 응답도 같은 JSON 계약을 따르게 하려는 것으로 보인다. 해석 로그인·로그아웃의 전체 흐름은 11강에서 본다.

4. DispatcherServlet에서 컨트롤러까지: 인자 변환

Security를 통과한 요청은 DispatcherServlet에 도착한다. DispatcherServlet은 @PostMapping 정보로 처리할 메서드를 찾고, 메서드 파라미터 하나하나를 채운다.

// subscription/api/SubscriptionController.java (발췌)
@PostMapping("/subscriptions/{subscriptionId}/commands/{command}")
ResponseEntity<SubscriptionDetailResponse> command(
    @AuthenticationPrincipal AuthenticatedMemberPrincipal principal,          // ① 세션 인증에서
    @PathVariable long subscriptionId,                                        // ② URL에서, long 변환
    @PathVariable String command,
    @RequestHeader(value = "Idempotency-Key", required = false) String key,   // ③ 선택 헤더
    @RequestHeader(value = "If-Match", required = false) String ifMatch,
    @RequestBody(required = false) SubscriptionCommandRequest request) {      // ④ JSON → 객체
  validateIfMatchSyntax(ifMatch);                                             // ⑤ 문법만 여기서
  return response(service.command(principal.memberId(), subscriptionId, command, key, ifMatch,
      (request == null ? SubscriptionCommandRequest.empty() : request).toCommand()));  // ⑥ 중립 커맨드
}
  • ① 회원 ID는 본문이 아니라 인증에서 온다. @AuthenticationPrincipal은 3절에서 세션으로 복원한 SecurityContext에서 꺼낸다. 4강의 MVP1 결정(“요청 본문의 memberId를 신뢰하지 않는다”)이 이렇게 구현된다. 클라이언트는 남의 ID를 보낼 통로 자체가 없다.
  • ② 타입 변환 실패는 400이다. /subscriptions/abc/...처럼 숫자가 아니면 MethodArgumentTypeMismatchException이 나고, 6절의 공통 처리기가 VALIDATION_FAILED로 바꾼다.
  • ③ 왜 required = false인가. 멱등 키와 If-Match는 이 API에 필수다. 그런데도 프레임워크에 필수 표시를 맡기지 않았다.
    • 해석 프레임워크가 막으면 일반적인 400이 된다. 서비스가 직접 검사하면 도메인 의미가 있는 오류를 줄 수 있다. 예를 들어 5강에서 본 SubscriptionFailure.Kind에는 PRECONDITION_REQUIRED(428)가 있다. “조건부 요청 헤더가 필요하다”는 HTTP 표준 상태 코드다.
  • ④ 본문도 선택이다. 일시정지처럼 추가 입력이 없는 명령은 본문 없이 보낼 수 있다. null이면 빈 요청으로 바꾼다.
  • ⑤ 문법 검사와 의미 검사를 나눈다. 기록 컨트롤러는 If-Match 값이 "5" 같은 형식인지만 본다. 실제 버전 비교는 서비스가 트랜잭션 안에서 한다. 구조 정리 결정 기록도 이 둘의 순서를 바꾸지 않는다고 명시한다. 6강에서 본 대로 “성공 재생 판정이 버전 검사보다 먼저”여야 하기 때문이다.
  • ⑥ HTTP DTO는 여기서 끝난다. request.toCommand()로 중립 커맨드를 만들어 넘긴다. 7강 ArchUnit의 application-api 규칙이 지키는 경계다.

5. 프록시와 트랜잭션: 보이지 않는 한 층

컨트롤러는 파사드 SubscriptionService.command(...)를 부르고, 파사드는 명령 서비스를 부른다. 실제 일은 여기서 일어난다.

// subscription/application/SubscriptionCommandApplicationService.java (발췌)
class SubscriptionCommandApplicationService {          // public이 아닌 패키지 전용 클래스

  @Transactional
  SubscriptionOperationResult command(long memberId, long subscriptionId, String command,
      String key, String ifMatch, SubscriptionCommand request) {      // 메서드도 패키지 전용
    SubscriptionCommandType commandType = SubscriptionCommandType.fromExternalValue(command);
    support.validateKey(key);                                         // 멱등 키 검사
    String fingerprint = support.fingerprint(request);                // 요청 지문
    SubscriptionProjection subscription = store.lockOwnedSubscription(memberId, subscriptionId); // 행 잠금
    if (!reservations.reserveCommand(memberId, subscriptionId, normalized, key, fingerprint))
      return replay(...);                                             // 이미 있는 키 → 재생 또는 충돌
    ... // 5강: If-Match 비교 → 전이 → CAS로 version 증가
  }
}
  • @Transactional은 프록시가 처리한다. 원리 Spring은 이 클래스를 감싼 프록시 객체를 Bean으로 등록한다. 파사드가 commands.command(...)를 부르면 실제로는 프록시가 먼저 받는다. 프록시는 다음 일을 대신 한다.
    • 커넥션 풀에서 커넥션을 꺼내 트랜잭션을 시작한다.
    • 진짜 메서드를 부른다.
    • 정상 종료면 커밋, 런타임 예외면 롤백한다.
    • 우리 코드에는 BEGIN도 COMMIT도 보이지 않는다. 이것이 AOP(관점 지향 프로그래밍)다.
  • 패키지 전용 메서드인데 동작하나? Spring 공식 문서 「Using @Transactional」은 이렇게 적는다. 6.0부터는 클래스 기반 프록시에서 protected나 패키지 전용 메서드도 기본으로 트랜잭션이 된다. 인터페이스 기반 프록시라면 여전히 public이어야 한다. 이 클래스는 인터페이스를 구현하지 않으므로 CGLIB 클래스 프록시가 쓰이고, 그래서 동작한다. 예전 Spring 지식(“public만 된다”)으로 읽으면 오해하기 쉬운 부분이다.
  • 자기 호출의 함정. 같은 문서는 이렇게 경고한다. 프록시 모드에서는 프록시를 통해 들어오는 외부 호출만 가로챈다. 같은 객체 안에서 다른 @Transactional 메서드를 부르는 자기 호출은 실제 트랜잭션을 만들지 않는다.
    • 여기서는 파사드라는 다른 Bean이 부르므로 안전하다.
    • 7강에서 본 “파사드에는 SQL도, 트랜잭션 어노테이션도 없다”는 구조 결정이 이 함정을 구조적으로 피하는 역할도 한다.
  • 잠금 → 예약 순서. 트랜잭션을 열자마자 구독 행을 먼저 잠근다(lockOwnedSubscription, FOR UPDATE). 같은 구독에 대한 동시 명령은 여기서 줄을 선다. 그다음 멱등 예약(6강의 subscription_command_idempotency_results)을 시도한다. 3강의 교착 사례처럼 잠금 순서가 정합성의 핵심이라, 이 순서는 22강에서 다시 깊게 본다.
  • 응답은 트랜잭션 밖에서 만든다. 1강의 spring.jpa.open-in-view=false 때문에, 트랜잭션이 끝나면 영속성 컨텍스트도 닫힌다.
    • 기록 그래서 서비스는 응답에 필요한 값을 다 채운 완성된 View를 돌려주고, 컨트롤러가 SubscriptionDetailResponse.from(view)로 DTO를 만든다.
    • 결정 기록은 이것을 “DTO 생성이 커밋 뒤로 옮겨지는 비용을 인정”했다고 적는다. 그 대신 응답을 만드는 동안 SQL이 0회임을 테스트로 지킨다.
    • 응답 조립 중 지연 로딩으로 쿼리가 날아가는 일이 원천적으로 없다. 커넥션도 커밋 직후 풀에 반납된다. 커넥션을 쥐고 JSON을 직렬화하지 않으니, 3강의 커넥션 풀 압박을 줄인다.

  }
  @ExceptionHandler(Exception.class)
  ResponseEntity<ApiErrorResponse> unexpected(Exception exception) {
    log.error("Unexpected exception while processing subscription request", exception);
    return ResponseEntity.internalServerError().body(... "INTERNAL_ERROR", "요청을 처리할 수 없습니다.");
  }
}
  • HTTP 숫자는 API 계층만 안다. 서비스는 SubscriptionFailure.Kind.PRECONDITION_FAILED 같은 의미만 던지고, 숫자 412는 처리기가 정한다. 기록 이전에는 애플리케이션 7곳과 저장소 2곳이 HTTP 숫자를 가진 예외에 직접 의존했다. 그것을 41개 실패 지점에서 의미 기반으로 바꿨다(PR #391). 7강 그래프에서 기준선이 202 → 193으로 줄어든 지점이다.
  • 필드 오류를 정렬한다. 같은 잘못된 요청이면 언제나 같은 순서의 오류 목록이 나온다. Bean Validation은 필드 검사 순서를 보장하지 않기 때문이다. 프론트의 테스트와 화면 표시가 흔들리지 않는다.
  • 500은 숨기고 로그는 남긴다. 클라이언트에는 원인을 감춘 일반 메시지만 준다. 스택 트레이스와 SQL 오류는 서버 로그에만 남긴다. 2절의 요청 ID가 로그에 찍혔다면 이 로그와 사용자 문의를 묶을 수 있었을 것이다.

그리고 기록 이 구조가 실제로 구멍을 낸 사례가 있다. 공통 검증 처리기는 basePackages 목록으로 적용 범위를 정한다. 추천·상호작용·상품 API 패키지가 이 목록에서 빠져 있던 동안, 그 API들의 잘못된 입력(예: 숫자 자리에 문자)은 400이 아니라 catch-all 500으로 처리됐다. 패키지를 목록에 추가해 고쳤다(PR #424 계열, 결정 기록 PWC-0124).

  • 해석 문자열 패키지 목록은 새 패키지를 만들 때 잊기 쉽다. 7강의 보안 규칙(anyRequest().denyAll())처럼 “기본으로 적용되고 예외만 빼는” 방향이 더 안전하다. 예를 들어 basePackages = "com.pawcycle.backend" 전체에 적용하고, 다른 오류 형식을 쓰는 곳만 제외하는 식이다.
  • 해석 결정 기록은 이 사건의 교훈을 이렇게 남겼다. “mock으로 컨트롤러 메서드를 직접 호출한 테스트의 성공은 HTTP 바인딩의 성공을 대신하지 않는다.” 인자 변환과 예외 매핑은 DispatcherServlet을 거쳐야만 일어난다. 그래서 MockMvc나 실제 HTTP로 시험해야 이 층이 검증된다.

8강 정리

  • 요청 하나 = Tomcat 스레드 하나. 스레드는 응답을 다 쓸 때까지 묶인다. 스레드는 재사용되므로 ThreadLocal(MDC, SecurityContext)은 반드시 finally에서 비운다.
  • 두 영역의 경계. 서블릿 필터(Spring Security 포함)는 Spring MVC 바깥이라 @RestControllerAdvice가 닿지 않는다.
    • 그래서 Security용 EntryPoint·AccessDeniedHandler를 따로 두되, 같은 JSON 오류 계약을 지킨다.
    • Nginx의 429도 같은 모양이다.
  • Security 체인: 세션에서 인증 복원 → CSRF(헤더 토큰 = 세션 토큰) → 인가 규칙(처음 맞는 규칙, 구체적인 것이 먼저, 마지막은 denyAll).
  • 인자 변환
    • 회원 ID는 인증에서만 받는다.
    • 필수 헤더를 일부러 required = false로 두고 서비스가 428 같은 의미 있는 오류를 준다.
    • 컨트롤러는 문법만, 서비스는 의미를 검사한다.
  • 트랜잭션 프록시
    • Spring 6부터 패키지 전용 메서드도 CGLIB 프록시로 트랜잭션이 된다.
    • 자기 호출은 트랜잭션이 안 된다. 파사드가 다른 Bean이라 안전하다.
    • OSIV를 끄고 완성된 View → 커밋 후 DTO 순서로 응답을 만든다.
  • 발견한 빈틈
    • 요청 ID 필터가 Security 뒤에 실행되고, 로그 패턴에도 없고, Nginx와 이어지지 않는다.
    • 공통 검증 처리기의 패키지 목록은 새 패키지를 놓치기 쉽다. 실제로 500 사고가 났었다.

9강. 영속성 전략: JPA, 네이티브 SQL, 트랜잭션, 그리고 MVCC

이번 강의의 목표

  • PawCycle이 JPA, JPQL, Querydsl, 네이티브 SQL, JdbcTemplate을 어떤 기준으로 나눠 쓰는지 안다.
  • 영속성 컨텍스트, 플러시, 벌크 UPDATE의 관계를 코드로 이해한다.
  • 트랜잭션을 @Transactional과 TransactionTemplate 두 방식으로 여는 이유, 그리고 OSIV를 끈 이유를 안다.
  • MySQL InnoDB의 MVCC와 격리 수준을 깊게 이해한다. 그리고 그것이 재고 충돌 사고와 어떻게 이어졌는지 본다.

트랜잭션 @Transactional 257곳(읽기 전용 110), TransactionTemplate 13개 파일

JdbcTemplate이 9개 파일에만, 그것도 일반 요청 경로 밖에만 남은 것은 우연이 아니다. 기록 10월 8일 사용자가 승인한 결정은 다음과 같다.

  • 일반 런타임(고객, 스케줄러, 관리자, 운영, 추천, 구독)의 직접 JdbcTemplate 소유자를 0으로 만든다.
  • JPA/Spring Data를 기본 경계로 삼는다.
  • 다만 MySQL 고유 UPSERT, FOR UPDATE, 조건부 UPDATE, 잠금 순서처럼 의미가 정밀한 SQL은 EntityManager 네이티브 SQL로 근거를 남기고 유지한다.

같은 결정이 명시적으로 승인하지 않은 것도 있다.

  • JdbcTemplate SQL을 네이티브 SQL로 이름만 바꾸는 활동
  • “네이티브 SQL 0개”라는 목표

이유는 결정 기록의 한 문장에 있다.

SQL을 단지 JPA API로 감싼다고 MySQL의 FOR UPDATE, missing-row/gap, unique/CAS, microsecond timestamp, provider I/O의 의미가 같아지는 것은 아니다.

그래서 도구 선택 기준은 “쿼리의 성격” 이다.

  • 엔티티 상태 전이(결제 READY → PROCESSING, 장바구니 수량 변경) → JPA 엔티티 + 리포지토리
  • 고정된 조회(주문 목록 8종, 멤버십) → 타입 있는 JPQL
  • 조건이 선택적으로 붙는 조회(추천 필터) → Querydsl
  • MySQL만의 문법이나 정밀한 잠금(ON DUPLICATE KEY UPDATE, UNION과 JSON_TABLE이 섞인 운영 조회 16종, FOR UPDATE 순서) → 네이티브 SQL
  • 일반 요청 경로 밖의 도구(픽스처 적재, 일회성 이행, 부하 측정) → JdbcTemplate 유지. 그 격리는 7강의 ArchUnit runtime-maintenance 규칙이 지킨다.

기록 Querydsl을 전면에 쓰지 않은 이유. 7.7 버전을 패싯 조회 한 곳에 시범 적용했다. 기존 SQL과 결과가 같고 SELECT가 한 번인지 비교한 뒤, 범위를 제한해 유지했다. 단순 고정 조회까지 Querydsl로 바꾸면 Q타입 보일러플레이트만 늘기 때문이다. 이것도 4강의 YAGNI가 도구 선택에 적용된 예다.

2. 영속성 컨텍스트와 플러시: 재고 예약 코드로 보기 (깊게)

JPA의 핵심 개념인 영속성 컨텍스트(persistence context)부터 짚자.

  • 원리 EntityManager는 트랜잭션 동안 조회한 엔티티를 1차 캐시에 보관한다. 같은 ID를 다시 조회하면 SQL 없이 캐시에서 돌려준다.
  • 엔티티의 필드를 바꾸면 즉시 UPDATE하지 않는다. 커밋 직전(또는 JPQL 실행 직전)에 처음 상태와 비교해(dirty checking) 바뀐 것만 SQL로 내보낸다. 이 내보내기를 플러시(flush)라 한다.
  • 편리하지만, DB와 메모리가 잠시 어긋나는 구간이 생긴다. 그 구간을 정확히 다뤄야 하는 코드가 재고 예약이다.
// commerce/inventory/persistence/InventoryRepository.java
@Lock(LockModeType.PESSIMISTIC_WRITE)                               // ① 잠금 읽기
@Query("select inventory from InventoryEntity inventory where inventory.skuId = :skuId")
Optional<InventoryEntity> findLockedBySkuId(@Param("skuId") long skuId);

@Modifying(flushAutomatically = true, clearAutomatically = true)   // ③ 벌크 UPDATE 앞뒤 처리
@Query("""
    update InventoryEntity inventory
    set inventory.availableQuantity = inventory.availableQuantity - :quantity,
        inventory.reservedQuantity  = inventory.reservedQuantity  + :quantity,
        inventory.version = inventory.version + 1
    where inventory.skuId = :skuId
      and inventory.version = :expectedVersion                     -- ② CAS
      and inventory.availableQuantity >= :quantity
    """)
int reserveIfVersionMatches(...);

// commerce/inventory/application/InventoryService.java
public void reserve(long skuId, int quantity, long paymentId) {
  InventoryEntity inventory = inventories.findLockedBySkuId(skuId).orElse(null);   // SELECT ... FOR UPDATE
  if (inventory == null || inventory.availableQuantity() < quantity) throw ... "INVENTORY_INSUFFICIENT";
  int changed = inventories.reserveIfVersionMatches(skuId, quantity, inventory.version());
  if (changed != 1) throw ... "INVENTORY_CONFLICT";
  movements.save(InventoryMovementEntity.payment(skuId, paymentId, ...));           // 재고 이동 이력
}
  • ① PESSIMISTIC_WRITE 는 SQL로 SELECT ... FOR UPDATE가 된다. 이 행을 다른 트랜잭션이 바꾸지 못하게 커밋까지 잠근다.
  • ② CAS: WHERE version = :expectedVersion. 읽은 뒤 누가 바꿨다면 영향받은 행이 0이 되고 INVENTORY_CONFLICT가 된다. 재고 부족 조건(availableQuantity >= :quantity)도 같은 UPDATE 안에서 다시 검사한다.
  • ③ 벌크 UPDATE와 영속성 컨텍스트. 원리 @Modifying JPQL은 엔티티를 거치지 않고 DB에 바로 실행된다. 영속성 컨텍스트는 이 변경을 모른다. 그래서 두 옵션이 필요하다.
    • flushAutomatically = true: UPDATE 전에 아직 내보내지 않은 엔티티 변경을 먼저 플러시한다. 순서가 뒤집히지 않는다.
    • clearAutomatically = true: UPDATE 후에 1차 캐시를 비운다. 그러지 않으면 ①에서 읽은 inventory 객체가 옛 수량을 가진 채 남는다. 이후 코드가 그 값을 다시 읽으면 DB와 다른 숫자를 쓰게 된다.
    • 그래서 코드는 UPDATE 전에 availableBefore, reservedBefore를 미리 변수에 담아 이동 이력에 쓴다. 캐시가 비워진 뒤 객체를 다시 믿지 않는 것이다.

그런데 이상한 점이 있다. ①에서 이미 행을 잠갔으니 ②의 CAS는 절대 실패하지 않아야 한다. 왜 둘 다 있을까? 이 질문의 답이 5절의 MVCC다.

3. 트랜잭션을 여는 두 가지 방법과 OSIV

@Transactional: 메서드 전체가 하나의 트랜잭션

8강에서 본 구독 명령처럼, 메서드 경계가 곧 트랜잭션 경계인 경우다. 대부분(257곳)이 이 방식이다. 조회 메서드 110곳은 readOnly = true를 붙였다.

  • 원리 readOnly = true면 Hibernate는 플러시를 생략하고, 변경 감지를 위한 스냅샷을 만들지 않아 메모리를 아낀다.
  • JDBC 드라이버에도 읽기 전용 힌트가 전달된다. MySQL은 읽기 전용 트랜잭션에 트랜잭션 ID를 할당하지 않아 내부 비용이 조금 줄어든다.

TransactionTemplate: 한 메서드 안에서 여러 번 열고 닫기

확인 13개 서비스가 TransactionTemplate을 쓴다. 결제 승인, 정기결제, 환불, 취소, 반품, 배송, 체크아웃, 구독 대사다. 공통점은 외부 결제사 호출이 끼어 있다는 것이다. 결제 승인 코드가 그 이유를 가장 잘 보여 준다.

// commerce/payment/application/PaymentApplicationService.java (발췌)
public PaymentResult confirm(long memberId, String paymentKey, String providerOrderId, BigDecimal amount) {
  PaymentWork work = transaction.execute(status -> {                         // 트랜잭션 ①
    PaymentWork payment = payments.findByProviderOrderIdForUpdate(providerOrderId, memberId);
    if (payment == null) throw notFound();
    if ("SUCCEEDED".equals(payment.status()) && ... ) return payment;        // 이미 성공 → 재생
    if (!"READY".equals(payment.status()) || !"PAYMENT_PENDING".equals(payment.orderStatus())
        || payment.amount().compareTo(amount) != 0)
      throw new CommerceException(409, "PAYMENT_CONFIRM_CONFLICT", ...);
    payments.markProcessing(payment.paymentId(), paymentKey);                // READY → PROCESSING
    return payment;
  });                                                                        // 커밋 · 커넥션 반납

  TossPaymentAdapter.ConfirmResult result;
  try {
    result = tossPaymentAdapter.confirm(paymentKey, providerOrderId, amount);  // 외부 호출: 트랜잭션 밖
  } catch (RuntimeException exception) {
    return transaction.execute(status -> markProviderUnknown(work.paymentId()));   // 트랜잭션 ② 모름
  }
  return transaction.execute(status -> finalizePayment(work.paymentId(), result.status(), paymentKey)); // ② 확정
}
  • 외부 호출 동안 DB 커넥션을 쥐지 않는다. 토스 응답이 몇 초 걸려도, 그동안 커넥션과 FOR UPDATE 잠금은 이미 풀려 있다. @Transactional 하나로 메서드 전체를 감쌌다면 결제사 지연이 그대로 커넥션 풀 고갈과 잠금 대기로 번진다. 3강의 HikariCP 이야기, 5강 MVP3 구조 정리의 “외부 Provider I/O는 트랜잭션 밖”이 바로 이 코드다.
  • 5강 미확인 항목의 답. 5강에서 “PaymentEntity.markProcessing은 이전 상태를 검사하지 않는데, READY에서만 PROCESSING으로 가는 규칙은 어디서 지키는가?”를 남겼다. 확인 답은 트랜잭션 ① 안이다. FOR UPDATE로 결제와 주문을 함께 잠근 상태에서 READY / PAYMENT_PENDING / 금액 일치를 확인한다. 하나라도 어긋나면 409다. 엔티티가 아니라 잠금 아래의 서비스가 전이를 지킨다.
  • 대가: 트랜잭션 사이의 틈. ①이 커밋된 뒤 ②가 시작되기 전에 서버가 죽으면 결제는 PROCESSING에 남는다. 3강 위험 지도 1순위였던 PROCESSING 고립 문제(이슈 #417)가 정확히 이 틈이다. 커넥션을 쥐지 않는 이득과 상태가 갈라질 위험을 맞바꾼 것이고, 18·19강에서 복구 설계를 본다.

격리 수준은 “바깥 트랜잭션”이 정한다

두 곳이 기본값이 아닌 격리 수준을 쓴다. 그중 카테고리 관리 코드의 주석이 중요한 함정을 알려 준다.

// catalog/admin/application/AdminCatalogMutationService.java (발췌)
// The audit owner must set isolation too: a REQUIRED inner service joins this transaction.
@Transactional(isolation = Isolation.READ_COMMITTED)
public CategoryView createCategory(long adminId, CategoryCreateCommand request) {
  return execute(adminId, "CATALOG_CATEGORY_CREATE", "CATEGORY",
      () -> adminCatalogService.createCategory(request), CategoryView::categoryId);
}
  • 원리 격리 수준은 트랜잭션을 시작할 때 한 번 정해진다. 안쪽 서비스(AdminCatalogService.createCategory)에도 READ_COMMITTED가 붙어 있다. 하지만 바깥 감사 서비스가 이미 트랜잭션을 열었다면, 안쪽은 기본 전파 REQUIRED로 참여만 한다. 안쪽에 적힌 격리 수준은 조용히 무시된다.
  • 그래서 트랜잭션을 실제로 여는 바깥쪽(감사 기록 소유자)에도 같은 격리 수준을 적었다. 주석이 정확히 그 이유를 말한다.
  • 기록 이 변경은 카테고리 2단계 깊이 불변식과 동시성 보호 작업(이슈 #416)에서 들어왔다. 카테고리를 다른 부모 아래로 옮길 때 이미 자식이 있으면 3단계가 생길 수 있었고, 동시 생성·이동과의 경쟁도 함께 막아야 했다.
  • 미확인 왜 하필 READ_COMMITTED를 골랐는지 직접 적은 문장은 찾지 못했다. 해석 5절을 읽고 나면 이유를 추론할 수 있다. 자식 존재 여부를 검사할 때 가장 최근에 커밋된 상태를 봐야 하고, REPEATABLE READ의 간격 잠금으로 인한 교착도 줄이려는 선택으로 보인다.

OSIV를 끈 이유

1강에서 본 spring.jpa.open-in-view=false의 의미를 이제 정확히 말할 수 있다. 위키독스의 「OSIV의 진실」이 정리한 핵심은 두 가지다.

  • OSIV가 켜져 있으면 HTTP 요청의 시작부터 끝까지 DB 커넥션을 물고 있게 된다.
  • 컨트롤러나 JSON 변환 중에 지연 로딩이 일어나 의도하지 않은 SQL(N+1)이 생긴다.

글은 운영에서는 꺼야 하고, 그때 나는 LazyInitializationException은 숨겨진 문제를 드러내는 “건강한 예외”라고 말한다.

한 가지는 정밀하게 보충해야 한다.

  • 원리 Spring의 OSIV는 요청 내내 트랜잭션을 유지하는 것이 아니다. EntityManager(영속성 컨텍스트) 를 열어 두는 것이다. 서비스의 @Transactional이 끝나면 트랜잭션은 커밋된다.
  • 그 뒤 컨트롤러에서 일어나는 지연 로딩은 트랜잭션 없이(자동 커밋 모드로) 실행된다.
  • 그리고 EntityManager가 처음 커넥션을 얻은 순간부터 닫힐 때까지 커넥션을 놓지 않는다. 이것이 커넥션 점유의 실제 원인이다.

PawCycle은 8강에서 본 대로 “완성된 View → 커밋 후 DTO 조립”으로 이 문제를 구조적으로 피했다. 그리고 응답 조립 중 SQL이 0회임을 테스트로 지킨다.

작은 발견 해석 리뷰 요약 저장 코드(ReviewSummaryQueryRepository.saveSummaryIfCurrent)에 “OpenEntityManagerInView가 AI 호출 이전의 엔티티 값을 1차 캐시에 들고 있을 수 있다”는 주석이 있다. 현재 설정은 OSIV가 꺼져 있으므로 이 이유는 그대로 맞지 않는다. 다만 “같은 영속성 컨텍스트의 1차 캐시가 오래된 값을 줄 수 있으니 잠금 SQL로 다시 읽는다”는 결론 자체는 여전히 옳다. 주석의 근거만 낡은 것이다. 15강에서 이 코드를 다시 본다.

4. MVCC와 격리 수준 (깊게)

이제 2절의 질문으로 돌아가자. 잠금 읽기를 했는데 왜 CAS도 필요하고, 실제로 CAS 충돌이 났을까? 답을 위해 InnoDB가 동시성을 다루는 방식부터 이해해야 한다.

읽기는 기다리지 않는다: 다중 버전

원리 InnoDB는 행을 고칠 때 이전 값을 undo 로그에 남긴다. 그래서 같은 행의 여러 버전이 잠시 공존한다. 이것이 MVCC(Multi-Version Concurrency Control)다.

  • 잠금 없는 일반 SELECT는 스냅샷을 읽는다. 다른 트랜잭션이 그 행을 고치는 중이어도 기다리지 않고, 자기 시점에 보이는 버전을 undo 로그에서 찾아 읽는다.
  • “읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않는다.” 동시성이 높은 이유다.

문제는 어느 시점의 스냅샷인가다. MySQL 공식 문서 「Consistent Nonlocking Reads」가 정확히 적는다.

  • REPEATABLE READ (InnoDB 기본값): 같은 트랜잭션 안의 모든 일반 읽기는 그 트랜잭션의 첫 읽기가 만든 스냅샷을 계속 본다.
  • READ COMMITTED: 일반 읽기마다 새 스냅샷을 만든다. 매번 최신 커밋 상태를 본다.

그리고 같은 문서는 결정적인 문장을 덧붙인다.

스냅샷은 트랜잭션 안의 SELECT에 적용되며, 반드시 DML에 적용되는 것은 아니다. … 다른 REPEATABLE READ 트랜잭션의 DELETE나 UPDATE는 방금 커밋된 행들에 영향을 줄 수 있다. 그 세션이 그 행들을 조회로는 볼 수 없었더라도. (요지)

즉 REPEATABLE READ에서는 같은 트랜잭션 안에서 두 개의 다른 세계를 본다.

  • 일반 SELECT는 과거 스냅샷을 본다.
  • UPDATE, DELETE, SELECT ... FOR UPDATE(잠금 읽기)는 최신 커밋 버전을 보고, 잠근다.

그래서 일어난 일: 공유 SKU 재고 충돌

이 차이가 PawCycle에서 실제 문제를 일으켰다. 기록 같은 SKU를 여러 주문이 동시에 체크아웃하는 부하에서 INVENTORY_CONFLICT가 쏟아졌고, PR #336이 이를 고쳤다.

  • 그 전 코드는 재고를 일반 SELECT로 읽고(버전 5), CAS UPDATE(WHERE version = 5)를 했다.
  • 체크아웃 트랜잭션은 앞에서 이미 회원 행, 장바구니 등을 읽었다. 그래서 REPEATABLE READ의 스냅샷은 트랜잭션 초반에 고정돼 있었다.
  • 그 사이 다른 체크아웃이 같은 SKU 재고를 커밋해 버전이 6이 됐다. 그래도 이 트랜잭션의 일반 SELECT는 여전히 버전 5를 보여 준다.
  • 그런데 UPDATE는 최신 버전 6을 기준으로 WHERE version = 5를 평가한다. 영향받은 행은 0, 즉 CAS 실패다.
  • 결과적으로 재고가 충분한데도 “재고가 변경되었습니다”가 반복됐다. 오래된 스냅샷과 최신 DML이 서로 다른 세계를 보고 있었기 때문이다.

그림으로 정리하면 이렇다.

이제 2절의 질문에 답할 수 있다. 잠금 읽기(①)가 진짜 해결책이고, CAS(②)는 이력상 먼저 있던 방어선이다.

  • 기록 순서는 CAS가 먼저였고, 잠금 읽기는 PR #336에서 나중에 추가됐다. 잠금 읽기가 최신 버전을 읽고 행을 잠그므로, 같은 트랜잭션 안의 CAS는 정상 경로에서는 실패하지 않는다.
  • 해석 그래도 CAS를 지우지 않은 이유는 방어선을 겹치는 것이 싸기 때문이다. 누군가 나중에 findLockedBySkuId를 일반 조회로 바꿔도 이중 예약은 일어나지 않는다. 대신 충돌 오류로 드러난다. 조건(availableQuantity >= :quantity)이 UPDATE 안에 있는 것도 같은 이유다.

같은 문제를 푸는 다른 방법들과 비교하면 선택의 의미가 보인다.

방법 동작 이 코드에서의 평가 해석
잠금 읽기 + CAS (현재) FOR UPDATE로 최신 값을 잠그고 읽은 뒤 조건부 UPDATE 같은 SKU 예약이 줄을 선다. 충돌 오류는 사라지는 대신 대기가 생긴다. 인기 SKU에서는 이 대기가 처리량 상한이 된다.
READ COMMITTED로 전환 일반 SELECT도 매번 최신 스냅샷 읽기와 UPDATE 사이에 여전히 틈이 있어 CAS 충돌은 줄 뿐 사라지지 않는다. 트랜잭션 전체의 의미도 바뀐다.
낙관적 잠금 + 재시도 충돌하면 처음부터 다시 결제·쿠폰·장바구니가 한 트랜잭션이라 재시도 범위가 크다. 인기 SKU에서는 재시도 폭주가 난다.
읽지 않고 조건부 UPDATE 한 번 UPDATE … SET available = available - n WHERE available >= n 가장 짧다. 하지만 이동 이력에 남길 “이전 값”을 얻으려면 다시 읽어야 하고, version 의미도 사라진다.

간격 잠금: 없는 행도 잠근다

REPEATABLE READ에는 하나가 더 있다. 원리 잠금 읽기와 UPDATE·DELETE는 찾은 행만 잠그지 않는다. 인덱스상 그 행들 사이의 간격까지 잠근다(next-key lock = 레코드 잠금 + 간격 잠금). 그 범위에 새 행이 끼어드는 것(팬텀)을 막기 위해서다. READ COMMITTED는 대부분의 간격 잠금을 쓰지 않는다.

PawCycle에는 이 성질을 의도적으로 쓴 곳과 당한 곳이 둘 다 있다.

  • 의도적으로 쓴 곳: 리뷰 요약 저장.
// catalog/engagement/persistence/ReviewSummaryQueryRepository.java (발췌)
@Transactional(isolation = Isolation.REPEATABLE_READ)
public boolean saveSummaryIfCurrent(long productId, ...) {
  // The product_id index range includes hidden reviews and protects concurrent inserts
  // through InnoDB next-key locks at this method's explicit REPEATABLE READ isolation.
  entityManager.createNativeQuery("""
      SELECT id, rating, content, updated_at, visible
      FROM reviews FORCE INDEX (ix_reviews_product_visible_created)
      WHERE product_id = :productId FOR UPDATE
      """, Tuple.class) ...

- AI 요약을 만드는 동안 새 리뷰가 달리면, 요약은 **이미 낡은** 것이 된다.
- 저장 직전에 그 상품의 리뷰 **범위 전체**를 next-key 잠금으로 잡는다. 그러면 저장이 끝날 때까지 **새 리뷰 INSERT가 끼어들 수 없다**. 그 상태에서 “요약을 만들 때 본 리뷰 = 지금 리뷰”인지 비교하고, 같을 때만 저장한다.
- 격리 수준을 메서드에 **명시**하고, `FORCE INDEX`로 잠글 인덱스 범위까지 고정했다. 옵티마이저가 다른 인덱스를 고르면 잠금 범위가 달라지기 때문이다. 15강에서 다시 본다.
  • 당한 곳: 3강에서 본 체크아웃 멱등 행 교착(PR #332).
    • 아직 없는 멱등 키를 FOR UPDATE로 조회하면, 행이 없으니 그 자리의 간격이 잠긴다.
    • 서로 다른 회원 둘이 같은 간격을 잠근 뒤 각자 INSERT하려 하면, 서로의 간격 잠금을 기다리며 교착이 난다.
    • 그래서 그 잠금을 제거했다. 같은 메커니즘이 한 곳에서는 보호막이고 다른 곳에서는 함정이었던 것이다.

9강 정리

  • 도구 선택 기준은 쿼리의 성격이다.
    • 엔티티 상태 전이 → JPA
    • 고정 조회 → JPQL
    • 선택 조건 → Querydsl(범위 제한)
    • MySQL 고유 문법·정밀 잠금 → 네이티브 SQL
    • 일반 경로 밖 도구 → JdbcTemplate
    • “네이티브 0개”는 목표가 아니다. SQL의 의미를 보존하는 것이 목표다.
  • 영속성 컨텍스트: 벌크 @Modifying UPDATE는 1차 캐시를 거치지 않는다. 그래서 flushAutomatically(앞)와 clearAutomatically(뒤)가 필요하고, 비운 뒤에는 옛 객체를 믿지 않는다.
  • 트랜잭션 두 방식
    • @Transactional은 메서드 단위다.
    • TransactionTemplate은 외부 결제사 호출을 트랜잭션 밖으로 빼기 위해 쓴다. 대가는 PROCESSING 고립 틈이다.
    • 격리 수준은 트랜잭션을 여는 바깥쪽이 정한다. 안쪽 REQUIRED의 격리 수준은 무시된다.
  • OSIV를 끈 이유: 요청 내내 커넥션을 쥐고, 뷰에서 예측 못 한 SQL이 나가기 때문이다. 트랜잭션이 아니라 EntityManager가 열려 있는 것이다.
  • MVCC
    • REPEATABLE READ의 일반 SELECT는 첫 읽기의 스냅샷을, UPDATE와 잠금 읽기는 최신 커밋을 본다.
    • 이 차이가 재고 CAS 충돌을 만들었고, 잠금 읽기 추가(PR #336)로 풀었다. CAS는 겹친 방어선으로 남았다.
  • 간격 잠금: 리뷰 요약은 이것으로 새 리뷰 끼어들기를 막았고, 체크아웃 멱등 행은 이것 때문에 교착이 났다.
  • 5강 미확인 해결: READY → PROCESSING 전이는 결제 엔티티가 아니라, FOR UPDATE 아래의 서비스 조건문(트랜잭션 ①)이 지킨다.

9강에서 남긴 미확인 항목

  • 카테고리 관리에서 READ_COMMITTED를 고른 직접적인 이유
  • 공유 SKU 잠금 읽기 이후 인기 SKU의 대기 시간과 처리량 측정치(28강)
  • 리뷰 요약 주석의 OSIV 언급이 남은 경위(15강)

10강. 회원 배송지 CRUD: 가장 단순한 기능으로 모든 층을 꿰기

이번 강의의 목표

  • 1~9강에서 배운 층(요청 경로, 소유권, 트랜잭션, 엔티티, SQL, 테스트)이 가장 단순한 기능 하나에서 어떻게 맞물리는지 처음부터 끝까지 따라간다.
  • “기본 배송지는 하나만”이라는 규칙을 어디에 두느냐에 따라 설계가 어떻게 달라지는지 비교한다.
  • saveAndFlush가 꼭 필요했던 이유를 9강의 플러시 개념으로 설명한다.
  • 이 단순한 기능에도 남아 있는 동시성 빈틈과 테스트 빈틈을 찾는다.

1. 왜 배송지가 기준점인가

배송지는 회원이 자기 배송지를 만들고, 보고, 고치고, 지우고, 기본으로 지정하는 기능이다. 외부 결제사도, 재고도, 상태 전이도 없다. 그래서 지금까지 배운 층을 잡음 없이 볼 수 있다. 이후 강의에서 체크아웃이나 구독 명령이 복잡해 보일 때, “배송지에서는 이 층이 어떻게 생겼었지?”로 돌아오면 된다.

확인 API는 다섯 개, 구독 배송지까지 여섯 개다.

// member/address/api/MemberAddressController.java (요지)
@GetMapping("/addresses")                         → 200 목록
@PostMapping("/addresses")                        → 201 Created + Location: /api/addresses/{id}
@PatchMapping("/addresses/{addressId}")           → 204 No Content
@DeleteMapping("/addresses/{addressId}")          → 204 No Content
@PutMapping("/addresses/{addressId}/default")     → 204 No Content
@PutMapping("/subscriptions/{subscriptionId}/shipping-address") → 204 (구독 배송지 스냅샷)
  • 생성은 201 + Location 헤더, 본문 없는 성공은 204다. 3강에서 본 HTTP 계약 정리 결정이 여기서도 지켜진다.
  • 모든 메서드의 첫 인자는 @AuthenticationPrincipal AuthenticatedMemberPrincipal principal이다. 8강에서 본 대로 회원 ID는 세션 인증에서만 온다.

2. 물리 ERD: “기본 배송지”를 어디에 저장할까

확인 배송지 테이블은 V13에서 생겼다.

-- V13__add_commerce_supporting_domains.sql (발췌)
CREATE TABLE member_addresses (
    id BIGINT NOT NULL AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    name VARCHAR(100) NOT NULL,              -- "집", "회사" 같은 별칭
    recipient_name VARCHAR(100) NOT NULL,
    recipient_phone VARCHAR(30) NOT NULL,
    postal_code VARCHAR(20) NOT NULL,
    address_line1 VARCHAR(255) NOT NULL,
    address_line2 VARCHAR(255) NULL,
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL,
    CONSTRAINT pk_member_addresses PRIMARY KEY (id),
    CONSTRAINT fk_member_addresses_member FOREIGN KEY (member_id) REFERENCES members (id)
) ...;

ALTER TABLE members
    ADD COLUMN default_address_id BIGINT NULL,
    ADD CONSTRAINT fk_members_default_address
        FOREIGN KEY (default_address_id) REFERENCES member_addresses (id);

눈여겨볼 점은 member_addresses에 is_default 컬럼이 없다는 것이다. 대신 members 행이 기본 배송지를 가리킨다. 두 설계를 나란히 놓으면 차이가 보인다.

  • A의 강점: 규칙이 구조에 있다. 컬럼 하나에는 값이 하나만 들어간다. 그래서 “기본 배송지는 최대 하나”가 어떤 코드 버그로도 깨지지 않는다. 기본을 바꾸는 일도 members 한 행의 UPDATE 하나다. 4강의 PRIMARY KEY (subscription_id)로 pending을 최대 하나로 만든 것과 같은 발상이다. 개수 제약을 조건문이 아니라 스키마 모양으로 표현했다.
  • B의 약점. 플래그 방식은 직관적이지만, 두 요청이 동시에 서로 다른 주소를 기본으로 지정하면 두 행이 모두 1이 될 수 있다. 막으려면 5강에서 본 “생성 컬럼 + UNIQUE”(MySQL에는 부분 인덱스가 없으니)를 쓰거나, 회원 행을 잠가 직렬화해야 한다.
  • A의 약점 1: 같은 회원의 주소라는 보장이 없다. 해석 fk_members_default_address는 default_address_id가 어떤 배송지든 존재하기만 하면 통과시킨다. 회원 7의 기본 배송지로 회원 8의 주소를 가리키는 행도 DB는 막지 못한다.
    • 지금은 애플리케이션이 findByIdAndMemberId로 소유권을 확인한 주소만 지정하므로 실제로 일어나지 않는다(5절).
    • DB로 막으려면 4강의 복합 외래 키 기법을 쓰면 된다. member_addresses에 UNIQUE (id, member_id)를 두고, members의 (default_address_id, id)가 그것을 참조하게 한다. 플랜과 플랜 버전에서 이미 쓴 방법인데 여기서는 쓰지 않았다.
  • A의 약점 2: 순환 참조. member_addresses → members, members → member_addresses로 서로를 가리킨다. 6강에서 본 대로 테이블을 다 만든 뒤 ALTER TABLE로 FK를 나중에 붙였다. 삭제 순서도 신경 써야 한다(6절).

3. JPA 엔티티: 같은 컬럼을 두 번 매핑하는 이유

// member/domain/MemberAddress.java (발췌)
@Entity
@Table(name = "member_addresses")
@Getter
@NoArgsConstructor(access = lombok.AccessLevel.PROTECTED)
public class MemberAddress {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(name = "member_id", nullable = false)
  private Long memberId;                                    // ① 값으로 매핑

  @ManyToOne(fetch = FetchType.LAZY)
  @JoinColumn(name = "member_id", insertable = false, updatable = false)
  private Member member;                                    // ② 같은 컬럼을 연관관계로, 읽기 전용
  ...
}

// member/domain/Member.java (발췌)
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "default_address_id")
private MemberAddress defaultAddress;

public void assignDefaultAddress(MemberAddress address) { this.defaultAddress = address; }
public void clearDefaultAddress() { this.defaultAddress = null; }
  • ① 과 ② 가 같은 member_id 컬럼을 가리킨다. 원리 JPA는 한 컬럼을 두 필드가 동시에 쓰면 어느 값을 INSERT할지 정할 수 없어 시작 시 오류를 낸다. 그래서 ②에 insertable = false, updatable = false를 붙여 읽기 전용으로 만들었다. 쓰기는 ①의 Long memberId로만 한다.
    • 해석 이렇게 하면 배송지를 만들 때 Member 엔티티를 불러오지 않고 ID만으로 저장할 수 있다. 5강에서 본 “다른 애그리거트는 ID로 참조” 원칙을 지키면서, 필요하면 연관관계로 탐색할 길도 남긴 절충이다.
  • @NoArgsConstructor(access = PROTECTED). 원리 JPA(Hibernate)는 조회 결과로 객체를 만들 때와 지연 로딩 프록시를 만들 때 인자 없는 생성자가 필요하다. protected로 두면 JPA는 쓸 수 있지만, 다른 패키지의 코드가 빈 배송지를 함부로 만들 수는 없다.
  • IDENTITY 전략. MySQL의 AUTO_INCREMENT를 쓴다. 원리 ID는 INSERT를 해야 알 수 있으므로, Hibernate는 이 엔티티를 persist하는 즉시 INSERT를 실행한다. 트랜잭션 끝까지 모았다가 보내는 쓰기 지연이 이 엔티티의 INSERT에는 적용되지 않는다.
  • 기본 배송지는 @ManyToOne이다. 회원 한 명이 가리키는 주소는 하나지만, DB 모양은 단순한 외래 키 컬럼이다. @ManyToOne은 그 FK 컬럼을 가장 있는 그대로 매핑하는 방법이다.
  • 상태 변경 메서드가 있다. MemberAddress.update(...), Member.assignDefaultAddress(...). 5강의 구독 V2 엔티티(생성자뿐)와 달리, 여기는 엔티티 메서드 + 변경 감지(dirty checking) 로 수정하는 평범한 JPA 스타일이다. 9강에서 본 “엔티티 상태 전이 → JPA”의 전형이다.

4. HTTP 계약: 검증과 PATCH의 의미

// member/address/api/MemberAddressRequest.java
public record MemberAddressRequest(
    @NotBlank @Size(max = 100) String name,
    @NotBlank @Size(max = 100) String recipientName,
    @NotBlank @Size(max = 30)  String recipientPhone,
    @NotBlank @Size(max = 20)  String postalCode,
    @NotBlank @Size(max = 255) String addressLine1,
    @Size(max = 255)           String addressLine2) {}
  • 검증 길이가 DB 컬럼 길이와 같다. VARCHAR(100)이면 @Size(max = 100)이다. 길이 초과를 DB가 거절하면 SQL 오류(500)가 되지만, 여기서 막으면 필드별 400(VALIDATION_FAILED)이 된다. 8강에서 본 공통 검증 처리기가 이 오류를 필드 이름순으로 정렬해 돌려준다.
    • @Valid가 언제, 누구에 의해 실행되는지는 망나니개발자의 「@Valid와 @Validated를 이용한 유효성 검증의 동작 원리」가 자세히 설명한다. 컨트롤러 인자에 붙은 @Valid는 인자를 만드는 단계(ArgumentResolver)에서 검증되고, 실패하면 MethodArgumentNotValidException이 난다.
  • 해석 전화번호·우편번호 형식은 검사하지 않는다. 길이만 본다. recipientPhone = "아무 글자"도 통과한다. 배송사 연동을 하면 바로 문제가 될 부분이라, 개선 후보다(@Pattern 또는 값 객체).
  • addressLine2만 @NotBlank가 없다. 상세 주소는 비워도 되고, DB도 NULL 허용이다. 검증과 스키마가 서로 맞는다.

PATCH인데 사실은 PUT

수정 API는 @PatchMapping인데 요청은 생성과 같은 MemberAddressRequest다. 필수 필드 다섯 개를 다 보내야 하고, 서비스는 모든 필드를 덮어쓴다.

  • 원리 HTTP 의미로 보면 “리소스 전체를 보낸 값으로 바꾼다”는 PUT이다. PATCH는 “보낸 필드만 바꾼다”는 부분 수정이다.
  • 개발하는 곰돌이의 「실무에서의 PUT과 PATCH에 대한 개인적인 생각 정리」는 이 혼동이 실무에서 흔하다고 짚는다. 교과서 정의(PUT은 전체 대체, 빠진 속성은 null)와 달리, 실무에서는 일부만 수정하는 API도 PUT으로 부르는 경우가 많다는 것이다. 글은 결국 클라이언트 관점에서, 팀이 규칙을 정하고 협의해 쓰면 된다고 결론 낸다.

  • 해석 PawCycle 안에도 두 방식이 섞여 있다. 3강에서 본 쿠폰 관리 PATCH는 보낸 필드만 병합하고, 명시적 null과 생략을 구분한다(진짜 PATCH). 배송지 PATCH는 전체 대체다. 같은 동사가 다른 의미로 쓰이는 셈이다. 계약 문서에 “배송지 PATCH는 전체 필드 필수”라고 적혀 있는 한 동작에는 문제가 없지만, 일관성의 관점에서는 PUT이 더 정직하다.

5. 소유권: 남의 배송지는 “없다”

// MemberAddressApplicationService (발췌)
MemberAddress address = addresses
    .findByIdAndMemberId(addressId, memberId)                    // SELECT ... WHERE id=? AND member_id=?
    .orElseThrow(() -> notFound("ADDRESS_NOT_FOUND"));           // 404
  • 조회 조건에 회원 ID를 넣는다. “일단 ID로 찾고, 주인인지 검사”가 아니라 처음부터 내 것만 찾는다. 남의 주소는 조회 결과가 비어 있으니 “존재하지 않음”과 구별되지 않는다. 4강 MVP1부터 이어진 “타인 자원은 403이 아니라 404” 원칙이다.
  • 이 방식이 막는 공격을 IDOR(Insecure Direct Object Reference)라 한다. URL의 ID 숫자만 바꿔서 남의 자원에 접근하는 공격이다. 배움을 남기다의 「인증은 있는데 인가가 없었다: IDOR 허점 분석」은 제목 그대로 이 문제를 다룬다. 로그인(인증)은 확인했지만, 그 자원이 그 사람 것인지(인가) 는 확인하지 않은 상황이다.
  • 기록 다른 기능은 한 단계 더 나아갔다. 결제 승인, 리뷰·문의 수정, 회원 쿠폰은 ID와 회원 ID를 함께 PESSIMISTIC_WRITE(FOR UPDATE) 조건에 넣는다. 소유권 확인과 잠금을 한 번에 하는 것이다. 배송지는 소유권만 확인하고 잠그지는 않는다. 이 차이가 7절의 동시성 빈틈으로 이어진다. 인가 전체 구조는 12강에서 본다.

6. 트랜잭션과 플러시: saveAndFlush가 꼭 필요했던 이유

기본 배송지를 바꾸는 코드를 보자.

@Transactional
public void makeDefault(long memberId, long addressId) {
  Member member = requireMember(memberId);
  MemberAddress address = addresses.findByIdAndMemberId(addressId, memberId)
      .orElseThrow(() -> notFound("ADDRESS_NOT_FOUND"));
  member.assignDefaultAddress(address);
  members.saveAndFlush(member);                   // ← 왜 그냥 save가 아니라 saveAndFlush인가
  subscriptionShipping.releaseAddressHolds(memberId);
}

member는 이미 영속 상태라 변경 감지로 커밋 때 UPDATE가 나간다. 그런데도 saveAndFlush로 지금 당장 UPDATE를 보낸다. 이유는 바로 다음 줄에 있다.

// subscription/persistence/SubscriptionShippingPersistenceAdapter.java (발췌)
public void releaseAddressHolds(long memberId) {
  mutation("""
      UPDATE subscription_schedules schedule
      JOIN subscriptions subscription ON subscription.id=schedule.subscription_id
      JOIN members member ON member.id=subscription.member_id
      ...
      SET schedule.status='SCHEDULED', schedule.hold_reason=NULL
      WHERE subscription.member_id=:member
        AND member.default_address_id IS NOT NULL               -- ← DB에서 직접 읽는다
        AND subscription.status='ACTIVE' AND snapshot.subscription_id IS NULL
        AND schedule.status='HELD' AND schedule.hold_reason='MISSING_SHIPPING_ADDRESS'
        AND context.order_id IS NULL
      """).setParameter("member", memberId).executeUpdate();
}

private MutationQuery mutation(String sql) {
  // Preserve JDBC visibility: the address service owns its explicit saveAndFlush calls.
  return entities.unwrap(Session.class).createNativeMutationQuery(sql)
      .setHibernateFlushMode(FlushMode.COMMIT);
}
  • 이 SQL이 하는 일. 4강에서 정기배송 회차가 배송지가 없어 HELD / MISSING_SHIPPING_ADDRESS로 보류될 수 있다고 봤다. 회원이 기본 배송지를 만들거나 지정하면, 그 보류를 즉시 풀어 다음 자동 주문이 처리할 수 있게 한다.
  • 조건이 DB의 members.default_address_id를 직접 읽는다. 그런데 방금 바꾼 기본 배송지는 아직 영속성 컨텍스트(메모리)에만 있을 수 있다.
  • 이 네이티브 UPDATE는 자동 플러시를 하지 않는다. FlushMode.COMMIT은 “커밋 때만 플러시하라”는 뜻이다. 원리 9강에서 본 대로 Hibernate는 보통 JPQL이나 네이티브 쿼리 직전에 관련 변경을 자동으로 플러시한다(AUTO). 이 쿼리는 일부러 그것을 끄고, 플러시 책임을 호출하는 배송지 서비스에 넘겼다. 주석이 그 계약을 적는다. “배송지 서비스가 명시적 saveAndFlush 호출을 소유한다.”
  • saveAndFlush를 빼면? 메모리에서는 기본 배송지가 지정됐는데 DB에는 아직 NULL이다. 그러면 보류 해제 SQL이 default_address_id IS NOT NULL 조건에 걸려 아무것도 풀지 않는다. 사용자는 배송지를 등록했는데 정기배송은 계속 멈춰 있게 된다.
  • 확인 이 순서는 테스트가 지킨다. SubscriptionOrderAutomationServiceIntegrationTests.makeDefaultFlushesBeforeReleasingShippingHolds()가 이 시나리오를 검증한다.
    • 회원의 기본 배송지를 NULL로 만들고, 회차 세 개를 HELD로 둔다.
    • makeDefault를 호출한 뒤 자격이 있는 회차만 SCHEDULED로 풀렸는지 확인한다.
    • 이미 주문이 생긴 회차, 구독 배송지 스냅샷이 있는 회차는 풀리지 않아야 한다.
  • 영속성 컨텍스트와 플러시의 기본은 행복한 개발자의 「Spring jpa save(), saveAndFlush() 제대로 알고 쓰기」와 9강 참고 자료의 준현 · JPA 플러쉬가 설명한다. 두 글 모두 save는 영속성 컨텍스트에만 반영하고 커밋 때 SQL을 보내지만, saveAndFlush는 즉시 SQL을 보낸다는 차이를 다룬다.

설계 평가 해석 배송지 서비스가 정기배송의 회차 상태까지 바꾸는 것은 도메인 간 결합이다. 장점은 “배송지 등록 = 보류 해제”가 한 트랜잭션이라 어긋날 수 없다는 것이다. 단점은 배송지 코드가 정기배송의 보류 규칙을 알아야 하고, 플러시 순서라는 보이지 않는 계약이 생긴다는 것이다. 대안은 배송지 변경 이벤트를 발행하고 정기배송 쪽이 반응하게 하는 것이다(Spring @TransactionalEventListener 등). 그러면 결합은 줄지만 같은 트랜잭션 보장을 어떻게 유지할지 다시 설계해야 한다.

7. 동시성: 단순한 기능에도 빈틈은 있다

확인 배송지 서비스는 회원 행도, 배송지 행도 잠그지 않는다. requireMember는 members.findById(일반 조회)이고, 배송지도 findByIdAndMemberId(일반 조회)다. 동시 요청이 오면 어떻게 될까? 세 가지 상황을 따져 보자. 이 절의 분석은 모두 해석이며, 테스트로 재현된 것은 아니다.

상황 1. 첫 배송지를 두 개 동시에 만든다.

  • 두 트랜잭션 모두 “기본 배송지 없음”을 읽고, 각자 자기 주소를 기본으로 지정한다.
  • 같은 members 행을 UPDATE하므로 둘째는 첫째의 커밋을 기다렸다가 덮어쓴다. 결과적으로 나중에 커밋한 주소가 기본이 된다.
  • 그래도 기본은 여전히 하나다. 2절의 “부모가 가리키기” 설계가 바로 여기서 값을 한다. 플래그 방식이었다면 두 행이 모두 기본이 됐을 것이다.

상황 2. 같은 주소를 동시에 고친다.

  • 두 PATCH가 같은 주소를 읽고 각자 덮어쓴다. 나중 커밋이 먼저 커밋을 통째로 지운다.
  • 이것을 갱신 분실(lost update)이라 한다. @Version 같은 낙관적 잠금이 없어서 생긴다.
  • 배송지는 전체 대체 수정이라 “둘 중 마지막 사람의 의도”가 남는다. 업무적으로 큰 문제는 아닐 수 있다.

상황 3. 기본 배송지 A를 지우는 동시에 A를 다시 기본으로 지정한다. 이것이 가장 흥미롭다.

  • 데이터는 지켜진다. 외래 키가 “없는 주소를 기본으로 지정”하는 것을 DB에서 거절한다. 6강의 “제약은 마지막 방어선”이 여기서 일한다.
  • 사용자 경험은 지켜지지 않는다. 그 거절은 Spring에서 DataIntegrityViolationException이 되고, 배송지 예외 처리기의 catch-all에 걸려 500 MEMBER_ADDRESS_UNAVAILABLE 이 된다. 정상적인 경쟁 상황인데 서버 오류로 보인다.
    • 미확인 이 시나리오를 재현하는 테스트는 저장소에서 찾지 못했다. 위 흐름은 코드와 InnoDB 잠금 동작으로 추론한 것이다.

갱신 분실과 그 해결책은 개인 블로그 두 편이 그림과 함께 잘 설명한다.

  • 주니의 「갱신 분실(lost update) 문제를 어떻게 해결할 수 있을까」는 “매일 자정 재화 1개 지급”과 “사용자의 재화 사용”이 겹치는 실제 상황에서 출발한다. synchronized가 @Transactional과 왜 잘 맞지 않는지 검토하고, 최종적으로 balance = balance + 1 같은 원자적 UPDATE 쿼리를 택한 과정을 적는다. 9강에서 비교한 “읽지 않고 조건부 UPDATE 한 번” 방식과 같은 결론이다.

출처: 주니 · 갱신 분실(lost update) 문제를 어떻게 해결할 수 있을까. tistory 그림이라 11월 30일 만료.

  • 후디의 「JPA의 낙관적 락과 비관적 락을 통해 엔티티에 대한 동시성 제어하기」는 @Version(낙관적)과 @Lock(PESSIMISTIC_WRITE)(비관적)을 JPA 코드로 비교한다. 이 블로그의 그림은 자체 사이트에 있어 만료되지 않는다.

8. 배송지를 지워도 과거 주문은 안전한가

배송지는 수정·삭제가 자유롭다. 그런데 이미 그 주소로 나간 주문은 어떻게 될까?

  • 확인 주문은 주소를 참조하지 않고 복사한다. 6강에서 본 orders 테이블에는 address_id 같은 FK가 없다. 대신 recipient_name, recipient_phone, postal_code, address_line1, address_line2를 주문 시점의 값으로 갖고 있다. 4강의 스냅샷 원칙이 주소에도 적용된 것이다.
    • 배송지를 고쳐도 과거 주문의 배송 주소는 바뀌지 않는다.
    • 배송지를 지워도 FK 충돌이 없다.
  • 확인 정기배송 배송지도 별도 스냅샷이다. subscription_shipping_snapshots가 구독마다 주소 사본을 갖는다. 계약 문서는 “회원 주소 변경은 기존 구독 스냅샷이나 생성된 주문을 변경하지 않는다”고 적는다. 그래서 6절의 보류 해제 SQL에도 snapshot.subscription_id IS NULL 조건이 있다. 구독 전용 주소가 이미 있는 구독은 회원 기본 주소와 무관하다.
  • 삭제 순서. 지우려는 주소가 기본이면 먼저 members.default_address_id를 NULL로 바꾸고 나서 주소를 지운다. 순서가 반대면 fk_members_default_address가 삭제를 막는다. 2절의 순환 참조가 여기서 순서를 강제한다.
  • 미확인 기본 주소를 지우면 다른 주소가 자동으로 기본이 되지 않는다. 코드는 기본을 비우기만 한다. 이것이 의도된 제품 결정인지는 기록을 찾지 못했다. 그 상태에서 정기결제 회차가 오면 HELD / MISSING_SHIPPING_ADDRESS가 될 수 있다(23강).

9. 테스트: 무엇이 지켜지고 있고, 무엇이 비어 있나

확인 배송지 관련 테스트는 세 곳에 있다.

테스트 지키는 것
MemberAddressApiIntegrationTests (4개) 빈 이름·긴 전화번호의 필드 오류 형식, 없는 주소의 404 계약, 구독 배송지의 옛 요청 형식(이름 없음) 허용
SubscriptionOrderAutomationServiceIntegrationTests 기본 배송지 지정·첫 배송지 생성 시 플러시 후 자격 있는 보류만 해제
SubscriptionShippingWriteProtocolIntegrationTests 등 다른 시나리오의 준비 단계로 배송지 생성·기본 지정을 사용

비어 있는 것도 분명하다.

  • “첫 배송지는 자동으로 기본이 된다”는 규칙을 직접 검증하는 테스트가 없다.
  • “기본 배송지를 지우면 기본이 비워진다”를 검증하는 테스트가 없다.
  • 다른 회원의 주소를 기본으로 지정하려 하면 404인지 검증하는 테스트가 없다. 2절에서 본 대로 DB가 이것을 막지 못하므로, 이 테스트가 사실상 유일한 방어선이어야 한다.
  • 7절의 동시성 시나리오 테스트가 없다.

해석 배송지는 “단순한 CRUD라 테스트할 게 없다”고 여기기 쉬운 기능이다. 하지만 이 기능에도 스키마가 보장하지 않는 규칙(같은 회원 소유)과 도메인 간 부수 효과(보류 해제)가 있다. 테스트는 정확히 그 두 곳에 가장 먼저 필요하다. 지금은 부수 효과 쪽만 지켜지고 있다.

같이 읽을 자료

  • 망나니개발자 · @Valid와 @Validated를 이용한 유효성 검증의 동작 원리: @Valid가 실행되는 위치와 예외
  • 개발하는 곰돌이 · 실무에서의 PUT과 PATCH: 교과서 정의와 실무 관행의 차이
  • 배움을 남기다 · 인증은 있는데 인가가 없었다: IDOR 허점 분석: 소유권 검증이 빠졌을 때
  • 행복한 개발자 · Spring jpa save(), saveAndFlush() 제대로 알고 쓰기: 플러시 시점의 차이
  • 주니 · 갱신 분실 문제를 어떻게 해결할 수 있을까: 원자적 UPDATE로 푼 실제 사례
  • 후디 · JPA의 낙관적 락과 비관적 락: @Version과 @Lock 비교

10강 정리

  • “기본 하나”를 스키마 모양으로 표현했다. members.default_address_id 포인터 하나라서 어떤 버그로도 기본이 둘이 될 수 없다. 대신 FK는 “같은 회원의 주소”까지는 보장하지 않는다. 4강의 복합 FK 기법으로 막을 수 있지만 적용하지 않았다.
  • JPA 매핑
    • 같은 member_id 컬럼을 값(쓰기)과 읽기 전용 연관관계로 두 번 매핑해, ID 참조와 탐색을 함께 얻었다.
    • IDENTITY라서 INSERT가 즉시 나간다.
  • HTTP 계약
    • 검증 길이와 DB 길이가 같다. 형식 검증(전화번호)은 없다.
    • PATCH인데 실제로는 전체 대체(PUT 의미)다. 쿠폰의 진짜 PATCH와 일관되지 않는다.
  • 소유권: 조회 조건에 회원 ID를 넣어 남의 주소는 404다(IDOR 방어). 다만 다른 기능처럼 잠금과 함께 쓰지는 않는다.
  • saveAndFlush의 이유: 바로 뒤의 네이티브 보류 해제 SQL이 FlushMode.COMMIT이라 자동 플러시를 하지 않는다. 기본 배송지 변경이 먼저 DB에 있어야 한다. 테스트가 이 순서를 지킨다.
  • 동시성 빈틈: 잠금이 없어서 다음 세 가지가 생길 수 있다. 회원 행 FOR UPDATE 하나로 정리된다.
    • 첫 기본 배송지가 뒤바뀜
    • 갱신 분실
    • 삭제와 기본 지정이 겹칠 때 FK 위반이 500으로 보임
  • 스냅샷: 주문과 구독은 주소를 복사해 갖는다. 그래서 배송지 수정·삭제가 과거를 바꾸지 않는다.
  • 테스트 빈틈: 기본 배송지 규칙, 타인 주소 기본 지정, 동시성 테스트가 없다.

  • 7절 상황 3(삭제와 기본 지정의 경쟁)이 실제로 500이 되는지: 실험 단계 후보

11강. 세션 로그인과 CSRF: 로그인 한 번이 만드는 것들

이번 강의의 목표

  • PawCycle이 JWT가 아니라 서버 세션을 고른 이유와 그 대가를 안다.
  • 로그인 요청 하나가 세션, 쿠키, CSRF 토큰을 어떤 순서로 만들고 바꾸는지 코드로 따라간다.
  • 세션 고정 공격, CSRF, 계정 존재 노출이라는 세 가지 공격을 각각 무엇이 막는지 이해한다.
  • 메모리 세션의 한계(재시작, 확장, 권한 변경 반영)를 알고 개선 방향을 판단한다.

1. 왜 JWT가 아니라 세션인가

두 방식의 차이

HTTP는 요청마다 독립적이라 서버가 “이 요청이 누구인지”를 매번 알아내야 한다. 방법은 크게 둘이다.

  • 세션: 서버가 로그인 정보를 자기 메모리(또는 저장소) 에 두고, 브라우저에는 그것을 찾는 열쇠(세션 ID) 만 쿠키로 준다.
  • JWT: 서버가 로그인 정보를 서명한 토큰으로 만들어 브라우저에 주고, 요청마다 그 토큰을 검증한다. 서버는 아무것도 저장하지 않는다.

kimgunwooo의 「로그인 인증 방식 차이 (쿠키, 세션, JWT)」는 이전 프로젝트에서 “JWT가 제일 좋다는 얕은 지식으로” JWT를 골랐던 경험에서 출발한다. 그리고 HTTP의 비연결성·무상태성부터 세 방식을 차례로 비교한다.

출처: velog @kimgunwooo · 로그인 인증 방식 차이(velog 그림은 만료되지 않습니다)

쿠키와 세션이 실제로 주고받는 모습은 준현의 「쿠키와 세션」이 그림으로 보여 준다.

그림의 ③~⑥이 이 코드 한 메서드다.

// member/application/AuthApplicationService.java (발췌)
@Transactional(readOnly = true)
public AuthenticatedMemberPrincipal login(String email, String password,
                                         HttpServletRequest request, HttpServletResponse response) {
  NormalizedLoginCredentials credentials = emailNormalizer.normalize(email, password);   // ③
  Authentication authentication =
      credentialAuthenticator.authenticate(credentials.email(), credentials.password());  // ④
  sessionAuthenticationStrategy.onAuthentication(authentication, request, response);      // ⑤
  SecurityContext context = SecurityContextHolder.createEmptyContext();
  context.setAuthentication(authentication);
  SecurityContextHolder.setContext(context);
  securityContextRepository.saveContext(context, request, response);                     // ⑥
  return (AuthenticatedMemberPrincipal) authentication.getPrincipal();
}
  • Spring Security의 기본 로그인 폼(formLogin)을 쓰지 않았다. 기본 폼은 HTML 폼 POST와 리다이렉트를 전제로 한다. PawCycle은 JSON을 받고 JSON을 돌려주는 API다({ memberId }, 실패 시 401 INVALID_CREDENTIALS). 그래서 컨트롤러에서 필요한 부품만 직접 조립했다.
    • 인증: AuthenticationManager → MemberAuthenticationProvider
    • 세션 처리: SessionAuthenticationStrategy
    • 저장: SecurityContextRepository
    • 7강에서 본 SecurityConfig가 이 부품들을 Bean으로 만든다.
  • ⑥을 직접 해야 하는 이유. 원리 Spring Security 6부터 SecurityContextHolder에 인증을 넣는 것만으로는 세션에 자동 저장되지 않는다. 명시적으로 securityContextRepository.saveContext(...)를 불러야 한다. 이 줄을 빼면 로그인 응답은 성공인데 다음 요청에서 다시 익명이 된다. 직접 로그인 API를 만들 때 가장 흔한 실수다.
    • SecurityContextHolder가 스레드에 컨텍스트를 두는 방식은 준현의 「스프링 시큐리티 SecurityContextHolderStrategy」가 정리한다. 8강의 ThreadLocal 이야기가 여기서도 이어진다.
  • 세션에는 엔티티가 아니라 작은 기록이 들어간다. 인증 성공 시 세션에 저장되는 주체는 AuthenticatedMemberPrincipal(memberId, role)이라는 record 하나다. 비밀번호 해시도, Member 엔티티도 넣지 않는다. 클래스 주석도 “session-safe principal만 반환한다”고 적는다. 8강에서 @AuthenticationPrincipal로 꺼내 쓰던 그 객체다.

3. 세션 고정 공격: 로그인하면 열쇠를 바꾼다

그림의 ⑤에서 세션 ID가 S1 → S2로 바뀌었다. 왜 바꿀까?

pjs-world의 「세션 고정 공격(Session Fixation)과 Spring Security의 대응 전략」이 공격을 이렇게 정의한다.

  • 공격자가 먼저 정상적인 세션 ID를 하나 발급받는다.
  • 그 ID를 피해자의 브라우저에 심는다(링크, 쿠키 주입 등).
  • 피해자가 그 세션으로 로그인하게 유도한다.
  • 서버가 로그인 후에도 같은 세션 ID를 유지하면, 공격자는 자기가 아는 그 ID로 피해자의 로그인 상태를 그대로 쓴다.

출처: pjs-world · 세션 고정 공격과 Spring Security의 대응 전략. tistory 그림이라 11월 30일 만료.

PawCycle의 방어는 두 줄이다.

// common/security/SecurityConfig.java (발췌)
.sessionManagement(session -> session.sessionFixation(fixation -> fixation.changeSessionId()));

@Bean
SessionAuthenticationStrategy sessionAuthenticationStrategy(HttpSessionCsrfTokenRepository csrfTokenRepository) {
  return new CompositeSessionAuthenticationStrategy(List.of(
      new ChangeSessionIdAuthenticationStrategy(),          // 세션 ID 교체
      new CsrfAuthenticationStrategy(csrfTokenRepository)));  // CSRF 토큰 교체
}
  • changeSessionId vs newSession·migrateSession. 원리 서블릿 3.1의 HttpServletRequest.changeSessionId()는 세션 내용은 그대로 두고 ID만 바꾼다. 새 세션을 만들어 속성을 복사하는 방식보다 가볍다. 공격자가 아는 옛 ID는 그 순간부터 쓸모없어진다.
  • 두 전략을 묶었다. 로그인 순간 세션 ID와 CSRF 토큰도 함께 바꾼다. 로그인 전의 토큰이 노출됐더라도 로그인 후에는 쓸 수 없다. 대신 브라우저는 로그인 직후 새 토큰을 받아야 한다(그림의 ⑦).
  • [주의] 2절의 코드가 이 전략을 직접 호출한다(sessionAuthenticationStrategy.onAuthentication(...)). 기본 로그인 폼을 쓰면 필터가 알아서 부르지만, 직접 만든 로그인 API에서는 빼먹기 쉬운 부분이다.

4. CSRF: 쿠키 인증의 숙제

공격의 원리

준현의 「CSRF 공격과 방어」가 원리와 방어 방법을 GET·POST 공격 예제와 함께 정리한다. 방어 방법으로는 Referrer 검사, CSRF 토큰, 더블 서브밋 쿠키를 다룬다.

핵심은 이것이다. 브라우저는 pawcycle.duckdns.org로 가는 요청이라면, 그 요청을 누가 시작했든 쿠키를 붙인다. 악성 사이트가 숨겨 둔 폼이 POST /api/subscriptions/42/commands/cancel을 보내도 피해자의 세션 쿠키가 따라간다. 서버는 정상 요청과 구분할 수 없다.

두 겹의 방어

확인 PawCycle은 두 가지를 함께 쓴다.

① CSRF 토큰 (서버 세션에 저장, 헤더로 전송)

@Bean
HttpSessionCsrfTokenRepository csrfTokenRepository() {
  HttpSessionCsrfTokenRepository repository = new HttpSessionCsrfTokenRepository();
  repository.setHeaderName("X-CSRF-TOKEN");
  repository.setParameterName("_csrf");
  return repository;
}

// member/api/AuthController.java
@GetMapping("/csrf")
ResponseEntity<CsrfTokenResponse> csrf(CsrfToken csrfToken) {
  return ResponseEntity.ok().cacheControl(CacheControl.noStore())       // 캐시 금지
      .body(new CsrfTokenResponse(csrfToken.getToken()));
}
  • 토큰은 서버 세션에 있고, 브라우저는 GET /api/auth/csrf로 받아 메모리에 들고 있다가 변경 요청마다 X-CSRF-TOKEN 헤더에 싣는다.
  • 악성 사이트는 이 토큰을 읽을 수 없다. 다른 출처의 응답 본문은 브라우저의 동일 출처 정책(SOP) 때문에 읽히지 않는다. 그래서 위조 요청에 올바른 헤더를 실을 수 없다.
  • 응답에 Cache-Control: no-store를 붙였다. 토큰이 브라우저나 프록시 캐시에 남지 않게 한다.

기록 쿠키 저장소 대신 세션 저장소를 고른 이유. 설계 단계에서 CookieCsrfTokenRepository(자바스크립트가 읽을 수 있는 XSRF-TOKEN 쿠키)를 대안으로 검토했다.

  • 쿠키 방식은 SPA에서 쓰기 편하지만, 쿠키·요청 처리기·재발급 처리에 비용이 든다.
  • 응답 헤더로 토큰을 주는 방식은 헤더 노출과 CORS 계약 비용이 든다.
  • 최종적으로 세션 저장 + JSON 엔드포인트 + 프론트 메모리 보관을 추천안으로 승인했다.
  • 대가도 함께 적었다. 익명 사용자의 csrf 호출도 세션을 만든다(그림 ①의 S1). 새로고침하면 토큰을 다시 받아야 한다.

server.servlet.session.cookie.path=/
server.servlet.session.timeout=30m
  • 원리 SameSite=Lax면 다른 사이트에서 시작한 POST 요청에는 쿠키가 붙지 않는다. 위의 숨긴 폼 공격은 쿠키 없이 도착해 익명 요청이 된다.
  • 다른 사이트의 링크를 눌러 최상위 GET으로 이동할 때는 쿠키가 붙는다. 그래서 GET은 절대 상태를 바꾸면 안 된다. PawCycle의 모든 변경은 POST·PATCH·PUT·DELETE다.

준현의 「크롬 기본 SameSite 정책은 CSRF 공격에 안전한가?」는 여기에 중요한 함정을 짚는다.

  • 크롬 80부터 SameSite가 지정되지 않은 쿠키를 Lax처럼 취급한다.
  • 그런데 OAuth 리다이렉트 호환을 위해, 지정되지 않은 쿠키는 저장 후 처음 2분 동안 다른 사이트의 POST 폼 요청에도 붙도록 완화했다.
  • 즉 “기본값 Lax”는 진짜 Lax보다 약하고, 그 2분 동안은 CSRF에 여전히 취약하다.
  • 해석 PawCycle은 same-site=lax를 명시했으므로 이 완화 대상이 아니다. 설정 한 줄의 차이가 보안 경계를 바꾼다. 그리고 SameSite에 기대지 않고 토큰을 함께 쓰는 이유도 여기에 있다. 브라우저 정책은 바뀌고, 브라우저마다 다르다.

로그인에도 CSRF가 필요하다

POST /api/auth/login은 permitAll이지만, 확인 CSRF 검사는 인가 규칙과 별개로 모든 POST에 적용된다. 그래서 로그인 전에도 토큰을 받아야 한다(그림 ①). 이것이 막는 공격이 로그인 CSRF다.

  • 공격자가 피해자의 브라우저로 공격자 자신의 계정에 로그인시킨다.
  • 피해자는 모른 채 그 계정으로 결제 수단이나 주소를 등록하고, 공격자는 나중에 그 정보를 본다.
  • 기록 설계 단계 문서도 “CSRF는 인증 검사보다 먼저 403이 될 수 있다”고 적는다. 8강에서 본 대로 CSRF 필터가 인가 필터보다 앞에 있기 때문이다.

프론트는 실패한 POST를 자동으로 다시 보내지 않는다

기록 프론트엔드는 토큰을 메모리에 lazy하게 받고, 로그인 후 회전되면 새로 받으며, 익명이 되면 버린다.

CSRF_INVALID(8강의 403 코드)를 받으면 토큰은 새로 받지만, 원래 POST는 자동으로 재실행하지 않는다. 사용자가 결과를 확인하고 직접 다시 시도한다.

  • 해석 이유는 3강의 멱등성이다. 그 POST가 정말 실패했는지 클라이언트는 확신할 수 없다. 첫 구독 API처럼 멱등성 저장소가 없는 요청을 자동으로 다시 보내면 중복 생성이 될 수 있다. 4강의 “이전 POST 자동 재실행 금지” 결정과 같은 뿌리다.

3강에서 본 타이밍 부채널 방어의 실제 코드다.

  • 가입되지 않은 이메일에도 더미 해시로 BCrypt 비교를 한 번 한다. 그래서 “없는 회원”과 “틀린 비밀번호”가 비슷한 시간이 걸리고, 같은 401 INVALID_CREDENTIALS 를 받는다.
  • 인증 책임은 처음에 애플리케이션 서비스에 있었다. 이후 Spring Security의 AuthenticationProvider로 옮겼다(ARCH-010). 3강에서 미확인으로 남긴 “현재 코드 구조”가 이것이다.

BCrypt가 왜 일부러 느린지는 comgu의 「bcrypt 보안 분석: Salt와 Cost Factor를 통한 패스워드 보호」가 설명한다.

  • MD5·SHA-1 같은 일반 해시는 빠르기 때문에 대입 공격에 약하다.
  • BCrypt는 의도적으로 느린 연산(cost factor) 과 매번 다른 salt로 같은 비밀번호도 다른 해시를 만든다.
  • 확인 PawCycle은 new BCryptPasswordEncoder()(기본 cost 10)를 쓴다. 설계 문서는 해시 컬럼을 VARCHAR(100)으로 잡고 cost는 측정 전 미확정이라고 적었다. BCrypt 해시(60자)와 인코더 접두사가 바뀔 여유를 둔 길이다.

이메일 처리에도 세심한 결정이 있다. 기록

  • 앞뒤 공백·탭만 지운다.
  • 도메인만 소문자로 바꾸고, @ 앞부분(local-part)의 대소문자는 보존한다. 표준상 local-part는 대소문자를 구별할 수 있어서, 전부 소문자로 바꾸면 서로 다른 주소가 하나로 합쳐질 위험이 있기 때문이다.
  • 별칭 통합(+tag, Gmail의 점 무시)은 하지 않는다.

6. 쿠키 속성 하나하나의 의미

속성 값 막는 것
HttpOnly true 자바스크립트(document.cookie)로 세션 ID 읽기. XSS가 나도 세션 ID는 직접 훔칠 수 없다.
Secure true (기본값) HTTP 평문으로 쿠키 전송. 2강의 HSTS와 짝을 이룬다.
SameSite lax (명시) 다른 사이트의 POST에 쿠키가 붙는 것(4절)
Path / — 사이트 전체에서 사용
만료 없음(세션 쿠키) + 서버 유휴 30분 브라우저를 닫으면 쿠키가 사라지고, 30분 동안 요청이 없으면 서버 세션이 만료된다.

기록 설정이 새어 나간 교훈. 로컬 HTTP 개발을 위해 local-integration 프로필에 Secure=false를 두었던 적이 있다. 그런데 local-integration,production을 함께 켜는 조합에서 실행기는 막았지만, 프로필의 쿠키 완화 설정은 계속 로드됐다.

  • “기능을 실행하지 않는 것”과 “설정이 적용되지 않는 것”은 다르다.
  • 그래서 쿠키 완화를 프로필에서 빼고, 로컬 HTTP용 프로세스 환경 변수(SESSION_COOKIE_SECURE)로만 한정했다. 지금 ${SESSION_COOKIE_SECURE:true}의 기본값이 true인 이유다. 7강의 “관문이 보지 못하는 설정 경로” 교훈과 같은 계열이다.

7. 메모리 세션의 한계

확인 build.gradle에 Spring Session 의존성이 없다. 세션은 Tomcat 프로세스 메모리에 있다. 이 선택의 대가는 이렇다. 해석

  • 재시작·재배포 = 전원 로그아웃. 2강의 배포에서 backend 컨테이너를 교체하면 모든 세션이 사라진다. 사용자는 다음 요청에서 401을 받고 다시 로그인해야 한다. 무중단 배포를 미룬(DEFER) 상태라 지금은 큰 문제가 아니지만, 배포가 잦아지면 체감된다.
  • 서버를 늘리면 깨진다. 서버 B는 서버 A의 메모리 세션을 모른다. 해결책은 둘이다.
    • 로드 밸런서가 같은 사용자를 같은 서버로 보내는 스티키 세션: 서버가 죽으면 그 서버 사용자는 로그아웃된다.
    • 공유 세션 저장소: 준현의 「Redis를 활용한 Spring Session」이 설정 방법과 동작을 보여 준다.
    • 2강 트레이드오프 표에서 “서버 2대로 가려면 세션 공유 문제가 있다”고 했던 것이 이 이야기다.
  • 권한 변경이 바로 반영되지 않는다. 세션의 주체는 로그인 순간의 AuthenticatedMemberPrincipal(memberId, role) 복사본이다. 관리자가 어떤 회원의 역할을 USER로 낮춰도, 그 회원이 다시 로그인할 때까지 세션 속 역할은 ADMIN이다. 4강의 스냅샷이 여기서는 원치 않는 스냅샷이 된다. 기록 당시 관리자 기능은 역할 변경 API를 제공하지 않으므로 지금은 실제 문제가 아니다. 역할 변경 기능을 만들면 세션 무효화도 함께 설계해야 한다.

  return new CompositeLogoutHandler(
      new CsrfLogoutHandler(csrfTokenRepository),     // CSRF 토큰 제거

  • 로그아웃도 인증과 CSRF가 필요하다(.requestMatchers(POST, "/api/auth/logout").authenticated()). CSRF가 없으면 악성 사이트가 피해자를 강제로 로그아웃시킬 수 있다. 피해는 작지만, 로그인 CSRF와 엮으면 공격 흐름의 한 단계가 된다.
  • 세 처리기의 순서와 역할이 서버(세션), 보안 컨텍스트(스레드), 브라우저(쿠키) 세 곳을 모두 정리한다는 점이 중요하다. 하나라도 빠지면 어딘가에 로그인 흔적이 남는다.

11강 정리

  • 세션을 고른 이유: 같은 도메인, 서버 한 대, 즉시 무효화, HttpOnly로 숨기는 세션 ID. 대가는 CSRF 방어 필수와 메모리 세션의 한계다. JWT는 “기술 목록용 선도입”으로 기각됐다.
  • 로그인 흐름
    • CSRF 토큰 받기 → 로그인 POST(토큰 헤더) → 정규화 → BCrypt(더미 해시) → 세션 ID와 CSRF 토큰 교체 → SecurityContext를 직접 세션에 저장 → 새 토큰 다시 받기
    • Spring Security 6에서는 saveContext를 빼면 로그인이 유지되지 않는다.
  • 세 가지 공격과 방어
    • 세션 고정 → changeSessionId
    • CSRF → 세션 저장 토큰 + X-CSRF-TOKEN 헤더 + 명시적 SameSite=Lax(기본값 Lax는 2분 완화가 있어 더 약하다). 로그인·로그아웃에도 적용한다.
    • 계정 존재 노출 → 더미 해시와 같은 오류 응답
  • 쿠키 완화는 프로필이 아니라 프로세스 환경 변수로만: 설정은 실행하지 않아도 로드된다.
  • 메모리 세션의 한계: 재배포하면 전원 로그아웃, 확장하려면 Redis 세션, 권한 변경은 재로그인 전까지 반영되지 않는다.
  • 실패한 POST는 자동 재실행하지 않는다: 멱등성이 없는 요청의 중복을 막는다.

1. 인가의 세 관문

11강에서 "누구인가(인증)"를 다뤘다면, 이번 강의는 "이 사람이 이 일을 해도 되는가(인가)"다. PawCycle에서 이 판단은 한 곳에서 일어나지 않는다. 판단에 필요한 데이터가 다르기 때문에 세 곳으로 나뉜다.

그림의 마지막 줄이 이 강의의 요점이다.

  • ①은 URL만 보면 된다. 요청이 DB에 닿기 전에, 가장 싸게 판단한다.
  • ②는 그 행의 주인을 알아야 한다. DB를 봐야 한다.
  • ③은 그 행의 상태와 다른 행들(주문, 배송, 답변)까지 봐야 한다.

판단에 필요한 데이터가 다르니 판단하는 위치도 다르다. 이 세 관문을 하나로 합치려 하면 오히려 어색해진다.

2. 첫 관문: 역할과 URL 규칙

8강에서 본 인가 규칙을 다시 보자. 이번에는 역할 관점이다.

// common/security/SecurityConfig.java (발췌)
.requestMatchers(EndpointRequest.to("health", "prometheus")).permitAll()
.requestMatchers(HttpMethod.GET, "/api/products/*/reviews/me").authenticated()
.requestMatchers(HttpMethod.GET, "/api/products", "/api/products/**", "/api/categories", ...).permitAll()
.requestMatchers(HttpMethod.POST, "/api/auth/login").permitAll()
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/**").authenticated()
.anyRequest().denyAll()

// member/application/MemberAuthenticationProvider.java (발췌)
List.of(new SimpleGrantedAuthority("ROLE_" + member.getRole().name()))   // ROLE_USER / ROLE_ADMIN

hasRole("ADMIN")과 ROLE_ 접두사

  • 원리 Spring Security에서 역할(Role)은 ROLE_로 시작하는 권한(Authority) 이다. hasRole("ADMIN")은 내부적으로 ROLE_ADMIN 권한이 있는지 본다. hasAuthority("ADMIN")이라고 쓰면 접두사 없이 그대로 비교한다.
  • 그래서 인증 제공자가 권한을 만들 때 "ROLE_" + role로 접두사를 붙인다. 이 짝이 어긋나면, 예를 들어 "ADMIN"만 넣고 hasRole("ADMIN")으로 검사하면 관리자도 403을 받는다.

주리니e의 「역할(hasRole)과 권한(hasAuthority)의 차이는 무엇일까?」가 이 둘을 구분한다. 두 계정이 모두 SYSTEM 역할이어도 한 계정은 글 등록만, 다른 계정은 수정까지 할 수 있게 하려면 역할보다 세밀한 권한이 필요하다는 예로 설명한다.

출처: 주리니e · 역할(hasRole)과 권한(hasAuthority)의 차이. tistory 그림이라 11월 30일 만료.

확인 PawCycle은 역할이 USER, ADMIN 두 개뿐이고 세부 권한은 없다. 관리자는 모든 관리 기능을 쓸 수 있다.

  • 기록 관리자 기능 도입 때 역할 변경 API나 실제 관리자 계정 발급(provisioning)은 제공하지 않기로 했다. 기존 회원과 외부 역할 입력이 없는 신규 회원은 모두 USER다.
  • 해석 운영자가 여러 명이고 “재고만 조정할 수 있는 사람” 같은 구분이 필요해지면, 그때 hasAuthority("INVENTORY_WRITE") 같은 세부 권한으로 나눠야 한다. 지금 미리 만들지 않은 것은 4강의 YAGNI다.

규칙 순서가 곧 보안이다

dsjo의 「authorizeHttpRequests 우선순위 적용하기」는 실제로 겪은 문제를 보여 준다. /users/**에 permitAll을 먼저 걸고 그 아래에 /users/inactive를 관리자 전용으로 걸었더니, 관리자 규칙이 적용되지 않았다. 위에서부터 처음 맞는 규칙 하나만 쓰이기 때문이다.

출처: dsjo · authorizeHttpRequests 우선순위 적용하기. tistory 그림이라 11월 30일 만료.

PawCycle의 /api/products/*/reviews/me가 /api/products/**보다 위에 있는 이유가 정확히 이것이다(8강). 구체적인 규칙이 먼저, 넓은 규칙이 나중이다. 그리고 마지막 anyRequest().denyAll()이 “규칙을 깜빡한 경로”를 막는다.

확인 CommerceAdminAuthorizationIntegrationTests는 관리자 변경 API 목록을 파라미터로 돌며 같은 네 가지를 검사한다.

  • 관리자 영역에서 USER에게 404가 아니라 403을 주는 것은 의도된 차이다(6절).

두 번째 보안 체인 하나

확인 성능 측정용 설정이 @Order(1)로 별도의 보안 체인을 만든다.

// subscription/performance/SubscriptionBurstMeasurementSecurityConfiguration.java
@Profile("subscription-burst-measurement & !production & !prod")
class SubscriptionBurstMeasurementSecurityConfiguration {
  @Bean @Order(1)
  SecurityFilterChain subscriptionBurstMeasurementSecurityFilterChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/internal/performance/subscription-burst/**")
        .csrf(AbstractHttpConfigurer::disable)
        .authorizeHttpRequests(authorize -> authorize.anyRequest().permitAll());
    return http.build();
  }
}
  • 이 경로는 인증도 CSRF도 없이 열린다. 부하 측정 도구가 구독 데이터를 준비하고 흘려보내는 데 쓴다.
  • 보호 장치는 프로필 식 하나다. subscription-burst-measurement가 켜져 있고, production도 prod도 아닐 때만 등록된다. 컨트롤러에도 같은 프로필 조건이 붙어 있다.
  • 해석 7강과 11강에서 본 교훈(“관문이 보지 못하는 설정 경로”, “실행하지 않아도 설정은 로드된다”)을 떠올리면, 이런 체인은 프로필 이름이 바뀌거나 운영에서 다른 프로필명을 쓰는 순간 위험해진다. 운영 프로필 이름이 production인 지금은 안전하다. 그래도 7강의 ArchUnit처럼 “운영 이미지에 이 클래스가 활성화되지 않음”을 검사하는 테스트가 있다면 더 단단하다. 미확인 그런 테스트가 있는지는 확인하지 못했다. 다만 7강에서 본 MaintenanceJdbcIsolationTests가 default, test, production, prod 프로필 조합을 검사하는 것으로 보아, 비슷한 방식의 보호가 유지보수 도구에는 이미 있다.

3. 두 번째 관문: 소유권은 쿼리 조건에 있다

메서드 보안을 쓰지 않았다

확인 운영 코드에서 @PreAuthorize, @Secured, @EnableMethodSecurity를 쓰는 곳은 0곳이다. 대신 저장소 메서드 이름을 세어 보면 소유권 패턴이 드러난다.

패턴 사용 횟수 예
findOwnedPet 계열 16 반려동물 조회·구독 생성
findByIdAndMemberIdForUpdate 6 결제 확인, 회원 쿠폰, 리뷰
lockOwnedReview / lockOwnedQuestion 5 / 5 리뷰·문의 수정·삭제
findByIdAndMemberId 5 배송지(10강)
findForMember, findByMemberIdAndId... 8 주문, 구독 V2
lockOwnedSubscription, findOwnedSubscription 4 구독 명령(8강)

메서드 보안의 대안은 이런 모양이다. ASSU BLOG의 「Spring Security - 전역 메서드 보안: 사전/사후 권한 필터」가 정리한 대로 두 종류가 있다.

  • @PreAuthorize / @PostAuthorize: 권한 규칙에 맞지 않으면 메서드를 아예 호출하지 않거나 예외를 던진다.
  • @PreFilter / @PostFilter: 메서드는 호출하되, 매개 변수나 반환값 중 규칙에 맞는 요소만 남긴다.

이 블로그의 그림은 GitHub 저장소에 있어서 그대로 보인다.

왜 쿼리 조건을 택했나

@PostAuthorize("returnObject.memberId == principal.memberId")처럼 메서드 보안으로도 소유권을 검사할 수 있다. 그런데도 쿼리 조건을 택한 이유를 따져 보자. 해석

  • SQL 한 번으로 끝난다. “ID로 찾고 → 주인인지 비교”가 아니라 처음부터 내 것만 찾는다. 남의 행은 아예 메모리에 올라오지 않는다.
  • 404가 자연스럽게 나온다. 결과가 없으면 “없음”이다. 남의 것인지, 정말 없는지 구별할 수 없다. @PostAuthorize는 일단 찾은 뒤 거부하므로 403이 기본이고, 404로 바꾸려면 예외를 따로 번역해야 한다.
  • 잠금과 합칠 수 있다(4절). WHERE id = ? AND member_id = ? FOR UPDATE 한 줄로 소유권 확인과 행 잠금이 같은 순간에 일어난다. 메서드 보안은 메서드 바깥에서 동작하므로, 그 안의 트랜잭션·잠금과 원자적으로 묶기 어렵다.
  • 9강과 맞는다. 구독 V2는 명시 SQL과 트랜잭션 스크립트를 택했다. 소유권도 SQL 조건으로 표현하는 것이 그 스타일과 일관된다.

대가: 소유권 규칙이 약 30곳의 쿼리에 흩어져 있다. 새 기능에서 AND member_id = ?를 한 번만 빠뜨려도 10강에서 본 IDOR가 된다. 이를 막는 장치는 두 가지뿐이다.

  • 이름 규칙: findOwned..., lockOwned..., ...AndMemberId
  • 기능별 테스트

해석 7강의 ArchUnit처럼 “회원 자원 저장소의 공개 조회 메서드는 이름에 Owned나 MemberId를 포함해야 한다” 같은 규칙을 테스트로 강제하면, 이름 규칙이 문서에서 실행되는 규칙이 된다. 지금은 그런 규칙이 없다.

4. 소유권 확인과 잠금을 한 번에

기록 결제 확인, 고객의 리뷰·문의 수정, 체크아웃의 회원 쿠폰은 ID와 인증된 회원 ID를 함께 PESSIMISTIC_WRITE 조건에 넣는다. 결정 기록의 제목 그대로 “회원 소유권과 리소스 ID를 같은 비관적 잠금 조건에 넣는다”이다.

// catalog/engagement/persistence/ReviewRepository.java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select r from ReviewEntity r where r.id = :reviewId and r.memberId = :memberId")
Optional<ReviewEntity> findByIdAndMemberIdForUpdate(...);

// catalog/engagement/application/ProductEngagementService.java (발췌)
@Transactional
public ReviewView updateReview(long reviewId, long memberId, ReviewPatchCommand request) {
  if (!request.ratingPresent() && !request.contentPresent())
    throw error(400, "VALIDATION_FAILED", "수정할 필드를 하나 이상 입력해 주세요.");
  ReviewMutationState current = lockOwnedReview(reviewId, memberId);   // 소유권 + 잠금
  int rating = request.ratingPresent() ? validRating(request.rating()) : current.rating();
  String content = request.contentPresent() ? validContent(request.content()) : current.content();
  persistence.updateReview(reviewId, rating, content, ...);
  ...
}

private ReviewMutationState lockOwnedReview(long reviewId, long memberId) {
  var state = persistence.lockOwnedReview(reviewId, memberId);
  if (state == null) throw error(404, "REVIEW_NOT_FOUND", "리뷰를 확인할 수 없습니다.");
  ...
}

왜 잠가야 할까? 확인과 실행 사이의 틈 때문이다. 6강·9강의 TOCTOU, 그리고 10강의 “삭제와 기본 지정” 경쟁과 같은 문제다.

  • 리뷰 수정 요청이 “내 리뷰 맞음”을 확인한 직후, 같은 회원의 삭제 요청이 먼저 커밋할 수 있다. 잠금이 있으면 둘째 요청은 첫째가 끝날 때까지 기다린다. 그 뒤 리뷰가 사라졌으면 깨끗하게 404를 받는다.
  • 문의는 더 분명하다. 기록 답변이 달린 문의는 고객이 수정·삭제할 수 없다. 이 규칙이 지켜지려면 고객의 삭제와 관리자의 답변이 같은 행 잠금을 써야 한다. 그렇지 않으면 “답변이 없음을 확인 → 그 사이 답변 등록 → 삭제 실행”으로 답변 달린 문의가 지워진다. 첫 답변 알림이 한 번만 가는 것도 이 잠금 덕분이다.
  • 10강과의 대비. 배송지는 소유권만 확인하고 잠그지 않는다. 그래서 10강에서 동시성 빈틈을 찾았다. 같은 프로젝트 안에서도 기능별로 성숙도가 다르다. 리뷰·문의·결제는 그 빈틈을 이미 막았다.
    • 체크아웃은 쿠폰에 이 패턴을 쓰지만, 소유권 오류를 COUPON_UNAVAILABLE로 돌려준다. 결정 기록은 “남의 쿠폰”과 “쓸 수 없는 쿠폰”을 같은 응답으로 묶은 이 동작을 보존했다고 적는다.

작은 관찰 해석 저장소의 lockOwnedReview에는 @Transactional(readOnly = true)가 붙어 있다. 잠금(FOR UPDATE)을 하는 메서드에 읽기 전용이라니 이상해 보인다. 하지만 9강에서 본 대로 바깥 서비스(updateReview)가 이미 쓰기 트랜잭션을 열었으므로, 안쪽은 REQUIRED로 참여만 하고 readOnly 설정은 무시된다. 지금은 문제가 없다. 다만 누군가 이 저장소 메서드를 트랜잭션 없이 직접 부르면 읽기 전용 트랜잭션 안의 잠금 읽기가 되어 의도와 다르게 동작할 수 있다. 미확인 그때 MySQL과 Hibernate가 실제로 어떻게 동작하는지는 확인하지 않았다. 주석이나 어노테이션을 의도에 맞게 고치면(readOnly 제거, 또는 MANDATORY 전파로 “반드시 바깥 트랜잭션 안에서만”을 강제) 오해의 여지가 사라진다.

5. 세 번째 관문: 자격은 상태에 달려 있다

주인이라고 해서 언제나 할 수 있는 것은 아니다. [기록·확인]

기능 자격 규칙 실패 응답
리뷰 작성 배송 완료된 구매가 있어야 하고, 회원·상품당 리뷰 하나 409 등
문의 수정·삭제 답변이 아직 없어야 함 409
구독 일시정지·건너뛰기·플랜 변경 구독이 ACTIVE여야 함(5강) 409
구독 명령 If-Match 버전이 최신이어야 함(8강) 412 · 428
결제 승인 결제 READY, 주문 PAYMENT_PENDING, 금액 일치(9강) 409
  • 이 규칙들은 역할로도, 소유권으로도 표현할 수 없다. “배송 완료된 구매가 있는가”는 주문·배송 테이블을 봐야 하고, “답변이 있는가”는 그 행의 상태를 봐야 한다.
  • 그래서 서비스의 도메인 로직에 있다. 응답도 401·403·404가 아니라 409(충돌) 다. “당신은 할 권한이 없다”가 아니라 “지금 이 상태에서는 할 수 없다”이기 때문이다.
  • 해석 이 구분은 프론트에 중요하다. 403이면 “이 기능은 당신 것이 아니다”이므로 버튼을 숨기고, 409면 “조건이 바뀌면 가능하다”이므로 이유를 보여 준다. MVP3 계약 문서의 주문 상세 availableActions(4강)는 이 판단을 서버가 미리 계산해서 주는 장치다. 프론트가 규칙을 중복 구현하지 않게 한다. 1강의 전역 규칙(“가격, 재고, 주문 상태의 기준은 백엔드”)과 같은 원칙이다.

6. 403과 404: 무엇을 숨기고 무엇을 드러내나

지금까지 본 응답을 한 표로 정리하면 원칙이 보인다.

상황 응답 드러내는 것
로그인 안 함 401 AUTH_REQUIRED 로그인하면 될 수도 있다
USER가 /api/admin/** 403 ACCESS_DENIED 관리자 영역이 있다(이미 공개된 사실)
CSRF 불일치 403 CSRF_INVALID 토큰을 새로 받아라(11강)
남의 구독·배송지·리뷰·결제 404 ..._NOT_FOUND 아무것도 드러내지 않는다
남의 쿠폰 409 COUPON_UNAVAILABLE 쓸 수 없다는 것만
내 것이지만 상태가 안 맞음 409 조건이 바뀌면 된다
  • 해석 기준은 “그 사실이 비밀인가”다. 관리자 기능의 존재는 비밀이 아니므로 403으로 정직하게 거부한다. 반면 “ID 42번 구독이 존재하고 다른 사람 것이다”는 그 자체가 정보다. ID를 하나씩 바꿔 가며 403과 404를 구분하면 어떤 ID가 실제로 쓰이는지 알아낼 수 있다(열거 공격). 그래서 자원 단위의 거부는 404로 숨긴다. 4강 MVP1부터 일관된 원칙이다.
  • 기록 결제 확인의 소유권 오류를 403에서 404로 바꿀 때, 결정 기록은 “기존 403 분기에 의존하는 프론트가 없음을 별도로 검토했다”고 적는다. 응답 코드를 바꾸는 것은 API 계약 변경이기 때문이다. 이번처럼 프론트 영향 분류기가 이것을 잡지 못한 구멍도 숨기지 않고 기록했다.

    • hasRole("ADMIN") = ROLE_ADMIN 권한이다. 인증 제공자가 접두사를 붙인다.
    • 규칙은 처음 맞는 하나만 적용되고, 마지막은 denyAll이다.
    • 관리자 경계는 파라미터 테스트(익명 401 / USER 403 / CSRF 없음 403 / ADMIN 성공)가 지킨다.
    • 프로필로만 보호되는 무인증 성능 측정 체인이 하나 있다.
  • 소유권
    • 메서드 보안 0곳, 쿼리 조건 약 30곳이다. SQL 한 번, 자연스러운 404, 잠금과 결합이라는 장점이 있다.
    • 대가는 규칙이 흩어진다는 것이다. 이름 규칙을 ArchUnit으로 강제할 여지가 있다.
  • 소유권 + 잠금
    • 리뷰·문의·결제·쿠폰은 확인과 실행 사이의 틈을 FOR UPDATE로 막았다.
    • 배송지는 아직이다(10강).
  • 자격: “지금 이 상태에서는 안 된다”는 409이고, 서버가 availableActions로 미리 계산해 준다.
  • 403 vs 404: 그 사실이 비밀이면 404, 이미 공개된 사실이면 403이다. 응답 코드 변경은 계약 변경이다.

12강에서 남긴 미확인 항목

  • 성능 측정 체인이 운영 이미지에서 활성화되지 않음을 검사하는 테스트가 있는지
  • 기능별로 “남의 자원 → 404” 테스트가 얼마나 있는지(테스트 전체에서 isNotFound()는 39곳이지만, 타인 소유 시나리오만 따로 세지는 않았다)
