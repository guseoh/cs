12강. 인가와 소유권: 누가, 무엇을, 지금 할 수 있는가

이번 강의의 목표

  • PawCycle의 인가를 세 관문(역할·URL 규칙, 소유권, 자격·상태)으로 나누어 설명할 수 있다.

표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 원리 일반 원리 · 미확인

1. 인가의 세 관문

11강에서 "누구인가(인증)"를 다뤘다면, 이번 강의는 "이 사람이 이 일을 해도 되는가(인가)"다. PawCycle에서 이 판단은 한 곳에서 일어나지 않는다. 판단에 필요한 데이터가 다르기 때문에 세 곳으로 나뉜다.

그림의 마지막 줄이 이 강의의 요점이다.

  • ①은 URL만 보면 된다. 요청이 DB에 닿기 전에, 가장 싸게 판단한다.
  • ②는 그 행의 주인을 알아야 한다. DB를 봐야 한다.
  • ③은 그 행의 상태와 다른 행들(주문, 배송, 답변)까지 봐야 한다.

판단에 필요한 데이터가 다르니 판단하는 위치도 다르다. 이 세 관문을 하나로 합치려 하면 오히려 어색해진다.

2. 첫 관문: 역할과 URL 규칙

8강에서 본 인가 규칙을 다시 보자. 이번에는 역할 관점이다.

// common/security/SecurityConfig.java (발췌)
.requestMatchers(EndpointRequest.to("health", "prometheus")).permitAll()
.requestMatchers(HttpMethod.GET, "/api/products/*/reviews/me").authenticated()
.requestMatchers(HttpMethod.GET, "/api/products", "/api/products/**", "/api/categories", ...).permitAll()
.requestMatchers(HttpMethod.POST, "/api/auth/login").permitAll()
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/**").authenticated()
.anyRequest().denyAll()

// member/application/MemberAuthenticationProvider.java (발췌)
List.of(new SimpleGrantedAuthority("ROLE_" + member.getRole().name()))   // ROLE_USER / ROLE_ADMIN

hasRole("ADMIN")과 ROLE_ 접두사

  • 원리 Spring Security에서 역할(Role)은 ROLE_로 시작하는 권한(Authority) 이다. hasRole("ADMIN")은 내부적으로 ROLE_ADMIN 권한이 있는지 본다. hasAuthority("ADMIN")이라고 쓰면 접두사 없이 그대로 비교한다.
  • 그래서 인증 제공자가 권한을 만들 때 "ROLE_" + role로 접두사를 붙인다. 이 짝이 어긋나면, 예를 들어 "ADMIN"만 넣고 hasRole("ADMIN")으로 검사하면 관리자도 403을 받는다.

주리니e의 「역할(hasRole)과 권한(hasAuthority)의 차이는 무엇일까?」가 이 둘을 구분한다. 두 계정이 모두 SYSTEM 역할이어도 한 계정은 글 등록만, 다른 계정은 수정까지 할 수 있게 하려면 역할보다 세밀한 권한이 필요하다는 예로 설명한다.

출처: 주리니e · 역할(hasRole)과 권한(hasAuthority)의 차이. tistory 그림이라 11월 30일 만료.

확인 PawCycle은 역할이 USER, ADMIN 두 개뿐이고 세부 권한은 없다. 관리자는 모든 관리 기능을 쓸 수 있다.

  • 기록 관리자 기능 도입 때 역할 변경 API나 실제 관리자 계정 발급(provisioning)은 제공하지 않기로 했다. 기존 회원과 외부 역할 입력이 없는 신규 회원은 모두 USER다.
  • 해석 운영자가 여러 명이고 “재고만 조정할 수 있는 사람” 같은 구분이 필요해지면, 그때 hasAuthority("INVENTORY_WRITE") 같은 세부 권한으로 나눠야 한다. 지금 미리 만들지 않은 것은 4강의 YAGNI다.

규칙 순서가 곧 보안이다

dsjo의 「authorizeHttpRequests 우선순위 적용하기」는 실제로 겪은 문제를 보여 준다. /users/**에 permitAll을 먼저 걸고 그 아래에 /users/inactive를 관리자 전용으로 걸었더니, 관리자 규칙이 적용되지 않았다. 위에서부터 처음 맞는 규칙 하나만 쓰이기 때문이다.

출처: dsjo · authorizeHttpRequests 우선순위 적용하기. tistory 그림이라 11월 30일 만료.

PawCycle의 /api/products/*/reviews/me가 /api/products/**보다 위에 있는 이유가 정확히 이것이다(8강). 구체적인 규칙이 먼저, 넓은 규칙이 나중이다. 그리고 마지막 anyRequest().denyAll()이 “규칙을 깜빡한 경로”를 막는다.

관리자 경로는 테스트가 지킨다

확인 CommerceAdminAuthorizationIntegrationTests는 관리자 변경 API 목록을 파라미터로 돌며 같은 네 가지를 검사한다.

// CommerceAdminAuthorizationIntegrationTests (요지)
void adminMutationsRequireCsrfAndAllowOnlyAdmin(String path, String body) {
  익명                        → 401 Unauthorized
  USER (+CSRF)                → 403 Forbidden
  ADMIN (CSRF 없음)           → 403 Forbidden   // 11강: CSRF는 역할과 별개
  ADMIN (+CSRF)               → 성공
}
  • 새 관리자 API를 만들면 이 목록에 한 줄 추가하는 것만으로 네 가지 경계가 검증된다.
  • 관리자 영역에서 USER에게 404가 아니라 403을 주는 것은 의도된 차이다(6절).

두 번째 보안 체인 하나

확인 성능 측정용 설정이 @Order(1)로 별도의 보안 체인을 만든다.

// subscription/performance/SubscriptionBurstMeasurementSecurityConfiguration.java
@Profile("subscription-burst-measurement & !production & !prod")
class SubscriptionBurstMeasurementSecurityConfiguration {
  @Bean @Order(1)
  SecurityFilterChain subscriptionBurstMeasurementSecurityFilterChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/internal/performance/subscription-burst/**")
        .csrf(AbstractHttpConfigurer::disable)
        .authorizeHttpRequests(authorize -> authorize.anyRequest().permitAll());
    return http.build();
  }
}
  • 이 경로는 인증도 CSRF도 없이 열린다. 부하 측정 도구가 구독 데이터를 준비하고 흘려보내는 데 쓴다.
  • 보호 장치는 프로필 식 하나다. subscription-burst-measurement가 켜져 있고, production도 prod도 아닐 때만 등록된다. 컨트롤러에도 같은 프로필 조건이 붙어 있다.
  • 해석 7강과 11강에서 본 교훈(“관문이 보지 못하는 설정 경로”, “실행하지 않아도 설정은 로드된다”)을 떠올리면, 이런 체인은 프로필 이름이 바뀌거나 운영에서 다른 프로필명을 쓰는 순간 위험해진다. 운영 프로필 이름이 production인 지금은 안전하다. 그래도 7강의 ArchUnit처럼 “운영 이미지에 이 클래스가 활성화되지 않음”을 검사하는 테스트가 있다면 더 단단하다. 미확인 그런 테스트가 있는지는 확인하지 못했다. 다만 7강에서 본 MaintenanceJdbcIsolationTests가 default, test, production, prod 프로필 조합을 검사하는 것으로 보아, 비슷한 방식의 보호가 유지보수 도구에는 이미 있다.

3. 두 번째 관문: 소유권은 쿼리 조건에 있다

메서드 보안을 쓰지 않았다

확인 운영 코드에서 @PreAuthorize, @Secured, @EnableMethodSecurity를 쓰는 곳은 0곳이다. 대신 저장소 메서드 이름을 세어 보면 소유권 패턴이 드러난다.

패턴 사용 횟수 예
findOwnedPet 계열 16 반려동물 조회·구독 생성
findByIdAndMemberIdForUpdate 6 결제 확인, 회원 쿠폰, 리뷰
lockOwnedReview / lockOwnedQuestion 5 / 5 리뷰·문의 수정·삭제
findByIdAndMemberId 5 배송지(10강)
findForMember, findByMemberIdAndId... 8 주문, 구독 V2
lockOwnedSubscription, findOwnedSubscription 4 구독 명령(8강)

메서드 보안의 대안은 이런 모양이다. ASSU BLOG의 「Spring Security - 전역 메서드 보안: 사전/사후 권한 필터」가 정리한 대로 두 종류가 있다.

  • @PreAuthorize / @PostAuthorize: 권한 규칙에 맞지 않으면 메서드를 아예 호출하지 않거나 예외를 던진다.
  • @PreFilter / @PostFilter: 메서드는 호출하되, 매개 변수나 반환값 중 규칙에 맞는 요소만 남긴다.

이 블로그의 그림은 GitHub 저장소에 있어서 그대로 보인다.

왜 쿼리 조건을 택했나

@PostAuthorize("returnObject.memberId == principal.memberId")처럼 메서드 보안으로도 소유권을 검사할 수 있다. 그런데도 쿼리 조건을 택한 이유를 따져 보자. 해석

  • SQL 한 번으로 끝난다. “ID로 찾고 → 주인인지 비교”가 아니라 처음부터 내 것만 찾는다. 남의 행은 아예 메모리에 올라오지 않는다.
  • 404가 자연스럽게 나온다. 결과가 없으면 “없음”이다. 남의 것인지, 정말 없는지 구별할 수 없다. @PostAuthorize는 일단 찾은 뒤 거부하므로 403이 기본이고, 404로 바꾸려면 예외를 따로 번역해야 한다.
  • 잠금과 합칠 수 있다(4절). WHERE id = ? AND member_id = ? FOR UPDATE 한 줄로 소유권 확인과 행 잠금이 같은 순간에 일어난다. 메서드 보안은 메서드 바깥에서 동작하므로, 그 안의 트랜잭션·잠금과 원자적으로 묶기 어렵다.
  • 9강과 맞는다. 구독 V2는 명시 SQL과 트랜잭션 스크립트를 택했다. 소유권도 SQL 조건으로 표현하는 것이 그 스타일과 일관된다.

대가: 소유권 규칙이 약 30곳의 쿼리에 흩어져 있다. 새 기능에서 AND member_id = ?를 한 번만 빠뜨려도 10강에서 본 IDOR가 된다. 이를 막는 장치는 두 가지뿐이다.

  • 이름 규칙: findOwned..., lockOwned..., ...AndMemberId
  • 기능별 테스트

해석 7강의 ArchUnit처럼 “회원 자원 저장소의 공개 조회 메서드는 이름에 Owned나 MemberId를 포함해야 한다” 같은 규칙을 테스트로 강제하면, 이름 규칙이 문서에서 실행되는 규칙이 된다. 지금은 그런 규칙이 없다.

4. 소유권 확인과 잠금을 한 번에

기록 결제 확인, 고객의 리뷰·문의 수정, 체크아웃의 회원 쿠폰은 ID와 인증된 회원 ID를 함께 PESSIMISTIC_WRITE 조건에 넣는다. 결정 기록의 제목 그대로 “회원 소유권과 리소스 ID를 같은 비관적 잠금 조건에 넣는다”이다.

// catalog/engagement/persistence/ReviewRepository.java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select r from ReviewEntity r where r.id = :reviewId and r.memberId = :memberId")
Optional<ReviewEntity> findByIdAndMemberIdForUpdate(...);

// catalog/engagement/application/ProductEngagementService.java (발췌)
@Transactional
public ReviewView updateReview(long reviewId, long memberId, ReviewPatchCommand request) {
  if (!request.ratingPresent() && !request.contentPresent())
    throw error(400, "VALIDATION_FAILED", "수정할 필드를 하나 이상 입력해 주세요.");
  ReviewMutationState current = lockOwnedReview(reviewId, memberId);   // 소유권 + 잠금
  int rating = request.ratingPresent() ? validRating(request.rating()) : current.rating();
  String content = request.contentPresent() ? validContent(request.content()) : current.content();
  persistence.updateReview(reviewId, rating, content, ...);
  ...
}

private ReviewMutationState lockOwnedReview(long reviewId, long memberId) {
  var state = persistence.lockOwnedReview(reviewId, memberId);
  if (state == null) throw error(404, "REVIEW_NOT_FOUND", "리뷰를 확인할 수 없습니다.");
  ...
}

왜 잠가야 할까? 확인과 실행 사이의 틈 때문이다. 6강·9강의 TOCTOU, 그리고 10강의 “삭제와 기본 지정” 경쟁과 같은 문제다.

  • 리뷰 수정 요청이 “내 리뷰 맞음”을 확인한 직후, 같은 회원의 삭제 요청이 먼저 커밋할 수 있다. 잠금이 있으면 둘째 요청은 첫째가 끝날 때까지 기다린다. 그 뒤 리뷰가 사라졌으면 깨끗하게 404를 받는다.
  • 문의는 더 분명하다. 기록 답변이 달린 문의는 고객이 수정·삭제할 수 없다. 이 규칙이 지켜지려면 고객의 삭제와 관리자의 답변이 같은 행 잠금을 써야 한다. 그렇지 않으면 “답변이 없음을 확인 → 그 사이 답변 등록 → 삭제 실행”으로 답변 달린 문의가 지워진다. 첫 답변 알림이 한 번만 가는 것도 이 잠금 덕분이다.
  • 10강과의 대비. 배송지는 소유권만 확인하고 잠그지 않는다. 그래서 10강에서 동시성 빈틈을 찾았다. 같은 프로젝트 안에서도 기능별로 성숙도가 다르다. 리뷰·문의·결제는 그 빈틈을 이미 막았다.
    • 체크아웃은 쿠폰에 이 패턴을 쓰지만, 소유권 오류를 COUPON_UNAVAILABLE로 돌려준다. 결정 기록은 “남의 쿠폰”과 “쓸 수 없는 쿠폰”을 같은 응답으로 묶은 이 동작을 보존했다고 적는다.

작은 관찰 해석 저장소의 lockOwnedReview에는 @Transactional(readOnly = true)가 붙어 있다. 잠금(FOR UPDATE)을 하는 메서드에 읽기 전용이라니 이상해 보인다. 하지만 9강에서 본 대로 바깥 서비스(updateReview)가 이미 쓰기 트랜잭션을 열었으므로, 안쪽은 REQUIRED로 참여만 하고 readOnly 설정은 무시된다. 지금은 문제가 없다. 다만 누군가 이 저장소 메서드를 트랜잭션 없이 직접 부르면 읽기 전용 트랜잭션 안의 잠금 읽기가 되어 의도와 다르게 동작할 수 있다. 미확인 그때 MySQL과 Hibernate가 실제로 어떻게 동작하는지는 확인하지 않았다. 주석이나 어노테이션을 의도에 맞게 고치면(readOnly 제거, 또는 MANDATORY 전파로 “반드시 바깥 트랜잭션 안에서만”을 강제) 오해의 여지가 사라진다.

문의 수정·삭제 답변이 아직 없어야 함 409
구독 일시정지·건너뛰기·플랜 변경 구독이 ACTIVE여야 함(5강) 409
구독 명령 If-Match 버전이 최신이어야 함(8강) 412 · 428
결제 승인 결제 READY, 주문 PAYMENT_PENDING, 금액 일치(9강) 409
  • 이 규칙들은 역할로도, 소유권으로도 표현할 수 없다. “배송 완료된 구매가 있는가”는 주문·배송 테이블을 봐야 하고, “답변이 있는가”는 그 행의 상태를 봐야 한다.
  • 그래서 서비스의 도메인 로직에 있다. 응답도 401·403·404가 아니라 409(충돌) 다. “당신은 할 권한이 없다”가 아니라 “지금 이 상태에서는 할 수 없다”이기 때문이다.
  • 해석 이 구분은 프론트에 중요하다. 403이면 “이 기능은 당신 것이 아니다”이므로 버튼을 숨기고, 409면 “조건이 바뀌면 가능하다”이므로 이유를 보여 준다. MVP3 계약 문서의 주문 상세 availableActions(4강)는 이 판단을 서버가 미리 계산해서 주는 장치다. 프론트가 규칙을 중복 구현하지 않게 한다. 1강의 전역 규칙(“가격, 재고, 주문 상태의 기준은 백엔드”)과 같은 원칙이다.

6. 403과 404: 무엇을 숨기고 무엇을 드러내나

지금까지 본 응답을 한 표로 정리하면 원칙이 보인다.

상황 응답 드러내는 것
로그인 안 함 401 AUTH_REQUIRED 로그인하면 될 수도 있다
USER가 /api/admin/** 403 ACCESS_DENIED 관리자 영역이 있다(이미 공개된 사실)
CSRF 불일치 403 CSRF_INVALID 토큰을 새로 받아라(11강)
남의 구독·배송지·리뷰·결제 404 ..._NOT_FOUND 아무것도 드러내지 않는다
남의 쿠폰 409 COUPON_UNAVAILABLE 쓸 수 없다는 것만
내 것이지만 상태가 안 맞음 409 조건이 바뀌면 된다
  • 해석 기준은 “그 사실이 비밀인가”다. 관리자 기능의 존재는 비밀이 아니므로 403으로 정직하게 거부한다. 반면 “ID 42번 구독이 존재하고 다른 사람 것이다”는 그 자체가 정보다. ID를 하나씩 바꿔 가며 403과 404를 구분하면 어떤 ID가 실제로 쓰이는지 알아낼 수 있다(열거 공격). 그래서 자원 단위의 거부는 404로 숨긴다. 4강 MVP1부터 일관된 원칙이다.
  • 기록 결제 확인의 소유권 오류를 403에서 404로 바꿀 때, 결정 기록은 “기존 403 분기에 의존하는 프론트가 없음을 별도로 검토했다”고 적는다. 응답 코드를 바꾸는 것은 API 계약 변경이기 때문이다. 이번처럼 프론트 영향 분류기가 이것을 잡지 못한 구멍도 숨기지 않고 기록했다.

12강 정리

  • 인가의 세 관문: 판단에 필요한 데이터가 다르니 위치도 다르다.
    • 역할: URL 규칙, Security 필터, 401·403
    • 소유권: 쿼리 조건, 저장소, 404
    • 자격: 도메인 규칙, 서비스, 409
  • 역할
    • hasRole("ADMIN") = ROLE_ADMIN 권한이다. 인증 제공자가 접두사를 붙인다.
    • 규칙은 처음 맞는 하나만 적용되고, 마지막은 denyAll이다.
    • 관리자 경계는 파라미터 테스트(익명 401 / USER 403 / CSRF 없음 403 / ADMIN 성공)가 지킨다.
    • 프로필로만 보호되는 무인증 성능 측정 체인이 하나 있다.
  • 소유권
    • 메서드 보안 0곳, 쿼리 조건 약 30곳이다. SQL 한 번, 자연스러운 404, 잠금과 결합이라는 장점이 있다.
    • 대가는 규칙이 흩어진다는 것이다. 이름 규칙을 ArchUnit으로 강제할 여지가 있다.
  • 소유권 + 잠금
    • 리뷰·문의·결제·쿠폰은 확인과 실행 사이의 틈을 FOR UPDATE로 막았다.
    • 배송지는 아직이다(10강).
  • 자격: “지금 이 상태에서는 안 된다”는 409이고, 서버가 availableActions로 미리 계산해 준다.
  • 403 vs 404: 그 사실이 비밀이면 404, 이미 공개된 사실이면 403이다. 응답 코드 변경은 계약 변경이다.

12강에서 남긴 미확인 항목

  • 성능 측정 체인이 운영 이미지에서 활성화되지 않음을 검사하는 테스트가 있는지
  • 기능별로 “남의 자원 → 404” 테스트가 얼마나 있는지(테스트 전체에서 isNotFound()는 39곳이지만, 타인 소유 시나리오만 따로 세지는 않았다)
