11강. 세션 로그인과 CSRF: 로그인 한 번이 만드는 것들

이번 강의의 목표

  • PawCycle이 JWT가 아니라 서버 세션을 고른 이유와 그 대가를 안다.
  • 로그인 요청 하나가 세션, 쿠키, CSRF 토큰을 어떤 순서로 만들고 바꾸는지 코드로 따라간다.
  • 세션 고정 공격, CSRF, 계정 존재 노출이라는 세 가지 공격을 각각 무엇이 막는지 이해한다.
  • 메모리 세션의 한계(재시작, 확장, 권한 변경 반영)를 알고 개선 방향을 판단한다.

1. 왜 JWT가 아니라 세션인가

두 방식의 차이

HTTP는 요청마다 독립적이라 서버가 “이 요청이 누구인지”를 매번 알아내야 한다. 방법은 크게 둘이다.

  • 세션: 서버가 로그인 정보를 자기 메모리(또는 저장소) 에 두고, 브라우저에는 그것을 찾는 열쇠(세션 ID) 만 쿠키로 준다.
  • JWT: 서버가 로그인 정보를 서명한 토큰으로 만들어 브라우저에 주고, 요청마다 그 토큰을 검증한다. 서버는 아무것도 저장하지 않는다.

kimgunwooo의 「로그인 인증 방식 차이 (쿠키, 세션, JWT)」는 이전 프로젝트에서 “JWT가 제일 좋다는 얕은 지식으로” JWT를 골랐던 경험에서 출발한다. 그리고 HTTP의 비연결성·무상태성부터 세 방식을 차례로 비교한다.

출처: velog @kimgunwooo · 로그인 인증 방식 차이(velog 그림은 만료되지 않습니다)

쿠키와 세션이 실제로 주고받는 모습은 준현의 「쿠키와 세션」이 그림으로 보여 준다.

그림의 ③~⑥이 이 코드 한 메서드다.

// member/application/AuthApplicationService.java (발췌)
@Transactional(readOnly = true)
public AuthenticatedMemberPrincipal login(String email, String password,
                                         HttpServletRequest request, HttpServletResponse response) {
  NormalizedLoginCredentials credentials = emailNormalizer.normalize(email, password);   // ③
  Authentication authentication =
      credentialAuthenticator.authenticate(credentials.email(), credentials.password());  // ④
  sessionAuthenticationStrategy.onAuthentication(authentication, request, response);      // ⑤
  SecurityContext context = SecurityContextHolder.createEmptyContext();
  context.setAuthentication(authentication);
  SecurityContextHolder.setContext(context);
  securityContextRepository.saveContext(context, request, response);                     // ⑥
  return (AuthenticatedMemberPrincipal) authentication.getPrincipal();
}
  • Spring Security의 기본 로그인 폼(formLogin)을 쓰지 않았다. 기본 폼은 HTML 폼 POST와 리다이렉트를 전제로 한다. PawCycle은 JSON을 받고 JSON을 돌려주는 API다({ memberId }, 실패 시 401 INVALID_CREDENTIALS). 그래서 컨트롤러에서 필요한 부품만 직접 조립했다.
    • 인증: AuthenticationManager → MemberAuthenticationProvider
    • 세션 처리: SessionAuthenticationStrategy
    • 저장: SecurityContextRepository
    • 7강에서 본 SecurityConfig가 이 부품들을 Bean으로 만든다.
  • ⑥을 직접 해야 하는 이유. 원리 Spring Security 6부터 SecurityContextHolder에 인증을 넣는 것만으로는 세션에 자동 저장되지 않는다. 명시적으로 securityContextRepository.saveContext(...)를 불러야 한다. 이 줄을 빼면 로그인 응답은 성공인데 다음 요청에서 다시 익명이 된다. 직접 로그인 API를 만들 때 가장 흔한 실수다.
    • SecurityContextHolder가 스레드에 컨텍스트를 두는 방식은 준현의 「스프링 시큐리티 SecurityContextHolderStrategy」가 정리한다. 8강의 ThreadLocal 이야기가 여기서도 이어진다.
  • 세션에는 엔티티가 아니라 작은 기록이 들어간다. 인증 성공 시 세션에 저장되는 주체는 AuthenticatedMemberPrincipal(memberId, role)이라는 record 하나다. 비밀번호 해시도, Member 엔티티도 넣지 않는다. 클래스 주석도 “session-safe principal만 반환한다”고 적는다. 8강에서 @AuthenticationPrincipal로 꺼내 쓰던 그 객체다.

3. 세션 고정 공격: 로그인하면 열쇠를 바꾼다

그림의 ⑤에서 세션 ID가 S1 → S2로 바뀌었다. 왜 바꿀까?

pjs-world의 「세션 고정 공격(Session Fixation)과 Spring Security의 대응 전략」이 공격을 이렇게 정의한다.

  • 공격자가 먼저 정상적인 세션 ID를 하나 발급받는다.
  • 그 ID를 피해자의 브라우저에 심는다(링크, 쿠키 주입 등).
  • 피해자가 그 세션으로 로그인하게 유도한다.
  • 서버가 로그인 후에도 같은 세션 ID를 유지하면, 공격자는 자기가 아는 그 ID로 피해자의 로그인 상태를 그대로 쓴다.

출처: pjs-world · 세션 고정 공격과 Spring Security의 대응 전략. tistory 그림이라 11월 30일 만료.

PawCycle의 방어는 두 줄이다.

// common/security/SecurityConfig.java (발췌)
.sessionManagement(session -> session.sessionFixation(fixation -> fixation.changeSessionId()));

@Bean
SessionAuthenticationStrategy sessionAuthenticationStrategy(HttpSessionCsrfTokenRepository csrfTokenRepository) {
  return new CompositeSessionAuthenticationStrategy(List.of(
      new ChangeSessionIdAuthenticationStrategy(),          // 세션 ID 교체
      new CsrfAuthenticationStrategy(csrfTokenRepository)));  // CSRF 토큰 교체
}
  • changeSessionId vs newSession·migrateSession. 원리 서블릿 3.1의 HttpServletRequest.changeSessionId()는 세션 내용은 그대로 두고 ID만 바꾼다. 새 세션을 만들어 속성을 복사하는 방식보다 가볍다. 공격자가 아는 옛 ID는 그 순간부터 쓸모없어진다.
  • 두 전략을 묶었다. 로그인 순간 세션 ID와 CSRF 토큰도 함께 바꾼다. 로그인 전의 토큰이 노출됐더라도 로그인 후에는 쓸 수 없다. 대신 브라우저는 로그인 직후 새 토큰을 받아야 한다(그림의 ⑦).
  • [주의] 2절의 코드가 이 전략을 직접 호출한다(sessionAuthenticationStrategy.onAuthentication(...)). 기본 로그인 폼을 쓰면 필터가 알아서 부르지만, 직접 만든 로그인 API에서는 빼먹기 쉬운 부분이다.

4. CSRF: 쿠키 인증의 숙제

공격의 원리

준현의 「CSRF 공격과 방어」가 원리와 방어 방법을 GET·POST 공격 예제와 함께 정리한다. 방어 방법으로는 Referrer 검사, CSRF 토큰, 더블 서브밋 쿠키를 다룬다.

핵심은 이것이다. 브라우저는 pawcycle.duckdns.org로 가는 요청이라면, 그 요청을 누가 시작했든 쿠키를 붙인다. 악성 사이트가 숨겨 둔 폼이 POST /api/subscriptions/42/commands/cancel을 보내도 피해자의 세션 쿠키가 따라간다. 서버는 정상 요청과 구분할 수 없다.

두 겹의 방어

확인 PawCycle은 두 가지를 함께 쓴다.

① CSRF 토큰 (서버 세션에 저장, 헤더로 전송)

@Bean
HttpSessionCsrfTokenRepository csrfTokenRepository() {
  HttpSessionCsrfTokenRepository repository = new HttpSessionCsrfTokenRepository();
  repository.setHeaderName("X-CSRF-TOKEN");
  repository.setParameterName("_csrf");
  return repository;
}

// member/api/AuthController.java
@GetMapping("/csrf")
ResponseEntity<CsrfTokenResponse> csrf(CsrfToken csrfToken) {
  return ResponseEntity.ok().cacheControl(CacheControl.noStore())       // 캐시 금지
      .body(new CsrfTokenResponse(csrfToken.getToken()));
}
  • 토큰은 서버 세션에 있고, 브라우저는 GET /api/auth/csrf로 받아 메모리에 들고 있다가 변경 요청마다 X-CSRF-TOKEN 헤더에 싣는다.
  • 악성 사이트는 이 토큰을 읽을 수 없다. 다른 출처의 응답 본문은 브라우저의 동일 출처 정책(SOP) 때문에 읽히지 않는다. 그래서 위조 요청에 올바른 헤더를 실을 수 없다.
  • 응답에 Cache-Control: no-store를 붙였다. 토큰이 브라우저나 프록시 캐시에 남지 않게 한다.

기록 쿠키 저장소 대신 세션 저장소를 고른 이유. 설계 단계에서 CookieCsrfTokenRepository(자바스크립트가 읽을 수 있는 XSRF-TOKEN 쿠키)를 대안으로 검토했다.

  • 쿠키 방식은 SPA에서 쓰기 편하지만, 쿠키·요청 처리기·재발급 처리에 비용이 든다.
  • 응답 헤더로 토큰을 주는 방식은 헤더 노출과 CORS 계약 비용이 든다.
  • 최종적으로 세션 저장 + JSON 엔드포인트 + 프론트 메모리 보관을 추천안으로 승인했다.
  • 대가도 함께 적었다. 익명 사용자의 csrf 호출도 세션을 만든다(그림 ①의 S1). 새로고침하면 토큰을 다시 받아야 한다.

② SameSite=Lax 쿠키

# application.properties
server.servlet.session.cookie.name=JSESSIONID
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.same-site=lax
server.servlet.session.cookie.secure=${SESSION_COOKIE_SECURE:true}
server.servlet.session.cookie.path=/
server.servlet.session.timeout=30m
  • 원리 SameSite=Lax면 다른 사이트에서 시작한 POST 요청에는 쿠키가 붙지 않는다. 위의 숨긴 폼 공격은 쿠키 없이 도착해 익명 요청이 된다.
  • 다른 사이트의 링크를 눌러 최상위 GET으로 이동할 때는 쿠키가 붙는다. 그래서 GET은 절대 상태를 바꾸면 안 된다. PawCycle의 모든 변경은 POST·PATCH·PUT·DELETE다.

준현의 「크롬 기본 SameSite 정책은 CSRF 공격에 안전한가?」는 여기에 중요한 함정을 짚는다.

  • 크롬 80부터 SameSite가 지정되지 않은 쿠키를 Lax처럼 취급한다.
  • 그런데 OAuth 리다이렉트 호환을 위해, 지정되지 않은 쿠키는 저장 후 처음 2분 동안 다른 사이트의 POST 폼 요청에도 붙도록 완화했다.
  • 즉 “기본값 Lax”는 진짜 Lax보다 약하고, 그 2분 동안은 CSRF에 여전히 취약하다.
  • 해석 PawCycle은 same-site=lax를 명시했으므로 이 완화 대상이 아니다. 설정 한 줄의 차이가 보안 경계를 바꾼다. 그리고 SameSite에 기대지 않고 토큰을 함께 쓰는 이유도 여기에 있다. 브라우저 정책은 바뀌고, 브라우저마다 다르다.

로그인에도 CSRF가 필요하다

POST /api/auth/login은 permitAll이지만, 확인 CSRF 검사는 인가 규칙과 별개로 모든 POST에 적용된다. 그래서 로그인 전에도 토큰을 받아야 한다(그림 ①). 이것이 막는 공격이 로그인 CSRF다.

  • 공격자가 피해자의 브라우저로 공격자 자신의 계정에 로그인시킨다.
  • 피해자는 모른 채 그 계정으로 결제 수단이나 주소를 등록하고, 공격자는 나중에 그 정보를 본다.
  • 기록 설계 단계 문서도 “CSRF는 인증 검사보다 먼저 403이 될 수 있다”고 적는다. 8강에서 본 대로 CSRF 필터가 인가 필터보다 앞에 있기 때문이다.

프론트는 실패한 POST를 자동으로 다시 보내지 않는다

기록 프론트엔드는 토큰을 메모리에 lazy하게 받고, 로그인 후 회전되면 새로 받으며, 익명이 되면 버린다.

CSRF_INVALID(8강의 403 코드)를 받으면 토큰은 새로 받지만, 원래 POST는 자동으로 재실행하지 않는다. 사용자가 결과를 확인하고 직접 다시 시도한다.

  • 해석 이유는 3강의 멱등성이다. 그 POST가 정말 실패했는지 클라이언트는 확신할 수 없다. 첫 구독 API처럼 멱등성 저장소가 없는 요청을 자동으로 다시 보내면 중복 생성이 될 수 있다. 4강의 “이전 POST 자동 재실행 금지” 결정과 같은 뿌리다.

5. 비밀번호와 응답 시간

// member/application/MemberAuthenticationProvider.java (발췌)
public MemberAuthenticationProvider(MemberRepository memberRepository, PasswordEncoder passwordEncoder) {
  this.dummyPasswordHash = passwordEncoder.encode(UUID.randomUUID().toString());   // 시작 시 한 번
}

public Authentication authenticate(Authentication authentication) {
  Optional<Member> candidate = memberRepository.findByEmail(email);
  String passwordHash = candidate.map(Member::getPasswordHash).orElse(dummyPasswordHash);
  boolean passwordMatches = passwordEncoder.matches(password, passwordHash);        // 항상 정확히 한 번
  if (candidate.isEmpty() || !passwordMatches) throw new InvalidCredentialsException();
  ...
}

3강에서 본 타이밍 부채널 방어의 실제 코드다.

  • 가입되지 않은 이메일에도 더미 해시로 BCrypt 비교를 한 번 한다. 그래서 “없는 회원”과 “틀린 비밀번호”가 비슷한 시간이 걸리고, 같은 401 INVALID_CREDENTIALS 를 받는다.
  • 인증 책임은 처음에 애플리케이션 서비스에 있었다. 이후 Spring Security의 AuthenticationProvider로 옮겼다(ARCH-010). 3강에서 미확인으로 남긴 “현재 코드 구조”가 이것이다.

BCrypt가 왜 일부러 느린지는 comgu의 「bcrypt 보안 분석: Salt와 Cost Factor를 통한 패스워드 보호」가 설명한다.

  • MD5·SHA-1 같은 일반 해시는 빠르기 때문에 대입 공격에 약하다.
  • BCrypt는 의도적으로 느린 연산(cost factor) 과 매번 다른 salt로 같은 비밀번호도 다른 해시를 만든다.
  • 확인 PawCycle은 new BCryptPasswordEncoder()(기본 cost 10)를 쓴다. 설계 문서는 해시 컬럼을 VARCHAR(100)으로 잡고 cost는 측정 전 미확정이라고 적었다. BCrypt 해시(60자)와 인코더 접두사가 바뀔 여유를 둔 길이다.

이메일 처리에도 세심한 결정이 있다. 기록

  • 앞뒤 공백·탭만 지운다.
  • 도메인만 소문자로 바꾸고, @ 앞부분(local-part)의 대소문자는 보존한다. 표준상 local-part는 대소문자를 구별할 수 있어서, 전부 소문자로 바꾸면 서로 다른 주소가 하나로 합쳐질 위험이 있기 때문이다.
  • 별칭 통합(+tag, Gmail의 점 무시)은 하지 않는다.

6. 쿠키 속성 하나하나의 의미

속성 값 막는 것
HttpOnly true 자바스크립트(document.cookie)로 세션 ID 읽기. XSS가 나도 세션 ID는 직접 훔칠 수 없다.
Secure true (기본값) HTTP 평문으로 쿠키 전송. 2강의 HSTS와 짝을 이룬다.
SameSite lax (명시) 다른 사이트의 POST에 쿠키가 붙는 것(4절)
Path / — 사이트 전체에서 사용
만료 없음(세션 쿠키) + 서버 유휴 30분 브라우저를 닫으면 쿠키가 사라지고, 30분 동안 요청이 없으면 서버 세션이 만료된다.

기록 설정이 새어 나간 교훈. 로컬 HTTP 개발을 위해 local-integration 프로필에 Secure=false를 두었던 적이 있다. 그런데 local-integration,production을 함께 켜는 조합에서 실행기는 막았지만, 프로필의 쿠키 완화 설정은 계속 로드됐다.

  • “기능을 실행하지 않는 것”과 “설정이 적용되지 않는 것”은 다르다.
  • 그래서 쿠키 완화를 프로필에서 빼고, 로컬 HTTP용 프로세스 환경 변수(SESSION_COOKIE_SECURE)로만 한정했다. 지금 ${SESSION_COOKIE_SECURE:true}의 기본값이 true인 이유다. 7강의 “관문이 보지 못하는 설정 경로” 교훈과 같은 계열이다.

7. 메모리 세션의 한계

확인 build.gradle에 Spring Session 의존성이 없다. 세션은 Tomcat 프로세스 메모리에 있다. 이 선택의 대가는 이렇다. 해석

  • 재시작·재배포 = 전원 로그아웃. 2강의 배포에서 backend 컨테이너를 교체하면 모든 세션이 사라진다. 사용자는 다음 요청에서 401을 받고 다시 로그인해야 한다. 무중단 배포를 미룬(DEFER) 상태라 지금은 큰 문제가 아니지만, 배포가 잦아지면 체감된다.
  • 서버를 늘리면 깨진다. 서버 B는 서버 A의 메모리 세션을 모른다. 해결책은 둘이다.
    • 로드 밸런서가 같은 사용자를 같은 서버로 보내는 스티키 세션: 서버가 죽으면 그 서버 사용자는 로그아웃된다.
    • 공유 세션 저장소: 준현의 「Redis를 활용한 Spring Session」이 설정 방법과 동작을 보여 준다.
    • 2강 트레이드오프 표에서 “서버 2대로 가려면 세션 공유 문제가 있다”고 했던 것이 이 이야기다.
  • 권한 변경이 바로 반영되지 않는다. 세션의 주체는 로그인 순간의 AuthenticatedMemberPrincipal(memberId, role) 복사본이다. 관리자가 어떤 회원의 역할을 USER로 낮춰도, 그 회원이 다시 로그인할 때까지 세션 속 역할은 ADMIN이다. 4강의 스냅샷이 여기서는 원치 않는 스냅샷이 된다. 기록 당시 관리자 기능은 역할 변경 API를 제공하지 않으므로 지금은 실제 문제가 아니다. 역할 변경 기능을 만들면 세션 무효화도 함께 설계해야 한다.

8. 로그아웃

// common/security/SecurityConfig.java (발췌)
.logout(logout -> logout.disable())        // 기본 로그아웃 필터는 끈다

@Bean
LogoutHandler logoutHandler(HttpSessionCsrfTokenRepository csrfTokenRepository) {
  return new CompositeLogoutHandler(
      new CsrfLogoutHandler(csrfTokenRepository),     // CSRF 토큰 제거
      new SecurityContextLogoutHandler(),             // 세션 무효화 + 컨텍스트 비우기
      new CookieClearingLogoutHandler("JSESSIONID")); // 브라우저 쿠키 삭제
}
  • 기본 로그아웃 필터는 리다이렉트를 하므로 끄고, 같은 일을 하는 처리기 세 개를 묶어 POST /api/auth/logout(204)에서 호출한다. 8강에서 “로그아웃도 같은 JSON 계약을 따르게 하려는 것”이라고 해석한 부분이다.
  • 로그아웃도 인증과 CSRF가 필요하다(.requestMatchers(POST, "/api/auth/logout").authenticated()). CSRF가 없으면 악성 사이트가 피해자를 강제로 로그아웃시킬 수 있다. 피해는 작지만, 로그인 CSRF와 엮으면 공격 흐름의 한 단계가 된다.
  • 세 처리기의 순서와 역할이 서버(세션), 보안 컨텍스트(스레드), 브라우저(쿠키) 세 곳을 모두 정리한다는 점이 중요하다. 하나라도 빠지면 어딘가에 로그인 흔적이 남는다.

11강 정리

  • 세션을 고른 이유: 같은 도메인, 서버 한 대, 즉시 무효화, HttpOnly로 숨기는 세션 ID. 대가는 CSRF 방어 필수와 메모리 세션의 한계다. JWT는 “기술 목록용 선도입”으로 기각됐다.
  • 로그인 흐름
    • CSRF 토큰 받기 → 로그인 POST(토큰 헤더) → 정규화 → BCrypt(더미 해시) → 세션 ID와 CSRF 토큰 교체 → SecurityContext를 직접 세션에 저장 → 새 토큰 다시 받기
    • Spring Security 6에서는 saveContext를 빼면 로그인이 유지되지 않는다.
  • 세 가지 공격과 방어
    • 세션 고정 → changeSessionId
    • CSRF → 세션 저장 토큰 + X-CSRF-TOKEN 헤더 + 명시적 SameSite=Lax(기본값 Lax는 2분 완화가 있어 더 약하다). 로그인·로그아웃에도 적용한다.
    • 계정 존재 노출 → 더미 해시와 같은 오류 응답
  • 쿠키 완화는 프로필이 아니라 프로세스 환경 변수로만: 설정은 실행하지 않아도 로드된다.
  • 메모리 세션의 한계: 재배포하면 전원 로그아웃, 확장하려면 Redis 세션, 권한 변경은 재로그인 전까지 반영되지 않는다.
  • 실패한 POST는 자동 재실행하지 않는다: 멱등성이 없는 요청의 중복을 막는다.

11강에서 남긴 미확인 항목

  • 운영 환경에서 실제 로그인·CSRF 흐름이 정상 동작하는지: 결정 기록도 “운영 로그인·CSRF 정상 동작을 다시 검증한 것은 아니다”라고 적는다.
  • BCrypt cost 10이 운영 서버(1 OCPU)에서 로그인 한 번에 걸리는 시간: 실험 단계 후보
  • Spring Security 6의 기본 CSRF 토큰 처리기(BREACH 대응 마스킹)가 GET /api/auth/csrf 응답 값과 어떻게 맞물리는지
