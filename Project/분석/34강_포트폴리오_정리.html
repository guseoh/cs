34. 포트폴리오 정리

들어가기 전

33개 강의에서 찾은 결정과 결함은 백 가지가 넘는다. 포트폴리오에는 그중 3~4개만 깊게 싣는 것이 좋다. 면접관은 목록의 길이를 보지 않는다. 고른 주제 하나를 얼마나 깊이 파고들어도 버티는지를 본다.

주제를 고르는 기준은 네 가지다.

  1. 근거가 남아 있는가. 코드, 측정 숫자, 결정 기록(PWC·ADR), PR이 있어서 "왜 그렇게 했나"에 증거로 답할 수 있어야 한다.
  2. 판단이 있는가. "구현했다"가 아니라 "A와 B 중 이런 이유로 A를 골랐고, 그 대가는 C다"를 말할 수 있어야 한다.
  3. 실패나 한계가 포함되는가. 면접의 마지막 질문은 대부분 "그래서 문제는 없었나요?"다. 이 프로젝트에는 정직하게 기록된 실패가 많다. 그것이 오히려 강점이 된다.
  4. 검증 수준을 정확히 말할 수 있는가. 로컬 합성 측정, 운영 측정, Production Verified를 구분해서 말해야 한다. 과장은 한 번의 꼬리 질문에 무너진다.

진한 색 네 개(①~④)가 메인 후보다. 판단이 깊고, 숫자나 코드 근거가 분명하다. 보라(⑤⑥⑦)는 메인 주제 안에 녹이면 좋은 보조 소재다. 회색(⑧⑨⑩)은 "이런 것도 했다" 수준으로 짧게 언급한다.

아래에서는 주제마다 같은 틀로 정리한다. 문제 → 판단 → 근거 → 대가와 한계 → 예상 질문의 순서다.

① 결제 승인과 대사

한 줄 요약

외부 결제사 호출을 DB 트랜잭션 밖으로 빼고, 결과를 모르는 결제를 UNKNOWN으로 남겨 조회로만 확정했다. "응답을 모르면 다시 청구하지 않는다."

문제·판단·근거·한계

항목 내용 근거
문제 결제사 호출 중 잠금을 잡으면 대기가 쌓인다. 응답을 못 받았을 때 다시 보내면 이중 청구가 된다 18강
판단 TX1(READY→PROCESSING 선점) → 트랜잭션 밖 호출 → TX2(확정). 무응답은 FAILED가 아니라 UNKNOWN PaymentApplicationService.confirm 확인
근거 금액 위변조 검증, 성공 결과 재생(멱등), UNKNOWN 재청구 금지, 대사는 NOT_SUPPORTED로 시도 기록을 먼저 커밋 18·19강, #417·#450 확인 기록
대가와 한계 고립된 PROCESSING의 2단계 확정(#417)은 미구현이다. 성공 처리가 3곳에 복제되어 장바구니 소비 조건이 다르다. 33-4에 개선 설계가 있다 확인

예상 질문

  • "PROCESSING에서 프로세스가 죽으면요?" 지금 구조의 빈칸이다. 리스 컬럼과 2단계 복구 설계(33-4)로 답한다.
  • "4xx는 실패 아닌가요?" 4xx는 "결제가 일어나지 않았다"는 보증이 아니다. 지금 코드는 승인 경로와 조회 경로의 해석이 다르다는 결함까지 함께 말한다.

② 250 RPS 운영 장애 분석

한 줄 요약

운영 HTTPS에 계단식 부하를 걸었다. 250 RPS에서 실패했고, 원인이 RDS가 아니라 Backend 컨테이너의 memory cgroup OOM임을 커널 로그와 재시작 시각으로 확정했다. "그럴듯한 가설을 버리는 근거."

문제·판단·근거·한계

항목 내용 근거
결과 25~200 RPS PASS(p95 15~18ms). 250 RPS FAIL: 실제 236.89 RPS, 오류 6.88%, p95 약 4.2초 Issue #168 기록
기각한 가설 k6 VU 소진(지연의 결과), CPU 1.0(재시작 직후 JVM 기동 포함), Hikari pending 189(결과), 작은 RDS(CPU 8~12%, 지연 1.5ms 이하) 30강 기록
확정한 원인 커널 Memory cgroup out of memory, RestartCount=1. heap 274MiB/max 402MiB로 힙 OOM이 아님. 스레드 217개 등 힙 밖 메모리 기록
대가와 한계 같은 조건(640MiB, MaxRAMPercentage=65, Tomcat 기본 스레드)이 지금 compose에 그대로 남아 있다(BL-30-01) 확인

이 주제가 강한 이유

운영에서 실제로 측정한 숫자다. 그리고 결론이 "증설"이 아니다. RDS를 키우지 않은 판단 자체가 이야기가 된다.

주의할 표현

"250 RPS를 처리했다"가 아니다. "200 RPS까지 통과, 250 RPS에서 실패 원인을 찾았다"다. 236.89 RPS를 Backend나 RDS의 최대 처리량처럼 말하지 않는다.

③ 상품 목록 성능 진단

한 줄 요약

로컬에서 운영과 같은 제한(CPU 0.75, 640MiB)을 걸고 변수를 하나씩 바꿔 병목을 좁혔다. 근거 없는 코드 최적화는 하지 않았다. 구조적 해법(Redis 캐시)으로 p95를 6,855ms에서 4.71ms로 줄였다. 그리고 그 결정을 지키지 못한 이야기까지 함께 있다.

문제·판단·근거·한계

항목 내용 근거
측정 원칙 k6 열린 모델(constant-arrival-rate), dropped 0 임계, 첫 결과 보존과 재실행 금지 28강 확인
반직관적 결과 Hikari 10→20에서 악화. SQL 평균 0.68ms인데 p95 6.8초. 일하는 시간이 아니라 줄 서는 시간 PERF-PH9-014 기록
no-change 판정 JFR 표본이 0개라 핫스팟을 특정할 수 없어 코드를 바꾸지 않았다 기록
구조 해법 Redis 캐시 After: 250 RPS 목표 달성, dropped 0, p95 4.71ms, SQL 48,154 → 194 PERF-PH10-008 기록
후일담 2주 뒤 PR #279가 캐시 호출을 지웠는데 모든 테스트가 통과했다 커밋 1af3022c 확인

이 주제가 강한 이유

성공 숫자와 실패 이야기가 함께 있다. "측정으로 내린 결정이 왜 조용히 사라졌는가 → 성능 회귀 게이트와 보호할 계약이 필요하다(33-2)"까지 이어서 말할 수 있다. 이 대목에서 면접관은 단순 구현자와 시스템을 보는 사람을 구분한다.

주의할 표현

모든 숫자는 로컬 합성 부하다. 운영 SLA나 최대 용량이 아니다. 저장소 문서도 스스로 그렇게 적었다.

④ 정기배송 1만 건 몰림

한 줄 요약

자동 주문 1만 건이 한꺼번에 몰리는 상황을 측정했다. 처리 속도가 아니라 배치 사이의 대기가 병목임을 찾았다. 그래서 메시지 큐 없이 배치 크기와 주기만 조정했다. "Kafka를 쓰지 않기로 한 근거."

측정 결과

항목 Before After 근거
배치 / 주기 100건 / 60초 500건 / 15초 PERF-PH10-004·006 기록
순수 처리율 20.19 orders/s 21.80 orders/s 기록
완료 시간(투영) 6,435초 743초 기록
정합성 10,000 → 0, 실패 0 동일, 행 잠금 대기 0 기록

판단의 핵심은 이것이다. 처리율은 8%만 올랐는데 완료 시간은 약 9분의 1이 됐다. 쉬는 시간이 줄었기 때문이다. 정합성 손실·잠금 대기·커넥션 대기가 모두 0이므로 Kafka·Outbox는 NOT SELECTED로 판정했다. 재검토 조건(재시작을 넘어 살아남아야 하는 작업, 독립 소비자 확장 등)도 함께 기록했다.

함께 말할 수 있는 설계 소재

  • 회차별 REQUIRES_NEW로 한 회차의 실패가 배치 전체를 롤백하지 않게 한 구조
  • 회차당 주문 하나를 보장하는 UNIQUE(schedule_id)
  • UNKNOWN 정기결제를 다시 청구하지 않는 원칙(22~24강)

주의할 표현

743초는 측정이 아니라 투영값이다. 실제 스케줄러로 끝까지 돌린 시간이 아니다. 그리고 재시도 간격이 없는 문제(3분 안에 3회 소진)는 한계로 함께 말한다.

⑤⑥⑦ 보조 소재

메인 주제 안에서 꼬리 질문이 나왔을 때 꺼내는 소재다.

소재 핵심 한 문장 이어지는 메인
⑤ 재고 동시성 FOR UPDATE + version CAS + 원장 UNIQUE(payment_id, type, sku_id). 잠금 순서가 경로마다 반대라는 교착 후보도 직접 찾았다(17·18강) ①
⑥ 멱등성 길이 접두사 지문 + SHA-256, 같은 키·다른 요청은 409. 보관은 첫 성공 + 30일이고, 재생과 정리가 경쟁하는 두 순서를 모두 테스트했다(16·17·25강) ①④
⑦ 배포 엔진 운영 호스트가 바깥으로만 조회하는 pull CD, 커밋 SHA 태그와 digest 검증, 전이 전에 남기는 WAL 표식, fsync·rename·디렉터리 fsync로 원자적 쓰기, DB는 되돌리지 않는 롤백(29·31강) ②

⑦은 단독 주제로도 쓸 수 있다. 다만 검증 범위를 정확히 말해야 한다. 감독형 배포, adopt, CD 타이머 활성화까지는 Production Verified(2026-10-31)다. 새 커밋의 자동 배포 E2E와 실제 롤백은 아직 실행하지 않았다.

⑧⑨⑩ 짧게 언급할 소재

  • ⑧ 관측: Actuator 노출을 두 개로 줄이고 metrics-proxy로 한 경로만 열었다. 진단은 두 신호를 교차하고, 모르면 UNKNOWN으로 판정한다(fail-closed). 다만 알림 실행 트리거가 없다(27강).
  • ⑨ AWS → OCI 이전: 기술이 아니라 비용으로 내린 결정이다. AWS의 검증 수준을 OCI가 자동으로 물려받지 않는다고 명시했다(30·31강). Git 소유권 문제를 두 번 만나 두 가지로 다르게 해결한 이야기도 있다.
  • ⑩ AI 활용 경계: AI는 구매 가능 상품을 결정하지 않고 검증된 후보만 재정렬한다(PWC-0010). 개발 과정에서는 실행 권한 4단계와 "Production Verified" 어휘를 가진 하네스로 AI 작업을 통제했다(15·32강).

⑩을 말할 때는 본인이 무엇을 결정했고 AI가 무엇을 수행했는지를 본인 기준으로 정리해서 말해야 한다. 하네스 문서는 "사용자는 Product Owner이자 Tech Lead이고, AI는 승인된 범위에서 실행한다"고 역할을 정의한다. 이 문서는 실제 기여의 경계를 추론하지 않았다. 그 부분은 직접 채워야 한다.

1분 설명 틀

틀

문제 → 관찰 → 기각한 가설 → 확정 근거 → 하지 않은 것 → 다음 단계 순서로 말한다. "하지 않은 것"이 들어가는 것이 핵심이다. 무엇을 하지 않기로 판단했는지가 판단력을 가장 잘 보여 준다.

② 예시

"운영 서버의 한계를 알기 위해 상품 목록 API에 25 RPS부터 계단식 부하를 걸었습니다. 200 RPS까지는 p95 20ms 안쪽이었고, 250 RPS에서 오류율 6.9%로 실패했습니다. CPU 100%, 커넥션 풀 대기 189, 작은 RDS 인스턴스가 모두 의심스러웠습니다. 그런데 RDS 지표는 CPU 10% 안팎에 지연 1.5ms 이하라 DB 병목 가설을 버렸습니다. 결정적 증거는 커널의 memory cgroup OOM 로그와 컨테이너 재시작 시각이었습니다. 힙은 최대치에 닿지 않았는데, 스레드 217개 같은 힙 밖 메모리가 640MiB 제한을 넘긴 것입니다. 그래서 인스턴스를 키우지 않았고, 다음 단계는 스레드 상한과 힙 밖 메모리 예산을 같은 부하에서 함께 측정하는 것으로 정했습니다."

④ 예시

"정기배송 자동 주문이 1만 건 몰리는 상황을 측정했습니다. 처리율은 초당 20건 정도였는데, 완료까지 투영하면 6,400초가 넘었습니다. 원인은 처리 속도가 아니라 60초마다 100건씩 처리하고 쉬는 배치 주기였습니다. 메시지 큐를 도입하는 대신 배치를 500건, 주기를 15초로 바꿨고, 정합성 손실과 잠금 대기 없이 투영 완료 시간이 743초로 줄었습니다. 이 측정을 근거로 Kafka와 Outbox는 선택하지 않았고, 다시 검토할 조건을 결정 기록에 남겼습니다. 다만 743초는 실측이 아닌 투영값이라, 실제 스케줄러로 끝까지 돌리는 측정이 남아 있습니다."

"서버가 한 대인데 장애 나면요?" 맞다, 단일 장애점이다. 다중 인스턴스 전제 조건(세션 저장소, 리스 기반 대사, 후보 선점)을 목록으로 정리해 두었다(33-7)
"DB 백업은 복원해 봤나요?" AWS 시절 격리 복원까지만 했고 운영 DB 복원과 RTO는 미검증이다. 첫 migration 전 필수 작업으로 계획했다(33-2)
"테스트가 다 통과했는데 왜 캐시가 빠졌죠?" 기능 테스트는 성능 회귀를 잡지 못한다. 경로 계약 테스트와 SQL 수 기반 회귀 게이트를 설계했다(33-2)
"AI가 짠 코드 아닌가요?" 본인의 역할(결정, 승인, 검증)을 본인 기준으로 답한다. 하네스의 권한 구분과 검증 절차를 근거로 든다
