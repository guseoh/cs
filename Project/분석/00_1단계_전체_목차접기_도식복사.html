1강. PawCycle Commerce는 무엇이고, 어떻게 생겼는가

기준: GitHub main = f9ab9f87 (2026-11-12) · 깊이: L1 전체 지도 표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 미확인

이번 강의에서 설명할 수 있게 되는 것

  • PawCycle이 어떤 문제를 푸는 서비스이고, 왜 정기배송이 도메인의 중심인가
  • 그 도메인 판단이 DB 스키마에 어떤 모양으로 남았는가 (가장 깊게 다룸)
  • 실행하면 어떤 컨테이너가 어떻게 연결되어 떠 있는가
  • 코드가 도메인 → 계층 순서로 나뉜 방식과, 그 규칙을 테스트로 강제하는 방법
  • 기술 스택 각각을 왜 골랐는지, 근거가 어디에 있는가

중요도에 따라 깊이를 다르게 했다. 2절(도메인이 스키마에 남긴 흔적)과 4절(실행 구성), 5절(코드 구조)을 깊게 다루고, 나머지는 지도를 그리는 수준으로 짧게 간다.

1. 이 서비스가 푸는 문제: 반복 구매

PawCycle은 사료·간식·모래·배변 패드 같은 반려동물 소모품을 파는 커머스다. 이 상품군의 특징은 한 번 사고 끝나지 않는다는 것이다. 사료는 몇 주마다 떨어지므로 같은 물건을 정해진 주기로 계속 받고 싶은 수요가 생긴다. 그래서 이 프로젝트에는 구매 흐름이 두 개 있다.

위 두 번째 그림(두 구매 흐름) 이 그 구조다.

  • 일반 구매(청록): 장바구니에 담고 → 체크아웃에서 재고·쿠폰을 예약하고 → 토스 결제 승인에서 확정하고 → 배송한다.
  • 정기배송(보라): 플랜을 고르고 → 구독을 만들 때 가격·구성을 스냅샷으로 고정하고 → 회차가 오면 → 스케줄러가 자동으로 주문을 만들고 → 정기결제한다.
  • 공유 기반(회색): 두 흐름은 회원, 상품·SKU, 재고, 결제 테이블을 함께 쓴다. 확인 결제 테이블은 type 컬럼으로 일반 결제(NORMAL)와 정기결제(BILLING)를 구분한다. 결제 대사 코드가 이 값으로 분기한다.

도메인 용어 가운데 코드를 읽을 때 반드시 구분해야 하는 것만 추리면 다음과 같다.

용어 뜻 구분하는 이유
상품 · SKU 상품은 “연어 사료”, SKU는 “연어 사료 2kg” 가격·재고·주문은 SKU에 걸린다
판매 상태 · 구독 가능 여부 일반 구매로 팔 수 있는가 · 정기배송 대상으로 고를 수 있는가 기록 1차 MVP부터 별개 개념으로 정의했다
플랜 · 플랜 버전 종별 패키지 상품 · 그 가격과 구성의 한 판 가격이 바뀌면 버전을 새로 만든다
스냅샷 가입 시점의 가격·구성 복사본 플랜이 바뀌어도 기존 고객 조건을 지킨다
회차 · 정기 주문 예정된 배송 · 그 회차를 실제로 처리한 결과 한 회차에 주문은 최대 하나

2. 도메인 판단이 스키마에 남긴 흔적 (깊게)

도메인 설명을 문서로만 읽으면 추상적이다. 이 프로젝트에서는 마이그레이션 파일이 도메인 결정의 화석이다. 같은 subscriptions 테이블이 1차 MVP와 2차 MVP에서 어떻게 달라졌는지 보면 도메인이 어떻게 자랐는지가 그대로 보인다.

1차 MVP의 구독: SKU 하나를 고르는 단순한 약속

-- backend/src/main/resources/db/migration/V2__create_subscriptions.sql
CREATE TABLE subscriptions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    sku_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    created_date DATE NOT NULL,
    next_order_date DATE NOT NULL,
    ...
    CONSTRAINT chk_subscriptions_quantity CHECK (quantity BETWEEN 1 AND 10),
    CONSTRAINT chk_subscriptions_delivery_cycle CHECK (delivery_cycle_weeks IN (2, 4, 8)),
    CONSTRAINT chk_subscriptions_date_order CHECK (next_order_date > created_date)
);

이 DDL은 1차 MVP 요구사항(PS-002)을 거의 한 줄씩 옮긴 것이다.

  • sku_id 하나 → 기록 “구독 하나는 SKU 하나만 대상으로 한다”
  • quantity BETWEEN 1 AND 10 → “구독 수량은 1~10”
  • delivery_cycle_weeks IN (2, 4, 8) → “배송 주기는 2주, 4주, 8주”
  • next_order_date > created_date → “다음 주문 예정일 = 생성일 + 배송 주기”

해석 규칙을 애플리케이션 코드뿐 아니라 DB의 CHECK 제약에도 걸어 둔 것이 이 프로젝트의 습관이다. 코드에 버그가 있거나 누군가 SQL로 직접 넣어도 규칙을 어기는 행은 저장되지 않는다. 기록 결정 기록 PWC-0044는 여기서 한 가지를 더 구분한다. 도메인 코드는 “정확히 생성일 + 주기”라는 등식을 검사하고, DB는 “예정일이 생성일보다 뒤”라는 순서만 검사한다. DB 제약은 최후 방어선이고, 정확한 규칙은 도메인이 가진다는 역할 분담이다.

2차 MVP의 구독: 스냅샷으로 약속을 고정한다

2차 MVP에서 구독은 “SKU 하나”가 아니라 “종별 패키지 플랜”을 구독하는 것으로 바뀌었다. 핵심 문제는 이것이다. 판매자가 플랜 가격을 올리면, 이미 가입한 고객의 다음 결제 금액도 바뀌어야 하는가? 기록 2차 MVP 요구사항(PS-004)의 답은 “아니다”였다. 가격·구성 변경은 새 플랜 버전으로만 하고, 기존 구독 가격은 자동으로 바꾸지 않는다.

-- V3__add_second_mvp_subscription_schema.sql (발췌)
CREATE TABLE plan_versions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    plan_id BIGINT NOT NULL,
    package_price_krw BIGINT NOT NULL,
    ...
);
ALTER TABLE subscription_plans
    ADD CONSTRAINT fk_subscription_plans_current_version
        FOREIGN KEY (current_plan_version_id, id) REFERENCES plan_versions (id, plan_id);

CREATE TABLE subscription_snapshots (
    id BIGINT NOT NULL AUTO_INCREMENT,
    subscription_id BIGINT NULL,
    source_plan_version_id BIGINT NOT NULL,
    package_total_krw BIGINT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    ...
);
CREATE TABLE subscription_schedules (
    ...
    effective_snapshot_id BIGINT NULL,
    CONSTRAINT uk_schedules_subscription_date UNIQUE (subscription_id, scheduled_date),
    CONSTRAINT chk_schedules_status CHECK (status IN ('SCHEDULED', 'SKIPPED', 'HELD', 'CANCELED'))
);
CREATE TABLE pending_plan_changes (
    subscription_id BIGINT NOT NULL,          -- PK: 구독당 대기 변경 하나
    snapshot_id BIGINT NOT NULL,
    target_schedule_id BIGINT NOT NULL,       -- 어느 회차부터 적용할지
    ...
);

이 DDL에서 읽어야 할 설계 판단은 네 가지다.

  • 가격이 두 번 저장된다. plan_versions.package_price_krw는 “지금 파는 가격”, subscription_snapshots.package_total_krw는 “이 고객이 약속받은 가격”이다. 정규화 원칙만 보면 중복이지만, 둘은 의미가 다른 값이다. 스냅샷이 플랜 버전을 참조하지 않고 금액을 복사해 두므로, 플랜이 바뀌어도 고객의 약속은 그대로다.
  • 복합 외래 키로 “엉뚱한 버전”을 막는다. (current_plan_version_id, id) → plan_versions(id, plan_id)는 “플랜의 현재 버전은 반드시 그 플랜의 버전이어야 한다”를 DB가 보장하게 한다. 단순히 current_plan_version_id → plan_versions(id)로 걸면 다른 플랜의 버전을 가리켜도 막을 수 없다.
  • 플랜 변경은 “다음 회차부터”다. pending_plan_changes는 구독당 한 행(PK가 subscription_id)이고, 어느 회차부터 적용할지(target_schedule_id)를 가진다. 변경을 즉시 덮어쓰지 않고 대기시켜 두었다가, 그 회차의 주문을 만들 때 현재 스냅샷으로 승격한다.
  • 회차 하나에 날짜 하나. UNIQUE (subscription_id, scheduled_date)는 같은 구독에 같은 날 회차가 두 번 생기지 않게 한다. 뒤에서 볼 “스케줄러가 여러 번 돌아도 결과는 하나” 규칙의 바닥이 된다.

해석 테이블 = 엔티티 = 애그리거트가 아니다. 스냅샷·대기 변경·회차는 모두 별도 테이블이지만, 도메인으로는 “구독 하나의 상태”를 이루는 부분들이다. 결정 기록의 학습 가이드(PWK-0001)가 “DB 테이블을 도메인 애그리거트와 동일시하지 않는다”고 따로 적어 둔 이유가 여기 있다. 이 차이는 5강(도메인 모델)에서 코드와 함께 본다.

멱등성 테이블이 네 개라는 것의 의미

확인 같은 V3에 subscription_creation_idempotency_results와 subscription_command_idempotency_results가 함께 생겼고, 이후 V14에 체크아웃, V22에 빠른 재주문의 결과 테이블이 생겼다. 모두 (회원, 키)를 기본 키로 삼고, 요청 지문과 응답을 저장한다.

해석 이 프로젝트는 “두 번 실행되면 사고가 나는 요청”을 처음부터 의식했다. 구독 생성, 구독 변경, 체크아웃, 재주문이 그렇다. 기록 다만 처음부터 그랬던 것은 아니다. 결정 기록 PWC-0031은 1차 MVP 구독 API에서 멱등성을 도입하지 않았고, 그 대가를 당시에 받아들였다고 기록한다. 2차 MVP에서 구독 변경 명령이 생기면서 도입됐다.

3. 어떻게 자라 왔는가

위 세 번째 그림(MVP 이력) 이 커밋 이력(681개)을 단계로 묶은 것이다. 이 그림에서 기억할 것은 두 가지다.

  • 정기배송(보라)이 먼저, 일반 구매(청록)가 나중이다. 결제·재고·장바구니는 첫 커밋 한 달 뒤인 8월 13일에야 붙었다. 그래서 같은 “주문”이 subscription_orders(V9)와 orders(V14) 두 벌로 존재한다. 확인 V15의 이름이 backfill_legacy_subscription_orders인 것으로 보아 둘을 잇는 이행 작업이 있었다. 미확인 두 주문 모델의 현재 관계는 6강(ERD)에서 확인한다.
  • 과거를 고치지 않고 덧붙인다. 기록 PS-005는 “PS-004는 당시의 역사적 계약이며 소급 수정하지 않는다”고 적는다. 마이그레이션도 V1부터 V28까지 기존 파일을 고치지 않고 새 파일을 쌓는다. 그래서 코드 곳곳에 “예전 형식의 데이터”를 다루는 분기가 남는다. 체크아웃이 최초 장바구니 버전이 없는 예전 멱등성 결과를 거절하던 코드가 그 예다.

4. 실행하면 무엇이 떠 있는가 (깊게)

위 첫 번째 그림(컨테이너 구성) 이 운영 Compose 파일을 그대로 옮긴 것이다.

요청의 길

확인 infra/production/nginx.conf의 핵심은 두 줄이다.

location /api/ { proxy_pass http://backend:8080; }   # Spring Boot
location /     { proxy_pass http://frontend:3000; }  # Next.js

브라우저는 서버 하나(Nginx)에만 말을 건다. 주소가 /api/로 시작하면 Spring Boot로, 나머지는 Next.js로 간다. 같은 도메인을 쓰므로 세션 쿠키와 CSRF 처리가 단순해진다. 해석 프론트와 백엔드가 서로 다른 도메인이었다면 CORS와 쿠키의 SameSite 설정을 따로 다뤄야 했을 것이다. 세션 인증을 고른 결정(PWC-0007)과 이 라우팅은 함께 읽어야 한다.

컨테이너 설정이 말해 주는 운영 판단

# infra/production/compose.yaml (backend 서비스 발췌)
backend:
  image: ${BACKEND_IMAGE}:${BACKEND_RELEASE_SHA:-${RELEASE_SHA}}
  environment:
    JAVA_TOOL_OPTIONS: -XX:MaxRAMPercentage=65.0 -XX:+ExitOnOutOfMemoryError
    SPRING_PROFILES_ACTIVE: production
  healthcheck:
    test: [CMD, curl, --fail, ..., http://127.0.0.1:8080/api/products]
  read_only: true
  security_opt: [no-new-privileges:true]
  networks: [app, database-egress]
  mem_limit: 640m
  cpus: 0.75
  • 이미지 태그가 커밋 SHA다. latest 같은 이름이 아니라 정확한 커밋으로 배포한다. 어떤 코드가 떠 있는지 항상 알 수 있고, 되돌릴 때도 그 SHA로 돌아간다. 기록 PWC-0025가 “정확한 이미지·소스·DB 호환 근거를 승인한다”고 정한 결정의 구현이다.
  • JVM 힙을 컨테이너 메모리의 비율로 정한다. 컨테이너 한도 640MB의 65%를 힙 상한으로 쓰고, 메모리가 부족하면 어정쩡하게 버티지 않고 프로세스를 종료한다. 기록 교훈 PWL-0032에 따르면 AWS 시절 250 RPS 장애의 원인은 힙 부족이 아니라 컨테이너 메모리 한도 초과(cgroup OOM) 였다. 힙 바깥 메모리까지 컨테이너 한도 안에 들어가야 한다는 경험이 이 설정에 남아 있다.
  • 헬스 체크가 실제 API를 부른다. /api/products가 응답해야 건강하다고 본다. 해석 프로세스가 떠 있는지만이 아니라 DB까지 연결돼 상품을 읽을 수 있는지를 본다는 뜻이다. Nginx는 depends_on: condition: service_healthy로 백엔드가 건강해진 뒤에 뜬다.
  • 파일 시스템은 읽기 전용이다. 쓰기는 /tmp 메모리 영역만 허용하고, 권한 상승도 막는다.

Compose에 없는 것

  • MySQL이 없다. 확인 백엔드는 database-egress 네트워크로 바깥의 DB에 붙는다. 기록 운영 개요는 이를 OCI의 Managed MySQL로 적는다. DB의 생명주기를 애플리케이션 Compose가 소유하지 않게 한 결정이다(ARCH-012).
  • Redis가 없다. 확인 상품 목록 캐시는 PAWCYCLE_PRODUCT_LIST_CACHE_ENABLED 기본값이 false다. 미확인 운영 환경 파일에서 켜져 있는지는 확인하지 않았다.

애플리케이션 설정이 말해 주는 것

# backend/src/main/resources/application.properties (발췌, 비밀값 생략)
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
spring.jpa.properties.hibernate.jdbc.time_zone=UTC
spring.flyway.validate-on-migrate=true
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.same-site=lax
management.endpoints.web.exposure.include=health,prometheus
pawcycle.toss.test.enabled=${PAWCYCLE_TOSS_TEST_ENABLED:false}
pawcycle.ai.review-summary.enabled=${PAWCYCLE_AI_REVIEW_SUMMARY_ENABLED:false}
  • 스키마는 Flyway만 바꾼다. ddl-auto=validate는 Hibernate가 엔티티와 테이블이 맞는지 검사만 하고 스키마를 고치지 않게 한다. 그래서 2절의 DDL이 곧 실제 스키마다.
  • OSIV를 끈다. 영속성 컨텍스트가 요청 내내 열려 있지 않다. 리뷰 요약·결제 승인에서 본 “트랜잭션 밖 외부 호출” 설계가 성립하는 전제다.
  • 시간은 UTC로 저장한다. 기록 PWC-0021은 장바구니·찜 시각을 UTC로 바꾸면서, 기존 행의 표시 재해석을 “승인된 대가”로 받아들였다.
  • 외부 연동은 기본이 꺼짐이다. 토스 실결제, 리뷰 요약 AI, 상품 비교 AI, 추천 AI가 모두 기본값 false다. 켜지 않으면 서비스는 외부 없이 동작한다.

5. 코드는 어떻게 나뉘어 있는가 (깊게)

패키지를 나누는 두 방식

출처: Ogu, 「[Spring] Spring 패키지 구조」 (velog). 이미지는 원문을 직접 열어 내용을 확인했다.

이 그림의 왼쪽이 계층형, 오른쪽이 도메인형이다. 왼쪽은 Controller 폴더 안에 상품·회원·주문 컨트롤러가 모여 있고, 오른쪽은 상품 폴더 안에 상품의 Entity·Repository·Controller·Service가 모여 있다. 원문은 계층형은 전체 구조를 빨리 파악할 수 있지만 클래스가 한 폴더에 쌓이고, 도메인형은 응집도가 높지만 처음에는 전체를 파악하기 어렵다고 정리한다.

PawCycle의 선택: 도메인 먼저, 그 안에서 계층

위 네 번째 그림(패키지와 계층) 이 그 구조다.

  • 위쪽: 최상위는 도메인이다. 그림 속 숫자는 손으로 쓴 소스 파일 수다. 확인 commerce(232개)가 가장 크고, 그 안에 장바구니·체크아웃·결제·재고 등 하위 기능이 18개 있다.
  • 아래쪽: 기능 하나를 열면 다섯 계층이 있다. application이 중심에서 domain·persistence·infrastructure를 부르고, api는 application만 부른다.

기록 아키텍처 문서(backend-architecture-v2.md)는 계층마다 금지 사항을 정해 두었다.

  • api: HTTP·검증·DTO만. 저장소·엔티티·SQL 도구를 직접 참조하지 않는다.
  • application: 유스케이스와 트랜잭션의 주인. API DTO를 참조하거나 SQL을 직접 실행하지 않는다.
  • domain: 엔티티·값·불변식·상태 전이. api와 infrastructure에 의존하지 않는다.
  • persistence: JPA·잠금·쿼리·이유 있는 네이티브 SQL.
  • infrastructure: 토스·AI·Redis 세부 구현. 외부 DTO를 안으로 흘리지 않는다.

규칙을 테스트로 강제한다

이 규칙은 문서로만 있지 않다. 확인 테스트 의존성에 com.tngtech.archunit:archunit:1.5.0이 있고, 기록 BackendArchitectureTests가 위 규칙을 위반하면 빌드를 실패시킨다. ArchUnit의 사용법은 lango의 「ArchUnit을 활용한 아키텍처 테스트 작성하기」가 layeredArchitecture()로 “어느 계층이 어느 계층에만 접근할 수 있다”를 쓰는 예제로 보여 준다. 규칙을 테스트로 남기면 그 자체가 살아 있는 문서가 된다는 것이 그 글의 요지다.

여기서 이 프로젝트만의 현실적인 장치가 나온다.

  • 기록 이미 있던 위반 204개를 목록 파일에 동결했다(legacy-dependencies.txt). 그중 186개가 금지한 바로 그 방향(application → api) 이다.
  • 새 위반은 막고, 사라진 위반은 목록에서 지우게 한다. 테스트가 목록을 자동으로 고치지 않는다.

해석 대규모 리팩터링 없이 아키텍처 규칙을 도입하는 방법이다. 동시에 계층 규칙은 목표이지 현재 상태가 아니다. 코드를 읽다 규칙상 있으면 안 되는 의존을 만나도 놀랄 필요가 없다. 기록 결정 기록은 OOP·DDD 리팩터링이 별도로 진행 중이라고 적고 있다. 확인 기준 커밋(main)에는 아직 들어오지 않았다.

도메인 사이의 경계는 아직 느슨하다

해석 계층 규칙에 비해 도메인끼리의 경계는 강제되지 않는다. 체크아웃 저장소 어댑터 하나가 주문·결제·쿠폰·회원 주소·SKU·장바구니 저장소 아홉 개를 직접 쓰는 것을 앞선 분석에서 봤다. 하나의 배포 단위 안에서 도메인 모듈 사이 경계까지 지키는 구조를 모듈러 모놀리스라 부른다. msbaek의 「Spring Modulith with DDD」 정리는 바운디드 컨텍스트를 모듈로 삼고, 계층별 패키징은 정의상 응집도가 낮아 모듈이 되지 못한다고 설명한다. PawCycle은 도메인별 패키징까지 했지만 도메인 사이 경계는 아직 강제하지 않는 단계에 있다.

1. C4 모델: 지도를 네 배율로 그리는 법

아키텍처 그림이 쓸모없어지는 가장 흔한 이유는 한 장에 모든 것을 그리려 하기 때문이다. 사용자, 서버, 클래스, 테이블이 한 그림에 섞이면 아무도 읽지 못한다. C4 모델은 지도 앱처럼 배율을 나눈다.

  • Level 1 System Context: 우리 시스템을 상자 하나로 두고, 누가 쓰고 어떤 외부 시스템과 이야기하는가
  • Level 2 Container: 시스템을 따로 실행되는 단위(웹 앱, API 서버, DB)로 쪼갠다
  • Level 3 Component: 컨테이너 하나 안의 주요 구성 요소와 책임
  • Level 4 Code: 클래스 수준. 대부분 코드에서 자동 생성하고 손으로 그리지 않는다

teamsmiley의 「C4 model introduce」가 네 단계를 레벨별로 정리하고, 코드 다이어그램은 손으로 그리기보다 자동 생성을 권한다고 적는다. 아래는 C4를 만든 Simon Brown의 공식 사이트에 있는 Container 다이어그램 예시다.

이 그림에서 볼 점은 세 가지다.

  • 파란 테두리 안이 시스템 하나이고, 그 안의 상자(UI, Backend, Database)가 Container다. 바깥의 초록 사람과 빨강·주황 상자는 사용자와 외부 시스템이다.
  • 화살표마다 “무엇을, 어떤 방식으로” 가 적혀 있다(“Makes API requests to [JSON/HTTPS]”). 선만 긋고 끝내지 않는다.
  • 여기서 Container는 Docker 컨테이너가 아니다. “따로 배포·실행되는 단위”라는 뜻이다. 우연히 PawCycle에서는 둘이 거의 일치하지만, 개념은 구분해야 한다.

PawCycle의 System Context

PawCycle을 상자 하나로 놓으면 다음과 같다.

  • 사람은 둘이다. 비회원·회원 고객과 관리자다. 확인 관리자 기능은 /api/admin/**가 hasRole("ADMIN")으로 분리돼 있다.
  • 외부 시스템은 둘이다. 토스는 결제 승인과 조회, OpenAI는 리뷰 요약·상품 비교·추천에 쓰인다. 점선은 설정으로 켰을 때만 존재하는 연결이다. 확인 AI 기능은 모두 기본값이 꺼짐이다.
  • 해석 이 그림에서 가장 중요한 정보는 “외부 시스템이 둘뿐”이라는 사실이다. 이 시스템의 정합성 설계가 대부분 “잠금 + DB 트랜잭션”으로 풀리고, 복잡한 상태(PROCESSING, UNKNOWN)는 이 두 외부 경계에서만 생기는 이유가 여기 있다.

2. Container 수준: 세 컨테이너와 세 네트워크

1강에서 컨테이너 셋(proxy, frontend, backend)을 봤다. 이번에는 그 컨테이너들이 어떤 네트워크에 붙어 있는가를 본다. 이 설계가 보안 경계를 만든다.

# infra/production/compose.yaml (발췌)
services:
  backend:
    expose: ["8080"]                        # 다른 컨테이너에게만 공개
    networks: [app, database-egress]
  frontend:
    expose: ["3000"]
    networks: [app]
  proxy:
    ports:
      - "${PAWCYCLE_HTTP_PORT:-80}:80"      # 호스트 포트 → 컨테이너 포트
      - "${PAWCYCLE_HTTPS_PORT:-443}:443"
    networks: [edge, app]

networks:
  edge:
    name: pawcycle-production-edge
  app:
    name: pawcycle-production-app
    internal: true                          # 바깥으로 나가는 길이 없는 네트워크
  database-egress:
    name: pawcycle-production-database-egress

코드에서 읽어야 할 것은 두 가지다.

  • ports와 expose는 다르다. ports는 호스트의 포트를 컨테이너 포트로 연결해 인터넷에서 닿을 수 있게 한다. expose는 같은 네트워크의 다른 컨테이너에게만 포트를 알린다. 인터넷에서 닿는 컨테이너는 proxy 하나뿐이다.
  • internal: true 인 app 네트워크는 원리 외부로 나가는 경로(게이트웨이)가 없는 네트워크다. 그 네트워크에만 붙은 컨테이너는 같은 네트워크의 이웃과만 통신하고 인터넷으로 나갈 수 없다.

이 설정을 그림으로 옮기면 다음과 같다.

주황색 화살표가 암호화된 구간이다. 브라우저와 Nginx 사이만 암호화되고, Nginx와 Spring 사이(⑥⑦)는 평문 HTTP다. 이 구조를 TLS 종료(TLS termination) 라고 한다. 단계별로 내려가 보자.

①② DNS: 이름을 주소로 바꾸기

컴퓨터는 이름이 아니라 IP 주소로 통신한다. 브라우저는 먼저 OS에 이름을 묻고, OS는 설정된 재귀 리졸버(보통 통신사나 공용 DNS)에 묻는다. 리졸버는 답을 모르면 계층을 따라 내려간다.

  • 루트 서버에 묻는다 → “.org는 이 TLD 서버에 물어라”
  • TLD 서버(.org)에 묻는다 → “duckdns.org는 이 권한 서버에 물어라”
  • 권한 네임 서버(DuckDNS)에 묻는다 → “pawcycle.duckdns.org의 A 레코드는 이 IP다, TTL은 N초”

리졸버는 받은 답을 TTL 동안 캐시한다. 그래서 두 번째 사용자부터는 루트까지 가지 않는다. 대신 IP를 바꾸면 TTL이 끝날 때까지 옛 주소로 가는 사용자가 생긴다. Dale Seo의 「DNS 서버 동작 원리」가 이 질의 흐름을 단계별로 따라가고, 캐시와 TTL이 응답 속도와 변경 반영 지연에 어떤 영향을 주는지 설명한다.

트레이드오프: 왜 무료 동적 DNS인가? 해석 DuckDNS는 무료이고 IP가 바뀌어도 갱신할 수 있지만, 레코드 종류와 TTL 조절, 장애 시 지원을 직접 통제하지 못한다. 개인 프로젝트에서 비용을 0으로 유지하려는 방향(뒤의 8절)과 같은 선택이다. 실제 서비스라면 자기 도메인과 관리형 DNS를 쓰는 것이 기본이다. 미확인 DuckDNS를 고른 기록은 찾지 못했다.

③ TCP: 연결을 맺는 세 번의 악수

IP를 알았으면 그 주소의 443번 포트로 TCP 연결을 맺는다. TCP는 데이터가 순서대로, 빠짐없이 도착하도록 보장하는 프로토콜이고, 그 전에 양쪽이 준비됐는지 확인하는 3-way handshake를 한다.

  1. 클라이언트 → 서버: SYN (연결하고 싶다, 내 시작 번호는 x)
  2. 서버 → 클라이언트: SYN-ACK (좋다, x+1을 기다리겠다, 내 시작 번호는 y)
  3. 클라이언트 → 서버: ACK (y+1을 기다리겠다)

원리 연결 하나는 (출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트) 네 값으로 구분된다. 서버 쪽에서 443을 듣는 소켓은 하나지만, 연결마다 새 소켓이 만들어진다. 이 왕복 한 번이 지연 시간에 그대로 더해지므로, 연결을 재사용(keep-alive)하는 것이 성능에 중요하다.

원리 여기서 OS가 하나 끼어든다. 호스트의 443번 포트로 들어온 패킷은 어떻게 proxy 컨테이너의 443으로 갈까? Docker는 호스트 커널의 패킷 필터(iptables)에 목적지 주소를 바꾸는 규칙(DNAT) 을 넣는다. 호스트 443으로 온 패킷의 목적지를 proxy 컨테이너의 내부 IP:443으로 바꿔 보내는 것이다. Compose의 ports: "443:443" 한 줄이 커널 수준에서는 이 규칙이 된다.

④ TLS: 암호화된 통로 만들기

TCP 연결 위에서 TLS 핸드셰이크가 일어난다. 목적은 세 가지다. 내가 말하는 상대가 진짜 pawcycle.duckdns.org인지 확인하고(인증), 엿들을 수 없게 하고(기밀성), 중간에 바꿀 수 없게 한다(무결성).

  • 클라이언트가 지원하는 방식과 SNI(접속하려는 도메인 이름)를 보낸다.
  • 서버가 인증서를 보낸다. 브라우저는 “사이트 인증서 → 중간 인증서 → 브라우저가 이미 믿는 루트 인증서”로 서명 사슬을 따라가 검증한다.
  • 양쪽이 키 합의를 해서, 이후 데이터를 암호화할 대칭키를 만든다. 공개키 암호는 느리므로 키를 정할 때만 쓰고, 실제 데이터는 빠른 대칭키로 암호화한다.

Dale Seo의 「HTTPS란 무엇인가」가 TLS가 HTTP 아래에서 기밀성·무결성·인증을 제공하는 구조와 인증서 신뢰 사슬을 설명한다. 이 개념이 Nginx 설정에 그대로 나타난다.

# infra/production/nginx.https.conf (발췌)
server {                                   # (가) 모르는 이름으로 온 HTTPS
    listen 443 ssl default_server;
    server_name _;
    ssl_certificate ...;
    ssl_reject_handshake on;
}
server {                                   # (나) 진짜 도메인
    listen 443 ssl;
    server_name __PAWCYCLE_DOMAIN__;
    ssl_certificate     /etc/letsencrypt/live/pawcycle.duckdns.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/pawcycle.duckdns.org/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;
    ...
}
server {                                   # (다) 모르는 이름으로 온 HTTP
    listen 80 default_server;
    server_name _;
    return 444;
}
  • (나)의 fullchain.pem: 사이트 인증서와 중간 인증서를 함께 담은 파일이다. 중간 인증서를 빠뜨리면 사슬이 끊겨 일부 클라이언트에서 검증이 실패한다.
  • ssl_protocols TLSv1.2 TLSv1.3: 취약한 옛 버전(TLS 1.0·1.1)을 받지 않는다.
  • ssl_session_cache + ssl_session_timeout 1d: 한 번 핸드셰이크한 클라이언트가 다시 오면 키 합의를 생략하고 세션을 재개한다. 위 그림 ④의 비용을 줄인다.
  • (가) ssl_reject_handshake on: SNI가 우리 도메인이 아니면 핸드셰이크 자체를 거절한다. 해석 인터넷에는 IP 대역을 훑으며 아무 서버에나 접속해 보는 스캐너가 많다. 이들에게 인증서조차 보여 주지 않아, 이 IP에 어떤 도메인이 있는지 노출하지 않는다.
  • (다) return 444: Nginx 고유 코드로, 응답 없이 연결을 끊는다. 모르는 Host로 온 HTTP 요청에 아무 정보도 주지 않는다.

⑤⑥ 리버스 프록시: Nginx가 요청을 대신 전달한다

TLS를 푼 Nginx는 요청을 다시 Spring에 보낸다. 클라이언트 대신 서버를 대리하는 이런 서버를 리버스 프록시라 한다. Dale Seo의 「프록시 서버와 리버스 프록시」가 구분 기준을 정리한다. 포워드 프록시는 클라이언트 편에서 접근 제어·익명성을 맡고, 리버스 프록시는 서버 편에서 로드 밸런싱·TLS 종료·보안 경계를 맡는다.

문제는 Spring 입장에서 모든 요청이 Nginx에서 온 것처럼 보인다는 점이다. 접속자의 IP도, 원래 HTTPS였다는 사실도 사라진다. 그래서 Nginx가 헤더로 원래 정보를 실어 보낸다.

location /api/ {
    proxy_pass http://pawcycle_application_backend;
    proxy_http_version 1.1;
    proxy_set_header Host              $http_host;                  # 원래 요청한 호스트
    proxy_set_header X-Real-IP         $remote_addr;                # Nginx가 본 접속자 IP
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;  # 지나온 IP 목록
    proxy_set_header X-Forwarded-Proto https;                       # 원래는 HTTPS였다
    proxy_read_timeout 60s;
}

Spring은 이 헤더를 믿도록 설정돼 있다.

# compose.yaml의 backend 환경 변수
SERVER_FORWARD_HEADERS_STRATEGY: framework
SESSION_COOKIE_SECURE: "true"
  • 원리 framework 전략이면 Spring이 X-Forwarded-* 헤더를 읽어 요청의 스킴·호스트·접속자 주소를 원래 값으로 바꿔 끼운다. 그래야 Spring이 “이 요청은 HTTPS로 들어왔다”고 판단하고, 리다이렉트 주소를 https://로 만들 수 있다.
  • 세션 쿠키 Secure: 브라우저가 이 쿠키를 HTTPS로만 보내게 한다. Nginx와 Spring 사이가 평문이어도 상관없다. Secure는 브라우저가 언제 쿠키를 보내는가에 대한 속성이기 때문이다.

트레이드오프: 클라이언트가 보낸 헤더를 믿어도 되는가? X-Forwarded-For는 클라이언트가 위조할 수 있는 헤더다. $proxy_add_x_forwarded_for는 클라이언트가 보낸 값 뒤에 Nginx가 본 IP를 덧붙인다. 그래서 목록의 맨 앞 값은 믿을 수 없고, Nginx가 붙인 맨 뒤 값만 믿을 수 있다. Dale Seo의 글도 이 헤더는 위조될 수 있으니 신뢰하는 프록시가 붙인 값만 믿어야 한다고 경고한다. - 해석 이 프로젝트에서 헤더를 믿는 것이 안전한 근거는 2절의 네트워크 설계다. backend는 app 내부 네트워크에만 공개돼 있어서, 헤더를 조작해 backend에 직접 접속할 길이 없다. 모든 요청이 Nginx를 거친다는 전제 위에서만 이 설정이 성립한다. - 개선 후보: 미확인 Spring이 X-Forwarded-For의 어느 값을 접속자 IP로 쓰는지, 그리고 그 값을 로그나 보안 판단에 쓰는 코드가 있는지는 확인하지 않았다. 맨 앞 값을 쓴다면 로그의 IP가 위조될 수 있다. 신뢰할 수 있는 X-Real-IP를 쓰거나, Spring에 신뢰할 프록시를 명시하는 방법이 있다.

Docker 안의 DNS: 컨테이너 이름이 주소가 되는 원리

proxy_pass http://backend:8080의 backend는 도메인이 아니라 Compose 서비스 이름이다. 이것이 IP로 바뀌는 원리가 Nginx 설정 맨 위에 있다.

# Re-resolve service addresses after application container replacement.
resolver 127.0.0.11 valid=5s ipv6=off;

upstream pawcycle_application_backend {
    zone pawcycle_application_backend 64k;
    server backend:8080 resolve;
}
  • 원리 Docker는 사용자 정의 네트워크에 붙은 컨테이너에게 127.0.0.11에서 동작하는 내장 DNS 서버를 제공한다. 이 서버가 같은 네트워크의 서비스 이름을 컨테이너 IP로 바꿔 준다. 그래서 IP를 하드코딩하지 않고 이름으로 부를 수 있다.
  • 왜 valid=5s와 resolve인가. 원리 Nginx는 기본적으로 시작할 때 한 번 이름을 IP로 바꾸고 그 값을 계속 쓴다. 그런데 새 버전을 배포하며 backend 컨테이너를 다시 만들면 IP가 바뀐다. Nginx가 옛 IP를 붙들고 있으면 모든 요청이 실패하고, Nginx를 재시작해야만 복구된다. 위 설정은 upstream 이름을 5초마다 다시 해석하게 해서 이 문제를 없앤다. 주석이 정확히 그 이유를 적고 있다(“컨테이너 교체 후 서비스 주소를 다시 해석한다”).
  • 해석 이 설정 덕분에 backend만 새로 배포할 때 proxy를 건드리지 않아도 된다. 뒤의 8절에서 볼 “바뀐 서비스만 배포한다”는 배포 정책이 성립하는 전제다.

4. Nginx가 맡은 보안: 헤더와 로그인 속도 제한

보안 헤더

add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header X-XSS-Protection "0" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

proxy_hide_header Strict-Transport-Security;   # 뒤쪽 앱이 보낸 같은 헤더는 지운다
proxy_hide_header X-Frame-Options;
...
  • HSTS: “앞으로 1년 동안 이 도메인은 HTTPS로만 접속하라”고 브라우저에 기억시킨다. 사용자가 http://를 쳐도 브라우저가 알아서 HTTPS로 바꿔 보내므로, 첫 HTTP 요청을 가로채는 공격을 막는다.
  • nosniff: 브라우저가 응답 내용을 보고 타입을 멋대로 추측하지 못하게 한다.
  • X-Frame-Options: DENY: 다른 사이트가 이 페이지를 iframe에 넣지 못하게 해서, 투명한 프레임을 덮어 클릭을 훔치는 공격을 막는다.
  • X-XSS-Protection: 0: 원리 일부러 끄는 설정이다. 옛 브라우저의 XSS 필터는 오히려 오동작과 정보 유출 문제가 있어 현재는 끄는 것이 권장된다.
  • proxy_hide_header: Spring Security도 일부 보안 헤더를 기본으로 붙인다. 그대로 두면 같은 헤더가 두 번 나가므로, 앱이 보낸 것을 지우고 Nginx의 값 하나만 남긴다.

로그인 속도 제한: 새는 양동이

limit_req_zone $binary_remote_addr zone=login_per_ip:10m rate=10r/m;

location = /api/auth/login {
    limit_req zone=login_per_ip burst=5 nodelay;
    limit_req_status 429;
    error_page 429 = @login_rate_limited;
    proxy_pass http://pawcycle_application_backend;
    ...
}
location @login_rate_limited {
    default_type application/json;
    return 429 '{"code":"RATE_LIMITED","message":"로그인 요청이 너무 많습니다. 잠시 후 다시 시도해 주세요.","fieldErrors":[]}';
}

원리 Nginx의 limit_req는 새는 양동이(leaky bucket) 방식이다. 양동이 바닥에 구멍이 있어 물이 일정한 속도로 빠지고, 요청이 올 때마다 물을 한 컵 붓는다고 생각하면 된다.

  • rate=10r/m: 구멍으로 6초에 한 컵씩 빠진다. 같은 IP는 평균 6초에 한 번 로그인을 시도할 수 있다.
  • burst=5: 양동이에 여분으로 5컵까지 담을 수 있다. 사람이 비밀번호를 몇 번 연달아 틀리는 정도는 허용한다.
  • nodelay: 여분 안의 요청을 줄 세워 기다리게 하지 않고 바로 처리한다. 여분까지 넘치면 즉시 429다.
  • $binary_remote_addr: IP를 문자열 대신 바이너리로 저장해 메모리를 아낀다. 10m은 이 상태를 담을 공유 메모리 크기다.
  • location = /api/auth/login: =는 정확히 이 경로만 일치시킨다. 다른 API에는 제한을 걸지 않는다.
  • @login_rate_limited: 429 응답을 백엔드의 다른 오류와 같은 JSON 형식으로 맞춘다. 프론트가 오류를 한 가지 방식으로 처리할 수 있다.

트레이드오프: 왜 IP 기준이고, 왜 Nginx인가? 기록 이 제한은 세션·CSRF 제품 계약을 바꾸지 않고 공개 로그인 하나에만 IP당 제한을 추가한 변경이다(PR #296). 당시 계정 잠금, 이메일별 제한, Redis 기반 제한, WAF, CSP, JWT 전환은 별도 범위로 남겼다. - 얻는 것: 애플리케이션 코드를 바꾸지 않고, 요청이 Spring에 닿기도 전에 막는다. 비밀번호 대입 공격의 속도를 크게 늦춘다. - 한계: 해석 여러 사용자가 같은 공인 IP를 쓰는 환경(회사, 학교, 통신사 NAT)에서는 정상 사용자끼리 한도를 나눠 쓴다. 반대로 IP를 계속 바꾸는 공격자(봇넷, IPv6 주소 대역)는 막지 못한다. 한 계정에 여러 IP에서 대입하는 공격도 IP 기준으로는 보이지 않는다. 계정 기준 제한이 함께 있어야 하는 이유다. - 기록 이 값(10r/m, burst 5)은 당시 구현 계약이며, 실제 사용량을 측정해 정한 운영 임계치가 아니라고 남겨 두었다.

5. 컨테이너는 가상 머신이 아니다: namespace와 cgroup (깊게)

지금까지 “컨테이너”를 상자처럼 말했지만, OS 입장에서 컨테이너는 특별한 옷을 입은 일반 프로세스다. 가상 머신은 하드웨어를 흉내 내고 그 위에 운영체제를 통째로 하나 더 띄운다. 컨테이너는 호스트의 커널 하나를 함께 쓰면서, 커널 기능 두 가지로 프로세스를 가둔다.

  • namespace — 무엇이 보이는가(격리): 프로세스가 볼 수 있는 세상을 좁힌다.
    • PID namespace: 컨테이너 안에서 java는 자신이 PID 1이라고 본다. 호스트에서는 그냥 수많은 프로세스 중 하나다.
    • Network namespace: 컨테이너마다 자기만의 네트워크 인터페이스·IP·라우팅 표를 가진다. 2절의 네트워크 분리가 가능한 이유다.
    • Mount namespace: 컨테이너마다 다른 파일 시스템 뷰를 가진다. 이미지의 파일이 루트(/)처럼 보인다.
    • 이 밖에 호스트 이름(UTS), 프로세스 간 통신(IPC), 사용자 ID(User) namespace가 있다.
  • cgroup — 얼마나 쓸 수 있는가(제한): 프로세스 묶음이 쓸 수 있는 CPU·메모리·프로세스 수를 커널이 세고 제한한다.

이 두 기능이 PawCycle의 Compose 설정에 어떻게 대응하는지 그리면 다음과 같다.

컨테이너 안의 java는 자신이 PID 1이고 서버를 혼자 쓴다고 본다. 실제로는 커널이 namespace로 보이는 범위를 좁히고, cgroup으로 쓸 수 있는 양을 세고 있을 뿐이다. 이 관점으로 backend 컨테이너 설정을 한 줄씩 읽어 보자.

# infra/production/compose.yaml — backend 서비스의 격리·제한 설정 (요지)
backend:
  read_only: true            # 루트 파일 시스템 읽기 전용
  tmpfs:
    - /tmp                   # 쓰기가 필요한 곳만 메모리 파일 시스템으로
  security_opt:
    - no-new-privileges:true # 실행 중 권한 상승 금지
  mem_limit: 640m            # cgroup memory.max
  cpus: 0.75                 # cgroup cpu.max (CFS quota)
  pids_limit: 256            # cgroup pids.max
  • read_only: true: 컨테이너의 파일 시스템 전체를 읽기 전용으로 마운트한다. 해석 공격자가 애플리케이션 취약점으로 코드를 실행하게 되더라도 실행 파일을 내려받아 심거나 설정을 고쳐 쓰기 어렵다. 실행 중 디스크가 이미지와 달라지지 않으니 “어제와 오늘 같은 이미지인데 동작이 다르다”는 문제도 줄어든다.
  • tmpfs: /tmp: 그래도 쓰기가 꼭 필요한 곳이 있다. Spring Boot의 내장 Tomcat은 작업 디렉터리와 업로드 임시 파일을 /tmp 아래에 만든다. 그래서 /tmp만 메모리 위의 파일 시스템으로 열어 준다.
    • 원리 tmpfs에 쓴 데이터는 RAM에 있으므로 컨테이너의 메모리 사용량으로 계산된다. 큰 파일을 /tmp에 쓰면 디스크가 아니라 640MB 한도를 깎아 먹는다. 앞 절의 client_max_body_size 1m이 요청 본문 크기를 막아 주기 때문에 이 조합이 안전하다.
  • no-new-privileges: 원리 리눅스 커널의 PR_SET_NO_NEW_PRIVS 플래그다. 이 플래그가 켜진 프로세스와 자식 프로세스는 setuid 프로그램(예: sudo)을 실행해도 권한이 올라가지 않는다. 아래의 non-root 사용자와 함께 쓰면 컨테이너 안에서 root가 될 길이 거의 막힌다.
  • pids_limit: 256: 컨테이너가 만들 수 있는 프로세스 수 상한이다. 원래 목적은 fork를 무한히 반복하는 fork bomb이 호스트 전체를 마비시키지 못하게 하는 것이다.
    • 원리 리눅스 커널에게 스레드도 태스크 하나다. pids.max는 프로세스가 아니라 태스크 수를 센다. 그러니 이 숫자는 사실상 JVM 스레드 수 상한이다.
    • 해석 Tomcat의 기본 최대 작업 스레드는 200개다. 여기에 커넥션 풀, GC, JIT 컴파일러, 스케줄러 스레드가 더해진다. 부하가 몰려 Tomcat이 스레드를 끝까지 늘리면 256에 꽤 가까워진다. 이 한도에 닿으면 새 스레드를 만들지 못해 OutOfMemoryError: unable to create native thread가 난다. 이름은 메모리 오류지만 실제 원인은 pids 한도다.
    • 미확인 가상 스레드 사용 여부와 Tomcat 스레드 수 설정은 아직 확인하지 않았다. 9강(Spring 실행 구조)에서 함께 본다.
  • cpus: 0.75: 원리 CFS 스케줄러의 quota로 구현된다. 기본 100ms 주기마다 이 컨테이너는 75ms만큼만 CPU를 쓸 수 있다. 다 쓰면 남은 25ms 동안 멈춘다(throttling). 평균 CPU 사용률이 낮아 보여도, 요청이 몰리는 짧은 순간에 응답 지연이 튀는 원인이 된다.

cpus: 0.75는 JVM의 판단에도 영향을 준다. 컨테이너를 인식하는 JVM은 CPU quota를 읽어 availableProcessors()를 1로 계산한다(0.75를 올림).

  • 원리 HotSpot JVM은 CPU가 2개 이상이고 메모리가 약 1792MB 이상일 때만 “서버급 머신”으로 보고 G1 GC를 고른다. 그 조건에 못 미치면 Serial GC를 기본으로 고른다.
  • 해석 JAVA_TOOL_OPTIONS에 GC를 지정하는 옵션이 없으므로, 이 backend는 Serial GC로 돌고 있을 가능성이 높다. Serial GC는 스레드 하나로 애플리케이션을 멈추고 수거한다. 힙이 400MB 남짓이면 감당할 만하지만, 멈춤 시간이 응답 시간에 그대로 더해진다.
  • 미확인 실제 GC 종류는 운영 서버의 -Xlog:gc 출력이나 jcmd VM.flags로 확인해야 한다. 실험은 프로젝트 이해를 마친 뒤 하기로 했으니 여기서는 질문으로 남긴다.

이미지 쪽에도 같은 원칙이 있다.

# infra/production/backend.Dockerfile (요지)
FROM eclipse-temurin:25-jdk AS build      # 1단계: 빌드 도구가 있는 JDK
WORKDIR /workspace
COPY . .
RUN ./gradlew bootJar

FROM eclipse-temurin:25-jre               # 2단계: 실행만 하는 JRE
RUN useradd --system --shell /usr/sbin/nologin pawcycle
COPY --from=build /workspace/build/libs/*.jar /app/app.jar
USER pawcycle
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
  • 멀티 스테이지 빌드: 1단계 이미지에는 JDK·Gradle·소스 코드가 있지만, 최종 이미지에는 JRE와 jar 하나만 남는다. 이미지가 작아지고, 공격자가 쓸 수 있는 컴파일러나 빌드 도구가 운영 컨테이너에 없다.
  • USER pawcycle + nologin: 컨테이너는 기본으로 root로 실행된다. 원리 User namespace를 따로 켜지 않으면 컨테이너 안의 root는 호스트 커널 입장에서도 UID 0이다. 컨테이너 탈출 취약점이 생기면 피해 범위가 크게 달라진다. 그래서 로그인 셸이 없는 시스템 사용자로 낮춰 실행한다. frontend도 USER node로 같은 원칙을 따른다.

6. JVM과 컨테이너 메모리: 640MB는 어떻게 나뉘는가 (깊게)

mem_limit: 640m은 컨테이너 전체의 한도다. JVM 프로세스가 쓰는 메모리는 힙만이 아니다.

  • 힙(Heap): new로 만든 객체가 사는 곳. GC가 관리한다.
  • 메타스페이스(Metaspace): 로드된 클래스의 정보. Spring Boot는 클래스를 수만 개 로드하므로 생각보다 크다.
  • 스레드 스택: 스레드마다 기본 약 1MB까지 예약된다. 실제로 쓴 만큼만 물리 메모리를 차지한다.
  • 코드 캐시: JIT 컴파일러가 만든 기계어.
  • Direct buffer, GC 자료구조, 네이티브 라이브러리: 네트워크 I/O 버퍼나 GC가 쓰는 표.
  • tmpfs의 /tmp: 앞에서 본 것처럼 이것도 같은 한도에 포함된다.

-XX:MaxRAMPercentage=65.0은 최대 힙을 컨테이너 한도의 65%로 정한다. Braindetox의 「JVM 컨테이너 리소스 제한」 글이 이 구조를 설명한다. JVM이 cgroup의 메모리 한도를 읽어 힙 크기를 정하고, 비율을 너무 높게 잡으면 힙 밖의 메모리 때문에 컨테이너가 강제 종료될 수 있다는 내용이다. PawCycle의 숫자를 넣어 보면 다음과 같다.

그림 아래쪽의 두 상자는 서로 다른 두 종류의 죽음이다. 운영 중 장애를 볼 때 이 둘을 구분하는 것이 핵심이다.

  • 왼쪽: 힙 OOM. JVM이 객체를 둘 자리를 못 찾아 OutOfMemoryError를 던진다.
    • 이 오류는 아무 스레드에서나 터질 수 있다. 어떤 스레드는 죽고 어떤 스레드는 살아남아, 서버가 반쯤 고장 난 채로 계속 요청을 받는 상태가 생길 수 있다.
    • -XX:+ExitOnOutOfMemoryError는 OOM이 한 번이라도 나면 JVM을 즉시 끝낸다. 어중간하게 살아 있는 서버보다 깨끗하게 죽은 서버가 낫다는 판단이다. 죽은 컨테이너는 healthcheck와 재시작 정책으로 처리하는 편이 예측 가능하다.
    • 미확인 compose 파일에서 restart 정책을 다시 확인해야 한다. 정책이 없으면 “깨끗하게 죽은” 서버는 사람이 다시 띄울 때까지 그대로 멈춰 있다.
  • 오른쪽: 컨테이너 OOM. 힙은 여유가 있는데 힙 밖 메모리까지 합쳐 640MB를 넘은 경우다.
    • 원리 이때는 JVM이 아니라 커널의 OOM killer가 나선다. 프로세스에 SIGKILL(9번 신호)을 보내 즉시 죽인다. JVM은 로그 한 줄 남길 기회도 없다.
    • 종료 코드는 137 = 128 + 9다. docker inspect에서 OOMKilled: true와 137을 보면 Java 로그가 아니라 메모리 설정을 의심해야 한다.
  • 왜 65%인가. 해석 비율을 80%로 올리면 힙 밖에 남는 몫이 약 128MB로 줄어든다. Spring Boot 애플리케이션의 메타스페이스와 스레드 스택만으로도 그 정도를 쓰기 쉬워, 힙이 넉넉해 보이는데 커널이 죽이는 상황이 생긴다. 반대로 50%로 낮추면 컨테이너 OOM은 멀어지지만 GC가 더 자주 돌고 힙 OOM이 가까워진다. 65%는 그 사이의 절충이다.
    • 미확인 이 숫자가 운영 부하에서 실제로 측정해 정한 값인지는 확인하지 못했다. 힙 밖 메모리를 실제로 재려면 -XX:NativeMemoryTracking=summary가 필요하다. 이 측정은 뒤의 실험 단계 후보로 둔다.

7. 인증서는 누가, 어떻게 갱신하는가: ACME HTTP-01

HTTPS를 쓰려면 인증서가 있어야 하고, Let's Encrypt 인증서는 90일마다 만료된다. 사람이 손으로 갱신하면 언젠가 반드시 잊는다. 그래서 ACME라는 자동화 프로토콜을 쓴다. 핵심 질문은 하나다. “인증서를 요청한 사람이 정말 이 도메인의 주인인가?” HTTP-01 방식은 이것을 이렇게 증명한다.

그림의 각 단계는 앞에서 본 설정과 그대로 연결된다.

  • ③④가 80번 포트를 남겨 둔 이유다. 3절의 HTTP server 블록은 도메인으로 온 요청을 모두 HTTPS로 301 리다이렉트하지만, /.well-known/acme-challenge/만은 예외로 /var/www/certbot에서 파일을 직접 내준다. 인증서가 만료돼 HTTPS가 깨진 상황에서도 갱신이 가능하도록 평문 HTTP로 증명할 길을 남겨 둔 것이다.
  • 볼륨 공유와 읽기 전용. certbot 컨테이너는 webroot에 토큰을 쓰고, nginx는 같은 볼륨을 :ro로 읽기만 한다. 발급된 인증서가 들어 있는 letsencrypt 볼륨도 nginx에는 읽기 전용이다. 해석 nginx가 털려도 개인 키를 바꿔치기할 수 없다.
  • 타이머 03:00 · 15:00, Persistent=true. certbot은 만료가 30일 이내로 남았을 때만 실제로 갱신하므로, 하루 두 번 실행해도 대부분은 “아직 갱신할 필요 없음”으로 끝난다. 하루 두 번 시도하는 것은 Let's Encrypt가 권장하는 방식이다. 원리 Persistent=true는 서버가 꺼져 있던 동안 놓친 실행을 부팅 직후 한 번 따라잡게 한다. 일반 cron에는 이 기능이 없다.
  • reload-pending 상태 파일. 확인 갱신 스크립트는 실제로 인증서가 바뀌었고 검증이 통과한 경우에만 nginx를 reload한다. reload가 실패하면 그 사실을 상태 파일에 남겨, 다음 실행 때 reload를 다시 시도한다.
    • 원리 nginx는 인증서 파일을 시작하거나 reload할 때 한 번 읽어 메모리에 들고 있다. 디스크의 파일만 바뀌고 reload가 빠지면, 갱신은 “성공”했는데 nginx는 30일 뒤 만료될 옛 인증서를 계속 내보낸다. 이 실패는 만료일까지 아무도 모른다. 상태 파일은 이 조용한 실패를 막는 장치다.
    • reload는 restart와 다르다. nginx는 새 설정으로 새 worker를 띄우고, 옛 worker는 처리 중인 연결을 마친 뒤 종료한다. 그래서 인증서를 바꿀 때 연결이 끊기지 않는다.
  • certbot 이미지를 digest로 고정. 태그(latest)는 같은 이름으로 내용이 바뀔 수 있지만, @sha256:... digest는 내용이 1비트만 달라도 값이 바뀐다. 인증서 개인 키를 다루는 도구가 어느 날 몰래 바뀌는 일을 막는다. proxy의 nginx 이미지도 같은 방식으로 고정돼 있다.

트레이드오프: 왜 DNS-01이 아니라 HTTP-01인가? 해석 DNS-01은 도메인의 DNS에 TXT 레코드를 써서 증명한다. 80번 포트를 열지 않아도 되고 와일드카드 인증서(*.example.com)도 받을 수 있다. 대신 DNS 제공자의 API 토큰을 서버에 두어야 하고, 그 토큰이 새면 도메인 전체를 빼앗길 수 있다. 이 서비스는 도메인이 하나이고 80번은 리다이렉트용으로 어차피 열려 있다. 그러니 비밀 정보를 하나 덜 두는 HTTP-01이 더 단순하고 안전하다.

8. 배포와 운영: 무엇을 했고, 무엇을 일부러 미뤘나

마지막으로 이 구조가 어떻게 배포되고, 어떤 위험을 받아들였는지 본다. 포트폴리오 면접에서 가장 많이 묻는 부분이다. “왜 이렇게 했나요?”보다 “이 구조의 약점이 뭔가요?” 를 더 자주 묻는다.

backend:
  image: ghcr.io/.../pawcycle-backend:${BACKEND_RELEASE_SHA:-${RELEASE_SHA}}
  • 이미지를 커밋 SHA로 부른다. 확인 이미지 태그가 latest가 아니라 커밋 SHA다. 어떤 코드가 운영에 떠 있는지 정확히 알 수 있다. 롤백은 “이전 SHA로 태그를 바꾸고 다시 올리기”가 된다.
  • ${BACKEND_RELEASE_SHA:-${RELEASE_SHA}}. 셸의 기본값 문법이다. backend 전용 SHA가 있으면 그것을, 없으면 공통 SHA를 쓴다. 해석 frontend는 그대로 두고 backend만 새 버전으로 바꾸는 배포가 가능하다. 3절에서 본 Nginx의 resolve 재해석이 이 배포의 전제다. 배포 쪽에서는 호스트가 바뀐 서비스만 반영하고, 위험한 변경(스키마 마이그레이션 등)은 별도로 확인받는 방향으로 다듬어졌다(PR #474, #486, #490).
  • 서버 한 대, 수동 배포. 기록 운영 대상은 OCI의 app01 한 대(1 OCPU / 6GB)다. 자동 배포(CD)와 무중단 배포는 의도적으로 미뤘다(DEFER). 무료 등급 안에서 운영하려는 선택이었고, 다른 클라우드 대안을 비교한 결과다(이슈 #276).
  • DB는 컴포즈 밖에. MySQL은 관리형 서비스로 분리돼 있고, backend만 database-egress 네트워크로 나간다. 해석 서버 한 대가 통째로 날아가도 데이터는 남는다. 컨테이너는 이미지와 설정으로 다시 만들 수 있지만 데이터는 다시 만들 수 없다. “상태가 있는 것과 없는 것을 분리한다”는 원칙이 서버 한 대 구조에서도 지켜진다.
  • 관측 도구도 같은 서버에. 메트릭·로그 수집을 같은 호스트에 두었고, 앞에서 본 app 내부 네트워크는 그 과정에서도 느슨하게 풀지 않았다(PR #287, #293).

이 선택들이 받아들인 위험을 정리하면 다음과 같다.

받아들인 위험 구체적으로 무슨 일이 생기나 미룬 대안과 그 비용
단일 장애 지점 호스트가 죽으면 proxy·frontend·backend가 함께 멈춘다 서버 2대 + 로드 밸런서: 비용과 세션 공유 문제(세션이 서버 메모리에 있다)
배포 중 짧은 중단 backend 컨테이너를 교체하는 동안 /api 요청이 실패한다 블루-그린 배포: 같은 서버에 두 벌을 띄울 메모리가 6GB에 빠듯하다
같은 곳에 있는 감시자 호스트가 죽으면 모니터링도 같이 죽어 장애 알림이 오지 않는다 외부 업타임 체크: 비용은 거의 없지만 아직 없다
사람이 하는 배포 절차를 빠뜨릴 수 있다 CD 파이프라인: 운영 서버에 접근할 비밀을 CI에 맡겨야 한다

개선 우선순위 제안 해석 비용 대비 효과로 보면 첫 번째는 외부 업타임 체크다. 돈이 거의 들지 않고, “같은 곳에 있는 감시자” 문제를 바로 해결한다. 세션 저장소를 Redis로 옮기는 것은 서버 2대로 가는 데 필요한 전제지만, 지금 트래픽 규모에서는 이르다. 세션 구조는 Security 파트에서 자세히 본다.

마지막으로, 문서끼리 맞지 않는 부분이 하나 있다.

  • 확인 운영 개요 문서는 운영 대상을 OCI app01로 적고, 2026-10-25에 읽기 전용으로 점검한 결과(컨테이너 healthy, 주요 GET 200, 인증서 갱신 타이머 동작)를 남겼다. 동시에 “Production Verified”는 아니라고 분명히 적어 두었다.
  • 확인 그런데 README에는 운영 대상이 “없음”으로 남아 있다. 어느 한쪽이 갱신되지 않은 문서 드리프트다.
  • 포트폴리오로 정리할 때는 이 차이를 정확히 말할 수 있어야 한다. “운영 중입니다”가 아니라 “단일 서버에 배포해 읽기 전용 점검까지 했고, 운영 검증 단계는 아니다” 가 사실에 맞는 표현이다.

2강 정리

  • C4 System Context·Container 수준에서 PawCycle은 브라우저 → Nginx(proxy) → Next.js(frontend) / Spring(backend) → 관리형 MySQL 구조다. Toss와 OpenAI는 기본 설정에서 꺼져 있다.
  • 네트워크 경계: 외부로 공개된 것은 proxy의 80/443뿐이다. app 네트워크는 internal: true라 backend는 인터넷에서 직접 닿을 수 없다. 이 경계 덕분에 X-Forwarded-* 헤더를 믿을 수 있다.
  • 요청 한 번의 여정은 DNS → TCP 3-way → TLS(SNI·인증서 사슬·대칭키) → Nginx에서 TLS 종료 → Docker 내장 DNS(127.0.0.11) → backend 순이다.
  • Nginx 보안은 모르는 이름 거절(444, ssl_reject_handshake), 보안 헤더, 로그인 IP당 속도 제한(leaky bucket)이다.
  • 컨테이너 = namespace(보이는 것) + cgroup(쓸 수 있는 양): read_only, tmpfs, no-new-privileges, non-root, pids_limit(= 스레드 상한), cpus(= throttling, JVM의 CPU 수 판단과 GC 선택)다.
  • 640MB = 힙 65% + 힙 밖 35%: 힙 OOM과 컨테이너 OOM(exit 137)은 원인과 대응이 다르다.
  • 운영: SHA 이미지, 서비스별 배포, ACME HTTP-01 자동 갱신(reload-pending으로 조용한 실패 방지), 그리고 의도적으로 받아들인 단일 서버 위험.

  • 실제 GC 종류
  • Tomcat 스레드 수와 가상 스레드 사용 여부
  • restart 정책
  • Spring이 접속자 IP로 쓰는 X-Forwarded-For 값
  • 힙 밖 메모리 실측

3강. 비기능 요구와 위험 지도: 이 시스템은 무엇을 두려워하는가

이번 강의의 목표

  • 기능 요구(“무엇을 하는가”)와 비기능 요구(“얼마나 잘, 얼마나 안전하게 하는가”)를 구분한다.
  • PawCycle의 다섯 가지 비기능 축이 어떤 실제 사건과 측정에서 나왔고, 어떤 기술 선택으로 이어졌는지 연결한다.
  • 네트워크·OS 쪽에서는 두 가지를 깊게 본다.
    • “정확히 한 번”이 왜 불가능하고 멱등성이 왜 그 대안인가
    • TIME_WAIT와 임시 포트 고갈은 왜 생기는가
  • 마지막에 위험 지도를 만든다. 남은 강의에서 무엇을 깊게 볼지 정하는 기준이 된다.

1. 비기능 요구란 무엇이고, 이 프로젝트에서는 무엇인가

“주문을 생성한다”, “구독을 변경한다”는 기능 요구다. 그런데 같은 기능이라도 다음 질문에 어떻게 답하느냐에 따라 코드가 완전히 달라진다.

  • 버튼을 두 번 누르면 주문이 두 개 생기는가?
  • 결제사 응답이 안 오면 돈은 빠져나갔는가?
  • 서버가 죽으면 누가 언제 알게 되는가?

이런 “얼마나 잘”에 대한 요구를 비기능 요구(품질 속성)라 한다. 문제는 비기능 요구가 요구사항 문서에 잘 적히지 않는다는 점이다. 보통은 사고가 나고 나서야 드러난다.

PawCycle도 그랬다. README는 이 프로젝트를 “기술을 먼저 늘리기보다 현재 구조에서 문제를 재현·측정하고, 필요가 확인될 때 다음 기술을 선택한다”고 소개한다. 그래서 이 프로젝트의 비기능 요구는 문서의 선언보다 사건과 측정 기록에서 더 정확히 읽힌다. 아래 다섯 축이 그 결과다.

다섯 축 중 첫 번째가 가장 무겁다. 이커머스에서 돈과 재고가 틀리는 것은 느린 것보다 훨씬 나쁘다. 느리면 사용자가 기다리지만, 두 번 결제되면 환불과 신뢰 문제가 생긴다.

2. 정합성·멱등성: “정확히 한 번”은 왜 불가능한가 (깊게)

네트워크는 “응답이 안 왔다”와 “처리가 안 됐다”를 구분해 주지 않는다

사용자가 “결제하기”를 눌렀는데 응답이 오지 않았다고 하자. 가능한 경우는 셋이다.

  1. 요청이 서버에 도착하지 못했다. 아무 일도 일어나지 않았다.
  2. 서버가 처리하는 중에 죽었다. 일부만 일어났을 수 있다.
  3. 서버는 처리를 끝냈는데 응답이 돌아오다 사라졌다. 결제는 이미 됐다.

원리 클라이언트 쪽에서는 이 셋이 똑같이 “타임아웃”으로 보인다. 분산 시스템에서 유명한 두 장군 문제(Two Generals' Problem)가 이것이다. 메시지가 사라질 수 있는 통신로에서는, 상대가 받았다는 확인조차 사라질 수 있다. 그래서 양쪽이 “확실히 합의했다”고 확신할 방법이 없다. 결과적으로 클라이언트가 고를 수 있는 전략은 둘뿐이다.

  • 재시도하지 않는다 → 최대 한 번(at-most-once): 3번 경우가 아니었다면 결제가 누락된다.
  • 재시도한다 → 최소 한 번(at-least-once): 3번 경우였다면 결제가 두 번 된다.

“정확히 한 번 전달(exactly-once delivery)”은 네트워크 수준에서 보장할 수 없다. 대신 실무에서는 “최소 한 번 전달 + 받는 쪽의 중복 제거” 로 “정확히 한 번의 효과(effect)” 를 만든다. 그 중복 제거 장치가 멱등성이다.

토스페이먼츠의 「멱등성이 뭔가요?」가 이 흐름을 결제 취소 예제로 설명한다.

  • 결제 API가 멱등하지 않으면 타임아웃 후 실제 결제 여부를 사람이 확인해야 한다.
  • 멱등하면 같은 요청을 다시 보내 못 받은 결과만 다시 받을 수 있다.
  • 서버는 Idempotency-Key 헤더의 키로 요청 기록을 저장하고, 같은 키가 다시 오면 처리하지 않고 저장된 응답을 돌려준다.
  • 같은 키에 다른 본문이 오면 422, 앞 요청이 아직 처리 중이면 409로 거절하라는 IETF 초안의 권고도 소개한다.

글의 결제 취소 흐름 그림은 원문에서 보면 된다. 토스페이먼츠가 콘텐츠의 무단 전재를 금하고 있어, 여기서는 직접 싣지 않고 같은 구조를 도식으로 다시 그린다.

그림에서 가장 중요한 칸은 가운데 초록 상자다. 업무 처리와 결과 저장이 한 트랜잭션이어야 한다.

  • 처리만 커밋되고 저장이 빠지면, 재시도가 왔을 때 기록이 없으니 다시 처리한다. 이중 결제다.
  • 저장만 되고 처리가 빠지면, 결과가 거짓이 된다.

PawCycle에서 이 원리가 어디에 쓰였는지 보자.

  • 확인 체크아웃, 구독 명령 등에 멱등 결과 테이블이 4개 있다.
    • 키만 보지 않고 요청 내용의 지문(fingerprint)을 함께 저장한다. 같은 키로 다른 내용을 보내는 요청을 구분하기 위해서다. 토스페이먼츠 글의 422 상황과 같은 문제를 푸는 장치다.
    • 미확인 지문이 다를 때 돌려주는 HTTP 상태 코드는 17강에서 코드로 확인한다.
  • 기록 멱등 기록도 영원히 둘 수는 없다. 성공 결과를 다시 보낼 수 있게 유지하면서 데이터가 무한히 늘지 않도록 완료 시각 기준 30일 보관 + 한 번에 정해진 양만 지우는 정리(bounded cleanup) 를 넣었다. 정리 작업과 replay가 경쟁하는 경우도 검증했다(PR #108). 토스페이먼츠 글이 말한 “멱등키의 유효 기간”과 같은 개념이다.
  • 기록 멱등성 장치 자체가 사고를 냈다. 체크아웃은 처음에 멱등 행을 SELECT ... FOR UPDATE로 잠갔다. 그런데 아직 없는 행을 잠그면 InnoDB는 그 자리의 간격(gap) 을 잠근다. 서로 다른 회원의 INSERT가 같은 간격에 걸려 교착 상태(deadlock)가 났고, 그 잠금은 제거됐다(PR #332). 간격 잠금의 원리는 17강에서 깊게 본다.
  • 기록 외부 결제는 멱등 테이블만으로 해결되지 않는다. 결제사 승인은 우리 DB 트랜잭션 밖에서 일어난다. 그래서 위 그림의 초록 상자처럼 “한 트랜잭션”으로 묶을 수 없다.
    • PawCycle은 결제를 PROCESSING으로 먼저 기록하고, 토스를 호출한 뒤, 결과를 반영한다. 응답을 알 수 없으면 UNKNOWN으로 남긴다.
    • 그 사이에 서버가 죽으면 PROCESSING에 고립된 결제가 남을 수 있다(이슈 #417). 결제사에 상태를 조회만 하는 1단계는 들어갔고(PR #450), 자동으로 바로잡는 2단계는 아직이다. 18·19강의 핵심 주제다.
  • 기록 실패를 가두는 것도 정합성이다. 정기배송 배치가 여러 구독을 한 트랜잭션에서 처리하면, 구독 하나의 실패가 배치 전체를 롤백시킨다. 그래서 구독마다 독립 트랜잭션으로 나눠, 실패한 구독만 롤백하고 나머지는 계속 처리하게 했다(PR #106).

타이밍 부채널: 응답 본문이 같아도 정보가 샌다

기록 로그인 기능의 첫 초안은 이렇게 동작했다(PR #34).

  • 가입되지 않은 이메일 → DB에 회원이 없으니 즉시 401
  • 가입된 이메일 + 틀린 비밀번호 → BCrypt로 비밀번호를 비교한 뒤 401

두 경우 모두 응답은 똑같은 401 JSON이다. 하지만 원리 BCrypt는 일부러 느리게 만든 해시 함수다. 비밀번호 대입 공격을 늦추려고 비교 한 번에 수십~수백 ms를 쓴다. 그러니 가입된 이메일에서만 응답이 눈에 띄게 늦다. 공격자는 응답 시간만 재서 “이 이메일은 가입돼 있다”를 알아낼 수 있다. 이런 공격을 타이밍 부채널 공격이라 한다.

  • 고친 방식: 시작할 때 무작위 더미 해시를 한 번 만들어 둔다. 가입되지 않은 이메일에도 그 더미 해시로 BCrypt 비교를 정확히 한 번 수행해 두 경로의 비용을 맞췄다. 요청마다 새로 해시를 만드는 방식은 쓰지 않았다. 그렇게 하면 비용이 오히려 달라지기 때문이다.
  • 증명한 범위: 두 실패 경로의 비교 횟수, 응답, 미인증 상태 유지까지만 테스트로 확인했다(PR #38). 기록 모든 타이밍 차이가 통계적으로 사라졌다는 실측은 없다. 형식이 틀린 이메일의 검증 경로도 같은 비용이라는 주장은 아니다.
  • 이후 인증 책임은 Spring Security의 AuthenticationProvider 구조로 옮겨졌다. 11강에서 현재 코드로 다시 확인한다.

로그에 새는 개인정보

기록 정기결제 처리의 INFO 로그에 회원 ID가 그대로 찍히는 부분을 제거했다. 그리고 Java 소스의 구문 트리(AST)를 검사하는 테스트를 넣었다(PR #298). 비밀번호·토큰·세션·CSRF·결제·빌링키 같은 값을 로거 인자로 직접 넘기면 빌드가 실패한다.

  • 한계 기록: 이 검사는 직접 인자만 본다. 변수에 담았다가 넘기거나, 예외 메시지 안에 섞여 들어가는 경로(데이터 흐름, taint)는 추적하지 않는다.
  • 해석 정적 검사는 “실수로 찍는 것”을 싸게 막는 1차 방어선이다. 완전한 보장이 필요하면 로그 출력 단계에서 패턴을 가리는 마스킹 필터를 추가로 둬야 한다. 비용(성능, 오탐)과 보장 수준의 트레이드오프다.

4. 가용성·복구: “200 OK”는 무엇을 증명하는가

어디서 재느냐가 결과를 바꾼다

기록 2026-08-14, AWS 운영 환경에서 일부러 장애를 내는 훈련(drill)을 했다(이슈 #146).

  • backend 컨테이너 하나만 멈췄다.
  • Prometheus의 backend 대상은 up → down → up으로 정확히 변했다.
  • 그런데 backend가 멈춘 동안에도 /products 페이지는 HTTP 200이었다. 프론트 페이지는 backend에 실제로 묻지 않고도 200을 돌려줄 수 있기 때문이다.

교훈은 “검사가 어떤 실행 경계를 지나가는가”를 알아야 한다는 것이다. 이후 backend API, Docker 헬스 상태, 메트릭 수집 대상을 함께 읽는 진단 도구가 만들어졌다(이슈 #147).

이 교훈을 2강의 설정에 대 보면 흥미로운 점이 보인다.

  • backend 헬스체크는 /api/products로 backend 자신을 검사한다. 옳다.
  • proxy 헬스체크는 127.0.0.1:8081/products다. 이 경로는 Nginx → frontend로만 간다.
  • 해석 그래서 proxy가 healthy라는 것은 “Nginx와 frontend 경로가 산다”까지만 증명하고, backend 상태는 증명하지 않는다. depends_on: condition: service_healthy는 시작 순서만 보장할 뿐, 실행 중 backend가 죽은 것은 proxy 헬스에 반영되지 않는다. 이것이 의도된 설계인지는 29강에서 배포 검증 스크립트와 함께 확인한다.

Dale Seo의 「SLI, SLO, SLA 정리」도 같은 지점을 짚는다. 같은 “성공률”이라도 서버 로그로 재면 서버까지 도달한 요청만 세고, 로드 밸런서에서 재면 서버가 죽어 응답하지 못한 요청까지 센다. 사용자에게 가까운 곳에서 잴수록 정직한 지표가 된다.

SLO가 없다는 것의 의미

  • 확인 README는 성능 수치를 소개하면서 “Production SLO나 현재 Production 성능으로 표현하지 않는다”고 명시한다. 즉 이 서비스에는 아직 SLO(서비스 수준 목표)가 없다.
  • 원리 SLO는 “어떤 지표를, 어느 값 이상으로, 어느 기간 동안”의 세 요소로 이루어진다. 예를 들어 99.9%/30일은 한 달에 약 43분, 99%/30일은 약 7시간 12분의 장애를 허용한다. 이 숫자가 있어야 “지금 알림을 울릴 만큼 나쁜가”, “이번 배포는 위험을 감수해도 되는가”를 판단할 수 있다.
  • 해석 2강에서 본 단일 서버, 수동 배포, 무중단 배포 보류는 SLO가 없기 때문에 정당화되는 선택이기도 하다. 포트폴리오에서 “가용성 목표를 정하지 않은 상태에서 비용 0을 우선했다”고 정확히 말하는 편이, 근거 없는 “고가용성”보다 강하다.

복구: 아직 증명되지 않은 것

  • 확인 운영 개요 문서는 OCI 환경에서 다음 항목을 검증하지 않았다고 적는다. 애플리케이션 롤백, 인증서 갱신 중단 복구, DB 백업·특정 시점 복구(PITR)·복원, 전체 알림 연결, 로그인·주문 같은 업무 흐름이다.
  • AWS 시절에는 S3 논리 백업과 격리 복원을 실제로 했던 기록이 남아 있다(30강).
  • 원리 백업은 복원해 보기 전까지 백업이 아니다. 복구 목표는 보통 두 숫자로 말한다.
    • RPO(Recovery Point Objective): 얼마만큼의 데이터를 잃어도 되는가
    • RTO(Recovery Time Objective): 얼마 안에 되살려야 하는가
    • PawCycle은 둘 다 아직 정의돼 있지 않다.

사건 1: N+1, 측정하고 나서 고쳤다

기록 페이지 크기를 바꿔 가며 API 하나가 실행하는 SQL 수를 먼저 쟀다(PR #102). 그다음 batch 조회로 바꾸고 같은 조건에서 다시 쟀다(PR #103).

API 개선 전 10 / 20 / 100건 개선 후 10 / 20 / 100건
Plans 32 / 52 / 212 14 / 14 / 14
Subscriptions 51 / 91 / 411 15 / 15 / 19

개선 전 쿼리 수가 페이지 크기에 비례해 늘어난다는 것이 N+1의 지문이다. 개선 후에는 거의 상수다. 원리와 JPA의 해결 방법(fetch join, @BatchSize, DTO 조회)은 9강과 13강에서 본다.

사건 2: 커넥션 풀을 늘렸더니 더 나빠졌다

기록 로컬 부하 실험에서 HikariCP 커넥션이 10개 모두 사용 중이고 대기 요청이 117개까지 쌓였다. 직관적인 처방은 “풀을 늘리자”다.

후보 실제 처리량 버려진 요청 p95
기준(CPU 1.5, 풀 10) 약 154 RPS 10,497 약 8.0초
풀 10 → 20 약 142 RPS (악화) 11,950 약 8.0초
CPU 1.5 → 2.0, 풀 10 약 193 RPS (개선) 5,808 —

(이슈 #191, #193, #195)

  • 해석 커넥션 대기는 증상이지 원인이 아니다. CPU가 부족하면 각 요청이 커넥션을 쥐고 있는 시간이 길어지고, 그래서 대기가 쌓인다. 이 상태에서 풀을 늘리면 더 많은 요청이 동시에 CPU와 DB를 두고 경쟁해 오히려 느려진다.
  • 그래서 풀 20은 기각하고 원래대로 돌렸다. CPU 증설은 처리량을 올렸지만 대기가 여전히 남아 부분 원인으로만 판정했다.

커넥션 풀이 단순히 “부족”한 것을 넘어 완전히 멈추는 경우도 있다. 우아한형제들의 「HikariCP Dead lock에서 벗어나기 (이론편)」이 그 사례다.

  • 메시지 플랫폼에서 소비 스레드 16개가 크기 10인 풀을 나눠 썼다.
  • 메시지 하나를 저장하는 트랜잭션이 커넥션을 동시에 2개 필요로 했다.
  • 스레드들이 커넥션 1개씩을 쥔 채 두 번째 커넥션을 서로 기다리며 멈췄다.

출처: 우아한형제들 기술블로그 · HikariCP Dead lock에서 벗어나기 (이론편), 이재훈. 이미지가 자리표시자로 보이면 링크에서 원문 그림을 볼 수 있다.

  • 그림에서 각 스레드는 커넥션 하나를 이미 쥐고 있고, 풀은 비어 있다. 아무도 두 번째 커넥션을 얻지 못하니 아무도 첫 번째를 반납하지 못한다. 2강에서 본 교착 상태 조건(점유하며 대기, 순환 대기)이 DB 행이 아니라 커넥션 풀에서 성립한 것이다.
  • 글은 교착을 피하는 최소 풀 크기를 스레드 수 × (작업당 동시 필요 커넥션 수 − 1) + 1로 제시한다.
  • 해석 PawCycle과의 연결: 한 요청이 커넥션 2개를 동시에 쥐는 대표적인 경우는 바깥 트랜잭션이 열린 채 REQUIRES_NEW로 새 트랜잭션을 여는 것이다. 리뷰 요약 Slice에서 트랜잭션을 나눈 방식이 이 패턴에 해당하는지는 15강에서 코드로 확인한다.

사건 3: 포트가 바닥났다 — TIME_WAIT와 임시 포트 (깊게)

기록 로컬 부하 실험에서 초당 832건을 처리한 것처럼 보였다. 그런데 오류율이 44.7% 였다(이슈 #166, PR #167).

  • Nginx 로그에는 backend로 연결할 때 EADDRNOTAVAIL(쓸 수 있는 주소 없음)과 502가 찍혔다.
  • proxy 컨테이너의 TIME_WAIT 소켓은 26개에서 약 28,300개로 늘었다.
  • 이 502는 Spring까지 오지도 않았으니 Spring의 메트릭에는 보이지 않았다. 4절의 “어디서 재느냐” 문제가 성능에서도 그대로 나타난 것이다.
  • 목표를 초당 250건으로 맞추면 오류 0%였고, 500건에서는 오류 10.8%로 실패했다.

왜 이런 일이 생기는지 OS 수준에서 보자.

그림의 숫자가 기록과 맞아떨어지는지 확인해 보자.

  • 원리 연결 하나는 네 값으로 구분된다. 2강에서 본 (출발 IP, 출발 포트, 목적지 IP, 목적지 포트)다. Nginx → backend 연결은 출발 IP, 목적지 IP, 목적지 포트(8080)가 모두 고정이다. 달라질 수 있는 것은 출발 포트 하나뿐이다. 리눅스는 이 출발 포트를 임시 포트 범위(기본 32768–60999, 28,232개)에서 골라 쓴다. 기록에 남은 포트 범위가 바로 이 값이다.
  • 원리 TIME_WAIT는 버그가 아니라 안전장치다. TCP 연결을 먼저 닫은 쪽은 소켓을 바로 버리지 않고 일정 시간 TIME_WAIT 상태로 둔다. 이유는 두 가지다.
    • 내가 보낸 마지막 ACK가 사라졌다면 상대가 FIN을 다시 보낼 것이다. 그때 다시 답하려면 소켓이 남아 있어야 한다.
    • 네트워크를 떠돌던 옛 연결의 늦은 패킷이, 같은 네 값을 재사용한 새 연결에 섞여 들어가는 것을 막는다.
    • 리눅스는 이 시간을 60초로 고정해 두었다.
  • 해석 계산이 기록과 맞는다. 포트 28,232개를 각각 60초씩 붙잡으면, 같은 목적지로 만들 수 있는 새 연결은 초당 약 470개가 상한이다.
    • 목표 250건에서 오류가 0이고 500건에서 실패한 결과가 이 상한과 일치한다.
    • TIME_WAIT가 약 28,300개까지 쌓인 것은 포트 범위를 거의 다 쓴 상태다.
    • 처음의 “초당 832건”은 실제 처리량이 아니었다. 포트가 없어 즉시 실패한 502가 빠르게 쌓인 숫자였다. 빠른 실패는 처리량으로 세면 안 된다.
  • 해법과 트레이드오프.
    • upstream keepalive: Nginx가 backend 연결을 닫지 않고 재사용한다. 근본 해법이다. 다만 upstream 블록의 keepalive N, proxy_http_version 1.1, 빈 Connection 헤더가 함께 있어야 동작한다.
    • 커널 튜닝: 포트 범위를 넓히거나 tcp_tw_reuse를 켜는 방법도 있지만, 증상을 미루는 성격이 강하다.
    • 기록 이 개선은 측정 PR에 섞지 않고 다음 단계로 넘겼다. 측정과 개선을 한 PR에 섞으면 무엇이 효과를 냈는지 알 수 없기 때문이다.
    • 미확인 현재 운영 설정에 upstream keepalive가 들어갔는지는 28강에서 확인한다. 2강에서 본 proxy_http_version 1.1은 필요조건의 하나일 뿐이다.

2강 보충: 640MB 컨테이너의 실제 OOM 기록

2강에서 “힙 밖 메모리 실측은 미확인”이라고 했는데, AWS 시절 기록이 이 질문에 답을 준다.

  • 기록 단일 backend + RDS 구성에서 초당 200건은 정상이었다. 250건에서 실패했다. 오류율 약 6.9%, p95 약 4.2초, backend 재시작 1회였다(이슈 #166, #168).
  • 커널 로그의 cgroup OOM kill 시각과 재시작 시각을 대조해, 종료 원인을 컨테이너 OOM으로 확정했다.
  • 그 순간 힙은 274MiB / 최대 402MiB로 여유가 있었다. 힙 밖 메모리는 152MiB였고, 스레드는 217개였다.
  • 즉 2강 그림의 오른쪽 상자(커널이 죽임, exit 137) 가 실제로 일어난 것이다. 원인은 힙이 아니라 스레드 스택과 네이티브 메모리를 포함한 전체 메모리 압력이었다.
  • 기록 스레드와 네이티브 메모리가 각각 얼마를 차지했는지는 NMT 측정이 없어 가설로 남겼다. 풀과 힙을 바로 늘리지 않고, 동시 요청 수·커넥션 점유 시간·스레드 예산을 같은 조건에서 실험하는 과제로 넘겼다.
  • 스레드 217개라는 숫자를 2강의 pids_limit: 256과 나란히 놓아 보자. 메모리가 먼저 터지지 않았다면 다음은 스레드 한도였을 수 있다. 해석

6. 관측: 모르는 것을 “정상”이라고 말하지 않기

관측 축의 핵심은 정직한 판정이다. 운영 상태 알림 스크립트의 판정 규칙이 이를 잘 보여 준다.

# docs/runbook/OPS-AUTO-010 — 판정 결과별 동작 (요지)
NORMAL                   → 알림 없이 종료
BACKEND_DOWN             → Discord와 Slack에 각각 독립적으로 전송 시도
OBSERVABILITY_DEGRADED   → 〃
DEGRADED                 → 〃
UNKNOWN                  → 〃
형식이 깨졌거나 믿을 수 없는 입력 → UNKNOWN (fail-closed)
알림 전송 결과는 운영 상태 판정을 바꾸지 않음
  • OBSERVABILITY_DEGRADED가 따로 있다. “backend는 살아 있는데 감시 장치가 고장 났다”는 상태를 구분한다. 감시가 죽은 것을 “장애 없음”으로 읽으면, 4절의 /products 200처럼 조용한 거짓 정상이 된다.
  • fail-closed: 입력을 해석할 수 없으면 정상으로 넘기지 않고 UNKNOWN으로 알린다.
    • 원리 보안의 기본 거부(anyRequest().denyAll())와 같은 사고방식이다. 모를 때는 안전한 쪽으로 실패한다.
    • 알림 쪽에서 안전한 실패는 “일단 사람을 부르는 것”이다. 그 대가로 거짓 알람이 늘 수 있는데, 이것이 트레이드오프다.
  • 두 채널에 독립 전송: Discord가 실패해도 Slack 전송은 시도한다. 한 채널의 장애가 알림 전체를 막지 않게 한 것이다.
  • 기록 측정 자체의 정직성도 반복된 주제였다. 다음을 구분하지 않으면 Before/After 비교가 무효가 된다.
    • 측정 실패: 부하 도구가 목표만큼 요청을 보내지 못했다.
    • 수집 실패: Prometheus가 값을 긁어 오지 못했다.
    • 표본 부재: 비교할 데이터가 아예 없었다.
    • 이것은 28강(성능 측정의 방법과 실패)의 주제다.
  • 확인 실제 Webhook 생성, 비밀 배치, 운영 전송은 별도 승인 뒤에만 하도록 문서에 경계가 그어져 있다. 운영 개요 문서도 OCI에서 “전체 알림 연결”은 검증하지 않았다고 적는다. 2강에서 지적한 “같은 서버에 있는 감시자” 문제와 함께, 이 축은 설계는 있으나 운영 증명은 남은 상태다.

    • 핵심은 처리와 결과 저장을 한 트랜잭션에 묶는 것이다. 외부 결제처럼 묶을 수 없는 곳이 가장 위험하다.
  • 보안
    • 응답 본문이 같아도 응답 시간으로 정보가 샐 수 있다(타이밍 부채널).
    • 정적 로그 검사는 직접 인자만 막는다.
  • 가용성
    • “200 OK”는 그 검사가 지나간 경계까지만 증명한다.
    • SLO·RPO·RTO가 아직 없다. 이 사실이 단일 서버 선택의 맥락이다.
  • 성능
    • 커넥션 대기는 증상이고 풀 증설은 악화를 불렀다.
    • TIME_WAIT 60초 × 임시 포트 28,232개가 초당 약 470 연결이라는 상한을 만든다.
    • 640MB 컨테이너는 힙이 아니라 전체 메모리로 죽었다.
  • 관측: 모를 때는 정상이라 하지 않는다(fail-closed). 감시 장치의 고장도 별도 상태로 판정한다.

4강. 요구사항의 진화: 무엇을 만들었고, 무엇을 일부러 뺐는가

이번 강의의 목표

  • MVP1부터 MVP4까지 요구사항이 어떤 순서로 자랐는지 한 줄로 설명할 수 있다.
  • 각 단계에서 일부러 뺀 것이 무엇이고, 그것이 나중에 어떤 비용으로 돌아왔는지 말할 수 있다.
  • 제품 결정이 SQL 제약(CHECK, 복합 외래 키, UNIQUE)으로 굳어지는 과정을 코드로 확인한다.

표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 원리 일반 원리 · 미확인

1. 한 장으로 보는 흐름

PawCycle은 처음부터 지금의 모습이 아니었다. 7월의 MVP1은 "SKU 하나를 고르는 구독"뿐이었다. 8월 초 MVP2에서 반려동물·플랜 버전·불변 스냅샷·구독 상태가 생겼고, 8월 11일 자동 주문, 8월 13일 MVP3에서 일반 구매와 결제가, 8월 말 MVP4에서 신뢰·추천·직접 관리가 붙었다. 9~11월은 기능 추가보다 구조 정리와 운영의 시간이었다. 아래 타임라인이 그 흐름이다.

2. MVP1 (7월): SKU 하나를 고르는 구독

MVP1의 요구사항 문서(PS-001)에는 제품 범위를 그린 mermaid 도식이 들어 있다. 저장소의 원문 도식을 그대로 렌더링하면 다음과 같다.

도식에서 눈여겨볼 점은 배송 주기와 다음 주문 예정일이 독립된 상자로 그려졌지만, 문서는 이것을 “구독을 설명하는 값이지 별도 엔티티가 아니다”라고 못 박았다는 것이다. 개념을 그리는 것과 테이블을 만드는 것을 구분한 것이다. 실제로 이 요구사항은 테이블 하나로 굳었다.

-- V2__create_subscriptions.sql (MVP1의 구독 전부)
CREATE TABLE subscriptions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    sku_id BIGINT NOT NULL,                       -- 구독 하나 = SKU 하나
    quantity INT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    created_date DATE NOT NULL,                   -- 시각이 아니라 날짜
    next_order_date DATE NOT NULL,
    CONSTRAINT chk_subscriptions_quantity CHECK (quantity BETWEEN 1 AND 10),
    CONSTRAINT chk_subscriptions_delivery_cycle CHECK (delivery_cycle_weeks IN (2, 4, 8)),
    CONSTRAINT chk_subscriptions_date_order CHECK (next_order_date > created_date),
    ...
);
CREATE INDEX idx_subscriptions_member_id ON subscriptions (member_id, id);
  • CHECK (quantity BETWEEN 1 AND 10), IN (2, 4, 8): 제품 결정(“수량 1~10, 주기 2·4·8주 고정, 임의 주기 금지”)이 DB 제약으로 그대로 옮겨졌다. 애플리케이션 검증이 뚫려도 DB가 마지막으로 막는다. 원리 MySQL은 8.0.16부터 CHECK를 실제로 강제한다. 그 전 버전은 문법만 받아들이고 무시했다.
  • created_date DATE: 시각이 아니라 날짜다. 정기배송은 “몇 시 몇 분”이 아니라 “며칠”의 문제이고, 기준 시간대는 Asia/Seoul로 정했다. 휴일 보정은 하지 않기로 했다.
  • CHECK (next_order_date > created_date): 정확한 계산(생성일 + 주기)은 도메인 코드가 책임진다. DB는 순서만 검사한다. 정확한 등식까지 DB에 넣지 않은 이유는 계산 규칙이 바뀔 때 마이그레이션이 필요해지기 때문이다. 책임을 나눈 것이다.
  • INDEX (member_id, id): “내 구독 목록을 최신순으로” 조회 한 가지를 위해 만든 인덱스다. 기록 측정 없이 추가 인덱스를 만들지 않는다는 원칙도 함께 정했다.
  • status 컬럼이 없다. 일시정지도 해지도 없으니 상태가 필요 없었다.

일부러 뺀 것과 그 대가

확인 제외 목록은 30개가 넘는다. 주문 생성, 장바구니, 결제, PG 연동, 재고, 배송, 구독 변경·일시정지·해지, 쿠폰, 추천, 관리자 화면 등이다. 문서는 “제외된 기능은 전체 제품 방향에서 삭제하지 않는다. 후속 후보로 남긴다”고 덧붙인다.

그중 세 가지 결정이 이후 설계에 큰 흔적을 남겼다.

  • 멱등성을 일부러 넣지 않았다. 기록 첫 구독 API 계약은 같은 회원이 같은 조건으로 구독을 여러 개 만드는 것을 허용했다. Idempotency-Key 저장소도 두지 않았다. 클라이언트는 처리 중 제출 버튼만 비활성화했다.
    • 문서는 “타임아웃 후 반복 POST가 실제 중복 구독을 만들 수 있는 위험”을 사용자가 승인한 트레이드오프로 남겼다.
    • 3강의 언어로 말하면, 이 API는 최소 한 번 전달 + 중복 제거 없음이었다. 결제가 없으니 중복이 생겨도 돈이 움직이지 않는다. 그래서 감수할 수 있는 위험이었다.
    • 돈이 움직이기 시작한 MVP2·MVP3에서는 이 결정이 뒤집힌다(아래 3·5절).
  • 남의 구독은 403이 아니라 404로 숨긴다. “없음”, “남의 것”, “숫자가 아닌 ID”를 모두 같은 404로 돌려준다. 403(“있지만 권한 없음”)으로 구분하면 그 ID가 존재한다는 사실이 새어 나가기 때문이다. 3강의 타이밍 부채널과 같은 계열의 정보 누설 방지이고, 12강(인가와 소유권)에서 코드로 본다.
  • 다음 주문 예정일은 서버만 계산한다. 생성 전에는 화면에 정확한 날짜를 보여 주지 않는다.
    • 브라우저가 미리 계산하면 시간대(사용자 PC가 Asia/Seoul이 아닐 수 있다)와 날짜 기준이 서버와 어긋날 수 있다.
    • 그래서 “생성 후 확인” 안내만 하고, 생성 직후 구독 상세 화면으로 이동해 서버가 확정한 날짜를 보여 준다.
    • 로그인 후에는 서비스 내부의 GET 경로로만 복귀시킨다. 외부 URL로 돌아가게 허용하면 Open Redirect 공격(피싱 사이트로 보내는 신뢰 링크)이 되기 때문이다. 이전 POST를 자동으로 다시 실행하는 것도 금지했다. 중복 구독 위험 때문이다.

3. MVP2 (8/2): “가격이 바뀌면?”이라는 질문

MVP1의 구독은 sku_id와 quantity만 들고 있었다. 그러면 SKU 가격이 오를 때 기존 구독자의 다음 결제 금액도 조용히 바뀐다. 반려동물별 패키지(사료 + 간식 + 모래)도 표현할 수 없다.

기록 MVP2는 이 문제를 네 개념으로 풀었다.

  • Pet: 회원이 소유하는 반려동물. 이름과 종(DOG/CAT)만 있다.
  • SubscriptionPlan → PlanVersion → PlanItem: 종별 패키지 플랜과 그 버전, 버전의 구성 SKU·수량.
  • 불변 스냅샷: 구독할 때 선택한 PlanVersion의 가격·구성·배송 주기를 복사해 둔 기록.
  • pending 변경: 플랜을 바꾸면 즉시 적용하지 않고 다음 실행 가능한 회차에 적용할 스냅샷을 대기시킨다.

왜 참조가 아니라 복사인가

이 설계의 핵심은 가격을 참조하지 않고 복사한다는 것이다. 영수증을 생각하면 쉽다. 영수증에 “상품 #42의 현재 가격”이라고 적혀 있으면, 상품 가격이 바뀔 때마다 과거 영수증의 금액도 바뀐다. 영수증은 그 순간의 값을 그대로 적어 두는 문서여야 한다.

  • 가격·구성을 바꾸고 싶으면 새 PlanVersion을 만든다. 기존 버전은 고치지 않는다.
  • 이미 구독 중인 사람은 자기 스냅샷의 가격을 유지한다. 판매가 끝나도 자동 해지하거나 다른 플랜으로 옮기지 않는다.
  • 기록 기각한 대안: 활성 PlanVersion이나 과거 스냅샷을 제자리에서 수정하는 방식이다. 이미 생성된 구독의 가격 의미가 바뀌기 때문에 기각됐다.

이 규칙들이 SQL에서 어떻게 강제되는지 보자. V3 마이그레이션에서 중요한 세 덩어리다.

-- V3__add_second_mvp_subscription_schema.sql (발췌)

-- (가) "플랜의 현재 버전"은 반드시 그 플랜의 버전이어야 한다
ALTER TABLE plan_versions
    ADD CONSTRAINT uk_plan_versions_id_plan UNIQUE (id, plan_id);
ALTER TABLE subscription_plans
    ADD CONSTRAINT fk_subscription_plans_current_version
        FOREIGN KEY (current_plan_version_id, id) REFERENCES plan_versions (id, plan_id);

-- (나) 스냅샷: 출처 버전을 기억하되, 금액·주기는 복사본을 들고 있다
CREATE TABLE subscription_snapshots (
    id BIGINT NOT NULL AUTO_INCREMENT,
    subscription_id BIGINT NULL,
    source_plan_version_id BIGINT NOT NULL,
    package_total_krw BIGINT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    CONSTRAINT chk_subscription_snapshots_total
        CHECK (package_total_krw BETWEEN 0 AND 9007199254740991),
    ...
);

-- (다) 구독당 pending 변경은 최대 하나
CREATE TABLE pending_plan_changes (
    subscription_id BIGINT NOT NULL,
    snapshot_id BIGINT NOT NULL,
    target_schedule_id BIGINT NOT NULL,
    CONSTRAINT pk_pending_plan_changes PRIMARY KEY (subscription_id),
    CONSTRAINT uk_pending_snapshot UNIQUE (snapshot_id),
    CONSTRAINT uk_pending_target_schedule UNIQUE (target_schedule_id),
    ...
);
  • (가) 복합 외래 키 트릭. 단순히 current_plan_version_id → plan_versions(id)로 걸면, 플랜 A의 현재 버전으로 플랜 B의 버전을 가리키는 실수를 DB가 막지 못한다.
    • 그래서 plan_versions에 (id, plan_id) 조합 UNIQUE를 만든다. id가 이미 PK라 이 조합은 당연히 유일하지만, 외래 키의 참조 대상이 되려고 만든 것이다.
    • 그다음 (current_plan_version_id, 자기 id)가 그 조합을 참조하게 한다. 이렇게 하면 “현재 버전의 plan_id = 나의 id”가 DB 수준에서 보장된다.
    • 애플리케이션 버그 하나로 다른 플랜의 가격이 섞이는 일을 구조적으로 막는 기법이고, 6강(ERD)에서 다시 쓴다.
  • (나) 9007199254740991이라는 이상한 상한. 이 수는 2⁵³ − 1이고, JavaScript의 Number.MAX_SAFE_INTEGER다.
    • 원리 JavaScript의 숫자는 64비트 부동소수점(IEEE 754 double)이라 가수부가 53비트다. 그보다 큰 정수는 정확히 표현되지 않는다. 예를 2⁵³ + 1은 2⁵³으로 반올림된다.
    • 서버의 BIGINT는 2⁶³ − 1까지 담지만, JSON으로 프론트에 가는 순간 큰 금액이 조용히 다른 숫자로 바뀔 수 있다.
    • 해석 그래서 금액 상한을 프론트가 안전하게 다룰 수 있는 범위로 DB에서 묶었다. 화면(Next.js)까지 고려한 제약이다.
  • (다) “최대 하나”를 PK로 표현. PRIMARY KEY (subscription_id)이니 한 구독에 pending 행은 물리적으로 하나만 존재할 수 있다.
    • 제품 규칙도 이에 맞춰져 있다. 적용 전에 새 변경이 오면 대기열에 쌓지 않고 최신 요청으로 교체한다. 교체 전 명령은 명령 이력에 남긴다.
    • 대기열로 쌓는 대안은 “어느 변경이 언제 적용되는가”라는 복잡한 규칙을 만든다.

멱등성이 돌아왔다

MVP2의 구독 명령(플랜 변경, 건너뛰기, 일시정지, 재개, 해지)에는 Idempotency-Key와 If-Match(버전 검사)가 들어갔다. MVP1에서 뺐던 것이 돌아온 것이다. 구독 상태가 생기고 명령이 상태를 바꾸기 시작했으니, “같은 해지 요청이 두 번 들어오는” 문제가 현실이 됐기 때문이다. 동시 수정 보호(If-Match, 낙관적 버전)는 22강에서 본다.

기존 데이터라는 청구서

MVP1 구독은 스냅샷 없이 이미 만들어져 있었다. 기록 MVP2는 이 데이터를 버리거나 초기화하지 않고 손실 없이 이행하기로 했다. 규칙은 이렇다.

  • 기존 구독의 가격은 마이그레이션 시점의 SKU 단가 × 기존 수량으로 계산한다. 문서는 이것이 “구독 생성 당시 가격이 아니다”라고 정직하게 적는다. 당시 가격을 기록해 두지 않았으니 복원할 방법이 없다.
  • 기존 구독 보존 전용 PlanVersion·PlanItem을 만들어 연결한다. 이 버전은 신규 구독의 선택 후보가 아니다.
  • 변환할 수 없는 행이 하나라도 있으면, 값을 추측·반올림·절삭하지 않고 쓰기 전에 전체 마이그레이션을 중단한다.

이것이 MVP1에서 스냅샷을 뺀 결정의 대가다. 이 대가를 어떻게 평가할지는 7절에서 YAGNI의 틀로 다시 본다.

4. 자동 주문 (8/11): 스케줄러는 최소 한 번 실행된다

MVP2까지 “다음 주문 예정일”은 화면에 보여 주는 값일 뿐, 실제로 주문이 생기지는 않았다. 8월 11일 자동 주문이 들어오면서 처음으로 시스템이 스스로 데이터를 만들기 시작했다.

확인 요구사항 문서의 핵심 문장은 이것이다.

Scheduler 실행은 at-least-once여도 DB 결과는 Schedule당 Order 하나다. — docs/product/PS-005-subscription-automation-requirements.md

3강에서 배운 “최소 한 번 전달 + 중복 제거 = 정확히 한 번의 효과”가 그대로 요구사항이 됐다. 스케줄러가 같은 회차를 두 번 집거나 서버 두 대가 동시에 돌아도, 결과는 주문 하나여야 한다. 그 마지막 방어선이 SQL 한 줄이다.

-- V9__create_subscription_orders.sql (발췌)
CREATE TABLE subscription_orders (
    ...
    schedule_id BIGINT NOT NULL,
    effective_snapshot_id BIGINT NOT NULL,       -- 이 주문에 적용된 스냅샷
    source_plan_version_id BIGINT NOT NULL,
    scheduled_date DATE NOT NULL,                -- 원래 예정일
    processed_at DATETIME(6) NOT NULL,           -- 실제 처리 시각
    package_total_krw BIGINT NOT NULL,           -- 금액도 다시 복사
    status VARCHAR(20) NOT NULL,
    CONSTRAINT uk_subscription_orders_schedule UNIQUE (schedule_id),
    CONSTRAINT chk_subscription_orders_status CHECK (status = 'CREATED'),
    ...
);
  • UNIQUE (schedule_id): 회차 하나에 주문 하나. 경쟁에서 진 쪽은 중복 키 오류를 받는다.
    • 기록 이 오류를 바로 실패로 보지 않는다. 실제 주문이 존재하는지 다시 확인한 뒤에만 정상적인 “이미 처리됨(no-op)”으로 처리한다.
  • scheduled_date와 processed_at을 둘 다 저장: “언제 처리됐어야 했나”와 “실제로 언제 처리됐나”를 구분한다. 스케줄러가 멈췄다 재개되면 둘이 벌어지는데, 이 차이가 운영의 증거가 된다.
  • CHECK (status = 'CREATED'): 상태가 하나뿐이다. 결제·배송이 없으니 다른 상태가 필요 없다. 필요해질 때 늘린다. 이것도 MVP1의 status 없음과 같은 원칙이다.

처리 방식에서 일부러 하지 않은 것들이 특히 중요하다.

  • 배치 전체를 한 트랜잭션으로 묶지 않았다. 후보마다 REQUIRES_NEW로 독립 트랜잭션을 연다. 3강에서 본 PR #106의 실패 격리 원칙이 그대로 이어진다.
  • 누락된 회차를 몰아서 만들지 않는다. 스케줄러가 3주 멈췄다가 살아나도 가장 오래된 회차의 주문 하나만 만든다. 그다음 원래 예정일에서 주기를 반복해 오늘보다 미래인 첫 날짜로 건너뛴다.
    • 예: 2주 주기, 예정일 10/1, 오늘 10/20 → 10/1 회차 주문 1건 생성 → 다음 회차는 10/15를 지나 10/29.
    • 이유: 장애 뒤에 의도하지 않은 대량 주문이 생기는 위험이 회차 누락보다 크다고 판단했다.
  • 기록 기각한 대안:
    • 애플리케이션 메모리 락, Redis 분산 락, Kafka: DB 행 잠금과 UNIQUE 제약만으로 불변식을 표현할 수 있어서, 새 운영 의존성을 정당화하지 못했다.
    • HTTP 명령의 멱등 행 재사용: 스케줄러의 처리 단위와 보관 의미가 다르다.
    • 재시도 API, backoff, DLQ, 새 PROCESSED 상태: 다음 스케줄러 실행이 다시 집으면 되므로 두지 않았다.
  • 기본값은 꺼짐. 명시적으로 켜야만 동작한다. 운영 DB에 자동으로 데이터를 만드는 기능은 켜는 것 자체가 별도 결정이어야 하기 때문이다.

5. MVP3 (8/13): 돈이 움직이기 시작했다

MVP3는 하루에 거대한 PR 하나(PR #138)로 일반 구매 Commerce를 들여왔다. MVP1에서 뺐던 목록 대부분이 한꺼번에 돌아왔다.

  • 장바구니, 찜, 배송지
  • 체크아웃(재고 예약, 쿠폰), 토스 결제 승인, 정기결제(빌링키)
  • 배송·취소·반품·환불, 알림
  • 관리자: 재고 조정, 쿠폰, 회원 등급, 운영 조회, 감사 로그

확인 계약 문서에서 MVP1과 대비되는 문장들을 골라 보면 진화가 선명하다.

주제 MVP1 MVP3
중복 요청 멱등성 없음, 버튼 비활성화만 체크아웃에 Idempotency-Key 필수, 회원 단위로 직렬화해 동시 요청도 기존 결과를 재생
가격의 권위 서버가 계산한 날짜만 신뢰 장바구니는 가격·재고를 예약하지 않고, 체크아웃에서 현재 가격·재고를 다시 검증. 결제 금액은 서버의 체크아웃 응답 값을 쓰고, 토스 리다이렉트 URL의 금액은 일치 검사에만 사용

일부러 막아 둔 것들도 분명하다.

  • 실결제는 없다. 토스 연동은 local-integration 프로필에서 test_sk_ 테스트 키로만 동작한다. 라이브 키는 거부한다.
  • 결제사가 없으면 실패한다(fail-closed). 실제 결제사가 구성되지 않은 환경에서는 결제 승인과 빌링 등록이 실패로 끝난다. 가짜 결제 성공을 만들지 않는다. 3강 관측 축의 “모를 때는 정상이라 하지 않는다”와 같은 원칙이다.
  • UNKNOWN 결제는 재시도 대상으로 바꾸지 않는다. 예약된 재고와 쿠폰은 유지한다. 결제 대사는 최대 10회까지만 하며, 대사 스케줄러 실행 자체는 범위 밖이다. 이 빈칸이 3강 위험 지도의 1순위였던 PROCESSING 고립 문제로 이어진다(18·19강).
  • 결제 응답 대기 시간 30분. 결제창으로 넘어간 뒤 30분 안에 승인되지 않으면 주문을 만료시키고 재고와 쿠폰을 돌려준다. PROCESSING·UNKNOWN 결제는 이 만료 대상이 아니다. 돈이 움직였을지도 모르는 상태를 함부로 되돌리지 않기 위해서다.

같은 날 바로 구조 정리 PR(PR #139)이 뒤따랐다. 기록 여기서 정한 원칙은 이렇다.

  • API와 기존 스키마는 유지한다.
  • 일반 엔티티는 JPA로 옮기되, 잠금·CAS·운영 조회·구독 V2 호환 경계는 명시 SQL로 남긴다.
  • 외부 결제사 호출은 DB 트랜잭션 밖에 둔다. 느리거나 실패하는 외부 I/O가 DB 커넥션과 잠금 점유로 번지지 않게 하기 위해서다. 3강의 HikariCP 이야기와 연결된다.
  • 관리자 변경은 감사 기록까지 한 트랜잭션에서 처리한다. 감사 기록이 실패하면 상태 변경도 커밋하지 않는다.

6. MVP4 (8/24–8/28): 신뢰와 추천, 그리고 AI의 자리

MVP4는 “살 수 있다”를 넘어 “믿고 살 수 있다”로 갔다.

  • 구독 직접 관리: 회원이 구독 명령을 더 넓게 스스로 수행한다. 기존 Idempotency-Key, If-Match, ETag 계약을 그대로 이어받고, 성공 재생을 버전 검사보다 먼저 판정한다.
    • 왜 순서가 중요한가: 이미 성공한 요청을 재시도하면, 그 사이 버전이 올라가 있으므로 버전 검사를 먼저 하면 충돌로 오판한다. 3강 그림의 “저장된 결과 재전송”이 먼저여야 한다.
  • 상품 신뢰: 리뷰와 상품 문의. 공개 응답에 작성자의 이메일이나 회원 ID를 넣지 않는다.
  • 구매 정합성: 장바구니에 version을 추가했다. 내용이 실제로 바뀔 때만 올라가고, 변화 없는 요청은 버전을 올리지 않는다(16·17강).
  • 반려동물 프로필: 품종과 체중을 추가했다. 삭제 API는 없다.

가장 흥미로운 결정은 AI 추천의 경계다. 기록

  • 서버가 후보, 소유권, 의료 관련 상품 제외, 최종 구매 가능 여부를 모두 결정한다.
  • AI에는 최대 10개로 제한된 후보 ID와 공개 상품 정보만 넘긴다. AI는 순서와 짧은 이유만 제안한다. 회원 식별자, 이름, 연락처, 주소, 결제 정보는 넘기지 않는다.
  • AI가 후보 밖 ID나 중복을 돌려주거나 오류가 나면, 그 결과를 버리고 결정적인 기본 순서로 채운다.
  • AI 호출 뒤에 최신 카탈로그 조건을 다시 조회한다.
    • 원리 이것을 TOCTOU(Time-Of-Check to Time-Of-Use) 문제라 한다. 검사한 시점과 사용하는 시점 사이에 상태가 바뀌는 문제다. AI 호출이 몇 초 걸리는 동안 상품이 품절될 수 있다.
  • 외부 AI 호출 중에는 DB 트랜잭션을 열어 두지 않는다. MVP3 구조 정리와 같은 원칙이다.
  • 기본값은 꺼짐. 실제 API 키, 모델, 운영 비용 승인은 별도다.
  • 기록 기각한 대안: AI가 후보 선택과 유효성까지 판단하는 방식(확률적 응답에 정책을 맡김), 추천 전용 Redis·RAG·임베딩·큐 도입(근거 부족).

해석 이 결정은 포트폴리오에서 가장 설명하기 좋은 소재 중 하나다. “AI를 붙였다”가 아니라 “AI가 틀려도 시스템이 틀리지 않게 경계를 그었다” 고 말할 수 있기 때문이다. 15강에서 코드로 확인한다.

7. 판단의 틀: YAGNI와 네 가지 비용

다섯 단계를 관통하는 원칙은 하나다. 필요가 확인되기 전에는 만들지 않는다. 이것을 YAGNI(You Aren't Gonna Need It)라 한다. 데브원영의 「YAGNI, 그 기능이 필요할 때 만들어라!」는 Ron Jeffries의 말로 이 원칙을 소개한다. 미래에 필요할 것 같을 때가 아니라 실제로 필요할 때 구현하라는 것이다. 그리고 한계로 장기 설계를 간과하거나 과도하게 단순화할 위험도 함께 짚는다.

Martin Fowler는 「Yagni」에서 이 원칙을 비용으로 분해한다. 미리 만든 기능(presumptive feature)은 네 가지 비용을 낳는다는 것이다.

출처: Martin Fowler · Yagni (2015).

  • 만드는 비용(cost of build): 결국 필요 없었던 기능에 쓴 분석·개발·테스트 노력.
  • 지연 비용(cost of delay): 그 시간에 지금 필요한 기능을 만들지 못해 가치가 늦게 나온 비용. 필요한 기능이었더라도 생긴다.
  • 유지 비용(cost of carry): 미리 만든 코드가 복잡도를 더해, 이후 모든 기능의 개발과 디버깅을 느리게 하는 비용.
  • 수리 비용(cost of repair): 필요한 기능을 잘못된 모양으로 미리 만들어, 나중에 고쳐야 하는 비용. 그 사이 팀은 도메인과 코드를 더 배우기 때문에 이런 일이 흔하다.

Fowler는 중요한 단서를 하나 붙인다. YAGNI는 미리 만든 기능에만 적용되고, 코드를 바꾸기 쉽게 만드는 노력에는 적용되지 않는다. 리팩터링, 자가 테스트 코드, 지속적 전달은 YAGNI 위반이 아니라 YAGNI를 가능하게 하는 조건이다. 코드가 바꾸기 어려우면 YAGNI는 저주가 된다.

이 틀로 PawCycle의 결정들을 평가해 보자. 아래 판정은 모두 해석 이다.

결정 YAGNI 관점의 평가
MVP1에서 주문·결제·재고 제외 잘 맞았다. 구독 흐름이 먼저 동작했고, 결제 설계는 실제 요구가 생긴 MVP3에서 했다. 지연 비용을 피했다.
MVP1에서 status 없음, V9의 CREATED 하나 잘 맞았다. 필요한 상태만 그때그때 추가했다. 미리 만든 상태 머신은 대부분 틀린 모양이 된다(수리 비용).
Redis 락·Kafka·DLQ 기각 잘 맞았다. DB 제약으로 충분했고, 새 운영 의존성의 유지 비용을 피했다.
MVP1에서 가격 스냅샷 없음 비용이 실제로 청구됐다. MVP2에서 손실 없는 이행 규칙을 따로 설계해야 했고, 원래 생성 당시 가격은 영원히 복원할 수 없게 됐다. 데이터는 코드와 달리 나중에 리팩터링으로 되살릴 수 없다.
MVP1에서 멱등성 없음 조건부로 맞았다. 돈이 움직이지 않는 동안에는 위험이 작았다. 돈이 움직이기 시작한 MVP2·MVP3에서 바로 들어왔다.

여기서 실무 교훈 하나가 나온다. YAGNI는 코드에는 관대하지만 데이터에는 가혹하다. 코드는 나중에 고치면 되지만, 기록하지 않은 사실(생성 당시 가격, 처리 시각, 누가 바꿨는지)은 나중에 만들어 낼 수 없다. 그래서 다음은 “미리 만드는 기능”이 아니라 비용이 작은 보험으로 보는 편이 맞다.

  • 시점 값을 복사해 두는 스냅샷
  • 예정 시각과 실제 처리 시각을 함께 남기는 컬럼
  • 감사 기록

Fowler가 말한 “지금 하기 쉽고, 복잡도를 거의 늘리지 않으면서, 나중 비용을 크게 줄이는 것”에 해당한다. PawCycle은 V9에서 scheduled_date와 processed_at을 처음부터 둘 다 저장해, 이 교훈을 반영했다.

5강. 도메인 모델: 엔티티, 테이블, 애그리거트는 1:1이 아니다

이번 강의의 목표

  • 구독을 하나의 묶음(애그리거트)으로 보는 이유와, 그 묶음을 지키는 장치(version)를 설명할 수 있다.
  • 상품과 SKU, 판매 상태와 구독 가능 여부, 회차와 주문, 주문과 결제처럼 헷갈리기 쉬운 쌍을 구분한다.
  • 문서에서는 "채택"했다고 적힌 설계(값 객체 등)가 코드에는 어떻게 남았는지, 문서와 코드가 다를 때 어떻게 읽는지 익힌다.

표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 원리 일반 원리 · 미확인

1. 구독은 하나의 묶음이다

구독 하나는 테이블 하나가 아니다. 구독 본체, 그 시점의 약속을 고정한 스냅샷과 스냅샷 항목, 다음 회차에 적용될 대기 변경, 회차 일정, 명령 이력이 모두 "구독 하나의 상태"를 이룬다. 개념으로 보면 하나의 묶음이고, 테이블로 보면 여러 개다.

그림의 점선이 DDD에서 말하는 애그리거트(aggregate)다. 위키독스의 「애그리거트와 루트 엔티티 설계: 트랜잭션 경계의 확립」은 애그리거트를 “데이터 변경의 일관성을 유지하기 위해 하나의 단위로 취급되어야 하는 객체들의 묶음”으로 정의한다. 글이 강조하는 규칙은 세 가지다.

  • 외부는 루트(여기서는 Subscription)만 참조한다.
  • 내부 객체는 루트를 통해서만 바꾼다.
  • 묶음 전체가 한 트랜잭션으로 저장된다.

그리고 다른 애그리거트는 객체가 아니라 ID로만 참조하라고 한다. 객체로 직접 참조하면 조회할 때마다 불필요한 로딩(JPA N+1)이 생기고, 두 애그리거트의 변경이 서로의 트랜잭션에 얽히기 때문이다.

PawCycle에 대 보면 이렇다.

  • 확인 ID 참조: 현재 SubscriptionEntity는 long memberId, long skuId, Long petId, Long currentSnapshotId처럼 ID 필드만 가진다. 반면 MVP1의 첫 Subscription 엔티티는 @ManyToOne Member member, @ManyToOne Sku sku로 객체를 참조했다. V2로 오면서 ID 참조로 바뀐 것이다.
  • 확인 경계를 지키는 장치: 그림 위쪽 상자에 적힌 version 하나다. 플랜 변경, 건너뛰기, 일시정지, 자동 주문 등 무엇이 구독 묶음을 바꾸든 같은 version을 올린다. 4강에서 본 자동 주문 처리 규칙에도 “Subscription version 한 번 증가”가 들어 있었다. version이 묶음 전체의 일관성 경계를 대표하는 숫자다.
  • 해석 테이블과는 1:1이 아니다: 이 묶음은 subscriptions, subscription_snapshots, subscription_snapshot_items, pending_plan_changes, subscription_schedules, 명령 이력 테이블 등 여러 테이블에 걸쳐 있다. 반대로 LegacyInitialSnapshot이나 PendingPlanChange는 도메인 문서에 개념으로 있지만, 문서 스스로 “별도 엔티티 구현을 요구하지 않는다”고 적는다.

2. 상품 vs SKU, 판매 상태 vs 구독 가능 여부

상품과 SKU는 “보는 단위”와 “사는 단위”다

  • 확인 용어집의 정의:
    • Product: 사용자에게 하나의 상품으로 인식되는 공통 정보다(“연어 사료”).
    • SKU: 용량·구성이 확정된 실제 선택 단위다(“연어 사료 5kg”).
  • 가격도, 재고도, 구독 가능 여부도 SKU에 붙는다. 같은 사료라도 2kg과 10kg은 가격과 재고가 다르기 때문이다.
  • 도메인 문서는 Product에 “구독 생성 불변 조건을 직접 검증하지 않는다”고 못 박는다. Product는 보여 주는 책임, SKU는 선택되는 책임을 진다.

하나의 SKU에 독립된 두 스위치

SKU에는 비슷해 보이지만 서로 독립인 두 속성이 있다.

// catalog/sku/domain/Sku.java (발췌)
private BigDecimal price;
private boolean subscribable;   // 구독 가능 여부: 정기배송 대상으로 고를 수 있는가
private SkuStatus status;       // 판매 상태(ACTIVE/INACTIVE): 공개 상품 API에 보이는가

확인 도메인 규칙은 “SKU 판매 status는 구독 적격성인 subscribable과 독립이다. INACTIVE라도 기존 구독 조건은 subscribable만 사용한다”고 적는다. 두 스위치를 조합하면 네 가지 상태가 나온다.

status subscribable 의미하는 상황
ACTIVE true 일반 판매 중이고 정기배송도 가능
ACTIVE false 일반 구매만 가능 (예: 한정 수량 이벤트 상품)
INACTIVE true 공개 목록에서는 내렸지만 기존 정기배송 대상으로는 유지
INACTIVE false 판매도 구독도 불가
  • 왜 하나로 합치지 않았나. 해석 하나의 상태값(SELLING, SUBSCRIPTION_ONLY, …)으로 합치면 “공개 목록에서 내린다”는 운영 행위가 기존 구독자의 배송까지 끊는 부작용을 만들기 쉽다. 두 축을 나누면 각 변경의 영향 범위가 분명해진다.
  • 같은 원칙이 곳곳에 있다. 확인
    • Product 관리 상태는 DRAFT → PUBLIC, PUBLIC → INACTIVE, INACTIVE → PUBLIC만 허용하고 나머지 전이는 409다.
    • 카테고리를 비활성화해도 Product 공개 상태를 연쇄 변경하지 않는다.
    • ACTIVE SKU가 하나도 없어도 PUBLIC Product는 빈 SKU 배열로 남는다.
  • 재고와 품절도 별개다. MVP1의 구독 생성 조건은 subscribable 하나뿐이었다. 재고, 품절, 판매 상태는 구독 생성과 연결하지 않았다. 재고는 실제 주문·결제 시점(MVP3)에서야 의미를 가진다.

3. 스냅샷의 세 가지 역할

4강에서 “가격은 참조하지 않고 복사한다”를 봤다. 도메인 문서를 자세히 읽으면 같은 subscription_snapshots 테이블의 행이 세 가지 역할로 쓰인다.

역할 무엇을 가리키나 언제 바뀌나
현재 스냅샷 (current) 지금 구독에 적용 중인 가격·구성·주기 pending이 적용될 때만 교체
pending 스냅샷 플랜 변경 후 다음 실행 가능한 회차에 적용할 값 새 플랜 변경이 오면 최신 요청으로 교체(대기열 아님)
effective 스냅샷 특정 회차의 주문에 실제로 쓰인 값 회차를 처리할 때 한 번 기록되고 이후 불변

자동 주문이 회차를 처리할 때 도메인 규칙은 이렇다(DOMAIN-003).

  1. 이 회차가 pending의 적용 대상이면 pending 스냅샷을, 아니면 현재 스냅샷을 effective로 정한다.
  2. effective 스냅샷의 가격과 항목을 주문에 다시 복사한다.
  3. pending을 썼다면 현재 스냅샷 포인터를 그것으로 바꾸고 pending을 지운다.
  4. 이 모든 것을 version 증가와 함께 한 트랜잭션으로 커밋한다.

명령들도 pending을 다르게 다룬다.

  • 건너뛰기: pending의 적용 대상을 새 회차로 옮긴다.
  • 일시정지: pending을 보존하고, 재개로 만든 회차에 적용한다.
  • 해지: pending을 적용하지 않는다. 코드에서는 deletePendingPlanChange로 지운다.

해석 이 규칙들이 복잡해 보이는 이유는, 시간에 따라 변하는 값을 “언제부터 유효한가” 까지 함께 관리하기 때문이다. 스냅샷 하나로 보이는 개념이 실은 시점이 다른 세 값이라는 것을 알아야 22강(구독 명령)과 23강(자동 주문) 코드가 읽힌다.

4. 구독 상태 전이와 회차 상태

구독에는 상태가 세 개, 회차에는 네 개 있다. 둘은 함께 움직인다.

그림의 핵심 불변 조건은 상자 안의 부제다. ACTIVE 구독은 미래 SCHEDULED 회차를 정확히 하나 갖고, PAUSED는 그 대신 HELD 회차를 갖는다. CANCELED는 되살리지 않으며, 다시 쓰려면 새 구독을 만든다. 이 규칙이 실제 코드에서는 이렇게 구현돼 있다.

// subscription/application/SubscriptionCommandApplicationService.java (발췌)
long expected = support.parseEtag(ifMatch);
if (subscription.version() != expected)                       // ① 낙관적 버전 검사
  throw new SubscriptionFailure(PRECONDITION_FAILED, "SUBSCRIPTION_VERSION_MISMATCH", ...);
switch (commandType) {
  case PAUSE  -> pause(subscription);
  case RESUME -> resume(subscription);
  case CANCEL -> cancel(subscription);
  ...
}
if (!store.incrementVersion(subscriptionId, expected))         // ② CAS로 version 증가
  throw new SubscriptionFailure(PRECONDITION_FAILED, ...);

private void pause(SubscriptionProjection subscription) {
  if (!"ACTIVE".equals(subscription.status())) throw support.state();   // ③ 전이 규칙
  ScheduleProjection schedule = store.lockNextScheduled(subscription.id());
  store.setSubscriptionStatus(subscription.id(), "PAUSED");
  store.setScheduleStatus(schedule.id(), "HELD");

  store.setSubscriptionStatus(subscription.id(), "CANCELED");
  store.cancelUnorderedSchedules(subscription.id());

  • ③: 전이 규칙이 애플리케이션 서비스의 문자열 비교로 구현돼 있다. "ACTIVE".equals(...) 검사가 이 파일에만 7번 나온다.
  • 상태를 바꾸는 일도 store.setSubscriptionStatus(id, "PAUSED"), 즉 저장소 메서드 호출이다. SubscriptionEntity에는 상태를 바꾸는 메서드가 하나도 없다. 생성자 하나뿐이고, 생성 시 status = "ACTIVE"로 고정된다.

이것은 나쁜 설계인가: 도메인 모델 vs 트랜잭션 스크립트

Martin Fowler는 「Anemic Domain Model」에서 이런 모양을 경고한다. 객체들이 도메인 명사의 이름을 갖고 관계도 갖췄지만, 행위가 거의 없는 getter/setter 묶음이다. 로직은 전부 서비스 객체에 있다. 그는 이것이 도메인 모델의 비용(객체-DB 매핑)은 다 치르면서 이점은 얻지 못하는, 사실상 트랜잭션 스크립트라고 말한다. 다만 같은 글에서 “도메인 모델이 항상 최선의 도구는 아니다”라고도 덧붙인다.

그런데 PawCycle의 구독 V2는 매핑 비용 자체를 치르지 않는 쪽을 택했다. 확인 구조 결정 문서(ARCH-011, Accepted)는 이렇게 정한다.

  • 구독 V2는 명시적 JDBC SQL, FOR UPDATE, version CAS 쓰기, UNIQUE 충돌 처리를 저장소에 둔다.
  • 저장소는 타입이 있는 조회 결과(projection)만 내놓는다. 검증, 멱등 판정, 상태 전이, 응답 조립은 하지 않는다.
  • 생성, 조회, 명령, 대사는 각각의 애플리케이션 서비스가 유스케이스와 트랜잭션 경계를 소유한다.

즉 이 코드는 의도적으로 “트랜잭션 스크립트 + 명시 SQL” 을 택했다. 이유는 3강·4강에서 본 요구들에 있다. 해석

  • 어떤 행을 어떤 순서로 잠그는지(구독 행 → 회차 행)가 정합성의 핵심이다. JPA의 지연 로딩과 플러시 순서에 맡기면 이 순서가 코드에서 보이지 않는다.
  • 상태 변경 하나가 테이블 여러 개를 조건부 UPDATE로 함께 바꾼다. 엔티티 그래프를 불러와 고치는 방식보다 SQL이 의도를 더 정확히 드러낸다.
  • MVP2에서 MVP1 데이터와 호환되는 경계를 유지해야 했다.

그렇다고 개선할 점이 없는 것은 아니다.

개선 제안 해석 트랜잭션 스크립트를 유지하더라도 전이 규칙만은 한 곳에 모을 수 있다. 지금은 “ACTIVE에서만 가능”이 7곳에 흩어져 있어, 새 상태(예: 결제 실패로 인한 SUSPENDED)를 추가하면 모든 곳을 찾아 고쳐야 한다.

java // 제안 예시 — 저장소에 없는 코드다 enum SubscriptionStatus { ACTIVE, PAUSED, CANCELED; boolean canPause() { return this == ACTIVE; } boolean canResume() { return this == PAUSED; } boolean canCancel() { return this != CANCELED; } }

SQL과 잠금 순서는 저장소에 그대로 두고, “무엇이 허용되는가”만 타입으로 옮기는 절충이다. DB의 CHECK (status IN (...))와 문자열이 어긋나는 실수도 컴파일 단계에서 줄어든다. 이 리팩터링은 33강(재설계) 후보로 남긴다.

5. 회차와 주문은 다르다

확인 자동화 도메인 문서는 둘을 이렇게 나눈다.

  • SubscriptionSchedule(회차): 구독의 예정된 한 회차와 원래 예정일이다. “실제 처리 결과가 아니다.”
  • Recurring Order(주문): 그 회차를 실제로 처리해 생긴 결과다.
  • 관계는 회차 1개 → 주문 0개 또는 1개다.

왜 이것을 굳이 나눌까?

  • 계획과 사실을 섞지 않기 위해서다. 회차는 바뀔 수 있는 계획이다. 건너뛰면 SKIPPED, 일시정지하면 HELD, 재개하면 날짜가 바뀐다. 주문은 바뀌면 안 되는 사실이다. 가격, 항목, 출처 PlanVersion, 예정일, 처리 시각이 생성 뒤 불변이다.
  • “처리 안 됨”을 정직하게 남기기 위해서다. 주문이 없는 지난 회차는 “아직 처리되지 않았다”는 뜻이다. 확인 대사(reconciliation) 작업은 이런 회차를 처리된 것으로 바꾸지 않는다. 이미 주문이 있는데 다음 회차가 빠진 경우처럼, 주문 원본만으로 안전하게 재구성할 수 있을 때만 보정한다.
  • 해석 회차와 주문을 한 테이블에 합쳐 status = ORDERED로 표현하는 대안도 가능하다. 하지만 그러면 “계획을 바꾸는 명령”과 “사실을 기록하는 자동화”가 같은 행을 두고 경쟁한다. 분리해 두었기 때문에 4강의 UNIQUE (schedule_id) 한 줄로 중복 주문을 막을 수 있다.

6. 주문과 결제는 다르다

일반 구매로 오면 같은 원리가 한 번 더 나온다. 주문은 “무엇을 샀는가”, 결제는 “돈을 받으려는 시도” 다.

확인 V14 마이그레이션의 상태값부터 다르다.

  • 주문: CREATED, PAYMENT_PENDING, PAID, PAYMENT_FAILED, EXPIRED, PAYMENT_ACTION_REQUIRED
  • 결제: READY, PROCESSING, SUCCEEDED, FAILED, UNKNOWN

결제에만 UNKNOWN이 있다. 3강에서 본 대로, 외부 결제사와의 통신은 “모름”이라는 결과를 낳을 수 있기 때문이다. 주문의 상태는 결제 시도들의 결과를 요약한 것이다.

결정적인 차이는 개수다. 주문 하나에 결제 시도는 여러 번 있을 수 있다. 정기결제가 실패해 재시도하면 같은 주문에 두 번째 결제 행이 생긴다. 그래도 성공한 결제는 하나뿐이어야 한다. 이 규칙을 SQL로 어떻게 강제하는지가 이 절의 핵심이다.

-- V14__add_common_order_payment_and_billing.sql — payments 테이블 (발췌)
provider_order_id VARCHAR(100) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
idempotency_key   VARCHAR(128) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
attempt_no INT NOT NULL,
reconciliation_attempts INT NOT NULL DEFAULT 0,
succeeded_order_id BIGINT GENERATED ALWAYS AS
    (CASE WHEN status = 'SUCCEEDED' THEN order_id ELSE NULL END) STORED,

CONSTRAINT uk_payments_order_attempt   UNIQUE (order_id, attempt_no),
CONSTRAINT uk_payments_successful_order UNIQUE (succeeded_order_id),
CONSTRAINT uk_payments_idempotency      UNIQUE (idempotency_key),
CONSTRAINT chk_payments_reconciliation_attempts CHECK (reconciliation_attempts BETWEEN 0 AND 10)

그림의 트릭을 풀어 보자.

  • 문제: “성공한 결제는 주문당 하나”는 조건부 유일성이다. 상태가 SUCCEEDED인 행에 대해서만 order_id가 유일해야 한다. PostgreSQL이라면 CREATE UNIQUE INDEX ... WHERE status = 'SUCCEEDED'처럼 부분 인덱스(partial index)로 한 줄에 끝난다. MySQL에는 부분 인덱스가 없다.
  • 해법: 생성 컬럼(generated column)을 만든다. SUCCEEDED일 때만 order_id를 담고 나머지는 NULL을 담는다. 그 컬럼에 UNIQUE를 건다.
    • 원리 SQL 표준과 MySQL에서 UNIQUE 인덱스는 NULL을 여러 개 허용한다. NULL은 “모르는 값”이라 서로 같다고 판정하지 않기 때문이다. 그래서 실패·미확정 시도는 몇 개든 공존한다.
    • SUCCEEDED 행이 두 번째로 생기는 순간 101이 중복되어 DB가 거부한다. 애플리케이션에 버그가 있어도 이중 성공은 기록되지 않는다.
    • STORED는 값을 실제로 디스크에 저장한다는 뜻이다. 기본값인 VIRTUAL은 읽을 때 계산한다. MySQL 공식 문서의 「Secondary Indexes and Generated Columns」가 생성 컬럼 인덱스의 조건을 설명한다. 미확인 이 프로젝트가 왜 VIRTUAL 대신 STORED를 골랐는지는 기록을 찾지 못했다.
    • 대가: 부분 인덱스와 달리, NULL인 행도 인덱스 항목을 차지해 공간을 쓴다.
  • UNIQUE (order_id, attempt_no): 같은 주문의 같은 번째 시도는 하나뿐이다. 확인 계약 문서는 “같은 실패 결제에 대한 중복 재시도 요청은 이미 만들어진 다음 시도를 재사용한다”고 적는다. 재시도 요청 자체도 멱등이다.
  • CHECK (reconciliation_attempts BETWEEN 0 AND 10): 3강·4강에서 본 “UNKNOWN 결제는 최대 10회까지만 결제사에 조회한다”는 규칙이 DB 제약이 됐다.
  • CHARACTER SET ascii COLLATE ascii_bin: 결제 키와 멱등 키 컬럼만 문자셋이 다르다.
    • 원리 테이블 기본값인 utf8mb4_0900_ai_ci의 ai_ci는 악센트 무시(accent-insensitive), 대소문자 무시(case-insensitive) 비교다. 그러면 abc와 ABC가 같은 키로 취급된다.
    • 외부 결제사가 준 ID나 클라이언트의 UUID는 바이트 그대로 비교해야 한다. ascii_bin은 바이트 단위로 비교하고, 문자당 1바이트라 utf8mb4(최대 4바이트)보다 인덱스도 작다.
    • 해석 문자열 키를 대소문자 무시로 비교하면 서로 다른 두 키가 충돌하거나, 같은 키가 다르게 저장될 수 있다. 식별자 컬럼에는 이진 비교 콜레이션을 쓰는 것이 원칙이다.

한 가지 짚을 점이 있다.

  • 확인 PaymentEntity의 markProcessing, markSucceeded, markFailed, markUnknown은 이전 상태를 검사하지 않고 상태를 덮어쓴다. CommerceOrderEntity.markPaid도 마찬가지다.
  • 미확인 그렇다면 “READY에서만 PROCESSING으로 갈 수 있다” 같은 규칙은 어디서 지켜질까? 애플리케이션 서비스의 조건문인지, 조건부 UPDATE인지, 아니면 비어 있는지는 18강(결제 승인)에서 코드로 확인한다. 위 DB 제약들은 최후의 방어선이지, 전이 규칙 전체를 대신하지는 않는다.

7. 값 객체: 문서에서는 “채택”, 코드에서는 없음

이번 강의에서 가장 중요한 발견이다.

확인 첫 MVP 도메인 설계(DOMAIN-001)는 값 객체 후보 다섯 개를 하나씩 따져, 두 개를 채택(Accepted) 했다.

후보 판단 이유
SubscriptionQuantity Accepted 1~10 범위를 생성 시점에 보장
DeliveryCycle Accepted 2·4·8주 검증과 날짜 계산 기간을 한 의미로 묶음
SubscriptionCreatedDate Deferred 추가 불변 조건이 없음
NextOrderScheduledDate Deferred 생성일과 주기에서 계산되는 파생 값, 별도 행위 없음
SubscriptionEligibility Deferred 저장 방식과 상태 모델 미정

판단 기준 자체가 훌륭하다. 해결하는 문제, 보장하는 불변 조건, 이점, 현재 단계의 복잡성을 나란히 놓고 결정했다. 4강의 YAGNI를 값 객체 단위로 적용한 것이다.

// subscription/domain/DeliverySchedulePolicy.java (현재)
public static LocalDate firstFutureDate(LocalDate scheduledDate, int cycleWeeks, LocalDate today) {
  LocalDate next = scheduledDate;
  do { next = next.plusWeeks(cycleWeeks); } while (!next.isAfter(today));
  return next;
}

4강에서 본 “장기 중단 뒤 오늘보다 미래인 첫 날짜로 건너뛰기” 규칙이 이 일곱 줄이다. 주석은 이 함수가 “조회, 잠금, 영속성과 독립적인 산술”이라고 밝힌다. **도메인 계층에 남은 것이 순수 계산뿐**이라는 점이 V2의 성격을 잘 보여 준다.

이 차이는 문제인가

해석 판단은 두 갈래로 나뉜다.

  • 문제가 아닌 이유:
    • 불변 조건 자체는 지켜지고 있다. 수량과 주기는 API 검증과 DB CHECK의 이중 방어를 받는다.
    • V2가 명시 SQL로 간 이상, 값 객체를 만들면 JDBC 매핑에서 매번 감싸고 푸는 비용이 생긴다.
    • 그리고 V2 신규 구독은 수량을 사용자가 고르지 않는다. 생성자의 this.quantity = 1이 보여 주듯 패키지 구성 수량이 PlanItem에 있다. SubscriptionQuantity가 지키려던 규칙이 도메인 자체에서 사라진 것이다.
  • 문제인 이유:
    • int cycleWeeks는 아무 정수나 받는다. firstFutureDate(date, 0, today)를 부르면 plusWeeks(0) 때문에 루프가 영원히 끝나지 않는다. 지금은 호출 전에 값이 검증돼 있어 실제로 일어나지 않지만, 함수 자체는 그 사실을 모른다.
    • 이것이 원시 타입 집착(primitive obsession)의 전형적 위험이다. 규칙이 타입에 있지 않고 호출자의 선의에 있다.

개선 제안 해석 가장 싼 개선은 주기만 값 객체로 만드는 것이다. 주기는 V2에서도 살아 있는 규칙이고, 날짜 계산이라는 행위를 가지기 때문이다.

java // 제안 예시 — 저장소에 없는 코드다 public record DeliveryCycle(int weeks) { public DeliveryCycle { if (weeks != 2 && weeks != 4 && weeks != 8) throw new IllegalArgumentException("배송 주기는 2·4·8주"); } public LocalDate firstFutureDate(LocalDate from, LocalDate today) { LocalDate next = from; do { next = next.plusWeeks(weeks); } while (!next.isAfter(today)); return next; } }

  • Java record는 불변이고, compact 생성자에서 검증하면 잘못된 값으로는 객체 자체를 만들 수 없다.
  • 저장소는 SQL에서 int를 읽어 new DeliveryCycle(weeks)로 감싸기만 하면 된다. 잠금과 SQL 구조는 건드리지 않는다.
  • 무한 루프 위험이 타입 수준에서 사라진다.

6강. ERD: 28개 마이그레이션이 그린 데이터 지도

이번 강의의 목표

  • 개념 → 논리 → 물리 모델링의 차이를 알고, PawCycle 문서와 코드가 각각 어느 단계인지 구분한다.
  • Flyway V1–V28이 쌓아 올린 약 60개 테이블의 지도를 그리고, 핵심 테이블 사이의 관계를 읽는다.
  • PK·FK·UNIQUE·CHECK·인덱스가 각각 어떤 업무 규칙을 지키는지 SQL로 읽는다. B-Tree 인덱스의 원리도 함께 본다.
  • 주문 테이블이 두 벌인 이유와 멱등성 테이블 네 종류의 차이를 이해한다.

1. 개념 → 논리 → 물리

데이터 모델링은 보통 세 단계로 나눈다. itwiki의 데이터 모델링 항목이 정리한 기준은 이렇다.

단계 질문 산출물 DBMS 종속
개념 업무에 어떤 핵심 개체와 관계가 있나 개념 ERD 아님
논리 식별자는 무엇이고, 정규화하면 어떤 구조가 되나 논리 ERD, 엔터티·속성 정의서 아님
물리 실제 DBMS에 어떤 테이블·타입·인덱스로 만드나 물리 ERD, DDL 맞음

PawCycle의 문서와 코드가 정확히 이 세 단계로 나뉜다.

  • 개념: DATA-001은 Member, Product, Sku, Subscription 네 개념과 “첫 MVP에 왜 필요한가”만 적는다. 그리고 “테이블명과 컬럼명은 후속 마이그레이션에서 최종 확정한다”고 못 박는다.
  • 논리: DATA-002는 논리 ERD 초안이다. 문서 상태도 Proposed다.
  • 물리: backend/src/main/resources/db/migration/V1__…sql ~ V28__…sql. 확인 1강에서 본 spring.jpa.hibernate.ddl-auto=validate 설정 때문에 JPA는 테이블을 만들지 않고 검사만 한다. 테이블의 유일한 원본은 Flyway 마이그레이션이다.

그래서 이 강의의 ERD는 문서가 아니라 마이그레이션 SQL에서 직접 뽑는다. 문서는 의도를, SQL은 사실을 말한다. 5강에서 배운 “문서 → 코드 → 이력” 대조 원칙 그대로다.

2. 핵심 테이블 지도

28개 마이그레이션이 만든 테이블은 약 60개다. 전부 한 그림에 넣으면 읽을 수 없으니, 구독과 주문·결제의 뼈대만 추렸다. mermaid 원문에서 렌더링한 ERD다.

ERD를 읽는 방법부터 짚자. 선 끝의 기호가 카디널리티(몇 대 몇인가)다.

  • || 정확히 하나, o| 0 또는 1, o{ 0 이상, |{ 1 이상
  • 예: orders ||--|{ order_items는 “주문 하나에 항목이 1개 이상”이다. orders ||--o{ payments는 “결제 시도가 0개 이상”이다. 5강에서 본 그대로다.

그림에서 눈에 띄는 것이 둘 있다.

  • subscription_schedules에서 주문 쪽으로 선이 두 개 나간다. subscription_orders(V9)와 subscription_order_context(V14)다. 이것이 6절의 “주문 모델 두 벌”이다.
  • subscriptions와 subscription_snapshots 사이에도 선이 두 개다.
    • 하나는 “구독이 여러 스냅샷을 쌓는다”(1:N, subscription_snapshots.subscription_id).
    • 다른 하나는 “구독이 그중 하나를 현재로 가리킨다”(subscriptions.current_snapshot_id).
    • 두 테이블이 서로를 참조한다. 그래서 V3는 스냅샷 테이블을 만든 뒤 ALTER TABLE subscriptions ADD CONSTRAINT ... FOREIGN KEY (current_snapshot_id)로 외래 키를 나중에 붙였다(4강 SQL). 순환 참조에서는 한쪽을 먼저 만들 수 없으니, 테이블을 다 만든 뒤 FK를 거는 것이 정석이다.

3. 마이그레이션 연대기: 데이터베이스도 버전 관리된다

확인 28개 마이그레이션을 묶으면 4강의 MVP 흐름과 그대로 겹친다.

구간 마이그레이션 생긴 것
MVP1 V1–V2 members, products, skus, subscriptions
MVP2 V3–V8 Pet·플랜·스냅샷·회차·pending·명령 이력, 멱등 테이블 2종과 completed_at
자동 주문 V9–V11 subscription_orders(+items), 자동화용 인덱스
MVP3 V12–V19 카테고리·RBAC, 재고·장바구니·쿠폰·멤버십, 공통 주문·결제, 배송·환불, 알림·감사 로그
MVP4 V20–V27 비즈니스 키, 리뷰·문의, 장바구니 버전·체크아웃 지문, 카탈로그 확장, 개인화 이벤트, 회차 추가 상품, 리뷰 요약
정리 V28 관리 플래그 이름 변경

이 중 V4 → V8 다섯 개가 마이그레이션 작성의 교과서적인 패턴을 보여 준다. 멱등 결과에 “완료 시각”을 추가해 30일 보관 정리를 가능하게 만든 과정이다(3강 PR #108).

-- V4 / V5: 컬럼을 NULL 허용으로 먼저 추가 (확장)
ALTER TABLE subscription_creation_idempotency_results ADD COLUMN completed_at DATETIME(6) NULL;

-- V6: 기존 행 채우기 (백필) — 고정된 한 시각을 변수로 잡는다
SET @v6_completed_at = UTC_TIMESTAMP(6);
UPDATE subscription_creation_idempotency_results
SET completed_at = @v6_completed_at
WHERE response_status BETWEEN 200 AND 299
  AND response_body IS NOT NULL
  AND completed_at IS NULL;

-- V7 / V8: 정리 작업이 쓸 인덱스 추가
CREATE INDEX idx_creation_idempotency_completed_at
    ON subscription_creation_idempotency_results (completed_at, member_id, idempotency_key);
  • 확장 → 백필 → 인덱스를 다른 파일로 나눈다. 원리 MySQL에서 ALTER TABLE, CREATE INDEX 같은 DDL은 암묵적으로 커밋된다. PostgreSQL과 달리 DDL을 트랜잭션으로 묶어 되돌릴 수 없다. 한 파일에 여러 DDL과 DML을 섞었다가 중간에 실패하면 앞부분만 반영된 어중간한 상태가 남는다. 파일을 나누면 Flyway 이력에 “어디까지 성공했는가”가 정확히 남는다.
  • NULL로 추가한다. 처음부터 NOT NULL로 추가하면 기존 행에 넣을 값이 필요하다. 그런데 기존 행의 “진짜 완료 시각”은 알 수 없다. 4강의 “기록하지 않은 사실은 복원할 수 없다”가 여기서도 나온다.
  • 백필 시각을 변수 하나로 고정한다. UTC_TIMESTAMP(6)를 행마다 부르는 대신 한 번 잡아 모든 행에 같은 값을 넣는다. 해석 “이 행들은 V6 시점에 일괄 백필됐다”는 사실이 데이터에 식별 가능하게 남는다. 보관 기간 계산도 백필 시점부터 30일로 일관된다.
  • 성공한 결과만 채운다. response_status BETWEEN 200 AND 299 AND response_body IS NOT NULL. 처리 중이던(응답이 아직 없는) 행에 완료 시각을 넣으면, 정리 작업이 진행 중인 요청의 멱등 기록을 지울 수 있다.
  • 이미 적용된 마이그레이션은 고치지 않는다. 원리 Flyway는 적용한 파일의 체크섬을 flyway_schema_history에 저장하고, 내용이 바뀌면 시작을 거부한다. 그래서 잘못을 고칠 때도 새 버전 파일을 추가한다. V19(0원 환불 허용), V28(이름 변경)이 그런 예다.

4. 제약 조건이 지키는 업무 규칙

4강과 5강에서 이미 여러 제약을 봤다. 복합 외래 키, PRIMARY KEY (subscription_id)로 pending 최대 하나, 생성 컬럼 UNIQUE가 그것이다. 이번에는 주문 테이블에서 두 가지를 더 본다. 둘 다 CHECK가 단순 범위 검사를 넘어 업무 규칙 자체를 표현하는 예다.

-- V14: orders — 금액 공식이 DB 제약이다
CONSTRAINT chk_orders_amounts CHECK (
  original_amount >= 0 AND discount_amount >= 0 AND shipping_fee >= 0 AND payment_amount >= 0
  AND payment_amount = original_amount - discount_amount + shipping_fee
)

-- V14: order_items — "완전한 스냅샷"이면 모든 스냅샷 컬럼이 있어야 한다
snapshot_quality VARCHAR(30) NOT NULL,
CONSTRAINT chk_order_items_snapshot CHECK (snapshot_quality IN ('FULL','LEGACY_PARTIAL')),
CONSTRAINT chk_order_items_full CHECK (
  (snapshot_quality = 'LEGACY_PARTIAL')
  OR (sku_code_snapshot IS NOT NULL AND product_name_snapshot IS NOT NULL
      AND sku_name_snapshot IS NOT NULL AND unit_price IS NOT NULL AND line_amount IS NOT NULL)
)
  • 금액 공식 CHECK. 결제 금액 = 원가 − 할인 + 배송비. 애플리케이션이 할인을 두 번 적용하는 버그를 내도, 공식이 안 맞는 주문은 저장 자체가 안 된다. 금액이 DECIMAL(18,2)인 것도 중요하다. 원리 DOUBLE은 이진 부동소수점이라 0.1 같은 값을 정확히 표현하지 못해, 등식 비교가 어긋날 수 있다. 돈은 항상 고정소수점(DECIMAL)이다.
  • 조건부 필수 컬럼. A OR B 형태로 “LEGACY_PARTIAL이 아니라면, 스냅샷 컬럼 다섯 개가 모두 있어야 한다”를 표현했다. 원리 논리식 P → Q(P이면 Q)는 NOT P OR Q와 같다. 이 CHECK가 바로 “FULL이면 → 전부 NOT NULL”이다.
  • 왜 LEGACY_PARTIAL이 있나. 6절에서 볼 V15 백필 때문이다. 옛 정기 주문에는 상품명과 단가 스냅샷이 원래 없었다. 없는 값을 지어내지 않고 “이 행은 불완전하다”는 사실을 품질 컬럼으로 기록했다. 4강의 MVP2 이행 원칙(“추측·반올림·절삭하지 않는다”)과 같은 태도다.

5. 인덱스: B-Tree와 컬럼 순서 (깊게)

인덱스를 이해하려면 먼저 그 모양을 알아야 한다. 향로(이동욱)의 「[mysql] 인덱스 정리 및 팁」은 인덱스를 한 줄로 요약한다. “인덱스 == 정렬”. 지정한 컬럼 순서대로 정렬된 목차를 만들어 두는 것이다. 그 목차의 실제 모양이 B-Tree다.

출처: 향로 · [mysql] 인덱스 정리 및 팁.

  • 탐색은 루트 → 브랜치 → 리프 → 데이터 순으로 내려간다. 그림의 예시는 (dept_no, emp_no) 두 컬럼 인덱스다. dept_no = 'd001' AND emp_no = 10018이면 루트와 브랜치를 거쳐 해당 리프 페이지 하나로 바로 간다.
  • 글의 핵심 문장은 이것이다. 두 번째 컬럼은 첫 번째 컬럼에 의존해 정렬돼 있다. 두 번째 컬럼의 순서는 첫 번째 컬럼 값이 같은 구간 안에서만 의미가 있다.
    • 그래서 첫 번째 컬럼 조건 없이 두 번째 컬럼만으로 찾으면, 정렬을 이용하지 못한다.
    • 이것을 가장 왼쪽 접두사 규칙(leftmost prefix)이라 한다.
  • InnoDB는 데이터를 16KB 페이지 단위로 관리한다. 그래서 키가 길수록 한 페이지에 들어가는 항목이 줄어 더 많은 페이지를 읽어야 한다. 5강에서 키 컬럼을 4바이트 utf8mb4 대신 1바이트 ascii로 둔 것이 여기서 이득이 된다.

이 원리로 PawCycle의 자동 주문 인덱스를 읽어 보자.

-- V11__index_due_subscription_schedules.sql
CREATE INDEX idx_schedules_due_automation
    ON subscription_schedules (status, scheduled_date, id, subscription_id);

자동 주문은 대략 “status = 'SCHEDULED'이고 scheduled_date <= 오늘인 회차를 오래된 순으로 N개”를 찾는다(4강).

  • ① status (등호 조건)가 맨 앞이다. 인덱스 안에서 SCHEDULED인 구간이 한 덩어리로 모여 있으니, 그 구간으로 바로 간다.
  • ② scheduled_date (범위 조건)가 그다음이다. 그 구간 안에서는 날짜순으로 정렬돼 있으니, <= 오늘까지 순서대로 읽기만 하면 된다. 결과도 이미 오래된 순이다.
    • 원리 등호 조건 컬럼을 범위 조건 컬럼보다 앞에 둔다가 복합 인덱스 설계의 기본 원칙이다. 순서가 반대인 (scheduled_date, status)라면 어떻게 될까? 날짜 범위 안에 SKIPPED, HELD, CANCELED 회차가 섞여 있어서, 범위 전체를 읽으며 상태를 걸러내야 한다.
  • ③ id, subscription_id가 뒤에 붙는다. 날짜가 같은 회차들의 순서를 id로 결정적으로 고정한다. 자동화가 “구독별 가장 오래된 회차 하나”를 고를 때 필요한 subscription_id도 인덱스에 들어 있다. 그래서 테이블 본문을 읽지 않고 인덱스만으로 후보를 고를 수 있다. 이것을 커버링 인덱스라 한다.

멱등 정리 인덱스 (completed_at, member_id, idempotency_key)도 같은 논리다. “completed_at이 30일 이전인 것”이라는 범위를 맨 앞에 두고, 그 뒤에 삭제할 행의 PK 컬럼을 붙였다.

  • 원리 사실 InnoDB의 보조 인덱스는 리프에 PK 값을 자동으로 함께 저장한다. 보조 인덱스로 찾은 뒤 PK로 본문(클러스터드 인덱스)을 다시 찾아가야 하기 때문이다. 그래서 member_id, idempotency_key를 명시하지 않아도 물리적으로는 들어간다.
  • 해석 그런데도 명시한 이유는 두 가지로 보인다. 정리 쿼리가 PK만 읽어 삭제 대상을 정한다는 의도를 스키마에 드러내고, 컬럼 순서를 확정하기 위해서다.

6. 주문 모델이 두 벌인 이유

이제 ERD의 가장 이상한 부분을 보자. 정기배송 회차 하나를 처리하면 주문 기록이 두 군데 생긴다.

  • 확인 subscription_orders(V9, 8/11): 자동 주문이 처음 만든 정기 주문 전용 테이블이다. 스냅샷 ID, 출처 PlanVersion, 예정일, 처리 시각, 금액을 담는다.
  • 확인 orders + order_items + subscription_order_context(V14, 8/13): MVP3의 공통 주문이다. 일반 구매(source = 'ONE_TIME')와 정기배송('SUBSCRIPTION')이 같은 주문·결제·배송·환불 흐름을 쓴다. 정기 주문이면 subscription_order_context가 어느 구독의 어느 회차인지 연결한다.

이틀 차이로 두 모델이 생긴 사정은 V15에 남아 있다.

-- V15__backfill_legacy_subscription_orders.sql (발췌)
INSERT INTO orders (order_number, member_id, source, status, original_amount, ...)
SELECT CONCAT('LEGACY-SUB-', legacy.id), legacy.member_id, 'SUBSCRIPTION', 'CREATED',
       legacy.package_total_krw, 0, 0, legacy.package_total_krw, legacy.processed_at
FROM subscription_orders legacy;
...
INSERT INTO order_items (order_id, sku_id, snapshot_quality, quantity)
SELECT context.order_id, legacy_item.sku_id, 'LEGACY_PARTIAL', legacy_item.quantity
FROM subscription_order_items legacy_item ...;
  • MVP3는 기존 정기 주문을 공통 주문으로 복사했다. 주문 번호는 LEGACY-SUB-{id}로 출처가 드러나게 했다.
  • 상품명·단가 스냅샷이 원래 없었으니 항목은 LEGACY_PARTIAL이다. 4절의 조건부 CHECK가 이 행들을 허용한다.

그런데 확인 그 뒤에도 옛 테이블은 사라지지 않았다. 지금 자동 주문 코드는 한 트랜잭션 안에서 두 곳에 모두 쓴다.

// subscription/automation/SubscriptionOrderProcessor.java (발췌)
if (orderExists(candidate.scheduleId())) {          // 옛 테이블로 "이미 처리됨" 판정
  return ProcessingOutcome.NO_OP;
}
...
long orderId =
    createCommonOrder(subscription, schedule, effectiveSnapshot, shipping, items, addOns);  // ① 공통 주문
persistence.insertSubscriptionOrder(                 // ② 옛 정기 주문
    subscription.memberId(), candidate.subscriptionId(), candidate.scheduleId(),
    effectiveSnapshotId, effectiveSnapshot.sourcePlanVersionId(), scheduledDate, ...);

왜 하나로 합치지 않았나.

  • 기록 백엔드 구조 문서에 실마리가 있다. 영속성 계층을 정리할 때 subscription_order_context를 매핑하는 엔티티로 subscription_orders를 대체하는 안을 검토했다. 그러나 “대체하면 처리 완료 판정(processed exclusion)이 바뀐다”는 이유로 하지 않았다.
  • 구독 영역의 여러 쿼리가 “이 회차에 subscription_orders 행이 있는가”로 처리 여부를 판단한다. 자동화 후보 조회, 대사, 회차 조회, 배송 알림이 그렇다. 그 기준을 바꾸면 3·4강의 “회차당 주문 하나” 보장을 처음부터 다시 검증해야 한다.
  • 구독 영속성 정리는 별도 승인 작업으로 미뤄졌다. 문서는 그 조건으로 “엔티티 애그리거트와 잠금 순서 테스트를 먼저 승인한다”를 건다.

이 이중 기록은 위험한가. 원리 분산 시스템에서 “두 곳에 쓰기”(dual write)는 악명 높은 문제다. DB와 메시지 큐처럼 서로 다른 저장소에 쓰면, 한쪽만 성공하고 다른 쪽이 실패하는 순간이 반드시 생긴다. 그런데 여기서는 두 테이블이 같은 MySQL, 같은 트랜잭션 안에 있다. 원자성이 보장되므로 그 고전적인 위험은 없다. 남는 비용은 이것들이다. 해석

  • 진실이 두 군데: “처리됐는가”를 구독 영역은 subscription_orders로, 커머스 영역은 orders로 본다. 지금은 같은 트랜잭션이라 일치하지만, 누군가 한쪽에만 쓰는 코드를 추가하면 조용히 갈라진다.
    • 그 마지막 방어선은 양쪽의 UNIQUE (schedule_id)다. 중복은 막지만 누락은 막지 못한다.
  • 저장과 이해 비용: 같은 사실을 두 번 저장하고, 새로 온 개발자는 “어느 쪽이 원본인가”를 매번 물어야 한다. 이번 강의에서 우리가 그랬듯이.

개선 방향 해석 한쪽으로 수렴하려면 순서가 중요하다. 1. 구독 영역의 처리 여부 판정을 subscription_order_context(또는 orders) 기준으로 바꾸는 쿼리를 만든다. 2. 두 기준이 같은 결과를 내는지 병행 비교 테스트를 둔다. 3. 그다음에야 subscription_orders 쓰기를 멈추고, 마지막에 테이블을 제거한다.

3절에서 본 확장 → 이전 → 축소(expand–contract) 패턴을 테이블 단위로 적용하는 것이다. 23강(자동 주문)과 33강(재설계)의 핵심 과제로 남긴다.

7. 멱등성 테이블 네 종류

3강에서 멱등성의 원리를, 4강에서 그것이 MVP마다 돌아온 과정을 봤다. 물리 스키마에서는 목적이 다른 네 테이블로 나타난다.

테이블 생긴 곳 PK (= 키의 범위) 무엇을 저장하나
subscription_creation_idempotency_results V3 (member_id, idempotency_key) 요청 지문, 응답 전체(상태·본문·Location·ETag), 완료 시각
subscription_command_idempotency_results V3 (member_id, subscription_id, command_type, idempotency_key) 요청 지문, 응답 전체, 완료 시각
checkout_idempotency_results V14 (+V22) (member_id, idempotency_key) 만들어진 주문·결제 ID, 요청 지문(V22에 추가)
quick_reorder_idempotency_results V22 (member_id, idempotency_key) 응답 JSON, 그 시점 장바구니 버전

표에서 읽어 낼 설계 포인트는 다음과 같다.

  • PK가 곧 “같은 요청”의 정의다.
    • 구독 명령은 PK에 subscription_id와 command_type이 들어간다. 그래서 같은 키를 다른 구독이나 다른 명령에 써도 충돌하지 않는다.
    • 5강에서 본 도메인 규칙(“다른 구독 또는 다른 명령 유형의 같은 키는 전역 충돌이 아니다”)이 PK 설계로 굳은 것이다.
    • 모든 PK에 member_id가 있다. 다른 회원의 키와는 절대 섞이지 않는다.
  • 응답을 저장할까, 참조를 저장할까.
    • 구독 테이블은 HTTP 응답을 통째로 저장한다. 재시도 때 그대로 돌려주면 된다. 대신 응답 형식이 바뀌면 옛 기록과 새 형식이 섞인다.
    • 체크아웃 테이블은 주문 ID와 결제 ID만 저장하고, 재시도 때 현재 상태로 응답을 다시 만든다. 결제 상태가 계속 변하니(READY → PROCESSING → …) 과거 응답을 그대로 주면 오히려 틀린다.
    • 해석 결과가 고정되는가, 계속 변하는가에 따라 저장 방식을 다르게 고른 것이다.
  • 응답 컬럼이 NULL 허용인 이유. 구독 테이블의 response_status, response_body는 NULL일 수 있다.
    • 해석 처리를 시작할 때 키와 지문을 먼저 예약해 두고, 끝나면 응답을 채우는 2단계 구조로 보인다. 응답이 아직 NULL인 행은 “처리 중”이라는 뜻이다. 3강의 토스페이먼츠 글이 말한 “앞 요청이 처리 중이면 409” 상황을 판정하는 근거가 된다.
    • 3절의 V6 백필이 응답이 있는 행만 채운 것도 같은 이유다.
    • 미확인 예약과 완료의 실제 코드 흐름은 22·25강에서 확인한다.
  • 체크아웃 지문은 나중에 들어왔다. V14에는 지문 컬럼이 없었다. V22가 request_fingerprint를 NULL 허용으로 추가했다. 그 전에 저장된 행에는 지문이 없으니 NULL로 둘 수밖에 없다. 3절의 “기존 행에 넣을 진짜 값이 없으면 NULL로 확장한다” 원칙 그대로다.
  • 왜 범용 테이블 하나로 합치지 않았나. 해석 (scope, key, payload) 형태의 범용 멱등 테이블 하나로 합칠 수도 있다. 하지만 네 테이블은 키의 범위, 저장 내용, 외래 키 대상(구독 vs 주문·결제)이 모두 다르다. 합치면 FK를 걸 수 없고, 범위 규칙이 문자열 scope 안으로 숨는다. 4강에서 자동 주문이 “HTTP 멱등 행 재사용”을 기각한 것과 같은 판단이다.

6강 정리

  • 개념 → 논리 → 물리: DATA-001(개념) → DATA-002(논리, Proposed) → Flyway V1–V28(물리, 유일한 원본). JPA는 validate로 검사만 한다.
  • 마이그레이션 원칙
    • 적용된 파일은 고치지 않고 새 버전을 추가한다.
    • MySQL DDL은 암묵 커밋되므로 확장 → 백필 → 인덱스를 파일로 나눈다.
    • 진짜 값이 없는 과거 행은 NULL이나 품질 표시(LEGACY_PARTIAL)로 정직하게 남긴다.
  • 제약이 곧 업무 규칙이다.
    • 금액 공식 CHECK, P → Q를 NOT P OR Q로 쓴 조건부 필수 CHECK
    • 돈은 DECIMAL
    • 순환 참조는 테이블을 만든 뒤 FK를 건다.
  • 인덱스 = 정렬된 B-Tree
    • 복합 인덱스는 등호 조건 → 범위 조건 → 정렬·커버링 컬럼 순으로 짠다.
    • InnoDB 보조 인덱스는 PK를 자동으로 품는다.
  • 주문 모델 두 벌: V9 subscription_orders(구독 영역의 처리 사실)와 V14 orders(커머스 공통 주문). 지금도 같은 트랜잭션에서 둘 다 쓴다. 원자성은 지켜지지만 진실이 두 군데다. 수렴은 expand–contract로 해야 한다.
  • 멱등성 테이블 네 종류: PK가 “같은 요청”의 범위를 정한다. 결과가 고정되면 응답을, 변하면 참조를 저장한다.

6강에서 남긴 미확인 항목

  • 멱등 예약(응답 NULL) → 완료로 가는 실제 코드와 409 처리(22·25강)
  • subscription_orders와 orders가 실제로 어긋난 사례가 있었는지, 일치를 검사하는 테스트가 있는지(23강)
  • V11 인덱스를 자동화 쿼리가 실제로 타는지: EXPLAIN 확인은 실험 단계 후보
