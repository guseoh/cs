카드 01 · 결제사 예외와 요청 ID를 로그로 남기기

항목 내용
상태 대기
등급 일반
묶는 항목 D-01, O-06, C-30, C-31
선행 없음(가장 먼저)

문제

  • 결제 승인·대사·정기결제·환불이 결제사 호출의 RuntimeException을 잡아 UNKNOWN으로만 기록한다. 네 클래스 모두 로거가 없다.
  • 위치: PaymentApplicationService:73, PaymentReconciliationService:93·121, SubscriptionBillingProcessor:96, RefundService:67·122
  • RequestCorrelationFilter가 MDC에 requestId를 넣지만 로그 패턴이 없어 출력되지 않는다. 응답 헤더로도 돌려주지 않는다.
  • 로거를 가진 파일은 666개 중 12개다.

완료 조건

  • 위 여섯 곳이 예외 종류·결제 ID·주문 ID를 WARN 이상으로 남긴다. 결제 키·카드 정보 같은 민감 값은 남기지 않는다.
  • 로그 패턴에 requestId가 찍히고, 응답에 X-Request-ID가 있다.
  • AI 폴백(RecommendationService:80, ReviewSummaryService, ProductComparisonService)도 폴백 사유를 남긴다.

범위·제외: 동작은 바꾸지 않는다. UNKNOWN 판정 규칙은 카드 06에서 다룬다.

검증: 가짜 결제사가 예외를 던지는 테스트에서 로그 이벤트와 MDC 값을 단언한다. 응답 헤더 테스트를 추가한다.

카드 02 · 시간 바인딩 단일화와 시간대 독립 테스트

항목 내용
상태 대기
등급 고위험(데이터 기록 경로)
묶는 항목 D-02, C-09, C-10, BL-B-07
선행 03(시간 관련 특성 테스트)

문제

  • JPA는 hibernate.jdbc.time_zone=UTC로, 네이티브·QueryDSL은 JVM 기본 시간대로 시간을 바인딩한다. 그 차이를 PaymentPersistenceQueries.jdbcTime과 SubscriptionJdbcTime.forUtcCalendar가 ZoneId.systemDefault()로 보정한다.
  • BillingRecoveryPersistenceParityIntegrationTests의 4개가 KST에서 9시간 차이로 실패하고, UTC에서 통과한다.
  • *TimestampJdbcType 10개가 같은 구조로 복제되어 있다. ZoneId.of("Asia/Seoul")이 13곳에 하드코딩되어 있다.

완료 조건

  • 모든 쓰기 경로가 같은 방식으로 UTC를 바인딩한다. MySQL 드라이버의 connectionTimeZone·preserveInstants 설정 또는 공용 JdbcType 하나로 통일한다.
  • systemDefault() 보정 함수 두 개를 없앤다.
  • 백엔드 전체 테스트가 user.timezone=Asia/Seoul과 UTC 양쪽에서 통과한다. CI에 시간대를 바꾼 실행을 하나 추가한다.
  • 업무 날짜 계산은 공용 BusinessCalendar 하나를 쓴다.

범위·제외: DB 컬럼 형식(UTC DATETIME)은 바꾸지 않는다. 데이터 이행이 없다.

검증: 두 시간대의 전체 테스트. 운영 데이터와 같은 저장 값이 나오는지 특성 테스트로 확인한다.

완료 조건

  • 33-2 표의 흐름(체크아웃, 승인 성공·실패·무응답, 대사, 정기 회차, 정기결제, 멱등 재생)마다 응답 + DB 상태 스냅숏 특성 테스트가 있다.

검증: 특성 테스트가 현재 main에서 모두 통과하고, 의도적으로 동작을 바꾼 임시 변경에서 실패하는지 확인한다.

카드 04 · 상태 enum과 전이 표 도입

항목 내용
상태 대기
등급 일반
묶는 항목 C-01, M-07
선행 03

문제: 상태가 문자열 리터럴로 흩어져 있다("UNKNOWN" 33, "ACTIVE" 24, "SUCCEEDED" 23 …). 결제·주문·구독 상태 enum이 없고, CANCELED와 CANCELLED 철자가 섞여 있다.

완료 조건

  • DB CHECK 제약의 값과 같은 이름으로 enum을 만든다. 대상은 결제, 주문, 회차, 쿠폰, 배송, 취소·반품, 정기결제 시도다.
  • 허용 전이를 enum 안의 표로 둔다.
  • 조건부 UPDATE의 상태 조건을 enum에서 만든다.
  • 새 코드에서 상태 문자열 리터럴을 쓰면 빌드가 실패한다(ArchUnit 또는 정적 검사, 기존 위반은 동결).

범위·제외: DB 값과 migration은 바꾸지 않는다.

검증: 특성 테스트 무변경. SELECT DISTINCT status로 실제 값과 enum을 대조한다.

카드 05 · 도메인 예외와 HTTP 매핑 분리, 예외 처리기 통합

항목 내용
상태 대기
등급 일반
묶는 항목 C-02, C-06
선행 03

문제: 애플리케이션 계층이 new CommerceException(409, …)처럼 HTTP 숫자를 69곳에서 던진다. @RestControllerAdvice가 13개로 흩어져 있다.

완료 조건

  • CommerceError(코드 + 범주)로 예외를 표현한다. HTTP 숫자는 웹 계층 한 곳에서 매핑한다.
  • 응답 JSON의 code 문자열과 형식은 그대로 둔다(프론트 보호 계약).
  • 예외 처리기를 공통 하나 + 모듈별 코드 등록으로 정리한다.

검증: 응답 스냅숏 특성 테스트 무변경. 배치 경로에서 범주로 분기하는 테스트를 추가한다.

카드 13 · 멱등 공용 구조와 정리 트리거

항목 내용
상태 대기
등급 일반
묶는 항목 D-20, C-07
선행 03

문제: 멱등 테이블 네 개가 같은 절차를 따로 구현한다. 구독 쪽 정리 코드는 런타임 트리거가 없고, 체크아웃·빠른 재주문은 정리 정책 자체가 없다. 위임만 하는 파사드가 있다.

완료 조건: IdempotencyStore(예약 → 재생/충돌/신규 → 완료) 하나로 네 경로를 처리한다. 범위마다 보관 기간과 정리 배치를 정의하고, 정리 스케줄러가 실제로 돈다. 지문 계산 방식과 "첫 성공 + N일, 재생으로 연장하지 않음" 규칙은 유지한다.

검증: 재생·충돌 특성 테스트 무변경. 재생과 정리가 경쟁하는 두 순서의 테스트를 유지한다.

카드 14 · 스케줄러 스레드 구성 확인과 분리

항목 내용
상태 대기
등급 일반
묶는 항목 D-05
선행 01

검증: 정기 주문 대량 처리 중에 체크아웃 만료가 지연되지 않는 통합 테스트 또는 측정.

카드 18 · 모듈 경계 규칙 도입(위반 동결)

항목 내용
상태 대기
등급 일반
묶는 항목 C-05, C-08, C-12
