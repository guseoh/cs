16강. 장바구니·찜·재주문: "아직 사지 않은 것"을 어떻게 다루는가

장바구니, 찜, 빠른 재주문은 결제 전 단계라서 가볍게 보인다. 하지만 이 프로젝트에서는 이 단계의 설계가 다음 강의(체크아웃·결제)의 안전장치가 된다. 이번 강의는 질문 세 개를 따라간다.

  • 장바구니는 무엇을 보장하고, 무엇을 보장하지 않는가? 재고는 잡지 않는다. 대신 "내용이 바뀌었다"는 사실을 버전 번호로 남긴다.
  • 아직 없는 행을 동시에 만들려 할 때 어떻게 막는가? 부모 행(회원)을 먼저 잠근다.
  • "이전 주문 다시 담기" 버튼을 두 번 눌러도 한 번만 담기게 하려면? Idempotency-Key와 저장된 응답을 쓴다.

1. 테이블 세 개로 보는 경계

CREATE TABLE carts (
    id BIGINT NOT NULL AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    created_at DATETIME(6) NOT NULL, updated_at DATETIME(6) NOT NULL,
    CONSTRAINT uk_carts_member UNIQUE (member_id),          -- ① 회원당 장바구니 하나
    ...);
-- V22: ALTER TABLE carts ADD COLUMN version BIGINT NOT NULL DEFAULT 0, CHECK (version >= 0)  -- ② 내용 버전

CREATE TABLE cart_items (
    cart_id BIGINT NOT NULL, sku_id BIGINT NOT NULL, quantity INT NOT NULL,
    CONSTRAINT pk_cart_items PRIMARY KEY (cart_id, sku_id),   -- ③ 같은 SKU는 한 줄
    CONSTRAINT chk_cart_items_quantity_positive CHECK (quantity > 0), ...);

CREATE TABLE wishlist_items (
    member_id BIGINT NOT NULL, product_id BIGINT NOT NULL, created_at DATETIME(6) NOT NULL,
    CONSTRAINT pk_wishlist_items PRIMARY KEY (member_id, product_id), ...);   -- ④ 찜은 상품 단위
  • ① UNIQUE(member_id): 동시에 두 요청이 장바구니를 만들어도 DB가 하나만 허락한다. 마지막 방어선이다. 확인
  • ② version: JPA의 @Version이 아니다. 직접 올리는 내용 버전 번호다. 3절에서 자세히 본다. 확인
  • ③ 복합 PK (cart_id, sku_id): 같은 SKU를 또 담으면 새 줄이 아니라 수량이 더해진다. 대리 키(id) 없이 자연 키를 PK로 썼다. 그래서 "같은 SKU 두 줄"이라는 잘못된 상태가 스키마상 불가능하다. 원리
  • ④ 찜은 product_id, 장바구니는 sku_id: 찜은 "이 상품이 마음에 든다"이고, 장바구니는 "이 옵션(사이즈·맛)을 몇 개 산다"이다. 도메인의 단위가 다르다. 해석

장바구니에 재고나 가격을 저장하는 컬럼은 없다. 장바구니는 "사고 싶다는 의도"일 뿐이다. 재고 확인과 가격 확정은 체크아웃(17강)이 잠금을 걸고 다시 한다. 장바구니에 담을 때 재고를 잡으면, 사지 않고 떠난 사용자가 재고를 묶어 둔다. 그래서 그 방식을 택하지 않았다 해석.

2. 담기 — 아직 없는 장바구니를 동시에 만들려 할 때

CartApplicationService.add(CartApplicationService.java)는 두 줄이다.

@Transactional
public void add(long memberId, long skuId, int quantity) {
  if (!cart.isPurchasable(skuId))                                   // ① 판매 중인 SKU인가
    throw new CommerceException(409, "SKU_NOT_PURCHASABLE", "구매할 수 없는 SKU입니다.");
  cart.add(cart.lockForAdd(memberId), skuId, quantity);              // ② 잠그고 → 담기
}

진짜 내용은 CartPersistenceAdapter.lockForAdd(CartPersistenceAdapter.java)에 있다.

public CartLock lockForAdd(long memberId) {
  Member member = members.findByIdForUpdate(memberId)                // ① 회원 행부터 잠근다
      .orElseThrow(() -> new CommerceException(404, "MEMBER_NOT_FOUND", ...));
  CartEntity cart = carts.findByMemberIdForUpdate(memberId)          // ② 장바구니 행 잠금
      .orElseGet(() -> carts.saveAndFlush(new CartEntity(member.getId(), now())));  // ③ 없으면 즉시 INSERT
  return new CartLock(cart.getId(), cart.getVersion());
}

왜 장바구니를 담는데 회원 행을 잠그나? 첫 담기 때는 잠글 장바구니 행이 아직 없기 때문이다. 없는 행에 SELECT ... FOR UPDATE를 하면 InnoDB는 그 자리의 갭 락을 건다(15강 3-5). 갭 락끼리는 서로 막지 않으므로 두 트랜잭션이 동시에 갭 락을 쥘 수 있다. 그다음 각자 INSERT하려고 하면 INSERT INTENTION 락이 필요한데, 이 락은 상대의 갭 락에 막힌다. 서로가 서로를 기다리니 교착 상태(deadlock)다.

  • 회원 행은 항상 존재한다. 그래서 그 행의 레코드 락은 "줄 세우기 표"처럼 동작한다. 같은 회원의 요청은 이 줄에서 한 명씩 지나간다. 존재하는 부모 행을 잠가서, 아직 없는 자식 행의 생성을 직렬화하는 패턴이다. 원리
  • InnoDB의 교착 탐지기는 사이클을 발견하면 한쪽을 롤백시킨다. 그래서 왼쪽 상황이 데이터를 망가뜨리지는 않는다. 다만 사용자에게 500 오류가 나간다. 원리
  • ③ saveAndFlush: 생성 직후 INSERT를 바로 DB로 보낸다. 그래야 cart.getId()(IDENTITY 키)를 얻을 수 있고, 이후 같은 트랜잭션의 쿼리가 이 행을 본다(10강의 flush 타이밍 이야기).
  • 잠금 순서는 회원 → 장바구니 → 장바구니 항목이다. 결제 대사가 장바구니를 소비할 때도 장바구니 → 항목 순서로 잠근다(#414·PR #415). 모든 경로가 같은 순서로 잠가야 서로 엇갈려 교착되지 않는다. 14강의 "카테고리를 PK 오름차순으로 잠근다"와 같은 원리다.

이 프로젝트는 같은 교착을 실제로 겪었다. 체크아웃의 멱등성 결과를 조회할 때 없는 행을 FOR UPDATE로 잠그다가, 서로 다른 회원의 요청끼리 교착된 것이다(#331). 로컬 MySQL 8.4.10에서 PRIMARY 인덱스의 supremum(맨 끝) 갭 X 락을 서로 쥔 채 상대의 INSERT INTENTION을 기다리는 사이클이 deadlock 그래프로 재현됐다. PR #332는 그 조회의 잠금만 제거했다. 기록 회원 행 잠금은 같은 회원의 요청만 줄 세운다. 다른 회원끼리 같은 갭을 공유하는 경우는 막지 못한다는 점이 이 사건의 교훈이다. 6절에서 다시 나온다.

개선점 해석

  • 수량 상한이 없다. @Positive만 검사하고, increase()는 this.quantity += quantity다. 큰 값을 여러 번 담으면 int가 넘쳐(overflow) 음수가 될 수 있다. 그러면 DB의 CHECK (quantity > 0) 위반으로 500 오류가 난다. DB가 잘못된 데이터를 막아 주긴 하지만, 사용자에게는 400이 맞다. @Max와 Math.addExact를 함께 쓰는 것이 좋다.
  • 담기는 재고를 보지 않는데, 빠른 재주문은 재고 부족을 건너뛴다(6절). 두 진입점의 정책이 다르다. 의도된 차이일 수도 있다(직접 담기는 재입고를 기다리는 장바구니를 허용). 그래도 설명해 둘 지점이다.
  • isPurchasable 확인은 잠금 전에 한다. 그 사이 상품이 비공개가 될 수 있지만(TOCTOU), 장바구니는 의도일 뿐이고 체크아웃이 잠금을 걸고 다시 검사하므로 허용 가능한 틈이다.

3. 장바구니 version — "내가 본 그 장바구니로 결제하는가"

carts.version은 왜 필요할까? 결제 버튼을 누른 순간과, 사용자가 화면에서 장바구니를 본 순간 사이에 장바구니가 바뀔 수 있기 때문이다.

체크아웃 코드에서 이 비교가 일어난다(CheckoutApplicationService.java:53-69).

CartPersistenceAdapter.CartLock cartLock = cart.lockForAdd(memberId);     // 장바구니 담기와 같은 잠금 경로
...
if (requestedCartVersion != null && requestedCartVersion != cartLock.version()) {
  throw new CommerceException(409, "CART_CHANGED", "장바구니가 변경되었습니다.");
}

이것은 낙관적 동시성 제어(optimistic concurrency control)의 한 형태다. 클라이언트가 "내가 본 버전"을 들고 오고, 서버는 잠근 상태에서 현재 버전과 비교한다. JPA @Version과 무엇이 다른지가 면접 포인트다.

JPA @Version PawCycle carts.version
언제 오르나 그 엔티티(행)가 UPDATE될 때마다 자동 장바구니 내용(항목 추가·수량 변경·삭제)이 실제로 바뀔 때 코드가 직접
무엇을 보호하나 같은 행의 lost update(10강) "사용자가 화면에서 본 장바구니 = 결제할 장바구니"
충돌 시점 flush 때 UPDATE ... WHERE version=?가 0행 → 예외 체크아웃 시작 시 비교 → 409
자식 변경 반영 cart_items가 바뀌어도 carts 행은 그대로라 버전 불변 항목 변경이 장바구니 버전을 올림

마지막 줄이 @Version을 쓰지 않은 이유다 해석. 장바구니의 "내용"은 cart_items에 있다. carts 행 자체는 거의 바뀌지 않는다. 그래서 집합(aggregate) 전체의 변경을 루트의 숫자 하나로 나타내도록, 직접 관리하는 버전을 두었다.

4-1. 9시간 버그 — LocalDateTime은 "시각"이 아니다 원리

찜과 장바구니의 시각 저장 방식에는 사건이 있다(#448 → PR #451). 먼저 CS 개념부터 정리한다.

  • Instant: 1970-01-01T00:00Z부터 흐른 나노초다. 지구상 어디서나 같은 한 순간이다.
  • LocalDateTime: "2026-11-13 18:00"이라는 벽시계 글자다. 어느 시간대의 18시인지 모른다.
  • MySQL DATETIME(6): 역시 시간대 없는 벽시계 글자다. TIMESTAMP는 저장할 때 세션 시간대 → UTC로 바꾸고, 읽을 때 되돌린다. 그런데 DATETIME은 아무 변환 없이 글자 그대로 저장한다.

그래서 쓰는 쪽과 읽는 쪽이 "이 글자가 어느 시간대 기준인지"를 같은 규칙으로 약속해야 한다. 버그는 이 약속이 어긋나서 생겼다. 기록

단계 버그가 있던 흐름 수정 후 흐름
실제 순간 한국 시각 18:00 (= 09:00Z) 같음
쓰기 Asia/Seoul Clock의 LocalDateTime → '18:00' 저장 LocalDateTime.ofInstant(clock.instant(), UTC) → '09:00' 저장
읽기 '18:00'을 UTC로 해석 → 18:00Z '09:00'을 UTC로 해석 → 09:00Z
화면(KST) 다음 날 03:00 → +9시간 오류 18:00 ✓

  • 기존 행은 고치지 않았다. 이미 '18:00'(서울 기준)으로 저장된 옛 행은 이제 UTC로 읽혀 화면에서 9시간 밀려 보인다. 2026-10-22에 사용자가 이 표시 변화를 승인된 대가로 선택했다. 기록 기각된 대안은 다음과 같다.
    • 옛 행 전체에 SQL로 −9시간 보정: 각 행을 누가 어떤 시간대로 썼는지 기록이 없다. 이미 UTC로 쓴 행까지 잘못 고칠 위험이 있다.
    • 날짜·패턴으로 옛 행과 새 행을 추정 분류: 잘못 변환할 위험이 있다.
    • 전역 Clock이나 Hibernate 시간대 변경: 결제·재고 같은 다른 경로의 시간 의미까지 바뀐다.
  • 이 결정은 추천의 기간 경계와도 맞물린다. 30일 인기는 UTC 기준 롤링 윈도우로, 최근/이전 7일 추세는 서울 달력의 자정 기준으로 계산한다. "하루"의 경계는 사람이 사는 시간대에 따라 다르기 때문이다. 기록

6. 재구매 시기 알림 — 중앙값을 쓴 이유

GET /api/.../recommendations/reorder-timing은 단건 구매 이력으로 "곧 다시 살 때"를 알려 준다(RepeatPurchaseApplicationService). 확인

  • 상품별로 최근 구매일을 최대 5개 모은다. 3개 미만이면 건너뛴다. 구매 간격이 최소 2개는 있어야 주기를 말할 수 있기 때문이다.
  • 간격들의 중앙값을 마지막 구매일에 더해 예상일을 구한다. 예상일이 오늘+7일 이내면 노출하고, 지났으면 OVERDUE, 아니면 DUE_SOON이다.
  • "오늘"은 Asia/Seoul 기준 날짜다. 4절과 같은 이유로, 사람의 하루 경계는 서울 달력을 따른다.
  • 왜 평균이 아니라 중앙값인가 해석: 간격이 30, 31, 29, 90일(한 번 깜빡함)이라면 평균은 45일로 끌려가지만 중앙값은 30.5일이다. 이상값(outlier)에 강하다. 짝수 개일 때 두 값의 평균을 long 나눗셈으로 내므로 0.5일은 버려진다.

17강. 체크아웃: 결제 직전의 약속을 한 트랜잭션으로 만든다

체크아웃은 "결제하기" 버튼을 눌렀을 때 실행된다. 돈은 아직 오가지 않는다. 결제 승인은 18강에서 다룬다. 이 단계의 일은 결제창을 띄우기 전에 서버가 지킬 약속을 DB에 확정하는 것이다.

  • 이 가격과 이 배송지로 주문서(Order, PAYMENT_PENDING)를 만든다.
  • 결제 대기 건(Payment, READY, 30분 후 만료)을 만든다.
  • 그동안 남이 사 가지 못하도록 재고를 예약하고, 쿠폰을 예약한다.
  • 같은 요청이 다시 와도 하나만 생기도록 멱등성 결과를 남긴다.

이 모든 것이 CheckoutApplicationService.checkout(CheckoutApplicationService.java) 안의 TransactionTemplate 한 번으로 일어난다. 중간에 하나라도 실패하면 전부 없던 일이 된다. 먼저 전체 순서와, 각 단계가 무엇을 잠그는지 보자.

여기서 눈여겨볼 점이 하나 있다. 체크아웃은 장바구니를 비우지 않는다. 결제가 실패하거나 30분 안에 결제하지 않으면 사용자는 장바구니를 그대로 다시 써야 하기 때문이다. 장바구니는 결제 성공이 확정되는 대사 단계에서 주문 수량만큼 차감된다. 이때 16강에서 본 "version 정확히 +1" 규칙이 적용된다. 확인·기록

3. 쿠폰 할인 — BigDecimal과 내림

public static BigDecimal discount(BigDecimal original, BigDecimal minimum,
    String type, BigDecimal value, BigDecimal maximum) {
  if (original.compareTo(minimum) < 0)                              // 최소 주문 금액
    throw new CommerceException(409, "COUPON_MINIMUM_ORDER", ...);
  BigDecimal discount = "PERCENTAGE".equals(type)
      ? original.multiply(value).divide(BigDecimal.valueOf(100), 0, RoundingMode.DOWN)  // 원 단위 내림
      : value;                                                       // 정액
  if (maximum != null) discount = discount.min(maximum);            // 최대 할인 한도
  return discount.min(original);                                    // 결제 금액이 음수가 되지 않게
}
  • BigDecimal을 쓰는 이유 원리: double은 2진 부동소수점이라 0.1을 정확히 표현하지 못한다(0.1 + 0.2 = 0.30000000000000004). 돈 계산에서는 1원 오차도 정산 불일치다. DB 컬럼도 DECIMAL(18,2)다.
  • RoundingMode.DOWN: 15% 할인에서 12,345원 → 1,851.75원 → 1,851원이다. 할인을 내려 깎으므로 회사가 1원 덜 깎아 준다. 반올림 규칙은 정책이다. 그래서 이 메서드처럼 한곳에 모아야 화면과 주문, 환불이 같은 숫자를 낸다. 해석
  • 할인 후 금액이 100원 미만이면 409다(PAYMENT_AMOUNT_TOO_LOW). PG의 최소 결제 금액과 맞춘 값으로 보이지만, 근거 문서는 확인하지 못했다. 미확인
  • 쿠폰 잠금 순서는 member_coupons(내 쿠폰) FOR UPDATE → coupons(쿠폰 정의) FOR UPDATE다. 예약은 UPDATE ... SET status='RESERVED' WHERE status='AVAILABLE'처럼 상태 조건을 건 UPDATE로 한다. 결제가 성공하면 USED, 만료되면 AVAILABLE로 돌아간다. 확인 21강에서 다시 본다.
    • 사소한 관찰 해석: reserveCoupon은 reserveIfAvailable의 반환값(갱신된 행 수)을 확인하지 않는다. 바로 앞에서 잠그고 AVAILABLE을 확인했으니 실제로는 1이다. 하지만 재고 예약처럼 != 1이면 실패시키는 편이 방어적이다.

4. 재고 예약 — 비관적 잠금과 버전 CAS를 둘 다 쓴다

재고는 숫자 두 개로 관리한다(inventories).

  • available_quantity: 지금 팔 수 있는 수량
  • reserved_quantity: 결제를 기다리며 묶여 있는 수량
  • 둘 다 CHECK (>= 0)이고, version이 있다.

이 두 숫자가 사건마다 어떻게 움직이는지가 재고 모델의 전부다.

  • 예약 시점이 결제 전이다. 결제를 마친 뒤에 재고를 빼면, 마지막 1개를 두 사람이 동시에 결제했을 때 늦은 사람은 돈이 빠져나간 뒤에야 "재고 없음"을 듣는다. 그러면 자동 환불을 해야 한다. 결제 전에 예약하면 늦은 사람은 결제창을 띄우기 전에 409를 받는다. 대가는 "결제하지 않고 떠난 사람이 30분 동안 재고를 묶는다"는 점이고, 5절의 만료가 이를 푼다. 원리·해석
  • 모든 이동은 inventory_movements에 직전·직후 숫자와 함께 한 줄씩 남는다. 그리고 UNIQUE (payment_id, type, sku_id)가 있다. 같은 결제가 같은 SKU를 두 번 RESERVE하거나 두 번 DEDUCT하는 것을 DB가 막는다. 재고 숫자는 "결과"이고, movement는 그 결과를 설명하는 "원장(ledger)"이다. 확인

@Service
@Transactional(propagation = Propagation.MANDATORY)      // ① 혼자서는 실행 불가
public class InventoryService {
  public void reserve(long skuId, int quantity, long paymentId) {
    InventoryEntity inventory = inventories.findLockedBySkuId(skuId).orElse(null);   // ② FOR UPDATE
    if (inventory == null || inventory.availableQuantity() < quantity)
      throw new CommerceException(409, "INVENTORY_INSUFFICIENT", "재고가 부족합니다.");
    int changed = inventories.reserveIfVersionMatches(skuId, quantity, inventory.version());  // ③ CAS
    if (changed != 1) throw new CommerceException(409, "INVENTORY_CONFLICT", "재고가 변경되었습니다.");
    movements.save(InventoryMovementEntity.payment(skuId, paymentId, "RESERVE", ...));         // ④ 원장
  }
}

-- ③ reserveIfVersionMatches
UPDATE inventories
SET available_quantity = available_quantity - :quantity,
    reserved_quantity  = reserved_quantity  + :quantity,
    version = version + 1
WHERE sku_id = :skuId
  AND version = :expectedVersion          -- 내가 읽은 그 버전일 때만
  AND available_quantity >= :quantity     -- 그리고 여전히 충분할 때만
  • ① Propagation.MANDATORY: 바깥 트랜잭션이 없으면 예외를 던진다. 재고 변경은 반드시 주문·결제 생성과 같은 커밋에 묶여야 하기 때문이다. 재고만 따로 커밋되면 "주문은 롤백됐는데 재고는 빠진" 상태가 생긴다. 5강의 전파 속성을 "실수를 막는 계약"으로 쓴 사례다. 원리
  • ② 비관적 잠금: 같은 SKU를 사는 다른 체크아웃은 여기서 줄을 선다.
  • ③ 조건부 UPDATE(CAS, Compare-And-Swap): 이미 잠갔는데 왜 버전 조건까지 거나? 최종 방어막이다. 잠금이 누락된 경로가 생기거나 잠금 범위가 바뀌어도, 버전과 available >= quantity 조건이 음수 재고와 lost update를 막는다. DB의 CHECK (available_quantity >= 0)이 그 뒤의 세 번째 방어선이다. 해석
  • 이 UPDATE는 @Modifying(flushAutomatically = true, clearAutomatically = true)다. 실행 전에 대기 중인 변경을 flush하고, 실행 후 영속성 컨텍스트를 비운다. 벌크 UPDATE는 1차 캐시를 거치지 않으므로, 캐시에 남은 옛 InventoryEntity(옛 수량)를 다시 쓰지 않으려는 것이다. 그래서 이 호출 뒤에는 앞서 읽은 엔티티가 모두 준영속(detached)이 된다. 체크아웃이 그 뒤에 persist나 쿼리만 하는 이유이기도 하다. 원리·해석

18강. 결제 승인: 돈이 오가는 순간, 트랜잭션은 어디서 끊어야 하는가

17강의 체크아웃이 결제 대기 건(Payment READY)을 만들었다. 이번 강의는 사용자가 결제창에서 카드 인증을 마친 뒤, 서버가 결제사(PG, 여기서는 토스페이먼츠)에 "이 결제를 승인하라"고 요청하고 그 결과를 DB에 반영하는 과정을 다룬다.

이 단계가 어려운 이유는 하나다. 외부 결제사의 승인과 우리 DB의 커밋은 하나의 원자적 작업으로 묶을 수 없다. 결제사에 돈을 빼라고 요청한 뒤 우리 서버가 죽으면, "돈은 나갔는데 주문은 결제 대기"인 상태가 남는다. 이 강의의 모든 설계는 그 틈을 어떻게 다루는지에 대한 이야기다.

먼저 프론트엔드부터 DB까지의 전체 흐름을 보자.

3. 결제사 호출 — "응답이 없다"는 "실패했다"가 아니다

TX1이 커밋된 뒤, DB 커넥션 없이 토스 승인 API를 부른다. 결과는 세 갈래로 나뉜다. 여기서 결제의 상태 기계를 먼저 그려 보자.

(그림 아래쪽 점선은 UNKNOWN에서 READY로 되돌아가 재승인하는 경로가 없다는 뜻이다.)

어댑터(TossTestPaymentAdapter, TossTestPaymentAdapter.java)가 응답을 이렇게 나눈다. 확인

결제사 응답 어댑터 결과 이유
2xx + status=DONE SUCCEEDED 승인 완료
2xx + CANCELED/ABORTED FAILED 확정 실패
2xx + 그 밖의 상태 UNKNOWN 진행 중일 수 있음
4xx FAILED (응답의 code 보관) 결제사가 요청을 거절함(카드 한도 등)
5xx, 타임아웃, I/O 오류, 인터럽트 예외 → 서비스가 UNKNOWN 처리 결과를 모름

왜 타임아웃이 실패가 아니라 "모름"인가 원리. 네트워크에서 응답을 못 받은 경우는 세 가지가 섞여 있다.

  1. 요청이 결제사에 도착하지 못했다.
  2. 도착해서 승인되었는데 응답이 돌아오다 끊겼다.
  3. 결제사가 아직 처리 중이다.

클라이언트는 이 셋을 구분할 수 없다. 분산 시스템의 "두 장군 문제"와 같은 구조다. 여기서 FAILED로 단정하고 재고를 풀면, 2번 경우 돈은 빠져나갔는데 재고는 남에게 팔리는 최악의 결과가 된다. 그렇다고 바로 승인을 다시 요청하면 이중 승인 위험이 있다. 그래서 UNKNOWN으로 표시하고 예약을 유지한 채, 조회 API로 결과를 확인하는 대사(19강)에 넘긴다.

  • 타임아웃 10초: HttpClient의 connectTimeout과 요청별 timeout이 모두 10초다. 15강의 AI 요약 클라이언트와 달리 타임아웃을 명시했다. 결제 응답을 무한정 기다리면 Tomcat 워커 스레드가 묶이기 때문이다. 확인·원리
  • InterruptedException 처리: Thread.currentThread().interrupt()로 인터럽트 플래그를 복원한 뒤 UNKNOWN 처리한다. 인터럽트를 삼키면 스레드를 종료하려는 상위 코드(서버 종료 등)가 신호를 잃는다. 자바 동시성의 기본 예절이다. 원리
  • 비밀키 보호: test_sk_로 시작하지 않는 키로는 빈 생성 자체가 실패한다. 실수로 라이브 키를 넣어도 기동하지 않는다. 키는 Authorization: Basic base64(secretKey + ":")로만 쓰이고 로그로 나가지 않는다. 확인

짚어 볼 지점: 4xx를 모두 확정 실패로 보는 매핑 해석. 승인 요청이 4xx를 받으면 대부분은 정말 거절이다(잔액 부족, 카드 정지 등). 하지만 19강에서 볼 조회 경로는 결정 기록상 "404 등 4xx, 5xx, timeout, 신원 불일치, 미발견을 일괄 FAILED로 간주하지 않는다"이고, 코드에서도 비-2xx를 UNKNOWN으로 처리한다. 즉 같은 결제사 응답 코드를 승인 경로는 확정 실패로, 조회 경로는 불명으로 다룬다. 승인에서 4xx가 나오는 상황 중 실제로는 이미 승인된 경우가 있는지(예: 같은 결제를 두 번 승인 요청했을 때)는 결제사 오류 코드 문서를 대조해야 한다. 나는 그 문서를 확인하지 않았다 미확인. 우리 서버는 2절의 선점 덕분에 같은 결제의 승인을 두 번 보내지 않는다. 그래서 위험은 작지만, 오류 코드별 허용 목록(allowlist)으로 좁히는 편이 일관된다.

4-1. 잠금 순서가 체크아웃과 반대다 [해석, 재현하지 않음]

경로 잠금 순서
체크아웃(17강) 회원 → 장바구니 → 장바구니 항목 → SKU → 쿠폰 → 재고

같은 회원이 탭 A에서 주문 1의 결제 승인을 받는 순간, 탭 B에서 같은 SKU가 담긴 장바구니로 새 체크아웃을 시작했다고 하자. 그러면 이런 순서가 가능하다.

  1. TX2가 재고 X를 잠근다.
  2. 체크아웃이 장바구니를 잠근다.
  3. TX2가 장바구니를 기다린다.
  4. 체크아웃이 재고 X를 기다린다. → 교착

InnoDB는 한쪽을 롤백시킨다. TX2가 희생되면 결제사 승인은 끝났는데 DB는 PROCESSING으로 남는다. 바로 5절의 "고립된 PROCESSING"이다. 사용자 조작 두 개가 밀리초 단위로 겹쳐야 하므로 확률은 낮다. 하지만 결과가 무겁다. TX2에서 장바구니 소비를 재고보다 먼저 잠그거나, 장바구니 소비를 커밋 후 별도 트랜잭션으로 빼는 방안을 검토할 수 있다. 실제로 교착을 재현한 기록은 찾지 못했다.

5. 고립된 PROCESSING — 자동으로 고치지 않기로 한 결정

TX1과 TX2 사이에는 프로세스가 죽을 수 있는 구간이 있다.

#414·PR #415의 고장 주입 실험(일회용 MySQL과 가짜 결제사)은 두 틈을 모두 재현했다. 기록

  • 주문은 PAYMENT_PENDING, 결제는 PROCESSING, 재고 예약은 그대로 남았다.
  • 17강의 만료 스케줄러는 READY만 다룬다. 19강의 대사는 UNKNOWN만 다룬다. 그래서 어느 자동 경로도 이 결제를 집어 가지 않는다.
  • 이 실험은 실제 토스나 운영 장애가 아니다.

두 틈이 DB에서는 똑같이 보인다는 점이 문제의 본질이다. 틈 1이면 예약을 풀어도 되고, 틈 2면 결제를 완료 처리해야 한다. 경과 시간만 보고 "오래됐으니 실패"로 판정하면 틈 2에서 사고가 난다.

  • "타임아웃·5xx는 실패가 아니라 UNKNOWN입니다. 요청이 도착했는지 알 수 없어서, 예약을 유지하고 조회 대사로 넘기며 재승인은 하지 않습니다."

19강. 결제 대사: "모른다"를 "안다"로 바꾸는 절차

18강은 결제사 응답을 받지 못하면 결제를 UNKNOWN으로 남기고 끝났다. 이번 강의는 그 다음 이야기다. 우리 장부(DB)와 결제사 장부가 다를 때, 어느 쪽을 믿고 어떻게 맞추는가. 이 작업을 대사(對査, reconciliation)라고 부른다.

0. 대사란 무엇이고, PawCycle은 어느 것을 하는가

대사는 금융·결제 도메인의 용어로, "내 장부와 상대방 장부가 같은지 맞춰 보는 작업"이다. 보통 두 종류로 나눈다. 원리

실시간·단기 대사 정기·정산 대사
시점 결제 직후 ~ 수 분 다음 날(D+1) 등 주기적
방식 결제사 조회 API로 한 건씩 상태 확인 결제사가 주는 거래 내역 파일 전체와 비교
목적 미확정(PENDING·UNKNOWN) 건을 빨리 확정 전체 거래액과 정산금 검증

PawCycle이 구현한 것은 첫 번째뿐이다. 그것도 일반 결제는 관리자가 버튼을 눌러야 실행된다. 정산 파일 대사와 결제사 웹훅 수신은 코드에 없다. [확인: webhook 검색 결과 0건, 대사 호출자는 AdminPaymentController와 정기결제 처리기 두 곳]

같이 읽을 자료:

  • 4offoff, 거래대사(Transaction Reconciliation) (2026-04-07) — 열어서 본문을 읽었다. 위 표의 두 유형 구분이 이 글의 정리다. 그 밖에 타임아웃, 데이터 유실, "우리는 PENDING인데 결제사는 SUCCESS" 같은 상태 불일치가 왜 생기는지 설명한다. "PENDING·PROCESSING 건을 1분마다 조회 API로 확인하는 스케줄러"라는 실무 시나리오도 있다. PawCycle에 없는 부분(스케줄러)을 이 글이 보여 준다. 대표 그림은 제목 표지라 싣지 않았다.

1. 누가 어떤 상태를 맡는가 — 대사 지도

18강까지 나온 결제 상태와, 각 상태를 정리하는 주체를 한 장에 모아 보자.

대사의 입구 조건이 이 지도를 그대로 강제한다(PaymentReconciliationService.java).

  throw new CommerceException(409, "PAYMENT_RECONCILIATION_NOT_ALLOWED", "UNKNOWN 결제 또는 처리 중 Billing만 대사할 수 있습니다.");

일반 결제의 PROCESSING은 대사로 확정할 수 없다. 18강 5절에서 본 것처럼, 고립된 PROCESSING은 "승인 요청 전에 죽었는지 후에 죽었는지" 구분이 안 된다. 게다가 지금 이 순간 승인 요청이 진행 중일 수도 있다. 18강의 TX1과 TX2 사이에 있는 정상 요청을 대사가 가로채 FAILED로 만들면, 몇 초 뒤 결제사 승인이 성공해도 TX2는 "이미 PROCESSING이 아니다"를 보고 손을 뗀다. 돈은 빠졌는데 주문은 실패가 된다. 그래서 진행 중인 워커가 없다는 펜스(fence) 없이는 열지 않는다. 기록·해석 반면 UNKNOWN은 18강의 TX2가 "결과를 모른다"고 확정해서 기록한 상태다. 진행 중인 승인 요청이 없음이 보장되므로 대사가 안전하게 손댈 수 있다.

    • 결제사를 과하게 두드리지 않는다. 장애 중인 결제사에 조회가 몰리면 상대의 상황이 더 나빠진다.

  • 안전(safe): 서버 상태를 바꾸지 않는다. GET이 해당한다.
  • 멱등(idempotent): 여러 번 보내도 결과 상태가 한 번 보낸 것과 같다. GET, PUT, DELETE가 해당한다.
  • 승인 POST /confirm은 안전하지도 멱등하지도 않다. 그래서 18강은 승인을 절대 자동 재시도하지 않는다.
  • 조회 GET은 안전하다. 그래서 대사는 "모르면 다시 물어보면 된다"는 전략을 쓸 수 있다.

쓰기는 위험하니 한 번만 하고, 읽기를 반복해서 진실을 찾는다. 이것이 대사 설계의 핵심 원리다.

벌크 쿼리는 영속성 컨텍스트를 거치지 않고 DB에 직접 쓴다. 그래서 ① 앞서 엔티티로 바꾼 값이 아직 DB에 없으면 벌크 쿼리가 옛 값을 기준으로 실행된다. ③ 벌크로 바꾼 행이 1차 캐시에 옛 값으로 남아 있으면 같은 트랜잭션의 다음 조회가 옛 값을 본다. 17강의 @Modifying(flushAutomatically, clearAutomatically)와 같은 문제를 직접 처리한 것이다. 원리 시각은 jdbcTime()으로 예전 저장 방식(벽시계 값)과 맞춘다. 16강의 "UTC 결정은 필드별로 좁게 적용"이 여기서도 이어진다. 확인

5. 빠진 것과 트레이드오프

이 대사는 "틀리지 않는 것"을 "빨리 맞추는 것"보다 우선한다. 대가는 다음과 같다. 해석

  • 일반 UNKNOWN은 사람이 눌러야 풀린다. 결제사 장애로 UNKNOWN이 100건 쌓이면 관리자가 100번 눌러야 한다. 그동안 그 주문들의 재고는 예약된 채 팔리지 않는다.
  • 웹훅이 없다. 결제사가 "이 결제 DONE 됐어"라고 먼저 알려 주는 경로가 없다. 웹훅을 붙이더라도 웹훅 본문을 진실로 믿지 않고 "조회를 해 보라는 신호"로만 쓰는 것이 안전하다. 위조나 순서 뒤바뀜이 가능하기 때문이다. 이 프로젝트의 "조회 + 신원 3종 확인" 구조는 그 처리기를 그대로 받아 줄 수 있다.
  • D+1 정산 대사가 없다. 조회 대사는 우리가 아는 결제만 확인한다. "결제사에는 있는데 우리 DB에는 없는" 거래(예: TX1 전에 실패한 요청이 결제사에서는 처리된 경우)는 거래 내역 파일과 전수 비교해야만 찾는다.

20강. 배송·취소·반품·환불: 결제 이후의 "되돌리기"를 설계하기

결제가 성공하면 끝이 아니다. 상품은 배송되어야 하고, 고객은 마음을 바꾸고(취소), 받은 물건을 돌려보내며(반품), 그때마다 돈을 돌려줘야 한다(환불). 이 강의는 결제 이후의 네 가지 흐름을 다룬다.

이 영역에서 PawCycle이 내린 가장 큰 구조적 결정은 이것이다. 주문(orders)의 상태는 결제 이후 PAID에서 더 바뀌지 않는다. 대신 배송, 취소, 반품, 환불이 각자 자기 테이블과 상태 기계를 가진다. 각 테이블에는 주문당 하나라는 UNIQUE(order_id)가 붙는다(환불은 시도마다 한 행). 확인 주문 하나에 상태 값 하나를 두고 PAID → SHIPPED → CANCELLED → REFUNDED…처럼 계속 덮어쓰는 방식과 비교해 보자.

  • 덮어쓰는 방식은 "배송 중에 반품 요청 + 환불 실패" 같은 동시에 성립하는 사실을 표현하지 못한다.
  • 단계별 시각과 담당자를 담을 곳도 없다.

먼저 전체 지도를 보자.

두 가지가 그림의 핵심이다. 취소는 배송 준비 중(PREPARING)일 때만 할 수 있고, 반품은 배송 완료 후 7일 이내에만 할 수 있다. 출고된 뒤에는 취소가 막히고, 고객은 받은 다음 반품해야 한다. 어느 쪽이든 결국 환불 행 하나를 만들고, 실제 돈을 돌려주는 실행은 따로 일어난다.

1. 배송 — 상태와 시각의 조합을 DB가 강제한다

2. 취소 — 한 트랜잭션에서 "되돌림의 의도"까지만 확정한다

CancellationService.request(CancellationService.java)는 고객이 호출한다(POST /api/orders/{orderId}/cancellations).

CancellationPersistenceAdapter.OrderLock order = cancellations.findOrderForUpdate(memberId, orderId);  // ① 내 주문, 잠금
if (order == null) throw ...404 ORDER_NOT_FOUND;

  • ⑥ 환불은 "만들기만" 한다: 환불 행은 READY 상태이고, 금액은 orders.payment_amount 전액을 INSERT ... SELECT로 복사한다. 결제사 호출은 이 트랜잭션 안에서 하지 않는다. 15·18강과 같은 이유다. 대신 "돌려줘야 할 돈이 있다"는 의도가 취소와 같은 커밋으로 남는다. 그래서 환불 실행이 몇 번 실패해도 사라지지 않는다. Outbox 패턴의 핵심 아이디어("외부 작업을 DB에 먼저 기록")를 도메인 테이블로 구현한 셈이다. 해석

한계와 관찰 해석

  • 부분 취소가 없다. 3개를 산 주문에서 하나만 취소할 수 없고, 금액도 항상 전액이다. 주문 항목 단위 취소를 하려면 취소 항목 테이블, 부분 환불 금액 계산(쿠폰 할인을 항목에 어떻게 나눌지), 부분 재고 복원이 필요하다. 업계에서도 까다로운 문제다.
  • 없는 행 잠금: findExisting과 hasReturnForUpdate는 대부분 없는 행을 FOR UPDATE로 읽는다(order_cancellations, order_returns의 order_id 유니크 인덱스). 16·17강의 #331 교착과 같은 모양이다. 같은 주문은 ①이 줄 세우지만, 서로 다른 주문의 취소가 같은 갭을 공유하면 갭 락과 INSERT INTENTION이 엇갈릴 수 있다. 실제 재현 기록은 찾지 못했다. 주문 행 잠금이 이미 같은 주문을 직렬화하므로, 이 두 조회는 잠금 없이 읽어도 된다.

3. 반품 — 고객 요청, 관리자 승인, 관리자 수령

반품은 사람이 끼는 단계가 많다. 상태 기계로 먼저 보자.

ReturnService.java의 규칙이다. 확인

  • 요청 조건: 주문 PAID, 배송 DELIVERED, 그리고 deliveredAt + 7일이 현재보다 뒤여야 한다. 7일은 설정값(pawcycle.commerce.return-request-days)이다. 취소가 이미 있으면 409다. 취소와 반품은 상호 배타이며, 양쪽 모두 주문 행을 먼저 잠그고 상대 테이블을 확인한다.
  • 승인·거절은 REQUESTED에서만: 거절 사유와 결정한 관리자 ID, 결정 시각을 남긴다. DB의 chk_order_returns_decision은 REQUESTED면 decided_at이 NULL, 그 밖의 상태면 NOT NULL을 강제한다. 배송 CHECK와 같은 발상이다.
  • 수령은 APPROVED에서만, 그리고 재입고 여부(restock)를 관리자가 정한다. 돌아온 사료 포대가 뜯어졌거나 파손됐다면 다시 팔 수 없다. 그럴 때는 재고를 복원하지 않고 환불만 한다. restock=true일 때만 inventory.restoreReturn이 available을 늘린다. 재고 숫자가 "실제로 팔 수 있는 물건"을 뜻하도록 지키는 규칙이다. 확인·해석

4. 환불 — 결제 승인의 거울상

환불 실행(RefundService.process, RefundService.java)은 18강 결제 승인과 같은 3단 구조다.

  1. 선점: READY를 PROCESSING으로 바꿔 커밋한다.
  2. 결제사 호출: 트랜잭션 밖에서 취소(환불) API를 부른다. 금액이 0원이면 호출하지 않고 로컬 성공으로 처리한다(V19에서 amount > 0 제약을 완화).
  3. 완료 트랜잭션

같은 점보다 다른 점이 공부할 거리다. 확인

  • PROCESSING 대사의 위험 해석: 18·19강에서 결제는 진행 중일 수 있는 PROCESSING을 대사 대상에서 뺐다. 환불은 넣었다. 환불은 행마다 고유한 idempotency key로 결제사에 요청하고, 대사도 그 키로 조회한다. 그래서 "같은 환불이 두 번 실행되는" 위험은 결제사 쪽 멱등성에 기대어 줄였다고 볼 수 있다. 그래도 실행 중인 요청과 대사가 겹쳐 대사가 먼저 "실패"를 관측하면 판단이 엇갈릴 수 있다. 결제사의 멱등 키 동작은 문서로 확인하지 않았다 미확인.
  • 재시도는 "같은 행 재실행"이 아니라 "새 행"이다: FAILED 행에서만, attempt_no + 1 ≤ 3일 때, 같은 출처(취소 또는 반품)로 새 환불 행을 READY로 만든다. 새 idempotency key를 받는다. 이미 만들어 둔 같은 차수 행이 있으면 그것을 돌려준다(멱등). 실패한 시도의 기록이 덮이지 않고 행으로 남는다. 확인

  • 성공하면 한 커밋에서 다음을 처리한다.

    • 쿠폰 반환: USED를 AVAILABLE로 되돌린다.
    • 취소 또는 반품을 COMPLETED로 바꾼다.
    • 멤버십 등급을 재평가한다(21강).
    • 완료 알림을 보낸다.

4-1. "주문당 성공한 환불은 하나" — 생성 컬럼 + UNIQUE

환불은 한 주문에 여러 행이 생긴다(재시도). 그래서 UNIQUE(order_id)를 걸 수 없다. 그런데 "성공한 환불"은 주문당 하나여야 한다. 두 번 성공하면 돈을 두 번 돌려준 것이다. PostgreSQL이라면 부분 인덱스로 쉽게 해결한다.

-- PostgreSQL (저장소에 없는 비교용 예시)
CREATE UNIQUE INDEX uk_refunds_succeeded ON refunds(order_id) WHERE status = 'SUCCEEDED';

MySQL에는 부분 인덱스가 없다. 그래서 V16은 생성 컬럼(generated column)으로 같은 효과를 낸다.

succeeded_order_id BIGINT GENERATED ALWAYS AS
    (CASE WHEN status='SUCCEEDED' THEN order_id ELSE NULL END) STORED,
CONSTRAINT uk_refunds_succeeded_order UNIQUE (succeeded_order_id),
  • 성공 행에서만 order_id 값이 생기고, 나머지는 NULL이다.
  • MySQL의 UNIQUE는 NULL을 서로 다른 값으로 취급한다. 그래서 실패·대기 행은 몇 개든 공존하고, 성공 행만 주문당 하나로 제한된다. 원리
  • 18강의 payments 테이블에도 같은 장치(uk_payments_successful_order)가 있다. "주문당 성공한 결제도 하나"다. 승인 경로와 대사 경로가 동시에 같은 주문을 성공 처리하려 해도, 두 번째 쓰기는 DB가 거부한다. 확인

  • 그 밖의 제약도 상태 기계를 받쳐 준다.

    • UNIQUE(source, source_id, attempt_no): 같은 취소·반품의 같은 차수는 하나
    • UNIQUE(idempotency_key): 결제사 요청 키 중복 금지
    • CHECK: 출처가 취소면 cancellation_id만, 반품이면 return_id만 존재

    source_id도 COALESCE(cancellation_id, return_id)로 만든 생성 컬럼이다.
