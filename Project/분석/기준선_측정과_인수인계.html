이름 스크립트 부하 모델 내용

run.sh는 k6 실행 전후의 MySQL 명령 수(Com_select, Com_insert, Com_update, Questions)를 기록한다. 측정 60초 시점에 docker stats를 한 번 찍고, 끝난 뒤 backend 스레드 수와 재시작·OOM 여부를 남긴다.

다시 재는 방법

모든 파일은 이 폴더의 기준선_2026-11-13/에 있다.

  1. GitHub에서 측정할 커밋을 작업 폴더에 받는다. 원래 저장소에서 checkout하지 않는다.
  2. 스택을 띄운다(비밀 값은 원래 저장소의 .env.local을 경로로만 참조).
cd <작업폴더>/repo/infra/local-integration
docker compose -p pawcycle-baseline --env-file <원래저장소>/infra/local-integration/.env.local \
  -f compose.yaml -f compose.phase9-envelope.yaml -f <기준선폴더>/compose.baseline-catalog.yaml \
  up --build -d --wait --wait-timeout 600
  1. 측정 전용 DB에서 구매 흐름용 재고를 올린다(값은 컨테이너 안의 환경 변수로만 쓴다).
docker exec pawcycle-baseline-mysql-1 sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot "$MYSQL_DATABASE" \
  -e "UPDATE inventories SET available_quantity=100000, version=version+1 WHERE sku_id=7;"'
  1. JVM을 데운 뒤 측정한다. 기동 직후 첫 측정은 버린다(5절 참고). 측정 사이에 20~30초 쉰다.
bash run.sh list75 read.js -e BASE_URL=http://127.0.0.1:8080 -e TARGET=list -e RATE=75
bash run.sh detail50w read.js -e BASE_URL=http://127.0.0.1:8080 -e TARGET=detail -e RATE=50
  1. 구매 흐름은 QA 계정을 환경 변수로만 넘긴다.
( set -a; . <원래저장소>/infra/local-integration/.env.local >/dev/null 2>&1; set +a
  export QA_EMAIL="$PAWCYCLE_LOCAL_QA_BOOTSTRAP_EMAIL" QA_PASSWORD="$PAWCYCLE_LOCAL_QA_BOOTSTRAP_PASSWORD"
  bash run.sh flow5 flow.js -e BASE_URL=http://127.0.0.1:8080 -e SKU_ID=7 )

기능 기준선 (Gradle 전체 테스트)

CI와 같은 조건으로 돌렸다. 조건은 MySQL 8.4.10 일회용 컨테이너, CI와 같은 계정·권한, 잠금 관측 옵션(lock-ci.init.gradle)이다.

항목 값
테스트 클래스 185개
테스트 4,526개
실패 4개 (모두 BillingRecoveryPersistenceParityIntegrationTests의 같은 파라미터 테스트)
건너뜀 4개
소요 시간 43분 15초(이 PC 기준)

실패 4개의 차이는 updated_at 하나다. 기대값은 23:59:59, 실제값은 14:59:59로 정확히 9시간 차이가 난다. 같은 테스트 클래스를 JVM 시간대만 UTC로 바꿔(utc.init.gradle) 다시 돌리자 전부 통과했다 확인. CI는 UTC로 돌고 이 PC는 한국 시간(UTC+9)이다. 그래서 테스트 결과가 실행 환경의 시간대에 따라 달라진다.

시스템 기본 시간대를 쓰는 곳이 운영 코드인지 테스트 픽스처인지는 아직 확인하지 않았다 미확인. 33-3에서 다룬 시간 타입 혼용(Timestamp·LocalDateTime·Instant, *TimestampJdbcType 10개)과 같은 뿌리로 보인다 해석.

기준선 판정: 이 PC에서 기능 기준선은 "4,526개 중 4,522개 통과, 실패 4개는 시간대 의존"이다. 리팩터링 전후 비교는 user.timezone=UTC로 맞춰서 한다.

5. 측정 과정에서 배운 것

기동 직후와 과부하 직후는 따로 봐야 한다

같은 50 RPS가 처음에는 p95 8.7초로 붕괴했고, 데워진 뒤에는 23ms로 안정적이었다. 상품 상세 50 RPS도 같은 일이 있었다.

  • 기동 직후: JIT 컴파일 전이라 요청당 CPU가 크다. 30초·2 VU 예열로는 부족했다.
  • 과부하 직후: Tomcat 스레드가 220개 넘게 늘어난 상태가 한동안 유지된다. 이 상태에서는 평소 버티던 부하에서도 다시 무너진다. 30초쯤 쉬면 스레드가 49개 수준으로 줄었다.

이 현상은 운영에도 그대로 적용된다. 배포 직후(JVM이 차가움)와 순간 과부하 직후가 가장 위험하다 해석. 앞으로 측정할 때는 "첫 측정 버리기"와 "측정 사이 휴식"을 절차로 고정한다.

측정 도구 쪽 실수 세 가지

증상 원인 서버 결함인가
담기가 매번 실패 담기는 성공 시 204를 돌려주는데 200·201만 성공으로 봤다 아니다
체크아웃 실패 배송지 응답 필드가 addressId인데 id로 읽었다 아니다

세 번째는 curl로 같은 흐름을 세 번 연속 돌려 세션이 유지됨을 확인한 뒤에 결론 내렸다 확인. 28강에서 PowerShell 래퍼가 무너졌던 것과 같은 종류의 실패다. 측정 도구를 먼저 검증해야 한다는 교훈이 다시 확인됐다.

Gradle 테스트를 다시 돌리는 방법

docker start pawcycle-baseline-testdb      # 처음이면 docker run (포트 127.0.0.1:33306, CI와 같은 계정)
cd <작업폴더>/repo/backend
SPRING_DATASOURCE_URL=jdbc:mysql://127.0.0.1:33306/pawcycle_test \
SPRING_DATASOURCE_USERNAME=pawcycle_ci SPRING_DATASOURCE_PASSWORD=ci-only-not-a-secret \
./gradlew test --no-daemon --init-script <기준선폴더>/utc.init.gradle

테스트 계정 정보는 CI 워크플로에 공개된 일회용 값(ci-only-not-a-secret)이다. 운영 비밀이 아니다.

Gradle 테스트 DB 준비

CI는 테스트 계정에 PROCESS 권한 말고도 performance_schema의 잠금 관측 테이블 조회 권한을 준다. 처음에는 이 단계를 빠뜨려 AdminCatalogConcurrencyIntegrationTests 등이 SELECT command denied ... data_lock_waits로 실패했다. CI 워크플로의 준비 SQL을 그대로 적용한 뒤 다시 돌렸다. 테스트 결함이 아니다.

BL-B-03 위험 과부하 뒤 스레드가 줄기 전까지 처리 능력이 떨어진다. Tomcat 최대 스레드 상한이 없다 확인 해석
BL-B-04 개선 요청당 SELECT보다 부가 명령이 많다(목록 2 대 약 5) 확인 미확인명령 종류
BL-B-05 코드 스타일·구성 기동 로그에 Spring Data Redis가 JPA 리포지토리를 Redis 리포지토리 후보로 검사하는 경고가 리포지토리마다 찍힌다. spring.data.redis.repositories.enabled=false 후보 확인
BL-B-06 결함(재확인) 상품 목록 캐시가 켜져 있어도 읽히지 않는다(BL-28-01). 기준선은 캐시 없는 숫자 확인
BL-B-07 결함 테스트가 실행 환경의 시간대에 의존한다. BillingRecoveryPersistenceParityIntegrationTests의 4개가 KST에서 9시간 차이로 실패하고 UTC에서 통과한다. 운영 코드인지 테스트 픽스처인지 확인 필요 확인 미확인원인 위치
BL-B-08 개선 백엔드 전체 테스트가 이 PC에서 43분 걸린다. 리팩터링 중 빠른 피드백을 위해 영역별 실행 묶음(태그)이 필요하다 확인

7. 현재 상태

대상 상태
측정 스택 pawcycle-baseline 멈춤(컨테이너와 볼륨은 남김). 다시 켜려면 3절 2번 명령을 그대로 실행한다. 측정 데이터(SKU 7번 재고, 측정 회원의 주문 약 270건)가 남아 있으므로, 깨끗한 기준선이 필요하면 docker compose -p pawcycle-baseline down -v로 볼륨까지 지우고 다시 만든다
테스트 DB pawcycle-baseline-testdb 멈춤. docker start pawcycle-baseline-testdb로 다시 켠다. 권한은 이미 부여돼 있다. 지우려면 docker rm -f pawcycle-baseline-testdb
작업 폴더 사본 세션 작업 폴더에 있다. 세션이 끝나면 사라질 수 있다. 다시 받으면 된다
