4강. 요구사항의 진화: 무엇을 만들었고, 무엇을 일부러 뺐는가

이번 강의의 목표

  • MVP1부터 MVP4까지 요구사항이 어떤 순서로 자랐는지 한 줄로 설명할 수 있다.
  • 각 단계에서 일부러 뺀 것이 무엇이고, 그것이 나중에 어떤 비용으로 돌아왔는지 말할 수 있다.
  • 제품 결정이 SQL 제약(CHECK, 복합 외래 키, UNIQUE)으로 굳어지는 과정을 코드로 확인한다.

표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 원리 일반 원리 · 미확인

1. 한 장으로 보는 흐름

PawCycle은 처음부터 지금의 모습이 아니었다. 7월의 MVP1은 "SKU 하나를 고르는 구독"뿐이었다. 8월 초 MVP2에서 반려동물·플랜 버전·불변 스냅샷·구독 상태가 생겼고, 8월 11일 자동 주문, 8월 13일 MVP3에서 일반 구매와 결제가, 8월 말 MVP4에서 신뢰·추천·직접 관리가 붙었다. 9~11월은 기능 추가보다 구조 정리와 운영의 시간이었다. 아래 타임라인이 그 흐름이다.

2. MVP1 (7월): SKU 하나를 고르는 구독

MVP1의 요구사항 문서(PS-001)에는 제품 범위를 그린 mermaid 도식이 들어 있다. 저장소의 원문 도식을 그대로 렌더링하면 다음과 같다.

도식에서 눈여겨볼 점은 배송 주기와 다음 주문 예정일이 독립된 상자로 그려졌지만, 문서는 이것을 “구독을 설명하는 값이지 별도 엔티티가 아니다”라고 못 박았다는 것이다. 개념을 그리는 것과 테이블을 만드는 것을 구분한 것이다. 실제로 이 요구사항은 테이블 하나로 굳었다.

-- V2__create_subscriptions.sql (MVP1의 구독 전부)
CREATE TABLE subscriptions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    sku_id BIGINT NOT NULL,                       -- 구독 하나 = SKU 하나
    quantity INT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    created_date DATE NOT NULL,                   -- 시각이 아니라 날짜
    next_order_date DATE NOT NULL,
    CONSTRAINT chk_subscriptions_quantity CHECK (quantity BETWEEN 1 AND 10),
    CONSTRAINT chk_subscriptions_delivery_cycle CHECK (delivery_cycle_weeks IN (2, 4, 8)),
    CONSTRAINT chk_subscriptions_date_order CHECK (next_order_date > created_date),
    ...
);
CREATE INDEX idx_subscriptions_member_id ON subscriptions (member_id, id);
  • CHECK (quantity BETWEEN 1 AND 10), IN (2, 4, 8): 제품 결정(“수량 1~10, 주기 2·4·8주 고정, 임의 주기 금지”)이 DB 제약으로 그대로 옮겨졌다. 애플리케이션 검증이 뚫려도 DB가 마지막으로 막는다. 원리 MySQL은 8.0.16부터 CHECK를 실제로 강제한다. 그 전 버전은 문법만 받아들이고 무시했다.
  • created_date DATE: 시각이 아니라 날짜다. 정기배송은 “몇 시 몇 분”이 아니라 “며칠”의 문제이고, 기준 시간대는 Asia/Seoul로 정했다. 휴일 보정은 하지 않기로 했다.
  • CHECK (next_order_date > created_date): 정확한 계산(생성일 + 주기)은 도메인 코드가 책임진다. DB는 순서만 검사한다. 정확한 등식까지 DB에 넣지 않은 이유는 계산 규칙이 바뀔 때 마이그레이션이 필요해지기 때문이다. 책임을 나눈 것이다.
  • INDEX (member_id, id): “내 구독 목록을 최신순으로” 조회 한 가지를 위해 만든 인덱스다. 기록 측정 없이 추가 인덱스를 만들지 않는다는 원칙도 함께 정했다.
  • status 컬럼이 없다. 일시정지도 해지도 없으니 상태가 필요 없었다.

일부러 뺀 것과 그 대가

확인 제외 목록은 30개가 넘는다. 주문 생성, 장바구니, 결제, PG 연동, 재고, 배송, 구독 변경·일시정지·해지, 쿠폰, 추천, 관리자 화면 등이다. 문서는 “제외된 기능은 전체 제품 방향에서 삭제하지 않는다. 후속 후보로 남긴다”고 덧붙인다.

그중 세 가지 결정이 이후 설계에 큰 흔적을 남겼다.

  • 멱등성을 일부러 넣지 않았다. 기록 첫 구독 API 계약은 같은 회원이 같은 조건으로 구독을 여러 개 만드는 것을 허용했다. Idempotency-Key 저장소도 두지 않았다. 클라이언트는 처리 중 제출 버튼만 비활성화했다.
    • 문서는 “타임아웃 후 반복 POST가 실제 중복 구독을 만들 수 있는 위험”을 사용자가 승인한 트레이드오프로 남겼다.
    • 3강의 언어로 말하면, 이 API는 최소 한 번 전달 + 중복 제거 없음이었다. 결제가 없으니 중복이 생겨도 돈이 움직이지 않는다. 그래서 감수할 수 있는 위험이었다.
    • 돈이 움직이기 시작한 MVP2·MVP3에서는 이 결정이 뒤집힌다(아래 3·5절).
  • 남의 구독은 403이 아니라 404로 숨긴다. “없음”, “남의 것”, “숫자가 아닌 ID”를 모두 같은 404로 돌려준다. 403(“있지만 권한 없음”)으로 구분하면 그 ID가 존재한다는 사실이 새어 나가기 때문이다. 3강의 타이밍 부채널과 같은 계열의 정보 누설 방지이고, 12강(인가와 소유권)에서 코드로 본다.
  • 다음 주문 예정일은 서버만 계산한다. 생성 전에는 화면에 정확한 날짜를 보여 주지 않는다.
    • 브라우저가 미리 계산하면 시간대(사용자 PC가 Asia/Seoul이 아닐 수 있다)와 날짜 기준이 서버와 어긋날 수 있다.
    • 그래서 “생성 후 확인” 안내만 하고, 생성 직후 구독 상세 화면으로 이동해 서버가 확정한 날짜를 보여 준다.
    • 로그인 후에는 서비스 내부의 GET 경로로만 복귀시킨다. 외부 URL로 돌아가게 허용하면 Open Redirect 공격(피싱 사이트로 보내는 신뢰 링크)이 되기 때문이다. 이전 POST를 자동으로 다시 실행하는 것도 금지했다. 중복 구독 위험 때문이다.

3. MVP2 (8/2): “가격이 바뀌면?”이라는 질문

MVP1의 구독은 sku_id와 quantity만 들고 있었다. 그러면 SKU 가격이 오를 때 기존 구독자의 다음 결제 금액도 조용히 바뀐다. 반려동물별 패키지(사료 + 간식 + 모래)도 표현할 수 없다.

기록 MVP2는 이 문제를 네 개념으로 풀었다.

  • Pet: 회원이 소유하는 반려동물. 이름과 종(DOG/CAT)만 있다.
  • SubscriptionPlan → PlanVersion → PlanItem: 종별 패키지 플랜과 그 버전, 버전의 구성 SKU·수량.
  • 불변 스냅샷: 구독할 때 선택한 PlanVersion의 가격·구성·배송 주기를 복사해 둔 기록.
  • pending 변경: 플랜을 바꾸면 즉시 적용하지 않고 다음 실행 가능한 회차에 적용할 스냅샷을 대기시킨다.

왜 참조가 아니라 복사인가

이 설계의 핵심은 가격을 참조하지 않고 복사한다는 것이다. 영수증을 생각하면 쉽다. 영수증에 “상품 #42의 현재 가격”이라고 적혀 있으면, 상품 가격이 바뀔 때마다 과거 영수증의 금액도 바뀐다. 영수증은 그 순간의 값을 그대로 적어 두는 문서여야 한다.

  • 가격·구성을 바꾸고 싶으면 새 PlanVersion을 만든다. 기존 버전은 고치지 않는다.
  • 이미 구독 중인 사람은 자기 스냅샷의 가격을 유지한다. 판매가 끝나도 자동 해지하거나 다른 플랜으로 옮기지 않는다.
  • 기록 기각한 대안: 활성 PlanVersion이나 과거 스냅샷을 제자리에서 수정하는 방식이다. 이미 생성된 구독의 가격 의미가 바뀌기 때문에 기각됐다.

이 규칙들이 SQL에서 어떻게 강제되는지 보자. V3 마이그레이션에서 중요한 세 덩어리다.

-- V3__add_second_mvp_subscription_schema.sql (발췌)

-- (가) "플랜의 현재 버전"은 반드시 그 플랜의 버전이어야 한다
ALTER TABLE plan_versions
    ADD CONSTRAINT uk_plan_versions_id_plan UNIQUE (id, plan_id);
ALTER TABLE subscription_plans
    ADD CONSTRAINT fk_subscription_plans_current_version
        FOREIGN KEY (current_plan_version_id, id) REFERENCES plan_versions (id, plan_id);

-- (나) 스냅샷: 출처 버전을 기억하되, 금액·주기는 복사본을 들고 있다
CREATE TABLE subscription_snapshots (
    id BIGINT NOT NULL AUTO_INCREMENT,
    subscription_id BIGINT NULL,
    source_plan_version_id BIGINT NOT NULL,
    package_total_krw BIGINT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    CONSTRAINT chk_subscription_snapshots_total
        CHECK (package_total_krw BETWEEN 0 AND 9007199254740991),
    ...
);

-- (다) 구독당 pending 변경은 최대 하나
CREATE TABLE pending_plan_changes (
    subscription_id BIGINT NOT NULL,
    snapshot_id BIGINT NOT NULL,
    target_schedule_id BIGINT NOT NULL,
    CONSTRAINT pk_pending_plan_changes PRIMARY KEY (subscription_id),
    CONSTRAINT uk_pending_snapshot UNIQUE (snapshot_id),
    CONSTRAINT uk_pending_target_schedule UNIQUE (target_schedule_id),
    ...
);
  • (가) 복합 외래 키 트릭. 단순히 current_plan_version_id → plan_versions(id)로 걸면, 플랜 A의 현재 버전으로 플랜 B의 버전을 가리키는 실수를 DB가 막지 못한다.
    • 그래서 plan_versions에 (id, plan_id) 조합 UNIQUE를 만든다. id가 이미 PK라 이 조합은 당연히 유일하지만, 외래 키의 참조 대상이 되려고 만든 것이다.
    • 그다음 (current_plan_version_id, 자기 id)가 그 조합을 참조하게 한다. 이렇게 하면 “현재 버전의 plan_id = 나의 id”가 DB 수준에서 보장된다.
    • 애플리케이션 버그 하나로 다른 플랜의 가격이 섞이는 일을 구조적으로 막는 기법이고, 6강(ERD)에서 다시 쓴다.
  • (나) 9007199254740991이라는 이상한 상한. 이 수는 2⁵³ − 1이고, JavaScript의 Number.MAX_SAFE_INTEGER다.
    • 원리 JavaScript의 숫자는 64비트 부동소수점(IEEE 754 double)이라 가수부가 53비트다. 그보다 큰 정수는 정확히 표현되지 않는다. 예를 2⁵³ + 1은 2⁵³으로 반올림된다.
    • 서버의 BIGINT는 2⁶³ − 1까지 담지만, JSON으로 프론트에 가는 순간 큰 금액이 조용히 다른 숫자로 바뀔 수 있다.
    • 해석 그래서 금액 상한을 프론트가 안전하게 다룰 수 있는 범위로 DB에서 묶었다. 화면(Next.js)까지 고려한 제약이다.
  • (다) “최대 하나”를 PK로 표현. PRIMARY KEY (subscription_id)이니 한 구독에 pending 행은 물리적으로 하나만 존재할 수 있다.
    • 제품 규칙도 이에 맞춰져 있다. 적용 전에 새 변경이 오면 대기열에 쌓지 않고 최신 요청으로 교체한다. 교체 전 명령은 명령 이력에 남긴다.
    • 대기열로 쌓는 대안은 “어느 변경이 언제 적용되는가”라는 복잡한 규칙을 만든다.

멱등성이 돌아왔다

MVP2의 구독 명령(플랜 변경, 건너뛰기, 일시정지, 재개, 해지)에는 Idempotency-Key와 If-Match(버전 검사)가 들어갔다. MVP1에서 뺐던 것이 돌아온 것이다. 구독 상태가 생기고 명령이 상태를 바꾸기 시작했으니, “같은 해지 요청이 두 번 들어오는” 문제가 현실이 됐기 때문이다. 동시 수정 보호(If-Match, 낙관적 버전)는 22강에서 본다.

기존 데이터라는 청구서

MVP1 구독은 스냅샷 없이 이미 만들어져 있었다. 기록 MVP2는 이 데이터를 버리거나 초기화하지 않고 손실 없이 이행하기로 했다. 규칙은 이렇다.

  • 기존 구독의 가격은 마이그레이션 시점의 SKU 단가 × 기존 수량으로 계산한다. 문서는 이것이 “구독 생성 당시 가격이 아니다”라고 정직하게 적는다. 당시 가격을 기록해 두지 않았으니 복원할 방법이 없다.
  • 기존 구독 보존 전용 PlanVersion·PlanItem을 만들어 연결한다. 이 버전은 신규 구독의 선택 후보가 아니다.
  • 변환할 수 없는 행이 하나라도 있으면, 값을 추측·반올림·절삭하지 않고 쓰기 전에 전체 마이그레이션을 중단한다.

이것이 MVP1에서 스냅샷을 뺀 결정의 대가다. 이 대가를 어떻게 평가할지는 7절에서 YAGNI의 틀로 다시 본다.

4. 자동 주문 (8/11): 스케줄러는 최소 한 번 실행된다

MVP2까지 “다음 주문 예정일”은 화면에 보여 주는 값일 뿐, 실제로 주문이 생기지는 않았다. 8월 11일 자동 주문이 들어오면서 처음으로 시스템이 스스로 데이터를 만들기 시작했다.

확인 요구사항 문서의 핵심 문장은 이것이다.

Scheduler 실행은 at-least-once여도 DB 결과는 Schedule당 Order 하나다. — docs/product/PS-005-subscription-automation-requirements.md

3강에서 배운 “최소 한 번 전달 + 중복 제거 = 정확히 한 번의 효과”가 그대로 요구사항이 됐다. 스케줄러가 같은 회차를 두 번 집거나 서버 두 대가 동시에 돌아도, 결과는 주문 하나여야 한다. 그 마지막 방어선이 SQL 한 줄이다.

-- V9__create_subscription_orders.sql (발췌)
CREATE TABLE subscription_orders (
    ...
    schedule_id BIGINT NOT NULL,
    effective_snapshot_id BIGINT NOT NULL,       -- 이 주문에 적용된 스냅샷
    source_plan_version_id BIGINT NOT NULL,
    scheduled_date DATE NOT NULL,                -- 원래 예정일
    processed_at DATETIME(6) NOT NULL,           -- 실제 처리 시각
    package_total_krw BIGINT NOT NULL,           -- 금액도 다시 복사
    status VARCHAR(20) NOT NULL,
    CONSTRAINT uk_subscription_orders_schedule UNIQUE (schedule_id),
    CONSTRAINT chk_subscription_orders_status CHECK (status = 'CREATED'),
    ...
);
  • UNIQUE (schedule_id): 회차 하나에 주문 하나. 경쟁에서 진 쪽은 중복 키 오류를 받는다.
    • 기록 이 오류를 바로 실패로 보지 않는다. 실제 주문이 존재하는지 다시 확인한 뒤에만 정상적인 “이미 처리됨(no-op)”으로 처리한다.
  • scheduled_date와 processed_at을 둘 다 저장: “언제 처리됐어야 했나”와 “실제로 언제 처리됐나”를 구분한다. 스케줄러가 멈췄다 재개되면 둘이 벌어지는데, 이 차이가 운영의 증거가 된다.
  • CHECK (status = 'CREATED'): 상태가 하나뿐이다. 결제·배송이 없으니 다른 상태가 필요 없다. 필요해질 때 늘린다. 이것도 MVP1의 status 없음과 같은 원칙이다.

처리 방식에서 일부러 하지 않은 것들이 특히 중요하다.

  • 배치 전체를 한 트랜잭션으로 묶지 않았다. 후보마다 REQUIRES_NEW로 독립 트랜잭션을 연다. 3강에서 본 PR #106의 실패 격리 원칙이 그대로 이어진다.
  • 누락된 회차를 몰아서 만들지 않는다. 스케줄러가 3주 멈췄다가 살아나도 가장 오래된 회차의 주문 하나만 만든다. 그다음 원래 예정일에서 주기를 반복해 오늘보다 미래인 첫 날짜로 건너뛴다.
    • 예: 2주 주기, 예정일 10/1, 오늘 10/20 → 10/1 회차 주문 1건 생성 → 다음 회차는 10/15를 지나 10/29.
    • 이유: 장애 뒤에 의도하지 않은 대량 주문이 생기는 위험이 회차 누락보다 크다고 판단했다.
  • 기록 기각한 대안:
    • 애플리케이션 메모리 락, Redis 분산 락, Kafka: DB 행 잠금과 UNIQUE 제약만으로 불변식을 표현할 수 있어서, 새 운영 의존성을 정당화하지 못했다.
    • HTTP 명령의 멱등 행 재사용: 스케줄러의 처리 단위와 보관 의미가 다르다.
    • 재시도 API, backoff, DLQ, 새 PROCESSED 상태: 다음 스케줄러 실행이 다시 집으면 되므로 두지 않았다.
  • 기본값은 꺼짐. 명시적으로 켜야만 동작한다. 운영 DB에 자동으로 데이터를 만드는 기능은 켜는 것 자체가 별도 결정이어야 하기 때문이다.

5. MVP3 (8/13): 돈이 움직이기 시작했다

MVP3는 하루에 거대한 PR 하나(PR #138)로 일반 구매 Commerce를 들여왔다. MVP1에서 뺐던 목록 대부분이 한꺼번에 돌아왔다.

  • 장바구니, 찜, 배송지
  • 체크아웃(재고 예약, 쿠폰), 토스 결제 승인, 정기결제(빌링키)
  • 배송·취소·반품·환불, 알림
  • 관리자: 재고 조정, 쿠폰, 회원 등급, 운영 조회, 감사 로그

확인 계약 문서에서 MVP1과 대비되는 문장들을 골라 보면 진화가 선명하다.

주제 MVP1 MVP3
중복 요청 멱등성 없음, 버튼 비활성화만 체크아웃에 Idempotency-Key 필수, 회원 단위로 직렬화해 동시 요청도 기존 결과를 재생
가격의 권위 서버가 계산한 날짜만 신뢰 장바구니는 가격·재고를 예약하지 않고, 체크아웃에서 현재 가격·재고를 다시 검증. 결제 금액은 서버의 체크아웃 응답 값을 쓰고, 토스 리다이렉트 URL의 금액은 일치 검사에만 사용
남의 자원 남의 구독은 404 남의 결제 providerOrderId도 똑같이 404 PAYMENT_NOT_FOUND

일부러 막아 둔 것들도 분명하다.

  • 실결제는 없다. 토스 연동은 local-integration 프로필에서 test_sk_ 테스트 키로만 동작한다. 라이브 키는 거부한다.
  • 결제사가 없으면 실패한다(fail-closed). 실제 결제사가 구성되지 않은 환경에서는 결제 승인과 빌링 등록이 실패로 끝난다. 가짜 결제 성공을 만들지 않는다. 3강 관측 축의 “모를 때는 정상이라 하지 않는다”와 같은 원칙이다.
  • UNKNOWN 결제는 재시도 대상으로 바꾸지 않는다. 예약된 재고와 쿠폰은 유지한다. 결제 대사는 최대 10회까지만 하며, 대사 스케줄러 실행 자체는 범위 밖이다. 이 빈칸이 3강 위험 지도의 1순위였던 PROCESSING 고립 문제로 이어진다(18·19강).
  • 결제 응답 대기 시간 30분. 결제창으로 넘어간 뒤 30분 안에 승인되지 않으면 주문을 만료시키고 재고와 쿠폰을 돌려준다. PROCESSING·UNKNOWN 결제는 이 만료 대상이 아니다. 돈이 움직였을지도 모르는 상태를 함부로 되돌리지 않기 위해서다.

같은 날 바로 구조 정리 PR(PR #139)이 뒤따랐다. 기록 여기서 정한 원칙은 이렇다.

  • API와 기존 스키마는 유지한다.
  • 일반 엔티티는 JPA로 옮기되, 잠금·CAS·운영 조회·구독 V2 호환 경계는 명시 SQL로 남긴다.
  • 외부 결제사 호출은 DB 트랜잭션 밖에 둔다. 느리거나 실패하는 외부 I/O가 DB 커넥션과 잠금 점유로 번지지 않게 하기 위해서다. 3강의 HikariCP 이야기와 연결된다.
  • 관리자 변경은 감사 기록까지 한 트랜잭션에서 처리한다. 감사 기록이 실패하면 상태 변경도 커밋하지 않는다.

6. MVP4 (8/24–8/28): 신뢰와 추천, 그리고 AI의 자리

MVP4는 “살 수 있다”를 넘어 “믿고 살 수 있다”로 갔다.

  • 구독 직접 관리: 회원이 구독 명령을 더 넓게 스스로 수행한다. 기존 Idempotency-Key, If-Match, ETag 계약을 그대로 이어받고, 성공 재생을 버전 검사보다 먼저 판정한다.
    • 왜 순서가 중요한가: 이미 성공한 요청을 재시도하면, 그 사이 버전이 올라가 있으므로 버전 검사를 먼저 하면 충돌로 오판한다. 3강 그림의 “저장된 결과 재전송”이 먼저여야 한다.
  • 상품 신뢰: 리뷰와 상품 문의. 공개 응답에 작성자의 이메일이나 회원 ID를 넣지 않는다.
  • 구매 정합성: 장바구니에 version을 추가했다. 내용이 실제로 바뀔 때만 올라가고, 변화 없는 요청은 버전을 올리지 않는다(16·17강).
  • 반려동물 프로필: 품종과 체중을 추가했다. 삭제 API는 없다.

가장 흥미로운 결정은 AI 추천의 경계다. 기록

  • 서버가 후보, 소유권, 의료 관련 상품 제외, 최종 구매 가능 여부를 모두 결정한다.
  • AI에는 최대 10개로 제한된 후보 ID와 공개 상품 정보만 넘긴다. AI는 순서와 짧은 이유만 제안한다. 회원 식별자, 이름, 연락처, 주소, 결제 정보는 넘기지 않는다.
  • AI가 후보 밖 ID나 중복을 돌려주거나 오류가 나면, 그 결과를 버리고 결정적인 기본 순서로 채운다.
  • AI 호출 뒤에 최신 카탈로그 조건을 다시 조회한다.
    • 원리 이것을 TOCTOU(Time-Of-Check to Time-Of-Use) 문제라 한다. 검사한 시점과 사용하는 시점 사이에 상태가 바뀌는 문제다. AI 호출이 몇 초 걸리는 동안 상품이 품절될 수 있다.
  • 외부 AI 호출 중에는 DB 트랜잭션을 열어 두지 않는다. MVP3 구조 정리와 같은 원칙이다.
  • 기본값은 꺼짐. 실제 API 키, 모델, 운영 비용 승인은 별도다.
  • 기록 기각한 대안: AI가 후보 선택과 유효성까지 판단하는 방식(확률적 응답에 정책을 맡김), 추천 전용 Redis·RAG·임베딩·큐 도입(근거 부족).

해석 이 결정은 포트폴리오에서 가장 설명하기 좋은 소재 중 하나다. “AI를 붙였다”가 아니라 “AI가 틀려도 시스템이 틀리지 않게 경계를 그었다” 고 말할 수 있기 때문이다. 15강에서 코드로 확인한다.

7. 판단의 틀: YAGNI와 네 가지 비용

다섯 단계를 관통하는 원칙은 하나다. 필요가 확인되기 전에는 만들지 않는다. 이것을 YAGNI(You Aren't Gonna Need It)라 한다. 데브원영의 「YAGNI, 그 기능이 필요할 때 만들어라!」는 Ron Jeffries의 말로 이 원칙을 소개한다. 미래에 필요할 것 같을 때가 아니라 실제로 필요할 때 구현하라는 것이다. 그리고 한계로 장기 설계를 간과하거나 과도하게 단순화할 위험도 함께 짚는다.

Martin Fowler는 「Yagni」에서 이 원칙을 비용으로 분해한다. 미리 만든 기능(presumptive feature)은 네 가지 비용을 낳는다는 것이다.

출처: Martin Fowler · Yagni (2015).

  • 만드는 비용(cost of build): 결국 필요 없었던 기능에 쓴 분석·개발·테스트 노력.
  • 지연 비용(cost of delay): 그 시간에 지금 필요한 기능을 만들지 못해 가치가 늦게 나온 비용. 필요한 기능이었더라도 생긴다.
  • 유지 비용(cost of carry): 미리 만든 코드가 복잡도를 더해, 이후 모든 기능의 개발과 디버깅을 느리게 하는 비용.
  • 수리 비용(cost of repair): 필요한 기능을 잘못된 모양으로 미리 만들어, 나중에 고쳐야 하는 비용. 그 사이 팀은 도메인과 코드를 더 배우기 때문에 이런 일이 흔하다.

Fowler는 중요한 단서를 하나 붙인다. YAGNI는 미리 만든 기능에만 적용되고, 코드를 바꾸기 쉽게 만드는 노력에는 적용되지 않는다. 리팩터링, 자가 테스트 코드, 지속적 전달은 YAGNI 위반이 아니라 YAGNI를 가능하게 하는 조건이다. 코드가 바꾸기 어려우면 YAGNI는 저주가 된다.

이 틀로 PawCycle의 결정들을 평가해 보자. 아래 판정은 모두 해석 이다.

결정 YAGNI 관점의 평가
MVP1에서 주문·결제·재고 제외 잘 맞았다. 구독 흐름이 먼저 동작했고, 결제 설계는 실제 요구가 생긴 MVP3에서 했다. 지연 비용을 피했다.
MVP1에서 status 없음, V9의 CREATED 하나 잘 맞았다. 필요한 상태만 그때그때 추가했다. 미리 만든 상태 머신은 대부분 틀린 모양이 된다(수리 비용).
Redis 락·Kafka·DLQ 기각 잘 맞았다. DB 제약으로 충분했고, 새 운영 의존성의 유지 비용을 피했다.
MVP1에서 가격 스냅샷 없음 비용이 실제로 청구됐다. MVP2에서 손실 없는 이행 규칙을 따로 설계해야 했고, 원래 생성 당시 가격은 영원히 복원할 수 없게 됐다. 데이터는 코드와 달리 나중에 리팩터링으로 되살릴 수 없다.
MVP1에서 멱등성 없음 조건부로 맞았다. 돈이 움직이지 않는 동안에는 위험이 작았다. 돈이 움직이기 시작한 MVP2·MVP3에서 바로 들어왔다.

여기서 실무 교훈 하나가 나온다. YAGNI는 코드에는 관대하지만 데이터에는 가혹하다. 코드는 나중에 고치면 되지만, 기록하지 않은 사실(생성 당시 가격, 처리 시각, 누가 바꿨는지)은 나중에 만들어 낼 수 없다. 그래서 다음은 “미리 만드는 기능”이 아니라 비용이 작은 보험으로 보는 편이 맞다.

  • 시점 값을 복사해 두는 스냅샷
  • 예정 시각과 실제 처리 시각을 함께 남기는 컬럼
  • 감사 기록

Fowler가 말한 “지금 하기 쉽고, 복잡도를 거의 늘리지 않으면서, 나중 비용을 크게 줄이는 것”에 해당한다. PawCycle은 V9에서 scheduled_date와 processed_at을 처음부터 둘 다 저장해, 이 교훈을 반영했다.

같이 읽을 자료

  • Martin Fowler · Yagni: 네 가지 비용, YAGNI가 리팩터링과 충돌하지 않는 이유(영문)
  • 데브원영 · YAGNI, 그 기능이 필요할 때 만들어라!: 원칙과 한계를 한국어로 짧게 정리
  • 토스페이먼츠 · 멱등성이 뭔가요?: MVP1에서 뺐다가 MVP3에서 필수가 된 Idempotency-Key의 동작

4강 정리

  • 흐름: MVP1(7월, 단일 SKU 구독) → MVP2(8/2, Pet·플랜 버전·불변 스냅샷·상태) → 자동 주문(8/11) → MVP3(8/13, 일반 구매·결제) → MVP4(8/24–28, 신뢰·추천·직접 관리) → 9–11월 구조 정리와 운영.
  • 수직 슬라이스: 모든 층을 관통하되 기능 폭을 하나로 좁혀, 첫 주부터 동작하는 흐름을 얻는다.
  • 제품 결정은 SQL 제약으로 굳는다.
    • 수량·주기 CHECK
    • 복합 외래 키로 “현재 버전은 그 플랜의 버전”을 보장
    • PRIMARY KEY (subscription_id)로 pending 최대 하나
    • UNIQUE (schedule_id)로 회차당 주문 하나
    • 금액 상한 2⁵³ − 1로 JavaScript 숫자 정밀도까지 보호
  • 뺀 것은 사라지지 않고 돌아온다.
    • 멱등성은 상태가 생기자(MVP2), 돈이 움직이자(MVP3) 돌아왔다.
    • 스냅샷 부재는 이행 비용과 영구적인 가격 정보 손실로 청구됐다.
  • AI의 자리: 서버가 결정하고 AI는 재정렬만 한다. TOCTOU를 막으려고 호출 뒤 다시 검증하고, 기본값은 꺼짐이다.
  • YAGNI의 네 비용(만들기·지연·유지·수리). YAGNI는 코드에는 관대하지만 데이터에는 가혹하다.
