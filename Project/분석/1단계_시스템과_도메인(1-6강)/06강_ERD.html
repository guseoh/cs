6강. ERD: 28개 마이그레이션이 그린 데이터 지도

이번 강의의 목표

  • 개념 → 논리 → 물리 모델링의 차이를 알고, PawCycle 문서와 코드가 각각 어느 단계인지 구분한다.
  • Flyway V1–V28이 쌓아 올린 약 60개 테이블의 지도를 그리고, 핵심 테이블 사이의 관계를 읽는다.
  • PK·FK·UNIQUE·CHECK·인덱스가 각각 어떤 업무 규칙을 지키는지 SQL로 읽는다. B-Tree 인덱스의 원리도 함께 본다.
  • 주문 테이블이 두 벌인 이유와 멱등성 테이블 네 종류의 차이를 이해한다.

1. 개념 → 논리 → 물리

데이터 모델링은 보통 세 단계로 나눈다. itwiki의 데이터 모델링 항목이 정리한 기준은 이렇다.

단계 질문 산출물 DBMS 종속
개념 업무에 어떤 핵심 개체와 관계가 있나 개념 ERD 아님
논리 식별자는 무엇이고, 정규화하면 어떤 구조가 되나 논리 ERD, 엔터티·속성 정의서 아님
물리 실제 DBMS에 어떤 테이블·타입·인덱스로 만드나 물리 ERD, DDL 맞음

PawCycle의 문서와 코드가 정확히 이 세 단계로 나뉜다.

  • 개념: DATA-001은 Member, Product, Sku, Subscription 네 개념과 “첫 MVP에 왜 필요한가”만 적는다. 그리고 “테이블명과 컬럼명은 후속 마이그레이션에서 최종 확정한다”고 못 박는다.
  • 논리: DATA-002는 논리 ERD 초안이다. 문서 상태도 Proposed다.
  • 물리: backend/src/main/resources/db/migration/V1__…sql ~ V28__…sql. 확인 1강에서 본 spring.jpa.hibernate.ddl-auto=validate 설정 때문에 JPA는 테이블을 만들지 않고 검사만 한다. 테이블의 유일한 원본은 Flyway 마이그레이션이다.

그래서 이 강의의 ERD는 문서가 아니라 마이그레이션 SQL에서 직접 뽑는다. 문서는 의도를, SQL은 사실을 말한다. 5강에서 배운 “문서 → 코드 → 이력” 대조 원칙 그대로다.

2. 핵심 테이블 지도

28개 마이그레이션이 만든 테이블은 약 60개다. 전부 한 그림에 넣으면 읽을 수 없으니, 구독과 주문·결제의 뼈대만 추렸다. mermaid 원문에서 렌더링한 ERD다.

ERD를 읽는 방법부터 짚자. 선 끝의 기호가 카디널리티(몇 대 몇인가)다.

  • || 정확히 하나, o| 0 또는 1, o{ 0 이상, |{ 1 이상
  • 예: orders ||--|{ order_items는 “주문 하나에 항목이 1개 이상”이다. orders ||--o{ payments는 “결제 시도가 0개 이상”이다. 5강에서 본 그대로다.

그림에서 눈에 띄는 것이 둘 있다.

  • subscription_schedules에서 주문 쪽으로 선이 두 개 나간다. subscription_orders(V9)와 subscription_order_context(V14)다. 이것이 6절의 “주문 모델 두 벌”이다.
  • subscriptions와 subscription_snapshots 사이에도 선이 두 개다.
    • 하나는 “구독이 여러 스냅샷을 쌓는다”(1:N, subscription_snapshots.subscription_id).
    • 다른 하나는 “구독이 그중 하나를 현재로 가리킨다”(subscriptions.current_snapshot_id).
    • 두 테이블이 서로를 참조한다. 그래서 V3는 스냅샷 테이블을 만든 뒤 ALTER TABLE subscriptions ADD CONSTRAINT ... FOREIGN KEY (current_snapshot_id)로 외래 키를 나중에 붙였다(4강 SQL). 순환 참조에서는 한쪽을 먼저 만들 수 없으니, 테이블을 다 만든 뒤 FK를 거는 것이 정석이다.

3. 마이그레이션 연대기: 데이터베이스도 버전 관리된다

확인 28개 마이그레이션을 묶으면 4강의 MVP 흐름과 그대로 겹친다.

구간 마이그레이션 생긴 것
MVP1 V1–V2 members, products, skus, subscriptions
MVP2 V3–V8 Pet·플랜·스냅샷·회차·pending·명령 이력, 멱등 테이블 2종과 completed_at
자동 주문 V9–V11 subscription_orders(+items), 자동화용 인덱스
MVP3 V12–V19 카테고리·RBAC, 재고·장바구니·쿠폰·멤버십, 공통 주문·결제, 배송·환불, 알림·감사 로그
MVP4 V20–V27 비즈니스 키, 리뷰·문의, 장바구니 버전·체크아웃 지문, 카탈로그 확장, 개인화 이벤트, 회차 추가 상품, 리뷰 요약
정리 V28 관리 플래그 이름 변경

이 중 V4 → V8 다섯 개가 마이그레이션 작성의 교과서적인 패턴을 보여 준다. 멱등 결과에 “완료 시각”을 추가해 30일 보관 정리를 가능하게 만든 과정이다(3강 PR #108).

-- V4 / V5: 컬럼을 NULL 허용으로 먼저 추가 (확장)
ALTER TABLE subscription_creation_idempotency_results ADD COLUMN completed_at DATETIME(6) NULL;

-- V6: 기존 행 채우기 (백필) — 고정된 한 시각을 변수로 잡는다
SET @v6_completed_at = UTC_TIMESTAMP(6);
UPDATE subscription_creation_idempotency_results
SET completed_at = @v6_completed_at
WHERE response_status BETWEEN 200 AND 299
  AND response_body IS NOT NULL
  AND completed_at IS NULL;

-- V7 / V8: 정리 작업이 쓸 인덱스 추가
CREATE INDEX idx_creation_idempotency_completed_at
    ON subscription_creation_idempotency_results (completed_at, member_id, idempotency_key);
  • 확장 → 백필 → 인덱스를 다른 파일로 나눈다. 원리 MySQL에서 ALTER TABLE, CREATE INDEX 같은 DDL은 암묵적으로 커밋된다. PostgreSQL과 달리 DDL을 트랜잭션으로 묶어 되돌릴 수 없다. 한 파일에 여러 DDL과 DML을 섞었다가 중간에 실패하면 앞부분만 반영된 어중간한 상태가 남는다. 파일을 나누면 Flyway 이력에 “어디까지 성공했는가”가 정확히 남는다.
  • NULL로 추가한다. 처음부터 NOT NULL로 추가하면 기존 행에 넣을 값이 필요하다. 그런데 기존 행의 “진짜 완료 시각”은 알 수 없다. 4강의 “기록하지 않은 사실은 복원할 수 없다”가 여기서도 나온다.
  • 백필 시각을 변수 하나로 고정한다. UTC_TIMESTAMP(6)를 행마다 부르는 대신 한 번 잡아 모든 행에 같은 값을 넣는다. 해석 “이 행들은 V6 시점에 일괄 백필됐다”는 사실이 데이터에 식별 가능하게 남는다. 보관 기간 계산도 백필 시점부터 30일로 일관된다.
  • 성공한 결과만 채운다. response_status BETWEEN 200 AND 299 AND response_body IS NOT NULL. 처리 중이던(응답이 아직 없는) 행에 완료 시각을 넣으면, 정리 작업이 진행 중인 요청의 멱등 기록을 지울 수 있다.
  • 이미 적용된 마이그레이션은 고치지 않는다. 원리 Flyway는 적용한 파일의 체크섬을 flyway_schema_history에 저장하고, 내용이 바뀌면 시작을 거부한다. 그래서 잘못을 고칠 때도 새 버전 파일을 추가한다. V19(0원 환불 허용), V28(이름 변경)이 그런 예다.

4. 제약 조건이 지키는 업무 규칙

4강과 5강에서 이미 여러 제약을 봤다. 복합 외래 키, PRIMARY KEY (subscription_id)로 pending 최대 하나, 생성 컬럼 UNIQUE가 그것이다. 이번에는 주문 테이블에서 두 가지를 더 본다. 둘 다 CHECK가 단순 범위 검사를 넘어 업무 규칙 자체를 표현하는 예다.

-- V14: orders — 금액 공식이 DB 제약이다
CONSTRAINT chk_orders_amounts CHECK (
  original_amount >= 0 AND discount_amount >= 0 AND shipping_fee >= 0 AND payment_amount >= 0
  AND payment_amount = original_amount - discount_amount + shipping_fee
)

-- V14: order_items — "완전한 스냅샷"이면 모든 스냅샷 컬럼이 있어야 한다
snapshot_quality VARCHAR(30) NOT NULL,
CONSTRAINT chk_order_items_snapshot CHECK (snapshot_quality IN ('FULL','LEGACY_PARTIAL')),
CONSTRAINT chk_order_items_full CHECK (
  (snapshot_quality = 'LEGACY_PARTIAL')
  OR (sku_code_snapshot IS NOT NULL AND product_name_snapshot IS NOT NULL
      AND sku_name_snapshot IS NOT NULL AND unit_price IS NOT NULL AND line_amount IS NOT NULL)
)
  • 금액 공식 CHECK. 결제 금액 = 원가 − 할인 + 배송비. 애플리케이션이 할인을 두 번 적용하는 버그를 내도, 공식이 안 맞는 주문은 저장 자체가 안 된다. 금액이 DECIMAL(18,2)인 것도 중요하다. 원리 DOUBLE은 이진 부동소수점이라 0.1 같은 값을 정확히 표현하지 못해, 등식 비교가 어긋날 수 있다. 돈은 항상 고정소수점(DECIMAL)이다.
  • 조건부 필수 컬럼. A OR B 형태로 “LEGACY_PARTIAL이 아니라면, 스냅샷 컬럼 다섯 개가 모두 있어야 한다”를 표현했다. 원리 논리식 P → Q(P이면 Q)는 NOT P OR Q와 같다. 이 CHECK가 바로 “FULL이면 → 전부 NOT NULL”이다.
  • 왜 LEGACY_PARTIAL이 있나. 6절에서 볼 V15 백필 때문이다. 옛 정기 주문에는 상품명과 단가 스냅샷이 원래 없었다. 없는 값을 지어내지 않고 “이 행은 불완전하다”는 사실을 품질 컬럼으로 기록했다. 4강의 MVP2 이행 원칙(“추측·반올림·절삭하지 않는다”)과 같은 태도다.

5. 인덱스: B-Tree와 컬럼 순서 (깊게)

인덱스를 이해하려면 먼저 그 모양을 알아야 한다. 향로(이동욱)의 「[mysql] 인덱스 정리 및 팁」은 인덱스를 한 줄로 요약한다. “인덱스 == 정렬”. 지정한 컬럼 순서대로 정렬된 목차를 만들어 두는 것이다. 그 목차의 실제 모양이 B-Tree다.

출처: 향로 · [mysql] 인덱스 정리 및 팁.

  • 탐색은 루트 → 브랜치 → 리프 → 데이터 순으로 내려간다. 그림의 예시는 (dept_no, emp_no) 두 컬럼 인덱스다. dept_no = 'd001' AND emp_no = 10018이면 루트와 브랜치를 거쳐 해당 리프 페이지 하나로 바로 간다.
  • 글의 핵심 문장은 이것이다. 두 번째 컬럼은 첫 번째 컬럼에 의존해 정렬돼 있다. 두 번째 컬럼의 순서는 첫 번째 컬럼 값이 같은 구간 안에서만 의미가 있다.
    • 그래서 첫 번째 컬럼 조건 없이 두 번째 컬럼만으로 찾으면, 정렬을 이용하지 못한다.
    • 이것을 가장 왼쪽 접두사 규칙(leftmost prefix)이라 한다.
  • InnoDB는 데이터를 16KB 페이지 단위로 관리한다. 그래서 키가 길수록 한 페이지에 들어가는 항목이 줄어 더 많은 페이지를 읽어야 한다. 5강에서 키 컬럼을 4바이트 utf8mb4 대신 1바이트 ascii로 둔 것이 여기서 이득이 된다.

이 원리로 PawCycle의 자동 주문 인덱스를 읽어 보자.

-- V11__index_due_subscription_schedules.sql
CREATE INDEX idx_schedules_due_automation
    ON subscription_schedules (status, scheduled_date, id, subscription_id);

자동 주문은 대략 “status = 'SCHEDULED'이고 scheduled_date <= 오늘인 회차를 오래된 순으로 N개”를 찾는다(4강).

  • ① status (등호 조건)가 맨 앞이다. 인덱스 안에서 SCHEDULED인 구간이 한 덩어리로 모여 있으니, 그 구간으로 바로 간다.
  • ② scheduled_date (범위 조건)가 그다음이다. 그 구간 안에서는 날짜순으로 정렬돼 있으니, <= 오늘까지 순서대로 읽기만 하면 된다. 결과도 이미 오래된 순이다.
    • 원리 등호 조건 컬럼을 범위 조건 컬럼보다 앞에 둔다가 복합 인덱스 설계의 기본 원칙이다. 순서가 반대인 (scheduled_date, status)라면 어떻게 될까? 날짜 범위 안에 SKIPPED, HELD, CANCELED 회차가 섞여 있어서, 범위 전체를 읽으며 상태를 걸러내야 한다.
  • ③ id, subscription_id가 뒤에 붙는다. 날짜가 같은 회차들의 순서를 id로 결정적으로 고정한다. 자동화가 “구독별 가장 오래된 회차 하나”를 고를 때 필요한 subscription_id도 인덱스에 들어 있다. 그래서 테이블 본문을 읽지 않고 인덱스만으로 후보를 고를 수 있다. 이것을 커버링 인덱스라 한다.

멱등 정리 인덱스 (completed_at, member_id, idempotency_key)도 같은 논리다. “completed_at이 30일 이전인 것”이라는 범위를 맨 앞에 두고, 그 뒤에 삭제할 행의 PK 컬럼을 붙였다.

  • 원리 사실 InnoDB의 보조 인덱스는 리프에 PK 값을 자동으로 함께 저장한다. 보조 인덱스로 찾은 뒤 PK로 본문(클러스터드 인덱스)을 다시 찾아가야 하기 때문이다. 그래서 member_id, idempotency_key를 명시하지 않아도 물리적으로는 들어간다.
  • 해석 그런데도 명시한 이유는 두 가지로 보인다. 정리 쿼리가 PK만 읽어 삭제 대상을 정한다는 의도를 스키마에 드러내고, 컬럼 순서를 확정하기 위해서다.

6. 주문 모델이 두 벌인 이유

이제 ERD의 가장 이상한 부분을 보자. 정기배송 회차 하나를 처리하면 주문 기록이 두 군데 생긴다.

  • 확인 subscription_orders(V9, 8/11): 자동 주문이 처음 만든 정기 주문 전용 테이블이다. 스냅샷 ID, 출처 PlanVersion, 예정일, 처리 시각, 금액을 담는다.
  • 확인 orders + order_items + subscription_order_context(V14, 8/13): MVP3의 공통 주문이다. 일반 구매(source = 'ONE_TIME')와 정기배송('SUBSCRIPTION')이 같은 주문·결제·배송·환불 흐름을 쓴다. 정기 주문이면 subscription_order_context가 어느 구독의 어느 회차인지 연결한다.

이틀 차이로 두 모델이 생긴 사정은 V15에 남아 있다.

-- V15__backfill_legacy_subscription_orders.sql (발췌)
INSERT INTO orders (order_number, member_id, source, status, original_amount, ...)

  • MVP3는 기존 정기 주문을 공통 주문으로 복사했다. 주문 번호는 LEGACY-SUB-{id}로 출처가 드러나게 했다.
  • 상품명·단가 스냅샷이 원래 없었으니 항목은 LEGACY_PARTIAL이다. 4절의 조건부 CHECK가 이 행들을 허용한다.

그런데 확인 그 뒤에도 옛 테이블은 사라지지 않았다. 지금 자동 주문 코드는 한 트랜잭션 안에서 두 곳에 모두 쓴다.

// subscription/automation/SubscriptionOrderProcessor.java (발췌)
if (orderExists(candidate.scheduleId())) {          // 옛 테이블로 "이미 처리됨" 판정
  return ProcessingOutcome.NO_OP;
}
...

    subscription.memberId(), candidate.subscriptionId(), candidate.scheduleId(),
    effectiveSnapshotId, effectiveSnapshot.sourcePlanVersionId(), scheduledDate, ...);

왜 하나로 합치지 않았나.

  • 기록 백엔드 구조 문서에 실마리가 있다. 영속성 계층을 정리할 때 subscription_order_context를 매핑하는 엔티티로 subscription_orders를 대체하는 안을 검토했다. 그러나 “대체하면 처리 완료 판정(processed exclusion)이 바뀐다”는 이유로 하지 않았다.
  • 구독 영역의 여러 쿼리가 “이 회차에 subscription_orders 행이 있는가”로 처리 여부를 판단한다. 자동화 후보 조회, 대사, 회차 조회, 배송 알림이 그렇다. 그 기준을 바꾸면 3·4강의 “회차당 주문 하나” 보장을 처음부터 다시 검증해야 한다.
  • 구독 영속성 정리는 별도 승인 작업으로 미뤄졌다. 문서는 그 조건으로 “엔티티 애그리거트와 잠금 순서 테스트를 먼저 승인한다”를 건다.

이 이중 기록은 위험한가. 원리 분산 시스템에서 “두 곳에 쓰기”(dual write)는 악명 높은 문제다. DB와 메시지 큐처럼 서로 다른 저장소에 쓰면, 한쪽만 성공하고 다른 쪽이 실패하는 순간이 반드시 생긴다. 그런데 여기서는 두 테이블이 같은 MySQL, 같은 트랜잭션 안에 있다. 원자성이 보장되므로 그 고전적인 위험은 없다. 남는 비용은 이것들이다. 해석

  • 진실이 두 군데: “처리됐는가”를 구독 영역은 subscription_orders로, 커머스 영역은 orders로 본다. 지금은 같은 트랜잭션이라 일치하지만, 누군가 한쪽에만 쓰는 코드를 추가하면 조용히 갈라진다.
    • 그 마지막 방어선은 양쪽의 UNIQUE (schedule_id)다. 중복은 막지만 누락은 막지 못한다.
  • 저장과 이해 비용: 같은 사실을 두 번 저장하고, 새로 온 개발자는 “어느 쪽이 원본인가”를 매번 물어야 한다. 이번 강의에서 우리가 그랬듯이.

개선 방향 해석 한쪽으로 수렴하려면 순서가 중요하다. 1. 구독 영역의 처리 여부 판정을 subscription_order_context(또는 orders) 기준으로 바꾸는 쿼리를 만든다. 2. 두 기준이 같은 결과를 내는지 병행 비교 테스트를 둔다. 3. 그다음에야 subscription_orders 쓰기를 멈추고, 마지막에 테이블을 제거한다.

3절에서 본 확장 → 이전 → 축소(expand–contract) 패턴을 테이블 단위로 적용하는 것이다. 23강(자동 주문)과 33강(재설계)의 핵심 과제로 남긴다.

7. 멱등성 테이블 네 종류

3강에서 멱등성의 원리를, 4강에서 그것이 MVP마다 돌아온 과정을 봤다. 물리 스키마에서는 목적이 다른 네 테이블로 나타난다.

테이블 생긴 곳 PK (= 키의 범위) 무엇을 저장하나
subscription_creation_idempotency_results V3 (member_id, idempotency_key) 요청 지문, 응답 전체(상태·본문·Location·ETag), 완료 시각
subscription_command_idempotency_results V3 (member_id, subscription_id, command_type, idempotency_key) 요청 지문, 응답 전체, 완료 시각
checkout_idempotency_results V14 (+V22) (member_id, idempotency_key) 만들어진 주문·결제 ID, 요청 지문(V22에 추가)
quick_reorder_idempotency_results V22 (member_id, idempotency_key) 응답 JSON, 그 시점 장바구니 버전

표에서 읽어 낼 설계 포인트는 다음과 같다.

  • PK가 곧 “같은 요청”의 정의다.
    • 구독 명령은 PK에 subscription_id와 command_type이 들어간다. 그래서 같은 키를 다른 구독이나 다른 명령에 써도 충돌하지 않는다.
    • 5강에서 본 도메인 규칙(“다른 구독 또는 다른 명령 유형의 같은 키는 전역 충돌이 아니다”)이 PK 설계로 굳은 것이다.
    • 모든 PK에 member_id가 있다. 다른 회원의 키와는 절대 섞이지 않는다.
  • 응답을 저장할까, 참조를 저장할까.
    • 구독 테이블은 HTTP 응답을 통째로 저장한다. 재시도 때 그대로 돌려주면 된다. 대신 응답 형식이 바뀌면 옛 기록과 새 형식이 섞인다.
    • 체크아웃 테이블은 주문 ID와 결제 ID만 저장하고, 재시도 때 현재 상태로 응답을 다시 만든다. 결제 상태가 계속 변하니(READY → PROCESSING → …) 과거 응답을 그대로 주면 오히려 틀린다.
    • 해석 결과가 고정되는가, 계속 변하는가에 따라 저장 방식을 다르게 고른 것이다.
  • 응답 컬럼이 NULL 허용인 이유. 구독 테이블의 response_status, response_body는 NULL일 수 있다.
    • 해석 처리를 시작할 때 키와 지문을 먼저 예약해 두고, 끝나면 응답을 채우는 2단계 구조로 보인다. 응답이 아직 NULL인 행은 “처리 중”이라는 뜻이다. 3강의 토스페이먼츠 글이 말한 “앞 요청이 처리 중이면 409” 상황을 판정하는 근거가 된다.
    • 3절의 V6 백필이 응답이 있는 행만 채운 것도 같은 이유다.
    • 미확인 예약과 완료의 실제 코드 흐름은 22·25강에서 확인한다.
  • 체크아웃 지문은 나중에 들어왔다. V14에는 지문 컬럼이 없었다. V22가 request_fingerprint를 NULL 허용으로 추가했다. 그 전에 저장된 행에는 지문이 없으니 NULL로 둘 수밖에 없다. 3절의 “기존 행에 넣을 진짜 값이 없으면 NULL로 확장한다” 원칙 그대로다.
  • 왜 범용 테이블 하나로 합치지 않았나. 해석 (scope, key, payload) 형태의 범용 멱등 테이블 하나로 합칠 수도 있다. 하지만 네 테이블은 키의 범위, 저장 내용, 외래 키 대상(구독 vs 주문·결제)이 모두 다르다. 합치면 FK를 걸 수 없고, 범위 규칙이 문자열 scope 안으로 숨는다. 4강에서 자동 주문이 “HTTP 멱등 행 재사용”을 기각한 것과 같은 판단이다.

6강 정리

  • 개념 → 논리 → 물리: DATA-001(개념) → DATA-002(논리, Proposed) → Flyway V1–V28(물리, 유일한 원본). JPA는 validate로 검사만 한다.
  • 마이그레이션 원칙
    • 적용된 파일은 고치지 않고 새 버전을 추가한다.
    • MySQL DDL은 암묵 커밋되므로 확장 → 백필 → 인덱스를 파일로 나눈다.
    • 진짜 값이 없는 과거 행은 NULL이나 품질 표시(LEGACY_PARTIAL)로 정직하게 남긴다.
  • 제약이 곧 업무 규칙이다.
    • 금액 공식 CHECK, P → Q를 NOT P OR Q로 쓴 조건부 필수 CHECK
    • 돈은 DECIMAL
    • 순환 참조는 테이블을 만든 뒤 FK를 건다.
  • 인덱스 = 정렬된 B-Tree
    • 복합 인덱스는 등호 조건 → 범위 조건 → 정렬·커버링 컬럼 순으로 짠다.
    • InnoDB 보조 인덱스는 PK를 자동으로 품는다.
  • 주문 모델 두 벌: V9 subscription_orders(구독 영역의 처리 사실)와 V14 orders(커머스 공통 주문). 지금도 같은 트랜잭션에서 둘 다 쓴다. 원자성은 지켜지지만 진실이 두 군데다. 수렴은 expand–contract로 해야 한다.
  • 멱등성 테이블 네 종류: PK가 “같은 요청”의 범위를 정한다. 결과가 고정되면 응답을, 변하면 참조를 저장한다.

6강에서 남긴 미확인 항목

  • 멱등 예약(응답 NULL) → 완료로 가는 실제 코드와 409 처리(22·25강)
  • subscription_orders와 orders가 실제로 어긋난 사례가 있었는지, 일치를 검사하는 테스트가 있는지(23강)
  • V11 인덱스를 자동화 쿼리가 실제로 타는지: EXPLAIN 확인은 실험 단계 후보
