3강. 비기능 요구와 위험 지도: 이 시스템은 무엇을 두려워하는가

이번 강의의 목표

  • 기능 요구(“무엇을 하는가”)와 비기능 요구(“얼마나 잘, 얼마나 안전하게 하는가”)를 구분한다.
  • PawCycle의 다섯 가지 비기능 축이 어떤 실제 사건과 측정에서 나왔고, 어떤 기술 선택으로 이어졌는지 연결한다.
  • 네트워크·OS 쪽에서는 두 가지를 깊게 본다.
    • “정확히 한 번”이 왜 불가능하고 멱등성이 왜 그 대안인가
    • TIME_WAIT와 임시 포트 고갈은 왜 생기는가
  • 마지막에 위험 지도를 만든다. 남은 강의에서 무엇을 깊게 볼지 정하는 기준이 된다.

1. 비기능 요구란 무엇이고, 이 프로젝트에서는 무엇인가

“주문을 생성한다”, “구독을 변경한다”는 기능 요구다. 그런데 같은 기능이라도 다음 질문에 어떻게 답하느냐에 따라 코드가 완전히 달라진다.

  • 버튼을 두 번 누르면 주문이 두 개 생기는가?
  • 결제사 응답이 안 오면 돈은 빠져나갔는가?
  • 서버가 죽으면 누가 언제 알게 되는가?

이런 “얼마나 잘”에 대한 요구를 비기능 요구(품질 속성)라 한다. 문제는 비기능 요구가 요구사항 문서에 잘 적히지 않는다는 점이다. 보통은 사고가 나고 나서야 드러난다.

PawCycle도 그랬다. README는 이 프로젝트를 “기술을 먼저 늘리기보다 현재 구조에서 문제를 재현·측정하고, 필요가 확인될 때 다음 기술을 선택한다”고 소개한다. 그래서 이 프로젝트의 비기능 요구는 문서의 선언보다 사건과 측정 기록에서 더 정확히 읽힌다. 아래 다섯 축이 그 결과다.

다섯 축 중 첫 번째가 가장 무겁다. 이커머스에서 돈과 재고가 틀리는 것은 느린 것보다 훨씬 나쁘다. 느리면 사용자가 기다리지만, 두 번 결제되면 환불과 신뢰 문제가 생긴다.

2. 정합성·멱등성: “정확히 한 번”은 왜 불가능한가 (깊게)

네트워크는 “응답이 안 왔다”와 “처리가 안 됐다”를 구분해 주지 않는다

사용자가 “결제하기”를 눌렀는데 응답이 오지 않았다고 하자. 가능한 경우는 셋이다.

  1. 요청이 서버에 도착하지 못했다. 아무 일도 일어나지 않았다.
  2. 서버가 처리하는 중에 죽었다. 일부만 일어났을 수 있다.
  3. 서버는 처리를 끝냈는데 응답이 돌아오다 사라졌다. 결제는 이미 됐다.

원리 클라이언트 쪽에서는 이 셋이 똑같이 “타임아웃”으로 보인다. 분산 시스템에서 유명한 두 장군 문제(Two Generals' Problem)가 이것이다. 메시지가 사라질 수 있는 통신로에서는, 상대가 받았다는 확인조차 사라질 수 있다. 그래서 양쪽이 “확실히 합의했다”고 확신할 방법이 없다. 결과적으로 클라이언트가 고를 수 있는 전략은 둘뿐이다.

  • 재시도하지 않는다 → 최대 한 번(at-most-once): 3번 경우가 아니었다면 결제가 누락된다.
  • 재시도한다 → 최소 한 번(at-least-once): 3번 경우였다면 결제가 두 번 된다.

“정확히 한 번 전달(exactly-once delivery)”은 네트워크 수준에서 보장할 수 없다. 대신 실무에서는 “최소 한 번 전달 + 받는 쪽의 중복 제거” 로 “정확히 한 번의 효과(effect)” 를 만든다. 그 중복 제거 장치가 멱등성이다.

토스페이먼츠의 「멱등성이 뭔가요?」가 이 흐름을 결제 취소 예제로 설명한다.

  • 결제 API가 멱등하지 않으면 타임아웃 후 실제 결제 여부를 사람이 확인해야 한다.
  • 멱등하면 같은 요청을 다시 보내 못 받은 결과만 다시 받을 수 있다.
  • 서버는 Idempotency-Key 헤더의 키로 요청 기록을 저장하고, 같은 키가 다시 오면 처리하지 않고 저장된 응답을 돌려준다.
  • 같은 키에 다른 본문이 오면 422, 앞 요청이 아직 처리 중이면 409로 거절하라는 IETF 초안의 권고도 소개한다.

글의 결제 취소 흐름 그림은 원문에서 보면 된다. 토스페이먼츠가 콘텐츠의 무단 전재를 금하고 있어, 여기서는 직접 싣지 않고 같은 구조를 도식으로 다시 그린다.

그림에서 가장 중요한 칸은 가운데 초록 상자다. 업무 처리와 결과 저장이 한 트랜잭션이어야 한다.

  • 처리만 커밋되고 저장이 빠지면, 재시도가 왔을 때 기록이 없으니 다시 처리한다. 이중 결제다.
  • 저장만 되고 처리가 빠지면, 결과가 거짓이 된다.

PawCycle에서 이 원리가 어디에 쓰였는지 보자.

  • 확인 체크아웃, 구독 명령 등에 멱등 결과 테이블이 4개 있다.
    • 키만 보지 않고 요청 내용의 지문(fingerprint)을 함께 저장한다. 같은 키로 다른 내용을 보내는 요청을 구분하기 위해서다. 토스페이먼츠 글의 422 상황과 같은 문제를 푸는 장치다.
    • 미확인 지문이 다를 때 돌려주는 HTTP 상태 코드는 17강에서 코드로 확인한다.
  • 기록 멱등 기록도 영원히 둘 수는 없다. 성공 결과를 다시 보낼 수 있게 유지하면서 데이터가 무한히 늘지 않도록 완료 시각 기준 30일 보관 + 한 번에 정해진 양만 지우는 정리(bounded cleanup) 를 넣었다. 정리 작업과 replay가 경쟁하는 경우도 검증했다(PR #108). 토스페이먼츠 글이 말한 “멱등키의 유효 기간”과 같은 개념이다.
  • 기록 멱등성 장치 자체가 사고를 냈다. 체크아웃은 처음에 멱등 행을 SELECT ... FOR UPDATE로 잠갔다. 그런데 아직 없는 행을 잠그면 InnoDB는 그 자리의 간격(gap) 을 잠근다. 서로 다른 회원의 INSERT가 같은 간격에 걸려 교착 상태(deadlock)가 났고, 그 잠금은 제거됐다(PR #332). 간격 잠금의 원리는 17강에서 깊게 본다.
  • 기록 외부 결제는 멱등 테이블만으로 해결되지 않는다. 결제사 승인은 우리 DB 트랜잭션 밖에서 일어난다. 그래서 위 그림의 초록 상자처럼 “한 트랜잭션”으로 묶을 수 없다.
    • PawCycle은 결제를 PROCESSING으로 먼저 기록하고, 토스를 호출한 뒤, 결과를 반영한다. 응답을 알 수 없으면 UNKNOWN으로 남긴다.
    • 그 사이에 서버가 죽으면 PROCESSING에 고립된 결제가 남을 수 있다(이슈 #417). 결제사에 상태를 조회만 하는 1단계는 들어갔고(PR #450), 자동으로 바로잡는 2단계는 아직이다. 18·19강의 핵심 주제다.
  • 기록 실패를 가두는 것도 정합성이다. 정기배송 배치가 여러 구독을 한 트랜잭션에서 처리하면, 구독 하나의 실패가 배치 전체를 롤백시킨다. 그래서 구독마다 독립 트랜잭션으로 나눠, 실패한 구독만 롤백하고 나머지는 계속 처리하게 했다(PR #106).

3. 보안·개인정보: 응답이 같아도 시간은 다를 수 있다

보안 축의 기본 장치는 1강과 2강에서 봤다.

  • 세션 로그인과 CSRF 헤더 (11강)
  • /api/admin/**는 ADMIN만, 나머지는 기본 거부
  • Nginx 로그인 속도 제한

여기서는 눈에 잘 띄지 않는 두 가지 위험을 본다.

타이밍 부채널: 응답 본문이 같아도 정보가 샌다

기록 로그인 기능의 첫 초안은 이렇게 동작했다(PR #34).

  • 가입되지 않은 이메일 → DB에 회원이 없으니 즉시 401
  • 가입된 이메일 + 틀린 비밀번호 → BCrypt로 비밀번호를 비교한 뒤 401

두 경우 모두 응답은 똑같은 401 JSON이다. 하지만 원리 BCrypt는 일부러 느리게 만든 해시 함수다. 비밀번호 대입 공격을 늦추려고 비교 한 번에 수십~수백 ms를 쓴다. 그러니 가입된 이메일에서만 응답이 눈에 띄게 늦다. 공격자는 응답 시간만 재서 “이 이메일은 가입돼 있다”를 알아낼 수 있다. 이런 공격을 타이밍 부채널 공격이라 한다.

  • 고친 방식: 시작할 때 무작위 더미 해시를 한 번 만들어 둔다. 가입되지 않은 이메일에도 그 더미 해시로 BCrypt 비교를 정확히 한 번 수행해 두 경로의 비용을 맞췄다. 요청마다 새로 해시를 만드는 방식은 쓰지 않았다. 그렇게 하면 비용이 오히려 달라지기 때문이다.
  • 증명한 범위: 두 실패 경로의 비교 횟수, 응답, 미인증 상태 유지까지만 테스트로 확인했다(PR #38). 기록 모든 타이밍 차이가 통계적으로 사라졌다는 실측은 없다. 형식이 틀린 이메일의 검증 경로도 같은 비용이라는 주장은 아니다.
  • 이후 인증 책임은 Spring Security의 AuthenticationProvider 구조로 옮겨졌다. 11강에서 현재 코드로 다시 확인한다.

로그에 새는 개인정보

기록 정기결제 처리의 INFO 로그에 회원 ID가 그대로 찍히는 부분을 제거했다. 그리고 Java 소스의 구문 트리(AST)를 검사하는 테스트를 넣었다(PR #298). 비밀번호·토큰·세션·CSRF·결제·빌링키 같은 값을 로거 인자로 직접 넘기면 빌드가 실패한다.

  • 한계 기록: 이 검사는 직접 인자만 본다. 변수에 담았다가 넘기거나, 예외 메시지 안에 섞여 들어가는 경로(데이터 흐름, taint)는 추적하지 않는다.
  • 해석 정적 검사는 “실수로 찍는 것”을 싸게 막는 1차 방어선이다. 완전한 보장이 필요하면 로그 출력 단계에서 패턴을 가리는 마스킹 필터를 추가로 둬야 한다. 비용(성능, 오탐)과 보장 수준의 트레이드오프다.

4. 가용성·복구: “200 OK”는 무엇을 증명하는가

어디서 재느냐가 결과를 바꾼다

기록 2026-08-14, AWS 운영 환경에서 일부러 장애를 내는 훈련(drill)을 했다(이슈 #146).

  • backend 컨테이너 하나만 멈췄다.
  • Prometheus의 backend 대상은 up → down → up으로 정확히 변했다.
  • 그런데 backend가 멈춘 동안에도 /products 페이지는 HTTP 200이었다. 프론트 페이지는 backend에 실제로 묻지 않고도 200을 돌려줄 수 있기 때문이다.

교훈은 “검사가 어떤 실행 경계를 지나가는가”를 알아야 한다는 것이다. 이후 backend API, Docker 헬스 상태, 메트릭 수집 대상을 함께 읽는 진단 도구가 만들어졌다(이슈 #147).

이 교훈을 2강의 설정에 대 보면 흥미로운 점이 보인다.

  • backend 헬스체크는 /api/products로 backend 자신을 검사한다. 옳다.
  • proxy 헬스체크는 127.0.0.1:8081/products다. 이 경로는 Nginx → frontend로만 간다.
  • 해석 그래서 proxy가 healthy라는 것은 “Nginx와 frontend 경로가 산다”까지만 증명하고, backend 상태는 증명하지 않는다. depends_on: condition: service_healthy는 시작 순서만 보장할 뿐, 실행 중 backend가 죽은 것은 proxy 헬스에 반영되지 않는다. 이것이 의도된 설계인지는 29강에서 배포 검증 스크립트와 함께 확인한다.

Dale Seo의 「SLI, SLO, SLA 정리」도 같은 지점을 짚는다. 같은 “성공률”이라도 서버 로그로 재면 서버까지 도달한 요청만 세고, 로드 밸런서에서 재면 서버가 죽어 응답하지 못한 요청까지 센다. 사용자에게 가까운 곳에서 잴수록 정직한 지표가 된다.

SLO가 없다는 것의 의미

  • 확인 README는 성능 수치를 소개하면서 “Production SLO나 현재 Production 성능으로 표현하지 않는다”고 명시한다. 즉 이 서비스에는 아직 SLO(서비스 수준 목표)가 없다.
  • 원리 SLO는 “어떤 지표를, 어느 값 이상으로, 어느 기간 동안”의 세 요소로 이루어진다. 예를 들어 99.9%/30일은 한 달에 약 43분, 99%/30일은 약 7시간 12분의 장애를 허용한다. 이 숫자가 있어야 “지금 알림을 울릴 만큼 나쁜가”, “이번 배포는 위험을 감수해도 되는가”를 판단할 수 있다.
  • 해석 2강에서 본 단일 서버, 수동 배포, 무중단 배포 보류는 SLO가 없기 때문에 정당화되는 선택이기도 하다. 포트폴리오에서 “가용성 목표를 정하지 않은 상태에서 비용 0을 우선했다”고 정확히 말하는 편이, 근거 없는 “고가용성”보다 강하다.

복구: 아직 증명되지 않은 것

  • 확인 운영 개요 문서는 OCI 환경에서 다음 항목을 검증하지 않았다고 적는다. 애플리케이션 롤백, 인증서 갱신 중단 복구, DB 백업·특정 시점 복구(PITR)·복원, 전체 알림 연결, 로그인·주문 같은 업무 흐름이다.
  • AWS 시절에는 S3 논리 백업과 격리 복원을 실제로 했던 기록이 남아 있다(30강).
  • 원리 백업은 복원해 보기 전까지 백업이 아니다. 복구 목표는 보통 두 숫자로 말한다.
    • RPO(Recovery Point Objective): 얼마만큼의 데이터를 잃어도 되는가
    • RTO(Recovery Time Objective): 얼마 안에 되살려야 하는가
    • PawCycle은 둘 다 아직 정의돼 있지 않다.

5. 성능·비용: 측정이 직관을 뒤집은 세 사건 (깊게)

이 축의 원칙은 README 그대로다. 최적화를 먼저 하지 않고, 측정한 뒤 고친다. 세 사건이 이 원칙을 잘 보여 준다.

사건 1: N+1, 측정하고 나서 고쳤다

기록 페이지 크기를 바꿔 가며 API 하나가 실행하는 SQL 수를 먼저 쟀다(PR #102). 그다음 batch 조회로 바꾸고 같은 조건에서 다시 쟀다(PR #103).

API 개선 전 10 / 20 / 100건 개선 후 10 / 20 / 100건
Plans 32 / 52 / 212 14 / 14 / 14
Subscriptions 51 / 91 / 411 15 / 15 / 19

개선 전 쿼리 수가 페이지 크기에 비례해 늘어난다는 것이 N+1의 지문이다. 개선 후에는 거의 상수다. 원리와 JPA의 해결 방법(fetch join, @BatchSize, DTO 조회)은 9강과 13강에서 본다.

사건 2: 커넥션 풀을 늘렸더니 더 나빠졌다

기록 로컬 부하 실험에서 HikariCP 커넥션이 10개 모두 사용 중이고 대기 요청이 117개까지 쌓였다. 직관적인 처방은 “풀을 늘리자”다.

후보 실제 처리량 버려진 요청 p95
기준(CPU 1.5, 풀 10) 약 154 RPS 10,497 약 8.0초
풀 10 → 20 약 142 RPS (악화) 11,950 약 8.0초
CPU 1.5 → 2.0, 풀 10 약 193 RPS (개선) 5,808 —

(이슈 #191, #193, #195)

  • 해석 커넥션 대기는 증상이지 원인이 아니다. CPU가 부족하면 각 요청이 커넥션을 쥐고 있는 시간이 길어지고, 그래서 대기가 쌓인다. 이 상태에서 풀을 늘리면 더 많은 요청이 동시에 CPU와 DB를 두고 경쟁해 오히려 느려진다.
  • 그래서 풀 20은 기각하고 원래대로 돌렸다. CPU 증설은 처리량을 올렸지만 대기가 여전히 남아 부분 원인으로만 판정했다.

커넥션 풀이 단순히 “부족”한 것을 넘어 완전히 멈추는 경우도 있다. 우아한형제들의 「HikariCP Dead lock에서 벗어나기 (이론편)」이 그 사례다.

  • 메시지 플랫폼에서 소비 스레드 16개가 크기 10인 풀을 나눠 썼다.
  • 메시지 하나를 저장하는 트랜잭션이 커넥션을 동시에 2개 필요로 했다.
  • 스레드들이 커넥션 1개씩을 쥔 채 두 번째 커넥션을 서로 기다리며 멈췄다.

출처: 우아한형제들 기술블로그 · HikariCP Dead lock에서 벗어나기 (이론편), 이재훈. 이미지가 자리표시자로 보이면 링크에서 원문 그림을 볼 수 있다.

  • 그림에서 각 스레드는 커넥션 하나를 이미 쥐고 있고, 풀은 비어 있다. 아무도 두 번째 커넥션을 얻지 못하니 아무도 첫 번째를 반납하지 못한다. 2강에서 본 교착 상태 조건(점유하며 대기, 순환 대기)이 DB 행이 아니라 커넥션 풀에서 성립한 것이다.
  • 글은 교착을 피하는 최소 풀 크기를 스레드 수 × (작업당 동시 필요 커넥션 수 − 1) + 1로 제시한다.
  • 해석 PawCycle과의 연결: 한 요청이 커넥션 2개를 동시에 쥐는 대표적인 경우는 바깥 트랜잭션이 열린 채 REQUIRES_NEW로 새 트랜잭션을 여는 것이다. 리뷰 요약 Slice에서 트랜잭션을 나눈 방식이 이 패턴에 해당하는지는 15강에서 코드로 확인한다.

사건 3: 포트가 바닥났다 — TIME_WAIT와 임시 포트 (깊게)

기록 로컬 부하 실험에서 초당 832건을 처리한 것처럼 보였다. 그런데 오류율이 44.7% 였다(이슈 #166, PR #167).

  • Nginx 로그에는 backend로 연결할 때 EADDRNOTAVAIL(쓸 수 있는 주소 없음)과 502가 찍혔다.
  • proxy 컨테이너의 TIME_WAIT 소켓은 26개에서 약 28,300개로 늘었다.
  • 이 502는 Spring까지 오지도 않았으니 Spring의 메트릭에는 보이지 않았다. 4절의 “어디서 재느냐” 문제가 성능에서도 그대로 나타난 것이다.
  • 목표를 초당 250건으로 맞추면 오류 0%였고, 500건에서는 오류 10.8%로 실패했다.

왜 이런 일이 생기는지 OS 수준에서 보자.

그림의 숫자가 기록과 맞아떨어지는지 확인해 보자.

  • 원리 연결 하나는 네 값으로 구분된다. 2강에서 본 (출발 IP, 출발 포트, 목적지 IP, 목적지 포트)다. Nginx → backend 연결은 출발 IP, 목적지 IP, 목적지 포트(8080)가 모두 고정이다. 달라질 수 있는 것은 출발 포트 하나뿐이다. 리눅스는 이 출발 포트를 임시 포트 범위(기본 32768–60999, 28,232개)에서 골라 쓴다. 기록에 남은 포트 범위가 바로 이 값이다.
  • 원리 TIME_WAIT는 버그가 아니라 안전장치다. TCP 연결을 먼저 닫은 쪽은 소켓을 바로 버리지 않고 일정 시간 TIME_WAIT 상태로 둔다. 이유는 두 가지다.
    • 내가 보낸 마지막 ACK가 사라졌다면 상대가 FIN을 다시 보낼 것이다. 그때 다시 답하려면 소켓이 남아 있어야 한다.
    • 네트워크를 떠돌던 옛 연결의 늦은 패킷이, 같은 네 값을 재사용한 새 연결에 섞여 들어가는 것을 막는다.
    • 리눅스는 이 시간을 60초로 고정해 두었다.
  • 해석 계산이 기록과 맞는다. 포트 28,232개를 각각 60초씩 붙잡으면, 같은 목적지로 만들 수 있는 새 연결은 초당 약 470개가 상한이다.
    • 목표 250건에서 오류가 0이고 500건에서 실패한 결과가 이 상한과 일치한다.
    • TIME_WAIT가 약 28,300개까지 쌓인 것은 포트 범위를 거의 다 쓴 상태다.
    • 처음의 “초당 832건”은 실제 처리량이 아니었다. 포트가 없어 즉시 실패한 502가 빠르게 쌓인 숫자였다. 빠른 실패는 처리량으로 세면 안 된다.
  • 해법과 트레이드오프.
    • upstream keepalive: Nginx가 backend 연결을 닫지 않고 재사용한다. 근본 해법이다. 다만 upstream 블록의 keepalive N, proxy_http_version 1.1, 빈 Connection 헤더가 함께 있어야 동작한다.
    • 커널 튜닝: 포트 범위를 넓히거나 tcp_tw_reuse를 켜는 방법도 있지만, 증상을 미루는 성격이 강하다.
    • 기록 이 개선은 측정 PR에 섞지 않고 다음 단계로 넘겼다. 측정과 개선을 한 PR에 섞으면 무엇이 효과를 냈는지 알 수 없기 때문이다.
    • 미확인 현재 운영 설정에 upstream keepalive가 들어갔는지는 28강에서 확인한다. 2강에서 본 proxy_http_version 1.1은 필요조건의 하나일 뿐이다.

2강 보충: 640MB 컨테이너의 실제 OOM 기록

2강에서 “힙 밖 메모리 실측은 미확인”이라고 했는데, AWS 시절 기록이 이 질문에 답을 준다.

  • 기록 단일 backend + RDS 구성에서 초당 200건은 정상이었다. 250건에서 실패했다. 오류율 약 6.9%, p95 약 4.2초, backend 재시작 1회였다(이슈 #166, #168).
  • 커널 로그의 cgroup OOM kill 시각과 재시작 시각을 대조해, 종료 원인을 컨테이너 OOM으로 확정했다.
  • 그 순간 힙은 274MiB / 최대 402MiB로 여유가 있었다. 힙 밖 메모리는 152MiB였고, 스레드는 217개였다.
  • 즉 2강 그림의 오른쪽 상자(커널이 죽임, exit 137) 가 실제로 일어난 것이다. 원인은 힙이 아니라 스레드 스택과 네이티브 메모리를 포함한 전체 메모리 압력이었다.
  • 기록 스레드와 네이티브 메모리가 각각 얼마를 차지했는지는 NMT 측정이 없어 가설로 남겼다. 풀과 힙을 바로 늘리지 않고, 동시 요청 수·커넥션 점유 시간·스레드 예산을 같은 조건에서 실험하는 과제로 넘겼다.
  • 스레드 217개라는 숫자를 2강의 pids_limit: 256과 나란히 놓아 보자. 메모리가 먼저 터지지 않았다면 다음은 스레드 한도였을 수 있다. 해석

6. 관측: 모르는 것을 “정상”이라고 말하지 않기

관측 축의 핵심은 정직한 판정이다. 운영 상태 알림 스크립트의 판정 규칙이 이를 잘 보여 준다.

# docs/runbook/OPS-AUTO-010 — 판정 결과별 동작 (요지)
NORMAL                   → 알림 없이 종료
BACKEND_DOWN             → Discord와 Slack에 각각 독립적으로 전송 시도
OBSERVABILITY_DEGRADED   → 〃
DEGRADED                 → 〃
UNKNOWN                  → 〃
형식이 깨졌거나 믿을 수 없는 입력 → UNKNOWN (fail-closed)
알림 전송 결과는 운영 상태 판정을 바꾸지 않음
  • OBSERVABILITY_DEGRADED가 따로 있다. “backend는 살아 있는데 감시 장치가 고장 났다”는 상태를 구분한다. 감시가 죽은 것을 “장애 없음”으로 읽으면, 4절의 /products 200처럼 조용한 거짓 정상이 된다.
  • fail-closed: 입력을 해석할 수 없으면 정상으로 넘기지 않고 UNKNOWN으로 알린다.
    • 원리 보안의 기본 거부(anyRequest().denyAll())와 같은 사고방식이다. 모를 때는 안전한 쪽으로 실패한다.
    • 알림 쪽에서 안전한 실패는 “일단 사람을 부르는 것”이다. 그 대가로 거짓 알람이 늘 수 있는데, 이것이 트레이드오프다.
  • 두 채널에 독립 전송: Discord가 실패해도 Slack 전송은 시도한다. 한 채널의 장애가 알림 전체를 막지 않게 한 것이다.
  • 기록 측정 자체의 정직성도 반복된 주제였다. 다음을 구분하지 않으면 Before/After 비교가 무효가 된다.
    • 측정 실패: 부하 도구가 목표만큼 요청을 보내지 못했다.
    • 수집 실패: Prometheus가 값을 긁어 오지 못했다.
    • 표본 부재: 비교할 데이터가 아예 없었다.
    • 이것은 28강(성능 측정의 방법과 실패)의 주제다.
  • 확인 실제 Webhook 생성, 비밀 배치, 운영 전송은 별도 승인 뒤에만 하도록 문서에 경계가 그어져 있다. 운영 개요 문서도 OCI에서 “전체 알림 연결”은 검증하지 않았다고 적는다. 2강에서 지적한 “같은 서버에 있는 감시자” 문제와 함께, 이 축은 설계는 있으나 운영 증명은 남은 상태다.

해석 이 표에서 영향이 “매우 큼”인 위험은 모두 돈과 데이터에 관한 것이다. 그래서 1강의 로드맵이 Part 7·8(구매·정기배송)에 가장 많은 강의를 배정했다. 이 위험 지도가 그 배분의 근거다.

3강 정리

  • 비기능 요구는 “얼마나 잘”에 대한 요구다. PawCycle에서는 문서보다 사건과 측정 기록에서 더 정확히 드러난다.
  • 정합성
    • 네트워크에서 “정확히 한 번 전달”은 불가능하다.
    • 그래서 최소 한 번 전달 + 멱등성으로 “정확히 한 번의 효과”를 만든다.
    • 핵심은 처리와 결과 저장을 한 트랜잭션에 묶는 것이다. 외부 결제처럼 묶을 수 없는 곳이 가장 위험하다.
  • 보안
    • 응답 본문이 같아도 응답 시간으로 정보가 샐 수 있다(타이밍 부채널).
    • 정적 로그 검사는 직접 인자만 막는다.
  • 가용성
    • “200 OK”는 그 검사가 지나간 경계까지만 증명한다.
    • SLO·RPO·RTO가 아직 없다. 이 사실이 단일 서버 선택의 맥락이다.
  • 성능
    • 커넥션 대기는 증상이고 풀 증설은 악화를 불렀다.
    • TIME_WAIT 60초 × 임시 포트 28,232개가 초당 약 470 연결이라는 상한을 만든다.
    • 640MB 컨테이너는 힙이 아니라 전체 메모리로 죽었다.
  • 관측: 모를 때는 정상이라 하지 않는다(fail-closed). 감시 장치의 고장도 별도 상태로 판정한다.

3강에서 남긴 미확인 항목

  • 멱등 지문이 불일치할 때의 응답 코드
  • 리뷰 요약의 트랜잭션 분리가 커넥션 2개를 동시에 쥐는지
  • proxy 헬스체크가 backend를 보지 않는 것이 의도인지
  • 운영 Nginx의 upstream keepalive 적용 여부
