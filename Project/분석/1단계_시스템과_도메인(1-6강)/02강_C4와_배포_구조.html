2강. C4로 본 시스템, 그리고 요청이 서버에 닿기까지

기준: GitHub main = f9ab9f87 · 깊이: L1 + 네트워크·OS 개념 L3 표시: 확인 코드·설정 · 기록 문서·PR·이슈의 결정 · 해석 내 판단 · 원리 일반 지식 · 미확인

이번 강의의 목표

  • C4 모델로 PawCycle을 System Context → Container 수준에서 그릴 수 있다
  • 운영 Compose의 세 컨테이너와 세 네트워크가 각각 왜 그렇게 나뉘었는지 설명한다
  • 브라우저가 주소를 치는 순간부터 Spring 컨트롤러에 닿기까지 DNS → TCP → TLS → HTTP → 리버스 프록시 과정을 설명한다
  • 컨테이너가 사실은 namespace와 cgroup으로 둘러싼 프로세스라는 것, 그리고 그것이 JVM 메모리 설정과 어떻게 연결되는지 설명한다
  • Nginx 보안 설정, 인증서 갱신, 배포 구조의 트레이드오프를 설명한다

깊이 배분: 3절(요청의 여정)과 5절(컨테이너와 OS), 6절(JVM 메모리)을 가장 깊게 다룬다.

1. C4 모델: 지도를 네 배율로 그리는 법

아키텍처 그림이 쓸모없어지는 가장 흔한 이유는 한 장에 모든 것을 그리려 하기 때문이다. 사용자, 서버, 클래스, 테이블이 한 그림에 섞이면 아무도 읽지 못한다. C4 모델은 지도 앱처럼 배율을 나눈다.

  • Level 1 System Context: 우리 시스템을 상자 하나로 두고, 누가 쓰고 어떤 외부 시스템과 이야기하는가
  • Level 2 Container: 시스템을 따로 실행되는 단위(웹 앱, API 서버, DB)로 쪼갠다
  • Level 3 Component: 컨테이너 하나 안의 주요 구성 요소와 책임
  • Level 4 Code: 클래스 수준. 대부분 코드에서 자동 생성하고 손으로 그리지 않는다

teamsmiley의 「C4 model introduce」가 네 단계를 레벨별로 정리하고, 코드 다이어그램은 손으로 그리기보다 자동 생성을 권한다고 적는다. 아래는 C4를 만든 Simon Brown의 공식 사이트에 있는 Container 다이어그램 예시다.

출처: c4model.com · Container diagram, Simon Brown, CC BY 4.0. 원본을 열어 내용을 확인했다.

이 그림에서 볼 점은 세 가지다.

  • 파란 테두리 안이 시스템 하나이고, 그 안의 상자(UI, Backend, Database)가 Container다. 바깥의 초록 사람과 빨강·주황 상자는 사용자와 외부 시스템이다.
  • 화살표마다 “무엇을, 어떤 방식으로” 가 적혀 있다(“Makes API requests to [JSON/HTTPS]”). 선만 긋고 끝내지 않는다.
  • 여기서 Container는 Docker 컨테이너가 아니다. “따로 배포·실행되는 단위”라는 뜻이다. 우연히 PawCycle에서는 둘이 거의 일치하지만, 개념은 구분해야 한다.

PawCycle의 System Context

PawCycle을 상자 하나로 놓으면 다음과 같다.

  • 사람은 둘이다. 비회원·회원 고객과 관리자다. 확인 관리자 기능은 /api/admin/**가 hasRole("ADMIN")으로 분리돼 있다.
  • 외부 시스템은 둘이다. 토스는 결제 승인과 조회, OpenAI는 리뷰 요약·상품 비교·추천에 쓰인다. 점선은 설정으로 켰을 때만 존재하는 연결이다. 확인 AI 기능은 모두 기본값이 꺼짐이다.
  • 해석 이 그림에서 가장 중요한 정보는 “외부 시스템이 둘뿐”이라는 사실이다. 이 시스템의 정합성 설계가 대부분 “잠금 + DB 트랜잭션”으로 풀리고, 복잡한 상태(PROCESSING, UNKNOWN)는 이 두 외부 경계에서만 생기는 이유가 여기 있다.

2. Container 수준: 세 컨테이너와 세 네트워크

1강에서 컨테이너 셋(proxy, frontend, backend)을 봤다. 이번에는 그 컨테이너들이 어떤 네트워크에 붙어 있는가를 본다. 이 설계가 보안 경계를 만든다.

# infra/production/compose.yaml (발췌)
services:
  backend:
    expose: ["8080"]                        # 다른 컨테이너에게만 공개
    networks: [app, database-egress]
  frontend:
    expose: ["3000"]
    networks: [app]
  proxy:
    ports:
      - "${PAWCYCLE_HTTP_PORT:-80}:80"      # 호스트 포트 → 컨테이너 포트
      - "${PAWCYCLE_HTTPS_PORT:-443}:443"
    networks: [edge, app]

networks:
  edge:
    name: pawcycle-production-edge
  app:
    name: pawcycle-production-app
    internal: true                          # 바깥으로 나가는 길이 없는 네트워크
  database-egress:
    name: pawcycle-production-database-egress

코드에서 읽어야 할 것은 두 가지다.

  • ports와 expose는 다르다. ports는 호스트의 포트를 컨테이너 포트로 연결해 인터넷에서 닿을 수 있게 한다. expose는 같은 네트워크의 다른 컨테이너에게만 포트를 알린다. 인터넷에서 닿는 컨테이너는 proxy 하나뿐이다.
  • internal: true 인 app 네트워크는 원리 외부로 나가는 경로(게이트웨이)가 없는 네트워크다. 그 네트워크에만 붙은 컨테이너는 같은 네트워크의 이웃과만 통신하고 인터넷으로 나갈 수 없다.

이 설정을 그림으로 옮기면 다음과 같다.

주황색 화살표가 암호화된 구간이다. 브라우저와 Nginx 사이만 암호화되고, Nginx와 Spring 사이(⑥⑦)는 평문 HTTP다. 이 구조를 TLS 종료(TLS termination) 라고 한다. 단계별로 내려가 보자.

①② DNS: 이름을 주소로 바꾸기

컴퓨터는 이름이 아니라 IP 주소로 통신한다. 브라우저는 먼저 OS에 이름을 묻고, OS는 설정된 재귀 리졸버(보통 통신사나 공용 DNS)에 묻는다. 리졸버는 답을 모르면 계층을 따라 내려간다.

  • 루트 서버에 묻는다 → “.org는 이 TLD 서버에 물어라”
  • TLD 서버(.org)에 묻는다 → “duckdns.org는 이 권한 서버에 물어라”
  • 권한 네임 서버(DuckDNS)에 묻는다 → “pawcycle.duckdns.org의 A 레코드는 이 IP다, TTL은 N초”

리졸버는 받은 답을 TTL 동안 캐시한다. 그래서 두 번째 사용자부터는 루트까지 가지 않는다. 대신 IP를 바꾸면 TTL이 끝날 때까지 옛 주소로 가는 사용자가 생긴다. Dale Seo의 「DNS 서버 동작 원리」가 이 질의 흐름을 단계별로 따라가고, 캐시와 TTL이 응답 속도와 변경 반영 지연에 어떤 영향을 주는지 설명한다.

트레이드오프: 왜 무료 동적 DNS인가? 해석 DuckDNS는 무료이고 IP가 바뀌어도 갱신할 수 있지만, 레코드 종류와 TTL 조절, 장애 시 지원을 직접 통제하지 못한다. 개인 프로젝트에서 비용을 0으로 유지하려는 방향(뒤의 8절)과 같은 선택이다. 실제 서비스라면 자기 도메인과 관리형 DNS를 쓰는 것이 기본이다. 미확인 DuckDNS를 고른 기록은 찾지 못했다.

③ TCP: 연결을 맺는 세 번의 악수

IP를 알았으면 그 주소의 443번 포트로 TCP 연결을 맺는다. TCP는 데이터가 순서대로, 빠짐없이 도착하도록 보장하는 프로토콜이고, 그 전에 양쪽이 준비됐는지 확인하는 3-way handshake를 한다.

  1. 클라이언트 → 서버: SYN (연결하고 싶다, 내 시작 번호는 x)
  2. 서버 → 클라이언트: SYN-ACK (좋다, x+1을 기다리겠다, 내 시작 번호는 y)
  3. 클라이언트 → 서버: ACK (y+1을 기다리겠다)

원리 연결 하나는 (출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트) 네 값으로 구분된다. 서버 쪽에서 443을 듣는 소켓은 하나지만, 연결마다 새 소켓이 만들어진다. 이 왕복 한 번이 지연 시간에 그대로 더해지므로, 연결을 재사용(keep-alive)하는 것이 성능에 중요하다.

원리 여기서 OS가 하나 끼어든다. 호스트의 443번 포트로 들어온 패킷은 어떻게 proxy 컨테이너의 443으로 갈까? Docker는 호스트 커널의 패킷 필터(iptables)에 목적지 주소를 바꾸는 규칙(DNAT) 을 넣는다. 호스트 443으로 온 패킷의 목적지를 proxy 컨테이너의 내부 IP:443으로 바꿔 보내는 것이다. Compose의 ports: "443:443" 한 줄이 커널 수준에서는 이 규칙이 된다.

④ TLS: 암호화된 통로 만들기

TCP 연결 위에서 TLS 핸드셰이크가 일어난다. 목적은 세 가지다. 내가 말하는 상대가 진짜 pawcycle.duckdns.org인지 확인하고(인증), 엿들을 수 없게 하고(기밀성), 중간에 바꿀 수 없게 한다(무결성).

  • 클라이언트가 지원하는 방식과 SNI(접속하려는 도메인 이름)를 보낸다.
  • 서버가 인증서를 보낸다. 브라우저는 “사이트 인증서 → 중간 인증서 → 브라우저가 이미 믿는 루트 인증서”로 서명 사슬을 따라가 검증한다.
  • 양쪽이 키 합의를 해서, 이후 데이터를 암호화할 대칭키를 만든다. 공개키 암호는 느리므로 키를 정할 때만 쓰고, 실제 데이터는 빠른 대칭키로 암호화한다.

Dale Seo의 「HTTPS란 무엇인가」가 TLS가 HTTP 아래에서 기밀성·무결성·인증을 제공하는 구조와 인증서 신뢰 사슬을 설명한다. 이 개념이 Nginx 설정에 그대로 나타난다.

# infra/production/nginx.https.conf (발췌)
server {                                   # (가) 모르는 이름으로 온 HTTPS
    listen 443 ssl default_server;
    server_name _;
    ssl_certificate ...;
    ssl_reject_handshake on;
}
server {                                   # (나) 진짜 도메인
    listen 443 ssl;
    server_name __PAWCYCLE_DOMAIN__;
    ssl_certificate     /etc/letsencrypt/live/pawcycle.duckdns.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/pawcycle.duckdns.org/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;
    ...
}
server {                                   # (다) 모르는 이름으로 온 HTTP
    listen 80 default_server;
    server_name _;
    return 444;
}
  • (나)의 fullchain.pem: 사이트 인증서와 중간 인증서를 함께 담은 파일이다. 중간 인증서를 빠뜨리면 사슬이 끊겨 일부 클라이언트에서 검증이 실패한다.
  • ssl_protocols TLSv1.2 TLSv1.3: 취약한 옛 버전(TLS 1.0·1.1)을 받지 않는다.
  • ssl_session_cache + ssl_session_timeout 1d: 한 번 핸드셰이크한 클라이언트가 다시 오면 키 합의를 생략하고 세션을 재개한다. 위 그림 ④의 비용을 줄인다.
  • (가) ssl_reject_handshake on: SNI가 우리 도메인이 아니면 핸드셰이크 자체를 거절한다. 해석 인터넷에는 IP 대역을 훑으며 아무 서버에나 접속해 보는 스캐너가 많다. 이들에게 인증서조차 보여 주지 않아, 이 IP에 어떤 도메인이 있는지 노출하지 않는다.
  • (다) return 444: Nginx 고유 코드로, 응답 없이 연결을 끊는다. 모르는 Host로 온 HTTP 요청에 아무 정보도 주지 않는다.

⑤⑥ 리버스 프록시: Nginx가 요청을 대신 전달한다

TLS를 푼 Nginx는 요청을 다시 Spring에 보낸다. 클라이언트 대신 서버를 대리하는 이런 서버를 리버스 프록시라 한다. Dale Seo의 「프록시 서버와 리버스 프록시」가 구분 기준을 정리한다. 포워드 프록시는 클라이언트 편에서 접근 제어·익명성을 맡고, 리버스 프록시는 서버 편에서 로드 밸런싱·TLS 종료·보안 경계를 맡는다.

문제는 Spring 입장에서 모든 요청이 Nginx에서 온 것처럼 보인다는 점이다. 접속자의 IP도, 원래 HTTPS였다는 사실도 사라진다. 그래서 Nginx가 헤더로 원래 정보를 실어 보낸다.

location /api/ {
    proxy_pass http://pawcycle_application_backend;
    proxy_http_version 1.1;
    proxy_set_header Host              $http_host;                  # 원래 요청한 호스트
    proxy_set_header X-Real-IP         $remote_addr;                # Nginx가 본 접속자 IP
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;  # 지나온 IP 목록
    proxy_set_header X-Forwarded-Proto https;                       # 원래는 HTTPS였다
    proxy_read_timeout 60s;
}

Spring은 이 헤더를 믿도록 설정돼 있다.

# compose.yaml의 backend 환경 변수
SERVER_FORWARD_HEADERS_STRATEGY: framework
SESSION_COOKIE_SECURE: "true"
  • 원리 framework 전략이면 Spring이 X-Forwarded-* 헤더를 읽어 요청의 스킴·호스트·접속자 주소를 원래 값으로 바꿔 끼운다. 그래야 Spring이 “이 요청은 HTTPS로 들어왔다”고 판단하고, 리다이렉트 주소를 https://로 만들 수 있다.
  • 세션 쿠키 Secure: 브라우저가 이 쿠키를 HTTPS로만 보내게 한다. Nginx와 Spring 사이가 평문이어도 상관없다. Secure는 브라우저가 언제 쿠키를 보내는가에 대한 속성이기 때문이다.

트레이드오프: 클라이언트가 보낸 헤더를 믿어도 되는가? X-Forwarded-For는 클라이언트가 위조할 수 있는 헤더다. $proxy_add_x_forwarded_for는 클라이언트가 보낸 값 뒤에 Nginx가 본 IP를 덧붙인다. 그래서 목록의 맨 앞 값은 믿을 수 없고, Nginx가 붙인 맨 뒤 값만 믿을 수 있다. Dale Seo의 글도 이 헤더는 위조될 수 있으니 신뢰하는 프록시가 붙인 값만 믿어야 한다고 경고한다. - 해석 이 프로젝트에서 헤더를 믿는 것이 안전한 근거는 2절의 네트워크 설계다. backend는 app 내부 네트워크에만 공개돼 있어서, 헤더를 조작해 backend에 직접 접속할 길이 없다. 모든 요청이 Nginx를 거친다는 전제 위에서만 이 설정이 성립한다. - 개선 후보: 미확인 Spring이 X-Forwarded-For의 어느 값을 접속자 IP로 쓰는지, 그리고 그 값을 로그나 보안 판단에 쓰는 코드가 있는지는 확인하지 않았다. 맨 앞 값을 쓴다면 로그의 IP가 위조될 수 있다. 신뢰할 수 있는 X-Real-IP를 쓰거나, Spring에 신뢰할 프록시를 명시하는 방법이 있다.

Docker 안의 DNS: 컨테이너 이름이 주소가 되는 원리

proxy_pass http://backend:8080의 backend는 도메인이 아니라 Compose 서비스 이름이다. 이것이 IP로 바뀌는 원리가 Nginx 설정 맨 위에 있다.

# Re-resolve service addresses after application container replacement.
resolver 127.0.0.11 valid=5s ipv6=off;

upstream pawcycle_application_backend {
    zone pawcycle_application_backend 64k;
    server backend:8080 resolve;
}
  • 원리 Docker는 사용자 정의 네트워크에 붙은 컨테이너에게 127.0.0.11에서 동작하는 내장 DNS 서버를 제공한다. 이 서버가 같은 네트워크의 서비스 이름을 컨테이너 IP로 바꿔 준다. 그래서 IP를 하드코딩하지 않고 이름으로 부를 수 있다.
  • 왜 valid=5s와 resolve인가. 원리 Nginx는 기본적으로 시작할 때 한 번 이름을 IP로 바꾸고 그 값을 계속 쓴다. 그런데 새 버전을 배포하며 backend 컨테이너를 다시 만들면 IP가 바뀐다. Nginx가 옛 IP를 붙들고 있으면 모든 요청이 실패하고, Nginx를 재시작해야만 복구된다. 위 설정은 upstream 이름을 5초마다 다시 해석하게 해서 이 문제를 없앤다. 주석이 정확히 그 이유를 적고 있다(“컨테이너 교체 후 서비스 주소를 다시 해석한다”).
  • 해석 이 설정 덕분에 backend만 새로 배포할 때 proxy를 건드리지 않아도 된다. 뒤의 8절에서 볼 “바뀐 서비스만 배포한다”는 배포 정책이 성립하는 전제다.

4. Nginx가 맡은 보안: 헤더와 로그인 속도 제한

보안 헤더

add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header X-XSS-Protection "0" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

proxy_hide_header Strict-Transport-Security;   # 뒤쪽 앱이 보낸 같은 헤더는 지운다
proxy_hide_header X-Frame-Options;
...
  • HSTS: “앞으로 1년 동안 이 도메인은 HTTPS로만 접속하라”고 브라우저에 기억시킨다. 사용자가 http://를 쳐도 브라우저가 알아서 HTTPS로 바꿔 보내므로, 첫 HTTP 요청을 가로채는 공격을 막는다.
  • nosniff: 브라우저가 응답 내용을 보고 타입을 멋대로 추측하지 못하게 한다.
  • X-Frame-Options: DENY: 다른 사이트가 이 페이지를 iframe에 넣지 못하게 해서, 투명한 프레임을 덮어 클릭을 훔치는 공격을 막는다.
  • X-XSS-Protection: 0: 원리 일부러 끄는 설정이다. 옛 브라우저의 XSS 필터는 오히려 오동작과 정보 유출 문제가 있어 현재는 끄는 것이 권장된다.
  • proxy_hide_header: Spring Security도 일부 보안 헤더를 기본으로 붙인다. 그대로 두면 같은 헤더가 두 번 나가므로, 앱이 보낸 것을 지우고 Nginx의 값 하나만 남긴다.

로그인 속도 제한: 새는 양동이

limit_req_zone $binary_remote_addr zone=login_per_ip:10m rate=10r/m;

location = /api/auth/login {
    limit_req zone=login_per_ip burst=5 nodelay;
    limit_req_status 429;
    error_page 429 = @login_rate_limited;
    proxy_pass http://pawcycle_application_backend;
    ...
}
location @login_rate_limited {
    default_type application/json;
    return 429 '{"code":"RATE_LIMITED","message":"로그인 요청이 너무 많습니다. 잠시 후 다시 시도해 주세요.","fieldErrors":[]}';
}

원리 Nginx의 limit_req는 새는 양동이(leaky bucket) 방식이다. 양동이 바닥에 구멍이 있어 물이 일정한 속도로 빠지고, 요청이 올 때마다 물을 한 컵 붓는다고 생각하면 된다.

  • rate=10r/m: 구멍으로 6초에 한 컵씩 빠진다. 같은 IP는 평균 6초에 한 번 로그인을 시도할 수 있다.
  • burst=5: 양동이에 여분으로 5컵까지 담을 수 있다. 사람이 비밀번호를 몇 번 연달아 틀리는 정도는 허용한다.
  • nodelay: 여분 안의 요청을 줄 세워 기다리게 하지 않고 바로 처리한다. 여분까지 넘치면 즉시 429다.
  • $binary_remote_addr: IP를 문자열 대신 바이너리로 저장해 메모리를 아낀다. 10m은 이 상태를 담을 공유 메모리 크기다.
  • location = /api/auth/login: =는 정확히 이 경로만 일치시킨다. 다른 API에는 제한을 걸지 않는다.
  • @login_rate_limited: 429 응답을 백엔드의 다른 오류와 같은 JSON 형식으로 맞춘다. 프론트가 오류를 한 가지 방식으로 처리할 수 있다.

트레이드오프: 왜 IP 기준이고, 왜 Nginx인가? 기록 이 제한은 세션·CSRF 제품 계약을 바꾸지 않고 공개 로그인 하나에만 IP당 제한을 추가한 변경이다(PR #296). 당시 계정 잠금, 이메일별 제한, Redis 기반 제한, WAF, CSP, JWT 전환은 별도 범위로 남겼다. - 얻는 것: 애플리케이션 코드를 바꾸지 않고, 요청이 Spring에 닿기도 전에 막는다. 비밀번호 대입 공격의 속도를 크게 늦춘다. - 한계: 해석 여러 사용자가 같은 공인 IP를 쓰는 환경(회사, 학교, 통신사 NAT)에서는 정상 사용자끼리 한도를 나눠 쓴다. 반대로 IP를 계속 바꾸는 공격자(봇넷, IPv6 주소 대역)는 막지 못한다. 한 계정에 여러 IP에서 대입하는 공격도 IP 기준으로는 보이지 않는다. 계정 기준 제한이 함께 있어야 하는 이유다. - 기록 이 값(10r/m, burst 5)은 당시 구현 계약이며, 실제 사용량을 측정해 정한 운영 임계치가 아니라고 남겨 두었다.

5. 컨테이너는 가상 머신이 아니다: namespace와 cgroup (깊게)

지금까지 “컨테이너”를 상자처럼 말했지만, OS 입장에서 컨테이너는 특별한 옷을 입은 일반 프로세스다. 가상 머신은 하드웨어를 흉내 내고 그 위에 운영체제를 통째로 하나 더 띄운다. 컨테이너는 호스트의 커널 하나를 함께 쓰면서, 커널 기능 두 가지로 프로세스를 가둔다.

  • namespace — 무엇이 보이는가(격리): 프로세스가 볼 수 있는 세상을 좁힌다.
    • PID namespace: 컨테이너 안에서 java는 자신이 PID 1이라고 본다. 호스트에서는 그냥 수많은 프로세스 중 하나다.
    • Network namespace: 컨테이너마다 자기만의 네트워크 인터페이스·IP·라우팅 표를 가진다. 2절의 네트워크 분리가 가능한 이유다.
    • Mount namespace: 컨테이너마다 다른 파일 시스템 뷰를 가진다. 이미지의 파일이 루트(/)처럼 보인다.
    • 이 밖에 호스트 이름(UTS), 프로세스 간 통신(IPC), 사용자 ID(User) namespace가 있다.
  • cgroup — 얼마나 쓸 수 있는가(제한): 프로세스 묶음이 쓸 수 있는 CPU·메모리·프로세스 수를 커널이 세고 제한한다.

이 두 기능이 PawCycle의 Compose 설정에 어떻게 대응하는지 그리면 다음과 같다.

컨테이너 안의 java는 자신이 PID 1이고 서버를 혼자 쓴다고 본다. 실제로는 커널이 namespace로 보이는 범위를 좁히고, cgroup으로 쓸 수 있는 양을 세고 있을 뿐이다. 이 관점으로 backend 컨테이너 설정을 한 줄씩 읽어 보자.

# infra/production/compose.yaml — backend 서비스의 격리·제한 설정 (요지)
backend:
  read_only: true            # 루트 파일 시스템 읽기 전용
  tmpfs:
    - /tmp                   # 쓰기가 필요한 곳만 메모리 파일 시스템으로
  security_opt:
    - no-new-privileges:true # 실행 중 권한 상승 금지
  mem_limit: 640m            # cgroup memory.max
  cpus: 0.75                 # cgroup cpu.max (CFS quota)
  pids_limit: 256            # cgroup pids.max
  • read_only: true: 컨테이너의 파일 시스템 전체를 읽기 전용으로 마운트한다. 해석 공격자가 애플리케이션 취약점으로 코드를 실행하게 되더라도 실행 파일을 내려받아 심거나 설정을 고쳐 쓰기 어렵다. 실행 중 디스크가 이미지와 달라지지 않으니 “어제와 오늘 같은 이미지인데 동작이 다르다”는 문제도 줄어든다.
  • tmpfs: /tmp: 그래도 쓰기가 꼭 필요한 곳이 있다. Spring Boot의 내장 Tomcat은 작업 디렉터리와 업로드 임시 파일을 /tmp 아래에 만든다. 그래서 /tmp만 메모리 위의 파일 시스템으로 열어 준다.
    • 원리 tmpfs에 쓴 데이터는 RAM에 있으므로 컨테이너의 메모리 사용량으로 계산된다. 큰 파일을 /tmp에 쓰면 디스크가 아니라 640MB 한도를 깎아 먹는다. 앞 절의 client_max_body_size 1m이 요청 본문 크기를 막아 주기 때문에 이 조합이 안전하다.
  • no-new-privileges: 원리 리눅스 커널의 PR_SET_NO_NEW_PRIVS 플래그다. 이 플래그가 켜진 프로세스와 자식 프로세스는 setuid 프로그램(예: sudo)을 실행해도 권한이 올라가지 않는다. 아래의 non-root 사용자와 함께 쓰면 컨테이너 안에서 root가 될 길이 거의 막힌다.
  • pids_limit: 256: 컨테이너가 만들 수 있는 프로세스 수 상한이다. 원래 목적은 fork를 무한히 반복하는 fork bomb이 호스트 전체를 마비시키지 못하게 하는 것이다.
    • 원리 리눅스 커널에게 스레드도 태스크 하나다. pids.max는 프로세스가 아니라 태스크 수를 센다. 그러니 이 숫자는 사실상 JVM 스레드 수 상한이다.
    • 해석 Tomcat의 기본 최대 작업 스레드는 200개다. 여기에 커넥션 풀, GC, JIT 컴파일러, 스케줄러 스레드가 더해진다. 부하가 몰려 Tomcat이 스레드를 끝까지 늘리면 256에 꽤 가까워진다. 이 한도에 닿으면 새 스레드를 만들지 못해 OutOfMemoryError: unable to create native thread가 난다. 이름은 메모리 오류지만 실제 원인은 pids 한도다.
    • 미확인 가상 스레드 사용 여부와 Tomcat 스레드 수 설정은 아직 확인하지 않았다. 9강(Spring 실행 구조)에서 함께 본다.
  • cpus: 0.75: 원리 CFS 스케줄러의 quota로 구현된다. 기본 100ms 주기마다 이 컨테이너는 75ms만큼만 CPU를 쓸 수 있다. 다 쓰면 남은 25ms 동안 멈춘다(throttling). 평균 CPU 사용률이 낮아 보여도, 요청이 몰리는 짧은 순간에 응답 지연이 튀는 원인이 된다.

cpus: 0.75는 JVM의 판단에도 영향을 준다. 컨테이너를 인식하는 JVM은 CPU quota를 읽어 availableProcessors()를 1로 계산한다(0.75를 올림).

  • 원리 HotSpot JVM은 CPU가 2개 이상이고 메모리가 약 1792MB 이상일 때만 “서버급 머신”으로 보고 G1 GC를 고른다. 그 조건에 못 미치면 Serial GC를 기본으로 고른다.
  • 해석 JAVA_TOOL_OPTIONS에 GC를 지정하는 옵션이 없으므로, 이 backend는 Serial GC로 돌고 있을 가능성이 높다. Serial GC는 스레드 하나로 애플리케이션을 멈추고 수거한다. 힙이 400MB 남짓이면 감당할 만하지만, 멈춤 시간이 응답 시간에 그대로 더해진다.
  • 미확인 실제 GC 종류는 운영 서버의 -Xlog:gc 출력이나 jcmd VM.flags로 확인해야 한다. 실험은 프로젝트 이해를 마친 뒤 하기로 했으니 여기서는 질문으로 남긴다.

이미지 쪽에도 같은 원칙이 있다.

# infra/production/backend.Dockerfile (요지)
FROM eclipse-temurin:25-jdk AS build      # 1단계: 빌드 도구가 있는 JDK
WORKDIR /workspace
COPY . .
RUN ./gradlew bootJar

FROM eclipse-temurin:25-jre               # 2단계: 실행만 하는 JRE
RUN useradd --system --shell /usr/sbin/nologin pawcycle
COPY --from=build /workspace/build/libs/*.jar /app/app.jar
USER pawcycle
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
  • 멀티 스테이지 빌드: 1단계 이미지에는 JDK·Gradle·소스 코드가 있지만, 최종 이미지에는 JRE와 jar 하나만 남는다. 이미지가 작아지고, 공격자가 쓸 수 있는 컴파일러나 빌드 도구가 운영 컨테이너에 없다.
  • USER pawcycle + nologin: 컨테이너는 기본으로 root로 실행된다. 원리 User namespace를 따로 켜지 않으면 컨테이너 안의 root는 호스트 커널 입장에서도 UID 0이다. 컨테이너 탈출 취약점이 생기면 피해 범위가 크게 달라진다. 그래서 로그인 셸이 없는 시스템 사용자로 낮춰 실행한다. frontend도 USER node로 같은 원칙을 따른다.

6. JVM과 컨테이너 메모리: 640MB는 어떻게 나뉘는가 (깊게)

mem_limit: 640m은 컨테이너 전체의 한도다. JVM 프로세스가 쓰는 메모리는 힙만이 아니다.

  • 힙(Heap): new로 만든 객체가 사는 곳. GC가 관리한다.
  • 메타스페이스(Metaspace): 로드된 클래스의 정보. Spring Boot는 클래스를 수만 개 로드하므로 생각보다 크다.
  • 스레드 스택: 스레드마다 기본 약 1MB까지 예약된다. 실제로 쓴 만큼만 물리 메모리를 차지한다.
  • 코드 캐시: JIT 컴파일러가 만든 기계어.
  • Direct buffer, GC 자료구조, 네이티브 라이브러리: 네트워크 I/O 버퍼나 GC가 쓰는 표.
  • tmpfs의 /tmp: 앞에서 본 것처럼 이것도 같은 한도에 포함된다.

-XX:MaxRAMPercentage=65.0은 최대 힙을 컨테이너 한도의 65%로 정한다. Braindetox의 「JVM 컨테이너 리소스 제한」 글이 이 구조를 설명한다. JVM이 cgroup의 메모리 한도를 읽어 힙 크기를 정하고, 비율을 너무 높게 잡으면 힙 밖의 메모리 때문에 컨테이너가 강제 종료될 수 있다는 내용이다. PawCycle의 숫자를 넣어 보면 다음과 같다.

그림 아래쪽의 두 상자는 서로 다른 두 종류의 죽음이다. 운영 중 장애를 볼 때 이 둘을 구분하는 것이 핵심이다.

  • 왼쪽: 힙 OOM. JVM이 객체를 둘 자리를 못 찾아 OutOfMemoryError를 던진다.
    • 이 오류는 아무 스레드에서나 터질 수 있다. 어떤 스레드는 죽고 어떤 스레드는 살아남아, 서버가 반쯤 고장 난 채로 계속 요청을 받는 상태가 생길 수 있다.
    • -XX:+ExitOnOutOfMemoryError는 OOM이 한 번이라도 나면 JVM을 즉시 끝낸다. 어중간하게 살아 있는 서버보다 깨끗하게 죽은 서버가 낫다는 판단이다. 죽은 컨테이너는 healthcheck와 재시작 정책으로 처리하는 편이 예측 가능하다.
    • 미확인 compose 파일에서 restart 정책을 다시 확인해야 한다. 정책이 없으면 “깨끗하게 죽은” 서버는 사람이 다시 띄울 때까지 그대로 멈춰 있다.
  • 오른쪽: 컨테이너 OOM. 힙은 여유가 있는데 힙 밖 메모리까지 합쳐 640MB를 넘은 경우다.
    • 원리 이때는 JVM이 아니라 커널의 OOM killer가 나선다. 프로세스에 SIGKILL(9번 신호)을 보내 즉시 죽인다. JVM은 로그 한 줄 남길 기회도 없다.
    • 종료 코드는 137 = 128 + 9다. docker inspect에서 OOMKilled: true와 137을 보면 Java 로그가 아니라 메모리 설정을 의심해야 한다.
  • 왜 65%인가. 해석 비율을 80%로 올리면 힙 밖에 남는 몫이 약 128MB로 줄어든다. Spring Boot 애플리케이션의 메타스페이스와 스레드 스택만으로도 그 정도를 쓰기 쉬워, 힙이 넉넉해 보이는데 커널이 죽이는 상황이 생긴다. 반대로 50%로 낮추면 컨테이너 OOM은 멀어지지만 GC가 더 자주 돌고 힙 OOM이 가까워진다. 65%는 그 사이의 절충이다.
    • 미확인 이 숫자가 운영 부하에서 실제로 측정해 정한 값인지는 확인하지 못했다. 힙 밖 메모리를 실제로 재려면 -XX:NativeMemoryTracking=summary가 필요하다. 이 측정은 뒤의 실험 단계 후보로 둔다.

7. 인증서는 누가, 어떻게 갱신하는가: ACME HTTP-01

HTTPS를 쓰려면 인증서가 있어야 하고, Let's Encrypt 인증서는 90일마다 만료된다. 사람이 손으로 갱신하면 언젠가 반드시 잊는다. 그래서 ACME라는 자동화 프로토콜을 쓴다. 핵심 질문은 하나다. “인증서를 요청한 사람이 정말 이 도메인의 주인인가?” HTTP-01 방식은 이것을 이렇게 증명한다.

그림의 각 단계는 앞에서 본 설정과 그대로 연결된다.

  • ③④가 80번 포트를 남겨 둔 이유다. 3절의 HTTP server 블록은 도메인으로 온 요청을 모두 HTTPS로 301 리다이렉트하지만, /.well-known/acme-challenge/만은 예외로 /var/www/certbot에서 파일을 직접 내준다. 인증서가 만료돼 HTTPS가 깨진 상황에서도 갱신이 가능하도록 평문 HTTP로 증명할 길을 남겨 둔 것이다.
  • 볼륨 공유와 읽기 전용. certbot 컨테이너는 webroot에 토큰을 쓰고, nginx는 같은 볼륨을 :ro로 읽기만 한다. 발급된 인증서가 들어 있는 letsencrypt 볼륨도 nginx에는 읽기 전용이다. 해석 nginx가 털려도 개인 키를 바꿔치기할 수 없다.
  • 타이머 03:00 · 15:00, Persistent=true. certbot은 만료가 30일 이내로 남았을 때만 실제로 갱신하므로, 하루 두 번 실행해도 대부분은 “아직 갱신할 필요 없음”으로 끝난다. 하루 두 번 시도하는 것은 Let's Encrypt가 권장하는 방식이다. 원리 Persistent=true는 서버가 꺼져 있던 동안 놓친 실행을 부팅 직후 한 번 따라잡게 한다. 일반 cron에는 이 기능이 없다.
  • reload-pending 상태 파일. 확인 갱신 스크립트는 실제로 인증서가 바뀌었고 검증이 통과한 경우에만 nginx를 reload한다. reload가 실패하면 그 사실을 상태 파일에 남겨, 다음 실행 때 reload를 다시 시도한다.
    • 원리 nginx는 인증서 파일을 시작하거나 reload할 때 한 번 읽어 메모리에 들고 있다. 디스크의 파일만 바뀌고 reload가 빠지면, 갱신은 “성공”했는데 nginx는 30일 뒤 만료될 옛 인증서를 계속 내보낸다. 이 실패는 만료일까지 아무도 모른다. 상태 파일은 이 조용한 실패를 막는 장치다.
    • reload는 restart와 다르다. nginx는 새 설정으로 새 worker를 띄우고, 옛 worker는 처리 중인 연결을 마친 뒤 종료한다. 그래서 인증서를 바꿀 때 연결이 끊기지 않는다.
  • certbot 이미지를 digest로 고정. 태그(latest)는 같은 이름으로 내용이 바뀔 수 있지만, @sha256:... digest는 내용이 1비트만 달라도 값이 바뀐다. 인증서 개인 키를 다루는 도구가 어느 날 몰래 바뀌는 일을 막는다. proxy의 nginx 이미지도 같은 방식으로 고정돼 있다.

트레이드오프: 왜 DNS-01이 아니라 HTTP-01인가? 해석 DNS-01은 도메인의 DNS에 TXT 레코드를 써서 증명한다. 80번 포트를 열지 않아도 되고 와일드카드 인증서(*.example.com)도 받을 수 있다. 대신 DNS 제공자의 API 토큰을 서버에 두어야 하고, 그 토큰이 새면 도메인 전체를 빼앗길 수 있다. 이 서비스는 도메인이 하나이고 80번은 리다이렉트용으로 어차피 열려 있다. 그러니 비밀 정보를 하나 덜 두는 HTTP-01이 더 단순하고 안전하다.

8. 배포와 운영: 무엇을 했고, 무엇을 일부러 미뤘나

마지막으로 이 구조가 어떻게 배포되고, 어떤 위험을 받아들였는지 본다. 포트폴리오 면접에서 가장 많이 묻는 부분이다. “왜 이렇게 했나요?”보다 “이 구조의 약점이 뭔가요?” 를 더 자주 묻는다.

backend:
  image: ghcr.io/.../pawcycle-backend:${BACKEND_RELEASE_SHA:-${RELEASE_SHA}}
  • 이미지를 커밋 SHA로 부른다. 확인 이미지 태그가 latest가 아니라 커밋 SHA다. 어떤 코드가 운영에 떠 있는지 정확히 알 수 있다. 롤백은 “이전 SHA로 태그를 바꾸고 다시 올리기”가 된다.
  • ${BACKEND_RELEASE_SHA:-${RELEASE_SHA}}. 셸의 기본값 문법이다. backend 전용 SHA가 있으면 그것을, 없으면 공통 SHA를 쓴다. 해석 frontend는 그대로 두고 backend만 새 버전으로 바꾸는 배포가 가능하다. 3절에서 본 Nginx의 resolve 재해석이 이 배포의 전제다. 배포 쪽에서는 호스트가 바뀐 서비스만 반영하고, 위험한 변경(스키마 마이그레이션 등)은 별도로 확인받는 방향으로 다듬어졌다(PR #474, #486, #490).
  • 서버 한 대, 수동 배포. 기록 운영 대상은 OCI의 app01 한 대(1 OCPU / 6GB)다. 자동 배포(CD)와 무중단 배포는 의도적으로 미뤘다(DEFER). 무료 등급 안에서 운영하려는 선택이었고, 다른 클라우드 대안을 비교한 결과다(이슈 #276).
  • DB는 컴포즈 밖에. MySQL은 관리형 서비스로 분리돼 있고, backend만 database-egress 네트워크로 나간다. 해석 서버 한 대가 통째로 날아가도 데이터는 남는다. 컨테이너는 이미지와 설정으로 다시 만들 수 있지만 데이터는 다시 만들 수 없다. “상태가 있는 것과 없는 것을 분리한다”는 원칙이 서버 한 대 구조에서도 지켜진다.
  • 관측 도구도 같은 서버에. 메트릭·로그 수집을 같은 호스트에 두었고, 앞에서 본 app 내부 네트워크는 그 과정에서도 느슨하게 풀지 않았다(PR #287, #293).

이 선택들이 받아들인 위험을 정리하면 다음과 같다.

받아들인 위험 구체적으로 무슨 일이 생기나 미룬 대안과 그 비용
단일 장애 지점 호스트가 죽으면 proxy·frontend·backend가 함께 멈춘다 서버 2대 + 로드 밸런서: 비용과 세션 공유 문제(세션이 서버 메모리에 있다)
배포 중 짧은 중단 backend 컨테이너를 교체하는 동안 /api 요청이 실패한다 블루-그린 배포: 같은 서버에 두 벌을 띄울 메모리가 6GB에 빠듯하다
같은 곳에 있는 감시자 호스트가 죽으면 모니터링도 같이 죽어 장애 알림이 오지 않는다 외부 업타임 체크: 비용은 거의 없지만 아직 없다
사람이 하는 배포 절차를 빠뜨릴 수 있다 CD 파이프라인: 운영 서버에 접근할 비밀을 CI에 맡겨야 한다

개선 우선순위 제안 해석 비용 대비 효과로 보면 첫 번째는 외부 업타임 체크다. 돈이 거의 들지 않고, “같은 곳에 있는 감시자” 문제를 바로 해결한다. 세션 저장소를 Redis로 옮기는 것은 서버 2대로 가는 데 필요한 전제지만, 지금 트래픽 규모에서는 이르다. 세션 구조는 Security 파트에서 자세히 본다.

마지막으로, 문서끼리 맞지 않는 부분이 하나 있다.

  • 확인 운영 개요 문서는 운영 대상을 OCI app01로 적고, 2026-10-25에 읽기 전용으로 점검한 결과(컨테이너 healthy, 주요 GET 200, 인증서 갱신 타이머 동작)를 남겼다. 동시에 “Production Verified”는 아니라고 분명히 적어 두었다.
  • 확인 그런데 README에는 운영 대상이 “없음”으로 남아 있다. 어느 한쪽이 갱신되지 않은 문서 드리프트다.
  • 포트폴리오로 정리할 때는 이 차이를 정확히 말할 수 있어야 한다. “운영 중입니다”가 아니라 “단일 서버에 배포해 읽기 전용 점검까지 했고, 운영 검증 단계는 아니다” 가 사실에 맞는 표현이다.

2강 정리

  • C4 System Context·Container 수준에서 PawCycle은 브라우저 → Nginx(proxy) → Next.js(frontend) / Spring(backend) → 관리형 MySQL 구조다. Toss와 OpenAI는 기본 설정에서 꺼져 있다.
  • 네트워크 경계: 외부로 공개된 것은 proxy의 80/443뿐이다. app 네트워크는 internal: true라 backend는 인터넷에서 직접 닿을 수 없다. 이 경계 덕분에 X-Forwarded-* 헤더를 믿을 수 있다.
  • 요청 한 번의 여정은 DNS → TCP 3-way → TLS(SNI·인증서 사슬·대칭키) → Nginx에서 TLS 종료 → Docker 내장 DNS(127.0.0.11) → backend 순이다.
  • Nginx 보안은 모르는 이름 거절(444, ssl_reject_handshake), 보안 헤더, 로그인 IP당 속도 제한(leaky bucket)이다.
  • 컨테이너 = namespace(보이는 것) + cgroup(쓸 수 있는 양): read_only, tmpfs, no-new-privileges, non-root, pids_limit(= 스레드 상한), cpus(= throttling, JVM의 CPU 수 판단과 GC 선택)다.
  • 640MB = 힙 65% + 힙 밖 35%: 힙 OOM과 컨테이너 OOM(exit 137)은 원인과 대응이 다르다.
  • 운영: SHA 이미지, 서비스별 배포, ACME HTTP-01 자동 갱신(reload-pending으로 조용한 실패 방지), 그리고 의도적으로 받아들인 단일 서버 위험.

2강에서 남긴 미확인 항목 (뒤 강의나 실험 단계에서 확인한다)

  • 실제 GC 종류
  • Tomcat 스레드 수와 가상 스레드 사용 여부
  • restart 정책
  • Spring이 접속자 IP로 쓰는 X-Forwarded-For 값
  • 힙 밖 메모리 실측
