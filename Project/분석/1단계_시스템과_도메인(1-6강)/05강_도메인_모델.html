5강. 도메인 모델: 엔티티, 테이블, 애그리거트는 1:1이 아니다

이번 강의의 목표

  • 구독을 하나의 묶음(애그리거트)으로 보는 이유와, 그 묶음을 지키는 장치(version)를 설명할 수 있다.
  • 상품과 SKU, 판매 상태와 구독 가능 여부, 회차와 주문, 주문과 결제처럼 헷갈리기 쉬운 쌍을 구분한다.
  • 문서에서는 "채택"했다고 적힌 설계(값 객체 등)가 코드에는 어떻게 남았는지, 문서와 코드가 다를 때 어떻게 읽는지 익힌다.

표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 원리 일반 원리 · 미확인

1. 구독은 하나의 묶음이다

구독 하나는 테이블 하나가 아니다. 구독 본체, 그 시점의 약속을 고정한 스냅샷과 스냅샷 항목, 다음 회차에 적용될 대기 변경, 회차 일정, 명령 이력이 모두 "구독 하나의 상태"를 이룬다. 개념으로 보면 하나의 묶음이고, 테이블로 보면 여러 개다.

그림의 점선이 DDD에서 말하는 애그리거트(aggregate)다. 위키독스의 「애그리거트와 루트 엔티티 설계: 트랜잭션 경계의 확립」은 애그리거트를 “데이터 변경의 일관성을 유지하기 위해 하나의 단위로 취급되어야 하는 객체들의 묶음”으로 정의한다. 글이 강조하는 규칙은 세 가지다.

  • 외부는 루트(여기서는 Subscription)만 참조한다.
  • 내부 객체는 루트를 통해서만 바꾼다.
  • 묶음 전체가 한 트랜잭션으로 저장된다.

그리고 다른 애그리거트는 객체가 아니라 ID로만 참조하라고 한다. 객체로 직접 참조하면 조회할 때마다 불필요한 로딩(JPA N+1)이 생기고, 두 애그리거트의 변경이 서로의 트랜잭션에 얽히기 때문이다.

PawCycle에 대 보면 이렇다.

  • 확인 ID 참조: 현재 SubscriptionEntity는 long memberId, long skuId, Long petId, Long currentSnapshotId처럼 ID 필드만 가진다. 반면 MVP1의 첫 Subscription 엔티티는 @ManyToOne Member member, @ManyToOne Sku sku로 객체를 참조했다. V2로 오면서 ID 참조로 바뀐 것이다.
  • 확인 경계를 지키는 장치: 그림 위쪽 상자에 적힌 version 하나다. 플랜 변경, 건너뛰기, 일시정지, 자동 주문 등 무엇이 구독 묶음을 바꾸든 같은 version을 올린다. 4강에서 본 자동 주문 처리 규칙에도 “Subscription version 한 번 증가”가 들어 있었다. version이 묶음 전체의 일관성 경계를 대표하는 숫자다.
  • 해석 테이블과는 1:1이 아니다: 이 묶음은 subscriptions, subscription_snapshots, subscription_snapshot_items, pending_plan_changes, subscription_schedules, 명령 이력 테이블 등 여러 테이블에 걸쳐 있다. 반대로 LegacyInitialSnapshot이나 PendingPlanChange는 도메인 문서에 개념으로 있지만, 문서 스스로 “별도 엔티티 구현을 요구하지 않는다”고 적는다.

2. 상품 vs SKU, 판매 상태 vs 구독 가능 여부

상품과 SKU는 “보는 단위”와 “사는 단위”다

  • 확인 용어집의 정의:
    • Product: 사용자에게 하나의 상품으로 인식되는 공통 정보다(“연어 사료”).
    • SKU: 용량·구성이 확정된 실제 선택 단위다(“연어 사료 5kg”).
  • 가격도, 재고도, 구독 가능 여부도 SKU에 붙는다. 같은 사료라도 2kg과 10kg은 가격과 재고가 다르기 때문이다.
  • 도메인 문서는 Product에 “구독 생성 불변 조건을 직접 검증하지 않는다”고 못 박는다. Product는 보여 주는 책임, SKU는 선택되는 책임을 진다.

하나의 SKU에 독립된 두 스위치

SKU에는 비슷해 보이지만 서로 독립인 두 속성이 있다.

// catalog/sku/domain/Sku.java (발췌)
private BigDecimal price;
private boolean subscribable;   // 구독 가능 여부: 정기배송 대상으로 고를 수 있는가
private SkuStatus status;       // 판매 상태(ACTIVE/INACTIVE): 공개 상품 API에 보이는가

확인 도메인 규칙은 “SKU 판매 status는 구독 적격성인 subscribable과 독립이다. INACTIVE라도 기존 구독 조건은 subscribable만 사용한다”고 적는다. 두 스위치를 조합하면 네 가지 상태가 나온다.

status subscribable 의미하는 상황
ACTIVE true 일반 판매 중이고 정기배송도 가능
ACTIVE false 일반 구매만 가능 (예: 한정 수량 이벤트 상품)
INACTIVE true 공개 목록에서는 내렸지만 기존 정기배송 대상으로는 유지
INACTIVE false 판매도 구독도 불가
  • 왜 하나로 합치지 않았나. 해석 하나의 상태값(SELLING, SUBSCRIPTION_ONLY, …)으로 합치면 “공개 목록에서 내린다”는 운영 행위가 기존 구독자의 배송까지 끊는 부작용을 만들기 쉽다. 두 축을 나누면 각 변경의 영향 범위가 분명해진다.
  • 같은 원칙이 곳곳에 있다. 확인
    • Product 관리 상태는 DRAFT → PUBLIC, PUBLIC → INACTIVE, INACTIVE → PUBLIC만 허용하고 나머지 전이는 409다.
    • 카테고리를 비활성화해도 Product 공개 상태를 연쇄 변경하지 않는다.
    • ACTIVE SKU가 하나도 없어도 PUBLIC Product는 빈 SKU 배열로 남는다.
  • 재고와 품절도 별개다. MVP1의 구독 생성 조건은 subscribable 하나뿐이었다. 재고, 품절, 판매 상태는 구독 생성과 연결하지 않았다. 재고는 실제 주문·결제 시점(MVP3)에서야 의미를 가진다.

3. 스냅샷의 세 가지 역할

4강에서 “가격은 참조하지 않고 복사한다”를 봤다. 도메인 문서를 자세히 읽으면 같은 subscription_snapshots 테이블의 행이 세 가지 역할로 쓰인다.

역할 무엇을 가리키나 언제 바뀌나
현재 스냅샷 (current) 지금 구독에 적용 중인 가격·구성·주기 pending이 적용될 때만 교체
pending 스냅샷 플랜 변경 후 다음 실행 가능한 회차에 적용할 값 새 플랜 변경이 오면 최신 요청으로 교체(대기열 아님)
effective 스냅샷 특정 회차의 주문에 실제로 쓰인 값 회차를 처리할 때 한 번 기록되고 이후 불변

자동 주문이 회차를 처리할 때 도메인 규칙은 이렇다(DOMAIN-003).

  1. 이 회차가 pending의 적용 대상이면 pending 스냅샷을, 아니면 현재 스냅샷을 effective로 정한다.
  2. effective 스냅샷의 가격과 항목을 주문에 다시 복사한다.
  3. pending을 썼다면 현재 스냅샷 포인터를 그것으로 바꾸고 pending을 지운다.
  4. 이 모든 것을 version 증가와 함께 한 트랜잭션으로 커밋한다.

명령들도 pending을 다르게 다룬다.

  • 건너뛰기: pending의 적용 대상을 새 회차로 옮긴다.
  • 일시정지: pending을 보존하고, 재개로 만든 회차에 적용한다.
  • 해지: pending을 적용하지 않는다. 코드에서는 deletePendingPlanChange로 지운다.

해석 이 규칙들이 복잡해 보이는 이유는, 시간에 따라 변하는 값을 “언제부터 유효한가” 까지 함께 관리하기 때문이다. 스냅샷 하나로 보이는 개념이 실은 시점이 다른 세 값이라는 것을 알아야 22강(구독 명령)과 23강(자동 주문) 코드가 읽힌다.

4. 구독 상태 전이와 회차 상태

구독에는 상태가 세 개, 회차에는 네 개 있다. 둘은 함께 움직인다.

그림의 핵심 불변 조건은 상자 안의 부제다. ACTIVE 구독은 미래 SCHEDULED 회차를 정확히 하나 갖고, PAUSED는 그 대신 HELD 회차를 갖는다. CANCELED는 되살리지 않으며, 다시 쓰려면 새 구독을 만든다. 이 규칙이 실제 코드에서는 이렇게 구현돼 있다.

// subscription/application/SubscriptionCommandApplicationService.java (발췌)
long expected = support.parseEtag(ifMatch);
if (subscription.version() != expected)                       // ① 낙관적 버전 검사
  throw new SubscriptionFailure(PRECONDITION_FAILED, "SUBSCRIPTION_VERSION_MISMATCH", ...);
switch (commandType) {
  case PAUSE  -> pause(subscription);
  case RESUME -> resume(subscription);
  case CANCEL -> cancel(subscription);
  ...
}
if (!store.incrementVersion(subscriptionId, expected))         // ② CAS로 version 증가
  throw new SubscriptionFailure(PRECONDITION_FAILED, ...);

private void pause(SubscriptionProjection subscription) {
  if (!"ACTIVE".equals(subscription.status())) throw support.state();   // ③ 전이 규칙
  ScheduleProjection schedule = store.lockNextScheduled(subscription.id());
  store.setSubscriptionStatus(subscription.id(), "PAUSED");
  store.setScheduleStatus(schedule.id(), "HELD");
  store.deleteDeliveryReminder(schedule.id());
}

private void cancel(SubscriptionProjection subscription) {
  if (!List.of("ACTIVE", "PAUSED").contains(subscription.status())) throw support.state();
  store.setSubscriptionStatus(subscription.id(), "CANCELED");
  store.cancelUnorderedSchedules(subscription.id());
  store.deletePendingPlanChange(subscription.id());
  ...
}
  • ① → ②: 먼저 클라이언트가 보낸 If-Match 버전과 비교한다. 작업을 마친 뒤에는 UPDATE ... SET version = version + 1 WHERE id = ? AND version = ? 형태의 CAS(compare-and-set)로 다시 한번 확인하며 올린다. 4강에서 본 것처럼, 그 사이 자동 주문이 먼저 커밋했다면 ②가 실패해 덮어쓰기를 막는다. 낙관적 잠금의 원리는 22강에서 깊게 본다.
  • ③: 전이 규칙이 애플리케이션 서비스의 문자열 비교로 구현돼 있다. "ACTIVE".equals(...) 검사가 이 파일에만 7번 나온다.
  • 상태를 바꾸는 일도 store.setSubscriptionStatus(id, "PAUSED"), 즉 저장소 메서드 호출이다. SubscriptionEntity에는 상태를 바꾸는 메서드가 하나도 없다. 생성자 하나뿐이고, 생성 시 status = "ACTIVE"로 고정된다.

이것은 나쁜 설계인가: 도메인 모델 vs 트랜잭션 스크립트

Martin Fowler는 「Anemic Domain Model」에서 이런 모양을 경고한다. 객체들이 도메인 명사의 이름을 갖고 관계도 갖췄지만, 행위가 거의 없는 getter/setter 묶음이다. 로직은 전부 서비스 객체에 있다. 그는 이것이 도메인 모델의 비용(객체-DB 매핑)은 다 치르면서 이점은 얻지 못하는, 사실상 트랜잭션 스크립트라고 말한다. 다만 같은 글에서 “도메인 모델이 항상 최선의 도구는 아니다”라고도 덧붙인다.

그런데 PawCycle의 구독 V2는 매핑 비용 자체를 치르지 않는 쪽을 택했다. 확인 구조 결정 문서(ARCH-011, Accepted)는 이렇게 정한다.

  • 구독 V2는 명시적 JDBC SQL, FOR UPDATE, version CAS 쓰기, UNIQUE 충돌 처리를 저장소에 둔다.
  • 저장소는 타입이 있는 조회 결과(projection)만 내놓는다. 검증, 멱등 판정, 상태 전이, 응답 조립은 하지 않는다.
  • 생성, 조회, 명령, 대사는 각각의 애플리케이션 서비스가 유스케이스와 트랜잭션 경계를 소유한다.

즉 이 코드는 의도적으로 “트랜잭션 스크립트 + 명시 SQL” 을 택했다. 이유는 3강·4강에서 본 요구들에 있다. 해석

  • 어떤 행을 어떤 순서로 잠그는지(구독 행 → 회차 행)가 정합성의 핵심이다. JPA의 지연 로딩과 플러시 순서에 맡기면 이 순서가 코드에서 보이지 않는다.
  • 상태 변경 하나가 테이블 여러 개를 조건부 UPDATE로 함께 바꾼다. 엔티티 그래프를 불러와 고치는 방식보다 SQL이 의도를 더 정확히 드러낸다.
  • MVP2에서 MVP1 데이터와 호환되는 경계를 유지해야 했다.

그렇다고 개선할 점이 없는 것은 아니다.

개선 제안 해석 트랜잭션 스크립트를 유지하더라도 전이 규칙만은 한 곳에 모을 수 있다. 지금은 “ACTIVE에서만 가능”이 7곳에 흩어져 있어, 새 상태(예: 결제 실패로 인한 SUSPENDED)를 추가하면 모든 곳을 찾아 고쳐야 한다.

java // 제안 예시 — 저장소에 없는 코드다 enum SubscriptionStatus { ACTIVE, PAUSED, CANCELED; boolean canPause() { return this == ACTIVE; } boolean canResume() { return this == PAUSED; } boolean canCancel() { return this != CANCELED; } }

SQL과 잠금 순서는 저장소에 그대로 두고, “무엇이 허용되는가”만 타입으로 옮기는 절충이다. DB의 CHECK (status IN (...))와 문자열이 어긋나는 실수도 컴파일 단계에서 줄어든다. 이 리팩터링은 33강(재설계) 후보로 남긴다.

같이 읽을 자료

  • 위키독스 · 애그리거트와 루트 엔티티 설계: 트랜잭션 경계의 확립: 애그리거트의 세 규칙과 ID 참조
  • Martin Fowler · Anemic Domain Model: 빈약한 도메인 모델이 사실상 트랜잭션 스크립트인 이유(영문)
  • Martin Fowler · Transaction Script (P of EAA): 요청 하나를 절차 하나로 처리하는 패턴의 정의(영문)

5. 회차와 주문은 다르다

확인 자동화 도메인 문서는 둘을 이렇게 나눈다.

  • SubscriptionSchedule(회차): 구독의 예정된 한 회차와 원래 예정일이다. “실제 처리 결과가 아니다.”
  • Recurring Order(주문): 그 회차를 실제로 처리해 생긴 결과다.
  • 관계는 회차 1개 → 주문 0개 또는 1개다.

왜 이것을 굳이 나눌까?

  • 계획과 사실을 섞지 않기 위해서다. 회차는 바뀔 수 있는 계획이다. 건너뛰면 SKIPPED, 일시정지하면 HELD, 재개하면 날짜가 바뀐다. 주문은 바뀌면 안 되는 사실이다. 가격, 항목, 출처 PlanVersion, 예정일, 처리 시각이 생성 뒤 불변이다.
  • “처리 안 됨”을 정직하게 남기기 위해서다. 주문이 없는 지난 회차는 “아직 처리되지 않았다”는 뜻이다. 확인 대사(reconciliation) 작업은 이런 회차를 처리된 것으로 바꾸지 않는다. 이미 주문이 있는데 다음 회차가 빠진 경우처럼, 주문 원본만으로 안전하게 재구성할 수 있을 때만 보정한다.
  • 해석 회차와 주문을 한 테이블에 합쳐 status = ORDERED로 표현하는 대안도 가능하다. 하지만 그러면 “계획을 바꾸는 명령”과 “사실을 기록하는 자동화”가 같은 행을 두고 경쟁한다. 분리해 두었기 때문에 4강의 UNIQUE (schedule_id) 한 줄로 중복 주문을 막을 수 있다.

6. 주문과 결제는 다르다

일반 구매로 오면 같은 원리가 한 번 더 나온다. 주문은 “무엇을 샀는가”, 결제는 “돈을 받으려는 시도” 다.

확인 V14 마이그레이션의 상태값부터 다르다.

  • 주문: CREATED, PAYMENT_PENDING, PAID, PAYMENT_FAILED, EXPIRED, PAYMENT_ACTION_REQUIRED
  • 결제: READY, PROCESSING, SUCCEEDED, FAILED, UNKNOWN

결제에만 UNKNOWN이 있다. 3강에서 본 대로, 외부 결제사와의 통신은 “모름”이라는 결과를 낳을 수 있기 때문이다. 주문의 상태는 결제 시도들의 결과를 요약한 것이다.

결정적인 차이는 개수다. 주문 하나에 결제 시도는 여러 번 있을 수 있다. 정기결제가 실패해 재시도하면 같은 주문에 두 번째 결제 행이 생긴다. 그래도 성공한 결제는 하나뿐이어야 한다. 이 규칙을 SQL로 어떻게 강제하는지가 이 절의 핵심이다.

-- V14__add_common_order_payment_and_billing.sql — payments 테이블 (발췌)
provider_order_id VARCHAR(100) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
idempotency_key   VARCHAR(128) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
attempt_no INT NOT NULL,
reconciliation_attempts INT NOT NULL DEFAULT 0,
succeeded_order_id BIGINT GENERATED ALWAYS AS
    (CASE WHEN status = 'SUCCEEDED' THEN order_id ELSE NULL END) STORED,

CONSTRAINT uk_payments_order_attempt   UNIQUE (order_id, attempt_no),
CONSTRAINT uk_payments_successful_order UNIQUE (succeeded_order_id),
CONSTRAINT uk_payments_idempotency      UNIQUE (idempotency_key),
CONSTRAINT chk_payments_reconciliation_attempts CHECK (reconciliation_attempts BETWEEN 0 AND 10)

그림의 트릭을 풀어 보자.

  • 문제: “성공한 결제는 주문당 하나”는 조건부 유일성이다. 상태가 SUCCEEDED인 행에 대해서만 order_id가 유일해야 한다. PostgreSQL이라면 CREATE UNIQUE INDEX ... WHERE status = 'SUCCEEDED'처럼 부분 인덱스(partial index)로 한 줄에 끝난다. MySQL에는 부분 인덱스가 없다.
  • 해법: 생성 컬럼(generated column)을 만든다. SUCCEEDED일 때만 order_id를 담고 나머지는 NULL을 담는다. 그 컬럼에 UNIQUE를 건다.
    • 원리 SQL 표준과 MySQL에서 UNIQUE 인덱스는 NULL을 여러 개 허용한다. NULL은 “모르는 값”이라 서로 같다고 판정하지 않기 때문이다. 그래서 실패·미확정 시도는 몇 개든 공존한다.
    • SUCCEEDED 행이 두 번째로 생기는 순간 101이 중복되어 DB가 거부한다. 애플리케이션에 버그가 있어도 이중 성공은 기록되지 않는다.
    • STORED는 값을 실제로 디스크에 저장한다는 뜻이다. 기본값인 VIRTUAL은 읽을 때 계산한다. MySQL 공식 문서의 「Secondary Indexes and Generated Columns」가 생성 컬럼 인덱스의 조건을 설명한다. 미확인 이 프로젝트가 왜 VIRTUAL 대신 STORED를 골랐는지는 기록을 찾지 못했다.
    • 대가: 부분 인덱스와 달리, NULL인 행도 인덱스 항목을 차지해 공간을 쓴다.
  • UNIQUE (order_id, attempt_no): 같은 주문의 같은 번째 시도는 하나뿐이다. 확인 계약 문서는 “같은 실패 결제에 대한 중복 재시도 요청은 이미 만들어진 다음 시도를 재사용한다”고 적는다. 재시도 요청 자체도 멱등이다.
  • CHECK (reconciliation_attempts BETWEEN 0 AND 10): 3강·4강에서 본 “UNKNOWN 결제는 최대 10회까지만 결제사에 조회한다”는 규칙이 DB 제약이 됐다.
  • CHARACTER SET ascii COLLATE ascii_bin: 결제 키와 멱등 키 컬럼만 문자셋이 다르다.
    • 원리 테이블 기본값인 utf8mb4_0900_ai_ci의 ai_ci는 악센트 무시(accent-insensitive), 대소문자 무시(case-insensitive) 비교다. 그러면 abc와 ABC가 같은 키로 취급된다.
    • 외부 결제사가 준 ID나 클라이언트의 UUID는 바이트 그대로 비교해야 한다. ascii_bin은 바이트 단위로 비교하고, 문자당 1바이트라 utf8mb4(최대 4바이트)보다 인덱스도 작다.
    • 해석 문자열 키를 대소문자 무시로 비교하면 서로 다른 두 키가 충돌하거나, 같은 키가 다르게 저장될 수 있다. 식별자 컬럼에는 이진 비교 콜레이션을 쓰는 것이 원칙이다.

한 가지 짚을 점이 있다.

  • 확인 PaymentEntity의 markProcessing, markSucceeded, markFailed, markUnknown은 이전 상태를 검사하지 않고 상태를 덮어쓴다. CommerceOrderEntity.markPaid도 마찬가지다.
  • 미확인 그렇다면 “READY에서만 PROCESSING으로 갈 수 있다” 같은 규칙은 어디서 지켜질까? 애플리케이션 서비스의 조건문인지, 조건부 UPDATE인지, 아니면 비어 있는지는 18강(결제 승인)에서 코드로 확인한다. 위 DB 제약들은 최후의 방어선이지, 전이 규칙 전체를 대신하지는 않는다.

같이 읽을 자료

  • MySQL 8.0 Reference · Secondary Indexes and Generated Columns: 생성 컬럼에 UNIQUE 인덱스를 거는 조건(영문)
  • SQL for Devs · Unique Indexes With Some Rows Excluded: DB별 부분 유일성 구현 비교(영문)

7. 값 객체: 문서에서는 “채택”, 코드에서는 없음

이번 강의에서 가장 중요한 발견이다.

확인 첫 MVP 도메인 설계(DOMAIN-001)는 값 객체 후보 다섯 개를 하나씩 따져, 두 개를 채택(Accepted) 했다.

후보 판단 이유
SubscriptionQuantity Accepted 1~10 범위를 생성 시점에 보장
DeliveryCycle Accepted 2·4·8주 검증과 날짜 계산 기간을 한 의미로 묶음
SubscriptionCreatedDate Deferred 추가 불변 조건이 없음
NextOrderScheduledDate Deferred 생성일과 주기에서 계산되는 파생 값, 별도 행위 없음
SubscriptionEligibility Deferred 저장 방식과 상태 모델 미정

판단 기준 자체가 훌륭하다. 해결하는 문제, 보장하는 불변 조건, 이점, 현재 단계의 복잡성을 나란히 놓고 결정했다. 4강의 YAGNI를 값 객체 단위로 적용한 것이다.

그런데 확인 저장소 이력 전체에서 SubscriptionQuantity 클래스는 한 번도 만들어진 적이 없다. DeliveryCycle이라는 클래스도 없다.

  • 첫 구현(PR #42, 7/14)은 Subscription 엔티티 생성자 안에서 int를 직접 검사했다.
// PR #42 시점의 subscription/domain/Subscription.java (발췌, 현재는 없음)
private static final Set<Integer> ALLOWED_DELIVERY_CYCLES = Set.of(2, 4, 8);
...
if (quantity < 1 || quantity > 10) throw new IllegalArgumentException(...);
if (!ALLOWED_DELIVERY_CYCLES.contains(deliveryCycleWeeks)) throw new IllegalArgumentException(...);
if (!nextOrderDate.equals(createdDate.plusWeeks(deliveryCycleWeeks))) throw new IllegalArgumentException(...);

값 객체는 아니지만, **불변 조건이 엔티티 안에 모여 있는** 풍부한 엔티티였다. 다음 주문 예정일의 정확한 등식(생성일 + 주기)도 여기서 검사했다. DB는 순서만 검사했다(4강).
  • V2 구조 정리 이후 이 엔티티는 사라졌다. 지금 같은 규칙은 세 곳으로 흩어져 있다.
    • API 경계의 DeliveryCycleValidator(요청 검증)
    • DB의 CHECK 제약
    • DeliverySchedulePolicy.firstFutureDate(...) 같은 정적 계산 함수
// subscription/domain/DeliverySchedulePolicy.java (현재)
public static LocalDate firstFutureDate(LocalDate scheduledDate, int cycleWeeks, LocalDate today) {
  LocalDate next = scheduledDate;
  do { next = next.plusWeeks(cycleWeeks); } while (!next.isAfter(today));
  return next;
}

4강에서 본 “장기 중단 뒤 오늘보다 미래인 첫 날짜로 건너뛰기” 규칙이 이 일곱 줄이다. 주석은 이 함수가 “조회, 잠금, 영속성과 독립적인 산술”이라고 밝힌다. **도메인 계층에 남은 것이 순수 계산뿐**이라는 점이 V2의 성격을 잘 보여 준다.

이 차이는 문제인가

해석 판단은 두 갈래로 나뉜다.

  • 문제가 아닌 이유:
    • 불변 조건 자체는 지켜지고 있다. 수량과 주기는 API 검증과 DB CHECK의 이중 방어를 받는다.
    • V2가 명시 SQL로 간 이상, 값 객체를 만들면 JDBC 매핑에서 매번 감싸고 푸는 비용이 생긴다.
    • 그리고 V2 신규 구독은 수량을 사용자가 고르지 않는다. 생성자의 this.quantity = 1이 보여 주듯 패키지 구성 수량이 PlanItem에 있다. SubscriptionQuantity가 지키려던 규칙이 도메인 자체에서 사라진 것이다.
  • 문제인 이유:
    • int cycleWeeks는 아무 정수나 받는다. firstFutureDate(date, 0, today)를 부르면 plusWeeks(0) 때문에 루프가 영원히 끝나지 않는다. 지금은 호출 전에 값이 검증돼 있어 실제로 일어나지 않지만, 함수 자체는 그 사실을 모른다.
    • 이것이 원시 타입 집착(primitive obsession)의 전형적 위험이다. 규칙이 타입에 있지 않고 호출자의 선의에 있다.

개선 제안 해석 가장 싼 개선은 주기만 값 객체로 만드는 것이다. 주기는 V2에서도 살아 있는 규칙이고, 날짜 계산이라는 행위를 가지기 때문이다.

java // 제안 예시 — 저장소에 없는 코드다 public record DeliveryCycle(int weeks) { public DeliveryCycle { if (weeks != 2 && weeks != 4 && weeks != 8) throw new IllegalArgumentException("배송 주기는 2·4·8주"); } public LocalDate firstFutureDate(LocalDate from, LocalDate today) { LocalDate next = from; do { next = next.plusWeeks(weeks); } while (!next.isAfter(today)); return next; } }

  • Java record는 불변이고, compact 생성자에서 검증하면 잘못된 값으로는 객체 자체를 만들 수 없다.
  • 저장소는 SQL에서 int를 읽어 new DeliveryCycle(weeks)로 감싸기만 하면 된다. 잠금과 SQL 구조는 건드리지 않는다.
  • 무한 루프 위험이 타입 수준에서 사라진다.

문서와 코드가 다를 때 읽는 법

이번 발견에서 얻을 교훈은 특정 클래스의 유무보다 읽는 태도에 있다.

  • 설계 문서의 “Accepted”는 그 시점의 설계 판단이지 구현 증거가 아니다. 이 프로젝트의 결정 기록들도 “문서 병합은 구현 완료의 증거가 아니다”라고 반복해서 적는다.
  • 그래서 해체 분석에서는 문서 → 코드 → 이력 순으로 대조한다. 이번에는 git log -S'SubscriptionQuantity'로 그 이름이 한 번도 코드에 들어온 적이 없음을 확인했다.

  • 포트폴리오에서는 이 차이를 숨기지 말고 설명할 수 있어야 한다. 예를 들면 이렇게다.

    “초기 설계에서 값 객체를 채택했지만, V2에서 명시 SQL과 트랜잭션 스크립트로 전환하며 불변 조건을 API 검증과 DB 제약으로 옮겼다. 주기 계산은 값 객체로 되돌릴 가치가 있다고 본다.”

    이것이 “DDD를 적용했다”보다 훨씬 강한 설명이다.
