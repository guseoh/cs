1강. PawCycle Commerce는 무엇이고, 어떻게 생겼는가

기준: GitHub main = f9ab9f87 (2026-11-12) · 깊이: L1 전체 지도 표시: 확인 코드·설정·DDL · 기록 승인 문서·PR·이슈·결정 기록 · 해석 내 판단 · 미확인

이번 강의에서 설명할 수 있게 되는 것

  • PawCycle이 어떤 문제를 푸는 서비스이고, 왜 정기배송이 도메인의 중심인가
  • 그 도메인 판단이 DB 스키마에 어떤 모양으로 남았는가 (가장 깊게 다룸)
  • 실행하면 어떤 컨테이너가 어떻게 연결되어 떠 있는가
  • 코드가 도메인 → 계층 순서로 나뉜 방식과, 그 규칙을 테스트로 강제하는 방법
  • 기술 스택 각각을 왜 골랐는지, 근거가 어디에 있는가

중요도에 따라 깊이를 다르게 했다. 2절(도메인이 스키마에 남긴 흔적)과 4절(실행 구성), 5절(코드 구조)을 깊게 다루고, 나머지는 지도를 그리는 수준으로 짧게 간다.

1. 이 서비스가 푸는 문제: 반복 구매

PawCycle은 사료·간식·모래·배변 패드 같은 반려동물 소모품을 파는 커머스다. 이 상품군의 특징은 한 번 사고 끝나지 않는다는 것이다. 사료는 몇 주마다 떨어지므로 같은 물건을 정해진 주기로 계속 받고 싶은 수요가 생긴다. 그래서 이 프로젝트에는 구매 흐름이 두 개 있다.

위 두 번째 그림(두 구매 흐름) 이 그 구조다.

  • 일반 구매(청록): 장바구니에 담고 → 체크아웃에서 재고·쿠폰을 예약하고 → 토스 결제 승인에서 확정하고 → 배송한다.
  • 정기배송(보라): 플랜을 고르고 → 구독을 만들 때 가격·구성을 스냅샷으로 고정하고 → 회차가 오면 → 스케줄러가 자동으로 주문을 만들고 → 정기결제한다.
  • 공유 기반(회색): 두 흐름은 회원, 상품·SKU, 재고, 결제 테이블을 함께 쓴다. 확인 결제 테이블은 type 컬럼으로 일반 결제(NORMAL)와 정기결제(BILLING)를 구분한다. 결제 대사 코드가 이 값으로 분기한다.

도메인 용어 가운데 코드를 읽을 때 반드시 구분해야 하는 것만 추리면 다음과 같다.

용어 뜻 구분하는 이유
상품 · SKU 상품은 “연어 사료”, SKU는 “연어 사료 2kg” 가격·재고·주문은 SKU에 걸린다
판매 상태 · 구독 가능 여부 일반 구매로 팔 수 있는가 · 정기배송 대상으로 고를 수 있는가 기록 1차 MVP부터 별개 개념으로 정의했다
플랜 · 플랜 버전 종별 패키지 상품 · 그 가격과 구성의 한 판 가격이 바뀌면 버전을 새로 만든다
스냅샷 가입 시점의 가격·구성 복사본 플랜이 바뀌어도 기존 고객 조건을 지킨다
회차 · 정기 주문 예정된 배송 · 그 회차를 실제로 처리한 결과 한 회차에 주문은 최대 하나

2. 도메인 판단이 스키마에 남긴 흔적 (깊게)

도메인 설명을 문서로만 읽으면 추상적이다. 이 프로젝트에서는 마이그레이션 파일이 도메인 결정의 화석이다. 같은 subscriptions 테이블이 1차 MVP와 2차 MVP에서 어떻게 달라졌는지 보면 도메인이 어떻게 자랐는지가 그대로 보인다.

1차 MVP의 구독: SKU 하나를 고르는 단순한 약속

-- backend/src/main/resources/db/migration/V2__create_subscriptions.sql
CREATE TABLE subscriptions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    sku_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    created_date DATE NOT NULL,
    next_order_date DATE NOT NULL,
    ...
    CONSTRAINT chk_subscriptions_quantity CHECK (quantity BETWEEN 1 AND 10),
    CONSTRAINT chk_subscriptions_delivery_cycle CHECK (delivery_cycle_weeks IN (2, 4, 8)),
    CONSTRAINT chk_subscriptions_date_order CHECK (next_order_date > created_date)
);

이 DDL은 1차 MVP 요구사항(PS-002)을 거의 한 줄씩 옮긴 것이다.

  • sku_id 하나 → 기록 “구독 하나는 SKU 하나만 대상으로 한다”
  • quantity BETWEEN 1 AND 10 → “구독 수량은 1~10”
  • delivery_cycle_weeks IN (2, 4, 8) → “배송 주기는 2주, 4주, 8주”
  • next_order_date > created_date → “다음 주문 예정일 = 생성일 + 배송 주기”

해석 규칙을 애플리케이션 코드뿐 아니라 DB의 CHECK 제약에도 걸어 둔 것이 이 프로젝트의 습관이다. 코드에 버그가 있거나 누군가 SQL로 직접 넣어도 규칙을 어기는 행은 저장되지 않는다. 기록 결정 기록 PWC-0044는 여기서 한 가지를 더 구분한다. 도메인 코드는 “정확히 생성일 + 주기”라는 등식을 검사하고, DB는 “예정일이 생성일보다 뒤”라는 순서만 검사한다. DB 제약은 최후 방어선이고, 정확한 규칙은 도메인이 가진다는 역할 분담이다.

2차 MVP의 구독: 스냅샷으로 약속을 고정한다

2차 MVP에서 구독은 “SKU 하나”가 아니라 “종별 패키지 플랜”을 구독하는 것으로 바뀌었다. 핵심 문제는 이것이다. 판매자가 플랜 가격을 올리면, 이미 가입한 고객의 다음 결제 금액도 바뀌어야 하는가? 기록 2차 MVP 요구사항(PS-004)의 답은 “아니다”였다. 가격·구성 변경은 새 플랜 버전으로만 하고, 기존 구독 가격은 자동으로 바꾸지 않는다.

-- V3__add_second_mvp_subscription_schema.sql (발췌)
CREATE TABLE plan_versions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    plan_id BIGINT NOT NULL,
    package_price_krw BIGINT NOT NULL,
    ...
);
ALTER TABLE subscription_plans
    ADD CONSTRAINT fk_subscription_plans_current_version
        FOREIGN KEY (current_plan_version_id, id) REFERENCES plan_versions (id, plan_id);

CREATE TABLE subscription_snapshots (
    id BIGINT NOT NULL AUTO_INCREMENT,
    subscription_id BIGINT NULL,
    source_plan_version_id BIGINT NOT NULL,
    package_total_krw BIGINT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    ...
);
CREATE TABLE subscription_schedules (
    ...
    effective_snapshot_id BIGINT NULL,
    CONSTRAINT uk_schedules_subscription_date UNIQUE (subscription_id, scheduled_date),
    CONSTRAINT chk_schedules_status CHECK (status IN ('SCHEDULED', 'SKIPPED', 'HELD', 'CANCELED'))
);
CREATE TABLE pending_plan_changes (
    subscription_id BIGINT NOT NULL,          -- PK: 구독당 대기 변경 하나
    snapshot_id BIGINT NOT NULL,
    target_schedule_id BIGINT NOT NULL,       -- 어느 회차부터 적용할지
    ...
);

이 DDL에서 읽어야 할 설계 판단은 네 가지다.

  • 가격이 두 번 저장된다. plan_versions.package_price_krw는 “지금 파는 가격”, subscription_snapshots.package_total_krw는 “이 고객이 약속받은 가격”이다. 정규화 원칙만 보면 중복이지만, 둘은 의미가 다른 값이다. 스냅샷이 플랜 버전을 참조하지 않고 금액을 복사해 두므로, 플랜이 바뀌어도 고객의 약속은 그대로다.
  • 복합 외래 키로 “엉뚱한 버전”을 막는다. (current_plan_version_id, id) → plan_versions(id, plan_id)는 “플랜의 현재 버전은 반드시 그 플랜의 버전이어야 한다”를 DB가 보장하게 한다. 단순히 current_plan_version_id → plan_versions(id)로 걸면 다른 플랜의 버전을 가리켜도 막을 수 없다.
  • 플랜 변경은 “다음 회차부터”다. pending_plan_changes는 구독당 한 행(PK가 subscription_id)이고, 어느 회차부터 적용할지(target_schedule_id)를 가진다. 변경을 즉시 덮어쓰지 않고 대기시켜 두었다가, 그 회차의 주문을 만들 때 현재 스냅샷으로 승격한다.
  • 회차 하나에 날짜 하나. UNIQUE (subscription_id, scheduled_date)는 같은 구독에 같은 날 회차가 두 번 생기지 않게 한다. 뒤에서 볼 “스케줄러가 여러 번 돌아도 결과는 하나” 규칙의 바닥이 된다.

해석 테이블 = 엔티티 = 애그리거트가 아니다. 스냅샷·대기 변경·회차는 모두 별도 테이블이지만, 도메인으로는 “구독 하나의 상태”를 이루는 부분들이다. 결정 기록의 학습 가이드(PWK-0001)가 “DB 테이블을 도메인 애그리거트와 동일시하지 않는다”고 따로 적어 둔 이유가 여기 있다. 이 차이는 5강(도메인 모델)에서 코드와 함께 본다.

멱등성 테이블이 네 개라는 것의 의미

확인 같은 V3에 subscription_creation_idempotency_results와 subscription_command_idempotency_results가 함께 생겼고, 이후 V14에 체크아웃, V22에 빠른 재주문의 결과 테이블이 생겼다. 모두 (회원, 키)를 기본 키로 삼고, 요청 지문과 응답을 저장한다.

해석 이 프로젝트는 “두 번 실행되면 사고가 나는 요청”을 처음부터 의식했다. 구독 생성, 구독 변경, 체크아웃, 재주문이 그렇다. 기록 다만 처음부터 그랬던 것은 아니다. 결정 기록 PWC-0031은 1차 MVP 구독 API에서 멱등성을 도입하지 않았고, 그 대가를 당시에 받아들였다고 기록한다. 2차 MVP에서 구독 변경 명령이 생기면서 도입됐다.

3. 어떻게 자라 왔는가

위 세 번째 그림(MVP 이력) 이 커밋 이력(681개)을 단계로 묶은 것이다. 이 그림에서 기억할 것은 두 가지다.

  • 정기배송(보라)이 먼저, 일반 구매(청록)가 나중이다. 결제·재고·장바구니는 첫 커밋 한 달 뒤인 8월 13일에야 붙었다. 그래서 같은 “주문”이 subscription_orders(V9)와 orders(V14) 두 벌로 존재한다. 확인 V15의 이름이 backfill_legacy_subscription_orders인 것으로 보아 둘을 잇는 이행 작업이 있었다. 미확인 두 주문 모델의 현재 관계는 6강(ERD)에서 확인한다.
  • 과거를 고치지 않고 덧붙인다. 기록 PS-005는 “PS-004는 당시의 역사적 계약이며 소급 수정하지 않는다”고 적는다. 마이그레이션도 V1부터 V28까지 기존 파일을 고치지 않고 새 파일을 쌓는다. 그래서 코드 곳곳에 “예전 형식의 데이터”를 다루는 분기가 남는다. 체크아웃이 최초 장바구니 버전이 없는 예전 멱등성 결과를 거절하던 코드가 그 예다.

4. 실행하면 무엇이 떠 있는가 (깊게)

위 첫 번째 그림(컨테이너 구성) 이 운영 Compose 파일을 그대로 옮긴 것이다.

요청의 길

확인 infra/production/nginx.conf의 핵심은 두 줄이다.

location /api/ { proxy_pass http://backend:8080; }   # Spring Boot
location /     { proxy_pass http://frontend:3000; }  # Next.js

브라우저는 서버 하나(Nginx)에만 말을 건다. 주소가 /api/로 시작하면 Spring Boot로, 나머지는 Next.js로 간다. 같은 도메인을 쓰므로 세션 쿠키와 CSRF 처리가 단순해진다. 해석 프론트와 백엔드가 서로 다른 도메인이었다면 CORS와 쿠키의 SameSite 설정을 따로 다뤄야 했을 것이다. 세션 인증을 고른 결정(PWC-0007)과 이 라우팅은 함께 읽어야 한다.

컨테이너 설정이 말해 주는 운영 판단

# infra/production/compose.yaml (backend 서비스 발췌)
backend:
  image: ${BACKEND_IMAGE}:${BACKEND_RELEASE_SHA:-${RELEASE_SHA}}
  environment:
    JAVA_TOOL_OPTIONS: -XX:MaxRAMPercentage=65.0 -XX:+ExitOnOutOfMemoryError
    SPRING_PROFILES_ACTIVE: production
  healthcheck:
    test: [CMD, curl, --fail, ..., http://127.0.0.1:8080/api/products]
  read_only: true
  security_opt: [no-new-privileges:true]
  networks: [app, database-egress]
  mem_limit: 640m
  cpus: 0.75
  • 이미지 태그가 커밋 SHA다. latest 같은 이름이 아니라 정확한 커밋으로 배포한다. 어떤 코드가 떠 있는지 항상 알 수 있고, 되돌릴 때도 그 SHA로 돌아간다. 기록 PWC-0025가 “정확한 이미지·소스·DB 호환 근거를 승인한다”고 정한 결정의 구현이다.
  • JVM 힙을 컨테이너 메모리의 비율로 정한다. 컨테이너 한도 640MB의 65%를 힙 상한으로 쓰고, 메모리가 부족하면 어정쩡하게 버티지 않고 프로세스를 종료한다. 기록 교훈 PWL-0032에 따르면 AWS 시절 250 RPS 장애의 원인은 힙 부족이 아니라 컨테이너 메모리 한도 초과(cgroup OOM) 였다. 힙 바깥 메모리까지 컨테이너 한도 안에 들어가야 한다는 경험이 이 설정에 남아 있다.
  • 헬스 체크가 실제 API를 부른다. /api/products가 응답해야 건강하다고 본다. 해석 프로세스가 떠 있는지만이 아니라 DB까지 연결돼 상품을 읽을 수 있는지를 본다는 뜻이다. Nginx는 depends_on: condition: service_healthy로 백엔드가 건강해진 뒤에 뜬다.
  • 파일 시스템은 읽기 전용이다. 쓰기는 /tmp 메모리 영역만 허용하고, 권한 상승도 막는다.

Compose에 없는 것

  • MySQL이 없다. 확인 백엔드는 database-egress 네트워크로 바깥의 DB에 붙는다. 기록 운영 개요는 이를 OCI의 Managed MySQL로 적는다. DB의 생명주기를 애플리케이션 Compose가 소유하지 않게 한 결정이다(ARCH-012).
  • Redis가 없다. 확인 상품 목록 캐시는 PAWCYCLE_PRODUCT_LIST_CACHE_ENABLED 기본값이 false다. 미확인 운영 환경 파일에서 켜져 있는지는 확인하지 않았다.

애플리케이션 설정이 말해 주는 것

# backend/src/main/resources/application.properties (발췌, 비밀값 생략)
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
spring.jpa.properties.hibernate.jdbc.time_zone=UTC
spring.flyway.validate-on-migrate=true
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.same-site=lax
management.endpoints.web.exposure.include=health,prometheus
pawcycle.toss.test.enabled=${PAWCYCLE_TOSS_TEST_ENABLED:false}
pawcycle.ai.review-summary.enabled=${PAWCYCLE_AI_REVIEW_SUMMARY_ENABLED:false}
  • 스키마는 Flyway만 바꾼다. ddl-auto=validate는 Hibernate가 엔티티와 테이블이 맞는지 검사만 하고 스키마를 고치지 않게 한다. 그래서 2절의 DDL이 곧 실제 스키마다.
  • OSIV를 끈다. 영속성 컨텍스트가 요청 내내 열려 있지 않다. 리뷰 요약·결제 승인에서 본 “트랜잭션 밖 외부 호출” 설계가 성립하는 전제다.
  • 시간은 UTC로 저장한다. 기록 PWC-0021은 장바구니·찜 시각을 UTC로 바꾸면서, 기존 행의 표시 재해석을 “승인된 대가”로 받아들였다.
  • 외부 연동은 기본이 꺼짐이다. 토스 실결제, 리뷰 요약 AI, 상품 비교 AI, 추천 AI가 모두 기본값 false다. 켜지 않으면 서비스는 외부 없이 동작한다.

시작점에 숨은 운영 도구

// PawcycleBackendApplication.java
public static void main(String[] args) {
  int catalogImportExitCode = ProductionDemoCatalogImportCommand.runIfRequested(args);
  if (catalogImportExitCode != ProductionDemoCatalogImportCommand.NOT_REQUESTED) { ... return; }
  int maintenanceExitCode = ProductionAuthSmokeMemberBootstrap.runIfRequested(args);
  if (maintenanceExitCode != ProductionAuthSmokeMemberBootstrap.NOT_REQUESTED) { ... return; }
  SpringApplication.run(PawcycleBackendApplication.class, args);
}

평범한 Spring Boot 시작점처럼 보이지만, 웹 서버를 띄우기 전에 두 가지 일회성 명령을 확인한다. 특정 인자가 오면 카탈로그 적재나 점검용 회원 생성만 하고 종료한다. 기록 PWC-0024는 운영 카탈로그를 “서버가 뜰 때 자동으로 넣는 방식(startup seed)” 대신 “명시적으로 검증·확인한 뒤 한 번만 적용하는 방식”으로 정했다. 같은 이미지를 웹 서버로도, 일회성 도구로도 쓰게 만든 구조다.

지금 운영 중인가: 정정

이전 1강에서 “README는 운영 배포 대상이 없다고 밝힌다”고만 썼는데, 그것은 반쪽 사실이었다.

  • 확인 README: “Production deployment target: 없음”
  • 확인 같은 커밋의 production-operations-overview.md: “Production deployment target: OCI app01”, 단 “Production Verified가 아니다”
  • 기록 프로젝트 결정 기록도 이 불일치를 짚고 “현재 운영 대상과 상태는 미해결”로 두었다.

정확한 표현은 “문서끼리 충돌하고, 실제 운영 상태는 확인되지 않았다” 이다. 이 강의 시리즈의 설명은 모두 소스와 기록에서 읽은 것이며, 운영 관측이 아니다.

5. 코드는 어떻게 나뉘어 있는가 (깊게)

패키지를 나누는 두 방식

출처: Ogu, 「[Spring] Spring 패키지 구조」 (velog). 이미지는 원문을 직접 열어 내용을 확인했다.

이 그림의 왼쪽이 계층형, 오른쪽이 도메인형이다. 왼쪽은 Controller 폴더 안에 상품·회원·주문 컨트롤러가 모여 있고, 오른쪽은 상품 폴더 안에 상품의 Entity·Repository·Controller·Service가 모여 있다. 원문은 계층형은 전체 구조를 빨리 파악할 수 있지만 클래스가 한 폴더에 쌓이고, 도메인형은 응집도가 높지만 처음에는 전체를 파악하기 어렵다고 정리한다.

PawCycle의 선택: 도메인 먼저, 그 안에서 계층

위 네 번째 그림(패키지와 계층) 이 그 구조다.

  • 위쪽: 최상위는 도메인이다. 그림 속 숫자는 손으로 쓴 소스 파일 수다. 확인 commerce(232개)가 가장 크고, 그 안에 장바구니·체크아웃·결제·재고 등 하위 기능이 18개 있다.
  • 아래쪽: 기능 하나를 열면 다섯 계층이 있다. application이 중심에서 domain·persistence·infrastructure를 부르고, api는 application만 부른다.

기록 아키텍처 문서(backend-architecture-v2.md)는 계층마다 금지 사항을 정해 두었다.

  • api: HTTP·검증·DTO만. 저장소·엔티티·SQL 도구를 직접 참조하지 않는다.
  • application: 유스케이스와 트랜잭션의 주인. API DTO를 참조하거나 SQL을 직접 실행하지 않는다.
  • domain: 엔티티·값·불변식·상태 전이. api와 infrastructure에 의존하지 않는다.
  • persistence: JPA·잠금·쿼리·이유 있는 네이티브 SQL.
  • infrastructure: 토스·AI·Redis 세부 구현. 외부 DTO를 안으로 흘리지 않는다.

규칙을 테스트로 강제한다

이 규칙은 문서로만 있지 않다. 확인 테스트 의존성에 com.tngtech.archunit:archunit:1.5.0이 있고, 기록 BackendArchitectureTests가 위 규칙을 위반하면 빌드를 실패시킨다. ArchUnit의 사용법은 lango의 「ArchUnit을 활용한 아키텍처 테스트 작성하기」가 layeredArchitecture()로 “어느 계층이 어느 계층에만 접근할 수 있다”를 쓰는 예제로 보여 준다. 규칙을 테스트로 남기면 그 자체가 살아 있는 문서가 된다는 것이 그 글의 요지다.

여기서 이 프로젝트만의 현실적인 장치가 나온다.

  • 기록 이미 있던 위반 204개를 목록 파일에 동결했다(legacy-dependencies.txt). 그중 186개가 금지한 바로 그 방향(application → api) 이다.
  • 새 위반은 막고, 사라진 위반은 목록에서 지우게 한다. 테스트가 목록을 자동으로 고치지 않는다.

해석 대규모 리팩터링 없이 아키텍처 규칙을 도입하는 방법이다. 동시에 계층 규칙은 목표이지 현재 상태가 아니다. 코드를 읽다 규칙상 있으면 안 되는 의존을 만나도 놀랄 필요가 없다. 기록 결정 기록은 OOP·DDD 리팩터링이 별도로 진행 중이라고 적고 있다. 확인 기준 커밋(main)에는 아직 들어오지 않았다.

도메인 사이의 경계는 아직 느슨하다

해석 계층 규칙에 비해 도메인끼리의 경계는 강제되지 않는다. 체크아웃 저장소 어댑터 하나가 주문·결제·쿠폰·회원 주소·SKU·장바구니 저장소 아홉 개를 직접 쓰는 것을 앞선 분석에서 봤다. 하나의 배포 단위 안에서 도메인 모듈 사이 경계까지 지키는 구조를 모듈러 모놀리스라 부른다. msbaek의 「Spring Modulith with DDD」 정리는 바운디드 컨텍스트를 모듈로 삼고, 계층별 패키징은 정의상 응집도가 낮아 모듈이 되지 못한다고 설명한다. PawCycle은 도메인별 패키징까지 했지만 도메인 사이 경계는 아직 강제하지 않는 단계에 있다.

6. 기술 스택과 그 선택 근거 (요약)

확인 backend/build.gradle에서 읽은 스택과, 각 선택의 근거가 된 결정 기록을 짝지으면 다음과 같다. 근거를 찾지 못한 것은 비워 두었다.

기술 쓰는 곳 왜 근거
Spring Boot 4.1 · Java 25 백엔드 전체 기술 버전 추천안은 Proposed였고 일부만 별도 승인 PWC-0032

해석 마지막 줄이 이 프로젝트의 태도를 잘 보여 준다. 기술을 먼저 늘리지 않고, 측정해서 필요가 확인될 때만 도입한다. README의 로드맵(“Measured Optimization → Technology Decision → Scale when justified”)과 같은 말이다.

7. 문서와 결정 기록을 읽는 법 (짧게)

이 저장소는 코드만큼 문서가 많다. 요구사항(PS), 도메인(DOMAIN), 데이터(DATA), API, ADR, 그리고 별도로 정리된 결정 기록(결정 129건, 교훈 49건)다. 근거로 쓸 때 지킬 것은 세 가지다.

  • 상태를 본다. 첫 아키텍처 결정 ARCH-001은 “Proposed”이고, 결정 기록 129건 중 9건도 proposed다. 제안과 승인과 구현은 다르다.
  • 코드와 대조한다. 이번 강의에서도 README와 운영 개요가 충돌했고, 결정 기록 PWC-0020이 리뷰 요약의 원래 트랜잭션을 “read-only”라고 적었지만 실제 코드는 그냥 @Transactional이었다.
  • 기여를 추정하지 않는다. 기록 AGENTS.md는 사용자가 Product Owner·Tech Lead로 결정과 병합을 승인하고 AI가 구현한다고 정한다. 어떤 판단이 누구의 것인지는 내가 추정하지 않는다.

1강을 마치며: 이제 설명할 수 있어야 하는 것

  • 정기배송이 도메인의 중심인 이유와, 두 구매 흐름이 공유하는 것
  • 스냅샷이 왜 가격을 복사해 두는지, 복합 외래 키와 CHECK 제약이 무엇을 보장하는지
  • /api/와 /가 어디로 가는지, MySQL과 Redis가 Compose에 없는 이유
  • 도메인 → 계층 패키징, ArchUnit 규칙과 동결된 위반 204개의 의미
  • 기술 선택마다 근거가 어디에 있는지

다음 2강은 이번 그림 1을 더 깊게 판다. C4의 System Context·Container·Component 를 그리고, DNS → TLS → Nginx → 컨테이너 → DB로 가는 배포 경로를 실제 설정 파일과 대조한다. 운영 상태의 문서 불일치도 그때 정리한다.

한계: 그림 4개는 실제 설정·DDL·디렉터리 구조를 바탕으로 이 강의에서 직접 그렸다. 외부 이미지는 원문을 열어 내용을 확인한 한 장만 넣었다. 테스트는 실행하지 않았다.
