13강. 상품 조회와 성능: 측정하고, 고치고, 다시 측정하기

이번 강의의 목표

  • 공개 상품 목록이 하나의 SQL로 어떻게 만들어지는지 해부한다.
  • N+1, 페이지 우선 조회(page-first), 옵티마이저 힌트가 각각 어떤 측정에서 출발했는지 따라간다.
  • 힌트 하나를 넣었다가 다시 측정해서 일부를 뺀 과정을 통해, 성능 개선이 “한 번 하고 끝”이 아님을 이해한다.
  • OFFSET 페이지네이션과 LIKE '%검색어%'의 한계, 그 대안을 판단한다.

1. 공개 상품 목록이라는 API

GET /api/products는 비로그인 사용자도 부르는 가장 많이 호출되는 API다. 필터가 많다.

// catalog/product/application/ProductQueryService.java (발췌)
public ProductListView findProducts(String q, String petType, String category, String subcategory,
    String brand, List<String> facets, BigDecimal minPrice, BigDecimal maxPrice,
    Boolean subscribable, Boolean purchasable, int page, int size, ProductSort sort) {
  if (page < 0 || size < 1 || size > 100)
    throw new IllegalArgumentException("page는 0 이상, size는 1~100이어야 합니다.");
  try {
    Math.multiplyExact(page, size);                       // ① OFFSET 계산의 정수 오버플로 방지
  } catch (ArithmeticException exception) {
    throw new IllegalArgumentException("page가 너무 큽니다.", exception);
  }
  ...
  try (var scope = diagnostics.openScope()) {             // ② 단계별 시간 측정
    return productDiscoveryReader.read(..., sort == null ? ProductSort.NEWEST : sort);
  } catch (RuntimeException exception) {
    throw new ProductListUnavailableException(exception);
  }
}
  • ① size ≤ 100과 multiplyExact. 크기 제한이 없으면 size=1000000 한 번으로 서버가 백만 행을 만든다. page × size가 int 범위를 넘으면 음수 OFFSET이 되는데, multiplyExact는 이때 예외를 던져 조용한 오동작을 막는다.
  • ② 목록은 엔티티가 아니라 read model이다. 기록 첫 구현(PR #36, 7/12)부터 엔티티를 그대로 반환하지 않고 목록 전용 모델을 조립했다. 그리고 상품 1회 + 그 상품들의 SKU 1회, 두 번의 일괄 조회로 N+1을 처음부터 막았다. 7강의 api-storage 규칙(컨트롤러가 엔티티를 내보내지 않음)과 같은 뿌리다.

2. N+1: 측정하고 나서 고친다

N+1은 목록 1번을 조회한 뒤, 목록의 각 항목마다 연관 데이터를 1번씩 더 조회하는 문제다. 상품 20개를 보여 주는데 SQL이 21번 나간다. 성하의 「JPA N+1 문제 해결 및 성능 비교 (feat. Batch Size)」는 실제 프로젝트에서 쿼리 수를 먼저 세어 보고 N+1을 발견한 뒤, 해결 전후 성능을 비교한 과정을 보여 준다. fetch join, @EntityGraph, @BatchSize가 대표적인 해결책이다.

PawCycle에서 N+1을 정면으로 다룬 곳은 상품이 아니라 구독이었다(3강·4강). 그 순서가 이 프로젝트의 성능 문화를 잘 보여 준다. 기록

  1. PR #102: 100건 픽스처로 페이지 크기 10/20/100마다 SQL 수를 먼저 쟀다(워밍업 3회, 9회 반복).
  2. PR #103: API와 스키마는 그대로 두고, 현재 페이지의 ID들에 대한 연관 행만 일괄 조회하도록 바꿨다.
  3. 캐시, 새 인덱스, 새 의존성은 도입하지 않았다. 가장 작은 변경을 골랐다.
API 개선 전 10 / 20 / 100건 개선 후
Plans 32 / 52 / 212 14 / 14 / 14
Subscriptions 51 / 91 / 411 15 / 15 / 19
  • 기록 결정 기록은 이 숫자가 헬스체크 쿼리까지 섞인 전역 카운터라서, 정확한 애플리케이션 SQL 수나 운영 용량으로 일반화하지 않는다고 적는다. 측정값의 한계까지 기록한 것이다.

3. 현재 목록 쿼리 해부

지금 목록은 JPA 엔티티 조회가 아니라 네이티브 SQL 하나다. 9강의 기준(“MySQL 고유 문법과 정밀한 실행 계획이 필요하면 네이티브”)에 해당한다.

-- catalog/product/persistence/ProductDiscoveryQueryRepository.java가 조립하는 SQL (요지)
SELECT p.id, p.name, ...,
       c.id, c.name, b.id, b.name, ...,
       (SELECT s2.price FROM skus s2 WHERE s2.product_id=p.id AND s2.status='ACTIVE'
         ORDER BY s2.price ASC, s2.id ASC LIMIT 1)                 representative_price,   -- ①
       (SELECT s2.compare_at_price ... 같은 조건 ... LIMIT 1)       compare_at_price,
       (SELECT s2.id   ... 같은 조건 ... LIMIT 1)                   representative_sku_id,
       (SELECT s2.name ... 같은 조건 ... LIMIT 1)                   representative_sku_name,
       (SELECT AVG(r.rating) FROM reviews r WHERE r.product_id=p.id AND r.visible=true) average_rating,
       (SELECT COUNT(*)      FROM reviews r WHERE r.product_id=p.id AND r.visible=true) review_count,
       MAX(CASE WHEN s.status='ACTIVE' AND s.subscribable=true THEN 1 ELSE 0 END) has_subscribable,  -- ②
       MAX(CASE WHEN s.status='ACTIVE' AND i.available_quantity > 0 THEN 1 ELSE 0 END) purchasable
FROM {상품 원천}  p
JOIN categories c ON c.id=p.category_id JOIN brands b ON b.id=p.brand_id
LEFT JOIN categories parent ON parent.id=c.parent_id
LEFT JOIN product_images main_image ON main_image.product_id=p.id AND main_image.image_type='MAIN'
LEFT JOIN skus s ON s.product_id=p.id LEFT JOIN inventories i ON i.sku_id=s.id
WHERE p.display_status='PUBLIC' AND c.active=true AND b.active=true ...                         -- ③
GROUP BY p.id, ...
ORDER BY ...
LIMIT :limit OFFSET :offset
  • ① 대표 SKU는 상관 서브쿼리 4개로 고른다. “활성 SKU 중 가장 싼 것”의 가격, 정가, ID, 이름을 각각 서브쿼리로 가져온다.
    • 해석 같은 조건의 서브쿼리가 네 번 실행된다. 페이지 20개면 상품마다 4번, 총 80번이다. 인덱스(skus.product_id)를 타므로 각각은 싸지만 중복이다.
    • MySQL 8.0의 LATERAL 파생 테이블이나 ROW_NUMBER() 창 함수를 쓰면 한 번에 고를 수 있다. 다만 실측 없이 바꾸지 않는다는 원칙을 따르면, 이것은 “EXPLAIN과 측정으로 확인할 후보”다.
  • ② 플래그는 LEFT JOIN + GROUP BY + MAX(CASE ...)로 만든다. 상품 하나에 SKU가 여러 개라 행이 늘어나는데, GROUP BY p.id로 다시 하나로 접는다. “활성 SKU 중 하나라도 구독 가능하면 1”을 MAX로 표현했다.
  • ③ 동적 WHERE지만 SQL 인젝션은 막혀 있다. 조건 문자열은 코드가 조립하지만, 사용자 값은 전부 :p1 같은 이름 있는 파라미터로 바인딩한다. 정렬도 사용자 문자열을 이어 붙이지 않고 ProductSort enum의 switch로 고른다. 사용자 입력이 SQL 문법이 될 길이 없다.
  • 카테고리·브랜드가 비활성이면 상품도 안 보인다. c.active=true AND b.active=true가 목록 조건에 있다. 5강에서 “카테고리 비활성화는 상품 상태를 연쇄 변경하지 않는다”고 했다. 상품의 상태값은 그대로 두고, 조회할 때 걸러 내는 방식이다.

4. 페이지 우선 조회 (page-first)

기록 PR #321은 최신순·추천순 정렬에서 쿼리의 순서를 바꿨다. 무엇이 달라졌는지 그림으로 보자.

코드에서는 정렬에 따라 “상품 원천”을 바꿔 끼운다.

boolean pageFirst = sort == ProductSort.NEWEST || sort == ProductSort.RECOMMENDED;
// Bound filters may benefit from selective indexes; constrain only the unfiltered page.
boolean orderedPageFirst = pageFirst && parameters.isEmpty() && subscribable == null && purchasable == null;

// LIMIT prevents MySQL from merging this derived table into the outer aggregation.
String productSource = pageFirst
    ? (orderedPageFirst
          ? "(SELECT /*+ JOIN_PREFIX(p) NO_BNL(c, b) */ p.* FROM products p FORCE INDEX(PRIMARY) "
          : "(SELECT p.* FROM products p ")
      + "JOIN categories c ... JOIN brands b ... LEFT JOIN categories parent ..."
      + where + order + " LIMIT :limit OFFSET :offset) p"
    : "products p";
  • 왜 최신·추천순만인가. 최신순은 ORDER BY p.id DESC, 상품 테이블에 이미 있는 컬럼이다. 그래서 집계 전에 순서를 알 수 있다. 가격순은 “활성 SKU 중 최저가”라는 계산된 값이라, SKU를 다 조인해 계산하기 전에는 순서를 모른다. 그림 왼쪽 경로를 피할 수 없다.
  • 파생 테이블의 LIMIT이 하는 일. 주석이 정확히 설명한다. 원리 MySQL 옵티마이저는 FROM (SELECT ...) 같은 파생 테이블을 바깥 쿼리에 병합(merge) 해서 하나의 쿼리로 펴 버리기도 한다. 그러면 “먼저 20개를 고른다”는 의도가 사라진다. 파생 테이블 안에 LIMIT이 있으면 병합할 수 없어서, 먼저 잘라 낸 결과가 물리적으로 따로 만들어진다(materialize).
  • 필터가 있으면 힌트를 빼는 이유. 주석의 첫 줄이다. 브랜드나 카테고리 필터가 있으면 그 조건을 잘 거르는 인덱스가 더 나을 수 있다. 그때 PK 스캔을 강제하면 오히려 느려진다. 그래서 힌트는 필터 없는 첫 화면에만 쓴다.

5. 옵티마이저 힌트: 넣고, 재고, 일부를 뺐다 (깊게)

힌트 세 개의 의미부터 보자.

  • FORCE INDEX(PRIMARY): 상품을 기본 키 순서로 읽게 강제한다. ORDER BY p.id DESC LIMIT 20이면 PK를 역순으로 읽다가 20개(필터를 통과한)가 모이면 멈출 수 있다. 정렬(filesort)도 필요 없다. 6강의 “인덱스 = 정렬”이 여기서 일한다.
  • JOIN_PREFIX(p): 조인 순서에서 p(상품)를 맨 앞에 두라는 힌트다. 상품을 먼저 읽고, 각 상품의 카테고리·브랜드를 찾아가는 순서다.
  • NO_BNL(c, b): 카테고리·브랜드 조인에 해시 조인(블록 조인)을 쓰지 말라는 힌트다.

해시 조인이 무엇인지는 Hoing의 「MySQL8 해시조인(Hash Join)」이 그림으로 설명한다. MySQL은 오래도록 중첩 루프 조인(한쪽 행마다 다른 쪽을 찾아감)만 지원했다. 그 개선책으로 BKA와 BNL(Block Nested Loop)이 들어왔고, 8.0.18부터 해시 조인이 들어왔다.

  • 해시 조인은 작은 쪽 입력으로 해시 테이블을 만들고(build), 큰 쪽을 읽으며 찾아본다(probe).
  • 원리 MySQL 8.0.18 이후 BNL / NO_BNL 힌트가 해시 조인 사용 여부를 제어하는 데 쓰인다. 블록 조인 자리를 해시 조인이 대신하게 됐기 때문이다.

출처: Hoing · MySQL8 해시조인(Hash Join). 블로그 자체 서버의 그림이라 만료되지 않는다.

목록 쿼리: 27.4ms → 4.0ms

기록 PR #322는 실제 실행 계획(EXPLAIN)을 보고, 페이지 우선 조회 안에서도 1만 행을 스캔한 뒤에야 LIMIT이 적용되고 있음을 발견했다. 그래서 필터 없는 목록에 세 힌트를 넣었다. 단일 쿼리 시간이 27.4ms → 4.0ms가 됐다.

  • 결정 기록은 이것을 “단일 쿼리 측정이며, 용량이나 p95 개선 주장이 아니다”라고 선을 긋는다.

개수 쿼리: 힌트를 넣었다가, 일부를 뺐다

이 이야기의 핵심은 여기다. 목록 위의 “전체 N개” 숫자를 위한 COUNT 쿼리에도 같은 힌트를 넣었다.

  • PR #325: COUNT 쿼리에도 “상품 먼저(JOIN_PREFIX)” 힌트를 추가했다.
  • PR #330: 다시 측정해 보니, 그 힌트가 카테고리·브랜드 조회를 상품마다 1만 번씩 하도록 강제하고 있었다.
    • COUNT는 상품 전부를 세야 한다. LIMIT에서 멈출 수 없다.
    • 이때는 작은 카테고리·브랜드 테이블로 해시 테이블을 한 번 만들고, 상품을 한 번 훑는 편이 낫다.
  • 그래서 JOIN_PREFIX만 빼고 NO_BNL과 FORCE INDEX(PRIMARY)는 남겼다. 같은 조건의 격리 실험 50회에서 결과는 이렇다.
    • COUNT: 25.652ms → 5.972ms
    • p95: 311.5ms → 89.7ms
    • 오류·드롭 0, 응답 전체 해시가 같음(결과가 바뀌지 않았음을 확인)

확인 현재 코드도 정확히 그렇다. 목록용 힌트는 /*+ JOIN_PREFIX(p) NO_BNL(c, b) */, COUNT용은 /*+ NO_BNL(c, b) */다.

해석 여기서 배울 것은 세 가지다.

  • 같은 힌트가 목록에는 약이고 COUNT에는 독이었다. LIMIT에서 멈출 수 있는가가 갈랐다. 힌트는 쿼리의 모양에 묶여 있다.
  • 힌트는 데이터에 묶여 있다. 상품이 1만 개일 때의 최적이 100만 개일 때도 최적이라는 보장이 없다. 결정 기록도 “힌트를 영구적인 성능 법칙으로 일반화하지 않는다”고 적는다.
  • 결과가 같은지 확인했다. 성능 변경이 응답 내용을 바꾸지 않았음을 응답 전체 해시로 비교했다. 빨라졌는데 틀린 결과를 내는 개선은 개선이 아니다.

EXPLAIN 결과를 읽는 법은 짱구의 「MySQL EXPLAIN 실행계획 보는 법 — type, key, rows, Extra」가 Real MySQL 8.0을 바탕으로 컬럼별로 정리한다.

출처: 짱구 · MySQL EXPLAIN 실행계획 보는 법. tistory 그림이라 11월 30일 만료.

6. 측정이 “효과 약함”이라고 말할 때

모든 시도가 성공한 것은 아니다. 기록 성능 9단계에서 이런 가설을 세웠다. “목록 조회가 DB 쿼리 뒤의 그룹핑·DTO 조립까지 커넥션을 쥐고 있어서 느리다.”

  • 그래서 별도의 읽기 Bean이 짧은 읽기 전용 트랜잭션 안에서 상품과 SKU를 불변 값으로만 꺼내고, DTO 조립은 트랜잭션 밖에서 하도록 나눴다. 9강의 “커넥션을 오래 쥐지 않는다”와 같은 방향이다.
  • 같은 조건(Tomcat 128, CPU 1.5, 1GiB, Hikari 10, 목표 250 RPS)에서 결과는 이렇다.
    • 처리량: 145.7 → 154.2 RPS (+5.8%)
    • 드롭: 11,521 → 10,497
    • p95: 8.136s → 7.996s
    • 그러나 p99: 9.258s → 9.916s로 나빠졌고, 커넥션 대기는 116 → 117로 그대로였다.
  • 판정은 “효과 약함”이었다. 결정 기록은 “이 분리가 큐 붕괴의 주원인을 해결했다고 주장하지 않는다”고 적는다. 수집기 실패로 커넥션 점유 시간을 직접 재지 못한 한계도 남겼다.

해석 포트폴리오에서 이런 기록이 가장 강하다. “최적화해서 몇 배 빨라졌다”보다 “가설을 세웠고, 측정했고, 효과가 약해서 다른 원인을 찾았다”가 실력을 더 잘 보여 준다. 3강에서 본 “풀을 늘렸더니 오히려 나빠졌다”와 같은 계열이다.

확인 이런 측정을 위해 목록 쿼리는 단계별 타이머를 갖고 있다. pawcycle.catalog.product.discovery.phase 메트릭에 count-query, list-query, row-mapping 등이 태그로 기록된다. 다만 진단 플래그(PAWCYCLE_CATALOG_PRODUCT_DISCOVERY_DIAGNOSTICS_ENABLED)가 켜졌을 때만이다. 기본은 꺼짐이라 운영 비용이 없다.

7. 아직 남은 두 가지 한계

OFFSET은 뒤로 갈수록 비싸다

향로의 「페이징 성능 개선하기 - No Offset 사용하기」는 이 문제를 정면으로 다룬다. 데이터가 적을 때는 문제없던 페이징이, 데이터가 쌓이면 수십 초에서 수 분까지 느려진다.

  • LIMIT 20 OFFSET 100000은 앞의 10만 행을 읽고 버린 뒤 20개를 준다. 페이지가 뒤로 갈수록 느려진다.
  • 해결책은 “마지막으로 본 ID보다 작은 것 20개”(WHERE id < :lastId ORDER BY id DESC LIMIT 20)처럼 시작 지점을 조건으로 주는 것이다. 인덱스에서 바로 그 위치로 뛰어간다.

출처: 향로 · 페이징 성능 개선하기 - No Offset 사용하기. 만료 없는 옛 주소.

  • 해석 PawCycle에 적용하면. 최신순(p.id DESC)은 No Offset으로 바꾸기 쉽다. 하지만 가격순·평점순은 “마지막으로 본 가격 + ID” 같은 복합 커서가 필요하다. 그리고 “3페이지로 바로 가기” 같은 페이지 번호 UI는 쓸 수 없게 된다(무한 스크롤 전용).
    • 지금 상품 수(카탈로그 수천 단위)에서는 OFFSET 비용이 크지 않다. 그래서 측정으로 문제가 확인되면 최신순부터 바꾸는 것이 이 프로젝트다운 순서다.
    • 같은 시리즈의 「커버링 인덱스 사용하기」는 OFFSET을 유지하면서 비용을 줄이는 다른 방법이다. 미확인 이 둘째 글의 주소는 시리즈 번호로 추정한 것이며 열어 보지 않았다.

LIKE '%검색어%'는 인덱스를 못 쓴다

String needle = "%" + q.trim().toLowerCase(Locale.ROOT) + "%";
where.append(" AND (LOWER(p.name) LIKE :q1 OR LOWER(p.short_description) LIKE :q2 OR LOWER(COALESCE(p.description,'')) LIKE :q3)");
  • 원리 B-Tree 인덱스는 앞에서부터 정렬돼 있다(6강). LIKE '사료%'는 그 범위로 바로 갈 수 있지만, LIKE '%사료%'는 어디서 시작할지 몰라 전부 읽는다. 컬럼에 LOWER() 함수를 씌운 것도 인덱스 사용을 막는다.
  • 해석 LOWER()는 사실 필요 없다. 6강에서 본 테이블 기본 콜레이션 utf8mb4_0900_ai_ci는 이미 대소문자를 무시하고 비교한다. name LIKE '%Salmon%'도 salmon을 찾는다. 함수를 빼도 결과는 같다. 다만 앞 % 때문에 어차피 인덱스는 못 쓰므로, 지금 당장 성능 차이는 거의 없다.
  • 대안: MySQL FULLTEXT 인덱스와 ngram 파서(한국어처럼 띄어쓰기로 단어를 나누기 어려운 언어용)를 쓰거나, 검색 엔진(Elasticsearch 등)을 따로 둔다. 둘 다 운영 비용이 생긴다. 카탈로그가 작은 지금은 전체 스캔이 더 단순하다.

13강 정리

  • 목록은 엔티티가 아니라 read model이고, 지금은 네이티브 SQL 하나다.
    • size ≤ 100, multiplyExact로 입력 폭주와 오버플로를 막는다.
    • 동적 WHERE지만 값은 바인딩, 정렬은 enum이라 인젝션이 없다.
  • N+1: 먼저 SQL 수를 쟀고, 현재 페이지 ID로 일괄 조회해 211 → 14로 줄였다. 측정값의 한계까지 기록했다.
  • 페이지 우선 조회
    • 정렬 키가 상품 테이블에 있을 때(최신·추천)만, 20개를 먼저 고르고 그 20개에만 조인·집계한다.
    • 파생 테이블의 LIMIT이 병합을 막는다.
  • 힌트
    • 목록에는 JOIN_PREFIX + NO_BNL + FORCE INDEX(PRIMARY)로 27.4 → 4.0ms.
    • COUNT에는 JOIN_PREFIX가 1만 번 조회를 강제해서 빼고 다시 쟀다(25.7 → 6.0ms, p95 311 → 90ms).
    • 힌트는 쿼리 모양과 데이터에 묶여 있다.
  • “효과 약함”도 결과다: 짧은 읽기 트랜잭션 분리는 +5.8%에 그쳤고, 그렇게 기록했다.
  • 남은 한계
    • OFFSET은 뒤 페이지로 갈수록 비싸다(No Offset은 최신순부터 가능).
    • LIKE '%q%'는 전체 스캔이고, LOWER()는 ci 콜레이션에서 불필요하다.
    • 대표 SKU 서브쿼리가 4중으로 중복된다.
