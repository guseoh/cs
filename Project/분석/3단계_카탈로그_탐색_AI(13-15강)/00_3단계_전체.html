13강. 상품 조회와 성능: 측정하고, 고치고, 다시 측정하기

이번 강의의 목표

  • 공개 상품 목록이 하나의 SQL로 어떻게 만들어지는지 해부한다.
  • N+1, 페이지 우선 조회(page-first), 옵티마이저 힌트가 각각 어떤 측정에서 출발했는지 따라간다.
  • 힌트 하나를 넣었다가 다시 측정해서 일부를 뺀 과정을 통해, 성능 개선이 “한 번 하고 끝”이 아님을 이해한다.
  • OFFSET 페이지네이션과 LIKE '%검색어%'의 한계, 그 대안을 판단한다.

1. 공개 상품 목록이라는 API

GET /api/products는 비로그인 사용자도 부르는 가장 많이 호출되는 API다. 필터가 많다.

// catalog/product/application/ProductQueryService.java (발췌)
public ProductListView findProducts(String q, String petType, String category, String subcategory,
    String brand, List<String> facets, BigDecimal minPrice, BigDecimal maxPrice,
    Boolean subscribable, Boolean purchasable, int page, int size, ProductSort sort) {
  if (page < 0 || size < 1 || size > 100)
    throw new IllegalArgumentException("page는 0 이상, size는 1~100이어야 합니다.");
  try {
    Math.multiplyExact(page, size);                       // ① OFFSET 계산의 정수 오버플로 방지
  } catch (ArithmeticException exception) {
    throw new IllegalArgumentException("page가 너무 큽니다.", exception);
  }
  ...
  try (var scope = diagnostics.openScope()) {             // ② 단계별 시간 측정
    return productDiscoveryReader.read(..., sort == null ? ProductSort.NEWEST : sort);
  } catch (RuntimeException exception) {
    throw new ProductListUnavailableException(exception);
  }
}
  • ① size ≤ 100과 multiplyExact. 크기 제한이 없으면 size=1000000 한 번으로 서버가 백만 행을 만든다. page × size가 int 범위를 넘으면 음수 OFFSET이 되는데, multiplyExact는 이때 예외를 던져 조용한 오동작을 막는다.
  • ② 목록은 엔티티가 아니라 read model이다. 기록 첫 구현(PR #36, 7/12)부터 엔티티를 그대로 반환하지 않고 목록 전용 모델을 조립했다. 그리고 상품 1회 + 그 상품들의 SKU 1회, 두 번의 일괄 조회로 N+1을 처음부터 막았다. 7강의 api-storage 규칙(컨트롤러가 엔티티를 내보내지 않음)과 같은 뿌리다.

2. N+1: 측정하고 나서 고친다

N+1은 목록 1번을 조회한 뒤, 목록의 각 항목마다 연관 데이터를 1번씩 더 조회하는 문제다. 상품 20개를 보여 주는데 SQL이 21번 나간다. 성하의 「JPA N+1 문제 해결 및 성능 비교 (feat. Batch Size)」는 실제 프로젝트에서 쿼리 수를 먼저 세어 보고 N+1을 발견한 뒤, 해결 전후 성능을 비교한 과정을 보여 준다. fetch join, @EntityGraph, @BatchSize가 대표적인 해결책이다.

PawCycle에서 N+1을 정면으로 다룬 곳은 상품이 아니라 구독이었다(3강·4강). 그 순서가 이 프로젝트의 성능 문화를 잘 보여 준다. 기록

  1. PR #102: 100건 픽스처로 페이지 크기 10/20/100마다 SQL 수를 먼저 쟀다(워밍업 3회, 9회 반복).
  2. PR #103: API와 스키마는 그대로 두고, 현재 페이지의 ID들에 대한 연관 행만 일괄 조회하도록 바꿨다.
  3. 캐시, 새 인덱스, 새 의존성은 도입하지 않았다. 가장 작은 변경을 골랐다.

  • 기록 결정 기록은 이 숫자가 헬스체크 쿼리까지 섞인 전역 카운터라서, 정확한 애플리케이션 SQL 수나 운영 용량으로 일반화하지 않는다고 적는다. 측정값의 한계까지 기록한 것이다.

3. 현재 목록 쿼리 해부

지금 목록은 JPA 엔티티 조회가 아니라 네이티브 SQL 하나다. 9강의 기준(“MySQL 고유 문법과 정밀한 실행 계획이 필요하면 네이티브”)에 해당한다.

-- catalog/product/persistence/ProductDiscoveryQueryRepository.java가 조립하는 SQL (요지)
SELECT p.id, p.name, ...,
       c.id, c.name, b.id, b.name, ...,
       (SELECT s2.price FROM skus s2 WHERE s2.product_id=p.id AND s2.status='ACTIVE'
         ORDER BY s2.price ASC, s2.id ASC LIMIT 1)                 representative_price,   -- ①
       (SELECT s2.compare_at_price ... 같은 조건 ... LIMIT 1)       compare_at_price,
       (SELECT s2.id   ... 같은 조건 ... LIMIT 1)                   representative_sku_id,
       (SELECT s2.name ... 같은 조건 ... LIMIT 1)                   representative_sku_name,
       (SELECT AVG(r.rating) FROM reviews r WHERE r.product_id=p.id AND r.visible=true) average_rating,
       (SELECT COUNT(*)      FROM reviews r WHERE r.product_id=p.id AND r.visible=true) review_count,
       MAX(CASE WHEN s.status='ACTIVE' AND s.subscribable=true THEN 1 ELSE 0 END) has_subscribable,  -- ②
       MAX(CASE WHEN s.status='ACTIVE' AND i.available_quantity > 0 THEN 1 ELSE 0 END) purchasable
FROM {상품 원천}  p
JOIN categories c ON c.id=p.category_id JOIN brands b ON b.id=p.brand_id
LEFT JOIN categories parent ON parent.id=c.parent_id
LEFT JOIN product_images main_image ON main_image.product_id=p.id AND main_image.image_type='MAIN'
LEFT JOIN skus s ON s.product_id=p.id LEFT JOIN inventories i ON i.sku_id=s.id
WHERE p.display_status='PUBLIC' AND c.active=true AND b.active=true ...                         -- ③
GROUP BY p.id, ...
ORDER BY ...
LIMIT :limit OFFSET :offset
  • ① 대표 SKU는 상관 서브쿼리 4개로 고른다. “활성 SKU 중 가장 싼 것”의 가격, 정가, ID, 이름을 각각 서브쿼리로 가져온다.
    • 해석 같은 조건의 서브쿼리가 네 번 실행된다. 페이지 20개면 상품마다 4번, 총 80번이다. 인덱스(skus.product_id)를 타므로 각각은 싸지만 중복이다.
    • MySQL 8.0의 LATERAL 파생 테이블이나 ROW_NUMBER() 창 함수를 쓰면 한 번에 고를 수 있다. 다만 실측 없이 바꾸지 않는다는 원칙을 따르면, 이것은 “EXPLAIN과 측정으로 확인할 후보”다.
  • ② 플래그는 LEFT JOIN + GROUP BY + MAX(CASE ...)로 만든다. 상품 하나에 SKU가 여러 개라 행이 늘어나는데, GROUP BY p.id로 다시 하나로 접는다. “활성 SKU 중 하나라도 구독 가능하면 1”을 MAX로 표현했다.
  • ③ 동적 WHERE지만 SQL 인젝션은 막혀 있다. 조건 문자열은 코드가 조립하지만, 사용자 값은 전부 :p1 같은 이름 있는 파라미터로 바인딩한다. 정렬도 사용자 문자열을 이어 붙이지 않고 ProductSort enum의 switch로 고른다. 사용자 입력이 SQL 문법이 될 길이 없다.
  • 카테고리·브랜드가 비활성이면 상품도 안 보인다. c.active=true AND b.active=true가 목록 조건에 있다. 5강에서 “카테고리 비활성화는 상품 상태를 연쇄 변경하지 않는다”고 했다. 상품의 상태값은 그대로 두고, 조회할 때 걸러 내는 방식이다.

4. 페이지 우선 조회 (page-first)

기록 PR #321은 최신순·추천순 정렬에서 쿼리의 순서를 바꿨다. 무엇이 달라졌는지 그림으로 보자.

코드에서는 정렬에 따라 “상품 원천”을 바꿔 끼운다.

boolean pageFirst = sort == ProductSort.NEWEST || sort == ProductSort.RECOMMENDED;
// Bound filters may benefit from selective indexes; constrain only the unfiltered page.
boolean orderedPageFirst = pageFirst && parameters.isEmpty() && subscribable == null && purchasable == null;

// LIMIT prevents MySQL from merging this derived table into the outer aggregation.
String productSource = pageFirst
    ? (orderedPageFirst
          ? "(SELECT /*+ JOIN_PREFIX(p) NO_BNL(c, b) */ p.* FROM products p FORCE INDEX(PRIMARY) "
          : "(SELECT p.* FROM products p ")
      + "JOIN categories c ... JOIN brands b ... LEFT JOIN categories parent ..."
      + where + order + " LIMIT :limit OFFSET :offset) p"
    : "products p";
  • 왜 최신·추천순만인가. 최신순은 ORDER BY p.id DESC, 상품 테이블에 이미 있는 컬럼이다. 그래서 집계 전에 순서를 알 수 있다. 가격순은 “활성 SKU 중 최저가”라는 계산된 값이라, SKU를 다 조인해 계산하기 전에는 순서를 모른다. 그림 왼쪽 경로를 피할 수 없다.
  • 파생 테이블의 LIMIT이 하는 일. 주석이 정확히 설명한다. 원리 MySQL 옵티마이저는 FROM (SELECT ...) 같은 파생 테이블을 바깥 쿼리에 병합(merge) 해서 하나의 쿼리로 펴 버리기도 한다. 그러면 “먼저 20개를 고른다”는 의도가 사라진다. 파생 테이블 안에 LIMIT이 있으면 병합할 수 없어서, 먼저 잘라 낸 결과가 물리적으로 따로 만들어진다(materialize).
  • 필터가 있으면 힌트를 빼는 이유. 주석의 첫 줄이다. 브랜드나 카테고리 필터가 있으면 그 조건을 잘 거르는 인덱스가 더 나을 수 있다. 그때 PK 스캔을 강제하면 오히려 느려진다. 그래서 힌트는 필터 없는 첫 화면에만 쓴다.

5. 옵티마이저 힌트: 넣고, 재고, 일부를 뺐다 (깊게)

힌트 세 개의 의미부터 보자.

  • FORCE INDEX(PRIMARY): 상품을 기본 키 순서로 읽게 강제한다. ORDER BY p.id DESC LIMIT 20이면 PK를 역순으로 읽다가 20개(필터를 통과한)가 모이면 멈출 수 있다. 정렬(filesort)도 필요 없다. 6강의 “인덱스 = 정렬”이 여기서 일한다.
  • JOIN_PREFIX(p): 조인 순서에서 p(상품)를 맨 앞에 두라는 힌트다. 상품을 먼저 읽고, 각 상품의 카테고리·브랜드를 찾아가는 순서다.
  • NO_BNL(c, b): 카테고리·브랜드 조인에 해시 조인(블록 조인)을 쓰지 말라는 힌트다.

해시 조인이 무엇인지는 Hoing의 「MySQL8 해시조인(Hash Join)」이 그림으로 설명한다. MySQL은 오래도록 중첩 루프 조인(한쪽 행마다 다른 쪽을 찾아감)만 지원했다. 그 개선책으로 BKA와 BNL(Block Nested Loop)이 들어왔고, 8.0.18부터 해시 조인이 들어왔다.

  • 해시 조인은 작은 쪽 입력으로 해시 테이블을 만들고(build), 큰 쪽을 읽으며 찾아본다(probe).
  • 원리 MySQL 8.0.18 이후 BNL / NO_BNL 힌트가 해시 조인 사용 여부를 제어하는 데 쓰인다. 블록 조인 자리를 해시 조인이 대신하게 됐기 때문이다.

출처: Hoing · MySQL8 해시조인(Hash Join). 블로그 자체 서버의 그림이라 만료되지 않는다.

목록 쿼리: 27.4ms → 4.0ms

기록 PR #322는 실제 실행 계획(EXPLAIN)을 보고, 페이지 우선 조회 안에서도 1만 행을 스캔한 뒤에야 LIMIT이 적용되고 있음을 발견했다. 그래서 필터 없는 목록에 세 힌트를 넣었다. 단일 쿼리 시간이 27.4ms → 4.0ms가 됐다.

  • 결정 기록은 이것을 “단일 쿼리 측정이며, 용량이나 p95 개선 주장이 아니다”라고 선을 긋는다.

개수 쿼리: 힌트를 넣었다가, 일부를 뺐다

이 이야기의 핵심은 여기다. 목록 위의 “전체 N개” 숫자를 위한 COUNT 쿼리에도 같은 힌트를 넣었다.

  • PR #325: COUNT 쿼리에도 “상품 먼저(JOIN_PREFIX)” 힌트를 추가했다.
  • PR #330: 다시 측정해 보니, 그 힌트가 카테고리·브랜드 조회를 상품마다 1만 번씩 하도록 강제하고 있었다.
    • COUNT는 상품 전부를 세야 한다. LIMIT에서 멈출 수 없다.
    • 이때는 작은 카테고리·브랜드 테이블로 해시 테이블을 한 번 만들고, 상품을 한 번 훑는 편이 낫다.
  • 그래서 JOIN_PREFIX만 빼고 NO_BNL과 FORCE INDEX(PRIMARY)는 남겼다. 같은 조건의 격리 실험 50회에서 결과는 이렇다.
    • COUNT: 25.652ms → 5.972ms
    • p95: 311.5ms → 89.7ms
    • 오류·드롭 0, 응답 전체 해시가 같음(결과가 바뀌지 않았음을 확인)

확인 현재 코드도 정확히 그렇다. 목록용 힌트는 /*+ JOIN_PREFIX(p) NO_BNL(c, b) */, COUNT용은 /*+ NO_BNL(c, b) */다.

해석 여기서 배울 것은 세 가지다.

  • 같은 힌트가 목록에는 약이고 COUNT에는 독이었다. LIMIT에서 멈출 수 있는가가 갈랐다. 힌트는 쿼리의 모양에 묶여 있다.
  • 힌트는 데이터에 묶여 있다. 상품이 1만 개일 때의 최적이 100만 개일 때도 최적이라는 보장이 없다. 결정 기록도 “힌트를 영구적인 성능 법칙으로 일반화하지 않는다”고 적는다.
  • 결과가 같은지 확인했다. 성능 변경이 응답 내용을 바꾸지 않았음을 응답 전체 해시로 비교했다. 빨라졌는데 틀린 결과를 내는 개선은 개선이 아니다.

EXPLAIN 결과를 읽는 법은 짱구의 「MySQL EXPLAIN 실행계획 보는 법 — type, key, rows, Extra」가 Real MySQL 8.0을 바탕으로 컬럼별로 정리한다.

6. 측정이 “효과 약함”이라고 말할 때

모든 시도가 성공한 것은 아니다. 기록 성능 9단계에서 이런 가설을 세웠다. “목록 조회가 DB 쿼리 뒤의 그룹핑·DTO 조립까지 커넥션을 쥐고 있어서 느리다.”

  • 그래서 별도의 읽기 Bean이 짧은 읽기 전용 트랜잭션 안에서 상품과 SKU를 불변 값으로만 꺼내고, DTO 조립은 트랜잭션 밖에서 하도록 나눴다. 9강의 “커넥션을 오래 쥐지 않는다”와 같은 방향이다.
  • 같은 조건(Tomcat 128, CPU 1.5, 1GiB, Hikari 10, 목표 250 RPS)에서 결과는 이렇다.
    • 처리량: 145.7 → 154.2 RPS (+5.8%)
    • 드롭: 11,521 → 10,497
    • p95: 8.136s → 7.996s
    • 그러나 p99: 9.258s → 9.916s로 나빠졌고, 커넥션 대기는 116 → 117로 그대로였다.
  • 판정은 “효과 약함”이었다. 결정 기록은 “이 분리가 큐 붕괴의 주원인을 해결했다고 주장하지 않는다”고 적는다. 수집기 실패로 커넥션 점유 시간을 직접 재지 못한 한계도 남겼다.

해석 포트폴리오에서 이런 기록이 가장 강하다. “최적화해서 몇 배 빨라졌다”보다 “가설을 세웠고, 측정했고, 효과가 약해서 다른 원인을 찾았다”가 실력을 더 잘 보여 준다. 3강에서 본 “풀을 늘렸더니 오히려 나빠졌다”와 같은 계열이다.

확인 이런 측정을 위해 목록 쿼리는 단계별 타이머를 갖고 있다. pawcycle.catalog.product.discovery.phase 메트릭에 count-query, list-query, row-mapping 등이 태그로 기록된다. 다만 진단 플래그(PAWCYCLE_CATALOG_PRODUCT_DISCOVERY_DIAGNOSTICS_ENABLED)가 켜졌을 때만이다. 기본은 꺼짐이라 운영 비용이 없다.

OFFSET은 뒤로 갈수록 비싸다

향로의 「페이징 성능 개선하기 - No Offset 사용하기」는 이 문제를 정면으로 다룬다. 데이터가 적을 때는 문제없던 페이징이, 데이터가 쌓이면 수십 초에서 수 분까지 느려진다.

  • LIMIT 20 OFFSET 100000은 앞의 10만 행을 읽고 버린 뒤 20개를 준다. 페이지가 뒤로 갈수록 느려진다.

14강. 캐시와 관리자 카탈로그: 캐시가 효과를 낸 길이 사라졌을 때

이번 강의의 목표

  • PawCycle이 Redis 캐시를 어떤 측정에서 출발해 들였는지 안다.
  • 캐시를 비우는 순간과 다시 채우는 순간이 엇갈릴 때 생기는 낡은 값 재적재(stale refill) 경쟁과, 이를 막는 세대 번호 + Lua 스크립트 + 커밋 후 무효화를 이해한다.
  • [이번 강의의 핵심 발견] 그렇게 정교하게 만든 캐시가 지금은 읽히지 않는다는 사실과, 그 의미를 판단한다.
  • 관리자 카탈로그의 상태 전이, 감사 기록, 카테고리 2단계 규칙을 보고, 9강에서 남긴 “왜 READ COMMITTED인가”에 답한다.

1. 캐시를 들인 이유: “DB가 느리다”고 가정하지 않았다

기록 3강과 13강에서 본 성능 9단계의 상황은 이랬다.

  • GET /api/products는 CPU를 늘리면 처리량이 좋아졌지만, CPU 2.0에서도 요청 드롭, 긴 꼬리 지연, 커넥션 대기가 남았다.
  • 관련 SQL 자체는 비교적 쌌다. 커넥션 풀을 늘리면 오히려 나빠졌다. Java 핫스팟을 짚을 유효한 프로파일링 결과도 없었다.

그래서 결정 기록은 이렇게 적는다. “DB가 느리기 때문에 Redis가 필요하다고 가정하지 않고, 반복 조회의 JPA 객체화·DTO 조립과 커넥션 사용을 캐시 적중으로 우회할 수 있는지 시험했다.”

결과는 극적이었다. 기록 로컬·합성 조건의 첫 결과 기준이다.

처리량 드롭 p95 p99
Before (CPU 2.0) 약 193.5 RPS 5,808 6,854.56ms 8,590.75ms
Redis After 250 RPS (목표 상한) 0 4.71ms 26.99ms

판정은 KEEP이었다. 결정 기록은 이 수치를 “현재 운영 성능, 최대 RPS, SLO 달성으로 쓸 수 없다”고 선을 긋는다. 목표가 250 RPS였으니 최대치는 탐색하지 않았다는 한계도 적었다.

2. 캐시 무효화의 함정: 낡은 값 재적재

가장 흔한 캐시 방식은 캐시 어사이드(cache-aside, lazy loading)다.

  • 읽을 때 캐시에 있으면 쓰고, 없으면 DB에서 읽어 캐시에 넣는다.
  • 쓸 때는 DB를 바꾸고 캐시를 지운다.

Inpa Dev의 「[REDIS] 캐시(Cache) 설계 전략 지침 총정리」가 캐시 어사이드, 라이트 스루(write-through), 라이트 백(write-back) 같은 읽기·쓰기 전략을 그림과 함께 정리한다. 그림은 지연 로딩이라 직접 싣지 못했고, 원문에서 볼 수 있다.

문제는 “지운다”와 “다시 채운다”가 동시에 일어날 때다. 정훈섭의 「Redis 캐시 동기화 문제와 해결 전략 - 일관성, Race Condition, 분산 락」은 캐시 어사이드의 기본 동작부터 시작해, 캐시와 DB가 어긋나는 경쟁 상황과 해결책(분산 락 등)을 실무 경험과 함께 다룬다.

// catalog/product/application/ProductListCache.java (발췌)
static final String CACHE_KEY = "pawcycle:catalog:product-list:v2";
static final String GENERATION_KEY = CACHE_KEY + ":generation";

// 세대가 그대로일 때만 저장
static final DefaultRedisScript<Long> STORE_IF_GENERATION_UNCHANGED_SCRIPT = new DefaultRedisScript<>("""
    local current = redis.call('GET', KEYS[1])
    if not current then current = '0' end
    if current ~= ARGV[1] then return 0 end
    redis.call('SET', KEYS[2], ARGV[2], 'PX', ARGV[3])
    return 1
    """, Long.class);

// 세대 증가와 삭제를 한 번에
static final DefaultRedisScript<Long> INVALIDATE_SCRIPT = new DefaultRedisScript<>("""
    redis.call('INCR', KEYS[1])
    redis.call('DEL', KEYS[2])
    return 1
    """, Long.class);

public ProductListView getOrLoad(Supplier<ProductListView> loader) {
  if (!enabled) return loader.get();                       // 기본은 꺼짐
  String generation;
  try {
    String cached = redisTemplate.opsForValue().get(CACHE_KEY);
    if (cached != null) { hitCounter.increment(); return objectMapper.readValue(cached, ProductListView.class); }
    missCounter.increment();
    generation = redisTemplate.opsForValue().get(GENERATION_KEY);   // ① DB 읽기 전에 세대 기억
    if (generation == null) generation = "0";
  } catch (RuntimeException exception) {
    errorCounter.increment();
    return loader.get();                                   // ② Redis 장애 → DB로
  }
  ProductListView value = loader.get();                    // DB에서 읽기
  try {
    redisTemplate.execute(STORE_IF_GENERATION_UNCHANGED_SCRIPT, List.of(GENERATION_KEY, CACHE_KEY),
        generation, objectMapper.writeValueAsString(value), Long.toString(ttl.toMillis()));
  } catch (RuntimeException exception) { errorCounter.increment(); }
  return value;
}
  • 왜 Lua인가. 후디의 「레디스 다중 명령에 대한 원자성 보장 방법」이 정확히 이것을 다룬다.
    • 원리 Redis는 싱글 스레드라 명령 하나는 원자적이다. 하지만 GET 하고 비교한 뒤 SET하는 여러 명령 사이에는 다른 클라이언트의 명령이 끼어들 수 있다.
    • 이를 막는 방법은 MULTI/EXEC 트랜잭션과 Lua 스크립트 두 가지다. Lua 스크립트는 Redis 안에서 통째로 한 번에 실행되므로, 중간에 다른 명령이 끼지 않는다. MULTI/EXEC와 달리 스크립트 안에서 조건 분기(if current ~= ARGV[1])도 할 수 있다.
    • PawCycle의 “세대가 같으면 저장”은 조건 분기가 필요해서 Lua가 맞는 도구다.

출처: 후디 · 레디스 다중 명령에 대한 원자성 보장 방법(블로그 자체 서버, 만료 없음)

  • 값은 명시적 JSON이다. 기록 Spring Cache 추상화 + Java 기본 직렬화는 기각됐다. 키·값 형식과 장애 경계를 직접 통제하기 어렵고, Java 직렬화는 클래스가 바뀌면 호환이 깨지는 데다 역직렬화 보안 위험도 있다. 그래서 키에 형식 버전(v2) 을 넣었다. 응답 형식이 바뀌면 키 이름을 바꿔 옛 값과 섞이지 않게 한다.
  • ② Redis가 죽어도 목록은 나온다(fail-open). 캐시는 “있으면 빠르고 없어도 맞는” 기능이다. 그래서 Redis 오류는 error 메트릭만 올리고 DB로 간다. 11강의 세션이나 3강의 결제처럼 틀리면 안 되는 것에는 fail-closed를, 캐시처럼 늦어도 되는 것에는 fail-open을 쓴다. 이 구분이 일관적이다.
  • TTL 5분은 안전망일 뿐이다. 정확성은 세대 번호가 지킨다. TTL은 무효화 자체가 실패했을 때(Redis 장애) 낡은 값이 최대 5분만 남게 하는 보조 장치다.

  productListCache.invalidate();       // 트랜잭션 밖이면 즉시
}
  • 커밋 전에 지우면? 지운 직후, 아직 커밋되지 않은 DB를 다른 요청이 읽으면 옛 값을 가져와 캐시를 다시 채운다. 2절의 경쟁이 더 쉽게 일어난다.
  • 롤백되면? afterCommit은 호출되지 않는다. 바뀌지 않은 데이터 때문에 캐시를 비울 이유가 없다.
  • “트랜잭션은 있는데 동기화가 없다”면 예외. 조용히 즉시 무효화로 빠지지 않고 시끄럽게 실패한다. 설정이 이상한 환경을 일찍 드러내는 방어적 코드다.

같은 일을 Spring 이벤트로 하는 방법도 있다. 누블렛의 「@TransactionalEventListener 동작 방식」은 @EventListener와 @TransactionalEventListener의 차이, AFTER_COMMIT 같은 단계 옵션, 리스너에서 예외가 날 때의 동작, @Async와의 결합을 정리한다.

출처: 누블렛 · @TransactionalEventListener 동작 방식. tistory 그림이라 11월 30일 만료.

  • 해석 이벤트 방식은 상품 서비스가 캐시를 모르게 해 준다(느슨한 결합). PawCycle은 관리자 서비스가 무효화기를 직접 부르는 쪽을 택했다. 호출 지점이 코드에 명시적으로 보이지만, 무효화가 필요한 모든 쓰기 지점에 한 줄씩 넣어야 한다. 실제로 그 호출이 15곳에 흩어져 있다. 이 숫자가 다음 절의 실마리다.

  • 9월 6일 구조 정리에서 옛 경로가 사라지며 캐시 읽기도 함께 사라졌다.

해석 이것을 어떻게 읽어야 할까.

  • 측정 결과는 코드 경로에 묶여 있다. 13강의 “힌트는 쿼리 모양에 묶여 있다”와 같은 교훈이다. “Redis로 p95 4.7ms”는 그 API에 대한 사실이었다. API가 바뀐 뒤에는 근거가 되지 못한다. 포트폴리오에서 이 숫자를 쓰려면 반드시 “필터 없는 옛 목록 API 기준” 이라고 함께 말해야 한다.
  • 죽은 코드에도 비용이 있다. 4강 YAGNI의 “유지 비용”이다.
    • 새 관리자 기능을 만들 때마다 “캐시 무효화를 넣어야 하나?”를 고민하게 된다.
    • Redis 스타터 의존성, 헬스 설정, 테스트가 계속 유지된다.
    • 이 강의처럼 코드를 처음 읽는 사람이 “캐시가 동작한다”고 오해하게 된다.
  • 선택지는 셋이다.
    1. 제거: 읽기 경로가 없으니 무효화 호출, 설정, 의존성을 함께 걷어 낸다. 가장 정직하다.
    2. 새 API에 맞게 재설계: 필터 없는 첫 페이지(가장 많이 열리는 화면)만 키 하나로 캐시한다. 조건별로 키를 만들면 무효화가 “모든 조합 지우기”가 되므로, 세대 번호를 키 접두사로 쓰는 방식(...:gen6:page0:newest)이 어울린다. 세대를 올리면 옛 키는 아무도 찾지 않다가 TTL로 사라진다.
    3. 다른 층의 캐시: Nginx나 CDN의 짧은 HTTP 캐시(예: 10초)로 첫 페이지를 받는다. 애플리케이션 코드는 그대로 둔다. - 어느 쪽이든 13강 이후의 현재 API로 다시 측정하는 것이 먼저다. 13강의 힌트 최적화로 첫 페이지 쿼리가 이미 수 ms라면, 캐시의 이득은 예전보다 훨씬 작을 수 있다.

7. 카테고리 2단계와 READ COMMITTED: 9강의 답

9강에서 “카테고리 관리가 왜 READ_COMMITTED인지 직접 적은 문장을 찾지 못했다”고 했다. 확인 답은 코드 주석에 있었다.

// catalog/admin/application/AdminCatalogService.java (발췌)
@Transactional(isolation = Isolation.READ_COMMITTED)
public CategoryView updateCategory(Long categoryId, CategoryPatchCommand request) {
  Category category = lockCategoryAndParent(categoryId, request.parentIdPresent() ? request.parentId() : null);
  if (request.parentIdPresent()) {
    Category parent = request.parentId() == null ? null : requireParentCategory(request.parentId(), categoryId);
    // READ_COMMITTED observes children committed while the row locks were awaited.
    // Child creation/reparenting must lock this target as its new parent first.
    if (parent != null && categoryRepository.existsByParentId(categoryId))
      throw new AdminCatalogConflictException("CATEGORY_DEPTH_EXCEEDED", "카테고리는 최대 2 depth까지만 지원합니다.");
    category.updateParent(parent);
  }
  ...
}

private Category lockCategoryAndParent(Long categoryId, Long parentId) {
  if (parentId != null && parentId < categoryId) requireCategoryForUpdate(parentId);   // 작은 ID 먼저
  Category category = requireCategoryForUpdate(categoryId);
  if (parentId != null && parentId > categoryId) requireCategoryForUpdate(parentId);
  return category;
}

주석을 9강의 MVCC로 풀면 이렇다.

  • 카테고리 A를 다른 부모 아래로 옮기려면 “A에 자식이 없는지”를 확인해야 한다. 있으면 3단계가 된다.
  • 그런데 동시에 다른 관리자가 A 아래에 자식을 만들고 있을 수 있다. 그래서 A의 행을 잠그고 기다린다.
  • 잠금을 얻은 뒤의 existsByParentId(A)는 일반 SELECT다.
    • REPEATABLE READ였다면 트랜잭션 초반에 만든 스냅샷을 보므로, 기다리는 동안 커밋된 자식을 보지 못한다. 9강의 재고 CAS 충돌과 똑같은 “오래된 스냅샷” 문제다.
    • READ COMMITTED는 SELECT마다 새 스냅샷을 만든다. 그래서 방금 커밋된 자식을 본다. 주석의 “잠금을 기다리는 동안 커밋된 자식을 관찰한다”가 바로 이것이다.
  • 9강의 재고는 같은 문제를 잠금 읽기(FOR UPDATE)로 풀었고, 여기서는 격리 수준으로 풀었다. 해법은 다르지만 원인은 같다.

함께 쓰인 장치도 9강의 내용 그대로다.

  • 격리 수준은 바깥이 정한다. 6절의 감사 서비스(최상위 트랜잭션 소유자)에도 READ_COMMITTED를 붙인 이유다. 9강의 그 주석(“감사 소유자도 격리 수준을 설정해야 한다. 안쪽 REQUIRED 서비스는 이 트랜잭션에 참여한다”)이 여기와 짝을 이룬다.
  • 잠금 순서는 ID 오름차순이다. lockCategoryAndParent는 이동 대상과 새 부모를 항상 작은 ID부터 잠근다. 두 관리자가 “A를 B 아래로”, “B를 A 아래로”를 동시에 하면, 순서가 제각각일 때 서로를 기다리는 교착이 난다. 순서를 고정하면 원천적으로 사라진다. 3강·9강의 교착 이야기에 대한 고전적인 해법이다.
  • 부모를 자식 INSERT보다 먼저 잠근다. 카테고리 생성은 부모를 먼저 FOR UPDATE로 잡은 뒤 자식을 만든다(주석: “acquire the parent lock before the child's FK insert”). 이동과 생성이 같은 행(부모) 에서 줄을 서게 된다.
  • 기록 결정 기록은 트리 전체나 테이블 잠금, DDL 재설계 대신 최소 범위를 택했다고 적는다. 그리고 “모든 interleaving이나 과거의 잘못된 트리 자동 복구를 증명하지는 않는다”는 한계도 함께 남겼다(이슈 #416).

15강. 리뷰·문의와 AI: AI에게 맡기는 일과 서버가 지키는 일

이번 강의의 질문은 하나다. "외부 AI를 서비스에 붙일 때, 무엇을 AI에게 맡기고 무엇을 서버가 끝까지 쥐고 있어야 하는가." PawCycle은 AI를 두 곳에 쓴다.

  • 리뷰 요약: 공개 리뷰를 AI가 한 문단으로 요약한다. 결과는 DB에 캐시한다.
  • 반려동물 맞춤 추천: 서버가 고른 후보의 순서만 AI가 바꾼다.

3. 리뷰 요약 — AI 호출을 트랜잭션 밖으로 빼낸 이유

이번 강의의 핵심이다. ReviewSummaryService.summary()(ReviewSummaryService.java:44)에는 @Transactional이 없다. 일부러 뺀 것이다. 먼저 전체 흐름과, 각 단계에서 트랜잭션·DB 커넥션이 잡혀 있는지를 함께 본다.

3-1. 왜 외부 호출을 트랜잭션 안에 두면 안 되는가 원리

트랜잭션 하나를 열면, 끝날 때까지 다음 자원을 붙잡는다.

  • DB 커넥션 하나. Hikari 풀의 기본 크기는 10이다. AI 응답을 5초 기다리는 요청이 10개 동시에 오면 풀이 비고, 상품 목록처럼 AI와 상관없는 요청까지 커넥션을 기다린다. 이 프로젝트가 Phase 9 부하 실험에서 "pending이 높다고 풀을 키우는 게 답은 아니다"라는 결론을 얻은 것과 같은 자원이다(#191·#193).
  • 잠금. 트랜잭션에서 잠근 행은 커밋할 때까지 잠긴 채로 남는다.
  • MVCC의 undo 이력. 오래 열린 REPEATABLE READ 읽기 트랜잭션이 있으면, InnoDB는 그 트랜잭션이 볼 수도 있는 옛 버전을 지우지 못한다(purge 지연).

그리고 외부 HTTP 호출은 롤백할 수 없다. DB를 롤백해도 이미 나간 AI 요청과 그 비용은 되돌릴 수 없다.

OS 관점도 하나 덧붙인다. Tomcat은 요청 하나를 워커 스레드 하나가 처리한다(thread-per-request). AI 응답을 기다리는 동안 그 스레드는 소켓 read()에서 블로킹되어 잠든다. CPU는 쓰지 않지만 스레드와 커넥션이라는 "슬롯"을 점유한다. 트랜잭션을 밖으로 빼면 커넥션 슬롯은 풀리지만, 워커 스레드 슬롯은 여전히 묶여 있다. 이 차이는 5절의 개선점으로 이어진다.

대안 왜 기각했나
메서드 전체를 readOnly 트랜잭션으로 유지 3-1의 자원 점유가 그대로 남는다. 게다가 readOnly 안에서는 저장할 수 없다.
어노테이션을 지우고 무조건 저장 AI를 기다리는 동안 리뷰가 숨겨지거나 수정되면, 이미 사라진 리뷰를 요약한 글이 캐시에 남는다. 신고되어 숨긴 리뷰 내용이 요약으로 계속 노출될 수 있다.
큐·Redis 워커로 비동기 생성 정답에 가깝지만 인프라와 운영 대상이 늘어난다. 지금 규모에서는 동기 + 조건부 저장으로 충분하다고 판단했다.

두 번째 대안이 이 설계의 핵심 위험이다. "AI 결과가 나온 시점에, 그 결과의 재료가 아직 유효한가?"를 다시 확인해야 한다. 이것이 TOCTOU(Time-Of-Check to Time-Of-Use) 문제다. 확인한 시점(스냅샷)과 사용하는 시점(저장) 사이에 수 초짜리 틈이 있고, 그 틈에서 세상이 바뀔 수 있다.

3-5. 잠금 재확인 — FOR UPDATE가 막는 범위

AI 결과가 나온 뒤, 저장 직전에 짧은 트랜잭션 B를 연다(ReviewSummaryQueryRepository.java:86).

@Transactional(isolation = Isolation.REPEATABLE_READ)     // ① 격리 수준을 명시
public boolean saveSummaryIfCurrent(long productId, List<ReviewRow> expectedVisibleReviews, ...) {
  List<Tuple> rows = entityManager.createNativeQuery("""
      SELECT id, rating, content, updated_at, visible
      FROM reviews FORCE INDEX (ix_reviews_product_visible_created)   -- ② 이 인덱스로 범위를 잡아라
      WHERE product_id = :productId FOR UPDATE                         -- ③ 잠그는 현재 읽기
      """, Tuple.class) ...;
  List<ReviewRow> currentVisibleReviews = rows.stream()
      .filter(row -> booleanValue(row.get("visible")))                 // ④ 숨김 리뷰도 읽고 잠근 뒤 여기서 거른다
      ...sorted(comparingLong(ReviewRow::id)).toList();
  if (!currentVisibleReviews.equals(expectedVisibleReviews)) return false;   // ⑤ 하나라도 다르면 포기
  summaries.upsert(...);                                                       // ⑥ 같으면 저장
  return true;
}

한 줄씩 보자.

  • ① REPEATABLE READ 명시. 14강의 카테고리 수정은 READ_COMMITTED를 썼다. 여기서는 반대로 RR을 명시한다. RR에서만 InnoDB가 갭 락(gap lock)을 건다. 그래서 "이 상품에 새 리뷰가 끼어드는 것"까지 막을 수 있다.
  • ② FORCE INDEX. 잠금은 옵티마이저가 고른 인덱스에서 스캔한 범위에 걸린다. 옵티마이저가 풀스캔을 고르면 테이블 전체가 잠길 수 있다. 그래서 product_id로 시작하는 인덱스를 강제해 잠금 범위를 "이 상품"으로 고정한다. 원리
  • ③ FOR UPDATE = 잠그는 현재 읽기(locking read). 일반 SELECT는 MVCC 스냅샷(과거)을 읽는다. FOR UPDATE는 지금 커밋된 최신 버전을 읽고 그 행을 잠근다. "AI를 기다리는 동안 바뀌었나?"는 최신 값을 봐야만 알 수 있다.
  • ④ visible 조건을 WHERE에 넣지 않은 이유 해석: WHERE product_id = ? AND visible = 1이면 숨김 리뷰는 잠기지 않는다. 그러면 누군가 숨김 리뷰를 "다시 보이게" 바꾸는 것을 막지 못한다. 상품의 리뷰 전체를 잠근 뒤 메모리에서 거르는 쪽이 안전하다.
  • ⑤ 지문이 아니라 목록 전체를 비교한다. 해시 충돌 걱정 없이 정확히 비교한다. 데이터가 바뀌었으면 저장을 포기하고 UNAVAILABLE을 반환한다. 다음 요청이 새 스냅샷으로 다시 만든다.

넥스트 키 락이 실제로 어디를 막는지 그림으로 보자. 인덱스는 (product_id, visible, created_at) 순서로 정렬되어 있다. 상품 42를 잠근 상황이다.

  • 비유니크 인덱스에서 같은 값을 찾는 잠금 읽기는, RR에서 찾은 레코드마다 넥스트 키 락(레코드 + 그 앞 갭)을 건다. 그리고 마지막으로 확인한 다음 레코드(43) 앞의 갭에도 갭 락을 건다. 원리
  • 그래서 상품 42에 새 리뷰를 넣는 INSERT는 트랜잭션 B가 커밋할 때까지 기다린다. #441이 검증한 것이 바로 이 대기다. 기록
  • 그림 왼쪽은 눈여겨볼 부작용이다. 상품 41의 최신 리뷰는 인덱스상 (41, 보임, 최신시각)인데, 이 자리가 (42, 숨김) 바로 앞 갭이다. 그래서 다른 상품의 INSERT도 잠깐 기다릴 수 있다. 원리 트랜잭션 B가 짧아서(SELECT 1회 + upsert 1회) 실제 영향은 작다고 본다 해석. 그래도 "갭 락은 내가 의도한 행 밖으로 번질 수 있다"는 감각은 꼭 가져가자.
  • 보조 인덱스뿐 아니라 해당 행들의 클러스터드 인덱스(PK) 레코드에도 레코드 락이 걸린다. 그래서 숨김 처리 UPDATE(PK로 찾아 들어오는 쓰기)도 막힌다. 원리

  • PK가 product_id라서 상품당 요약은 한 행이다. 처음이면 INSERT, 있으면 UPDATE를 한 문장으로 원자적으로 처리한다. "있는지 SELECT 후 분기"의 경합(1절 ③과 같은 문제)이 없다. 원리

  • 메서드의 주석은 "OpenEntityManagerInView가 AI 이전 엔티티 값을 1차 캐시에 들고 있을 수 있어 native 쿼리를 쓴다"라고 설명한다. 9강에서 봤듯이 이 주석은 현재 설정과 맞지 않는 오래된 주석이다. 다만 결론(엔티티 대신 native 잠금 읽기)은 OSIV 여부와 상관없이 맞다. 1차 캐시는 같은 영속성 컨텍스트 안에서 "이미 읽은 엔티티"를 다시 돌려주므로, 최신 값을 보장하려면 우회해야 한다. 해석

4. AI 출력 검증 — AI의 답을 "데이터"로 다루기

AI의 응답은 신뢰할 수 없는 외부 입력이다. 사용자 입력과 똑같이 검증한다(ReviewSummaryService.java:82).

private boolean validAiText(String text) {
  if (text == null || text.isBlank()
      || text.codePointCount(0, text.length()) > 500      // ① 글자 수는 코드 포인트로
      || text.contains("<") || text.contains(">")) return false;   // ② 마크업 차단
  if (text.codePoints().anyMatch(cp -> Character.isISOControl(cp) && cp != '\n' && cp != '\r'))
    return false;                                          // ③ 제어 문자 차단
  if (text.codePoints().noneMatch(cp -> Character.UnicodeScript.of(cp) == Character.UnicodeScript.HANGUL))
    return false;                                          // ④ 한글이 하나도 없으면 거부
  String lower = text.toLowerCase(Locale.ROOT);
  return UNSAFE_TERMS.stream().noneMatch(lower::contains); // ⑤ 의료 용어 차단
}
  • ① codePointCount. Java String.length()는 UTF-16 코드 유닛 수다. 이모지 하나가 2로 세어진다. DB의 CHAR_LENGTH(문자 수)와 기준을 맞추려고 코드 포인트로 센다. 원리
  • ② <, > 거부. 요약은 상품 페이지에 그대로 보인다. 프론트엔드가 이스케이프하더라도, 서버에서 마크업 자체를 받지 않는 심층 방어다. 해석
  • ③ 제어 문자. 줄바꿈만 허용한다. 터미널 제어 시퀀스나 NUL 같은 문자가 로그·화면을 깨뜨리는 것을 막는다.
  • ④ 한글 필수. 모델이 영어로 답하거나 이상한 출력을 낸 경우를 걸러 낸다.
  • ⑤ 의료 용어 차단. 반려동물 용품 쇼핑몰이 "이 사료가 피부병을 치료한다" 같은 문장을 노출하면 법적·신뢰 문제가 된다. 시스템 프롬프트에도 "의료나 치료 주장을 하지 마세요"라고 적었지만(ProductCommerceAiConfiguration.java:28), 프롬프트는 부탁이고 검증은 강제다. 그래서 둘 다 둔다.

개선점: "약" 한 글자 해석

lower.contains("약")은 부분 문자열 검사다. 그래서 다음 같은 리뷰 요약이 모두 거부된다.

  • "사이즈가 약간 작다는 의견이 많다"
  • "포장이 약하다는 지적이 있다"
  • "약속한 배송일에 도착했다"

반려용품 리뷰에서 "약간"은 매우 흔한 단어다. 그래서 정상 요약이 UNAVAILABLE로 떨어지는 오탐(false positive)이 자주 날 것으로 보인다. 측정한 것은 아니다. 보수적으로 막는 쪽을 택한 결과지만, 대안이 있다.

// 저장소에 없는 예시 — 단어 경계를 고려한 차단 목록
private static final Pattern UNSAFE = Pattern.compile(

5. 이 GET 요청이 비싼 이유 — 개선이 필요한 지점

GET /api/products/{productId}/reviews/summary는 SecurityConfig에서 /api/products/** GET permitAll에 포함된다(SecurityConfig.java:50-57). 로그인하지 않은 사용자도 호출할 수 있다. 확인 이 요청은 캐시가 비어 있으면 다음 두 가지를 한다.

  1. 유료 AI 호출
  2. DB 쓰기(upsert)와 잠금

여기서 세 가지 위험이 나온다 해석.

  • 캐시 스탬피드(Cache Stampede). 인기 상품에 새 리뷰가 달려 지문이 바뀐 순간, 동시에 들어온 요청 N개가 모두 "캐시 불일치"를 보고 각자 AI를 호출한다. 모두 재확인을 통과하면 모두 upsert하고, 마지막 쓰기가 남는다. 결과는 맞지만 AI 비용이 N배다.
  • 속도 제한 없음. 익명 사용자가 리뷰를 숨김·수정하며 반복 호출하면 AI 비용을 유발할 수 있다. 리뷰 작성에는 구매 자격이 필요해서 실제 악용 난도는 높다.
  • 타임아웃이 코드에 보이지 않는다. OpenAiChatModel.builder()에 타임아웃 설정이 없다. HTTP 클라이언트의 기본값을 따르는데, 그 값은 확인하지 못했다 미확인. 3-1에서 봤듯이, 트랜잭션을 밖으로 빼도 Tomcat 워커 스레드는 AI 응답까지 묶인다. 기본 200개 스레드 중 상당수가 느린 AI를 기다리면, 무관한 요청이 대기열에 쌓인다.

다행히 기본 설정에서는 이 위험이 열려 있지 않다. pawcycle.ai.review-summary.enabled=true가 아니면 @ConditionalOnMissingBean의 대체 빈이 reviews -> null을 반환한다. null은 ④ 검증에서 거부되어 항상 UNAVAILABLE이 된다. 확인 7강의 Null Object 패턴이다. AI가 꺼져 있어도 서비스 코드에 if (enabled) 분기가 없다.

스탬피드의 대표적 해법은 세 가지다.

  • 락/싱글 플라이트: 한 요청만 생성하고 나머지는 기다리거나 이전 값을 받는다.
  • 이전 값 반환 + 백그라운드 갱신(stale-while-revalidate)
  • 확률적 조기 갱신(PER)
// 저장소에 없는 예시 — 같은 상품의 동시 생성 요청을 하나로 합치는 인프로세스 single-flight
private final ConcurrentHashMap<Long, CompletableFuture<String>> inFlight = new ConcurrentHashMap<>();

String generateOnce(long productId, Supplier<String> generator) {
  CompletableFuture<String> mine = new CompletableFuture<>();
  CompletableFuture<String> existing = inFlight.putIfAbsent(productId, mine);
  if (existing != null) return existing.join();          // 이미 누가 생성 중이면 그 결과를 기다림
  try { String v = generator.get(); mine.complete(v); return v; }
  catch (RuntimeException e) { mine.completeExceptionally(e); throw e; }
  finally { inFlight.remove(productId, mine); }
}

단, 서버가 여러 대면 인스턴스마다 한 번씩 호출된다. 완전히 하나로 합치려면 14강의 Redis 원자 연산(SET NX PX)이 필요하다. 지금의 단일 백엔드 구성에서는 인프로세스 방식으로 충분하다 해석.

6. AI 추천 — AI는 결정하지 않고, 순서만 바꾼다

두 번째 AI 사용처다. 핵심 경계는 한 문장으로 요약된다. "무엇을 팔 수 있는가"는 서버가 정하고, AI는 그 안에서 순서와 이유 문장만 제안한다.

  • ② 후보 계산은 전부 서버가 한다. 반려동물 유형이 맞고, 구매 가능하고, 이미 정기배송 중이 아니고, 의료 용어가 없는(isNonMedical) 상품만 남는다. 그 뒤 점수(구매·찜·클릭·조회·카테고리·브랜드·속성 가중치) → 인기도 → id 순으로 정렬한다. 결정적(deterministic) 정렬이라 AI가 없어도 완성된 추천 목록이 나온다.
  • AI에게는 상위 최대 10개(탐색 슬롯이 있으면 9개)만 보낸다. 보내는 것은 후보 상품 정보와 관심 카테고리뿐이다. 회원 ID, 구매 이력 같은 개인 정보는 프롬프트로 나가지 않는다. [확인: aiClient.recommend(candidates, preferences)의 인자]
  • ③ AI 실패는 예외가 아니라 "제안 없음"이다. 사용자는 오류 화면 대신 서버 순서의 추천을 받는다.
  • ④ 재조회가 이 서비스판 TOCTOU 방어다. AI가 응답하는 몇 초 사이에 상품이 품절되거나 비공개가 될 수 있다. 처음 목록(initialCandidates)을 믿지 않고 카탈로그 경계를 다시 읽은 목록만 병합의 기준으로 쓴다. 3-5의 리뷰 요약이 "저장 직전에 잠금 재확인"을 하는 것과 같은 발상이다. 추천은 쓰기가 아니라서 잠금 대신 재조회만 한다.

    • AI가 준 productId가 null이거나 중복이면 버린다.
    • AI가 준 ID가 eligible(재조회한 상위 후보)에 없으면 버린다. 모델이 지어낸 ID(환각)나 그사이 사라진 상품은 여기서 걸러진다.
    • 이유 문장은 safeReason이 검증한다. 100자 이하, 한글 포함, 의료 용어 없음이 조건이다. 실패하면 서버의 고정 문장("반려동물 유형에 맞는 구매 가능 상품입니다.")으로 바꾼다.
    • 빈자리는 서버 순서로 채운다. 하나라도 대체했으면 metrics.fallback(), 아니면 metrics.success()를 기록한다. AI가 얼마나 자주 실패하거나 무시되는지 운영에서 볼 수 있다.

추천 클라이언트는 리뷰 요약과 달리 .call().content()(문자열)가 아니라 .call().entity(RecommendationAiResponse.class)를 쓴다. Spring AI의 구조화된 출력으로, 모델 응답을 JSON 스키마에 맞춰 Java record로 받는다. 형식이 맞는다고 내용이 옳은 것은 아니다. 그래서 ⑤의 검증이 여전히 필요하다. 확인·해석

왜 AI에게 "선택"까지 맡기지 않았나 해석

  • 추천이 곧 판매 행위다. 품절 상품, 의료 효능을 암시하는 상품, 다른 반려동물 종의 상품을 추천하면 곧바로 고객 피해다. 이 경계를 확률적 모델에 맡길 수 없다.
  • 재현성. 서버 정렬은 같은 입력에 같은 결과를 낸다. 장애가 나도 설명할 수 있다.
  • 가용성. AI는 기본으로 꺼져 있다(7강의 @ConditionalOnProperty + Null Object). 꺼져 있어도 기능은 그대로 동작한다. AI는 "있으면 조금 더 나은" 부가 기능이다.
  • 대가: AI가 후보 밖의 좋은 상품을 발견할 여지가 없다. 탐색 슬롯(EXPLORATION) 하나가 이 경직성을 조금 풀어 주는 장치다.

  • "AI 출력은 사용자 입력처럼 검증합니다. 길이, 마크업, 제어 문자, 한글, 의료 용어를 검사합니다. 프롬프트의 금지 문구는 부탁일 뿐이고, 강제는 검증 코드가 합니다."
