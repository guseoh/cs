14강. 캐시와 관리자 카탈로그: 캐시가 효과를 낸 길이 사라졌을 때

이번 강의의 목표

  • PawCycle이 Redis 캐시를 어떤 측정에서 출발해 들였는지 안다.
  • 캐시를 비우는 순간과 다시 채우는 순간이 엇갈릴 때 생기는 낡은 값 재적재(stale refill) 경쟁과, 이를 막는 세대 번호 + Lua 스크립트 + 커밋 후 무효화를 이해한다.
  • [이번 강의의 핵심 발견] 그렇게 정교하게 만든 캐시가 지금은 읽히지 않는다는 사실과, 그 의미를 판단한다.
  • 관리자 카탈로그의 상태 전이, 감사 기록, 카테고리 2단계 규칙을 보고, 9강에서 남긴 “왜 READ COMMITTED인가”에 답한다.

1. 캐시를 들인 이유: “DB가 느리다”고 가정하지 않았다

기록 3강과 13강에서 본 성능 9단계의 상황은 이랬다.

  • GET /api/products는 CPU를 늘리면 처리량이 좋아졌지만, CPU 2.0에서도 요청 드롭, 긴 꼬리 지연, 커넥션 대기가 남았다.
  • 관련 SQL 자체는 비교적 쌌다. 커넥션 풀을 늘리면 오히려 나빠졌다. Java 핫스팟을 짚을 유효한 프로파일링 결과도 없었다.

그래서 결정 기록은 이렇게 적는다. “DB가 느리기 때문에 Redis가 필요하다고 가정하지 않고, 반복 조회의 JPA 객체화·DTO 조립과 커넥션 사용을 캐시 적중으로 우회할 수 있는지 시험했다.”

결과는 극적이었다. 기록 로컬·합성 조건의 첫 결과 기준이다.

처리량 드롭 p95 p99
Before (CPU 2.0) 약 193.5 RPS 5,808 6,854.56ms 8,590.75ms
Redis After 250 RPS (목표 상한) 0 4.71ms 26.99ms

판정은 KEEP이었다. 결정 기록은 이 수치를 “현재 운영 성능, 최대 RPS, SLO 달성으로 쓸 수 없다”고 선을 긋는다. 목표가 250 RPS였으니 최대치는 탐색하지 않았다는 한계도 적었다.

2. 캐시 무효화의 함정: 낡은 값 재적재

가장 흔한 캐시 방식은 캐시 어사이드(cache-aside, lazy loading)다.

  • 읽을 때 캐시에 있으면 쓰고, 없으면 DB에서 읽어 캐시에 넣는다.
  • 쓸 때는 DB를 바꾸고 캐시를 지운다.

Inpa Dev의 「[REDIS] 캐시(Cache) 설계 전략 지침 총정리」가 캐시 어사이드, 라이트 스루(write-through), 라이트 백(write-back) 같은 읽기·쓰기 전략을 그림과 함께 정리한다. 그림은 지연 로딩이라 직접 싣지 못했고, 원문에서 볼 수 있다.

문제는 “지운다”와 “다시 채운다”가 동시에 일어날 때다. 정훈섭의 「Redis 캐시 동기화 문제와 해결 전략 - 일관성, Race Condition, 분산 락」은 캐시 어사이드의 기본 동작부터 시작해, 캐시와 DB가 어긋나는 경쟁 상황과 해결책(분산 락 등)을 실무 경험과 함께 다룬다.

출처: 정훈섭 · Redis 캐시 동기화 문제와 해결 전략. tistory 그림이라 11월 30일 만료.

PawCycle의 설계 문서(ARCH-014)가 짚은 경쟁을 그림으로 그리면 이렇다.

3. 세대 번호와 Lua 스크립트

// catalog/product/application/ProductListCache.java (발췌)
static final String CACHE_KEY = "pawcycle:catalog:product-list:v2";
static final String GENERATION_KEY = CACHE_KEY + ":generation";

// 세대가 그대로일 때만 저장
static final DefaultRedisScript<Long> STORE_IF_GENERATION_UNCHANGED_SCRIPT = new DefaultRedisScript<>("""
    local current = redis.call('GET', KEYS[1])
    if not current then current = '0' end
    if current ~= ARGV[1] then return 0 end
    redis.call('SET', KEYS[2], ARGV[2], 'PX', ARGV[3])
    return 1
    """, Long.class);

// 세대 증가와 삭제를 한 번에
static final DefaultRedisScript<Long> INVALIDATE_SCRIPT = new DefaultRedisScript<>("""
    redis.call('INCR', KEYS[1])
    redis.call('DEL', KEYS[2])
    return 1
    """, Long.class);

public ProductListView getOrLoad(Supplier<ProductListView> loader) {
  if (!enabled) return loader.get();                       // 기본은 꺼짐
  String generation;
  try {
    String cached = redisTemplate.opsForValue().get(CACHE_KEY);
    if (cached != null) { hitCounter.increment(); return objectMapper.readValue(cached, ProductListView.class); }
    missCounter.increment();
    generation = redisTemplate.opsForValue().get(GENERATION_KEY);   // ① DB 읽기 전에 세대 기억
    if (generation == null) generation = "0";
  } catch (RuntimeException exception) {
    errorCounter.increment();
    return loader.get();                                   // ② Redis 장애 → DB로
  }
  ProductListView value = loader.get();                    // DB에서 읽기
  try {
    redisTemplate.execute(STORE_IF_GENERATION_UNCHANGED_SCRIPT, List.of(GENERATION_KEY, CACHE_KEY),
        generation, objectMapper.writeValueAsString(value), Long.toString(ttl.toMillis()));
  } catch (RuntimeException exception) { errorCounter.increment(); }
  return value;
}
  • 왜 Lua인가. 후디의 「레디스 다중 명령에 대한 원자성 보장 방법」이 정확히 이것을 다룬다.
    • 원리 Redis는 싱글 스레드라 명령 하나는 원자적이다. 하지만 GET 하고 비교한 뒤 SET하는 여러 명령 사이에는 다른 클라이언트의 명령이 끼어들 수 있다.
    • 이를 막는 방법은 MULTI/EXEC 트랜잭션과 Lua 스크립트 두 가지다. Lua 스크립트는 Redis 안에서 통째로 한 번에 실행되므로, 중간에 다른 명령이 끼지 않는다. MULTI/EXEC와 달리 스크립트 안에서 조건 분기(if current ~= ARGV[1])도 할 수 있다.
    • PawCycle의 “세대가 같으면 저장”은 조건 분기가 필요해서 Lua가 맞는 도구다.

출처: 후디 · 레디스 다중 명령에 대한 원자성 보장 방법(블로그 자체 서버, 만료 없음)

  • 값은 명시적 JSON이다. 기록 Spring Cache 추상화 + Java 기본 직렬화는 기각됐다. 키·값 형식과 장애 경계를 직접 통제하기 어렵고, Java 직렬화는 클래스가 바뀌면 호환이 깨지는 데다 역직렬화 보안 위험도 있다. 그래서 키에 형식 버전(v2) 을 넣었다. 응답 형식이 바뀌면 키 이름을 바꿔 옛 값과 섞이지 않게 한다.
  • ② Redis가 죽어도 목록은 나온다(fail-open). 캐시는 “있으면 빠르고 없어도 맞는” 기능이다. 그래서 Redis 오류는 error 메트릭만 올리고 DB로 간다. 11강의 세션이나 3강의 결제처럼 틀리면 안 되는 것에는 fail-closed를, 캐시처럼 늦어도 되는 것에는 fail-open을 쓴다. 이 구분이 일관적이다.
  • TTL 5분은 안전망일 뿐이다. 정확성은 세대 번호가 지킨다. TTL은 무효화 자체가 실패했을 때(Redis 장애) 낡은 값이 최대 5분만 남게 하는 보조 장치다.

4. 커밋한 뒤에만 지운다

// catalog/product/application/ProductListCacheInvalidator.java
public void invalidateAfterCommit() {
  if (TransactionSynchronizationManager.isActualTransactionActive()) {
    if (!TransactionSynchronizationManager.isSynchronizationActive())
      throw new IllegalStateException("active transaction has no synchronization");
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
      @Override public void afterCommit() { productListCache.invalidate(); }
    });
    return;
  }
  productListCache.invalidate();       // 트랜잭션 밖이면 즉시
}
  • 커밋 전에 지우면? 지운 직후, 아직 커밋되지 않은 DB를 다른 요청이 읽으면 옛 값을 가져와 캐시를 다시 채운다. 2절의 경쟁이 더 쉽게 일어난다.
  • 롤백되면? afterCommit은 호출되지 않는다. 바뀌지 않은 데이터 때문에 캐시를 비울 이유가 없다.
  • “트랜잭션은 있는데 동기화가 없다”면 예외. 조용히 즉시 무효화로 빠지지 않고 시끄럽게 실패한다. 설정이 이상한 환경을 일찍 드러내는 방어적 코드다.

같은 일을 Spring 이벤트로 하는 방법도 있다. 누블렛의 「@TransactionalEventListener 동작 방식」은 @EventListener와 @TransactionalEventListener의 차이, AFTER_COMMIT 같은 단계 옵션, 리스너에서 예외가 날 때의 동작, @Async와의 결합을 정리한다.

출처: 누블렛 · @TransactionalEventListener 동작 방식. tistory 그림이라 11월 30일 만료.

  • 해석 이벤트 방식은 상품 서비스가 캐시를 모르게 해 준다(느슨한 결합). PawCycle은 관리자 서비스가 무효화기를 직접 부르는 쪽을 택했다. 호출 지점이 코드에 명시적으로 보이지만, 무효화가 필요한 모든 쓰기 지점에 한 줄씩 넣어야 한다. 실제로 그 호출이 15곳에 흩어져 있다. 이 숫자가 다음 절의 실마리다.

5. 그런데, 지금은 아무도 이 캐시를 읽지 않는다

여기까지 본 설계는 교과서적으로 훌륭하다. 그런데 코드를 검색하면 이상한 점이 나온다.

  • 확인 getOrLoad(...)를 호출하는 운영 코드가 한 곳도 없다. 호출은 테스트(ProductListCacheTests)에만 있다.
  • 확인 반면 invalidateAfterCommit()은 관리자 카탈로그, 브랜드, 패싯, 카탈로그 적재 도구 등 15곳에서 여전히 호출된다.
  • 확인 git log -S'getOrLoad('로 추적하면 이렇다.
    • 8/24 PR #203에서 캐시가 들어왔다.
    • 9/6 PR #279 “backend persistence 구조 수렴”에서 호출이 사라졌다.
    • 영속성 수렴 문서는 “ProductQueryService는 … authoritative ProductDiscoveryReader 경로만 사용한다. nullable legacy/cache fallback은 없다”고 적는다.
  • 확인 캐시 설계 문서(ARCH-014) 자체도 이미 이렇게 정했다. “pageable 공개 목록은 DB-native filter/sort/pagination reader를 직접 실행하며 Redis 전체 목록 cache를 우회한다. 기존 ProductListReader와 v2 키는 인자 없는 레거시 호환성 검증에만 남긴다.”
    • 그 ProductListReader도 지금은 운영 코드 어디에서도 주입되지 않는다.

정리하면 이렇다.

  • 캐시가 극적인 효과(p95 6.8초 → 4.7ms)를 낸 것은 필터·정렬·페이지가 없던 옛 “전체 목록” API였다.
  • 8월 24일 공개 상품 탐색(13강의 필터·정렬·페이지)이 들어오면서 API의 모양이 바뀌었고, 새 API는 설계상 캐시를 우회했다.
  • 9월 6일 구조 정리에서 옛 경로가 사라지며 캐시 읽기도 함께 사라졌다.
  • 남은 것은 아무도 읽지 않는 키를 지우는 코드 15곳과, 기본값 false인 설정과, 측정 기록의 “KEEP” 판정이다.

해석 이것을 어떻게 읽어야 할까.

  • 측정 결과는 코드 경로에 묶여 있다. 13강의 “힌트는 쿼리 모양에 묶여 있다”와 같은 교훈이다. “Redis로 p95 4.7ms”는 그 API에 대한 사실이었다. API가 바뀐 뒤에는 근거가 되지 못한다. 포트폴리오에서 이 숫자를 쓰려면 반드시 “필터 없는 옛 목록 API 기준” 이라고 함께 말해야 한다.
  • 죽은 코드에도 비용이 있다. 4강 YAGNI의 “유지 비용”이다.
    • 새 관리자 기능을 만들 때마다 “캐시 무효화를 넣어야 하나?”를 고민하게 된다.
    • Redis 스타터 의존성, 헬스 설정, 테스트가 계속 유지된다.
    • 이 강의처럼 코드를 처음 읽는 사람이 “캐시가 동작한다”고 오해하게 된다.
  • 선택지는 셋이다.
    1. 제거: 읽기 경로가 없으니 무효화 호출, 설정, 의존성을 함께 걷어 낸다. 가장 정직하다.
    2. 새 API에 맞게 재설계: 필터 없는 첫 페이지(가장 많이 열리는 화면)만 키 하나로 캐시한다. 조건별로 키를 만들면 무효화가 “모든 조합 지우기”가 되므로, 세대 번호를 키 접두사로 쓰는 방식(...:gen6:page0:newest)이 어울린다. 세대를 올리면 옛 키는 아무도 찾지 않다가 TTL로 사라진다.
    3. 다른 층의 캐시: Nginx나 CDN의 짧은 HTTP 캐시(예: 10초)로 첫 페이지를 받는다. 애플리케이션 코드는 그대로 둔다. - 어느 쪽이든 13강 이후의 현재 API로 다시 측정하는 것이 먼저다. 13강의 힌트 최적화로 첫 페이지 쿼리가 이미 수 ms라면, 캐시의 이득은 예전보다 훨씬 작을 수 있다.

6. 관리자 카탈로그: 잠그고, 검사하고, 기록한다

상품 수정

// catalog/admin/application/AdminCatalogService.java (발췌)
@Transactional
public ProductView updateProduct(Long productId, ProductPatchCommand request) {
  CatalogAdminPatchValidation.validate(request);
  Product product = requireProductForUpdate(productId);              // ① 행 잠금
  ...
  if (request.brandIdPresent()) {                                    // ② 보낸 필드만
    if (request.brandId() == null) throw ... "Brand cannot be cleared.";
    requireActiveBrand(request.brandId());
    product.updateBrandId(request.brandId());
  }
  product.update(category, request.categoryIdPresent(), request.name(), ...,
                 request.description(), request.descriptionPresent(), ...);
  if (request.statusPresent()) {
    if (!product.canTransitionTo(request.status()))                  // ③ 상태 전이
      throw new AdminCatalogConflictException("PRODUCT_STATUS_TRANSITION_CONFLICT", "...");
    product.transitionTo(request.status());
  }
  ProductView view = productView(productRepository.saveAndFlush(product));
  productListCacheInvalidator.invalidateAfterCommit();               // ④
  return view;
}

// catalog/product/domain/Product.java
public boolean canTransitionTo(ProductStatus target) {
  return (status == DRAFT && target == PUBLIC)
      || (status == PUBLIC && target == INACTIVE)
      || (status == INACTIVE && target == PUBLIC);
}
  • ① 행 잠금. 기록 두 관리자가 같은 상품을 동시에 PATCH하면 행 잠금으로 직렬화한다. 각자 다른 필드를 고쳐도 서로를 덮어쓰지 않는다. 10강의 갱신 분실을 막는 장치가 여기에는 있다.
  • ② 진짜 PATCH. ...Present() 플래그로 “필드를 보내지 않음”과 “null을 보냄(지움)”을 구분한다. 보낸 필드만 바꾼다. 10강의 배송지 PATCH(전체 대체)와 대비되는 부분 수정이다. 브랜드처럼 지울 수 없는 필드는 null을 거부한다.
  • ③ 상태 전이 규칙이 엔티티에 있다. 5강에서 본 구독 V2(서비스의 문자열 비교)와 달리, 상품은 canTransitionTo라는 도메인 메서드가 규칙을 갖는다. 5강에서 “개선 제안”으로 보여 준 모양이 여기에는 이미 있다. 같은 프로젝트 안에서도 스타일이 다르다.
  • ④ 커밋 후 캐시 무효화. 5절에서 본 대로 지금은 읽는 사람이 없는 키를 지운다.

감사 기록은 같은 트랜잭션에

// catalog/admin/application/AdminCatalogMutationService.java (발췌)
private <T> T execute(long adminId, String action, String referenceType,
                      Supplier<T> mutation, ToLongFunction<T> referenceId) {
  T result = mutation.get();
  audits.append(adminId, action, referenceType, referenceId.applyAsLong(result));
  return result;
}

@Transactional
public BrandView createBrand(long adminId, BrandCreateCommand request) {
  return execute(adminId, "CATALOG_BRAND_CREATE", "BRAND",
      () -> adminCatalogService.createBrand(request), BrandView::brandId);
}
  • 변경과 감사 기록이 한 트랜잭션이다. 기록 5강의 MVP3 구조 정리 결정대로 “감사 실패 후 상태 변경만 커밋”은 허용하지 않는다. 감사 기록 INSERT가 실패하면 변경도 롤백된다. “누가 바꿨는지 모르는 변경”은 존재할 수 없다.
  • 그래서 이 바깥 메서드가 트랜잭션의 소유자다. 다음 절의 격리 수준 이야기가 여기서 이어진다.

7. 카테고리 2단계와 READ COMMITTED: 9강의 답

9강에서 “카테고리 관리가 왜 READ_COMMITTED인지 직접 적은 문장을 찾지 못했다”고 했다. 확인 답은 코드 주석에 있었다.

// catalog/admin/application/AdminCatalogService.java (발췌)
@Transactional(isolation = Isolation.READ_COMMITTED)
public CategoryView updateCategory(Long categoryId, CategoryPatchCommand request) {
  Category category = lockCategoryAndParent(categoryId, request.parentIdPresent() ? request.parentId() : null);
  if (request.parentIdPresent()) {
    Category parent = request.parentId() == null ? null : requireParentCategory(request.parentId(), categoryId);
    // READ_COMMITTED observes children committed while the row locks were awaited.
    // Child creation/reparenting must lock this target as its new parent first.
    if (parent != null && categoryRepository.existsByParentId(categoryId))
      throw new AdminCatalogConflictException("CATEGORY_DEPTH_EXCEEDED", "카테고리는 최대 2 depth까지만 지원합니다.");
    category.updateParent(parent);
  }
  ...
}

private Category lockCategoryAndParent(Long categoryId, Long parentId) {
  if (parentId != null && parentId < categoryId) requireCategoryForUpdate(parentId);   // 작은 ID 먼저
  Category category = requireCategoryForUpdate(categoryId);
  if (parentId != null && parentId > categoryId) requireCategoryForUpdate(parentId);
  return category;
}

주석을 9강의 MVCC로 풀면 이렇다.

  • 카테고리 A를 다른 부모 아래로 옮기려면 “A에 자식이 없는지”를 확인해야 한다. 있으면 3단계가 된다.
  • 그런데 동시에 다른 관리자가 A 아래에 자식을 만들고 있을 수 있다. 그래서 A의 행을 잠그고 기다린다.
  • 잠금을 얻은 뒤의 existsByParentId(A)는 일반 SELECT다.
    • REPEATABLE READ였다면 트랜잭션 초반에 만든 스냅샷을 보므로, 기다리는 동안 커밋된 자식을 보지 못한다. 9강의 재고 CAS 충돌과 똑같은 “오래된 스냅샷” 문제다.
    • READ COMMITTED는 SELECT마다 새 스냅샷을 만든다. 그래서 방금 커밋된 자식을 본다. 주석의 “잠금을 기다리는 동안 커밋된 자식을 관찰한다”가 바로 이것이다.
  • 9강의 재고는 같은 문제를 잠금 읽기(FOR UPDATE)로 풀었고, 여기서는 격리 수준으로 풀었다. 해법은 다르지만 원인은 같다.

함께 쓰인 장치도 9강의 내용 그대로다.

  • 격리 수준은 바깥이 정한다. 6절의 감사 서비스(최상위 트랜잭션 소유자)에도 READ_COMMITTED를 붙인 이유다. 9강의 그 주석(“감사 소유자도 격리 수준을 설정해야 한다. 안쪽 REQUIRED 서비스는 이 트랜잭션에 참여한다”)이 여기와 짝을 이룬다.
  • 잠금 순서는 ID 오름차순이다. lockCategoryAndParent는 이동 대상과 새 부모를 항상 작은 ID부터 잠근다. 두 관리자가 “A를 B 아래로”, “B를 A 아래로”를 동시에 하면, 순서가 제각각일 때 서로를 기다리는 교착이 난다. 순서를 고정하면 원천적으로 사라진다. 3강·9강의 교착 이야기에 대한 고전적인 해법이다.
  • 부모를 자식 INSERT보다 먼저 잠근다. 카테고리 생성은 부모를 먼저 FOR UPDATE로 잡은 뒤 자식을 만든다(주석: “acquire the parent lock before the child's FK insert”). 이동과 생성이 같은 행(부모) 에서 줄을 서게 된다.
  • 기록 결정 기록은 트리 전체나 테이블 잠금, DDL 재설계 대신 최소 범위를 택했다고 적는다. 그리고 “모든 interleaving이나 과거의 잘못된 트리 자동 복구를 증명하지는 않는다”는 한계도 함께 남겼다(이슈 #416).

14강 정리

  • 캐시를 들인 방식이 모범적이었다.
    • “DB가 느리다”고 가정하지 않고 우회 가능성을 시험했다.
    • 옛 전체 목록 API에서 p95 6.8초 → 4.7ms로 KEEP 판정을 받았다(로컬·합성 조건).
  • 정교한 무효화
    • 세대 번호를 미스 직후에 기억하고, Lua로 “세대 같을 때만 저장”, Lua로 “세대 증가 + 삭제”를 원자적으로 한다.
    • 무효화는 커밋 후에만 한다(afterCommit). 분산 락 없이 낡은 값 재적재를 막는다.
    • Redis 장애는 fail-open, TTL은 안전망, 값은 버전 붙은 JSON이다.
  • 핵심 발견: 지금은 읽히지 않는다
    • 필터·페이지 API(8/24)는 설계상 캐시를 우회했다.
    • 9/6 구조 정리로 getOrLoad 호출이 사라졌다.
    • 무효화 호출 15곳만 남았다.
    • 측정 결과는 코드 경로에 묶여 있다. 제거, 재설계(세대 접두사 키), HTTP 캐시 중에서 현재 API로 다시 측정한 뒤 고른다.
  • 관리자 카탈로그
    • 행 잠금으로 동시 수정을 직렬화한다.
    • 진짜 PATCH(present 플래그)다.
    • 엔티티의 canTransitionTo가 전이 규칙을 갖는다.
    • 감사 기록은 같은 트랜잭션이라, 감사가 실패하면 변경도 롤백된다.
  • 카테고리 2단계와 READ COMMITTED (9강의 답)
    • 잠금을 기다린 뒤 방금 커밋된 자식을 보려고 RC를 썼다.
    • 바깥 감사 서비스에도 같은 격리 수준을 둔다.
    • ID 오름차순으로 잠가 교착을 막는다.
    • 부모를 자식 INSERT보다 먼저 잠근다.
