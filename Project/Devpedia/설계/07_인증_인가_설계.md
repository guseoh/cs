## 1. 인증 구조

- **로그인 식별자:** 회원 이메일. DB에는 BCrypt 비밀번호 해시만 저장한다.
- **인증 유지:** Spring Security + 서버 `HttpSession`, 브라우저 세션 쿠키 (`HttpOnly`, 운영 HTTPS에서는 `Secure`, `SameSite=Lax`).
- **로그인 처리:** Spring Security `formLogin`의 URL을 `/api/v1/auth/login`으로 구성하고 `usernameParameter("email")`; 요청 본문은 `application/x-www-form-urlencoded`.
- **로그인 성공:** JSON `MyAccountResponse` 200, 리다이렉트 없음. 자격 증명 실패는 Problem Details 401 `BAD_CREDENTIALS`, 폼 계약 위반은 400 `INVALID_LOGIN_REQUEST`다. 재로그인 실패 시 기존 인증 제거는 09를 따른다.
- **로그아웃:** `POST /api/v1/auth/logout`, 세션 무효화·SecurityContext 정리, 204.
- **회원가입:** `POST /api/v1/auth/signup`은 비회원에게 허용, 가입 직후 자동 로그인하지 않는다.
- **현재 회원 ID:** `Authentication`의 커스텀 principal이 가진 `memberId`를 서버에서 사용한다. 작성자 ID·지원자 ID를 Request Body로 받지 않는다.
- **내 정보:** `GET /auth/me`는 로그인 필요, 미인증 401.

## 2. CSRF 계약 — SPA와 세션

1. 브라우저에서 `GET /api/v1/auth/csrf`를 호출한다.
2. 서버는 `HttpSessionCsrfTokenRepository` 기반 CSRF 토큰을 생성/조회하고 `{"headerName":"X-CSRF-TOKEN","token":"..."}`으로 반환한다.
3. 모든 POST/PUT/PATCH/DELETE에 `X-CSRF-TOKEN` 헤더를 포함한다. 기본 검증은 켜 둔다.
4. 로그인 또는 로그아웃이 성공하면 이전 토큰을 재사용하지 않고 `GET /auth/csrf`를 다시 호출한다.
5. 유효하지 않은 요청은 403 `CSRF_INVALID`로 반환한다.

Spring Security의 지연 CSRF 토큰 로딩과 BREACH masking을 고려하여 반환된 `CsrfToken`의 값과 헤더 처리기를 함께 검증한다. 인증 성공/종료 뒤 토큰 무효화도 통합 테스트한다. 임의로 CSRF를 전역 비활성화하지 않는다.

## 3. 인가 규칙

| 리소스·행동 | 비회원 | 로그인 회원 | 해당 작성자/소유자 |
|---|---:|---:|---:|
| 모집글/프로필/댓글/기준정보 조회 | 허용 | 허용 | 허용 |
| 모집글 생성·지원·댓글 등록·북마크 | 401 | 업무 규칙에 따라 허용 | 업무 규칙에 따라 허용 |
| 모집글 수정·마감·제거 | 401 | 다른 글 403 | 허용 |
| 글 전체 지원 목록·상세 | 401 | 다른 글 403 | 허용 |
| 지원 승인·거절 | 401 | 다른 글 403 | 허용 |
| 내 지원 목록·철회 | 401 | 자신의 지원만 | 자신의 지원만 |
| 내 프로필 변경 | 401 | 자신만 | 자신만 |
| 댓글 수정·삭제 | 401 | 다른 사람 댓글 403 | 작성자 본인만 |

`ROLE_USER` 등 인증 권한은 **서비스 계정의 인증 여부를 나타내는 기술적 권한**이다. `roles` 테이블의 `백엔드/프론트엔드`는 모집 참여 분야이며 Spring Security의 `GrantedAuthority`가 아니다.

**리소스 소유권 검사:** 경로에 글 ID 또는 지원 ID가 있다고 권한이 생기는 것이 아니다. 조회된 글의 `author_member_id`와 현재 회원을 비교하고 지원서의 글 소속까지 함께 확인한다. `@PreAuthorize`만으로 해결되지 않는 리소스 소유권은 Service에서 검사한다.

## 4. SecurityFilterChain 설정 범위

| 요소 | 계약 |
|---|---|
| CSRF | enabled, session token repository, `/auth/csrf` 발급 API 제공 |
| 세션 | 인증 시 세션 고정 공격 방지·세션 ID 교체, 로그아웃 무효화 |
| Permit All | `GET /auth/csrf`, `POST /auth/signup`, `POST /auth/login`, 공개 조회 GET |
| Authenticated | 그 밖의 보호된 `/api/v1/**` |
| 예외 핸들러 | 인증 401 Problem Details, 인가/CSRF 403 Problem Details |
| 로그인 필터 | 이메일/비밀번호, 성공 200 JSON, 실패 401 JSON |
| 로그아웃 필터 | POST, 성공 204 |
| CORS | 운영 프런트와 API를 **동일 출처**로 제공해 불필요한 credentialed cross-origin 설정을 만들지 않음 |
| 공개 범위 | `/api/v1` REST JSON, `actuator`의 세부 운영 정보는 공개하지 않음 |

### 동일 출처 배포 구조

```text
https://devpedia.example (예시 도메인)
  ├─ /                  → React 정적 자원
  └─ /api/v1/**         → Spring Boot API
                                └─ HttpSession / MySQL
```

도메인은 **구성 설명용 예시**일 뿐 실제 배포 도메인을 확정한 것이 아니다. 중요한 기술 계약은 *브라우저 관점에서 UI와 API가 같은 origin*을 사용한다는 점이다.

## 5. 보안 테스트 최소 세트

- 보호 API에 세션 없음 → 401, HTML 로그인 화면이나 리다이렉트가 아닌 JSON.
- 로그인 실패 → 401 `BAD_CREDENTIALS`; 이메일 존재 여부 비공개.
- CSRF 토큰 없음/오류 → 403 `CSRF_INVALID`; 유효 토큰으로 성공.
- 로그인 전/후 세션 고정 방지 및 토큰 재발급 확인.
- 세션 쿠키 `HttpOnly`, 운영 HTTPS `Secure` 확인.
- 공개 프로필에서 이메일/비밀번호 해시/지원 동기 누출 0건.
- 타인의 글 수정, 타인의 지원서 조회/승인, 타인의 댓글 수정 실패.
- 로그아웃 후 이전 세션으로 보호 API 접근 시 401.

## 6. 구현 컴포넌트

| 컴포넌트 | 입력·출력과 책임 |
|---|---|
| CustomUserDetails | memberId, email, passwordHash, ROLE_USER; 비밀번호는 응답 DTO로 노출하지 않음 |
| MemberUserDetailsService | trim·소문자 email로 회원 검색, 없으면 인증 실패 |
| DaoAuthenticationProvider | UserDetailsService와 PasswordEncoder로 자격 증명 검증 |
| BCryptPasswordEncoder | 가입 encode, 로그인 matches |
| AuthenticationSuccessHandler | 현재 회원을 조회해 200 MyAccountResponse, redirect 없음 |
| AuthenticationFailureHandler | 401 BAD_CREDENTIALS |
| AuthenticationEntryPoint | 401 UNAUTHENTICATED |
| AccessDeniedHandler | CSRF 관련 예외 403 CSRF_INVALID, 나머지 403 ACCESS_DENIED |
| LogoutSuccessHandler | 204, 본문 없음 |
| CsrfController | 요청에 연결된 CsrfToken의 headerName/token 반환 |

세션 생성 정책은 IF_REQUIRED, 유휴 만료는 30분이다. remember-me와 HTTP Basic은 사용하지 않는다. 로그인/CSRF/내 계정·프로필·지원 응답은 Cache-Control: no-store로 반환한다. 세션 종료 후 principal 캐시만으로 계정 응답을 만들지 않는다.

## 7. 경로 매칭

공개 GET은 `/auth/csrf`, `/roles`, `/tech-stacks`, `/members/{memberId}`, `/recruitment-posts`, `/recruitment-posts/{postId}`, `/recruitment-posts/{postId}/comments`만 허용한다. `/recruitment-posts/**` 전체를 공개하지 않는다. 특히 하위 applications 조회는 인증과 작성자 검사가 필요하다.

회원가입·로그인은 permitAll로 두되 CSRF 검사를 적용한다. 로그아웃은 유효한 CSRF 요청이면 비회원도 종료 성공 204를 반환한다. 그 밖의 V1 보호 API는 authenticated다. 서비스에서 글·댓글 소유권과 지원 소속을 검사한다. Spring Security의 ROLE_USER는 모든 가입 회원에게 부여하는 기술 권한이며 DB roles 테이블을 조회해 생성하지 않는다.

## 8. CSRF 요청·세션 동작

HttpSessionCsrfTokenRepository와 XorCsrfTokenRequestAttributeHandler를 함께 사용한다. csrf API는 request attribute의 CsrfToken에서 getToken()을 호출해 지연 로딩된 토큰을 실제로 얻고 그 masked token을 반환한다. 브라우저는 그 값을 그대로 X-CSRF-TOKEN 헤더에 넣는다. repository의 raw token을 별도로 읽어 섞지 않는다.

로그인 성공으로 기존 CSRF 토큰이 제거되면 브라우저는 새 토큰을 GET으로 받아 다음 변경 요청에 사용한다. 로그아웃 후에도 새 csrf GET을 통해 비회원 세션 토큰을 받는다. 401/403을 받았다고 실패한 쓰기를 자동 재전송하지 않는다. 먼저 세션 상태·오류 코드를 확인한다.

| 확인 상황 | 결과 |
|---|---|
| 비회원 + 공개 GET | 200 또는 리소스 404 |
| 비회원 + 보호 GET | 401 |
| CSRF 없는 변경 요청 | 인증 유무와 관계없이 403 CSRF_INVALID |
| 유효 CSRF + 비회원 보호 변경 | 401 |
| 유효 CSRF + 로그인 + 타인 글 변경 | 403 ACCESS_DENIED |
| 유효 CSRF + 정상 로그인 | 200 JSON, 세션 ID 교체 |
| 로그아웃 후 과거 세션으로 보호 GET | 401 |

로컬은 HttpOnly=true, SameSite=Lax, Secure=false이고 운영 HTTPS에서 Secure=true다. 브라우저가 JSESSIONID를 관리하며 JavaScript가 직접 읽지 않는다. URL에 세션 ID를 넣지 않는다.
