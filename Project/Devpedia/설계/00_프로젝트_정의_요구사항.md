## 1. 프로젝트 정의

**서비스:** 프로젝트와 스터디에 참여할 개발자를 모집하는 플랫폼. 사용자는 모집글의 특정 역할에 지원하고, 모집자는 지원서를 검토·승인·거절하며, 지원자는 결과를 서비스 안에서 확인한다.

**포트폴리오 목표:** Java/Spring 백엔드 개발자의 도메인 모델링, 객체 책임 분리, REST API 설계, 인증·인가, JPA/SQL, 트랜잭션과 테스트 역량을 검증 가능한 결과로 보여준다. 기능 수 증가 자체는 목표가 아니다.

**완료할 사용자 흐름:** `회원가입 → 로그인 → 모집글 생성(역할·정원) → 다른 회원의 지원 → 모집자의 승인/거절 → 지원자의 결과 확인 → 정원 충족/마감`. 이 흐름을 기본 기능 테스트로 검증한다.

### 사용자 구분

| 사용자 | 할 수 있는 일 |
|---|---|
| 비회원 | 모집글 목록·상세, 역할·기술 목록, 공개 프로필, 댓글 조회 |
| 로그인 회원 | 프로필 관리, 모집글 작성, 모집 역할 지원, 지원 철회, 댓글 작성, 북마크 |
| 모집글 작성자 | 자기 글의 수정·마감·삭제, 해당 글 지원서 열람·승인·거절 |

작성자와 지원자는 별도의 계정 등급이 아니다. **작성자 = 해당 모집글의 소유 회원**, **지원자 = 해당 지원서의 제출 회원**이다.

## 2. 기능 범위와 수용 기준

| ID | 기능 | V1 수용 기준 |
|---|---|---|
| MEM-01 | 회원가입 | 이메일·닉네임 중복 방지, 비밀번호 해시 저장, 생성 회원 조회 |
| AUTH-01 | 세션 인증 | 로그인·로그아웃·내 정보, 미인증 401, 인가 실패 403, CSRF 적용 |
| PROFILE-01 | 프로필 | 본인 수정, 타인 공개 조회, 이메일·비밀번호 해시 비노출 |
| REF-01 | 역할·기술 스택 | 관리자가 사전 등록한 선택 목록 조회; 사용자 임의 생성 불가 |
| POST-01 | 모집글 생성 | 프로젝트/스터디 타입, 시작일, 역할별 정원 최소 1개, 기술 선택을 한 트랜잭션에 저장 |
| POST-02 | 모집글 관리 | 목록·상세·검색·필터·페이징, 본인 수정·마감·공개 제거 |
| APPLY-01 | 지원 | 특정 모집 역할에 지원; 제출 당시 URL을 별도 저장; 중복·재지원 정책 준수 |
| APPLY-02 | 선발 | 작성자만 승인·거절; 역할 정원 초과 금지; 마지막 승인 시 자동 종료 |
| APPLY-03 | 지원 확인 | 내 지원 목록·상세·결과 조회, 검토 중 철회 |
| COMMENT-01 | 댓글 | 댓글과 한 단계 답글, 작성자 수정/삭제, 답글 존재 시 부모 표시 유지 |
| BOOKMARK-01 | 북마크 | 중복 저장 금지, 목록·추가·해제 |

## 3. 화면에 필요한 최소 사용자 동선

**모집자:** 로그인 → 모집글 작성(역할+정원) → 내 모집글 → 지원 목록 → 지원서 확인 → 승인 또는 거절 → 마감 상태 확인.

**지원자:** 모집글 검색 → 글 상세 → 역할 선택 → 로그인 → 지원 동기 제출 → 내 지원 확인 → 결과 확인 또는 검토 중 철회.

**비회원:** 목록 검색 → 글 상세·작성자 공개 프로필·댓글 열람. 쓰기 기능을 요청하면 인증을 요구한다.

## 4. 비기능 완료 기준

| 주제 | 검증 가능한 결과 |
|---|---|
| 데이터 무결성 | 동일 글의 검토 중 지원은 회원당 최대 1개, 승인 수는 역할별 정원 이하; 동시 요청에도 보장 |
| 권한 | 타인의 모집글 수정·지원서 열람·승인 및 타인의 지원 철회 차단 |
| 트랜잭션 | 모집글+역할+기술 생성, 승인+자동 종료+마감을 원자적으로 처리 |
| 개인정보 | 공개 API에 이메일, 비밀번호 해시, 지원 동기, 지원 결과가 노출되지 않음 |
| 관측 | 실패 로그의 원인을 추적하되 인증정보·지원서 민감정보는 로그에서 제외 |

## 5. 현재 제품 경계

**구현 대상:** 회원/프로필, 기준정보, 모집·지원·선발, 댓글, 북마크, 검색.

**구현하지 않음:** 채팅, 팀 운영, 알림 전송, 소셜 로그인, 관리자 CRUD 화면, 추천/AI, 결제, 광고. 역할과 기술 스택은 초기 SQL 데이터로 공급한다. 별도의 탈퇴·개인정보 파기 API는 V1에서 제공하지 않는다.

## 7. 구현할 화면과 API 연결

| 화면 | 진입·주요 행동 | 연결 API |
|---|---|---|
| 모집 목록 | 검색, 타입·역할·기술·진행 방식·모집 상태 선택 | 모집글 목록, 역할/기술 목록 |
| 모집 상세 | 본문·정원·작성자 확인, 북마크, 댓글, 역할 선택 | 모집 상세, 댓글 목록, 북마크 PUT/DELETE |
| 회원가입·로그인 | 가입 후 별도 로그인, 세션 유지 | csrf, signup, login, me, logout |
| 공개 프로필 | 닉네임·소개·링크·역할·기술 확인 | members/{memberId} |
| 내 프로필 | 공개 정보 전체 교체 | me/profile GET/PUT |
| 모집 작성·수정 | 역할별 정원·일정·기술 입력 | 모집 POST/PATCH |
| 내 모집 | 작성 글 목록, 지원서 관리, 마감·제거 | me/recruitment-posts, closure, DELETE |
| 지원서 제출 | 역할 확인, 동기·링크 제출 | slots/{slotId}/applications POST |
| 내 지원 | 결과·제출 내용 확인, 검토 중 철회 | me/applications 목록/상세/withdrawal |
| 지원자 관리 | 글 소유자만 지원서 열람·선발 | 글 applications 목록/상세/approval/rejection |
| 내 북마크 | 저장 글·마감 상태 확인 | me/bookmarks |

커뮤니티 기능은 모집글에 연결된 댓글과 한 단계 답글로 제공한다. 독립 자유게시판·카테고리·게시판 관리 기능은 이번 구현 범위에 포함하지 않는다. 스터디와 프로젝트는 동일한 모집 모델을 사용하고 type으로 구분한다. 스터디도 최소 하나의 모집 역할과 역할별 정원을 지정한다.

## 8. 화면 상태와 사용자 결과

빈 목록은 오류 화면이 아니라 빈 items와 안내를 표시한다. 401이면 로그인 화면으로 이동하고, 로그인 후 원래 조회 화면으로 돌아온다. 쓰기 요청을 자동 재전송하지 않는다. 403은 권한 없음, 404는 조회 불가, 409는 최신 상세를 다시 조회하여 변경된 상태를 표시한다. 입력 오류는 errors의 필드 경로로 해당 입력 옆에 표시한다.

마감된 글은 조회와 북마크가 가능하지만 지원·새 댓글 버튼을 비활성화한다. OPEN이라도 acceptingApplications=false이면 지원을 비활성화하고 접수 종료 사유를 표시한다. 정원이 찬 역할은 선택할 수 없다. 버튼 숨김과 무관하게 서버가 같은 규칙을 검사한다.

## 9. 문서 사용 순서

환경 구성은 01, 구현 순서는 08에서 시작한다. 각 기능의 업무 규칙은 02, 테이블·제약은 03, HTTP는 04, JSON 필드는 05, 오류는 06, 인증·소유권은 07을 함께 적용한다. 04의 API 번호는 구현 완료 여부를 추적하는 기준이다. 03의 SQL 블록과 동일한 sql/001_schema.sql 및 sql/002_seed.sql로 최초 스키마를 구성한다.
## 10. 이번 문서의 범위

V1 도메인과 기본 API 구현을 다룬다. 동시 요청의 정합성, 날짜에 따른 접수 가능 여부, 공개 제거 후 이력 처리는 V1 완료 조건이다. 구체적인 정책은 09를 따른다. 알림·팀 운영·모집 재개는 V2 후보로 둔다.
