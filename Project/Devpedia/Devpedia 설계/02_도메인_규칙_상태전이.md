## 1. 도메인 구성

| 도메인 | 책임 | 주요 객체 |
|---|---|---|
| 회원 | 가입·로그인 식별 정보, 공개 프로필 관리 | Member |
| 기준정보 | 관심·모집 역할과 기술 목록 제공 | Role, TechStack |
| 모집 | 프로젝트·스터디 모집 정보와 역할별 정원 관리 | RecruitmentPost, RecruitmentSlot |
| 지원 | 특정 역할에 대한 지원과 선발 결과 기록 | Application |
| 커뮤니티 | 모집글별 질문·의견과 한 단계 답글 | Comment |
| 북마크 | 회원이 관심 있는 모집글 저장 | Bookmark |

모집글 작성자와 지원자는 계정 종류가 아니라 해당 리소스와 회원의 관계다. 회원은 어떤 글에서는 작성자이고 다른 글에서는 지원자일 수 있다. 공개 프로필은 Member의 공개 필드와 관심 역할·기술 연결로 구성한다.

## 2. 회원과 프로필

회원가입에는 email, password, nickname이 필요하다. 이메일은 trim 후 소문자로 저장하고 로그인 시에도 같은 변환을 한다. 닉네임은 trim 후 저장한다. 이메일과 닉네임의 중복 비교는 데이터베이스 기준에 맞춰 대소문자와 악센트를 구분하지 않는다. 가입과 프로필 변경에 같은 기준을 적용한다. 이메일·닉네임은 중복될 수 없다. 비밀번호는 trim하거나 정규화하지 않고 BCrypt 해시만 저장한다.

프로필은 nickname, bio, githubUrl, portfolioUrl, interestRoles, techStacks로 구성한다. 회원은 본인 프로필만 수정한다. 공개 프로필에서는 email과 passwordHash를 반환하지 않는다. 이메일·비밀번호 변경과 탈퇴는 V1 API에 포함하지 않는다.

관심 역할·기술은 기준 목록에서 선택한다. 빈 목록을 허용하고 중복 ID와 존재하지 않는 ID를 거절한다. PUT은 프로필 전체 교체다. nullable 필드 생략은 null, 필수 배열 생략은 입력 오류다.

## 3. 기준정보

Role은 백엔드·프론트엔드·스터디원 같은 모집 분야다. 인증 권한 ROLE_USER와 별개다. TechStack은 Java·Spring Boot·React 같은 기술이다. 기준 목록은 displayOrder ASC, id ASC 순서로 반환한다. V1에는 조회 API만 있으며 초기 데이터는 03에 정의한다.

## 4. 모집글

| 항목 | 규칙 |
|---|---|
| 작성자 | 로그인 회원 한 명, 생성 후 변경 불가 |
| type | PROJECT 또는 STUDY, 생성 후 변경 불가 |
| title/content | 필수, 길이는 05의 계약 적용 |
| 일정 | startDate 필수·생성 시 오늘 이후, 마감일은 선택·오늘 이상·시작일 미만 |
| 진행 방식 | ONLINE/OFFLINE/HYBRID |
| 지역·기간 | 선택 문자열 |
| 기술 | 기준 기술 0..50개 |
| 모집 역할 | 1..20개, 동일 역할 중복 불가, 역할당 정원 1..20명 |

모집 역할은 ‘특정 글에서 특정 분야 몇 명을 모집하는가’를 나타낸다. 전역 Role의 ID와 모집 역할 RecruitmentSlot의 ID는 서로 다르다. 지원할 때는 slotId를 사용한다. 작성자는 모집 정원에 자동 포함되지 않는다.

생성 시 글·모집 역할·기술 연결을 함께 저장한다. 수정은 OPEN인 자기 글만 가능하다. 지원 이력이 있으면 slots·startDate·applicationDeadlineDate를 변경하지 않는다. 제목·본문·진행 방식·지역·기간·기술은 수정할 수 있다. slots는 전체 목록 교체 입력이며 같은 roleId의 slotId는 유지한다. 지원 이력이 없을 때 날짜를 수정하면 변경된 필드를 반영한 일정 조합을 검사한다. 변경하지 않은 날짜에는 생성 시의 오늘 기준 검사를 다시 적용하지 않는다.

### 기본 상태

| 상태 | 의미 | 가능한 기본 행동 |
|---|---|---|
| OPEN | 모집 중 | 조회·수정·지원·새 댓글·직접 마감 |
| CLOSED | 모집 마감 | 조회·기존 본인 댓글 수정/삭제·북마크 |
| REMOVED | 공개에서 제거됨 | 공개 조회 불가 |

작성자의 직접 마감은 OPEN → CLOSED, 글 제거는 OPEN/CLOSED → REMOVED다. CLOSED를 OPEN으로 되돌리는 기능은 없다. 이미 CLOSED인 글의 직접 마감과 이미 REMOVED인 글의 제거 재요청은 성공으로 처리한다. 이 문서는 저장된 상태를 기준으로 기본 기능을 설명한다.

## 5. 지원서와 선발

지원서는 모집글 전체가 아니라 한 RecruitmentSlot에 제출한다. 지원자는 로그인 회원이며 글 작성자 자신은 지원할 수 없다. motivation이 필수이고 GitHub·포트폴리오 URL은 선택이다. URL은 제출된 값을 snapshot으로 저장한다. 프로필 수정이 과거 지원서 링크를 바꾸지 않는다. 서버는 생략된 링크를 프로필에서 자동 복사하지 않는다.

| 상태 | 의미 | 변경 주체 |
|---|---|---|
| UNDER_REVIEW | 제출 후 검토 중 | 제출 시 생성 |
| APPROVED | 선발됨 | 모집글 작성자 |
| REJECTED | 선발되지 않음 | 모집글 작성자 |
| WITHDRAWN | 지원자가 철회함 | 해당 지원자 |
| AUTO_CLOSED | 모집 종료로 검토가 종료됨 | 모집 종료 처리 |

변경은 UNDER_REVIEW에서만 가능하다. APPROVED/REJECTED/WITHDRAWN/AUTO_CLOSED는 최종 상태이며 다시 검토 중으로 돌리지 않는다. 지원 내용 수정 API는 없다. 승인·거절·철회 재요청은 이미 최종 상태이면 409다.

### 지원 가능 조건

글이 OPEN이고 09의 접수 날짜 조건을 만족하며 선택한 역할의 승인 인원이 정원보다 작아야 한다. 동일 글에 검토 중인 지원 또는 승인 이력이 있으면 새 지원은 불가하다. 동일 역할에서 거절된 이력이 있으면 해당 역할에 다시 지원할 수 없다. 철회 후에는 조건을 충족할 때 새 지원서를 제출할 수 있다. 다른 역할에서 거절된 이력은 해당 글의 다른 역할 지원을 막지 않는다.

### 선발과 모집 종료

작성자만 자기 글의 지원서를 조회·승인·거절한다. 승인 수는 정원 이하다. 한 역할이 차면 그 역할의 남은 검토 중 지원은 AUTO_CLOSED/ROLE_FILLED가 된다. 모든 역할이 차면 글은 CLOSED/ALL_ROLES_FILLED다. 직접 마감은 CLOSED/OWNER이며 남은 검토 중 지원은 AUTO_CLOSED/POST_CLOSED다. 종료된 지원 결과는 덮어쓰지 않는다.

### 기록 필드

| 변경 | decidedAt | decidedByMemberId | autoCloseReason |
|---|---|---|---|
| 제출 | null | null | null |
| 승인·거절 | 처리 시각 | 모집자 ID | null |
| 철회 | 처리 시각 | 지원자 ID | null |
| 자동 종료 | 처리 시각 | null | ROLE_FILLED/POST_CLOSED/POST_REMOVED |

## 6. 댓글·답글

댓글은 모집글에 속한다. 루트는 parentCommentId=null, 답글은 같은 글의 루트 댓글을 부모로 가진다. 답글의 답글은 만들 수 없다. OPEN 글에서만 새 댓글을 작성한다. 수정·삭제는 댓글 작성자 본인만 가능하며 글 작성자에게 다른 사람의 댓글 삭제 권한은 없다.

답글과 답글 없는 루트는 물리 삭제한다. 답글이 있는 루트는 content=null, isContentRemoved=true로 내용을 제거하여 답글의 부모를 남긴다. 내용이 제거된 댓글은 수정할 수 없다. 내용 제거된 루트에 새 답글은 허용하지 않는다. 마감된 글의 기존 댓글은 본인이 수정·삭제할 수 있다.

목록은 루트와 답글을 평탄한 배열로 반환하고 parentCommentId로 구분한다. 페이지를 넘기면 부모와 답글이 나뉠 수 있으므로 답글에는 09의 parentPreview를 포함한다. 정렬은 createdAt ASC, commentId ASC다.

## 7. 북마크

회원은 존재하는 공개 모집글을 북마크할 수 있다. OPEN/CLOSED 모두 가능하다. 회원·글 조합은 한 건이며 중복 추가와 없는 북마크 해제는 204다. 목록은 본인 저장 항목만 조회하고 createdAt DESC, postId DESC로 정렬한다.

## 8. 서비스 책임

| 서비스 | 주요 작업 |
|---|---|
| MemberService | 회원가입, 공개/본인 프로필 조회, 프로필 교체 |
| ReferenceService | 역할·기술 목록 조회 |
| RecruitmentService | 글 생성·조회·검색·수정·직접 마감·공개 제거 |
| ApplicationService | 제출·본인 조회·모집자 조회·철회·승인·거절 |
| CommentService | 목록·작성·수정·삭제 |
| BookmarkService | 추가·해제·본인 목록 |

Controller는 입력 검증·현재 회원 전달·HTTP 응답을 담당한다. Service는 소유권·참조 존재·상태·도메인 규칙을 검사한다. Entity는 자신의 필드 변경과 상태 전이를 표현한다. 여러 객체가 함께 변경되는 기본 저장 작업은 하나의 트랜잭션으로 묶는다.
