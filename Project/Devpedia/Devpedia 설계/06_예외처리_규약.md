## 1. 오류 응답 형식

성공 응답에는 공통 래퍼를 사용하지 않는다. **실패 응답은 RFC 9457 Problem Details**를 사용하며 `code`와 필요한 경우 `errors` 확장 필드를 포함한다.

**HTTP 헤더:** `Content-Type: application/problem+json`.

```json
{
  "type":"about:blank",
  "title":"Conflict",
  "status":409,
  "detail":"동일 모집글에 검토 중인 지원서가 존재합니다.",
  "instance":"/api/v1/recruitment-posts/10/slots/30/applications",
  "code":"ACTIVE_APPLICATION_EXISTS"
}
```

검증 실패는 `errors` 배열을 추가한다.

```json
{
  "type":"about:blank",
  "title":"Bad Request",
  "status":400,
  "detail":"요청 필드가 올바르지 않습니다.",
  "instance":"/api/v1/auth/signup",
  "code":"VALIDATION_FAILED",
  "errors":[
    {"field":"email","reason":"올바른 이메일 형식이어야 합니다."},
    {"field":"nickname","reason":"2자 이상 30자 이하여야 합니다."}
  ]
}
```

**응답 금지 정보:** Java 예외 클래스명, stack trace, SQL/DB명, 비밀번호, 세션 ID, 내부 리소스 식별 범위, 사용자 민감정보. 요청 `instance`에는 query 문자열을 포함하지 않는다.

## 2. Java 예외 타입

| 클래스/컴포넌트 | 책임 |
|---|---|
| `ErrorCode` enum | 안정적인 오류 식별자, HTTP status, 기본 메시지 |
| `BusinessException extends RuntimeException` | 도메인 규칙 위반; `ErrorCode` 보유 |
| `GlobalExceptionHandler` (`@RestControllerAdvice`) | MVC 예외를 ProblemDetail로 변환 |
| `AuthenticationEntryPoint` | 인증 실패/미인증 요청을 401로 변환 |
| `AccessDeniedHandler` | 접근 권한 또는 CSRF 문제를 403으로 변환 |
| `AuthenticationFailureHandler` | 로그인 실패 시 401 반환 |

**계층마다 `ControllerException`, `ServiceException`, `RepositoryException`을 따로 만들지 않는다.** 업무 오류를 의미로 구별한다. DB 제약 충돌은 Repository 내부 타입을 HTTP로 그대로 노출하지 않고 Service에서 기대한 코드로 변환한다.

## 3. ErrorCode 목록

### 공통·인증

| 코드 | HTTP | 트리거 |
|---|---:|---|
| `VALIDATION_FAILED` | 400 | `@Valid` 필드 오류 |
| `INVALID_JSON` | 400 | 잘못된 JSON/알 수 없는 필드/enum 값 |
| `INVALID_QUERY` | 400 | 잘못된 page/size/filter/정렬 |
| `UNAUTHENTICATED` | 401 | 비로그인 세션으로 보호된 API 접근 |
| `BAD_CREDENTIALS` | 401 | 로그인 이메일 또는 비밀번호 불일치 (어느 쪽인지 구별하지 않음) |
| `ACCESS_DENIED` | 403 | 로그인 사용자가 타인의 리소스 변경·열람 요청 |
| `CSRF_INVALID` | 403 | CSRF 토큰 없음·불일치 |
| `INTERNAL_ERROR` | 500 | 예상하지 못한 서버 실패 |

### 회원·기준정보

| 코드 | HTTP | 트리거 |
|---|---:|---|
| `MEMBER_NOT_FOUND` | 404 | 회원 없음 |
| `DUPLICATE_EMAIL` | 409 | 이메일 UNIQUE 충돌 |
| `DUPLICATE_NICKNAME` | 409 | 닉네임 UNIQUE 충돌 |
| `REFERENCE_NOT_FOUND` | 422 | 존재하지 않는 Role/TechStack 선택 |
| `INVALID_REFERENCE_SELECTION` | 422 | 중복 선택 ID 또는 허용 개수 초과 |

### 모집글·역할

| 코드 | HTTP | 트리거 |
|---|---:|---|
| `POST_NOT_FOUND` | 404 | 글이 없거나 REMOVED라서 공개 접근 불가 |
| `SLOT_NOT_FOUND` | 404 | 역할 없음 또는 해당 글에 속하지 않음 |
| `POST_ALREADY_CLOSED` | 409 | 마감 글 수정·지원 제출·승인·거절 요청 |
| `INVALID_POST_DATES` | 422 | 시작일·마감일 유효 조건 불충족 |
| `INVALID_POST_SLOTS` | 422 | 역할 없음/정원 범위 위반/중복 역할 |
| `POST_HAS_APPLICATIONS` | 409 | 지원 이력 존재 후 역할·날짜 변경 시도 |

### 지원·선발

| 코드 | HTTP | 트리거 |
|---|---:|---|
| `APPLICATION_NOT_FOUND` | 404 | 본인 또는 해당 모집글 소속 지원서가 아님 |
| `SELF_APPLICATION_FORBIDDEN` | 409 | 자기 모집글에 지원 |
| `ACTIVE_APPLICATION_EXISTS` | 409 | 같은 글 검토 중인 지원서가 이미 있음 |
| `ALREADY_APPROVED_FOR_POST` | 409 | 같은 글 승인 이력이 존재 |
| `REAPPLY_REJECTED_SLOT` | 409 | 동일 역할에서 거절된 이력이 있음 |
| `SLOT_FILLED` | 409 | 역할 승인 정원 충족 |
| `APPLICATION_STATE_CONFLICT` | 409 | 최종 상태에 다시 승인/거절/철회 시도 |

### 댓글·북마크

| 코드 | HTTP | 트리거 |
|---|---:|---|
| `COMMENT_NOT_FOUND` | 404 | 댓글 없음 또는 공개 불가 |
| `INVALID_COMMENT_PARENT` | 422 | 다른 글의 부모/답글의 답글 |
| `COMMENT_ALREADY_REMOVED` | 409 | 내용이 제거된 부모에 답글 작성 또는 해당 댓글 수정 |
| `COMMENT_CREATION_CLOSED` | 409 | 마감 글에 새 댓글/답글 작성 |

북마크 중복 추가·없는 항목 해제는 오류가 아니라 **204**다.

## 4. 처리 위치 및 우선순위

| 오류 출처 | 처리 |
|---|---|
| `MethodArgumentNotValidException` | `GlobalExceptionHandler` → 400 `VALIDATION_FAILED` |
| `HttpMessageNotReadableException` | → 400 `INVALID_JSON` |
| 파라미터 타입/enum 바인딩 실패 | → 400 `INVALID_QUERY` |
| `BusinessException` | `ErrorCode`의 HTTP 상태·메시지를 ProblemDetail로 변환 |
| `DataIntegrityViolationException` | 알려진 email/nickname 유일성 충돌만 업무 코드로 매핑, 그 외 500으로 처리·서버 로그에서 원인 보존 |
| Spring Security 미인증 | **필터 영역**의 EntryPoint → 401 |
| Spring Security 인가 실패 | **필터 영역**의 AccessDeniedHandler → 403 |
| CSRF 실패 | **필터 영역**의 AccessDeniedHandler → 403 `CSRF_INVALID` |
| 기타 예외 | 서버 내부 로그 후 500 `INTERNAL_ERROR` |

**중요:** `@RestControllerAdvice`만으로 Spring Security 필터에서 발생한 예외를 모두 처리할 수 없다. 필터 영역 401/403은 별도 핸들러가 같은 JSON 규격을 작성해야 한다.

## 5. 구현 흐름

```text
Controller (@Valid) → Service (업무 규칙) → Repository (DB 제약)
          │                 │                       │
          └─ Validation ────┴─ BusinessException ───┴─ 무결성 충돌 변환
                                 ↓
                        GlobalExceptionHandler
                                 ↓
                         ProblemDetail + code
```

- `ErrorCode`는 변하지 않는 식별자다. 프런트엔드는 한국어 detail 문구가 아닌 code로 처리한다.
- 특정 DB index 이름에 의존하는 중복 오류 분기는 최소화한다. 선검사 + 최종 DB 보호 후 최종 실패를 의미 있는 업무 오류로 반환한다.
- 500 오류는 사용자에게 일반화된 문구만 반환하고, 서버 로그에는 요청 상관관계 ID와 민감정보가 제거된 원인을 남긴다.

## 6. 확인 테스트

- 회원가입 잘못된 email → 400 `VALIDATION_FAILED` + errors 배열
- 중복 이메일 가입 → 409 `DUPLICATE_EMAIL`
- 유효 CSRF를 가진 비회원의 모집글 작성 → 401 `UNAUTHENTICATED`
- 다른 회원의 모집글 수정 → 403 `ACCESS_DENIED`
- CSRF 헤더 없는 POST → 403 `CSRF_INVALID`
- 마감 글 지원 → 409 `POST_ALREADY_CLOSED`
- 예상 밖 예외 → 500 `INTERNAL_ERROR` (stack trace 노출 금지)

## 7. 추가 공통 오류와 메시지 계약

| code | HTTP | detail |
|---|---:|---|
| EMPTY_PATCH | 422 | 변경할 필드를 하나 이상 입력해야 합니다. |
| METHOD_NOT_ALLOWED | 405 | 지원하지 않는 HTTP 메서드입니다. |
| UNSUPPORTED_MEDIA_TYPE | 415 | 지원하지 않는 요청 형식입니다. |
| NOT_ACCEPTABLE | 406 | 지원하지 않는 응답 형식입니다. |
| ROUTE_NOT_FOUND | 404 | 요청한 API를 찾을 수 없습니다. |

명세에서 빈 본문으로 지정한 명령은 본문을 읽지 않는다. JSON을 요구하는 API에서 본문이 없거나 형식이 깨졌으면 INVALID_JSON이다. 필드 누락과 필드 길이 문제는 VALIDATION_FAILED다. Query·Path 변환 오류는 INVALID_QUERY다. 입력 바인딩이 끝난 뒤 업무 규칙을 검사한다.

400 title은 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 405 Method Not Allowed, 406 Not Acceptable, 409 Conflict, 415 Unsupported Media Type, 422 Unprocessable Content, 500 Internal Server Error다. status와 HTTP 응답 상태는 일치해야 한다. type은 about:blank, instance는 쿼리를 제외한 요청 경로다. errors는 필드 검증 실패에만 포함하고 그 외에는 생략한다.

필드 경로는 nickname, slots[0].capacity, techStackIds[1]처럼 요청 JSON 경로로 반환한다. rejectedValue는 반환하지 않는다. 여러 오류는 field 오름차순으로 정렬한다. 배열·날짜 조합 같은 업무 오류는 단일 code를 반환한다. 사용자에게 표시할 메시지는 ErrorCode에서 관리하며 프런트 분기는 code를 기준으로 한다.

## 8. 서비스와 필터의 처리 경계

MVC 예외와 Security 필터 예외는 동일한 Problem 응답 팩토리를 사용한다. RestControllerAdvice가 필터 내부 오류까지 처리한다고 가정하지 않는다. 로그인 실패 핸들러는 이메일 존재 여부를 구분하지 않고 BAD_CREDENTIALS를 반환한다. CSRF 핸들러는 CSRF_INVALID, 일반 소유권 위반은 ACCESS_DENIED다.

검증 우선순위는 CSRF·인증 필터 → 요청 바인딩 → 리소스 존재 → 소유권 → 상태 → 업무 조건이다. 내 지원 상세는 본인 조건을 포함하여 조회하므로 타인 리소스에 403 대신 404를 반환한다. 모집자 지원 상세는 글 소유권을 먼저 확인하고 해당 글에 없는 지원 ID는 404다.

DB 예외는 알려진 회원 email/nickname 유일성 충돌만 해당 코드로 변환한다. 모든 무결성 예외를 중복 오류로 간주하지 않는다. 예상 밖 실패는 INTERNAL_ERROR와 ‘요청 처리 중 오류가 발생했습니다.’만 응답한다. 서버 로그에는 요청 경로·상관관계 ID·오류 원인을 남기되 password, Cookie, CSRF, 지원서 본문은 기록하지 않는다.

## 보완 오류 코드

| code | HTTP | 기본 detail |
|---|---:|---|
| APPLICATION_PERIOD_ENDED | 409 | 지원 접수 기간이 종료되었습니다. |
| CONCURRENT_MODIFICATION | 409 | 다른 요청이 처리 중입니다. 최신 상태를 확인해 주세요. |
| INVALID_LOGIN_REQUEST | 400 | 로그인 요청 필드가 올바르지 않습니다. |

이름이 확인된 회원 UNIQUE 충돌은 트랜잭션 flush/commit 경계까지 고려하여 변환한다. 북마크 중복은 잠금 후 존재 확인으로 204 처리한다. 잠금 시간 초과·교착 피해 트랜잭션은 롤백하고 CONCURRENT_MODIFICATION으로 반환한다. 예상하지 못한 제약 실패는 500이다. 메시지 문구는 구현의 ErrorCode에서 관리하며 API 호환성 기준은 code/status/errors 구조다.
