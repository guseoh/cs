# DevPedia V1 도메인 이해 가이드

DevPedia는 프로젝트·스터디에 참여할 사람을 모집하고, 지원서를 검토하여 선발 결과를 확인하는 서비스다. V1의 끝은 ‘선발 결과 확인’이다. 실제 팀 운영·채팅·알림은 후속 버전의 후보다. 이 문서는 00~09의 설계를 업무 사례로 설명한다. 세부 필드와 오류 코드는 각각 05와 06, 경계 조건은 09를 기준으로 한다.

## 1. 전체 흐름으로 이해하기

민지는 Spring 프로젝트를 함께할 백엔드 1명과 프론트엔드 1명을 모집한다. 준호와 수아는 백엔드 역할에 지원하고, 지훈은 프론트엔드 역할에 지원한다.

1. 민지가 회원가입·로그인하고 모집글을 만든다.
2. 모집글에 백엔드 정원 1명, 프론트엔드 정원 1명의 모집 역할을 만든다.
3. 준호·수아·지훈이 각각 특정 모집 역할을 선택하여 지원서를 제출한다.
4. 민지가 준호를 승인한다. 백엔드 정원이 차므로 수아의 검토 중 지원은 자동 종료된다.
5. 프론트엔드가 남아 있으므로 모집글은 계속 OPEN이다.
6. 민지가 지훈을 승인하면 모든 역할이 충족되어 글이 CLOSED가 된다.
7. 각 지원자는 본인의 결과를 확인한다. 지원서의 제출 내용과 결과는 기록으로 남는다.

민지도 다른 모집글에서는 지원자가 될 수 있다. ‘모집자’와 ‘지원자’는 회원 등급이 아니라 특정 글·지원서와 맺는 관계다.

## 2. 도메인 지도

| 도메인 | 답하는 질문 | 저장하는 핵심 정보 |
|---|---|---|
| 회원·프로필 | 누가 활동하는가? | 계정, 공개 소개, 관심 역할·기술 |
| 기준정보 | 어떤 분야·기술을 선택할 수 있는가? | 역할과 기술의 공통 선택 목록 |
| 모집 | 무엇을, 언제, 어떤 역할로 몇 명 모집하는가? | 모집글, 역할별 정원, 사용 기술 |
| 지원·선발 | 누가 어떤 역할에 지원했고 어떤 결과를 받았는가? | 제출 내용, 링크 스냅샷, 선발 결과 |
| 댓글 | 모집 내용에 어떤 질문·답변이 오갔는가? | 댓글, 한 단계 답글 |
| 북마크 | 회원이 어떤 글을 다시 보고 싶어 하는가? | 회원과 모집글의 저장 관계 |

인증은 현재 요청자가 누구인지 확인한다. 인가는 그 회원에게 해당 행동이 허용되는지 확인한다. 로그인했더라도 다른 모집자의 지원서를 열람할 수 없다.

## 3. 11개 테이블을 읽는 방법

| 테이블 | 업무 의미 | 예시 |
|---|---|---|
| members | 회원 계정과 공개 프로필 | 민지의 이메일·닉네임·소개 |
| roles | 공통 모집 분야 | 백엔드, 프론트엔드, 스터디원 |
| tech_stacks | 공통 기술 목록 | Java, Spring Boot, React |
| member_interest_roles | 회원의 관심 분야 | 민지 ↔ 백엔드 |
| member_tech_stacks | 회원 프로필의 기술 선택 | 민지 ↔ Java |
| recruitment_posts | 하나의 모집 공고 | Spring 프로젝트 팀원 모집 |
| recruitment_slots | 글 안의 역할별 모집 정원 | 그 글의 백엔드 1명 |
| recruitment_post_tech_stacks | 모집글의 사용 기술 | 해당 모집글 ↔ Spring Boot |
| applications | 특정 역할에 제출한 지원서 한 건 | 준호가 백엔드 역할에 지원 |
| comments | 모집글의 댓글 또는 답글 | ‘주 몇 회 진행하나요?’ |
| bookmarks | 회원이 저장한 모집글 | 준호가 민지의 모집글 저장 |

연결 테이블은 다대다 관계를 풀어 표현한다. 회원은 여러 기술을 선택할 수 있고, 한 기술은 여러 회원에게 선택될 수 있다. 이를 한 컬럼에 쉼표로 저장하지 않고 member_tech_stacks의 여러 행으로 관리한다. 복합 PK는 같은 연결이 두 번 저장되는 것을 막는다.

## 4. Role과 RecruitmentSlot의 차이

Role은 공통 사전의 ‘백엔드’다. RecruitmentSlot은 ‘민지의 특정 모집글에서 백엔드 1명을 뽑는 자리’다. 다른 글이 백엔드 3명을 모집하면 같은 roleId를 사용하지만 slotId와 정원은 다르다.

지원서는 roleId가 아니라 slotId에 연결한다. 그래야 어느 글의 어떤 정원에 지원했는지 알 수 있다. 한 글에서 동일한 roleId를 두 번 등록할 수 없으며 UNIQUE(post_id, role_id)가 이를 보호한다. 작성자는 정원에 자동 포함되지 않는다.

Spring Security의 ROLE_USER는 로그인 회원을 나타내는 기술적 권한이다. DB roles의 백엔드·프론트엔드와는 별개다.

## 5. 모집글 상태와 접수 가능 여부

| 상태/조건 | 의미 | 가능한 행동 |
|---|---|---|
| OPEN + 접수 기간 내 | 모집 관리 중이며 접수 가능 | 수정·지원·선발·마감, 규칙에 따른 댓글 |
| OPEN + 접수 기간 경과 | 신규 접수 종료, 기존 지원 검토 중 | 기존 지원 선발·직접 마감; 신규 지원 불가 |
| CLOSED | 직접 마감 또는 모든 역할 충족 | 조회·북마크·기존 본인 댓글 수정/삭제 |
| REMOVED | 공개에서 제거 | 공개 조회 불가; 권한 있는 지원 이력 조회 |

날짜 경과와 저장 상태는 다르다. V1은 날짜가 지났다는 이유만으로 DB 상태를 자동 변경하지 않는다. acceptingApplications는 글 상태와 서울 기준 날짜에서 계산한다. 역할에 남은 자리가 있는지와 해당 회원이 재지원할 수 있는지는 별도로 판단한다.

지원 마감일 당일까지 접수하며 시작일 당일부터는 접수하지 않는다. 마감일을 지정하지 않았더라도 시작일 조건은 적용한다. CLOSED를 OPEN으로 재개하는 기능은 V1에 없다.

지원 이력이 생기면 모집 역할·정원과 시작일·마감일을 바꿀 수 없다. 지원 당시의 모집 조건을 나중에 변경하는 문제를 막기 위한 제한이다. 제목·본문 등 허용된 필드는 OPEN에서 수정할 수 있다.

## 6. 지원서의 생명주기

지원서는 제출 시 UNDER_REVIEW로 생성되고 아래 네 가지 최종 상태 중 하나로 끝난다. 최종 상태를 다시 검토 중으로 되돌리지 않는다.

| 최종 상태 | 주체 | 상황 |
|---|---|---|
| APPROVED | 모집자 | 해당 지원자를 선발 |
| REJECTED | 모집자 | 해당 지원자를 거절 |
| WITHDRAWN | 지원자 본인 | 검토 중 지원을 철회 |
| AUTO_CLOSED | 서비스 | 역할 충족, 글 마감, 글 공개 제거 |

자동 종료 사유는 ROLE_FILLED / POST_CLOSED / POST_REMOVED다. 한 역할만 찼다면 해당 역할의 검토 중 지원만 종료한다. 다른 역할의 지원서는 계속 검토할 수 있다.

같은 글에 검토 중 지원이 있거나 승인 이력이 있으면 새 지원을 제출할 수 없다. 같은 역할에서 거절된 이력이 있어도 다시 지원할 수 없다. 철회한 사람은 다른 조건을 만족하면 새 지원서를 제출한다. 과거 지원서를 되살리지 않으므로 철회 이력과 새 제출 이력이 각각 남는다.

decidedAt은 검토가 끝난 시각이다. 승인·거절에서는 모집자, 철회에서는 지원자 ID를 decidedByMemberId에 기록한다. 자동 종료는 서비스 처리이므로 처리자 ID가 null이다.

## 7. 스냅샷과 공개 정보

준호가 지원할 때 GitHub 주소 A를 제출한 뒤 프로필 주소를 B로 바꾸더라도, 과거 지원서에는 A가 남는다. 이것이 제출 시점 스냅샷이다. 프로필과 지원서는 목적과 공개 범위가 다르다.

| 정보 | 공개 범위 |
|---|---|
| 닉네임·소개·공개 프로필 링크·관심 분야·기술 | 비회원 포함 공개 |
| 이메일 | 본인 계정/프로필 응답 |
| 비밀번호 해시 | 응답에 포함하지 않음 |
| 지원 동기·제출 링크·개별 지원 결과 | 지원자 본인과 해당 모집자 |
| 역할 정원·승인 인원 집계 | 모집글에서 공개 |

서버는 생략된 지원 링크를 프로필에서 자동 복사하지 않는다. 화면이 프로필 값을 미리 채울 수는 있지만 최종 제출값을 사용자가 확인하고 보내야 한다.

## 8. 공개 제거와 물리 삭제

모집글 제거는 행을 지우는 것이 아니라 REMOVED 상태로 바꾸는 작업이다. 제출 기록과 참조 관계가 남아 있어야 하기 때문이다. 검토 중 지원은 자동 종료하고 기존 승인·거절·철회 결과는 보존한다.

공개 상세와 댓글 목록은 더 이상 조회할 수 없다. 본인의 지원 목록에서는 제거된 글의 상태와 제출 결과를 확인할 수 있고, 모집자도 자기 글의 지원 이력을 볼 수 있다. 내 모집 목록과 북마크 목록에서는 제거된 글을 제외한다. 북마크 연결을 해제하는 것은 가능하다.

댓글의 삭제는 다르다. 답글이 없는 루트와 답글은 물리 삭제한다. 답글이 있는 루트는 내용을 비우고 삭제 표시를 남겨 답글의 맥락을 유지한다. 내용이 제거된 루트에는 새 답글을 달 수 없다. 마지막 답글을 삭제해도 이미 내용 제거된 루트는 유지한다.

## 9. 관계와 무결성이 필요한 이유

applications에는 post_id와 slot_id가 모두 있다. 둘을 각각 존재하는 ID로만 확인하면 다른 글의 슬롯을 잘못 연결할 수 있다. 복합 FK(slot_id, post_id)는 슬롯이 해당 글에 속한다는 사실까지 보장한다. 댓글의 복합 FK(parent_comment_id, post_id)도 부모가 같은 글에 속함을 보장한다. 답글의 답글을 금지하는 규칙은 서비스가 검사한다.

DB는 PK·FK·UNIQUE·CHECK로 행과 참조의 기본 정합성을 지킨다. 정원 이하의 승인 수, 지원 이력에 따른 재지원 허용, 소유권과 날짜처럼 여러 행이나 현재 사용자에 걸친 규칙은 서비스가 담당한다.

마지막 한 자리에 두 승인 요청이 동시에 들어올 수 있다. 두 요청이 모두 ‘현재 0명’이라고 읽는 것을 막기 위해 해당 글의 변경 명령은 동일한 글 행을 먼저 잠그고 최신 상태를 확인한다. 승인·역할 충족·다른 지원 자동 종료·전체 마감은 하나의 트랜잭션으로 성공하거나 함께 취소된다. 구체적인 잠금 순서와 격리 수준은 09를 따른다.

## 10. ERD 읽는 순서

1. [전체 ERD 탐색](ERD_탐색.html)에서 모집글을 찾는다.
2. 모집글의 작성자가 회원에 연결되는 것을 확인한다.
3. 모집 역할을 따라가 공통 역할과 정원을 확인한다.
4. 지원서가 모집글·모집 역할·지원자·처리자에 각각 연결되는 것을 확인한다.
5. 댓글과 북마크가 회원과 모집글 사이에 어떻게 연결되는지 본다.
6. 관심 역할·보유 기술·모집글 기술의 연결 테이블을 읽는다.

논리도는 한국어 업무 속성 중심, 물리도는 SQL 컬럼·타입·NULL 허용 여부 중심이다. 두 도면은 동일한 11개 엔티티와 18개 FK를 표현한다. 각 테이블은 한 번만 나타난다. 청록 실선은 부모 FK가 자식 PK에 포함되는 식별 관계, 분홍 점선은 비식별 관계다. 부모 쪽 막대는 1, 원+막대는 0 또는 1, 자식 쪽 원+갈퀴는 0개 이상이다. 선택 FK가 있는 지원 처리자와 댓글 부모를 특히 구분해서 읽는다.

UQ 표시는 복합 UNIQUE에 참여하는 컬럼도 포함한다. 표시된 컬럼 각각이 단독으로 유일하다는 의미는 아니다. 복합키 조합과 CHECK의 정확한 정의는 [03 데이터 사전](03_데이터베이스_ERD.md)의 DDL을 확인한다.

## 11. 이해 확인 질문

| 질문 | 답 |
|---|---|
| 백엔드 Role과 백엔드 Slot은 같은가? | 공통 분야와 특정 글의 모집 자리이므로 다르다. |
| 마감일이 지나면 자동으로 CLOSED인가? | 아니다. 신규 접수는 막지만 기존 지원 검토는 가능하다. |
| 프로필 링크를 수정하면 과거 지원서도 바뀌는가? | 아니다. 제출값은 스냅샷이다. |
| 글 작성자는 다른 회원의 댓글을 삭제할 수 있는가? | 없다. 댓글 작성자 본인만 가능하다. |
| 한 역할이 차면 모든 역할의 지원이 종료되는가? | 아니다. 충족된 역할만 종료한다. |
| 철회 후 재지원은 이전 지원서 수정인가? | 아니다. 조건을 확인한 뒤 새 지원서를 생성한다. |
| 공개 제거 후 지원 결과가 사라지는가? | 아니다. 권한 있는 개인 이력으로 보존한다. |

구현 작업 단위와 완료 조건은 [08 Slice 계획](08_구현_순서_완료조건.md)을 따른다. 이 가이드는 설계를 설명하며 실제 구현이나 테스트가 완료되었다는 뜻은 아니다.
