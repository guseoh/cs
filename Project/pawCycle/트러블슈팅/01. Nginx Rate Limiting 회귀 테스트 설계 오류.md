# Nginx Rate Limiting 회귀 테스트 설계 오류

AUTH-005에서 실제 문제가 된 것은 Nginx 설정 문법이 아니라 **테스트가 Rate Limiter의 동작을 잘못 가정한 것**이었다.

설정은 `rate=10r/m + burst=5 + nodelay`였는데, 초기 테스트는 이를 “처음 15개 요청은 모두 성공하고 16번째부터 429”인 고정 quota처럼 해석했다. Nginx `limit_req`는 그렇게 동작하지 않기 때문에 정상적인 429가 반복문 중간에 나타나면 테스트가 즉시 실패했다.

---

## 처음 만든 잘못된 테스트

초기 설정은 다음과 같았다.

```nginx
limit_req_zone $binary_remote_addr
    zone=login_per_ip:10m
    rate=10r/m;

location = /api/auth/login {
    limit_req zone=login_per_ip burst=5 nodelay;
    limit_req_status 429;
}
```

그런데 Regression Test는 빠른 로그인 요청 15개를 모두 200으로 기대했다.

```bash
for (( attempt = 1; attempt <= 15; attempt++ )); do
  login_code="$(curl ...)"
  [[ "$login_code" == "200" ]]
done
```

이 테스트에는 다음과 같은 잘못된 모델이 숨어 있었다.

```text
10r/m
→ 10개 허용

burst=5
→ 추가 5개 허용

따라서
1~15번째는 반드시 200
16번째부터 429
```

하지만 Nginx 공식 문서는 `limit_req`를 Leaky Bucket 방식으로 설명한다. `10r/m`은 1분짜리 Counter를 만들어 10개를 먼저 소진시키는 Fixed Window가 아니다. 요청 간격과 excess 상태가 계속 계산되므로 요청을 빠르게 몰아 보내면 15회 안에서도 429가 발생할 수 있다.

> 참고  
> - [Nginx ngx_http_limit_req_module](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)

## CodeRabbit finding

CodeRabbit도 같은 문제를 Functional Correctness finding으로 지적했다.

핵심은 세 가지였다.

```text
15개 요청이 모두 성공한다는 가정을 제거할 것
429가 중간에 나와도 테스트가 종료되지 않게 할 것
실제 limit_req 동작에 맞춰 200 / 429를 분류할 것
```

이 finding은 현재 설정과 Nginx 공식 동작을 대조했을 때 유효했다.

따라서 정책값을 바꾸는 것이 아니라 **테스트가 실제 알고리즘을 검증하도록 수정**했다.

## 테스트 목적을 다시 정의

원래 확인해야 했던 것은 “정확히 몇 번째 요청이 429인가”가 아니었다.

진짜 계약은 다음이었다.

```text
빠른 Public login 요청을 보내면
├─ 일부 요청은 Backend로 정상 전달된다.
└─ 일부 요청은 Edge에서 429로 거절된다.

그리고
429 요청은 Backend까지 전달되지 않는다.
```

그래서 반복 요청의 결과를 Status별로 분류했다.

```bash
case "$login_code" in
  200)
    [[ "$(cat "$body")" == '{"source":"backend"}' ]]
    public_success_count=$((public_success_count + 1))
    ;;

  429)
    [[ "$(cat "$body")" == "$RATE_LIMITED_BODY" ]]
    public_rate_limited_count=$((public_rate_limited_count + 1))
    ;;

  *)
    false
    ;;
esac
```

반복 후에는 특정 성공 개수를 고정하지 않고 다음만 확인했다.

```bash
(( public_success_count > 0 ))
(( public_rate_limited_count > 0 ))
```

이렇게 하면 Timing에 따라 실제 성공 개수가 달라져도 우리가 보장하려는 계약은 안정적으로 검증할 수 있다.

## 429 자체도 같은 반복에서 검증

429 응답은 단순 Status만 확인하지 않았다.

반복 중 실제 429가 발생하면 다음 JSON 계약을 확인한다.

```json
{
  "code": "RATE_LIMITED",
  "message": "로그인 요청이 너무 많습니다. 잠시 후 다시 시도해 주세요.",
  "fieldErrors": []
}
```

또한 다음도 같이 검증한다.

```text
Content-Type: application/json
Strict-Transport-Security
X-Content-Type-Options
X-Frame-Options
X-XSS-Protection
Referrer-Policy
```

즉 Rate Limit이 동작하는지만 보는 것이 아니라 **Edge가 만들어 낸 실제 Public Error Contract**까지 확인하도록 바뀌었다.

## Backend 전달 수 검증도 실제 결과 기반으로 변경

초기 테스트는 Backend Log의 Login 요청 수를 고정 숫자와 비교했다.

```bash
[[ "$backend_login_count" == "31" ]]
```

하지만 이 값도 Public 15회가 모두 성공한다는 잘못된 가정에 의존했다.

수정 후에는 기대값을 실제 성공 요청에서 계산한다.

```text
expected backend login count
=
public_success_count
+
internal_success_count
```

실제 Script도 이 값을 Mock Backend Access Log와 비교한다.

이 검증으로 다음을 직접 증명할 수 있다.

```text
Public 200
→ Backend Log에 존재

Public 429
→ Backend Log에 존재하지 않음

Internal 8081 200
→ Backend Log에 존재
```

Rate Limiting을 넣은 목적이 Backend와 BCrypt까지 도달하는 반복 요청을 줄이는 것이므로, 이 검증이 단순 Status 확인보다 더 직접적인 Evidence다.

## CRLF Header Parsing 문제

후속 검증 과정에서 HTTP Header 값 끝의 Carriage Return도 문제가 될 수 있었다.

HTTP Header는 CRLF로 끝나므로 Shell에서 값을 잘라 비교하면 문자열 끝에 `\r`이 남을 수 있다.

그래서 Header Value를 비교하기 전에 다음처럼 정규화했다.

```bash
actual_value="$(
  grep ... |
  cut -d: -f2- |
  tr -d '\r' |
  sed 's/^ *//'
)"
```

이 변경은 보안 정책 변경이 아니라 Linux CI와 Git Bash 같은 환경에서 HTTP Header 문자열을 안정적으로 비교하기 위한 Test Harness 보정이다.

## 이번 문제의 핵심 교훈

이 문제는 단순한 테스트 코드 실수가 아니다.

근본 흐름은 다음과 같았다.

```text
잘못된 동작 모델
→ 잘못된 Acceptance Criteria
→ 잘못된 테스트 기대값
→ 정상 구현을 실패로 판정
```

Rate Limiter, Cache, Lock, Retry, Queue처럼 **시간과 상태가 개입하는 기술**은 고정된 숫자를 테스트 계약으로 만들기 전에 실제 동작 모델을 먼저 확인해야 한다.

이번 Rate Limiting에서 우리가 지켜야 할 계약은 “몇 번째 요청부터 막는다”가 아니라 다음이다.

```text
정상 요청은 통과한다.
과도한 요청은 429가 된다.
429는 PawCycle JSON 계약을 따른다.
429 요청은 Backend까지 전달되지 않는다.
일반 API와 Internal 8081은 Login Limiter의 영향을 받지 않는다.
```

테스트는 구현의 순간적인 숫자를 외우는 것이 아니라 **시스템이 계속 보장해야 할 행동을 검증해야 한다.**
