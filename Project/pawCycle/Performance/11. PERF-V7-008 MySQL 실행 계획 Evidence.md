## 1. 진단 세션 identity와 read-only 경계

MySQL client는 app01에서 기존 runtime env와 protected password file을 이용해 실행했다. password는 화면에 출력하지 않았다.

접속 뒤 identity 확인 결과:

```text
DATABASE()    = pawcycle_perf_core_10k
CURRENT_USER  = pawcycle_perf_catalog@%
VERSION()     = 26.7.0-cloud
```

처음 세션 상태는 다음이었다.

```text
@@transaction_read_only = 0
@@autocommit            = 1
```

따라서 진단 전에 session만 명시적으로 read-only로 바꿨다.

```sql
SET SESSION TRANSACTION READ ONLY;
```

실제 확인 결과:

```text
+---------------------------------+--------------+
| @@session.transaction_read_only | @@autocommit |
+---------------------------------+--------------+
|                               1 |            1 |
+---------------------------------+--------------+
```

이후 실행한 것은 일반 `SELECT`, `SHOW INDEX`, `INFORMATION_SCHEMA`, `EXPLAIN FORMAT=TREE`, `EXPLAIN FORMAT=JSON` 범위다.

다음은 실행하지 않았다.

```text
EXPLAIN ANALYZE
ANALYZE TABLE
UPDATE HISTOGRAM
CREATE INDEX
ALTER TABLE
DB configuration mutation
```

`EXPLAIN ANALYZE`는 실제 쿼리를 실행하기 때문에 이미 수 초가 걸린 것으로 관측된 목록 SQL을 공유 OCI MySQL DB System에서 다시 강하게 실행하지 않았다.

이 계획에서 실제 진단에 사용한 핵심은 다음이다.

```text
products
→ SKU
→ Inventory
→ GROUP BY temporary table
→ temporary scan
→ Sort
→ 마지막 LIMIT 20
```

즉 `LIMIT 20`이 SQL에 있다고 해서 처음부터 Product 20개만 대상으로 child relation을 붙이는 계획은 아니었다.

또 대표 SKU를 구하는 네 개의 dependent subquery가 같은 패턴을 반복했다.

```text
product_id lookup
→ status ACTIVE filter
→ price, id sort
→ LIMIT 1
```

Review 쪽은 `(product_id, visible, ...)` index lookup이 잡혔고 COUNT는 covering index lookup이었다.

## 8. 실제 JOIN Fan-out Count

메인 Product/Category/Brand/Image/SKU/Inventory join을 집계한 실제 결과:

```text
+----------+-------------+
| products | joined_rows |
+----------+-------------+
|    10000 |       19977 |
+----------+-------------+
```

즉 기본 목록 조건에서 실제로:

```text
10,000 Product
→ 19,977 Product-SKU joined rows
```

가 만들어진다.

이는 첫 실행 계획의 `rows≈108`과 큰 차이가 있다.

단순 비교:

```text
EXPLAIN estimated rows ≈ 108.44
actual joined rows     = 19,977

actual / estimate ≈ 184배
```

`EXPLAIN`의 rows는 실제 실행 행 수가 아니라 estimate이므로 184배라는 값은 “실행 계획 자체가 실제로 184배 느리다”는 뜻이 아니다. **옵티마이저가 GROUP BY 앞의 데이터 규모를 실제보다 매우 작게 보고 있었다**는 뜻이다.

## 9. 대표 SKU / Review subquery 제거 후에도 메인 구조는 유지됐다

대표 SKU와 Review scalar subquery를 모두 제거하고 `has_subscribable`, `purchasable` 집계만 남긴 진단용 쿼리 계획:

```text
-> Limit: 20 row(s)
    -> Sort: p.id DESC, limit input to 20 row(s) per chunk
        -> Table scan on <temporary>
            -> Aggregate using temporary table
                -> Nested loop left join  (cost=559 rows=108)
                    -> Nested loop left join  (cost=413 rows=108)
                        -> Nested loop inner join  (cost=267 rows=48.8)
                            -> Inner hash join (no condition)  (cost=1.1 rows=0.2)
                                -> Filter: (c.`active` = true)  (cost=0.75 rows=1)
                                    -> Table scan on c  (cost=0.75 rows=5)
                                -> Hash
                                    -> Filter: (b.`active` = true)  (cost=0.35 rows=1)
                                        -> Table scan on b  (cost=0.35 rows=1)
                            -> Filter: ((p.brand_id = b.id) and (p.display_status = 'PUBLIC'))  (cost=241 rows=244)
                                -> Index lookup on p using idx_products_category (category_id = c.id)  (cost=241 rows=2442)
                        -> Index lookup on s using idx_skus_product_display (product_id = p.id)  (cost=0.556 rows=2.22)
                    -> Single-row index lookup on i using PRIMARY (sku_id = s.id)  (cost=0.25 rows=1)
```

이 결과가 중요한 이유는 dependent subquery를 제거해도 다음 흐름이 그대로였기 때문이다.

```text
전체 eligible Product
→ SKU/Inventory
→ temporary aggregate
→ sort
→ LIMIT 20
```

따라서 첫 개선 우선순위를 dependent subquery 통합보다 **메인 aggregate 입력 범위 축소**에 두었다.

먼저 Product ID 20개만 고르는 SQL을 EXPLAIN했다.

```text
-> Limit: 20 row(s)
    -> Sort: p.id DESC, limit input to 20 row(s) per chunk
        -> Stream results  (cost=267 rows=48.8)
            -> Nested loop inner join  (cost=267 rows=48.8)
                -> Inner hash join (no condition)  (cost=1.1 rows=0.2)
                    -> Filter: (c.`active` = true)  (cost=0.75 rows=1)
                        -> Table scan on c  (cost=0.75 rows=5)
                    -> Hash
                        -> Filter: (b.`active` = true)  (cost=0.35 rows=1)
                            -> Table scan on b  (cost=0.35 rows=1)
                -> Filter: ((p.brand_id = b.id) and (p.display_status = 'PUBLIC'))  (cost=241 rows=244)

```

여기서는 아직 Product 선택 자체가 `idx_products_category` 중심이고 Sort가 남는다. 즉 page-first만으로 Product access path까지 최적이라고 말할 수는 없었다.

## 11. Page-first 뒤 SKU / Inventory를 붙인 가상 계획

Product page를 derived table로 먼저 materialize하고 outer query에서 SKU/Inventory를 붙인 계획:

```text
-> Sort: base.id DESC
    -> Table scan on <temporary>
        -> Aggregate using temporary table
            -> Nested loop left join  (cost=24.7 rows=0)
                -> Nested loop left join  (cost=13.6 rows=0)
                    -> Table scan on base  (cost=2.5..2.5 rows=0)
                        -> Materialize  (cost=0..0 rows=0)
                            -> Limit: 20 row(s)
                                -> Sort: p.id DESC, limit input to 20 row(s) per chunk
                                    -> Stream results  (cost=267 rows=48.8)
                                        -> Nested loop inner join  (cost=267 rows=48.8)
                                            -> Inner hash join (no condition)  (cost=1.1 rows=0.2)
                                                -> Filter: (c.`active` = true)  (cost=0.75 rows=1)
                                                    -> Table scan on c  (cost=0.75 rows=5)
                                                -> Hash
                                                    -> Filter: (b.`active` = true)  (cost=0.35 rows=1)
                                                        -> Table scan on b  (cost=0.35 rows=1)
                                            -> Filter: ((p.brand_id = b.id) and (p.display_status = 'PUBLIC'))  (cost=241 rows=244)
                                                -> Index lookup on p using idx_products_category (category_id = c.id)  (cost=241 rows=2442)
                    -> Index lookup on s using idx_skus_product_display (product_id = base.id)  (cost=0.566 rows=2.22)
                -> Single-row index lookup on i using PRIMARY (sku_id = s.id)  (cost=0.252 rows=1)
```

이 계획에서 중요한 변화:

```text
Materialize
→ LIMIT 20
→ base scan
→ SKU lookup by base.id
→ Inventory lookup
→ Aggregate
```

즉 SKU/Inventory join이 전체 Product가 아니라 `base` page 뒤로 이동했다.

`cost=24.7`을 실제 시간이나 성능 개선률로 해석하지는 않는다. 이 값은 옵티마이저 내부 비용 추정치다. 이 진단에서 사용한 핵심은 **계획의 데이터 흐름이 바뀌었다는 사실**이다.

## 12. FORCE INDEX(PRIMARY) + STRAIGHT_JOIN counterfactual

Product를 최신 ID부터 먼저 읽을 수 있는지 확인하기 위해 진단용으로만 다음 조건을 강제했다.

```text
FORCE INDEX(PRIMARY)
STRAIGHT_JOIN
ORDER BY p.id DESC
LIMIT 20
```

실제 계획:

```text
-> Limit: 20 row(s)  (cost=8.86 rows=1.9)
    -> Nested loop inner join  (cost=8.86 rows=1.9)
        -> Nested loop inner join  (cost=8.32 rows=1.9)
            -> Filter: (p.display_status = 'PUBLIC')  (cost=6.46 rows=1.9)
                -> Index scan on p using PRIMARY (reverse)  (cost=6.46 rows=19)
            -> Filter: ((c.id = p.category_id) and (c.`active` = true))  (cost=0.00103 rows=1)
                -> Table scan on c  (cost=0.00103 rows=5)
        -> Filter: ((b.id = p.brand_id) and (b.`active` = true))  (cost=467e-6 rows=1)
            -> Table scan on b  (cost=467e-6 rows=1)
```

기존 계획과 달리 Product에서 다음 접근이 나타났다.

```text
Index scan on p using PRIMARY (reverse)
```

즉 최신 Product 후보를 id 역순으로 앞에서부터 읽는 counterfactual이 가능했다.

## 13. STRAIGHT_JOIN 제거 후에도 PRIMARY reverse 유지

`STRAIGHT_JOIN`의 영향과 `FORCE INDEX(PRIMARY)`의 영향을 분리하기 위해 `STRAIGHT_JOIN`만 제거했다.

실제 결과:

```text
-> Limit: 20 row(s)  (cost=8.87 rows=1.9)
    -> Nested loop inner join  (cost=8.87 rows=1.9)
        -> Nested loop inner join  (cost=7 rows=1.9)
            -> Filter: (p.display_status = 'PUBLIC')  (cost=6.46 rows=1.9)
                -> Index scan on p using PRIMARY (reverse)  (cost=6.46 rows=19)
            -> Filter: ((b.id = p.brand_id) and (b.`active` = true))  (cost=458e-6 rows=1)
                -> Table scan on b  (cost=458e-6 rows=1)
        -> Filter: ((c.id = p.category_id) and (c.`active` = true))  (cost=0.00105 rows=1)
            -> Table scan on c  (cost=0.00105 rows=5)
```

따라서 이번 조건에서:

```text
STRAIGHT_JOIN 없이도
PRIMARY reverse scan 유지
```

가 확인됐다.

다만 이것은 `FORCE INDEX`를 운영 코드에 넣으라는 결론이 아니다. **다른 접근 경로가 존재하고 page selection을 최신 ID 중심으로 만들 수 있다는 진단 근거**로 사용했다.

## 15. 왜 첫 correction에 FORCE INDEX를 포함하지 않는가

진단에서는 `FORCE INDEX(PRIMARY)`가 분명히 plan shape을 바꿨다.

하지만 실제 API는 기본 무필터 NEWEST만 존재하는 것이 아니다.

```text
q
petType
category / subcategory
brand
facet
min/max price
subscribable
purchasable
```

같은 filter 조합이 있다.

어떤 filter에서는 category나 다른 접근 경로가 유리할 수 있다. 따라서 다음을 동시에 적용하면 어떤 변경이 효과를 냈는지 분리하기 어려워진다.

```text
page-first
+ FORCE INDEX
+ new index
+ histogram
```

PCC의 최소 변경 원칙에 따라 첫 단계는:

```text
KEEP
page-first for NEWEST / RECOMMENDED

DEFER
FORCE INDEX(PRIMARY)
new index
histogram
representative SKU consolidation
```

로 제한했다.

## 16. Evidence에서 직접 도출한 현재 판단

### 확인된 사실

```text
1. I10K eligible Product는 10,000개다.
2. Product-SKU join row는 실제 19,977개다.
3. 기존 plan은 SKU join 뒤 rows≈108 수준으로 예상했다.
4. 기존 List SQL은 Aggregate/Sort 뒤에 LIMIT 20을 적용한다.
5. representative/review subquery를 제거해도 메인 Aggregate 구조는 유지됐다.
6. page-first plan은 LIMIT 20 뒤에 SKU/Inventory lookup을 배치했다.
7. PRIMARY reverse scan이 가능한 counterfactual을 확인했다.
8. STRAIGHT_JOIN은 그 counterfactual에 필요하지 않았다.
9. full projection page-first에서도 page-scoped child lookup 구조가 유지됐다.
```

### 아직 확정하지 않은 것

```text
Histogram을 만들면 실제 latency가 얼마나 줄어드는가
신규 index가 필요한가
FORCE INDEX가 모든 filter 조합에서 안전한가
representative SKU subquery 통합 효과가 얼마나 큰가
page-first correction 뒤 실제 25 RPS가 통과하는가
Host evidence collector timeout이 application saturation 때문인가
```

따라서 현재 Root Cause 표현은 다음 수준으로 제한한다.

> **I10K에서 Product 목록 SQL이 page LIMIT 전에 큰 Product-SKU 집계 작업을 수행했고, 이 List query의 장기 Connection lease가 Hikari queueing을 증폭시킨 것이 현재 가장 강한 failure mechanism이다. Page-first plan은 해당 집계 범위를 페이지 단위로 줄일 수 있음을 read-only EXPLAIN으로 확인했다. 실제 개선 효과는 correction 후 동일 I10K 25 RPS 재측정으로 검증해야 한다.**
