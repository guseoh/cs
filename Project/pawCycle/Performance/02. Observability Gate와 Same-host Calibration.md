# Observability Gate와 Same-host Calibration

일반 개념은 [[../../../Study/Performance/03. Observability와 계층별 병목 분리|Observability와 계층별 병목 분리]]와 [[../../../Study/Performance/08. Observer Effect와 Same-host Calibration|Observer Effect와 Same-host Calibration]]에서 다룬다.

이 문서는 PawCycle OCI Production에서 실제로 수행한 Gate와 측정 결과만 기록한다.

## Calibration 해석 경계

이 실험은 capacity test가 아니다.

30 samples × 3구간의 짧은 calibration이므로 p99/max는 outlier 영향을 크게 받는다. 따라서 이번 판정은 다음 증거를 함께 사용했다.

~~~text
HTTP error 0
p50/p95 방향
CPU headroom
iowait
swap in/out
OOM/restart
Application identity
Observability runtime stability
~~~

이 결과로 “OCI 최대 처리량”이나 “Production capacity”를 주장하지 않는다.

## 이 측정이 무엇을 검증한 것인지 다시 설명하면

이 실험의 목적은 “Prometheus와 Grafana가 켜진 상태의 최대 RPS”를 찾는 것이 아니었다.

PawCycle은 Application과 Observability가 같은 app01 Compute를 공유하고 있다. 따라서 성능 측정을 시작하기 전에 **관측 도구 자체가 Application 성능을 크게 흔들지 않는지** 먼저 확인해야 했다.

쉽게 말하면 다음 질문이었다.

~~~text
Prometheus / Grafana를 켜두면
Application 응답 시간이 눈에 띄게 나빠지는가?

CPU나 memory를 너무 많이 가져가
실제 성능 측정을 왜곡하는가?
~~~

그래서 ON → OFF → ON 구조를 사용했다.

## Production READY는 무엇을 뜻했는가

Production READY는 단순히 HTTP 200 하나를 뜻하지 않았다.

당시 진단기는 Application과 운영 상태가 성능 실험을 시작해도 될 만큼 안정적인지 여러 조건을 확인했다.

~~~text
release coordination 정상
Docker 상태 조회 가능
Backend healthy
상품 API 200
metrics-proxy 200
~~~

이 조건이 먼저 통과해야 이후 p95나 CPU 수치를 성능 근거로 사용할 수 있었다.

Production 상태가 UNKNOWN인데 바로 부하를 넣으면 “부하 때문에 느려진 것인지 이미 운영 상태가 비정상이었는지”를 구분하기 어렵기 때문이다.

## Observability NORMAL은 무엇을 뜻했는가

Observability NORMAL은 Prometheus Container가 떠 있다는 뜻만이 아니다.

~~~text
Production READY
+
Prometheus 자체 readiness 정상
+
Backend metric target = UP
~~~

을 함께 확인했다.

Prometheus Target이 UP이라는 것은 성능 실험 중 Backend metric을 실제로 가져올 수 있다는 뜻이다.

실험이 끝난 뒤 Target이 DOWN이었다는 사실을 알게 되면 CPU, JVM, Hikari 같은 내부 원인 근거가 비어버릴 수 있다.

## p50, p95, p99를 이 실험에서 어떻게 읽었는가

각 window는 HTTP sample 30개뿐이었다.

이 정도 표본에서 p99는 사실상 가장 느린 한두 요청의 영향을 크게 받는다.

그래서 다음처럼 해석했다.

~~~text
p50
→ 중앙적인 응답 시간 변화

p95
→ 느린 구간의 방향 확인

p99 / Max
→ 일회성 이상치 참고
~~~

Initial ON에서 p99가 277ms이고 Restored ON에서 57ms라고 해서 “관측 도구를 다시 켜니 p99가 220ms 개선됐다”고 해석하지 않았다.

표본이 작기 때문에 p99는 calibration의 주 판정 지표로 쓰기 어렵다.

일반적인 백분위 해석은 [[../../../Study/Performance/07. Latency Percentile과 Tail Latency|응답 시간 백분위와 꼬리 지연]]에서 자세히 설명한다.

## 왜 OFF와 Restored ON을 최종 비교했는가

Initial ON은 historical approved source에서 실행 중이었다.

OFF 뒤 Observability를 복구할 때는 최신 승인 SHA의 exact source로 다시 올렸다.

따라서 최종적으로는 다음 두 구간을 비교했다.

~~~text
OFF
→ 관측 도구 없음

Restored ON
→ latest approved SHA로 관측 도구 복구
~~~

이렇게 해야 앞으로 실제 성능 측정에 사용할 정상 상태와 OFF 상태를 직접 비교할 수 있다.

## p95 +1.167ms를 어떻게 해석했는가

OFF에서 p95는 31.810ms였고 Restored ON에서는 32.977ms였다.

차이는 약 1.167ms다.

이 수치 하나만 보고 “Observability overhead는 1.167ms다”라고 단정하지 않았다.

이유는 sample 수가 작고 각 요청의 자연 변동이 있기 때문이다.

대신 다음 근거를 같이 봤다.

~~~text
HTTP error
0 → 0

p50
23.016 → 23.442ms

p95
31.810 → 32.977ms

CPU user + system
약 2.475% → 3.204%

I/O wait
0 → 0

Restart / OOM
없음
~~~

응답 시간과 CPU가 조금 증가했지만 Application 안정성을 깨뜨리거나 capacity 해석을 불가능하게 만들 수준의 신호는 보이지 않았다.

## CPU +0.73%p는 왜 허용 가능하다고 봤는가

OFF의 user+system CPU 평균은 약 2.475%, Restored ON은 약 3.204%였다.

차이는 약 0.73 퍼센트포인트다.

여기서 중요한 것은 상대 증가율만 보는 것이 아니다.

Host CPU idle은 두 구간 모두 약 97% 수준이었다.

~~~text
CPU가 2.5% → 3.2%
→ 절대 사용량 자체가 낮음
→ 여전히 약 97% idle
~~~

즉 관측 도구가 CPU를 조금 더 사용했지만 당시 Host의 CPU 여유를 의미 있게 잠식하지 않았다.

이런 “남은 여유”를 Headroom이라고 부른다.

## Memory 감소는 왜 바로 문제로 보지 않았는가

Observability ON에서는 MemAvailable이 OFF보다 약 227~259MiB 낮았다.

Prometheus와 Grafana가 실행 중이므로 memory를 더 사용하는 것은 자연스럽다.

중요한 것은 그 결과 Application에 pressure가 생겼는지다.

당시:

~~~text
Swap activity 없음
I/O wait 0
Application error 0
Container restart 0
OOMKilled false
~~~

였다.

따라서 “memory를 사용했다”는 사실은 확인했지만 “그 memory 사용 때문에 Application 성능이 나빠졌다”는 근거는 없었다.

## KEEP와 DEFER 판정의 의미

최종 결론은 다음과 같았다.

~~~text
same-host Observability
= KEEP

separate Observability Compute
= DEFER
~~~

KEEP은 같은 Host에 두는 구조가 완벽하다는 뜻이 아니다.

현재 측정 조건에서는 관측 도구의 간섭이 작고 Host 여유도 충분해 **지금 당장 별도 Compute로 분리할 근거가 부족하다**는 뜻이다.

DEFER는 별도 Compute가 나쁜 선택이라는 뜻이 아니다.

앞으로 부하가 커지거나 Prometheus/Grafana가 CPU, memory, I/O를 의미 있게 잠식하는 근거가 생기면 다시 검토한다.

개념적인 판단 기준은 [[../../../Study/Performance/08. Observer Effect와 Same-host Calibration|관측자 효과와 같은 서버 보정 실험]]에 정리한다.
