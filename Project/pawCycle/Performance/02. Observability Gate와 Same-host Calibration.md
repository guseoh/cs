# Observability Gate와 Same-host Calibration

## 왜 부하 테스트보다 먼저 Observability를 확인했는가

성능 문제는 결과 숫자만으로 원인을 알 수 없다. 응답 시간이 느려졌을 때 Host CPU인지, container memory인지, JVM/Tomcat인지, HikariCP 대기인지, DB인지 구분할 근거가 필요하다.

그래서 PawCycle은 실제 Re-baseline보다 먼저 다음 Gate를 요구했다.

~~~text
Production Backend 정상
+ metrics-proxy 정상
+ Prometheus target up
+ Production READY
+ Observability NORMAL
~~~

이 Gate의 목적은 관측 도구를 구축했다는 사실을 증명하는 것이 아니라 **실제 성능 실험에서 실패 계층을 분리할 수 있는가**를 확인하는 것이다.

## same-host를 먼저 유지한 이유

Prometheus와 Grafana를 Application과 별도 Compute에 두면 failure domain은 분리할 수 있지만 비용, network, security와 운영 복잡도가 늘어난다.

PawCycle은 먼저 같은 app01에서 운영하고 실제 오버헤드를 측정한 뒤, 문제가 근거로 확인될 때만 별도 Compute를 검토하기로 했다.

~~~text
same-host 운영
→ 실제 CPU / memory / HTTP 영향 측정
→ 문제가 작으면 KEEP
→ 측정 왜곡이나 memory pressure가 재현되면 분리 재검토
~~~

## 실험 조건

승인 main과 최종 restored runtime provenance:

~~~text
df74023e96a3afe37219ecd50d48adac8b7b3c60
~~~

세 구간 모두 다음 조건을 최대한 동일하게 유지했다.

- 2 CPU host
- /api/products read-only 요청 30회
- 요청 간격 2초
- 약 60초 vmstat 1 60
- free -b, root filesystem, docker stats --no-stream
- Application runtime identity 확인
- OOM / restart 확인
- Backend, Frontend, Nginx, Managed MySQL, release SHA는 변경하지 않음

## Memory 비용

same-host의 비용이 없는 것은 아니다.

OFF MemAvailable:

~~~text
start 4,129,521,664 bytes
end   4,144,447,488 bytes
~~~

Restored ON MemAvailable:

~~~text
start 3,891,687,424 bytes
end   3,872,800,768 bytes
~~~

OFF 대비 Restored ON에서 host MemAvailable은 약 227~259 MiB 줄었다.

Restored ON container snapshot:

- Grafana: 약 216.9 MiB / 256 MiB
- Prometheus: 약 49.62 MiB / 384 MiB
- metrics-proxy: 약 4.7~4.9 MiB / 32 MiB

즉 **same-host Observability의 memory 비용은 명확히 존재**한다.

다만 해당 window에서 OOM, container restart, 지속적인 swap-in, I/O wait, HTTP 오류 증가는 확인되지 않았다.

## 판정

~~~text
same-host Observability = KEEP
separate Observability Compute = DEFER
same-host overhead calibration Gate = PASS
runtime 측면 Performance Measurement Ready = PASS
~~~

이 결론은 “별도 Compute가 필요 없다”는 영구 결론이 아니다. 현재 측정 근거에서는 비용과 복잡성을 추가할 이유가 부족하다는 의미다.

다음 상황이 재현되면 다시 검토한다.

- Grafana가 memory limit 근처에 지속적으로 머무름
- OOM 또는 restart 발생
- 지속적 swap-in
- steady-state 높은 I/O wait
- Observability ON에서 재현 가능한 latency / error 악화
- Application 성능 실험 자체가 관측 도구 자원 사용 때문에 흔들림

## 근거의 한계

이 실험은 capacity test가 아니다.

60초와 30개의 read-only request로 정상 상태 오버헤드를 짧게 확인한 calibration이다. 따라서 여기서 “최대 처리량에 영향이 없다”거나 “고부하에서도 안전하다”고 확장해서 말하지 않는다.

Canonical 실행 기록은 [PERF-V7-001 Issue #300](https://github.com/guseoh/pawcycle-commerce/issues/300)에 있다.
