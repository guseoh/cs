# I0 25→150 RPS Re-baseline과 첫 처리 용량 경계 구간

이 문서는 PawCycle Commerce의 **대규모 데이터·대규모 트래픽 성능 단계**에서 실제 OCI 환경을 사용해 Catalog I0 기준선을 다시 측정한 과정과 첫 처리 용량 경계 구간을 기록한다.

이번 작업의 목적은 “높은 RPS 숫자”를 만드는 것이 아니었다. Product 32개인 작은 기준 Dataset에서 요청률만 단계적으로 올리면서 현재 단일 Backend 구조가 어디에서 압박받기 시작하는지 찾고, 이후 I10K 10,000 Product Dataset과 동일 조건으로 비교할 수 있는 기준선을 만드는 것이 목적이었다.

일반 개념은 [[../../../Study/Performance/14. 단계적 부하 증가와 처리 용량 경계 판정]]에서 설명한다. 이 문서에서는 PawCycle에서 실제로 사용한 조건, 실패, 잘못된 가설, 수정, 측정값과 현재 판정만 기록한다.

## 1. 이번 측정이 전체 프로젝트에서 차지하는 위치

PawCycle 성능 단계는 요청 부하와 데이터 규모를 분리한다.

```text
Request Load
25 → 50 → 100 → 150 → 200 → 250 ...

Dataset Scale
I0   = Product 32
I10K = Product 10,000
이후 필요 시 100K / 1M
```

이번 측정은 첫 번째 축의 기준선이었다. I0 Dataset을 고정하고 `GET /api/products` 요청률만 올렸다.

I0에서 한계를 찾고 원인을 개선한 뒤 I10K에서 같은 workload를 반복하면 “요청이 많아져서 느려진 것”과 “데이터가 많아져서 느려진 것”을 분리할 수 있다.

상위 작업은 `PERF-V7-002`이고, 단일 stage 실행과 단계별 승인 경계는 `PERF-V7-005`에서 정리됐다. 당시 자동으로 `25 → 50 → 100 → ...` 전체를 연속 실행하지 않고, **한 stage 측정 → 증거 검토 → 사용자 승인 → 다음 stage** 순서로 실행하도록 runner를 수정했다.

- [PERF-V7-002 Issue #302](https://github.com/guseoh/pawcycle-commerce/issues/302)
- [PERF-V7-005 Issue #312](https://github.com/guseoh/pawcycle-commerce/issues/312)
- [PR #313 - single-stage capacity runs](https://github.com/guseoh/pawcycle-commerce/pull/313)

측정 Source는 다음 canonical main이었다.

```text
ad4e4ed703cc48aca53b46a31858d400a8096781
```

이 SHA에는 `PERF-V7-005` 단일 stage 실행 지원이 포함되어 있다.

## 2. 실험 조건

이번 기록의 수치를 비교할 수 있는 이유는 부하 외 조건을 고정했기 때문이다.

| 항목 | 조건 |
| --- | --- |
| Dataset | `catalog-core-control-v1` |
| Product | 32 |
| SKU | 42 |
| Backend Source | exact approved SHA `ad4e4ed...` |
| Endpoint | `GET /api/products` |
| Load Model | k6 `constant-arrival-rate` |
| Warm-up | 30초 |
| Measurement | 120초 |
| RPS 단계 | 25 → 50 → 100 → 150 |
| Backend 노출 | app01 loopback-only isolated runtime |
| DB | 별도 performance schema/account |
| DB System | Production과 같은 OCI MySQL DB System 공유 |
| Evidence | Host / Container / JVM / Tomcat / Hikari / OCI MySQL |

여기서 중요한 점은 **데이터 격리(Data Isolation)는 되어 있지만 자원 격리(Resource Isolation)는 아니라는 것**이다.

Backend runtime은 별도로 띄우고 performance schema/account를 사용했지만 app01 Host와 OCI MySQL DB System은 Production과 공유했다. 따라서 Host와 DB System 전체 Metric은 성능 테스트 요청만의 사용량으로 단정하지 않고, stage별 추세와 Application 내부 Metric을 함께 해석했다.

실제 Secret, OCI OCID, DB endpoint, SSH key 내용, raw Production row는 기록하지 않는다.

## 3. 실제 부하 전에 Source와 Dataset을 다시 맞춘 이유

단일 stage runner가 main에 병합되면서 approved Source SHA가 기존 성능 준비 시점과 달라졌다. Dataset 내용 자체는 바뀌지 않았지만 provenance에는 이전 SHA가 기록되어 있었다.

read-only 검증 결과는 다음 흐름이었다.

```text
Dataset manifest / report 내용
→ 이전 Source와 새 Source에서 동일

provenance.approvedSourceSha
→ 이전 SHA를 가리킴

validator
→ source identity mismatch로 fail-closed
```

여기서 Dataset을 다시 만들거나 validator를 약화하지 않았다. 기존 provenance만 안전하게 백업한 뒤 exact 새 Source를 기준으로 provenance를 재생성했고 전체 preflight를 다시 통과시켰다.

이 과정에서 배운 점은 **데이터 내용이 같다는 사실과 어떤 Source에서 그 데이터가 검증되었는가는 다른 문제**라는 것이다. 성능 수치가 나중에 재현 가능하려면 Dataset과 Source identity를 같이 보존해야 한다.

관련 기존 기록은 [[08. I0 Dataset Provenance와 Root-owned 경로 Drift]]에 있다.

## 4. PowerShell을 기준으로 실행하면서 생긴 Shell 경계 문제

실제 부하 실행 단계에서는 성능 문제가 아니라 Windows PowerShell, Git Bash, Windows OpenSSH, 원격 Linux가 만나는 경계에서 여러 문제가 발생했다.

이 부분은 단순한 명령 오류처럼 보이지만 재현 가능한 운영 도구를 만들 때 중요한 교훈이 있어 실패 과정까지 남긴다.

### 4.1 `export`를 PowerShell에서 사용한 문제

처음 안내에는 다음 형태가 포함됐다.

```bash
export PAWCYCLE_PERF_OCI_COMPARTMENT_ID=...
export PAWCYCLE_PERF_OCI_DB_SYSTEM_ID=...
```

하지만 사용 환경은 PowerShell이었다. PowerShell 환경 변수는 다음과 같이 설정해야 한다.

```powershell
$env:PAWCYCLE_PERF_OCI_COMPARTMENT_ID = ...
$env:PAWCYCLE_PERF_OCI_DB_SYSTEM_ID = ...
```

두 값은 Secret이 아니라 OCI Monitoring에서 대상 Compartment와 MySQL DB System을 선택하는 리소스 식별자였다. 그래도 프로젝트 정책상 실제 식별자 값은 문서에 남기지 않고, OCI CLI Resource Search 결과에서 로컬 환경 변수로 직접 주입했다.

재발 방지 기준은 단순하다.

> 사용자가 PowerShell을 기준 셸로 지정하면 사용자에게 보이는 명령은 PowerShell을 기준으로 작성하고, Bash는 기존 `.sh` runner를 실행하는 내부 실행 엔진으로만 사용한다.

### 4.2 WSL 경로를 Git Bash에 사용한 문제

Desktop exact Source를 만들 때 처음에는 다음과 같은 WSL 경로를 가정했다.

```text
/mnt/c/Users/...
```

실제 셸은 Git Bash였고 Git for Windows가 이를 `C:/Program Files/Git/mnt/c/...`처럼 해석해 Git repository를 찾지 못했다.

Git Bash에서는 Windows C drive를 다음처럼 사용해야 했다.

```text
/c/Users/...
```

또한 첫 시도는 pipeline 중간 실패 뒤에도 마지막 `echo PASS`가 실행될 수 있는 구조였다. 이후 `set -Eeuo pipefail`을 적용해 중간 실패가 성공 메시지로 가려지지 않도록 했다.

### 4.3 PowerShell에서 `bash -lc`로 긴 문자열을 넘기며 quoting이 깨짐

처음에는 PowerShell 문자열에 여러 줄 Bash 명령을 넣고 다음처럼 실행하려 했다.

```powershell
& $GitBash -lc $BashCommand
```

그 결과 Bash의 `$(date ...)` 부근에서 다음 오류가 발생했다.

```text
unexpected EOF while looking for matching `)'
```

PowerShell → Windows process argument → Bash parser를 거치는 동안 긴 multi-line command의 quoting 경계가 불안정해진 것이 문제였다.

수정은 복잡한 escaping을 더 추가하는 대신 **UTF-8 BOM 없는 임시 `.sh` 파일을 만들고 Git Bash가 파일 자체를 실행하게 하는 방식**으로 단순화했다.

```text
PowerShell
→ 임시 run-i0-25.sh 작성
→ Git Bash가 파일 실행
→ canonical run-isolated-capacity.sh 호출
```

이후 50, 100, 150 RPS는 이전 stage 스크립트를 복사하고 `--target-rps`만 변경해 같은 실행 경로를 유지했다.

## 5. SSH와 MSYS 경로 변환 트러블슈팅

### 5.1 Git Bash SSH가 기존 Windows OpenSSH 키 경로를 사용하지 못함

runner는 Host evidence collector를 원격 app01에서 실행하기 위해 내부적으로 `ssh`를 호출한다.

PowerShell에서 Windows OpenSSH로 직접 접속할 때는 정상인데, Git Bash 내부 `ssh`에서는 다음과 같은 인증 실패가 발생했다.

```text
Permission denied (publickey,...)
Host evidence collector did not start
```

처음에는 SSH alias의 `IdentityFile` 경로만 수정했지만 해결되지 않았다. 원인은 “키가 틀렸다”기보다 **PowerShell에서 성공한 Windows OpenSSH와 Git Bash의 OpenSSH가 서로 다른 실행 경로·설정을 사용한다는 점**이었다.

해결은 Git Bash 안에 작은 `ssh` wrapper를 두고 실제 접속은 이미 검증된 Windows OpenSSH가 수행하게 하는 것이었다.

이때 중요한 원칙은 새 SSH 설정을 계속 늘리는 것이 아니라 **이미 정상 동작한 경로를 재사용한 것**이다.

### 5.2 원격 Linux `/opt/...` 경로가 `C:/Program Files/Git/...`로 변환됨

Windows OpenSSH wrapper를 사용한 뒤에는 인증은 통과했지만 원격 Python에서 다음 형태의 오류가 발생했다.

```text
python3: can't open file '/home/opc/C:/Program': ...
```

runner가 원격 Linux의 `/opt/pawcycle-performance/...` 경로를 인자로 넘겼는데, Git Bash의 MSYS argument conversion이 이 값을 Windows 로컬 경로로 자동 변환한 것이 원인이었다.

수정은 wrapper에서 다음 경계를 명시한 것이다.

```bash
MSYS_NO_PATHCONV=1
MSYS2_ARG_CONV_EXCL='*'
```

이후 `/opt/...`는 원격 Linux 경로 그대로 Windows OpenSSH에 전달됐다.

이 트러블슈팅의 핵심 교훈은 다음과 같다.

> Windows에서 Bash 도구와 native Windows executable을 섞으면 “문자열 그대로 전달될 것”이라고 가정하지 않는다. MSYS의 자동 경로 변환 여부를 확인한다.

## 6. Evidence 수집 실패는 부하 실패와 분리했다

각 stage runner는 대략 다음 순서로 동작한다.

```text
원격 Host/JVM/Hikari collector 시작
→ k6 부하 실행
→ collector 종료
→ OCI MySQL metric 포함 evidence 조립
```

따라서 collector가 시작하지 못하면 k6를 실행하지 않고 중단한다. 실제로 100 RPS 첫 시도에서 `Host evidence collector did not start`가 발생했을 때는 **100 RPS 부하 자체는 시작되지 않았다.**

이때 전체 설정을 다시 구성하지 않고, 원격 collector를 짧게 직접 실행해 실제 stderr와 runtime 상태를 확인한 뒤 같은 100 RPS stage만 재실행했다.

또 25, 50, 100, 150 RPS에서 k6 summary와 host JSONL은 존재하지만 최종 evidence JSON이 자동 생성되지 않은 경우가 있었다. 이때도 부하를 다시 넣지 않았다.

기존 파일을 이용해 다음 assemble 단계만 수행했다.

```text
k6 summary
+ host/JVM/Tomcat/Hikari samples
+ OCI MySQL Monitoring
→ evidence.json
```

이 방식으로 **측정값을 재사용하고 불필요한 재부하를 피했다.** 공유 Host/DB System에 반복 부하를 넣지 않는다는 운영 안전성 측면에서도 중요했다.

## 7. PowerShell `$Host` 예약 변수 충돌

수동 evidence assemble 과정에서 다음 변수명을 사용했다.

```powershell
$Host = Join-Path ...
```

PowerShell의 `$Host`는 현재 PowerShell Host 객체를 나타내는 읽기 전용 자동 변수다. 따라서 덮어쓸 수 없었고, Python에는 파일 경로 대신 다음 문자열이 전달됐다.

```text
System.Management.Automation.Internal.Host.InternalHost
```

결과적으로 Python은 존재하지 않는 파일을 찾으려 했다.

수정은 변수명을 의미가 명확한 다음 이름으로 바꾸는 것이었다.

```powershell
$HostSamplesPath
```

이 실패는 단순한 이름 충돌이지만, PowerShell 자동 변수와 사용자 변수의 경계를 모르면 오류 메시지가 Python 파일 경로 문제처럼 보일 수 있다는 점이 중요했다.

50 RPS에서도 목표 처리량을 거의 정확하게 따라갔다.

```text
Actual RPS              49.975

p95                     144.79 ms

```

내부 지표도 여유가 컸다.

```text
Host CPU avg            7.69%

Hikari pending max      0

```

## 10. 100 RPS — 첫 Hikari 압박 신호

100 RPS에서도 workload의 hard threshold는 통과했다.

```text
Actual RPS              99.958
Dropped                 0
Error                   0
p50                     66.12 ms
p95                     155.89 ms
p99                     642.69 ms
max                     988.87 ms
```

하지만 내부에서는 처음으로 Hikari가 한 번 maximumPoolSize에 도달했다.

```text
Tomcat busy max         15 / 200
Hikari active max       10 / 10
Hikari pending max      4
Hikari acquire avg      0.102 ms
Hikari usage avg        8.593 ms
```

Host CPU는 평균 10.08%, Container CPU는 평균 8.18%, MySQL CPU는 평균 39.26% / 최대 42.94%였다. CPU 포화와 Tomcat Thread 포화는 아니었다.

Hikari sample을 추가로 확인했다.

```text
Total samples     19
Pending samples    1
Full-pool samples  1
Pending max        4
```

19개 샘플 중 1개에서만 발생했으므로 **지속적인 Connection Pool 포화라고 단정하지 않았다.**

판정:

```text
I0 / 100 RPS = PASS
Watch = Tail latency + transient Hikari pressure
```

이 단계에서 바로 Hikari Pool을 늘리지 않고 150 RPS에서 같은 신호가 재현되는지 확인하기로 했다.

## 11. 150 RPS — 첫 명확한 실패와 Capacity Boundary 구간

150 RPS에서는 처음으로 canonical threshold가 깨졌다.

k6 결과:

```text
Actual RPS              149.233
Dropped                 34
Error                   0
p50                     66.98 ms
p95                     1,205.59 ms
p99                     1,893.77 ms
max                     2,914.38 ms
Active VUs              270
```

`dropped_iterations > 0`이므로 150 RPS는 PASS가 아니다.

더 중요한 것은 지연 분포다.

```text
100 → 150 RPS

p50    66.12ms →   66.98ms   거의 동일
p95   155.89ms → 1205.59ms   약 7.7배
p99   642.69ms → 1893.77ms   약 2.9배
max   988.87ms → 2914.38ms   약 2.9배
```

절반의 요청은 여전히 약 67ms에 끝났지만 일부 요청이 초 단위로 밀리기 시작했다. 전체 요청이 느려진 것이 아니라 **Tail Latency가 무너지면서 동시 실행 중 요청이 쌓이는 패턴**이었다.

## 12. 150 RPS 내부 지표 — CPU보다 Connection Queue가 먼저 커졌다

150 RPS evidence는 다음과 같았다.

```text
Host CPU avg            13.017%
Host CPU max            14.286%
Host iowait max          0.082%
Container CPU avg       11.935%
Container CPU max       14.72%
Heap max                135.2 MiB
GC pause total          219 ms
Tomcat busy max         43 / 200

Hikari active max       10 / 10
Hikari pending max      32
Hikari acquire avg      5.806 ms
Hikari usage avg        13.857 ms

MySQL CPU avg           44.369%
MySQL CPU max           53.918%
MySQL active conn max   5
```

CPU, iowait, Tomcat Thread는 여전히 크게 남아 있었다. 반면 Hikari는 maximumPoolSize 10에 도달했고 waiting 수요가 최대 32까지 발생했다.

100 RPS와 비교하면 변화가 더 명확하다.

```text
Hikari acquire avg
0.102 ms → 5.806 ms
약 57배 증가

Hikari usage avg
8.593 ms → 13.857 ms
약 1.6배 증가
```

Connection을 실제로 사용하는 시간도 늘었지만, **Connection을 얻기 위해 기다리는 시간이 훨씬 가파르게 증가**했다.

샘플 빈도도 확인했다.

```text
100 RPS
Pending samples    1 / 19
Full pool samples  1 / 19
Pending max        4

150 RPS
Pending samples    3 / 19
Full pool samples  2 / 19
Pending max        32
```

100 RPS의 단발성 신호가 150 RPS에서 더 강하게 재현됐다.

현재 가장 강한 병목 후보는 다음과 같다.

```text
DB connection path / Hikari queueing
```

## 13. 하지만 “Pool 10이 작다”라고 결론 내리지 않은 이유

Hikari pending이 32까지 올라갔다고 해서 `maximumPoolSize=10`을 바로 20으로 늘리지 않았다.

첫째, pending은 결과다. 원인은 다음처럼 여러 가지일 수 있다.

```text
Pool 자체가 작음
SQL이 느림
Lock 대기
Transaction이 Connection을 오래 점유
동시 DB 접근의 순간 Burst
```

둘째, PawCycle에는 이미 관련 historical evidence가 있었다. Phase 9 local-only 실험에서 Hikari maximum pool을 10에서 20으로 늘렸을 때 처리량이 개선되지 않고 오히려 악화된 기록이 있다.

현재 main의 `PERF-PH9-014-phase9-conclusion.md`도 다음 결론을 남긴다.

```text
Hikari 10→20에서 처리량 악화
→ connection pool capacity 확대를 해법에서 제외
→ 높은 pending만으로 DB capacity 병목을 단정하지 않음
```

따라서 이번 I0 Re-baseline에서도 같은 실수를 반복하지 않는다.

현재 확인된 것은 **Connection acquisition queue가 150 RPS에서 커졌다**는 사실이지, “Connection 수가 부족하니 늘리면 된다”는 해결책이 아니다.

## 14. 현재 `/api/products` 조회 경로와 다음 진단 가설

현재 `GET /api/products`는 `ProductQueryService`에서 `ProductDiscoveryReader`로 내려가고, read-only transaction 안에서 `ProductDiscoveryQueryRepository`가 native query를 수행한다.

목록 조회는 단순한 `SELECT * FROM products`가 아니다.

현재 경로에는 크게 다음이 포함된다.

```text
COUNT query
+
목록 query
  ├─ categories / brands join
  ├─ SKU 대표 가격 관련 subquery
  ├─ review AVG / COUNT subquery
  ├─ SKU / inventory join
  ├─ GROUP BY
  ├─ sort
  └─ LIMIT / OFFSET
```

따라서 다음 성능 개선 단계에서는 Pool 크기를 바꾸기 전에 다음을 read-only로 분해해야 한다.

1. 150 RPS에서 실제 SQL별 실행 비용과 호출 수
2. Query plan과 사용 Index
3. Connection usage가 100→150에서 증가한 원인
4. Transaction 경계 안에서 불필요하게 오래 수행되는 작업이 있는지
5. DB Lock / I/O가 실제로 존재하는지
6. Hikari queue가 Query 실행시간 때문인지 동시성 제한 때문인지

## 15. OCI MySQL Metric 해석에서 수정한 오해

25 RPS 증거에서 `StatementLatency` 값이 약 `107075.889`처럼 크게 보였다.

처음 숫자만 보면 “SQL 한 번이 107초 걸린 것인가?”라고 오해하기 쉽다. OCI 공식 문서에서 `StatementLatency`의 단위는 ms이고 설명은 “DB System에서 실행된 모든 statement의 statement latency”다.

- [OCI MySQL HeatWave - Metrics](https://docs.oracle.com/en-us/iaas/mysql-database/doc/metrics.html)

하지만 이번 실험의 OCI MySQL DB System은 Production과 공유된다. 따라서 DB System 전체 `Statements`, `StatementLatency`, `CurrentConnections`를 I0 workload 한 요청의 평균 SQL latency처럼 해석하면 안 된다.

이후 판정에서는 OCI MySQL Metric을 **DB System 전체의 추세와 포화 여부를 보는 보조 근거**로 사용하고, Hikari usage/acquire, SQL별 진단, 동일 stage 간 비교를 더 직접적인 근거로 사용하기로 했다.

이 수정은 중요한 학습이었다.

> Metric의 단위를 아는 것과 그 Metric이 어떤 집계 범위를 나타내는지 아는 것은 별개의 문제다.

## 17. 현재 Capacity 판정

현재 조건에서 확인된 범위는 다음과 같다.

```text
I0 / Product 32

25 RPS   PASS
50 RPS   PASS
100 RPS  PASS + Watch
150 RPS  FAIL
```

정확한 최대 RPS가 100이라는 뜻은 아니다. 실제 경계는 100과 150 사이에 있을 수 있다.

현재 실험의 목적에서는 125, 130, 140을 바로 추가로 실행하는 것보다 150 RPS에서 관측된 병목을 먼저 분해하는 편이 가치가 크다.

따라서 **200 RPS와 250 RPS는 중단**했다.

이것은 테스트가 실패해서 멈춘 것이 아니라, 이미 다음 분석 단계로 전환할 충분한 실패 근거를 얻었기 때문이다.

## 18. Evidence 파일과 복구 원칙

각 stage는 다음 세 파일을 기준 증거로 사용했다.

```text
catalog-core-control-v1-<RPS>rps.json
→ k6 workload summary

catalog-core-control-v1-<RPS>rps-host.jsonl
→ Host / Container / JVM / Tomcat / Hikari 시계열 sample

catalog-core-control-v1-<RPS>rps-evidence.json
→ workload + host samples + OCI MySQL metric을 측정 시간창에 맞춰 합친 evidence
```

결과 디렉터리는 실행마다 별도 RUN_ID를 사용했고 기존 결과가 있는 디렉터리를 재사용하지 않았다. 자동 assemble이 실패했더라도 summary와 host sample이 유효하면 부하를 다시 발생시키지 않고 **기존 측정 시간창을 이용해 evidence assemble만 복구**했다.

이 원칙 덕분에 “증거 파일 하나가 없으니 같은 부하를 다시 넣는” 불필요한 재실행을 피할 수 있었다. 특히 Production과 Host·DB System을 공유하는 현재 구조에서는 재현성만큼 **불필요한 부하를 줄이는 운영 안전성**도 중요하다.

## 19. 지금까지의 증거 수준

이번 작업에서 실제로 완료된 것은 다음과 같다.

```text
Repository single-stage runner
→ Implemented / Verified / Merged

I0 25 / 50 / 100 / 150 RPS 실제 측정
→ 실행 완료
→ summary / host samples / evidence 확보
→ 단계별 판정 완료

150 RPS 병목 원인
→ Connection queueing 강한 후보 확인
→ SQL / Transaction 상세 Root Cause는 아직 미확정
```

전체 성능 단계는 `Production Verified`가 아니다. Production 기능 변경을 적용하고 검증한 작업이 아니며, 현재는 격리된 성능 runtime과 performance schema에서 실제 측정 근거를 확보한 상태다.

## 20. 다음 작업

다음 단계는 더 큰 RPS를 넣는 것이 아니다.

```text
150 RPS FAIL
→ SQL / Transaction / Connection hold read-only 진단
→ 원인 가설 구체화
→ 가장 작은 개선 선택
→ 동일 I0 / 150 RPS 재측정
→ Before / After 확인
→ 200 RPS 진행 여부 결정
```

이후 I0에서 동시성 병목을 충분히 이해하고 개선한 뒤, I10K Product 10,000 Dataset으로 동일 조건을 반복한다.

그때 비교 질문은 다음과 같다.

```text
I0 / 100 RPS와 I10K / 100 RPS는 어떻게 다른가?
I0 / 150 RPS 병목은 I10K에서 더 빨리 나타나는가?
Query plan과 Index selectivity는 어떻게 달라지는가?
Connection usage와 Tail latency는 데이터 규모에 따라 어떻게 변하는가?
```

이 흐름이 PawCycle 성능 프로젝트의 핵심이다. **대규모 데이터와 대규모 트래픽을 각각 재현하고, 측정된 한계를 먼저 현재 구조 안에서 개선한 뒤, 근거가 생길 때만 Redis·Async·Queue·Scale-out 같은 아키텍처 확장으로 넘어간다.**
