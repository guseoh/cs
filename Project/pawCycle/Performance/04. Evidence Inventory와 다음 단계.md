## 최소 metric set

Issue #300에서 실제 Production metric 계약과 OCI MySQL Monitoring metric을 대조해 첫 Re-baseline 최소 세트를 확정했다.

### Workload

- target / actual throughput
- request status / error ratio
- p50 / p95 / p99 / max
- dropped iteration
- start/end UTC
- dataset checksum / cardinality

### Backend HTTP

~~~text
http_server_requests_seconds_count
http_server_requests_seconds_bucket
~~~

외부 k6 결과를 사용자 경로의 primary outcome으로 두고 server histogram은 correlation evidence로 사용한다.

### Host / Container

- CPU user / system / iowait
- MemAvailable
- swap in / out
- filesystem
- Backend CPU / memory / RestartCount / OOMKilled
- same-host Prometheus / Grafana / metrics-proxy resource snapshot

### JVM

~~~text
process_cpu_usage
jvm_memory_used_bytes
jvm_memory_committed_bytes
jvm_memory_max_bytes
jvm_gc_pause_seconds_count
jvm_gc_pause_seconds_sum

~~~

### Tomcat

~~~text
tomcat_threads_config_max_threads

~~~

Prometheus scrape interval이 30초이므로 짧은 thread spike는 놓칠 수 있다. 첫 baseline에서는 이 한계를 evidence에 명시한다.

### Catalog Core 10K

10K는 추가 Product 10,000개가 아니라 **최종 Product 10,000개**다.

~~~text

~~~

~~~text
20260826
~~~

PR #304의 Harness regression에서는 실제 10K manifest 생성까지 수행해 다음 계약을 검증했다.


이 Dataset은 Catalog Core cardinality control이다. V3 Brand/Subcategory/Facet/Image/Option/Review 분포를 재현했다고 해석하지 않는다.

### Stage 분리

다음 순서를 유지한다.

~~~text
Stage 0
현재 Canonical Catalog
→ 데이터 mutation 없는 OCI control baseline

Dataset A
Catalog Core 10K
→ Product / SKU / Inventory cardinality 증가 영향

필요할 때 Dataset B
Discovery Realism 10K
→ V3 Brand / Category / Facet / Image / Option 분포 확대

별도 필요성이 생기면
Engagement Scale
→ Review / Rating
~~~

Request load와 dataset scale을 동시에 바꾸지 않는다.
