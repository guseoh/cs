## 최소 metric set 확정

실제 OCI Re-baseline에서는 결과 숫자만 모으지 않고 병목 계층을 분리할 최소 지표를 확정해야 한다.

Issue #300에서 실제 Production metric 계약과 OCI MySQL 기본 Monitoring metric을 대조해 최소 세트를 확정했다.

### Workload

- target / actual throughput
- request status / error ratio
- p50 / p95 / p99 / max
- dropped iteration
- start/end UTC
- dataset checksum / cardinality

### Host / Container

- CPU user / system / iowait
- MemAvailable
- swap in / out
- filesystem
- Backend CPU / memory / RestartCount / OOMKilled
- same-host Prometheus / Grafana / metrics-proxy resource snapshot

### JVM / Hikari

~~~text
process_cpu_usage
system_cpu_usage
jvm_memory_used_bytes
jvm_memory_committed_bytes
~~~


Tomcat thread metric은 현재 Production 기본 노출 계약이 아니므로 첫 baseline 필수 세트로 강제하지 않는다. JVM/Hikari/DB 근거만으로 원인을 좁히지 못하거나 thread saturation 가설이 생길 때 별도 experiment로 추가한다.

## 다음 단계

다음 작업은 [PERF-V7-002 Issue #302](https://github.com/guseoh/pawcycle-commerce/issues/302)로 분리했다. #302는 #300이 닫힐 때까지 blocked 상태다.

#302에서 먼저 현재 customer-visible Production Catalog와 synthetic dataset의 **격리 경계**를 승인한 뒤 다음 순서로 진행한다.

~~~text
Scale Dataset 설계
→ 관계 / cardinality / distribution / skew 정의
→ 10K 데이터 준비와 검증
→ OCI 10K Re-baseline
→ 필요할 때 100K
→ 병목 분석
→ 기존 구조의 가장 작은 개선
→ 동일 조건 재측정
→ KEEP / DEFER / REJECT
~~~

현재 generator는 base 32 Product에 synthetic Product를 추가하는 Catalog Read 전용 자산이다. 10K total은 additional 9,968, 100K total은 additional 99,968로 정의했다.

외부 manifest를 OCI에 안전하게 주입하는 승인 경로는 아직 없고, synthetic ACTIVE Product를 live customer-visible Catalog에 직접 apply하면 안 된다. 따라서 #302의 첫 Gate는 데이터 격리 방식 승인이다.

Scale Dataset 설계 원리 자체는 [[../../../Study/Performance/10. 대규모 데이터 Volume Cardinality Distribution Skew|Volume·Cardinality·Distribution·Skew]]에서 분리해 학습한다. Project 기록에는 실제 PawCycle table별 row 수·관계·분포와 생성/검증 결과만 남긴다.
