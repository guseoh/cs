## 남은 repository correction

Production에서 deploy.lock mode를 0644 → 0600으로 최소 수정해 READY를 복구했지만, 재발 방지는 아직 저장소에 반영하지 않았다.

후속 작업은 다음 범위다.

~~~text
shared deploy.lock permission invariant 정렬
→ 회귀 테스트 / validator
→ PR / CI
→ 각 리뷰 대상 HEAD에서 수동 CodeRabbit review
→ 사용자 승인 뒤 merge
~~~

Production 파일을 다시 수정하는 작업과 repository contract correction은 분리한다.

## 최소 metric set 확정

실제 OCI Re-baseline에서는 결과 숫자만 모으지 않고 병목 계층을 분리할 최소 지표를 확정해야 한다.

현재 후보:

- HTTP: actual RPS, status/error, p50/p95/p99/max
- Host: CPU user/system/iowait, MemAvailable, swap, disk
- Container: CPU, memory, restart, OOM
- JVM: heap/non-heap, GC, thread
- Tomcat: thread / request concurrency 관련 지표
- HikariCP: active, idle, pending, max
- DB: CPU, connection, latency, slow query / query pattern에 필요한 근거

모든 지표를 수집하는 것이 목적이 아니라 **실패했을 때 어느 계층부터 조사할지 결정할 수 있는 최소 세트**를 만든다.

## 다음 단계

PERF-V7-001의 남은 항목을 닫은 뒤 다음 순서로 진행한다.

~~~text
Scale Dataset 설계
→ 관계 / cardinality / distribution / skew 정의
→ 10K 데이터 준비와 검증
→ OCI 10K Re-baseline
→ 필요할 때 100K
→ 병목 분석
→ 기존 구조의 가장 작은 개선
→ 동일 조건 재측정
→ KEEP / DEFER / REJECT
~~~

요청 부하와 데이터 규모는 분리해서 해석한다. 10K와 100K는 목표 숫자가 아니라 Query/JPA/Index/Transaction/Connection Pool 병목이 어떻게 달라지는지 보기 위한 실험 조건이다.

## 기록 원칙

이 디렉터리는 명령어 복사본이 아니다.

각 작업은 다음 질문에 답하는 형태로 남긴다.

~~~text
무엇이 실패했는가
왜 실패했는가
어느 계층 문제였는가
어떻게 범위를 좁혔는가
어떤 수정이 최소였는가
어떻게 같은 조건에서 재검증했는가
무엇을 유지 / 보류 / 제외했는가
남은 한계는 무엇인가
~~~

Secret, Credential, Private Key, Token, raw Production DB data는 이 저장소에 기록하지 않는다.
