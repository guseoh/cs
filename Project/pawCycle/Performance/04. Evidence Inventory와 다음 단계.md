## 왜 live Production schema에 10K를 넣지 않는가

현재 Demo Catalog importer는 normal Catalog table에 직접 write하고 새 Product를 `display_status='PUBLIC'`로 생성한다.

Production wrapper도 실행 중 Backend의 datasource 환경을 재사용한다.

따라서 단순히 external manifest 옵션만 추가하면 synthetic Product가 실제 고객 Catalog에 노출될 수 있다.

또한 Production database-egress Docker network는 현재 정상 Backend 단독 membership을 전제로 검증한다. benchmark container를 같은 network에 붙이는 것도 기존 운영 invariant를 깨뜨린다.

## 구현된 isolation boundary

설계는 PR #306에서 저장소 계약으로 구현·검증·병합됐다. 상세 과정은 [[05. Isolated Catalog Runtime과 10K Scale 실행 계약]]에서 다룬다.

실제 OCI schema/account/runtime/load 실행은 별도 고위험 승인 전까지 금지한다.

### DB

같은 OCI Managed MySQL DB System을 사용하되 logical schema/database를 분리한다.

~~~text
pawcycle_perf_core_control
pawcycle_perf_core_10k
~~~

별도 performance DB account는 performance schema에만 권한을 갖고 live Production schema 권한은 갖지 않는다.

schema/user 생성과 삭제는 실제 운영 DB mutation이므로 별도 승인 없이는 실행하지 않는다.

### Runtime

동일한 승인 Backend image/revision을 별도 performance Compose project로 실행한다.

- production profile
- performance datasource
- Flyway enabled
- Hibernate validate
- Product list cache disabled
- scheduler/automation disabled
- no Frontend
- no Production Nginx
- no Production app/database-egress network membership
- 별도 DB egress bridge
- read-only filesystem
- tmpfs
- non-root pawcycle
- loopback-only endpoint

### Dataset pair

public Production과 10K를 pure cardinality Before/After로 직접 비교하지 않는다.

~~~text
P0 — Public Production reference
현재 public Catalog
end-to-end reference

I0 — Isolated Core control
V1 base
32 Product

I10K — Isolated Core 10K
V1 + deterministic V2
10,000 Product
~~~

순수 Catalog Core cardinality 비교는:

~~~text
I0 ↔ I10K
~~~

로 제한한다.

P0는 현재 실제 서비스 경로의 참고값이며 I10K의 직접 denominator가 아니다.

### Load path

첫 isolated 비교에서는 endpoint를 public에 열지 않는다.

제안:

~~~text
isolated Backend
→ app01 loopback-only port
→ SSH local forward
→ desktop k6
~~~

이 경로는 public HTTPS와 동일하지 않으므로 absolute Production capacity로 해석하지 않는다.

I0/I10K 모두 동일한 tunnel/runtime 조건을 사용해 상대 cardinality 영향만 본다.

이 방식은 새 NSG, public port, Nginx/DNS/TLS 변경과 새 paid Compute를 피한다.

## 남은 위험

이 설계는 data isolation이지 resource isolation이 아니다.

isolated Backend는 app01을 공유하고 performance schema는 같은 OCI MySQL DB System을 공유한다.

따라서 실제 실행 시:

- Production READY / Observability NORMAL 사전 확인
- low-traffic window
- Production health degradation 즉시 중단
- host/container/MySQL metric 동시 기록
- cleanup exact identity fail-closed

가 필요하다.

## 다음 단계

현재 다음 Gate는 **실제 OCI isolated experiment 실행 승인**이다.

repository preparation은 완료됐으며 실제 cloud/DB mutation과 load는 아직 시작하지 않는다.

~~~text
approved merge SHA exact source materialize
→ performance schema/account 준비
→ I0 / I10K dataset + provenance 설치
→ Production READY / Observability NORMAL
→ import validate/apply
→ isolated Backend up
→ SSH local-forward
→ I0 load
→ cleanup / post-check
→ I10K load
→ evidence 비교
→ 병목 분석
→ 최소 개선
→ 동일 조건 재측정
~~~

100K는 10K 결과가 추가 scale evidence의 필요성을 보여 줄 때만 진행한다.

Secret, Credential, Private Key, Token, raw Production DB data는 기록하지 않는다.


## Evidence Inventory는 무엇을 위한 문서인가

이 문서는 성능 개념을 설명하는 문서가 아니라 **PawCycle이 현재 무엇까지 실제 근거를 확보했고, 무엇은 아직 주장하면 안 되는지 경계를 관리하는 문서**다.

성능 프로젝트는 진행하면서 상태가 쉽게 섞인다.

~~~text
코드는 구현함
하지만 실제 OCI에는 아직 실행 안 함

로컬 테스트는 통과함
하지만 Production에서는 검증 안 함

10K Dataset은 생성 가능
하지만 실제 성능 측정은 아직 안 함
~~~

이 차이를 구분하지 않으면 “준비 완료”를 “성능 개선 완료”로 과장하게 된다.

## Implemented는 무엇을 뜻하는가

Implemented는 필요한 코드, script, 설정, 문서가 저장소에 구현됐다는 뜻이다.

예를 들어 PR #306에서 isolated runtime wrapper와 k6 runner가 merge됐다면 repository contract는 Implemented다.

하지만 실제 app01에서 실행됐다는 뜻은 아니다.

## Verified는 무엇을 뜻하는가

Verified는 저장소에서 정의한 test, validator, fake lifecycle, CI 같은 검증을 통과했다는 뜻이다.

~~~text
문법 검사
회귀 테스트
validator
fake Docker lifecycle
Repository Validation
~~~

이런 근거로 “저장소 계약이 의도한 규칙을 지키는지 검증했다”고 말할 수 있다.

하지만 실제 OCI resource와 Managed MySQL에서 동작했다는 뜻은 아니다.

## Production Verified는 무엇을 뜻하는가

Production Verified는 실제 운영 환경에서 변경이나 실험을 수행하고 필요한 전후 상태와 복구 근거까지 확보했다는 뜻이다.

PR #306은 현재 다음 상태다.

~~~text
Implemented = YES
Verified = YES
Production Verified = NO
~~~

이 표현이 중요한 이유는 repository 준비가 매우 잘 되어 있어도 실제 OCI에서 schema/account를 만들고 Dataset을 import하고 load를 실행하기 전까지는 Production 결과를 주장하면 안 되기 때문이다.

## Performance Measurement Ready와 성능 기준선 완료는 다르다

PERF-V7-001에서 확보한 Performance Measurement Ready는 **측정을 시작할 수 있는 운영·관측 상태가 준비됐다**는 뜻이다.

~~~text
Production READY
Observability NORMAL
Prometheus target UP
same-host calibration PASS
~~~

하지만 아직 I0/I10K load를 실행하지 않았기 때문에 OCI capacity baseline 자체가 완료된 것은 아니다.

~~~text
측정 장비 준비 완료
≠ 측정 결과 확보 완료
~~~

로 이해하면 쉽다.

## P0, I0, I10K를 왜 나눴는가

P0는 현재 public Production 경로다.

~~~text
Internet
→ HTTPS
→ Nginx
→ Production Backend
→ Production DB
~~~

실제 사용자 경로를 참고하기 위한 값이다.

I0는 격리된 Backend와 performance schema를 사용하면서 Product 32개인 control 조건이다.

I10K는 같은 격리 구조에서 Product를 최종 10,000개로 늘린 조건이다.

~~~text
I0
32 Product
isolated runtime

I10K
10,000 Product
same isolated runtime
~~~

순수 데이터 규모 영향은 I0와 I10K를 비교한다.

P0와 I10K를 직접 Before/After로 사용하지 않는 이유는 Network 경로, Runtime, Dataset 성격이 동시에 다르기 때문이다.

## 10K가 정확히 무엇을 의미하는가

PawCycle에서 10K는 synthetic Product를 10,000개 추가한다는 뜻이 아니다.

기존 base 32개를 포함해 **최종 Product 수를 10,000개로 맞춘다**는 뜻이다.

~~~text
base Product
32

synthetic 추가
9,968

최종
10,000
~~~

이 정의를 고정해야 실행할 때마다 “10K”의 의미가 달라지지 않는다.

## Dataset 분포를 왜 같이 기록했는가

Product 총 수만 맞춰도 성능 결과는 데이터 모양에 따라 달라질 수 있다.

그래서 SKU/Inventory 수와 DOG/CAT 분포, Product당 SKU 수, 상태값, 재고 구간까지 함께 검증했다.

이 정보는 “실제 Commerce 전체 분포를 완벽하게 재현했다”는 뜻이 아니다.

오히려 반대로 **이 Dataset이 무엇을 재현하고 무엇은 재현하지 않는지 한계를 명확히 하기 위해서** 기록한다.

현재 10K Dataset은 Product/SKU/Inventory 중심의 Catalog Core cardinality 실험용이다.

## 같은 MySQL을 쓰는데 왜 격리됐다고 말하는가

performance schema/account는 Production schema와 분리된다.

따라서 실험 Product가 고객 Catalog table에 직접 섞이지 않는다.

이것은 데이터 격리다.

하지만 같은 OCI Managed MySQL DB System을 쓰기 때문에 CPU, memory, storage 같은 물리 자원은 공유한다.

그래서 다음 두 문장을 동시에 기록한다.

~~~text
Data Isolation
= YES

Resource Isolation
= NO
~~~

실제 load 중 Production 상태도 같이 봐야 하는 이유다.

## 현재 남은 위험을 왜 문서에 남기는가

안전장치를 구현했다고 위험이 0이 되는 것은 아니다.

현재 남은 중요한 위험은 다음이다.

~~~text
같은 app01 CPU/memory 공유
같은 OCI MySQL DB System 자원 공유
실제 DB schema/user 생성은 아직 미검증
실제 import/apply는 아직 미실행
실제 k6 load도 미실행
~~~

따라서 다음 단계에서는 실험 성공 여부뿐 아니라 Production health degradation이 없는지도 확인해야 한다.

## 이 문서를 읽는 기준

표의 상태값은 “완료율”이 아니다.

각 항목이 **어느 수준의 근거까지 확보됐는지**를 나타낸다.

~~~text
MERGED
→ 저장소에 반영

VERIFIED
→ 저장소 검증 통과

미실행
→ 실제 OCI에서 아직 수행 안 함

Production Verified = NO
→ 실제 운영 실행 근거까지는 아직 없음
~~~

이 구분을 유지해야 다음 단계에서 성능 결과를 과장하지 않고 포트폴리오에도 정확하게 설명할 수 있다.
