# I0 Dataset Provenance와 Root-owned 경로 Drift

이 문서는 [[07. OCI Performance DB Provisioning과 재검증]] 다음 단계에서 `catalog-core-control-v1` I0 dataset을 생성하고 immutable provenance를 준비하면서 발견한 **실제 host ownership과 repository 실행 계약의 drift**를 기록한다.

작업 기준 PawCycle canonical main은 다음이다.

~~~text
9d2db627486b2940a7c357aefe66ebe927c974af
~~~

이번 단계의 목적은 I0 부하를 아직 실행하는 것이 아니라, 이후 import/runtime/load가 동일한 데이터와 exact approved source를 사용했다는 것을 검증할 수 있는 dataset evidence를 만드는 것이다.

## 1. I0 dataset 생성

exact approved source에서 repository generator를 사용해 control dataset을 생성했다.

고정 조건:

~~~text
dataset = catalog-core-control-v1
Product target = 32
base Product = 32
synthetic Product = 0
seed = 20260826
SKU = 42
~~~

실제 generator 실행은 성공했고 manifest/report가 만들어졌다.

~~~text
prepared Product scale dataset = PASS
Product total = 32
synthetic = 0
SKU total = 42
~~~

manifest SHA-256 자체는 Evidence로 보존할 수 있지만 이 문서에서는 실행 로그의 식별 hash를 중복 기록하지 않는다. 중요한 것은 다음 provenance 단계에서 exact source 재생성 결과와 byte 단위로 연결되는지 여부다.

## 2. provenance 생성이 fail-closed로 중단

manifest/report 생성 뒤 `prepare-isolated-catalog-provenance.py`를 실행했지만 다음 이유로 중단됐다.

~~~text
path component must be root-owned: /opt/pawcycle
~~~

처음에는 dataset 파일 자체의 owner/mode 문제를 의심할 수 있었지만 read-only path inspection 결과는 달랐다.

~~~text
source root 이하
→ root-owned
→ source directory 0555
→ source file 0444

dataset directory
→ root:root 0700

manifest/report
→ root:root 0444
~~~

실제 불일치는 공통 부모 디렉터리였다.

~~~text
/opt/pawcycle
owner = opc:opc
mode = 0700
~~~

provenance 도구는 source file까지 이어지는 부모 chain이 root-owned인지 fail-closed로 확인한다. 따라서 source와 dataset 자체가 정상이어도 `/opt/pawcycle`이 비특권 사용자 소유이면 승인 provenance를 만들 수 없다.

## 3. 왜 `/opt/pawcycle` 자체를 chown하지 않았는가

`/opt/pawcycle`은 performance 전용 디렉터리만 담는 isolated root가 아니다. Production source/state/runtime 관련 경로도 같은 상위 영역을 사용한다.

따라서 단순히 다음처럼 처리하지 않았다.

~~~text
chown root:root /opt/pawcycle
~~~

이 변경은 provenance 하나를 통과시키기 위해 Production 공용 경로의 ownership 의미까지 바꾸는 넓은 수정이 된다.

현재 문제는 “dataset이 잘못 생성됐다”가 아니라 **Runbook의 권장 performance path와 실제 host의 공통 부모 ownership이 호환되지 않는 것**이었다.

## 4. 가장 작은 안전한 correction

Production 공용 `/opt/pawcycle`은 그대로 두고, 별도의 root-owned sibling root를 만들었다.

~~~text
/opt/pawcycle-performance/
  source/<approved-sha>
  data/catalog/catalog-core-control-v1/
  runtime/catalog/db-password
~~~

이 경로는 `/opt` 바로 아래에서 root-owned performance tree로 분리된다.

기존 exact source를 새 root로 복사한 뒤 source 계약을 다시 정규화했다.

~~~text
source directories = root-owned / 0555
source files = root-owned / 0444
.git = 없음
.approved-sha = exact approved SHA
~~~

이미 성공적으로 생성된 I0 manifest/report는 삭제하거나 다시 임의 생성하지 않고 새 secure tree로 보존 복사했다.

~~~text
dataset directory = root:root / 0700
manifest.json = root:root / 0444
report.json = root:root / 0444
~~~

DB runtime secret도 값 자체를 출력하지 않고 새 root-owned runtime parent 아래로 복사했다. 실제 Secret 값은 이 문서에 기록하지 않는다.

중요한 점은 기존 `/opt/pawcycle/**` 자료를 즉시 삭제하지 않았다는 것이다. 새 경로의 provenance/runtime contract가 충분히 검증될 때까지 이전 performance artifact는 rollback/reference 용도로 보존한다.

## 5. provenance 재실행 결과

새 root-owned tree에서 provenance 생성기를 다시 실행했다.

결과:

~~~text
catalog_dataset_provenance=PASS
PERF_ROOT_MIGRATION=PASS
I0_DATASET_PROVENANCE=PASS
~~~

따라서 I0 manifest/report가 exact approved source의 generator와 같은 seed/target으로 재현됐고 immutable `provenance.json` 생성까지 완료됐다.

provenance는 다음 항목을 서로 연결한다.

~~~text
approved source SHA
prepare wrapper digest
Data V2 generator digest
base manifest digest
generated manifest digest
report digest
dataset identity
seed
Product total
~~~

이제 I0 dataset은 단순 JSON 파일이 아니라 “어떤 승인 source와 generator로 재현 가능한 데이터인가”까지 검증할 수 있는 상태다.

## 6. 이번 drift가 의미하는 것

이번 실패는 application bug나 데이터 생성 실패가 아니었다.

~~~text
repository 권장 path
+ provenance security contract
+ 실제 host ownership
→ 서로 충돌
~~~

특히 보안 validator가 strict할수록 문서의 예시 path도 실제 운영 host의 ownership model과 맞아야 한다. 경로 문자열이 단순 예시처럼 보여도 parent-chain security check가 있으면 실행 계약의 일부가 된다.

이번에는 validator를 느슨하게 바꾸거나 Production parent ownership을 바꾸지 않고 **performance 전용 secure root를 분리**하는 쪽을 선택했다.

이 drift는 이후 PawCycle repository Runbook correction 후보로 남긴다. 단, Actual Re-baseline 중 즉시 repository 변경을 끼워 넣어 실행 source를 흔들지는 않는다. 현재 approved SHA와 실행 조건을 유지한 채 실험을 계속한다.

## 다음 단계

다음은 I0 runtime config를 repository 밖 root-owned 0600 file로 준비하고, Production과 같은 승인 Backend image digest를 고정한 뒤 isolated runtime validator를 실행하는 것이다.

~~~text
I0 dataset/provenance PASS
→ runtime config 준비
→ exact Backend RepoDigest 확인
→ isolated runtime preflight
→ Production READY / Observability NORMAL 재확인
→ import validate
→ import apply
→ isolated Backend start
→ I0 load + evidence
~~~

실제 import mutation 직전에는 Production/Observability Gate를 다시 확인한다.
