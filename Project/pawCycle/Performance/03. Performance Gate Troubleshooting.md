# Performance Gate Troubleshooting

일반적인 성능 문제 분석 순서는 [[../../../Study/Performance/12. 성능 문제 분석 플레이북|성능 문제 분석 플레이북]]에서 다룬다.

이 문서는 PERF-V7-001에서 실제로 발생한 장애·오판·수정·재검증만 시간 순서로 기록한다. Canonical 실행 근거는 [Issue #300](https://github.com/guseoh/pawcycle-commerce/issues/300)이다.

## 1. 최신 승인 SHA가 Git object store에 없었다

첫 read-only 진단에서 app01의 Application control HEAD는 과거 release를 그대로 가리키고 있었다. 최신 승인 main SHA를 cat-file로 확인하려 했지만 local Git object store에 아직 없어서 fail-closed로 중단됐다.

여기서 checkout, pull, reset, rebase를 하지 않았다.

~~~text
git fetch --prune origin main
~~~

만 수행하고 fetch 전후 HEAD와 working tree가 동일한지 검증했다.

핵심은 **최신 진단 근거를 읽는 것과 실제 Production release를 바꾸는 것을 분리**한 것이다.

## 2. Backend는 정상인데 Production diagnostic은 UNKNOWN

진단 결과:

~~~text
production_assessment=UNKNOWN
release_coordination=invalid
docker_query=ok
backend=healthy
api_products_http=200
metrics_proxy_http=200
~~~

당시 확인한 정상 근거:

- Docker query 정상
- Backend healthy
- Product API 200
- metrics-proxy 200

실패 근거는 release_coordination=invalid 하나였다. 그래서 다음 read-only 확인 범위를 /opt/pawcycle/state와 shared lock contract로 제한했다.

## 3. deploy.lock mode drift

read-only inspection:

~~~text
state directory
type=directory
mode=700
owner=root:root
symlink=no

deploy.lock
type=regular file
mode=644
owner=root:root
symlink=no

release-state-transition=absent
open lock fd=0
~~~

진단기는 deploy.lock이 regular non-symlink file이면서 mode 0600이어야 stable로 인정한다.

직접 원인:

~~~text
실제 mode 0644
expected   0600
~~~

실제 lock holder와 transition이 없음을 확인한 뒤 수정 범위를 한 파일로 제한했다.

~~~text
/opt/pawcycle/state/deploy.lock
0644 → 0600
~~~

재검증에서 Production READY가 됐다.

### repository contract gap

Production drift만 수정하고 끝내지 않았다.

diagnose-backend-state.sh는 existing lock의 0600을 요구하지만 일부 Production helper는 regular/non-symlink 여부만 확인하고 existing mode를 같은 invariant로 정렬하지 않는 빈틈이 있었다.

따라서 저장소 correction을 PR #301로 분리했다.

### PR #301 — release lock 재발 방지

초기 correction은 두 Production helper가 shared `deploy.lock`을 다음 계약으로 처리하도록 맞췄다.

~~~text
existing lock
→ regular non-symlink
→ mode 0600
→ 아니면 fail-closed

missing lock
→ umask 077
→ 생성
→ open 후 다시 mode 0600 검증
~~~

첫 HEAD에서는 Git tree 작성 과정에서 `create-production-auth-smoke-member.sh`의 기존 executable bit를 보존하지 못해 CI가 실패했다. 로직 문제가 아니라 file mode regression이었고, 원래 `100755`만 복구했다.

그 뒤 CodeRabbit 분석에서 검사와 open 사이 TOCTOU 가능성이 제기됐다.

문제가 되는 전제는 caller가 `--state-dir`로 비특권 사용자가 소유한 0700 directory를 전달할 수 있다는 점이었다. 기존 validator는 mode 0700만 확인하고 owner까지 확인하지 않았다.

따라서 최신 correction은 state path 자체와 각 parent component의 trust boundary를 강화했다.

~~~text
absolute / canonical path
→ 각 component directory 확인
→ root owner(uid 0)
→ group/other writable이면 sticky 경계 확인
→ 최종 state directory mode 0700
→ 그 뒤 deploy.lock 검사/생성/open
~~~

비특권 사용자가 소유한 caller-controlled state directory는 Git/Docker/credential 단계 전에 fail-closed하도록 회귀 테스트를 추가했다.

최종 review 대상 HEAD:

~~~text
7024ef0fff488307d77dcd0d90c0a168317fe8d2
~~~

최종 검증:

~~~text
Repository Validation #1758 = SUCCESS
manual @coderabbitai review = SUCCESS
inline review thread = 0
mergeable = true
~~~

사용자 승인 후 PR #301을 squash merge했다.

~~~text
merge commit
b669c5a8e0a5d5bf61a20331216003a2a404cb85
~~~

따라서 Production의 직접 correction과 저장소 재발 방지는 모두 닫혔다.

## 4. 정상 runtime이 최신 source라는 보장은 없다

Production READY와 Observability NORMAL 뒤에도 runtime provenance를 확인했다.

실행 중인 metrics-proxy와 Prometheus/Grafana는 historical approved source에서 올라온 상태였다. 하지만 관련 설정 checksum을 최신 main과 비교했을 때 content drift는 없었다.

따라서 다음 둘을 구분했다.

~~~text
configuration drift
→ 없음

runtime provenance mismatch
→ 존재
~~~

즉 즉시 장애는 아니지만 앞으로 성능 Evidence를 최신 승인 SHA와 정확히 연결하려면 provenance를 정렬해야 했다.

latest SHA exact source를 준비하고 OFF/ON 복구 때 그 source로 다시 올린 뒤 container Compose working directory가 최신 source 경로인지 검증했다.

## 5. SSH 장애처럼 보였던 shell 종료

작업 중 여러 번 다음 메시지를 봤다.

~~~text
Connection to ... closed.
~~~

처음에는 SSH transport 또는 host/network 문제 후보로 보았다. 실제로 별도의 client_loop: send disconnect: Connection reset 사건도 한 번 있었다.

하지만 이후 반복된 종료 중 상당수는 interactive login shell에 다음 옵션을 직접 설정한 상태에서 발생했다.

~~~bash
set -Eeuo pipefail
~~~

이 상태에서 curl, Python 파일 수정, Git object read 같은 명령 하나가 non-zero를 반환하면 -e 때문에 현재 login shell 자체가 종료된다. SSH session은 그 shell을 실행하고 있으므로 사용자 화면에서는 연결이 닫힌 것처럼 보인다.

Host 진단에서는 다음이 확인됐다.

- host load 낮음
- MemAvailable 충분
- root filesystem 57%
- kernel OOM event 0
- physical NIC enp0s5 error/drop 0
- PawCycle container restart 0
- container OOMKilled false
- Prometheus ready
- Grafana health PASS
- Prometheus backend target up

따라서 반복된 모든 종료를 OCI network 장애로 해석하지 않았다.

### 운영 규칙 보정

앞으로 interactive Production shell에는 set -e를 직접 남기지 않는다.

엄격한 fail-fast가 필요한 경우:

~~~text
독립 실행 script 내부에 set -Eeuo pipefail
→ stdout/stderr와 exit code를 파일로 보존
→ login shell은 유지
~~~

로 분리한다.

## 6. 긴 측정을 SSH와 분리

60초 calibration 도중 SSH 상태가 측정 자체에 영향을 주지 않도록 마지막 Restored ON 측정은 detached worker로 전환했다.

~~~text

→ 시작만 수행

→ 60초 vmstat + HTTP samples
→ status / log file
~~~

worker 내부에서 Production READY, Observability NORMAL, latest source provenance, Application identity를 다시 검증한 뒤 측정을 수행했다.

최종 결과:

~~~text
production_ready=PASS
observability_normal=PASS
latest_sha_runtime_provenance=PASS
application_identity_post_measurement=PASS
observability_runtime_stability=PASS
restored_on_baseline=PASS
~~~

## 이 Troubleshooting의 핵심은 무엇이었나

PERF-V7-001에서 가장 중요한 부분은 “deploy.lock 권한을 0600으로 바꿨다”는 사실 하나가 아니다.

실제 핵심은 **정상 신호와 비정상 신호를 분리하고, 조사 범위를 가능한 한 작게 줄인 뒤, Production 수정과 저장소 재발 방지를 분리했다는 과정**이다.

~~~text
Backend healthy
API 200
metrics-proxy 200

그런데
Production diagnostic = UNKNOWN
~~~

이 상황에서 DB, Nginx, Backend를 전부 건드리지 않고 release coordination만 조사했다.

## 왜 git checkout 대신 fetch만 했는가

app01의 Application checkout은 실제 Production release와 연결된 운영 경계다.

성능 진단용 최신 script가 필요하다고 해서 checkout을 최신 main으로 이동시키면 **진단을 위해 실제 release source 상태를 바꾸는 셈**이 된다.

그래서 다음을 분리했다.

~~~text
Production Application checkout
→ 그대로 유지

Git object store
→ 최신 main commit object만 fetch
~~~

git fetch는 필요한 Git object를 가져오되 현재 checkout HEAD를 바꾸지 않는다.

fetch 전후 HEAD와 working tree가 같은지도 다시 확인했다.

이 방식으로 “최신 저장소의 진단 로직을 읽는 것”과 “현재 Production release를 바꾸는 것”을 분리했다.

## deploy.lock은 무엇을 보호하는 파일인가

deploy.lock은 여러 운영 작업이 동시에 release 관련 상태를 바꾸지 않도록 조정하는 공유 lock 경계다.

당시 state Directory는 root-owned 0700이었지만 deploy.lock 자체는 0644였다.

~~~text
0644
owner  read/write
group  read
other  read

0600
owner  read/write
group  no access
other  no access
~~~

진단 계약은 민감한 release coordination 상태에 사용하는 lock을 0600으로 요구했다.

실제 상태가 0644였기 때문에 진단기는 release coordination을 stable로 인정하지 않았다.

## 왜 바로 chmod하지 않고 lock holder부터 확인했는가

lock file 권한만 보고 바로 변경하면 현재 다른 운영 작업이 그 lock을 사용 중일 가능성을 놓칠 수 있다.

그래서 먼저 다음을 확인했다.

~~~text
release transition 없음
open lock fd = 0
현재 lock holder 없음
~~~

그 뒤 정확히 deploy.lock 한 파일만 0644 → 0600으로 바꿨다.

Application Container, DB, Network, Release SHA는 건드리지 않았다.

이런 방식이 “가장 작은 수정” 원칙이다.

## Production 수정과 저장소 수정은 왜 분리했는가

Production 파일을 chmod 0600으로 바꾸면 현재 장애 상태는 복구된다.

하지만 helper가 다음 실행에서 다시 잘못된 mode를 만들 수 있다면 재발 방지는 끝난 것이 아니다.

그래서 두 문제를 따로 닫았다.

~~~text
현재 Production drift
→ 실제 file mode correction

재발 가능성
→ repository helper contract correction
→ test / validator / PR
~~~

PR #301은 두 번째 문제를 해결하기 위한 작업이었다.

## file mode 100755 regression은 왜 중요했는가

PR #301 correction 과정에서 create-production-auth-smoke-member.sh의 executable bit가 보존되지 않아 CI가 실패했다.

Script 내용이 맞아도 Git file mode가 100644로 바뀌면 실행 파일로서의 계약이 깨질 수 있다.

~~~text
100755
→ executable

100644
→ regular non-executable
~~~

따라서 저장소 변경에서는 파일 내용뿐 아니라 Git mode도 계약의 일부라는 점을 다시 확인했다.

## state-dir TOCTOU는 어떤 문제였나

초기 correction은 deploy.lock 자체를 안전하게 검사하려고 했다.

하지만 사용자가 전달하는 state Directory가 비특권 사용자 소유라면 검사 직후 Directory entry가 바뀔 가능성이 남아 있었다.

쉽게 말하면:

~~~text
검사 시점
/unsafe/state/deploy.lock
정상

검사 후
비특권 사용자가 path 교체

사용 시점
다른 file 접근 가능
~~~

이것이 검사 시점과 사용 시점의 차이를 이용하는 TOCTOU 문제다.

그래서 최종 file만 확인하지 않고 parent path 전체를 trust boundary로 봤다.

~~~text
absolute / canonical path
→ 각 parent가 Directory인지
→ symlink가 아닌지
→ root-owned인지
→ group/other writable인지
→ 최종 state Directory 0700인지
~~~

일반 개념은 [[../../../Study/Performance/13. 재현 가능한 성능 실험과 안전한 격리|재현 가능한 성능 실험과 안전한 격리]]에서 설명한다.

## runtime provenance mismatch는 왜 즉시 장애가 아니었나

Prometheus와 Grafana는 과거 승인 source에서 실행 중이었지만 최신 main과 관련 설정 checksum을 비교했을 때 내용 차이는 없었다.

즉:

~~~text
configuration content
→ 동일

실행 source identity
→ 과거 SHA
~~~

였다.

기능적으로 잘못된 설정이 실행 중인 것은 아니었지만 앞으로 성능 Evidence를 “어떤 승인 source에서 실행했는가”와 정확히 연결하려면 provenance를 최신 SHA에 맞춰야 했다.

그래서 즉시 장애 수정으로 다루지 않고 OFF/ON calibration 복구 과정에서 latest approved SHA source로 정렬했다.

## 왜 SSH가 끊긴 것처럼 보였는가

interactive shell에 다음 옵션을 직접 설정한 상태가 문제였다.

~~~bash
set -Eeuo pipefail
~~~

여기서 -e는 명령이 non-zero로 끝나면 shell이 종료될 수 있게 만든다.

login shell 자체에 이 옵션을 걸어 둔 상태에서 curl이나 Git 명령 하나가 실패하면 shell이 끝난다.

SSH는 그 shell에 연결되어 있으므로 사용자 입장에서는 다음처럼 보인다.

~~~text
명령 실패
→ login shell 종료
→ SSH session 종료
→ 화면에는 Connection closed
~~~

따라서 모든 Connection closed 메시지를 Network 장애로 해석하면 안 된다.

실제 Host CPU, memory, NIC error, OOM, Container restart 등을 확인해 반복적인 Host 장애 근거가 없음을 확인했다.

## strict mode를 script 안에 두는 이유

set -Eeuo pipefail 자체가 나쁜 것은 아니다.

자동화 script에서는 오류를 숨기지 않고 즉시 실패하게 만드는 좋은 도구다.

문제는 **interactive login shell 전체에 걸어 둔 것**이다.

그래서 규칙을 다음처럼 바꿨다.

~~~text
interactive shell
→ 계속 유지

실제 작업 script
→ 내부에서 set -Eeuo pipefail
→ stdout / stderr / exit code 보존
~~~

실패해도 SSH 연결 자체는 유지되므로 로그를 읽고 다음 진단을 할 수 있다.

## detached worker는 왜 사용했는가

60초 calibration을 SSH session에 직접 묶어 두면 session 종료가 측정 프로세스 종료로 이어질 수 있다.

그래서 마지막 측정은 다음처럼 분리했다.

~~~text
SSH
→ 측정 시작 명령만 전달

detached worker
→ 60초 측정 수행
→ 결과 file / status 보존
~~~

이렇게 하면 SSH 연결의 일시적인 문제와 실제 성능 측정을 분리할 수 있다.

## 이번 Troubleshooting에서 배운 조사 방식

이 사건을 일반화하면 다음과 같다.

~~~text
1. 정상 신호와 실패 신호 분리
2. 실패한 invariant 하나로 조사 범위 축소
3. read-only 확인
4. 실제 사용 중 여부 확인
5. 가장 작은 Production correction
6. 동일 진단 재실행
7. 저장소 재발 방지 과제 분리
8. review / regression
~~~

즉 “문제를 발견하면 설정을 많이 바꾼다”가 아니라 **증거로 범위를 줄이고 필요한 것만 바꾼다**는 흐름이 핵심이다.
