# Performance Gate Troubleshooting

성능 단계 첫 Gate에서 발생한 문제는 “Prometheus가 안 뜬다”나 “Backend가 느리다”가 아니었다. 여러 정상 신호와 실패 신호를 분리하면서 문제 범위를 좁힌 과정 자체가 핵심 근거다.

## 1. 최신 승인 SHA가 Git object store에 없었다

첫 read-only 진단에서 app01의 Application control HEAD는 과거 release를 그대로 가리키고 있었다. 최신 승인 main SHA를 cat-file로 확인하려 했지만 local Git object store에 아직 없어서 fail-closed로 중단됐다.

여기서 checkout, pull, reset, rebase를 하지 않았다.

~~~text
git fetch --prune origin main
~~~

만 수행하고 fetch 전후 HEAD와 working tree가 동일한지 검증했다.

핵심은 **최신 진단 근거를 읽는 것과 실제 Production release를 바꾸는 것을 분리**한 것이다.

## 2. Backend는 정상인데 Production diagnostic은 UNKNOWN

진단 결과:

~~~text
production_assessment=UNKNOWN
release_coordination=invalid
docker_query=ok
backend=healthy
api_products_http=200
metrics_proxy_http=200
~~~

여기서 Application이나 DB를 의심하면 조사 범위가 불필요하게 커진다.

정상 근거:

- Docker query 정상
- Backend healthy
- Product API 200
- metrics-proxy 200

실패 근거:

- release coordination invalid

그래서 조사 범위를 /opt/pawcycle/state와 shared lock contract로 축소했다.

## 3. deploy.lock mode drift

read-only inspection:

~~~text
state directory
type=directory
mode=700
owner=root:root
symlink=no

deploy.lock
type=regular file
mode=644
owner=root:root
symlink=no

release-state-transition=absent
open lock fd=0
~~~

진단기는 deploy.lock이 regular non-symlink file이면서 mode 0600이어야 stable로 인정한다.

직접 원인:

~~~text
실제 mode 0644
expected   0600
~~~

실제 lock holder와 transition이 없음을 확인한 뒤 수정 범위를 한 파일로 제한했다.

~~~text
/opt/pawcycle/state/deploy.lock
0644 → 0600
~~~

재검증에서 Production READY가 됐다.

### repository contract gap

Production drift만 수정하고 끝내지 않았다.

diagnose-backend-state.sh는 existing lock의 0600을 요구하지만 일부 Production helper는 regular/non-symlink 여부만 확인하고 existing mode를 같은 invariant로 정렬하지 않는 빈틈이 있었다.

따라서 남은 과제는 **모든 shared lock helper가 같은 permission invariant를 생성·검증하도록 저장소 계약과 회귀 테스트를 맞추는 것**이다.

이 repository correction은 아직 완료되지 않았다.

## 4. 정상 runtime이 최신 source라는 보장은 없다

Production READY와 Observability NORMAL 뒤에도 runtime provenance를 확인했다.

실행 중인 metrics-proxy와 Prometheus/Grafana는 historical approved source에서 올라온 상태였다. 하지만 관련 설정 checksum을 최신 main과 비교했을 때 content drift는 없었다.

따라서 다음 둘을 구분했다.

~~~text
configuration drift
→ 없음

runtime provenance mismatch
→ 존재
~~~

즉 즉시 장애는 아니지만 앞으로 성능 Evidence를 최신 승인 SHA와 정확히 연결하려면 provenance를 정렬해야 했다.

latest SHA exact source를 준비하고 OFF/ON 복구 때 그 source로 다시 올린 뒤 container Compose working directory가 최신 source 경로인지 검증했다.

## 5. SSH 장애처럼 보였던 shell 종료

작업 중 여러 번 다음 메시지를 봤다.

~~~text
Connection to ... closed.
~~~

처음에는 SSH transport 또는 host/network 문제 후보로 보았다. 실제로 별도의 client_loop: send disconnect: Connection reset 사건도 한 번 있었다.

하지만 이후 반복된 종료 중 상당수는 interactive login shell에 다음 옵션을 직접 설정한 상태에서 발생했다.

~~~bash
set -Eeuo pipefail
~~~

이 상태에서 curl, Python 파일 수정, Git object read 같은 명령 하나가 non-zero를 반환하면 -e 때문에 현재 login shell 자체가 종료된다. SSH session은 그 shell을 실행하고 있으므로 사용자 화면에서는 연결이 닫힌 것처럼 보인다.

Host 진단에서는 다음이 확인됐다.

- host load 낮음
- MemAvailable 충분
- root filesystem 57%
- kernel OOM event 0
- physical NIC enp0s5 error/drop 0
- PawCycle container restart 0
- container OOMKilled false
- Prometheus ready
- Grafana health PASS
- Prometheus backend target up

따라서 반복된 모든 종료를 OCI network 장애로 해석하지 않았다.

### 운영 규칙 보정

앞으로 interactive Production shell에는 set -e를 직접 남기지 않는다.

엄격한 fail-fast가 필요한 경우:

~~~text
독립 실행 script 내부에 set -Eeuo pipefail
→ stdout/stderr와 exit code를 파일로 보존
→ login shell은 유지
~~~

로 분리한다.

## 6. 긴 측정을 SSH와 분리

60초 calibration 도중 SSH 상태가 측정 자체에 영향을 주지 않도록 마지막 Restored ON 측정은 detached worker로 전환했다.

~~~text
SSH session
→ 시작만 수행
→ detached worker
→ 60초 vmstat + HTTP samples
→ status / log file
~~~

worker 내부에서 Production READY, Observability NORMAL, latest source provenance, Application identity를 다시 검증한 뒤 측정을 수행했다.

최종 결과:

~~~text
production_ready=PASS
observability_normal=PASS
latest_sha_runtime_provenance=PASS
application_identity_post_measurement=PASS
observability_runtime_stability=PASS
restored_on_baseline=PASS
~~~

## 이번 Troubleshooting에서 남긴 기준

문제 발생 시 “어떤 도구가 실패했다”에서 바로 설정을 바꾸지 않는다.

~~~text
정상 invariant 확인
→ 실패 계층 분리
→ read-only evidence
→ 가장 작은 correction
→ 동일 진단 재실행
→ repository contract gap 확인
→ 재발 방지 과제 분리
~~~
