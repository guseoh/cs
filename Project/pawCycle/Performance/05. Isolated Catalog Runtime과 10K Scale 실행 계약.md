# PawCycle 10K 격리 성능 실행 계약

이 문서는 PawCycle에서 **실제 Production Catalog를 오염시키지 않으면서 Product 32개와 10,000개 조건을 비교하기 위해 만든 격리 성능 환경**을 기록한다.

명령어를 보관하는 작업 로그가 아니라, 왜 격리가 필요했는지부터 시작해 데이터와 Runtime을 어떻게 나눴는지, 어떤 보안 문제가 리뷰에서 발견됐는지, 어떤 대안을 버리고 어떤 최소 수정을 선택했는지, 최종적으로 무엇까지 검증됐고 무엇은 아직 실행하지 않았는지를 설명하는 프로젝트 사례 문서다.

일반 개념은 별도 학습 글에서 먼저 풀어 설명한다.

- [[../../../Study/Performance/02. 부하 테스트와 Workload Modeling|부하 테스트와 요청 흐름 모델링]]
- [[../../../Study/Performance/07. Latency Percentile과 Tail Latency|응답 시간 백분위와 꼬리 지연]]

여기서는 그 개념이 PawCycle에서 **어떤 실제 문제 때문에 필요했고 코드·테스트·운영 경계로 어떻게 바뀌었는지**에 집중한다.

## 이 문서에서 자주 나오는 표현을 먼저 이해한다

### 실행 환경(Runtime)

이 문서에서 Runtime은 단순히 Java 실행 파일 하나를 뜻하지 않는다. **실제로 성능 요청을 받아 처리하는 Backend Container와 그 설정, Network, DB 연결 조건을 합친 실행 환경**을 뜻한다.

PawCycle에서는 실제 고객 요청을 처리하는 Production Backend와 성능 실험용 Backend를 같은 것으로 사용하지 않는다.

~~~text
Production Runtime
→ 실제 고객 요청 처리

Performance Runtime
→ I0 / I10K 측정 전용
→ loopback-only
→ 별도 DB schema/account
→ Production network 비가입
~~~

이렇게 나누는 이유는 성능 실험을 위해 설정과 데이터를 바꾸다가 실제 서비스에 영향을 주지 않도록 하기 위해서다.

### 정확한 승인 소스(Exact Approved Source)

Git branch 이름인 main은 새로운 merge가 생기면 계속 움직인다.

그래서 실제 실험에서는 “현재 main”이라는 표현보다 **실험을 승인한 정확한 commit SHA의 파일 집합**을 별도 Directory에 추출해서 사용한다.

이 문서에서 exact source는 그 고정된 source snapshot을 뜻한다.

### 출처 정보(Provenance)

Provenance는 “이 파일이 어떤 과정을 거쳐 만들어졌는가”를 연결하는 근거다.

PawCycle에서는 10K Dataset manifest만 보관하지 않는다.

~~~text
어떤 승인 source SHA인가
어떤 generator 파일인가
generator의 SHA-256은 무엇인가
어떤 seed를 썼는가
Product 목표 수는 얼마인가
생성된 manifest/report digest는 무엇인가
~~~

를 하나로 연결한다.

이렇게 해야 나중에 같은 Dataset이 정말 같은 코드와 조건에서 만들어졌는지 다시 확인할 수 있다.

### 안전하게 중단(Fail-closed)

Fail-closed는 검증할 수 없는 상태가 나오면 임의로 계속 진행하지 않고 중단하는 방식이다.

예를 들어 Dataset ID가 예상과 다르면 “비슷하니 계속”하지 않는다.

~~~text
Dataset ID 불일치
→ import 중단

Container label 불일치
→ down 중단

source permission 이상
→ provenance 생성 중단
~~~

운영과 가까운 자동화에서는 잘못된 대상을 변경하는 것보다 멈추는 것이 안전하기 때문이다.

### 체크섬과 SHA-256

SHA-256은 파일 내용을 바탕으로 만드는 해시 값이다.

파일 내용이 달라지면 일반적으로 다른 값이 나오므로 “지금 파일이 이전에 확인한 파일과 같은 bytes인가”를 검사하는 데 사용한다.

하지만 SHA-256 하나만으로 생성 과정까지 알 수는 없기 때문에 PawCycle에서는 provenance와 함께 사용한다.

## 왜 live Production Catalog에 10K를 넣지 않았는가

처음 목표는 현재 Catalog Core 32 Product와 10,000 Product를 비교해 **데이터 cardinality 증가 자체가 조회 성능에 주는 영향**을 측정하는 것이었다.

가장 단순한 방법은 Production DB에 synthetic Product를 넣는 것이다. 하지만 실제 코드를 확인하니 이 방식은 실험 격리 경계를 깨뜨린다.

현재 demo importer는 normal Product table에 직접 write하고 새 Product를 `display_status='PUBLIC'`로 생성한다. Production import wrapper도 실행 중 Backend datasource를 재사용한다.

즉 synthetic 10K를 live schema에 넣으면 다음 문제가 생긴다.

~~~text
성능 실험 데이터
→ 실제 Product table
→ PUBLIC 상태
→ 고객이 보는 Catalog에 노출 가능
~~~

성능 측정을 위해 실제 서비스 데이터를 오염시키는 구조는 제외했다.

반대로 완전히 다른 로컬 DB와 runtime을 쓰면 현재 OCI Production과 환경 차이가 너무 커진다. 그래서 **같은 app01과 같은 OCI Managed MySQL DB System을 공유하되 논리 데이터와 runtime을 분리하는 방식**을 선택했다.

## 데이터 격리와 자원 격리는 다르다

최종 구조는 data isolation이다.

~~~text
desktop k6
   │
   │ SSH local-forward
   ▼
app01 127.0.0.1:<performance-port>
   │
   ▼
isolated Backend
   │
   │ performance-db-egress
   ▼
same OCI Managed MySQL DB System
   ├─ pawcycle_perf_core_control
   └─ pawcycle_perf_core_10k
~~~

분리되는 것:

- DB schema
- DB account
- Compose project
- Backend container
- Docker network
- loopback port
- dataset identity
- 결과 directory

공유되는 것:

- app01 CPU / memory
- OCI Managed MySQL DB System CPU / memory / storage
- 물리적인 DB System resource

따라서 I0와 I10K 측정 중 Production과 자원 경쟁이 발생할 수 있다. 실제 실행에서는 Production READY / Observability NORMAL을 전후로 확인하고 Host/Container/MySQL 지표를 같이 봐야 한다.

## P0 / I0 / I10K를 분리해서 해석한다

세 결과를 같은 의미로 비교하지 않는다.

~~~text
P0
현재 public Production
실제 HTTPS / Nginx / Application / Managed MySQL
end-to-end reference

I0
isolated Catalog Core control
V1 base
32 Product

I10K
isolated Catalog Core 10K
V1 + deterministic V2
10,000 Product
seed = 20260826
~~~

순수 cardinality 비교는:

~~~text
I0 ↔ I10K
~~~

다.

P0는 public HTTPS/Nginx 경로이고 I0/I10K는 SSH local-forward + isolated Backend 경로이므로 P0와 I10K를 pure Before/After로 표현하지 않는다.

PR #304에서 10K의 의미를 **synthetic 10,000개 추가가 아니라 최종 Product 10,000개**로 고정했다.

~~~text

synthetic Product  9,968
total Product      10,000
seed             20260826

SKU total         19,977
Inventory total   19,977
~~~

검증된 주요 분포:

~~~text

SKU fan-out
~~~

## Exact approved SHA source

실제 performance 작업은 mutable checkout에서 실행하지 않는다.

병합된 canonical main의 exact 40자리 SHA를 archive로 별도 materialize하고 그 source를 실행 기준으로 사용한다.

권장 app01 경로:

~~~text
/opt/pawcycle/performance-source/<APPROVED_SHA>
~~~

source 계약:

~~~text
directory name
= approved SHA

.approved-sha
= approved SHA

source root / internal directory
= root-owned + 0555

regular file
= root-owned + 0444

.git
= 없음
~~~

Application control checkout의 HEAD와 working tree를 성능 실험 source 준비 때문에 바꾸지 않는다.

## 왜 source permission을 여기까지 강하게 검사하는가

provenance generator는 approved source의 Python wrapper를 **root 권한으로 실행**한다.

따라서 source가 단순히 “현재 SHA와 같은 파일”인지만 확인해서는 부족하다. 검증 직후 path component가 교체될 수 있으면 확인한 파일과 실제 root가 실행한 파일이 달라질 수 있다.

이 문제는 PR #306 리뷰에서 TOCTOU 형태로 발견됐다.

~~~text
검증 시점
scripts/prepare-product-scale-data.py = 정상

중간 directory가 writable
→ wrapper 교체 가능

실행 시점
root Python이 같은 path를 다시 open
→ 다른 코드 실행 가능
~~~

## TOCTOU correction

초기 구현은 다음을 이미 확인했다.

- source root root-owned
- source root 0555
- 최종 source file root-owned
- 최종 source file 0444
- intermediate symlink 거부
- direct source file symlink 거부

하지만 **intermediate directory의 owner/writable 상태**는 충분히 검증하지 않았다.

수정 후 provenance creator와 validator 모두 source file까지 이어지는 전체 parent chain을 확인한다.

~~~text
각 parent path component

symlink?
→ 거부

directory?
→ 아니면 거부

owner uid == 0?
→ 아니면 거부

group/other writable?
→ 거부

root-owned sticky directory?
→ 허용 가능
~~~

최종 source file은 계속 root-owned + 0444여야 한다.

## wrapper를 임시 위치로 복사하지 않은 이유

CodeRabbit 제안의 한 방향은 검증한 wrapper를 trusted temporary location으로 복사해 실행하는 것이었다.

하지만 현재 `prepare-product-scale-data.py`는 자신의 `__file__` 위치를 기준으로 sibling `generate-product-data-v2.py`를 찾는다.

wrapper 하나만 다른 위치로 복사하면:

~~~text
기존
scripts/prepare-product-scale-data.py
→ scripts/generate-product-data-v2.py

wrapper만 temp로 복사
/tmp/.../prepare-product-scale-data.py
→ /tmp/.../generate-product-data-v2.py
~~~

처럼 실행 구조 자체가 바뀐다.

그래서 wrapper 복사보다 **exact source tree를 root-owned read-only boundary로 고정**하는 최소 수정이 현재 구조에 더 맞았다.

## Dataset provenance

`manifest.json`과 `report.json` checksum만 맞는다고 승인하지 않는다.

provenance creator는 approved source의 실제 generator로 dataset을 다시 생성하고 설치된 파일과 byte 단위로 비교한다.

흐름:

~~~text
approved SHA marker
→ prepare wrapper digest
→ actual Data V2 generator digest
→ base manifest digest
→ same seed / same target count 재생성
→ installed manifest bytes 비교
→ installed report bytes 비교
→ provenance.json 생성
~~~

`provenance.json`에는 다음을 연결한다.

- approved source SHA
- prepare wrapper SHA-256
- Data V2 generator SHA-256
- base manifest SHA-256
- generated manifest SHA-256
- report SHA-256
- dataset ID
- seed
- total Product count

이미 provenance가 존재하면 overwrite하지 않고 fail-closed한다.

## Dataset / Config / Secret permission

dataset directory:

~~~text
root-owned
0700
non-symlink
~~~

manifest / report / provenance:

~~~text
root-owned
regular non-symlink
0444
~~~

runtime config:

~~~text
root-owned
0600
DB password 없음
~~~

DB password file:

~~~text
root-owned
0400 또는 0600
Git / Issue / PR / 로그에 값 기록 금지
~~~

DB password, credential, raw Production DB data는 이 CS 레포에도 기록하지 않는다.

## Backend image를 tag가 아니라 digest로 고정

runtime config는 Backend image를 다음 형식으로 요구한다.

~~~text
<registry>/<image>@sha256:<64-hex>
~~~

실행 전에:

~~~text
local image 존재
→ linux/amd64
→ RepoDigest 일치
→ --pull never
~~~

를 확인한다.

실험 시작 순간에 tag가 다른 image를 가리키거나 Docker가 암묵적으로 새 image를 pull하는 것을 막는다.

## Isolated Compose 경계

isolated Backend의 host publish:

~~~text
127.0.0.1:<performance-port>:8080
~~~

public interface에는 열지 않는다.

Docker network:

~~~text
performance-db-egress
~~~

만 사용한다.

사용하지 않는 것:

- Production `app` network
- Production `database-egress`
- Production Nginx
- Production Frontend
- public performance listener
- 새 NSG
- 새 Load Balancer

runtime hardening:

- read-only filesystem
- tmpfs
- no-new-privileges
- capability drop
- resource limit

## 명시적 acknowledgement

위험한 동작은 command 이름만으로 실행되지 않는다.

~~~text
import-apply
→ APPLY:<DATASET_ID>

up
→ START:<DATASET_ID>

down
→ DOWN:pawcycle-performance-catalog
~~~

acknowledgement가 없거나 identity가 다르면 fail-closed한다.

## import 동작

`import-apply`는 바로 APPLY를 실행하지 않는다.

~~~text
ack 확인
→ image 확인
→ project identity 확인
→ Backend stopped 확인
→ import VALIDATE
→ import APPLY
~~~

주의할 점은 empty performance schema의 첫 Backend startup/import validation 과정에서도 Flyway migration이 적용될 수 있다는 것이다.

따라서 이름이 `validate`라고 해서 read-only 작업으로 취급하면 안 된다. 실제 OCI에서의 첫 실행은 DB mutation 승인 이후에만 한다.

## startup 실패 cleanup

isolated Backend `up` 과정은 다음을 확인한다.

~~~text
compose up
→ health
→ /actuator/health/readiness
→ /api/products
~~~

이 중 성공 완료 전에 실패하면 wrapper가 자신이 만든 performance project를:

~~~text
docker compose down --remove-orphans
~~~

로 정리한다.

Production project를 대상으로 하지 않는다.

## cleanup은 정상 입력 전체에 의존하지 않는다

성능 실행이 실패했는데 local Backend image나 dataset 파일이 손상됐다는 이유로 cleanup까지 못 하면 운영 위험이 커진다.

그래서 `down`은 runtime 생성에 필요한 전체 입력을 다시 요구하지 않는다.

필수 경계만 확인한다.

- config absolute path
- regular non-symlink
- root-owned
- 0600
- dataset identity
- existing performance container scope/dataset label
- explicit DOWN acknowledgement

그리고 fixed interpolation sentinel을 사용해 exact Compose project를 내린다.

local Backend image가 없어도 cleanup할 수 있다.

`--volumes`는 사용하지 않는다.

## 기존 container identity 확인

같은 Compose project 이름을 가진 container가 이미 있으면 무조건 재사용하거나 내리지 않는다.

각 container label의:

~~~text
com.pawcycle.performance.scope
com.pawcycle.performance.dataset
~~~

을 확인한다.

scope가 `catalog-isolated`가 아니거나 dataset이 현재 config와 다르면 중단한다.

이 경계는 다른 experiment의 container나 잘못된 project를 실수로 건드리는 것을 막는다.

## k6 실행 경계

첫 isolated 비교는 public endpoint를 만들지 않고 desktop에서 SSH local-forward를 사용한다.

~~~text
desktop 127.0.0.1:<local-port>
→ SSH
→ app01 127.0.0.1:<performance-port>
~~~

runner가 허용하는 target:

~~~text
http://127.0.0.1
http://localhost
http://[::1]
~~~

외부 URL은 거부한다.

runner source root도 자신의 실제 script source root와 전달된 `--source-root`가 같아야 한다.

`.approved-sha` 형식과 directory 이름도 다시 확인한다.

## 결과 directory를 재사용하지 않는다

이전 실행의 일부 stage 결과와 새 실행 결과가 섞이면 하나의 capacity series처럼 보일 수 있다.

그래서 기존 non-empty results directory는 fail-closed한다.

각 run은 새 directory를 사용한다.

## 부하 단계를 왜 25에서 250 RPS까지 올리는가

RPS(Requests Per Second)는 1초 동안 실행하려는 요청 수를 나타내는 단위다. 이번 실험에서는 한 번에 최대 부하를 넣지 않고 다음처럼 단계적으로 올린다.

~~~text
25
→ 50
→ 100
→ 150
→ 200
→ 250 RPS
~~~

목적은 “250이라는 큰 숫자를 달성하는 것”이 아니다. 어느 지점까지는 정상적으로 처리하다가 **어느 구간부터 실제 처리량이 목표를 따라가지 못하거나 응답 시간과 오류가 급격히 나빠지는지** 경계를 찾기 위해서다.

각 단계는 준비 구간 30초와 실제 측정 구간 120초로 나눈다. 준비 구간(Warm-up)은 JVM의 JIT 컴파일, Connection Pool 연결 생성, 캐시와 DB buffer 상태처럼 시작 직후와 일정 요청을 처리한 뒤가 달라질 수 있는 요소를 어느 정도 안정시키기 위한 시간이다.

~~~text
준비 구간
30초

측정 구간
120초
~~~

자세한 개념은 [[../../../Study/Performance/02. 부하 테스트와 Workload Modeling|부하 테스트와 요청 흐름 모델링]]에서 설명한다.

## p50, p95, p99를 왜 같이 기록하는가

평균 응답 시간 하나만 남기면 일부 느린 요청이 가려질 수 있다.

p50은 전체 요청을 빠른 순서부터 정렬했을 때 중앙에 가까운 지점이고, p95는 약 95%의 요청이 그 값 이하에서 끝나는 지점이다. p99는 더 느린 약 1% 근처의 꼬리 구간을 본다.

예를 들어 다음과 같은 결과라면:

~~~text
p50 = 40ms
p95 = 120ms
p99 = 900ms
~~~

절반 정도의 요청은 40ms 이하로 빠르지만 가장 느린 일부 요청은 훨씬 오래 걸렸다는 뜻이다. p50은 거의 그대로인데 p99만 크게 올라간다면 모든 요청이 느려진 것보다 일부 요청이 Lock, DB 연결 대기, GC pause 같은 특정 대기를 겪는 상황을 의심할 수 있다.

PawCycle runner는 p50, p95, p99와 최대값을 함께 기록한다. 자세한 숫자 해석은 [[../../../Study/Performance/07. Latency Percentile과 Tail Latency|응답 시간 백분위와 꼬리 지연]]에서 설명한다.

카카오 메시징팀도 실제 스트레스 테스트에서 초당 요청 수와 p50·p95·p99 응답 시간, 오류율을 먼저 확인한 뒤 내부 CPU·메모리·연결·스레드 지표로 내려간다.

- [카카오 — 메시징 서버의 스트레스 테스트 노하우](https://tech.kakao.com/posts/822)

## 누락된 반복 실행을 0으로 요구하는 이유

k6가 목표 도착률을 만들려고 해도 사용할 수 있는 가상 사용자나 부하 생성기 자원이 부족하면 일부 반복 실행 자체를 시작하지 못할 수 있다. 이를 누락된 반복 실행(dropped iteration)이라고 한다.

~~~text
목표
250회 실행

실제로 시작
230회

시작하지 못함
20회
~~~

이 상태에서 “서버가 230 RPS밖에 처리하지 못했다”고 단정하면 안 된다. 서버가 아니라 **부하 생성기가 목표 요청을 만들지 못했을 가능성**이 있기 때문이다.

그래서 이번 계약에서는 정상 응답으로 보지 않는 요청의 비율과 누락된 반복 실행을 모두 0으로 요구한다. 하나라도 실패하면 다음 RPS 단계로 진행하지 않는다.

## 결과 Directory를 재사용하지 않는 이유

이전 실험의 결과와 새 실험의 결과가 같은 Directory에 섞이면 서로 다른 실행을 하나의 연속된 결과처럼 오해할 수 있다.

~~~text
어제
25 / 50 / 100 RPS 결과

오늘
25 / 50 RPS만 새로 실행
~~~

같은 Directory를 재사용하면 어제의 100 RPS 결과가 오늘 결과처럼 남을 수 있다. 그래서 기존 결과가 하나라도 있는 Directory는 거부하고 실행마다 비어 있는 새 결과 Directory를 사용한다.

## Runbook source permission 검증 correction

source tree를 root-owned read-only로 정규화한 뒤 Runbook에서도 수동 확인한다.

최종 검사는 NUL-safe pipeline을 사용한다.

~~~text
directory
find -print0
→ xargs -0 stat -c '%u %a'
→ exact 0 555

regular file
find -print0
→ xargs -0 stat -c '%u %a'
→ exact 0 444
~~~

여기서 두 가지 문제가 추가로 발견됐다.

첫 번째는 pipeline 중간 command가 실패해도 마지막 `awk`가 성공하면 전체가 성공처럼 보일 수 있다는 점이다. 그래서 `set -euo pipefail`을 적용했다.

두 번째는 빈 stream이 들어오면 기존 awk가 아무 항목도 검사하지 않고 성공할 수 있다는 점이다. 그래서 `seen`을 두어 최소 한 항목도 검사하지 못하면 실패하도록 했다.

이 correction이 PR #306 최종 HEAD의 마지막 변경이다.

## 이번 작업에서 남긴 핵심 판단

### 1. 데이터 규모를 키우는 것보다 먼저 격리해야 한다

10K를 만드는 일보다 **그 10K를 어디에 넣어도 실제 서비스가 오염되지 않는 구조를 만드는 것**이 먼저였다.

### 2. 같은 인프라를 쓴다고 같은 실험은 아니다

같은 app01/MySQL DB System을 쓰더라도 schema/runtime/network/dataset identity를 분리하면 데이터는 격리할 수 있다. 하지만 resource는 공유되므로 결과 해석에는 그 한계를 남겨야 한다.

### 3. provenance는 checksum 하나보다 넓은 개념이다

결과 파일 checksum만이 아니라 **어떤 승인 source와 generator가 어떤 seed로 그 데이터를 만들었는지**까지 연결해야 재현 가능한 실험이 된다.

### 4. root 실행 전 path trust boundary가 중요하다

최종 file permission만 안전해도 중간 directory가 writable하면 실행 경로가 바뀔 수 있다. privileged script에서는 parent path 전체를 trust boundary로 봐야 한다.

### 5. cleanup은 정상 경로보다 더 단순하고 독립적이어야 한다

실패 상황에서 image/dataset/secret이 깨졌다는 이유로 cleanup이 막히면 복구가 더 위험해진다. exact project identity만 확인하고 runtime을 내릴 수 있도록 설계했다.

### 6. review status와 review evidence는 다르다

`Review finished`, passing status, unresolved 0은 중요한 근거지만 프로젝트 규칙에서 요구하는 exact-HEAD review submission과 동일하지 않다.

이번에는 사용자가 evidence gap을 인지하고 **PR 단위 예외를 명시 승인**했다. 이 차이를 기록으로 남기는 것이 중요하다.
