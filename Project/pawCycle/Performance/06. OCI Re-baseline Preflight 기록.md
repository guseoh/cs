# OCI Re-baseline Preflight 기록

이 문서는 PawCycle의 Catalog I0 / I10K OCI Re-baseline을 실제로 실행하기 직전, 성능 실험을 시작해도 되는 운영 상태인지 확인하고 성능 전용 DB 경계를 준비하기 위해 수행한 실제 Preflight와 Troubleshooting을 기록한다.

저장소 실행 계약은 [[05. Isolated Catalog Runtime과 10K Scale 실행 계약]]에서 다룬다. 여기서는 그 계약을 실제 OCI 환경에 적용하려고 했을 때 무엇이 막혔고, 어떤 가설이 틀렸으며, 어떤 수정과 재검증으로 다음 Gate까지 도달했는지를 정리한다.

현재 실제 I0 / I10K 부하는 아직 시작하지 않았다. 따라서 이 기록은 Re-baseline 완료 보고가 아니라 **Actual Execution의 Preflight 진행 기록**이다.

## 왜 부하 실행보다 Preflight를 먼저 했는가

이번 단계의 목적은 최대 RPS를 빨리 얻는 것이 아니다. I0와 I10K를 같은 조건에서 비교하려면 측정 전에 운영 상태, 실행 소스, 시간 기준, MySQL Metric, DB 접근 경계가 모두 설명 가능한 상태여야 한다.

이번 구조는 별도 DB System을 새로 만드는 완전한 자원 격리가 아니다. Production과 Performance experiment는 같은 OCI Managed MySQL DB System의 자원을 공유하고, 데이터와 Runtime만 별도 경계로 분리한다.

따라서 실제 부하보다 다음 Gate를 먼저 닫았다.

~~~text
시간 동기화
→ exact approved source
→ Production READY
→ Observability NORMAL
→ Prometheus target up
→ OCI MySQL Metric 확인
→ DB administrator 접근 확인
→ performance DB boundary 확인
~~~

## 실행 기준과 exact source

작업 시점 PawCycle canonical main은 다음 commit이었다.

~~~text
9d2db627486b2940a7c357aefe66ebe927c974af
~~~

실험 source를 Application control checkout에서 직접 실행하지 않았다. 승인된 SHA를 별도 source tree로 materialize하고 marker, owner, mode를 검증했다. Production control checkout의 HEAD와 working tree는 source 준비 전후 동일하게 유지했다.

핵심은 성능 실험에 사용할 최신 승인 source와 실제 Production release source를 분리한 것이다.

## 시간 동기화 Gate

Desktop과 app01의 측정 시각이 크게 다르면 k6 결과, Host Metric, OCI Monitoring Metric을 같은 시간 구간으로 맞추기 어렵다.

Desktop Windows 시간 동기화와 app01 NTP 동기화를 확인하고 여러 번 offset을 측정했다. 가장 좋은 측정의 상한은 약 0.40초였고 이번 Gate의 1초 기준 이내였다.

따라서 Clock Gate는 PASS로 판단했다.

## Production과 Observability Preflight

exact approved source 기준 진단에서 다음 상태를 다시 확인했다.

~~~text
production_assessment = READY
release_coordination = stable
observability status = NORMAL
prometheus_target = up
~~~

OCI Monitoring에서는 이번 Re-baseline에 필요한 MySQL Metric도 사전에 확인했다.

~~~text
CPUUtilization
MemoryUtilization
ActiveConnections
CurrentConnections
Statements
StatementLatency
~~~

각 Metric에서 대상 ACTIVE DB System의 stream과 최근 datapoint가 존재함을 확인했다. 실제 I0 / I10K 실행 중 DB 계층 관측이 불가능해 결과를 해석하지 못하는 상황을 사전에 차단한 것이다.

## Production runtime과 latest main의 차이

실험 준비 시점 Production Backend runtime은 현재 main보다 이전 revision에서 실행 중이었다. 그러나 이번 Catalog read 경로의 핵심 조회 코드와 migration 차이를 비교했을 때 측정 대상 경로에서 즉시 최신 main runtime으로 교체해야 할 근거는 없었다.

그래서 I0와 I10K는 같은 Production 승인 image digest를 고정해서 비교하는 방향을 유지했다.

따라서 이후 결과는 “동일 runtime 조건의 I0/I10K 비교”로 설명해야 하며 “latest main Backend의 절대 성능”이라고 표현하면 안 된다.

## DB administrator 접근이 blocker가 됐다

성능용 schema와 account는 Production schema/account와 분리해야 한다. 그러려면 처음 한 번은 schema와 user를 만들 수 있는 관리자 접근이 필요하다.

실제 실행 직전 확인해 보니 안전하게 재사용할 수 있는 기존 관리자 credential 경로를 찾지 못했다. Production Application datasource account는 administrator가 아니었기 때문에 그것을 대신 사용하는 것도 제외했다.

이 시점에서 import나 load로 진행하지 않고 DB Gate에서 중단했다.

## 관리자 식별 정보 복구

처음에는 OCI DB System 상세 조회에서 현재 administrator 식별 정보를 바로 얻을 수 있을 것이라고 가정했다. 실제 응답 구조에서는 해당 필드가 노출되지 않았다.

PowerShell history와 과거 local JSON 흔적에서도 후보를 찾지 못했다. 값을 추측해서 접속을 시도하지 않고 OCI Audit의 과거 DB System 생성 요청을 조회했다.

대상 기간 Audit 983개 이벤트에서 관련 후보가 정확히 1개로 좁혀졌다.

~~~text
local CLI history candidate = 0
local JSON candidate = 0
OCI Audit candidate = 1
~~~

실제 값은 이 CS 저장소에 기록하지 않는다. 필요한 근거는 **복구 경로와 후보가 유일했다는 사실**이다.

## credential rotation 과정에서의 실패

처음에는 administrator의 두 credential 속성을 함께 변경할 수 있다고 가정했다. 실제 OCI API는 요청을 InvalidParameter로 거부했고, administrator 식별 정보 변경은 지원되지 않으며 한 번에 하나의 속성만 바꿀 수 있다는 사실을 확인했다.

이 요청은 거부됐기 때문에 Cloud-side 변경은 발생하지 않았다.

하지만 실패 응답에 제출 값이 포함되어 터미널에 노출될 수 있다는 문제가 드러났다. 입력 단계에서 값을 마스킹했다고 해서 실패 응답까지 자동으로 안전해지는 것은 아니었다.

따라서 당시 제출 값은 즉시 폐기했고 다시 사용하지 않았다.

## 최소 수정과 재검증

실제 서비스 응답을 기준으로 변경 범위를 administrator credential의 필요한 한 속성으로 줄였다. 또한 CLI의 상세 오류 출력은 보호된 임시 경로로 격리하고, 작업 뒤 임시 파일을 제거하도록 수정했다.

수정된 rotation 요청은 성공적으로 제출됐고 DB System lifecycle이 다시 `ACTIVE`로 돌아온 것을 확인했다.

그 뒤 Desktop으로 이동한 후 로컬 PowerShell 변수나 이전 세션 상태를 신뢰하지 않고 OCI API에서 ACTIVE DB System을 다시 resolve했다.

~~~text
OCI profile authentication = PASS
ACTIVE DB System count = 1
DB lifecycle = ACTIVE
~~~

## 실제 관리자 인증과 권한 확인

app01의 private network 경로에서 MySQL client를 사용해 회전된 credential의 실제 인증을 확인했다. 인증은 성공했다.

`SHOW GRANTS FOR CURRENT_USER()`로 성능 전용 schema/account를 준비하는 데 필요한 CREATE, CREATE USER, GRANT 계열 권한과 administrator 역할이 존재함도 확인했다.

전체 grant 원문과 실제 credential 값, endpoint, resource identifier는 장기 기록에 남기지 않는다.

현재 기록 가능한 근거는 다음과 같다.

~~~text
administrator authentication = PASS
schema/user provisioning authority = CONFIRMED
~~~

## Performance schema/account Preflight에서 발견한 검증 오류

관리자 로그인 뒤 기존 performance schema/account가 이미 존재하는지 read-only로 확인했다.

performance account 검색에서는 관련 user가 발견되지 않았다. 따라서 기존 performance 전용 account는 현재 조회에서 미발견 상태다.

하지만 schema 확인 SQL에는 중요한 검증 오류가 있었다.

Repository contract의 정확한 schema 이름은 다음이다.

~~~text
pawcycle_perf_core_control
pawcycle_perf_core_10k
~~~

첫 수동 조회에서는 `core`가 빠진 다른 이름을 조회했다. 그 결과가 `Empty set`이었다고 해서 계약상 실제 performance schema 두 개가 없다고 증명할 수는 없다.

따라서 현재 Evidence는 다음처럼 나눈다.

~~~text
performance DB account
→ 현재 조회에서 미발견

contract schema 2개
→ 정확한 이름으로 재검증 필요
~~~

read-only SQL도 대상 identifier가 틀리면 “없음”의 근거가 되지 않는다.

## 이번 과정에서 배운 핵심

첫째, **Secret-safe 입력과 Secret-safe 실패 처리는 다른 문제**다. 입력 화면에서 마스킹되더라도 하위 API나 CLI validation error가 제출 값을 다시 출력할 수 있다. 운영 자동화에서는 성공 경로뿐 아니라 실패 stdout/stderr가 어떤 정보를 포함할 수 있는지도 설계해야 한다.

둘째, **Cloud API가 제공할 것이라고 추측한 필드와 실제 응답 계약은 다를 수 있다.** 필요한 식별 정보를 단순 조회에서 얻을 수 있다고 가정했지만 실제 응답으로 검증되지 않았다. 이후에는 Audit 근거로 복구했다.

셋째, **read-only 검증도 대상 이름이 틀리면 근거가 아니다.** SQL이 성공하고 `Empty set`이 나와도 조회한 schema identifier가 실행 계약과 다르면 “없음”을 증명하지 못한다.

넷째, **운영 변경과 성능 실험 완료를 분리해야 한다.** 이번에는 실제 administrator credential rotation과 인증 검증까지 수행했지만 performance schema 생성, dataset import, isolated runtime, k6 load는 아직 시작하지 않았다.

## 다음 Gate

다음 단계에서 가장 먼저 할 일은 정확한 contract schema 이름으로 read-only preflight를 다시 수행하는 것이다.

~~~text
pawcycle_perf_core_control
pawcycle_perf_core_10k
~~~

그 결과까지 확인한 뒤에만 performance 전용 schema/account provisioning으로 넘어간다.

그 이후 전체 Actual Re-baseline의 실행 흐름은 기존 계약을 유지한다.

~~~text
contract schema/account 확인 및 준비
→ I0 dataset/provenance
→ Production READY / Observability NORMAL 재확인
→ I0 import + isolated Backend
→ I0 25..250 RPS + evidence
→ cleanup + Production/Observability post-check
→ I10K 동일 조건 반복
→ Host/JVM/Tomcat/Hikari/MySQL 비교
→ cardinality 영향 판정
→ 병목 가설
→ 가장 작은 개선
→ 동일 조건 재측정
~~~

100K는 I0/I10K 결과가 추가 규모 실험의 필요성을 보여 줄 때까지 계속 보류한다.

## 기록하지 않은 값

이 문서는 실제 운영 과정의 설명과 검증 경계를 남기지만 credential 값, private key, DB endpoint 주소, resource identifier, raw Production DB row, 전체 administrator grant 원문은 기록하지 않는다.
