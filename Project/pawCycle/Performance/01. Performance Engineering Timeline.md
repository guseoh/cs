# Performance Engineering Timeline

성능 일반 이론은 [[../../../Study/Performance/README|Study/Performance]]로 분리한다. 이 Timeline은 PawCycle에서 실제로 어떤 Gate를 어떤 순서로 통과했는지만 기록한다.

## 왜 AWS 결과를 그대로 쓰지 않았는가

PawCycle은 AWS Production에서 read-only GET /api/products 부하를 단계적으로 올려 200 RPS까지 PASS, 250 RPS에서 first-failure를 확인한 적이 있다. 당시 직접 failure mechanism은 Backend container memory cgroup OOM이었다.

하지만 현재 Production은 OCI로 이동했고 Application 코드, 운영 구조, DB 환경과 Observability 계약도 달라졌다. 따라서 AWS 결과를 현재 최대 처리량처럼 재사용하지 않고 Historical Evidence로만 보존한다.

현재 성능 단계의 원칙은 다음과 같다.

~~~text
현재 OCI 운영 상태 확인
→ 측정 가능한 상태 확보
→ Scale Dataset 준비
→ OCI Re-baseline
→ 병목 계층 분리
→ 가장 작은 개선
→ 동일 조건 재측정
~~~

이유는 성능 문제가 발생했을 때 최소한 다음 계층을 구분할 수 있어야 하기 때문이다.

첫 목표는 최대 RPS가 아니라 다음 상태였다.

## 최신 승인 SHA를 checkout하지 않고 준비

Gate 기준 승인 main은 다음이었다.

~~~text
df74023e96a3afe37219ecd50d48adac8b7b3c60
~~~

하지만 app01의 Application control checkout은 과거 release를 그대로 가리키고 있었고 최신 commit object도 처음에는 local Git object store에 없었다.

Application checkout을 최신 main으로 이동시키는 대신 git fetch --prune origin main만 실행했다. fetch 전후 HEAD와 working tree가 그대로인지 확인한 뒤 승인 SHA의 진단 script만 읽어 사용했다.

이 방식의 핵심은 **현재 Production release와 진단에 사용할 최신 저장소 근거를 분리**한 것이다.

## Production diagnostic UNKNOWN

첫 Production 진단은 다음과 같았다.

~~~text
production_assessment=UNKNOWN
release_coordination=invalid
docker_query=ok
backend=healthy
api_products_http=200
metrics_proxy_http=200
~~~

Backend, public API, metrics-proxy가 모두 정상인데 전체 판정만 UNKNOWN이었다. 따라서 Application이나 DB 장애로 범위를 넓히지 않고 release coordination contract만 조사했다.

## deploy.lock 0644 → 0600

/opt/pawcycle/state는 root-owned 0700 directory였고 release transition도 없었다. 문제는 shared deploy.lock이었다.

~~~text
실제 mode   0644
진단 계약   0600
~~~

추가로 open lock FD가 0이고 transition도 없음을 확인했다. 실제 Production correction은 정확히 한 파일의 mode만 0644 → 0600으로 바꿨다.

Application container, Managed MySQL, network, release SHA, HTTPS, Secret은 변경하지 않았다.

재검증 결과:

~~~text
production_assessment=READY
release_coordination=stable
backend=healthy
api_products_http=200
metrics_proxy_http=200
~~~

동시에 repository helper 일부가 existing shared lock의 0600 invariant를 동일하게 강제하지 않는 contract gap도 발견했다. 실제 파일 correction과 저장소 재발 방지 과제를 분리했다.

## Observability NORMAL과 historical provenance

Production READY 뒤 Prometheus readiness와 backend target을 결합해 Observability diagnostic NORMAL을 확인했다.

그 다음 실제 실행 중인 metrics-proxy와 Prometheus/Grafana의 source provenance가 최신 main이 아니라 과거 승인 source라는 사실을 발견했다.

여기서 바로 재배포하지 않았다. 먼저 과거 source와 최신 main의 관련 설정 checksum을 비교했고 **실행 설정 content drift는 없음**을 확인했다.

즉 문제는 기능 configuration drift가 아니라 **runtime provenance가 최신 승인 SHA와 정렬되지 않은 상태**였다.

최신 승인 SHA의 exact source를 별도 경로에 materialize하고 다음 계약을 검증했다.

- source marker와 approved SHA 일치
- directory 0555
- regular file 0444
- pinned image digest와 platform 확인
- identity verifier checksum 일치
- Application control checkout 불변

## Same-host OFF / ON calibration

Observability가 Application과 같은 Compute에서 실행되기 때문에, 성능 기준선을 만들기 전에 관측 도구 자체가 측정을 크게 왜곡하지 않는지 확인했다.

순서는 다음과 같았다.

~~~text
Initial ON 60초
→ Observability + metrics-proxy controlled OFF
→ OFF 60초
→ exact latest-SHA source로 복구
→ READY / NORMAL / provenance 재검증
→ Restored ON 60초
~~~

모든 구간은 read-only /api/products 30 samples, 2초 간격을 유지했다. Application backend/frontend/proxy와 Managed MySQL은 OFF/ON 대상에서 제외했다.

최종 결과는 [[02. Observability Gate와 Same-host Calibration]]에 별도로 정리한다.
