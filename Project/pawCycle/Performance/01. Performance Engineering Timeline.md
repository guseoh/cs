# Performance Engineering Timeline

성능 일반 이론은 [[../../../Study/Performance/README|Study/Performance]]로 분리한다. 이 Timeline은 PawCycle에서 실제로 어떤 Gate를 어떤 순서로 통과했는지만 기록한다.

## 왜 AWS 결과를 그대로 쓰지 않았는가

PawCycle은 AWS Production에서 read-only GET /api/products 부하를 단계적으로 올려 200 RPS까지 PASS, 250 RPS에서 first-failure를 확인한 적이 있다. 당시 직접 failure mechanism은 Backend container memory cgroup OOM이었다.

하지만 현재 Production은 OCI로 이동했고 Application 코드, 운영 구조, DB 환경과 Observability 계약도 달라졌다. 따라서 AWS 결과를 현재 최대 처리량처럼 재사용하지 않고 Historical Evidence로만 보존한다.

현재 성능 단계의 원칙은 다음과 같다.

~~~text
현재 OCI 운영 상태 확인
→ 측정 가능한 상태 확보
→ Scale Dataset 준비
→ OCI Re-baseline
→ 병목 계층 분리
→ 가장 작은 개선
→ 동일 조건 재측정
~~~

## 최신 승인 SHA를 checkout하지 않고 준비

Gate 측정 당시 승인 main은 다음이었다.

~~~text
df74023e96a3afe37219ecd50d48adac8b7b3c60
~~~

하지만 app01의 Application control HEAD는 과거 release를 그대로 가리키고 있었고 최신 commit object도 처음에는 local Git object store에 없었다.

Application checkout을 최신 main으로 이동시키는 대신 git fetch --prune origin main만 실행했다. fetch 전후 HEAD와 working tree가 그대로인지 확인한 뒤 승인 SHA의 진단 script만 읽어 사용했다.

이 방식의 핵심은 **현재 Production release와 진단에 사용할 최신 저장소 근거를 분리**한 것이다.

## Production diagnostic UNKNOWN

첫 Production 진단은 다음과 같았다.

~~~text
production_assessment=UNKNOWN
release_coordination=invalid
docker_query=ok
backend=healthy
api_products_http=200
metrics_proxy_http=200
~~~

Backend, public API, metrics-proxy가 모두 정상인데 전체 판정만 UNKNOWN이었다. 따라서 Application이나 DB 장애로 범위를 넓히지 않고 release coordination contract만 조사했다.

## deploy.lock 0644 → 0600

/opt/pawcycle/state는 root-owned 0700 directory였고 release transition도 없었다. 문제는 shared deploy.lock이었다.

~~~text
실제 mode   0644
진단 계약   0600
~~~

추가로 open lock FD가 0이고 transition도 없음을 확인했다. 실제 Production correction은 정확히 한 파일의 mode만 0644 → 0600으로 바꿨다.

Application container, Managed MySQL, network, release SHA, HTTPS, Secret은 변경하지 않았다.

재검증 결과:

~~~text
production_assessment=READY
release_coordination=stable
backend=healthy
api_products_http=200
metrics_proxy_http=200
~~~

동시에 repository helper 일부가 existing shared lock의 0600 invariant를 동일하게 강제하지 않는 contract gap도 발견했다. 실제 파일 correction과 저장소 재발 방지 과제를 분리했다.

## Observability NORMAL과 historical provenance

Production READY 뒤 Prometheus readiness와 backend target을 결합해 Observability diagnostic NORMAL을 확인했다.

실행 중인 metrics-proxy와 Prometheus/Grafana의 source provenance가 최신 main이 아니라 과거 승인 source라는 사실도 확인했다.

관련 설정 checksum을 최신 main과 비교했을 때 configuration content drift는 없었다. 문제는 기능 설정 차이가 아니라 runtime provenance 정렬이었다.

latest approved SHA의 exact source를 별도 경로에 materialize하고 marker, directory/file mode, image digest/platform, identity verifier checksum, Application control checkout 불변을 검증했다.

## Same-host OFF / ON calibration

Observability가 Application과 같은 Compute에서 실행되므로 성능 기준선을 만들기 전에 관측 도구 자체가 측정을 크게 왜곡하지 않는지 확인했다.

~~~text
Initial ON 60초
→ Observability + metrics-proxy controlled OFF
→ OFF 60초
→ exact latest-SHA source로 복구
→ READY / NORMAL / provenance 재검증
→ Restored ON 60초
~~~

Application backend/frontend/proxy와 Managed MySQL은 OFF/ON 대상에서 제외했다.

최종 결과는 [[02. Observability Gate와 Same-host Calibration]]에 기록한다.

## 2026-09-22~23 — OCI dataset isolation boundary 구현

#302의 다음 Gate로 live Production Catalog를 오염시키지 않는 격리 구조를 확정했다.

코드 조사에서 demo importer가 normal Product table에 write하고 새 Product를 `display_status='PUBLIC'`로 생성하며, 기존 Production wrapper가 실행 중 Backend datasource를 재사용하는 것을 확인했다. 따라서 live Production schema에 synthetic 10K를 넣는 방식은 제외했다.

최종 repository 설계:

~~~text
same app01
+ same OCI Managed MySQL DB System

DB
├─ pawcycle_perf_core_control
└─ pawcycle_perf_core_10k

Runtime
└─ pawcycle-performance-catalog
   ├─ loopback-only Backend
   ├─ dedicated performance-db-egress bridge
   └─ Production app/database-egress network 비가입

Load
desktop k6
→ SSH local-forward
→ app01 127.0.0.1:<performance-port>
~~~

이 구조는 **data isolation**이지 **resource isolation**은 아니다. app01 CPU/memory와 OCI MySQL DB System resource는 Production과 공유한다.

비교 의미도 분리했다.

~~~text
P0
현재 public Production
end-to-end reference

I0
V1 Core 32 Product
isolated runtime

I10K
V1 + deterministic V2
10,000 Product
isolated runtime

순수 cardinality 비교 = I0 ↔ I10K
~~~

P0와 I10K는 transport와 dataset family가 모두 다르므로 pure Before/After로 사용하지 않는다.

## source provenance TOCTOU correction

CodeRabbit review에서 provenance generator가 root 권한으로 approved wrapper를 실행하기 전에 **중간 source directory의 쓰기 가능성**을 충분히 막지 않는 문제가 발견됐다.

기존 구현은 source root와 최종 source file의 owner/mode, 중간 symlink는 확인했지만 intermediate directory가 group/other writable인지 검사하지 않았다.

위험:

~~~text
검증
→ writable intermediate directory에서 wrapper path 교체
→ root provenance generator가 path를 다시 open
→ 검증한 파일과 다른 파일 실행 가능
~~~

단순히 wrapper를 임시 directory로 복사하는 방식은 사용하지 않았다. `prepare-product-scale-data.py`가 자신의 `__file__`을 기준으로 sibling generator를 찾기 때문에 wrapper 하나만 복사하면 실행 구조 자체가 바뀐다.

대신 provenance creator와 validator 모두 source file까지 이어지는 parent chain을 검사하도록 수정했다.

~~~text
각 parent
→ symlink 금지
→ directory 확인
→ root-owned
→ group/other writable 금지
→ /tmp 같은 root-owned sticky directory 예외

source root
→ root-owned 0555

source regular file
→ root-owned 0444
~~~

회귀 테스트에는 group-writable `scripts/`, intermediate directory symlink, direct source file symlink 거부를 포함했다.

## Runbook permission check correction

TOCTOU correction 뒤 Runbook의 수동 source-boundary 검증도 보강했다.

최종 형태는 다음 원칙을 갖는다.

~~~text
set -euo pipefail

directory
find -print0
→ xargs -0 stat -c '%u %a'
→ 모든 항목이 정확히 0 555
→ 하나도 없으면 실패

regular file
find -print0
→ xargs -0 stat -c '%u %a'
→ 모든 항목이 정확히 0 444
→ 하나도 없으면 실패
~~~

`pipefail`로 find/xargs/stat/awk 실패가 뒤 단계의 성공으로 숨지 않게 하고, `seen` 검사를 두어 empty/malformed stream이 성공하는 것도 막았다.
