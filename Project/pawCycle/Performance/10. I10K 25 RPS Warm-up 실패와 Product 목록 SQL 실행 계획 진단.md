# I10K 25 RPS Warm-up 실패와 Product 목록 SQL 실행 계획 진단

이 문서는 PawCycle Commerce의 `PERF-V7-008`에서 **Catalog Core I10K를 실제 OCI 환경에 올린 뒤 25 RPS warm-up 단계에서 발생한 실패**, 그리고 그 실패를 재부하하지 않고 read-only SQL 진단으로 좁혀 간 과정을 기록한다.

이번 작업의 핵심은 “25 RPS도 못 버텼다”는 결과 자체가 아니다. I0의 작은 Dataset에서는 정상적으로 처리되던 Product 목록 조회가 I10K 10,000 Product Dataset에서 왜 Connection을 오래 점유하게 되었는지, HikariCP pending이 왜 폭증했는지, MySQL 옵티마이저가 실제 데이터 규모를 어떻게 잘못 추정했는지, 그리고 **가장 작은 개선 후보를 어떻게 page-first 조회로 좁혔는지**가 핵심이다.

MySQL 실행 계획, 카디널리티 추정, 임시 테이블, dependent subquery, page-first 조회의 일반 개념은 [[../../../Study/Performance/15. MySQL 실행 계획과 카디널리티 추정, Page-first 조회]]에서 따로 설명한다. 이 문서에서는 PawCycle의 실제 Source, Dataset, 측정값, 실패와 판정에 집중한다.

- [PERF-V7-008 Issue #320](https://github.com/guseoh/pawcycle-commerce/issues/320)
- [ProductDiscoveryQueryRepository.java @ 56378e4](https://github.com/guseoh/pawcycle-commerce/blob/56378e4bc58e59bedf7efe200df8447633396abe/backend/src/main/java/com/pawcycle/backend/catalog/product/persistence/ProductDiscoveryQueryRepository.java)
- [MySQL 8.4 - EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html)

## 1. 이번 실험의 위치와 비교 계약

`PERF-V7-008`의 목적은 Product 32개인 I0 기준선과 Product 10,000개인 I10K를 같은 격리 runtime과 workload 계약으로 비교해 **Dataset 규모가 Catalog 목록 조회에 주는 영향**을 확인하는 것이다.

비교 축은 다음과 같이 분리했다.

```text
요청 부하 축
25 → 50 → 100 → 150 RPS

Dataset 축
I0   = Product 32
I10K = Product 10,000
```

I10K 단계에서는 한 stage라도 실패하면 다음 RPS로 가지 않는 `stop-on-fail` 계약을 적용했다. 200/250 RPS는 이번 작업 범위에서 제외했다.

이전 I0 첫 실험에서는 150 RPS에서 saturation이 관측된 적이 있었지만, 이후 lifecycle 진단이 포함된 동일 계열 재측정에서는 그 현상이 재현되지 않았다. 현재 I0의 유효 150 RPS 비교 기준은 다음이다.

| 항목 | I0 150 RPS 유효 기준 |
| --- | ---: |
| actual RPS | 149.8833 |
| dropped | 0 |
| expected-status error | 0 |
| p50 | 106.47 ms |
| p95 | 371.35 ms |
| p99 | 712.29 ms |
| max | 941.22 ms |
| Hikari active max | 7 / 10 |
| Hikari pending max | 0 |
| Tomcat busy max | 5 |

따라서 과거 “I0 150 RPS가 항상 Connection Pool을 포화시킨다”는 해석은 유지하지 않는다. I0의 과거 150 RPS saturation은 historical evidence로 남기되 현재 비교 기준에서는 `INCONCLUSIVE / DEFER`다.

## 2. I10K 실행 identity

I10K actual 실행은 다음 exact source를 기준으로 했다.

```text
56378e4bc58e59bedf7efe200df8447633396abe
```

Dataset은 deterministic generator와 canonical seed를 이용해 생성한 `catalog-core-10k-v1`이다.

| 항목 | 값 |
| --- | ---: |
| Product | 10,000 |
| base Product | 32 |
| synthetic Product | 9,968 |
| SKU | 19,977 |
| Inventory | 19,977 |
| seed | 20260826 |

Dataset manifest/report/provenance는 exact source에서 재생성·검증했고 관계 검증도 PASS였다. 실제 Secret, DB endpoint, OCI resource identifier와 raw Production row는 문서에 기록하지 않는다.

Runtime은 Production Backend와 별도의 loopback-only isolated Backend를 사용했고, performance 전용 schema/account를 사용했다. 그러나 Host와 OCI MySQL DB System 자체는 Production과 공유하므로 **데이터 격리는 되어 있지만 자원 격리는 아니다.**

## 3. 25 RPS 측정은 정상 stage가 아니라 warm-up 중 실패했다

I10K의 첫 stage는 25 RPS였다.

정상 계약은 다음과 같다.

```text
30초 warm-up
→ 120초 measurement
→ stage evidence assemble
→ safety gate
```

하지만 이번 실행은 warm-up 시작 약 15.9초 뒤 Host evidence collector가 timeout되면서 runner의 stop condition에 걸렸다. canonical runner는 collector 실패를 감지하고 k6를 종료했다.

따라서 이 실행에는 다음 값을 정상 stage 결과처럼 만들 수 없다.

```text
25 RPS actual throughput
p50 / p95 / p99 / max
정상 measurement 120초 결과
canonical stage PASS/FAIL summary
```

즉 “25 RPS p95가 몇 ms였다” 같은 숫자를 만들지 않는다. measurement가 시작되지 않았기 때문이다.

현재 공식 판정은 다음이다.

```text
I10K / 25 RPS
= FAIL / ABORTED DURING WARM-UP

50 / 100 / 150 RPS
= BLOCKED

200 / 250 RPS
= NOT IN SCOPE
```

실패한 stage를 자동 재실행하지 않고 먼저 원인을 분석한 것은 `PERF-V7-008`의 stop-on-fail 계약에 따른 것이다.

## 4. 짧은 warm-up에서도 Connection Pool 붕괴 흐름은 분명했다

Host evidence collector가 끝까지 살아 있지는 못했지만, 실패 직전 두 개의 주요 sample과 복구 sample은 남았다.

초기 sample:

```text
Hikari active / max = 0 / 10
Hikari pending      = 0
Tomcat busy         = 1
Backend CPU         = 0.04%
```

약 6초 뒤 sample:

```text
Hikari active / max = 10 / 10
Hikari pending      = 113
Tomcat busy         = 124
Backend CPU         = 7.22%
Host user CPU       = 7.53%
Host system CPU     = 1.31%
iowait              = 0
swap                = 0
```

복구 뒤:

```text
Hikari active       = 0
Hikari pending      = 0
Hikari idle         = 10
Tomcat busy         = 1
runtime healthy
restart             = 0
OOM                 = false
```

즉 실패 순간은 CPU 100%, swap 폭증, OOM 같은 자원 고갈 형태가 아니었다. **DB Connection 10개가 모두 점유된 뒤 Connection을 기다리는 요청이 급격히 늘어났고, 그 요청들이 Tomcat Thread까지 오래 붙잡는 흐름**이 먼저 관측됐다.

일반적인 Queueing 구조는 [[../../../Study/Performance/06. Tomcat HikariCP DB Queueing]]에서 설명한다.

## 5. lifecycle 진단은 “Connection을 얻기 전”보다 “얻은 뒤 Query가 오래 잡고 있음”을 가리켰다

첫 sample부터 복구까지의 누적 delta에는 실패 drain과 safety probe도 포함되어 있어 정상 stage 평균으로 사용할 수는 없다. 하지만 어느 구간이 비정상적으로 길었는지 비교하는 데는 의미가 있었다.

| 진단 구간 | 누적 구간 평균 |
| --- | ---: |
| Count query | 약 90.997 ms |
| List query | 약 6,658.668 ms |
| Repository total | 약 6,749.955 ms |
| Row mapping | 약 0.064 ms |
| matched connection acquire | 약 20,512.644 ms |
| connection lease | 약 6,756.513 ms |
| repository with connection | 약 6,749.953 ms |
| pre-repository | 약 1.624 ms |
| post-repository hold | 약 4.897 ms |
| release | 약 0.040 ms |

이 값은 timer들이 서로 겹칠 수 있으므로 더해서 전체 시간을 만들지 않는다.

가장 중요한 관계는 다음이었다.

```text
List query        ≈ 6.66초
Connection lease  ≈ 6.76초
Repository+conn   ≈ 6.75초
Row mapping       ≈ 0.064ms
Post-repo hold    ≈ 4.9ms
```

Connection을 빌린 뒤 대부분의 시간을 Repository/List SQL이 점유하고 있었다. Row mapping이나 Repository 이후 Connection hold는 너무 작았다.

따라서 첫 원인 후보는 다음처럼 좁혀졌다.

```text
I10K 데이터 증가
→ Product list SQL 실행시간 증가
→ 한 요청의 Connection lease 증가
→ Hikari 10개 모두 점유
→ pending 증가
→ connection acquire 대기
→ Tomcat busy 증가
→ 30초 connectionTimeout
```

Backend log에서도 `SQLTransientConnectionException`, `CannotCreateTransactionException`, 30초 Connection timeout이 다수 확인됐다. `CommunicationsException`, OOM은 확인되지 않았다.

HikariCP 공식 문서에 따르면 Pool이 `maximumPoolSize`에 도달하고 idle connection이 없으면 `getConnection()`은 `connectionTimeout`까지 기다린다. 따라서 pending과 acquire timeout은 이번 현상과 구조적으로 일치한다.

- [HikariCP - Configuration](https://github.com/brettwooldridge/HikariCP#frequently-used)
- [HikariCP - About Pool Sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)

## 6. “Pool 10이 작다”가 아니라 List SQL이 Connection을 오래 잡는 이유부터 조사했다

이 시점에서 가장 쉬운 수정은 `maximumPoolSize`를 늘리는 것이다. 하지만 그렇게 하지 않았다.

이유는 두 가지다.

첫째, pending은 “Pool이 무조건 작다”는 뜻이 아니다. SQL이 평소 50ms인데 갑자기 6초가 되면 같은 Pool 크기에서도 Connection 반환 속도가 크게 떨어진다.

둘째, Pool을 늘리면 동시에 DB에서 실행되는 무거운 SQL 수를 더 늘릴 수 있다. 근본 원인이 큰 목록 SQL이라면 DB가 더 많은 비싼 작업을 동시에 처리하게 되어 지연이 더 커질 가능성도 있다.

그래서 다음 순서를 선택했다.

```text
Pool size 조정 보류
→ List SQL 실제 구조 확인
→ Index / Statistics 확인
→ EXPLAIN으로 중간 행 수 확인
→ 가장 작은 SQL 작업량 감소 후보 찾기
```

## 7. DB 진단은 전용 계정과 read-only session에서 진행했다

실제 performance schema에 접속하되 Secret을 출력하지 않고 기존 protected password file과 runtime env를 이용해 MySQL client를 실행했다.

접속 뒤 대상 identity를 확인했다.

```text
DATABASE()    = pawcycle_perf_core_10k
CURRENT_USER  = performance 전용 account
```

현재 세션은 다음처럼 강제로 read-only로 바꿨다.

```sql
SET SESSION TRANSACTION READ ONLY;
```

확인:

```text
@@session.transaction_read_only = 1
@@autocommit                    = 1
```

이후 진단은 `SELECT`, `SHOW INDEX`, `INFORMATION_SCHEMA`, 일반 `EXPLAIN`만 사용했다.

**`EXPLAIN ANALYZE`는 사용하지 않았다.** MySQL 공식 문서상 `EXPLAIN ANALYZE`는 실제 SELECT를 실행하기 때문이다. 이미 List SQL이 수 초까지 늘어난 evidence가 있는 공유 DB System에서 추가 실행 부하를 넣을 필요가 없었다.

- [MySQL 8.4 - EXPLAIN Statement](https://dev.mysql.com/doc/refman/8.4/en/explain.html)

또한 다음 작업도 하지 않았다.

```text
ANALYZE TABLE
UPDATE HISTOGRAM
CREATE INDEX
ALTER TABLE
DB config 변경
```

## 8. 실제 Product 목록 SQL 구조

`GET /api/products`의 기본 요청은 `page=0`, `size=20`, `sort=NEWEST`다.

Repository의 List query는 크게 다음 구조다.

```text
products
JOIN categories
JOIN brands
LEFT JOIN parent category
LEFT JOIN main image
LEFT JOIN skus
LEFT JOIN inventories

+ 대표 SKU scalar subquery 4개
+ review avg/count scalar subquery 2개

WHERE public/active 조건
GROUP BY product projection
ORDER BY p.id DESC
LIMIT 20 OFFSET 0
```

대표 SKU 네 필드는 사실상 같은 대표 SKU 한 개를 찾기 위해 각각 다음 검색을 반복한다.

```sql
FROM skus s2
WHERE s2.product_id = p.id
  AND s2.status = 'ACTIVE'
ORDER BY s2.price ASC, s2.id ASC
LIMIT 1
```

그리고 `has_subscribable`, `purchasable`은 Product와 SKU/Inventory를 먼저 JOIN한 뒤 `MAX(CASE ...)`로 집계한다.

처음에는 대표 SKU dependent subquery 반복이 가장 큰 원인일 가능성도 열어 두었다. 그러나 이후 실험에서 이 subquery를 모두 제거해도 메인 `JOIN → GROUP BY → Sort → LIMIT` 구조가 그대로 남는 것을 확인했다.

## 9. 현재 Index는 존재하지만 실제 조회 패턴과 완전히 맞지는 않았다

### products

```text
PRIMARY(id)
uk_products_catalog_key(catalog_key)
idx_products_category(category_id, id)
idx_products_brand(brand_id, id)
```

### skus

```text
PRIMARY(id)
uk_skus_sku_code(sku_code)
idx_skus_product_display(product_id, display_order, id)
```

Inventory는 `sku_id` PRIMARY KEY로 조인되며, Review는 `(product_id, visible, created_at, id)` 계열 인덱스로 lookup된다.

대표 SKU 검색은 다음 열을 필요로 한다.

```text
product_id
status = ACTIVE
ORDER BY price, id
```

하지만 기존 SKU index는 `(product_id, display_order, id)`다. 따라서 대표 SKU 검색에서는 product_id lookup 뒤 status filter와 price/id 정렬이 별도로 발생했다.

Products도 기본 조건의 `display_status='PUBLIC'`을 선두에 포함한 인덱스는 없었다.

이 둘은 개선 후보였지만 **바로 새 Index를 만들지 않았다.** 더 큰 문제인 “20개 결과를 위해 모든 Product-SKU 관계를 먼저 집계하는가”를 먼저 확인할 필요가 있었기 때문이다.

## 10. 실제 데이터 분포는 옵티마이저 추정보다 훨씬 넓었다

실제 I10K 분포를 read-only 집계했다.

```text
products total = 10,000
PUBLIC         = 10,000 (100%)
eligible       = 10,000 (100%)

category_id 2  = 2,578
category_id 3  = 2,500
category_id 4  = 2,495
category_id 5  = 2,427

SKU ACTIVE     = 18,164
SKU INACTIVE   = 1,813
SKU avg/product = 1.9977
SKU min/max     = 1 / 3
```

`SHOW INDEX`와 `INFORMATION_SCHEMA`의 추정 통계는 다음 특징을 보였다.

```text
products table rows 추정 ≈ 9,768
category_id cardinality  = 4
brand_id cardinality     = 1

skus table rows 추정     ≈ 20,058
product_id cardinality   ≈ 9,034
```

Table row 추정 자체는 실제와 크게 다르지 않았다. 문제는 **조건 뒤에 몇 행이 살아남는지에 대한 분포 추정**이었다.

관련 컬럼의 `INFORMATION_SCHEMA.COLUMN_STATISTICS`를 조회했지만 결과는 `Empty set`이었다.

즉 다음 컬럼들에 histogram이 없었다.

```text
products.display_status
products.category_id
products.brand_id
skus.status
skus.product_id
```

히스토그램 부재가 곧바로 root cause라는 뜻은 아니다. 그러나 `PUBLIC=100%`, `brand 하나=100%`처럼 극단적인 실제 분포를 옵티마이저가 충분히 알지 못할 가능성을 확인하는 근거가 됐다.

- [MySQL 8.4 - Optimizer Statistics](https://dev.mysql.com/doc/refman/8.4/en/optimizer-statistics.html)

## 11. EXPLAIN은 실제 19,977행을 약 108행 규모로 예상했다

기본 List query에 `EXPLAIN FORMAT=TREE`와 `EXPLAIN FORMAT=JSON`을 사용했다.

Product 접근은 다음과 같았다.

```text
Index lookup on p using idx_products_category
(category_id = c.id)

estimated rows ≈ 2,442
```

category_id cardinality가 4이고 products 추정 row가 약 9,768이므로 `9768 / 4 ≈ 2442`와 일치한다.

문제는 다음 filter 단계였다.

```text
Filter:
p.brand_id = b.id
AND p.display_status = 'PUBLIC'

estimated rows ≈ 244.2
```

실제 해당 category에 있는 Product는 거의 전부 조건을 통과하지만 옵티마이저는 약 10%만 남는 것으로 예상했다.

이 추정은 이후 join에서 더 크게 벌어졌다.

```text
실행 계획의 Product join 예상
≈ 48.84 rows

실제 eligible Product
= 10,000 rows
```

그리고 SKU를 붙인 뒤 실행 계획은:

```text
estimated rows ≈ 108.44
```

로 봤다.

실제 join count를 직접 확인하면:

```text
Product = 10,000
joined rows = 19,977
```

이다.

즉 `GROUP BY` 직전 규모를 단순 비교하면:

```text
estimated ≈ 108.44
actual    = 19,977

약 184배 차이
```

가 있었다.

이것이 “옵티마이저 추정이 틀렸다”는 사실은 보여 주지만, 그 자체로 모든 지연의 root cause를 확정하지는 않는다. 더 중요한 것은 **실제 SQL 구조가 20개 결과를 반환하기 전에 19,977개의 Product-SKU join row를 집계하고 있다는 사실**이었다.

## 12. 기존 기본 쿼리는 LIMIT 20이 가장 뒤에 있었다

기본 실행 계획의 큰 흐름은 다음이었다.

```text
categories / brands
→ products
→ main image
→ skus
→ inventories
→ Aggregate using temporary table
→ Table scan on <temporary>
→ Sort p.id DESC
→ LIMIT 20
```

즉 API는 20개 Product를 요청하지만 DB 관점에서는:

```text
10,000 Product 후보
→ 19,977 Product-SKU rows
→ Product별 GROUP BY
→ temporary table
→ sort
→ 20개 반환
```

이었다.

여기서 `temporary table` 자체를 문제로 지목하지 않았다. Product별 `MAX(CASE ...)` 집계를 위해 임시 집계가 필요할 수 있다. 중요한 것은 **임시 집계에 들어가는 입력이 20개 Product의 SKU가 아니라 전체 I10K의 SKU라는 점**이다.

## 13. 대표 SKU / Review subquery를 제거해도 큰 구조는 그대로였다

원인을 분리하기 위해 대표 SKU 4개와 Review 2개 scalar subquery를 제거한 축약 SQL에 `EXPLAIN FORMAT=TREE`를 수행했다.

결과는 여전히 다음이었다.

```text
products
→ skus
→ inventories
→ Aggregate using temporary table
→ temporary scan
→ sort
→ LIMIT 20
```

즉 dependent subquery 반복은 분명 개선 후보지만, **I10K 전체를 먼저 SKU와 join한 뒤 GROUP BY하는 메인 구조와 독립적인 문제**였다.

이 진단으로 우선순위는 다음처럼 바뀌었다.

```text
1. 메인 Product + SKU + Inventory 집계 범위
2. optimizer cardinality 과소 추정
3. 현재 index 구성
4. 대표 SKU dependent subquery 반복
```

## 14. Page-first counterfactual plan에서 큰 집계 범위가 page 단위로 줄었다

다음으로 실제 코드를 바로 수정하지 않고 **가상 page-first SQL**을 `EXPLAIN`했다.

먼저 Product 20개를 내부 derived table에서 고른 뒤, 외부에서 SKU와 Inventory를 붙이는 구조다.

```text
filters
→ Product page LIMIT 20
→ SKU join
→ Inventory join
→ GROUP BY
```

실행 계획은 다음처럼 바뀌었다.

```text
Materialize base
  → Limit: 20
     → Product selection

Table scan on base
→ Index lookup SKU by base.id
→ Inventory PK lookup
→ Aggregate temporary table
```

옵티마이저의 cost 값 자체를 실제 ms로 해석하면 안 되지만, 계획 모양은 명확하게 달라졌다.

```text
기존 main aggregate cost 표시 ≈ 559
page-first 후보 cost 표시      ≈ 24.7
```

중요한 근거는 비용 숫자의 비율이 아니라 **SKU/Inventory 집계가 전체 10,000 Product 뒤가 아니라 page 20 Product 뒤로 이동했다는 것**이다.

## 15. Product를 PRIMARY reverse scan하게 하면 최신 20개 후보를 더 일찍 고를 수 있었다

Page-first 내부 Product selection도 기존 옵티마이저는 category부터 시작해 `idx_products_category`를 사용했다.

그래서 진단용으로만 다음 counterfactual을 확인했다.

```sql
FROM products p FORCE INDEX (PRIMARY)
...
ORDER BY p.id DESC
LIMIT 20
```

처음에는 `STRAIGHT_JOIN`까지 같이 사용해 Product-first를 강제했다.

실행 계획:

```text
Index scan on p using PRIMARY (reverse)
→ Filter display_status
→ category / brand 확인
→ LIMIT 20
```

그 뒤 `STRAIGHT_JOIN`만 제거하고 다시 확인했는데 동일하게 `PRIMARY (reverse)`가 유지됐다.

따라서:

```text
STRAIGHT_JOIN = 불필요
FORCE INDEX(PRIMARY) = 계획을 Product reverse scan으로 바꾸는 효과 확인
```

까지는 증명했다.

그러나 `FORCE INDEX`를 첫 구현에 넣기로 결정하지 않았다.

검색어, category, brand, 가격, facet 같은 필터가 있는 요청에서는 다른 인덱스가 더 유리할 수 있고, 향후 데이터 분포가 바뀌면 강제 PRIMARY가 오히려 손해가 될 수 있기 때문이다.

이번 실험에서 `FORCE INDEX`는 **다른 실행 경로가 가능한지 확인하는 진단 도구**로만 사용했다.

## 16. 전체 Projection을 유지한 page-first 계획도 동일한 방향을 확인했다

마지막으로 실제 List query의 projection을 거의 그대로 유지했다.

```text
base derived table
- Product / Category / Brand
- ORDER BY p.id DESC
- LIMIT 20

outer
- main image
- SKU
- Inventory
- GROUP BY
- 대표 SKU subquery
- Review subquery
```

`EXPLAIN` 결과:

```text
Materialize base
→ LIMIT 20
→ base scan
→ main image
→ SKU lookup by base.product_id
→ Inventory PK lookup
→ temporary aggregate

대표 SKU / Review dependent subquery
→ base.product_id에 대해서만 평가
```

즉 temporary table과 dependent subquery가 완전히 사라지지는 않는다. 대신 **그 비싼 연산의 outer 범위가 page 단위로 제한된다.**

이번 진단에서 목표는 “EXPLAIN을 예쁘게 만드는 것”이 아니라 **큰 중간 결과를 줄이는 것**이었다.

## 17. 왜 NEWEST / RECOMMENDED만 1차 page-first 대상으로 잡았는가

현재 Repository 정렬은 다음과 같다.

```text
NEWEST       → p.id DESC
RECOMMENDED  → p.id DESC
PRICE_ASC    → representative_price
PRICE_DESC   → representative_price
RATING       → average_rating
REVIEW_COUNT → review_count
```

`NEWEST`, `RECOMMENDED`는 Product 자체의 `id`만으로 순위를 결정할 수 있다. 기존 dynamic filter도 가격·구독가능·구매가능·facet 조건을 `EXISTS` 형태로 page selection 전에 평가할 수 있다.

반면 가격·평점·리뷰수는 child/subquery 계산 결과를 먼저 구해야 순위가 정해진다.

따라서 다음처럼 일괄 page-first를 적용하면 결과 의미가 달라질 수 있다.

```text
잘못된 예
Product 20개를 먼저 임의 선택
→ 그 20개 가격 계산
→ PRICE_ASC

실제 필요한 의미
전체 eligible Product 가격 계산/정렬 의미
→ 그중 상위 20개
```

그래서 1차 최소 수정 범위를 다음으로 제한했다.

```text
KEEP
NEWEST / RECOMMENDED page-first

DEFER
PRICE_ASC / PRICE_DESC
RATING / REVIEW_COUNT
```

## 18. 1차 개선에서 의도적으로 제외한 것

이번 진단으로 여러 후보가 보였지만 한 번에 넣지 않는다.

### DEFER

```text
FORCE INDEX(PRIMARY)
신규 products index
신규 skus representative index
Histogram 생성
ANALYZE TABLE
대표 SKU 4중 scalar subquery 통합
다른 sort mode 재설계
```

각 항목은 성능 개선 가능성이 있지만 page-first와 동시에 넣으면 **어떤 변경이 실제 효과를 냈는지 분리하기 어렵다.**

### 현재 REJECT

```text
Hikari pool 확대
Connection timeout 증가
Redis / Cache
Async / Queue
Multi-instance / Load Balancer
Read Replica
```

현재 측정 근거가 가리키는 첫 병목은 단일 목록 SQL의 긴 Connection lease다. 따라서 더 많은 기술을 추가하기 전에 SQL 작업량 자체를 줄이는 것이 우선이다.

## 19. Host evidence collector timeout은 아직 별도 미확정 항목이다

runner가 최종 중단한 직접 사건은 Host evidence collector timeout이다.

애플리케이션이 당시 Hikari pending 113, Tomcat busy 124까지 올라갔기 때문에 Actuator/metric 수집 요청도 서비스 내부 Queueing의 영향을 받았을 가능성은 있다.

하지만 **정확히 어떤 collector call이 timeout되었는지 원본 evidence에 보존되지 않았다.**

따라서 현재 판정은:

```text
Application saturation과 collector timeout의 연관 가능성 = 높음
직접 원인 확정 = 아님
```

이다.

SQL correction 뒤 25 RPS를 재측정할 때 collector가 정상 동작하면 강한 간접 근거가 된다. 다시 timeout된다면 collector 자체의 timeout/probe 경로를 별도 진단해야 한다.

## 20. 현재 구현 상태와 Codex Delta

read-only 진단이 끝난 뒤 1차 구현 범위를 Final Lightweight Delta Prompt로 분리했다.

핵심은 다음 하나다.

```text
NEWEST / RECOMMENDED

기존
모든 eligible Product
→ SKU/Inventory join
→ GROUP BY
→ sort
→ LIMIT/OFFSET

변경 후보
filters
→ Product page ORDER BY id DESC + LIMIT/OFFSET
→ page-scoped SKU/Inventory join
→ GROUP BY / projection
```

다음은 보존한다.

```text
count query
filter semantics
pagination metadata
projection contract
representative SKU / review 의미
diagnostic timer 의미
다른 sort mode 동작
```

Codex에는 저장소 구현과 Backend validation, Draft PR handoff까지만 요청했다.

**OCI 배포, DB mutation, `ANALYZE TABLE`, k6 재부하는 Codex 작업 범위가 아니다.**

현재 이 문서를 작성하는 시점에는 correction이 아직 구현·검증·재측정 완료된 상태가 아니므로 `Implemented`, `Verified`, `Production Verified`로 올려 적지 않는다.

## 21. 다음 검증 순서

Repository correction이 준비되면 먼저 코드 의미와 regression을 확인한다.

```text
NEWEST page 0
NEWEST non-zero page
RECOMMENDED 동일 의미
filtered page-first
representative projection
availability
기존 non-page-first sort mode
Backend test/build
```

그 뒤 별도 승인된 실제 OCI 단계에서 **동일 I10K 25 RPS**를 다시 측정한다.

```text
수정 Source identity 고정
→ I10K dataset 계약 유지
→ isolated runtime
→ safety preflight
→ 25 RPS warm-up + measurement
→ List query / lease / Hikari / Tomcat 비교
→ PASS일 때만 다음 RPS 검토
```

50 RPS 이상으로 바로 뛰지 않는다. 이번 실패 지점이 25 RPS였기 때문에 correction 효과를 비교하는 첫 조건도 25 RPS다.

재측정에서 특히 볼 값은 다음이다.

| 계층 | 핵심 비교 |
| --- | --- |
| 사용자 결과 | actual RPS, dropped, error, p50/p95/p99/max |
| Repository | count/list/mapping 시간 |
| Lifecycle | acquire, lease, repo-with-connection |
| Hikari | active, idle, pending |
| Tomcat | busy thread |
| Host/JVM | CPU, memory, GC, restart/OOM |
| OCI MySQL | CPU, connections, statement 지표 |

## 22. 현재 판정

현재까지의 근거를 한 문장으로 줄이면 다음과 같다.

> I10K에서 Product 목록 SQL은 최종 20개를 반환하기 전에 10,000 Product와 19,977 SKU 관계를 먼저 집계했고, 그 List query가 약 6.66초 동안 Connection을 점유하면서 Hikari 10/10 포화와 pending 폭증을 만들었다. Read-only 실행 계획 진단에서 Product page를 먼저 20개로 제한하면 SKU/Inventory 집계 범위를 page 단위로 줄일 수 있음을 확인했으므로, 첫 correction은 NEWEST/RECOMMENDED page-first로 제한한다.

현재 상태:

```text
I10K dataset / runtime preparation = 완료
25 RPS actual stage               = FAIL / warm-up aborted
Root mechanism                    = list-query 장기 Connection 점유 → pool queueing
SQL 구조 원인                     = 강한 근거 확보
page-first correction             = 구현 진행 중
25 RPS 재측정                     = 미실행
50 / 100 / 150                    = BLOCKED
100K                              = DEFER
Production Verified               = 아님
```

이번 과정에서 가장 중요한 판단은 기술을 추가하지 않은 것이다.

```text
측정된 문제
→ Connection lease가 길다
→ List SQL이 길다
→ 왜 긴지 실제 Query Plan 확인
→ 전체 join/aggregate 뒤 LIMIT이라는 작업량 문제 확인
→ page-first라는 작은 구조 변경 선택
→ 동일 조건 재측정 예정
```

이 흐름이 PawCycle 성능 단계의 기본 원칙인 **측정 → 원인 분리 → 가장 작은 개선 → 동일 조건 재검증**과 정확히 일치한다.
