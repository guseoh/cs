# OCI Performance DB Provisioning과 재검증

이 문서는 [[06. OCI Re-baseline Preflight 기록]] 이후, Catalog I0 / I10K 성능 실험을 위해 **성능 전용 MySQL schema와 account를 실제 OCI Managed MySQL에 준비한 과정**을 기록한다.

목표는 단순히 DB와 계정을 만드는 것이 아니었다. Production Catalog와 권한을 분리하고, 실패 중 생긴 부분 적용 상태를 근거로 재구성하고, Secret을 노출하지 않은 채 실제 인증과 권한 경계를 확인한 뒤 Production/Observability 상태가 그대로인지 재검증하는 것이 목적이었다.

작업 기준 PawCycle canonical main은 다음이었다.

~~~text
9d2db627486b2940a7c357aefe66ebe927c974af
~~~

Repository contract의 고정 identity는 다음과 같다.

~~~text
I0 schema     pawcycle_perf_core_control
I10K schema   pawcycle_perf_core_10k
DB account    pawcycle_perf_catalog
~~~

실제 password, Production DB endpoint, resource identifier, administrator grant 원문은 기록하지 않는다.

## 1. 잘못된 schema 조회를 정확한 identity로 다시 확인

초기 수동 확인에서는 schema 이름에서 `core`가 빠진 다른 이름을 조회하는 검증 오류가 있었다. 해당 `Empty set`은 계약상 schema 미존재 근거가 될 수 없었다.

정확한 두 schema 이름과 performance account를 read-only로 다시 조회했고 당시 결과는 모두 미존재였다.

~~~text
pawcycle_perf_core_control = missing
pawcycle_perf_core_10k = missing
pawcycle_perf_catalog = missing
~~~

따라서 기존 객체를 재사용하거나 덮어쓰는 작업이 아니라 clean provisioning이 필요하다고 판단했다.

## 2. DB mutation 직전 Runtime Gate 재확인

실제 schema/account mutation 직전에 Production과 Observability 상태를 다시 확인했다.

첫 실행 명령에서는 두 가지 operator command 오류가 있었다.

첫째, performance exact-source tree에 Production diagnostic script가 있을 것이라고 잘못 가정해 `DIAG_SCRIPT_MISSING`으로 중단됐다. 실제 계약은 `/opt/pawcycle/source/repo` Git object store에서 승인 SHA의 `infra/production/diagnose-backend-state.sh`만 임시 파일로 materialize하는 방식이었다.

둘째, `/opt/pawcycle/state/https-domain`에 완성된 `https://...` URL이 들어 있다고 잘못 가정해 `INVALID_HTTPS_ORIGIN`으로 중단됐다. 실제 state에는 승인 domain만 저장되고, 진단 시 `https://`를 조합해야 했다.

두 실패 모두 DB mutation 전에 발생했다. 저장소 계약을 다시 확인하고 command를 수정한 뒤 Gate는 다음 상태로 통과했다.

~~~text
production_assessment=READY
release_coordination=stable
backend=healthy
api_products_http=200
metrics_proxy_http=200
status=NORMAL
prometheus_target=up
PERF_RUNTIME_GATE=PASS
~~~

핵심은 명령이 실패했을 때 환경 이상으로 간주해 다른 계층을 건드리지 않고, source 위치와 state contract부터 다시 확인한 것이다.

## 3. 첫 provisioning 시도와 부분 적용

처음 provisioning은 두 schema를 만든 뒤 performance account를 생성하는 순서였다.

다음 재실행에서 첫 schema에 대해 `database exists`가 발생했다. `IF NOT EXISTS`로 그대로 밀어붙이지 않고 현재 상태를 read-only로 재구성했다.

확인 결과:

~~~text
pawcycle_perf_core_control
→ 존재
→ utf8mb4 / utf8mb4_0900_ai_ci
→ table 0

pawcycle_perf_core_10k
→ 존재
→ utf8mb4 / utf8mb4_0900_ai_ci
→ table 0

pawcycle_perf_catalog
→ 미존재
~~~

즉 실패한 작업의 결과는 **두 빈 schema까지만 생성된 partial provisioning**이었다. 아직 import/Flyway table도 없었고 performance account도 없었다.

따라서 schema를 삭제하고 처음부터 다시 만드는 대신 이미 계약과 일치하는 두 빈 schema를 유지하고 account 생성만 이어가는 최소 수정 방식을 선택했다.

## 4. password policy를 추측해서 실패

performance account password를 처음에는 무작위 hex 문자열로 만들었다. 길이는 충분했지만 Managed MySQL의 실제 password policy를 충족하지 못해 account 생성이 `ERROR 1819`로 거부됐다.

실제 policy를 조회한 결과:

~~~text
policy = MEDIUM
minimum length = 8
mixed case = required
number = required
special character = required
user-name check = ON
~~~

hex 문자열은 소문자와 숫자만 포함하므로 대문자와 특수문자 조건을 만족하지 못했다.

이 실패에서 중요한 점은 “충분히 긴 random password”와 “DBMS가 실제로 허용하는 password”가 같지 않다는 것이다. 운영 자동화에서는 password policy를 추측하지 말고 실제 DBMS 계약을 확인해야 한다.

## 5. MySQL이 password를 생성하도록 변경

두 번째 방식에서는 애플리케이션이나 shell이 정책을 흉내 내서 password를 만들지 않았다.

~~~text
CREATE USER ... IDENTIFIED BY RANDOM PASSWORD
~~~

를 사용해 MySQL이 자신의 policy를 만족하는 값을 생성하도록 했다.

생성 결과는 터미널이나 Git에 출력하지 않고 root-only 임시 파일에서 password 필드만 추출해 repository 밖 runtime secret file에 저장했다.

최종 Secret 경계:

~~~text
/opt/pawcycle/performance/catalog/db-password
owner = root:root
mode = 0600
~~~

값 자체는 이 문서와 Issue/PR/log에 기록하지 않는다.

performance account 존재 여부를 administrator read-only 조회로 확인했고 실제 계정이 생성됐음을 확인했다.

## 6. schema-local 권한만 부여

performance account에는 다음 두 schema에만 권한을 부여했다.

~~~text
pawcycle_perf_core_control.*
pawcycle_perf_core_10k.*
~~~

Flyway가 빈 performance schema를 초기화해야 하므로 schema-local DDL을 포함한 권한이 필요하다.

최종 `SHOW GRANTS`의 의미는 다음 세 항목으로 제한됐다.

~~~text
USAGE ON *.*
ALL PRIVILEGES ON pawcycle_perf_core_control.*
ALL PRIVILEGES ON pawcycle_perf_core_10k.*
~~~

확인되지 않은 것:

~~~text
WITH GRANT OPTION 없음
다른 schema 권한 없음
Production schema 권한 없음
global ALL PRIVILEGES ON *.* 없음
~~~

`USAGE ON *.*`는 전역 데이터 권한이 아니라 계정이 존재하고 인증될 수 있음을 나타내는 기본 grant다.

따라서 performance account의 privilege boundary는 repository contract와 일치한다.

## 7. Secret file을 사용한 실제 인증

계정 존재와 GRANT 원문만으로 끝내지 않았다.

repository 밖 root-only password file을 실제로 읽어 `pawcycle_perf_catalog`로 Managed MySQL에 접속하고 `SELECT 1`을 실행했다.

~~~text
PERF_DB_AUTH=PASS
~~~

이 검증으로 다음 연결이 실제로 성립함을 확인했다.

~~~text
runtime secret file
→ performance DB account
→ OCI Managed MySQL authentication
~~~

Secret 내용 자체는 출력하지 않았다.

## 8. DB mutation 후 Production/Observability 재검증

schema/account/grant 작업 뒤 같은 Production/Observability Gate를 다시 실행했다.

결과:

~~~text
production_assessment=READY
release_coordination=stable
docker_query=ok
backend=healthy
api_products_http=200
metrics_proxy_http=200
status=NORMAL
prometheus_target=up
PERF_POST_PROVISION_GATE=PASS
~~~

따라서 이번 performance DB provisioning 뒤에도 Production과 Observability의 확인된 상태는 정상으로 유지됐다.

이 결과는 전체 Re-baseline의 Production Verified를 뜻하지 않는다. DB provisioning substep이 실제 운영 환경에서 적용되고 재검증됐다는 근거일 뿐이며 I0/I10K import, isolated runtime, k6 load는 아직 미실행이다.

## 다음 단계

DB provisioning Gate는 닫혔다. 다음 실제 실행은 I0 control dataset을 exact approved source에서 생성하고 immutable provenance를 만드는 것이다.

~~~text
catalog-core-control-v1
32 Product
seed 20260826
→ manifest/report 생성
→ root-owned immutable file boundary
→ exact source로 재생성 비교
→ provenance.json 생성
→ runtime config 준비
→ import/runtime 전 READY/NORMAL 재확인
~~~

I0 측정이 완료되기 전에는 I10K와 병목 분석으로 넘어가지 않는다.
