
## 1. 이 서비스가 푸는 문제: 반복 구매

PawCycle은 사료·간식·모래·배변 패드 같은 **반려동물 소모품**을 파는 커머스다. 이 상품군의 특징은 한 번 사고 끝나지 않는다는 것이다. 사료는 몇 주마다 떨어지므로 같은 물건을 정해진 주기로 계속 받고 싶은 수요가 생긴다. 

그래서 이 프로젝트에는 구매 흐름이 두 개 있다.

![[Pasted image 20261113135858.png|두 구매 흐름|450]]
- 일반 구매(청록): 장바구니에 담고 → 체크아웃해서 재고·쿠폰을 **예약**하고 → 토스 결제 승인에서 확정 → 배송한다.
- 정기배송(보라): 플랜을 고르고 → 구독을 만들 때 가격·구성을 **스냅샷으로 고정**하고 → 회차가 오면 → 스케줄러가 자동으로 주문을 만들고 → 정기 결제한다.
- 공유 기반(회색): 두 흐름은 회원, 상품·SKU, 재고, 결제 테이블을 함께 쓴다.
	- 결제 테이블은 `type`컬럼으로 일반 결제(`NORMAL`)와 정기결제(`BILLING`)를 구분한다.

| 용어               | 뜻                                   | 구분하는 이유                      |
| ---------------- | ----------------------------------- | ---------------------------- |
| 상품 · SKU         | 상품은 “연어 사료”, SKU는 “연어 사료 2kg”       | 가격·재고·주문은 SKU에 걸린다           |
| 판매 상태 · 구독 가능 여부 | 일반 구매로 팔 수 있는가 · 정기배송 대상으로 고를 수 있는가 | **기록** 1차 MVP부터 별개 개념으로 정의했다 |
| 플랜 · 플랜 버전       | 종별 패키지 상품 · 그 가격과 구성의 한 판           | 가격이 바뀌면 버전을 새로 만든다           |
| 스냅샷              | 가입 시점의 가격·구성 복사본                    | 플랜이 바뀌어도 기존 고객 조건을 지킨다       |
| 회차 · 정기 주문       | 예정된 배송 · 그 회차를 실제로 처리한 결과           | 한 회차에 주문은 최대 하나              |

> [!more]-  🤷‍♂️**구독 스냅샷(Snapshot)**
> ##### 1. 스냅샷이란?
> 구독을 신청한 시점의 **가격·상품 구성·배송 주기를 별도로 저장해 보존하는 방식**이다.
> 
> 이후 판매 플랜의 가격이나 구성이 변경되더라도 기존 고객의 구독 조건이 의도치 않게 바뀌지 않도록 한다.
> 
> | 항목       | 구독 신청 당시      | 이후 판매 플랜 변경         |
> | -------- | ------------- | ------------------- |
> | 패키지 가격   | 30,000원       | 35,000원             |
> | 상품 구성    | 사료 2개 + 간식 1개 | 사료 1개               |
> | 배송 주기    | 4주            | 2주                  |
> | 기존 구독 고객 | **기존 조건 유지**  | **변경 사항 자동 적용 안 됨** |
> ##### 2. 구현
> 
> ```java
> long subscriptionId =
>     store.insertSubscription(
>         memberId, versionId, cycle,
>         petId, created, next);
> 
> long snapshotId =
>     store.createSnapshot(
>         subscriptionId,
>         versionId,
>         cycle,
>         version.packagePriceKrw());
> 
> store.setCurrentSnapshot(subscriptionId, snapshotId);
> store.insertScheduled(subscriptionId, next);
> ```
> 1. `Subscription` 생성 — 누가 어떤 정기배송을 구독하는지 저장한다.
> 2. `SubscriptionSnapshot` 생성 — 신청한 플랜의 가격과 배송 주기, 구성 정보를 별도로 보존한다.
> 3. `currentSnapshotId` 연결 — 현재 구독에 적용되는 조건을 지정한다.
> 4. `SubscriptionSchedule` 생성 — 다음 정기배송 예정 회차를 등록한다.


## 2. 도메인 판단이 스키마에 남긴 흔적

#### 1차 MVP의 구독: SKU 하나를 고르는 단순한 약속
```sql
-- backend/src/main/resources/db/migration/V2__create_subscriptions.sql
CREATE TABLE subscriptions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    sku_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    delivery_cycle_weeks INT NOT NULL,
    created_date DATE NOT NULL,
    next_order_date DATE NOT NULL,
    ...
    CONSTRAINT chk_subscriptions_quantity CHECK (quantity BETWEEN 1 AND 10),
    CONSTRAINT chk_subscriptions_delivery_cycle CHECK (delivery_cycle_weeks IN (2, 4, 8)),
    CONSTRAINT chk_subscriptions_date_order CHECK (next_order_date > created_date)
);
```
- `sku_id` 하나 → 구독 하나는 SKU 하나만 대상으로 한다.
- `quantity BETWEEN 1 AND 10` → 구독 수량은 1~10
- `delivery_cycle_weeks IN (2, 4, 8)` → 배송 주기는 2주, 4주, 8주
- `next_order_date > created_date` → 다음 주문 예정일 = 생성일 + 배송 주기

규칙을 애플리케이션 코드뿐 아니라 DB의 CHECK 제약에도 걸어 둔 것이 이 프로젝트의 습관이다.

#### 2차 MVP의 구독: 스냅샷으로 약속을 고정한다

2차 MVP에서 구독은 “SKU 하나”가 아니라 “종별 패키지 플랜”을 구독하는 것으로 바뀌었다. 

핵심 문제는 **판매자가 플랜 가격을 올리면, 이미 가입한 고객의 다음 결제 금액도 바뀌어야 하는가?**
- 답은 “아니다”
- 가격·구성 변경은 새 플랜 버전으로만 하고, 기존 구독 가격은 자동으로 바꾸지 않는다.

```sql
-- V3__add_second_mvp_subscription_schema.sql (발췌)
CREATE TABLE plan_versions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    plan_id BIGINT NOT NULL,
	package_price_krw BIGINT NOT NULL,       -- 지금 파는 가격
    ...
);
ALTER TABLE subscription_plans
    ADD CONSTRAINT fk_subscription_plans_current_version
        FOREIGN KEY (current_plan_version_id, id) REFERENCES plan_versions (id, plan_id);

CREATE TABLE subscription_snapshots (
    id BIGINT NOT NULL AUTO_INCREMENT,
    subscription_id BIGINT NULL,
    source_plan_version_id BIGINT NOT NULL,
    package_total_krw BIGINT NOT NULL,        -- 이 고객이 약속받은 가격
    delivery_cycle_weeks INT NOT NULL,
    ...
);
CREATE TABLE subscription_schedules (
    ...
    effective_snapshot_id BIGINT NULL,
    CONSTRAINT uk_schedules_subscription_date UNIQUE (subscription_id, scheduled_date),
    CONSTRAINT chk_schedules_status CHECK (status IN ('SCHEDULED', 'SKIPPED', 'HELD', 'CANCELED'))
);
CREATE TABLE pending_plan_changes (
    subscription_id BIGINT NOT NULL,          -- PK: 구독당 대기 변경 하나
    snapshot_id BIGINT NOT NULL,
    target_schedule_id BIGINT NOT NULL,       -- 어느 회차부터 적용할지
    ...
);
```

- **가격이 두 번 저장된다.**
	- `plan_versions.package_price_krw`는 “지금 파는 가격”, `subscription_snapshots.package_total_krw`는 “이 고객이 약속받은 가격”이다.
	- 정규화 원칙을 보면 중복이지만, 둘은 의미가 다른 값이다.
	- 스냅샷이 플랜 버전을 참조하지 않고 금액을 복사해 두므로, 플랜이 바뀌어도 고객의 약속은 그대로다.
- **복합 외래 키로 “엉뚱한 버전” 을 막는다.**
	-
