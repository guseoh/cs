# RDS Migration Troubleshooting

RDS 전환에서는 AWS resource 생성보다 shell, runtime state와 target identity 경계에서 여러 실제 실패가 발생했다. 각 문제는 Production source를 보존한 채 fail-close했고, 작은 회귀 테스트로 다시 고정했다.

## Windows AWS CLI CRLF가 SG 비교를 깨뜨린 문제

RDS base preflight를 Windows PowerShell, Git for Windows Bash와 AWS CLI v2에서 실행했다. AWS describe 결과와 실제 EC2 SG 연결은 맞았지만 `--output text` 끝의 carriage return `\r`가 membership 비교 문자열에 남아 `NO_MATCH`가 됐다.

처음에는 실제 SG 연결이나 AWS 조회 권한 문제를 의심할 수 있었다. Raw shell representation에서 `\r`를 확인하면서 AWS resource가 아니라 platform newline 문제로 좁혔다. Describe-only AWS 출력의 carriage return만 제거하고 기존 allowlist·fail-closed 검증을 유지했다. LF와 CRLF fixture를 모두 회귀 테스트에 넣었다.

근거: [Issue #155](https://github.com/guseoh/pawcycle-commerce/issues/155), [PR #156](https://github.com/guseoh/pawcycle-commerce/pull/156).

## Materialized env의 quoting을 raw value로 오해한 문제

Migration rehearsal에서 OPS-013 backup의 isolated restore와 schema·Flyway·core-table manifest는 일치했다. 그러나 candidate restore가 `candidate restore database name is invalid`로 중단됐다.

Materializer는 shell-safe single-quoted 형식으로 env file을 기록했다. 기존 backup/restore script는 `cut -d= -f2-` 결과에서 quote를 decode하지 않고 DB name과 credential로 사용했다. Test fixture는 quote 없는 값만 넣어 실제 materializer 계약을 재현하지 못했다.

`source`나 `eval`로 env file을 실행하면 malicious content와 shell side effect 위험이 생길 수 있어 사용하지 않았다. Managed single-quoted 형식만 안전하게 decode하는 parser를 추가하고, DB name과 user는 decode 후 기존 allowlist를 다시 적용했다. Password는 root-only temporary file에 전달했다. 기존 candidate fixture는 quote 없는 `KEY=value`만 사용해 실제 materializer 출력을 재현하지 못했으므로 fixture 자체를 production 형식으로 바꿨다.

근거: [PR #160](https://github.com/guseoh/pawcycle-commerce/pull/160).

## 같은 Application SHA에서 runtime만 바꾸지 못한 문제

RDS cutover는 Application code를 바꾸지 않고 Docker datasource runtime을 RDS runtime으로 바꾸는 작업이었다. 현재 Application SHA와 target SHA가 같자 기존 release boundary가 activation을 막았다.

Same-SHA를 무조건 허용하면 새로운 control script나 runtime을 승인 없이 채택할 수 있다. 수정은 현재와 target SHA가 같고 stored contract SHA와 current Control HEAD가 일치하는 경우만 기존 protected activation을 허용했다. Control HEAD가 바뀌었다면 old/new Control SHA의 명시 approval과 Backend quiesce를 요구하고 성공 뒤에만 새 contract state를 게시했다. 기존 release 회귀는 SHA가 바뀌는 배포와 동일 SHA adoption을 중심으로 했고 “Application SHA는 같지만 runtime과 Control 승인이 바뀌는 전환”을 독립 상태로 모델링하지 않았다. 수정 뒤에는 승인 누락·불일치와 Backend 실행 중 상태가 activation 전에 실패하는 전용 회귀를 추가했다.

근거: [PR #163](https://github.com/guseoh/pawcycle-commerce/pull/163).

## Scheduler preflight가 preserved source DB를 본 문제

Cutover 뒤 Scheduler activation preflight가 active RDS가 아니라 rollback을 위해 보존한 Docker MySQL을 query했다. Preflight가 PASS해도 실제 active datasource의 schema와 due candidate를 검사한 것이 아니므로 잘못된 승인으로 이어질 수 있었다.

Runtime datasource를 기준으로 query target을 분기했다. Docker runtime은 기존 MySQL service를 사용하고, RDS runtime은 Backend와 같은 network namespace의 ephemeral pinned MySQL client가 private RDS endpoint를 read-only query하도록 했다. Aggregate marker에 `DOCKER_MYSQL` 또는 `RDS` target을 남기고 raw row와 credential은 출력하지 않았다. 기존 검증은 Docker runtime의 source service query가 성공하는지만 보았기 때문에 cutover 후에도 preserved source를 읽는 잘못된 routing을 정상으로 받아들일 수 있었다. 새 회귀는 RDS runtime에서 Docker source query가 한 번이라도 사용되면 실패하도록 target identity를 고정했다.

근거: [PR #164](https://github.com/guseoh/pawcycle-commerce/pull/164).

## MySQL client에 SQL stdin이 전달되지 않은 문제

RDS target routing을 고친 뒤 실제 preflight는 `DATABASE_PREFLIGHT_TARGET=RDS`까지 갔지만 schema 결과가 비어 fail-close했다. Network와 credential을 먼저 의심할 수 있었으나 ephemeral `docker run`에서 pipe로 보낸 SQL이 container stdin에 연결되지 않은 것이 원인이었다.

`--interactive`를 추가해 stdin을 전달했고, 이 option이 빠지면 fixture가 즉시 실패하도록 회귀 테스트를 보강했다. 기존 fake 실행은 command가 호출됐다는 사실은 확인했지만 SQL이 container stdin까지 도달하는지는 증명하지 못했다. 수정은 Production script 한 줄과 test 한 줄에 가까운 최소 변경이었다. 실제 RDS preflight가 다시 통과하기 전까지 Scheduler는 OFF로 유지했다.

근거: [PR #165](https://github.com/guseoh/pawcycle-commerce/pull/165).

## 공통적으로 얻은 교훈

이 문제들은 모두 “RDS가 안 된다”는 하나의 증상으로 묶을 수 있지만 원인은 서로 다른 계층이었다.

| 사례 | 실제 계층 | 잘못 확대할 수 있던 가설 |
| --- | --- | --- |
| CRLF | Windows/AWS CLI text | SG·VPC 구성 오류 |
| Quoting | env materialization/parser | DB name·backup 손상 |
| Same-SHA | release state machine | image 또는 RDS activation 불가 |
| Wrong target | operational control routing | active RDS schema 정상 |
| stdin | Docker CLI process I/O | RDS connection·permission 실패 |

각 단계에서 source Docker volume과 RDS target을 삭제하거나 임의 수정하지 않았고, 원인을 좁힌 뒤 최소 회귀를 추가했다. 공통된 실패 원인은 테스트가 “정상 입력의 결과”만 보고 실제 Production 경계인 Windows newline, materialized quoting, runtime-only state transition, active datasource와 process stdin을 충분히 재현하지 못한 데 있었다. Migration은 data copy뿐 아니라 shell, state, target identity, process I/O와 rollback source를 함께 검증해야 한다.
