# PawCycle Architecture Decision과 Trade-off

PawCycle의 AWS architecture는 기술의 우열보다 당시 규모, 비용, 운영자가 감당할 수 있는 복잡성과 실제 evidence를 기준으로 선택됐다.

## 왜 EC2와 Docker Compose였는가

초기 목표는 작은 Commerce 서비스를 실제 internet에 배포하고 release, HTTPS, data와 복구를 직접 경험하는 것이었다. EC2 한 대와 Compose는 network와 process 관계가 눈에 보이고, Nginx·Backend·Frontend·MySQL을 하나의 control surface에서 운영할 수 있었다. Public GHCR image와 SSH 대신 SSM을 사용하면 작은 구조 안에서도 기본 보안 경계를 만들 수 있었다.

ECS/EKS 같은 managed container platform, Load Balancer와 Auto Scaling은 배포와 failover capability를 늘릴 수 있지만 control plane, IAM, network, health, 비용과 debugging 경계도 늘어난다. 단일 instance에서 실제 capacity와 운영 문제가 확인되기 전에는 그 복잡성을 정당화할 근거가 없었다.

포기한 것은 명확했다. Single host failure, single release 교체의 짧은 중단 가능성, 수동 OS/Docker 운영과 capacity ceiling을 감수했다. 무중단·Blue/Green·multi-instance는 완료했다고 쓰지 않았다.

## 왜 처음에는 Docker MySQL이었는가

Application과 DB를 같은 Compose에 두면 초기 비용이 작고 local/Production topology가 단순하다. Service name으로 연결하고 named volume만 보존하면 빠르게 Production을 시작할 수 있었다. 반면 host, storage와 engine 책임이 Application 운영과 결합됐다.

Logical backup과 isolated restore를 실제 검증하면서 직접 운영의 책임이 더 구체적으로 드러났다. Backup object뿐 아니라 bucket policy, checksum, temporary restore resource, memory와 cleanup을 관리해야 했다. Automated backup/PITR 부재, host/engine lifecycle과 공통 failure domain이 RDS 검토의 근거가 됐다.

## 왜 RDS Single-AZ였는가

RDS Single-AZ는 DB를 Application EC2에서 분리하고 managed backup/PITR capability를 얻으면서 Multi-AZ standby 비용은 피하는 중간 단계였다. Private endpoint와 SG source reference로 database exposure도 명확해졌다.

Multi-AZ를 선택하지 않은 이유는 DB HA가 가치 없어서가 아니다. Application은 여전히 단일 EC2였고, database만 failover돼도 ingress와 Backend가 죽으면 서비스는 사용할 수 없다. 당시 측정된 availability 목표나 장애 비용이 end-to-end multi-AZ 확장을 정당화하지 않았다.

| 질문 | 당시 답 |
| --- | --- |
| DB host 장애 책임을 줄여야 하는가? | 그렇다. RDS로 분리한다. |
| Automated backup/PITR capability가 필요한가? | 그렇다. 생성 시 활성화한다. |
| DB AZ failover만으로 전체 HA가 되는가? | 아니다. 단일 EC2가 SPOF다. |
| Multi-AZ 추가 비용을 지금 지불할 근거가 있는가? | 부족하다. 재평가 조건으로 남긴다. |
| Source Docker DB를 즉시 삭제하는가? | 아니다. Stabilization/rollback source로 보존한다. |

## 왜 HA와 failover를 더 확장하지 않았는가

완전한 HA에는 DB Multi-AZ 외에도 최소한 multi-AZ Application, load balancing, state/session 전략, health-based traffic routing, rolling deployment, shared observability와 failover test가 필요하다. 각 component를 늘리면 비용과 운영 경로도 늘어난다.

PawCycle은 당시 다음을 defer했다.

- Multi-AZ RDS와 실제 failover test
- Read replica와 RDS Proxy
- Multiple Application EC2, Load Balancer와 Auto Scaling
- Blue/Green과 무중단 배포
- Cross-region backup/DR
- 자동 certificate/backup schedule과 자동 복구

이는 영구 거부가 아니라 evidence-triggered decision이다. 실제 SLO, 장애 비용, load와 운영자의 대응 부담이 커지면 우선순위를 바꿔야 한다.

## 운영 편의성과 새 비용

AWS는 IAM Role, OIDC, SSM, RDS, S3, CloudWatch 같은 조합으로 장기 key 없이 배포하고 private DB와 managed backup, metric/alarm을 만들 수 있게 했다. 반면 작은 개인 프로젝트에서도 EC2, RDS, public IPv4, Observability EC2, storage와 data transfer가 지속 비용이 됐다. Service별 IAM·network·Runbook과 cleanup 책임도 커졌다.

RDS로 DB host 책임을 줄였지만 migration, runtime bundle 두 개, TLS와 rollback source 관리가 새로 생겼다. Observability를 분리해 Application host pressure를 줄였지만 추가 EC2와 metrics bridge를 운영해야 했다. 관리형 서비스는 복잡성을 없애기보다 다른 형태로 이동시켰다.

당시 결정을 상태와 재평가 조건으로 요약하면 다음과 같다.

| 선택 | 당시 판정 | 해결한 문제와 남은 한계 |
| --- | --- | --- |
| EC2 + Docker Compose | 초기 `KEEP`, AWS 종료 시 `Retired` | 작은 비용과 한 control surface를 얻었지만 host SPOF와 직접 OS 운영이 남았다. |
| Docker MySQL | 초기 `KEEP`, 이후 `REPLACE` | 시작은 단순했지만 App/DB failure domain과 backup·engine 책임이 결합됐다. |
| RDS Single-AZ | `ADOPT` | DB lifecycle과 host를 분리했지만 DB와 Application의 각 SPOF는 남았다. |
| RDS Multi-AZ | `DEFER` | DB failover 가치는 있었으나 단일 EC2 SPOF와 standby 비용 때문에 end-to-end 우선순위가 낮았다. |
| ECS/EKS·multi-instance·Load Balancer | `DEFER` | Application HA와 배포 능력을 늘리지만 당시 load/SLO가 추가 control plane과 비용을 정당화하지 않았다. |
| Read replica | `NOT NEEDED` | Read saturation evidence가 없었고 HA를 대신하지도 않았다. |
| RDS Proxy | `DEFER` | Connection churn·failover 대응 후보였지만 250 RPS failure의 선행 원인은 Backend OOM이었다. |
| AWS 장기 유지 | `RETIRE` | 운영 학습과 검증은 확보했지만 개인 프로젝트의 지속 비용 목표와 맞지 않았다. |
| OCI 전환 | `ADOPT AS PLATFORM MOVE` | 비용 목표에 맞춘 이전이었으며 AWS 검증 수준을 자동 승계하지 않았다. |

## 지금 다시 한다면

초기에도 무조건 managed container platform을 선택할 이유는 없다. 다만 다음은 더 일찍 명시할 수 있다.

- Container memory, JVM native memory와 thread budget을 capacity test 전에 함께 정한다.
- Application metric과 kernel/container restart evidence를 초기 observability에 포함한다.
- Database target identity를 모든 preflight와 automation에 명시한다.
- RDS TLS는 `REQUIRED`와 server identity verification을 별도 decision으로 분리한다.
- Backup capability를 도입하는 시점에 restore elapsed time과 RPO/RTO 후보를 함께 기록한다.
- Cloud 종료 비용과 exit plan을 처음부터 architecture decision에 포함한다.
