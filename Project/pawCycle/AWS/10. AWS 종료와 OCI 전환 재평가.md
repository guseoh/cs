# AWS 종료와 OCI 전환 재평가

PawCycle이 AWS를 떠난 이유는 AWS 기술이 부족해서가 아니었다. 실제 배포·backup·관측·RDS와 성능 troubleshooting을 수행한 뒤, 개인 프로젝트의 장기 공개 운영 비용을 계속 지불할 가치와 목표를 다시 비교한 결과였다.

[Issue #276](https://github.com/guseoh/pawcycle-commerce/issues/276)은 기존 AWS account의 PawCycle과 실험 resource를 비용 차단 목적으로 제거했다고 기록한다. EC2/EBS/EIP/RDS/Snapshot/S3/CloudWatch/SNS/SSM, IAM, Budget 등 비용과 운영 surface를 정리했고, AWS를 장기 Production 기반으로 사용하지 않기로 했다.

## OCI를 선택한 당시 조건

OCI 후보는 Ampere A1 Compute와 managed MySQL의 무료 quota를 활용해 장기 운영 비용을 줄이고, 기존 Java/MySQL/Docker 구조를 유지할 수 있다는 점이 중요했다. 선택은 “OCI가 AWS보다 우월하다”가 아니라 다음 조건에 맞춘 것이었다.

- Portfolio service를 장기간 공개하고 싶다.
- 지속 고정 비용을 최소화해야 한다.
- Spring Boot, Next.js, Nginx와 MySQL 계약을 유지하고 싶다.
- Load Balancer·multi-instance·HA는 현재 실제 요구보다 우선순위가 낮다.
- ARM64 image와 runtime compatibility를 검증할 수 있다.

OCI 공식 문서는 Always Free resource가 home region과 quota/capacity 조건을 가지며, A1이 ARM architecture임을 설명한다. 실제 signup 시 한국 Region을 선택할 수 없었고 free capacity 부족도 발생했다. 결국 temporary paid/trial-backed Compute provisioning과 장기 free 축소 후보를 분리해 판단했다. 무료 label만으로 운영 가능성을 확정하지 않은 이유다.

> [OCI 공식 — Arm-Based Compute](https://docs.oracle.com/en-us/iaas/Content/Compute/References/arm.htm)
> [OCI 공식 — Networking Overview](https://docs.oracle.com/en-us/iaas/Content/Network/Concepts/overview.htm)

## AWS와 OCI를 당시 PawCycle 조건으로 비교

| 관점 | AWS 당시 구조 | OCI 후보 구조 | Trade-off |
| --- | --- | --- | --- |
| Compute | x86 EC2 + 별도 arm Observability EC2 | ARM A1 중심 | OCI 비용 후보가 유리했지만 multi-arch build와 capacity 위험 추가 |
| Database | RDS MySQL Single-AZ | OCI managed MySQL standalone 후보 | 둘 다 managed DB지만 free tier의 HA·backup 제약을 다시 설계해야 함 |
| Network | VPC, SG, public EC2, private RDS | VCN, NSG, public app, private DB | 개념은 유사하나 provider별 IAM·gateway·운영 도구는 다름 |
| 배포 control | GitHub OIDC → IAM Role → SSM | OCI runtime·Run Command 계열 | AWS 경로와 OCI 경로는 identity·state 계약이 달라 별도 검증이 필요 |
| Backup | S3 logical backup + isolated restore | Object Storage 기반 후속 구조 | Provider가 달라지면 access·retention·restore evidence를 다시 확인해야 함 |
| Observability | 별도 EC2 Prometheus/Grafana + CloudWatch | `app01` same-host Lean baseline | OCI에서는 비용을 줄이는 대신 host 자원 경쟁과 failure domain을 다시 측정 |
| 비용 | 지속 EC2·RDS·IPv4·storage 비용 | Free quota 활용 가능성 | OCI도 quota/capacity·trial 종료·초과 사용 위험이 있음 |

AWS에서 검증한 Runbook을 이름만 바꿔 OCI에 이식하지 않았다. IAM Role과 OCI instance principal, SSM과 Run Command, S3와 Object Storage, RDS와 OCI MySQL은 유사한 목적을 가질 수 있지만 trust, endpoint, backup, failure와 billing 계약이 다르다.

## 전환 단계의 역사적 상태와 이 문서의 판정 범위

2026-09-04의 repository migration work는 ARM64/multi-arch image, external MySQL, OCI runtime materialization, Run Command dispatch와 Object Storage backup/restore 계약을 준비했다. Issue에는 Compute provisioning 성공도 기록됐다. PR #277은 이 단계에서 `Accepted — Repository Migration Readiness`, `Production Verified가 아니다`라고 명시한다. 이는 9월 4일 당시의 상태이지 이후 OCI 운영 전체의 현재 판정이 아니다.

2026-09-06 [PR #284](https://github.com/guseoh/pawcycle-commerce/pull/284)는 종료된 AWS Production의 실행 가능한 contract를 `main`에서 철거했다. 이 PR이 병합될 당시 저장소 상태는 다음처럼 정렬됐다.

```text
Production deployment target: 없음
CD: DEFER
무중단 배포: DEFER
OCI: 후속 방향이지만 active target 아님
```

그 뒤에는 [PR #286](https://github.com/guseoh/pawcycle-commerce/pull/286)의 현재 OCI HTTPS renewal 계약, [PR #287](https://github.com/guseoh/pawcycle-commerce/pull/287)과 PR #290~#293의 OCI `app01` observability 작업, [PR #294](https://github.com/guseoh/pawcycle-commerce/pull/294)의 current OCI runtime identity 지원이 이어졌다. 특히 ARCH-012에는 OCI Production에서 실제 확인된 localhost publish 실패가 기록돼 있어, PR #284의 snapshot을 현재 상태 판정으로 재사용할 수 없다.

이 AWS 역사 문서가 확정하는 결론은 AWS Production과 AWS 전용 active execution contract가 종료됐고 PawCycle이 OCI 기반 배포·운영 구조로 이동했다는 데까지다. 현재 OCI release, CD, backup, observability와 `Production Verified` 세부 범위는 이 문서의 판정 대상이 아니며, 읽는 시점의 OCI Runbook·ADR·실행 보고서를 확인해야 한다.

## 현재 시점의 재평가

AWS가 제공한 가장 큰 가치는 운영 기능의 폭과 조합이었다. OIDC·SSM의 temporary credential 배포, RDS backup/PITR, CloudWatch와 S3를 실제로 연결해 볼 수 있었다. 가장 큰 제약은 개인 프로젝트에서 그 조합을 장기간 유지하는 비용과 많은 control surface였다.

OCI 전환의 가치는 장기 비용 목표에 맞을 가능성이었다. 제약은 home region, free capacity, ARM64, backup/HA 제한과 새 provider 운영 지식이었다. 무료 resource는 availability guarantee나 무제한 capacity가 아니며, quota가 바뀌거나 capacity가 없으면 설계가 중단될 수 있다.

따라서 선택 기준은 provider 순위가 아니라 다음이다.

- 지금 서비스가 요구하는 availability와 recovery evidence는 무엇인가?
- 월 고정 비용과 장애 비용 중 어느 쪽이 더 중요한가?
- 운영자가 실제로 검증하고 유지할 수 있는 control surface는 어느 정도인가?
- Provider 종료·이전 시 data와 runtime을 꺼낼 exit plan이 있는가?

PawCycle에서는 장기 비용과 학습 목적이 OCI 전환을 정당화했지만, AWS에서 얻은 운영 evidence와 검증 수준을 자동으로 승계하지는 않았다.
