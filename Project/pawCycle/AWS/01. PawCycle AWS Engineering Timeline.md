# PawCycle AWS Engineering Timeline

PawCycle의 AWS 운영은 처음부터 완성된 HA architecture를 만든 과정이 아니다. 작은 비용으로 실제 Production을 열고, 운영하면서 필요한 안전장치를 증거에 따라 추가한 과정이다. 시점별 상태는 repository와 GitHub에 남은 사실만 사용한다.

초기 구조는 한 EC2 안에서 Application과 MySQL을 함께 운영했다. 빠르게 서비스를 열고 비용을 통제하기에는 적합했지만 EC2·EBS·Docker daemon과 host memory가 Nginx, Application과 DB의 공통 failure domain이었다. Backup과 restore를 직접 만들고 검증해야 했고, host나 engine lifecycle도 운영자가 맡았다.

초기에는 GitHub Actions가 image를 만들고 운영자가 Session Manager에서 수동 배포했다. 이후 OIDC로 temporary AWS credential을 얻고 SSM SendCommand를 호출하는 경로를 추가했다. Workflow는 40자 target SHA와 승인된 Document·target tag만 다뤘고 arbitrary shell이나 SSH 배포를 허용하지 않았다.

관측성은 Application EC2의 memory 여유가 작아 별도 arm64 `t4g.small` EC2로 분리했다. 당시 Application host에는 swap이 없고 `MemAvailable`이 약 500 MiB였으며, MySQL 약 504 MiB, Backend 309 MiB, Frontend 121 MiB, Proxy 8 MiB 사용 evidence가 있었다. 같은 host에 Prometheus·Grafana까지 올리는 대신 추가 비용과 network boundary를 수용했다.

RDS cutover의 정확한 실행 시각과 모든 cutover step을 정리한 독립 실행 보고서는 찾지 못했다. Issue #158도 최신 조회에서 Open이다. 다만 PR #164는 “Production RDS cutover 이후” 잘못된 preflight target을 수정한다고 명시하고, 8월 22일 Production 부하 측정은 단일 Backend + RDS 경로와 실제 RDS CloudWatch metric을 기록한다. 따라서 “8월 22일까지 Production datasource가 RDS로 전환됐다”는 사실은 확인되지만, rehearsal과 final consistency cutover의 전체 절차를 `Production Verified`로 확대하지 않는다.

## 250 RPS 장애와 AWS 종료

2026-08-22의 외부 read-only 부하는 25, 50, 100, 150, 200 RPS에서 error와 drop 없이 통과했다. 250 RPS에서는 actual 236.89 RPS, error 6.88%, dropped 1,572, p95 약 4.22초, p99 약 5.75초로 실패했다. Kernel log는 Backend container의 memory cgroup OOM이 Java process를 kill한 사실을 보여 줬다.

RDS는 같은 구간 CPU 약 8.35~11.69%, connection 10, read latency 최대 약 1.54 ms, 매우 낮은 read IOPS였다. 작은 `db.t4g.micro`였다는 이유만으로 DB 병목이라고 결론 내리지 않았고, Backend request concurrency, thread, Hikari pending과 container memory를 다음 분석 대상으로 정했다.

2026-09 초 기존 AWS resource는 비용 차단 목적으로 종료됐다. [Issue #276](https://github.com/guseoh/pawcycle-commerce/issues/276)은 AWS를 장기 Production 기반으로 사용하지 않고 OCI Always Free 중심으로 재구축하려는 결정을 기록한다. [PR #284](https://github.com/guseoh/pawcycle-commerce/pull/284)는 2026-09-06 AWS OIDC·SSM deploy, S3 backup/restore, RDS cutover와 EC2 alarm 같은 실행 가능한 계약을 `main`에서 철거했다.

PR #277의 repository migration readiness와 PR #284의 “활성 Production target 없음”은 2026년 9월 초 전환 단계의 역사적 snapshot이다. 이후 PR #286의 OCI HTTPS renewal 계약, PR #287·#290~#293의 `app01` 관측성 작업과 PR #294의 OCI runtime identity 지원처럼 OCI Production을 전제로 한 후속 근거가 이어졌다. 따라서 이 AWS Timeline은 AWS 종료와 OCI로의 이동까지만 확정하고, 현재 OCI release·CD·검증 수준은 판정하지 않는다. AWS와 OCI의 당시 비교는 [[10. AWS 종료와 OCI 전환 재평가]]에서 다룬다.
