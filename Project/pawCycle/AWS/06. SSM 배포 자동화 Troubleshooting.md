# SSM 배포 자동화 Troubleshooting

이 사례는 GitHub Actions와 SSM 상위 단계는 성공했지만 command invocation이 빈 output과 exit 1로 끝난 문제다. EC2에서 generated script를 수동으로 실행하면 preflight가 통과했기 때문에 deploy logic보다 SSM materialization과 Agent 실행 환경을 먼저 조사했다.

전체 근거는 [Issue #135](https://github.com/guseoh/pawcycle-commerce/issues/135), 수정 PR [#131](https://github.com/guseoh/pawcycle-commerce/pull/131)~[#134](https://github.com/guseoh/pawcycle-commerce/pull/134)에 있다.

## 증상과 초기 가설

GitHub OIDC Role assume과 SSM SendCommand는 성공했고 target instance도 Online이었다. 그러나 invocation은 다음 수준의 정보만 남겼다.

```text
Status: Failed
ResponseCode: 1
Output: empty
Error: failed to run commands: exit status 1
```

처음에는 SSM Parameter interpolation, shell/heredoc, environment, PATH, Snap 기반 Agent namespace를 차례로 의심했다. 같은 script의 수동 실행이 성공했기 때문에 Application, Compose와 deploy preflight 본문을 즉시 수정하지 않았다.

## v1에서 v6까지 가설을 제거한 과정

| Version | 변경과 관찰 | 판정 |
| --- | --- | --- |
| v1 | 초기 Production SSM Document | 기준 version |
| v2 | 운영 복구용 안정 version | 후속 실험 실패 시 Environment target을 v2로 되돌림 |
| v3 | `ENV_VAR`와 fallback 도입 | Generated script에 self-reference가 생겨 `set -u`와 함께 실패 가능 |
| v4 | Quoted heredoc으로 wrapper와 본문 분리 | 실제 실패 지속. Heredoc 진입은 root cause 아님 |
| v5 | 정확히 5개 positional argument로 전환 | EC2 수동 실행 PASS, 실제 SSM Agent 실행은 exit 1 지속 |
| v6 | Exact worktree의 process-scoped `safe.directory` | SSM invocation Success/0, 실제 deploy 성공 |

v3의 generated script에는 변수가 없을 때 자신을 참조하는 fallback이 materialize됐다. 이를 제거하고 Operation, Target SHA와 세 approval SHA만 positional argument로 넘겼다. 이 단계에서 interpolation과 heredoc을 정상화했지만 실제 SSM 경로는 계속 실패했다.

## 결정적 증거

SSM Agent와 worker는 처음부터 root로 실행됐다. Snap namespace, `/usr/bin/env`, Bash와 HOME을 확인했지만 shell 자체는 정상 동작했다. `bpftrace`로 child exec를 추적하자 다음 순서가 보였다.

```text
ssm-document-worker
→ /usr/bin/sh
→ generated script
→ /usr/bin/env
→ /usr/bin/bash
→ /usr/bin/git
→ git 종료
→ 전체 shell 종료
```

첫 Git 접근이 최초 실패 executable이었다. Production control worktree는 일반 운영 계정이 소유했다. 운영자가 `sudo`로 재현할 때는 `SUDO_UID`, `SUDO_GID`, `SUDO_USER`가 존재해 Git ownership 판단이 달랐다. 실제 SSM Agent처럼 처음부터 root이고 이 변수가 없는 환경에서는 Git이 repository를 신뢰하지 않아 실패했다.

Root cause는 AWS IAM이나 SSM network가 아니라 Git `safe.directory`와 filesystem ownership 경계였다. 수동 `sudo` root shell과 SSM Agent root process를 같은 환경으로 가정한 것이 재현의 함정이었다.

## 수정과 재검증

Repository ownership을 바꾸거나 `safe.directory=*`를 영구 설정하지 않았다. SSM process tree에만 exact path 하나를 신뢰하도록 Git config environment를 전달했다. Child `deploy.sh`의 Git 호출까지 상속되지만 system/global config는 수정하지 않았다.

새 immutable SSM Document v6를 생성하고 Active 상태를 확인한 뒤 GitHub Production Environment가 가리키는 version을 2에서 6으로 변경했다. 같은 target/approval로 manual preflight를 한 번 실행해 `Success / 0`을 확인했고, 이후 Production Deploy와 Flyway V9~V11, Scheduler OFF post-deploy preflight를 실제 검증했다.

## 기존 검증이 잡지 못한 이유와 재발 방지

Local validator는 generated document 형식과 parameter 수를 확인했지만 SSM Agent가 처음부터 root로 실행될 때의 Git ownership을 재현하지 않았다. EC2 수동 `sudo`도 `SUDO_UID`가 남아 실제 환경과 달랐다.

재발 방지는 다음으로 남겼다.

- Immutable document version을 덮어쓰지 않고 새 version으로 전진한다.
- Environment가 실제 사용하는 version을 별도로 통제해 실패 version을 빠르게 분리한다.
- Generated script와 child process tree를 실제 SSM 경로에서 확인한다.
- Exact `safe.directory`만 process-scoped로 허용하고 wildcard와 persistent config를 차단한다.
- Empty stdout의 상위 exit 1에서 배포 본문을 먼저 바꾸지 않고 최초 실패 executable을 찾는다.

이 사례는 IAM→SSM control plane→Agent→shell→Git을 계층별로 분리한 troubleshooting이다. 일반 IAM/SSM 개념은 [[02. IAM과 임시 자격 증명]]과 [[09. GitHub Actions에서 EC2까지의 배포]]를 참고한다.
