## 1. 인터페이스를 사용했는데도 코드 변경이 필요한 이유

주문 서비스가 할인 금액을 계산해야 한다고 생각하면 할인 정책에는 두 가지 구현이 존재한다.
- `FixDiscountPolicy`: 주문 금액과 관계없이 1,000원 할인
- `RateDiscountPolicy`: 주문 금액의 10% 할인

할인 정책이 바뀔 수 있으므로 `DiscountPolicy` 인터페이스를 정의하고 두 구현 클래스가 이를 구현하도록 설계한다.

```java
public interface DiscountPolicy {
    int discount(int price);
}

public class FixDiscountPolicy implements DiscountPolicy {
    @Override
    public int discount(int price) {
        return 1_000;
    }
}

public class RateDiscountPolicy implements DiscountPolicy {
    @Override
    public int discount(int price) {
        return price * 10 / 100;
    }
}
```

- 이 구조에서는 주문 서비스가 `DiscountPolicy`의 `discount()`메서드만 호출하면 된다.
- 실제로 어떤 할인 계산이 수행되는지는 연결된 **구현 객체**에 따라 달라진다.
- 이것이 **인터페이스를 이용한 역할과 구현의 분리**, 그리고 **다형성**이다.


### 1.1 첫 번째 코드 - 구현체를 직접 생성한다.
```java
public class OrderServiceImpl {

	// DIP 위반!
    private final DiscountPolicy discountPolicy =
            new FixDiscountPolicy();

	// OCP 위반!
    public int calculatePrice(int price) {
        return price - discountPolicy.discount(price);
    }
}
```

- 현재 `OrderServiceImpl`은 `DiscountPolicy`인터페이스를 사용하지만, 내부에서 `FixDiscountPolicy`객체를 직접 생성하고 있다.
- 요구사항이 바뀌어 정률 할인을 적용하려면 `new FixDiscountPolicy()`를 `new RateDiscountPolicy()`로 수정해야 한다.

**문제는 할인 계산을 사용하는 주문 서비스가 구체적인 할인 정책까지 선택하고 있다는 점이다.**

![[Pasted image 20261120153424.png|강의 PDF 5쪽 — 위쪽은 기대한 인터페이스 의존관계, 아래쪽은 실제 클래스 의존관계|500]]
그림의 아래쪽에서 `OrderServiceImpl`은 `DiscountPolicy`뿐 아니라 `FixDiscountPolicy`에도 직접 연결된다.
- `DiscountPolicy` 의존: 어떤 메서드를 사용할 수 있는지 정의한다.
- `FixDiscountPolicy` 의존: 구체적으로 어떤 할인 구현을 사용할지 직접 결정한다.

인터페이스 타입으로 필드를 선언했더라도 `new FixDiscountPolicy()` 코드 때문에 구체적인 구현 클래스에 대한 의존관계가 남아 있는 것이다.


### 1.2 DIP와 OCP를 위반하는 이유
| 원칙             | 의미                                | 현재 코드의 문제                             |
| -------------- | --------------------------------- | ------------------------------------- |
| DIP 의존관계 역전 원칙 | 핵심 로직이 구체적인 구현보다 추상화에 의존하도록 설계한다. | 주문 서비스가 `FixDiscountPolicy`를 직접 생성한다. |
| OCP 개방-폐쇄 원칙   | 기능 확장 시 기존 코드의 불필요한 변경을 줄인다.      | 할인 정책을 교체할 때 주문 서비스 코드를 수정한다.         |
- **DIP는 의존관계의 방향**을 다룬다. 핵심 비즈니스 로직이 변경 가능한 구현 세부사항에 직접 의존하지 않도록 보호하는 원칙이다.
- **OCP는 변경의 전파 범위**를 다룬다. 새로운 기능을 추가할 때 기존의 안정적인 로직을 가능한 유지하도록 설계하는 원칙이다.

DIP를 잘 적용하면 OCP를 지키기 쉬워진다. 다만 인터페이스를 만든 것만으로 두 원칙이 자동으로 만족되는 것은 아니다.

## 2. 문제 해결 - 객체를 사용하는 책임과 생성하는 책임을 분리한다.

DIP를 지키기 위해 `OrderServiceImpl`에서 구체적인 구현체 생성 코드를 제거하자.

그런데 단순히 `new FixDiscountPolicy()`를 제거하고 필드만 남겨두면 사용할 객체가 연결되지 않는다. 초기화되지 않은 필드에서 `discount()`를 호출한다면 `NullPointerException`이 발생한다.

따라서 **구현 객체를 대신 생성하고 주문 서비스에 전달할 다른 구성 요소가 필요하다.**

### 2.1 생성자 주입으로 변경한다

```java
public class OrderServiceImpl {

    private final DiscountPolicy discountPolicy;

    public OrderServiceImpl(DiscountPolicy discountPolicy) {
        this.discountPolicy = discountPolicy;
    }

    public int calculatePrice(int price) {
        return price - discountPolicy.discount(price);
    }
}
```

`OrderServiceImpl`이 자신이 사용할 할인 정책을 생성자에서 전달받도록 수정한다. 
- `new FixDiscountPolicy()`가 사라져 구체적인 구현 클래스를 직접 선택하지 않는다.
- 생성자의 `DiscountPolicy discountPolicy` 매개변수를 통해 외부에서 객체를 전달받는다.
- 필드의 타입과 가격 계산 로직은 그대로 유지된다.

하지만 이 상태만으로는 어떤 할인 정책을 사용할지 결정할 수 없다. 그 **결정을 내리는 책임을 별도의 구성 클래스로 옮겨야 한다.**

### 2.2 AppConfig가 구현체를 선택하고 연결한다
```java
public class AppConfig {

    public DiscountPolicy discountPolicy() {
        return new RateDiscountPolicy();
    }

    public OrderServiceImpl orderService() {
        return new OrderServiceImpl(discountPolicy());
    }
}
```
- `discountPolicy()`는 실제로 사용할 할인 정책 객체를 생성한다.
- `orderService()`는 할인 정책 객체를 `OrderServiceImpl`생성자에 전달한다.
- `OrderServiceImpl`은 전달받은 객체를 사용하여 주문 금액을 계산한다.

**객체를 사용하는 책임은 `OrderServiceImpl`에, 객체를 선택하고 연결하는 책임은 `AppConfig`에 있다.**

이처럼 서로 다른 이유로 변경되는 책임을 분리하는 것이 **관심사의 분리**이다. 또한 주문 계산과 구현체 선택이라는 서로 다른 변경 이유를 분리한다는 점에서 SRP(단일 책임 원칙)와도 연결된다.

### 2.3 실제 코드가 어떻게 실행되는가?
```java
public class Main {

    public static void main(String[] args) {
        AppConfig appConfig = new AppConfig();

        OrderServiceImpl orderService = appConfig.orderService();

        System.out.println(orderService.calculatePrice(20_000));
    }
}
```
1. `new AppConfig()`로 구성 객체를 생성한다.
2. `orderService()`가 호출되면서 `discountPolicy()`가 실행된다.
3. `new RateDiscountPolicy()`로 생성한 객체의 참조값을 `OrderServiceImpl`생성자에 전달한다.
4. `calculatePrice(20_000)`에서 `RateDiscountPolicy.discount()`가 호출되어 최종 가격을 계산한다.

여기서 `OrderServiceImpl`에 전달되는 것은 `RateDiscountPolicy` 객체의 복사본이 아니라 **이미 생성된 객체를 가리키는 참조값**이다.

생성자에서 `this.discountPolicy = discountPolicy`가 실행되면 주문 서비스의 필드가 해당 객체를 참조하게 된다. 이후 `discount()`를 호출하면 Java의 다형성에 의해 실제 객체인 `RateDiscountPolicy`의 메서드가 실행된다.

이것이 실행 시점에 형성되는 객체 의존관계이다. 소스 코드에서 `OrderServiceImpl`이 `DiscountPolicy` 인터페이스를 사용한다는 사실은 프로그램을 실행하지 않아도 확인할 수 있는 정적인 클래스 의존관계이다.

- `memoryMemberRepository`는 현재 예제의 `RateDiscountPolicy`에, `memberServiceImpl`은 `OrderServiceImpl`에 대응한다.
