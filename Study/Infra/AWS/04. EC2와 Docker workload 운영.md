# EC2와 Docker workload 운영

EC2 instance는 AWS가 제공하는 virtual machine이다. 사용자는 instance type, image, network와 storage를 선택하고, 그 위의 OS, package, Docker daemon, container, log와 disk 사용량을 운영한다. EC2가 관리형 compute라고 해도 application process의 health나 OS memory pressure를 AWS가 자동으로 해결해 주지는 않는다.

Instance에는 하나 이상의 Elastic Network Interface, ENI가 연결된다. ENI는 subnet의 private IP와 Security Group을 가진다. Public IPv4는 instance OS 안의 interface에 직접 설정되는 주소가 아니라 AWS network에서 private IP로 변환되는 주소이므로 OS의 `ip addr`에서 public address가 보이지 않을 수 있다. 일반 public IPv4는 stop/start에서 바뀔 수 있고, Elastic IP는 account에 할당해 instance나 ENI에 다시 연결할 수 있는 고정 public IPv4다.

AWS는 현재 public IPv4 주소에 비용을 부과하므로, 고정 IP가 편리하다는 이유만으로 방치하면 안 된다. DNS, certificate와 연결된 Elastic IP를 해제하면 같은 주소를 다시 확보할 수 있다는 보장도 없다. 생성과 연결뿐 아니라 dependency 제거와 release 순서까지 운영 절차에 포함해야 한다.

## EBS와 instance lifecycle

EBS volume은 EC2와 분리된 block storage지만 특정 AZ에 속한다. Root volume과 data volume은 instance 종료 시 삭제 여부가 다를 수 있다. `Delete on termination=false`는 instance 실수 종료에서 volume을 보존할 수 있지만, 고아 volume이 계속 비용을 만들 수 있다. 반대로 delete를 켜면 정리는 단순하지만 복구할 마지막 copy를 잃을 수 있다.

Container volume이 EBS 위에 있어도 backup은 아니다. 동일 volume에 Application과 MySQL이 함께 있으면 host filesystem corruption, operator deletion, AZ 장애와 credential compromise가 같은 failure domain에 남는다. Snapshot이나 논리 dump를 만들었다면 실제 별도 resource로 restore하고 application이 사용할 수 있는지를 검증해야 한다.

EC2 stop/start, reboot와 terminate도 구분한다.

| 동작 | 일반적인 의미 | 확인할 것 |
| --- | --- | --- |
| Reboot | 같은 instance를 재부팅 | Docker 자동 시작, container restart policy, mount와 state 복구 |
| Stop/Start | compute를 중지 후 재할당 | public IP 변화, instance store 손실 가능성, EBS·ENI 관계 |
| Terminate | instance 삭제 | root EBS delete flag, EIP disassociate/release, 잔존 volume과 비용 |

## Docker Compose를 운영 계약으로 보기

Compose file은 단순 실행 편의 파일이 아니라 service, network, volume, health, resource limit과 restart 정책을 묶은 운영 계약이다. Production에서는 다음을 명시적으로 본다.

- 외부에 publish하는 port는 reverse proxy의 80·443뿐인가?
- Backend와 DB는 내부 network에서만 통신하는가?
- MySQL data volume이 release 교체나 rollback 때 삭제되지 않는가?
- health check가 process 존재가 아니라 실제 dependency 준비를 반영하는가?
- image가 mutable `latest`가 아니라 commit SHA와 digest로 추적되는가?
- CPU, memory와 PID limit이 workload 특성과 맞는가?
- `restart: unless-stopped`가 crash를 숨기지 않도록 restart count와 kernel log를 함께 보는가?

Container가 restart 후 healthy라고 해서 장애가 없었던 것은 아니다. OOM으로 Java process가 죽고 restart policy가 새 container process를 띄우면 현재 상태만 보면 정상으로 보일 수 있다. `RestartCount`, `StartedAt`, Docker event, cgroup와 kernel OOM log를 부하 지표의 시간축과 대조해야 한다.

## SSM을 기본 운영 접속으로 사용할 때

Session Manager는 inbound SSH port와 private key 없이 IAM으로 managed node에 접속할 수 있다. 이를 위해 instance role, SSM Agent와 outbound service endpoint 경로가 필요하다. 비상 SSH는 기본 경로가 실패한 원인을 찾기 위한 제한된 수단으로 두고, 현재 운영자 IP 한 주소만 일시적으로 열고 작업 후 제거할 수 있다.

Run Command는 interactive shell이 아니라 SSM Agent가 document와 parameter를 materialize해 child process를 실행하는 방식이다. 수동 shell과 다음 조건이 다를 수 있다.

- 실행 user와 UID/GID
- `HOME`, `PATH`, `SUDO_UID` 같은 environment
- shell 종류와 quoting
- working directory와 filesystem ownership
- Snap/package의 mount namespace
- stdout/stderr 수집과 timeout

따라서 “EC2에서 sudo로 같은 명령이 된다”만으로 Run Command 동작을 증명할 수 없다. 실제 generated script와 process tree의 최초 실패 executable을 좁혀야 한다.

PawCycle은 SSM을 기본 접속과 자동 배포 control path에 사용했고, Docker Compose로 Nginx·Frontend·Backend·MySQL을 단일 EC2에서 운영했다. 실제 250 RPS 장애에서는 RDS보다 먼저 Backend container의 640 MiB memory cgroup이 포화돼 Java process가 kill됐다. 이 사례는 [[08. 250 RPS Production 장애 분석]]에 자세히 정리했다.
