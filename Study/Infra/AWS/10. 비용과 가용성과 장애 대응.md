# 비용과 가용성과 장애 대응

Cloud 비용과 가용성은 서로 독립적인 체크리스트가 아니다. 여러 AZ, standby, NAT, log retention과 snapshot을 추가하면 장애 대응 능력이 커질 수 있지만 고정비와 운영 복잡성도 늘어난다. 반대로 비용을 줄이기 위해 모든 것을 한 instance에 모으면 구조는 단순하지만 장애 범위가 커진다.

비용은 instance 가격만 보면 놓치기 쉽다. EC2, RDS와 storage 외에도 public IPv4, NAT Gateway 처리량, cross-AZ data transfer, snapshot·backup storage, log ingestion·retention과 monitoring host가 비용을 만든다. 정확한 금액은 Region과 시점에 따라 바뀌므로 실행 전 Pricing Calculator와 실제 billing 화면에서 다시 확인한다.

Budget alarm은 지출을 차단하지 않는다. 비용 데이터도 실시간이 아닐 수 있다. 예상 금액 알림, 실제 사용 알림과 resource inventory를 함께 운영하고, 종료할 때 ENI, EBS, Elastic IP, snapshot과 log group 같은 잔존 resource를 확인해야 한다.

## 가용성은 요청 전체 경로의 속성이다

사용자 요청이 다음 구성요소를 지난다고 하자.

```text
DNS → Public IP → EC2/Nginx → Backend → RDS
```

RDS만 Multi-AZ여도 EC2가 한 대면 EC2 장애가 전체 요청을 막는다. EC2를 두 대로 늘려도 public entrypoint와 session, deploy, database가 failover를 지원하지 않으면 end-to-end HA가 아니다. Component의 SLA나 HA label을 더해서 서비스 가용성을 계산하기 전에 shared dependency와 correlated failure를 찾아야 한다.

Single-AZ가 항상 나쁜 것도 아니다. 개인 프로젝트나 낮은 장애 비용의 서비스에서는 비용을 줄이고 검증된 backup/restore를 갖추는 편이 합리적일 수 있다. 중요한 것은 해당 선택이 제공하지 않는 것을 명시하는 것이다.

| 선택 | 얻는 것 | 포기하거나 추가되는 것 |
| --- | --- | --- |
| 단일 EC2 + Docker MySQL | 최소 비용, 단순 배포 | App·DB 같은 failure domain, host 운영 책임 |
| 단일 EC2 + RDS Single-AZ | DB lifecycle 분리, backup/PITR capability | DB 비용, migration, 여전히 App·DB 각각 SPOF |
| 단일 EC2 + RDS Multi-AZ | DB host/AZ failover | App SPOF 유지, standby 비용, reconnect 검증 |
| Multi-AZ App + Multi-AZ DB | 넓은 장애 격리 | LB/session/deploy/observability 복잡성·비용 |

## RTO와 RPO를 증거로 만들기

RPO는 허용 가능한 data loss 범위이고 RTO는 허용 가능한 복구 시간이다. Backup retention이나 service feature만으로 두 값을 확정할 수 없다.

- RPO에는 backup 주기, transaction log 보존, 마지막 성공 backup과 복제 lag가 영향을 준다.
- RTO에는 감지, 의사결정, restore resource 생성, data load, DNS/endpoint 전환, application validation 시간이 포함된다.
- Operator가 Runbook을 찾고 승인받는 시간도 실제 복구 시간의 일부다.

Restore rehearsal은 elapsed time과 실패 지점을 기록해야 의미가 있다. Single-AZ에서 실제 장애를 만들 수 없다면 최소한 isolated restore, application connection과 rollback source 보존을 검증하고 미검증 범위를 명시한다.

## 계층별 장애 대응

장애 시 가장 큰 실수는 첫 가설을 사실로 바꾸는 것이다. 작은 RDS instance를 쓴다고 해서 RDS가 병목이라고 단정하거나, CPU가 한 번 100%였다고 CPU가 최초 원인이라고 단정하면 잘못된 scaling으로 이어진다.

1. 사용자 증상과 발생 시간을 고정한다.
2. 배포·설정 변경과 resource event를 대조한다.
3. Client부터 Nginx, container, OS, JVM, pool, DB 순서로 signal을 같은 시간축에 놓는다.
4. 가설을 지지하는 증거와 배제하는 증거를 함께 찾는다.
5. 가장 먼저 실패한 resource 또는 invariant를 root cause 수준으로 좁힌다.
6. 최소 변경을 적용하고 같은 workload로 재검증한다.
7. 복구 뒤 정상 상태와 data 보존을 확인한다.

PawCycle은 250 RPS 실패에서 Hikari pending과 작은 RDS instance 때문에 DB 병목을 의심할 수 있었지만, RDS CPU와 latency가 낮았고 kernel log가 Backend cgroup OOM kill을 보여 줬다. 이처럼 비용이 작은 resource를 사용했다는 사실과 실제 병목 evidence를 분리해야 한다.
