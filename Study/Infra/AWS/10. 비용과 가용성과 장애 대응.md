# 비용과 가용성과 장애 대응

Cloud 비용과 가용성은 서로 독립적인 체크리스트가 아니다. 여러 AZ, Standby, NAT, Log 보존과 Snapshot을 추가하면 장애 대응 능력이 커질 수 있지만 고정비와 운영 복잡성도 늘어난다. 반대로 비용을 줄이기 위해 모든 것을 한 instance에 모으면 구조는 단순하지만 장애 범위가 커진다.

비용은 instance 가격만 보면 놓치기 쉽다. EC2, RDS와 storage 외에도 public IPv4, NAT Gateway의 시간당 사용료와 처리 데이터량, cross-AZ data transfer, snapshot·backup storage, log ingestion·retention과 monitoring host가 비용을 만든다. 정확한 금액은 Region과 시점에 따라 바뀌므로 실행 전 Pricing Calculator와 실제 billing 화면에서 다시 확인한다.

> [AWS 공식 — NAT Gateway 요금 구조](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-pricing.html)

Budget alarm은 지출을 차단하지 않는다. 비용 데이터도 실시간이 아닐 수 있다. 예상 금액 알림, 실제 사용 알림과 resource inventory를 함께 운영하고, 종료할 때 ENI, EBS, Elastic IP, snapshot과 log group 같은 잔존 resource를 확인해야 한다.

## 가용성은 요청 전체 경로의 속성이다

사용자 요청이 다음 구성요소를 지난다고 하자.

```text
DNS → Public IP → EC2/Nginx → Backend → RDS
```

RDS만 Multi-AZ여도 EC2가 한 대면 EC2 장애가 전체 요청을 막는다. EC2를 두 대로 늘려도 public entrypoint와 session, deploy, database가 failover를 지원하지 않으면 end-to-end HA가 아니다. 개별 Component에 붙은 SLA나 HA 표시를 단순히 더하기 전에 여러 계층이 공유하는 의존성과 함께 실패할 수 있는 장애 범위를 찾아야 한다.

Single-AZ가 항상 나쁜 것도 아니다. 개인 프로젝트나 장애 비용이 낮은 서비스에서는 비용을 줄이고 검증된 Backup/Restore를 갖추는 편이 합리적일 수 있다. 중요한 것은 해당 선택이 **무엇을 제공하지 않는지**를 명시하는 것이다.

| 선택 | 얻는 것 | 포기하거나 추가되는 것 |
| --- | --- | --- |
| 단일 EC2 + Docker MySQL | 최소 비용, 단순 배포 | App·DB 같은 failure domain, host 운영 책임 |
| 단일 EC2 + RDS Single-AZ | DB lifecycle 분리, backup/PITR capability | DB 비용, migration, 여전히 App·DB 각각 SPOF |
| 단일 EC2 + RDS Multi-AZ | DB host/AZ failover | App SPOF 유지, standby 비용, reconnect 검증 |
| Multi-AZ App + Multi-AZ DB | 넓은 장애 격리 | LB/session/deploy/observability 복잡성·비용 |

가용성(Availability)과 재해 복구(Disaster Recovery)도 같은 말이 아니다. 가용성은 개별 Component 장애 중에도 서비스를 계속 제공하거나 빠르게 전환하는 문제에 가깝고, DR은 큰 장애 뒤에 Workload와 데이터를 어느 시점까지, 얼마 안에 복구할지를 다룬다. Multi-AZ나 Load Balancer는 주로 가용성 쪽 설계이고, Backup·PITR·별도 환경 복원과 전환 절차는 DR과 복구 설계에 더 직접적으로 연결된다. 둘은 서로 보완하지만 하나가 있다고 다른 하나가 자동으로 해결되지는 않는다.

> [AWS 공식 — Reliability Pillar의 Disaster Recovery 계획](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/plan-for-disaster-recovery-dr.html)

## RTO와 RPO를 증거로 만들기

RPO는 허용 가능한 data loss 범위이고 RTO는 허용 가능한 복구 시간이다. 더 정확히는 **먼저 정해야 하는 복구 목표(Objective)**다. 실제 Restore 시험에서 측정한 18분 같은 값은 그 목표를 충족할 수 있는지 판단하는 운영 근거이지 RTO 자체와 같은 말이 아니다. Backup retention이나 서비스 기능을 켰다는 사실만으로 두 목표를 충족한다고 선언할 수 없다.

- RPO에는 backup 주기, transaction log 보존, 마지막 성공 backup과 복제 lag가 영향을 준다.
- RTO에는 감지, 의사결정, restore resource 생성, data load, DNS/endpoint 전환, application validation 시간이 포함된다.
- Operator가 Runbook을 찾고 승인받는 시간도 실제 복구 시간의 일부다.

Restore rehearsal은 실제 걸린 시간과 실패 지점을 기록해야 의미가 있다. 목표 RTO가 30분인데 Restore와 Application 검증에 45분이 걸렸다면 기능은 동작해도 목표는 충족하지 못한 것이다. RPO도 마지막 성공 Backup/PITR 지점과 장애 발생 시각을 비교해야 판단할 수 있다. Single-AZ에서 실제 장애를 만들 수 없다면 최소한 isolated restore, application connection과 rollback source 보존을 검증하고 미검증 범위를 명시한다.

> [AWS 공식 — RTO/RPO 복구 목표 정의](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_planning_for_recovery_objective_defined_recovery.html)

## 계층별 장애 대응

장애 시 가장 큰 실수는 첫 가설을 사실로 바꾸는 것이다. 작은 RDS instance를 쓴다고 해서 RDS가 병목이라고 단정하거나, CPU가 한 번 100%였다고 CPU가 최초 원인이라고 단정하면 잘못된 scaling으로 이어진다.

1. 사용자 증상과 발생 시간을 고정한다.
2. 배포·설정 변경과 resource event를 대조한다.
3. Client부터 Nginx, container, OS, JVM, pool, DB 순서로 signal을 같은 시간축에 놓는다.
4. 가설을 지지하는 증거와 배제하는 증거를 함께 찾는다.
5. 가장 먼저 실패한 resource 또는 invariant를 root cause 수준으로 좁힌다.
6. 최소 변경을 적용하고 같은 workload로 재검증한다.
7. 복구 뒤 정상 상태와 data 보존을 확인한다.

PawCycle은 250 RPS 실패에서 Hikari pending과 작은 RDS instance 때문에 DB 병목을 의심할 수 있었지만, RDS CPU와 latency가 낮았고 kernel log가 Backend cgroup OOM kill을 보여 줬다. 이처럼 비용이 작은 리소스를 사용했다는 사실과 실제 병목 근거를 분리해야 한다.

PawCycle의 비용·HA·OCI 이전 결정은 [[09. PawCycle Architecture Decision과 Trade-off]]와 [[10. AWS 종료와 OCI 전환 재평가]]에서 이어서 다룬다.
