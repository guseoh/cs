# 관측자 효과와 같은 서버 보정 실험

성능을 측정하려면 시스템 내부 상태를 봐야 한다. 그래서 Prometheus, Grafana, Exporter, APM Agent, Log Collector 같은 관측 도구를 추가한다.

문제는 이런 도구도 공짜가 아니라는 점이다.

Prometheus는 주기적으로 Metric을 가져오고 저장한다. Grafana는 Query를 실행하고 그래프를 만든다. Exporter와 Agent도 CPU, Memory, Network, Disk를 사용한다.

따라서 Application과 관측 도구를 같은 서버에서 실행하면 관측 도구가 성능 측정 대상에 영향을 줄 수 있다.

이 현상을 관측자 효과(Observer Effect)라고 생각할 수 있다.

성능 측정에서 중요한 질문은 “관측 도구를 쓰면 영향이 0인가?”가 아니다. 실제로는 0이기 어렵다.

더 현실적인 질문은 다음이다.

**관측 도구의 부하가 현재 Application 성능을 해석하기 어려울 정도로 큰가, 아니면 현재 자원 여유 안에서 충분히 작고 안정적인가?**

이 질문에 답하기 위해 같은 서버에서 관측 도구를 켰다 껐다 하며 비교하는 보정 실험(Calibration)을 사용할 수 있다.

## 관측 도구도 하나의 워크로드다

Application만 CPU와 Memory를 사용하는 것이 아니다.

같은 Host에 다음 Container가 있다고 가정하자.

~~~text
Backend
Prometheus
Grafana
Node Exporter
Metric Proxy
~~~

이들은 모두 같은 물리 자원을 공유할 수 있다.

~~~text
CPU Scheduler
RAM
Page Cache
Disk
Network Stack
Filesystem
~~~

Container가 분리되어 있다고 물리 자원까지 분리된 것은 아니다.

Docker Container는 Process와 Network, File System 경계를 나눌 수 있지만 같은 Host의 CPU와 Memory를 나눠 사용한다.

그래서 관측 도구를 추가한 뒤 Application p95가 변했다면 단순 우연인지 실제 관측 Overhead인지 확인할 필요가 있다.

## 왜 처음부터 별도 서버로 옮기지 않는가

관측 도구가 Application 성능에 영향을 줄 가능성이 있다고 해서 항상 별도 서버가 정답은 아니다.

별도 서버를 만들면 물리 자원 경쟁은 줄일 수 있지만 다음 비용이 생긴다.

~~~text
추가 Compute 비용
새 Network 경로
Firewall / NSG 관리
배포 대상 증가
Storage 관리
Backup / 복구
Monitoring 자체의 장애 대응
운영 복잡성
~~~

현재 Application CPU가 3%, Prometheus/Grafana를 포함해도 Host CPU가 5%이고 Memory도 충분하다면 별도 Compute를 만드는 것이 과도할 수 있다.

반대로 Host가 이미 90% CPU와 높은 I/O wait를 보이는데 Prometheus TSDB 쓰기까지 같은 Disk를 사용한다면 분리 근거가 강해진다.

기술 구성은 “보통 이렇게 한다”보다 **현재 측정된 간섭과 운영 요구**로 결정하는 것이 좋다.

## 보정 실험은 관측 도구가 결과를 얼마나 바꾸는지 확인한다

Calibration은 측정 장비 자체의 영향 범위를 확인하는 실험이다.

성능 최대치 탐색과 목적이 다르다.

질문은 다음과 같다.

~~~text
같은 Application
같은 Dataset
같은 HTTP 요청
같은 Host

Observability ON
vs
Observability OFF

Application 결과가
해석하기 어려울 정도로 달라지는가?
~~~

여기서 최대 RPS를 찾을 필요는 없다.

가벼운 고정 workload를 사용해 ON/OFF 상태의 차이를 비교하면 된다.

## ON → OFF 두 구간만 비교하면 시간 변화가 섞일 수 있다

다음처럼 측정했다고 하자.

~~~text
10:00 Observability ON
10:10 Observability OFF
~~~

OFF에서 p95가 5ms 낮아졌다고 해도 이것만으로 관측 도구 영향이라고 결론내리기 어렵다.

10분 사이에 다음이 달라졌을 수 있다.

~~~text
JIT warm-up
DB Buffer warm-up
Page Cache
Background Job
Network 상태
외부 부하
GC 주기
~~~

즉 시간 순서 자체가 교란 변수가 된다.

그래서 다음처럼 다시 ON으로 복구하는 구조가 더 강한 근거를 준다.

~~~text
Initial ON
→ OFF
→ Restored ON
~~~

마지막 ON이 처음 ON과 비슷한 범위로 돌아오고 OFF에서만 반복적으로 차이가 난다면 관측 도구 영향이라는 설명이 더 강해진다.

## 같은 조건을 유지해야 한다

Calibration에서는 다음 조건을 최대한 같게 유지한다.

~~~text
Application commit
Container image
Dataset
Endpoint
Request 수
Request 간격
Host
Container limit
JVM Option
DB
Network path
측정 시간
~~~

Observability ON/OFF 외에 다른 조건까지 바뀌면 결과 차이의 원인을 분리하기 어렵다.

예를 들어 OFF 실험만 새 Application Version으로 배포했다면 관측 도구 영향과 코드 변경 영향을 구분할 수 없다.

## 사용자 응답과 내부 자원을 같이 비교한다

관측 도구 영향은 Prometheus CPU만 보는 것으로 끝나지 않는다.

Application 사용자 결과가 실제로 변했는지 확인해야 한다.

예를 들어:

~~~text
HTTP error
p50
p95
p99
~~~

를 보고 같은 시각의 Host/Container 상태를 본다.

~~~text
CPU user/system/iowait
MemAvailable
Swap in/out
Backend CPU / Memory
Prometheus CPU / Memory
Grafana CPU / Memory
Disk I/O
RestartCount
OOMKilled
~~~

Prometheus Memory가 300MiB 늘었다는 사실 자체보다 **그 결과 Application에 Memory Pressure와 응답 지연이 생겼는가**가 더 중요하다.

## 퍼센트와 퍼센트포인트는 다르다

CPU 사용률 비교에서 자주 혼동하는 표현이 있다.

OFF 상태 CPU가 2.5%이고 ON 상태가 3.2%라고 하자.

절대 차이는:

~~~text
3.2% - 2.5%
= 0.7%p
~~~

즉 0.7 퍼센트포인트 증가다.

상대 증가율은:

~~~text
0.7 / 2.5
≈ 28%
~~~

정도다.

“CPU가 28% 증가했다”라고만 쓰면 변화가 매우 커 보이지만 실제 Host CPU 사용률은 2.5%에서 3.2%로 변한 것이다.

그래서 성능 보고에서는 %와 %p를 구분하는 것이 좋다.

## Headroom은 한계까지 남은 여유다

Headroom은 현재 사용량과 시스템 한계 사이에 남은 여유를 뜻한다.

다음 두 변화는 모두 1%p 증가지만 의미가 다르다.

~~~text
CPU 3% → 4%

CPU 95% → 96%
~~~

첫 번째는 CPU 여유가 매우 크다.

두 번째는 이미 포화에 가까운 상태다.

따라서 관측 Overhead를 평가할 때 단순 증가량뿐 아니라 **현재 한계까지 얼마나 여유가 남았는지** 같이 본다.

## Memory도 절대 사용량과 압력을 구분한다

Observability ON에서 MemAvailable이 300MiB 줄었다고 해보자.

Prometheus와 Grafana가 Memory를 사용하기 때문에 자연스러운 변화일 수 있다.

다음 상태라면 실제 Application 간섭은 제한적일 수 있다.

~~~text
MemAvailable 충분
Swap activity 없음
iowait 없음
Application p95 변화 작음
Restart 없음
OOM 없음
~~~

반대로:

~~~text
MemAvailable 거의 0
Swap in/out 지속
iowait 증가
Backend RSS 증가
p95 증가
~~~

라면 같은 Host 구조를 재검토할 근거가 강해진다.

## Prometheus의 Disk 사용도 볼 수 있다

Prometheus는 Time Series Database에 Metric을 저장한다.

수집하는 Series 수가 많고 Scrape Interval이 짧으면 Storage Write와 Compaction 작업도 늘 수 있다.

같은 Disk를 Application이 사용한다면 I/O 경쟁이 생길 가능성이 있다.

그래서 Same-host 구조에서는 CPU와 Memory뿐 아니라 다음도 본다.

~~~text
Prometheus TSDB 크기
Disk Available
Disk I/O
I/O wait
Compaction 시각
~~~

Application이 DB를 외부 Managed DB에 두더라도 Local Log나 Temporary File과 Prometheus Storage가 같은 Disk를 사용할 수 있다.

## Scrape Interval을 짧게 하면 더 정확하기만 한 것은 아니다

Scrape Interval을 30초에서 1초로 줄이면 더 세밀한 시계열을 얻을 수 있다.

하지만 Target 요청 수와 Time Series Write 양도 크게 증가한다.

~~~text
30초마다 수집
→ 분당 2회

1초마다 수집
→ 분당 60회
~~~

Target 수와 Metric 수가 많다면 차이는 더 커진다.

따라서 더 짧은 수집 주기가 항상 더 좋은 것은 아니다.

보고 싶은 사건의 시간 크기와 Storage/CPU 비용을 같이 고려한다.

## APM Agent도 Overhead가 있다

APM Agent는 Method 호출, Trace, SQL, External Call 같은 정보를 수집한다.

Sampling 비율과 Instrumentation 범위가 넓어질수록 CPU, Allocation, Network, Storage 비용이 커질 수 있다.

성능 Before/After 테스트에서 한쪽만 APM을 켜고 다른 쪽은 끄면 결과 조건이 달라진다.

따라서 APM 설정도 성능 실험 조건에 포함해야 한다.

## Debug Log는 특히 측정 결과를 크게 바꿀 수 있다

성능 문제를 조사하기 위해 Debug Log를 대량으로 켜면 String 생성, Serialization, File Write, Log Collector 전송 비용이 증가할 수 있다.

다음과 같은 조건 차이는 직접 비교하기 어렵다.

~~~text
Before
INFO Log

After
DEBUG Log
모든 SQL Parameter 기록
모든 HTTP Body 기록
~~~

성능 측정에서는 Production과 가까운 Log Level을 유지하고 필요한 경우 제한된 구간에서만 추가 진단을 한다.

## 관측 도구가 죽는 것도 운영 문제다

Observability Stack을 같은 Host에 두는 문제는 Application 간섭만이 아니다.

Application Host 자체가 장애 나면 Monitoring도 함께 사라질 수 있다.

~~~text
Host 장애
→ Backend down
→ Prometheus도 down
→ 장애 순간 Metric 수집 중단
~~~

운영 요구가 높아지면 이런 Failure Domain 공유가 별도 Host 분리 근거가 될 수 있다.

LINE의 Prometheus Container 장애 사례처럼 Monitoring 시스템도 하나의 운영 시스템이므로 자체 Resource와 장애 상태를 관찰해야 한다.

관련 자료:
- [LINE — Prometheus Container CrashLoopBackOff Troubleshooting](https://engineering.linecorp.com/ko/blog/prometheus-container-kubernetes-cluster)

## 같은 서버 보정 실험에서 작은 표본의 p99를 과해석하지 않는다

Calibration은 보통 짧은 고정 요청으로 실행할 수 있다.

예를 들어 각 구간에 HTTP Sample이 30개뿐이라면 p99는 가장 느린 한두 요청에 크게 좌우된다.

~~~text
29개
20~30ms

1개
250ms
~~~

이면 p99가 크게 튈 수 있다.

따라서 짧은 Calibration에서는 p50, p95, 오류, Host Resource를 중심으로 보고 p99와 Max는 이상치 참고로 해석하는 편이 안전하다.

백분위 해석은 [[07. Latency Percentile과 Tail Latency]]에서 더 자세히 설명한다.

## ON/OFF 결과를 읽는 예

가상의 결과다.

~~~text
Observability OFF

p50 = 23ms
p95 = 32ms
error = 0%

CPU user+system = 2.5%
MemAvailable = 2.4GiB
iowait = 0
~~~

~~~text
Observability ON

p50 = 24ms
p95 = 34ms
error = 0%

CPU user+system = 3.3%
MemAvailable = 2.1GiB
iowait = 0
~~~

ON 상태에서 CPU와 Memory 사용은 분명히 증가했다.

하지만 CPU 전체 사용률은 여전히 매우 낮고, I/O wait와 오류가 없으며, p95 변화도 작은 범위라면 현재 실험 환경에서는 관측 간섭이 제한적이라고 판단할 수 있다.

이 판단은 “Prometheus Overhead가 0이다”라는 뜻이 아니다.

**Overhead는 존재하지만 현재 성능 실험을 해석하지 못하게 할 정도는 아니라는 제한된 결론**이다.

## 별도 서버로 분리할 근거는 반복되는 간섭에서 만든다

다음 현상이 같은 조건에서 반복된다면 분리 근거가 강해진다.

~~~text
Observability ON에서
p95 / error가 반복 악화

Prometheus/Grafana가
CPU Headroom을 크게 사용

MemAvailable 급감
Swap 발생

TSDB I/O와
Application I/O 경쟁

Backend OOM / Restart

Application Host 장애 시
Monitoring이 같이 사라지는 것이
운영 요구상 허용 불가
~~~

이때 별도 Compute를 검토한다.

반대로 여유가 충분하고 사용자 결과 변화가 작다면 같은 Host 구성을 유지하고 비용과 복잡도를 줄이는 것도 합리적이다.

## 관측 도구 자체의 Overhead를 추상적으로 가정하지 않는다

우아한형제들의 Performance Insights 관련 글에서도 Monitoring 기능의 성능 영향을 막연히 두려워하기보다 실제 테스트를 통해 확인한다.

이 사고방식이 중요하다.

~~~text
관측 도구가 느릴 것 같다
→ 분리

가 아니라

실제 Overhead 측정
→ 현재 여유와 사용자 결과 확인
→ 유지 또는 분리 판단
~~~

으로 접근한다.

- [우아한형제들 — Performance Insight 써도 돼요?](https://techblog.woowahan.com/2593/)

## Calibration도 Before/After 실험이다

관측자 효과 측정도 일반 성능 실험과 같은 원칙을 따른다.

~~~text
가설
Observability Stack이
Application 성능에 의미 있는 영향을 준다.

통제
Application / Dataset / Request / Host 동일

변경
Observability ON ↔ OFF

측정
응답 시간 + 오류 + Host/Container

복구
다시 ON

판정
차이가 반복적으로 재현되는가
~~~

따라서 Same-host Calibration은 단순 운영 확인이 아니라 작은 인과 실험이다.

Before/After 설계는 [[09. Before After와 성능 실험의 인과관계]]에서 이어서 다룬다.
