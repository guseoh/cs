# Observer Effect와 Same-host Calibration

## 관측 도구도 Workload다

Prometheus는 scrape와 TSDB 저장을 수행하고 Grafana는 query/rendering을 수행한다. Exporter와 Agent도 CPU, memory, network를 사용한다.

같은 host에 있으면 Application과 다음을 공유한다.

- CPU scheduler
- memory
- page cache
- disk I/O
- network stack

따라서 측정 도구가 측정 대상에 영향을 주는 observer effect를 확인해야 한다.

## 왜 별도 서버로 바로 분리하지 않는가

Separate host는 resource competition을 줄이지만:

- Compute 비용
- network/security
- 운영 대상
- failure mode
- storage 관리

가 늘어난다.

우아한형제들 Performance Insights 글도 모니터링 기능 자체의 overhead를 “얼마나 나빠지는가”로 정량화하려는 관점을 보여 준다.

- [우아한형제들 — Performance Insight 써도 돼요?](https://techblog.woowahan.com/2593/)

## 관측/로깅 파이프라인은 실제로 Stress Test 대상이다

2026년 카카오 메시징팀은 관측/로깅 인프라 추가를 명시적인 스트레스 테스트 사례로 다룬다. logstash, fluent bit, OpenTelemetry 같은 도구는 운영 대응에 중요하지만 서버 입장에서는 새로운 CPU/Memory/Network workload이기도 하다.

- [카카오 — 메시징 서버의 스트레스 테스트 노하우와 AI가 덜어 준 부분](https://tech.kakao.com/posts/822)

따라서 다음 변경은 “기능 코드 변경이 아니니까 성능 검증 불필요”로 처리하면 안 된다.

~~~text
Logging pipeline 변경
Metrics exporter 추가
Trace agent 추가
Sidecar 추가
Profiling agent 추가
~~~

이런 변경은 동일 workload 전후 비교 대상이 된다.

## Calibration의 질문

~~~text
Observability ON이
Application baseline을 해석하기 어려울 만큼
결과를 바꾸는가?
~~~

Capacity stress test와 목적이 다르다.

## ON → OFF → ON

두 구간만 비교하면 시간 변화와 observer effect를 분리하기 어렵다.

~~~text
Initial ON
→ OFF
→ Restored ON
~~~

으로 마지막 ON이 원래 범위로 돌아오는지 확인한다.

통제할 것:

- Application version
- dataset
- endpoint
- request rate/interval
- duration
- host
- container limit
- DB
- network path

## 비교 지표

- HTTP error
- p50/p95
- CPU us/sy/wa
- MemAvailable
- swap si/so
- container CPU/memory
- restart/OOM
- disk

### Memory

ON에서 MemAvailable 감소는 자연스럽다.

하지만:

~~~text
memory 감소
→ swap-in 반복
→ iowait 증가
→ latency 악화
~~~

같은 연결이 있어야 Application 성능 영향으로 강하게 말할 수 있다.

### CPU

OFF 2.5%, ON 3.2%면 +0.7%p다.

idle 97% host에서의 +0.7%p와 CPU 95% host에서의 +0.7%p는 의미가 다르다.

절대 차이와 headroom을 같이 본다.

## Observability 자체도 관측한다

- Prometheus memory
- TSDB size
- scrape duration/failure
- Grafana memory
- restart
- OOM

관측 시스템이 불안정하면 성능 evidence도 불완전해진다.

LINE은 성능 테스트 리포트에 Prometheus/Grafana로 수집한 시스템·JVM 지표를 같이 제공한다.

- [LINE — 서버 사이드 테스트 자동화 여정 5](https://engineering.linecorp.com/ko/blog/server-side-test-automation-5/)

## Separate-host 재검토 조건

- ON에서 latency/error 반복 악화
- 지속적인 swap-in
- iowait 증가
- OOM/restart
- Grafana/Prometheus가 Application headroom 크게 잠식
- TSDB I/O가 baseline에 영향
- Application host 장애 시 monitoring 동시 손실을 허용할 수 없음

기술 취향이 아니라 **측정된 interference와 운영 요구**로 분리를 결정한다.

실제 적용은 [[../../Project/pawCycle/Performance/02. Observability Gate와 Same-host Calibration|PawCycle Same-host Calibration]]을 참고한다.


## 관측자 효과라는 말을 쉽게 이해하기

관측자 효과(Observer Effect)는 **측정하기 위해 추가한 도구가 측정 대상 자체의 상태를 바꾸는 현상**을 뜻한다.

예를 들어 Application CPU를 보기 위해 Exporter와 Prometheus를 같은 서버에 추가했다고 하자.

이 도구들도 CPU와 memory를 사용한다.

~~~text
Application
Prometheus
Grafana
Exporter

→ 같은 Host CPU와 memory를 사용
~~~

따라서 관측 도구가 없을 때와 있을 때의 Application 성능이 조금 달라질 수 있다.

## 같은 서버에 둔다는 것은 무엇을 공유한다는 뜻인가

같은 Host에 Application과 관측 도구를 같이 실행하면 다음 자원을 공유할 수 있다.

~~~text
CPU scheduler
물리 memory
page cache
disk I/O
network stack
filesystem
~~~

Application Container와 Prometheus Container를 따로 만들었다고 해서 물리 자원까지 완전히 분리된 것은 아니다.

Container는 실행 경계를 나눌 수 있지만 같은 Host의 CPU와 memory를 나눠 쓸 수 있다.

## Calibration은 무엇인가

Calibration은 쉽게 말하면 **측정 장비가 결과를 얼마나 바꾸는지 먼저 확인하는 보정 실험**이다.

여기서 질문은 최대 처리량이 아니다.

~~~text
관측 도구가 켜져 있을 때
Application 기준선이
해석하기 어려울 만큼 달라지는가?
~~~

를 확인한다.

## 왜 ON과 OFF 두 번만 비교하지 않는가

다음처럼 한 번씩만 비교했다고 하자.

~~~text
10:00 Observability ON
10:10 Observability OFF
~~~

OFF에서 p95가 낮아졌다고 해서 반드시 관측 도구 때문이라고 볼 수 없다.

시간이 지나며 DB cache가 따뜻해졌거나 background job이 끝났을 수도 있다.

그래서 다음처럼 다시 ON으로 돌리는 구조가 더 강한 근거를 준다.

~~~text
Initial ON
→ OFF
→ Restored ON
~~~

마지막 ON에서 결과가 다시 처음 ON 범위로 돌아온다면 관측 도구 영향이라는 주장이 더 강해진다.

## %와 %p는 다르다

CPU 사용률을 비교할 때 퍼센트와 퍼센트포인트를 구분해야 한다.

예를 들어 CPU가 2.5%에서 3.2%로 올랐다.

절대 차이는:

~~~text
3.2% - 2.5%
= 0.7%p
~~~

이다.

상대 증가율은 약 28%다.

“CPU가 28% 증가했다”는 표현과 “0.7%p 증가했다”는 표현은 느낌이 매우 다르다.

성능 보고에서는 어떤 기준으로 표현했는지 명확하게 적는 것이 좋다.

## Headroom은 무엇인가

Headroom은 현재 사용량에서 한계까지 남은 여유를 뜻한다.

CPU가 3%에서 4%로 1%p 올랐을 때와 95%에서 96%로 1%p 올랐을 때는 의미가 다르다.

~~~text
CPU 3% → 4%
→ 여유가 매우 큼

CPU 95% → 96%
→ 이미 포화점에 매우 가까움
~~~

따라서 관측 도구의 CPU overhead를 볼 때 절대 증가량과 남은 여유를 같이 본다.

## Memory overhead도 같은 방식으로 본다

Prometheus와 Grafana가 memory를 추가로 사용하는 것은 자연스럽다.

중요한 질문은 Application에 실제 문제를 만들 정도인가이다.

~~~text
ON
MemAvailable 조금 감소
Swap activity 없음
Application latency 동일
→ 영향 제한적일 수 있음
~~~

반대로:

~~~text
ON
MemAvailable 크게 감소
Swap-in/out 반복
iowait 증가
p95 증가
→ 같은 Host 관측 구조 재검토 근거
~~~

처럼 여러 지표가 연결되면 영향이 더 강하다.

## 관측 도구를 별도 서버로 옮기면 무조건 좋은가

물리 자원 경쟁은 줄어들 수 있지만 새로운 비용이 생긴다.

~~~text
추가 Compute 비용
추가 Network 경로
보안 규칙
배포 대상 증가
Storage 관리
Monitoring 자체의 장애 대응
~~~

그래서 Prometheus를 무조건 별도 서버에 두는 식의 정답보다 현재 규모와 실제 간섭을 측정한 뒤 판단한다.

우아한형제들의 Performance Insights 관련 글도 관측 기능의 overhead를 추상적으로 걱정하기보다 실제 성능 영향을 측정해 판단하는 관점을 보여 준다.

- [우아한형제들 — Performance Insight 써도 돼요?](https://techblog.woowahan.com/2593/)

## Same-host Calibration을 어떻게 기록하는가

최소한 다음 조건을 고정해야 한다.

~~~text
Application version
Dataset
Endpoint
Request rate
측정 시간
Host
Container limit
DB
Network path
~~~

그리고 ON/OFF/ON 각 구간에서 다음을 같이 본다.

~~~text
HTTP 오류
p50 / p95
CPU us/sy/wa
MemAvailable
Swap si/so
Container CPU / memory
RestartCount
OOMKilled
Disk I/O
~~~

한 지표만 조금 변했다고 결론내리지 않고 사용자 응답 시간과 Host/Container 상태를 같이 본다.

## Separate Host로 옮길 근거

다음이 반복적으로 관찰되면 별도 Host를 검토할 근거가 강해진다.

~~~text
Observability ON에서 p95/error 반복 악화
지속적인 Swap
iowait 증가
Application OOM / Restart
Prometheus/Grafana가 Headroom 크게 잠식
TSDB I/O가 Application과 경쟁
Application Host 장애 시 Monitoring까지 같이 사라지는 구조를 허용하기 어려움
~~~

즉 분리 여부는 기술 취향보다 **측정된 간섭과 운영 요구**로 결정한다.

실제 PawCycle 적용은 [[../../Project/pawCycle/Performance/02. Observability Gate와 Same-host Calibration|PawCycle Same-host Calibration]]에서 확인할 수 있다.
