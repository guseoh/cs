# Observability와 계층별 병목 분리

## 느리다는 사실과 느린 이유는 다르다

외부 부하 도구는 주로 결과를 알려 준다.

- actual RPS
- status/error
- p50/p95/p99
- timeout
- dropped request

이 값으로 문제가 발생했다는 사실은 알 수 있다. 하지만 CPU인지, GC인지, Hikari인지, DB인지 알 수는 없다.

성능 분석에는 결과 지표와 원인 후보 지표를 같은 시간축으로 연결하는 작업이 필요하다.

LINE은 CPU·memory·load·swap·disk I/O뿐 아니라 GC, heap, thread, direct memory, file descriptor를 같이 수집해야 병목 범위를 좁힐 수 있다고 설명한다.

- [LINE — 서버 사이드 테스트 자동화 여정 4](https://engineering.linecorp.com/ko/blog/server-side-test-automation-4/)
- [LINE — 서버 사이드 테스트 자동화 여정 5](https://engineering.linecorp.com/ko/blog/server-side-test-automation-5/)

## 계층별로 나눈다

~~~mermaid
flowchart LR
    C["Client"] --> N["Nginx / LB"]
    N --> H["Host / Container"]
    H --> J["JVM"]
    J --> T["Tomcat Thread"]
    T --> P["HikariCP"]
    P --> D["Database"]
~~~

| 계층 | 대표 지표 | 질문 |
| --- | --- | --- |
| Client | RPS, latency, error | 사용자가 실제로 느린가 |
| Nginx/LB | upstream, connection | ingress 경계인가 |
| Host | CPU, memory, swap, iowait | 머신 자원이 포화됐나 |
| Container | limit, OOM, restart | cgroup 제한인가 |
| JVM | heap, GC, thread, direct memory | Java runtime 문제인가 |
| Tomcat | active thread, queue | 요청이 thread 앞에서 기다리나 |
| Hikari | active, idle, pending | DB connection을 기다리나 |
| DB | CPU, query, lock, I/O | SQL/lock/storage 문제인가 |

## Metric 하나로 Root Cause를 정하지 않는다

CPU가 높다고 최초 원인이 CPU라는 뜻은 아니다. OOM 후 restart한 JVM의 startup/JIT 때문에 CPU가 순간적으로 높아질 수 있다.

Hikari pending도 “DB가 느리다”와 같은 말이 아니다.

~~~text
Query가 느림
→ connection 반환 지연
→ pending 증가
~~~

~~~text
Transaction이 김
→ connection hold time 증가
→ pending 증가
~~~

~~~text
요청 동시성 급증
→ connection demand 증가
→ pending 증가
~~~

그래서 Hikari와 DB CPU/query latency/lock/thread를 같이 본다.

- [우아한형제들 — HikariCP Dead lock 실전편](https://techblog.woowahan.com/2663/)

## 시계열 순서

Snapshot 하나보다 사건의 순서가 중요하다.

~~~text
latency 증가
→ thread 증가
→ Hikari pending 증가
→ OOM
→ restart
~~~

순서가 보이면 원인 후보를 훨씬 좁힐 수 있다.

LINE 데이터 엔지니어링 사례는 failover 직전 JVM thread가 급증한 것을 Prometheus/Grafana로 확인하고 thread dump로 더 좁혔다.

## Prometheus와 Grafana

Prometheus는 시계열 metric을 수집·저장하고 Grafana는 질의·시각화한다.

중요한 것은 dashboard가 존재한다는 사실이 아니다.

~~~text
metric endpoint가 실제로 reachable한가
target이 up인가
필요한 metric이 있는가
label이 올바른가
실험 시각과 일치하는가
단위와 집계 방식을 이해하는가
~~~

를 확인해야 한다.

- [LINE — Armeria에서 Prometheus 지표 모니터링하기](https://engineering.linecorp.com/ko/blog/armeria-prometheus-monitoring/)
- [LINE — Armeria 지표 커스터마이징하기](https://engineering.linecorp.com/ko/blog/armeria-metrics-customizing/)

## 가설을 버리는 것이 중요하다

~~~text
가설: DB가 병목

DB CPU 낮음
Query latency 낮음
I/O 낮음
Application OOM 확인

→ DB scale-up 가설 폐기
~~~

성능 분석은 가능한 기술을 다 적용하는 것이 아니라 **근거로 틀린 가설을 제거하는 과정**이다.

LINE Kafka 사례도 Produce API p99 악화를 시작점으로 disk read와 network thread utilization을 함께 확인해 범위를 좁힌다.

- [LINE — Kafka를 사용하는 방법 2편](https://engineering.linecorp.com/ko/blog/how-to-use-kafka-in-line-2/)

## Observability Gate

부하 테스트가 끝난 뒤 metric이 없다는 사실을 발견하면 실험을 다시 해야 한다.

부하 전 최소 확인:

- metric endpoint
- Prometheus target
- JVM metric
- Hikari metric
- container restart/OOM
- DB metric time window

Observability는 성능 테스트의 부가 기능이 아니라 **실험 장비의 일부**다.
