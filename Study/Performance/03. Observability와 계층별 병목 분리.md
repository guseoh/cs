# 관측 가능성과 계층별 병목 분리

사용자는 “느리다”, “오류가 난다”, “화면이 멈췄다”처럼 결과를 경험한다. 하지만 서버 내부에서 실제로 어떤 일이 일어났는지는 외부 결과만으로 알기 어렵다.

같은 2초 응답도 원인은 전혀 다를 수 있다.

~~~text
CPU가 포화됨
GC pause가 길어짐
Tomcat Thread가 부족함
HikariCP에서 Connection을 기다림
MySQL Query가 느려짐
DB Lock을 기다림
외부 API 응답이 늦음
Container가 OOM 후 재시작함
Network 연결 생성이 지연됨
~~~

관측 가능성(Observability)은 이런 내부 상태를 볼 수 있도록 도구를 많이 설치한다는 뜻이 아니다. **외부에서 보이는 결과와 내부 신호를 연결해서, 시스템 안에서 어떤 일이 일어났는지 추론할 수 있는 상태를 만드는 것**이다.

성능 분석에서 관측 가능성이 중요한 이유는 성능 테스트가 “문제가 있다”는 사실만 알려주고 끝나면 실제 원인 조사에 다시 많은 시간이 들기 때문이다.

LINE의 성능 테스트 자동화 사례에서도 CPU, 메모리, Load, Swap, Disk I/O 같은 시스템 자원뿐 아니라 GC, Heap, Thread, Direct Memory, File Descriptor를 함께 수집했다. 성능 저하를 발견한 뒤 어디를 조사해야 하는지 실마리를 남기기 위해서다.

## 모니터링과 관측 가능성은 무엇이 다른가

모니터링(Monitoring)은 미리 정한 지표와 상태를 계속 확인하는 활동이다.

예를 들어:

~~~text
CPU 사용률
HTTP 5xx
Backend Health
DB Connection
Disk 사용량
~~~

을 대시보드나 알림으로 보는 것이 모니터링이다.

관측 가능성은 그보다 한 단계 넓다.

예상하지 못한 문제가 생겼을 때 현재 확보한 지표, 로그, 추적 정보를 이용해 **왜 그런 상태가 되었는지 새로운 질문을 던지고 조사할 수 있는가**를 본다.

예를 들어 CPU Alert는 미리 만들어 둔 모니터링 규칙이다.

하지만 “CPU는 정상인데 p99만 증가했다. 왜 특정 요청만 느려졌는가?” 같은 질문에 답하려면 Thread, Connection Pool, Query, Trace 같은 다른 신호가 필요하다.

따라서 관측 가능성은 대시보드 개수보다 **원인 후보를 줄일 수 있는 데이터가 있는가**가 더 중요하다.

## Metric은 시간에 따라 변하는 상태를 숫자로 표현한다

지표(Metric)는 시스템 상태를 숫자로 표현한 값이다.

예를 들어:

~~~text
process CPU usage
JVM Heap used
GC pause count
Tomcat active thread
Hikari active connection
Hikari pending
HTTP request count
HTTP response latency
~~~

이런 값은 보통 시간과 함께 저장된다.

Metric의 장점은 많은 요청과 긴 시간 구간을 압축해서 추세를 보기 좋다는 것이다.

예를 들어 개별 요청 로그 수십만 줄을 읽지 않아도 p95 응답 시간이 어느 시각부터 증가했는지 그래프로 볼 수 있다.

하지만 Metric은 상세 문맥을 잃는다.

“p95가 1초”라는 값만으로 어떤 URL의 어떤 사용자 요청이 왜 1초 걸렸는지 알 수 없다.

따라서 Metric은 전체 상태와 방향을 보고 **어느 계층을 더 깊게 조사할지 결정하는 신호**로 사용한다.

## Log는 사건의 세부 문맥을 남긴다

로그(Log)는 특정 시점에 발생한 사건을 비교적 구체적인 문장이나 구조화된 필드로 남긴다.

예를 들어:

~~~text
DB Connection 획득 Timeout
OutOfMemoryError
upstream connect error
specific exception
retry exhausted
~~~

같은 사건은 Metric보다 Log에서 원인을 더 직접적으로 볼 수 있다.

반대로 모든 요청 로그를 다 읽어야 전체 오류율이 1%에서 10%로 증가했다는 사실을 파악한다면 매우 비효율적이다.

Metric과 Log는 서로 대체 관계가 아니다.

~~~text
Metric
→ 언제, 얼마나 이상해졌는가

Log
→ 그 시각에 어떤 사건이 발생했는가
~~~

처럼 연결해서 본다.

## Trace는 요청 하나가 여러 계층을 지나간 시간을 보여준다

분산 추적(Distributed Tracing)은 하나의 요청이 여러 서비스와 내부 구간을 지나가는 흐름을 추적한다.

예를 들어:

~~~text
HTTP 요청 900ms

Controller       10ms
Service          20ms
DB Connection   400ms
SQL              30ms
External API    420ms
기타             20ms
~~~

처럼 요청 시간이 어디에서 사용됐는지 볼 수 있다.

모놀리식 애플리케이션에서도 APM이나 Trace를 사용하면 Controller, Service, JDBC, 외부 호출의 시간을 나눠 볼 수 있다.

Trace는 특히 “평균은 정상인데 일부 요청만 느리다”는 문제에서 느린 요청 샘플을 구체적으로 분석하는 데 유용하다.

다만 모든 Trace를 100% 저장하면 비용과 부하가 커질 수 있기 때문에 Sampling 정책이 필요할 수 있다.

## 시계열은 값보다 사건의 순서를 보여준다

성능 원인을 찾을 때 현재 값 하나보다 시간 순서가 중요하다.

다음 Snapshot만 보면:

~~~text
CPU = 90%
p95 = 2초
~~~

CPU가 원인처럼 보인다.

하지만 시계열을 보면 다음과 같을 수 있다.

~~~text
10:00 Container OOM
10:00:02 Backend Restart
10:00:04 Class Loading / JIT
10:00:05 CPU 90%
10:00:06 p95 2초
~~~

이 경우 CPU 증가는 최초 원인이 아니라 재시작 이후의 결과일 수 있다.

반대로:

~~~text
10:00 RPS 증가
10:01 Hikari pending 증가
10:02 DB Query latency 증가
10:03 p95 증가
~~~

라면 DB/Connection 계층을 조사할 근거가 더 강해진다.

그래서 성능 분석에서는 여러 지표를 **같은 시간축으로 맞추는 것**이 중요하다.

## Prometheus는 무엇을 하는가

Prometheus는 Metric을 수집하고 시계열 형태로 저장하는 시스템이다.

Spring Boot에서는 Micrometer와 Actuator를 통해 Prometheus가 읽을 수 있는 Metric Endpoint를 제공할 수 있다.

Prometheus는 일정 주기마다 이 Endpoint를 호출해서 값을 가져온다. 이 과정을 Scrape라고 부른다.

~~~text
Prometheus
→ 일정 주기
→ /actuator/prometheus 요청
→ Metric 수집
→ 시각과 함께 저장
~~~

예를 들어 Scrape Interval이 30초라면 약 30초마다 값을 수집한다.

여기서 중요한 한계가 있다.

2초 동안만 발생한 짧은 CPU Spike가 30초 사이에 나타났다 사라지면 특정 Metric 표현 방식에서는 직접 관찰하기 어려울 수 있다.

따라서 수집 주기, Metric 종류, 집계 방식이 무엇인지 알아야 그래프를 올바르게 해석할 수 있다.

## Prometheus Target은 무엇인가

Target은 Prometheus가 Metric을 가져오려는 대상이다.

예를 들어 Production Backend의 Metric Proxy가 Target이 될 수 있다.

Target 상태가 UP이라는 것은 Prometheus가 현재 그 Endpoint에 접근해 Metric을 가져오는 데 성공하고 있다는 뜻이다.

DOWN이면 다음과 같은 이유를 생각할 수 있다.

~~~text
Backend down
Metric Endpoint 오류
Network 연결 실패
잘못된 Target 주소
Authentication 문제
Proxy 문제
~~~

성능 테스트 전에 Target이 UP인지 확인하는 이유는 간단하다.

테스트가 끝난 뒤 “Metric이 수집되지 않았다”는 사실을 발견하면 내부 원인을 분석할 자료가 없기 때문이다.

## Grafana는 Metric을 예쁘게 보여주는 도구 이상의 역할을 한다

Grafana는 Prometheus 같은 데이터 소스에 Query를 보내 시계열을 시각화한다.

Grafana 자체가 Root Cause를 찾아주는 것은 아니다.

대시보드의 중요한 역할은 **서로 다른 계층의 지표를 같은 시간축에서 비교하기 쉽게 배치하는 것**이다.

예를 들어 한 화면에서 다음을 함께 볼 수 있다.

~~~text
actual RPS
p95 / p99
HTTP error

Host CPU / Memory

JVM Heap / GC / Thread

Tomcat Thread

Hikari active / pending

MySQL CPU / Query latency
~~~

p95가 증가한 바로 그 시각에 Hikari pending이 올라갔는지, GC pause가 있었는지 확인할 수 있다.

그래서 대시보드는 지표 개수를 늘리는 것보다 **질문에 답하기 좋은 구조로 배치하는 것**이 중요하다.

## Label은 Metric을 구분하지만 너무 많으면 비용이 커질 수 있다

Prometheus Metric에는 Label을 붙여 여러 차원을 구분할 수 있다.

예를 들어 HTTP 요청 수를 다음처럼 나눌 수 있다.

~~~text
method="GET"
status="200"
uri="/api/products"
~~~

이렇게 하면 Endpoint와 상태 코드별로 Metric을 나눠 볼 수 있다.

하지만 사용자 ID, 주문 ID처럼 값 종류가 매우 많은 필드를 Label로 넣으면 시계열 수가 폭발적으로 증가할 수 있다.

예를 들어 사용자 100만 명의 ID를 Label로 사용하면 Metric 하나가 매우 많은 별도 Time Series를 만들 수 있다.

이것을 Metric Cardinality 문제라고 부른다.

성능 관측을 위해 세부 정보를 많이 넣는다고 항상 좋은 것은 아니다.

개별 ID 같은 세부 문맥은 Log나 Trace가 더 적합할 수 있다.

## 외부 결과와 내부 원인 후보를 먼저 나눈다

성능 분석에서 가장 먼저 보는 것은 사용자 관점 결과다.

~~~text
target RPS
actual RPS
error rate
timeout
p50
p95
p99
~~~

이 값들이 정상이라면 내부 Metric이 약간 변했다고 바로 장애라고 볼 필요는 없다.

반대로 사용자 결과가 나빠졌다면 내부 지표를 이용해 원인을 좁힌다.

~~~text
Host / Container
→ CPU / Memory / I/O / Network

JVM
→ Heap / GC / Thread / Native Memory

Application Server
→ Tomcat Thread

Connection Pool
→ Hikari active / pending

Database
→ Query / Lock / CPU / I/O
~~~

이 순서는 항상 고정된 정답은 아니지만 “사용자가 실제로 느렸는가?”와 “왜 느렸는가?”를 분리하는 데 도움이 된다.

## 하나의 Metric으로 Root Cause를 결정하지 않는다

예를 들어 Hikari pending이 20으로 증가했다고 하자.

이 값은 “DB Connection을 기다리는 요청이 있다”는 사실을 보여 준다.

하지만 원인은 여러 가지다.

~~~text
Query가 느려 Connection 반납이 늦음
Transaction이 너무 길음
DB Lock 대기
요청 동시성 급증
Pool 크기가 너무 작음
Application이 Connection을 잡은 채 다른 작업 대기
~~~

따라서 pending만 보고 Pool Size를 올리면 잘못된 수정이 될 수 있다.

우아한형제들의 HikariCP 장애 사례에서도 Thread 수, 한 Task가 요구하는 동시 Connection 수, Pool Size의 관계를 조사한다. 단순히 “Connection이 부족하니 숫자를 키운다”로 끝나지 않는다.

- [우아한형제들 — HikariCP Dead lock 실전편](https://techblog.woowahan.com/2663/)

## CPU가 높다는 사실과 CPU가 원인이라는 주장은 다르다

CPU 사용률과 p95가 동시에 증가했다고 가정하자.

~~~text
CPU 95%
p95 1.5초
~~~

CPU가 병목일 가능성은 있다.

하지만 요청량 증가라는 제3의 원인이 둘을 동시에 만들었을 수도 있다.

~~~text
RPS 급증
├─ CPU 증가
└─ Queue 증가
   → p95 증가
~~~

또는 OOM 후 재시작 과정에서 CPU가 일시적으로 증가했을 수도 있다.

그래서 상관관계(Correlation)와 인과관계(Causation)를 구분해야 한다.

성능 분석에서는 다음을 같이 본다.

~~~text
무엇이 먼저 변했는가
다른 원인 후보는 정상인가
변경을 되돌리면 현상이 사라지는가
같은 조건에서 재현되는가
~~~

이 내용은 [[09. Before After와 성능 실험의 인과관계]]에서 더 자세히 다룬다.

## Thread 수 증가를 발견한 뒤 Thread Dump로 내려가는 이유

Metric은 Thread 수가 증가했다는 사실을 빠르게 알려 준다.

예를 들어:

~~~text
평소 Thread
300

장애 직전
15,000
~~~

처럼 보일 수 있다.

하지만 Metric만으로 “어떤 Thread가 왜 늘었는가”는 알기 어렵다.

이때 Thread Dump를 보면 각 Thread의 Stack과 상태를 확인할 수 있다.

LINE의 데이터 엔지니어링 장애 대응 사례에서는 Prometheus/Grafana에서 failover 직전 Thread 수가 크게 증가한 것을 확인한 뒤 Thread Dump를 수집해 어떤 Thread가 늘어났는지 조사했다.

이 흐름이 관측 가능성의 좋은 예다.

~~~text
Metric
→ 이상 위치 발견

Thread Dump
→ 구체적인 실행 상태 확인

원인 후보 축소
~~~

## 로그와 Metric의 시간이 맞아야 한다

성능 테스트 결과는 Load Generator 시각, Application Log 시각, Prometheus 시각, DB Metric 시각이 서로 맞아야 한다.

시간대가 다르거나 Clock 차이가 크면 같은 사건을 연결하기 어렵다.

예를 들어 k6 결과는 UTC인데 Grafana를 KST로 보고 있으면 9시간 차이로 잘못된 구간을 볼 수 있다.

따라서 중요한 실험에서는 다음을 명확히 한다.

~~~text
start time
end time
timezone
source commit
dataset
target RPS
~~~

그리고 같은 구간의 Metric과 Log를 본다.

## 관측 시스템 자체도 자원을 사용한다

Prometheus는 주기적으로 Metric을 가져오고 디스크에 저장한다.

Grafana는 Query를 실행하고 결과를 Rendering한다.

Exporter와 Agent도 CPU, Memory, Network를 사용한다.

따라서 Application과 같은 Host에 Observability Stack을 두면 관측 도구 자체가 성능에 영향을 줄 수 있다.

이것이 관측자 효과(Observer Effect)다.

관측 도구가 있다고 무조건 별도 서버로 분리할 필요는 없지만 영향이 어느 정도인지 실제로 측정해야 한다.

이 내용은 [[08. Observer Effect와 Same-host Calibration]]에서 자세히 다룬다.

## 너무 많은 로그와 Trace도 성능을 바꿀 수 있다

관측을 강화하기 위해 모든 요청 Body를 Log로 남기고 Trace를 100% 수집하면 I/O와 저장 비용이 크게 증가할 수 있다.

성능 테스트에서 Debug Log를 켰다가 Production과 다른 결과를 얻을 수도 있다.

따라서 관측 설정도 실험 조건의 일부다.

~~~text
Log Level
Trace Sampling
Prometheus Scrape Interval
Exporter
APM Agent
~~~

Before/After를 비교할 때 이런 설정이 같아야 한다.

## 관측 가능성 Gate는 부하 전에 확인한다

실제 성능 부하를 넣기 전에 최소한 다음 상태를 확인하는 것이 좋다.

~~~text
Application 정상
Metric Endpoint 정상
Prometheus Target UP
주요 JVM Metric 존재
주요 Hikari Metric 존재
Host / Container Metric 존재
시간대 확인
Disk 여유 확인
~~~

이 Gate가 필요한 이유는 성능 테스트 후에 관측 데이터가 없다는 사실을 발견하지 않기 위해서다.

성능 테스트는 부하 도구 실행보다 Evidence 수집 준비가 먼저다.

## 계층별로 병목을 줄여가는 예

가상의 결과를 보자.

~~~text
target = 200 RPS
actual = 199 RPS
error = 0%
p95 = 120ms

target = 250 RPS
actual = 248 RPS
error = 0%
p95 = 1,400ms
~~~

250 RPS에서 응답 시간만 크게 증가했다.

먼저 Host를 본다.

~~~text
CPU 45%
Memory 여유
I/O wait 0
~~~

Host CPU 포화 가능성은 낮아진다.

JVM을 본다.

~~~text
Heap 안정
GC pause 변화 작음
Thread 수 증가
~~~

GC보다는 Thread 계층을 더 본다.

Tomcat/Hikari를 본다.

~~~text
Tomcat busy 증가
Hikari active = max
Hikari pending 증가
~~~

Connection 대기 가능성이 강해진다.

DB를 본다.

~~~text
DB CPU 낮음
특정 Query latency 증가
Lock wait 존재
~~~

이제 “DB가 느리다”가 아니라 특정 Query 또는 Lock 때문에 Connection 반납이 늦어지고 그 앞에서 pending이 증가했다는 가설을 세울 수 있다.

이런 식으로 **정상인 계층은 후보에서 제거하고 이상이 연결되는 계층을 좁혀간다.**

## 관측 가능성은 모든 데이터를 수집하는 것이 아니다

관측 가능성을 높이겠다고 모든 Metric, Log, Trace를 무한정 수집하면 비용과 복잡도가 커진다.

좋은 관측 설계는 “어떤 장애 질문에 답해야 하는가?”에서 출발한다.

성능 분석이라면 예를 들어 다음 질문이 중요하다.

~~~text
사용자 응답은 언제 느려졌는가?
그때 실제 RPS는 유지됐는가?
Process가 재시작했는가?
CPU나 Memory가 포화됐는가?
GC pause가 있었는가?
Thread가 기다렸는가?
DB Connection을 기다렸는가?
Query나 Lock이 느렸는가?
~~~

이 질문에 답할 수 있는 최소 지표를 먼저 확보하고 필요할 때 확장한다.

도구가 많아지는 것이 관측 가능성의 목표가 아니라 **문제 원인을 설명할 수 있는 상태**가 목표다.
