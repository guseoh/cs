# Observability와 계층별 병목 분리

## 느리다는 사실과 느린 이유는 다르다

외부 부하 도구는 주로 결과를 알려 준다.

- actual RPS
- status/error
- p50/p95/p99
- timeout
- dropped request

이 값으로 문제가 발생했다는 사실은 알 수 있다. 하지만 CPU인지, GC인지, Hikari인지, DB인지 알 수는 없다.

성능 분석에는 결과 지표와 원인 후보 지표를 같은 시간축으로 연결하는 작업이 필요하다.

LINE은 CPU·memory·load·swap·disk I/O뿐 아니라 GC, heap, thread, direct memory, file descriptor를 같이 수집해야 병목 범위를 좁힐 수 있다고 설명한다.

- [LINE — 서버 사이드 테스트 자동화 여정 4](https://engineering.linecorp.com/ko/blog/server-side-test-automation-4/)
- [LINE — 서버 사이드 테스트 자동화 여정 5](https://engineering.linecorp.com/ko/blog/server-side-test-automation-5/)

## 계층별로 나눈다

~~~mermaid
flowchart LR
    C["Client"] --> N["Nginx / LB"]
    N --> H["Host / Container"]
    H --> J["JVM"]
    J --> T["Tomcat Thread"]
    T --> P["HikariCP"]
    P --> D["Database"]
~~~

| 계층 | 대표 지표 | 질문 |
| --- | --- | --- |
| Client | RPS, latency, error | 사용자가 실제로 느린가 |
| Nginx/LB | upstream, connection | ingress 경계인가 |
| Host | CPU, memory, swap, iowait | 머신 자원이 포화됐나 |
| Container | limit, OOM, restart | cgroup 제한인가 |
| JVM | heap, GC, thread, direct memory | Java runtime 문제인가 |
| Tomcat | active thread, queue | 요청이 thread 앞에서 기다리나 |
| Hikari | active, idle, pending | DB connection을 기다리나 |
| DB | CPU, query, lock, I/O | SQL/lock/storage 문제인가 |

## Metric 하나로 Root Cause를 정하지 않는다

CPU가 높다고 최초 원인이 CPU라는 뜻은 아니다. OOM 후 restart한 JVM의 startup/JIT 때문에 CPU가 순간적으로 높아질 수 있다.

Hikari pending도 “DB가 느리다”와 같은 말이 아니다.

~~~text
Query가 느림
→ connection 반환 지연
→ pending 증가
~~~

~~~text
Transaction이 김
→ connection hold time 증가
→ pending 증가
~~~

~~~text
요청 동시성 급증
→ connection demand 증가
→ pending 증가
~~~

그래서 Hikari와 DB CPU/query latency/lock/thread를 같이 본다.

- [우아한형제들 — HikariCP Dead lock 이론편](https://techblog.woowahan.com/2664/)
- [우아한형제들 — HikariCP Dead lock 실전편](https://techblog.woowahan.com/2663/)

## 시계열 순서

Snapshot 하나보다 사건의 순서가 중요하다.

~~~text
latency 증가
→ thread 증가
→ Hikari pending 증가
→ OOM
→ restart
~~~

순서가 보이면 원인 후보를 훨씬 좁힐 수 있다.

LINE 데이터 엔지니어링 사례는 failover 직전 JVM thread가 급증한 것을 Prometheus/Grafana로 확인하고 thread dump로 더 좁혔다.

- [LINE — 데이터 엔지니어링 관련 소프트웨어 장애 대응 사례](https://engineering.linecorp.com/ko/blog/data-engineering-software-troubleshooting/)

## Prometheus와 Grafana

Prometheus는 시계열 metric을 수집·저장하고 Grafana는 질의·시각화한다.

중요한 것은 dashboard가 존재한다는 사실이 아니다.

~~~text
metric endpoint가 실제로 reachable한가
target이 up인가
필요한 metric이 있는가
label이 올바른가
실험 시각과 일치하는가
단위와 집계 방식을 이해하는가
~~~

를 확인해야 한다.

- [LINE — Armeria에서 Prometheus 지표 모니터링하기](https://engineering.linecorp.com/ko/blog/armeria-prometheus-monitoring/)
- [LINE — Armeria 지표 커스터마이징하기](https://engineering.linecorp.com/ko/blog/armeria-metrics-customizing/)

## 가설을 버리는 것이 중요하다

~~~text
가설: DB가 병목

DB CPU 낮음
Query latency 낮음
I/O 낮음
Application OOM 확인

→ DB scale-up 가설 폐기
~~~

성능 분석은 가능한 기술을 다 적용하는 것이 아니라 **근거로 틀린 가설을 제거하는 과정**이다.

LINE Kafka 사례도 Produce API p99 악화를 시작점으로 disk read와 network thread utilization을 함께 확인해 범위를 좁힌다.

- [LINE — Kafka를 사용하는 방법 2편](https://engineering.linecorp.com/ko/blog/how-to-use-kafka-in-line-2/)

## 어떤 지표를 같이 캡처할 것인가

2026년 카카오 메시징팀은 스트레스 테스트 한 사이클을 끝낼 때 RPS, latency, GC, thread pool, connection, CPU 등을 Grafana에서 함께 확인한다고 설명한다. 여기서 중요한 것은 dashboard 패널 개수가 많다는 것이 아니라 **외부 결과와 내부 상태를 같은 테스트 구간으로 묶는다**는 점이다.

- [카카오 — 메시징 서버의 스트레스 테스트 노하우와 AI가 덜어 준 부분](https://tech.kakao.com/posts/822)

예를 들어:

~~~text
RPS 정상
p95 급증
GC pause 없음
CPU 여유
Hikari pending 증가
DB latency 증가
~~~

라면 JVM GC나 CPU보다 DB/Connection 경계를 먼저 볼 근거가 생긴다.

반대로:

~~~text
RPS 하락
p95 급증
GC pause 급증
Heap old 증가
Thread 정상
DB 정상
~~~

이면 JVM memory/GC 쪽 가설이 강해진다.

## 관측 인프라 추가도 성능 변경이다

카카오 메시징팀은 logstash, fluent bit, OpenTelemetry 같은 관측/로깅 인프라 추가 자체를 stress test 대상의 한 종류로 다룬다. 기능 코드는 바뀌지 않았어도 CPU, Memory, Network, Serialization, Disk write가 늘 수 있기 때문이다.

이 관점은 매우 중요하다.

~~~text
Observability 추가
≠ 기능 변화 없음
≠ 성능 영향 없음
~~~

따라서 Agent, Exporter, Sidecar, Trace pipeline을 추가했다면 전후 CPU/Memory/latency를 동일 workload로 다시 확인해야 한다.

## Observability Gate

부하 테스트가 끝난 뒤 metric이 없다는 사실을 발견하면 실험을 다시 해야 한다.

부하 전 최소 확인:

- metric endpoint
- Prometheus target
- JVM metric
- Hikari metric
- container restart/OOM
- DB metric time window

Observability는 성능 테스트의 부가 기능이 아니라 **실험 장비의 일부**다.


## 관측 가능성이라는 말을 쉽게 풀어보면

관측 가능성(Observability)은 대시보드를 많이 만드는 것을 뜻하지 않는다.

외부에서 보이는 결과와 내부 상태를 함께 보면서 **시스템 안에서 무슨 일이 일어났는지 추론할 수 있는 상태**를 만드는 것이다.

예를 들어 사용자는 단지 “상품 목록이 2초 걸렸다”는 사실만 볼 수 있다.

하지만 원인은 여러 가지일 수 있다.

~~~text
CPU가 바빴는가
GC가 오래 멈췄는가
Tomcat Thread가 부족했는가
DB Connection을 기다렸는가
특정 Query가 느렸는가
DB Lock을 기다렸는가
Container가 OOM으로 재시작했는가
~~~

관측 가능성은 이 후보들을 하나씩 확인하고 제거할 수 있게 하는 근거를 제공한다.

## 지표(Metric)는 무엇인가

지표는 시간에 따라 변하는 시스템 상태를 숫자로 표현한 값이다.

예를 들면 다음과 같다.

~~~text
CPU 사용률
JVM Heap 사용량
GC pause 시간
Tomcat 활성 Thread 수
Hikari pending 수
DB Connection 수
HTTP 요청 수
응답 시간
~~~

지표 하나만 보면 원인을 확정하기 어렵다.

CPU 90%라는 숫자는 “CPU가 많이 사용됐다”는 사실은 알려 주지만 왜 그런지는 알려 주지 않는다.

그래서 지표는 **가설을 좁히는 증거**로 사용한다.

## 시계열(Time Series)은 왜 중요한가

시계열은 같은 지표를 시간 순서대로 기록한 데이터다.

예를 들어 단순 snapshot으로는 다음만 볼 수 있다.

~~~text
현재 CPU = 85%
~~~

하지만 시계열에서는 사건의 순서를 볼 수 있다.

~~~text
10:00 RPS 증가
10:01 p95 증가
10:02 Hikari pending 증가
10:03 Thread 증가
10:04 Container memory 증가
10:05 OOM
10:06 Restart
~~~

이 순서는 원인 추론에 매우 중요하다.

OOM 이후 JVM이 재시작하면서 CPU가 올라갔다면 CPU spike는 최초 원인이 아니라 **재시작의 결과**일 수 있다.

## Prometheus는 무엇을 하는가

Prometheus는 일정 주기마다 대상의 metric endpoint에서 지표를 가져와 시간과 함께 저장한다.

이 과정을 scrape라고 부른다.

쉽게 말하면:

~~~text
Prometheus
→ 15초 또는 30초마다
→ 애플리케이션 metric endpoint에 요청
→ 그 시점의 지표를 저장
~~~

처럼 동작한다고 이해할 수 있다.

Scrape 간격이 30초라면 2초 동안만 발생한 매우 짧은 spike는 직접 포착하지 못할 수도 있다. 따라서 지표 수집 간격은 결과 해석의 한계가 된다.

## Target은 무엇인가

Prometheus의 Target은 **Prometheus가 주기적으로 지표를 가져오려고 하는 대상**이다.

Target이 UP이면 Prometheus가 현재 그 endpoint에서 metric을 수집할 수 있다는 뜻이다.

Target이 DOWN이라면 성능 테스트 중 Application이 정상이어도 metric이 비어 있을 수 있다.

그래서 부하를 넣기 전에 다음을 확인한다.

~~~text
metric endpoint 응답
Prometheus Target = UP
필요한 JVM/Hikari metric 존재
label 정상
시간대 정상
~~~

실험이 끝난 뒤 “아, Prometheus가 수집을 못 하고 있었다”는 사실을 발견하면 내부 원인 분석 근거가 사라진다.

## Grafana는 무엇을 하는가

Grafana는 Prometheus 같은 데이터 소스에 질의해서 시계열을 그래프로 보여 주는 도구다.

Grafana가 원인을 자동으로 찾아 주는 것은 아니다.

좋은 대시보드는 다음과 같은 질문을 같은 시간축에서 보기 쉽게 한다.

~~~text
사용자 응답 시간은 언제 나빠졌는가
그때 CPU는 어땠는가
GC pause가 있었는가
Thread가 늘었는가
Hikari pending이 늘었는가
DB latency가 늘었는가
~~~

그래프를 예쁘게 만드는 것이 목적이 아니라 **같은 사건의 여러 신호를 시간축으로 연결하는 것**이 목적이다.

## 외부 결과 지표와 내부 원인 후보를 나눈다

외부 결과는 사용자가 실제로 경험한 상태다.

~~~text
실제 RPS
오류율
Timeout
p50
p95
p99
~~~

내부 지표는 그 결과를 만든 원인 후보를 좁히는 데 사용한다.

~~~text
Host CPU / memory
Container restart / OOM
JVM Heap / GC / Thread
Tomcat Thread
Hikari active / pending
DB CPU / Query / Lock / I/O
~~~

이 둘을 섞으면 “Hikari pending이 늘었으니 사용자가 느렸다”처럼 근거 방향이 뒤집힐 수 있다.

먼저 사용자가 실제로 느렸는지 확인하고, 그 시각의 내부 상태를 연결한다.

## 상관관계만으로 원인을 확정하지 않는다

두 값이 동시에 올라갔다고 한쪽이 다른 쪽의 원인이라는 뜻은 아니다.

~~~text
CPU 증가
p95 증가
~~~

만으로 CPU가 최초 원인이라고 단정하면 안 된다.

다음처럼 제3의 원인이 둘을 동시에 만들 수도 있다.

~~~text
요청 폭증
→ CPU 증가
→ Queue 증가
→ p95 증가
~~~

또는 OOM 이후 JVM 재기동이 CPU를 올렸을 수도 있다.

그래서 성능 분석에서는 **시간 순서, 반대 근거, 변경 실험**을 함께 사용한다.

## Hikari pending이 보인다고 DB가 범인인 것은 아니다

Hikari pending은 Connection을 얻기 위해 기다리는 요청 수가 있다는 뜻이다.

하지만 원인은 여러 가지다.

~~~text
DB Query가 느림
→ Connection 반납 지연
→ pending 증가

Transaction이 김
→ Connection 오래 점유
→ pending 증가

요청 동시성 급증
→ Connection 수요 증가
→ pending 증가

Pool이 지나치게 작음
→ Connection 부족
→ pending 증가
~~~

그래서 pending 하나만 보고 DB scale-up이나 Pool 증가를 결정하면 안 된다.

우아한형제들의 HikariCP 장애 사례는 Thread 수, Pool 크기, Task당 Connection 수가 서로 어떻게 영향을 주는지 실제 장애를 통해 보여 준다.

## 관측 시스템 자체도 부하를 만든다

Prometheus는 주기적으로 metric을 읽고 저장한다. Grafana는 query와 rendering을 수행한다. Exporter와 Agent도 CPU, memory, network를 사용한다.

따라서 관측 도구를 추가하면 “기능 코드는 안 바뀌었으니 성능도 같다”고 가정하면 안 된다.

이 문제는 [[08. Observer Effect와 Same-host Calibration]]에서 자세히 다룬다.

## 관측 가능성 문서를 읽을 때 기억할 것

관측 가능성의 목적은 metric을 많이 모으는 것이 아니다.

다음 질문에 답할 수 있어야 한다.

~~~text
언제 문제가 시작됐는가
사용자 결과는 무엇이 달라졌는가
어느 계층부터 이상이 보였는가
어떤 가설은 근거로 버릴 수 있는가
어떤 추가 자료가 필요한가
~~~
