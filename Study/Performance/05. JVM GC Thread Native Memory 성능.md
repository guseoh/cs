# JVM GC Thread Native Memory 성능

## JVM Memory는 Heap만이 아니다

Java process와 container memory에는 Heap 외의 영역도 존재한다.

~~~text
Java Process
├─ Heap
├─ Metaspace
├─ Code Cache
├─ Thread Native Stack
├─ Direct Buffer
├─ JNI / Native allocation
├─ libc
└─ socket / mmap 등
~~~

따라서 Heap 사용률이 70%인데 container OOM이 발생하는 것도 가능하다.

LINE messaging-hub 사례도 container memory와 JVM heap 사이에 native 영역을 위한 headroom이 필요함을 보여 준다.

- [LINE — messaging-hub 트러블 슈팅](https://engineering.linecorp.com/ko/blog/messaing-hub-troubleshooting/)

## Heap을 볼 때

질문:

- used가 지속적으로 증가하는가
- GC 후 baseline이 내려오는가
- max에 얼마나 가까운가
- allocation rate가 급증하는가

Heap used가 높다고 바로 memory leak은 아니다. 같은 workload인데 GC 이후 live set baseline이 지속적으로 상승하는지 봐야 한다.

## GC

GC에서 중요한 것은 “GC가 발생한다”가 아니다.

- 얼마나 자주
- 얼마나 오래
- 어떤 workload에서
- latency와 어떤 시간 관계로

발생하는지가 중요하다.

NAVER D2의 GC 모니터링 글은 YGC/YGCT/FGC/FGCT를 이용해 횟수와 누적 시간을 읽는 방법과 평균만 보면 긴 pause를 놓칠 수 있다는 점을 설명한다.

- [NAVER D2 — Garbage Collection 모니터링 방법](https://d2.naver.com/helloworld/6043)

## GC Tuning부터 하지 않는다

GC pause가 보였다고 collector option부터 바꾸면 위험하다.

먼저:

~~~text
GC가 정말 latency 원인인가
allocation이 비정상적으로 많은가
heap size가 적절한가
memory leak이 있는가
container headroom이 있는가
~~~

를 본다.

NAVER D2는 다른 서비스에서 잘 된 옵션을 그대로 가져오면 안 되고 실제 workload에서 측정·비교해야 한다고 강조한다.

- [NAVER D2 — Garbage Collection 튜닝](https://d2.naver.com/helloworld/37111)
- [NAVER D2 — 자바 애플리케이션 성능 튜닝의 도](https://d2.naver.com/helloworld/184615)

## Thread도 Memory를 쓴다

Platform Thread는 native stack을 가진다.

동시 요청이 늘어 thread가 증가하면:

~~~text
thread 수 증가
→ native stack memory 증가
→ context switch 증가
→ container memory pressure 가능
~~~

Heap만 보고 container memory를 설명하면 안 된다.

## Thread State

대표 상태:

- RUNNABLE
- BLOCKED
- WAITING
- TIMED_WAITING

Thread가 많다고 모두 CPU를 쓰는 것은 아니다.

Connection Pool이나 lock을 기다리는 thread가 쌓일 수 있다.

LINE 데이터 엔지니어링 사례는 failover 직전 thread 수가 급증한 것을 metric으로 발견하고 thread dump로 어떤 thread가 증가했는지 좁혔다.

- [LINE — 데이터 엔지니어링 관련 소프트웨어 장애 대응 사례](https://engineering.linecorp.com/ko/blog/data-engineering-software-troubleshooting/)

## Direct Memory

NIO/Netty는 off-heap direct buffer를 사용할 수 있다.

~~~text
Heap 안정
Container RSS 증가
~~~

라면 direct/native memory도 후보가 된다.

LINE 성능 테스트 자동화 글도 JVM 진단 지표에 direct memory를 포함한다.

- [LINE — 서버 사이드 테스트 자동화 여정 4](https://engineering.linecorp.com/ko/blog/server-side-test-automation-4/)

## 최신 GC를 선택한다고 문제가 자동으로 해결되지는 않는다

ZGC는 낮은 pause를 목표로 발전한 collector지만 “ZGC를 사용하면 성능 문제가 해결된다”는 식으로 이해하면 안 된다.

NAVER D2의 ZGC 글은 ZPage, colored pointer, load barrier 같은 내부 구조를 설명하며 기존 collector와 다른 방식으로 동시 작업 비중을 높이는 배경을 보여 준다.

- [NAVER D2 — ZGC의 기본 개념 이해하기](https://d2.naver.com/helloworld/0128759)

Collector 선택은 다음 요구와 연결해야 한다.

~~~text
Heap 크기
Latency 요구
Throughput 요구
CPU headroom
JDK Version
실제 Allocation Pattern
~~~

짧은 pause가 중요할수록 CPU/throughput 측 trade-off도 같이 봐야 한다.

## Average GC Time의 함정

NAVER D2 GC 모니터링 글은 YGC/YGCT, FGC/FGCT로 평균 시간을 계산할 수 있지만 평균만으로는 긴 pause 한 번을 숨길 수 있다고 설명한다.

예를 들어:

~~~text
두 번의 Full GC 합계 = 60ms
평균 = 30ms
~~~

여도 실제 값이:

~~~text
1ms
59ms
~~~

일 수 있다.

사용자 latency는 59ms pause의 영향을 받기 때문에 GC log의 개별 event와 Application p95/p99를 연결해야 한다.

- [NAVER D2 — Garbage Collection 모니터링 방법](https://d2.naver.com/helloworld/6043)

## Persistent Connection과 JVM

카카오 실시간 댓글 사례에서는 10K WebSocket connection과 2800 TPS라는 목표를 검증하면서 Java/Spring WebSocket, Tomcat, Docker memory, file descriptor, GC를 함께 다뤘다.

- [카카오 — 실시간 댓글 개발기 part.2](https://tech.kakao.com/posts/391)

이런 workload에서는 단순 Heap allocation뿐 아니라 수많은 connection 객체, buffer, socket, thread/event 처리 구조가 JVM/Native Memory에 영향을 줄 수 있다.

## 조사 순서

~~~text
1. 외부 latency/error
2. container restart/OOM
3. heap/non-heap/direct memory
4. GC count/pause
5. thread count/state
6. CPU 시간축
7. 필요하면 GC log / thread dump / heap dump
~~~

## 핵심

~~~text
Heap 정상
≠ Process Memory 정상
≠ Container Memory 정상

GC 존재
≠ GC가 병목

Thread 증가
≠ CPU 병목
~~~

결과 지표와 시간축으로 연결해야 한다.


## JVM 메모리를 쉽게 나눠보면

Java 애플리케이션의 메모리를 생각할 때 Heap만 떠올리기 쉽지만 실제 Process는 Heap 바깥에도 여러 영역을 사용한다.

~~~text
Java Process 전체 메모리

Heap
→ Java 객체

Metaspace
→ 클래스 메타데이터

Code Cache
→ JIT이 컴파일한 기계어 코드

Thread Stack
→ 각 Thread의 호출 스택

Direct Buffer
→ Heap 밖의 직접 Buffer

Native Library / JNI
→ Native 코드가 사용하는 영역
~~~

그래서 Heap 사용률이 60%인데도 Container memory limit에 도달해 OOM이 발생할 수 있다.

## Heap은 무엇인가

Heap은 Java에서 생성한 객체 대부분이 저장되는 메모리 영역이다.

성능 분석에서는 단순 사용률보다 다음 흐름을 본다.

~~~text
요청 증가
→ 객체 생성 증가
→ Heap 사용 증가
→ GC 수행
→ GC 후 얼마나 내려오는가
~~~

GC 후에도 사용량의 바닥선이 계속 올라간다면 살아남는 객체가 점점 많아지고 있다는 신호일 수 있다.

## Allocation Rate는 무엇인가

Allocation은 새 객체를 만들면서 Heap 공간을 사용하는 것이다.

Allocation Rate는 일정 시간 동안 객체가 얼마나 빠르게 만들어지는지를 뜻한다.

같은 100 RPS인데 코드 변경 후 객체 생성 속도가 크게 증가하면 Young 영역이 빨리 차고 GC가 더 자주 발생할 수 있다.

~~~text
객체 생성 속도 증가
→ GC 빈도 증가 가능
→ CPU 사용 증가
→ 일부 workload에서 응답 시간 영향
~~~

객체가 많이 생성된다고 무조건 문제는 아니다. 중요한 것은 현재 latency 요구와 CPU 여유 안에서 감당 가능한가이다.

## Live Set은 무엇인가

Live Set은 GC가 끝난 뒤에도 여전히 참조되어 살아남은 객체 집합이다.

쉽게 말하면 “현재 애플리케이션이 계속 필요로 해서 버릴 수 없는 Heap 객체”다.

~~~text
700MB
↓ GC
300MB
↑ allocation
700MB
↓ GC
300MB
~~~

처럼 GC 후 300MB 부근으로 계속 돌아온다면 현재 workload의 live set이 대략 그 근처일 수 있다.

반대로 GC 후 바닥선이 300 → 350 → 420 → 500MB처럼 계속 올라가면 장기 보관 객체 증가나 memory leak 가능성을 조사할 근거가 생긴다.

## GC는 무엇을 하는가

GC(Garbage Collection)는 더 이상 사용하지 않는 Java 객체가 차지한 Heap 공간을 회수하는 작업이다.

GC가 실행된다는 사실 자체는 문제가 아니다.

중요한 질문은 다음이다.

~~~text
얼마나 자주 발생하는가
한 번 멈출 때 얼마나 오래 걸리는가
CPU를 얼마나 사용하는가
p95/p99 악화 시점과 겹치는가
Full GC가 반복되는가
~~~

NAVER D2의 GC 모니터링 글은 횟수와 누적 시간뿐 아니라 평균값이 긴 단일 pause를 숨길 수 있음을 설명한다.

- [NAVER D2 — Garbage Collection 모니터링 방법](https://d2.naver.com/helloworld/6043)

## GC Pause는 무엇인가

일부 GC 단계에서는 애플리케이션 Thread가 잠시 멈출 수 있다. 이 구간을 GC pause라고 부른다.

사용자 요청이 처리 중인데 JVM이 200ms 동안 애플리케이션 Thread를 멈췄다면 해당 요청 응답 시간에도 영향을 줄 수 있다.

하지만 p99가 200ms 늘었다고 바로 GC 때문이라고 단정하면 안 된다. 같은 시각의 GC event와 응답 시간 상승이 실제로 겹치는지 확인해야 한다.

## Young GC와 Full GC는 어떻게 이해하면 되는가

Collector에 따라 내부 구조는 다르지만 세대형 GC를 처음 이해할 때는 다음처럼 생각할 수 있다.

~~~text
Young GC
→ 최근 생성된 객체가 많은 영역 중심

Full GC
→ 더 넓은 Heap 영역을 대상으로 하는 무거운 정리 작업
~~~

Full GC는 일반적으로 비용이 더 클 수 있어 반복적으로 발생하면 강한 조사 대상이 된다.

하지만 Full GC 한 번이 있었다는 사실만으로 장애 원인이라고 단정하지 않는다. pause 시간, 발생 빈도, Heap 상태와 사용자 응답 시간을 같이 본다.

## Thread는 CPU만 사용하는 것이 아니다

Java Platform Thread는 각자 Native Stack을 가진다.

Thread가 많아지면 두 종류의 비용이 생길 수 있다.

~~~text
메모리
→ 각 Thread의 Stack 공간

CPU
→ 많은 Thread 사이를 전환하는 Context Switch 비용
~~~

Blocking I/O를 기다리는 Thread가 수백 개 쌓이면 CPU를 계속 쓰지 않아도 Native Memory는 증가할 수 있다.

따라서 다음 세 문장은 서로 다른 뜻이다.

~~~text
Thread가 많다
CPU가 높다
Heap이 높다
~~~

## RUNNABLE, BLOCKED, WAITING은 어떻게 읽는가

RUNNABLE은 JVM 관점에서 실행 가능한 상태다. 실제 CPU를 사용하고 있을 수도 있고 OS 스케줄링을 기다리는 중일 수도 있다.

BLOCKED는 Java monitor lock을 얻기 위해 기다리는 상태다.

WAITING은 다른 Thread의 동작이나 신호를 기한 없이 기다리는 상태다.

TIMED_WAITING은 일정 시간이 지나거나 신호가 올 때까지 기다리는 상태다.

Thread 수와 상태 분포를 보고 어디에서 기다리는지 좁힌 다음 필요하면 Thread Dump를 본다.

## Thread Dump는 무엇인가

Thread Dump는 특정 시점에 JVM Thread들이 어떤 호출 흐름에서 어떤 상태로 있는지 보여 주는 자료다.

Metric에서 Thread 수가 50개에서 500개로 증가한 사실을 발견해도 왜 증가했는지는 알 수 없다.

Thread Dump를 보면 여러 Thread가 DB Connection 획득 코드에서 기다리는지, Lock에서 BLOCKED인지, 외부 API 호출에서 대기하는지 더 구체적으로 좁힐 수 있다.

LINE의 데이터 엔지니어링 장애 대응 사례는 Prometheus/Grafana에서 Thread 증가를 발견한 뒤 Thread Dump로 범위를 좁히는 흐름을 보여 준다.

- [LINE — 데이터 엔지니어링 관련 소프트웨어 장애 대응 사례](https://engineering.linecorp.com/ko/blog/data-engineering-software-troubleshooting/)

## Direct Memory는 무엇인가

Direct Memory는 Java Heap 밖에 할당되는 Buffer 메모리를 말할 때 자주 사용하는 표현이다.

NIO나 Netty 같은 네트워크 I/O 처리에서 Direct Buffer를 사용할 수 있다.

그래서 다음 패턴이 보이면 Heap 바깥도 조사한다.

~~~text
Heap 사용량은 안정적
그런데 Process RSS / Container memory는 계속 증가
~~~

가능한 후보는 Direct Buffer, Thread Stack, Metaspace, Native Library와 기타 Native allocation이다.

## Metaspace는 무엇인가

Metaspace는 클래스 메타데이터를 저장하는 Native Memory 영역이다.

애플리케이션이 매우 많은 Class를 로드하거나 ClassLoader가 정상적으로 정리되지 않는 문제가 있으면 Metaspace가 증가할 수 있다.

일반적인 요청 처리 성능에서 가장 먼저 보는 지표는 아닐 수 있지만 Process memory가 증가하는데 Heap이 안정적이라면 후보 중 하나다.

## GC 튜닝은 근거가 생긴 뒤 한다

GC 그래프가 있다는 이유만으로 GC 옵션을 바꾸면 안 된다.

먼저 다음을 확인한다.

~~~text
GC pause가 실제 p95/p99 악화 시각과 겹치는가
Allocation Rate가 비정상적으로 증가했는가
Heap이 workload에 비해 지나치게 작은가
GC 후 Live Set이 계속 증가하는가
Container memory 여유가 충분한가
~~~

그 다음에 Collector나 Heap 크기, 관련 옵션 변경을 검토한다.

- [NAVER D2 — Garbage Collection 튜닝](https://d2.naver.com/helloworld/37111)
- [NAVER D2 — 자바 애플리케이션 성능 튜닝의 도](https://d2.naver.com/helloworld/184615)

## JVM 메모리 문제를 읽는 예

다음 상황을 보자.

~~~text
p95 증가
Container memory 95%
Heap 사용 55%
GC pause 정상
Thread 800개
~~~

이 경우 Heap 부족보다 Thread Stack이나 기타 Native Memory가 Container memory를 압박하는 가설을 먼저 볼 수 있다.

반대로:

~~~text
p95 증가
Heap max 근처 반복
Full GC 반복
GC pause와 p99 spike 시각 일치
~~~

라면 GC/Heap pressure 가설이 훨씬 강하다.
