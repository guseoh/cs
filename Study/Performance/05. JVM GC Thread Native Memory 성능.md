# JVM, GC, Thread와 Native Memory 성능

Java 애플리케이션의 성능 문제를 볼 때 Heap 사용률과 GC 그래프만 확인하면 충분하다고 생각하기 쉽다. 하지만 실제 JVM Process가 사용하는 Memory는 Heap보다 넓고, 응답 시간이 느려지는 이유도 GC 하나로 설명되지 않는다.

Java Process는 대략 다음과 같은 영역을 사용한다.

~~~text
Java Heap
Metaspace
Code Cache
Thread Stack
Direct Buffer
JVM 내부 Native Memory
Native Library
mmap 영역
Socket / 기타 OS 자원
~~~

그래서 Heap이 50%인데도 Container가 OOM으로 종료될 수 있고, GC가 정상인데 Thread가 수천 개로 늘면서 Native Memory가 부족해질 수도 있다.

JVM 성능을 볼 때 중요한 것은 “GC를 튜닝해야 하나?”가 아니다. **사용자 응답 시간 악화가 Heap, Allocation, GC Pause, Thread 대기, Native Memory 중 어느 경로와 연결되는지 먼저 찾는 것**이다.

LINE의 messaging-hub 사례에서도 OOM이 발생했을 때 바로 미세한 GC Option 조정부터 하지 않고 Container Memory와 JVM Memory 설정, Heap Dump를 함께 조사했다. NAVER D2의 GC 글도 다른 서비스의 튜닝 값을 그대로 복사하기보다 실제 workload를 측정하고 변경 후 다시 검증해야 한다는 관점을 강조한다.

## Heap은 Java 객체가 주로 저장되는 공간이다

Java에서 new로 생성한 객체 대부분은 Heap에 만들어진다.

예를 들어:

~~~java
Order order = new Order();
~~~

를 실행하면 Order 객체는 일반적으로 Heap에 생성된다.

Heap에는 계속 새로운 객체가 들어오고, 더 이상 사용하지 않는 객체는 GC가 회수한다.

그래서 Heap 그래프는 보통 톱니 모양처럼 보일 수 있다.

~~~text
객체 생성
→ Heap 사용 증가

GC
→ 사용하지 않는 객체 제거
→ Heap 사용 감소

다시 객체 생성
→ 증가
~~~

이 반복 자체는 정상이다.

성능 분석에서 중요한 것은 Heap이 오르내린다는 사실이 아니라 **얼마나 빠르게 차고, GC 뒤에 얼마나 내려오며, 그 패턴이 부하 증가와 함께 어떻게 달라지는가**다.

## Heap Used, Committed, Max는 서로 다른 값이다

JVM Metric에서는 Heap을 여러 값으로 볼 수 있다.

### Used

현재 실제로 객체 등이 사용하고 있는 Heap 양이다.

### Committed

JVM이 운영체제로부터 확보해 현재 Heap으로 사용할 수 있도록 준비한 양이다.

### Max

JVM이 설정상 사용할 수 있는 최대 Heap 크기다.

예를 들어:

~~~text
used       = 400MiB
committed  = 600MiB
max        = 1024MiB
~~~

라면 현재 400MiB 정도를 실제 사용하고 있고 JVM은 600MiB를 이미 확보했으며 최대 1GiB까지 사용할 수 있다고 이해할 수 있다.

Used가 Max에 가까워지는 상황이 반복되면 GC Pressure를 조사할 근거가 된다.

하지만 Heap Max가 Container Memory Limit과 같으면 안 될 수 있다. Heap 외 Native Memory도 필요하기 때문이다.

## Allocation은 새 객체를 만드는 과정이다

객체를 만들 때 Heap 공간을 할당하는 것을 Allocation이라고 한다.

Allocation Rate는 일정 시간 동안 얼마나 빠르게 새 객체가 만들어지는지를 나타낸다.

예를 들어 100 RPS에서 초당 50MiB의 객체를 만들던 코드가 변경 후 초당 300MiB를 만든다면 GC가 더 자주 필요할 수 있다.

~~~text
Allocation Rate 증가
→ Young 영역 더 빨리 채움
→ GC 빈도 증가 가능
→ GC Worker CPU 증가 가능
~~~

그렇다고 객체 생성량이 많으면 무조건 나쁜 것은 아니다.

JVM은 짧게 살고 사라지는 객체를 빠르게 처리하도록 최적화되어 있다.

중요한 것은 현재 workload에서 Allocation이 CPU와 Pause 요구를 감당할 수 있는지다.

## Live Set은 GC가 끝난 뒤에도 살아 있는 객체의 양이다

GC는 참조되지 않는 객체를 제거한다.

GC 뒤에도 Application이 계속 참조하고 있어 제거할 수 없는 객체 집합을 Live Set이라고 생각할 수 있다.

다음 패턴을 보자.

~~~text
700MiB
↓ GC
300MiB
↑ Allocation
700MiB
↓ GC
300MiB
~~~

GC 후 계속 300MiB 부근으로 돌아온다면 현재 workload에서 장기간 살아 있는 객체 규모가 대략 그 근처일 수 있다.

반대로:

~~~text
GC 후 300MiB
다음 GC 후 350MiB
다음 GC 후 430MiB
다음 GC 후 520MiB
~~~

처럼 바닥선이 계속 높아지면 다음 가능성을 조사한다.

~~~text
실제로 상태 데이터가 계속 증가 중
Cache가 계속 커짐
Session/Queue가 누적됨
객체가 잘못 참조되어 해제되지 않음
Memory Leak
~~~

단순히 Heap 사용률이 높다는 것보다 **GC 후에도 남는 양이 어떻게 변하는지**가 중요하다.

## GC는 더 이상 사용하지 않는 객체 공간을 회수한다

GC(Garbage Collection)는 개발자가 직접 free를 호출하지 않아도 JVM이 더 이상 사용하지 않는 객체를 찾아 Heap 공간을 회수하는 기능이다.

GC가 수행된다는 사실은 장애가 아니다.

정상 Java 애플리케이션에서도 계속 GC가 발생한다.

성능에서 확인하는 질문은 다음과 같다.

~~~text
GC가 얼마나 자주 발생하는가?
한 번의 Pause는 얼마나 긴가?
누적 Pause 시간은 얼마인가?
GC CPU 사용은 어느 정도인가?
부하 증가와 함께 패턴이 어떻게 변하는가?
p95/p99 악화 시각과 실제로 겹치는가?
~~~

이 질문을 통해 GC가 단순히 존재하는지와 실제 성능 병목인지 구분한다.

## Stop-The-World는 무엇인가

일부 GC 단계에서는 JVM이 애플리케이션 Thread를 잠시 멈춘다.

이 상태를 Stop-The-World라고 부른다.

예를 들어 요청을 처리하던 Thread가 있고 GC가 150ms 동안 Application Thread를 멈췄다고 하자.

~~~text
요청 처리
→ GC Stop-The-World 150ms
→ 요청 처리 재개
~~~

그 요청은 최소한 이 Pause의 영향을 받을 수 있다.

따라서 긴 GC Pause가 발생하면 p95나 p99가 증가할 수 있다.

하지만 p99가 증가했다고 자동으로 GC 원인이라고 판단하면 안 된다.

같은 시각에 실제 GC Pause가 있었는지 확인해야 한다.

## 평균 GC 시간만 보면 긴 Pause를 숨길 수 있다

다음 두 시스템을 생각해보자.

~~~text
System A
GC 100번
각각 10ms

평균 10ms
~~~

~~~text
System B
GC 99번 1ms
GC 1번 900ms

평균 약 10ms
~~~

평균값은 비슷하지만 System B 사용자는 한 번 매우 긴 Pause를 경험할 수 있다.

그래서 GC는 평균 Pause뿐 아니라 긴 Pause, Max, Distribution, 발생 시각을 보는 것이 좋다.

NAVER D2의 GC 모니터링 글도 GC 횟수와 누적 시간만으로는 긴 단일 GC를 놓칠 수 있는 점을 설명한다.

## Young GC와 Old 영역을 이해하는 이유

많은 객체는 생성된 뒤 짧은 시간 안에 더 이상 사용되지 않는다.

세대형 GC는 이런 객체 생명 주기 특성을 활용한다.

JDK와 Collector에 따라 구체적인 구조는 다르지만 처음에는 다음처럼 이해할 수 있다.

~~~text
Young 영역
→ 최근 생성된 객체가 주로 위치
→ 짧게 사는 객체가 많음

Old 영역
→ 여러 GC를 거치고 오래 살아남은 객체
~~~

Young GC가 자주 발생하는 것은 높은 Allocation workload에서 자연스러울 수 있다.

문제는 Pause가 요구 범위를 넘거나 CPU를 과도하게 사용하거나 Old 영역이 계속 증가하는 경우다.

## Full GC라는 용어는 Collector에 따라 세부 의미가 다를 수 있다

전통적으로 Full GC는 Heap의 넓은 영역을 대상으로 하는 무거운 GC를 의미하는 경우가 많다.

하지만 G1, ZGC 같은 Collector에서는 내부 동작과 용어가 다를 수 있다.

그래서 “Full GC가 있었다”라는 말만으로 원인을 판단하기보다 사용하는 Collector, GC Log, 실제 Pause 종류를 확인하는 것이 정확하다.

## G1 GC는 왜 자주 보이는가

Oracle JDK 21의 HotSpot JVM에서는 G1 Garbage Collector가 기본 Collector다. 다른 JVM 구현이나 다른 JDK 버전에서는 기본값이 다를 수 있으므로 실제 실행 환경은 `java -version`, JVM Option과 GC Log로 확인한다.

G1은 Heap을 여러 Region으로 나누어 관리하고 Young/Old 세대의 객체를 처리한다. Oracle 문서는 G1을 세대형·점진적·병렬·대부분 동시 실행되는 Collector로 설명하며 Stop-The-World 구간에서 Pause 목표를 고려한다.

목표는 단순히 “GC를 없애는 것”이 아니라 Application 처리량과 Pause 시간 사이에서 현재 workload에 적합한 균형을 만드는 것이다.

하지만 G1을 사용한다고 GC 문제가 자동으로 사라지는 것은 아니다.

Heap이 너무 작거나 Allocation이 지나치게 많고 Live Set이 크면 여전히 GC Pressure가 생길 수 있다.

따라서 Collector 이름보다 Metric과 GC Log를 먼저 본다.

관련 자료:
- [Oracle JDK 21 — G1 Garbage Collector](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)

## ZGC는 짧은 Pause를 목표로 하지만 무조건 더 빠른 Collector는 아니다

ZGC는 대부분의 GC 작업을 Application Thread와 동시에 수행해 매우 짧은 Pause를 목표로 설계된 Collector다.

큰 Heap과 낮은 Pause 요구에서 장점이 있을 수 있다.

그러나 “p99가 높으니 ZGC로 바꾸자”처럼 바로 선택하면 안 된다.

현재 병목이 DB Lock이나 Connection Pool 대기라면 Collector 변경은 문제를 해결하지 못한다.

또 Collector마다 CPU 사용, Memory overhead, workload 적합성이 다르다.

먼저 GC가 실제 원인이라는 근거가 필요하다.

Oracle JDK 21 문서는 ZGC를 낮은 지연을 목표로 하며 대부분의 무거운 작업을 Application Thread와 동시에 수행하는 Collector로 설명한다. 다만 이런 특성은 “모든 workload에서 가장 빠르다”는 뜻이 아니다.

관련 자료:
- [Oracle JDK 21 — Z Garbage Collector](https://docs.oracle.com/en/java/javase/21/gctuning/z-garbage-collector2.html)

관련 자료:
- [NAVER D2 — ZGC의 기본 개념 이해하기](https://d2.naver.com/helloworld/0128759)

## Thread는 실행 흐름이면서 Memory 소비자다

Java Platform Thread는 각자 호출 Stack을 가진다.

Thread가 많아지면 단순히 CPU Scheduling 문제만 생기는 것이 아니다.

각 Thread의 Native Stack도 Memory를 사용한다.

예를 들어 Thread당 Stack이 1MiB 수준이고 Thread가 1,000개라면 이론적으로 상당한 Address Space와 Native Memory가 필요할 수 있다.

실제 사용량은 설정과 운영체제에 따라 다르지만 중요한 개념은 다음이다.

~~~text
Thread 증가
→ Stack Memory 증가 가능
→ Context Switch 증가 가능
→ Scheduler 경쟁 증가 가능
~~~

Heap이 안정적인데 Container RSS가 증가하고 Thread 수가 급증했다면 Native Stack을 후보로 볼 수 있다.

## RUNNABLE은 실제로 CPU를 사용 중이라는 뜻만은 아니다

Java Thread State에서 RUNNABLE은 JVM 관점에서 실행 가능한 상태다.

실제로 CPU에서 실행 중일 수도 있고 운영체제 Scheduler가 CPU를 줄 때까지 기다릴 수도 있다.

따라서 RUNNABLE Thread 500개가 있다고 해서 500개가 동시에 CPU를 사용한다는 뜻은 아니다.

Core가 4개라면 실제로 동시에 실행 가능한 Thread 수는 제한된다.

많은 RUNNABLE Thread는 CPU 경쟁과 Context Switch를 늘릴 수 있다.

## BLOCKED는 Java Monitor Lock을 기다리는 상태다

synchronized 구문 등에서 다른 Thread가 Monitor를 가지고 있다면 해당 Lock을 얻으려는 Thread는 BLOCKED가 될 수 있다.

예를 들어 초기화 작업을 synchronized로 보호했는데 서버 시작 직후 수백 개 요청이 동시에 들어오면 한 Thread만 초기화를 수행하고 나머지가 같은 Lock을 기다릴 수 있다.

LINE의 성능 테스트 자동화 사례에서는 서버 기동 직후 대량 요청에서 수백 개 Thread가 BLOCKED 상태로 쌓이는 문제를 발견했다.

- [LINE — 서버 사이드 테스트 자동화 여정 5](https://engineering.linecorp.com/ko/blog/server-side-test-automation-5/)

## WAITING과 TIMED_WAITING은 대기 상태지만 항상 문제는 아니다

WAITING은 다른 Thread의 신호나 작업 완료를 기한 없이 기다리는 상태다.

TIMED_WAITING은 일정 시간 제한을 두고 기다리는 상태다.

Thread Pool의 유휴 Worker는 정상적으로 WAITING 상태일 수 있다.

sleep을 호출한 Thread는 TIMED_WAITING에 있을 수 있다.

따라서 WAITING Thread가 많다는 사실만으로 장애라고 판단하지 않는다.

어떤 Stack에서 왜 기다리는지 봐야 한다.

## Thread Dump는 대기 위치를 구체적으로 보여 준다

Metric은 Thread 수가 갑자기 300에서 3,000으로 증가했다는 사실을 보여 줄 수 있다.

하지만 왜 늘었는지는 알 수 없다.

Thread Dump는 각 Thread의 Stack과 상태를 보여 준다.

예를 들어:

~~~text
500개 Thread
→ HikariPool.getConnection 부근 대기

또는

500개 Thread
→ 동일 synchronized 초기화 Lock에서 BLOCKED

또는

500개 Thread
→ 외부 HTTP 호출 응답 대기
~~~

처럼 대기 위치를 좁힐 수 있다.

LINE의 데이터 엔지니어링 장애 대응 사례에서는 Metric에서 Thread 급증을 발견한 뒤 Thread Dump로 어떤 Thread가 증가했는지 확인했다.

## Thread가 많다고 Thread 수부터 줄이면 안 된다

Thread가 많아진 이유가 중요하다.

~~~text
Traffic 증가로 정상 Worker 증가
DB Connection 대기로 쌓임
External API 대기로 쌓임
Lock 대기로 쌓임
Thread Leak
~~~

원인이 Connection Pool 대기라면 Tomcat Thread 수만 줄이는 것은 사용자 대기 위치를 다른 곳으로 옮길 수 있다.

반대로 Thread 수를 늘리면 더 많은 요청이 DB에 몰려 병목을 악화시킬 수도 있다.

Thread는 [[06. Tomcat HikariCP DB Queueing]]의 Queue 구조와 함께 봐야 한다.

## Metaspace는 클래스 메타데이터를 저장한다

Metaspace는 Java Class에 대한 메타데이터를 저장하는 Native Memory 영역이다.

애플리케이션이 많은 Class를 로드하는 것은 정상이다.

하지만 동적 Class 생성이나 ClassLoader Leak이 있으면 Metaspace가 계속 증가할 수 있다.

Heap이 안정적인데 Process RSS가 계속 증가한다면 Metaspace도 후보 중 하나가 된다.

## Code Cache는 JIT으로 컴파일된 코드를 저장한다

JVM은 자주 실행되는 Bytecode를 JIT Compiler가 Native Machine Code로 변환해 실행 성능을 높인다.

이 컴파일된 코드를 저장하는 영역이 Code Cache다.

일반적인 웹 애플리케이션에서 가장 먼저 의심할 영역은 아닐 수 있지만 JVM Process Memory에는 Heap 외 이런 영역도 있다는 점이 중요하다.

## Direct Memory는 Heap 밖의 Buffer에 사용될 수 있다

Java NIO나 Netty는 Direct ByteBuffer를 사용해 Heap 밖에 Memory를 할당할 수 있다.

Direct Buffer는 Native I/O와 효율적으로 연결할 수 있지만 Heap Metric에는 직접 나타나지 않는다.

따라서:

~~~text
Heap 안정
GC 정상
Container RSS 계속 증가
~~~

라면 Direct Memory를 조사할 이유가 생긴다.

Network workload가 많거나 Netty를 사용하는 시스템에서는 특히 중요할 수 있다.

## Native Memory는 하나의 Metric으로 설명되지 않는다

JVM Process의 Native Memory에는 여러 요소가 섞여 있다.

~~~text
Thread Stack
Metaspace
Code Cache
Direct Buffer
GC 내부 구조
JIT Compiler
JNI / Native Library
기타 JVM 내부 Allocation
~~~

그래서:

~~~text
Container memory
-
Heap
=
모두 Direct Memory
~~~

처럼 계산하면 안 된다.

Heap 밖 전체가 Native 영역이지만 구성 요소는 여러 개다.

## Native Memory Tracking은 JVM 내부 Native 사용을 조사하는 도구다

HotSpot JVM은 Native Memory Tracking(NMT)을 지원한다.

NMT를 활성화하면 JVM 내부 Native Memory를 영역별로 조사하는 데 도움이 된다.

예를 들어 jcmd를 이용해 Memory Summary를 볼 수 있다.

다만 NMT 자체도 추적 Overhead가 있을 수 있고 사전에 활성화가 필요한 설정이 있으므로 Production에서 무조건 켜는 기능은 아니다.

성능 문제 조사에 필요할 때 검토한다.

## Heap Dump는 객체가 무엇을 차지하고 있는지 본다

Heap이 계속 커지고 GC 후에도 내려오지 않는다면 Heap Dump를 사용해 어떤 객체가 Memory를 차지하는지 분석할 수 있다.

Heap Dump에는 실제 객체 데이터가 포함될 수 있다.

따라서 Production Heap Dump는 개인정보와 Secret이 포함될 수 있는 민감한 Artifact로 취급해야 한다.

공개 저장소나 일반 채팅에 올리지 않는다.

## OOM이라고 모두 Java heap space는 아니다

OutOfMemoryError에는 여러 형태가 있을 수 있다.

예를 들어:

~~~text
Java heap space
Metaspace
Direct buffer memory
unable to create native thread
~~~

등 원인이 다르다.

또 Container OOMKilled는 JVM이 Java OutOfMemoryError를 출력하기 전에 운영체제가 Process를 죽인 것일 수도 있다.

따라서 OOM을 조사할 때는 Error 메시지, Container OOMKilled, RSS, Heap, Thread를 함께 본다.

LINE의 messaging-hub 사례처럼 Heap Dump에서 명확한 Leak이 보이지 않더라도 Container Memory와 JVM 설정 관계가 문제일 수 있다.

관련 자료:
- [LINE — messaging-hub 트러블 슈팅](https://engineering.linecorp.com/ko/blog/messaing-hub-troubleshooting/)

## Xmx를 Container Limit까지 꽉 채우면 위험할 수 있다

Container Memory Limit이 1GiB인데 Xmx도 1GiB로 설정하면 Heap 외 Native Memory를 위한 공간이 거의 없다.

실제로 JVM은 Thread Stack, Metaspace, Code Cache, Direct Buffer 등도 필요하다.

따라서:

~~~text
Container Limit
>
Heap Max
+
Native Memory 여유
~~~

가 필요하다.

정확한 비율은 workload와 JVM 구성에 따라 달라지므로 측정해야 한다.

## GC 튜닝은 문제를 측정한 뒤 선택한다

성능 문제를 보면 흔히 다음과 같은 유혹이 있다.

~~~text
GC가 보임
→ Collector 변경
→ Heap 늘림
→ GC Option 추가
~~~

하지만 GC가 실제 사용자 지연의 원인이 아니라면 복잡도만 늘어난다.

먼저 다음을 확인한다.

~~~text
GC Pause가 p95/p99 Spike와 시간상 겹치는가?
Allocation Rate가 변경 전보다 크게 증가했는가?
GC 후 Live Set이 계속 증가하는가?
Heap Max에 반복적으로 접근하는가?
Container RSS와 Heap 차이는 안정적인가?
Thread 수는 정상인가?
~~~

그 뒤 가장 작은 변경을 적용하고 같은 조건에서 재측정한다.

NAVER D2의 성능 튜닝 글도 다른 서비스의 JVM Option을 그대로 가져오는 대신 실제 측정과 반복 검증을 강조한다.

관련 자료:
- [NAVER D2 — 자바 애플리케이션 성능 튜닝의 도](https://d2.naver.com/helloworld/184615)
- [NAVER D2 — Garbage Collection 튜닝](https://d2.naver.com/helloworld/37111)

## 사용자 응답과 JVM 지표를 연결해서 읽는다

가상의 예를 보자.

~~~text
200 RPS
p95 = 100ms

250 RPS
p95 = 1,200ms
~~~

JVM을 확인했더니:

~~~text
Heap used
안정

GC pause
변화 작음

Thread
200 → 800

Hikari pending
증가
~~~

라면 GC보다 Thread/DB Connection 대기를 먼저 조사할 근거가 생긴다.

반대로:

~~~text
p99 Spike 시각
= 긴 GC Pause 시각과 반복적으로 일치

Heap
Max 근처 반복

Old 영역
계속 증가
~~~

라면 GC/Heap Pressure 가설이 강해진다.

또:

~~~text
Heap 50%
GC 정상
Thread 1,500
Container memory 98%
OOMKilled
~~~

라면 Heap보다 Thread Stack이나 Native Memory를 더 먼저 볼 수 있다.

이처럼 JVM Metric은 독립된 그래프가 아니라 **사용자 응답 시간과 같은 시간축에서 읽어야 한다.**
