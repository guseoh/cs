# 대규모 데이터 — 양, 관계, 고유도, 분포와 쏠림

대규모 데이터 테스트를 한다고 하면 가장 먼저 “몇 건을 만들까?”를 떠올리기 쉽다.

하지만 성능은 단순한 Row 수만으로 결정되지 않는다.

Product가 10,000개 있어도 각 Product에 SKU가 1개씩만 연결된 데이터와 평균 20개씩 연결된 데이터는 Join 결과 크기가 크게 다르다. Category가 100개 있어도 Product가 고르게 분산된 데이터와 한 Category에 80%가 몰린 데이터는 Index 선택과 Query 비용이 달라질 수 있다.

따라서 대규모 데이터는 적어도 다음 요소를 함께 봐야 한다.

~~~text
데이터 양(Volume)
관계(Relation)
고유값 수와 고유도(Cardinality)
값의 분포(Distribution)
특정 값으로의 쏠림(Skew)
시간에 따른 분포
Null 비율
부모-자식 Fan-out
~~~

이 요소를 의도적으로 설계해야 “10K 데이터”가 단순한 포트폴리오 숫자가 아니라 실제 성능 질문에 답하는 실험 변수가 된다.

## 데이터 양은 전체 크기의 출발점이다

가장 단순한 규모는 Table Row 수다.

~~~text
Product     10,000
SKU         20,000
Inventory   20,000
Order     1,000,000
~~~

데이터가 늘면 다음이 바뀔 수 있다.

~~~text
Table 크기
Index 크기
Buffer Pool에 들어가는 비율
읽어야 하는 Page 수
Sort 대상 Row 수
Join 중간 결과
Temporary Table
Disk I/O
Backup / Migration 시간
~~~

따라서 데이터 양은 중요하다.

하지만 “Product 10,000개”만으로 Query 비용을 설명할 수는 없다.

실제 Query가 어떤 관계를 따라 몇 Row를 읽는지 봐야 한다.

## 관계형 데이터에서는 부모 하나에 자식이 몇 개 붙는지가 중요하다

Commerce 서비스는 여러 Table이 연결된다.

~~~text
Category
→ Product
→ SKU
→ Inventory

Customer
→ Order
→ OrderItem

Subscription
→ SubscriptionItem
→ Plan
~~~

Product 10,000개라는 숫자가 같아도 SKU 수가 다르면 Join 결과도 달라진다.

예를 들어:

~~~text
Dataset A
Product 10,000
SKU 평균 1개
SKU 총 10,000

Dataset B
Product 10,000
SKU 평균 5개
SKU 총 50,000
~~~

다음 Query를 생각해보자.

~~~sql
SELECT ...
FROM product p
JOIN sku s ON s.product_id = p.id
WHERE ...
~~~

Product 수는 같지만 B에서는 더 많은 SKU Row를 읽고 Join할 수 있다.

이처럼 부모 하나에서 자식이 여러 개로 퍼지는 정도를 Fan-out이라고 부르기도 한다.

영어 용어보다 **부모 하나에 자식이 몇 개씩 달리는가**라고 이해하면 쉽다.

## 평균 Fan-out만 보면 극단값을 놓칠 수 있다

Product당 SKU가 평균 2개라고 해보자.

모든 Product에 정확히 2개씩 있는 것처럼 느껴질 수 있지만 실제로는 다음과 같을 수 있다.

~~~text
90% Product
SKU 1개

9% Product
SKU 3개

1% Product
SKU 매우 많음
~~~

평균은 비슷해도 일부 Product 조회에서는 Join Row가 매우 커질 수 있다.

그래서 관계 분포를 볼 때 다음을 확인하는 것이 좋다.

~~~text
최소
평균
중앙값
p95
최대
구간별 Product 수
~~~

대규모 데이터에서 평균 하나만 보는 것은 응답 시간에서 평균만 보는 문제와 비슷하다.

분포가 중요하다.

## Cardinality는 두 가지 문맥으로 사용된다

Cardinality라는 용어는 문맥에 따라 뜻이 다를 수 있다.

### 컬럼의 고유값 수

Index와 Query 최적화 문맥에서는 컬럼에 서로 다른 값이 몇 개 있는지 뜻하는 경우가 많다.

예를 들어 Product 10,000개가 있다고 하자.

~~~text
id
고유값 10,000개

display_status
PUBLIC / HIDDEN
고유값 2개

category_id
고유값 100개
~~~

이 문서에서는 이런 의미를 **고유값 수 또는 고유도(Cardinality)**라고 부른다.

### 관계의 개수

ERD나 데이터 모델링에서는 1:1, 1:N 같은 관계 수를 설명할 때 Cardinality라는 용어를 사용하기도 한다.

~~~text
Product 1
→ SKU N
~~~

따라서 문서를 읽을 때 “Column의 고유값 수인가?”와 “Entity 관계 수인가?”를 먼저 구분해야 한다.

## 고유값 수가 많으면 Index가 무조건 좋은가

고유값 수가 많은 Column은 특정 값을 찾을 때 검색 범위를 크게 줄일 가능성이 있다.

예를 들어:

~~~text
Product 10,000,000개

WHERE id = 123
→ 결과 거의 1개
~~~

이 조건은 매우 좁은 범위를 선택한다.

반면:

~~~text
WHERE display_status = 'PUBLIC'
~~~

이고 전체 Product의 80%가 PUBLIC이라면 결과가 800만 건일 수 있다.

Index가 있어도 많은 Row를 읽어야 한다.

따라서 “Cardinality가 높다/낮다”만으로 Index 유효성을 판단하면 부족하다.

실제 조건이 전체 중 얼마나 많은 Row를 선택하는지 봐야 한다.

## 선택도는 조건이 얼마나 좁은 범위를 고르는지 이해하는 개념이다

선택도(Selectivity)는 전체 Row 중 조건에 해당하는 Row 비율을 생각할 때 사용하는 개념이다.

100만 건 중 100건만 선택한다면:

~~~text
100 / 1,000,000
= 0.01%
~~~

매우 좁은 범위다.

반대로 조건 결과가 전체의 70%라면 범위가 매우 넓다.

Index가 유리한지는 Index 구조와 실제 I/O 비용, Covering 여부 등 여러 요소가 있지만 일반적으로 조건이 적은 Row를 좁혀 줄수록 Index를 사용할 이점이 커질 가능성이 있다.

## 분포는 같은 고유값 수에서도 결과를 완전히 바꾼다

Category가 10개인 두 Dataset을 비교해보자.

Dataset A:

~~~text
각 Category
약 10%씩
~~~

Dataset B:

~~~text
Category A
70%

Category B
10%

나머지 8개
총 20%
~~~

두 데이터 모두 category_id의 고유값 수는 10개다.

하지만:

~~~sql
WHERE category_id = 'A'
~~~

가 선택하는 Row 수는 크게 다르다.

즉 Cardinality는 값 종류의 수를 말하고 Distribution은 그 값들이 어떤 비율로 나타나는지를 말한다.

둘을 함께 봐야 한다.

## 쏠림은 일부 값에 데이터가 집중되는 현상이다

쏠림(Skew)은 특정 값이나 구간에 데이터가 몰리는 현상이다.

실제 서비스에는 균등한 데이터보다 쏠린 데이터가 흔하다.

예를 들어:

~~~text
인기 Product 몇 개에 주문 집중
일부 대형 고객에 주문 이력 집중
특정 Category에 상품 집중
최근 날짜에 조회 집중
특정 Tenant에 Traffic 집중
~~~

이런 쏠림은 여러 성능 문제를 만든다.

특정 Product Row를 동시에 갱신하면 Lock 경쟁이 커질 수 있다.

특정 고객의 주문이 수십만 건이면 대부분 고객의 주문 목록은 빠른데 그 고객만 느릴 수 있다.

Cache에서는 특정 Key에 요청이 몰리는 Hot Key 문제가 생길 수 있다.

카카오의 Spark 최적화 글도 특정 Key에 데이터가 몰리면 일부 Task에 부담이 집중되어 Spill과 처리 시간 불균형이 발생하는 사례를 보여 준다.

DB와 Spark의 내부 구조는 다르지만 **같은 전체 데이터량에서도 분포와 쏠림 때문에 처리 비용이 달라진다**는 개념을 이해하기 좋은 사례다.

관련 자료:
- [카카오 — Spark Shuffle Partition과 최적화](https://tech.kakao.com/posts/461)

## Hot Data는 최근 또는 인기 데이터에 접근이 몰리는 현상이다

데이터가 1억 건 있어도 실제 요청의 90%가 최근 1일 데이터만 조회할 수 있다.

이 경우 전체 Table 크기와 실제 자주 읽는 Working Set이 다르다.

~~~text
전체 데이터
100,000,000 rows

자주 접근
최근 1,000,000 rows
~~~

Buffer Pool이나 Cache에 최근 데이터가 잘 올라가 있다면 전체 데이터량이 매우 커도 일부 Query는 안정적으로 빠를 수 있다.

반대로 테스트 데이터가 모든 날짜에 균등하게 접근하도록 만들어져 있으면 실제 Production과 다른 Cache 특성이 나타난다.

따라서 시간 분포도 중요하다.

## 시간 데이터는 생성 시점이 모두 같으면 현실성이 떨어질 수 있다

Order 1,000만 건을 만들면서 created_at을 모두 같은 날로 넣었다고 하자.

시간 Range Query나 Partition, Index 정렬 특성을 테스트하기 어렵다.

실제 서비스가 2년 동안 데이터를 쌓았다면 Synthetic Data도 필요에 따라 다음처럼 시간 분포를 설계할 수 있다.

~~~text
2년 전 ~ 현재

최근 30일에 요청 집중
최근 7일에 주문량 증가
행사 기간 Spike
~~~

어떤 분포를 만들지는 검증하려는 질문에 따라 결정한다.

## Null 비율도 Query Plan과 Application 동작에 영향을 줄 수 있다

실제 데이터에서는 Column이 항상 값으로 채워져 있지 않을 수 있다.

~~~text
coupon_id
NULL 95%

promotion_id
NULL 70%
~~~

같은 분포가 있을 수 있다.

Synthetic Data에서 모든 Row를 무조건 채우면 실제 조건 Query와 Join 결과가 달라질 수 있다.

Null 여부가 Business Rule과 Query 조건에 영향을 준다면 비율을 재현하는 것이 좋다.

## 가격 분포도 단순 Random Uniform으로 만들면 실제와 다를 수 있다

상품 가격이 1원에서 100만원 사이에 균등하게 존재하는 Commerce 서비스는 흔하지 않다.

실제 가격은 특정 범위에 몰리고 일부 고가 상품이 있을 수 있다.

가격 정렬, Range Filter, 통계 Query를 테스트하려면 이런 분포가 중요할 수 있다.

다만 Catalog List의 단순 Row 수 영향만 보는 실험이라면 가격 현실성을 지나치게 높일 필요는 없다.

여기서 중요한 원칙은 **Dataset의 현실성은 실험 질문에 필요한 만큼만 높인다**는 것이다.

## 데이터 규모와 요청 부하는 다른 실험 변수다

성능에서 자주 섞이는 두 축이 있다.

~~~text
Dataset Scale
1K → 10K → 100K → 1M

Request Load
25 → 50 → 100 → 200 RPS
~~~

다음 비교는 해석이 어렵다.

~~~text
1K / 50 RPS
vs
100K / 250 RPS
~~~

느려진 이유가 데이터 증가인지 요청 증가인지 분리하기 어렵기 때문이다.

따라서:

~~~text
같은 100 RPS
1K vs 10K
→ 데이터 규모 효과

같은 10K
50 vs 100 vs 200 RPS
→ 부하 효과
~~~

처럼 한 축을 고정해서 비교한다.

이 원리는 [[09. Before After와 성능 실험의 인과관계]]와 연결된다.

## 10K, 100K, 1M은 목표가 아니라 관측 지점이다

큰 숫자를 만드는 것 자체는 성능 엔지니어링 성과가 아니다.

10K에서 이미 Full Table Scan과 N+1 문제가 명확히 드러났다면 100K와 1M으로 무작정 늘리기 전에 먼저 문제를 분석할 수 있다.

~~~text
10K
→ 병목 발견
→ 원인 분석
→ 최소 개선
→ 동일 10K 재측정

추가 Scale 필요성이 남음
→ 100K
~~~

이렇게 해야 Scale 단계가 포트폴리오용 숫자 수집이 아니라 **새로운 한계를 발견하기 위한 실험 단계**가 된다.

## Synthetic Data는 실제 Production Data를 복제하는 것과 다르다

Production Data를 그대로 복제하면 실제 분포와 관계를 유지하기 쉽다.

하지만 다음 위험이 있다.

~~~text
개인정보
주소
연락처
결제 관련 데이터
운영 Secret
고객 주문 이력
~~~

성능 환경으로 복사하는 순간 보안과 개인정보 문제가 생길 수 있다.

Synthetic Data는 이런 실제 값을 사용하지 않고 가짜 데이터를 만든다.

대신 현실적인 관계와 분포는 직접 설계해야 한다.

## 가짜 이름보다 관계와 분포가 더 중요할 수 있다

Synthetic Commerce Data에서 상품명이 진짜 브랜드처럼 보이는 것보다 다음이 성능에는 더 중요할 수 있다.

~~~text
Product당 SKU 수
Category별 Product 비율
Inventory 분포
OrderItem Fan-out
시간 분포
Null 비율
상태값 비율
Hot Product 비율
~~~

성능 테스트 목적이라면 데이터의 겉모양보다 Query가 읽는 구조와 분포가 더 중요하다.

## 고정 Seed는 같은 Random Data를 다시 만드는 데 사용한다

Synthetic Data Generator에서 Random을 사용하면 매 실행마다 결과가 달라질 수 있다.

Seed는 난수 생성 과정의 시작값이다.

같은 Generator와 같은 Seed를 사용하면 같은 Random Sequence를 재현하기 쉽다.

~~~text
Generator Version
+ Seed
+ Target Size

→ 같은 Dataset 재생성 가능
~~~

하지만 Seed만 같다고 충분한 것은 아니다.

Generator 코드가 바뀌면 같은 Seed에서도 다른 결과가 나올 수 있다.

그래서 중요한 실험에서는 Source Commit이나 Generator Digest도 같이 기록한다.

이 내용은 [[13. 재현 가능한 성능 실험과 안전한 격리]]에서 자세히 다룬다.

## Dataset 검증은 총 Row 수만 확인하면 부족하다

“Product 10,000개 생성 완료”만 검사하면 관계가 깨진 데이터를 놓칠 수 있다.

Commerce Dataset이라면 다음을 검사할 수 있다.

~~~text
Product 총 수
SKU 총 수
Inventory 총 수

Category별 Product 수
Product당 SKU 분포
상태값 분포
구독 가능 여부 비율
재고 구간 분포

중복 business key
중복 skuCode
없는 Category 참조
SKU가 하나도 없는 Product
고아 Inventory
~~~

이렇게 해야 **의도한 모양의 10K Dataset**이라고 말할 수 있다.

## SQL로 데이터 분포를 직접 확인할 수 있다

Category별 Product 수:

~~~sql
SELECT category_id, COUNT(*) AS product_count
FROM product
GROUP BY category_id
ORDER BY product_count DESC;
~~~

Product별 SKU 수:

~~~sql
SELECT product_id, COUNT(*) AS sku_count
FROM sku
GROUP BY product_id;
~~~

상태 분포:

~~~sql
SELECT status, COUNT(*) AS cnt
FROM sku
GROUP BY status;
~~~

Null 비율:

~~~sql
SELECT
  COUNT(*) AS total,
  SUM(coupon_id IS NULL) AS null_count
FROM orders;
~~~

이 Query의 목적은 성능을 측정하는 것이 아니라 **실험 입력이 설계대로 만들어졌는지 검증하는 것**이다.

## 데이터가 커지면 Query 실행 계획이 달라질 수 있다

MySQL Optimizer는 Query를 실행할 때 Table 통계와 Index 정보를 이용해 비용을 추정한다.

작은 Dataset에서는 Full Scan이 충분히 싸서 Index를 사용하지 않을 수 있다.

데이터가 커지면 Index Range Scan이 더 유리해질 수 있다.

반대로 조건이 전체의 대부분을 선택하면 Index보다 Full Scan이 나을 수 있다.

따라서 10K → 100K에서 느려졌다면 단순히 “데이터가 많아져서”라고 끝내지 않는다.

다음을 확인한다.

~~~text
EXPLAIN
실제 Rows Examined
사용 Index
Join 순서
Sort
Temporary Table
Query latency
~~~

## 통계 정보가 실제 분포와 어긋나면 Optimizer 판단도 달라질 수 있다

Database Optimizer는 실제 모든 Row를 매번 확인하고 Plan을 만드는 것이 아니다.

통계 정보를 사용해 결과 Row 수와 비용을 추정한다.

데이터를 대량 삽입한 뒤 통계가 충분히 갱신되지 않았거나 분포가 극단적으로 쏠려 있으면 추정과 실제가 다를 수 있다.

따라서 실행 계획에서 Estimated Row와 실제 처리 Row가 크게 다르면 통계와 분포를 조사할 수 있다.

MySQL 버전과 설정에 따라 Histogram 같은 통계 기능도 사용할 수 있다.

## 복합 Index는 Column 순서와 Query 조건이 함께 중요하다

예를 들어 다음 Index가 있다고 하자.

~~~text
(category_id, status, price)
~~~

Query가 어떤 Column을 Equality로 사용하고 어떤 Column을 Range로 사용하는지에 따라 Index 활용 방식이 달라질 수 있다.

“Index가 있다”가 아니라 **실제 Query Predicate와 정렬 조건에서 어떻게 사용되는가**를 EXPLAIN으로 확인해야 한다.

NAVER D2의 SQL 성능 글은 B-Tree Index와 복합 Index를 이해하는 데 참고하기 좋다.

## Hotspot은 같은 Index Page나 Row에 접근이 몰리는 상황이다

데이터 쏠림은 Read 양만 바꾸는 것이 아니라 경합도 만들 수 있다.

카카오의 MySQL Ascending/Descending Index 실험에서는 Query가 Index의 특정 부분에 집중되는 Hotspot 조건에서 Thread 간 Page 경합으로 처리량 차이가 커지는 사례를 보여 준다.

같은 Query와 비슷한 데이터량이어도 **어디에 접근이 집중되는가**가 성능을 바꿀 수 있다는 예다.

관련 자료:
- [카카오 — MySQL Ascending index vs Descending index](https://tech.kakao.com/posts/351)

## 매우 큰 고유값 수는 정확히 세는 비용도 커질 수 있다

Cardinality를 계산하려고 모든 고유값을 정확히 Set에 저장하면 데이터가 매우 클 때 Memory 비용이 커질 수 있다.

HyperLogLog 같은 확률적 자료구조는 훨씬 적은 Memory로 고유 원소 수를 근사한다.

현재 일반적인 Commerce 10K Dataset 검증에서 반드시 필요한 기술은 아니지만, Cardinality라는 용어가 “고유 원소 수”라는 의미로도 사용된다는 점을 이해하는 데 도움이 된다.

관련 자료:
- [NAVER D2 — 유일한 원소 개수(Cardinality) 추정과 HyperLogLog](https://d2.naver.com/helloworld/711301)

## Dataset에는 재현하는 범위와 재현하지 않는 범위를 같이 적는다

예를 들어 Product/SKU/Inventory만 현실적인 분포로 만든 10K Dataset이 있다고 하자.

이 Dataset으로 다음 질문은 검증할 수 있다.

~~~text
Product Row 증가가 목록 Query에 미치는 영향
SKU Fan-out 증가가 Join에 미치는 영향
Inventory Join의 비용
~~~

하지만 다음까지 현실적으로 재현한다고 주장하면 과장이다.

~~~text
실제 Review 분포
실제 Image 수
실제 Brand 비율
실제 Order History
실제 Subscription 관계
실제 사용자 행동
~~~

좋은 Dataset 문서는 무엇을 포함했는지뿐 아니라 **어디까지 일반화할 수 없는지**도 적는다.

## 규모가 커질수록 생성 시간과 검증 시간도 성능 문제가 된다

1M 또는 10M 데이터를 만들면 Application Query 성능만 문제가 되는 것이 아니다.

~~~text
Dataset 생성 시간
Import 시간
Migration 시간
Index 생성 시간
Backup 크기
Restore 시간
CI 실행 시간
Storage 비용
~~~

도 커진다.

따라서 매우 큰 Dataset을 매 CI마다 생성하는 것은 비효율적일 수 있다.

작은 Fixture로 Generator 계약을 검증하고, 실제 큰 Dataset 생성은 별도 실험 단계에서 수행하는 식으로 나눌 수 있다.

## 대규모 데이터 설계는 실제 질문에서 출발한다

“10M까지 해봐야 대규모 프로젝트처럼 보인다”는 이유로 데이터를 키우면 실험이 기술 전시가 된다.

더 좋은 질문은 다음과 같다.

~~~text
현재 10K에서 Query Plan이 어떻게 변하는가?
10K에서 이미 병목이 재현되는가?
100K가 새로운 한계를 보여줄 가능성이 있는가?
어떤 관계/분포가 현재 Query에 가장 큰 영향을 주는가?
~~~

이 질문에 답하면서 필요한 Scale만 추가한다.

**데이터 규모는 성과가 아니라 병목을 드러내기 위한 조절 가능한 실험 변수다.**
