# 대규모 데이터 — 양, 관계, 고유도, 분포, 쏠림

“대규모 데이터 테스트를 한다”는 말을 들으면 먼저 10만 건, 100만 건처럼 데이터 건수를 떠올리기 쉽다. 하지만 성능 관점에서 중요한 것은 단순한 개수만이 아니다.

같은 Product 10,000개라도 각 Product에 SKU가 1개씩만 달린 경우와 평균 20개씩 달린 경우는 전체 row 수와 Join 결과 크기가 크게 다르다. Category 100개에 Product가 고르게 분산된 경우와 한 Category에 대부분이 몰린 경우도 쿼리가 읽는 범위와 캐시 접근 패턴이 달라질 수 있다.

그래서 대규모 데이터는 다음 축을 함께 본다.

~~~text
데이터 양(Volume)
관계(Relation)
고유값 수와 고유도(Cardinality)
값의 분포(Distribution)
특정 값으로의 쏠림(Skew)
~~~

## 데이터 양은 무엇인가

데이터 양은 전체 데이터 규모다. 가장 단순하게는 테이블 row 수로 볼 수 있다.

~~~text
Product     10,000 rows
SKU         20,000 rows
Inventory   20,000 rows
~~~

하지만 Product가 10,000건이라는 사실만으로 쿼리 비용을 예측하기는 어렵다. 데이터가 늘면 테이블과 인덱스의 크기, Buffer Pool에 들어갈 수 있는 비율, 읽어야 하는 page 수, 정렬해야 하는 row 수, Join 중간 결과 크기와 Disk I/O가 같이 달라질 수 있기 때문이다.

따라서 데이터 건수는 출발점이고, 그 데이터가 실제 쿼리에서 어떻게 연결되고 얼마나 선택되는지까지 봐야 한다.

## 관계는 왜 중요한가

Commerce 데이터는 서로 연결되어 있다.

~~~text
Category
→ Product
→ SKU
→ Inventory

Customer
→ Order
→ OrderItem
~~~

Product 10,000개라는 숫자만 같아도 SKU와 Inventory의 연결 수가 다르면 실제 조회 비용은 달라진다.

예를 들어 다음 두 데이터셋을 비교해보자.

~~~text
Dataset A
Product 10,000
Product당 SKU 평균 1개
SKU 총 10,000

Dataset B
Product 10,000
Product당 SKU 평균 5개
SKU 총 50,000
~~~

Product 수는 같지만 Product와 SKU를 함께 읽는 쿼리에서는 Dataset B가 훨씬 많은 row를 다룰 수 있다.

부모 하나에서 자식이 몇 개로 퍼지는지를 fan-out이라고 부르기도 한다. 영어 표현 자체보다 “Product 하나에 SKU가 몇 개씩 달리는가”라고 이해하면 쉽다.

## Cardinality는 문맥을 구분해야 한다

Cardinality는 성능 글과 데이터 모델링 글에서 자주 등장하는데, 문맥에 따라 뜻이 달라질 수 있다.

데이터베이스와 인덱스 문맥에서는 한 컬럼에 서로 다른 값이 몇 개 있는지, 즉 **고유값 수**를 의미하는 경우가 많다.

~~~text
Product.id
10,000개의 Product가 모두 다른 id
→ 고유값 수가 많음

display_status
PUBLIC / HIDDEN 두 종류
→ 고유값 수가 적음

category_id
100개 Category
→ 중간 정도
~~~

반면 ERD나 관계 모델에서는 1:1, 1:N처럼 엔티티 사이의 관계 개수를 표현할 때도 Cardinality라는 말을 쓴다.

~~~text
Product 1
→ SKU N
~~~

따라서 문서를 읽을 때는 “컬럼의 고유값 수를 말하는가?”와 “관계의 개수를 말하는가?”를 먼저 구분해야 한다.

이 문서에서는 인덱스와 쿼리 문맥에서는 **고유값 수 또는 고유도(Cardinality)**라고 표현한다.

## 고유값 수가 높으면 인덱스가 항상 좋은가

아니다.

고유값 수가 많은 컬럼은 특정 값을 찾을 때 검색 범위를 좁히기 유리한 경우가 많다. 하지만 실제 인덱스 효율은 조건이 전체 데이터 중 얼마나 적은 row를 선택하는지와 함께 봐야 한다.

예를 들어 Product 1,000만 건에서 id 하나를 찾는다면 결과는 거의 1건이다.

~~~text
WHERE id = 123
~~~

반면 status가 PUBLIC과 HIDDEN 두 값뿐이고 PUBLIC이 전체의 70%라면 다음 조건은 수백만 건을 선택할 수 있다.

~~~text
WHERE status = 'PUBLIC'
~~~

인덱스가 존재해도 결국 많은 row를 읽어야 하므로 항상 전체 스캔보다 유리하다고 볼 수 없다.

NAVER D2의 SQL 성능 글도 인덱스가 항상 빠른 것이 아니며 조건이 선택하는 범위와 I/O 비용을 함께 봐야 한다고 설명한다.

## 선택도는 무엇인가

선택도(Selectivity)는 전체 row 중 조건이 선택하는 범위가 얼마나 좁은지를 이해할 때 사용하는 개념이다.

100만 row 중 100건만 선택한다면 매우 좁은 범위다.

~~~text
100 / 1,000,000
= 0.01%
~~~

반대로 조건 하나가 전체의 70%를 선택한다면 범위가 매우 넓다.

그래서 고유값 수와 선택도는 연결되어 있지만 같은 말은 아니다. 고유값 수가 많아도 값 분포가 한쪽으로 심하게 쏠려 있다면 특정 조건은 많은 row를 선택할 수 있다.

## 분포는 무엇인가

분포는 각 값이 데이터 안에서 어떤 비율로 나타나는지 말한다.

Category가 10개라고 가정하자.

균등한 데이터는 다음처럼 보일 수 있다.

~~~text
Category A 10%
Category B 10%
Category C 10%
...
~~~

하지만 실제 서비스는 다음처럼 한쪽으로 몰릴 수 있다.

~~~text
Category A 70%
Category B 10%
나머지 20%
~~~

두 데이터셋 모두 Category 고유값 수는 10개지만 실제 쿼리가 읽는 row 수는 크게 달라질 수 있다.

따라서 “고유값이 몇 개인가”와 “각 값이 몇 퍼센트를 차지하는가”를 함께 봐야 한다.

## 쏠림은 무엇인가

쏠림(Skew)은 일부 값이나 일부 구간에 데이터가 집중되는 현상이다.

실제 서비스에는 균등한 데이터보다 쏠린 데이터가 흔하다.

~~~text
일부 인기 상품에 주문 집중
특정 대형 고객에게 주문 이력 집중
특정 Category에 Product 집중
최근 7일 데이터에 조회 집중
특정 tenant에 요청 집중
~~~

쏠림은 같은 row 수에서도 다른 성능 문제를 만든다.

예를 들어 인기 Product 하나에 수정 요청이 몰리면 같은 row나 index page에 접근이 집중될 수 있다. 특정 고객에게 주문이 수십만 건 몰려 있다면 대부분 고객의 주문 조회는 빠르지만 그 고객만 매우 느릴 수 있다.

카카오의 Spark 최적화 글에서도 특정 key에 데이터가 몰리면 일부 작업에 부담이 집중되어 Spill과 처리 시간 불균형이 생길 수 있음을 보여 준다.

## 평균값만 보면 fan-out을 놓칠 수 있다

Product 하나당 SKU가 평균 2개라고 해보자.

이 숫자만 보면 모든 Product에 SKU가 2개씩 붙어 있다고 생각하기 쉽다. 하지만 실제로는 다음처럼 일부 Product에 자식 row가 크게 몰릴 수도 있다.

~~~text
90% Product
SKU 1개

9% Product
SKU 3개

1% Product
SKU 매우 많음
~~~

평균은 비슷해도 특정 Product를 조회할 때 Join 결과가 크게 늘어날 수 있다.

그래서 데이터 관계를 검증할 때는 평균만 보지 않고 최소, 최대, 중앙값, 구간별 분포와 극단값도 함께 보는 것이 좋다.

## 데이터 규모와 요청 부하는 다른 변수다

성능 실험에서 자주 섞이는 두 축이 있다.

첫 번째는 데이터 규모다.

~~~text
1K
→ 10K
→ 100K
→ 1M
~~~

두 번째는 요청 부하다.

~~~text
25 RPS
→ 50
→ 100
→ 200
→ 250
~~~

두 축을 동시에 크게 바꾸면 결과가 나빠졌을 때 원인을 분리하기 어렵다.

~~~text
Product 1K / 50 RPS
→ Product 100K / 250 RPS
~~~

를 바로 비교하면 데이터가 커져서 느려진 것인지 동시 요청이 늘어서 느려진 것인지 판단하기 어렵다.

그래서 다음처럼 한 축씩 바꾸는 것이 해석하기 쉽다.

~~~text
같은 100 RPS
1K vs 10K
→ 데이터 규모 영향

같은 10K Dataset
50 vs 100 vs 200 RPS
→ 요청 부하 영향
~~~

## 왜 처음부터 1M을 만들지 않는가

데이터를 크게 만들었다는 사실 자체는 성능 개선의 성과가 아니다.

10K에서 이미 Full Table Scan이나 N+1 문제, 잘못된 인덱스 선택이 드러났다면 100K와 1M으로 더 키우기 전에 먼저 원인을 분석하는 편이 낫다.

~~~text
10K
→ 병목 발견
→ 원인 확인
→ 최소 수정
→ 동일 10K 조건 재측정

필요할 때만
→ 100K
~~~

이렇게 해야 데이터 규모를 늘리는 작업 자체가 목표가 되지 않는다.

## 고정 seed는 왜 필요한가

합성 데이터(Synthetic Data)를 만들 때 난수를 사용하면 실행할 때마다 데이터 모양이 달라질 수 있다.

seed는 난수 생성 과정의 시작값이다.

같은 생성 로직과 같은 seed를 사용하면 같은 데이터 구성을 다시 만들기 쉬워진다.

~~~text
같은 생성 코드
+ 같은 seed
+ 같은 목표 건수
→ 같은 결과를 재현할 가능성 확보
~~~

하지만 seed만 같다고 충분한 것은 아니다.

생성 코드가 바뀌면 같은 seed에서도 다른 데이터가 나올 수 있다. 그래서 중요한 실험에서는 어떤 코드 버전으로 어떤 seed를 사용해 어떤 결과를 만들었는지도 같이 기록해야 한다.

## 데이터셋 검증은 건수 확인으로 끝나지 않는다

Commerce 데이터라면 다음과 같은 내용을 확인할 수 있다.

~~~text
Product 총 수
SKU 총 수
Inventory 총 수

Category별 Product 수
Product당 SKU 수 분포
상태값 분포
구독 가능 여부 분포
재고 구간 분포

중복 business key
중복 SKU code
없는 Category 참조
SKU가 하나도 없는 Product
~~~

이렇게 해야 “10,000 row를 넣었다”가 아니라 **의도한 관계와 분포를 가진 10K 데이터셋을 만들었다**고 말할 수 있다.

## SQL로 분포를 직접 확인하기

Category별 Product 수는 다음처럼 확인할 수 있다.

~~~sql
SELECT category_id, COUNT(*) AS product_count
FROM product
GROUP BY category_id
ORDER BY product_count DESC;
~~~

Product별 SKU 수는 다음처럼 볼 수 있다.

~~~sql
SELECT product_id, COUNT(*) AS sku_count
FROM sku
GROUP BY product_id;
~~~

상태값 분포도 집계할 수 있다.

~~~sql
SELECT status, COUNT(*)
FROM sku
GROUP BY status;
~~~

이 쿼리의 목적은 성능을 측정하는 것이 아니라 **실험 데이터가 설계한 모양대로 만들어졌는지 검증하는 것**이다.

## 데이터 분포가 실행 계획을 바꿀 수 있다

데이터베이스 옵티마이저는 어떤 인덱스를 사용할지, 어떤 순서로 Join할지 비용을 추정한다.

데이터 규모와 분포가 바뀌면 이 추정도 달라질 수 있다.

작은 테이블에서는 전체 스캔이 충분히 싸지만 데이터가 커지면 인덱스가 더 유리해질 수 있다. 반대로 조건에 해당하는 row가 너무 많으면 인덱스를 사용하는 것보다 전체 스캔이 나을 수도 있다.

그래서 데이터셋 규모를 바꿀 때는 다음을 같이 본다.

~~~text
EXPLAIN
실제 읽은 row 수
사용 인덱스
Join 순서
정렬
Temporary Table
실제 응답 시간
~~~

“10K에서 느려졌다”는 것은 출발점이다. 10K가 되면서 어떤 실행 계획과 읽기 범위가 달라졌는지를 확인해야 원인을 설명할 수 있다.

## Cardinality를 추정하는 기술도 있다

아주 큰 데이터에서는 모든 고유값을 정확히 저장해서 세는 비용이 클 수 있다.

HyperLogLog 같은 확률적 자료구조는 적은 메모리로 고유 원소 수를 근사한다.

이 기술이 현재 PawCycle 성능 데이터 생성의 핵심은 아니지만 “Cardinality가 고유한 원소 수라는 뜻으로 사용된다”는 점을 이해하는 데 도움이 된다.

## 실제 운영 데이터와 합성 데이터는 다르다

Production 데이터를 그대로 복사하면 실제 분포를 유지하기 쉽지만 개인정보와 민감정보, 운영 데이터 노출 위험이 있다.

합성 데이터는 안전하게 만들 수 있지만 분포와 관계를 잘못 설계하면 현실성이 떨어진다.

따라서 합성 데이터에서 중요한 것은 실제 사람 이름처럼 보이는 값이 아니라 다음 특성이다.

~~~text
관계 수
분포
쏠림
시간 범위
null 비율
고유값 수
조회 조건별 결과 크기
~~~

실제 운영 데이터를 복제하지 않아도 이 특성을 의도적으로 재현하면 특정 성능 가설을 검증할 수 있다.

## 좋은 대규모 데이터 기록은 무엇을 남겨야 하는가

“10K 데이터 생성 완료” 한 줄로 끝내면 나중에 그 데이터가 무엇을 검증하려고 만든 것인지 알기 어렵다.

최소한 다음 흐름이 설명되어야 한다.

~~~text
왜 이 규모가 필요한가
→ 어떤 테이블을 키웠는가
→ 관계는 어떻게 유지했는가
→ 어떤 값 분포를 만들었는가
→ 어떤 쏠림을 넣거나 넣지 않았는가
→ seed와 생성 코드 버전은 무엇인가
→ 어떻게 데이터 모양을 검증했는가
→ 어떤 성능 질문에 사용할 수 있는가
→ 무엇은 재현하지 못했는가
~~~

Product/SKU/Inventory만 키운 데이터셋을 Review, Rating, Image, Facet까지 실제 Commerce 분포를 재현했다고 표현하면 안 된다.

데이터셋이 **무엇을 재현하는지와 무엇을 재현하지 않는지**를 같이 적어야 한다.

## 핵심 정리

대규모 데이터는 “몇 건인가”만으로 설명할 수 없다.

데이터 양은 전체 크기를 말하고, 관계는 row가 어떻게 연결되는지를 말한다. 고유값 수는 한 컬럼에 서로 다른 값이 얼마나 존재하는지 보여 주고, 분포는 그 값들이 어떤 비율로 나타나는지를 설명한다. 쏠림은 일부 값이나 일부 관계에 데이터가 집중되는 현상이다.

성능 실험에서는 이 요소를 의도적으로 설계하고 검증해야 한다.

**데이터 규모는 포트폴리오용 숫자가 아니라 쿼리, 인덱스, Join, 캐시와 동시성 병목을 재현하기 위한 실험 변수**로 사용해야 한다.
