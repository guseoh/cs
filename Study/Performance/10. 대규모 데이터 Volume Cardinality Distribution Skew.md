# 대규모 데이터 Volume Cardinality Distribution Skew

## Row 수만 늘리는 것은 실제 데이터 모델이 아니다

“100만 건 데이터”라고 할 때 먼저 물어야 한다.

~~~text
어느 테이블에?
어떤 관계로?
어떤 값 분포로?
어떤 Query를 검증하려고?
~~~

모든 테이블에 100만 row를 똑같이 넣는 것은 실제 Commerce workload를 잘 표현하지 못할 수 있다.

대량 데이터는 다음 축으로 본다.

~~~text
Volume
Relation
Cardinality
Distribution
Skew
~~~

## Volume

총 데이터량이다.

하지만 DB 비용은 row 수에만 비례하지 않는다.

- index 크기
- buffer pool
- selected rows
- join
- sort/temp table

가 같이 변한다.

## Relation

Commerce 데이터는 연결된다.

~~~text
Category
→ Product
→ SKU
→ Inventory

Customer
→ Order
→ OrderItem

Customer
→ Subscription
→ Plan
~~~

Query가 relation을 따라가므로 fan-out도 데이터 규모의 일부다.

## Cardinality

column 값의 고유도다.

~~~text
boolean status
→ 낮은 cardinality

order_id
→ 높은 cardinality
~~~

Index 선택도는 cardinality와 실제 분포에 영향을 받는다.

## Distribution

균등 분포:

~~~text
brand A 10%
brand B 10%
...
~~~

와 skewed distribution:

~~~text
brand A 70%
나머지 30%
~~~

는 같은 row 수여도 Query 결과와 index 효율이 다를 수 있다.

## Skew

실제 서비스에는 hot data가 생긴다.

- 인기 상품 주문 집중
- 일부 customer의 많은 주문
- 특정 category SKU 집중
- 최신 기간 조회 집중

Skew는 lock contention, cache hot key, index access pattern을 바꾼다.

## 데이터 규모와 요청 부하는 분리한다

~~~text
Dataset
1K → 10K → 100K → 1M

Load
10 → 50 → 100 → 200 RPS
~~~

두 축을 동시에 올리면 원인을 분리하기 어렵다.

같은 RPS에서 dataset을 바꾸면 Query/JPA/Index 영향이 더 잘 보이고, 같은 dataset에서 RPS를 올리면 concurrency/connection/thread capacity 영향이 더 잘 보인다.

## 단계적으로 키운다

1M을 만드는 것이 목표가 아니다.

~~~text
10K에서 병목 발견
→ 먼저 원인 분석
→ 수정
→ 필요하면 100K
~~~

처럼 실제 한계가 드러날 때 다음 규모로 간다.

## Scale Dataset 검증

count만 확인하지 않는다.

- table row count
- FK relation
- null ratio
- distinct count
- 주요 값 frequency
- fan-out max/min
- time distribution
- hot value distribution

예:

~~~sql
SELECT brand_id, COUNT(*)
FROM product
GROUP BY brand_id
ORDER BY COUNT(*) DESC;
~~~

로 실제 skew가 설계대로 생성됐는지 확인할 수 있다.

## Query Plan과 연결

데이터 규모와 분포가 바뀌면 optimizer가 다른 plan을 선택할 수 있다.

같이 볼 것:

- EXPLAIN
- examined rows
- index
- join order
- sort/temp
- actual latency

## 정리

대규모 데이터는 포트폴리오 숫자가 아니라 **병목을 재현하기 위한 실험 변수**다. Volume만이 아니라 Relation, Cardinality, Distribution, Skew를 같이 설계해야 한다.
