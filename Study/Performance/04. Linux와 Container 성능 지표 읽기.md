# Linux와 Container 성능 지표 읽기

JVM은 Linux process이고 container는 cgroup 위에서 동작한다. Java 코드만 보면 host와 container 경계에서 발생하는 병목을 놓칠 수 있다.

## CPU

vmstat에서 자주 보는 값:

- us: user space CPU
- sy: kernel space CPU
- id: idle
- wa: I/O wait

user가 높으면 Application 계산, serialization, GC worker 등 user-space 작업을 의심할 수 있다.

system이 높으면 syscall, networking, filesystem, context switch 같은 kernel 작업이 커졌을 수 있다.

iowait가 높으면 storage I/O completion을 기다리는 시간이 커졌을 수 있다. 하지만 wa 하나만 보고 disk 병목으로 확정하지 않고 실제 device/query/application 흐름을 같이 본다.

## Load Average

load average는 CPU 사용률이 아니다.

실행 가능한 task와 uninterruptible 상태의 task가 영향을 준다. 따라서 2 CPU host에서 load가 높으면 CPU us/sy/id/wa와 함께 봐야 한다.

## Memory

Linux는 남는 memory를 page cache로 사용한다. free가 작다고 바로 부족한 것이 아니다.

일반적인 여유 판단에는 MemAvailable이 더 유용하다.

~~~text
total
used
free
buff/cache
available
~~~

을 같이 본다.

## Swap

swap used가 존재해도 현재 pressure가 있다는 뜻은 아니다.

현재 window에서는 vmstat의:

- si: swap in
- so: swap out

을 본다.

~~~text
Swap used 500 MiB
si=0
so=0
→ 현재 측정 구간에는 swap activity 없음
~~~

지속적인 si/so와 latency 증가가 같이 나타나면 memory pressure 가능성이 커진다.

## Host와 Container Memory는 다르다

Host에 4 GiB가 남아 있어도 Backend container limit이 640 MiB라면 container 경계를 넘을 때 OOMKilled될 수 있다.

~~~text
Host memory 충분
≠ Container memory 충분
~~~

LINE messaging-hub OOM 사례는 container 상한과 JVM heap 비율을 분리해서 봐야 하는 이유를 잘 보여 준다.

- [LINE — messaging-hub 트러블 슈팅](https://engineering.linecorp.com/ko/blog/messaing-hub-troubleshooting/)

## Restart와 OOM

자동 restart가 있으면 외부 health는 금방 정상처럼 보일 수 있다.

성능 window에서 같이 기록하면 좋은 값:

- container ID
- StartedAt
- RestartCount
- OOMKilled

restart가 발생하면 그 전후 metric을 하나의 steady process로 보면 안 된다.

## Network와 File Descriptor

많은 connection은 socket과 file descriptor를 사용한다.

확인 후보:

- open file limit
- socket state
- TIME_WAIT
- local port
- retransmission
- NIC error/drop

LINE messaging-hub 사례는 websocket drop을 조사하며 port range, TIME_WAIT, open files, Nginx connection limit을 실제 수치로 하나씩 배제한다.

- [LINE — messaging-hub 트러블 슈팅](https://engineering.linecorp.com/ko/blog/messaing-hub-troubleshooting/)

## Snapshot과 Time-series

docker stats --no-stream은 한 시점의 snapshot이다.

장점:

- 빠른 현재 상태
- container limit 확인

한계:

- spike를 놓침
- 평균/최대 추세를 모름

긴 load test에서는 Prometheus 같은 time-series가 필요하고 짧은 calibration에서는 snapshot과 vmstat interval sampling을 같이 쓸 수 있다.

## 최소 읽기 순서

~~~text
CPU
→ us / sy / id / wa

Memory
→ MemAvailable / si / so

Container
→ usage / limit / restart / OOM

Disk
→ available / I/O

Network
→ error / drop / socket

마지막으로
→ Application latency/error와 같은 시간축으로 연결
~~~


## Linux 지표를 보는 이유

Spring Boot 애플리케이션은 JVM 위에서 실행되지만 JVM 자체는 Linux Process다.

Container를 사용해도 CPU와 memory를 실제로 배분하고 제한하는 것은 Linux Kernel과 cgroup이다.

그래서 애플리케이션이 느릴 때 Java 코드만 보면 다음 문제를 놓칠 수 있다.

~~~text
Container memory limit
Host memory pressure
Swap
Disk I/O
Network packet drop
File Descriptor 부족
Kernel CPU 사용 증가
~~~

## CPU 사용률의 us, sy, id, wa는 무엇인가

vmstat이나 일부 Linux 도구에서는 CPU 시간을 여러 구간으로 나눠 보여 준다.

### us — 사용자 영역 CPU

us는 user space에서 실행한 작업에 사용한 CPU 시간 비율이다.

Java 애플리케이션 코드, JIT으로 컴파일된 코드, GC worker 같은 작업은 주로 이 영역에서 CPU를 사용한다.

us가 높다면 애플리케이션 계산량이 많거나 GC 작업이 증가했을 가능성을 생각할 수 있다.

하지만 us가 높다고 곧바로 “Java 코드가 비효율적”이라고 단정하면 안 된다. 실제로는 정상적으로 많은 요청을 처리하면서 CPU를 많이 사용하는 것일 수도 있다.

### sy — 커널 영역 CPU

sy는 system 또는 kernel space에서 사용한 CPU 시간이다.

네트워크 처리, 파일 시스템, system call, context switch 같은 작업이 영향을 줄 수 있다.

sy가 비정상적으로 증가한다면 다음 후보를 볼 수 있다.

~~~text
네트워크 packet 처리 증가
system call 증가
많은 context switch
파일 I/O 증가
socket 작업 증가
~~~

### id — 쉬고 있는 CPU

id는 idle, 즉 CPU가 일을 하지 않고 있던 비율이다.

CPU 사용률이 30%라면 대략 70%의 idle이 남을 수 있다.

물론 여러 CPU core를 가진 시스템에서는 도구의 집계 방식을 확인해야 한다.

### wa — I/O 완료를 기다리는 시간

wa는 I/O wait를 뜻한다.

CPU가 직접 계산을 하지는 않지만 block I/O가 끝나기를 기다리는 시간이 늘면 wa가 증가할 수 있다.

wa가 높다고 곧바로 “Disk가 병목”이라고 단정하면 안 된다.

DB가 느린 이유가 원격 storage인지, 특정 query가 많은 page를 읽는지, Host 자체의 filesystem이 느린지 추가 확인이 필요하다.

## Load Average는 CPU 사용률과 다르다

Load Average를 CPU 사용률로 오해하기 쉽다.

Load Average는 단순히 “CPU를 몇 퍼센트 썼는가”가 아니라 **실행할 준비가 되어 있거나 특정 I/O 때문에 끊을 수 없는 상태의 작업이 얼마나 쌓여 있는가**와 관련된 값이다.

예를 들어 2 vCPU 서버에서 Load Average가 8이라고 해서 곧바로 CPU 사용률 400%라는 식으로 읽으면 안 된다.

다음과 같이 같이 본다.

~~~text
Load Average 증가

CPU us/sy도 높음
→ CPU 경쟁 가능성 강화

CPU는 여유
wa 높음
→ I/O 대기 가능성 확인

CPU도 여유, wa도 낮음
→ 다른 원인 추가 조사
~~~

## free memory가 작아도 바로 메모리 부족은 아니다

Linux는 사용하지 않는 memory를 page cache 등으로 활용한다.

그래서 free가 작다는 사실만으로 memory pressure라고 판단하면 안 된다.

MemAvailable은 현재 실행 중인 workload를 크게 방해하지 않고 새 Process나 추가 할당에 사용할 수 있을 것으로 추정되는 memory를 보여 주기 때문에 실무에서 더 유용하게 본다.

~~~text
MemFree
→ 지금 완전히 비어 있는 memory

MemAvailable
→ cache 회수 등을 고려한 실제 사용 가능 여유 추정
~~~

## RSS는 무엇인가

RSS(Resident Set Size)는 Process가 현재 실제 물리 memory에 올려 사용하고 있는 page의 양을 표현할 때 쓰는 지표다.

Java Process의 RSS에는 Heap만 들어가는 것이 아니다.

~~~text
Heap
Metaspace
Code Cache
Thread Stack
Direct Buffer
Native library
mmap 영역
기타 Native allocation
~~~

이 때문에 Heap이 400 MiB인데 Container memory usage가 600 MiB가 될 수 있다.

Heap과 Process/Container memory를 같은 값으로 보면 안 된다.

## Swap은 무엇이고 왜 si/so를 보는가

Swap은 RAM이 아닌 storage 공간 일부를 memory 보조 공간처럼 사용하는 방식이다.

Swap이 사용 중이라는 사실만으로 현재 문제가 있다는 뜻은 아니다.

과거에 한 번 swap-out된 page가 그대로 남아 있을 수도 있다.

현재 pressure를 보려면 vmstat의 si와 so를 같이 본다.

~~~text
si
→ swap 영역에서 RAM으로 다시 읽어오는 양

so
→ RAM의 page를 swap으로 내보내는 양
~~~

지속적인 si/so가 발생하고 동시에 응답 시간과 I/O wait가 악화된다면 memory pressure 가설이 강해진다.

## Host memory와 Container memory limit은 별개다

Host에 4 GiB 여유가 있어도 Backend Container limit이 640 MiB라면 Container는 640 MiB 경계 안에서 살아야 한다.

~~~text
Host
8 GiB 중 4 GiB 여유

Backend Container
limit 640 MiB
usage 640 MiB 접근

→ Host는 여유가 있어도
→ Container OOM 가능
~~~

그래서 성능 분석에서는 Host memory와 Container usage/limit을 따로 기록한다.

LINE의 messaging-hub 장애 대응 사례도 JVM Heap과 Container memory 사이의 Native 영역을 함께 고려해야 하는 이유를 보여 준다.

- [LINE — messaging-hub 트러블 슈팅](https://engineering.linecorp.com/ko/blog/messaing-hub-troubleshooting/)

## OOMKilled는 무엇인가

Container가 memory 제한을 넘거나 Kernel이 메모리 부족 상황에서 Process를 종료하면 Docker 상태에 OOMKilled가 남을 수 있다.

이 값은 매우 강한 실패 근거다.

예를 들어 부하 테스트 중 다음이 나타났다면:

~~~text
p99 급증
→ Backend 응답 오류
→ OOMKilled=true
→ RestartCount 증가
~~~

단순 latency 문제보다 Process가 실제로 죽고 재시작한 사건을 먼저 봐야 한다.

자동 재시작 정책이 있으면 잠시 뒤 health check가 다시 정상으로 보일 수 있으므로 성능 window의 RestartCount와 OOMKilled를 반드시 확인하는 것이 좋다.

## File Descriptor는 무엇인가

Linux에서는 file뿐 아니라 socket도 file descriptor라는 번호로 관리한다.

많은 HTTP/WebSocket Connection을 유지하면 file descriptor를 많이 사용한다.

한 Process가 열 수 있는 descriptor 한도에 접근하면 새 socket이나 file을 열지 못할 수 있다.

그래서 장기 Connection workload에서는 다음을 같이 볼 수 있다.

~~~text
open file limit
현재 열린 descriptor 수
socket state
TIME_WAIT
local port 범위
Network error/drop
~~~

## TIME_WAIT는 무엇인가

TCP Connection을 닫은 뒤 일정 시간 동안 연결 정보를 유지하는 상태가 TIME_WAIT다.

짧은 Connection을 매우 많이 만들고 닫으면 TIME_WAIT가 많이 쌓일 수 있다.

그 자체로 장애는 아니지만 local port 고갈, 연결 생성 방식, Connection 재사용 여부를 조사할 때 중요한 단서가 된다.

LINE messaging-hub 사례는 port range, TIME_WAIT, open file 수, Nginx Connection limit을 실제 수치로 확인하며 후보를 제거한다.

## Snapshot과 시계열의 차이

docker stats --no-stream 같은 명령은 현재 순간의 상태를 빠르게 볼 수 있다.

하지만 1초 전에 발생한 CPU spike나 10초 동안의 memory 증가를 놓칠 수 있다.

~~~text
Snapshot
→ 지금 이 순간

Time Series
→ 시간에 따른 변화
~~~

짧은 상태 확인에는 snapshot이 편하지만 부하 테스트에서는 Prometheus 같은 시계열 수집과 interval sampling을 함께 사용하는 것이 좋다.

## Linux 지표를 읽을 때 순서

다음 순서를 기계적으로 외울 필요는 없지만 문제 범위를 빠르게 줄이는 데 도움이 된다.

~~~text
1. Restart / OOM 확인
2. CPU us/sy/id/wa
3. MemAvailable
4. Swap si/so
5. Container usage/limit
6. Disk / Network
7. File Descriptor / socket
8. 사용자 응답 시간과 같은 시간축으로 연결
~~~

핵심은 숫자를 단독으로 읽지 않는 것이다.

~~~text
wa 높음
≠ Disk 병목 확정

free 낮음
≠ Memory 부족 확정

Load Average 높음
≠ CPU 100% 확정

Host 여유
≠ Container 여유
~~~
