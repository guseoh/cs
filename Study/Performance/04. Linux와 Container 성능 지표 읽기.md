# Linux와 Container 성능 지표 읽기

Spring Boot 애플리케이션은 JVM 위에서 실행되지만 JVM 자체는 Linux Process다. Docker Container 안에서 실행하더라도 CPU 시간을 배분하고 Memory를 제한하며 Socket과 File Descriptor를 관리하는 것은 결국 운영체제다.

그래서 Java 코드만 보고는 설명할 수 없는 성능 문제가 생긴다.

예를 들어 Heap은 50%밖에 사용하지 않는데 Container가 OOM으로 종료될 수 있다. CPU 사용률은 낮은데 I/O wait 때문에 요청이 오래 걸릴 수 있다. Host Memory는 여유가 있지만 Container Memory Limit이 작아서 Process가 죽을 수도 있다.

Linux와 Container 지표를 보는 목적은 “운영체제 명령어를 많이 아는 것”이 아니다. **애플리케이션이 실제로 어떤 물리 자원에서 막히는지 확인하는 것**이다.

LINE의 성능 테스트 자동화 사례에서도 CPU, Memory, Load, Swap, Disk I/O, File Descriptor 같은 시스템 지표를 JVM 지표와 함께 수집한다. JVM 내부만 봐서는 Host와 Container 경계에서 생기는 문제를 놓칠 수 있기 때문이다.

## CPU 사용률은 하나의 숫자가 아니다

CPU 80%라는 값만 보고서는 어떤 종류의 작업이 CPU 시간을 사용했는지 알기 어렵다.

Linux 도구는 CPU 시간을 여러 범주로 나눠 보여 줄 수 있다.

대표적으로 vmstat에서는 user, system, idle, wait 계열을 볼 수 있다.

~~~text
us
→ 사용자 영역에서 사용한 CPU 시간

sy
→ Kernel 영역에서 사용한 CPU 시간

id
→ CPU가 쉬고 있던 시간

wa
→ I/O 완료를 기다리는 시간
~~~

이 값을 각각 어떤 의미로 읽는지 알아야 한다.

## us는 사용자 영역에서 사용한 CPU 시간이다

us는 user space에서 실행한 작업이 사용한 CPU 시간 비율이다.

Java 애플리케이션 코드, JIT으로 컴파일된 코드, GC Worker 같은 작업은 주로 이 영역에서 CPU를 사용한다.

예를 들어 부하가 증가하면서 다음처럼 변할 수 있다.

~~~text
25 RPS
us = 5%

100 RPS
us = 25%

200 RPS
us = 70%
~~~

이 패턴만 보면 요청 증가에 따라 Application 계산량도 늘어난 것으로 볼 수 있다.

하지만 us가 높다고 바로 “Java 코드가 비효율적이다”라고 결론내리면 안 된다.

200 RPS를 정상적으로 처리하기 위해 CPU를 70% 사용하는 것이라면 오히려 자연스러운 결과일 수 있다.

중요한 것은 실제 처리량이 유지되는지, 응답 시간과 오류율이 어떻게 변하는지, CPU 여유가 얼마나 남았는지를 같이 보는 것이다.

## sy는 Kernel 영역에서 사용한 CPU 시간이다

sy는 system 또는 kernel space에서 사용한 CPU 시간이다.

Application이 Socket을 열고 닫거나 파일을 읽고 쓰고, Network Packet을 처리하고, Context Switch가 발생할 때 Kernel 작업이 늘 수 있다.

sy가 평소보다 크게 증가하면 다음 후보를 생각할 수 있다.

~~~text
Socket 생성/종료 증가
Network Packet 처리 증가
System Call 증가
Context Switch 증가
파일 I/O 증가
Container / cgroup 관련 Kernel 작업 증가
~~~

예를 들어 HTTP Keep-Alive 없이 아주 짧은 Connection을 대량으로 만들고 끊는 구조라면 Application 계산 자체보다 Network와 Kernel 작업이 많이 늘 수 있다.

따라서 sy 상승은 “CPU 병목”이라는 한 문장보다 **왜 Kernel 작업량이 늘었는가**로 이어서 봐야 한다.

## id는 CPU의 남은 여유를 보여 준다

id는 idle, 즉 CPU가 사용되지 않고 있던 시간 비율이다.

예를 들어:

~~~text
us = 30
sy = 10
id = 60
~~~

이라면 대략 60% 정도의 CPU 시간이 쉬고 있었다고 볼 수 있다.

성능 테스트에서 id가 거의 0에 가까워지고 us와 sy가 계속 높은 상태라면 CPU 포화 가능성이 강해진다.

하지만 Multi-core 시스템에서는 CPU 전체 집계 방식과 도구 표현을 확인해야 한다. Docker나 cgroup limit으로 사용할 수 있는 CPU가 Host 전체보다 적을 수도 있다.

## wa는 I/O 대기와 관련 있지만 Disk 병목을 확정하지 않는다

wa는 I/O wait다.

CPU가 직접 계산하지 못하고 Block I/O 완료를 기다리는 시간이 늘면 wa가 높아질 수 있다.

예를 들어:

~~~text
us = 20
sy = 5
wa = 40
id = 35
~~~

라면 CPU 계산 자체보다 I/O 대기 가능성을 더 조사할 근거가 생긴다.

하지만 wa가 높다고 “Disk가 느리다”라고 바로 결론내리면 안 된다.

어떤 Process가 어떤 I/O를 기다리는지, Disk latency와 queue가 실제로 증가했는지, DB Query가 많은 Page를 읽고 있는지 추가로 확인해야 한다.

## CPU 100%가 아니어도 특정 Core는 포화될 수 있다

전체 CPU 사용률이 50%라고 해도 Thread가 특정 Core에 몰리거나 Single-threaded 작업 하나가 Core 하나를 100% 사용할 수 있다.

예를 들어 2 vCPU에서 Thread 하나가 CPU Core 하나를 완전히 사용하고 다른 Core는 거의 쉬고 있다면 전체 평균은 약 50%처럼 보일 수 있다.

따라서 특정 작업이 Single-threaded인지, Process/Thread 단위 CPU가 어떤지 필요하면 더 세밀하게 본다.

## Load Average는 CPU 사용률이 아니다

Load Average를 CPU 사용률처럼 읽으면 안 된다.

Linux의 Load Average는 일정 시간 동안 **CPU에서 실행 중이거나 실행할 준비가 되었고, 일부 끊을 수 없는 I/O 대기 상태에 있는 작업의 평균적인 수**와 관련된 값이다.

예를 들어 2 vCPU 서버에서 Load Average가 8이라고 하자.

이 값이 CPU 사용률 800%라는 뜻은 아니다.

다음과 같이 같이 본다.

~~~text
Load Average 증가
+
us/sy 매우 높음
+
id 거의 0
→ CPU 경쟁 가능성 강화
~~~

반대로:

~~~text
Load Average 증가
CPU는 여유
wa 높음
→ I/O 대기 가능성 확인
~~~

또한 1분, 5분, 15분 Load Average는 서로 다른 시간 창의 평균을 보여 준다.

짧은 Spike와 장기적인 과부하를 구분하는 데 사용할 수 있다.

## Run Queue는 실행을 기다리는 작업 수를 더 직접적으로 보여 준다

CPU를 사용하고 싶은 Runnable Task가 Core 수보다 많이 쌓이면 일부 작업은 CPU를 바로 받지 못하고 기다린다.

vmstat의 r 값은 Run Queue를 볼 때 참고할 수 있다.

예를 들어 2 vCPU 환경에서 r 값이 지속적으로 10 이상이라면 CPU를 사용하려는 작업이 Core보다 훨씬 많다는 신호일 수 있다.

하지만 한 번의 Snapshot보다 부하 구간에서 지속적으로 높은지 봐야 한다.

## Memory는 free 하나만 보면 안 된다

Linux는 비어 있는 Memory를 Page Cache 등으로 적극 활용한다.

그래서 free Memory가 작아도 실제로는 회수 가능한 Cache가 많을 수 있다.

~~~text
MemFree
→ 지금 완전히 사용되지 않는 Memory

MemAvailable
→ Cache 회수 등을 고려했을 때
   새 작업에 사용할 수 있을 것으로 추정되는 여유
~~~

성능 분석에서는 MemAvailable을 함께 보는 것이 유용하다.

예를 들어 free가 100MiB밖에 없어도 MemAvailable이 2GiB라면 즉시 Memory 부족이라고 보기는 어렵다.

반대로 MemAvailable이 계속 낮아지고 Swap 활동과 OOM이 나타난다면 실제 Memory Pressure 가능성이 강해진다.

## Page Cache는 왜 Memory를 사용해도 문제라고 볼 수 없는가

Linux는 Disk에서 읽은 데이터를 Memory에 Cache해 다음 접근을 빠르게 할 수 있다.

이 Page Cache도 사용 중인 Memory로 보인다.

그래서 “사용 Memory가 90%”라는 숫자만으로 위험하다고 판단하지 않는다.

필요하면 Kernel이 Cache 일부를 회수해서 Application에 줄 수 있기 때문이다.

중요한 것은 회수 가능한 Memory를 고려한 Available, Swap Activity, OOM, Reclaim Pressure 같은 신호를 함께 보는 것이다.

## RSS는 Process가 실제 물리 Memory에 올려 둔 양을 보여 준다

RSS(Resident Set Size)는 Process의 Page 중 현재 실제 RAM에 올라가 있는 양을 표현할 때 사용한다.

Java Process의 RSS에는 Heap만 들어가는 것이 아니다.

~~~text
Java Heap
Metaspace
Code Cache
Thread Stack
Direct Buffer
Native Library
mmap 영역
기타 Native Allocation
~~~

그래서:

~~~text
Heap used = 400MiB
RSS = 650MiB
~~~

같은 상황은 충분히 가능하다.

Heap 그래프만 보고 “Memory는 400MiB만 사용한다”고 생각하면 Container Limit을 잘못 계산할 수 있다.

JVM의 Native Memory는 [[05. JVM GC Thread Native Memory 성능]]에서 자세히 다룬다.

## Swap은 RAM이 부족할 때만 생기는 비상 공간이라고 단순화하면 안 된다

Swap은 Disk 또는 Storage 일부를 Memory 보조 공간처럼 사용하는 기능이다.

시스템이 과거에 사용하지 않던 Page를 Swap으로 내보냈다가 현재는 충분한 RAM이 남아 있을 수도 있다.

따라서 Swap 사용량이 500MiB라는 사실만으로 지금 Memory Pressure라고 판단하면 안 된다.

현재 활발하게 Swap을 읽고 쓰는지를 같이 본다.

vmstat에서는 다음 값이 도움이 된다.

~~~text
si
→ Swap 영역에서 RAM으로 다시 가져오는 양

so
→ RAM Page를 Swap 영역으로 내보내는 양
~~~

부하 구간에서 si/so가 지속적으로 발생하고 p95와 I/O wait가 같이 증가한다면 Memory Pressure 가설이 강해질 수 있다.

## Host Memory와 Container Memory Limit은 완전히 다른 경계다

Docker Container에는 cgroup을 이용해 Memory Limit을 설정할 수 있다.

Host에 Memory가 많이 남아 있어도 Container Limit이 작으면 Container는 그 범위를 넘을 수 없다.

~~~text
Host
8GiB
Available 4GiB

Backend Container
Memory Limit 640MiB
Usage 630MiB
~~~

이 경우 Host는 여유가 있지만 Backend Container는 OOM에 가까울 수 있다.

그래서 성능 분석에서는 다음을 따로 기록한다.

~~~text
Host MemAvailable
Container usage
Container limit
Container OOMKilled
Container restart
~~~

LINE의 messaging-hub 사례에서는 Kubernetes Container 환경에서 OOM이 발생한 뒤 JVM Heap만이 아니라 Container Memory와 JVM 설정을 함께 보며 문제를 해결한다.

관련 자료:
- [LINE — messaging-hub 트러블 슈팅](https://engineering.linecorp.com/ko/blog/messaing-hub-troubleshooting/)

## cgroup은 Container가 사용할 자원을 제한한다

Docker Container는 Process를 완전히 별도 물리 서버에 옮기는 것이 아니다.

Linux cgroup을 통해 CPU와 Memory 같은 자원의 사용량과 제한을 관리한다.

예를 들어 Host가 4 vCPU를 가지고 있어도 Container CPU Limit이 1 CPU라면 Application이 사용할 수 있는 CPU 처리량은 더 작다.

따라서 다음 두 실험은 같은 Host에서도 다른 결과를 낼 수 있다.

~~~text
Container CPU Limit = 1
vs
Container CPU Limit = 2
~~~

성능 결과를 재현하려면 Container Limit도 실험 조건에 포함해야 한다.

## OOMKilled는 단순 응답 지연보다 강한 실패 신호다

Container가 Memory Limit을 넘고 Kernel 또는 Container Runtime에 의해 종료되면 OOMKilled 상태를 확인할 수 있다.

예를 들어:

~~~text
p99 급증
HTTP error 증가
OOMKilled = true
RestartCount 증가
~~~

라면 “일부 요청이 느렸다”보다 Process가 실제로 죽었다는 사건을 먼저 조사해야 한다.

자동 재시작 정책이 있으면 몇 초 뒤 Backend가 다시 Healthy로 보일 수 있다.

그래서 현재 Health만 보고 성능 Window에 장애가 없었다고 판단하면 안 된다.

실험 시작 전과 종료 후 RestartCount를 비교하고 OOMKilled를 확인하는 것이 좋다.

## RestartCount는 측정 중 Process가 바뀌었는지 알려 준다

성능 테스트 중 Container가 한 번 재시작하면 전후 요청은 서로 다른 JVM Process가 처리했다.

~~~text
측정 시작
JVM A

중간 OOM
→ JVM A 종료
→ Container Restart

이후
JVM B
~~~

JVM B는 Class Loading, JIT, Connection Pool 초기화 같은 시작 비용을 다시 겪을 수 있다.

따라서 하나의 안정된 120초 측정처럼 해석하면 안 된다.

## File Descriptor는 파일만을 위한 번호가 아니다

Linux에서는 열린 File, Socket, Pipe 같은 자원을 File Descriptor로 다룬다.

웹 서버는 HTTP Connection을 위해 많은 Socket을 열 수 있으므로 File Descriptor 한계와 연결 수가 관계가 있다.

한 Process가 열 수 있는 FD 한도에 접근하면 새 Socket이나 File을 열지 못할 수 있다.

장시간 연결이나 WebSocket workload에서는 다음을 볼 수 있다.

~~~text
ulimit
현재 Open FD
Socket 수
Connection State
TIME_WAIT
Network error
~~~

LINE messaging-hub 사례도 WebSocket Connection 문제를 조사하면서 열린 File 수, Port 범위, TIME_WAIT 등을 확인한다.

## TIME_WAIT는 TCP Connection 종료 후 남는 상태다

TCP Connection을 정상적으로 닫은 뒤에도 일정 시간 Connection 정보를 유지하는 상태가 TIME_WAIT다.

짧은 HTTP Connection을 매우 많이 만들고 닫으면 TIME_WAIT가 많이 쌓일 수 있다.

TIME_WAIT가 많다는 사실 자체가 장애는 아니다.

하지만 Connection 재사용이 거의 없고 짧은 Connection을 대량 생성하면 다음 문제가 연결될 수 있다.

~~~text
Local Port 사용 증가
Kernel Socket 관리 비용 증가
Connection 생성 비용 증가
Ephemeral Port 고갈 가능성
~~~

따라서 Reverse Proxy와 Backend 사이 Connection churn을 조사할 때 TIME_WAIT를 확인할 수 있다.

## ESTABLISHED가 많다는 것도 workload에 따라 정상일 수 있다

WebSocket이나 Server-Sent Events처럼 장시간 Connection을 유지하는 서비스는 ESTABLISHED Socket 수가 매우 많을 수 있다.

이 경우 Connection 수 자체보다 다음이 중요하다.

~~~text
예상 Connection 수와 일치하는가
FD Limit 안에 있는가
Memory 사용은 안정적인가
Heartbeat / Idle Timeout이 정상인가
Reconnect Storm이 있는가
~~~

같은 지표라도 서비스 형태에 따라 정상 범위가 다르다.

## Disk I/O는 처리량과 지연을 나눠 본다

Disk 문제를 볼 때 단순 Read/Write Byte 수만 보면 부족하다.

많은 데이터를 순차적으로 빠르게 쓰는 workload와 작은 Random I/O를 매우 많이 수행하는 workload는 특성이 다르다.

다음 요소를 함께 본다.

~~~text
Read / Write Throughput
IOPS
I/O Latency
Queue
Utilization
iowait
~~~

Database가 느릴 때 Disk Throughput이 높지 않아도 Storage Latency가 증가할 수 있다.

또 Remote Storage나 Cloud Managed DB에서는 Application Host의 Disk Metric만으로 DB Storage 상태를 알 수 없다.

DB 자체 Metric을 별도로 봐야 한다.

## Network도 단순 Mbps로 끝나지 않는다

Network 성능은 다음 요소가 모두 영향을 준다.

~~~text
Bandwidth
Latency
Packet Loss
Retransmission
Connection 생성
DNS
TLS Handshake
Proxy
Socket Buffer
~~~

API 응답 Payload가 매우 크면 Bandwidth가 먼저 문제가 될 수 있다.

반대로 작은 요청이 많아도 Connection 생성과 TLS Handshake 비용이 클 수 있다.

따라서 Network Throughput이 낮다는 이유만으로 Network 문제가 없다고 단정하지 않는다.

## Container Network와 Host Network 경로를 구분한다

Docker에서는 요청이 다음처럼 여러 Network 경계를 지나갈 수 있다.

~~~text
Client
→ Host Port
→ Docker bridge
→ Container
~~~

Reverse Proxy가 있다면:

~~~text
Client
→ Nginx
→ Docker Network
→ Backend
~~~

처럼 된다.

Localhost에서 Container에 직접 보내는 부하와 public HTTPS로 보내는 부하는 Network 경로가 다르다.

따라서 응답 시간 절대값도 직접 비교하지 않는다.

## Snapshot은 지금 상태만 보여 준다

docker stats --no-stream 같은 명령은 현재 순간의 CPU와 Memory를 빠르게 볼 수 있다.

하지만 5초 전에 OOM 직전 Memory가 급증했다가 Restart된 상황은 현재 Snapshot에서 사라질 수 있다.

~~~text
Snapshot
→ 지금 이 순간

Time Series
→ 시간에 따라 어떻게 변했는가
~~~

성능 테스트에서는 둘을 같이 사용하는 것이 좋다.

Snapshot은 실행 전후 상태를 빠르게 확인하고, Prometheus 같은 Time Series는 측정 Window 전체의 변화를 본다.

## Linux 지표는 사용자 결과와 같은 시간축으로 읽는다

가상의 예를 보자.

~~~text
250 RPS 시작
→ p95 200ms

30초 후
p95 1.5초
wa 35%
Disk latency 증가
CPU id 50%
~~~

CPU는 아직 50% Idle이지만 I/O wait와 Disk latency가 같이 증가했다.

이 경우 CPU Scale-up보다 Disk/Storage 경로를 먼저 조사할 근거가 생긴다.

다른 예:

~~~text
p95 증가
us 95%
sy 3%
id 2%
wa 0%
GC 정상
DB 정상
~~~

이라면 Application 계산 CPU 포화 가설이 더 강해진다.

이렇게 한 지표만 보는 것이 아니라 **사용자 결과와 자원 상태를 시간순으로 연결하는 것**이 중요하다.

## Container가 정상이어도 Host가 불안정할 수 있다

Backend Container CPU가 40%로 보여도 Host에서 다른 Container나 Prometheus가 CPU를 많이 쓰고 있을 수 있다.

반대로 Host 전체 CPU가 높아도 Backend Container가 제한된 CPU 범위 안에서 안정적으로 동작할 수도 있다.

따라서 같은 Host에 여러 workload가 있으면:

~~~text
Host 전체
+
Backend Container
+
Observability Container
+
Database Container가 있다면 DB Container
~~~

를 분리해서 본다.

관측 도구가 같은 Host에 미치는 영향은 [[08. Observer Effect와 Same-host Calibration]]에서 다룬다.

## Linux 지표는 병목을 확정하는 답이 아니라 다음 질문을 정한다

성능 분석에서 다음과 같은 단정은 피한다.

~~~text
wa 높음
= Disk 병목 확정

free 낮음
= Memory 부족 확정

Load Average 높음
= CPU 100% 확정

TIME_WAIT 많음
= Network 장애 확정
~~~

대신 다음처럼 사용한다.

~~~text
wa 증가
→ 어떤 I/O가 느린지 확인

MemAvailable 감소 + swap activity
→ Memory Pressure 확인

Load 증가 + CPU run queue 증가
→ CPU 경쟁 확인

TIME_WAIT 급증 + connect error
→ Connection churn / port pressure 확인
~~~

지표는 원인의 이름이 아니라 **조사 방향을 좁혀 주는 근거**다.
