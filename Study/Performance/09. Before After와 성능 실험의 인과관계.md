# Before After와 성능 실험의 인과관계

## 빨라졌다는 것과 변경 때문에 빨라졌다는 것은 다르다

~~~text
Before p95 = 200ms
After  p95 = 120ms
~~~

만으로는 변경이 원인이라고 할 수 없다.

다른 조건이 바뀌었을 수 있다.

- request rate
- dataset
- cache
- JVM state
- DB state
- background workload
- network

## 한 번에 작은 변경

가능하면:

~~~text
Baseline
→ Index 하나 추가
→ 동일 조건 재측정
~~~

처럼 변경 변수를 작게 유지한다.

Index + Cache + Pool + JVM option을 한 번에 바꾸면 무엇이 효과를 냈는지 알 수 없다.

## Controlled Variable

Before/After에서 최대한 고정:

- dataset
- query/request
- rate/concurrency
- duration
- host
- container limit
- JVM option
- DB config
- measurement method

완전히 동일하게 만들 수 없다면 차이를 기록한다.

## 반복 측정

시스템에는 noise가 있다.

~~~text
Before
31 / 34 / 32ms

After
30 / 31 / 32ms
~~~

이면 효과가 run-to-run variation 안일 수 있다.

반면:

~~~text
Before
310 / 295 / 320ms

After
42 / 40 / 44ms
~~~

이면 훨씬 강한 evidence다.

카카오 메시징 성능 테스트 글도 같은 부하 포인트에서 반복해 결과를 분석하는 작업의 중요성을 보여 준다.

- [카카오 — 메시징 서버의 스트레스 테스트 노하우](https://tech.kakao.com/posts/822)

## Correlation과 Causation

CPU와 latency가 같이 증가했다고 CPU가 원인이라고 확정할 수 없다.

~~~text
원인 A
→ CPU 증가
→ latency 증가
~~~

일 수도 있고:

~~~text
원인 B
→ queue 증가
→ latency 증가
→ backlog 처리로 CPU 증가
~~~

일 수도 있다.

문제 재현 후 하나의 intervention을 하고 같은 조건으로 다시 측정하면 인과 주장이 강해진다.

## 실패한 가설도 결과다

~~~text
가설: DB가 병목

DB CPU 낮음
DB latency 낮음
I/O 낮음
Application OOM 확인

→ DB scale-up 보류
~~~

틀린 가설을 버린 것은 기술을 추가하지 않은 중요한 결정이다.

NAVER D2도 GC option을 다른 서비스에서 그대로 복사하기보다 실제 workload에서 비교해 적용하라고 강조한다.

- [NAVER D2 — Garbage Collection 튜닝](https://d2.naver.com/helloworld/37111)

## Trade-off

| 개선 | 대표 대가 |
| --- | --- |
| Cache | consistency, invalidation |
| Pool 증가 | DB concurrency |
| Thread 증가 | native memory, context switch |
| Replica | lag, routing |
| Async | eventual consistency |
| Queue | 운영 복잡도 |
| Scale-out | 비용, 분산 상태 |

최종 기록:

~~~text
효과
+ 비용
+ 복잡도
+ failure mode
+ 남은 한계
~~~

까지 포함한다.

## KEEP / DEFER / REJECT

- KEEP: 현재 문제에 효과가 있고 대가를 감당 가능
- DEFER: 필요 가능성은 있지만 현재 근거로 비용이 더 큼
- REJECT: 현재 문제와 맞지 않거나 효과 근거 없음
