# Before/After와 성능 실험의 인과관계

성능 개선에서 가장 위험한 착시는 “변경 후 숫자가 좋아졌으니 내가 바꾼 코드 때문에 좋아졌다”고 바로 결론내리는 것이다.

실제 시스템에서는 동시에 많은 변수가 움직인다.

~~~text
요청량
Dataset
Cache 상태
JVM JIT 상태
Heap / GC 상태
DB Buffer 상태
Network
Background Job
Host 부하
다른 Container
관측 도구
~~~

그래서 변경 전과 변경 후 숫자가 다르다는 사실과 **그 차이를 내가 적용한 변경이 만들었다는 주장**은 분리해야 한다.

성능 실험의 핵심은 새로운 기술을 넣는 것이 아니라, 결과 차이를 특정 원인과 연결할 수 있도록 다른 조건을 최대한 통제하는 것이다.

## 먼저 가설을 문장으로 만든다

성능 실험을 시작하기 전에 “무엇을 바꾸면 무엇이 왜 달라질 것인가”를 문장으로 적는 것이 좋다.

예를 들어 다음은 너무 넓다.

~~~text
성능이 안 좋다.
인덱스를 추가해 본다.
~~~

조금 더 구체적으로 바꾸면 다음과 같다.

~~~text
Product 10K에서
GET /api/products의 특정 조건 조회가 느리다.

실행 계획에서 많은 row를 읽고 있다.

가설:
현재 조건을 지원하는 인덱스가 없어
읽는 row 수가 커지고
이 때문에 p95가 증가한다.

예상:
필요한 인덱스 1개를 추가하면
Rows Examined가 줄고
같은 100 RPS에서 p95가 낮아질 것이다.
~~~

이렇게 적으면 변경 전 어떤 근거를 확인해야 하는지, 변경 후 무엇이 달라져야 가설을 지지할 수 있는지가 분명해진다.

## 독립 변수와 종속 변수를 구분한다

실험에서 의도적으로 바꾸는 요소를 독립 변수라고 부른다.

결과로 관찰하려는 값을 종속 변수라고 부른다.

예를 들어 인덱스 효과를 보는 실험에서는:

~~~text
독립 변수
→ Index 없음 / 있음

종속 변수
→ p95
→ actual RPS
→ Rows Examined
→ DB CPU
~~~

처럼 볼 수 있다.

이 구분이 필요한 이유는 실험 중 무엇을 의도적으로 바꾸고 무엇을 결과로 읽어야 하는지 명확해지기 때문이다.

## 통제 변수는 같게 유지하려는 조건이다

통제 변수(Controlled Variable)는 비교 전후에 최대한 같게 유지하는 조건이다.

인덱스 실험이라면 다음을 고정한다.

~~~text
Dataset
Query
Request Parameter
RPS
Warm-up
Measurement 시간
Backend 수
Container limit
JVM Option
DB 사양
Load Generator
Network 경로
관측 설정
~~~

그리고 Index만 바꾼다.

이렇게 해야 p95 차이를 Index 변경과 연결하기 쉬워진다.

## 교란 변수는 결과 해석을 흐리는 다른 변화다

교란 변수(Confounding Variable)는 우리가 보고 싶은 변경 외에 결과에 영향을 주는 요소다.

예를 들어:

~~~text
Before
Product 10K
100 RPS
Cold Cache
Index 없음

After
Product 100K
50 RPS
Warm Cache
Index 추가
~~~

결과가 빨라졌거나 느려져도 무엇 때문인지 알기 어렵다.

Dataset, RPS, Cache 상태가 모두 바뀌었기 때문이다.

이런 비교는 “Before/After” 형식만 가지고 있을 뿐 인과 실험으로는 약하다.

## 요청량과 데이터 규모를 동시에 바꾸지 않는다

성능 테스트에서 특히 자주 섞이는 두 변수는 요청 부하와 데이터 규모다.

~~~text
Dataset Scale
1K → 10K → 100K

Request Load
50 → 100 → 200 RPS
~~~

다음 비교는 해석하기 어렵다.

~~~text
1K / 50 RPS
vs
100K / 200 RPS
~~~

느려졌다면 데이터가 커져서인지 요청이 늘어서인지 분리하기 어렵다.

따라서 먼저 한 축을 고정한다.

~~~text
같은 100 RPS
1K vs 10K
→ 데이터 규모 영향

같은 10K
50 vs 100 vs 200 RPS
→ 요청 부하 영향
~~~

## Cache 상태도 중요한 교란 변수다

첫 Query는 Disk나 DB Buffer에서 데이터를 읽고 두 번째 Query는 이미 Cache된 데이터를 읽을 수 있다.

다음처럼 실행하면 After가 유리할 수 있다.

~~~text
Before
서버 재기동 직후
Cold Cache

After
여러 번 요청한 뒤
Warm Cache
~~~

반대로 Before만 Warm이고 After를 재기동 직후 측정하면 변경 효과를 과소평가할 수 있다.

Cache를 완전히 동일하게 만드는 것은 어려울 수 있지만 적어도 상태 차이를 기록하고 Warm-up 조건을 맞춰야 한다.

## 실행 순서 자체가 결과에 영향을 줄 수 있다

항상 Before를 먼저 실행하고 After를 나중에 실행하면 시간에 따라 자연스럽게 달라지는 요소가 After에 유리할 수 있다.

예를 들어:

~~~text
JIT warm-up
DB Buffer warm-up
OS Page Cache
Background Task 종료
Cloud Resource Noise
~~~

가 있다.

중요한 실험에서는 다음처럼 순서를 바꾸거나 복구해볼 수 있다.

~~~text
A
→ B
→ A
~~~

또는:

~~~text
A
→ B
→ A
→ B
~~~

마지막에 원래 상태로 되돌렸을 때 결과도 원래 범위로 돌아오는지 보면 변경 효과에 대한 근거가 강해진다.

관측 도구 ON/OFF/ON Calibration도 같은 원리를 사용한다.

## 반복 측정은 자연 변동과 실제 효과를 구분하는 데 필요하다

컴퓨터 시스템은 같은 조건에서도 결과가 완전히 같은 숫자로 나오지 않는다.

Scheduler, GC 시점, Network, DB Background Work, Cloud Noise 때문에 조금씩 흔들린다.

예를 들어:

~~~text
Before
31ms
34ms
32ms

After
30ms
31ms
32ms
~~~

이라면 두 결과가 많이 겹친다.

이 정도 차이를 큰 개선이라고 말하기 어렵다.

반면:

~~~text
Before
310ms
295ms
320ms

After
42ms
40ms
44ms
~~~

라면 변화가 반복적으로 크고 방향도 일정하다.

반복 측정은 “한 번 운 좋게 나온 숫자”를 개선으로 오해하는 위험을 줄인다.

## 평균만 비교하지 말고 분포와 오류를 같이 본다

다음 Before/After를 보자.

~~~text
Before
average = 100ms
p95 = 180ms
p99 = 300ms
error = 0%

After
average = 80ms
p95 = 170ms
p99 = 2,000ms
error = 0%
~~~

평균은 좋아졌지만 꼬리 지연은 크게 악화됐다.

특정 사용자에게는 더 나쁜 변경일 수 있다.

또:

~~~text
After
p95 = 50ms
error = 20%
~~~

라면 빠른 실패 때문에 응답 시간이 낮아졌을 수 있다.

따라서 효과는 여러 지표를 함께 본다.

## 효과 크기를 절대값과 상대값으로 나눠 본다

p95가 100ms에서 90ms로 줄었다고 하자.

절대 개선은 10ms다.

상대 개선율은 10%다.

~~~text
절대 차이
100 - 90
= 10ms

상대 차이
10 / 100
= 10%
~~~

두 표현은 모두 유용하다.

하지만 10%라는 숫자만 보면 실제 사용자 체감이 큰지 작은지 알기 어렵다.

예를 들어 10초가 9초로 줄어든 10%와 100ms가 90ms로 줄어든 10%는 사용자 의미가 다르다.

성능 개선은 통계적인 차이뿐 아니라 **실제 업무에 의미 있는 효과 크기인가**를 봐야 한다.

## 상관관계는 같이 변한다는 뜻이고 인과관계는 원인이라는 뜻이다

CPU와 p95가 동시에 올라갔다고 하자.

이 두 값은 상관관계가 있을 수 있다.

하지만 CPU 증가가 p95 증가의 원인이라고 바로 말할 수는 없다.

다음처럼 요청량 증가가 둘을 동시에 만들었을 수 있다.

~~~text
RPS 증가
├─ CPU 증가
└─ Queue 증가
   → p95 증가
~~~

또는 DB 지연이 Request Thread를 쌓이게 하고 그 과정에서 CPU가 증가했을 수도 있다.

인과관계를 더 강하게 주장하려면 다음 근거가 필요하다.

~~~text
시간 순서가 맞는가
다른 원인 후보가 배제되는가
변경했을 때 결과가 달라지는가
원래 상태로 복구하면 결과도 돌아오는가
같은 조건에서 반복되는가
~~~

## 개입은 원인 후보를 실제로 바꾸는 것이다

Intervention은 원인이라고 생각하는 요소에 실제로 변화를 주는 것이다.

예를 들어:

~~~text
가설
Index 부재 때문에 많은 row를 읽는다.

개입
Index 1개 추가.

예상
Rows Examined 감소.
p95 감소.
DB CPU 또는 I/O 감소 가능.
~~~

같은 조건에서 재측정하고 예상한 중간 지표와 사용자 결과가 같이 변하면 가설이 강해진다.

반대로 Index를 추가했는데 Rows Examined도 p95도 그대로라면 가설을 다시 봐야 한다.

## 중간 지표가 바뀌었는지 확인해야 한다

변경 후 p95만 낮아졌다고 끝내지 않는다.

가설에서 예상한 내부 변화도 확인하는 것이 좋다.

예를 들어 Query Plan 개선이라면:

~~~text
Before
Full Scan
Rows Examined 100,000

After
Index Range Scan
Rows Examined 200

그리고
p95 감소
~~~

처럼 원인 경로가 연결되어야 한다.

p95는 좋아졌는데 Rows Examined가 그대로라면 다른 변화가 결과를 만들었을 가능성을 생각해야 한다.

## 한 번에 여러 기술을 바꾸지 않는다

다음 변경을 한 번에 적용했다고 하자.

~~~text
Index 추가
Hikari Pool 10 → 30
Heap 512MiB → 1GiB
Redis Cache 추가
Tomcat Thread 200 → 400
~~~

결과가 좋아져도 어떤 변경이 실제로 필요했는지 알 수 없다.

또 새 복잡성과 비용을 모두 감수하게 된다.

따라서 가능한 한:

~~~text
가장 강한 가설
→ 최소 변경 하나
→ 재측정
~~~

순서를 따른다.

이 방식은 개선 효과뿐 아니라 “이 기술은 지금 필요하지 않다”는 결론도 만들 수 있다.

## 실패한 가설도 의미 있는 결과다

성능 분석에서 틀린 가설은 실패가 아니다.

예를 들어:

~~~text
가설
DB CPU가 병목이다.

확인
DB CPU 25%
Query latency 안정
Lock wait 없음

동시에
Backend OOMKilled 확인

판정
DB Scale-up 가설 약화
Memory 문제 조사
~~~

이 과정으로 불필요한 DB Scale-up과 비용을 피할 수 있다.

“기술을 도입하지 않았다”는 것도 근거 있는 성능 결정이다.

## Trade-off는 개선의 대가를 같이 보는 것이다

성능 개선은 거의 항상 다른 비용을 만든다.

### Cache

~~~text
장점
DB 조회 감소
응답 시간 감소 가능

대가
Cache invalidation
Stale Data
Memory
운영 복잡성
장애 경로 추가
~~~

### Pool 증가

~~~text
장점
Application Connection 대기 감소 가능

대가
DB 동시 Query 증가
Lock / CPU / I/O 경쟁 증가 가능
~~~

### 더 큰 Heap

~~~text
장점
GC 빈도 감소 가능

대가
Container Memory 증가
Collector에 따라 Pause/회수 특성 변화
비용 증가
~~~

따라서 개선 결과에는 성능 숫자와 함께 새 비용과 운영 복잡성도 기록한다.

## 유지, 보류, 제외는 기술에 대한 영구 평가가 아니다

성능 개선 후보를 다음처럼 판정할 수 있다.

### 유지(KEEP)

현재 측정된 문제를 실제로 개선했고 대가도 수용할 수 있어 현재 구조에 유지한다.

### 보류(DEFER)

효과가 있을 수 있지만 현재 문제에 필요하다는 근거가 부족하거나 우선순위가 낮아 나중으로 미룬다.

### 제외(REJECT)

현재 문제와 맞지 않거나 실험에서 기대한 효과가 없고 비용이 더 커서 현재 범위에서는 사용하지 않는다.

예를 들어 Redis가 좋은 기술인지 나쁜 기술인지를 평가하는 것이 아니다.

~~~text
현재 병목
JVM OOM

Redis
현재 원인 해결과 직접 관계 없음

판정
DEFER
~~~

처럼 **문제와 근거에 대한 현재 결정**이다.

## 성능 개선 기록은 조건을 포함한 문장으로 쓴다

약한 기록:

~~~text
Index를 추가해서 성능이 크게 좋아졌다.
~~~

더 설명력 있는 기록:

~~~text
Product 10,000개,
GET /api/products,
100 RPS,
동일 Runtime과 DB 조건에서 측정했다.

변경 전
p95 420ms
Rows Examined 약 100,000

필터 조건용 Index 1개 추가 후
p95 85ms
Rows Examined 약 200

동일 조건 반복 측정에서도
비슷한 범위가 재현됐다.

현재 이 Query 병목에는
해당 Index를 유지한다.
~~~

이렇게 쓰면 나중에 다른 사람이 결과의 범위와 근거를 판단할 수 있다.

## 우아한형제들 사례도 측정과 재측정을 반복한다

신규 포인트 시스템 전환 사례에서는 목표 TPS를 정한 뒤 nGrinder로 부하를 만들고 Pinpoint와 RDS를 확인해 병목을 찾는다.

문제를 수정한 뒤 다시 같은 종류의 성능 테스트를 수행한다.

여기서 배울 점은 nGrinder나 Pinpoint 자체가 아니다.

~~~text
업무량에서 목표 설정
→ 부하 생성
→ 내부 지표 관찰
→ 병목 수정
→ 재측정
~~~

이라는 반복 구조다.
