# Before After와 성능 실험의 인과관계

## 빨라졌다는 것과 변경 때문에 빨라졌다는 것은 다르다

~~~text
Before p95 = 200ms
After  p95 = 120ms
~~~

만으로는 변경이 원인이라고 할 수 없다.

다른 조건이 바뀌었을 수 있다.

- request rate
- dataset
- cache
- JVM state
- DB state
- background workload
- network

## 한 번에 작은 변경

가능하면:

~~~text
Baseline
→ Index 하나 추가
→ 동일 조건 재측정
~~~

처럼 변경 변수를 작게 유지한다.

Index + Cache + Pool + JVM option을 한 번에 바꾸면 무엇이 효과를 냈는지 알 수 없다.

## Controlled Variable

Before/After에서 최대한 고정:

- dataset
- query/request
- rate/concurrency
- duration
- host
- container limit
- JVM option
- DB config
- measurement method

완전히 동일하게 만들 수 없다면 차이를 기록한다.

## 반복 측정

시스템에는 noise가 있다.

~~~text
Before
31 / 34 / 32ms

After
30 / 31 / 32ms
~~~

이면 효과가 run-to-run variation 안일 수 있다.

반면:

~~~text
Before
310 / 295 / 320ms

After
42 / 40 / 44ms
~~~

이면 훨씬 강한 evidence다.

카카오 메시징 성능 테스트 글도 같은 부하 포인트에서 반복해 결과를 분석하는 작업의 중요성을 보여 준다.

- [카카오 — 메시징 서버의 스트레스 테스트 노하우](https://tech.kakao.com/posts/822)

## Correlation과 Causation

CPU와 latency가 같이 증가했다고 CPU가 원인이라고 확정할 수 없다.

~~~text
원인 A
→ CPU 증가
→ latency 증가
~~~

일 수도 있고:

~~~text
원인 B
→ queue 증가
→ latency 증가
→ backlog 처리로 CPU 증가
~~~

일 수도 있다.

문제 재현 후 하나의 intervention을 하고 같은 조건으로 다시 측정하면 인과 주장이 강해진다.

## 실패한 가설도 결과다

~~~text
가설: DB가 병목

DB CPU 낮음
DB latency 낮음
I/O 낮음
Application OOM 확인

→ DB scale-up 보류
~~~

틀린 가설을 버린 것은 기술을 추가하지 않은 중요한 결정이다.

NAVER D2도 GC option을 다른 서비스에서 그대로 복사하기보다 실제 workload에서 비교해 적용하라고 강조한다.

- [NAVER D2 — Garbage Collection 튜닝](https://d2.naver.com/helloworld/37111)

## Trade-off

| 개선 | 대표 대가 |
| --- | --- |
| Cache | consistency, invalidation |
| Pool 증가 | DB concurrency |
| Thread 증가 | native memory, context switch |
| Replica | lag, routing |
| Async | eventual consistency |
| Queue | 운영 복잡도 |
| Scale-out | 비용, 분산 상태 |

최종 기록:

~~~text
효과
+ 비용
+ 복잡도
+ failure mode
+ 남은 한계
~~~

까지 포함한다.

## KEEP / DEFER / REJECT

- KEEP: 현재 문제에 효과가 있고 대가를 감당 가능
- DEFER: 필요 가능성은 있지만 현재 근거로 비용이 더 큼
- REJECT: 현재 문제와 맞지 않거나 효과 근거 없음

우아한형제들 성능 사례도 병목을 수정한 뒤 다시 측정하는 반복을 보여 준다.

- [우아한형제들 — 결제 시스템 성능, 부하, 스트레스 테스트](https://techblog.woowahan.com/2572/)
- [우아한형제들 — 신규 포인트 시스템 전환기 #2](https://techblog.woowahan.com/2588/)


## 인과관계를 왜 따져야 하는가

성능 개선에서 가장 흔한 착시는 “변경 후 숫자가 좋아졌으니 내가 한 변경 덕분이다”라고 생각하는 것이다.

하지만 시스템 성능에는 동시에 많은 변수가 영향을 준다.

~~~text
Request Rate
Dataset
Cache 상태
JVM 상태
DB Buffer 상태
Background Job
Network
Host 부하
~~~

따라서 변경 전후 숫자가 다르다는 사실과 **그 차이를 내가 바꾼 요소가 만들었다는 주장**은 구분해야 한다.

## 통제 변수는 무엇인가

통제 변수(Controlled Variable)는 비교 실험에서 가능한 한 같게 유지하는 조건이다.

예를 들어 인덱스 효과를 보고 싶다면 다음 조건을 고정한다.

~~~text
Dataset
Query
RPS
측정 시간
Host
Container limit
JVM option
DB 설정
부하 도구
~~~

그리고 가능한 한 인덱스만 바꾼다.

~~~text
Before
Index 없음

After
Index 1개 추가
~~~

이렇게 해야 결과 차이를 인덱스와 연결하기 쉬워진다.

## 교란 변수는 무엇인가

교란 변수(Confounding Variable)는 우리가 보고 싶은 변경 외에 결과에 영향을 주는 다른 변수다.

예를 들어 다음 비교는 문제가 있다.

~~~text
Before
10K Dataset
100 RPS
cold cache

After
100K Dataset
50 RPS
warm cache
+ Index 추가
~~~

After가 빨라졌거나 느려졌어도 어떤 변화 때문인지 알기 어렵다.

Dataset, RPS, Cache가 모두 교란 변수로 작동한다.

## 반복 측정은 왜 필요한가

시스템에는 자연스러운 흔들림이 있다.

같은 조건에서도 Scheduler, GC 시점, Network, DB 상태 때문에 결과가 조금씩 달라질 수 있다.

다음 결과를 보자.

~~~text
Before
31ms
34ms
32ms

After
30ms
31ms
32ms
~~~

두 집단의 범위가 많이 겹친다.

이 정도 차이는 변경 효과보다 자연 변동일 수 있다.

반면:

~~~text
Before
310ms
295ms
320ms

After
42ms
40ms
44ms
~~~

라면 효과가 반복해서 크게 재현된다.

반복 측정은 “한 번 운 좋게 나온 숫자”를 개선으로 오해하는 위험을 줄인다.

## 상관관계와 인과관계는 무엇이 다른가

상관관계(Correlation)는 두 값이 함께 변하는 패턴이 있다는 뜻이다.

~~~text
CPU 증가
p95 증가
~~~

두 값이 같이 올라갔다면 상관관계는 있을 수 있다.

하지만 CPU 증가가 p95 증가의 원인인지 바로 알 수는 없다.

다음과 같은 제3의 원인이 둘을 같이 만들 수 있다.

~~~text
요청량 급증
├─ CPU 증가
└─ Queue 증가 → p95 증가
~~~

인과관계(Causation)는 한 요소의 변화가 다른 결과 변화에 실제로 영향을 줬다는 더 강한 주장이다.

성능 실험에서는 문제를 재현하고 하나의 변경을 적용한 뒤 같은 조건에서 결과가 반복적으로 달라지는지 확인하면서 인과 주장을 강화한다.

## Intervention은 무엇인가

Intervention은 원인으로 의심하는 요소를 실제로 바꿔 보는 개입이다.

예를 들어 Full Table Scan이 원인이라고 생각한다면 필요한 인덱스 하나를 추가한다.

~~~text
가설
Index 부재가 병목

개입
Index 1개 추가

같은 Query / 같은 Dataset / 같은 RPS 재측정
~~~

Rows Examined가 크게 줄고 p95도 반복적으로 낮아진다면 인덱스가 현재 병목에 영향을 줬다는 근거가 강해진다.

## 실패한 가설도 중요한 결과다

성능 분석은 정답 기술을 빨리 맞히는 게임이 아니다.

가설을 세우고 틀린 가설을 근거로 제거하는 과정이다.

~~~text
가설
DB CPU 병목

확인
DB CPU 낮음
Query latency 낮음
I/O 여유
Application OOM 확인

결론
DB scale-up 보류
~~~

DB를 키우지 않은 결정도 중요한 결과다.

쓸데없는 비용과 복잡도를 피했기 때문이다.

## Trade-off는 무엇인가

Trade-off는 한 가지 이점을 얻는 대신 다른 비용이나 단점을 감수하는 관계다.

성능 개선은 공짜가 아니다.

예를 들어 Cache를 추가하면 DB 조회를 줄일 수 있지만 데이터 일관성과 무효화 문제가 생긴다.

Connection Pool을 늘리면 Application 대기는 줄 수 있지만 DB 동시 부하가 증가할 수 있다.

~~~text
개선 효과
+
비용
+
복잡도
+
새로운 장애 형태
+
운영 부담
~~~

을 함께 기록해야 실제 의사결정이 된다.

## KEEP / DEFER / REJECT를 쉽게 이해하면

KEEP은 현재 문제에서 효과가 있고 비용도 감당할 수 있어 유지한다는 뜻이다.

DEFER는 기술 자체가 나쁜 것은 아니지만 **현재 근거로는 지금 도입할 이유가 부족해 보류**한다는 뜻이다.

REJECT는 현재 문제와 맞지 않거나 효과가 없다는 근거가 있어 제외한다는 뜻이다.

예를 들어:

~~~text
Redis 검토

현재 병목
DB Query가 아니라 JVM OOM

판정
DEFER 또는 REJECT

이유
현재 원인을 해결하지 않음
~~~

처럼 기술 이름이 아니라 현재 문제와 근거를 기준으로 판단한다.

## 실제 성능 개선 문장은 어떻게 써야 하는가

약한 문장:

~~~text
Index를 추가해서 성능이 좋아졌다.
~~~

더 좋은 문장:

~~~text
Product 10K
100 RPS
동일 Query 조건

Index 추가 전
p95 420ms

Index 추가 후
p95 85ms

Rows Examined도 크게 감소했고
동일 조건 3회에서 재현됨

현재 Query 병목에는 Index를 KEEP
~~~

조건, 변경, 결과, 반복 근거와 적용 범위를 같이 쓰면 과장을 줄일 수 있다.

우아한형제들의 포인트 시스템 사례도 목표 TPS를 정하고 부하를 만들며 Pinpoint/RDS로 병목을 찾은 뒤 수정하고 다시 테스트하는 반복 구조를 보여 준다.
