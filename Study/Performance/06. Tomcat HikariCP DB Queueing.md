# Tomcat HikariCP DB Queueing

Spring MVC 요청은 여러 자원 경계를 통과한다.

~~~text
Client
→ Nginx
→ Tomcat Thread
→ Spring
→ HikariCP Connection
→ MySQL Query / Lock / I/O
~~~

어느 한 곳에서 service rate보다 arrival rate가 높아지면 queue가 생긴다.

## Response Time에는 Waiting이 포함된다

~~~text
Response Time
= Queueing Time
+ Service Time
~~~

Query 자체가 10ms여도 Hikari connection을 500ms 기다리면 사용자는 510ms 이상을 경험한다.

## Tomcat Thread

전통적인 Spring MVC에서는 요청을 request thread가 처리한다.

DB I/O를 기다리는 동안에도 thread가 점유될 수 있다.

부하가 증가하면:

~~~text
동시 요청 증가
→ active thread 증가
→ max thread 접근
→ queue 증가
→ latency 증가
~~~

Thread 수를 무조건 늘리면:

- native stack memory
- context switch
- downstream concurrency
- DB connection demand

가 같이 커질 수 있다.

LINE은 blocking server와 asynchronous server의 차이를 설명하면서 I/O 대기 중 request thread가 묶이는 비용을 보여 준다.

- [LINE — Spring 대신 Armeria를 사용하는 이유](https://engineering.linecorp.com/ko/blog/hello-armeria-bye-spring/)

## HikariCP

Connection Pool의 대표 상태:

- active
- idle
- pending
- max

active=max이고 pending이 증가하면 connection을 기다리는 요청이 생겼다는 뜻이다.

하지만 원인은 여러 개다.

~~~text
느린 Query
긴 Transaction
DB Lock Wait
요청 동시성 급증
Pool이 지나치게 작음
~~~

## Pool Size를 크게 하면?

Application의 connection 대기는 줄 수 있다.

하지만 DB 동시 실행량이 늘어난다.

~~~text
Pool 증가
→ DB concurrency 증가
→ CPU / Lock / I/O 증가
→ Query latency 악화 가능
~~~

따라서 pool size는 Application만 보고 정하지 않는다.

우아한형제들 HikariCP 사례도 deadlock 회피 공식과 실제 pool size를 분리하고, 적절한 값은 성능 테스트로 찾아야 한다고 설명한다.

- [우아한형제들 — HikariCP Dead lock 이론편](https://techblog.woowahan.com/2664/)
- [우아한형제들 — HikariCP Dead lock 실전편](https://techblog.woowahan.com/2663/)

## DatabaseConnections=10의 함정

DB metric에 connection 10이 보여도 DB 최대치가 10이라는 뜻은 아니다.

Hikari max가 10이면 Application이 10개만 사용하므로 DB에서도 10으로 보일 수 있다.

DB saturation을 보려면 같이 확인한다.

- DB CPU
- query latency
- lock wait
- IOPS
- storage latency
- buffer pool
- slow query

## Pending의 원인을 분리한다

~~~text
Hikari pending 증가
+ DB query latency 증가
→ DB / Query 후보
~~~

~~~text
Hikari pending 증가
+ DB latency 낮음
+ Application thread 급증
→ concurrency / transaction 범위 후보
~~~

## Little's Law

~~~text
L = λW
~~~

평균 시스템 내 작업 수는 throughput과 평균 체류 시간의 곱으로 볼 수 있다.

100 RPS × 0.1초 = 평균 약 10개.

100 RPS × 2초 = 평균 약 200개.

Latency 증가가 thread와 connection demand를 다시 키우는 이유를 이해하는 데 유용하다.

## Tomcat만 따로 튜닝하면 안 되는 이유

카카오 실시간 댓글 서버 안정화 사례는 한 서버에서 10K WebSocket connection과 2800 TPS를 목표로 하면서 Spring WebSocket만 수정한 것이 아니라 Tomcat, 물리 장비, Docker container, memory, file descriptor까지 같이 검증했다.

- [카카오 — 실시간 댓글 개발기 part.2](https://tech.kakao.com/posts/391)

이 사례가 중요한 이유는 다음 경계가 연결돼 있기 때문이다.

~~~text
Connection 증가
→ Socket/File Descriptor 증가
→ Tomcat/Network 처리 증가
→ Memory 사용 증가
→ GC/Native Memory 변화
~~~

Tomcat max thread 같은 설정 한 개를 늘렸다고 capacity가 선형 증가하는 것이 아니다.

## Backpressure 관점

Downstream이 처리할 수 있는 속도보다 upstream이 계속 빠르게 요청을 보내면 queue가 커진다.

~~~text
Client arrival
> Tomcat 처리
> Hikari connection 확보
> DB 처리
~~~

각 단계 중 가장 느린 경계가 전체 처리량을 제한한다.

Pool과 Thread를 크게 만드는 방식은 queue 위치를 뒤로 미루는 것일 수 있다.

예:

~~~text
Tomcat Thread 200 → 500
Hikari max 10 유지

→ 더 많은 thread가 Hikari 앞에서 대기
→ latency와 native memory만 증가 가능
~~~

따라서 queue의 위치를 옮기는 것과 throughput을 실제로 높이는 것을 구분해야 한다.

## 실전 조사 순서

~~~text
1. p95/error 증가 시각
2. Tomcat thread
3. Hikari active/pending
4. DB query latency/CPU/lock
5. Transaction hold time
6. 원인 확정 전 pool size 변경 금지
~~~

## 요청 하나가 DB까지 가는 흐름을 먼저 이해한다

전통적인 Spring MVC 애플리케이션에서 DB를 사용하는 요청 하나를 단순화하면 다음처럼 볼 수 있다.

~~~text
HTTP 요청 도착
→ Tomcat이 요청 처리 Thread 배정
→ Controller / Service 실행
→ HikariCP에서 DB Connection 획득
→ MySQL Query 실행
→ Connection 반납
→ HTTP 응답
~~~

각 단계에는 사용할 수 있는 자원의 수가 있다.

~~~text
Tomcat
→ 동시에 처리할 Thread 수

HikariCP
→ 동시에 빌릴 수 있는 Connection 수

MySQL
→ 동시에 효율적으로 처리할 수 있는 Query 수
~~~

한 단계가 다른 단계보다 느리면 그 앞에서 요청이 기다리기 시작한다.

## Queueing은 무엇인가

Queueing은 바로 처리하지 못한 작업이 순서를 기다리는 것이다.

마트 계산대를 생각하면 쉽다.

~~~text
손님 도착 속도
> 계산대 처리 속도

→ 줄이 점점 길어짐
~~~

서버도 같다.

~~~text
요청 도착 속도
> 현재 시스템 처리 속도

→ 대기 요청 증가
→ 응답 시간 증가
~~~

사용자 응답 시간에는 실제 작업 시간뿐 아니라 기다린 시간도 포함된다.

DB Query가 10ms여도 Connection을 500ms 기다렸다면 사용자는 적어도 약 510ms 이상을 경험한다.

## Tomcat Thread는 어떤 역할을 하는가

Spring Boot의 전통적인 Spring MVC 구조에서는 내장 Tomcat이 HTTP 요청을 받고 요청 처리 Thread가 Controller와 Service 코드를 실행한다.

DB Query나 외부 API 호출처럼 Blocking I/O를 기다리는 동안에도 해당 Thread가 요청과 연결된 채 점유될 수 있다.

부하가 올라가면 다음 흐름이 가능하다.

~~~text
동시 요청 증가
→ 바쁜 Tomcat Thread 증가
→ 사용 가능한 Thread 감소
→ 새 요청 대기
→ p95/p99 증가
~~~

Thread 최대값을 크게 늘리면 무조건 해결되는 것이 아니다.

더 많은 Thread가 동시에 DB Connection을 요구하면서 HikariCP 앞의 Queue가 커질 수 있고 Thread Stack 때문에 Native Memory도 증가한다.

## HikariCP는 왜 필요한가

애플리케이션이 Query를 실행할 때마다 매번 새 DB Connection을 만들고 인증하고 끊으면 비용이 크다.

Connection Pool은 미리 만들어 둔 Connection을 재사용한다.

~~~text
요청
→ Pool에서 Connection 빌림
→ Query / Transaction
→ Connection 반납
→ 다른 요청이 재사용
~~~

Spring Boot에서 많이 사용하는 Connection Pool 구현이 HikariCP다.

## active는 무엇인가

active는 현재 애플리케이션 코드가 빌려 사용 중인 Connection 수다.

~~~text
active = 8
max = 10
~~~

이라면 최대 10개 중 8개가 현재 사용 중이라고 볼 수 있다.

active가 높다는 사실만으로 문제는 아니다. 정상적으로 많은 요청을 처리하면 높아질 수 있다.

## idle은 무엇인가

idle은 Pool 안에 있으면서 현재 사용되지 않고 바로 빌려줄 수 있는 Connection 수다.

~~~text
active = 8
idle = 2
max = 10
~~~

idle이 0이라고 바로 장애는 아니다. 모든 Connection이 잠깐 사용 중일 수 있다.

중요한 것은 그 상황에서 기다리는 요청이 발생하는가이다.

## pending은 무엇인가

pending은 Connection을 얻지 못해 기다리는 요청 또는 Thread가 있다는 뜻으로 이해할 수 있다.

~~~text
max = 10
active = 10
idle = 0
pending = 25
~~~

라면 10개의 Connection은 모두 사용 중이고 추가 요청들이 Connection 반납을 기다리고 있다는 강한 신호다.

하지만 pending이 증가했다고 Pool이 작으니 바로 50으로 늘리면 안 된다.

## pending이 생기는 이유는 여러 가지다

첫 번째는 Query가 느린 경우다.

~~~text
Query 2초
→ Connection 2초 점유
→ 반납 늦음
→ pending 증가
~~~

두 번째는 Transaction이 너무 긴 경우다.

Query 하나는 빠르더라도 Transaction 안에서 여러 작업을 수행하며 Connection을 오래 잡고 있을 수 있다.

세 번째는 DB Lock 대기다.

Transaction이 Lock을 기다리는 동안 Connection도 같이 점유될 수 있다.

네 번째는 순간적인 요청 동시성 증가다.

DB가 정상이어도 갑자기 너무 많은 요청이 동시에 Connection을 요구하면 pending이 생길 수 있다.

다섯 번째는 Pool 크기가 workload에 비해 지나치게 작은 경우다.

따라서 pending은 Connection 대기가 있다는 증거이지 원인을 직접 말해주는 지표는 아니다.

## maximumPoolSize는 무엇인가

maximumPoolSize는 HikariCP가 관리할 최대 Connection 수를 제한한다.

이 값을 10에서 50으로 올리면 애플리케이션이 DB에 동시에 보낼 수 있는 작업 수가 늘어날 수 있다.

하지만 DB 관점에서는 더 많은 Query와 Transaction이 동시에 들어오는 것이다.

~~~text
Pool 10
→ DB 동시 작업을 상대적으로 제한

Pool 50
→ 더 많은 Query 동시 실행 가능
→ DB CPU / Lock / I/O 경쟁 증가 가능
~~~

즉 Connection Pool 크기는 애플리케이션만의 설정이 아니라 DB에 전달하는 동시성의 문이기도 하다.

## Pool 크기를 크게 하면 왜 더 느려질 수도 있는가

DB가 CPU나 I/O 한계에 가까운 상황에서 Connection만 늘리면 더 많은 Query가 동시에 경쟁한다.

~~~text
Pool 증가
→ 동시 Query 증가
→ DB 경쟁 증가
→ Query latency 증가
→ Connection 반환 지연
→ 다시 pending 증가 가능
~~~

그래서 “대기하니까 Pool 증가”는 항상 정답이 아니다.

우아한형제들의 HikariCP 장애 사례에서도 Dead lock을 피할 수 있는 최소 조건과 실제 효율적인 Pool 크기를 구분하고 최적 크기는 성능 테스트로 찾아야 한다고 설명한다.

## 우아한형제들 사례에서 무엇을 배울 수 있는가

해당 사례에서는 Thread 수 16, HikariCP 최대 Connection 10, 하나의 Task에서 동시에 필요한 Connection 수 2라는 조건에서 문제가 발생했다. 일부 Thread가 이미 Connection 하나를 잡은 상태에서 추가 Connection을 기다렸고 Pool에 여유가 없어 진행이 막히는 형태였다.

핵심은 HikariCP 자체가 나쁘다는 것이 아니다.

~~~text
Thread 수
한 작업이 동시에 필요한 Connection 수
Pool 크기
Transaction 구조
~~~

가 서로 연결되어 있다는 점이다.

## DB Connection 수가 적다고 DB가 여유로운 것은 아니다

DB Monitoring에서 Connection이 10개라고 보여도 DB 최대치가 10이라는 뜻이 아니다.

애플리케이션 Hikari maximumPoolSize가 10이라면 Application이 애초에 10개까지만 Connection을 사용해서 DB에서도 10개가 보이는 것일 수 있다.

DB 자체 포화를 판단하려면 다음을 함께 본다.

~~~text
DB CPU
Query latency
Lock wait
Storage I/O
Buffer Pool
Slow Query
Execution Plan
~~~

## Little's Law를 쉽게 이해하기

Little's Law는 평균적으로 시스템 안에 머무는 작업 수와 처리량, 체류 시간의 관계를 설명한다.

~~~text
평균 시스템 내 작업 수
≈ 초당 처리량 × 평균 체류 시간
~~~

100 RPS이고 평균 응답 시간이 0.1초라면 평균 약 10개 작업이 시스템 안에 존재한다.

같은 100 RPS인데 평균 응답 시간이 2초라면 평균 약 200개가 된다.

즉 요청량이 그대로여도 응답 시간이 느려지면 시스템 안에서 동시에 살아 있는 요청 수가 커질 수 있다.

이 때문에 latency 악화가 Thread와 Connection demand를 다시 증가시키는 악순환이 가능하다.

## Backpressure는 무엇인가

Backpressure는 뒤쪽 시스템이 처리할 수 있는 속도보다 앞쪽에서 작업을 계속 밀어 넣을 때 속도를 조절하거나 밀려드는 양을 제한하는 개념이다.

DB가 초당 100개의 무거운 Query를 안정적으로 처리할 수 있는데 Application이 500개 Query를 계속 밀어 넣으면 Queue가 커지거나 DB가 더 느려질 수 있다.

Thread와 Pool을 무한정 늘리는 것은 Backpressure가 아니라 Queue 위치를 뒤로 옮기는 것일 수 있다.

~~~text
Tomcat Thread 200 → 500
Hikari max 10 유지

→ 더 많은 Thread가 Hikari 앞에서 대기
→ 처리량은 그대로일 수 있음
→ memory와 latency만 증가 가능
~~~

## 조사할 때는 Queue가 어디에 생겼는지 찾는다

p95가 나빠졌다면 다음 순서가 도움이 된다.

~~~text
Tomcat busy Thread가 max에 접근했는가
→ Hikari active가 max인가
→ pending이 증가했는가
→ DB Query latency가 증가했는가
→ Lock wait가 있는가
→ Transaction이 Connection을 오래 잡는가
~~~

이렇게 보면 Thread나 Pool 값을 먼저 바꾸기보다 실제로 어디에서 기다리는지를 찾게 된다.

우아한형제들의 포인트 시스템 사례도 nGrinder로 부하를 만들고 Pinpoint와 RDS 지표를 같이 보며 병목을 수정한 뒤 다시 측정하는 흐름을 보여 준다.
