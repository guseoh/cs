# Tomcat, HikariCP와 데이터베이스 대기 구조

Spring Boot 애플리케이션에서 HTTP 요청 하나가 데이터베이스까지 내려가는 경로를 단순화하면 다음과 같다.

~~~text
HTTP 요청
→ Tomcat이 요청 처리 Thread 배정
→ Controller / Service 실행
→ HikariCP에서 DB Connection 획득
→ Transaction / SQL 실행
→ Connection 반납
→ HTTP 응답
~~~

이 흐름에는 여러 개의 “동시에 처리할 수 있는 수”가 존재한다.

Tomcat은 동시에 실행할 Request Thread 수에 한계가 있고, HikariCP는 동시에 빌려줄 수 있는 DB Connection 수에 한계가 있으며, MySQL도 CPU·Lock·I/O 관점에서 안정적으로 처리할 수 있는 동시 Query 수에 한계가 있다.

한 계층의 처리 속도가 그 앞 계층에서 들어오는 속도를 따라가지 못하면 요청은 줄을 서기 시작한다.

성능 분석에서 중요한 것은 “Tomcat Thread를 몇 개로 해야 하는가?”나 “Hikari Pool은 몇 개가 적당한가?”를 외우는 것이 아니다. **지금 요청이 어디에서 기다리고 있고, 그 대기가 다음 계층에 어떤 압력을 만들고 있는지 이해하는 것**이다.

## 응답 시간에는 실제 처리 시간뿐 아니라 기다린 시간이 포함된다

사용자 응답 시간이 800ms라고 해서 Application 코드가 800ms 동안 CPU 계산을 했다는 뜻은 아니다.

예를 들어 다음과 같을 수 있다.

~~~text
Tomcat Queue 대기      100ms
DB Connection 대기    400ms
SQL 실행               20ms
Application 처리       30ms
Network 등 기타       250ms
----------------------------
전체                   800ms
~~~

실제 SQL은 20ms밖에 걸리지 않았지만 사용자는 800ms를 기다렸다.

그래서 “Query가 빠르니 DB 쪽은 문제가 아니다”라는 결론도 성급할 수 있다. Query를 실행하기 위한 Connection을 오래 기다렸을 수 있기 때문이다.

반대로 Hikari pending이 증가해도 DB Query 자체가 느린 것이 아니라 Application이 Connection을 오래 들고 외부 API를 기다리고 있을 수도 있다.

성능 분석에서는 **실제 처리 시간과 대기 시간을 분리**하려고 한다.

## Tomcat은 들어온 HTTP 요청을 Thread로 처리한다

전통적인 Spring MVC 애플리케이션에서 Tomcat은 HTTP 요청을 받고 Worker Thread를 사용해 Request를 처리한다.

대략 다음 흐름이다.

~~~text
Connection 수신
→ 요청 읽기
→ Worker Thread 배정
→ Spring Filter / DispatcherServlet
→ Controller
→ Service
→ Repository
→ 응답 생성
~~~

한 Request Thread는 Controller 코드만 실행하는 것이 아니다.

Blocking JDBC Query를 기다리는 동안에도 그 요청과 연결된 Thread는 계속 점유될 수 있다.

외부 REST API를 동기 방식으로 호출하고 2초 기다려도 Thread가 그 시간 동안 다른 Request를 처리하지 못할 수 있다.

## Tomcat Thread가 모두 바쁘면 새 요청은 기다려야 한다

예를 들어 최대 Worker Thread가 200개이고 200개의 요청이 모두 오래 걸리는 DB 작업을 수행 중이라고 하자.

그 순간 새 요청이 들어오면 바로 실행할 Thread가 없다.

요청은 Tomcat Connector 설정과 Queue 구조에 따라 대기하거나 거부될 수 있다.

~~~text
200 Worker Thread
전부 Busy

새 요청
→ 바로 처리할 Thread 없음
→ 대기
→ 대기가 길어지면 응답 시간 증가
~~~

그래서 p95나 p99가 올라갈 때 Tomcat Busy Thread가 Max 근처에 있는지 볼 수 있다.

하지만 Thread가 가득 찼다고 Max Thread를 무조건 400으로 늘리면 안 된다.

더 많은 Thread가 HikariCP에서 Connection을 요구하면서 다음 Queue가 커질 수 있기 때문이다.

## maxThreads를 늘리면 처리량이 항상 증가하지 않는다

CPU Core가 4개인데 CPU 계산 중심 작업을 하는 Thread를 1,000개로 늘린다고 1,000개가 동시에 계산할 수 있는 것은 아니다.

운영체제는 제한된 Core에서 Thread를 번갈아 실행한다.

Thread가 지나치게 많으면 Context Switch 비용과 Memory 사용이 증가할 수 있다.

Blocking I/O 중심 Application에서는 CPU Core 수보다 많은 Thread가 유용할 수 있지만 그래도 무한히 늘릴 수는 없다.

따라서 Tomcat Thread 크기는 다음과 연결해서 본다.

~~~text
요청 동시성
Blocking 시간
CPU Core
Hikari Pool
DB 처리 능력
Thread Stack Memory
~~~

## acceptCount와 maxConnections는 Thread와 다른 경계다

Tomcat Connector에는 동시에 유지할 Connection과 Thread Queue에 관련된 여러 설정이 있다.

설정 이름과 동작은 Tomcat 버전과 Connector 구현에 따라 확인해야 하지만 개념적으로는 다음 단계를 구분할 필요가 있다.

~~~text
TCP Connection 수용
→ 요청 대기
→ Worker Thread 배정
→ Application 실행
~~~

Worker Thread가 부족하다고 바로 Connection 자체가 거부되는 것은 아닐 수 있다. 일정 Queue에서 기다릴 수 있다.

이런 Queue는 순간 Spike를 흡수할 수 있지만 너무 커지면 요청이 오래 기다리다가 Timeout을 만날 수 있다.

**Queue를 늘리는 것은 처리 능력을 늘리는 것이 아니라 대기할 공간을 늘리는 것**일 수 있다는 점이 중요하다.

Apache Tomcat 공식 문서에서도 `maxThreads`, `maxConnections`, `acceptCount`를 서로 다른 경계로 설명한다. `maxThreads`가 실제 요청 처리 Thread 수를 제한하고, 연결 수가 `maxConnections`에 도달한 뒤에는 운영체제의 연결 Queue가 `acceptCount`의 영향을 받을 수 있다. 실제 Spring Boot 설정에서는 사용하는 Tomcat 버전과 별도 Executor 설정 여부를 함께 확인해야 한다.

## HikariCP는 DB Connection을 재사용한다

DB Connection을 만들 때는 TCP 연결, 인증, Session 설정 같은 비용이 든다.

매 Query마다 새 Connection을 만들고 끊는 것은 비효율적이다.

Connection Pool은 일정 수의 Connection을 유지하고 요청이 필요할 때 빌려준다.

~~~text
요청
→ HikariCP에서 Connection 대여
→ SQL / Transaction
→ Connection 반납
→ 다른 요청이 재사용
~~~

Spring Boot에서 널리 사용하는 Connection Pool 구현 중 하나가 HikariCP다.

## active는 현재 빌려간 Connection 수다

HikariCP의 active Connection은 Application이 현재 빌려서 사용 중인 Connection 수다.

예를 들어:

~~~text
maximumPoolSize = 10
active = 8
idle = 2
pending = 0
~~~

이라면 10개까지 사용할 수 있는 Pool에서 8개가 사용 중이고 2개가 바로 빌릴 수 있는 상태라고 볼 수 있다.

active가 높다는 사실만으로 문제는 아니다.

많은 요청을 정상 처리하고 있다면 대부분의 Connection이 사용 중인 것은 자연스러울 수 있다.

## idle은 현재 사용하지 않는 Connection 수다

idle은 Pool 안에서 현재 어떤 요청도 사용하지 않고 대기 중인 Connection이다.

~~~text
active = 10
idle = 0
pending = 0
~~~

이라고 해서 바로 장애는 아니다.

모든 Connection이 사용 중이지만 추가로 기다리는 요청이 없을 수 있다.

중요한 것은 **Connection 수요가 공급을 초과했는가**다.

## pending은 Connection을 얻기 위해 기다리는 수요가 있다는 신호다

HikariCP에서 pending이 증가하면 Connection을 요청했지만 바로 받지 못하고 기다리는 Thread 또는 Request가 있다는 의미로 해석할 수 있다.

~~~text
maximumPoolSize = 10
active = 10
idle = 0
pending = 25
~~~

이 상태라면 10개 Connection이 모두 사용 중이고 추가 요청이 반납을 기다리고 있다는 강한 신호다.

하지만 pending의 원인은 Pool Size 하나가 아니다.

HikariCP의 공식 Metric에서 pending은 Connection을 기다리는 Thread 수를 나타낸다. Micrometer 연동에서는 `hikaricp.connections.pending` 계열 Metric으로 노출될 수 있다.

다만 active, idle, pending 같은 값은 매우 빠르게 변하는 상태다. 서로 다른 시각에 수집한 Snapshot을 억지로 더해서 항상 정확한 등식이 성립한다고 가정하면 안 된다. 추세와 같은 시각의 acquire/usage 시간을 함께 보는 편이 안전하다.

- [HikariCP — Micrometer Metrics 구현](https://github.com/brettwooldridge/HikariCP/blob/dev/src/main/java/com/zaxxer/hikari/metrics/micrometer/MicrometerMetricsTracker.java)
- [HikariCP — JMX Monitoring and Management](https://github.com/brettwooldridge/HikariCP/wiki/MBean-%28JMX%29-Monitoring-and-Management)

## Query가 느리면 Connection 반납도 늦어진다

가장 단순한 원인 중 하나는 SQL이 오래 걸리는 경우다.

~~~text
빠른 상태
Query 20ms
→ Connection 20ms 부근 점유

느린 상태
Query 2초
→ Connection 2초 이상 점유
~~~

같은 10개의 Connection이라도 각 요청이 100배 오래 점유하면 초당 처리할 수 있는 요청 수는 크게 줄어든다.

그 결과 pending이 생길 수 있다.

이 경우 Pool Size를 키우는 것보다 Query가 왜 느려졌는지 조사하는 것이 먼저일 수 있다.

## 긴 Transaction도 Connection을 오래 잡을 수 있다

Spring Transaction 안에서 JDBC Connection을 획득한 뒤 다음과 같은 작업을 오래 수행하면 Connection이 계속 점유될 수 있다.

~~~text
DB Query
→ 복잡한 Application 계산
→ 외부 API 호출
→ 추가 Query
→ Commit
~~~

외부 API 응답을 2초 기다리는 동안 Connection을 잡고 있다면 DB는 아무 일도 하지 않아도 Pool 자원은 사용 중이다.

그래서 Connection 사용 시간과 Transaction 경계를 함께 봐야 한다.

## DB Lock 대기는 Connection도 같이 붙잡을 수 있다

Transaction이 다른 Transaction의 Lock 해제를 기다리면 SQL이 실제 CPU 계산을 많이 하지 않아도 오래 걸릴 수 있다.

~~~text
Transaction A
row lock 보유

Transaction B
같은 row 수정 시도
→ Lock 대기
→ Connection 계속 점유
~~~

이 상태에서 동시 요청이 늘면 Hikari active가 Max에 붙고 pending이 증가할 수 있다.

DB CPU가 낮아도 Lock 때문에 Application은 느릴 수 있다.

따라서 “DB CPU가 30%니까 DB는 문제없다”라고 단정하지 않는다.

## Connection Pool이 너무 작아서 대기가 생길 수도 있다

Query와 Transaction이 충분히 빠른데 요청 동시성이 Pool Size보다 크다면 pending이 발생할 수 있다.

예를 들어:

~~~text
Query 평균 10ms
Pool = 5
동시 요청 급증
→ 짧은 pending 발생
~~~

이 경우 Pool을 조금 늘리는 것이 실제로 도움이 될 수 있다.

하지만 Pool Size 증가는 DB에 전달할 수 있는 동시 Query 수를 늘리는 결정이기도 하다.

DB가 감당할 수 있는지 같이 검증해야 한다.

## maximumPoolSize는 Application과 DB 사이의 동시성 문이다

maximumPoolSize를 10에서 50으로 올리면 Application은 동시에 더 많은 DB 작업을 실행할 수 있다.

~~~text
Pool 10
→ 최대 10개 수준의 DB Connection 동시 사용

Pool 50
→ 최대 50개 수준의 DB Connection 동시 사용
~~~

이것은 “Application 대기 감소”만 의미하지 않는다.

MySQL 입장에서는 동시에 실행되는 Query와 Transaction이 늘 수 있다.

DB CPU, Lock, Buffer Pool, Storage I/O 경쟁이 커질 수 있다.

따라서 Pool을 키우면 어느 순간 오히려 개별 Query가 느려질 수도 있다.

## Pool을 키우는 악순환이 생길 수 있다

다음 흐름을 생각해보자.

~~~text
pending 증가
→ Pool 10 → 50으로 증가
→ DB 동시 Query 크게 증가
→ Query latency 증가
→ Connection 반환 더 늦어짐
→ pending 다시 증가
~~~

이 경우 “Connection이 부족해서”라는 최초 해석이 실제로는 DB 동시성 과부하를 더 키운다.

Connection Pool은 Application만의 성능 설정이 아니다.

**DB가 동시에 얼마나 많은 일을 받게 할 것인지 조절하는 Backpressure 경계**이기도 하다.

## 우아한형제들 HikariCP 사례는 Thread와 Pool의 관계를 잘 보여 준다

우아한형제들의 HikariCP Dead lock 사례에서는 실제 환경의 Thread Count와 maximumPoolSize, 하나의 Task가 동시에 요구하는 Connection 수를 조사했다.

해당 사례에서 중요한 부분은 단순 공식이 아니다.

애플리케이션이 “한 요청당 Connection을 하나만 쓴다”고 생각했지만 실제 실행에서는 하나의 Task가 동시에 두 개의 Connection을 요구하는 경로가 있었다.

일부 Thread가 이미 Connection 하나를 보유한 상태에서 두 번째 Connection을 기다리면서 Pool이 고갈될 수 있었다.

이 사례는 다음을 보여 준다.

~~~text
Thread 수
Pool Size
한 Task의 동시 Connection 요구량
Transaction / ORM 동작
~~~

을 따로 보면 안 된다.

## acquire time은 Connection을 얻기까지 기다린 시간을 보여 줄 수 있다

HikariCP Metric에서는 Connection 획득에 걸린 시간을 볼 수 있다.

Query 실행 시간이 정상인데 acquire time이 크게 늘었다면 실제 병목이 SQL 자체보다 Pool 앞 대기일 수 있다.

예를 들어:

~~~text
SQL 실행
20ms

Connection acquire
500ms
~~~

라면 사용자는 최소 520ms 이상을 기다릴 수 있다.

이런 경우 p95가 높아져도 Slow Query만 찾으면 원인을 놓칠 수 있다.

## usage time은 Connection을 얼마나 오래 들고 있었는지 보는 데 도움이 된다

Connection 사용 시간이 길어졌다면 다음 질문을 한다.

~~~text
Query가 느려졌는가?
Transaction 안에 외부 I/O가 있는가?
Lock 대기가 있는가?
많은 Query를 한 Transaction에 묶었는가?
N+1로 Query 수가 증가했는가?
~~~

Connection 사용 시간이 길어지는 원인을 찾으면 pending의 뿌리를 좁힐 수 있다.

## DB Connection 수가 적다고 DB가 한가한 것은 아니다

Cloud DB Metric에서 Connection이 10개라고 보인다고 가정하자.

이 값이 DB가 최대 10개밖에 못 받는다는 뜻은 아니다.

Application Hikari maximumPoolSize가 10이면 애초에 Application이 10개까지만 연결을 사용하고 있을 수 있다.

따라서 DB 자체 포화는 다음을 같이 본다.

~~~text
CPU
Memory
Query latency
Statement rate
Lock wait
Storage latency
Rows examined
Execution Plan
Buffer Pool
~~~

Connection 숫자 하나로 DB capacity를 판단하지 않는다.

## Little's Law는 대기 구조를 이해하는 데 유용하다

Little's Law는 안정된 시스템에서 평균적인 작업 수, 처리량, 체류 시간 사이의 관계를 설명한다.

쉽게 다음처럼 생각할 수 있다.

~~~text
평균 시스템 안의 작업 수
≈ 처리량 × 평균 체류 시간
~~~

100 RPS를 처리하고 평균 요청 시간이 0.1초라면:

~~~text
100 × 0.1
≈ 평균 10개 요청이 시스템 안에 존재
~~~

같은 100 RPS인데 평균 요청 시간이 2초라면:

~~~text
100 × 2
≈ 평균 200개 요청
~~~

가 된다.

요청량이 그대로여도 응답 시간이 늘면 동시 작업 수가 커진다.

그 요청들이 Thread와 Connection을 오래 점유하면서 다시 대기를 키울 수 있다.

## Queue를 늘리는 것은 처리 능력을 늘리는 것과 다르다

Tomcat Queue, Thread Pool, Connection Pool을 크게 만들면 더 많은 요청을 내부에 보관할 수 있다.

하지만 실제 CPU와 DB 처리 능력이 그대로라면 일을 더 빨리 끝내는 것은 아니다.

~~~text
처리 능력
100 req/s

유입
300 req/s

Queue 확대
→ 더 많은 요청을 버리지 않고 기다리게 함
→ 처리 능력은 여전히 100 req/s
→ 대기 시간은 길어질 수 있음
~~~

Queue는 순간 Spike를 흡수하는 데 도움이 될 수 있지만 지속적인 과부하를 해결하지 않는다.

## Backpressure는 뒤쪽 처리 능력에 맞춰 압력을 조절하는 개념이다

Backpressure는 뒤쪽 시스템이 처리할 수 있는 속도보다 앞에서 계속 일을 밀어 넣지 않도록 조절하는 개념이다.

예를 들어 DB가 안정적으로 처리할 수 있는 동시 Query 수가 제한되어 있다면 Application에서 무한히 많은 Thread와 Connection을 열어 보내는 것이 좋은 전략이 아닐 수 있다.

~~~text
Client
→ Tomcat
→ Hikari
→ MySQL
~~~

각 단계가 다음 단계를 보호할 수 있는 경계가 된다.

실패를 빠르게 반환하거나 Queue를 제한하고, Retry를 제어하고, 동시 요청을 제한하는 설계도 Backpressure와 연결된다.

## Timeout은 Queue가 무한히 길어지는 것을 막는 경계다

Connection Pool에서 Connection을 무한정 기다리게 하면 사용자 요청도 끝없이 대기할 수 있다.

HikariCP의 Connection Timeout 같은 설정은 일정 시간이 지나도 Connection을 얻지 못하면 실패하게 만든다.

Timeout은 장애 자체가 아니다.

**지나치게 긴 대기를 제한하고 실패를 명확하게 드러내는 안전 경계**다.

다만 Timeout을 너무 짧게 하면 정상적인 순간 Spike에서도 실패가 늘 수 있고 너무 길면 사용자가 오래 기다린다.

실제 workload에서 검증해야 한다.

## Tomcat Thread와 Hikari Pool 비율에는 만능 공식이 없다

“Tomcat Thread는 Hikari Pool의 두 배로 한다” 같은 고정 공식은 모든 서비스에 맞지 않는다.

요청마다 DB를 얼마나 사용하는지, 외부 I/O가 있는지, Query 시간이 어떤지, CPU Core가 몇 개인지에 따라 달라진다.

예를 들어:

~~~text
요청 A
DB 사용 거의 없음
CPU 계산 중심

요청 B
Transaction 2초
DB Connection 오래 점유
~~~

같은 Thread 수라도 Hikari 수요가 전혀 다르다.

따라서 Pool과 Thread 크기는 성능 테스트와 Metric으로 결정한다.

## Blocking 방식에서는 느린 뒤쪽 계층이 앞쪽 Thread를 붙잡는다

Spring MVC + JDBC 같은 Blocking 구조에서 DB가 느려지면 Request Thread도 같이 기다린다.

~~~text
DB 느려짐
→ Connection 오래 점유
→ Hikari pending 증가
→ Tomcat Thread가 Connection 대기
→ Busy Thread 증가
→ 새 요청 Queue
→ p95/p99 증가
~~~

이런 연쇄를 보면 “DB 하나가 느리다”가 Application 전체 응답으로 어떻게 전파되는지 이해할 수 있다.

LINE의 Armeria 글은 Blocking I/O에서 많은 Thread가 대기할 때 Thread 고갈과 Context Switch 비용이 발생할 수 있다는 점을 설명한다.

관련 자료:
- [LINE — 개발자들이 Spring 대신 Armeria를 사용하는 이유](https://engineering.linecorp.com/ko/blog/hello-armeria-bye-spring/)

## 비동기 방식이 모든 Queue 문제를 없애는 것은 아니다

비동기 I/O는 Thread 하나가 I/O 완료를 기다리는 동안 다른 일을 할 수 있게 해 Thread 효율을 높일 수 있다.

하지만 DB 처리 능력 자체가 100 req/s인데 1,000 req/s를 계속 넣는다면 어디엔가 대기와 Backpressure가 필요하다.

Thread Queue가 줄어들어도 Reactive Stream Buffer나 DB Connection Queue가 커질 수 있다.

그래서 Architecture를 바꾸기 전에 실제 병목이 Thread Blocking인지 확인해야 한다.

## 성능 문제에서는 대기가 처음 생긴 위치를 찾는다

가상의 예를 보자.

~~~text
200 RPS
p95 = 100ms

250 RPS
p95 = 1,300ms
~~~

Tomcat:

~~~text
busy thread
80 → 180
max = 200
~~~

Hikari:

~~~text
active
8 → 10
max = 10

pending
0 → 40
~~~

DB:

~~~text
CPU
35%

특정 Query latency
20ms → 900ms

Lock wait
증가
~~~

이 결과에서는 Tomcat Thread를 먼저 늘리기보다 Query/Lock 때문에 Connection이 오래 점유되고 pending이 증가한 가설이 더 강하다.

반대로:

~~~text
Hikari pending = 0
DB 정상
Tomcat busy = max
CPU 100%
~~~

라면 Application CPU나 Thread 계층을 더 먼저 볼 수 있다.

## 병목을 찾은 뒤 가장 작은 변경을 적용한다

Pool Size, Thread Count, Query, Index를 한 번에 바꾸면 결과가 좋아져도 무엇이 효과를 냈는지 알기 어렵다.

예를 들어 Lock을 만드는 Query가 확인되었다면 먼저 Query와 Transaction을 수정하고 같은 부하로 다시 측정한다.

그 뒤 pending이 사라지고 p95가 안정된다면 원인 관계가 강해진다.

우아한형제들의 신규 포인트 시스템 전환 사례도 부하를 만들고 Pinpoint와 RDS 지표로 병목을 찾은 뒤 수정하고 다시 테스트하는 반복 흐름을 사용한다.
