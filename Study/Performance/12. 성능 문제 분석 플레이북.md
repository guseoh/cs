# 성능 문제 분석 플레이북

성능 문제가 발생하면 가장 먼저 “CPU가 높은가?”, “DB가 느린가?”부터 보고 싶어진다. 하지만 처음부터 특정 계층을 범인으로 정하면 실제 원인을 놓치기 쉽다.

성능 문제 분석의 목적은 모든 지표를 한 번에 보는 것이 아니다. **사용자에게 실제로 어떤 문제가 있었는지 확인하고, 강한 실패 신호부터 조사하면서 원인 후보를 단계적으로 줄이는 것**이다.

이 문서는 체크리스트를 외우기 위한 문서가 아니다. 왜 이런 순서로 조사하는지, 각 지표가 무엇을 말해 주고 무엇까지는 말해 주지 않는지 설명하는 분석 흐름이다.

## 먼저 테스트 자체가 유효했는지 확인한다

성능 결과가 나쁘다고 해서 바로 서버 문제라고 볼 수 없다.

부하 생성기가 목표 요청을 만들지 못했거나 잘못된 URL을 호출했을 수 있다. 예상 상태 코드가 아닌 Redirect를 성공으로 집계했을 수도 있다. 관측 시스템이 Down되어 내부 Metric이 비어 있을 수도 있다.

따라서 가장 먼저 실험 자체를 확인한다.

예를 들어 다음 조건을 본다.

~~~text
정확한 대상 Endpoint인가?
정확한 Source / Image인가?
정확한 Dataset인가?

target RPS와 actual RPS는 얼마인가?
dropped iteration이 있는가?

예상 상태 코드는 무엇인가?
Redirect를 따라갔는가?
Timeout은 얼마인가?

부하 생성기 CPU/Memory는 충분한가?

Prometheus Target은 UP인가?
측정 시작/종료 시각은 정확한가?
~~~

이 단계가 필요한 이유는 간단하다.

실험이 잘못되었는데 서버를 튜닝하면 잘못된 문제를 해결하게 되기 때문이다.

특히 k6의 `dropped_iterations`는 원인을 하나로 단정하지 않는다. arrival-rate 실행기에서는 준비한 VU가 부족해서도 생길 수 있고, 시스템 응답 시간이 길어져 VU가 반환되지 않아서도 생길 수 있다. 따라서 dropped가 보이면 부하 생성기와 시스템 응답을 둘 다 확인한다.

## 사용자 관점 결과부터 본다

테스트가 유효하다면 먼저 사용자가 경험한 결과를 본다.

~~~text
target RPS
actual RPS
error rate
timeout
dropped iteration
p50
p95
p99
max
~~~

여기서 몇 가지 대표 패턴을 구분할 수 있다.

### 실제 RPS는 유지되는데 p95만 증가한다

~~~text
target = 200
actual = 200
error = 0
p95 증가
~~~

시스템은 요청을 계속 처리하고 있지만 일부 요청 대기가 길어진 상태일 수 있다.

Connection Pool 대기, Lock, GC Pause, 특정 Query 같은 Tail 원인을 조사한다.

### actual RPS가 target을 따라가지 못한다

~~~text
target = 250
actual = 180
~~~

먼저 dropped iteration과 Load Generator 상태를 확인한다.

부하 생성기가 요청을 만들지 못한 것인지, 서버 오류와 Timeout 때문에 실제 완료율이 낮아진 것인지 구분해야 한다.

### 오류율이 증가한다

~~~text
error
0% → 5%
~~~

응답 시간이 어떻게 변했는지와 함께 오류 종류를 본다.

500인지, 502인지, 503인지, Timeout인지에 따라 조사 방향이 달라진다.

## Process가 죽었는지 먼저 확인하는 이유

성능 저하 중 가장 강한 사건 중 하나는 Process 종료와 재시작이다.

Backend Container가 OOM으로 종료되어 자동 재시작했다고 하자.

현재 시점에는 다시 Healthy일 수 있다.

하지만 측정 Window 중에는 분명 장애가 있었다.

그래서 다음 값을 일찍 확인한다.

~~~text
RestartCount
OOMKilled
Container Health 변화
Process Start Time
~~~

이 신호는 “p95가 조금 높다”보다 훨씬 강하다.

## RestartCount는 하나의 측정 Window에 여러 JVM이 섞였는지 알려 준다

측정 시작 전 RestartCount가 2였고 종료 후 3이라면 중간에 한 번 재시작했다.

~~~text
초반 요청
→ JVM A

중간 OOM / Crash

후반 요청
→ JVM B
~~~

이 결과를 하나의 안정된 JVM 상태처럼 평균내면 안 된다.

JVM B는 Class Loading, JIT, Connection Pool 초기화 같은 기동 비용을 다시 겪을 수 있다.

따라서 재시작이 있으면 먼저 장애 원인을 조사하고 해당 Window를 정상 Capacity 근거로 사용하지 않는 편이 안전하다.

## OOMKilled가 보이면 Heap만 보지 않는다

OOMKilled는 Container 또는 운영체제 Memory 경계에서 Process가 종료되었다는 강한 신호다.

하지만 원인이 Java Heap이라는 뜻은 아니다.

~~~text
Heap
Thread Stack
Direct Memory
Metaspace
Native Library
기타 Native Memory
~~~

가 모두 Container Memory를 사용한다.

따라서:

~~~text
OOMKilled=true
Heap used 50%
~~~

라고 해서 모순이라고 생각하지 않는다.

이 경우 Thread 수, RSS, Direct Memory, Container Limit을 조사한다.

## Host와 Container 자원을 구분한다

Process가 살아 있다면 Host와 Container 상태를 본다.

### CPU

다음 질문을 한다.

~~~text
us가 높은가?
sy가 높은가?
id가 거의 없는가?
wa가 높은가?
Run Queue가 쌓이는가?
~~~

CPU 전체 사용률 하나로 끝내지 않는다.

us가 매우 높고 DB/GC가 정상이라면 Application 계산 CPU를 의심할 수 있다.

sy가 비정상적으로 높다면 Network, System Call, Context Switch 같은 Kernel 작업을 더 볼 수 있다.

wa가 높다면 I/O 경로를 조사한다.

### Memory

다음 값을 구분한다.

~~~text
Host MemAvailable
Container Memory usage
Container Memory limit
Swap si/so
RSS
OOMKilled
~~~

Host에 Memory가 남아 있어도 Container Limit에 걸릴 수 있다.

### Disk

~~~text
I/O latency
IOPS
Throughput
Queue
iowait
~~~

를 같이 본다.

### Network

~~~text
Bandwidth
Packet error
Retransmission
Connection state
TIME_WAIT
File Descriptor
~~~

를 필요에 따라 확인한다.

## CPU가 높다고 바로 CPU를 늘리지 않는다

다음 결과를 보자.

~~~text
p95 증가
CPU 95%
~~~

CPU Scale-up이 떠오를 수 있다.

하지만 먼저 왜 CPU가 높아졌는지 본다.

~~~text
정상적으로 많은 요청 계산
GC Worker
JSON Serialization
압축
Encryption
무한 반복
Retry Storm
재시작 후 JIT
Network Kernel 처리
~~~

CPU가 최초 원인인지 다른 장애의 결과인지 시간축으로 확인한다.

## JVM에서는 Heap, GC, Thread를 따로 본다

Host 자원에서 명확한 원인이 없거나 Java 계층을 더 봐야 한다면 JVM Metric을 확인한다.

### Heap이 Max 근처까지 반복적으로 올라간다

~~~text
Heap used → Max
GC
잠깐 감소
다시 빠르게 Max
~~~

라면 Allocation Pressure나 Live Set 증가를 조사한다.

GC Pause가 p99 Spike와 반복적으로 겹치는지도 본다.

### Heap은 안정적인데 RSS가 계속 증가한다

Heap 밖 Native Memory를 의심할 근거가 생긴다.

~~~text
Thread Stack
Direct Buffer
Metaspace
Native Library
~~~

Thread 수도 함께 본다.

### Thread가 급격히 증가한다

Metric으로는 Thread 수 증가만 알 수 있다.

Thread Dump로 실제 대기 위치를 확인한다.

~~~text
Hikari Connection 대기?
Lock BLOCKED?
외부 API 대기?
Thread Leak?
~~~

## Tomcat과 HikariCP에서는 Queue 위치를 찾는다

사용자 p95가 증가하고 Thread도 많아졌다면 Tomcat과 HikariCP를 연결해서 본다.

### Tomcat Busy Thread가 Max에 접근한다

새 요청을 처리할 Worker가 부족해 Queue에서 기다릴 수 있다.

그런데 Thread를 늘리기 전에 왜 기존 Thread가 오래 점유되는지 본다.

### Hikari active가 Max이고 pending이 증가한다

Connection을 기다리는 요청이 있다는 뜻이다.

다음 질문은 “왜 Connection이 돌아오지 않는가?”다.

~~~text
Query가 느린가?
Transaction이 긴가?
Lock 대기인가?
외부 호출 중 Connection을 잡고 있는가?
Pool이 너무 작은가?
~~~

pending은 Pool Size를 늘리라는 명령이 아니다.

대기 위치를 알려주는 신호다.

## DB CPU가 낮아도 DB 계층 문제가 있을 수 있다

DB CPU가 30%라고 해서 DB 문제를 완전히 제외할 수 없다.

특정 Query 하나가 Lock을 기다릴 수 있다.

Storage latency가 높을 수 있다.

Query Plan이 잘못되어 특정 요청만 느릴 수 있다.

Connection은 Application이 오래 들고 있지만 DB 자체는 쉬고 있을 수도 있다.

따라서 다음을 함께 본다.

~~~text
Statement latency
Slow Query
Rows Examined
Execution Plan
Lock wait
Active Transaction
Storage latency
Buffer Pool
Connection
~~~

## 특정 Query만 느려졌다면 실행 계획과 데이터 분포를 본다

예를 들어 전체 DB CPU는 정상인데 상품 목록 Query의 latency만 증가했다면:

~~~text
EXPLAIN
사용 Index
Estimated Rows
Rows Examined
Sort
Temporary Table
Join 순서
~~~

를 확인한다.

10K Dataset에서만 느려졌다면 데이터 규모와 분포가 Plan을 바꾸었는지도 본다.

관련 개념:
- [[10. 대규모 데이터 Volume Cardinality Distribution Skew]]

## Lock 대기는 CPU가 낮아도 응답 시간을 크게 늘릴 수 있다

Transaction B가 Transaction A가 가진 Lock을 기다리면 CPU 계산을 거의 하지 않아도 오래 대기할 수 있다.

~~~text
A
row lock 보유

B
같은 row 수정
→ 기다림
→ Connection 점유
→ Hikari pending 증가
→ Tomcat Thread 대기
~~~

이처럼 DB Lock 하나가 Application Queue까지 전파될 수 있다.

따라서 DB CPU가 낮다는 사실만으로 DB를 제외하지 않는다.

## 시간축을 만들어 무엇이 먼저 변했는지 본다

성능 분석에서 가장 강한 도구 중 하나가 사건 순서다.

예를 들어:

~~~text
T0 RPS 증가
T1 Query latency 증가
T2 Hikari pending 증가
T3 Tomcat Busy 증가
T4 p95 증가
~~~

라면 DB/Connection 경로가 상위 후보가 된다.

반대로:

~~~text
T0 Thread 급증
T1 RSS 증가
T2 OOM
T3 Restart
T4 CPU Spike
~~~

라면 마지막 CPU Spike를 최초 원인으로 보면 안 된다.

가능하면 Load Test Result, Prometheus, Log, DB Metric의 시간을 맞춰 하나의 Timeline을 만든다.

## 가설은 지지 근거와 반대 근거를 같이 적는다

성능 조사에서 확증 편향을 줄이려면 원인 가설을 문장으로 적고 반대 근거도 함께 본다.

예를 들어:

~~~text
가설
DB가 병목이다.

지지 근거
Hikari pending 증가
특정 Query latency 증가

반대 근거
DB CPU 낮음
Lock wait 없음

다음 확인
Execution Plan
Rows Examined
Transaction hold time
~~~

반대 근거가 충분하면 가설을 약화하거나 버린다.

“DB일 것 같다”는 느낌 때문에 DB Metric만 계속 보는 일을 줄일 수 있다.

## 가장 작은 변경을 먼저 적용한다

원인이 어느 정도 좁혀졌다면 한 번에 여러 설정을 바꾸지 않는다.

예를 들어 Query Plan 문제가 확인되었는데 동시에:

~~~text
Index 추가
Pool 증가
Heap 증가
Tomcat Thread 증가
Cache 추가
~~~

를 모두 하면 결과가 좋아져도 어떤 변경이 필요했는지 알 수 없다.

가장 강한 가설에 대응하는 최소 변경 하나를 적용한다.

~~~text
문제 재현
→ 가설
→ 최소 변경
→ 같은 조건 재측정
~~~

## 재측정에서는 사용자 결과와 중간 원인 지표가 모두 변했는지 본다

Index를 추가해서 p95가 줄었다면 Rows Examined나 Execution Plan도 기대한 방향으로 변했는지 본다.

Pool Size를 바꿔 pending이 줄었다면 DB CPU와 Query latency가 악화되지 않았는지 본다.

JVM Heap을 조정했다면 GC Pause와 Container Memory Headroom을 같이 본다.

이렇게 해야 “숫자가 좋아졌다”가 아니라 **왜 좋아졌는지 연결된 설명**을 만들 수 있다.

## 복구 가능성도 성능 변경의 일부다

성능 튜닝이 운영 설정을 바꾼다면 잘못되었을 때 원래 상태로 돌아갈 수 있어야 한다.

~~~text
변경 전 값 기록
Rollback 절차
중단 조건
실행 후 검증
~~~

을 준비한다.

특히 DB Index 변경, Pool/Thread 설정, JVM Option, Cache 도입은 성능뿐 아니라 운영 안정성에도 영향을 줄 수 있다.

## 분석 결과가 “현재는 변경하지 않음”일 수도 있다

성능 분석의 목적은 반드시 기술을 추가하는 것이 아니다.

예를 들어:

~~~text
p95 안정
error 0
CPU 30%
Hikari pending 0
DB latency 안정
Headroom 충분
~~~

이라면 지금 Pool이나 JVM을 튜닝할 근거가 없을 수 있다.

이때 “현재 조건에서는 유지”가 올바른 결론이다.

반대로 특정 기술이 나쁜 것이 아니라 **현재 문제를 해결할 근거가 없어서 보류**하는 것이다.
