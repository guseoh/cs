# 성능 문제 분석 플레이북

이 문서는 실제 성능 저하가 발생했을 때 무엇부터 볼지 정리한 실전 순서다.

목표는 모든 지표를 보는 것이 아니라 **가장 적은 확인으로 문제 계층을 빠르게 줄이는 것**이다.

이 문서는 분석 순서를 빠르게 찾는 실행 안내서이므로 각 용어의 깊은 설명은 별도 개념 문서와 연결한다. 초당 요청 수(RPS), 실제 처리량, 가상 사용자, 준비 구간, 누락된 반복 실행은 [[02. 부하 테스트와 Workload Modeling]]에서 설명하고, p50·p95·p99와 꼬리 지연은 [[07. Latency Percentile과 Tail Latency]]에서 숫자를 읽는 방법부터 설명한다. 데이터 양·관계·고유값 수·분포·쏠림은 [[10. 대규모 데이터 Volume Cardinality Distribution Skew]], 재현 가능한 source·Dataset·격리·TOCTOU는 [[13. 재현 가능한 성능 실험과 안전한 격리]]에서 다룬다.

따라서 이 문서의 짧은 항목을 “정의”로 외우기보다, 실제 장애나 부하 테스트에서 **어떤 순서로 범위를 좁힐 것인지**를 찾는 목차로 사용한다.

## 0. 먼저 테스트 자체가 유효한가

~~~text
Target RPS가 실제로 생성됐는가?
Generator CPU/Memory는 충분한가?
Dropped iteration은 없는가?
Dataset이 의도한 규모/분포인가?
Code/Infra version이 기록됐는가?
~~~

여기가 틀리면 이후 서버 분석도 신뢰하기 어렵다.

## 1. 사용자 관점 결과

먼저 밖에서 무슨 일이 있었는지 본다.

- actual throughput
- status/error
- timeout
- p50
- p95
- p99
- max
- dropped

### 패턴 A

~~~text
RPS 유지
Error 0
p95 증가
~~~

서버는 처리하고 있지만 queueing/service time이 증가하는 상태일 수 있다.

### 패턴 B

~~~text
Target RPS 증가
Actual RPS 정체
Dropped 증가
~~~

서버 포화 또는 generator 포화를 분리해야 한다.

### 패턴 C

~~~text
Error 증가
Latency 오히려 감소
~~~

실패가 빠르게 반환되는 것일 수 있으므로 “성능 개선”으로 보면 안 된다.

## 2. Restart / OOM부터 확인

다음 두 값은 우선순위가 높다.

~~~text
RestartCount
OOMKilled
~~~

Process가 재시작했다면 CPU, GC, Thread metric의 연속성이 끊긴다.

Kernel OOM log가 있으면 직접 failure mechanism으로 강한 증거다.

## 3. Host / Container

### CPU

~~~text
us 높음
→ Application/JVM 계산 후보

sy 높음
→ kernel/network/syscall 후보

wa 높음
→ I/O wait 후보
~~~

### Memory

~~~text
MemAvailable
swap si/so
container usage/limit
~~~

Host memory가 충분해도 container limit 때문에 OOM이 날 수 있다.

## 4. JVM

확인:

- Heap used/max
- Non-heap
- Direct memory
- GC count
- GC pause
- Thread count/state

### Heap max 근처 + GC 반복

Memory/Allocation 문제 후보.

### Heap 안정 + Container RSS 증가

Native/Direct/Thread Stack 후보.

### Thread 폭증

어디서 기다리는지 Thread Dump 필요.

## 5. Tomcat / Hikari

### Tomcat active thread 증가

요청 동시성 또는 downstream wait 가능성.

### Hikari active=max + pending 증가

Connection wait 존재.

하지만 바로 pool을 늘리지 않는다.

~~~text
DB Query가 느린가?
Transaction이 긴가?
요청 concurrency가 늘었나?
~~~

를 먼저 확인한다.

## 6. Database

확인:

- CPU
- Connection
- Query latency
- Lock wait
- IOPS
- Storage latency
- Slow Query
- Execution Plan

### DB CPU 낮고 latency 낮음

DB 자체 saturation 가설은 약해진다.

### 특정 Query latency만 증가

Index/Plan/Data distribution 후보.

### Lock wait 증가

Transaction/Concurrency 문제 후보.

## 7. 시간축으로 순서를 만든다

좋은 분석은 snapshot 목록이 아니라 사건 순서가 있다.

~~~text
T0 RPS 증가
T1 p95 증가
T2 Hikari pending 증가
T3 Thread 증가
T4 Container memory 증가
T5 OOM
T6 Restart
~~~

이 순서를 만들면 “CPU도 높고 Hikari도 높다”보다 훨씬 강한 설명이 된다.

## 8. 가설 표

| 가설 | 지지 근거 | 반대 근거 | 다음 확인 |
| --- | --- | --- | --- |
| CPU 병목 | CPU 100% | restart 직후 spike | restart 전 시계열 |
| DB 병목 | Hikari pending | DB CPU/latency 낮음 | query/lock |
| Memory 병목 | OOMKilled | 없음 | kernel log |
| GC 병목 | pause 증가 | p95와 시각 불일치 | GC log |

가설을 문장으로 쓰면 “느낌”이 줄어든다.

## 9. 가장 작은 변경

~~~text
문제
→ 원인
→ 최소 변경
→ 동일 조건 재측정
~~~

예:

~~~text
Full Table Scan
→ 필요한 Index 1개
→ 동일 Query/Load 재측정
~~~

Redis/Kafka/Scale-out을 바로 넣지 않는다.

## 10. Before / After 판정

최소 비교:

- throughput
- error
- p50/p95/p99
- CPU
- memory
- GC
- thread
- pool
- DB

그리고 반드시 대가를 적는다.

~~~text
Latency 개선
하지만 Memory 증가

Throughput 개선
하지만 DB CPU 증가

DB 부하 감소
하지만 Cache consistency 비용 증가
~~~

## 11. 결론 표현

좋은 표현:

~~~text
현재 조건에서
Index 추가 후 p95가 420ms → 85ms로 감소했고
Rows Examined가 크게 줄었다.
동일 조건 3회에서 재현됐다.
따라서 현재 병목에는 KEEP.
~~~

나쁜 표현:

~~~text
Index가 성능을 해결했다.
~~~

실험 조건 밖으로 결론을 과장하지 않는다.

## 이 플레이북을 왜 이 순서로 보는가

성능 문제가 생겼을 때 가장 먼저 CPU나 DB부터 보면 원인 후보를 너무 빨리 좁힐 수 있다.

먼저 사용자 관점에서 실제로 문제가 있었는지 확인하고, 그 다음 Process가 죽거나 재시작했는지, Host/Container 자원이 포화됐는지, JVM과 Thread가 어떤 상태였는지, 마지막으로 DB까지 내려가는 편이 안전하다.

~~~text
사용자 결과
→ Process 생존 여부
→ Host / Container
→ JVM
→ Tomcat / Hikari
→ Database
~~~

이 순서는 “DB가 항상 마지막 원인”이라는 뜻이 아니다. **비교적 강한 실패 신호와 넓은 계층부터 확인하면서 조사 범위를 줄이는 방법**이다.

## RestartCount는 무엇인가

RestartCount는 Container가 몇 번 다시 시작됐는지 보여 주는 값이다.

부하 테스트 동안 0이던 값이 1로 증가했다면 같은 Process가 끝까지 측정된 것이 아니다.

~~~text
측정 시작
Process A

중간에 OOM
→ Process A 종료

자동 재시작
→ Process B 시작
~~~

이 상황에서 측정 구간 전체의 CPU, Heap, Thread 그래프를 하나의 안정된 Process처럼 해석하면 안 된다.

재시작 직후에는 Class Loading, JIT 컴파일, Connection Pool 재구성 같은 일회성 비용도 다시 발생할 수 있다.

## OOMKilled는 왜 강한 근거인가

OOMKilled는 운영체제나 Container memory 제한 때문에 Process가 메모리 부족으로 종료된 흔적이다.

p95가 높았다는 것은 여러 원인 후보가 있지만 OOMKilled=true는 실제 Process 종료라는 매우 구체적인 사건이다.

따라서 다음과 같이 우선순위를 바꿀 수 있다.

~~~text
p95 증가
CPU 증가
OOMKilled=true
RestartCount 증가

→ 먼저 memory/OOM 사건 조사
→ 그 뒤 CPU spike가 원인인지 결과인지 확인
~~~

## CPU가 높을 때 바로 튜닝하지 않는 이유

CPU 100%는 중요한 신호지만 원인이 여러 가지다.

~~~text
정상적으로 많은 요청을 계산
GC worker 증가
직렬화/압축 증가
무한 반복 또는 비효율 계산
재시작 후 JIT
Network/System Call 증가
~~~

그래서 us, sy, GC, RPS, 재시작 시각을 같이 본다.

CPU가 높다는 사실과 CPU가 병목의 최초 원인이라는 주장은 다르다.

## Hikari pending을 볼 때 기억할 질문

pending이 증가했다면 Connection을 기다리는 요청이 있다는 뜻이다.

그 다음 질문은 “왜 Connection이 돌아오지 않는가?”다.

~~~text
Query가 느린가
Transaction이 긴가
Lock을 기다리는가
요청 동시성이 급증했는가
Pool이 너무 작은가
~~~

즉 pending은 DB scale-up 버튼이 아니라 **대기 위치를 알려 주는 신호**다.

## DB CPU가 낮으면 DB 문제를 완전히 배제할 수 있는가

아니다.

DB 전체 CPU가 낮아도 특정 Query가 Lock을 기다리거나 특정 Index 접근이 느릴 수 있다.

반대로 Application이 Connection을 오래 들고 있으면서 외부 API를 기다리면 DB CPU는 낮은데 Hikari pending이 증가할 수도 있다.

그래서 DB에서는 CPU 하나가 아니라 다음을 같이 본다.

~~~text
Query latency
Lock wait
Rows examined
Execution Plan
I/O
Connection
Slow Query
~~~

## 시간축을 만드는 이유

성능 문제에서는 “무엇이 높았는가”보다 “무엇이 먼저 변했는가”가 더 강한 근거가 될 때가 많다.

~~~text
T0 RPS 증가
T1 p95 증가
T2 Hikari pending 증가
T3 DB Query latency 증가
~~~

라면 DB/Connection 계층을 우선 볼 근거가 있다.

반대로:

~~~text
T0 Thread 급증
T1 Container memory 증가
T2 OOM
T3 Restart
T4 CPU spike
~~~

라면 마지막 CPU spike를 최초 원인으로 보면 순서를 거꾸로 해석하게 된다.

## 가설 표는 왜 쓰는가

가설을 머릿속으로만 생각하면 보고 싶은 지표만 보게 되기 쉽다.

그래서 지지 근거와 반대 근거를 같이 적는다.

~~~text
가설
DB가 병목

지지 근거
Hikari pending 증가

반대 근거
DB CPU 낮음
Query latency 안정
Lock wait 없음

다음 확인
Transaction hold time
Thread Dump
~~~

반대 근거를 적는 순간 “pending이 있으니 DB가 문제” 같은 성급한 결론을 줄일 수 있다.

## 가장 작은 변경을 먼저 하는 이유

한 번에 Index, Cache, Pool, JVM 설정을 모두 바꾸면 결과가 좋아져도 무엇이 효과를 냈는지 알기 어렵다.

~~~text
문제 재현
→ 가장 강한 원인 가설
→ 최소 변경 1개
→ 같은 조건 재측정
~~~

이 과정을 반복하면 각 변경의 효과와 대가를 설명하기 쉽다.
