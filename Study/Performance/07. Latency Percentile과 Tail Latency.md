# 응답 시간 백분위와 꼬리 지연

성능 테스트 결과에서 평균 응답 시간 하나만 보면 시스템이 실제로 어떤 사용자 경험을 만들고 있는지 놓칠 수 있다.

예를 들어 요청 100개 중 95개는 30ms 안에 끝났지만 5개는 2초 이상 걸렸다고 해보자. 평균값은 빠른 요청과 매우 느린 요청을 하나의 숫자로 섞어서 보여 준다. 평균이 어느 정도 괜찮아 보여도 일부 사용자는 매우 긴 지연을 경험했을 수 있다.

그래서 웹 서비스 성능에서는 평균과 함께 p50, p95, p99 같은 백분위(Percentile)를 자주 본다.

백분위는 외워야 할 약어가 아니다. **요청 시간의 분포를 몇 개의 대표 지점으로 압축해서 보는 방법**이다.

카카오 메시징팀도 스트레스 테스트에서 초당 요청 수와 함께 p50, p95, p99, 오류율을 먼저 확인하고, 이상이 있으면 CPU·Memory·Connection·Thread 같은 내부 지표로 내려간다. 우아한형제들과 올리브영의 운영 사례에서도 평균값만이 아니라 상위 지연 구간을 따로 본다.

## 응답 시간은 어디서 측정하느냐에 따라 범위가 달라진다

응답 시간(Latency)은 요청을 시작한 시점부터 결과를 받을 때까지 걸린 시간을 뜻한다.

하지만 측정 위치에 따라 포함되는 구간이 다르다.

외부 Desktop에서 public HTTPS Endpoint를 측정하면 다음이 포함될 수 있다.

~~~text
Client
→ DNS
→ TCP 연결
→ TLS Handshake
→ Internet
→ Nginx
→ Backend
→ DB
→ 응답
~~~

반면 Backend Host의 localhost에서 직접 측정하면 Internet, Public TLS, 일부 Proxy 구간이 빠질 수 있다.

따라서 두 실험의 p95를 직접 비교해 “localhost가 더 빠르니 코드가 개선됐다”고 말하면 안 된다.

응답 시간을 기록할 때는 **어디서부터 어디까지 측정한 값인지** 같이 적어야 한다.

## 평균이 왜 느린 요청을 숨길 수 있는가

다음 두 결과를 비교해보자.

### 시스템 A

~~~text
100개 요청
모두 100ms
~~~

평균은 100ms다.

### 시스템 B

~~~text
99개 요청
20ms

1개 요청
8,020ms
~~~

평균은 역시 약 100ms다.

두 시스템의 평균은 비슷하지만 사용자 경험은 완전히 다르다.

A는 모든 사용자가 비슷한 시간을 기다린다.

B는 대부분 매우 빠르지만 한 사용자는 8초 넘게 기다린다.

평균은 분포의 중심을 보여 주지만 **느린 구간이 얼마나 길게 늘어지는지**를 직접 보여 주지 않는다.

그래서 백분위를 같이 본다.

## 백분위는 요청을 빠른 순서로 세웠을 때의 위치다

응답 시간 100개를 작은 값부터 큰 값까지 정렬했다고 생각해보자.

~~~text
1번째   가장 빠른 요청
2번째
3번째
...
50번째
...
95번째
...
99번째
100번째  가장 느린 요청
~~~

p95는 대략 95번째 지점의 응답 시간이다.

예를 들어:

~~~text
p95 = 300ms
~~~

라면 전체 요청의 약 95%가 300ms 이하에서 끝났고, 나머지 약 5%는 300ms보다 더 오래 걸릴 수 있다는 뜻이다.

여기서 흔한 오해가 있다.

p95가 300ms라는 것은 “95%의 요청이 정확히 300ms 걸렸다”는 뜻이 아니다.

또 “최대 응답 시간이 300ms다”라는 뜻도 아니다.

가장 느린 약 5%는 300ms보다 훨씬 오래 걸릴 수 있다.

## p50은 중앙적인 요청 경험을 보여 준다

p50은 50번째 백분위다.

일반적으로 중앙값과 비슷한 의미로 사용한다.

~~~text
p50 = 40ms
~~~

라면 전체 요청의 절반 정도가 40ms 이하에서 끝났다고 이해할 수 있다.

p50은 “평소 대부분의 요청이 어느 정도 속도로 느껴지는가”를 보는 데 유용하다.

하지만 p50이 빠르다고 시스템 전체가 안정적이라는 뜻은 아니다.

~~~text
p50 = 40ms
p95 = 100ms
p99 = 3,000ms
~~~

라면 중앙적인 요청은 빠르지만 가장 느린 일부 요청은 3초 근처까지 늘어나고 있다는 뜻이다.

## p95는 느린 상위 구간의 변화를 보기 좋다

p95는 95번째 백분위다.

요청 10,000개를 측정했다고 하자.

~~~text
p95 = 200ms
~~~

대략:

~~~text
약 9,500개
→ 200ms 이하

약 500개
→ 200ms 초과 가능
~~~

라고 볼 수 있다.

5%가 작아 보일 수 있지만 하루 요청이 수백만 건이면 실제 요청 수로는 매우 많다.

예를 들어 하루 요청 1,000만 건이라면 5%는 50만 건이다.

따라서 p95는 “아주 소수의 예외”가 아니라 실제 사용자 경험에 의미 있는 느린 구간을 보여 줄 수 있다.

## p99는 더 느린 꼬리 구간을 본다

p99는 99번째 백분위다.

~~~text
p99 = 800ms
~~~

라면 전체 요청의 약 99%가 800ms 이하이고 약 1%는 그보다 더 느릴 수 있다는 뜻이다.

1%도 대규모 서비스에서는 작은 수가 아니다.

~~~text
하루 요청 10,000,000

1%
= 100,000 요청
~~~

즉 p99가 나빠졌다는 것은 매일 수만~수십만 요청이 느린 경험을 할 수 있다는 뜻이 될 수 있다.

LINE의 Kafka 운영 사례에서도 Produce API의 99번째 백분위 응답 시간이 평소보다 크게 악화된 것을 성능 이상 신호로 사용하고 Disk와 Network Thread 상태를 함께 확인했다.

## p50, p95, p99의 간격도 중요하다

각 값 자체뿐 아니라 서로 얼마나 벌어지는지도 본다.

예를 들어:

~~~text
정상
p50 = 30ms
p95 = 60ms
p99 = 90ms
~~~

부하 증가 후:

~~~text
p50 = 32ms
p95 = 80ms
p99 = 1,500ms
~~~

가 되었다고 하자.

p50은 거의 변하지 않았다.

대부분 요청은 여전히 빠르다.

하지만 p99가 크게 늘었다.

이런 경우 “모든 요청의 처리 비용이 증가했다”기보다 **일부 요청만 특정 대기를 겪고 있다**는 가설을 세울 수 있다.

예를 들어:

~~~text
일부 Transaction만 Lock 대기
일부 요청만 Hikari Connection 대기
특정 Query Plan만 느림
간헐적 GC Pause
특정 Cache Miss
일부 Connection 재생성
~~~

같은 후보가 생긴다.

반대로:

~~~text
p50 = 30 → 300ms
p95 = 60 → 500ms
p99 = 90 → 800ms
~~~

처럼 전체 구간이 함께 올라가면 대부분 요청의 처리 비용 자체가 증가했을 가능성을 더 강하게 볼 수 있다.

## 꼬리 지연은 분포의 느린 쪽이다

응답 시간 분포에서 가장 느린 쪽을 꼬리(Tail)라고 부른다.

~~~text
대부분 요청
20~50ms

일부 요청
100~300ms

아주 느린 일부
1~3초
~~~

여기서 1~3초에 걸친 구간이 긴 꼬리를 만든다.

꼬리 지연(Tail Latency)은 사용자 경험뿐 아니라 시스템 내부에도 영향을 준다.

느린 요청은 그 시간 동안 자원을 오래 붙잡을 수 있기 때문이다.

~~~text
Tomcat Thread
DB Connection
Transaction
Socket
Memory Buffer
~~~

느린 요청이 늘면 사용 가능한 자원이 줄고 새 요청이 더 오래 기다리면서 다시 p95/p99가 악화될 수 있다.

## 응답 시간은 실제 처리 시간과 대기 시간의 합이다

요청이 600ms 걸렸다고 해서 Business Logic이 600ms 계산한 것은 아니다.

다음처럼 나뉠 수 있다.

~~~text
Tomcat Queue        50ms
Hikari acquire     400ms
SQL                 20ms
Application         30ms
Network            100ms
------------------------
전체                600ms
~~~

이 경우 SQL 자체는 빠르다.

하지만 Connection을 얻기 위해 400ms를 기다렸다.

따라서 p95가 높아졌다고 Slow Query만 찾으면 원인을 놓칠 수 있다.

응답 시간은 **어디서 기다렸는가**와 함께 봐야 한다.

## 최대값은 가장 느린 요청 하나다

Max는 측정한 요청 중 가장 큰 값이다.

~~~text
p99 = 500ms
max = 8,000ms
~~~

라면 대부분의 느린 요청은 500ms 부근 안에 있지만 한 요청이 8초까지 늘어났을 수 있다.

Max는 이상치를 발견하는 데 유용하지만 한 개 요청에 매우 민감하다.

따라서 Max 하나만 보고 시스템 전체가 불안정하다고 판단하지 않는다.

반대로 p99만 보면 극단적인 한두 요청을 숨길 수 있다.

그래서 p50, p95, p99, Max를 같이 보면 분포를 더 입체적으로 볼 수 있다.

우아한형제들의 대규모 트래픽 시스템 전환 사례에서도 평균과 Max, p95, p99를 함께 비교한다.

## p75, p90 같은 다른 백분위도 사용할 수 있다

백분위는 p50, p95, p99만 있는 것이 아니다.

목적에 따라 p75나 p90을 사용할 수 있다.

예를 들어 올리브영의 대규모 트래픽 운영 사례에서는 p50, p75, p95를 함께 본다.

중요한 것은 “p95가 업계 표준이니 무조건 쓴다”가 아니다.

서비스 목표와 사용자 경험에 맞는 지점을 정하고 같은 기준으로 계속 비교하는 것이다.

## 작은 표본의 p99는 사실상 극단값에 가깝다

백분위는 표본 수에 영향을 받는다.

요청 10,000개에서 p99는 약 100개의 가장 느린 요청 구간과 관련된다.

하지만 요청이 30개뿐이면 p99는 사실상 가장 느린 요청 한두 개에 매우 크게 영향을 받는다.

예를 들어:

~~~text
29개
20~30ms

1개
500ms
~~~

라면 p99가 크게 튈 수 있다.

이 값이 반복적인 꼬리 지연인지 한 번의 Connection 생성 같은 일회성 사건인지 짧은 표본만으로는 판단하기 어렵다.

따라서 짧은 Calibration에서는:

~~~text
p50
→ 중앙적인 상태

p95
→ 느린 구간의 방향

p99 / Max
→ 이상치 참고
~~~

처럼 해석하고 장시간 또는 반복 측정에서 재현되는지 확인하는 편이 안전하다.

## 백분위 계산 방식은 도구마다 다를 수 있다

p95라는 이름이 같아도 내부 계산 방식은 도구마다 조금 다를 수 있다.

가능한 방식은 다음과 같다.

~~~text
실제 정렬된 값의 특정 순위 선택
인접 값 사이 보간
Histogram Bucket 기반 근사
Streaming Quantile 알고리즘
~~~

따라서 k6의 p95와 Prometheus Histogram에서 계산한 0.95 Quantile이 소수점까지 똑같을 필요는 없다.

특히 Prometheus Histogram은 미리 나눈 Bucket에 요청 수를 누적하고 그 분포를 이용해 Quantile을 근사할 수 있다.

Bucket 경계가 거칠면 p95도 거칠게 추정될 수 있다.

Before/After 비교에서는 가능한 한 **같은 도구와 같은 집계 방식**을 유지하는 것이 좋다.

## Histogram은 응답 시간 분포를 구간으로 저장한다

예를 들어 응답 시간을 다음 Bucket으로 나눈다고 하자.

~~~text
≤ 50ms
≤ 100ms
≤ 200ms
≤ 500ms
≤ 1s
+Inf
~~~

각 요청이 어느 구간 이하에 들어오는지 누적한다.

이 데이터를 이용하면 여러 서버의 요청 분포를 합치거나 특정 시간 구간의 p95를 근사할 수 있다.

하지만 실제 모든 Raw Latency를 저장하는 방식은 아니기 때문에 Bucket 설계가 중요하다.

서비스 SLO가 300ms인데 Bucket이 100ms와 1초밖에 없다면 300ms 부근을 세밀하게 보기 어렵다.

## Summary와 Histogram은 집계 특성이 다르다

Prometheus 계열에서는 Summary와 Histogram 모두 분포를 표현할 수 있지만 집계 방식이 다르다.

Summary Quantile은 보통 개별 Instance에서 계산된 결과라 여러 Instance를 단순 합산하기 어렵다.

Histogram은 Bucket Count를 합산할 수 있어 여러 Instance 집계에 유리한 경우가 많다.

실제 운영에서는 Metric Library와 Prometheus 설계를 확인해야 한다.

이 문서에서 중요한 것은 제품 선택보다 **p95가 어디에서 어떤 방식으로 계산된 값인지 알아야 한다**는 점이다.

## 측정 시간 창이 달라지면 p95도 달라질 수 있다

10분 전체의 p95와 1분 단위 p95는 같은 의미가 아니다.

예를 들어 10분 중 9분은 30ms이고 1분 동안만 2초까지 느려졌다고 하자.

10분 전체 통계에서는 짧은 장애 구간이 어느 정도 희석될 수 있다.

운영에서는 다음을 같이 본다.

~~~text
장기간 추세
+
짧은 시간 Window의 급격한 변화
~~~

Grafana에서 1시간 범위를 볼 때와 5분 범위를 볼 때 그래프가 다르게 느껴지는 이유 중 하나다.

## 오류 요청이 빠르면 p95가 좋아 보일 수 있다

다음 결과를 생각해보자.

~~~text
변경 전
p95 = 350ms
error = 0%

변경 후
p95 = 80ms
error = 30%
~~~

변경 후 30%의 요청이 Business Logic을 끝까지 수행하지 않고 즉시 500을 반환했다면 응답 시간이 짧아질 수 있다.

그래서 p95는 항상 정상 응답률과 함께 본다.

~~~text
actual throughput
expected status error
timeout
p50
p95
p99
~~~

정상 요청을 같은 처리량으로 유지하면서 응답 시간이 개선됐는지가 중요하다.

## Timeout은 관측 가능한 최대 응답 시간을 잘라낼 수 있다

클라이언트 Timeout이 3초라고 하자.

실제 서버에서 10초가 걸릴 요청도 클라이언트는 3초에 포기할 수 있다.

따라서 도구에 따라 다음처럼 기록될 수 있다.

~~~text
request duration ≈ 3s
result = timeout
~~~

실제 서버 내부 작업이 10초 계속되었는지는 별도 관측이 필요하다.

Before와 After에서 Timeout 설정이 달라지면 p95 비교도 왜곡될 수 있다.

성능 테스트 설정에 Timeout을 기록해야 하는 이유다.

## Tail Latency가 커질 때 증폭이 일어날 수 있다

하나의 사용자 요청이 내부에서 여러 요청을 병렬로 보내고 모두 끝날 때까지 기다린다고 가정하자.

~~~text
Frontend 요청
→ Service A
→ Service B
→ Service C
→ 모두 완료되어야 응답
~~~

각 Service에서 1% 확률로 매우 느린 요청이 생기면 전체 사용자 요청은 셋 중 하나만 느려도 기다려야 한다.

Fan-out이 큰 시스템에서는 개별 Component의 작은 Tail 확률이 전체 End-to-End Tail을 더 자주 만들 수 있다.

그래서 분산 시스템에서 p99가 특히 중요하게 다뤄지는 경우가 있다.

Commerce Monolith에서도 한 요청이 여러 DB Query와 외부 API를 순차/병렬로 호출하면 비슷한 누적 효과를 경험할 수 있다.

## p95가 증가했을 때 먼저 확인할 것

p95 상승은 원인이 아니라 결과다.

다음 순서로 질문을 줄일 수 있다.

~~~text
실제 RPS는 목표를 유지했는가?
오류율이 증가했는가?
Timeout이 증가했는가?
dropped iteration이 있는가?

Process가 Restart/OOM 되었는가?

CPU / Memory / I/O는 어떤가?

GC Pause가 있었는가?
Thread 수가 늘었는가?

Tomcat Busy Thread는 어떤가?
Hikari pending은 있는가?

DB Query / Lock / I/O는 어떤가?
~~~

p95 자체가 “DB가 문제다”라고 말해주지는 않는다.

어느 요청 구간에서 문제가 생겼다는 신호만 준다.

## 숫자를 실제로 읽어보는 예

200 RPS 결과:

~~~text
target = 200
actual = 199

error = 0%
dropped = 0

p50 = 45ms
p95 = 110ms
p99 = 180ms
max = 240ms
~~~

이 상태에서는 목표 부하를 거의 만들었고 오류가 없으며 Tail도 비교적 짧다.

250 RPS 결과:

~~~text
target = 250
actual = 245

error = 0.5%
dropped = 0

p50 = 52ms
p95 = 850ms
p99 = 2,400ms
max = 3,000ms
~~~

p50은 조금만 증가했지만 p95와 p99가 크게 늘었다.

이 결과는 대부분 요청 자체가 10배 느려진 것보다 일부 요청에서 대기가 크게 증가했을 가능성을 보여 준다.

이때 Hikari pending, Lock, 특정 Query, GC Pause 같은 Tail 원인을 조사한다.

## 백분위는 단독 성능 점수가 아니다

p95 100ms가 항상 좋은 값이고 500ms가 항상 나쁜 값이라고 일반화할 수 없다.

업무 특성에 따라 요구가 다르다.

검색 자동완성은 수백 ms도 길게 느껴질 수 있지만 대규모 보고서 생성은 수초가 정상일 수 있다.

따라서 백분위는 **서비스 목표와 사용자 기대 안에서 평가**해야 한다.

다른 회사의 p95 수치를 그대로 목표로 가져오기보다 현재 기준선과 SLO를 먼저 정의한다.

## 운영 사례는 숫자와 자원을 함께 본다

카카오 사례는 RPS, p50/p95/p99, Error Rate를 먼저 보고 CPU, Memory, Connection, Thread로 내려간다.

올리브영 사례도 대규모 트래픽에서 p50, p75, p95와 CPU/Memory, 성공률을 같이 본다.

우아한형제들 사례는 평균과 Max, p95, p99를 함께 비교해 중심과 극단 지연을 분리한다.

공통점은 백분위를 하나의 성능 점수처럼 사용하지 않는다는 것이다.

**백분위는 사용자 결과를 압축해서 보여 주고, 내부 자원 지표는 그 결과가 왜 생겼는지 찾는 데 사용한다.**
