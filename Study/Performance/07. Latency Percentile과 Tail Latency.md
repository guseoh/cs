# 응답 시간 백분위와 꼬리 지연

응답 시간을 볼 때 평균만 확인하면 시스템이 실제로 어떤 사용자 경험을 만들고 있는지 놓칠 수 있다.

예를 들어 요청 100개 중 95개는 20ms 안에 끝났지만 5개는 1초 이상 걸렸다고 해보자. 평균값은 이 두 집단을 한 숫자로 섞어서 보여 준다. 평균이 어느 정도 괜찮아 보여도 일부 사용자는 매우 느린 요청을 경험했을 수 있다.

그래서 운영 환경과 부하 테스트에서는 평균 응답 시간과 함께 **백분위 응답 시간(Percentile)**을 자주 본다.

카카오 메시징팀도 스트레스 테스트에서 RPS와 함께 P50, P95, P99를 가장 먼저 확인하는 사용자 관점 지표로 다룬다. 우아한형제들과 올리브영의 실제 운영 사례에서도 평균값만이 아니라 p95, p99 같은 상위 지연 구간을 따로 확인한다.

## 응답 시간(Latency)은 무엇인가

응답 시간은 **요청을 보낸 시점부터 응답을 받을 때까지 걸린 시간**을 뜻한다.

예를 들어 브라우저나 부하 테스트 도구가 상품 목록 API를 호출했다고 하자.

~~~text
요청 전송
→ 서버가 요청을 받음
→ 애플리케이션 처리
→ DB 조회
→ 응답 생성
→ 클라이언트가 응답 수신
~~~

클라이언트 입장에서 이 전체 과정에 80ms가 걸렸다면 그 요청의 응답 시간은 약 80ms라고 볼 수 있다.

다만 “응답 시간”이라는 말은 측정 위치에 따라 범위가 달라질 수 있다.

클라이언트에서 잰 응답 시간에는 네트워크 왕복 시간이 포함될 수 있고, 서버 내부의 특정 구간만 측정한 값에는 네트워크가 포함되지 않을 수 있다. 따라서 서로 다른 도구의 응답 시간을 비교할 때는 **어디서부터 어디까지 측정한 값인지** 확인해야 한다.

## 평균 응답 시간만으로 부족한 이유

다음 두 시스템을 생각해보자.

### 시스템 A

~~~text
100개 요청
모두 100ms
~~~

평균 응답 시간은 100ms다.

### 시스템 B

~~~text
99개 요청
약 20ms

1개 요청
약 8초
~~~

시스템 B의 평균도 계산 방식에 따라 생각보다 크게 보이지 않을 수 있다. 하지만 한 사용자는 8초를 기다렸다.

평균은 전체 값을 하나로 합쳐 중심을 보여 주지만 **느린 요청이 얼마나 존재하는지와 느린 구간이 어디까지 늘어나는지**를 직접 보여 주지 않는다.

이 문제를 보완하기 위해 백분위를 본다.

## 백분위(Percentile)는 무엇인가

백분위는 값을 작은 순서대로 정렬했을 때 **전체 중 몇 퍼센트가 특정 값 이하에 들어오는지**를 나타낸다.

응답 시간 100개를 작은 값부터 정렬했다고 생각해보자.

~~~text
빠른 요청
1번째
2번째
3번째
...
95번째
96번째
...
100번째
느린 요청
~~~

이때 p95는 대략 “95번째 지점의 응답 시간”을 의미한다.

예를 들어:

~~~text
p95 = 300ms
~~~

라면 **전체 요청의 약 95%가 300ms 이하에서 끝났고, 나머지 약 5%는 300ms보다 더 오래 걸렸다는 뜻**이다.

이 문장을 정확하게 읽는 것이 중요하다.

p95가 300ms라는 것은 “95%의 요청이 정확히 300ms 걸렸다”는 뜻이 아니다.

또 “300ms보다 느린 요청이 없다”는 뜻도 아니다. 오히려 가장 느린 약 5%는 300ms를 넘을 수 있다.

## p50은 무엇인가

p50은 50번째 백분위다. 흔히 **중앙값에 가까운 응답 시간**으로 이해한다.

예를 들어:

~~~text
p50 = 40ms
~~~

라면 전체 요청의 절반 정도가 40ms 이하에 들어온다는 뜻이다.

p50은 “대부분의 요청이 평소 어느 정도 속도로 처리되는가”를 보는 데 유용하다.

하지만 p50만 정상이라고 시스템 전체가 정상인 것은 아니다.

~~~text
p50 = 40ms
p95 = 80ms
p99 = 2,000ms
~~~

라면 절반의 요청은 매우 빠르지만 가장 느린 일부 요청에서 큰 지연이 발생하고 있다는 뜻이다.

## p95는 무엇인가

p95는 95번째 백분위다.

운영에서 p95를 자주 보는 이유는 **대부분의 요청은 포함하면서도 평균이 숨길 수 있는 느린 구간을 함께 보기 좋기 때문**이다.

예를 들어 요청 10,000개를 측정했다고 하자.

~~~text
p95 = 200ms
~~~

라면 대략:

~~~text
약 9,500개 요청
→ 200ms 이하

약 500개 요청
→ 200ms 초과 가능
~~~

로 이해할 수 있다.

이때 500개는 “아주 적은 예외”로 치부하기 어려울 수 있다. 하루 요청량이 수백만 건이라면 5%의 느린 요청도 실제 사용자 수로는 매우 많아질 수 있기 때문이다.

그래서 p95는 평균보다 실제 느린 사용자 경험을 더 잘 드러내는 경우가 많다.

## p99는 무엇인가

p99는 99번째 백분위다.

~~~text
p99 = 800ms
~~~

라면 약 99%의 요청이 800ms 이하이고 약 1%는 그보다 더 느릴 수 있다는 뜻이다.

p99는 p95보다 더 극단적인 느린 구간을 본다.

대규모 서비스에서 1%는 작은 수가 아닐 수 있다.

예를 들어 하루 요청이 1,000만 건이면 1%는 10만 건이다.

~~~text
10,000,000 × 0.01
= 100,000
~~~

따라서 p99 악화는 “일부 요청만 느리다”고 끝낼 문제가 아니라 실제 사용자 경험과 운영 안정성에 영향을 줄 수 있다.

LINE의 Kafka 운영 사례에서도 Produce API의 99번째 백분위 응답 시간이 평소보다 크게 악화된 것을 성능 저하의 중요한 신호로 사용했다. 이후 디스크 읽기와 네트워크 스레드 사용률을 함께 보며 원인을 좁혔다.

## p50, p95, p99를 같이 보는 이유

세 값을 같이 보면 분포가 어느 쪽에서 변했는지 감을 잡을 수 있다.

예를 들어 다음 결과를 보자.

~~~text
정상 구간
p50 = 30ms
p95 = 60ms
p99 = 90ms
~~~

부하를 올린 뒤:

~~~text
p50 = 32ms
p95 = 75ms
p99 = 1,500ms
~~~

가 됐다면 중앙적인 요청은 거의 변하지 않았지만 가장 느린 일부 요청에서 큰 문제가 생겼다는 뜻이다.

이런 형태에서는 다음 후보를 생각할 수 있다.

~~~text
일부 요청만 DB Lock을 기다림
특정 쿼리만 느림
Connection Pool 대기 발생
간헐적 GC pause
특정 캐시 미스
일부 네트워크 연결 재생성
스레드 스케줄링 지연
~~~

반대로 p50부터 크게 올라간다면 대부분의 요청 처리 비용 자체가 증가했을 가능성을 더 강하게 볼 수 있다.

카카오 메시징팀도 어떤 백분위가 먼저 악화되는지에 따라 내부 병목을 의심하고 다음 계층으로 내려간다고 설명한다.

## 꼬리 지연(Tail Latency)은 무엇인가

응답 시간 분포에서 가장 느린 쪽을 **꼬리 구간(Tail)**이라고 부른다.

예를 들어:

~~~text
대부분
20~50ms

일부
100~300ms

아주 일부
1~3초
~~~

라면 1~3초에 걸친 느린 요청들이 분포의 꼬리를 만든다.

꼬리 지연은 사용자 경험뿐 아니라 시스템 내부에도 영향을 줄 수 있다.

응답이 늦게 끝나는 요청은 그 시간 동안 다음 자원을 더 오래 점유할 수 있다.

~~~text
Tomcat thread
DB connection
socket
transaction
memory
~~~

느린 요청이 늘면 자원이 오래 묶이고, 새 요청이 기다리기 시작하며, 그 대기가 다시 응답 시간을 늘리는 악순환이 생길 수 있다.

## 응답 시간은 처리 시간만이 아니다

응답 시간이 길어졌다고 해서 애플리케이션 코드 실행 자체가 느려졌다고 단정하면 안 된다.

응답 시간은 단순하게 생각하면 다음 두 부분으로 나눌 수 있다.

~~~text
응답 시간
= 대기 시간
+ 실제 처리 시간
~~~

예를 들어 DB 연결을 얻기 위해 500ms를 기다린 뒤 실제 쿼리는 20ms 만에 끝날 수 있다.

이 경우 쿼리 자체만 보면 빠르지만 사용자가 체감한 응답 시간은 길다.

같은 방식으로 Tomcat thread queue, DB lock, connection pool, 네트워크 연결 등 여러 위치에서 대기가 생길 수 있다.

그래서 p95나 p99가 올라갔다면 “코드가 느려졌다”고 바로 결론내리지 않고 어느 계층에서 대기가 생겼는지 확인해야 한다.

## 최대값(Max)과 p99는 무엇이 다른가

최대값은 측정한 요청 중 가장 느린 단 하나의 값이다.

~~~text
p99 = 500ms
max = 8,000ms
~~~

라면 대부분의 느린 요청도 500ms 부근 안에 있지만 하나의 극단적인 요청이 8초까지 늘어났을 수 있다.

최대값은 이상치를 찾는 데 유용하지만 단 하나의 요청에 매우 민감하다.

그래서 최대값 하나만으로 전체 사용자 경험을 판단하기 어렵다.

반대로 p99만 보면 극단적으로 느린 한두 요청을 숨길 수도 있다.

따라서 p50, p95, p99, max를 함께 보면 분포의 중심과 꼬리, 극단값을 더 입체적으로 볼 수 있다.

우아한형제들의 C++ 시스템 Java 전환 사례도 AVG, MAX, p95, p99를 함께 비교해 전체적인 응답 시간과 극단 구간을 분리해서 본다.

## p75 같은 값도 사용할 수 있다

백분위는 p50, p95, p99만 존재하는 것이 아니다.

목적에 따라 p75, p90 등 다른 지점을 볼 수도 있다.

예를 들어 올리브영의 대규모 트래픽 운영 사례에서는 p50, p75, p95를 함께 모니터링해 전체 요청의 중간 구간과 상위 지연 구간이 안정적으로 유지되는지 확인했다.

중요한 것은 “무조건 p95를 써야 한다”가 아니라 서비스 특성과 목표에 맞는 지점을 정하고 같은 기준으로 계속 비교하는 것이다.

## 작은 표본에서는 p99를 조심해서 해석한다

요청을 10,000개 측정했을 때 p99는 상당한 수의 요청을 기반으로 한다.

하지만 요청이 30개뿐이라면 p99는 사실상 가장 느린 한두 개 값에 매우 크게 영향을 받는다.

예를 들어:

~~~text
29개 요청 = 약 20ms
1개 요청 = 500ms
~~~

라면 p99가 크게 튈 수 있다.

이 값이 실제로 반복되는 꼬리 지연인지, 단 한 번 발생한 일회성 이상치인지 짧은 표본만으로는 판단하기 어렵다.

그래서 짧은 보정 실험이나 상태 확인에서는 p50은 중앙적인 상태, p95는 느린 구간의 방향, p99와 max는 이상치 참고로 보고 장시간 또는 반복 측정에서 꼬리 지연이 재현되는지 확인하는 편이 안전하다.

## 백분위 계산은 도구마다 조금 다를 수 있다

“p95”라는 이름이 같아도 모든 도구가 정확히 같은 방식으로 계산하는 것은 아니다.

대표적으로 실제 측정값 중 특정 순위 값을 선택하거나, 인접 값 사이를 보간하거나, Histogram 구간에서 근사하는 방식이 있다.

특히 Prometheus Histogram의 quantile은 원래 요청 하나하나의 raw latency를 정렬해서 구하는 방식과 다르다. 미리 나눈 구간에 누적된 개수를 기반으로 근사하기 때문이다.

따라서 서로 다른 도구에서 나온 p95를 소수점 단위까지 정확히 같은 값이라고 기대하면 안 된다.

Before/After 비교에서는 가능한 한 같은 도구, 같은 측정 구간, 같은 bucket 설정, 같은 집계 방식, 같은 요청 조건을 유지해야 한다.

## 시간 구간도 중요하다

10분 전체의 p95와 1분 단위 p95는 같은 의미가 아니다.

예를 들어 10분 중 9분은 빠르고 1분만 심하게 느렸다면 전체 10분 통계에서는 짧은 장애 구간이 어느 정도 희석될 수 있다.

그래서 운영에서는 전체 기간 추세와 짧은 시간 창의 급격한 변화를 같이 본다.

카카오의 관측성 사례도 p50, p90, p95 같은 절대값 하나로 서비스 상태를 단정하지 않고 이전 상태나 변경 전후와 비교해 해석하는 관점을 강조한다.

## 오류와 응답 시간을 반드시 같이 본다

응답 시간만 좋아졌다고 성능이 개선된 것은 아니다.

다음 예를 보자.

~~~text
변경 전
p95 = 350ms
오류율 = 0%

변경 후
p95 = 100ms
오류율 = 25%
~~~

변경 후 서버가 정상 로직을 끝까지 처리하지 않고 빠르게 500 오류를 반환한다면 실패 요청이 빨리 끝난 덕분에 p95가 낮아질 수 있다.

그래서 최소한 실제 처리량, 오류율, p50, p95, p99, dropped iteration을 함께 본다.

부하 테스트에서는 “응답 시간이 낮아졌다”보다 **정상 요청을 목표 처리량으로 유지하면서 응답 시간이 낮아졌는가**가 중요하다.

## 시간 초과 요청은 어떻게 볼 것인가

시간 초과(Timeout)는 특히 주의해야 한다.

부하 도구나 클라이언트가 3초에서 요청을 포기하도록 설정되어 있으면 실제 서버 내부에서는 그보다 더 오래 작업을 수행하고 있을 수도 있다.

또 도구에 따라 시간 초과 요청이 응답 시간 통계에 포함되는 방식이 다를 수 있다.

따라서 테스트 설정에는 요청 시간 초과 기준, 연결 시간 초과 기준, 실패 요청의 응답 시간 집계 방식, 오류율 계산 방식을 명확히 기록한다.

이 정보가 없으면 서로 다른 실험의 p95를 정확하게 비교하기 어렵다.

## p95가 올라갔을 때 어디를 볼 것인가

p95 상승은 원인이 아니라 증상이다.

다음과 같은 흐름으로 좁힌다.

~~~text
p95 상승 확인
→ 실제 RPS 유지 여부 확인
→ 오류율 확인
→ dropped iteration 확인
→ CPU / memory 확인
→ JVM GC / thread 확인
→ Tomcat thread 확인
→ Hikari active/pending 확인
→ DB latency / lock / query 확인
~~~

예를 들어 p50은 거의 같은데 p95가 증가했고 Hikari pending과 DB query latency가 같이 증가했다면 일부 요청이 DB connection 또는 query를 기다리는 가설이 강해진다.

반대로 p50, p95, p99가 모두 증가하고 CPU가 거의 100%인데 DB가 정상이라면 애플리케이션 CPU 포화 쪽을 더 먼저 의심할 수 있다.

이처럼 백분위는 원인을 직접 알려주는 값이 아니라 **어느 요청 구간에서 문제가 커지고 있는지 알려주는 출발점**이다.

## 실제 숫자로 읽어보기

다음 결과를 보자.

~~~text
target = 200 RPS
actual = 199 RPS
error = 0%
p50 = 45ms
p95 = 110ms
p99 = 180ms
max = 240ms
~~~

이 결과는 목표 요청량을 거의 유지했고 오류도 없으며 느린 구간도 비교적 제한적이라고 해석할 수 있다.

이후 250 RPS에서:

~~~text
target = 250 RPS
actual = 238 RPS
error = 1.8%
p50 = 50ms
p95 = 900ms
p99 = 2,500ms
max = 3,000ms
~~~

가 됐다면 중앙값은 조금만 증가했지만 꼬리 지연이 급격히 커졌다.

이때 핵심 질문은 “왜 일부 요청만 오래 기다리는가?”다.

Connection Pool, lock, 특정 쿼리, GC, thread queue처럼 일부 요청에만 크게 영향을 주는 대기 원인을 확인해야 한다.

## 핵심 정리

p50, p95, p99는 단순히 외워야 할 약어가 아니다.

p50은 중앙적인 요청 경험을, p95와 p99는 느린 요청 구간이 얼마나 커지는지를 보기 위한 압축된 분포 정보다.

하지만 이 값만으로 원인을 알 수는 없다. 처리량, 오류율, 누락 실행, CPU, 메모리, 스레드, 연결, DB 상태와 함께 봐야 한다.

특히 p95가 높아졌다면 “95%의 사용자가 느리다”라고 읽는 것이 아니라 **전체 요청의 약 95%가 그 값 이하에 있고, 나머지 느린 약 5%가 어디에서 기다리고 있는지 조사해야 한다**고 이해하는 것이 정확하다.
