# Latency Percentile과 Tail Latency

평균 latency 하나로는 분포를 볼 수 없다.

100개 중 99개가 20ms이고 1개가 3초라면 평균만으로는 일부 사용자의 매우 느린 요청이 흐려진다.

## p50, p95, p99

응답 시간을 작은 값부터 정렬하면:

- p50: 50%가 이 값 이하
- p95: 95%가 이 값 이하
- p99: 99%가 이 값 이하

p50은 중앙적인 상태, p95/p99는 tail을 보는 데 유용하다.

## Tail Latency

Tail이 커지는 대표 원인:

- queueing
- GC pause
- DB lock
- connection pool wait
- cache miss
- disk I/O
- network retransmission
- thread scheduling
- 특정 slow query

LINE Kafka 사례에서는 Produce API p99가 크게 악화된 시점에 disk read와 network thread utilization도 같이 확인했다.

- [LINE — Kafka를 사용하는 방법 2편](https://engineering.linecorp.com/ko/blog/how-to-use-kafka-in-line-2/)

## p50은 정상인데 p99만 나쁠 수 있다

~~~text
정상
p50 20ms
p95 35ms
p99 60ms

문제
p50 21ms
p95 40ms
p99 1500ms
~~~

소수 요청에만 GC, lock, connection setup 같은 문제가 발생할 수 있기 때문이다.

LINE 신년 트래픽 사례도 피크에서 connection 생성 latency와 Full GC 문제가 드러났다.

- [LINE — 메시징 서버가 새해 트래픽을 대비하는 과정](https://engineering.linecorp.com/ko/blog/how-line-messaging-servers-prepare-for-new-year-traffic)

## 소표본 p99

표본이 30개면 p99는 사실상 마지막 한두 개 값의 영향을 매우 크게 받는다.

~~~text
29개 ≈ 20ms
1개 = 400ms
~~~

이면 p99가 크게 뛴다.

짧은 calibration에서는:

- p50: 중심 상태
- p95: tail 방향
- p99/max: outlier 참고

정도로 보는 것이 안전하다.

## Percentile 계산 방식

도구마다 nearest-rank, interpolation, histogram quantile 같은 방식이 다를 수 있다.

따라서 서로 다른 도구의 p95를 비교할 때는 계산 방식도 확인한다.

Before/After에서는 같은 도구와 같은 집계 방식을 유지한다.

## Error와 같이 본다

~~~text
Before
p95 300ms
error 0%

After
p95 100ms
error 20%
~~~

이면 좋은 개선이 아닐 수 있다. 실패 요청이 빨리 끝나 latency만 낮아졌을 수도 있다.

따라서:

~~~text
Throughput
+ Error
+ Percentile
~~~

을 함께 본다.

k6 Threshold도 latency percentile과 error rate를 함께 PASS/FAIL로 만들 수 있다.

- [Grafana k6 — Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)

## Queueing과 Tail

포화점에 접근하면 service time보다 queueing time이 급격히 커질 수 있다.

~~~text
Response Time
= Queueing Time
+ Service Time
~~~

CPU가 아직 100%가 아니더라도 Connection Pool이나 thread queue가 tail latency를 키울 수 있다.

## 정리

Percentile은 “좋아 보이는 숫자”가 아니라 분포를 압축해서 보는 도구다. 표본 수, 계산 방식, error, workload가 다르면 같은 p95라는 이름도 직접 비교할 수 없다.
