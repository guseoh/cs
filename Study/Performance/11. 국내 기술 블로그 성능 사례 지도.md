# 국내 기술 블로그 성능 사례 지도

성능 개념을 책이나 공식 문서만으로 공부하면 각 지표가 실제 장애와 개선 과정에서 어떻게 사용되는지 감이 잘 오지 않을 수 있다.

예를 들어 p95의 정의를 알고 있어도 실제 팀이 p95가 올라갔을 때 CPU, Thread, DB 중 어디부터 보는지 모를 수 있다. HikariCP의 active와 pending을 이해해도 실제 장애에서 왜 Pool Size만 늘리면 안 되는지 연결하기 어려울 수 있다.

이 문서는 링크를 많이 모아놓는 자료실이 아니다.

**각 국내 기술 사례를 어떤 질문을 가지고 읽어야 하는지 설명하는 읽기 지도**다.

하나의 사례를 읽을 때 “어떤 기술을 썼는가”보다 다음을 본다.

~~~text
어떤 문제가 있었는가?
처음에는 무엇을 원인으로 의심했는가?
어떤 지표로 후보를 줄였는가?
무엇이 실제 원인이었는가?
어떤 변경을 했는가?
변경 뒤 무엇을 다시 측정했는가?
새로운 대가는 무엇이었는가?
~~~

이 관점으로 읽으면 특정 회사의 도구와 환경이 달라도 문제 해결 방식은 자신의 프로젝트에 가져올 수 있다.

## LINE 성능 테스트 자동화 사례는 “문제가 있다”에서 “어디가 문제인가”로 넘어가는 과정을 보여 준다

LINE의 서버 사이드 테스트 자동화 여정 4편은 성능 테스트를 자동화하면서 어떤 데이터를 함께 수집해야 하는지 설명한다.

처음에는 CPU, Memory, Load, Swap, Disk I/O, 초당 처리량, 처리 시간 같은 기본 지표를 생각한다.

하지만 이런 지표만으로는 “성능이 나쁘다”는 사실은 알 수 있어도 “왜 나쁜가”를 바로 알기 어렵다는 문제가 생긴다.

그래서 JVM 쪽으로 관측 범위를 넓힌다.

~~~text
GC
Heap
Thread 상태
Direct Memory
Thread 수
Open File Descriptor
Log 양
~~~

이 사례를 읽을 때 중요한 것은 Prometheus와 Grafana라는 도구 이름이 아니다.

**성능 테스트가 문제를 발견하는 것에서 끝나면 재현과 진단을 다시 해야 하므로, 테스트 순간에 원인 후보를 좁힐 자료도 함께 수집해야 한다**는 판단이다.

## LINE 5편은 정상 운영에서는 보이지 않던 Thread 문제를 성능 테스트가 어떻게 드러내는지 보여 준다

5편에서는 실제 자동 성능 테스트를 적용한 뒤 서버 기동 직후 많은 요청이 몰렸을 때 수백 개 Thread가 BLOCKED 상태에 머무르는 문제가 발견된다.

평상시 배포에서는 서버 기동 직후 그렇게 많은 요청이 몰리지 않기 때문에 문제가 잘 보이지 않았다.

하지만 대규모 장애 후 일부 서버만 먼저 복구되어 평소보다 큰 요청을 한꺼번에 받는다면 실제 장애 복구 과정에서 같은 문제가 발생할 수 있었다.

이 사례를 읽으면서 다음 흐름을 본다.

~~~text
일반 기능 테스트
→ 문제 없음

특정 부하 패턴
→ 문제 재현

Thread Metric
→ 이상 발견

Lock / 초기화 경로
→ 원인 확인
~~~

즉 성능 테스트는 단순 최대 RPS 경쟁이 아니라 **평상시에는 드러나지 않는 동시성·초기화·복구 상황의 문제를 만드는 도구**이기도 하다.

## 카카오 실시간 댓글 사례는 장시간 연결의 성능 문제가 일반 HTTP와 다를 수 있음을 보여 준다

## NAVER D2 GC 튜닝 글은 다른 서비스의 JVM Option을 복사하면 안 되는 이유를 보여 준다

GC 튜닝은 인터넷에서 좋은 Option을 찾아 붙이는 작업이 아니다.

Heap 크기, 객체 생명 주기, Allocation Rate, CPU 수, Latency 요구가 서비스마다 다르다.

NAVER D2의 GC 튜닝 글은 실제 상태를 모니터링하고 문제를 확인한 뒤 튜닝하고 다시 결과를 보는 접근을 이해하는 데 도움이 된다.

이 글을 읽을 때 “어떤 Option이 좋다”보다 다음 흐름을 본다.

~~~text
현재 상태 측정
→ 문제 정의
→ 변경
→ 다시 측정
~~~

이 흐름은 JVM뿐 아니라 모든 성능 개선의 기본이다.

## 우아한형제들 HikariCP 사례는 Pool Size를 단독 숫자로 보면 안 된다는 것을 보여 준다

Connection Pool 장애를 보면 가장 먼저 maximumPoolSize를 늘리고 싶어진다.

하지만 우아한형제들 사례에서는 Thread 수, 하나의 Task가 동시에 요구하는 Connection 수, Pool Size가 서로 연결되어 있었다.

특히 개발자가 한 작업에서 Connection 하나만 사용할 것이라고 생각했지만 실제 실행에서는 추가 Connection 요청이 발생하는 경로가 있었다.

이 사례를 읽으면서 다음을 본다.

~~~text
Application Thread는 몇 개인가?
한 Task가 동시에 몇 Connection을 요구하는가?
Connection을 얼마나 오래 잡는가?
Pool Size는 얼마인가?
대기 Timeout은 얼마인가?
~~~

Pool Size는 DB 동시성을 제한하는 문이기도 하다.

무작정 늘리면 DB가 더 많은 Query를 동시에 받아 오히려 느려질 수 있다.

## 우아한형제들 포인트 시스템 사례는 업무량에서 성능 목표를 만드는 방식을 보여 준다

성능 목표를 임의로 “1,000 TPS”라고 정하면 그 숫자가 실제 서비스 요구와 연결되지 않는다.

신규 포인트 시스템 전환 사례에서는 주말 피크 주문량을 기준으로 포인트 요청량을 추정해 목표 TPS를 정한다.

이후 nGrinder로 부하를 만들고 Pinpoint와 RDS를 확인해 병목을 수정하고 다시 테스트한다.

이 사례에서 배울 핵심 흐름은 다음이다.

~~~text
비즈니스 업무량
→ 목표 부하 도출
→ 테스트
→ APM / DB 관측
→ 병목 수정
→ 다시 테스트
~~~

또 RDS 사양 비교 사례에서는 더 높은 사양이 모든 작업에서 항상 더 빠르지 않을 수 있다는 점도 보여 준다.

Storage 구조와 Network 경로 같은 실제 아키텍처 특성이 특정 작업에 큰 영향을 줄 수 있다.

## LINE messaging-hub 사례는 OOM을 Heap 하나로 보면 안 되는 이유를 보여 준다

Container 환경에서 OOM이 발생했다고 하자.

Heap Dump만 보고 Leak이 없으면 “메모리 문제는 아니다”라고 생각할 수 있다.

하지만 JVM Process는 Heap 외에도 Thread Stack, Metaspace, Direct Memory 등 Native Memory를 사용한다.

LINE messaging-hub 사례에서는 Kubernetes Container 환경과 JVM Memory 설정을 함께 보면서 OOMKilled 문제를 다룬다.

또 WebSocket Connection 문제를 조사하면서 File Descriptor, TIME_WAIT, Port 범위 같은 Linux/Network 요소도 확인한다.

한 사례에서 다음 계층이 연결된다.

~~~text
Application
JVM
Container
Linux
Network
~~~

## LINE Armeria 사례는 Blocking Thread 모델의 한계를 이해하는 데 도움이 된다

Blocking 방식에서는 Request가 I/O를 기다리는 동안 Thread가 점유될 수 있다.

동시 요청이 많아지고 뒤쪽 I/O가 느려지면 Thread가 많이 쌓일 수 있고 Context Switch와 Memory 비용도 증가한다.

LINE의 Armeria 글은 비동기 방식으로 이런 문제를 어떻게 접근했는지 설명한다.

이 글을 읽을 때 “Reactive가 무조건 더 좋다”라고 결론내리면 안 된다.

현재 프로젝트에서 실제 병목이 Thread Blocking인지, DB 처리량인지, Lock인지 먼저 측정해야 한다.

Architecture 변경은 측정된 한계를 해결할 때 의미가 있다.

## 카카오 MySQL Index 사례는 같은 데이터량에서도 Hotspot 때문에 처리량이 달라질 수 있음을 보여 준다

Index가 있다는 사실만으로 성능을 설명할 수 없다.

카카오의 Ascending/Descending Index 실험에서는 Query가 Index의 특정 Page에 집중되는 Hotspot 상황에서 Thread 간 Page 경합이 커지고 처리량 차이가 크게 나타나는 결과를 보여 준다.

이 사례를 읽을 때는 Ascending Index가 무조건 빠른지 느린지를 외우는 것이 목적이 아니다.

**데이터 접근 분포가 균등한가, 특정 위치에 몰리는가가 성능을 바꿀 수 있다**는 점을 본다.

## KISA TOCTOU 공지는 성능 실험 Script의 Source 신뢰 경계와 연결된다

TOCTOU는 보안 취약점 용어라 성능 학습과 멀어 보일 수 있다.

하지만 성능 실험에서 root 권한 Script가 승인 Source를 검증한 뒤 실행한다면 검사 시점과 실행 시점 사이에 Path가 바뀌는 문제는 실제 안전 경계가 된다.

KISA 공지를 통해 TOCTOU가 이론적 단어가 아니라 실제 제품 취약점 유형이라는 점을 확인할 수 있다.

성능 실험을 운영 환경 가까이에서 실행할수록 재현성과 안전성은 분리되지 않는다.

## 기술 블로그를 읽을 때 결과보다 조사 과정을 옮긴다

다른 회사의 결과 숫자는 자신의 시스템에 그대로 적용할 수 없다.

~~~text
다른 CPU
다른 Memory
다른 Dataset
다른 Traffic
다른 Architecture
다른 DB
~~~

이기 때문이다.

가져와야 하는 것은 다음과 같은 문제 해결 방식이다.

~~~text
어떤 현상을 먼저 확인했는가
어떤 Metric을 봤는가
어떤 가설을 버렸는가
어떤 추가 자료를 수집했는가
어떤 최소 변경을 했는가
어떻게 재검증했는가
~~~

이 과정을 자신의 프로젝트에 적용하면 기술 블로그가 단순한 성공 사례 모음이 아니라 **성능 문제를 분석하는 사고방식 자료**가 된다.
