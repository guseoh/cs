# 재현 가능한 성능 실험과 안전한 격리

성능 테스트는 한 번 숫자를 얻는 것으로 끝나지 않는다.

오늘 p95가 120ms였고 다음 주에는 250ms가 나왔다고 해보자. 두 결과를 비교하려면 어떤 코드와 Container Image를 사용했는지, Dataset이 같은지, 요청량과 측정 시간이 같은지, JVM과 DB 설정이 같은지 알아야 한다.

조건을 다시 만들 수 없다면 결과 차이를 설명하기 어렵다.

그래서 성능 실험에는 두 가지 축이 필요하다.

첫 번째는 **재현 가능성**이다. 어떤 Source, Image, Dataset, 설정과 Workload로 결과가 만들어졌는지 나중에 다시 복원할 수 있어야 한다.

두 번째는 **안전한 격리**다. 성능 실험을 위해 만든 Synthetic Data와 Runtime이 실제 Production 데이터와 서비스에 의도하지 않은 변경을 만들지 않아야 한다.

이 문서에서는 Git Commit SHA, 불변 Source, Image Digest, Checksum, Provenance, 데이터 격리, 자원 격리, Fail-closed, TOCTOU, Symbolic Link, File Permission, Cleanup 같은 개념이 왜 성능 실험과 연결되는지 설명한다.

## 재현 가능성은 같은 명령어를 다시 입력할 수 있다는 뜻보다 넓다

다음 명령을 저장해두었다고 하자.

~~~text
k6 run test.js
~~~

이 명령을 내일도 실행할 수 있다고 해서 같은 실험이 되는 것은 아니다.

내일 다음 조건이 달라질 수 있기 때문이다.

~~~text
test.js 내용
Backend code
Docker image
Dataset
DB schema
JVM option
RPS setting
Network path
~~~

재현 가능한 실험은 **명령어뿐 아니라 입력과 실행 환경의 identity를 다시 찾을 수 있는 실험**이다.

예를 들어 최소한 다음을 연결한다.

~~~text
Source Commit SHA
Container Image Digest
Dataset ID
Dataset Checksum / Provenance
Runtime Config
Workload Config
Start / End Time
Result Directory
~~~

LINE의 성능 테스트 자동화 사례에서도 테스트할 Build 결과물을 Docker Image로 만들어 특정 결과를 다시 실행할 수 있게 하는 방향을 사용한다.

## Branch 이름은 움직이고 Commit SHA는 특정 시점을 가리킨다

Git의 main Branch는 계속 움직인다.

~~~text
오늘
main → Commit A

내일 Merge
main → Commit B
~~~

“main으로 테스트했다”고만 기록하면 나중에 정확히 어떤 Source인지 알기 어렵다.

반면 Commit SHA는 특정 Git Commit을 식별한다.

~~~text
7d2cf59c...
~~~

처럼 정확한 SHA를 기록하면 그 시점의 Source Tree를 다시 찾을 수 있다.

성능 Evidence에서는 Branch 이름보다 Commit SHA를 남기는 이유가 여기에 있다.

## 개발용 Checkout은 실험 중에도 변할 수 있다

개발자가 평소 사용하는 Git Working Tree는 mutable, 즉 변경 가능한 상태다.

~~~text
git pull
branch checkout
local edit
generated file
untracked file
~~~

이런 Checkout을 그대로 Production 진단이나 성능 실험의 실행 Source로 사용하면 실험 중 파일이 바뀔 수 있다.

또 Commit된 내용과 Local 수정이 섞일 수 있다.

그래서 중요한 실험에서는 승인한 Commit의 파일을 별도 Directory에 추출해 실행 Source로 사용할 수 있다.

~~~text
Developer Checkout
→ 계속 변경 가능

Approved Source Snapshot
→ 특정 Commit에서 추출
→ 실험 입력으로 고정
~~~

이렇게 하면 현재 Production Checkout을 움직이지 않고도 특정 승인 Source로 도구와 Script를 실행할 수 있다.

## 불변이라는 말은 실험 중 입력을 바꾸지 않는다는 뜻이다

불변(Immutable) Source나 Dataset은 “영원히 수정할 수 없는 파일”이라는 철학적 의미보다 **해당 실험에서 승인한 입력을 중간에 바꾸지 않는다는 운영 계약**으로 이해하면 쉽다.

예를 들어 25 RPS를 측정한 뒤 Dataset Manifest가 수정되고, 50 RPS를 새 Manifest로 측정하면 두 단계는 같은 Dataset을 사용한 것이 아니다.

~~~text
25 RPS
Dataset A

50 RPS
Dataset B
~~~

이 결과를 하나의 Capacity Series처럼 비교하면 잘못된 해석이 된다.

그래서 다음 순서를 사용할 수 있다.

~~~text
Dataset 생성
→ 검증
→ 읽기 전용 고정
→ 전체 실험 수행
~~~

## Linux Permission 0444와 0555를 어떻게 읽는가

Linux File Mode 숫자는 Read, Write, Execute Permission을 합쳐 표현한다.

~~~text
4 = read
2 = write
1 = execute
~~~

Regular File의 0444는 Owner, Group, Other 모두 Read만 가능하고 Write는 없다는 뜻이다.

~~~text
Owner  r--
Group  r--
Other  r--
~~~

Directory의 0555는 읽고 탐색할 수 있지만 Write가 없다는 뜻이다.

~~~text
Owner  r-x
Group  r-x
Other  r-x
~~~

Directory에서 Write가 없으면 일반적으로 새 Entry를 만들거나 이름을 바꾸고 삭제하는 작업을 제한할 수 있다.

중요한 Source Tree를 root-owned + no-write 상태로 고정하는 이유는 검증 후 내용이 바뀌는 위험을 줄이기 위해서다.

## Checksum은 파일 내용이 같은지 확인하는 지문이다

Checksum은 File Content를 기반으로 계산한 값이다.

SHA-256 같은 Cryptographic Hash를 사용하면 File Content가 달라질 때 매우 높은 확률로 다른 Digest가 나온다.

~~~text
manifest.json A
→ SHA-256 abc...

한 Byte 변경

manifest.json B
→ SHA-256 xyz...
~~~

그래서 Checksum은 다음 질문에 답하는 데 유용하다.

~~~text
지금 이 File은
이전에 승인한 File과
Byte 단위로 같은가?
~~~

하지만 Checksum만으로는 File이 어떤 코드로 만들어졌는지 알 수 없다.

## Provenance는 결과가 어디에서 만들어졌는지 연결한다

Provenance는 한국어로는 출처 정보, 생성 이력에 가깝다.

Dataset을 예로 들면 다음을 연결할 수 있다.

~~~text
Approved Source SHA
Generator File SHA-256
Wrapper SHA-256
Base Manifest SHA-256
Seed
Target Product Count
Generated Manifest SHA-256
Report SHA-256
~~~

이렇게 연결하면 다음 질문에 답할 수 있다.

~~~text
이 Dataset은 어떤 Source에서 만들었는가?
어떤 Generator를 사용했는가?
같은 Seed를 사용했는가?
목표 Row 수는 무엇이었는가?
설치된 File이 승인 결과와 같은가?
~~~

Checksum은 특정 File의 동일성을 보고, Provenance는 **그 File의 생성 과정과 입력을 연결한다.**

## 재생성 검증은 Checksum만 비교하는 것보다 더 강하다

Generated Manifest와 Report의 Checksum이 기록되어 있다고 하자.

두 File이 서로 맞는 것만으로는 잘못된 Generator로 둘 다 생성되었을 가능성을 배제하지 못한다.

더 강한 검증은 승인된 Source의 Generator를 다시 실행해 결과를 재생성한 뒤 설치된 File과 비교하는 것이다.

~~~text
Approved Generator
+ Same Seed
+ Same Target

→ Dataset 재생성

재생성 Manifest
vs
설치 Manifest

Byte 동일성 확인
~~~

이 검증은 **승인된 생성 코드가 현재 Dataset을 다시 만들 수 있다**는 근거를 추가한다.

## Docker Image Tag는 고정된 Version이 아닐 수 있다

다음 Image Tag를 사용한다고 하자.

~~~text
backend:latest
~~~

latest Tag가 오늘 Image A를 가리키고 내일 Image B를 가리킬 수 있다.

특정 Version Tag도 Registry 운영 방식에 따라 다시 Push할 수 있다면 절대적인 불변 식별자가 아닐 수 있다.

Image Digest는 Image Content에 연결된 식별자다.

~~~text
registry/backend@sha256:...
~~~

재현 가능한 실험에서는 Digest로 Image를 고정하면 “같은 이름의 다른 Image”가 실행되는 위험을 줄일 수 있다.

~~~text
Image 존재 확인
→ Platform 확인
→ RepoDigest 확인
→ pull 없이 실행
~~~

처럼 계약을 만들 수 있다.

관련 자료:
- [LINE — Immutable Kubernetes Architecture](https://engineering.linecorp.com/ko/blog/immutable-kubernetes-architecture-deepdive/)

## pull을 막는 이유는 실행 순간 입력이 바뀌지 않게 하기 위해서다

실험 직전에 Docker가 Registry에서 새 Image를 자동으로 가져오면 검증한 Image와 실제 실행 Image가 달라질 수 있다.

따라서 이미 승인하고 검증한 Local Image를 사용할 때는 --pull never 같은 경계를 사용할 수 있다.

이것은 Docker 사용법 자체보다 **실행 순간에 입력을 암묵적으로 바꾸지 않는다**는 재현성 원칙과 연결된다.

## 데이터 격리와 자원 격리는 서로 다르다

같은 Managed MySQL DB System 안에 다음 두 Schema가 있다고 하자.

~~~text
Production Schema
pawcycle_prod

Performance Schema
pawcycle_perf
~~~

Performance DB Account가 performance Schema에만 권한을 가지고 Production Schema에는 접근하지 못하도록 구성했다면 Synthetic Data가 실제 Customer Table에 섞이는 위험을 크게 줄일 수 있다.

이것을 데이터 격리(Data Isolation)라고 볼 수 있다.

하지만 두 Schema가 같은 MySQL DB System에 있다면 다음 Resource는 공유할 수 있다.

~~~text
CPU
Memory
Buffer Pool
Storage
I/O
Connection Capacity
~~~

즉:

~~~text
Data Isolation
= 있음

Resource Isolation
= 완전하지 않음
~~~

이다.

성능 실험 중 Performance Query가 DB CPU를 많이 사용하면 Production Query와 경쟁할 수 있다.

따라서 데이터가 분리됐다고 실제 서비스 영향 가능성이 0이 되는 것은 아니다.

## 같은 Host의 별도 Container도 완전한 자원 격리는 아니다

Backend Production Container와 Performance Container가 별도 Compose Project와 Network에 있어도 같은 app Host에서 실행하면 Host CPU와 Memory는 공유할 수 있다.

~~~text
Production Backend ─┐
                    ├→ same Host CPU / RAM
Performance Backend ┘
~~~

따라서 성능 실험 중 Production Health를 같이 확인해야 한다.

완전한 Resource Isolation이 필요하면 별도 Compute나 별도 DB가 필요할 수 있지만 비용과 운영 복잡성이 늘어난다.

현재 위험에 필요한 수준으로 경계를 설계한다.

## Loopback 주소는 외부 노출 범위를 줄인다

127.0.0.1은 현재 Host 자신을 가리키는 IPv4 Loopback 주소다.

성능용 Backend를 다음처럼 Bind한다고 하자.

~~~text
127.0.0.1:18080
~~~

일반적으로 Host의 외부 Network Interface에는 직접 Listener가 노출되지 않고 같은 Host에서 접근할 수 있다.

새 Public Port, DNS, Load Balancer를 만들지 않고 내부 실험 Endpoint를 만들 수 있다.

## SSH Local Forward는 Loopback Endpoint를 Desktop으로 연결한다

성능용 Backend가 app Host의 127.0.0.1에서만 열려 있으면 외부 Desktop의 k6가 직접 접근할 수 없다.

SSH Local Forward를 사용하면 Desktop의 Local Port를 SSH Tunnel을 통해 원격 Host의 Loopback Port에 연결할 수 있다.

~~~text
Desktop
127.0.0.1:19080
      │
      │ SSH Tunnel
      ▼
app Host
127.0.0.1:18080
~~~

이 구조는 Performance Endpoint를 Public Internet에 직접 공개하지 않으면서 외부 Load Generator를 사용할 수 있게 한다.

다만 이 경로는 실제 Public HTTPS/Nginx 경로와 다르다.

따라서 이 결과를 Production End-to-End Latency와 같은 값으로 해석하지 않는다.

## Fail-closed는 애매한 상태에서 계속 실행하지 않는 방식이다

Fail-closed는 검증에 실패하거나 예상하지 못한 상태를 만났을 때 위험한 동작을 계속하지 않고 중단하는 접근이다.

예를 들어 Dataset ID를 읽지 못했다고 하자.

위험한 방식:

~~~text
Dataset ID 읽기 실패
→ Default Dataset으로 계속 실행
~~~

Fail-closed:

~~~text
Dataset ID 읽기 실패
→ 실행 중단
~~~

운영과 가까운 Script에서는 잘못된 Schema나 Project에 Write하는 것보다 중단하고 다시 확인하는 편이 안전하다.

## 명시적 승인 문자열은 위험 동작의 대상을 다시 확인하게 한다

다음 동작은 실제 상태를 변경한다.

~~~text
Dataset APPLY
Performance Runtime START
Performance Runtime DOWN
Schema DROP
~~~

실수로 Command를 실행하지 않도록 단순 yes 대신 대상 Identity가 들어간 확인 문자열을 요구할 수 있다.

~~~text
APPLY:catalog-core-10k-v1
START:catalog-core-10k-v1
DOWN:pawcycle-performance-catalog
~~~

이것이 인증이나 권한 제어를 대체하지는 않는다.

하지만 사용자가 **지금 어떤 대상에 어떤 위험 동작을 하는지 명시적으로 확인하게 하는 추가 안전장치**가 된다.

## TOCTOU는 검사한 것과 실제 사용한 것이 달라지는 문제다

TOCTOU는 Time Of Check To Time Of Use의 약자다.

검사 시점과 사용 시점 사이에 대상이 바뀌는 Race Condition을 말한다.

root 권한 Script가 다음처럼 동작한다고 하자.

~~~text
1. /approved/scripts/run.py가 안전한지 검사
2. 잠깐의 시간 차이
3. /approved/scripts/run.py 실행
~~~

1번 검사 뒤 3번 실행 전에 공격자나 다른 Process가 Path를 다른 File로 바꿀 수 있다면 문제가 된다.

~~~text
검사할 때
정상 File

검사 후
Path 교체

실행할 때
다른 File
~~~

검사 결과와 실제 실행 대상이 달라졌다.

KISA 보호나라 보안 공지에서도 TOCTOU Race Condition을 실제 제품 취약점 유형으로 다룬다.

관련 자료:
- [KISA 보호나라 — TOCTOU Race Condition 보안 업데이트 권고 사례](https://www.krcert.or.kr/kr/bbs/view.do?bbsId=B0000133&categoryCode=&menuNo=205020&nttId=72064&pageIndex=1&searchCnd=&searchWrd=)

## Symbolic Link는 승인 Directory 밖을 가리킬 수 있다

Symbolic Link는 다른 File이나 Directory를 가리키는 특수한 Link다.

~~~text
/approved/scripts/current.py
→ /tmp/other.py
~~~

겉으로는 approved Directory 아래 Path처럼 보여도 실제 Resolve 결과는 /tmp를 가리킬 수 있다.

그래서 신뢰해야 하는 Source를 root 권한으로 실행할 때는 다음을 검사할 수 있다.

~~~text
Source Root가 Symlink인가?
중간 Directory가 Symlink인가?
최종 File이 Symlink인가?
Canonical Path가 승인 Root 내부인가?
~~~

## 최종 File만 read-only여도 Parent Directory가 writable하면 교체될 수 있다

다음 구조를 생각해보자.

~~~text
/approved
└─ scripts
   └─ run.py
~~~

run.py 자체가 root-owned 0444라고 하자.

하지만 scripts Directory가 일반 사용자에게 writable이라면 그 사용자가 Directory Entry를 바꿔 run.py를 다른 File로 교체할 수 있다.

~~~text
run.py
root-owned 0444

scripts/
other-writable
~~~

즉 최종 File만 안전하게 보여도 **File까지 이어지는 Path 전체가 안전하지 않으면 TOCTOU 위험이 남을 수 있다.**

그래서 privileged Source에서는 Parent Directory Chain을 Trust Boundary로 본다.

~~~text
각 Parent
→ Directory인가?
→ Symlink가 아닌가?
→ 신뢰할 Owner인가?
→ Group/Other Write가 가능한가?
~~~

## Sticky Bit는 공유 Directory의 삭제 권한을 제한한다

/tmp 같은 Directory는 여러 사용자가 File을 만들 수 있도록 writable이다.

이런 공유 Directory에는 Sticky Bit가 설정되어 다른 사용자가 소유한 File을 임의로 삭제하거나 Rename하는 것을 제한할 수 있다.

그래서 Parent Path 검증에서 “writable이면 무조건 거부”보다 root-owned Sticky Directory 같은 제한된 예외를 설계할 수도 있다.

중요한 것은 예외가 무엇인지 명확하게 코드와 Test로 고정하는 것이다.

## trusted 임시 Directory에 File 하나만 복사하는 방식도 항상 맞지는 않는다

TOCTOU를 줄이기 위해 검증한 Script를 root-owned Temporary Directory에 복사한 뒤 실행하는 방법을 생각할 수 있다.

하지만 Script가 자신의 위치를 기준으로 Sibling File을 찾는다면 Wrapper 하나만 복사할 때 의미가 바뀐다.

~~~text
원래

scripts/prepare.py
→ scripts/generator.py 사용
~~~

Wrapper만 /tmp로 복사:

~~~text
/tmp/prepare.py
→ /tmp/generator.py를 찾으려 할 수 있음
~~~

즉 보안 패턴을 기계적으로 적용하면 원래 실행 구조를 깨뜨릴 수 있다.

현재 프로그램이 Path를 어떻게 사용하는지 확인하고 가장 작은 안전한 수정 방식을 선택해야 한다.

## Cleanup은 정상 실행보다 의존성이 적어야 할 수 있다

Cleanup이 필요한 순간은 정상 입력이 깨졌을 가능성이 높은 순간이다.

~~~text
Image 삭제
Dataset 일부 손상
Backend unhealthy
Startup 실패
Config 일부 문제
~~~

Cleanup도 정상 Start와 동일하게 모든 Image와 Dataset을 요구하면 정리 자체가 막힐 수 있다.

그래서 안전한 Cleanup은 다음 원칙을 고려한다.

~~~text
정리 대상 Identity 확인
→ 최소 입력만 사용
→ 정확한 Project만 종료
→ Production 대상은 건드리지 않음
→ 필요하지 않은 Volume 삭제 금지
~~~

복구 경로가 정상 경로보다 더 복잡한 의존성을 가지면 장애 때 사용할 수 없을 수 있다.

## Cleanup 대상 Identity를 확인해야 한다

Compose Project 이름만 같다고 무조건 Container를 내리면 다른 실험이나 잘못된 Runtime을 건드릴 수 있다.

Container Label이나 Dataset ID를 확인해서 현재 Config가 기대하는 Performance Runtime인지 검사할 수 있다.

~~~text
scope = catalog-isolated
dataset = catalog-core-10k-v1
~~~

Expected Identity와 다르면 중단한다.

Fail-closed 원칙을 Cleanup에도 적용하는 것이다.

## 결과 Directory도 실험 Identity의 일부다

이전 실행 결과와 새 결과가 같은 Directory에 섞이면 서로 다른 실험이 하나의 결과처럼 보일 수 있다.

~~~text
어제
25 / 50 / 100 RPS

오늘
25 / 50 RPS만 다시 실행
~~~

Directory를 그대로 재사용하면 어제의 100 RPS Result가 오늘 결과인 것처럼 남을 수 있다.

그래서 중요한 Capacity Series에서는 non-empty Result Directory를 거부하고 실행마다 새로운 Directory를 만드는 것이 안전하다.

## Evidence에 Secret이나 Raw Production Data를 넣지 않는다

재현 가능성을 높이겠다고 모든 입력을 기록하면 안 된다.

다음 값은 Evidence에 직접 남기지 않는다.

~~~text
DB Password
Access Token
Private Key
Session Cookie
실제 고객 개인정보
Raw Production Row
Secret URL
~~~

재현에 필요한 것은 Secret Value 자체가 아니라 **어떤 Secret Boundary와 Config Contract를 사용했는가**다.

예를 들어 Password File Path와 Permission Contract는 기록할 수 있지만 Password 값은 기록하지 않는다.

## Performance Schema Account는 최소 권한을 가져야 한다

별도 Performance Schema를 만들었다면 DB Account도 그 Schema에 필요한 권한만 갖게 한다.

~~~text
Performance Account

ALLOW
pawcycle_perf_control
pawcycle_perf_10k

DENY / no grant
pawcycle_prod
~~~

이렇게 하면 Script에 버그가 있더라도 Credential 자체가 Production Schema Write를 허용하지 않는 추가 방어선이 된다.

Application Level Guard와 DB Privilege Guard를 겹쳐 두는 Defense in Depth다.

## 재현 가능한 실험은 안전 경계까지 함께 기록한다

좋은 성능 Evidence에는 결과 숫자뿐 아니라 다음이 들어간다.

~~~text
Source Commit SHA
Image Digest
Dataset ID
Dataset Provenance
Runtime Config Identity
Network 경계
DB Schema / Account 경계
Workload
Target / Actual RPS
Warm-up / Measurement
Result Directory
Stop Condition
Cleanup 결과
Production Pre/Post Health
~~~

이 정보가 있어야 “어떤 조건에서 얻은 숫자인가”뿐 아니라 “실험이 실제 서비스에 어떤 위험을 가졌고 어떻게 제한했는가”까지 설명할 수 있다.

## 재현성과 안전성은 서로 반대되는 목표가 아니다

성능 실험을 실제 환경과 가깝게 만들수록 Production 자원에 가까워지고 위험도 커질 수 있다.

그래서 단순히 “실제 환경과 동일하게”가 목표가 아니다.

~~~text
실제와 충분히 비슷한 조건
+
Production 데이터 오염 방지
+
위험 동작 명시 승인
+
실패 시 중단
+
정확한 Cleanup
+
재현 가능한 입력
~~~

을 함께 만족시키는 경계를 찾는다.

성능 숫자의 신뢰도는 k6나 Grafana 같은 도구 이름보다 먼저 **실험 입력과 실행 경계가 얼마나 정확하게 고정되어 있는가**에서 시작한다.
