# 재현 가능한 성능 실험과 안전한 격리

성능 테스트는 숫자를 한 번 얻는 것으로 끝나지 않는다. 나중에 같은 조건을 다시 만들 수 있어야 하고, 결과가 어느 코드와 어느 데이터에서 나왔는지 설명할 수 있어야 한다. 또한 테스트 데이터와 테스트용 실행 환경이 실제 서비스에 영향을 주지 않도록 경계를 분리해야 한다.

이 문서에서는 재현 가능성, 정확한 소스 버전, 불변 입력, 출처 정보(Provenance), 데이터 격리와 자원 격리, Fail-closed, image digest, TOCTOU, 심볼릭 링크, 권한 경계와 cleanup을 하나씩 설명한다.

실제 PawCycle 적용은 [[../../Project/pawCycle/Performance/05. Isolated Catalog Runtime과 10K Scale 실행 계약]]에서 별도로 기록한다.

## 재현 가능성이란 무엇인가

재현 가능성은 **나중에 같은 조건을 다시 만들었을 때 같은 문제와 비슷한 결과를 다시 확인할 수 있는 성질**이다.

오늘 p95가 120ms이고 다음 주에는 250ms라고 해도 두 실험의 코드, 데이터, 요청량, JVM 설정이 모두 다르면 코드 변경 때문에 느려졌다고 말할 수 없다.

~~~text
어떤 코드 버전인가
어떤 Container image인가
어떤 Dataset인가
목표 RPS와 실제 RPS는 얼마인가
요청 비율은 같은가
준비 시간과 측정 시간은 같은가
DB와 JVM 설정은 같은가
~~~

이 조건을 기록하고 고정해야 Before/After 비교가 의미를 가진다.

LINE도 성능 테스트용 빌드 결과물을 Docker image로 만들면 나중에 같은 결과물을 다시 실행해 문제를 재현하기 쉽다고 설명한다.

- [LINE — 서버 사이드 테스트 자동화 여정 4](https://engineering.linecorp.com/ko/blog/server-side-test-automation-4/)
- [LINE — 서버 사이드 테스트 자동화 여정 2](https://engineering.linecorp.com/ko/blog/server-side-test-automation-journey-2)

## 정확한 소스 버전이 왜 필요한가

Git의 branch 이름은 움직인다. 오늘 main이 A commit을 가리키더라도 내일 merge가 발생하면 main은 B commit을 가리킬 수 있다.

~~~text
오늘  main → A
내일  main → B
~~~

따라서 “main으로 테스트했다”는 기록만으로는 정확한 코드를 다시 찾기 어렵다.

중요한 실험에서는 40자리 commit SHA처럼 특정 commit 자체를 가리키는 식별자를 남기는 편이 좋다.

~~~text
main
→ 현재 위치를 가리키는 움직이는 이름

commit SHA
→ 특정 시점의 source를 가리키는 고정 식별자
~~~

## 개발 checkout과 실행용 source를 분리하는 이유

평소 개발 checkout은 git pull, branch 변경, 로컬 수정으로 계속 달라질 수 있다. 이런 working tree를 그대로 운영 진단이나 성능 실험 source로 사용하면 실험 중간에 파일이 달라지거나 commit되지 않은 수정이 섞일 수 있다.

승인한 commit의 archive를 별도 Directory에 추출하면 개발 checkout을 건드리지 않고 특정 시점의 source snapshot을 만들 수 있다.

~~~text
개발 checkout
→ 계속 변경 가능

승인 SHA archive
→ 특정 commit의 파일만 추출
→ 실행용 source로 고정
~~~

## 불변 입력은 무엇인가

불변(Immutable)은 실험에 사용하기로 검증한 입력을 실험 도중 바꾸지 않는다는 뜻이다.

Dataset manifest가 25 RPS 실험 뒤 수정되면 50 RPS 실험은 다른 데이터를 사용한 것이 된다. 이 경우 두 결과를 하나의 단계형 실험으로 비교하기 어렵다.

따라서 중요한 입력은 보통 다음 흐름으로 다룬다.

~~~text
생성
→ 검증
→ 쓰기 불가능하게 고정
→ 실험
~~~

Linux permission 0444는 일반적인 regular file에 쓰기 권한이 없고 읽기만 가능하다는 뜻이다. Directory 0555는 Directory를 탐색할 수는 있지만 일반적으로 그 안의 이름을 추가하거나 바꿀 write 권한이 없다는 뜻이다.

## Checksum은 무엇인가

Checksum은 파일 내용을 바탕으로 만든 식별값이다. SHA-256 같은 해시를 사용하면 파일 내용이 달라질 때 다른 digest가 나오는 것을 기대할 수 있다.

~~~text
manifest A
→ SHA-256 abc...

한 byte 수정

manifest B
→ SHA-256 xyz...
~~~

Checksum은 **지금 보는 파일이 이전에 확인한 bytes와 같은가**를 확인하는 데 유용하다.

하지만 checksum만으로는 그 파일을 어떤 코드가 만들었는지까지 알 수 없다.

## 출처 정보(Provenance)는 무엇인가

Provenance는 결과가 어디에서 만들어졌는지를 연결하는 정보다.

성능 Dataset이라면 다음을 하나로 묶을 수 있다.

~~~text
승인 source SHA
생성 wrapper SHA-256
실제 generator SHA-256
base manifest SHA-256
seed
목표 Product 수
생성 manifest SHA-256
report SHA-256
~~~

그러면 “이 10K Dataset이 어떤 코드로 만들어졌는가?”, “같은 코드와 seed로 다시 만들 수 있는가?”, “설치된 결과가 재생성한 결과와 같은가?”에 답할 수 있다.

Checksum이 파일 동일성을 확인한다면 provenance는 **파일의 생성 경로와 근거를 연결한다.**

## 재생성 검증이 더 강한 이유

manifest와 report checksum이 서로 맞아도 두 파일이 잘못된 generator에서 함께 만들어졌을 수 있다.

더 강한 검증은 승인 source의 generator로 Dataset을 다시 만든 뒤 설치된 결과와 byte 단위로 비교하는 것이다.

~~~text
승인 source
+ 같은 seed
+ 같은 target count
→ 다시 생성

재생성 결과
vs
설치된 결과

bytes가 동일한가?
~~~

이렇게 하면 “파일 둘이 서로 맞다”보다 더 강하게 **승인한 생성 로직이 이 Dataset을 재현한다**고 확인할 수 있다.

## 데이터 격리와 자원 격리는 다르다

테스트 환경이 Production과 분리됐다는 말은 무엇이 분리됐는지 구체적으로 봐야 한다.

같은 MySQL DB System을 사용하더라도 별도 schema와 별도 DB account를 쓰면 실험 데이터가 Production table에 섞이지 않도록 만들 수 있다. 이것이 데이터 격리다.

~~~text
same MySQL DB System

Production schema
Performance schema
~~~

하지만 두 schema는 같은 DB System의 CPU, memory, storage, connection capacity를 사용할 수 있다.

~~~text
Production query ─┐
                  ├→ 같은 DB CPU / memory
Performance query ┘
~~~

따라서 **데이터는 분리됐지만 자원은 공유한다**고 말해야 정확하다.

실제 성능 실험에서는 이 공유 자원 때문에 Production health가 나빠지지 않는지도 별도로 확인해야 한다.

## Loopback 주소는 왜 사용하는가

127.0.0.1은 현재 host 자신을 가리키는 loopback 주소다.

실험용 Backend를 127.0.0.1에만 publish하면 일반적으로 외부 network interface에 직접 열지 않고 host 내부에서만 접근할 수 있다.

~~~text
127.0.0.1:18080
→ app01 내부에서만 직접 접근
~~~

외부에 새 public port, DNS, Load Balancer를 만들 필요 없이 SSH tunnel을 통해 desktop 부하 도구에서 접근할 수 있다.

## SSH local-forward는 무엇인가

SSH local-forward는 내 PC의 port로 들어온 연결을 SSH 연결을 통해 원격 서버의 특정 주소와 port로 전달하는 방식이다.

~~~text
desktop
127.0.0.1:19080
      │
      │ SSH tunnel
      ▼
app01
127.0.0.1:18080
~~~

이 구조는 performance endpoint를 Internet에 직접 공개하지 않고도 부하 테스트를 가능하게 한다.

다만 public HTTPS와 Nginx를 거치지 않으므로 결과를 실제 사용자 전체 경로의 절대 latency라고 해석하면 안 된다.

## Fail-closed는 무엇인가

Fail-closed는 검증할 수 없는 상태가 나오면 계속 진행하지 않고 안전한 쪽으로 중단하는 방식이다.

예를 들어 Dataset identity를 읽지 못했다고 하자.

~~~text
위험한 방식
identity 읽기 실패
→ 기본값을 사용해 계속 실행

Fail-closed
identity 읽기 실패
→ 실행 중단
~~~

운영 script에서는 잘못된 대상에 write하는 것보다 멈추고 확인하는 편이 안전하다.

## 명시적 승인 문자열은 왜 필요한가

import apply, runtime start, cleanup처럼 실제 상태를 바꾸는 명령은 오타로 잘못 실행되면 위험하다.

그래서 단순히 명령어 이름만 입력하는 것이 아니라 대상 identity가 들어간 승인 문자열을 요구할 수 있다.

~~~text
APPLY:catalog-core-10k-v1
START:catalog-core-10k-v1
DOWN:pawcycle-performance-catalog
~~~

이것은 완벽한 보안 기능은 아니지만 사용자가 어느 Dataset과 어느 project에 위험 동작을 수행하는지 한 번 더 명시하게 한다.

## Image tag보다 digest가 강한 이유

Docker image tag는 다른 image를 가리키도록 바뀔 수 있다.

~~~text
backend:latest
→ 오늘 image A
→ 내일 image B
~~~

반면 digest는 특정 image content를 가리킨다.

~~~text
registry/backend@sha256:...
~~~

그래서 재현 가능한 실험에서는 image를 digest로 고정하는 것이 좋다. 실행 시 --pull never를 함께 사용하면 검증하지 않은 새 image를 실행 순간에 자동으로 가져오는 것도 막을 수 있다.

LINE의 불변 인프라 글은 image 기반 구조가 재현성을 높이는 이유를 이해하는 데 도움이 된다.

- [LINE — 딥다이브: Immutable Kubernetes Architecture](https://engineering.linecorp.com/ko/blog/immutable-kubernetes-architecture-deepdive/)

## TOCTOU는 무엇인가

TOCTOU는 Time Of Check To Time Of Use의 약자다. 한국어로 풀면 **검사한 시점과 실제 사용한 시점 사이에 대상이 바뀌는 문제**다.

root 권한 script가 다음 순서로 동작한다고 하자.

~~~text
1. /safe/run.py가 안전한 파일인지 검사
2. 잠깐의 시간 차이
3. /safe/run.py 실행
~~~

1번과 3번 사이에 누군가 path를 바꿀 수 있다면 검사한 파일과 실제 실행한 파일이 달라질 수 있다.

~~~text
검사할 때
/safe/run.py → 정상 파일

검사 뒤 path 교체

실행할 때
/safe/run.py → 다른 파일
~~~

이것이 “검사했으니 안전하다”만으로 부족한 이유다.

KISA 보호나라 보안 공지에서도 TOCTOU Race Condition을 실제 제품 취약점 유형으로 다룬다.

- [KISA 보호나라 — VMware Fusion TOCTOU Race Condition 보안 업데이트 권고](https://www.krcert.or.kr/kr/bbs/view.do?bbsId=B0000133&categoryCode=&menuNo=205020&nttId=72064&pageIndex=1&searchCnd=&searchWrd=)

## 심볼릭 링크는 왜 같이 확인하는가

심볼릭 링크(Symbolic Link)는 다른 file이나 Directory path를 가리키는 링크다.

~~~text
scripts/current.py
→ /tmp/other.py
~~~

겉으로는 승인 Directory 아래 path처럼 보여도 실제 resolve 결과가 외부를 가리킬 수 있다.

따라서 privileged source를 검증할 때는 source root, 중간 Directory, 최종 file이 symlink인지와 resolve된 path가 승인 root 안에 남는지를 확인할 수 있다.

## 최종 file permission만 확인하면 부족한 이유

다음 구조를 보자.

~~~text
/approved
└─ scripts
   └─ run.py
~~~

run.py가 root-owned 0444여도 scripts Directory가 일반 사용자에게 write 가능하면 Directory entry를 바꿔 run.py를 다른 파일로 교체할 수 있다.

즉 최종 file이 안전해도 **그 file까지 이어지는 parent path가 안전하지 않으면 교체 가능성이 남는다.**

그래서 root 권한으로 실행할 source에서는 parent Directory chain도 신뢰 경계로 본다.

~~~text
각 parent
→ Directory인가
→ symlink가 아닌가
→ root-owned인가
→ group/other write가 가능한가
~~~

## Sticky bit는 무엇인가

/tmp처럼 여러 사용자가 file을 만들 수 있도록 write가 허용된 Directory에는 sticky bit가 사용되기도 한다.

Sticky bit가 있으면 일반 사용자가 다른 사용자의 file을 마음대로 삭제하거나 rename하는 동작을 제한할 수 있다.

따라서 privileged path 검증에서 writable Directory를 다룰 때는 어떤 예외를 허용할지 명확하게 코드와 테스트로 고정해야 한다.

## Cleanup은 왜 따로 설계해야 하는가

Cleanup이 필요한 순간은 오히려 정상 입력이 깨졌을 가능성이 높은 시점이다.

~~~text
startup 실패
image 없음
Dataset 일부 누락
Backend unhealthy
~~~

이때 cleanup도 정상 실행과 똑같이 image, Dataset, secret 전체를 요구하면 정리 자체가 실패할 수 있다.

그래서 cleanup은 가능한 한 다음처럼 단순하게 만든다.

~~~text
정리 대상 identity 확인
→ 최소 입력만 사용
→ 정확한 project만 종료
→ 다른 project와 volume은 건드리지 않음
~~~

복구 경로가 정상 실행 경로보다 더 많은 의존성을 가지지 않는 것이 중요하다.

## 결과 Directory를 재사용하면 왜 위험한가

이전 실행 결과와 새 결과가 같은 Directory에 섞이면 서로 다른 실험이 하나의 series처럼 보일 수 있다.

~~~text
이전 실행
25 / 50 / 100 RPS 결과 존재

새 실행
25 / 50 RPS만 새로 생성
~~~

이 상태에서 Directory 전체를 보면 이전 100 RPS 결과가 새 실행에 속한 것처럼 오해할 수 있다.

그래서 중요한 실험에서는 non-empty result Directory를 거부하고 실행마다 새 Directory를 사용하는 편이 안전하다.

## 재현 가능한 성능 실험의 최소 기록

결과 숫자만 남기지 않고 다음을 연결하는 것이 좋다.

~~~text
source commit SHA
Container image digest
Dataset identity
Dataset checksum / provenance
요청 시나리오
목표 RPS
실제 RPS
준비 시간
측정 시간
부하 도구 버전
결과 Directory
서버와 DB 주요 설정
실행 시각
~~~

이 정보가 있으면 나중에 같은 조건을 복원하거나 무엇이 달라졌는지 확인하기 쉽다.

## 핵심 정리

재현 가능한 성능 실험은 같은 명령어를 다시 입력할 수 있다는 뜻보다 넓다. 어떤 source, image, Dataset, 설정과 요청 조건에서 결과가 나왔는지 다시 연결할 수 있어야 한다.

또 데이터가 Production과 분리됐다고 끝나는 것이 아니라 CPU, memory, DB 같은 자원까지 분리됐는지 따로 봐야 한다.

Privileged script에서는 최종 file만 안전한지 확인하는 것이 아니라 그 file까지 이어지는 path 전체가 바뀔 수 없는지도 확인해야 한다. 검사 시점과 사용 시점 사이의 TOCTOU 문제를 피하기 위해서다.

**성능 숫자의 신뢰도는 측정 도구보다 먼저, 실험 입력과 실행 경계를 얼마나 정확하게 고정했는지에서 시작한다.**
