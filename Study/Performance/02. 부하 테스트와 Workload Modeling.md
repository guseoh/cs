# 부하 테스트와 Workload Modeling

## 요청을 많이 보내는 것이 부하 모델은 아니다

같은 100 RPS라도 읽기 100%와 쓰기 50%가 섞인 시스템은 전혀 다르게 움직인다. 작은 payload 조회와 대형 JSON 처리·Transaction 수행도 같은 RPS로 비교할 수 없다.

Workload Modeling은 실제 또는 검증하려는 트래픽 특성을 테스트로 옮기는 과정이다.

~~~text
Workload
= Endpoint Mix
+ Request Rate
+ Concurrency
+ Payload
+ Think Time
+ Data Distribution
+ Duration
+ Arrival Pattern
~~~

## Endpoint Mix

실제 서비스가 다음이라면:

~~~text
목록 조회 60%
상세 조회 25%
장바구니 10%
주문 5%
~~~

목록 조회 100% 테스트를 서비스 전체 capacity로 표현하면 안 된다.

카카오 메시징 팀은 평시와 신년 트래픽의 프로토콜 비율이 다르기 때문에 실제 traffic mix를 별도 시나리오로 관리한다.

- [카카오 — 메시징 서버의 스트레스 테스트 노하우](https://tech.kakao.com/posts/822)

## Arrival Pattern

트래픽은 일정하지 않다.

- constant
- ramp-up
- peak
- spike
- burst

LINE 신년 트래픽 사례에서는 평소와 비슷한 처리량 숫자만으로는 보이지 않던 connection 생성과 Full GC 문제가 피크 상황에서 드러났다.

- [LINE — 메시징 서버가 새해 트래픽을 대비하는 과정](https://engineering.linecorp.com/ko/blog/how-line-messaging-servers-prepare-for-new-year-traffic)

## Closed Model과 Open Model

Closed Model은 정해진 VU가 응답을 받아야 다음 요청을 보낸다.

~~~text
VU
→ request
→ response 대기
→ 다음 request
~~~

서버가 느려지면 같은 VU 수에서 실제 arrival rate가 줄어들 수 있다.

Open Model은 응답 속도와 별개로 도착률을 예약한다.

~~~text
매초 100 iteration 도착
→ 서버가 느려져도 목표 도착률 유지
~~~

capacity와 queueing을 보기 좋지만 충분한 VU가 없으면 load generator가 dropped iteration을 만들 수 있다.

- [Grafana k6 — Scenarios](https://grafana.com/docs/k6/latest/using-k6/scenarios/)
- [Grafana k6 — API load testing](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/)

## Concurrency와 RPS

둘은 같은 값이 아니다.

간단히 Little's Law 관점으로:

~~~text
Concurrency ≈ Throughput × Response Time
~~~

100 RPS에서 평균 0.1초면 평균 동시 작업은 약 10개다.

같은 100 RPS인데 응답 시간이 2초가 되면 평균 약 200개가 시스템 안에 머문다.

이 때문에 latency 증가가 thread, socket, connection pool pressure를 다시 키울 수 있다.

## 한계점을 단계적으로 찾는다

처음부터 최대 부하를 넣으면 어느 구간부터 상태가 바뀌었는지 알기 어렵다.

~~~text
25
→ 50
→ 100
→ 150
→ 200
→ 250 RPS
~~~

known-good와 first-failure를 구분할 수 있다.

~~~text
known-good = 200
first-failure = 250
→ 실제 threshold는 200 < x <= 250
~~~

정확한 숫자가 필요할 때만 그 사이를 더 좁힌다.

## Load Generator 검증

서버가 아니라 client가 먼저 포화되면 성능 한계를 잘못 판단한다.

확인:

- generator CPU
- generator memory
- VU
- dropped iteration
- connection
- network
- timeout

카카오 글은 서버 분석에 집중하려고 load generator 리소스를 넉넉하게 확보하는 이유를 설명한다.

## 비즈니스 트래픽과 연결한다

우아한형제들 포인트 시스템은 “1000 TPS가 멋있어서” 목표를 정한 것이 아니라 피크 주문량의 배수를 기준으로 목표 TPS를 만들었다.

- [우아한형제들 — 신규 포인트 시스템 전환기 #2](https://techblog.woowahan.com/2588/)

성능 목표는 다음처럼 설명 가능해야 한다.

~~~text
피크 주문 200 TPS
× 안전 계수 3
= 목표 600 TPS
~~~

## Stress Test의 실패 신호

서버가 죽어야 실패가 아니다.

- actual RPS가 target을 못 따라감
- p95/p99 급증
- error 증가
- dropped iteration
- Hikari pending 증가
- thread 증가
- CPU saturation
- OOM/restart
- DB lock/latency 증가

우아한형제들 결제 시스템 사례도 병목 위치, 한계, 장시간 안정성, 장애 복구를 각각 검증한다.

- [우아한형제들 — 결제 시스템 성능, 부하, 스트레스 테스트](https://techblog.woowahan.com/2572/)

## 실제 운영과 동일한 스펙을 맞추는 이유

2026년 카카오 톡메시징팀의 스트레스 테스트 사례에서는 테스트 대상 서버를 **실 운영 인스턴스와 동일한 스펙**으로 유지한다고 설명한다. JVM heap, CPU/Memory 제한, Network 같은 장비 조건이 다르면 결과 자체의 비교 가능성이 약해지기 때문이다.

중요한 것은 “운영과 똑같은 서버를 만들었다”가 아니다. 운영 서버 대수까지 같지 않으면 절대 수치를 그대로 옮겨 쓸 수 없으므로, **어떤 것은 그대로 비교할 수 있고 어떤 것은 환산해야 하는지** 구분하는 것이다.

예를 들어 테스트 서버 한 대에서 CPU가 60% → 65%로 5%p 증가했을 때 실제 운영이 120대 규모라면, 동일 headroom을 유지하려면 필요한 서버 수가 달라질 수 있다. 작은 5%p가 운영 비용에서는 큰 차이가 될 수 있다.

- [카카오 — 메시징 서버의 스트레스 테스트 노하우와 AI가 덜어 준 부분](https://tech.kakao.com/posts/822)

이 사례는 성능 결과를 “서버 한 대의 CPU가 조금 올랐다”로 끝내지 않고 **실제 운영 규모와 비용 의사결정으로 연결**해야 한다는 점을 보여 준다.

## 단계적 Ramp-up이 필요한 이유

카카오 사례는 사용자를 10 → 50 → 100 → 150처럼 점진적으로 올리며 여러 구간을 반복한다. 이렇게 하면 단순히 “최대에서 죽었다”가 아니라 다음 질문에 답할 수 있다.

~~~text
어느 구간부터 latency가 꺾였는가?
어느 구간부터 GC가 늘었는가?
어느 구간부터 Thread Pool이 포화됐는가?
어느 구간부터 Connection이 쌓였는가?
~~~

특정 설정을 바꾼 뒤에도 처음부터 같은 ramp를 다시 돌려야 변경 효과를 비교할 수 있다.

## Persistent Connection Workload

HTTP 짧은 요청과 WebSocket 장기 연결은 workload가 다르다.

카카오 실시간 댓글 사례의 목표는 서버 한 대가 **10K WebSocket connection을 안정적으로 유지하면서 2800 TPS**를 처리하는 것이었다. 이 과정에서 단순 request latency만 본 것이 아니라 Tomcat, Docker container, memory, file descriptor, GC 등을 함께 조정했다.

- [카카오 — 실시간 댓글 개발기 part.2](https://tech.kakao.com/posts/391)

장기 연결 workload에서는 다음 자원이 더 중요해질 수 있다.

~~~text
connection 수
→ socket
→ file descriptor
→ thread/event-loop
→ memory
→ heartbeat/timeout
~~~

따라서 REST API capacity 결과를 WebSocket capacity로 일반화하면 안 된다.

## 정리

좋은 부하 테스트는 “얼마나 많이 때렸는가”가 아니라 **실제 workload를 모델링했고, generator가 그 workload를 만들었으며, 시스템 상태 변화의 경계를 설명할 수 있는가**로 평가한다.
