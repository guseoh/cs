# 부하 테스트와 요청 흐름 모델링

부하 테스트는 서버에 요청을 많이 보내는 작업이 아니다. 실제 서비스에서 어떤 요청이 어떤 속도와 비율로 들어오는지를 의도적으로 만들어 보고, 그 상황에서 시스템이 정상적으로 처리되는지 확인하는 실험이다.

같은 100 RPS라도 상품 목록 조회만 100번 들어오는 경우와 주문 생성, 결제, 재고 변경이 섞여 들어오는 경우는 전혀 다른 부하다. 같은 사용자 1,000명이 접속해 있어도 아무 요청을 보내지 않으면 RPS는 낮을 수 있고, 사용자 100명이 짧은 시간에 여러 API를 연속 호출하면 RPS는 높아질 수 있다.

따라서 부하 테스트를 설계할 때 첫 질문은 “몇 RPS까지 올릴까?”가 아니다.

**실제 서비스에서 누가 어떤 행동을 하고, 그 행동이 어떤 요청으로 변하며, 요청이 시간에 따라 어떤 모양으로 들어오는가**를 먼저 정해야 한다.

이 과정을 부하 모델링 또는 워크로드 모델링(Workload Modeling)이라고 부른다.

카카오 메시징팀의 스트레스 테스트 사례에서도 평상시와 신년 자정처럼 사용자 행동 비율이 달라지는 상황을 따로 모델링한다. 전체 요청량이 같아도 메시지 전송, 채팅방 조회처럼 요청 종류의 비율이 달라지면 서버가 사용하는 CPU, Thread, DB, Network의 부담도 달라지기 때문이다.

## 사용자 행동을 HTTP 요청으로 바꾸는 것부터 시작한다

실제 사용자는 RPS를 생각하면서 서비스를 사용하지 않는다.

사용자는 다음처럼 행동한다.

~~~text
상품 목록을 연다.
→ 상품 상세를 본다.
→ 장바구니에 담는다.
→ 주문을 생성한다.
→ 결제한다.
~~~

서버 입장에서는 이 행동이 여러 HTTP 요청과 데이터베이스 작업으로 바뀐다.

~~~text
GET /api/products
GET /api/products/{id}
POST /api/cart/items
POST /api/orders
POST /api/payments/...
~~~

여기서 상품 목록 조회는 읽기 중심일 수 있지만 주문 생성은 Transaction과 여러 테이블 변경을 포함할 수 있다. 결제는 외부 Provider 호출까지 포함할 수 있다.

따라서 실제 Commerce 서비스를 테스트하려면 “사용자 한 명이 무엇을 하는가”와 “각 행동이 서버 자원을 얼마나 사용하는가”를 연결해야 한다.

모든 테스트가 반드시 실제 사용자 전체 여정을 그대로 재현해야 하는 것은 아니다.

예를 들어 Product 목록 조회의 데이터 규모 영향만 보고 싶다면 GET /api/products만 독립적으로 테스트할 수 있다.

중요한 것은 **지금 만드는 부하가 서비스 전체를 대표하는지, 특정 API 하나의 처리 용량만 보는지 명확하게 말하는 것**이다.

## 초당 요청 수는 사용자 수와 다르다

초당 요청 수(Requests Per Second, RPS)는 1초 동안 실행되는 HTTP 요청의 수를 나타내는 단위다.

예를 들어 1초 동안 상품 목록 API가 100번 호출되었다면 그 구간은 약 100 RPS라고 표현할 수 있다.

~~~text
1초
→ HTTP 요청 100개

약 100 RPS
~~~

하지만 RPS는 사용자 수와 같지 않다.

사용자 1명이 1초 동안 5개의 API를 호출하면 5 RPS가 될 수 있다. 반대로 1,000명이 로그인한 채 화면만 보고 있다면 순간 요청 수는 매우 낮을 수 있다.

따라서 다음 세 값을 구분해야 한다.

~~~text
접속한 사용자 수
동시에 진행 중인 요청 수
초당 새로 시작되는 요청 수
~~~

이 세 값은 서로 영향을 주지만 같은 값은 아니다.

## TPS라는 용어도 문맥을 확인해야 한다

TPS(Transactions Per Second)는 일반적으로 초당 처리한 Transaction 수를 뜻한다.

하지만 여기서 Transaction이 무엇인지는 문맥마다 다를 수 있다.

데이터베이스에서는 commit 단위의 DB Transaction을 말할 수 있다. 서비스에서는 주문 한 건, 결제 한 건처럼 업무 단위를 Transaction이라고 부를 수 있다. 부하 테스트 도구에서는 사용자 시나리오 한 번을 Transaction이라고 부르기도 한다.

그래서 “우리 시스템은 1,000 TPS다”라는 문장만으로는 의미가 충분하지 않다.

다음 질문이 필요하다.

~~~text
한 Transaction은 무엇인가?
읽기 요청인가, 쓰기 요청인가?
여러 HTTP 요청을 하나로 묶은 것인가?
실패 요청도 포함하는가?
어떤 데이터와 서버 조건인가?
~~~

성능 문서에서는 RPS나 TPS를 쓸 때 **분모와 작업 단위를 먼저 정의**하는 것이 좋다.

LINE의 신년 트래픽 대응 글처럼 실제 서비스에서도 요청량과 처리량을 여러 단위로 나누어 보는 이유가 여기에 있다.

## 목표 RPS와 실제 RPS는 반드시 분리한다

부하 도구에서 250 RPS를 설정했다고 해서 서버가 실제로 250 RPS를 처리한 것은 아니다.

부하 생성기는 1초에 250개의 요청을 시작하려고 하지만 다음과 같은 이유로 목표를 만들지 못할 수 있다.

~~~text
부하 생성기 CPU 부족
사용 가능한 가상 사용자 부족
Network 한계
Connection 생성 지연
부하 테스트 script 자체의 blocking
도구 내부 scheduling 지연
~~~

따라서 결과에는 다음 두 값을 구분해서 남긴다.

~~~text
target RPS
→ 만들려고 한 요청량

actual RPS
→ 실제 실행된 요청량
~~~

예를 들어:

~~~text
target = 250 RPS
actual = 180 RPS
error = 0%
p95 = 70ms
~~~

라면 “250 RPS에서 p95 70ms”라고 기록하면 안 된다.

실제로는 180 RPS 정도만 만들어졌고 왜 250 RPS를 만들지 못했는지 조사해야 한다.

## 동시 처리 수는 응답 시간과 함께 늘어날 수 있다

동시 처리 수(Concurrency)는 한 시점에 아직 완료되지 않은 요청이 몇 개나 존재하는지를 나타낸다.

같은 100 RPS라도 요청이 매우 빨리 끝나면 동시에 존재하는 요청 수는 적다.

예를 들어 평균 응답 시간이 0.1초라면 직관적으로:

~~~text
100 RPS × 0.1초
≈ 평균 10개 요청이 시스템 안에 존재
~~~

할 수 있다.

같은 100 RPS인데 평균 응답 시간이 2초가 되면:

~~~text
100 RPS × 2초
≈ 평균 200개 요청이 시스템 안에 존재
~~~

하게 된다.

이 관계는 대기행렬에서 자주 사용하는 Little's Law를 단순화해서 이해한 것이다.

중요한 점은 **요청량이 그대로인데도 응답 시간이 증가하면 시스템 안에 동시에 머무는 요청 수가 커질 수 있다는 것**이다.

이 요청들은 Tomcat Thread, DB Connection, Socket, Memory를 더 오래 점유할 수 있다.

따라서 응답 시간 증가가 다시 자원 경쟁을 키우고, 자원 경쟁이 다시 응답 시간을 늘리는 악순환이 가능하다.

Tomcat과 HikariCP의 대기 구조는 [[06. Tomcat HikariCP DB Queueing]]에서 자세히 다룬다.

## 가상 사용자는 실제 사용자 한 명과 같지 않다

k6 같은 부하 도구에서는 가상 사용자(Virtual User, VU)를 사용한다.

가상 사용자는 실제 사람 한 명을 완벽하게 복제한 개념이 아니다. **테스트 script의 사용자 흐름을 반복해서 실행하는 실행 단위**라고 이해하는 편이 정확하다.

예를 들어 가상 사용자 하나가 다음 동작을 반복한다고 해보자.

~~~text
상품 목록 요청
→ 응답 대기
→ 1초 생각 시간
→ 상품 상세 요청
→ 응답 대기
→ 2초 생각 시간
→ 반복
~~~

서버가 느려지면 각 VU가 응답을 기다리는 시간도 늘어난다.

따라서 동일한 100 VU를 사용해도 서버 응답 시간이 늘면 실제 RPS가 낮아질 수 있다.

이 때문에 “VU 100명 테스트”라는 표현만으로는 부하 규모를 알 수 없다.

반드시 실제 요청량과 응답 시간을 함께 봐야 한다.

## 생각 시간은 실제 사용자 흐름을 바꾼다

사람은 페이지를 받은 즉시 다음 버튼을 무한정 누르지 않는다.

상품을 읽거나 옵션을 선택하거나 결제를 고민하는 시간이 있다.

이런 사용자 행동 사이의 대기 시간을 생각 시간(Think Time)이라고 부른다.

생각 시간을 넣으면 같은 VU 수에서도 RPS가 달라진다.

~~~text
100 VU
생각 시간 없음
→ 매우 높은 RPS 가능

100 VU
각 행동 사이 2초 대기
→ 훨씬 낮은 RPS
~~~

따라서 실제 사용자 흐름을 모델링할 때는 think time을 포함할 수 있다.

반면 특정 API의 최대 처리 용량만 보고 싶다면 think time 없이 목표 도착률을 직접 제어하는 편이 더 적절할 수 있다.

테스트 목적에 따라 모델이 달라진다.

## 닫힌 부하 모델은 응답이 느려지면 요청량도 줄어든다

닫힌 부하 모델(Closed Model)은 정해진 VU가 요청을 보내고 응답을 받은 뒤 다음 요청을 보내는 구조다.

~~~text
요청
→ 응답 대기
→ 다음 요청
~~~

서버가 느려지면 VU가 응답을 기다리는 시간이 길어지고 다음 요청도 늦게 보낸다.

이 때문에 서버가 포화되어 응답 시간이 길어질수록 실제 요청 유입량이 자연스럽게 감소할 수 있다.

사용자가 이전 화면이 끝나야 다음 행동을 하는 흐름을 표현하는 데는 유용하지만, 외부에서 일정 속도로 요청이 계속 들어오는 상황에서는 한계를 숨길 수 있다.

예를 들어 서버가 느려지면서 다음처럼 될 수 있다.

~~~text
정상
100 VU
actual = 500 RPS

서버 느려짐
100 VU
actual = 250 RPS
~~~

RPS가 낮아지면서 서버가 더 이상 심하게 무너지지 않는 것처럼 보일 수 있다.

## 열린 부하 모델은 요청 도착률을 유지하려고 한다

열린 부하 모델(Open Model)은 서버 응답 시간과 관계없이 정해진 속도로 새 요청을 시작하려고 한다.

예를 들어 매초 200번의 실행을 예약한다.

~~~text
매초
200개의 새로운 iteration 시작 시도
~~~

이전 요청이 느려도 새로운 요청 도착은 계속 예약된다.

따라서 외부 트래픽이 일정 속도로 밀려드는 상황에서 서버의 처리 한계를 확인하기 좋다.

k6의 arrival-rate 계열 executor는 이런 방식으로 사용할 수 있다.

- [Grafana k6 — Scenarios](https://grafana.com/docs/k6/latest/using-k6/scenarios/)

## 열린 모델에서도 부하 생성기가 무한히 요청을 만들 수 있는 것은 아니다

열린 모델에서 250 RPS를 예약했다고 해도 실행 자원이 부족하면 모든 iteration을 시작하지 못할 수 있다.

k6에서는 이런 상황을 누락된 반복 실행(dropped iteration)으로 확인할 수 있다.

예를 들어:

~~~text
1초 동안 목표
250 iteration

실제로 시작
230

시작하지 못함
20
~~~

이라면 dropped iteration이 발생한 것이다.

이 값은 서버 포화와 구분해서 봐야 한다.

부하 생성기 자체가 충분한 VU를 확보하지 못했거나 CPU가 부족해서 iteration을 만들지 못했을 수도 있기 때문이다.

그래서 서버의 용량을 측정하려는 단계형 실험에서는 dropped iteration을 0으로 요구하는 경우가 많다.

**목표 부하를 만들지 못한 결과를 서버 처리 한계처럼 해석하지 않기 위해서다.**

## 요청 종류의 비율이 바뀌면 같은 RPS도 다른 부하가 된다

Commerce 서비스에서 다음 요청 비율을 가정해보자.

~~~text
상품 목록 조회   50%
상품 상세 조회   25%
장바구니 조회    10%
장바구니 변경    8%
주문 생성        5%
결제 요청        2%
~~~

이 100 RPS와 상품 목록 조회 100 RPS는 같은 부하가 아니다.

쓰기 요청과 Transaction이 섞이면 다음이 달라질 수 있다.

~~~text
DB Connection 점유 시간
Lock
Disk Write
Transaction 유지 시간
외부 API 호출
Thread 점유 시간
오류 형태
~~~

따라서 서비스 전체 용량을 말하려면 실제 업무 비율을 반영한 혼합 워크로드가 필요하다.

반대로 특정 쿼리나 특정 API의 cardinality 영향만 확인하려는 실험에서는 한 API만 고정해서 테스트하는 편이 더 좋다.

**혼합 워크로드가 항상 더 현실적이라는 이유만으로 더 좋은 실험은 아니다.**

원인 분리를 위해서는 오히려 단순한 워크로드가 필요할 때가 있다.

## 시간에 따른 요청 모양도 설계해야 한다

총 요청 수가 같아도 요청이 들어오는 시간 모양에 따라 시스템 동작이 달라진다.

### 일정 부하

일정한 RPS를 유지한다.

~~~text
100
100
100
100 RPS
~~~

특정 처리량에서 장시간 안정적인지 확인하기 좋다.

### 점진적 증가

단계적으로 부하를 올린다.

~~~text
25
→ 50
→ 100
→ 150
→ 200
→ 250 RPS
~~~

어느 구간부터 응답 시간이나 오류가 급격히 변하는지 찾기 좋다.

### 순간 폭증

짧은 시간에 요청량이 크게 늘어난다.

~~~text
50 RPS
→ 순간 500 RPS
→ 다시 50 RPS
~~~

Connection 생성, Thread 증가, Cache Miss, 초기화 Lock처럼 정상 지속 부하에서는 보이지 않던 문제가 드러날 수 있다.

LINE의 성능 테스트 자동화 사례에서는 서버 기동 직후 많은 요청이 몰릴 때 초기화 Lock 때문에 수백 개 Thread가 BLOCKED 상태로 쌓이는 문제를 발견했다. 정상적인 평상시 흐름에서는 보기 어려운 장애 복구 상황의 문제였다.

관련 자료:
- [LINE — 서버 사이드 테스트 자동화 여정 5](https://engineering.linecorp.com/ko/blog/server-side-test-automation-5/)

## 준비 구간은 부하 모델에도 포함된다

성능 테스트 시작 직후에는 JIT, Connection 생성, Cache, DB Buffer 상태가 아직 안정되지 않았을 수 있다.

그래서 다음과 같이 준비 구간을 둔 뒤 측정한다.

~~~text
Warm-up
30초

Measurement
120초
~~~

하지만 Warm-up을 넣었다는 사실만으로 충분하지 않다.

Before와 After 비교에서 준비 시간과 측정 시간도 동일하게 유지해야 한다.

또 실제 배포 직후 요청 지연을 확인하는 실험이라면 warm-up으로 그 현상을 없애면 안 된다.

## 오류율과 시간 초과 조건도 워크로드 계약이다

응답 시간이 짧아도 정상 응답이 아니라면 성공한 부하 테스트가 아니다.

따라서 정상 상태 코드가 무엇인지 미리 정한다.

예를 들어 read-only API라면 200을 기대할 수 있다.

~~~text
expected status
200

unexpected
4xx / 5xx / timeout
~~~

Redirect가 정상인지 실패인지도 목적에 따라 정해야 한다.

인증이 필요한 API라면 401이 정상 결과인지 테스트 실패인지도 시나리오가 결정한다.

또 시간 초과 기준도 중요하다.

클라이언트가 3초에 요청을 포기한다면 3초보다 오래 걸리는 요청은 완료 시간이 아니라 Timeout으로 기록될 수 있다.

서로 다른 실험에서 timeout 설정이 다르면 p95도 직접 비교하기 어렵다.

## 부하 생성기의 위치가 네트워크 경로를 바꾼다

같은 API라도 어디에서 부하를 보내는지에 따라 응답 시간이 달라진다.

~~~text
같은 Host의 localhost
→ Network 구간 짧음

같은 VPC의 다른 Host
→ 내부 Network 포함

외부 Desktop
→ Internet + TLS + Proxy 경로 포함
~~~

따라서 Localhost 테스트 결과와 public HTTPS 테스트 결과를 같은 절대 지연 값으로 비교하면 안 된다.

Localhost 테스트는 Application 내부 처리 용량을 분리해서 보기 좋고, public HTTPS는 실제 사용자 경로에 더 가깝다.

각 테스트가 무엇을 포함하고 제외하는지 기록해야 한다.

## 부하 생성기 자체의 자원을 확인한다

테스트 중 다음 값도 본다.

~~~text
Load Generator CPU
Memory
Network
사용 가능한 VU
dropped iteration
socket / port 상태
~~~

서버가 여유로운데 target RPS를 만들지 못한다면 부하 생성기가 먼저 한계에 도달했을 수 있다.

특히 같은 노트북에서 Docker, DB, Application, k6를 모두 실행한다면 자원 경쟁이 생길 수 있다.

이런 결과는 Production capacity가 아니라 **그 로컬 실험 환경의 처리 한계**다.

## 단계형 결과를 읽는 예

다음은 가상의 결과다.

| 목표 RPS | 실제 RPS | 오류율 | p95 | 누락 실행 |
| ---: | ---: | ---: | ---: | ---: |
| 25 | 25 | 0% | 40ms | 0 |
| 100 | 100 | 0% | 58ms | 0 |
| 200 | 199 | 0% | 95ms | 0 |
| 250 | 220 | 2.5% | 1,100ms | 18 |

250 RPS 행에서 단순히 “최대 220 RPS”라고 결론내리지 않는다.

먼저 다음을 확인한다.

~~~text
왜 actual RPS가 target보다 낮아졌는가?
dropped iteration은 Load Generator 문제인가?
오류는 5xx인가 Timeout인가?
Backend CPU는 포화됐는가?
Tomcat Thread는 max에 접근했는가?
Hikari pending이 증가했는가?
MySQL Query latency는 증가했는가?
~~~

이 과정을 거쳐야 서버의 실제 first-failure 위치를 설명할 수 있다.

## 실제 사용자를 그대로 복제하는 것이 항상 목표는 아니다

성능 테스트는 실제 트래픽을 최대한 똑같이 만드는 작업처럼 보이지만, 실험 목적에 따라 현실성을 의도적으로 줄일 수도 있다.

예를 들어 데이터 규모가 Query에 미치는 영향만 보고 싶다면 다음 조건을 고정한다.

~~~text
같은 Endpoint
같은 RPS
같은 요청 Parameter
같은 Runtime

Dataset만
32 Product → 10,000 Product
~~~

이렇게 해야 결과 차이를 데이터 규모와 연결하기 쉽다.

반대로 서비스 전체 capacity를 알고 싶다면 인증, read/write 비율, think time, burst 패턴을 더 현실적으로 구성한다.

즉 좋은 workload는 “가장 복잡한 workload”가 아니라 **질문에 필요한 변수를 가장 잘 통제하는 workload**다.

## 같은 조건으로 재측정할 수 있어야 한다

성능 개선 전후를 비교하려면 다음 조건을 최대한 동일하게 유지한다.

~~~text
Dataset
요청 종류와 비율
target RPS
Warm-up
Measurement 시간
Load Generator 위치
Timeout
Server/Container limit
JVM 설정
DB 사양
Metric 수집 방식
~~~

그 뒤 변경하려는 요소만 최소화한다.

인덱스 효과를 보고 싶은데 동시에 JVM Heap과 Hikari Pool도 바꾸면 무엇이 결과를 만들었는지 알기 어렵다.

이 원리는 [[09. Before After와 성능 실험의 인과관계]]에서 더 자세히 설명한다.

## 실제 서비스 사례에서 워크로드를 어떻게 정하는지 본다

우아한형제들의 신규 포인트 시스템 전환 사례에서는 임의로 “1,000 TPS가 멋있어 보이니 1,000 TPS”라고 정하지 않았다.

주말 피크타임 주문 수를 기준으로 포인트 요청량을 추정하고 여기에 여유를 두어 테스트 기준을 정했다. 이후 nGrinder로 부하를 만들고 Pinpoint와 RDS 지표를 보며 병목을 수정한 뒤 다시 테스트했다.

이 사례에서 중요한 것은 도구 이름보다 **업무량에서 성능 테스트 목표를 유도하고, 결과를 내부 관측 지표와 연결한 방식**이다.
