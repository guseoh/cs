# 부하 테스트와 요청 흐름 모델링

부하 테스트는 서버에 요청을 많이 보내는 작업이 아니다. 더 정확하게 말하면 **실제 서비스에서 들어올 법한 요청의 종류와 도착 속도를 의도적으로 재현하고, 그 상황에서 시스템이 어디까지 안정적으로 처리하는지 확인하는 실험**이다.

예를 들어 초당 100개의 요청을 처리한다고 해도 모든 요청이 상품 목록 조회인지, 주문 생성과 결제가 섞여 있는지에 따라 서버가 사용하는 자원은 달라진다. 상품 목록 조회는 대부분 읽기 중심일 수 있지만 주문 생성은 데이터베이스 트랜잭션, 재고 수정, 결제 연동처럼 더 많은 작업을 포함할 수 있다.

그래서 성능 테스트를 시작할 때 가장 먼저 정해야 하는 것은 “몇 RPS까지 올릴까?”가 아니라 **어떤 사용자가 어떤 요청을 어느 비율로 보내는 상황을 검증하려는가**이다.

카카오 메시징팀도 실제 스트레스 테스트에서 평시와 신년 자정의 사용자 행동 비율이 다르다는 점을 따로 모델링한다. 같은 전체 요청량이라도 메시지 전송과 채팅방 조회 비율이 달라지면 서버가 받는 부하의 성격도 달라질 수 있기 때문이다.

## 초당 요청 수(RPS)는 무엇인가

RPS(Requests Per Second)는 **1초 동안 서버가 처리한 요청의 개수**를 뜻한다.

예를 들어 1초 동안 상품 목록 API에 100번의 HTTP 요청이 들어왔다면 그 구간의 요청량은 약 100 RPS라고 표현할 수 있다.

~~~text
1초 동안 들어온 요청
= 100개

요청량
= 100 RPS
~~~

여기서 중요한 것은 RPS가 “사용자 수”와 같은 값이 아니라는 점이다.

사용자 한 명이 1초에 요청을 한 번 보낼 수도 있고, 여러 API를 연속으로 호출할 수도 있다. 반대로 사용자가 1,000명 접속해 있어도 아무 동작을 하지 않으면 순간 RPS는 매우 낮을 수 있다.

따라서 다음 값을 서로 구분해서 봐야 한다.

~~~text
사용자 수
≠ 동시 요청 수
≠ 초당 요청 수
~~~

LINE의 신년 트래픽 준비 글에서도 요청량을 RPS, 처리량을 TPS, 동시에 접속한 사용자 수를 동시 사용자 수처럼 서로 다른 지표로 나누어 표현한다. 하나의 숫자로 트래픽 전체를 설명하기 어렵기 때문이다.

## 목표 RPS와 실제 RPS는 다르다

부하 도구에서 “250 RPS를 보내겠다”고 설정했다고 해서 서버가 실제로 250 RPS를 처리했다는 뜻은 아니다.

부하 생성기는 250 RPS를 목표로 요청을 만들었지만 서버가 느려지거나, 연결이 막히거나, 부하 생성기 자체가 포화되면 실제 처리량은 그보다 낮을 수 있다.

그래서 결과에서는 최소한 다음 두 값을 분리해서 본다.

~~~text
목표 RPS
부하 도구가 만들려고 한 요청량

실제 RPS
실제로 실행되거나 서버까지 도착해 처리된 요청량
~~~

예를 들어 목표를 250 RPS로 올렸는데 실제 처리량이 180 RPS 부근에서 더 이상 증가하지 않는다면 “250 RPS를 처리했다”고 기록하면 안 된다.

이 경우는 다음 질문으로 넘어가야 한다.

~~~text
서버가 180 RPS 부근에서 포화된 것인가?
부하 생성기가 요청을 충분히 만들지 못한 것인가?
네트워크나 연결 수가 먼저 제한된 것인가?
오류나 시간 초과 때문에 요청이 정상 완료되지 못한 것인가?
~~~

카카오의 스트레스 테스트 사례도 가장 먼저 전체 요청 처리량이 목표대로 발생하고 유지되는지를 본 뒤, 이상이 있을 때 CPU, 메모리, 연결, 스레드와 같은 내부 지표로 내려간다.

## 처리량(Throughput)은 RPS와 완전히 같은 말인가

처리량(Throughput)은 **일정 시간 동안 시스템이 실제로 처리한 작업량**을 뜻하는 더 넓은 개념이다.

HTTP API에서는 RPS가 처리량 지표로 자주 사용된다. 하지만 시스템에 따라 작업의 단위가 다를 수 있다.

~~~text
웹 API
→ 초당 요청 수(RPS)

주문 시스템
→ 초당 완료 주문 수

메시지 시스템
→ 초당 처리 메시지 수

데이터 처리
→ 초당 처리 레코드 수
~~~

즉 RPS는 처리량을 나타내는 대표적인 한 방법이지 모든 시스템의 처리량을 뜻하는 유일한 단위는 아니다.

## TPS는 무엇인가

TPS(Transactions Per Second)는 문맥에 따라 **초당 처리된 트랜잭션 수**를 의미한다.

여기서 트랜잭션이 무엇인지는 시스템에서 어떤 작업을 하나의 단위로 정의했는지에 따라 달라질 수 있다. 데이터베이스 트랜잭션 수를 말할 수도 있고, 서비스 관점에서 결제나 주문 같은 하나의 업무 처리를 뜻할 수도 있다.

따라서 “우리 시스템은 1,000 TPS다”라는 숫자만 보면 부족하다.

~~~text
어떤 작업을 1 Transaction으로 계산했는가?
읽기와 쓰기가 섞였는가?
실패한 요청도 포함하는가?
어떤 데이터 규모와 서버 사양에서 측정했는가?
~~~

를 함께 확인해야 의미가 생긴다.

## 요청 비율은 왜 중요한가

서비스에서는 여러 API가 같은 비율로 호출되지 않는다.

예를 들어 한 쇼핑 서비스의 실제 사용 흐름이 다음과 같다고 가정하자.

~~~text
상품 목록 조회     60%
상품 상세 조회     25%
장바구니 추가      10%
주문 생성           5%
~~~

그런데 성능 테스트에서 상품 목록 조회만 100% 실행하면 이 결과는 **상품 목록 조회 경로의 성능**을 설명할 수는 있지만 서비스 전체 처리 용량을 설명하지는 못한다.

주문 요청은 목록 조회와 달리 여러 테이블을 수정하고 트랜잭션을 오래 점유할 수 있다. 따라서 같은 100 RPS라도 요청 조합이 바뀌면 다음 값이 달라질 수 있다.

~~~text
CPU 사용량
데이터베이스 연결 점유 시간
잠금 대기
디스크 쓰기
외부 API 호출
스레드 점유 시간
응답 시간
~~~

이 때문에 부하 테스트 결과를 기록할 때는 RPS 숫자뿐 아니라 **어떤 요청을 어떤 비율로 보냈는지**를 같이 남겨야 한다.

## 요청이 들어오는 모양도 성능에 영향을 준다

같은 총 요청 수라도 요청이 시간에 따라 어떻게 몰리는지가 다르면 서버의 동작도 달라진다.

### 일정 부하

일정 부하는 일정한 요청량을 계속 유지하는 방식이다.

~~~text
100 RPS
100 RPS
100 RPS
100 RPS
~~~

특정 부하에서 장시간 안정적으로 동작하는지 확인하기 좋다.

### 점진적 증가

점진적 증가는 요청량을 단계적으로 올린다.

~~~text
25
→ 50
→ 100
→ 150
→ 200
→ 250 RPS
~~~

이 방식의 장점은 시스템 상태가 **어느 구간부터 달라지는지** 찾기 쉽다는 점이다.

200 RPS까지는 응답 시간과 오류율이 안정적이었는데 250 RPS에서 갑자기 응답 시간이 증가했다면 다음과 같이 표현할 수 있다.

~~~text
확인된 정상 구간
= 200 RPS

처음 실패가 확인된 구간
= 250 RPS

실제 한계가 존재하는 범위
= 200 < 한계 <= 250
~~~

필요하면 그 사이를 다시 210, 220, 230처럼 좁혀 나갈 수 있다.

### 순간 폭증

순간 폭증은 짧은 시간에 요청이 크게 증가하는 상황이다.

평균적으로는 문제가 없는 서버도 갑작스러운 요청 증가에서는 새로운 연결 생성, 스레드 생성, 캐시 미스, Full GC 같은 문제가 드러날 수 있다.

LINE의 신년 트래픽 사례에서는 평소에는 드러나지 않던 연결 생성 지연이 큰 트래픽이 몰렸을 때 관찰됐다.

## 동시 처리 수(Concurrency)는 무엇인가

동시 처리 수는 **한 시점에 시스템 안에서 아직 끝나지 않은 요청이 몇 개나 존재하는지**를 나타낸다.

예를 들어 매초 100개의 요청이 들어오고 각 요청이 평균 0.1초 만에 끝난다면 요청 하나가 시스템 안에 머무는 시간이 짧기 때문에 동시에 존재하는 요청 수는 비교적 적다.

반대로 같은 100 RPS라도 응답 시간이 평균 2초라면 앞선 요청이 끝나기 전에 새로운 요청이 계속 들어온다.

직관적으로 다음 관계를 생각할 수 있다.

~~~text
동시 처리 수
≈ 초당 처리량 × 평균 응답 시간
~~~

예를 들어:

~~~text
100 RPS × 0.1초
≈ 평균 10개 요청이 동시에 진행

100 RPS × 2초
≈ 평균 200개 요청이 동시에 진행
~~~

이 관계는 Little's Law라는 대기행렬의 기본 관계를 단순화해 이해한 것이다.

여기서 중요한 점은 **응답 시간이 길어지면 같은 RPS에서도 시스템 안에 쌓여 있는 작업의 수가 늘 수 있다**는 것이다.

그 결과 Tomcat 스레드, 데이터베이스 연결, 소켓, 메모리 같은 자원 압력이 다시 커지고 응답 시간이 더 늘어나는 악순환이 생길 수 있다.

## 가상 사용자(VU)는 실제 사용자와 같은가

k6 같은 부하 테스트 도구에서는 가상 사용자(Virtual User, VU)라는 개념을 사용한다.

가상 사용자는 실제 사람 한 명을 완벽하게 복제한 개념이라기보다 **요청 실행 흐름을 반복해서 수행하는 실행 단위**에 가깝다.

예를 들어 가상 사용자 10명이 각각 다음 동작을 반복한다고 해보자.

~~~text
상품 목록 조회
→ 응답 대기
→ 1초 대기
→ 다시 상품 목록 조회
~~~

서버 응답 시간이 길어지면 각 가상 사용자가 다음 요청을 보내기까지 더 오래 기다리게 된다. 따라서 같은 가상 사용자 수에서도 실제 RPS가 낮아질 수 있다.

이 때문에 “가상 사용자 100명으로 테스트했다”라는 말만으로는 실제 요청량을 알 수 없다.

항상 실제 RPS와 응답 시간을 함께 봐야 한다.

## 닫힌 부하 모델과 열린 부하 모델

부하 테스트에는 크게 두 가지 요청 생성 관점이 있다.

### 닫힌 모델

닫힌 모델에서는 정해진 가상 사용자가 요청을 보내고 응답을 받은 뒤 다음 요청을 보낸다.

~~~text
요청
→ 응답 대기
→ 다음 요청
~~~

서버가 느려지면 사용자가 다음 요청을 늦게 보내기 때문에 실제 요청 도착률도 자연스럽게 줄어든다.

이 방식은 “사용자가 이전 작업이 끝나야 다음 행동을 한다”는 흐름을 표현하기 좋다.

### 열린 모델

열린 모델에서는 서버 응답이 느려져도 **정해진 도착률로 요청을 계속 만들려고 한다.**

~~~text
매초 100개의 새 요청을 만들기로 함
→ 이전 요청이 느려도 다음 요청 도착은 계속 예약
~~~

이 방식은 “외부에서 요청이 계속 밀려드는 상황”을 재현하기 좋다.

다만 열린 모델은 충분한 실행 자원이 없으면 부하 생성기 자체가 목표 요청을 만들지 못할 수 있다. 이때 나타나는 대표적인 신호가 **누락된 반복 실행(dropped iteration)**이다.

- [Grafana k6 — Scenarios](https://grafana.com/docs/k6/latest/using-k6/scenarios/)

## 누락된 반복 실행은 무엇인가

k6에서 반복 실행(iteration)은 보통 테스트 스크립트의 한 번의 실행 단위를 의미한다.

도착률 기반 테스트에서 초당 250회의 반복 실행을 예약했는데 필요한 가상 사용자를 충분히 확보하지 못하면 일부 반복 실행을 시작하지 못할 수 있다. 이것이 dropped iteration이다.

쉽게 말하면:

~~~text
목표
이번 1초에 250번 실행

실제로 시작 가능
230번

시작조차 하지 못함
20번
~~~

인 상태다.

이 값이 발생하면 서버가 250 RPS를 못 버틴 것인지, 부하 생성기 자체가 250 RPS를 만들지 못한 것인지 먼저 분리해야 한다.

그래서 PawCycle과 같은 단계형 용량 테스트에서는 dropped iteration을 0으로 요구하는 것이 중요하다. 목표 요청량을 제대로 만들지 못한 결과를 서버 처리 한계처럼 해석하지 않기 위해서다.

## 준비 구간(Warm-up)은 왜 필요한가

애플리케이션은 시작 직후와 어느 정도 요청을 처리한 뒤의 상태가 다를 수 있다.

Java 애플리케이션에서는 다음 변화가 생길 수 있다.

~~~text
JIT 컴파일 진행
Connection Pool 연결 생성
클래스 로딩
캐시 채움
파일/페이지 캐시 변화
DB buffer 상태 변화
~~~

그래서 테스트를 시작하자마자 나온 첫 요청 몇 개를 본 측정 구간과, 일정 시간 준비 요청을 흘린 뒤 측정한 구간은 결과가 다를 수 있다.

준비 구간은 **측정 전에 시스템을 일정한 실행 상태로 만드는 시간**이다.

예를 들어:

~~~text
준비 구간 30초
→ 측정 구간 120초
~~~

처럼 나누면 시작 직후의 일회성 비용이 주 측정 결과에 과도하게 섞이는 것을 줄일 수 있다.

중요한 것은 준비 구간을 넣었다는 사실보다 Before/After 양쪽에서 **같은 준비 조건을 유지하는 것**이다.

## 오류율은 응답 시간과 같이 본다

응답 시간이 짧아졌다고 항상 성능이 좋아진 것은 아니다.

예를 들어:

~~~text
변경 전
p95 = 300ms
오류율 = 0%

변경 후
p95 = 80ms
오류율 = 20%
~~~

라면 변경 후가 더 좋은 결과라고 보기 어렵다.

서버가 정상 처리 대신 빠르게 500 오류를 반환해서 응답 시간이 짧아진 것일 수도 있기 때문이다.

그래서 사용자 관점 성능은 최소한 다음 세 축을 같이 본다.

~~~text
실제 처리량
+ 응답 시간 분포
+ 오류율
~~~

응답 시간의 p95가 정확히 무엇을 의미하는지는 [[07. Latency Percentile과 Tail Latency|07. 응답 시간 백분위와 꼬리 지연]]에서 자세히 설명한다.

## 부하 생성기도 테스트 대상이다

성능 테스트 결과를 볼 때 서버만 의심하면 안 된다.

부하를 만드는 컴퓨터가 먼저 CPU나 네트워크 한계에 도달하면 서버가 아직 여유가 있어도 목표 RPS를 만들지 못한다.

따라서 다음 상태도 확인해야 한다.

~~~text
부하 생성기 CPU
메모리
네트워크
사용 가능한 가상 사용자
연결 수
dropped iteration
timeout
~~~

카카오 메시징팀도 서버 분석에 집중할 수 있도록 부하 생성기 자원을 충분히 확보하고 실제 운영 서버와 테스트 서버의 자원 조건 차이를 함께 고려한다고 설명한다.

## 결과를 읽는 간단한 예

다음은 가상의 단계형 결과다.

| 목표 RPS | 실제 RPS | p95 | 오류율 | 누락 실행 | 해석 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 25 | 25 | 40ms | 0% | 0 | 정상 |
| 100 | 100 | 55ms | 0% | 0 | 정상 |
| 200 | 199 | 85ms | 0% | 0 | 아직 안정 |
| 250 | 215 | 900ms | 3% | 20 | 정상 처리 범위를 벗어난 신호 |

마지막 줄을 보고 곧바로 “서버 최대 처리량은 215 RPS”라고 단정하면 안 된다.

먼저 다음을 확인한다.

~~~text
부하 생성기가 250 RPS를 만들었는가?
dropped iteration이 왜 생겼는가?
서버 오류는 어떤 종류인가?
CPU나 메모리가 포화됐는가?
Tomcat thread가 쌓였는가?
HikariCP 연결 대기가 생겼는가?
DB 응답 시간이 늘었는가?
~~~

이렇게 외부 결과에서 내부 원인으로 내려가는 흐름이 성능 분석의 기본이다.

## 실제 운영과 비슷한 조건을 맞추는 이유

성능 결과는 코드만의 성질이 아니다.

같은 코드라도 CPU 수, 메모리 제한, JVM Heap, DB 사양, 네트워크, 데이터 규모가 다르면 한계가 달라질 수 있다.

그래서 운영과 테스트 환경의 차이를 명시해야 한다.

~~~text
같은 것
코드
JVM 설정
Container limit
DB 종류

다른 것
서버 대수
네트워크 경로
실제 데이터 분포
외부 연동
~~~

“운영과 완전히 같다”고 뭉뚱그리지 않고 어떤 조건은 같고 어떤 조건은 다른지 기록해야 결과를 어디까지 일반화할 수 있는지 판단할 수 있다.

카카오의 스트레스 테스트 글도 테스트 서버와 운영 서버의 조건을 최대한 맞추되 서버 대수가 다르면 절대 수치를 그대로 옮기지 않고 대당 처리량과 자원 사용량으로 해석한다.

## 같은 조건으로 다시 측정해야 한다

성능 개선은 변경 전과 변경 후를 비교하는 실험이다.

예를 들어 인덱스를 추가한 뒤 RPS도 바꾸고 데이터 규모도 바꾸면 무엇 때문에 결과가 달라졌는지 알기 어렵다.

따라서 비교할 때는 가능한 한 다음을 고정한다.

~~~text
동일한 코드 범위 외 조건
동일한 데이터셋
동일한 요청 비율
동일한 RPS 단계
동일한 준비 시간
동일한 측정 시간
동일한 부하 생성 환경
동일한 결과 집계 방식
~~~

그리고 바꾸려는 변수만 최소화한다.

## 핵심 정리

부하 테스트에서 가장 중요한 숫자는 “최대 RPS” 하나가 아니다.

먼저 어떤 요청을 어떤 비율과 속도로 만들었는지 설명할 수 있어야 한다. 그 다음 실제 처리량, 응답 시간 분포, 오류율, 누락된 반복 실행을 확인하고, 이상이 생겼을 때 CPU·메모리·스레드·연결·데이터베이스 같은 내부 계층으로 내려가야 한다.

좋은 부하 테스트는 서버를 세게 때리는 테스트가 아니라 **재현 가능한 조건에서 시스템 상태가 어느 지점부터 어떻게 변하는지 설명할 수 있는 실험**이다.
