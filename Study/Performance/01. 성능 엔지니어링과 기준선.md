# 성능 엔지니어링과 기준선

## 성능 문제를 측정 가능한 문제로 바꾼다

“API가 느리다”는 말에는 중요한 정보가 거의 없다. 어떤 요청이 느린지, 몇 명이 사용할 때 느린지, 데이터가 얼마나 있을 때 느린지, 오류율이 어떤지 모르기 때문이다.

성능 엔지니어링의 첫 단계는 느낌을 재현 가능한 조건과 숫자로 바꾸는 것이다.

~~~text
상품 목록이 느리다
~~~

보다 다음이 훨씬 좋은 문제 정의다.

~~~text
상품 100K, 동일 필터 분포, 100 RPS, 5분 steady-state에서
GET /api/products p95가 80ms → 620ms로 증가하고
Hikari pending이 0 → 35로 증가한다.
~~~

두 번째 문장은 조사할 수 있다.

LINE은 성능 테스트 자동화를 설계하면서 CPU, 메모리, load, swap, disk I/O, 처리량과 응답 시간만으로는 “성능 문제가 있다”는 사실만 확인할 수 있고 “어디가 문제인지”는 찾기 어렵다고 보았다. 그래서 GC, heap, thread, direct memory, file descriptor 같은 JVM 상태까지 같이 수집했다.

- [LINE — 서버 사이드 테스트 자동화 여정 4](https://engineering.linecorp.com/ko/blog/server-side-test-automation-4/)
- [LINE — 서버 사이드 테스트 자동화 여정 5](https://engineering.linecorp.com/ko/blog/server-side-test-automation-5/)

## Baseline은 숫자 하나가 아니다

기준선은 변경 전 p95 하나가 아니다. 다시 같은 조건을 만들 수 있도록 다음을 같이 기록해야 한다.

| 범주 | 기록할 내용 |
| --- | --- |
| 코드 | commit, release, JVM option |
| 인프라 | CPU, Memory, Container limit, DB spec |
| 데이터 | row 수, 관계, cardinality, distribution, skew |
| 요청 | endpoint, method, payload, request mix |
| 부하 | RPS, concurrency, duration, ramp-up |
| 상태 | cold/warm, cache, DB buffer 상태 |
| 결과 | throughput, error, p50/p95/p99 |
| 내부 | CPU, memory, GC, thread, Hikari, DB |

변경 전 p95가 200ms이고 변경 후 120ms라도 After에서 요청량이 절반이면 개선이라고 할 수 없다. 데이터 규모가 달라도 직접 비교가 어렵다.

## 무엇을 검증하는 테스트인가

테스트 이름보다 먼저 질문을 정한다.

~~~text
정상 예상 부하에서 요구 성능을 만족하는가?
→ Load Test

한계 지점은 어디인가?
→ Stress Test

순간 폭증에 어떻게 반응하는가?
→ Spike Test

오랜 시간 누수와 성능 저하 없이 유지되는가?
→ Endurance Test
~~~

우아한형제들 결제 시스템 사례는 정상 동작, 순간 최대치와 병목, 장기간 안정성, 장애·복구를 서로 다른 목적으로 나눠 테스트했다.

- [우아한형제들 — 결제 시스템 성능, 부하, 스트레스 테스트](https://techblog.woowahan.com/2572/)

카카오 메시징 팀도 평시 트래픽과 신년 트래픽을 구분하고 실제 서비스와 비슷한 READ/WRITE 비율을 맞춘다. 테스트 대상 서버 스펙 역시 운영과 맞추려 한다.

- [카카오 — 메시징 서버의 스트레스 테스트 노하우](https://tech.kakao.com/posts/822)

## Throughput과 Latency를 같이 본다

Throughput은 단위 시간 동안 처리한 양이고 latency는 한 작업의 체류 시간이다.

부하가 증가하면 보통 다음 흐름을 보인다.

~~~text
낮은 부하
→ 자원 여유
→ latency 안정

부하 증가
→ throughput 증가
→ 자원 사용 증가

포화 접근
→ queue 증가
→ tail latency 증가

포화 초과
→ timeout / error / dropped request
~~~

“CPU가 100%가 되는 순간이 한계”라고 단순화하면 안 된다. Connection Pool, DB lock, thread queue가 먼저 포화될 수 있다.

## Warm-up과 Steady State

Java/Spring 서비스는 시작 직후와 안정화 이후 상태가 다를 수 있다.

- class loading
- JIT compilation
- connection pool 준비
- filesystem cache
- DB buffer pool
- application cache

cold-start 자체가 목표가 아니라면:

~~~text
기동
→ warm-up
→ 지표 안정 확인
→ 측정 window
~~~

로 나눈다.

다만 warm-up 시간은 고정 규칙이 아니다. 배포 직후 첫 요청이 문제라면 cold-start가 바로 측정 대상이다.

## Load Generator도 측정 대상이다

서버가 아니라 부하 발생기가 먼저 포화되면 target RPS를 만들지 못한다.

확인할 것:

- generator CPU
- generator memory
- network
- VU 부족
- dropped iteration
- client timeout

카카오 메시징 팀은 server bottleneck을 보기 위해 client cluster에 충분한 자원을 주어 client-side noise를 줄인다.

Grafana k6도 arrival-rate에서 VU가 부족하면 scheduled iteration이 drop될 수 있음을 설명한다.

- [Grafana k6 — Scenario concepts](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/)

## Threshold는 목표를 코드로 만든다

예:

~~~text
error rate < 1%
p95 < 200ms
actual RPS가 목표를 충분히 따라감
~~~

k6 Threshold는 latency와 error 같은 요구를 PASS/FAIL 조건으로 만들 수 있다.

- [Grafana k6 — Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)

하지만 Threshold는 “문제가 있는가”를 판정할 뿐 “왜 문제인가”는 설명하지 않는다. 원인 분석에는 내부 지표가 필요하다.

## 실제 기준선을 만드는 순서

~~~text
1. 목적을 한 문장으로 정의
2. endpoint와 request mix 정의
3. dataset 조건 정의
4. load generator 검증
5. warm-up과 측정 window 분리
6. 외부 결과 + 내부 지표 동시 수집
7. error와 dropped request 확인
8. 동일 조건 재실행 가능하게 기록
~~~

우아한형제들 포인트 시스템도 실제 주문 피크를 기준으로 목표 TPS를 정하고, nGrinder로 부하를 조절하며 Pinpoint와 RDS를 같이 보고 병목을 수정한 뒤 다시 측정했다.

- [우아한형제들 — 신규 포인트 시스템 전환기 #2](https://techblog.woowahan.com/2588/)

## 정리

좋은 기준선은 “큰 숫자를 만든 결과”가 아니라 **같은 조건에서 다시 비교할 수 있는 출발점**이다.


## 기준선이라는 말을 쉽게 다시 풀어보면

기준선(Baseline)은 “변경하기 전 숫자” 한 개가 아니다. **나중에 변경 효과를 비교하기 위해 현재 상태를 조건과 함께 묶어서 저장한 출발점**이다.

예를 들어 다음 두 결과만 보면 개선처럼 보인다.

~~~text
변경 전 p95 = 200ms
변경 후 p95 = 120ms
~~~

하지만 변경 후 테스트에서 요청량이 절반으로 줄었다면 직접 비교할 수 없다.

~~~text
변경 전
100 RPS
p95 = 200ms

변경 후
50 RPS
p95 = 120ms
~~~

요청이 적어졌기 때문에 빨라졌을 수 있기 때문이다.

그래서 좋은 기준선은 숫자와 함께 조건을 저장한다.

~~~text
어떤 코드인가
어떤 데이터 규모인가
몇 RPS인가
요청 비율은 무엇인가
서버 CPU/메모리는 얼마인가
JVM 설정은 무엇인가
DB 사양은 무엇인가
준비 구간은 얼마인가
측정 시간은 얼마인가
오류율은 얼마인가
~~~

이 조건을 함께 보존해야 나중에 “같은 조건에서 인덱스 하나만 추가했더니 p95가 얼마나 달라졌다”처럼 말할 수 있다.

## 벤치마크와 기준선은 어떻게 다른가

벤치마크(Benchmark)는 특정 시스템이나 구현의 성능을 정해진 조건에서 측정하는 시험에 가깝다. 기준선은 그 벤치마크 결과 중 **앞으로 비교 기준으로 사용할 현재 상태**라고 이해하면 쉽다.

~~~text
벤치마크
→ 성능을 측정하는 시험

기준선
→ 그 시험에서 확보한 비교 출발점
~~~

예를 들어 같은 상품 목록 API를 25, 50, 100, 200 RPS에서 측정하는 과정 전체는 벤치마크가 될 수 있다. 이 가운데 개선 전 결과를 저장해 두고 이후 인덱스 추가 결과와 비교한다면 그 개선 전 결과가 기준선 역할을 한다.

## 처리량과 응답 시간을 함께 봐야 하는 이유

처리량(Throughput)은 일정 시간 동안 시스템이 처리한 작업량이다. HTTP API에서는 초당 요청 수(RPS)를 자주 사용한다.

응답 시간(Latency)은 요청 하나가 시작해서 끝날 때까지 걸린 시간이다.

둘은 서로 다른 질문에 답한다.

~~~text
처리량
→ 한 시간에 얼마나 많은 일을 끝냈는가

응답 시간
→ 한 작업은 얼마나 오래 걸렸는가
~~~

처리량이 늘어도 응답 시간이 크게 늘면 사용자 경험이 나빠질 수 있다.

반대로 응답 시간은 매우 짧지만 실제 처리량이 목표보다 낮다면 서버가 충분한 요청을 처리하고 있다고 말하기 어렵다.

그래서 성능 결과는 최소한 다음처럼 함께 읽는다.

~~~text
목표 RPS
실제 RPS
오류율
p50
p95
p99
~~~

응답 시간 백분위는 [[07. Latency Percentile과 Tail Latency|응답 시간 백분위와 꼬리 지연]]에서 자세히 설명한다.

## 부하 테스트, 스트레스 테스트, 순간 폭증 테스트는 무엇이 다른가

세 테스트는 모두 요청을 보내지만 질문이 다르다.

### 부하 테스트

부하 테스트(Load Test)는 **정상적으로 예상하는 부하에서 요구 성능을 만족하는지** 확인한다.

~~~text
예상 피크 100 RPS
→ 100 RPS에서 오류 없이 안정적인가
→ p95 요구를 만족하는가
→ CPU와 DB에 충분한 여유가 있는가
~~~

### 스트레스 테스트

스트레스 테스트(Stress Test)는 **어느 지점부터 시스템이 정상 범위를 벗어나는지** 찾는다.

~~~text
25
→ 50
→ 100
→ 150
→ 200
→ 250 RPS
~~~

처리량이 더 이상 증가하지 않거나 오류, 지연, 재시작이 나타나는 첫 구간을 찾는다.

### 순간 폭증 테스트

순간 폭증 테스트(Spike Test)는 짧은 시간에 요청이 크게 몰릴 때 시스템이 어떻게 반응하는지 확인한다.

평균 100 RPS를 처리할 수 있어도 순간적으로 1,000 RPS가 들어왔을 때 연결 생성, Thread 증가, GC, Queue가 급격히 변할 수 있다.

### 장시간 안정성 테스트

장시간 안정성 테스트(Endurance Test)는 오랜 시간 같은 부하를 유지했을 때 메모리 누수, 연결 누수, 파일 핸들 누수, 점진적인 지연 증가가 생기지 않는지 확인한다.

우아한형제들의 결제 시스템 사례는 이런 테스트 목적을 분리해서 접근한다.

- [우아한형제들 — 결제 시스템 성능, 부하, 스트레스 테스트](https://techblog.woowahan.com/2572/)

## 준비 구간과 안정 구간은 왜 필요한가

Java 애플리케이션은 시작 직후와 일정 시간 요청을 처리한 뒤의 상태가 다를 수 있다.

처음에는 클래스가 로딩되고 JIT 컴파일이 진행되며 DB 연결도 아직 충분히 만들어지지 않았을 수 있다.

그래서 cold-start 자체를 측정하려는 것이 아니라면 보통 다음처럼 나눈다.

~~~text
기동
→ 준비 구간
→ 지표가 어느 정도 안정
→ 실제 측정 구간
~~~

준비 구간(Warm-up)은 “30초가 정답” 같은 고정 규칙이 아니다. 현재 시스템에서 시작 직후의 일회성 비용을 주 측정 결과에서 얼마나 분리할지 결정하는 장치다.

반대로 배포 직후 첫 요청 지연이 문제라면 준비 구간으로 숨기면 안 된다. 그때는 cold-start 자체가 측정 대상이다.

## 임계값은 왜 필요한가

임계값(Threshold)은 성능 요구를 PASS/FAIL 조건으로 만든 것이다.

예를 들어:

~~~text
오류율 < 1%
p95 < 200ms
누락된 반복 실행 = 0
~~~

처럼 표현할 수 있다.

임계값의 장점은 “그래프가 대충 좋아 보인다”는 주관적 판단을 줄인다는 점이다.

하지만 임계값을 통과했다고 원인을 알 수 있는 것은 아니다. p95가 실패했다면 그 다음에는 CPU, GC, Thread, Connection Pool, DB 같은 내부 지표를 조사해야 한다.

## 기준선 문서를 읽을 때 기억할 것

좋은 기준선은 큰 숫자를 자랑하는 기록이 아니다.

다음 질문에 답할 수 있어야 한다.

~~~text
무엇을 측정했는가
왜 그 조건을 선택했는가
어떤 값이 정상 범위였는가
어디서 처음 실패했는가
결과를 다시 만들 수 있는가
이후 변경에서 무엇만 달라졌는가
~~~
