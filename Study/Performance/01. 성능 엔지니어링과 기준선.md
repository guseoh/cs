# 성능 엔지니어링과 기준선

성능을 공부할 때 가장 먼저 버려야 하는 생각은 “서버가 몇 RPS까지 버티는가”만 알면 된다는 생각이다. 시스템 성능은 하나의 숫자로 설명되지 않는다. 같은 서버가 500 RPS를 처리하더라도 요청이 모두 단순 조회인지, 데이터베이스 갱신과 외부 API 호출이 섞여 있는지에 따라 의미가 달라진다. 같은 500 RPS에서도 오류율이 0%인지 10%인지, p95 응답 시간이 100ms인지 3초인지에 따라 사용자가 경험하는 서비스 품질은 완전히 다르다.

그래서 성능 엔지니어링은 단순히 “빠르게 만드는 작업”이 아니다. **어떤 조건에서 시스템이 얼마나 많은 일을 처리하고, 사용자가 얼마나 기다리며, 어느 지점부터 정상 범위를 벗어나는지를 측정하고 설명하는 작업**에 가깝다.

LINE의 성능 테스트 자동화 사례도 단순 CPU와 요청 수만 확인하는 것으로는 병목 위치를 알기 어렵다고 보고, 시스템 자원과 JVM 상태를 함께 수집하는 방향으로 발전했다. 이 관점이 중요하다. 성능 테스트의 목적은 “느리다”를 발견하는 데서 끝나는 것이 아니라 “어느 계층에서 왜 느려지는가”를 조사할 수 있는 근거를 확보하는 데 있다.

## 성능 문제는 먼저 측정 가능한 질문으로 바꿔야 한다

“우리 서버가 느리다”는 문장은 문제를 해결하기에 너무 넓다. 느리다는 것이 사용자가 느끼는 HTTP 응답 시간이 길다는 뜻인지, 배치 작업이 오래 걸린다는 뜻인지, 데이터베이스 쿼리가 오래 걸린다는 뜻인지 알 수 없기 때문이다.

따라서 성능 문제를 다룰 때는 질문을 측정 가능한 형태로 바꾼다.

예를 들어 다음 문장은 아직 모호하다.

~~~text
상품 목록 API가 느리다.
~~~

이를 조금 더 구체적으로 바꾸면 다음과 같다.

~~~text
Product 10,000개 조건에서
GET /api/products에 100 RPS를 120초 동안 보냈을 때
정상 응답 비율은 얼마인가?

실제 처리량은 목표 100 RPS를 유지하는가?

p50 / p95 / p99 응답 시간은 각각 얼마인가?

같은 시간에
CPU / JVM GC / Tomcat Thread / HikariCP / MySQL은
어떤 상태인가?
~~~

이렇게 바꾸면 “느리다”가 단순한 인상이 아니라 검증할 수 있는 질문이 된다.

성능 엔지니어링의 첫 단계는 도구를 고르는 일이 아니다. **무엇을 성능 문제라고 부를 것인지 정의하는 것**이다.

## 처리량과 응답 시간은 서로 다른 질문에 답한다

처리량(Throughput)은 일정 시간 동안 시스템이 완료한 작업량을 뜻한다. HTTP 서비스에서는 초당 요청 수(Requests Per Second, RPS)를 처리량 지표로 자주 사용한다.

응답 시간(Latency)은 요청 하나를 보낸 뒤 결과를 받을 때까지 걸린 시간을 뜻한다.

둘은 같은 값이 아니다.

~~~text
처리량
→ 일정 시간 동안 얼마나 많은 일을 끝냈는가?

응답 시간
→ 한 요청을 끝내는 데 얼마나 오래 걸렸는가?
~~~

예를 들어 두 서버가 모두 실제 200 RPS를 처리한다고 해보자.

~~~text
서버 A
actual RPS = 200
p95 = 120ms
error = 0%

서버 B
actual RPS = 200
p95 = 2,000ms
error = 0%
~~~

두 서버의 처리량만 보면 같지만 사용자 경험은 크게 다르다.

반대로 다음과 같은 결과도 가능하다.

~~~text
목표 RPS = 250
실제 RPS = 170
p95 = 80ms
~~~

응답 시간만 보면 빨라 보이지만 애초에 목표 요청량을 충분히 실행하지 못했다면 “250 RPS에서 80ms”라고 기록하면 안 된다.

따라서 성능 결과를 읽을 때는 최소한 **목표 부하, 실제 처리량, 오류율, 응답 시간 분포**를 함께 봐야 한다.

초당 요청 수와 실제 요청 생성 방식은 [[02. 부하 테스트와 Workload Modeling|부하 테스트와 요청 흐름 모델링]]에서 더 자세히 다룬다. p50·p95·p99는 [[07. Latency Percentile과 Tail Latency|응답 시간 백분위와 꼬리 지연]]에서 설명한다.

## 기준선은 변경 전 숫자 하나가 아니다

기준선(Baseline)은 나중에 변경 효과를 비교하기 위해 저장해 두는 현재 상태다.

여기서 중요한 것은 “현재 p95가 200ms였다”는 숫자 하나가 기준선이 아니라는 점이다. 어떤 코드, 어떤 데이터, 어떤 부하, 어떤 인프라에서 측정했는지가 함께 있어야 한다.

예를 들어 다음 기록은 부족하다.

~~~text
Before p95 = 200ms
After  p95 = 100ms
~~~

After 테스트에서 요청량을 절반으로 줄였다면 응답 시간이 낮아지는 것은 자연스러운 결과일 수 있다.

~~~text
Before
Product 10K
100 RPS
p95 = 200ms

After
Product 10K
50 RPS
p95 = 100ms
~~~

이 결과로 “코드 변경 덕분에 2배 빨라졌다”고 말할 수 없다.

기준선은 보통 다음 조건과 함께 기록한다.

~~~text
소스 코드 버전
Container image
Dataset identity
데이터 규모와 분포
요청 시나리오
목표 RPS
실제 RPS
준비 구간
측정 구간
서버 사양
Container limit
JVM 설정
DB 사양
오류율
p50 / p95 / p99
주요 Host / JVM / DB 지표
~~~

이 조건이 있어야 나중에 하나의 요소만 바꾸고 비교할 수 있다.

## 벤치마크와 기준선은 같은 말이 아니다

벤치마크(Benchmark)는 정해진 조건에서 성능을 측정하는 시험이다. 기준선은 그 시험 결과 중 이후 비교에 사용할 출발점이다.

예를 들어 Product 10,000개 조건에서 25 → 50 → 100 → 150 → 200 RPS를 단계적으로 실행하는 전체 작업은 하나의 성능 벤치마크가 될 수 있다.

그 뒤 특정 쿼리에 인덱스를 추가하고 같은 벤치마크를 반복한다면 인덱스 추가 전 결과가 기준선이 된다.

~~~text
벤치마크
→ 측정 방법과 조건

기준선
→ 비교 대상으로 보존한 현재 결과
~~~

이 차이를 구분하면 “성능 테스트를 한 번 실행했다”와 “비교 가능한 성능 근거를 만들었다”의 차이가 보인다.

## 정상 부하와 한계 탐색은 목적이 다르다

부하 테스트(Load Test)는 예상되는 정상 부하에서 요구 성능을 만족하는지 확인한다.

예를 들어 서비스가 평상시 50 RPS, 피크 시간대 100 RPS를 예상한다면 100 RPS 부근에서 오류 없이 안정적인지 확인할 수 있다.

스트레스 테스트(Stress Test)는 정상 범위를 넘어 요청량을 점진적으로 올리면서 어느 구간부터 처리량, 응답 시간, 오류율, 자원 사용이 비정상적으로 변하는지 찾는다.

~~~text
25 RPS
→ 50
→ 100
→ 150
→ 200
→ 250
~~~

이 방식의 목적은 “250이라는 큰 숫자를 달성하는 것”이 아니다.

예를 들어 200 RPS까지는 정상인데 250 RPS에서 처음으로 오류와 누락된 반복 실행이 생겼다면 다음처럼 표현할 수 있다.

~~~text
확인된 정상 구간
≤ 200 RPS

처음 실패가 관찰된 구간
= 250 RPS

현재 한계가 존재하는 범위
200 < saturation point ≤ 250
~~~

필요하면 이후 210, 220, 230처럼 범위를 좁힐 수 있다.

순간 폭증 테스트(Spike Test)는 짧은 시간에 요청이 크게 증가하는 상황을 검증한다. 평상시에는 문제가 없는 서버도 갑작스러운 연결 생성, Thread 증가, 캐시 미스, GC, Connection Pool 경쟁 때문에 다른 동작을 보일 수 있다.

장시간 안정성 테스트(Endurance Test)는 일정 부하를 오랫동안 유지하면서 메모리 누수, 연결 누수, 점진적인 응답 시간 증가 같은 문제를 찾는다.

우아한형제들의 결제 시스템 성능 테스트 글은 성능 테스트와 부하·스트레스 테스트의 목적을 나누어 생각하는 데 참고하기 좋다.

- [우아한형제들 — 결제 시스템 성능, 부하, 스트레스 테스트](https://techblog.woowahan.com/2572/)

## 포화점은 단순 CPU 100%가 아니다

포화(Saturation)는 현재 시스템의 어떤 자원이 요청 증가를 더 이상 자연스럽게 흡수하지 못하는 상태를 뜻한다.

CPU가 100%가 되는 상황이 대표적이지만 포화는 여러 위치에서 발생할 수 있다.

~~~text
Tomcat Thread가 모두 바쁨
HikariCP Connection이 모두 사용 중
DB Lock 대기 증가
Disk I/O 대기 증가
Network Connection 생성 한계
Load Generator가 요청 생성에 실패
Container memory limit 도달
~~~

따라서 “CPU가 아직 60%니까 여유가 있다”는 결론은 위험하다.

CPU는 여유가 있어도 HikariCP pending이 증가하면서 요청이 Connection을 기다릴 수 있다. 또는 DB Lock 때문에 Connection이 오래 점유될 수 있다.

성능 한계를 찾을 때는 **사용자 관점 결과와 내부 자원 포화 신호를 연결해서** 봐야 한다.

## 준비 구간은 시작 직후의 일회성 비용을 분리한다

Java 애플리케이션은 실행 직후와 일정 시간 요청을 처리한 뒤 상태가 다를 수 있다.

처음에는 클래스 로딩이 진행될 수 있고 JIT 컴파일이 아직 충분히 이루어지지 않았을 수 있다. Connection Pool이 아직 필요한 연결을 만들지 않았거나 DB Buffer와 파일 시스템 Page Cache가 차갑게 시작할 수도 있다.

그래서 cold start 자체를 측정하려는 것이 아니라면 준비 구간(Warm-up)을 둔다.

~~~text
애플리케이션 기동
→ 준비 요청
→ 상태가 어느 정도 안정
→ 실제 측정
~~~

예를 들어 다음처럼 구성할 수 있다.

~~~text
준비 구간
30초

측정 구간
120초
~~~

여기서 30초가 정답이라는 뜻은 아니다. 준비 구간의 목적은 시작 직후의 일회성 비용과 정상적인 지속 상태를 구분하는 것이다.

반대로 배포 직후 첫 요청이 느린 문제가 실제 사용자 문제라면 준비 구간으로 숨기면 안 된다. 그 경우에는 cold start가 측정 대상이 된다.

## 안정 상태라는 말도 확인이 필요하다

준비 구간이 끝났다고 무조건 안정 상태(Steady State)가 되는 것은 아니다.

실제로 다음 값이 여전히 크게 변하고 있다면 아직 안정되지 않았을 수 있다.

~~~text
RPS가 계속 증가/감소
Heap 바닥선이 계속 상승
Thread 수가 계속 증가
Connection 수가 계속 증가
GC 패턴이 급격히 변함
Cache hit ratio가 계속 변함
~~~

따라서 “30초 Warm-up을 넣었으니 안정 상태”라고 기계적으로 생각하지 않는다.

측정 전에 주요 지표가 어느 정도 반복 가능한 패턴을 보이는지 확인하는 것이 좋다.

## 오류가 빠르게 반환되면 응답 시간은 좋아 보일 수 있다

성능을 응답 시간만으로 보면 잘못된 결론을 낼 수 있다.

예를 들어:

~~~text
변경 전
p95 = 300ms
error = 0%

변경 후
p95 = 70ms
error = 25%
~~~

변경 후 서버가 정상 처리를 하지 않고 즉시 500 오류를 반환한다면 응답 시간만 낮아질 수 있다.

이 경우 “성능이 좋아졌다”고 할 수 없다.

그래서 사용자 관점의 최소 결과는 다음과 같이 함께 본다.

~~~text
목표 요청량
실제 처리량
정상 응답 비율
오류율
시간 초과
p50
p95
p99
누락된 반복 실행
~~~

## 임계값은 기대 성능을 기계적으로 검사하게 한다

임계값(Threshold)은 “이 조건을 만족해야 정상으로 본다”는 기준을 코드나 설정으로 표현한 것이다.

예를 들어:

~~~text
정상 상태 코드 오류율 = 0%
누락된 반복 실행 = 0
p95 < 300ms
~~~

처럼 정할 수 있다.

임계값이 있으면 그래프를 보고 “대충 괜찮아 보인다”라고 판단하는 일을 줄일 수 있다.

하지만 임계값은 원인을 설명하지 않는다.

p95 임계값이 실패했다면 그 다음에는 CPU, GC, Thread, HikariCP, Query, Lock 같은 내부 상태를 조사해야 한다.

Grafana k6는 Threshold를 통해 성능 조건을 PASS/FAIL 기준으로 만들 수 있다.

관련 자료:
- [Grafana k6 — Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)

## 부하 생성기도 성능 실험의 일부다

성능 테스트에서는 서버만 테스트 대상이라고 생각하기 쉽다.

하지만 부하를 만드는 컴퓨터가 먼저 CPU, 메모리, Network, 가상 사용자 수 한계에 도달하면 서버가 아직 여유가 있어도 목표 요청량을 만들지 못한다.

예를 들어:

~~~text
target = 500 RPS
actual = 350 RPS
server CPU = 40%
server error = 0%
dropped iterations 증가
~~~

라면 서버가 350 RPS 한계라고 바로 결론내리면 안 된다.

부하 생성기가 500 RPS를 만들 수 있었는지부터 확인해야 한다.

그래서 목표 요청 수와 실제 처리량을 분리하고, 누락된 반복 실행과 부하 생성기 자원도 함께 본다.

LINE의 성능 테스트 자동화 사례에서도 테스트 전용 환경과 부하 생성 구조를 분리하고 서버 지표를 함께 수집했다.

## 성능 요구와 SLO는 같은 맥락에서 연결된다

서비스 수준 목표(Service Level Objective, SLO)는 서비스가 어느 정도 품질을 유지해야 하는지를 수치로 정의할 때 사용하는 개념이다.

예를 들어 API 성능 요구를 다음처럼 표현할 수 있다.

~~~text
정상 응답 성공률
99.9% 이상

p95 응답 시간
300ms 이하
~~~

이때 성능 테스트는 “이 요구를 현재 시스템이 어떤 부하에서 만족하는가”를 검증하는 수단이 된다.

하지만 SLO를 정할 때 다른 회사의 p95 100ms 같은 숫자를 그대로 가져오면 안 된다. 업무 특성, 사용자 기대, 네트워크 경로, 요청 종류가 다르기 때문이다.

먼저 현재 서비스의 실제 기준선을 만들고 비즈니스 요구와 사용자 경험을 고려해 목표를 잡는 것이 좋다.

## 성능 결과는 환경 설명과 함께 보존해야 한다

성능 결과는 코드 자체의 고정된 성질이 아니다.

같은 코드도 CPU 수, Container limit, JVM Heap, DB 사양, Network 경로, 데이터 규모에 따라 다른 결과를 낸다.

따라서 “우리 API는 500 RPS를 처리한다”라는 문장은 불완전하다.

더 정확한 표현은 다음과 같다.

~~~text
특정 commit
Product 10K Dataset
Backend 1개
2 vCPU
Container memory 640MiB
특정 MySQL 사양
GET /api/products
목표 500 RPS
120초 측정

→ actual RPS ...
→ p95 ...
→ error ...
~~~

이렇게 조건을 붙여야 다른 환경에 숫자를 그대로 일반화하는 실수를 줄일 수 있다.

## 성능 엔지니어링은 한 번의 테스트가 아니라 반복 실험이다

성능 문제를 개선하는 과정은 보통 다음 흐름을 반복한다.

~~~text
현재 조건 정의
→ 기준선 측정
→ 병목 후보 확인
→ 가설
→ 가장 작은 변경
→ 같은 조건 재측정
→ 결과와 대가 확인
→ 유지 / 보류 / 제외
~~~

중요한 것은 기술 도입이 아니라 **같은 조건에서 무엇이 실제로 달라졌는지 설명하는 것**이다.

Redis, 비동기 처리, Connection Pool 증가, JVM 옵션 변경 같은 기술은 모두 후보일 뿐이다. 현재 병목과 관계가 없다면 도입하지 않는 결정이 더 좋은 성능 엔지니어링일 수 있다.
