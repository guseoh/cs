## 1. 데이터 타입은 단순히 "숫자냐 문자열이냐"를 정하는 것이 아니다

```sql
CREATE TABLE products (
    id         BIGINT,
    name       VARCHAR(200),
    price      DECIMAL(12, 2),
    stock      INT,
    created_at DATETIME
);
```

데이터 타입은 가장 먼저 **값의 의미와 가능한 범위**를 결정한다. 하지만 백엔드 개발에서는 한 단계 더 생각해야 한다.

`INT`와 `BIGINT`는 둘 다 정수인데 왜 구분하고, `VARCHAR(50)`과 `VARCHAR(500)`은 무엇이 다르며, 가격에 왜 `DOUBLE`이 아니라 `DECIMAL`을 사용하는가? 타입 선택은 저장 공간뿐 아니라 비교 방식, 계산 정확성, 인덱스 크기, 향후 데이터 증가까지 영향을 준다.

#### 정수는 필요한 범위만큼 선택한다
| 타입          |   저장 공간 |        SIGNED 범위 |
| ----------- | ------: | ---------------: |
| `TINYINT`   |  1 byte |       -128 ~ 127 |
| `SMALLINT`  | 2 bytes | -32,768 ~ 32,767 |
| `MEDIUMINT` | 3 bytes |   약 -838만 ~ 838만 |
| `INT`       | 4 bytes |     약 -21억 ~ 21억 |
| `BIGINT`    | 8 bytes |          약 ±922경 |
- 무조건 가장 작은 타입이나 큰 타입을 선택하는 것은 좋은 선택이 아니다.

> [!more]- (확장) InnoDB의 Secondary Index에는 해당 Row의 Primary Key 값도 함께 저장되기 때문
> 
> 예를 들어 PK를 `INT`로 잡으면 4바이트이다. 그런데 굳이 `BIGINT`로 잡으면 8바이트이다. 차이는 그냥 Row 하나당 4바이트 차이처럼 보이지만 InnoDB에서는 Secondary Index마다 PK 값을 같이 저장하니 영향이 퍼진다.
> 
> ```SQL
> CREATE TABLE members (
>     id BIGINT PRIMARY KEY,
>     email VARCHAR(100),
>     nickname VARCHAR(50),
>     created_at DATETIME,
> 
>     INDEX idx_email (email),
>     INDEX idx_nickname (nickname),
>     INDEX idx_created_at (created_at)
> );
> 
> idx_email
> email + id
> 
> idx_nickname
> nickname + id
> 
> idx_created_at
> created_at + id
> ```
> - Secondary Index가 3개 있다면 내부적으로 대략 이런 식이다.
> - 즉, **`id`가 `BIGINT`면 8바이트짜리 PK가 각 Secondary Index에 반복해서 들어간다.**

## 2. 가격에 `FLOAT`를 쓰지 않는 이유 - 값의 "정확성"도 타입의 일부다

```SQL
price FLOAT

price DECIMAL(12, 2)
```
둘 다 소수점을 저장하지만 의미는 상당히 다르다. `FLOAT`와 `DOUBLE`은 [부동소수점(approximate value)]{소수점의 위치를 고정하지 않고 움직이게 해서 아주 큰 수와 아주 작은 수를 넓게 표현하는 방식} 타입이다. 표현 가능한 비트 패턴으로 실수를 근사하기 때문에 어떤 십진수는 정확히 표현되지 않을 수 있다.

`DECIMAL`은 MySQL에서 정확한 고정소수점(exact fixed-point) 값을 저장한다.

`DECIMAL(12, 2)`에서 `12`는 전체 자릿수, `2`는 소수점 아래 자릿수다. 따라서 최대 10자리 정수부 + 2자리 소수부를 표현할 수 있다.

상품 가격이 `19900.00`이고 결제·할인·세금 계산을 반복한다면 몇 원의 오차도 의미가 있다. 그래서 금액처럼 **십진수의 정확성이 비즈니스 의미 그 자체인 값에는 일반적으로 `DECIMAL`**이 자연스럽다.

반대로 센서 측정값이나 과학 계산처럼 미세한 근사 오차를 허용하면서 넓은 범위의 실수가 필요한 데이터라면 `FLOAT`나 `DOUBLE`이 적합할 수 있다.

## 3. 문자열과 시간 타입에서는 "길이와 의미"가 중요하다
```sql
code CHAR(10)
name VARCHAR(200)
```
- `CHAR`는 고정 길이 문자열이고 `VARCHAR`는 가변 길이 문자열이다.

상품명처럼 "고양이 사료", "강아지 ~"처럼 길이가 크게 달라지는 값에는 `VARCHAR`가 자연스럽다. 반면 길이가 항상 동일하거나 거의 고정된 코드 값은 `CHAR`가 후보가 될 수 있다.

MySQL에서 `VARCHAR(M)`의 `M`은 **byte가 아니라 [character]{사람이 보는 문자 하나} 수**다. 실제 저장 시에는 값 자체와 함께 길이를 표현하기 위한 1~2 byte가 추가되고, 실제 byte 수는 Character Set의 영향을 받는다. 그래서 `VARCHAR(255)`가 항상 255 byte를 의미하지 않는다.

예를 들어 `utf8mb4`에서는 문자 하나가 여러 byte를 사용할 수 있다. 따라서 `VARCHAR(100)`을 단순히 100 bytes라고 생각하면 안 된다.

## 4. 제약 조건은 "잘못된 데이터를 저장하지 못하도록 DB에 규칙을 선언하는 것"이다

데이터 타입으로는 `stock INT`에서 타입이 `INT`이므로 문자열을 넣는 문제를 막을 수 있다. 하지만 `-500` 값도 허용하므로 수량이 음수일 수는 없다는 도메인 규칙이 깨진다.

제약 조건은 **그 타입 안에서 어떤 상태가 우리 데이터 모델에서 유효한가**를 추가로 제한한다. 

```sql
CREATE TABLE products (
    id BIGINT NOT NULL AUTO_INCREMENT,
    sku VARCHAR(64) NOT NULL,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(12, 2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),

    PRIMARY KEY (id),
    CONSTRAINT uq_products_sku UNIQUE (sku),
    CONSTRAINT chk_products_price CHECK (price >= 0),
    CONSTRAINT chk_products_stock CHECK (stock >= 0)
);
```

`name VARCHAR(200) NOT NULL`은 상품명이 문자열이라는 것뿐 아니라 이름 없는 상품을 허용하지 않는다.는 뜻이고, `price DECIMAL(12, 2) NOT NULL`은 정확한 소수점 가격을 저장하면서 음수 가격도 허용하지 않는다는 뜻이다. 

```sql
INSERT INTO products (
    sku, name, price, stock
)
VALUES (
    'DOG-001', '강아지 사료', -10000, 10
);
```
애플리케이션이 실수로 위 SQL을 실행하면 `CHECK` 조건을 만족하지 않으므로 DB가 거부한다. MySQL에서 CHECK 조건은 각 Row에 대해 `FALSE`가 되면 제약 위반이 발생한다.

| 제약            | 막으려는 잘못된 상태            |
| ------------- | ---------------------- |
| `NOT NULL`    | 반드시 있어야 하는 값이 없음       |
| `PRIMARY KEY` | Row를 고유하게 식별할 수 없음     |
| `UNIQUE`      | 중복되면 안 되는 값이 중복됨       |
| `FOREIGN KEY` | 존재하지 않는 다른 Row를 참조함    |
| `CHECK`       | 비즈니스상 허용하지 않는 범위/조건의 값 |
| `DEFAULT`     | 값이 생략됐을 때 사용할 기본값 제공   |
- `email VARCHAR(255) UNIQUE` 구문은 중복 이메일 값은 저장할 수 없다는 뜻이다. 하지만 해당 Column이 `NULL`을 허용한다면 MySQL의 UNIQUE Index에는 여러 개의 NULL이 들어갈 수 있다.

#### `Check`와 `NULL`도 같이 생각해야 한다
```sql
price DECIMAL(12, 2)
    CHECK (price >= 0)
```

- Mysql의 CHECK는 조건식이 `FALSE`이면 실패하고 `TRUE`나 `UNKNOWN`이면 허용한다.
- `NULL ≥ 0`의 결과는 `TRUE/FALSE`가 아니라 `UNKNOWN`이므로 `CHECK(price >= 0)`만으로는 `NULL`을 금지하지 못한다.

```sql
price DECIMAL(12, 2)
    NOT NULL
    CHECK (price >= 0)
```
- 그래서 서로 다른 제약을 조합해야 한다.

## 5. 제약 조건은 애플리케이션 검증을 대신하는 것이 아니라 마지막 방어선이다

```sql
SELECT ... WHERE email = ?
→ 없음
→ INSERT
```

서버가 여러 대이거나 거의 동시에 두 요청이 들어오면 둘 다 `INSERT`가 가능하다. Application의 사전 확인만으로는 두 작업 사이에서 데이터 상태가 바뀌는 것을 완전히 막을 수 없다.
