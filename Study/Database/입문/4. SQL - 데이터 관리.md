## 1. SQL로 테이블 구조를 관리한다는 것은 무엇인가?

테이블은 단순히 데이터를 담는 표가 아닌 어떤 컬럼이 존재하는지, 각 컬럼이 어떤 값을 저장할 수 있는지, 어떤 값은 반드시 있어야 하는지, 중복을 허용할지 같은 **데이터의 구조와 규칙을 정의한 대상**이다.

이 구조를 만들거나 변경하는 SQL을 일반적으로 **DDL(Data Definition Language, 데이터 정의어)**이라고 부른다.

| SQL              | 역할                    |
| ---------------- | --------------------- |
| `CREATE TABLE`   | 새로운 테이블 생성            |
| `ALTER TABLE`    | 기존 테이블의 구조 변경         |
| `DROP TABLE`     | 테이블 자체 삭제             |
| `TRUNCATE TABLE` | 테이블 구조를 유지하면서 모든 행 제거 |
- `TRUNCATE`는 행을 제거하지만 MySQL에서는 DDL로 분류된다.
  

### 테이블 생성과 구조 정의
```sql

USE learning_shop;

CREATE TABLE products (
    id BIGINT NOT NULL PRIMARY KEY,
    sku VARCHAR(50) NOT NULL UNIQUE,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    CONSTRAINT chk_stock CHECK (stock >= 0)
);

```

- MySQL은 `CREATE TABLE`을 받으면 SQL에 작성된 컬럼 정의, 자료형, 제약 조건 등이 유효한지 검사하고 테이블을 등록한다. 
- InnoDB 테이블이라면 이후 행을 저장하고 인덱스를 관리할 수 있도록 관련 내부 구조도 준비한다.
	- InnoDB는 **MySQL에서 데이터를 실제로 저장하고 관리하는 스토리지 엔진(Storage Engine)**이다.
	- 즉, MySQL이 SQL을 해석하고 실행하는 데이터베이스 시스템이라면, InnoDB는 그 안에서 데이터를 저장·조회·수정하고 트랜잭션을 관리하는 핵심 구성 요소이다.

이 시점에서는 상품 데이터는 존재하지 않으며, **상품 데이터를 저장할 수 있는 구조**가 만들어진다.
예를 들어 `products`에는 아래 규칙이 적용된다.
- `id`는 각 상품 행을 고유하게 식별한다.
- `sku`는 반드시 존재하며 중복될 수 없다.
- `price`는 소수점 이하 두 자리까지 저장하는 숫자다.
- `stock`의 기본값은 0이고 음수는 허용하지 않는다.

여기서 `price`에 `CHECK(price ≥ 0)`이 없기 때문에 음수 가격은 현재 DDL에서 허용된다. 어떤 제약을 정의했느냐에 따라 DB가 보장하는 범위가 달라지는 것이다.

### 기존 테이블의 구조를 바꾸는 ALTER TABLE

```sql
ALTER TABLE products
ADD COLUMN description VARCHAR(500) NULL;
```
- 상품마다 상세 설명을 저장하는 기능이 추가됐다고 가정하면, 기존 `products`테이블에는 `description`이 없으므로 `ALTER`로 컬럼을 추가할 수 있다.
![[스크린샷 2026-10-10 132731.png|실행 전후의 구조|500]]

이 경우 기존 상품 행도 새로운 컬럼을 가진 테이블 구조에 맞춰 해석된다. 별도의 값을 채우지 않았고 새 컬럼이 `NULL`을 허용하므로, 기존 행의 `description`은 조회했을 때 `NULL`로 나타난다.

반면 기존 행들이 존재하는 테이블에 `NOT NULL` 컬럼을 추가한다면 기존 행을 어떤 값을 채울지까지 생각해야 한다.

또한 `ALTER TABLE`로 컬럼의 타입을 변경하거나, 이름을 바꾸거나, 인덱스와 제약 조건을 추가·삭제하는 작업도 가능하다.

### 실무에서는 ALTER TABLE 한 줄의 비용이 매우 클 수 있다

MySQL은 DDL 작업의 종류에 따라 테이블 구조를 변경하는 방식을 선택한다.

- `INSTANT`: 기존 데이터를 다시 작성하지 않고, 주로 테이블의 구조 정보(메타데이터)만 변경하는 방식이다.
- `INPLACE`: 테이블 전체를 새 테이블로 복사하지 않고 변경하는 방식이다. 다만 인덱스 생성이나 데이터 재구성이 필요하면 시간이 오래 걸릴 수 있다.
- `COPY`: 새로운 구조의 테이블을 만들고 기존 데이터를 복사하는 방식이다.

**`INPLACE`는 테이블 전체를 복사하지 않는다는 뜻이지, 반드시 빠르게 끝나거나 잠금(Lock)이 발생하지 않는다는 뜻은 아니다.** 실제 변경 작업에 따라 많은 데이터를 처리해야 할 수도 있고, 다른 사용자의 조회나 수정이 잠시 대기할 수도 있다.

MySQL에는 테이블 구조를 사용하는 작업끼리 충돌하지 않도록 **메타데이터 잠금(Metadata Lock)** 이라는 보호 장치가 있다. 

> [!more]- ❓INPLACE는 왜 Lock을 사용할까?
> 
> 데이터를 어떻게 변경하는지와, 변경하는 동안 다른 작업을 허용할지는 서로 다른 문제이기 때문이다.
> 
> 예를 들어  회원 100만 명의 `name`컬럼에 인덱스를 추가하는 동안 다른 사용자가 회원 이름을 수정하려고 한다고 가정하자.
> 
> MySQL은 인덱스를 만드는 중에도 일부 조건에서도 다른 사용자의 조회와 수정을 허용할 수 있지만 테이블 구조를 안전하게 변경하려면 작업 시작과 마무리 과정에서 잠금이 필요할 수 있다.
> 
> MySQL에서는 이 동시 접근 허용 수준을 지정하는 `LOCK` 옵션이 존재한다.
> 
> | 옵션 | 다른 사용자의 작업 |
> |---|---|
> | `LOCK=NONE` | 조회와 데이터 변경 허용 |
> | `LOCK=SHARED` | 조회 허용, 데이터 변경 차단 |
> | `LOCK=EXCLUSIVE` | 조회와 데이터 변경 모두 차단 |

따라서 `ALTER TABLE`은 SQL 실행 자체가 짧아 보여도 실제로는 잠금 대기나 테이블 재구성 때문에 시간이 길어지고, 다른 요청에도 영향을 줄 수 있다.

## 2. 데이터를 추가하고 변경하는 INSERT, UPDATE, DELETE

테이블 구조가 만들어져다면 이제 그 안에 실제 데이터를 저장해야 한다.

이처럼 기존 테이블의 데이터를 추가하거나 수정·삭제하는 SQL을 **DML(Data Manipulation Language, 데이터 조작어)** 이라고 한다.

DDL이 태이블 자체의 정의를 다룬다면, DML은 주로 그 구조 안에 저장된 **행(Row)**을 대상으로 작업한다.

### INSERT - 새로운 행을 저장한다

```sql
INSERT INTO products (id, sku, name, price, stock)
VALUES
    (101, 'SKU-001', '텀블러', 15900.00, 5),
    (102, 'SKU-002', '머그컵', 8900.00, 3);
```

SQL을 실행하면 MySQL은 컬럼과 값의 대응 관계를 해석하고 각 값이 컬럼의 데이터 타입 및 제약 조건을 만족하는지 검사한다. 제약 조건을 위반하지 않으면 행을 저장한다. InnoDB에서는 기본 키를 기준으로 행을 관리하며 관련 인덱스도 함께 유지한다.

위 SQL 구문에서는 `INSERT INTO products` 바로 뒤에 컬럼 이름을 명시했다는는 점이다.

컬럼 이름을 생략하고 값을 넣는 SQL도 가능하지만, 테이블에 새로운 컬럼이 추가되거나 컬럼 구성이 변경되면 SQL의 의미가 달라질 수 있다. 반면 **컬럼을 명시하면 어떤 값이 어느 컬럼에 저장되는지 분명해지고, 기본값을 사용하는 컬럼을 의도적으로 생략하기도 쉬워진다.**

### UPDATE - 기존 행의 값을 변경한다

```sql
UPDATE products
SET price = 14900.00
WHERE id = 101;
```
- `UPDATE`는 테이블에서 `WHERE` 조건을 만족하는 행을 찾아 해당 컬럼의 값을 변경한다.
- `WHERE id = 101`은 업데이트할 대상을 결정하고, `SET price = 14900.00`은 그 대상의 값을 어떻게 변경할지를 결정한다.

`UPDATE`가 단순히 새 값으로 덮어쓰는 기능만 있는 것은 아니다. 기존 값을 이용해 계산할 수도 있다.

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 101
  AND stock > 0;
```
- 현재 재고에서 1을 빼되, 재고가 0보다 큰 상품만 수정하라는 구문이다.

InnoDB에서 이 변경은 하나의 SQL 문장으로 처리되며, 동일한 행을 변경하는 동시 요청에 대해서도 DB의 잠금과 조건 평가가 관여한다. 이런 조건부 변경은 재고가 부족한데 무조건 감소시키는 실수를 예방하는 데 도움이 된다.

```sql
UPDATE products
SET stock = 0;
```
- `UPDATE`는 `WHERE`가 반드시 필요한 문법은 아니다.

### DELETE - 행 자체를 제거한다

```sql
DELETE FROM products
WHERE id = 102;
```
- 상품 ID가 102인 행을 삭제하고, 테이블 구조나 다른 행은 그대로 유지한다.
- UPDATE와 마찬가지로 `WHERE`를 생략할 수 있다. 하지만 모든 행이 삭제 대상이므로 신중하게 사용해야 한다.

SQL에서 행을 삭제했다고 해서 반드시 그 즉시 데이터 파일의 모든 관련 공간이 운영체제에 반환되는 것은 아니다. InnoDB는 트랜잭션과 이전 버전 처리 등을 관리하기 때문에 논리적으로 행이 삭제되는 것과 내부 저장 공간의 정리는 별개일 수 있다.

## 3. DELETE, TRUNCATE, DROP은 모두 삭제하지만 결과는 다르다


| SQL                              | 삭제 범위       | 테이블 구조 유지 | 일반적인 트랜잭션 ROLLBACK |
| -------------------------------- | ----------- | --------- | ------------------ |
| `DELETE FROM products WHERE ...` | 조건에 해당하는 행  | 유지        | 가능                 |
| `DELETE FROM products`           | 모든 행        | 유지        | 가능                 |
| `TRUNCATE TABLE products`        | 모든 행        | 유지        | 불가능                |
| `DROP TABLE products`            | 테이블 자체와 데이터 | 제거        | 불가능                |
`DELETE`는 행을 대상으로 작업한다. 따라서 InnoDB에서 아직 `COMMIT`하지 않은 트랜잭션이라면 `ROLLBACK`으로 해당 변경을 되돌릴 수 있다.

반면 `TRUNCATE TABLE`은 일반적인 행 삭제와 [다른 방식]{테이블 자체를 비우고 새로 만든 것처럼 초기화하는 방식}으로 테이블 내용을 비운다. **InnoDB에서는 실질적으로 테이블을 비우고 다시 생성하는 방식**에 가깝고, `AUTO_INCREMENT` 값도 초기화된다. 
- DDL이므로 일반적인 사용자 `ROLLBACK`으로 되돌릴 수 없고, 다른 테이블이 외래 키로 참조하는 경우 실행이 제한될 수 있다.

기존 회원의 ID가 1부터 100까지 사용된 상태에서 모든 회원을 삭제했다고 가정:
- `DELETE` 후 회원을 추가하면 일반적으로 ID가 101부터 시작.
- `TRUNCATE` 후 회원을 추가하면 일반적으로 ID가 1부터 다시 시작.

`DROP TABLE`은 데이터뿐 아니라 테이블의 정의 자체를 제거한다. 따라서 이후 같은 이름으로 조회하면 테이블이 존재하지 않는다는 오류가 발생한다.

`TRUNCATE`가 `DELETE`보다 대량 삭제에서 빠를 수 있다고 해서 운영에서 무조건 더 좋은 것은 아니다. 처리 결과뿐 아니라 되돌릴 수 있는지, 외래 키가 있는지, 다른 서비스가 동시에 테이블을 사용하고 있는지까지 고려해야 한다.

### DDL과 DML은 COMMIT에서도 중요한 차이가 있다

MySQL에서 일반적인 `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `TRUNCATE TABLE`은 **암묵적 커밋(Implicit Commit)**을 발생시킨다. (DDL은 암묵적 커밋을 발생시킨다.)

이것은 실행 중인 트랜잭션이 있더라도 DDL을 수행하기 전에 해당 트랜잭션이 커밋될 수 있다는 뜻이다.

```sql
START TRANSACTION;

UPDATE products
SET price = 10000
WHERE id = 101;

ALTER TABLE products
ADD COLUMN memo VARCHAR(100);

ROLLBACK;
```
- 마지막 `ROLLBACK`이 모든 작업을 취소할 것 같지만, MySQL에서는 그렇지 않다.

`ALTER TABLE` 실행 전에 앞선 변경이 암묵적으로 커밋된다. 따라서 마지막 `ROLLBACK`은 이미 확정된 가격 변경을 되돌리지 못한다. 테이블에 추가된 `memo` 컬럼도 그대로 남는다.

이것이 **DDL과 DML을 같은 트랜잭션에 넣었다고 해서 모두 함께 되돌릴 수 있는 것은 아니다**라는 의미다.

MySQL은 **원자적 DDL(Automic DDL)**을 지원하지만, 이것은 서버 장애가 발생했을 때 지원되는 DDL 작업이 일부만 반영된 상태로 남지 않도록 하는 성질이지, 사용자가 `ROLLBACK`으로 자유롭게 DDL을 취소할 수 있다는 뜻은 아니다.

| 구분     | Atomic DDL             | 사용자 `ROLLBACK`    |
| ------ | ---------------------- | ----------------- |
| 목적     | 장애 발생 시 DDL의 일관성 보장    | 트랜잭션의 변경 취소       |
| 작동 상황  | DDL 실패 또는 서버 장애 후 복구   | 사용자가 트랜잭션을 롤백할 때  |
| DDL 취소 | 미완료 작업을 내부적으로 복구·취소 가능 | 성공한 DDL을 취소할 수 없음 |
| 핵심     | 전부 반영되거나 반영되지 않음       | 트랜잭션의 변경을 되돌림     |

## 4. 실무에서는 UPDATE와 DELETE를 어떻게 안전하게 실행할까?

```sql
UPDATE products
SET price = price * 0.9
WHERE stock = 0;
```

SQL 자체는 유효하다. 하지만 실행 전에 아래 질문이 필요하다.

“재고가 없는 모든 상품의 가격을 할인하는 것이 맞는가? 판매 중지된 상품도 포함되는가? 몇 개 행이 변경되는가? 원래 가격을 복원할 수 있는가?” 이 질문들이 잘못되었다면 문법 오류가 아니라 **대상 선정 오류**인 것이다.

```sql
SELECT id, sku, name, price, stock
FROM products
WHERE stock = 0;
```
- 운영에서는 `WHERE` 조건을 `SELECT`에 먼저 적용해 대상 행을 확인한다.
- 대상과 건수를 확인하고, 사전에 정한 변경 범위가 맞는지 검토한 후 실제 `UPDATE`를 수행한다.

InnoDB라면 별도의 트랜잭션에서 변경하고 `COMMIT` 전에 결과를 검증하는 방법도 사용할 수 있다. 하지만 트랜잭션을 오래 열어두면 잠금을 오래 유지할 수 있으므로, 대량 변경은 별도의 작업 계획이 필요하다.

실제 운영에서는 아래 원칙이 중요하다.
- 변경 대상은 먼저 조회해서 확인한다.
- 가능한 한 고유한 식별자나 명확한 조건으로 대상을 제한한다.
- 변경 건수와 변경 후 결과를 검증한다.
- 복구 방법과 백업 상태를 확인한다.
- 대량 변경 시 잠금, 실행 시간, 다른 요청에 주는 영향을 고려한다.
