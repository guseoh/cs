## 들어가기 전

Spring Boot로 쇼핑몰을 개발한다고 가정하자. 상품 목록은 누구나 조회할 수 있지만 주문을 생성하거나 자신의 주문 내역을 확인하려면 로그인이 필요하다. 또한 일반 회원에게는 상품 가격을 변경하거나 다른 회원의 개인정보를 조회하는 기능이 허용되어서는 안 된다.

이러한 요구사항을 해결하려면 서버는 두 가지 문제를 해결해야 한다.
1. 요청을 보낸 사용자가 누구인지 신뢰할 수 있는 방법으로 확인
2. 그 사용자가 요청한 작업을 수행할 권한이 있는지도 판단

이 두 가지 역할을 **인증(Authentication)과 인가(Authorization)**라고 한다.

![[스크린샷 2026-10-20 132708.png|500]]Spring Security는 인증과 인가를 일관된 구조로 처리하도록 지원하는 보안 프레임워크이다.

## 1. 인증(Authentication): 사용자가 주장하는 신원을 어떻게 신뢰할 수 있을까?

인증은 **요청을 보낸 주체가 자신이 주장하는 신원을 가지고 있는지 검증하는 과정**이다.

예를 들어 아이디와 비밀번호를 이용한 로그인이다. 사용자가 로그인 화면에 계정 정보를 입력하면 서버는 제출한 정보가 실제로 등록된 계정의 인증 정보와 일치하는지 확인한다.

여기서 중요한 점은 사용자가 누구라고 말하는 것과 서버가 그 사용자를 확인하는 것은 다르다는 점이다.

```http
GET /api/members/10
```
- 예를 들어 회원 번호가 10인 사용자의 프로필을 조회하는 API가 있다고 가정하자.
- 이 요청에 포함된 `10`은 서버가 조회해야 할 회원의 식별자일 뿐이다.

![[스크린샷 2026-10-21 122253.png|500]]
#### 인증 과정에서는 실제로 무엇을 검증할까?

아이디와 비밀번호를 이용한 일반적인 로그인에서는 서버가 전달받은 아이디로 계정을 찾은 다음, 제출된 비밀번호가 해당 계정의 비밀번호 검증 정보와 일치하는지 확인한다.

실제 애플리케이션에서는 비밀번호를 평문으로 저장하지 않는다. 적절한 비밀번호 해시 알고리즘을 사용해 저장하고, 로그인 시에는 제풀된 비밀번호를 검증하는 방식으로 처리한다.

검증에 성공하면 서버는 요청자가 해당 계정의 올바른 안증 수단을 제시했다고 판단할 수 있다. 반대로 실패한다면 그 계정으로 인증을 하지 않는다.

#### 로그인에 성공한 뒤에는 어떻게 사용자를 알아볼까?

로그인은 인증을 수행하는 대표적인 과정이지만, 인**증이라는 개념이 최초 로그인에만 한정되는 것은 아니다.**

[HTTP는 기본적으로 각각의 요청이 독립적]{무상태(Stateless) 프로토콜로, 서버가 이전 요청의 상태를 기본적으로 기억하지 않는다.}이다. 따라서 사용자가 로그인에 성공한 뒤 새로운 HTTP 요청을 보내더라도, 서버가 아무런 근거 없이 이전 요청의 사용자와 동일하다고 판단할 수는 없다.

웹 애플리케이션은 이를 해결하기 위해 세션이나 토큰 등 인증 상태를 확인할 수 있는 수단을 활용한다.

세션 기반 인증에서는 서버가 관리하는 인증 상태를 이용할 수 있고, 토큰 기반 방식에서는 요청에 포함된 토큰을 검증하여 사용자 정보를 결정할 수 있다.
