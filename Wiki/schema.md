# Wiki 기록 스키마 — v1

UTF-8 Markdown과 Obsidian 호환 YAML frontmatter를 사용한다. 안정적인 ID, 독립된 주제별 파일, 상대 Markdown 링크를 우선한다. 파일 크기 자체보다 정보의 복원 가능성을 우선한다. 메타데이터는 기계 판독 가능하게 유지하고 본문으로 인과관계와 불확실성을 설명한다.

## 필수 메타데이터

```yaml
---
id: WIKI-0001
type: decision
project: llm-wiki
status: accepted
created_at: 2026-11-03
updated_at: 2026-11-03
evidence_level: user-confirmed
sources: []
depends_on: []
supersedes: []
related_to: []
---
```

- `id`: 전역 고유·불변 ID. 결정 파일은 `<PREFIX>-NNNN.md`, 프로젝트는 `PRJ-*`를 사용한다.
- `type`: `decision`, `project`, `knowledge`, `lesson`.
- `project`: 안정적인 소문자 식별자. 공통 지식은 `shared`를 사용한다.
- `status`: 결정은 `proposed`, `accepted`, `superseded`, `rejected`; 프로젝트는 `active`, `paused`, `archived`; 그 외는 `draft`, `published`.
- `created_at` / `updated_at`: ISO 날짜(`YYYY-MM-DD`), 생성일 이후 수정일을 사용한다.
- `evidence_level`: `source-verified`(출처 확인), `user-confirmed`(사용자 확정), `unverified`(추정·미확인).
- `sources`: 확인 가능한 URL 목록. 비어 있으면 본문에 근거와 한계를 설명한다.
- `depends_on`: 선행 기록 ID.
- `supersedes`: 이 결정이 대체하는 기존 결정 ID.
- `related_to`: 비방향 관련 기록 ID.
- 프로젝트의 선택 필드 `capture_mode`: `full`, `design-only`, `manual`. [기록 정책](capture-policy.md)과 일치해야 한다.

관계는 제목이 아닌 ID를 참조한다. 모든 ID는 기존 기록에 연결되어야 하며 related_to만으로 인과관계를 추정하지 않는다.

## 문서 작성 언어 및 상세도

신규·실질적으로 수정하는 Wiki 문서의 제목·본문·표 머리글·요약은 한국어를 기본으로 합니다. YAML 메타데이터, 식별자, 경로, URL 및 참조 ID는 그대로 보존합니다. 기존 영어 기록을 일괄 번역하여 이력을 변경하지 않습니다. 소제목도 한국어로 작성합니다.

이전 대화를 읽지 않은 에이전트도 기록만으로 판단의 이유와 현재 검증 범위를 복원할 수 있어야 한다. 중요한 항목은 설명 문단으로 구체화하며 표·코드·파일 경로·PR/CI/커밋 링크는 필요한 경우에 활용한다. 모르는 원인이나 측정하지 않은 수치를 채워 넣지 않는다. 다음 항목 중 적용되지 않거나 미확인인 부분은 그렇게 표시한다.

| 문서 유형 | 작성 기준 |
| --- | --- |
| Decision | 배경, 문제, 요구사항과 제약, 대안, 선택 근거, 트레이드오프와 영향, 구현·검증 및 출처 |
| Lesson | 발생 문제·증상, 원인 분석, 시도 및 실패 대안, 해결 과정, 재발 방지와 적용 한계 |
| Knowledge | 핵심 원리, 작동 흐름, 적용 조건, 사례, 근거와 한계 |
| Project Snapshot | 기준일, 구현·검증된 상태, 미확인 상태, 제약, 결정, 작업 의존성과 다음 단계 |
| Journal | 변경 목적, 주요 변경 및 관련 파일·PR, 검증 방법과 실제 결과, 남은 문제; 작은 사건은 간결하게 |
| History / Inbox | 변경 이력·출처 식별자·검토 상태 중심; 후보 메타데이터에 의미를 창작하지 않음 |

검증 근거는 확인한 경우 테스트 조건·수치·커밋 SHA·PR·CI 링크를 포함하고, 사용자 확정과 독립 검증을 구분한다. 상세도를 높이기 위해 기존 기록 범위를 확장하거나 대화 원문을 복제하지 않는다.

## 본문 계약

### 결정

```md
# 결정 요약
## 배경
## 결정
## 선택하지 않은 대안
## 결과와 제약
## 구현 및 검증
## 출처와 결정 경위
## 관련 기록
```

`accepted`는 선택 확정을 뜻한다. 구현·배포·실제 검증 성공은 별도의 근거로 기록한다.

### 프로젝트 현황

```md
# 프로젝트 이름
## 현재 상태 (기준일)
## 확정된 결정
## 제약 조건
## 미해결 질문과 다음 작업
## 근거와 검증 범위
```

프로젝트 현황은 최신 확인 상태를 담되 과거 결정을 덮어쓰지 않는다. 현재 상태를 모르면 미검증으로 표시한다.

### 지식 / 교훈

주장·원리·적용 조건·근거·한계·관련 ID를 기록한다. 실패와 교훈은 증상에서 원인, 시도, 결과, 해결 및 재발 방지까지 확인된 인과관계를 설명한다.

## 갱신 및 조회 규칙

1. 신규 기록 전 ID·제목·의미 중복을 확인한다.
2. 파일 하나에 독립 결정 하나를 기록한다. 대화 원문을 저장하지 않는다.
3. 관련 색인과 프로젝트 현황을 갱신한다.
4. 의미·관계 변경 시 updated_at을 갱신한다.
5. supersedes 관계를 따라 현재 결정의 유효성을 확인한다.
6. depends_on 순환과 끊긴 관계 ID를 금지한다.
7. 의미가 바뀐 확정 결정은 기존 근거를 덮어쓰지 않고 새 기록으로 남긴다.
