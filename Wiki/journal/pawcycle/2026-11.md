### 시스템 고도화와 로컬 검증

- **P0 후보 — 결제 복구와 운영 가시성.** 기존 `UNKNOWN` 및 정기결제 `PROCESSING` 대사와 일반 결제 `NORMAL/PROCESSING`을 구분한다. 관리자 운영 목록은 일반 결제 `PROCESSING`을 조회하지 않고, 일부 미확정 건은 대사 시도 상한에 도달하면 목록에서 빠진다. 오래 머문 결제·상한 도달 건의 조회와 운영자 수동 조회를 우선 검토한다. PG 호출 전 중단과 승인 후 내부 완료 실패를 격리 MySQL과 모의 PG에서 구분하고, 조회 단계에서는 결제·주문·재고가 그대로인지 확인하는 안이다. 내부 완료는 진행 중 요청과의 경합 및 중복 부작용 방지 조건을 별도로 검증해야 한다. - **P0 후보 — 장애 발생과 정상 복구 알림.** 로컬 Prometheus·Grafana·Alertmanager와 Discord 발생·복구 경로를 활용해 Slack 전달, 중복 억제, 복구 확인을 검증한다. 운영용 Slack·Discord 전송 경로는 정상 상태에선 알리지 않는다. [로컬 장애 Runbook](https://github.com/guseoh/pawcycle-commerce/blob/b3b2235d/docs/runbook/INC-BASE-001-local-incident-response.md) · [운영 알림 Runbook](https://github.com/guseoh/pawcycle-commerce/blob/b3b2235d/docs/runbook/OPS-AUTO-010-backend-state-alert.md)

### 프로젝트 전체 대규모 성능 검증 제안

- **검증 범위.** 사용자가 제시한 관심 범위는 관리자 화면 단독 조회에서 PawCycle 전체로 확장됐다. 회원·상품·리뷰·주문·정기배송을 연결한 합성 데이터에서 조회·쓰기·배치가 겹칠 때 어떤 흐름이 먼저 한계에 도달하는지 확인한다. 데이터 행 수, 요청률, CPU·메모리 한도를 각각 기록한다. 회원·상품·리뷰 100만 건은 검토할 데이터 규모 예시이며, 초기에는 한 축씩 늘려 원인을 구분한다. 인기 SKU에 리뷰와 주문을 집중시키고 오래된 주문 이력과 특정 시간에 몰린 정기배송 일정을 구성한다.
- **기존 근거.** 상품 1만 개 생성 계약, 상품·주문·구독 등을 포함한 혼합 읽기 k6 도구, 공유 SKU Checkout 경합 측정, 정기배송 예정 건 1만 개 처리 기록을 재사용한다. 기존 혼합 읽기 도구는 결제·Checkout 같은 쓰기를 포함하지 않으며 상품 생성 계약도 리뷰 정렬과 전체 커머스 분포를 재현하는 범위에는 한계가 있다. 통합 혼합 부하는 새로운 실험으로 설계한다. [상품 데이터 계약](https://github.com/guseoh/pawcycle-commerce/blob/b3b2235d/infra/performance/catalog-scale.md) · [혼합 읽기 부하](https://github.com/guseoh/pawcycle-commerce/blob/b3b2235d/docs/runbook/PERF-PH8-003-isolated-commerce-k6.md) · [공유 SKU 경합](https://github.com/guseoh/pawcycle-commerce/blob/b3b2235d/docs/reports/PERF-COMMERCE-003/report.md) · [정기배송 실험](https://github.com/guseoh/pawcycle-commerce/blob/b3b2235d/docs/reports/PERF-PH10-006/PERF-PH10-007-gate-a-decision-note.md)
- **측정 순서와 판정.** 같은 요청률에서 데이터 크기를 바꿔 비용 변화를 보고, 같은 데이터에서 요청률을 높여 기능별 한계를 찾는다. 이후 상품·리뷰 탐색을 유지하면서 인기 SKU Checkout과 정기배송 배치를 겹친다. p95·p99, 실제 처리량·오류·미실행 요청, MySQL 조회·락 대기, Hikari 대기, CPU·메모리·디스크를 같은 시간축으로 대조한다. 원인에 맞는 변경 하나를 골라 같은 조건에서 재측정하고 재고 초과 판매·중복 주문·정기배송 누락 여부를 확인한다. 결과물은 데이터 생성·부하 재현 스크립트, 첫 한계가 관측된 조건, 병목 근거, 개선 전후 비교, 정합성 검증이다.

위 운영·설계·성능 우선순위는 제안 상태다. 새 통합 데이터셋 생성·부하 실행·운영 검증은 미실행이며, 다음 설계 대상과 성능 합격 기준은 미확정이다.

- **동시성 결과.** 결제 만료, 정기결제, 재시도, 구독 주문에는 이미 동시 실행 테스트가 있었다. 빠져 있던 배송 알림만 추가했다. 회차 보정은 구독별 잠금·version 확인이 있고 기본으로 꺼져 있다. 분산 잠금을 도입할 근거는 없었다.
