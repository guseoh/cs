# 물류 시스템 — Java/Spring 학습 프로젝트

## 현재 상태 (기준일: 2026-11-19)

- **도메인 확정:** 물류 시스템. 후속 결정에 따라 물류는 [통합 학습 저장소](backend-systems-lab.md)의 6개 독립 앱 중 `logistics` 모듈로 운영한다.
- **목적 확정:** 학습·이해·설계와 실험 우선. 성과에 따라 추후 포트폴리오 확장 여부 별도 판단
- **진행 장소 확정:** 현재 ChatGPT 채팅 세션에서 AI와 요구사항을 함께 분석하고, 코드는 채팅으로 제공받아 사용자가 자신의 개발 환경에서 작성·실행
- **단계:** 요구사항 분석·학습 방식 및 기록 체계 확정. 구체적인 제품 요구사항, MVP 구현, 저장소는 아직 미완료
- **새 소스 저장소:** 아직 없음. 물류 전용 저장소 대신 여섯 앱 + 설계 교재 트랙을 담는 **단일 통합 저장소**를 만들기로 결정했다. 이름·URL·GitHub Wiki 주소는 미확정
- **기록 위치:** 현재 `guseoh/cs/Wiki`. 미래 원본 저장소의 GitHub Wiki에는 프로젝트별 상세 기록을 만들 계획이며, 연결·쓰기 가능 여부는 생성 후 확인해야 함

## 확정된 결정

1. [BLR-0014](../decisions/BLR-0014.md): AI가 채팅에 완성 코드/명령어를 주고 사용자가 빠르게 작성·실행한다. 요구사항·설계·핵심 로직·성능과 기술 선택은 공동 검토한 뒤 사용자 결정
2. [LGR-0001](../decisions/LGR-0001.md): 물류 학습을 현재 채팅에서 시작하며, 중요한 진행·설계·검증 결과를 `cs/Wiki`에 남긴다. 원본 저장소가 생기면 프로젝트 Wiki 상세 기록과 중앙 Wiki를 함께 관리한다
3. 어려운 기술(Kafka, 장애 복구, 데이터 파이프라인, 캐시, 고급 성능, 낯선 알고리즘)은 원리와 단계별 힌트를 먼저 제공하고 **첫 시도 기회**를 우선한다. 사용자 요청 시 정답 코드로 넘어갈 수 있다
4. 제안, 결정, 작성, 로컬 실행, 테스트, 성능 검증, 운영 적용은 분리한다

## 설계 방향 제안 (아직 확정되지 않음)

**첫 후보 문제: 출고센터 선택과 재고 할당.** 가상 주문의 상품·수량·배송지를 입력받아 출고 가능 센터 후보를 찾고, 재고를 안전하게 예약하며, 출고 이벤트로 상태를 변경하는 작은 시스템으로 시작한다.

- 처음부터 OMS/WMS/TMS 전체를 구현하거나 MSA·Kafka·Redis를 강제하지 않는다.
- 첫 기능과 도메인 경계를 정한 다음, 실패 사례와 실험을 통해 락·메시징·캐시 등을 필요에 따라 검토한다.
- 주문·재고·출고의 정합성은 후보 학습 문제이고, 기술 스택과 테이블·API·배포 전략은 아직 선택되지 않았다.

세부 실습 단계와 검토 질문: [물류 학습 설계·실험 로드맵 초안](../knowledge/LGK-0001.md).

## 기록·동기화 계획

| 정보 종류 | 생성 전 `cs/Wiki` | 미래 원본 저장소 Wiki | 계속 유지할 중앙 기록 |
| --- | --- | --- | --- |
| 프로젝트 상태·다음 작업 | 이 프로젝트 현황 및 월별 진행 기록 | Home·진행 현황 | 상태·검증 범위·원본 링크 |
| 확정된 설계·트레이드오프 | Decision으로 기록 | 상세 ADR/설계·ERD | 핵심 결정 및 관계 |
| 요구사항·API·데이터 모델 초안 | 학습 가이드에 제안/미확정 표시 | 요구사항·설계 문서 | 요지·링크·최종 승인 상태 |
| 코드·테스트·실험/실패 | 근거 수치 있는 진행 요약 | 실행 명령·실험 환경·결과·실패 로그 | 핵심 교훈·실험 링크 |

기록은 **확정·제안·미검증을 구분**한다. 원본 저장소가 생성되면 프로젝트 Wiki 지원 및 쓰기 권한을 확인한다. 지원 불가하면 사용자와 상의해 버전 관리되는 문서 폴더를 대체 대상으로 결정한다. 두 위치를 실제 갱신하지 못한 경우 완료라 주장하지 않는다.

## 제약 조건

- 단일 채팅에서 학습과 설계를 이어가되 진행 기록은 별도 Wiki에 남긴다.
- 처음 접한 기술에 정답부터 강제하지 않고 힌트 중심으로 학습한다.
- 과도한 학습 노트보다 실제 의사결정, 실패 원인, 검증 결과 위주로 자세히 기록한다.
- 기존 PawCycle/Board/DevPedia 소스와 로드맵은 이 신규 프로젝트의 규칙 때문에 자동 변경되지 않는다.
- 초기 학습용이므로 운영 트래픽, 수익화, 포트폴리오 성과를 입증했다고 주장하지 않는다.

## 다중 도메인 단일 저장소 운영 확정 (2026-11-19 후속)

이전에는 다중 도메인 저장소를 **검토 중**이었으나 후속 사용자 메시지에서 [BSL-0001](../decisions/BSL-0001.md)가 **accepted**로 확정되었다. 물류는 독립적으로 실행되는 Spring Boot `logistics` 모듈이며, 다른 5개 앱과 상호 연동을 강제하지 않는다. [교재 설계 1·2권 트랙](../decisions/BSL-0002.md)도 **같은 통합 저장소**에 둔다.

- 물류의 핵심 학습 목표(재고·출고·정합성·트랜잭션)는 유지한다.
- 실제 Gradle 설정·API/DB·첫 물류 기능 범위는 아직 논의 단계다.
- 신규 통합 저장소·Wiki 생성과 코드/테스트는 **미완료**다.
- 통합 공통 진행은 [프로젝트 현황](backend-systems-lab.md)과 [공통 Journal](../journal/backend-systems-lab/2026-11.md)을 확인한다.

## 미해결 질문과 다음 작업

1. 첫 문제 범위를 출고센터 결정·재고 할당으로 확정할지, 다른 물류 하위 도메인(창고 입출고·배송 상태 추적·경로 최적화)으로 정할지 논의
2. 핵심 사용자/업무 시나리오, 기능/비기능 요구사항, 정상·실패 흐름 도출
3. 용어와 도메인 경계(주문·센터·재고·할당·출고·배송)를 정의하고 정합성 규칙/수용 테스트 초안 제시
4. DB·API 설계 대안 검토 후 사용자의 결정 기록
5. 소스 저장소 생성 후 프로젝트 Wiki 쓰기 방식 점검 및 기존 설계·기록 이전
6. 첫 기능의 코드 제공 → 사용자 로컬 실행 결과 확인 → 설계·실험 기록 동기화

## 근거와 검증 범위

2026-11-19 사용자와의 현재 채팅에서 물류 도메인·학습 우선·코드 전달 방식·힌트 우선·Wiki 이중 기록 의사가 **직접 확정**되었다. 사용자 로컬 코드, GitHub 신규 저장소, Wiki 이중 기록, 데이터·성능 실측, 배포는 **아직 미검증**이다.
