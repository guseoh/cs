# 백엔드 시스템 설계·구현 연구실 — 통합 학습 프로젝트

## 현재 상태 (2026-11-19)

**확정된 목표:** 포트폴리오 완성이 아니라 **Backend Engineering(Java/Spring) + System Design + RAG**의 이해·설계·구현·검증 학습이다. 성과가 충분할 때만 일부를 포트폴리오로 발전시키는 것을 검토한다.

**확정한 구성:** **하나의 GitHub 저장소**에서 다음 **6개 독립 실행 Spring Boot 애플리케이션**을 각각 다른 문제·학습 목표로 운영한다. 같은 저장소에 『가상 면접 사례로 배우는 대규모 시스템 설계 기초』 **1·2권 설계 학습**도 별도 트랙으로 진행한다. 이 결정은 서비스 사이의 통신·MSA 또는 하나의 거대한 Spring Boot 애플리케이션 결합을 의미하지 않는다.

**아직 생성되지 않음:** 신규 GitHub 저장소 및 그 GitHub Wiki, Gradle 구성, 코드, 실험, CI, 배포. 저장소 이름 `backend-systems-lab`은 **최우선 추천 가칭**이며 사용자 확정 이름/URL이 아니다. `backend-ai-systems-lab` 등 다른 후보도 열려 있다. 각 세부 요구사항·기술 스택·순서도 추후 설계한다.

## 여섯 도메인별 목표

| 트랙 | 애플리케이션 | 독립적 학습 초점 | 주요 실험 후보 |
| --- | --- | --- | --- |
| 물류 | `logistics` | 출고센터 선택·재고 할당·정합성·도메인 모델 | 재고 경쟁, 락·트랜잭션, 중복/장애 이벤트 |
| 대중교통 | `transit-search` | 그래프·경로 탐색·공공 교통 데이터 처리 | 최단 경로, 검색 성능, 데이터 적재 |
| 부동산 | `real-estate` | 대량 공공 데이터 수집·정제·분석 쿼리 | 배치, 파티셔닝, 인덱스/집계 |
| 티켓팅 | `ticketing` | 고경합 좌석 예약·대기열·공정성 | 중복 예약, 락 선택, 동시 접속 부하 |
| 주차장 | `parking` | 공간 검색·예약 상태·캐싱 정합성 | 위치 검색, 만료, 예약 경쟁 |
| 이벤트 분석 | `event-analytics` | 대량 메시지·Kafka·집계·복구 | Consumer 중복/지연, 재처리, 이벤트 집계 |

*각 행의 문제와 실험은 해당 도메인을 학습하는 **권장 후보**이며 API/DB·아키텍처가 확정되었다는 의미는 아니다.*

## 현재 중심 학습 축과 RAG 범위 (2026-11-19 확정)

- **Backend Engineering:** 도메인 모델링, Spring Boot API, 영속성·트랜잭션·동시성, 이벤트·테스트·운영.
- **System Design:** 요구사항/규모 추정, 설계 대안과 트레이드오프, 데이터 흐름, 병목, 장애·복구 및 관측 가능성.
- **RAG Engineering:** 문서/데이터 수집·정제·청킹, 임베딩, 벡터/하이브리드 검색, 리랭킹, 근거 기반 답변·품질 평가, 보안·성능·비용의 실험을 **학습 후보**로 둔다.

RAG를 별도 Spring Boot 앱으로 만들지 또는 기존 도메인에 적용할지는 **미결**이다. 기존 여섯 독립 앱 구성은 그대로 보존한다. [학습 범위·우선순위 결정 BSL-0003](../decisions/BSL-0003.md).

## 교재 학습 트랙 (후순위·당장 착수하지 않음)

- **교재 1권:** 규모 추정, 처리율 제한, 해시/키-값·ID 생성, 알림·검색·크롤링 등 **기초 시스템 설계**.
- **교재 2권:** 근접성/지도·메시지 큐·집계·예약·모니터링 등 **분산 시스템 및 복잡한 서비스 설계**.
- **원칙:** 각 장을 모두 서비스로 구현하지 않는다. 요구사항→가정/규모 추정→개략 설계→상세 설계/비용·장애→선택적 작은 검증을 거친다.
- **문서/실험 연결:** 책에서 얻은 설계 원리를 도메인에 적용하고, 도메인에서 경험한 병목/정합성을 책의 설계안과 대조한다.
- [책 통합 결정 BSL-0002](../decisions/BSL-0002.md), [세부 대응 및 설계 가이드 초안 BSK-0001](../knowledge/BSK-0001.md).

## 확정된 결정

1. [BLR-0014](../decisions/BLR-0014.md): AI는 현재 채팅에서 완성 코드를 제공하며 사용자가 로컬에서 빠르게 작성·실행한다. 어려운 기술의 첫 학습은 힌트 우선이다. 사용자가 최종 의사결정한다.
2. [BSL-0001](../decisions/BSL-0001.md): 여섯 개 독립 실행 Spring Boot 애플리케이션을 하나의 저장소에서 각 도메인 모듈/하위 프로젝트로 관리한다.
3. [BSL-0002](../decisions/BSL-0002.md): 시스템 설계 교재 1·2권은 같은 저장소의 별도 설계 트랙으로 유지하지만 당장은 착수하지 않는다.
4. [BSL-0003](../decisions/BSL-0003.md): 학습 중심을 백엔드·시스템 설계·RAG로 확정하고 저장소 이름은 미확정 후보로 둔다.
5. [LGR-0001](../decisions/LGR-0001.md): 초기 주력 도메인은 물류이며 별도 [물류 진행 현황](logistics-learning.md)을 보존한다.

## 권장 구현 구조 (제안, 미구현)

```text
backend-systems-lab/              # 저장소 가칭
├── settings.gradle.kts           # 실제 생성한 하위 프로젝트만 포함
├── build.gradle.kts
├── gradle/
├── apps/
│   ├── logistics/                # 처음 학습할 앱 후보
│   ├── transit-search/
│   ├── real-estate/
│   ├── ticketing/
│   ├── parking/
│   └── event-analytics/
├── design-studies/
│   ├── volume-1/                 # 교재 1권 장별 설계
│   └── volume-2/                 # 교재 2권 장별 설계
├── experiments/                  # 필요한 장만 작은 코드 PoC
├── infra/                        # 필요할 때만 실행/테스트 환경
└── docs/                         # ADR, 실험 결과, 실행 안내
```

Gradle 멀티 프로젝트는 **추천 구현 방식**이며 하위 프로젝트들은 각자 독립 실행/테스트 경계를 가진다. 각 앱의 환경변수·포트·DB/스키마를 분리하고 다른 앱의 엔티티·서비스를 공유하지 않는다. 공통화는 빌드·테스트 도구와 중복이 충분히 검증된 유틸리티로 제한한다. 도메인 간 실시간 연동은 학습 과제로 실제 선택될 때 별도 결정한다.

각 모듈은 **학습 시작할 때 점진적으로 생성**한다. 초기부터 6개의 서버·DB·컨테이너를 동시에 띄우거나 같은 수준으로 완성하는 것을 필수 조건으로 두지 않는다.

## Wiki 운영 및 진행 기록

- **신규 저장소 생성 전:** 중앙 `guseoh/cs/Wiki`에 통합 프로젝트 결정·진척·교재 설계 방향을 기록한다. 실제 상세 GitHub Wiki 생성/업로드를 주장하지 않는다.
- **생성 후:** 신규 저장소의 GitHub Wiki나 버전 관리 문서에 6개 도메인별 설계/실험과 교재별 학습 설계를 각각 보존하고, 중앙 Wiki에는 공통 결정·진행 현황·검증 근거/링크를 유지한다.
- **이력:** [통합 진행 기록](../journal/backend-systems-lab/2026-11.md), 물류 세부 기록은 [기존 Journal](../journal/logistics-learning/2026-11.md)과 연결한다. 동일 내용을 중복 재작성하지 않는다.
- **검증 상태:** 구상/사용자 확정/코드 제시/로컬 작성/실행 확인/성능 검증/배포는 별도 기록한다.

## 미해결 질문과 다음 작업

1. GitHub 저장소의 실제 이름·공개 범위·Wiki 지원 여부 확인 및 생성(아직 사용자 요청 없음).
2. 초기 물류 앱의 첫 요구사항/기능 범위를 확정하고 도메인·정합성 모델을 설계.
3. 루트 Gradle 버전·Spring Boot·Java·테스트 기본 도구 및 모듈 간 의존성 경계를 결정.
4. RAG의 첫 학습 목표·데이터·실험 방식을 논의하되 독립 앱 생성 여부는 결정하지 않는다.
5. 교재 1·2권은 후순위로 두고 사용자가 재개할 때 장별 설계 실습을 시작한다.
6. 중요한 결정·실험·교훈을 실제 관측 후 Wiki에 기록.
7. 장별/도메인별 중복 학습은 기존 기록과 링크로 연결하고 필요할 때만 PoC 추가.

## 근거와 검증 한계

사용자는 여섯 **독립 Spring Boot 애플리케이션 + 동일 저장소의 교재 1·2권 설계 트랙 + 학습 목적**을 명시적으로 확인했다. 폴더명, 빌드 도구 세부 계약, 도메인 내부 구조, 교재별 실습 순서와 구현 범위는 **제안**이다. 실제 코드·테스트·성능 수치, 새로운 GitHub 저장소/Wiki 생성은 **미확인**이다.
