**판정:** 자식 있는 root를 다른 root 아래 옮겨3-depth가 되는 결함과 동시 검증/저장 경쟁을 확인했다.

**후속 댓글:** ## R1-02 병합 마감 근거 / 향후 재검토용 (2026-10-20)
- **Before (실증):** `A(root)→A1(child)`, `B(root)`에서 `A.parent=B` PATCH가 **200 성공**하여 3-depth `B→A→A1` 생성 가능 (Codex disposable MySQL 수정 전 회귀).
- **Root cause:** 기존 `requireParentCategory()`는 새 parent의 깊이·self/descendant만 확인했고 이동 target에 child가 있는지는 보지 않음. 동시 create/reparent 시 검증 시점과 저장 시점 경쟁 위험.
- **Selected fix:** parent lock-before-child FK insert, reparent 시 target+requested parent PK 오름차순 PESSIMISTIC_WRITE, lock 뒤 child 존재 검사. 실제 최상위 Audit owner와 서비스 create/update에서만 READ_COMMITTED, 기존 단일 transaction과 afterCommit cache를 보존. 타입/DDL/외부 API 변경 없음.
- **Alternatives / costs:** 테이블/전체 트리 잠금이나 DB schema rewrite는 확대 비용 때문에 제외. SELECT-after-wait 최신성을 위해 isolation 변경은 Category mutation 범위로 한정. 기존 불법 계층 데이터 정비는 이번 범위 밖.
- **After (검증):** 3-depth 시도는 HTTP `409 CATEGORY_DEPTH_EXCEEDED`, 잘못된 요청에 parent/name/audit/cache partial effect 없음. 동시 create↔move, chain/reciprocal move, 무관한 subtree 병행은 독립 MySQL … [전체 근거](https://github.com/guseoh/pawcycle-commerce/issues/416#issuecomment-6282225112). 댓글 작성 시점의 Draft/Open과 조회시 실제 병합 상태를 구분한다.
