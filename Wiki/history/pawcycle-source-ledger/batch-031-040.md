## #38 — AUTH-004 독립 QA: 조건부 통과와 로그 증거 경계

승인 입력은 AUTH-003만으로 분리하고 Backend 보고·인수인계·PR·자동 테스트는 구현/검증 증거로 구분했다. session ID와 CSRF 회전, logout, dummy BCrypt, principal, 동일 credential 오류, 기본 logout 금지에 기존 테스트가 충분해 중복 테스트를 추가하지 않았다. QA 문서 1개만 변경했다.

응답·URL의 민감정보 부재와 logger 인자로 credential을 직접 넘기지 않는 정적 근거는 있다. 그러나 임의 exception message의 일반적 redaction을 output-capture 테스트가 증명하지는 않는다. 안전한 500 응답과 원인 stack trace 기록은 자동 로그 마스킹과 다른 주장이다. 실제 인증 흐름에서 로그 유출 경로를 재현하지 못해 제품 결함을 발명하지 않았으며, 완전한 보안 통과로 단정하지도 않았다.

최종 판정은 **조건부 통과**다. 조건은 현재 head CI 성공과 배포·통합 QA에서 실제 인증 오류 로그의 민감정보 비노출을 재확인하는 것이다. 공개 작성자 답변과 최종 보고서에서 이 범위를 대조했다. 이번에 final-head CI success는 조회했지만 배포 로그 조건이 이후 해결됐는지는 미확인이다. **판정:** PWL-0015와 PWC-0007의 QA 한계를 갱신하고 #37 상품 통과와 구분한다.

## #39 — API-003: D1~D8 명시 승인과 제외 범위 정밀화

승인 계약은 POST 201/GET 200의 구독 API 3개, 최소 생성 ID·서버 날짜, 중첩 Product/SKU·ID DESC, principal 본인 조건과 미존재/타인/비숫자 ID의 동일 404를 정했다. 입력 오류는 단일 VALIDATION_FAILED와 fieldErrors, 도메인·endpoint 실패는 별도 안전 코드다. 동일 조건 복수 구독을 허용하고 멱등성 저장소는 도입하지 않았다. 새 migration의 최소 필드·FK·CHECK·(member_id,id) 인덱스와 하나의 Backend 수직 PR, FE 완료 후 독립 통합 QA를 승인했다. 대안과 대가는 기존 [PWC-0031](../../decisions/PWC-0031.md)에 보존한다.

리뷰 뒤 URL 자체에는 요청 ID가 포함된다는 점을 인정하고 status/body/timing과 application/access log·metric의 소유권 추론/마스킹 경계로 정밀화했다. UX-001의 승인 기준선 지위와 승인 전 구현 차단 문구를 맞췄고, 부분 수정 응답에서 미언급 항목을 자동 승인하지 않게 했다. 이후 사용자의 전체 명시 승인으로 후보 절차를 종료했다.

V1에 없는 감사 필드 convention을 따른다는 초안은 물리 계약이 아니므로 created_at/updated_at을 제외했다. 실제 감사 요구가 생기면 타입·nullability·default·갱신 책임을 별도로 결정해야 한다. 정확한 생성일+주기 계산은 도메인/테스트에, 날짜 순서 CHECK는 DB에 맡겼다. 측정 없는 추가 인덱스·가격 snapshot·동일 조건 unique·idempotency table은 미도입이다.

**판정:** 기존 PWC-0031 보강 및 API-001의 분리 validation code 후보/PWC-0037과 후속 선택 연결. 문서 4파일만 변경했으므로 실제 구독 구현 근거는 아니다. 번호상 다음 #40은 별도 SRE 작업이며 제품 구현 완료를 뜻하지 않는다.

## #40 — OPS-007: 알림 일원화와 신뢰·원본 상태 보존

두 CI 알림 경로와 main push 중복을 단일 workflow_run으로 모았다. 작업 맥락, 처리 과정, 검증/QA, 리뷰/미해결 thread, 현재 상태와 다음 행동을 정규화 context와 1~3개 embed에 담았다. Draft/Ready/새 커밋/reviewer 지정/승인·변경 요청/병합/Issue/CI conclusion별 행동과 Preview를 나누고, 단순 push·일반 review comment·미병합 close는 억제했다. fixture 20개·단위 테스트 36개 통과는 당시 보고다.

Secret과 함께 실행하는 script는 기본 브랜치의 신뢰 코드로 한정했다. collector 부재를 exit 0/notify false로 숨기는 호환안을 제거하고 명시적으로 실패시켰다. PR branch script로 얻은 수정 전 HTTP 204는 최종 안전 코드의 전송 근거로 기각했다. 수정 후 Preview·채널 수신은 병합 뒤 기본 브랜치에서 확인할 일로 남겼다. 이번 재구성에서는 dispatch나 전송을 실행하지 않았다.

리뷰 뒤 완료된 CI run SHA를 최신 PR SHA로 덮지 않고 원본 SHA와 이전 결과임을 보존했으며, API 실패에도 event의 PR 번호를 유지했다. QA/validation heading 중복 배정, 전체 6000자 한도, mention 억제, 10분 timeout과 GraphQL 전 페이지/반복 cursor 실패의 확인 불가 처리를 대조했다. Issue 본문은 전달하지 않고 task ID 추출에만 제한적으로 사용한다. PR fenced code 제거, JSON/YAML/env assignment·주요 token/AWS/PEM 패턴 마스킹, 최종 payload 검사와 전체 context 비전파 테스트를 보강했다. 이 정규식 검사가 모든 비밀·개인정보를 완전히 식별한다는 뜻은 아니다.

**판정:** [PWC-0043](../../decisions/PWC-0043.md) 신규, 초기 Discord 실패 PWL-0010과 연결. 32개 변경파일에는 fixture 중복 정리, 옛 workflow 삭제, collector/builder/limits/validator/test/runbook이 포함된다. final-head Repository Validation success는 확인했지만 당시 Collaboration report는 기본 브랜치 collector 부재로 실패하고 sender에 도달하지 않았다. 이를 모든 check 녹색이나 최종 채널 수신 완료로 합치지 않는다.
