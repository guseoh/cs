- 중요한 결정: `control-adopt`는 이전 `contract-sha`, clean Control HEAD, 현재 `current-sha`를 모두 명시 승인값과 대조하고 현재 서비스만 재검증한 뒤 `contract-sha`만 원자적으로 갱신한다.

- 외부 계약·데이터·보안·운영 영향: 고위험 저장소 준비이며 Container·Application SHA·MySQL volume·migration/RDS gate는 변경하지 않는다.

### 원본 진술: 검증

- 실패·미실행과 이유: 실제 Production/AWS/RDS/SSM 실행은 요청 범위에서 제외했다.

### 원본 진술: 위험과 복구

#### Phase 8 방향 보정 — 20 VU는 최종 목표가 아님

사용자 목표를 다시 확인해 Phase 8의 측정 방향을 보정한다.

PawCycle의 목표는 단순히 현재 저부하 성능을 기록하는 것이 아니라, **대규모 트래픽을 견딜 수 있도록 현재 한계를 측정하고 Phase 9 최적화와 Phase 10 수평 확장의 근거를 만드는 것**이다.

기존 `1/5/10/20 VU` 측정은 버리지 않는다. 이 결과는 k6 harness·관측성·기본 latency/throughput·Hikari/DB 반응을 검증한 **초기 Local 진단 기준선**으로 유지한다.

다만 `20 VU`를 최종 부하 상한으로 해석하지 않는다. 실제 재측정에서도 public API는 20 VU에서 약 `500 req/s` 수준까지 처리했으므로, 다음 측정은 raw VU 수가 아니라 **목표 RPS를 직접 주입하는 arrival-rate 모델**로 전환한다.

#### 개념 학습 메모 — TIME_WAIT 누적·ephemeral port 고갈·Persistent Connection

이번 Local 성능 측정에서 관측된 현상을 나중에 회고/기술 글로 정리할 때 아래 개념을 함께 학습 대상으로 남긴다.

##### 1. TIME_WAIT가 왜 존재하는가
- TCP 연결이 종료된 직후 바로 완전히 사라지지 않고 일정 시간 `TIME_WAIT` 상태로 남는다.
- 목적은 이전 연결의 지연 패킷이 새 연결에 섞이는 것을 막고, 연결 종료 과정에서 마지막 ACK 유실 등에 대응하기 위함이다.
- 따라서 `TIME_WAIT` 자체는 장애가 아니라 TCP의 정상적인 안전 장치다.

##### 2. 대량의 짧은 TCP 연결과 ephemeral port 고갈
- Nginx가 Backend로 HTTP 요청을 전달할 때, upstream TCP 연결을 충분히 재사용하지 않으면 짧은 연결이 대량 생성·종료될 수 있다.
- 종료된 연결이 `TIME_WAIT`로 누적되면 새 outbound TCP 연결에 사용할 ephemeral source port 공간이 빠르게 소모될 수 있다.
- 이번 환경의 `ip_local_port_range`는 `32768 ~ 60999`였고, 평상시 `TIME_WAIT=26` 수준에서 5 VU 부하 중 약 `28.3k`까지 증가했다.
- 같은 구간에서 Nginx 로그에 `connect() ... failed (99: Address not available)` 및 502가 반복되어, 새 upstream TCP 연결 생성 실패와 강한 상관관계가 확인됐다.

##### 3. HTTP Persistent Connection / Keep-Alive와의 관계
- HTTP 요청마다 TCP 연결을 새로 만들고 닫는 방식은 handshake 비용뿐 아니라 `TIME_WAIT` 누적과 port churn을 크게 만든다.
- Persistent Connection/Keep-Alive는 하나의 TCP 연결을 여러 HTTP 요청에 재사용해 연결 생성·종료 횟수를 줄이는 방식이다.
- 이 개념은 《HTTP 완벽 가이드》에서 설명하는 `TIME_WAIT`, 포트 고갈, persistent connection 문제와 직접 연결해서 학습할 수 있다.

##### 4. Reverse Proxy에서는 TCP 연결이 두 구간으로 나뉜다
```text
k6 ↔ Nginx ↔ Spring Boot
```
- `k6 ↔ Nginx` 연결과 `Nginx ↔ Spring Boot` 연결은 서로 다른 TCP 연결이다.
- 클라이언트와 Nginx 사이 keep-alive가 정상이어도, Nginx upstream 연결 재사용이 충분하지 않으면 `Nginx ↔ Backend` 구간에서 별도의 연결 고갈 문제가 생길 수 있다.

##### 5. 이번 실측과 연결
- 5 VU 재현: throughput `832.925 req/s`, expected-status error `44.68%`
- 정상 backend 처리량은 대략 460 req/s 수준으로 Grafana의 Spring HTTP 처리량 약 500 req/s 부근과 정합성이 있다.
- 실패 응답 상당수는 Spring Boot까지 도달하지 못하고 Nginx가 502로 반환한 것으로 해석된다.

##### 나중에 글로 정리할 때 포함할 학습 포인트
- TCP 4-tuple과 ephemeral port
- `TIME_WAIT`의 목적과 정상 동작
- 짧은 연결 대량 생성 시 port churn
- HTTP persistent connection / keep-alive
- reverse proxy 앞단/뒷단 연결의 분리
- Nginx upstream keepalive가 어떤 문제를 줄이는지
- 개선 전/후 `TIME_WAIT`, 502, 정상 RPS, p95/p99 비교

> 현재 단계에서는 원인 증거를 확정하는 것이 목적이며, 실제 Nginx upstream keepalive 적용은 Phase 9 측정 기반 최적화에서 별도 변경·재측정 대상으로 다룬다.

따라서 250 RPS 실패의 직접적인 종료 메커니즘은 **Backend container cgroup OOM → Java process kill → container restart**로 확정한다.

##### OOM 직전 JVM memory

| Metric | Value |
|---|---:|
| Heap used | 274.03 MiB |
| Heap committed | 282.20 MiB |
| Heap max | 402.19 MiB |
| Non-heap used | 151.87 MiB |
| Non-heap committed | 154.00 MiB |
| Buffer used | 0.01 MiB |
| Buffer capacity | 0.01 MiB |
| Backend container memory limit | 640 MiB |

Heap max에 도달한 Java heap OOM이 아니라 heap/non-heap/thread stack/JVM native memory 등을 합친 process RSS가 cgroup limit에 도달한 container-level OOM으로 판정한다.

##### RDS at failure window — `pawcycle-commerce-db` / db.t4g.micro

| Metric | 관측 범위 / 최대 |
|---|---|
| CPUUtilization | 약 3.62% ~ 11.69%, max 11.69% |
| DatabaseConnections | 10 지속 |
| FreeableMemory | 약 165.9 MB ~ 183.6 MB 범위, 급락 없음 |
| ReadLatency | 대부분 0, max 약 1.54 ms |
| ReadIOPS | 대부분 매우 낮음, max 약 1.35 ops/s |

현재 증거에서는 RDS CPU/latency/memory saturation이 없다. `DatabaseConnections=10`은 Hikari max=10과 일치하며 RDS의 최대 connection 한계를 의미하지 않는다.

##### Phase 8-C 최종 판정

```text
200 RPS: stable
250 RPS:
  Hikari active 10 / pending 189
  + JVM threads 217
  + process/native memory pressure
  → 640 MiB cgroup OOM
  → Java process kill / Backend restart
  → latency/error/drop cliff
```

RDS는 선행 saturation 증거가 없으므로 이번 first-failure의 직접 병목으로 판정하지 않는다. 다만 Hikari queueing이 왜 급증했는지에 대한 connection hold time/request concurrency/thread/native-memory 상호작용은 Phase 9 Before/After 분석 후보로 보존한다.
