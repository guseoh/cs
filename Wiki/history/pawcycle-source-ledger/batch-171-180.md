### 원본 진술: 배경

Phase 8-A/B에서 Local 진단 및 capacity envelope를 측정했고, Phase 8-C에서 외부 desktop → Production single Backend + RDS public read-only 경로를 측정했다.

Phase 8-C evidence:

- deployed known-good: 200 RPS
- first failed: 250 RPS
- saturation range: `200 < threshold <= 250`
- 250 RPS에서 Hikari active 10 / pending 189, JVM threads 217
- Backend 640 MiB memory cgroup OOM으로 Java process가 kill/restart됨
- RDS CPU/ReadLatency/FreeableMemory에는 선행 saturation 증거가 없음

상세 수치는 #166 measurement comment, Production troubleshooting chain은 #168, harness는 PR #169를 참조한다.

Phase 8-C의 `GET /api/products` 단일 read-only 결과만으로 실제 Commerce 대규모 트래픽 특성을 대표하지 않는다. 다음 단계에서는 Production을 더 밀지 않고 synthetic data를 사용하는 **격리 성능 환경**에서 현실적인 Commerce workload를 정의하고 재현 가능한 harness를 준비한다.

### 원본 진술: 1차 포함 범위 — workload model / repository preparation

### API workload inventory

최신 main의 실제 API 계약에서 다음 workload 후보를 inventory한다.

- Public catalog read
- authenticated member read
- Subscription read
- Commerce read
- bounded/safe Commerce write

정확한 endpoint/status/header/CSRF/session/idempotency/optimistic-lock 계약은 현재 코드와 API 문서에서 확인한다. 존재하지 않는 endpoint나 임의 업무 흐름을 만들지 않는다.

### Synthetic dataset

실제 Production row/ID를 사용하지 않는다.

필요한 synthetic fixture 예:

- members
- products / inventory
- pets
- subscription plans / versions
- subscriptions / schedules
- cart/wishlist/order 등 실제 workload에 필요한 Commerce 데이터

fixture 규모와 cardinality를 명시하고 실행 전후 재현 가능한 seed/reset 경계를 만든다. write workload 때문에 데이터가 누적되어 다음 측정이 왜곡되지 않도록 reset 또는 run-isolated data strategy를 정의한다.

### Workload families

비율은 이 Issue에서 임의 확정하지 않고 별도 승인한다.

1. **Mixed steady workload**
   - 실제 사용자 흐름에 가까운 read 중심 혼합 workload
2. **Burst workload**
   - 짧은 시간 트래픽 급증에서 latency/error/queueing 변화 확인
3. **Sustained workload**
   - 일정 처리량을 충분한 시간 유지해 memory/GC/thread/connection 누적과 안정성 확인
4. **Bounded write workload**
   - isolated synthetic data에서만 수행
   - idempotency/CAS/transaction/inventory 등 실제 Commerce write path를 깨뜨리지 않는 안전한 workload

### Authentication / state

- synthetic account/session만 사용
- 실제 인증 계약에 필요한 login/CSRF/session 흐름을 존중
- credential/cookie/session 값은 artifact에 저장하지 않음
- write 요청의 idempotency key/ETag/If-Match가 필요한 경우 계약을 그대로 따른다.

### Metrics

각 workload에서 최소 다음을 수치화한다.

- target / actual RPS
- operation별 RPS와 비율
- dropped iterations
- expected-status error rate
- p50 / p95 / p99 / max — 전체 + 주요 operation별
- Backend CPU / memory
- JVM heap / non-heap / GC / threads
- Hikari active / idle / pending / max
- DB query/connection/latency 관련 evidence
- container restart/OOM 여부
- workload generator saturation 여부
- sustained 실행에서는 시작/중간/종료 resource delta

### 원본 진술: Workload 비율 결정 원칙

- 단순히 `80:20` 같은 관습값을 복사하지 않는다.
- 현재 PawCycle 사용자 흐름과 API 호출 구조를 먼저 inventory한다.
- 실제 운영 traffic data가 없으므로 최초 비율은 **synthetic workload assumption**으로 명시한다.
- read-heavy / balanced / write-stress처럼 목적이 다른 profile이 필요하면 각각 별도 profile로 둔다.
- 한 profile의 수치를 다른 profile의 capacity로 일반화하지 않는다.

**실행별 증거 보존:** 아래 공개 원본 댓글의 수치는 당시 보고이며 이번 조사에서 새로 실행하거나 원시 측정값을 재계산하지 않았다. 과거와 correction 이후 표본·후속 마감 판단을 서로 대체하지 않는다.

##### 이번 Phase 8-D에서 제외할 write

첫 mixed/bounded-write harness에는 checkout/payment-confirm/billing-complete, cancellation/return, subscription state command를 넣지 않는 것을 제안한다. 이 경로들은 inventory/결제/상태전이/CAS/idempotency 위험이 커서 첫 synthetic workload의 범위를 불필요하게 넓힌다.

##### 1차 workload profile 제안 — 사용자 승인 필요

실제 traffic data가 없으므로 아래는 **synthetic assumption**으로만 사용한다.

**A. Mixed steady — read-heavy**
- 40% `GET /api/products`
- 25% `GET /api/products/{productId}`
- 10% Subscription read (`/api/v2/subscriptions` 또는 detail)
- 10% cart/wishlist read
- 10% orders read
- 5% member read (`/api/auth/me`, coupons, membership 중 fixture가 보장되는 경로)

인증 세션 생성/login은 측정 구간 밖의 setup 단계에서 수행하고, operation mix에 login 비용을 섞지 않는다.

**B. Burst**
- A와 동일 operation mix
- steady target에서 짧은 고점으로 상승 후 복귀
- mix는 고정하고 arrival pattern만 바꿔 burst 자체의 영향을 분리한다.

**C. Sustained**
- A와 동일 operation mix
- 충분한 지속 시간으로 heap/non-heap/GC/thread/Hikari/memory 누적과 container restart 여부를 확인한다.

**D. Bounded write — 별도 profile**
- synthetic cart + wishlist mutation만 1차 대상으로 제안
- add/update/delete가 run-isolated fixture 안에서 순환하도록 구성해 row가 무한 누적되지 않게 한다.
- checkout/payment/subscription command는 후속 별도 승인 없이는 포함하지 않는다.

##### Synthetic data / isolation 방향

기존 `local-integration`에는 전용 QA member + 공개 product/SKU + subscription reset bootstrap이 있고 V2 reconciliation이 활성화되어 있다. 다만 단일 fixture는 성능 측정 cardinality로는 부족하므로, 기존 Backend 제품 코드를 수정하지 않고 `infra/**`에서만 동작하는 **performance-only seed/reset**을 준비하는 방향이 적절하다.

필요 데이터는 최소:
- 여러 synthetic member/session
- public products/SKUs
- member별 cart/wishlist
- 일부 member의 subscription/pet
- order read가 profile에 포함되면 synthetic order fixture

Production host/DB에서는 실행 불가능하도록 환경 식별 + explicit acknowledgement + fail-close를 둔다. raw credential/session/ID는 aggregate 결과에 남기지 않는다.

##### 구현 전 승인 gate

다음 2가지만 사용자 승인 후 Codex 구현으로 넘긴다.
1. Mixed steady 비율: `40/25/10/10/10/5`
2. 1차 bounded write를 cart + wishlist mutation으로 한정하고 checkout/payment/subscription command는 제외

승인 후 branch는 `ops/sre/PERF-PH8-003`, 제품 Backend 코드는 변경하지 않고 `infra/**` + 필요 시 `docs/performance/**`/`docs/runbook/**`만 사용한다.
