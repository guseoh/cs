## #274 — Auth Architecture Decision — Session vs JWT vs Hybrid

**판정:** Session/JWT/Hybrid 비교는 미실행 보류·아카이브 관련 기록: [PWC-0007](../../decisions/PWC-0007.md)。 [원본](https://github.com/guseoh/pawcycle-commerce/issues/274)

현재Sessionfixation/CSRF/cookie/logout계약을배경으로JWT를보안patch가아닌아키텍처후보로비교하려던Issue다. tokenrotation/replay/revoke/key/storage와sharedSession운영대가까지비교하도록요구했다.

2026-11-03댓글에서전체비교/ADR결정은아직미실행이고구체Mobile/ExternalAPI/인증문제가확인되지않아not_planned아카이브했다. Session새ADR승인이나JWT영구배제결론이아니다. 재검토조건은외부client·다중instance/session비용·구체문제다.

**원본이 보고한 계약·검증·한계 추출:** 아래는 공개 Issue/PR의 당시 진술이다. 이번 Wiki 조사에서 제품/운영 검증을 재실행한 결과가 아니다. 승인·실행·병합 상태는 위 판정 및 manifest의 시각·SHA와 구분한다.

### 원본 진술: 배경

PawCycle Commerce는 현재 브라우저 중심의 Session 기반 인증을 사용한다.

현재 기반에는 다음이 이미 포함되어 있다.

- `HttpSession` 기반 `SecurityContext` 저장
- Session fixation 방어 (`changeSessionId`)
- Session 기반 CSRF token lifecycle
- `HttpOnly` / `Secure` / `SameSite=Lax` session cookie 정책
- 공통 401 / 403 JSON 응답
- `/api/admin/**` 관리자 경계와 `/api/**` 인증 경계
- logout 시 SecurityContext / CSRF / session cookie 정리

따라서 JWT는 기존 인증의 단순 보안 패치가 아니라 **인증 아키텍처 변경 후보**로 평가한다.

현재 진행 중인 `BACKEND-REFACTOR-001`에서는 이 결정을 섞지 않고, 리팩터링 완료 후 Clean Functional Baseline을 만들기 전 별도 Architecture Decision으로 진행한다.

### 원본 진술: 목적

다음 세 후보를 PawCycle의 실제 요구와 운영 모델을 기준으로 비교하고 최종적으로 `KEEP / DEFER / ADOPT`를 결정한다.

1. 현재 Session 인증 유지
2. JWT 기반 인증으로 전환
3. Browser는 Session을 유지하고 Mobile / External API / Service boundary가 필요할 때 JWT 또는 OAuth2 계열을 사용하는 Hybrid 모델

기술 자체의 선호가 아니라 **문제, 보안 특성, 운영 복잡성, 확장 요구, 장애·복구 특성**을 근거로 결정한다.

### 원본 진술: 범위

### 포함

- 현재 인증 코드와 Security 설정 재검토
- Session / JWT / Hybrid threat model 비교
- Access/Refresh Token lifecycle 설계안
- Browser token storage 선택지 비교
- revoke / rotation / replay / key lifecycle 설계
- Multi-instance 관점 비교
- 향후 Mobile / External API 요구와의 적합성
- Spring Security 표준 구현 방식 검토
- 도입 시 migration 범위와 rollback 경계 추정
- 최종 Architecture Decision 작성

### 제외

- 이 Issue에서 JWT 실제 구현
- Redis 도입
- Multi-instance 실제 전환
- OAuth Authorization Server 구축
- Social Login/OAuth2 Login 구현
- Production Secret / signing key 생성 또는 변경
- AWS/KMS 등 실제 Cloud resource 변경

실제 구현이 결정되면 별도의 고위험 저장소 작업으로 분리한다.

### 원본 진술: 완료 조건

- 현재 인증 코드의 실제 상태를 최신 `main`에서 다시 확인했다.
- 세 후보를 동일 기준으로 비교했다.
- JWT를 선택할 경우 Access/Refresh/Revoke/Rotation/Key lifecycle이 구체화됐다.
- Browser storage와 CSRF/XSS trade-off가 명시됐다.
- Multi-instance가 JWT 채택의 단일 근거가 아님을 검증했다.
- 실제 운영 복잡성과 장애/복구 비용을 비교했다.
- 최종 `KEEP / DEFER / ADOPT` 판정과 재검토 조건을 기록했다.
- 이 Issue에서는 Production/Cloud/Secret 변경이나 JWT 구현을 수행하지 않았다.

### 원본 진술: 2026-09-04 공식 문서 재검증 결과

### OCI Free Tier / Home Region

- Always Free 자원은 계정 수명 동안 무료 제공되는 별도 quota다.
- Always Free Compute는 Home Region에서 생성해야 한다.

### Compute

`VM.Standard.A1.Flex` Always Free allowance:

- 월 1,500 OCPU-hours
- 월 9,000 GB-hours memory
- Always Free tenancy 기준 약 `2 OCPU + 12 GB RAM`을 상시 사용할 수 있는 수준
- A1은 ARM64이므로 기존 PawCycle Docker image의 `linux/arm64` 호환성을 실제 배포 전 반드시 검증한다.
- 총 Always Free Block Volume: 200 GB (boot + block 합산)
- 기본 VM boot volume 약 50 GB를 우선 사용하고, 실측 필요 없이 storage를 크게 선점하지 않는다.

### MySQL HeatWave Always Free

공식 Always Free 제공 내용:

- Home Region에 standalone MySQL HeatWave DB System 1개
- shape: `MySQL.Free`
- data/log storage: 50 GB
- 추가 backup storage: 50 GB
- Always Free 생성은 standalone이며 HA 구성이 아니다.
- Always Free 자동 backup retention은 1일이며 configurable하지 않는다.
- Always Free manual backup 및 PITR에는 제한이 있으므로 PawCycle은 별도 logical backup + restore rehearsal을 후속 운영 계약으로 둔다.

현재 PawCycle은 MySQL/JPA/Flyway 계약을 유지하며 PostgreSQL 등 다른 DB 엔진으로 전환하지 않는다.

### HA / Failover / Replica 결정

MySQL HeatWave 일반 유료 서비스 자체는 HA / failover / replica를 지원한다. 그러나 **Always Free Production에서는 지원하지 않는다.**

현재 포트폴리오·비용 우선순위상 다음은 명시적으로 `DEFER`한다.

- Managed DB HA
- automatic failover
- read replica
- storage scaling 실험

이는 기술적으로 불가능하다는 의미가 아니라, Always Free 제약과 개인 프로젝트 비용 대비 가치를 근거로 현재 실제 검증 범위에서 제외한다는 의미다.
