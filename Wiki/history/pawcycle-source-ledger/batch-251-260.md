## #253 — chore(ops): MVP4 임시 main 자동 배포

**판정:** 임시 AWS 자동 dispatch 도입과 실제 배포 경계 관련 기록: [PWC-0089](../../decisions/PWC-0089.md), [PWC-0025](../../decisions/PWC-0025.md)。 [원본](https://github.com/guseoh/pawcycle-commerce/pull/253)

image workflow success+push+main+40자 SHA를 이중 검사하고 actions:write로 기존 Production Deploy를 dispatch한다. manual image publish는 자동 배포되지 않는다. 기존 immutable image/ancestry/GHCR/OIDC/SSM/concurrency/contract·Flyway 승인 경계를 유지한다.

이 PR 병합 자체도 첫 auto deploy를 유발할 수 있다는 고위험 영향과 사용자 별도 승인을 명시했다. dispatcher 성공은 실제 deploy 성공이 아니며 이 원본에는 실제 운영 실행 근거가 없다. 임시 workflow 제거로 기존 수동 경로에 복귀하며 운영 rollback/restore 실행은 별개다.

**원본이 보고한 계약·검증·한계 추출:** 아래는 공개 Issue/PR의 당시 진술이다. 이번 Wiki 조사에서 제품/운영 검증을 재실행한 결과가 아니다. 승인·실행·병합 상태는 위 판정 및 manifest의 시각·SHA와 구분한다.

### 원본 진술: 목적과 범위

목적: MVP4 기능·UI 수정 기간 동안 매 merge마다 `target_sha`를 복사해 `Production Deploy`를 수동 실행하는 반복을 제거하고, 성공한 main image release를 기존 검증된 Production Deploy 경로로 자동 연결한다.

변경 범위: `.github/workflows/mvp4-temporary-auto-production-deploy.yml`과 `docs/runbook/MVP4-CD-001-temporary-auto-production-deploy.md`만 추가·수정한다. 기존 `production-deploy.yml`, `publish-production-images.yml`, AWS/EC2/RDS/SSM/Secret, control-adopt, migration 승인, rollback/restore 실행은 변경하지 않는다.

```text
main push
→ Publish production images
→ image publish 성공
→ 기존 Production Deploy 자동 dispatch
→ 기존 SSM preflight/deploy
```

자동 dispatch 조건은 source workflow=`Publish production images`, conclusion=`success`, event=`push`, branch=`main`, `head_sha`=소문자 40자 SHA를 모두 만족해야 한다. `workflow_run` trigger 자체도 `branches: main`으로 제한하고 job 조건에서 다시 검증한다.

사람이 `Publish production images`를 `workflow_dispatch`로 실행한 경우에는 자동 Production deploy로 이어지지 않는다. 임시 workflow는 AWS/EC2에 직접 접근하지 않고 `GITHUB_TOKEN`의 `actions: write` 권한으로 기존 `production-deploy.yml`을 `ref=main`, `operation=deploy`, `target_sha=<successful image workflow head_sha>`로 dispatch한다.

기존 immutable image, main ancestry, GHCR image 존재, AWS OIDC, 단일 Production SSM target, SSM preflight/deploy, concurrency, rollback, Release contract/Flyway 승인 boundary는 그대로 유지한다. 자동 경로는 contract/migration 승인값을 임의 제공하지 않으므로 기존 preflight가 추가 승인을 요구하면 실패해야 한다.

### 원본 진술: 검증

실행한 검증: GitHub 공식 문서에서 `GITHUB_TOKEN`으로 발생한 `workflow_dispatch`가 새 workflow run을 생성하는 허용 예외임과 GitHub-hosted runner에 `gh` CLI가 제공됨을 확인했다. branch diff에서 기존 Production deploy/image publish workflow는 수정하지 않고 임시 workflow + Runbook만 추가했음을 확인했다. `workflow_run`은 main branch filter와 job-level `success + push + main` 이중 조건으로 제한했다.

실패·미실행과 이유: 이전 Repository Validation 실패들은 workflow 실행 실패가 아니라 PR artifact 형식 오류였다. 첫 실패는 `실행 구분` 값 형식, 이후 실패는 PR 본문의 validator 전용 라벨 누락이었다. 실제 Production 배포는 이 PR의 저장소 준비 단계에서 실행하지 않았으며, 최신 HEAD의 전체 Repository Validation을 다시 실행해 Green 여부를 확인한다.

### 원본 진술: 위험과 복구

남은 위험: 이 PR이 `main`에 병합되면 임시 Auto-CD가 활성화된다. 이 PR 자체의 merge도 main push이므로 merge SHA의 `Publish production images`가 성공하면 해당 SHA가 첫 자동 Production 배포 대상이 될 수 있다. 또한 `production` environment에 별도 reviewer gate가 설정돼 있다면 자동 dispatch 후 승인 대기 상태가 될 수 있으므로 최초 실제 chain에서 확인해야 한다.
