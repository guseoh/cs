### 원본 진술: 배경

현재 PawCycle의 Demo Catalog는 Product 탐색·필터·추천·Cart·Checkout·Subscription 흐름을 검증하기에는 데이터 밀도와 다양성이 부족하다.

또한 QA / Performance / Operations fixture가 persistent local DB에 남아 고객 화면에 섞이는 문제가 실제 Browser QA에서 확인되었다. 따라서 실제 서비스처럼 보이는 Customer Demo Catalog와 내부 검증 fixture의 경계를 명확히 해야 한다.

### 원본 진술: 목적

기존 Catalog schema와 runtime authority를 유지하면서, PawCycle의 사용자 흐름을 실제 서비스에 가깝게 검증할 수 있는 현실적인 Demo Catalog V1을 구축한다.

이 작업은 새로운 Product Detail schema나 Review/Rating/Q&A domain을 추가하는 작업이 아니다. 현재 승인된 Category / Product / SKU / Inventory / Subscription Plan 계약 안에서 데이터 품질과 다양성을 높이는 것이 목적이다.

### 원본 진술: 데이터 원칙

1. Runtime authority는 계속 MySQL이다.
2. 초기 Demo 판매 데이터는 기존 versioned manifest → validation/import/bootstrap → DB 흐름을 사용한다.
3. Java `List.of(...)` 또는 Flyway에 판매 Catalog row를 직접 하드코딩하지 않는다.
4. bootstrap은 멱등적이어야 한다.
5. 기존 mutable Inventory를 재시작 시 초기화하지 않는다.
6. QA / Performance / Operations fixture를 Customer Demo Catalog로 재사용하지 않는다.
7. `qa-*`, `v2-*`, `ops-*` 같은 문자열 prefix를 Frontend에서 숨기는 방식으로 문제를 해결하지 않는다.
8. 고객 공개 여부는 Category/Product/SKU의 승인된 상태 계약으로 결정한다.
9. 현재 schema에 없는 원재료·급여법·주의사항·리뷰·평점 같은 필드를 invent하지 않는다.

### 후속 Catalog ingestion 방향

현재 `demo-catalog.json`은 UI/UX 및 기능 검증을 위한 소규모 Demo fixture로 유지한다. 상품 수가 수백~수천 개로 증가할 때 이 파일을 사람이 계속 확장하는 방식을 장기 운영 모델로 사용하지 않는다.

실제 서비스에 가까운 Catalog 운영은 다음 경로를 단계적으로 검토한다.

- MD/Admin이 PawCycle Admin에서 Product/SKU를 직접 등록·수정
- 공급사가 제공하는 CSV/Excel 데이터를 검증 후 일괄 import
- 공급사가 정식 API/feed를 제공하는 경우 Catalog API 연동
- import 전 schema/business rule validation 및 dry-run
- 명시적 apply와 실행 결과/postflight 검증
- 중복 business key fail-close 및 기존 mutable Inventory 보존

개념적인 장기 흐름:

`MD/Admin 또는 공급사 원본 → CSV/Excel/API → PawCycle Catalog Import → validation/dry-run → 명시적 반영 → Product/SKU/Inventory`

외부 공급사 데이터는 무료 공개 데이터가 존재한다고 전제하지 않는다. 실제 공급사 계약, 이용약관, 라이선스, 이미지 사용권과 제공 형식을 확인한 뒤 채택한다. 공개 쇼핑몰/타사 상품 페이지 scraping을 기본 ingestion 전략으로 사용하지 않는다.

Production용 Demo/검증 데이터가 필요할 경우에도 startup 자동 bootstrap이나 수동 SQL 대량 입력보다 명시적 one-shot import 경로를 우선 검토한다. 이 후속 경로는 Production 데이터 변경이므로 별도 고위험 승인과 적용 전후 검증을 요구한다.

자동 merge하지 않는다. Production 실행은 별도 사용자 승인 후 수행한다.
