## #202 — [PERF-PH10] 기술 도입 및 Scale Scenario 검증

## #204 — [PERF-PH10] Subscription Burst Before 측정 준비

**판정:** 5k실행소비·상세artifact접근불가 관련 기록: [PWC-0012](../../decisions/PWC-0012.md), [PWC-0078](../../decisions/PWC-0078.md)。 [원본](https://github.com/guseoh/pawcycle-commerce/issues/204)

기본100/60초scheduler와sleep없는rawREQUIRES_NEW순차drain을분리해측정하도록요구했다. 5k는실사용자규모가아닌격리합성cohort이며공유volume/Production에쓰지않는다.

실first-result1회·runtime정상·summary생성은보고됐지만PC변경후temp상세수치에접근할수없다. orders/s·percentile·resource를추정하지않고재실행도금지했다. 현재증거만으로Kafka/async채택을정당화하지않는다.

**원본이 보고한 계약·검증·한계 추출:** 아래는 공개 Issue/PR의 당시 진술이다. 이번 Wiki 조사에서 제품/운영 검증을 재실행한 결과가 아니다. 승인·실행·병합 상태는 위 판정 및 manifest의 시각·SHA와 구분한다.

### 원본 진술: 배경

PERF-PH10-001 Read Scale에서 Redis After first-result가 동일 CPU2.0 local envelope의 250 RPS target을 dropped 0으로 처리했고, relevant SQL과 DB connection 사용이 크게 줄어 Redis 유지가 결정됐다.

다음 Scale Scenario는 특정 시각에 많은 Subscription이 동시에 due가 되는 **Subscription Burst**다. Kafka/Queue/async를 먼저 구현하지 않고 현재 구조의 처리 특성과 한계를 Before evidence로 확보한다.

현재 최신 main 구조:

- `SubscriptionOrderAutomationTrigger`
  - `pawcycle.subscription.automation.batch-size` 기본값 100
  - `fixed-delay-ms` 기본값 60000ms
- `SubscriptionOrderAutomationService.processDueSchedules(batchSize)`
  - stable due candidate 조회 + `LIMIT batchSize`
  - candidate를 순차 처리
  - candidate마다 `TransactionTemplate` + `PROPAGATION_REQUIRES_NEW`
  - target 실패는 격리하고 다음 candidate 계속 처리
- 기존 Micrometer metric
  - executions
  - processed candidates
  - orders created
  - failures
  - duplicate/no-op
  - duration

### 원본 진술: 목적

현재 단일 scheduler / 순차 REQUIRES_NEW 주문 생성 구조에서 burst backlog가 발생했을 때 다음을 **한 번의 통제된 local first-result**로 측정할 수 있는 저장소 harness를 준비한다.

1. 주문 생성 처리량
2. batch/tick 처리시간
3. 전체 backlog drain 특성
4. CPU / memory / GC / thread
5. Hikari active/pending/acquire/usage
6. MySQL connection / statement / lock-wait pressure
7. processed / created / failure / duplicate-noop과 실제 DB 결과 일치
8. target failure isolation 및 재선택 가능성
9. 현재 default batch-size/fixed-delay가 backlog completion에 주는 구조적 영향

### 원본 진술: 측정 원칙

### 1. Production scheduler 계약과 raw processing capacity를 구분한다

실제 60초 fixed-delay를 장시간 기다리는 방식으로 큰 cohort를 소진하지 않는다.

저장소 harness는 다음을 분리해 기록한다.

- **Raw drain evidence**: local-only driver가 `processDueSchedules(100)`을 반복 호출해 인위적 sleep 없이 현재 service/DB의 순차 처리 capacity를 측정
- **Default scheduler projection**: 관측된 batch duration과 현재 `fixed-delay-ms=60000`, `batch-size=100` 계약을 사용해 default scheduler에서 동일 backlog를 소진하는 데 필요한 tick 수와 최소/예상 completion 시간을 계산

projection은 실제 Production 측정값으로 표현하지 않고 구조적 계산값으로 표시한다.

### 2. Synthetic data는 기존 local data와 격리한다

대량 write workload이므로 기존 shared local MySQL 데이터나 `mysql-data`를 오염시키지 않는다.

Codex는 최신 compose/validator 구조를 분석해 가장 작은 안전한 방식을 선택하되 다음을 보장한다.

- Production/RDS 사용 금지
- 기존 local named volume의 기존 데이터 파괴 금지
- test fixture가 명확히 식별되고 실행 후 cleanup 가능
- destructive cleanup 범위가 해당 synthetic fixture 또는 전용 disposable measurement DB/project에 한정
- `docker compose --remove-orphans` 금지

전용 Docker Compose project/database/volume을 사용하는 것이 더 안전하면 그 방식을 우선 검토한다.

### 3. Cohort는 configurable하게 준비한다

특정 숫자를 실제 사용자 규모로 주장하지 않는다.

Harness는 future-scale synthetic cohort를 설정 가능하게 준비한다. 최소한 다음 규모를 표현할 수 있어야 한다.

- 100
- 500
- 1,000
- 2,500
- 5,000
- 10,000

이번 저장소 작업에서는 실제 performance first-result를 실행하지 않는다. 실제 first-result cohort와 중단 조건은 repository review 후 별도로 승인한다.

### 4. 실제 업무 correctness를 보존한다

Synthetic subscription은 기존 주문 자동화가 요구하는 최소 유효 상태를 가져야 한다.

- ACTIVE / MVP2-managed

### 2. Durable redacted evidence

현재 `%TEMP%` summary는 실행 중 intermediate artifact로 사용할 수 있으나 유일한 보존 위치가 되어서는 안 된다.


실행 도중 자동 commit/push는 금지한다.

### B. Prometheus snapshot consistency

허용 예:

- end snapshot의 automation executions/processed/created/duration이 동일한 authoritative scrape/evaluation boundary를 사용함

- freshness check 유지
