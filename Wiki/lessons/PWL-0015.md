# QA 판정은 assertion이 실제 증명한 범위까지만 남겨야 한다

## Product QA: empty와 array는 다른 주장
#37은 빈 목록의 isEmpty만으로 null/다른 빈 JSON 값 회귀를 막지 못한다는 리뷰 후 isArray+length0를 추가했다. 없는 상품의 SKU query는 특정 인수 never보다 전체 verifyNoInteractions로 강화했다. 실제 query 수는 MySQL 통합 통계에서 목록2·빈목록1·상세2로 보호했고 내부 호출 전체를 더 고정하는 verifyNoMoreInteractions는 불필요하다고 남겼다. 제품 코드 변경 없이 검증 공백만 보완했다.

## Auth QA: 안전 응답·로그 존재·redaction은 다른 주장
#34의 예외 handler는 안전한 500 응답을 유지하면서 서버에 stack trace를 기록하도록 바뀌었다. #38 QA는 응답에 credential/session 정보가 없고 제품 코드가 이를 logger 인자로 직접 넘기지 않는 정적 근거를 확인했다. 그러나 임의 exception message의 민감정보를 자동 제거한다는 테스트는 없었다.

재현된 실제 인증 로그 유출 경로가 없어 제품 결함을 발명하지 않았고, 반대로 완전한 로그 안전 보장을 주장하지도 않았다. 최종 판정은 **조건부 통과**: 현재 head CI 성공과 배포·통합 QA의 실제 인증 오류 로그 비노출 재확인이다. 이미 충분한 session lifecycle 테스트를 복제하지 않고 보고서만 변경했다.

## Limits / retrieval
이번 조사는 원본 QA 판정과 자동 증거의 범위를 복원했다. Production 로그 재확인·cookie/HTTPS 전달·브라우저 E2E를 새로 실행하지 않았다. 현재 위험 해소 여부는 후속 원본으로 확인해야 한다. [#37/#38 상세](../history/pawcycle-source-ledger/batch-031-040.md).
