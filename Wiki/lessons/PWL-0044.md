# UTC DATETIME은 Timestamp 변환과 JDBC Calendar 경계까지 비교해야 한다

## Context

UTC instant 에서 만든 Timestamp 라도 DATETIME 바인딩 경로가 JVM 기본 시간대를 해석하면 Seoul 에서 9시간 이동할 수 있다. SQL CURRENT_TIMESTAMP fixture 와 실제 JPA 생성 경로도 같은 저장값을 보장하지 않는다.

## Observed lesson

#362는 cleanup cutoff/repair 에 UTC LocalDateTime 을 직접 전달해 binding 의미만 고쳤고 SQL/정렬/limit/<cutoff 를 유지했다. coupon 은 제품 Checkout 로직을 바꾸지 않고 Clock+실제 CouponEntity/JPA 생성으로 fixture 를 맞췄다. 이후 native 전환에서도 JDBC4.2 LocalDateTime/LocalDate·Calendar 미사용 Timestamp custom binder/extractor 로 frozen JDBC 의 값을 보존했다.

## Alternatives and interpretation

전역 timezone 변경, 기간 기대값 완화, 기존 DB 값 일괄 변환, 모든 시간 타입을 한 방식으로 통일하는 안을 제외했다.

## Consequences and limits

시작 포함/종료 제외·±1µs·nullable·batch/rollback 과 UTC/Seoul JVM 을 분리 검증한다. descriptor 재사용은 할당 비용 교정이지 시간 의미 변경이 아니다. 과거 운영에서 이미 이동·삭제된 row 의 존재/복구는 미확인이다.

## Implementation and verification

main 에도 있던 coupon1/cleanup2 실패를 T10 회귀와 분리했다. #362 실제 MySQL 비교·최신 CI, #370 이후 frozen parity 를 연결한다. source 에 기록된 원시 local artifact 와 현재 운영 데이터는 새로 분석하지 않았다.
