# JFR 파일이 생겼어도 기록 완료·유효 샘플이 없으면 hotspot을 특정할 수 없다

## Claim and applicability
JFR file 존재, 파일 크기, 복사 성공, `jfr summary` 성공은 충분하지 않다. JVM recording 완료 상태·duration·필수 event coverage·정상 부하 aggregate를 모두 검증해야 특정 Java code hotspot을 귀속할 수 있다.

## Observed failure
[PERF-PH9-014](https://github.com/guseoh/pawcycle-commerce/blob/main/docs/performance/PERF-PH9-014-phase9-conclusion.md)은 `GET /api/products` CPU2.0 실험에서 약 193.49 RPS, dropped 5,808, p95 6,855ms, Hikari pending peak 116, SQL mean 0.68ms를 보고한다. Hikari 10→20은 처리량을 악화시켰다. CPU와 queueing의 영향은 관측됐지만 JPA materialization/Jackson/GC의 개별 책임까지 확인한 것은 아니었다.

PH9-011 JFR을 300초 recording으로 시작했으나 wrapper가 단지 container file `test -s`만 확인했다. JFR은 아직 종료되지 않아도 non-empty일 수 있다. 결과는 **Duration 0s, ExecutionSample 0**이며 정상 aggregate와 diagnostic-summary도 없었다. 일부 k6 출력은 정상 완료 결과가 아니다.

## Decision, trade-off and limitations
Phase 9은 검증되지 않은 loop 결합, DTO/projection, custom serialization 변경을 구현하지 않고 **NO CHANGE**로 마감했다. 병목 존재와 특정 코드 hotspot 식별을 분리한 판단이다. 후속 실험은 completion-aware JFR dump/stop, duration/event coverage 검증 및 실패 증거 보존이 먼저 필요하며 과거 PH9-011 one-shot 결과를 임의 재실행하지 않는다.

이전 수치는 당시 실험 조건에만 해당하며 현재 OCI Production baseline이 아니다. 후속 Redis [PWC-0009](../decisions/PWC-0009.md) 결정을 당시 JFR 실패의 원인 판정으로 소급하지 않는다. 이번 Wiki 조사에서 JFR/k6를 재실행하지 않았다.
