# "커밋 뒤에 별도 트랜잭션으로" 옮기는 것만으로는 부족했다 — 틀린 정답 코드와 그 리뷰

## Context

4단계 H에서 결제 확정 중 멤버십 INSERT gap lock 교착으로 결제 확정 전체가 롤백되는 결함을 찾았다([PWC-0142](../decisions/PWC-0142.md)). 사용자는 "결제 확정 트랜잭션에서 멤버십 평가를 분리"(A안)를 골랐고, 당시 분담대로 AI가 정답 코드를 채팅으로 보여 주고 사용자가 구현할 예정이었다. 사용자가 그 코드를 외부 AI 리뷰에 돌렸고, AI(Claude)가 리뷰 지적을 코드와 대조해 다시 검토했다. **정답이라고 준 코드에 결함 두 개가 있었다.** 이 기록은 그 코드와 리뷰를 학습용으로 남긴다. 이 코드는 저장소에 반영되지 않았다.

## 틀린 정답 코드(요지)

```java
@Component
public class MembershipReevaluation {
  public MembershipReevaluation(MembershipEvaluationService evaluation,
                                PlatformTransactionManager tm, MeterRegistry registry) {
    this.ownTransaction = new TransactionTemplate(tm);
    this.ownTransaction.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    ...
  }

  public void afterCommit(long memberId) {
    if (!TransactionSynchronizationManager.isSynchronizationActive()) { evaluateNow(memberId); return; }
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
      @Override public void afterCommit() { evaluateNow(memberId); }
    });
  }

  void evaluateNow(long memberId) {
    for (int attempt = 1; ; attempt++) {
      try {
        ownTransaction.executeWithoutResult(status -> evaluation.evaluate(memberId));
        return;
      } catch (PessimisticLockingFailureException lockFailure) {
        if (attempt == 2) { record(memberId, lockFailure); return; }
      } catch (RuntimeException failure) {
        record(memberId, failure); return;
      }
    }
  }
}
```

결제 확정·대사·정기결제·환불의 `membershipEvaluation.evaluate(memberId)`를 `membershipReevaluation.afterCommit(memberId)`로 바꾸는 안이었다. 결제가 멤버십 때문에 롤백되는 문제는 실제로 막는다.

## 리뷰 지적과 판정

| 지적 | 판정 | 내용 |
| --- | --- | --- |
| `REQUIRES_NEW`가 커넥션을 하나 더 씀 | **맞음, 리뷰보다 심각** | Spring은 커밋 뒤 `afterCommit` → `afterCompletion`을 부른 **다음에** 원래 커넥션을 반납한다. 콜백 안의 새 트랜잭션은 두 번째 커넥션을 잡는다. Hikari 기본 최대 10개에서 결제 확정이 동시에 10건 이상 이 지점에 오면, 모두 하나씩 쥔 채 두 번째를 기다려 획득 시간 초과(기본 30초)까지 멈춘다. 같은 날 10만 측정 전 1만 단계적 증가에서 **커넥션 풀(10개)이 가장 먼저 고갈되는 자원**임을 실측했다(120 iteration/s에서 활성 10·대기 126) |
| 실패 후 복구가 보장되지 않음 | **맞음, 이 수정이 새로 만든 틈** | 수정 전에는 멤버십이 결제와 같은 트랜잭션이라 함께 성공·실패했다. 이 코드는 커밋과 콜백 사이에 서버가 죽으면 재평가가 사라지고, 실패도 로그·지표만 남아 다시 처리할 목록이 없다 |
| 365일 기준이 지나도 재평가가 없음 | 맞지만 수정 전부터의 정책 공백 | 정기 재평가 작업이 없다. 등급을 언제 내릴지는 제품 정책이다 |
| 오래된 금액으로 등급을 덮어씀 | 경합은 맞음, 수정 전부터의 결함(P1 정도) | `evaluate()`가 금액을 일반 조회(REPEATABLE READ 스냅샷)로 먼저 읽고 나중에 `FOR UPDATE`로 잠근다. 같은 회원 재평가가 겹치면 낮은 금액으로 덮을 수 있고, 등급이 오르내리면 혜택 쿠폰이 두 번 나갈 수 있다 |
| `isSynchronizationActive()`가 애매함 | 이름만 애매. 대안은 받지 않음 | 리뷰가 제안한 `IllegalStateException`은 결제 확정 트랜잭션 안에서 던져져 결제사 승인 뒤 확정이 롤백되는 원래 결함을 다시 만든다 |
| `for (;;)` 가독성 | 맞음 | 최대 시도 횟수를 상수로 드러내는 편이 낫다 |
| 즉시 재시도 대신 대기 | 받지 않음 | 교착에서 진 쪽이 바로 재시도해도 이긴 쪽 gap lock 때문에 INSERT가 기다릴 뿐 교착이 다시 나지 않는다 |
| 인터페이스 불필요, `final` 필드, `RedactedFailure` 로깅 | 맞음 | 그대로 둘 부분 |

## Lesson

- **트랜잭션을 "나중에 별도로" 실행하는 코드는 커넥션 수명과 유실 경계를 함께 봐야 한다.** `afterCommit`은 비동기가 아니고 원래 커넥션도 아직 쥐고 있다. 그리고 커밋과 메모리 속 콜백 사이는 원자적이지 않다.
- **결제와 원자적으로 남겨야 하는 것은 "작업 결과"가 아니라 "해야 할 일"이다.** 결제 트랜잭션 안에 재평가 요청을 한 줄 기록하고, 별도 작업자가 처리하는 방식(DB 기반 Outbox)이면 유실·이중 커넥션·동시 평가가 함께 풀린다([PWC-0142](../decisions/PWC-0142.md)).
- **정답 코드라고 내놓은 코드도 리뷰 대상이다.** 외부 리뷰의 지적은 그대로 받지도 버리지도 않고, 코드·Spring 동작·실측과 대조해 하나씩 판정한다. 이번에도 맞는 지적, 과장된 지적, 받으면 안 되는 대안이 섞여 있었다.
- 이 일을 계기로 분담을 다시 정했다. AI가 구현하고 사용자는 완성 코드를 검토하며 학습한다([PWC-0141](../decisions/PWC-0141.md)).

## Limitations

`afterCommit` 중 원래 커넥션이 아직 반납되지 않는다는 점은 Spring `AbstractPlatformTransactionManager`의 커밋 처리 순서(after-commit 콜백 → after-completion 콜백 → 정리·반납)에 근거했다. 이 코드로 커넥션 고갈을 직접 재현하지는 않았다.
