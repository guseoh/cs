# MySQL CHECK가 거부했어도 Spring 예외 타입을 잘못 단정하면 테스트가 실패한다

## Failure and narrowing
#33의 초기 Security 테스트는 JSON Content-Type의 charset suffix를 exact match해 실패했고 compatible 비교로 고쳤다. 뒤이은 DB negative-path 테스트는 중복 email과 음수 가격을 같은 경계에서 검사하다 실패했다. transaction 격리·롤백, 두 테스트 분리 후에도 음수 가격 assertion이 실패해 transaction만으로 원인을 설명할 수 없었다.

최종 보고와 코드에 따르면 CHECK 위반은 실제 발생했지만 기대한 구체 DataIntegrityViolationException과 Spring 분류가 달랐다. MySQL CHECK 무효화 또는 DB가 음수값을 받아들였다고 단정하지 않는다. 공개 review의 여러 추정은 진단 가설이며 확정 원인이 아니다.

## Correction and proof
UNIQUE/CHECK를 독립 rollback 테스트로 분리하고 Product를 saveAndFlush했다. CHECK의 ENFORCED metadata와 실제 위반의 root SQLException을 함께 검증했다. 최종 assertion은 constraint명·SQLState HY000·vendor code3819를 확인해 목적이 다른 generic 실패로 통과하지 않도록 했다.

과거 실패 run→집중 수정→성공을 보고서에 보존했고 최종 head의 Repository Validation 성공 metadata를 이번 조사에서 확인했다. 실제 테스트·DB를 이번 세션에서 재실행한 것은 아니다.

## Applicability and limits
DB 무결성 보장은 실제 제약 위반 원인에 연결해야 한다. framework exception taxonomy를 하나로 단정하거나 assertion을 넓히기만 하면 다른 오류가 테스트를 통과시킬 수 있다. 이 사례의 SQLState/code를 모든 DB/driver의 보편값으로 쓰지 않는다. [배치 #33](../history/pawcycle-source-ledger/batch-031-040.md)을 따른다.
