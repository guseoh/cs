# Provider confirm과 DB 완료가 분리되면 PROCESSING 고립 상태가 남을 수 있다

## Claim and applicability
DB transaction 밖에서 Provider I/O를 수행하면 connection hold를 줄일 수 있지만 외부 승인과 내부 결제·주문·재고 완료가 단일 원자적 commit이 되는 것은 아니다.

## Observed failure
[Issue #414](https://github.com/guseoh/pawcycle-commerce/issues/414)와 [PR #415](https://github.com/guseoh/pawcycle-commerce/pull/415)의 일회성 MySQL/Fake Provider 고장 주입에서 PROCESSING commit 후 Provider 진입 전 중단과 Provider 승인이 성공한 다음 DB 완료 실패가 각각 재현됐다. 두 경우 주문은 PAYMENT_PENDING, 예약은 보존되고 정상 confirm replay/UNKNOWN 전용 대사로 안전한 완료를 자동 보장하지 못했다. Provider 호출 횟수와 잔여 효과는 격리 시험에서만 확인했으며 실제 Toss 고장은 아니다.

## Root cause and limits
상태를 저장하는 TX1, 외부 Provider 호출, 후속 효과를 저장하는 TX2 사이에는 프로세스 중단과 응답 모호성 구간이 있다. Payments·Inventory movement의 UNIQUE 제약은 중복 행 방어막이지만 Cart/Coupon/Delivery/Notification 전체 효과나 이미 진행 중인 외부 승인 요청의 취소까지 보장하지 않는다.

## Decision / reusable lesson
[Issue #417](https://github.com/guseoh/pawcycle-commerce/issues/417)의 정책은 조회만 수행→Provider identity 검증→명시적인 operator/worker fence→별도 승인된 안전한 DB 최종화다. [PR #450](https://github.com/guseoh/pawcycle-commerce/pull/450)은 오류 분류·query-only만 해결했다. 조회 실패를 결제 실패로 치환하거나 상태를 강제로 복구하면 안 된다. Phase 2는 여전히 Open이며 이번 Wiki 기록이 복구 실험을 새로 수행한 것은 아니다.
