# 공유 Hikari active 수치 대신 해당 요청의 연결 반환과 트랜잭션 정리를 검증한다

## Context

Discovery 호출이 끝나도 다른 thread 의 정상 차입 때문에 pool 전체 active 가 0이 아닐 수 있다. 동일 HEAD 에서 실패 후 rerun 성공은 요청 누수 부재나 scheduler 원인을 입증하지 않는다.

## Observed lesson

#366은 strict 최초값 실패를 유지한 관찰과 scheduler collaborator 격리를 시도했지만 A 도 성공해 실제 borrower 를 특정하지 못했다. #367은 요청별 Hibernate acquire/release 짝·Spring Tx/synchronization/ThreadLocal cleanup, 실제 disabled service 안에서 잡은 JDBC logical lease 의 열림→반환 후 isClosed 를 검증한다. 별도 정상 borrower 와 release 누락 부정 테스트를 둔다.

## Alternatives and interpretation

전역 0 assertion 을 timeout/자동 retry 로 숨기거나 제품 scheduler·pool 을 바꾸지 않았다. 원래 불필요해진 collaborator mock3개도 제거했다.

## Consequences and limits

Hikari logical handle 의 isClosed 는 풀 반환이며 물리 DB socket 종료가 아니다. 과거 실패의 실제 borrower·모든 경로의 물리 누수 부재·장기 CI 안정성은 미확정이다.

## Implementation and verification

#366 commit 제목 규칙 실패와 미병합을 보존하고 #367 test-only4파일/최종 MySQL·필수 lock5PASS·최신 HEAD 교정 review 를 연결한다. 최초 SQLException compile 실패와 별도 전체 CodeRabbit rerun 부재를 구분한다.
