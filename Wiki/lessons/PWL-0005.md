# Hikari pending은 pool 증설이 정답이라는 증거가 아니다

## Claim and applicability
Hikari active가 max에 도달하거나 pending이 높다는 사실은 요청이 connection을 기다린다는 관측이지 풀 크기가 **근본 병목**이라는 인과 증명이 아니다. CPU·application work·connection hold와 같은 조건의 단일 변수를 구분해야 한다.

## Observed Phase 9 experiment
250 target RPS의 당시 local 상품 목록 부하에서 CPU1.5/Hikari10 control은 actual 약 154.20 RPS, dropped 10,497, p95 약 7,996ms, pending peak 117이었다. Hikari max 10→20 변경은 active peak 20까지 사용했지만 **142.09 RPS, dropped 11,950, p95 약 8,027ms**로 악화돼 REJECT·원복했다([Issue #191](https://github.com/guseoh/pawcycle-commerce/issues/191), [#193](https://github.com/guseoh/pawcycle-commerce/issues/193)). CPU1.5→2.0만 올리고 Hikari10을 유지한 후보는 **193.49 RPS, dropped 5,808**로 개선했지만 pending peak 약 116이 남아 CPU가 부분 원인일 뿐이라고 판단했다([#195](https://github.com/guseoh/pawcycle-commerce/issues/195)).

## Decision, trade-off and limits
Connection 부족을 pool 숫자로만 완화하려고 하면 다른 처리 경로의 포화·경합을 악화시킬 수 있다. 해당 실험의 Hikari20은 기각했지만 다른 workload까지 영구 기각한 것은 아니다. JFR의 Duration 0s/ExecutionSample 0으로 Java hotspot을 특정하지 못한 사실은 [PWL-0002](PWL-0002.md)에 별도 기록돼 있다. Redis 목록 캐시의 효과는 [PWC-0009](../decisions/PWC-0009.md)의 **별도 반복 read 우회 실험**에서 평가했으며 'SQL이 느리기 때문'이라고 소급하지 않는다.
