# Network G1 의존성을 refactor에 먼저 이식하고 G2 변경을 보존한다

## 배경

Network & HTTP 53개 도식은 PR #298을 통해 `main`에 반영되었으나, 당시 `refactor`에는 필수 렌더러·스키마·Import 검증 계약이 없었다. G2는 `viz/network-g2` 브랜치에 127개 Concept 평가 보고서와 TCP 시퀀스 번호 SVG·Markdown 수정 등 3개 파일을 이미 보존하고 있었다. 이 상태에서 G2를 독립적으로 재구현하면 중복과 공유 진입점 충돌이 발생한다.

## 확정 결정

1. G2 브랜치를 변경하지 않고 보존한다.
2. PR #298 전체의 `main` 이력을 합치는 대신 53개 Network DIAGRAM을 실행하는 필수 의존성만 별도 PR로 `refactor`에 이식한다.
3. 실제 Frontend/Backend/Reader QA가 통과한 뒤에만 G1을 병합하고, G2는 통합된 `refactor` 기준으로 별도 재개한다.

## 검토한 대안과 제외 사유

- **G2에서 53개 도식을 다시 구현:** 이미 QA된 G1 코드를 중복 생성하고 기존 계약과 충돌할 위험이 있어 제외했다.
- **`main` 전체 병합:** Java/Heap/일반 Network 콘텐츠 수정 등 G1 목적 밖 변경이 섞여 `refactor` 작업 범위를 침범하므로 제외했다.
- **검증 없이 G1 코드만 이식:** canonical Import 멱등성과 Reader 실제 표시를 보장하지 못하므로 제외했다.

## 구현과 검증

[PR #303](https://github.com/guseoh/csforge/pull/303)에 필수 Network 모델·렌더러·53개 도식 선언·Reader 연결·Zod/Java allowlist·격리 Import 테스트를 선별 이식했다. 첫 [CI](https://github.com/guseoh/csforge/actions/runs/43703677032)에서 Backend 테스트 16개가 실패했다. 원인은 G1 `main` 원문을 그대로 이식하며 도식과 무관한 `cookie-scope.md` 및 `connection-teardown.md`의 공유 Reference 메타데이터까지 바뀐 것이었다. 일부 테스트에서 기록한 3,409개는 Source 총량이 아니라 재수입 시 `UNCHANGED` 결과였고, 전체 원본 3,410개는 유지됐다.

두 파일의 기존 `refactor` Reference frontmatter를 복원하면서 도식 선언을 유지한 HEAD `cf93a68d`에서 [CI #43706478668](https://github.com/guseoh/csforge/actions/runs/43706478668)이 성공했다. Frontend 1,001개 테스트, Backend 전체 테스트, Chromium Reader Guest 212조건 및 Owner 4조건을 통과했으며 [squash commit `8f01a8ba`](https://github.com/guseoh/csforge/commit/8f01a8ba820f0a3f33a234e93b400f8101f1c3a7)가 `refactor` HEAD가 된 것을 GitHub에서 확인했다.

## 결과와 제약

- 서로 다른 브랜치의 canonical Markdown을 복사할 때는 **도식 코드뿐 아니라 공용 Reference 메타데이터의 의도치 않은 변경**을 피해야 한다. 공유 URL을 가진 다른 Concept까지 `UPDATED`로 분류될 수 있다.
- Source 총량과 `UNCHANGED` 카운트는 별개 지표이다. 재수입 실패를 단순히 수량 기대값을 낮춰 해결해서는 안 된다.
- G2 원본 3개 파일은 계속 보존 상태이며, 실제 G2 개선·통합 후 rebase는 이 결정의 완료 범위가 아니다.
- `refactor`에 병합한 사실은 `main` 운영 배포, Production DB parity, 개인 실제 이력 검증을 증명하지 않는다.
