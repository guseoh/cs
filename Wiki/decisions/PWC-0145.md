# PawCycle을 실제 시스템 교재로 활용하고 설계 토론 중심의 세 병렬 트랙을 운영한다

## 배경과 문제

PawCycle은 Java/Spring 기반 Commerce·Subscription 시스템이며, 이미 구현된 제품 기능, 결제·재고·구독 정합성, 배포·관측·장애 대응, 합성 데이터·혼합 부하 측정 자산이 있다. 그러나 AI가 문제 분석부터 설계 선택·구현·검증까지 대부분 수행한 결과, 프로젝트의 기술적 성과와 사용자가 실제로 이해하고 판단할 수 있는 역량 사이에 차이가 생겼다. 사용자는 결제·멤버십 Gap Lock 문제를 해결한 기록이 있어도 자신이 해당 설계나 동작 원리를 충분히 이해하지 못한 상태임을 지적했다. 완성 코드 해설을 사후 제공하는 것만으로는 이 차이를 해소하기 어렵다.

[PWC-0141](PWC-0141.md)은 AI 구현과 사용자 코드 검토를 선택했었다. 이 역할 분담의 유용한 부분은 유지하지만 중요한 설계 선택을 구현 전 사용자와 토론하도록 강화한다. 기존 V10의 시스템 해체 분석 목표를 살리되 학습을 기초 문법의 일괄 이수나 로드맵 완수로 바꾸지 않는다. 새로운 기술을 많이 도입하는 것이 목표가 아니라 실제 프로젝트를 이해하고, 필요한 기술과 대안을 설명하고, 요구사항에 맞는 설계를 판단할 수 있는 역량을 확보하는 것이 목적이다.

## 사용자 확정 결정

- PawCycle의 기존 구현과 실제 문제 해결 경험을 교재로 삼아 Java/Spring, CS, 데이터베이스, 소프트웨어 설계, 인프라, 운영을 학습한다. 전체 아키텍처·주요 설계·포트폴리오 주제까지 포함하며 지나치게 기초부터 반복하지 않는다.
- 학습 자료는 중앙 Wiki의 결정·교훈·기록, 프로젝트의 최신 코드와 Commit·PR·Issue, ADR·테스트·실행 보고서, 접근 가능한 과거 채팅 메모리로 구성한다. 역사적 근거와 현재 구현을 구분한다.
- 학습, AWS 배포, 프로젝트 고도화·리팩터링을 선형 로드맵이 아니라 세 개의 병렬 트랙으로 진행한다. 학습을 모두 마칠 때까지 개발을 멈추거나 AWS를 구축해야만 코드 분석을 시작하는 구조를 만들지 않는다.
- AI의 구현 지원은 유지한다. 다만 중요한 기술 도입·설계·구조 변경·보안·운영 결정에서 AI가 선택을 확정한 다음 구현하지 않는다. 사용자에게 필요한 개념과 현재 상태, 대안, 트레이드오프를 충분히 설명하고 토론한 후 사용자 판단에 따라 구현한다.
- [PWC-0143](PWC-0143.md)의 AWS + RDS MySQL 시간제 운영, 월 AWS 비용 최대 15,000원, 최소 지출, OCI 활성 경로 정리, 저가 독립 도메인 구매 검토는 유지한다. 실제 자원·비용·데이터·운영 실행의 별도 승인도 유지한다.

## 세 병렬 트랙 — 구체적 운영안

아래 항목은 확정된 세 트랙의 적용 범위를 구체화한 지도이다. 세부 실행 순서·작업 우선순위·기술 도입은 각각 검토하며 이 표 자체를 일괄 구현 승인으로 해석하지 않는다.

| 트랙 | 목표 | 주요 내용 |
| --- | --- | --- |
| A — 인프라·운영 구축 및 학습 | AWS에서 실제 시스템을 설계하고 안전하게 운영하는 경험 | OCI 자원/백업/비용 확인 및 코드 정리, IAM·MFA·VPC·CIDR·Subnet·Routing·SG, EC2·Linux·EBS·SSM, private RDS·TLS·DB 권한·백업, Docker/GHCR/Nginx, 도메인·DNS·HTTPS, CI/CD·관측·운영 비용·장애·복구 |
| B — 프로젝트 해체 분석 및 핵심 기술 학습 | 실제 시스템의 구조와 설계 선택을 독립적으로 설명하는 역량 | 전체 아키텍처·요구사항·도메인·ERD·상태 전이, 패키지/객체 책임/의존관계, Java·JVM·Spring·Security·JPA/Hibernate·Querydsl·SQL, MySQL·CS, 기존 기술 선택과 포트폴리오 사례 |
| C — 프로젝트 고도화·리팩터링·기술 실험 | 실제 문제를 개선하고 결과를 검증하는 경험 | 기존 PR 마감, 코드 가독성·중복·과잉 추상화, 필요한 기능·UX 개선, 트랜잭션·동시성·결제 정합성, 합성 데이터·부하·SQL/JVM/Connection Pool 분석, 장애·복구 실험, 근거 기반 구조 확장 |

세 트랙은 서로 학습과 검증에 필요한 입력을 제공한다. 운영 구축 중 DNS나 TLS가 등장하면 그 시점에 원리를 학습하고, 코드 분석 중 위험을 발견하면 C의 후보로 전환한다. C의 부하 실험 중 DB 잠금 문제가 나오면 B에서 관련 원리를 보충한다. 하루에 세 트랙을 모두 실행해야 하는 것은 아니다. 개별 작업의 선행조건과 비용·운영 안전 Gate는 유지하며 상시 병행을 무조건 동시 실행으로 해석하지 않는다.

## 학습 방법과 깊이 — 적용 가이드

### 자료 조회와 출처 구분

1. 중앙 Wiki 색인·프로젝트 현황에서 관련 Decision/Lesson/Knowledge/Journal을 찾고 원본 PR·Issue·Commit·ADR로 이동한다. 전수 이력 복원은 원본 대장을 활용하며 새 질문마다 모든 PR을 다시 읽지 않는다.
2. 현재 동작은 작업 시점 최신 main의 실제 코드·migration·설정·테스트·승인 계약에서 확인한다. 과거 설계와 변경 후 동작은 당시 SHA 및 diff와 현재 구현을 대조한다.
3. 과거 채팅 메모리는 당시 논의와 사용자 확정 결정의 맥락을 보완하는 데 사용한다. 접근 가능 범위 내에서만 조회하고 비공개 대화 원문이나 개인정보를 공개 Wiki에 옮기지 않는다. 과거 제안·추측을 구현·운영 성공으로 승격하지 않는다.
4. 기술 원리·API·버전은 공식 문서로 검증하고 필요하면 국내 IT 기업 기술 블로그, 한국어/해외 기술 자료와 도식을 활용한다. 일반 자료가 프로젝트의 실제 증거를 대신하지 않도록 한다.

### 전체 시스템에서 필요한 개념으로 내려가기

추천 출발점은 전체 시스템 지도(클라이언트, Nginx, Next.js, Spring Boot, MySQL, 관측, 배포), 주요 요구사항·도메인·데이터 모델·경계이다. 이후 기능별 수직 흐름(HTTP 요청 → Security/Controller → Application/Domain → Persistence → SQL/DB → 응답·실패)과 기술별 수평 분석을 선택한다. 필요할 때 기초 개념을 보충하며, 전체 Java 문법이나 CS 전공 범위를 이수할 때까지 실제 분석을 미루지 않는다.

- 이미 이해한 내용: 현재 프로젝트 적용 방식과 주의점만 확인한다.
- 익숙하지 않은 기초: 객체·참조·인터페이스·다형성·DI·HTTP·SQL처럼 해당 주제를 이해하는 전제를 작은 예제로 설명한다.
- 실무 핵심: Java 예외·Collection·Generic·Record·시간·Thread/JVM, Spring IoC/DI/Bean/AOP/MVC/Transaction/Security, JPA 영속성/Flush/SQL/연관관계, DB 제약·Index·MVCC·Lock·Isolation, OS Process/Memory/I/O, TCP/HTTP/TLS/Connection 등의 작동 원리와 흔한 실패를 설명한다.
- 주요 설계·포트폴리오 사례: 요구·제약 → 변경 전 코드·데이터·실행 경계 → 재현 근거 → 내부 원리 → 대안/트레이드오프 → 현재 해결책 → 보호 테스트·한계 → 필요한 재현 또는 독립 재설계로 연결한다.
- 세부 내부 구현, 의무 퀴즈·암기, 모든 코드를 재작성하는 실습, 모든 개념을 장문으로 기록하는 작업은 목표에 필요할 때만 검토한다. 설명이나 실험의 완료를 사용자 이해 완료로 간주하지 않는다.

구조화된 설명, 간단한 코드와 실제 코드, 비교표, 실행 흐름 도식을 상황에 맞게 활용한다. 사용자가 이해되지 않는 부분을 질문하면 그 전제만 충분히 풀어 설명한다. 학습 주제 목록은 선택 가능한 지도이지 선형 과제 목록이 아니다.

### 대표 사례 적용: 결제·멤버십 교착

과거 결제 트랜잭션 안에서 멤버십 등급 평가를 실행했고, 첫 구매 회원의 `member_memberships` INSERT 관련 Gap Lock 교착으로 결제사 승인 이후 내부 결제 확정 전체가 롤백되는 문제가 예열 부하에서 관찰됐다. #558은 V29 요청 테이블을 추가해 결제·대사·정기결제·환불과 요청 기록을 같은 트랜잭션에 저장하고 별도 스케줄러가 재평가·삭제를 독립 트랜잭션으로 수행하도록 변경했다. Version 비교는 평가 중 재요청을 보존하고 Backoff는 평가 실패의 재시도를 지원한다. #564는 고립 결제 성공 복구에서 요청 기록 이후 감사 저장 단계에 실패를 주입해 롤백을 검증했다. 두 PR은 기준 SHA에 병합되어 있으나 수정 후 1만 규모 예열 재검증과 운영 적용은 별개로 미검증이다.

학습에서는 먼저 제품에서 멤버십이 왜 파생 상태인지, 결제사 승인과 로컬 DB 트랜잭션이 왜 하나의 원자적 단위가 아닌지, Spring 전파와 InnoDB 인덱스 잠금이 어떻게 연결되는지 설명한다. 이후 단순 재시도, 별도 트랜잭션, 커밋 후 콜백, DB 요청 테이블, 메시지 큐를 비교한다. 콜백의 커넥션 이중 점유·요청 유실 문제는 PWL-0057과 당시 원본을 조회하고, 현재 방식의 즉시 반영 지연, 요청 upsert의 트랜잭션 의존, 다중 인스턴스 점유 미검증, `postpone` 예외 시 배치 후속 처리 중단 가능성을 함께 검토한다. 기존 구현을 무조건 정답으로 취급하지 않으며 재현 없이 새로운 개선 효과를 주장하지 않는다.

## AI와 사용자의 협업 계약

중요한 설계·기술 선택·고위험 변경에서 AI는 다음 흐름을 사용한다.

1. 요구사항과 현재 문제: 실제 사용자 목적, 제약, 현재 코드·데이터·운영 경계와 관측 근거를 제시한다. 사실·가설·미검증을 구분한다.
2. 필요한 기술 설명: 사용자가 선택을 이해하는 데 필요한 Java/Spring/CS/DB/인프라 개념을 충분히 설명한다. 기존 설계가 그렇게 만들어진 이유는 원본에서 확인하고 추정이면 표시한다.
3. 대안과 토론: 현상 유지/보류와 최소 해결책을 포함한 실질적 대안을 비교한다. 정확성·정합성·보안·성능·비용·운영 복잡성·복구·유지보수성·실패 모드를 다루고 AI의 권장안과 근거도 명확하게 제시한다.
4. 사용자 판단: 사용자의 의문이나 대안을 근거에 따라 검토한다. 이미 결정한 내용을 매번 형식적으로 재승인받지 않되 새로운 중요 선택을 AI가 확정하지 않는다. 토론·방향 검토는 코드 변경·클라우드 실행의 승인이 아니다.
5. 승인 후 구현: AI가 승인된 범위 안에서 구현·검증을 지원한다. 구현 에이전트 전달 시 최신 main·관련 계약을 대조한 상세 분석 → Delta 추출 → 경량화 → Final Lightweight Delta Prompt를 적용하고 현재 AGENTS/Lean Harness/Skill·CI·독립 검토를 따른다.
6. 공동 검증·학습: 변경 전후 호출·SQL·데이터 상태, 핵심 파일·읽는 순서·테스트가 보장하는 것과 보장하지 않는 것, 실패/복구 경계, 실제 결과·대가·잔여 위험을 설명한다. 필요할 경우 동일 조건으로 재검증하고 KEEP/DEFER/REJECT를 판단한다.

작은 문서 수정, 오탈자, 명백하고 승인된 기계적 정리까지 매번 장시간 설계 토론으로 확대하지 않는다. 중요도가 높거나 새 정책·외부 계약·데이터·보안·비용·아키텍처 결정이 있는 경우에 충분히 토론한다. 사용자는 결정과 이해의 주체이며 AI는 대안·구현·검증의 조력자다. AI의 설명·구현·CI 성공을 사용자 역량이나 실제 운영 성공으로 대체하지 않는다.

## 선택하지 않은 대안과 트레이드오프

- AI가 계속 설계를 먼저 확정하고 완성 코드만 설명: 구현 속도는 빠르지만 사용자의 기술 판단·설계 이해가 축적되지 않을 수 있다.
- AI 정답 코드를 전부 받아 쓰거나 기존 시스템 전체를 재구축: 직접 작성 경험은 얻을 수 있지만 학습 목적에 비해 반복 비용이 크고 AI 정답의 결함도 전파할 수 있다. 필요한 작은 코드·독립 재설계·실험은 선택적으로 유지한다.
- 모든 Java/Spring/CS 이론을 기초부터 선형 이수한 뒤 실제 프로젝트에 접근: 누락 없이 공부할 수 있으나 실무 문제와 연결이 늦고 과도한 범위·완벽주의를 유발한다. 필요한 기초를 보충하는 방식을 선택한다.
- 학습이 끝날 때까지 배포·고도화·리팩터링 중단: 실제 학습 소재와 피드백이 사라진다. 반대로 개발만 계속하고 학습을 나중으로 미루는 방식도 채택하지 않는다.
- 기술 수, 이슈 완료율, 대규모 데이터 수, 문서량을 목표로 설정: 사용자의 이해나 실제 병목을 보장하지 않는다. Redis/Kafka/멀티 인스턴스/검색 엔진/신규 AI 기능은 필요성과 실측 근거에 따라 평가한다.

설계 토론은 일부 작업의 즉시 구현 속도를 낮출 수 있지만 이해 가능한 선택, 불필요한 변경 회피, 검증 기준 합의에 도움이 된다. 모든 설계와 모든 CS 세부 내용을 동일 깊이로 다루지 않아 지속 가능한 범위를 유지한다.
