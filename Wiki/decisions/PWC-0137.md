# 성능 작업은 AI가 측정하고 사용자가 해석·개선한다

## Context

고도화 1~3단계와 4단계 G-1은 AI(Claude) 구현 비중이 컸다. 사용자는 이 프로젝트를 포트폴리오로 쓰고, 로드맵이 끝난 뒤 Wiki를 다시 읽으며 학습할 계획이다. 성능 개선 경험은 "무엇이 병목이었고 어떻게 알았으며 다른 선택지는 무엇이었나"를 직접 설명할 수 있어야 의미가 있다.

## Decision

2026-11-19 사용자가 다음 분담을 확정했다.

| 단계 | AI | 사용자 |
| --- | --- | --- |
| 측정 실행 | 환경 구성, 실행, 원자료 정리(p95, Hikari, slow query digest, GC 등) | 측정 조건·시나리오 확인 |
| 해석 | 지표 의미 설명(요청할 때만) | 병목 판단, 가설 작성 |
| 개선 | 개선 코드는 쓰지 않는다. PR 리뷰어로 위험·누락 지적 | 구현, 테스트, 재측정 비교 |
| 기록 | 측정·환경 부분 Wiki 작성, 형식 검토 | 보고서·Wiki의 판단 근거 |

도움은 사용자가 요청한 단계까지만 준다: 1단계 힌트(어디를 보라) → 2단계 방향(가능한 방법들) → 3단계 코드 예시. AI가 먼저 병목 결론을 말하지 않는다.

## Rejected alternatives

- AI가 측정과 개선을 모두 구현: 진행은 빠르지만 판단 경험이 사용자에게 남지 않는다.
- 개선만 사용자가 구현하고 병목 판단은 AI: 가장 중요한 판단(어디가 병목인가)이 AI 몫으로 남는다.

## Consequences and constraints

- 측정 도구·환경(G-2 k6 script 등)은 계속 AI가 구현한다.
- H(10만·100만) 이후 AI는 원자료를 정리하지만 "병목은 X"라고 결론 내리지 않는다.
- 이미 AI가 구현한 1~3단계·G-1은 사용자가 설계 이유를 설명할 수 있도록 Wiki에 설계·과정·코드·트레이드오프를 상세히 남긴다.
- 포트폴리오에는 "측정·관측 환경은 AI 도움으로 구축, 병목 분석과 개선은 직접"처럼 분담을 밝힌다.

## Implementation/verification

작업 방식 결정이다. 첫 적용 대상은 4단계 H 이후 측정 결과의 해석과 5단계 개선이다.
