# 초기 공개 상품 조회는 read model과 두 번의 일괄 조회로 N+1을 막았다

## Context / selected implementation
2026-07-12 #36은 승인된 API-002의 목록/상세를 구현했다. Entity 직접 반환 대신 목록·상세 전용 read model을 read-only transaction 안에서 조립했다. 비어 있지 않은 목록은 Product 한 번 + productIds의 SKU batch 한 번, 상세는 공개 Product 한 번 + 정렬 SKU 한 번이다. 빈 목록은 Product 한 번 후 반환하고 없는/비공개 상세는 SKU 조회를 하지 않는다.

이 기록은 병합된 당시 구현 선택의 근거이며 별도 새 사용자 정책 승인이나 현재 query 구현이 동일하다는 주장이 아니다.

## Public boundary and correction
초기 schema의 case-insensitive collation에서 정확한 PUBLIC만 허용하도록 MySQL native BINARY 비교를 사용했다. 소문자·혼합 case·공백·다른 값과 없는 상품을 비공개/동일 404로 검증했다. Product ID 및 SKU display_order/id의 결정적 정렬, 구독 가능 SKU만 2/4/8주·그 외 빈 배열, SKU 없는 공개 상품 유지·명시적 null·가격 number를 API 계약과 연결했다.

## Alternatives / costs
상품별 SKU 조회 반복은 N+1을 만들므로 batch로 묶었다. fetch join·DTO projection 등 다른 구체 조회 방식의 별도 비교/기각 승인은 이번 원본에서 확인되지 않아 만들어 넣지 않는다. 전체 공개 목록이 pagination 없이 메모리에 올라오며 batch IN의 규모 한계와 MySQL 전용 조건의 이식 비용이 있다. 현재 성능 병목을 측정한 실험은 아니다.

## Verification and follow-up
#36의 단위/MockMvc/MySQL 통합 테스트와 #37 독립 QA가 statement 수와 응답 계약을 대조했다. #37은 빈 목록의 배열 타입+길이0/statement1, 없는 상품의 SKU 전체 미호출, 비숫자 ID의 안전 404를 보강했다. 실제 remote Java25/MySQL8.4 validation 이력은 [배치](../history/pawcycle-source-ledger/batch-031-040.md)에 연결한다. 이 조사에서 DB 부하·Production·브라우저 E2E를 실행하지 않았다.

후속 Redis read-scale [PWC-0009](PWC-0009.md)는 별도 시점의 측정/결정이다. 초기 query count 검증을 운영 처리량 보장으로 바꾸지 않는다.
