# OCI A1 capacity 조회·전이 알림·감시 건강·VM 생성을 분리한다

## Context

Tokyo A1 용량을 수동으로 확인하는 비용과 예약 조회 자체가 지연·누락되는 문제를 줄여야 했지만, capacity AVAILABLE 은 실제 VM 생성 성공을 보장하지 않았다.

## Decision

CapacityReport 를 조회하고 AVAILABLE 전이만 알리며 연속 상태는 중복을 억제한다. 최초 GitHub Issue 할당/멘션에서 Discord 알림+미할당 추적 Issue 로 변경했다. 당시 매시:17UTC 조회와 별도로 2시간:43UTC health,3시간 성공 공백/최근 실패 경고, 매일 00:47UTC(09:47KST) 상태 요약을 둔다. monitor enabled gate 를 사용하고 VM launch/reservation/resize/delete 는 포함하지 않는다.

## Alternatives and interpretation

용량 신호를 자동 생성 승인으로 해석하는 안, workflow health 를 capacity availability 로 간주하는 안을 제외했다. 같은 Actions 의 watchdog 을 독립 플랫폼 감시라고 하지 않는다.

## Consequences and limits

Discord 전송 뒤 Issue 저장 실패의 중복 가능성, GitHub schedule 지연·누락·플랫폼 공통 장애가 남는다. offline test/CI·실제 CapacityReport·실제 수신 화면·AVAILABLE 전이·장기 연속성은 서로 다른 증거다. 시간표는 당시 계약이다.

## Implementation and verification

#379→#380은 4파일 중 3blob 동일/문서 1차이, #383→#384는 2동일/테스트·문서 2차이다. 둘 모두 원본 unmerged 와 후속 merged 를 나눈다. #385 제한된 임시 trigger 와 #384 실제 명령 뒤 run38860330741 SUCCESS, 원본 #386은 OUT_OF_HOST_CAPACITY/Webhook204를 보고했고 trigger 를 삭제했다. 실제 AVAILABLE 이벤트는 없었다. #399 조회시 Open/reopened health 경고는 복구/최신 capacity 를 뜻하지 않는다. 최신 #501이후 도구 변경은 독립 상세 조사 전이다.
