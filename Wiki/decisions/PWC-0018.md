# AWS 알림 전달은 검증했지만 자동 스케줄·중복 억제는 보류한다

## Context
2026-08 AWS Production Incident Drill 이후 Backend/API/metrics-proxy/Prometheus를 조합한 read-only 진단을 준비했다. [OPS-AUTO-011 #151](https://github.com/guseoh/pawcycle-commerce/issues/151)은 승인 SHA의 진단·dispatcher로 실제 Discord와 Slack 수신, NORMAL 무알림, Production을 변경하지 않는 비정상 fixture 양 채널 수신을 검증했다. 이는 **알림 전달 수단의 검증**이지 상시 자동 감지의 검증이 아니다.

## Decision
[2026-08-15 후속 판단](https://github.com/guseoh/pawcycle-commerce/issues/151#issuecomment-5302163920)은 **scheduled execution과 dedupe 모두 DEFER**다. 당시 상태 진단은 Production과 Observability 두 호스트를 결합했다. 단순 cron 추가 전에 실행 사용자, 호스트 간 orchestration, root-owned 진단 결과/0400 Webhook Secret의 권한 경계를 정해야 했고, 실제 알림 storm·반복 중복 발송 부담도 확인되지 않았다.

## Rejected alternatives
- cron/systemd timer부터 활성화: 두 호스트 간 신뢰·경계·Secret 주입을 설계하지 못한다.
- 중복 알림 억제 선행 구현: 실제 연속 발송이 운영 요구로 확인되지 않았다.
- 자동 복구/auto-healing 도입: 알림 검증의 범위를 넘어 DB/Release 안전 Gate를 건너뛴다.

## Consequences and constraints
당시 직접 실행한 alert 전송은 Production Verified로 기록됐지만 자동 알림 운영체계나 현재 OCI의 알림 활성화까지 입증하지 않는다. 사람이 반복해서 진단해야 하거나 수동 확인 지연, SLO, 예정 실행 이후 중복 메시지가 실제 발생하면 필요성을 다시 평가한다.

## Implementation/verification
[Issue #151 결과 댓글](https://github.com/guseoh/pawcycle-commerce/issues/151#issuecomment-5302155988)에는 실제 Discord/Slack 채널 수신, 정상 무알림, synthetic DOWN 전송 및 전후 NORMAL이 기록돼 있다. Secret·raw 운영 정보는 위키에 옮기지 않는다. 현재 OCI에서 동일 경로가 동작하는지 이번 조사에서는 실증하지 않았다.
