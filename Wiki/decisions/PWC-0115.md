# Billing persistence 전환에서도 claim·외부 호출·completion 트랜잭션을 나눈다

## Context

Billing/Retry/Payment Reconciliation 은 재청구와 재고·쿠폰·장바구니 중복 효과를 막는 복구 protocol 이다. JDBC 제거를 이유로 transaction·missing-row 잠금 의미를 바꿀 수 없었다.

## Decision

세 owner 를 한 coherent T10으로 수렴하되 READY→PROCESSING commit 후 charge, 대사 attempt commit 후 query, 별도 completion 을 유지한다. UNKNOWN 재청구 금지, FAILED 에서만 retry1→2→3·재예약/hold, 대사 cap10을 보호한다. typed JPA/bulk write 와 기존 생성 ID 를 쓰고 실제 MySQL footprint 가 중요한 payment→order/context→ordered SKU·ACTIVE method LEFT JOIN·optional cart 잠금은 native 로 둔다.

## Alternatives and interpretation

JPQL lock 이 같은 gap/index footprint 일 것이라는 추정, 외부 I/O 의 Tx 내부 이동, missing cart 생성·cart version 정책의 무승인 변경을 제외했다. #389에서는 검증 없는 추가 production 책임 이동 대신 test-only 보호를 선택했다.

## Consequences and limits

flush/clear·생성 entity detach, 두 단계 사이 committed state 와 실패 후 고립 상태를 보존해야 한다. 실제 Provider·Production 복구는 이 저장소 작업의 완료 범위가 아니다.

## Implementation and verification

#359의 lock/read-view STOP·fixture cleanup/polling correction 과 Seoul baseline 분리를 보존한다. #364는 원본 핵심 15파일 blob 동일을 확인했고 JUnit gate2파일을 추가 교정해 실 MySQL physical1+3+1 PASS 후 실제 병합됐다. #359는 superseded/unmerged 다. #389는 준비 10분 TTL·claim CAS·provider callback Tx 없음·register rollback 을 실제 DB/provider mock 으로 검증하며 추가 설계 이동 완료로 세지 않는다.
