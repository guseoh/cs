# 신규 도메인 프로젝트는 AI와 함께 설계·구현하되 최종 의사결정은 사용자가 한다

## 배경

새 대규모 도메인 프로젝트에서 AI의 도움을 줄이고 핵심 코드를 무조건 혼자 작성하는 방식은 사용자가 원하는 학습 목표와 다르다. 목표는 직접 타이핑한 코드의 양이 아니라, AI를 활용하더라도 요구사항과 대안, 설계 근거, 실패 원인 및 검증 결과를 이해하고 스스로 선택하는 백엔드 개발 역량이다. [기존 AI 활용 설계·구현 트랙](BLR-0005.md)을 구체화하는 확정 결정이다.

## 결정

1. **협업 범위:** 요구사항 분석, 도메인 모델링, 핵심 로직과 알고리즘, 트랜잭션·동시성, 데이터 처리, 성능 실험, 기술 선택까지 **사용자와 AI가 함께 진행한다**. 이를 사용자의 단독 구현 의무로 표현하지 않는다.
2. **의사결정 주체:** AI는 질문, 설명, 힌트, 설계 대안, 트레이드오프, 코드·테스트 작성과 검증을 지원한다. 사용자는 핵심 요구사항, 설계·기술 선택, 수용 기준 및 최종 방향을 검토하고 결정한다. 모르거나 경험이 없는 기술은 결정을 내리기 전에 충분히 학습할 수 있다.
3. **단계적 도움:** 처음 접하는 기술(예: Kafka)은 실제 문제 → 필요한 개념과 작동 원리 → 적용 대안과 위험 → 사용자 결정 → 공동 구현 → 장애·정합성·성능 검증 순으로 안내한다. 기본적으로 힌트와 설명부터 제공하되 필요하면 코드 예제·완성 코드와 공동 구현으로 지원 수준을 높인다. 단계별로 사용자가 반드시 독립 코딩 시험을 통과할 필요는 없다.
4. **AI 기본 틀 허용:** 프로젝트 구성, 설정, 보일러플레이트, 테스트 자동화, 문서화뿐 아니라 핵심 구현도 AI와 함께 작성할 수 있다. 코드 작성자 여부보다 주요 실행 흐름을 이해하고 결과를 근거로 평가할 수 있는지를 중시한다.
5. **검증 기준:** 성능 수치, 정합성, 장애 복구, 부하 테스트 등은 실제 테스트나 관측 근거 없이 달성했다고 주장하지 않는다. 학습에서 확인한 선택·실험·수정 결과를 구분하여 기록한다.

## 선택하지 않은 대안

- **모든 핵심 코드를 사용자 혼자 작성하도록 강제:** 학습을 타이핑량 중심으로 바꾸고 낯선 기술의 도입을 불필요하게 지연할 수 있으므로 채택하지 않는다.
- **AI가 모든 기술·아키텍처를 최종 결정:** 빠른 구현은 가능해도 문제 해결 근거를 사용자가 설명하기 어렵기 때문에 채택하지 않는다.
- **기술 이름만 보고 Kafka·캐시·마이크로서비스 등을 선도입:** 문제·요구사항·실측 근거에 따라 선택한다.

## 결과와 제약

이 협업 방식은 **앞으로 선정할 별도의 대규모 도메인 프로젝트**에 적용한다. 물류 최적화와 대중교통 경로 검색 등은 검토 후보이며 이 결정으로 특정 도메인·기술 스택·착수 일정이 확정된 것은 아니다. [Large-scale Board의 사용자 중심 실습 로드맵](BLR-0003.md), DevPedia의 기존 설계 전용 기록 경계, PawCycle의 현재 작업 규칙을 자동 변경하지 않는다. Java/Spring 핵심 이해·선택적 심화라는 [학습 운영 원칙](BLR-0012.md)과 병행한다.

## 구현 및 검증

2026-11-19 사용자가 신규 프로젝트의 AI 협업 방식과 의사결정 주체를 명시적으로 확정하였다. 이는 **학습·협업 정책의 합의**일 뿐, 프로젝트 생성·코드 구현·실험 성공·서비스 배포를 검증한 사실은 아니다.

## 출처와 결정 경위

출처는 사용자와의 당일 대화에서 **명시적으로 확정된 원칙**이다. 공개 가능한 요지만 기록하며 비공개 대화의 원문이나 개인 정보는 기록하지 않는다. 별도 공개 원문 URL은 없다.
