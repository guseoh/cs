# 제안: A1 5분 감시를 호출·실제 조회·용량 알림·장애 감지로 분리한다

## Context — 관측된 실패와 경계
GitHub Actions에 `3-59/5 * * * *`를 설정한 뒤에도 예약 실행은 누락됐다. 2026-11-04 KST 05:34와 09:53의 실제 성공 실행 사이에는 약 4시간 19분의 간격이 있었다. 개별 Actions Job은 OCI API 조회에 성공했고 `OUT_OF_HOST_CAPACITY`를 반환했다. 따라서 *개별 OCI 조회 실패*와 *예약 이벤트 누락*을 혼동하지 않는다. [건강 상태 Issue #399](https://github.com/guseoh/pawcycle-commerce/issues/399)는 주기 누락을 경고했다.

[PR #502](https://github.com/guseoh/pawcycle-commerce/pull/502)는 Cloudflare Cron `*/5 * * * *` → GitHub Actions `workflow_dispatch(mode=check)` 경로를 저장소에서 준비했다. 기본값 `ENABLED=false`; Worker 배포, Token 등록, 실제 Dispatch, OCI/Discord 운영 E2E와 기존 GitHub Schedule cutover는 **미실행**이다. 성공한 CI와 Mock 테스트는 실환경 가용성을 증명하지 않는다.

## Proposed design (not yet approved)
이번 논의에서 검토하기로 한 후보 구조는 다음과 같다.

1. **Scheduler:** Cloudflare Worker는 5분마다 고정된 main 브랜치의 `check` 실행을 요청한다. GitHub API의 HTTP 204는 *접수*에 불과하며 OCI 조회 성공으로 취급하지 않는다. 중복 제어는 기존 GitHub Actions concurrency와 보수적인 실행 이력 확인을 조합한다.
2. **Executor:** GitHub Actions에서 기존 Python OCI Capacity Report와 Discord·Issue 상태 전이를 유지한다. OCI Credential은 GitHub에만 머문다. `self_test`, PR/다른 브랜치, 실행 요청만으로 건강 상태를 갱신하지 않는다.
3. **Success evidence:** 실제 OCI 조회와 해당 실행의 필수 후속 처리가 성공한 이후에만 독립 Heartbeat를 전송하는 것을 **제안**한다. `OUT_OF_HOST_CAPACITY`도 정상 API 조회 성공이다. `AVAILABLE`은 실제 보고 결과일 때만 전송한다.
4. **Independent failure detection:** Worker나 GitHub schedule이 통째로 멈추어도 일정 시간 Heartbeat가 없으면 외부에서 경고해야 한다. 별도 Heartbeat 서비스(예: Healthchecks.io)는 **후보**일 뿐 선정·연결·알림 검증은 안 했다.
5. **Timing:** 지연된 Cron의 `scheduledTime`만으로 실제 건강 상태를 산출하지 않는다. 실제 실행 시각과 Job 완료·조회 성공 타임스탬프를 측정한다. 10~15분 부재 경고는 **초기 제안 임계값**이며 실측 후 확정한다.

## Alternatives and trade-offs
- **GitHub Actions schedule 단독 유지 — 현 문제의 해결책으로 부적합:** 이미 실행 누락이 관측됐다. 기존 schedule은 cutover 전 fallback으로 유지한다.
- **Cloudflare → GitHub Actions — 우선 검증 후보:** Python·OCI Credential·Discord 상태 로직의 재작성 비용이 적다. 다만 GitHub Runner 대기·API 가시성 지연·중복 호출·단기 PAT 관리·Cloudflare 별도 운영 책임은 남는다.
- **Cloudflare Worker에서 OCI 직접 조회 — 후속 대안:** GitHub 실행 의존성을 제거할 수 있으나 OCI 인증과 기존 Python 기능을 이식해야 하므로 초기 변경 범위를 키운다.
- **OCI E5 Host systemd Timer — 장기 감시의 취약한 대안:** 감시 Host의 유지 가능성이 불확실하다.
- **Terraform으로 5분 감시 대체 — 부적합:** 선언형 자원 관리 도구 자체가 독립 감시 스케줄러를 제공하지 않는다.
- **Worker 에러 로그만으로 실패 인지 — 불충분:** Worker 자체 미실행이면 경고도 발생하지 않는다. 독립 감시의 인증·운영·무료 한도·전달 확인이 필요하다.

## Candidate acceptance and stop gates
- Offline 회귀: 잘못된 인증, API 실패·429, Timeout, Cron 지연, 중복 Job, stale/self_test 분리, Secret 비노출.
- 운영 별도 승인 후: 최소 24시간의 5분 슬롯(명목 288개) 대비 **실제 OCI 조회 성공 수, 최대 공백, Worker trigger와 Actions 실행의 시간차**를 측정한다. 288/288은 목표 비교치이지 보장 값이 아니다.
- 독립 경고: 성공 조회 부재 시 알림이 사용자에게 실제 전달되는지 **분리된 테스트 대상**으로 검증한다. 허위 Production `AVAILABLE` 이벤트를 생성하지 않는다.
- 지연·누락, 미승인 비용, 인증 사고, 중복 전이, 복구 불가능한 상태에서는 중지한다. 기존 GitHub schedule은 새 경로가 검증되고 별도로 cutover 승인되기 전까지 유지한다.
- 외부 서비스/계정 생성, Token 발급·등록, Cloudflare 배포, 모니터링 장애 주입, GitHub schedule 제거, PR 병합은 모두 별도 실행·승인 범위다.

## Evidence level and follow-up
현재 **설계 제안(PROPOSED)**만 기록한다. 사용자 요청은 재설계 검토와 Wiki 기록이며 특정 Heartbeat 제공업체 선정이나 실환경 활성화 승인으로 해석하지 않는다. 실제 채택·변경·검증이 이루어지면 새 증거를 대조하고 이 결정 기록의 상태·관계를 검토한다.

## Implementation checkpoint (2026-11-04; repository-only)

- [PawCycle Draft PR #503](https://github.com/guseoh/pawcycle-commerce/pull/503), HEAD `e41786634c002d8bf6c1ec99ceb50069e8569180`, stages the two-monitor design **without deploying it**. The Worker retains `ENABLED=false`, fixed main/check dispatch and active/recent-run suppression; comparisons now use actual invocation time. A scheduler heartbeat is emitted only after history/dispatch-or-legitimate-skip processing. A separate GitHub Actions heartbeat is emitted only after OCI Capacity Report plus required Issue/Discord processing succeeds. Healthchecks.io Ping URLs remain separate encrypted Secret inputs, not in code or Wiki.
- Cloudflare Dashboard read-only evidence: Workers Free, two existing Dark Todo Workers, two configured Production Crons, 292 recent worker invocations and zero Worker errors. The Cron Events view did not display November 4 data, so these aggregate calls **do not prove 288 successful scheduled events**. The new 10ms/Worker CPU utilization is unknown until measured.
- Healthchecks.io Hobbyist Free was investigated as a candidate with 20 Checks and 100 retained pings per Check. This is not a promise of 24-hour event retention: at a 5-minute cadence 100 pings cover approximately 8 hours. The initial 5-minute period / 10-minute grace is proposed pending observation and actual independent notification verification.
- [Original Draft PR #502](https://github.com/guseoh/pawcycle-commerce/pull/502) passed the Worker and health offline tests after changes but failed commit convention validation because three new commit subjects exceeded 72 characters. Rewriting the branch would violate PawCycle's no-history-rewrite guard, so the identical final 10-file change was submitted as one valid commit in **new Draft PR #503**. PR #502 was not closed or merged; user will decide its disposition.
- Neither external Healthchecks account/check creation, Cloudflare deployment, credentials, live dispatch, OCI check, delivery alarms, cutover nor rollback execution was performed. Accordingly this decision remains **`proposed`**, not operationally accepted or Production Verified.

## Short-term scope correction (2026-11-04)

The owner selected **Cloudflare Workers Free Cron → existing GitHub Actions → OCI Capacity Report**, only through approximately **2026-11-06/07**, instead of a permanent multi-service observability system. For this temporary campaign, **Healthchecks.io was explicitly rejected as unnecessary operational overhead**; the existing GitHub 2-hour/3-hour watchdog and Discord alerts are retained with acknowledged blind spots. The earlier two-heartbeat repository-only implementation in [Draft PawCycle PR #503](https://github.com/guseoh/pawcycle-commerce/pull/503) was **removed** on HEAD `03b21097588fe1c4636d2938be316d80e081a4d0`. No actual Cloudflare deployment or independent health alarm was run. `stale_check` in Cloudflare is only an execution error/log, not independent paging.

Slack Incoming Webhook was investigated as an **alternative to Discord**. It could send simple alerts on Slack Free, but current PawCycle Python code has Discord embed-specific payloads, delivery contract tests and existing notification paths; switching would require new Slack app/webhook Secret, formatting changes and delivery tests. For the short operation window **retain Discord unless the owner separately decides to switch**. This is a design trade-off, not a Slack change or delivery verification.

This checkpoint changes the scope of the original proposed redundant health system, **not** the accepted monitor-only/manual VM policy in PWC-0900. Neither PR #502 nor PR #503 was merged or used for Production.
