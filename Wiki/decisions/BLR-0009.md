# Selective Spring Framework / Spring Boot curriculum from user-provided course PDFs

## Context

The existing learning framework follows seven user-selected courses from the Kim Young-han Spring Boot roadmap: Spring Core basics, MVC 1/2, DB 1/2, Spring Core advanced, and Spring Boot principles/operations. Following every lecture and explaining every topic at equal depth makes the curriculum too large, slows useful backend development, and repeats separate JPA, database, HTTP and Spring Security studies.

The user supplies lecture PDFs and example code as *references* to the conceptual progression, not as a mandate to reproduce all lectures, course domains, implementation exercises or summaries. The overall goal remains Spring Framework / Spring Boot competence for modern Java REST API backend development.

## Decision

- **Preserve the seven-course order as a navigation scaffold**, not a verbatim course-by-course output requirement. Actual study units are the selected **Spring concepts**, often one complete, standalone explanatory article for a major concept.
- **Review each supplied PDF before teaching from it**; choose important structure, operational behavior, runtime flow, component relationships, API usage, design trade-offs and production cautions. Go deep only where important for backend development; explain other necessary concepts proportionately.
- **Omit, rather than automatically summarize, low-priority lecture material**: repetitive CRUD or introductory implementation, XML bean configuration exercises, Thymeleaf-specific template syntax and unrelated server-rendered page exercises. This is a *scope choice*, **not a claim that Spring XML configuration or Thymeleaf is removed or unsupported**.
- Retain a **bounded history of Servlet/JSP/handwritten front-controller MVC evolution** to understand why Spring MVC exists, without reconstructing every version of a teaching framework. Prioritize current Spring MVC request handling (DispatcherServlet, handler resolution/adaptation, argument resolution and HTTP message conversion).
- **Supplement verified essentials missing or underexplained in PDFs** when needed for modern Spring backend work: bean configuration/creation, dependency resolution, MVC validation and exception behavior, transactions and proxy boundaries, external configuration, auto-configuration and operational observability. Keep extra depth proportional and avoid duplicating separately established JPA, database, networking and Security tracks.
- **Teach as an independent Spring explanatory text**, not a course recap or private note: naturally connected Korean paragraphs, numbered substantive sections, precise Java object-reference and Spring runtime explanations, practical consequences and important limits. Put reliable official resources, Korean engineering sources (including Tecoble), relevant figures and concise diagrams near the explanation they support. Avoid repeated code and conclusions.
- **No mandatory quizzes, comprehension checks, new exercises or test tasks**. Prefer the PDF's existing code and figures to illustrate behavior. Additional implementation/verification only on explicit request or truly necessary to clarify a specific point.

## Rejected alternatives and trade-offs

- **Explain every lecture/PDF subsection in full depth:** rejected due to time, redundancy and excessive focus on teaching domains.
- **Give every low-priority topic a separate brief summary:** rejected; genuinely unnecessary material may be omitted.
- **Skip all non-immediate foundations:** rejected; retain prerequisite concepts needed to explain current Spring architecture correctly.
- **Rebuild each early MVC framework version:** rejected as a required exercise; keep only the evolution and conceptual constraints necessary to understand the Spring MVC architecture.
- **Treat XML or Thymeleaf as deprecated/unavailable:** incorrect and not the rationale for omission.

## Consequences and constraints

The teacher must distinguish the supplied-PDF scope from modern official documentation, verified additions and unresolved behavior. The exact filtered topic catalog, additions, omissions and per-topic depth **remain undecided** pending exhaustive source review. Revisions should not silently supersede separate learning roadmaps, add mandatory hands-on tasks or change existing project operations.

The user elected to conduct the **full PDF curriculum redesign first in ChatGPT Work**. A supplied `Spring.zip` archive was inspected only for its archive listing: 72 PDF entries along with example project files; **PDF content has not been audited in this Wiki task**, and no redesigned curriculum has been approved.

## Implementation/verification

The teaching preferences and broad seven-course scaffold were directly confirmed in conversation on 2026-11-08. This records a **curriculum-selection method**, not a completed 72-PDF review, a finalized new syllabus, verified up-to-date API details, completed study or executed code/test results.

Sanitized, user-confirmed learning-method decision in a ChatGPT conversation. The uploaded course archive and private chat are not copied into this public repository; there is no public source URL for the user-authored choice.
