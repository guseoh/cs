# 4단계 규모 측정은 Flyway schema 위에 합성 데이터를 채우고 backend에 직접 요청한다

## Context

4단계는 데이터 1만 → 10만 → 100만에서 같은 조건의 기준선을 얻어, 2단계 알림 임계값과 5단계 병목 개선의 근거로 쓴다. 합성 데이터 생성기([#547](https://github.com/guseoh/pawcycle-commerce/pull/547))는 Flyway history 없이 schema를 만들어 backend가 기동하지 않았다. 합성 회원은 로그인할 수 없었고, 처리할 구독 회차가 0건이었다. 이전 측정 compose가 쓰던 스케줄러 설정(`PAWCYCLE_SCHEDULER_ENABLED`)은 코드에 없는 이름이었다.

## Decision

사용자가 2026-11-18 설계 문서의 권장안을 승인했다("권장안대로 G-1 진행").

- **연결:** 실행마다 별도 compose project를 만든다. backend Flyway가 빈 DB에 schema와 history를 만든 뒤 생성기가 데이터를 채운다. 생성기는 history가 완전하고 저장소 최신 migration 버전과 같을 때만 받는다.
- **로그인 부하:** 실제 BCrypt 해시(cost 10) 하나를 이력 있는 합성 회원 K명(기본 1,000)에 복사한다. 비밀번호는 실행마다 무작위이고 저장하지 않는다.
- **경로:** backend에 직접 요청한다. nginx 포함 경로는 요청 제한 동작을 보는 별도 항목이다.
- **자원:** backend는 운영과 같은 상한(640m / 0.75 CPU), MySQL은 2 CPU / 2 GiB로 고정하고 기록한다.
- **스케줄러:** 코드의 실제 설정 이름으로만 켜고 끈다. 읽기 기준선에서는 끌 수 있는 작업을 모두 끈다.
- **정기배송:** `--due-count K`로 처음 K개 ACTIVE 구독의 회차를 `--as-of` 날짜로 둔다.
- **순서와 기준:** 1만 → 10만 → 100만(100만 생성이 2시간을 넘으면 생성기부터 개선), 혼합 부하 70/15/10/5와 정상 부하 10분, 성공 기준은 탐색 p95 < 300ms·쓰기 p95 < 1초·오류율 < 1%·Hikari 시간 초과 0·불변식 위반 0. 기준에 못 미치는 것은 실패가 아니라 5단계 후보로 기록한다.

## Rejected alternatives

- Flyway baseline: 가장 간단하지만 migration 검증을 건너뛰어 schema 차이를 놓칠 수 있다.
- 생성기가 history 행을 직접 씀: Flyway 내부 checksum 형식에 의존해 깨지기 쉽다.
- 회원가입 API로 측정 회원 생성: 이력 없는 회원이라 조회 부하가 빈 결과다. 구현 중 가입 API 자체가 없다는 것도 확인했다.
- 생성기에서 BCrypt 생성: Python 표준 라이브러리에 없어 새 dependency가 필요하다.
- nginx 경유: IP별 요청 제한에 걸려 backend가 아니라 nginx 거부를 측정한다.

## Consequences and constraints

- 결과는 로컬 Docker Desktop 기준의 상대 비교이며 운영 용량의 절대값이 아니다.
- backend를 한 번 더 기동해야 한다(1만 규모에서 약 50초).
- 해시 계산에 backend jar와 Dockerfile build stage의 JDK 이미지를 쓴다. 회원가입 API가 생기면 다시 검토할 수 있다.
- due 회차 날짜가 실행일보다 과거라 자동화를 켜면 overdue로 집계될 수 있다.
- cache·Redis 세션 없이 측정한다.
