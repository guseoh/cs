# Introduce Sentry for learning; evaluate portfolio adoption by trade-off

## Context

Sentry provides application-level error grouping, stack traces, issue tracking and selected performance insights. These overlap in part with logging, metrics and traces already available through existing observability tools; introduction has benefits as well as complexity, cost and data-handling trade-offs.

## Decision

- **Large-scale Board:** adopt Sentry as a **learning exercise** within the existing experimental/operational roadmap, including deliberately triggered exceptions, collection/issue grouping, context examination and comparison with application logs and metrics. This is a learning decision, not a claim that Sentry is installed.
- **Portfolio projects:** evaluate need and trade-offs **before** choosing whether Sentry should be adopted. Compare existing logging, Prometheus/Grafana and tracing coverage with new error-tracking value, cost, SDK/runtime complexity, alerting overlap and exposure of sensitive data.

## Rejected alternatives

- Deploy Sentry automatically to every portfolio project.
- Treat installing another tool as sufficient proof of production observability.
- Claim that a tool already present in a roadmap is currently enabled.

## Consequences and constraints

- Do not replace the Large-scale Board roadmap or add a mandatory earlier milestone without an explicit revision.
- Do not install Sentry in PawCycle, DevPedia or other portfolio services merely on the basis of this policy.
- Actual integration, usage costs, captured data and runtime behavior remain unverified.

## Implementation/verification

User confirmed the split learning-versus-portfolio policy on 2026-11-04. The [Board roadmap](https://github.com/guseoh/large-scale-board/blob/main/docs/ROADMAP.md) includes Sentry as a possible later operational extension; no code or service installation was made.

## Provenance

Direct user decision in the observability learning discussion.
