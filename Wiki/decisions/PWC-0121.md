# HTTP 입력·응답 변환은 API가 소유하고 내부에는 중립 Command와 완성된 View를 전달한다

## Context

Coupon/Catalog Admin/Engagement/Recommendation 의 application·persistence 가 API Request/Response 를 직접 참조했다. mapper 위치만 옮기면 API→persistence 역의존이나 lazy read·commit 시점 변화가 생길 수 있었다.

## Decision

기존 Command/View 를 먼저 재사용하고 Request→Command 는 API mapper, 완성된 scalar View→HTTP 는 각 ResponseDTO 의 public static from(View)가 소유한다. 사용자 선호에 따라 #393의 별도 API response mapper 안은 superseded 했고 #394에서 DTO factory 로 교정했다. materializing getter·연관 ID·조회/권한/검증·transaction·audit 는 기존 owner 에 남긴다. from 에는 DB 접근·검증·기본값·새 null 정책을 넣지 않는다.

## Alternatives and interpretation

복제 DTO/거대 공통 Mapper/Port/framework, API 가 persistence View 를 직접 알게 하기, 단순 파일·edge 수로 Task 분할을 제외했다. #398은 같은 응답 목적/검증/revert 경계인 Engagement+Recommendation 을 하나로 합쳤지만 기능별 model 은 유지한다.

## Consequences and limits

입력 presence/명시 NULL/false/목록 순서와 응답 nullable helper/페이지 metadata·UUID 생성 위치·List.copyOf 의 null 거부 시점을 보존해야 한다. DTO 생성이 commit 뒤로 옮겨지는 비용을 인정하며 정상 producer 의 materialized 값·SQL/entity load0으로 범위를 검증한다. 손상된 모든 View 의 예외·rollback 동등성까지 보장하지 않는다.

## Implementation and verification

#387 persistence-api1개, #392 입력 32개, #394 확장응답 30개, #397 core26개, #400 경험 14개를 compiled 실제 결과로 제거했다. 정상 View 의 OSIV=false/Tx·EntityManager 종료 뒤 SQL/entity load0, 실 Audit/Notification write 뒤 rollback/cacheafterCommit, UTC/Seoul·HTTP/JSON/frozen parity 를 보호한다. 각 최초 fixture/compile/stale baseline 실패와 최신 CI 성공을 나눠 보존한다. #397 rate-limit 및 #400 review0/0은 CodeRabbit 완료가 아니다.
