# Commerce 런타임 책임을 분리하되 API·DB·트랜잭션 불변식을 보존한다

## Context
MVP3의 API-006/API-007 및 Flyway V1–V19 계약이 이미 존재하는 상황에서 단일 `CommerceService`, Controller 트랜잭션, 중복 재고/회원 상태 변경으로 회귀 영향 범위가 커졌다. [ARCH-009](https://github.com/guseoh/pawcycle-commerce/blob/main/docs/adr/ARCH-009-commerce-runtime-refactoring.md)은 외부 계약을 보존하면서 책임을 나누는 변경을 선택했다.

## Decision
API와 V1–V19 Schema를 유지하고 Commerce 테이블에 JPA Entity/Repository와 Hibernate validate 모드를 도입한다. 잠금/CAS·일부 운영 조회·유지보수 및 구독 V2 호환 경계는 명시 SQL로 남긴다. 재고 변동, 회원 등급, Checkout 만료, HTTP adapter를 역할별 서비스로 분리하되 상태 변경과 필수 movement/audit는 같은 caller transaction에 둔다. 외부 Provider I/O는 트랜잭션 밖에 둔다. 관리자 주요 변경 6개는 `AdminCommerceService`의 트랜잭션에서 감사 기록까지 원자적으로 처리하고 감사 실패 시 mutation도 rollback한다.

## Rejected alternatives
- **모든 조회·쓰기 SQL을 일괄 JPA로 치환:** lock/CAS 및 운영·호환용 SQL 경계의 의미를 잃으므로 단계적으로 구분한다.
- **Controller가 트랜잭션·감사 기록을 각각 조정:** API adapter와 상태 불변식 책임이 섞이므로 변경한다.
- **감사 실패 후 상태 변경만 commit:** 성공한 비즈니스 변경에 요구되는 audit 불변성을 깨므로 허용하지 않는다.
- **외부 Provider 호출을 DB 트랜잭션 안에 포함:** 느리거나 실패하는 외부 I/O가 DB 자원 점유를 확대할 수 있어 분리한다.

## Consequences and constraints
클래스 수 감소 자체가 성공 기준이 아니다. 이전과 같은 HTTP 결과, DB 최종 상태, Provider 호출·멱등성, 재고 불변조건을 characterization test로 확인해야 한다. 당시 계획된 `CLEANUP-002/003`과 이후 Backend V2 변경은 별도 후속 이력이다.

## Implementation/verification
[PR #139](https://github.com/guseoh/pawcycle-commerce/pull/139)은 2026-08-13 병합됐다. 해당 시점의 저장소 리팩터링 근거이며 후속 전체 persistence 상태 또는 Production E2E까지 확인한 것은 아니다.
