# V11 학습 집중 전략과 프로젝트 해체 분석 방향

## 배경과 문제

기존 [PWC-0145](PWC-0145.md)의 실제 시스템 교재화, 세 병렬 트랙, 구현 전 설계 토론을 유지한다. 이미 축적한 구현·실험·포트폴리오 후보에 비해 사용자 이해가 부족하고, 기능 확장 및 작업 완료 자체에 끌려갈 위험이 있다. 2026-11-27 개정된 ChatGPT 프로젝트 V11 지침 및 네 소스 파일은 이러한 문제에 대응해 현재 집중 전략을 구체화했다. 이번 요청으로 분석 방향의 Wiki 등록과 Codex를 통한 경량 로드맵 구체화를 승인했다.

## 결정 및 제약

- 현재는 별도 Bottom-up 기본기 학습(Java·객체지향·Spring·JPA·DB·CS 등)과 Track B의 Top-down 프로젝트 해체에 집중한다. 두 진도를 강제로 일치시키지 않고 필요한 개념은 실제 코드 문맥에서 보충한다.
- Track B와 Track C의 개선 여지 검토를 병행한다. Track A 신규 AWS 구축과 Track C 선택적 기능·성능·구조 확장은 후순위다. 기존 AWS 시간제 운영 결정과 장기 목표를 폐기하지 않는다. 안전·정합성·비용 위험은 우선 평가하고 실행은 별도 승인한다.
- 전체 시스템에서 시작하여 실제 요구사항, 도메인/ERD, 패키지와 객체 책임, 기능 실행 흐름, 기술 선택과 역사적 문제 해결로 내려간다. 현재 구조도 정답으로 전제하지 않는다. 코드 품질·과잉 추상화·중복·방어 코드·보안·정합성·테스트를 같이 검토한다.
- 분석·설계는 읽기 전용이 기본이다. 개선 후보를 즉시 구현하거나 Issue/PR로 만들지 않는다. 현상 유지·최소 변경·대안의 장단점, 적용 조건·실패 가능성·검증을 비교한 뒤 사용자 판단에 따라 필요한 변경만 진행한다.
- 고정 일정·진도표·시험·전체 코드 재구현·모든 과거 PR 순차 분석·모든 주제 문서화를 강제하지 않는다. 이해가 쌓이면 사용자 판단으로 개선·실험·운영 비중을 늘린다.

## 분석 지도 — 구체 순서는 제안

| 분석 영역 | 핵심 범위 |
| --- | --- |
| 제품 및 요구사항 | 일반 구매·정기배송, 사용자·관리자, 비즈니스 정책, 기능/비기능 요구, Product Gap |
| 시스템 아키텍처 | 구성 요소·통신·기술 역할, 환경·배포·관측·빌드 경계 |
| 도메인 및 데이터 모델 | 논리/물리 ERD, 관계·카디널리티, 객체 모델, DB 제약·인덱스, 상태 전이와 불변식 |
| 백엔드 애플리케이션 구조 | 패키지·계층·객체 책임·의존성, 공통 코드·설정·보안·테스트 |
| 핵심 기능 실행 흐름 | 상품 조회·인증·장바구니·주문/Checkout·재고·결제/복구·환불·멤버십·구독·검색/추천·관리자 등 실제 존재하는 기능을 선별 |
| 기술적 선택과 문제 해결 | 동시성·멱등성·외부 I/O·교착·Snapshot·스케줄러·조회 최적화·캐시·관측/운영 사례의 당시 근거와 현재 구현 |
| 설계 평가 및 개선 | 전 영역에서 병행: 코드 품질·설계·성능·정합성·보안·제품 결함·대안 |

초기 추천 순서는 제품과 요구사항 → 전체 시스템 지도 → 도메인/ERD → 백엔드 패키지·공통 구조 → 비교적 단순한 상품 조회 수직 추적 → 핵심 비즈니스 및 문제 해결 사례다. 실제 코드와 의존성에 따라 조정하며 완료 의무가 있는 선형 로드맵이 아니다.

## 분석 방법과 자료

기능 수직 추적을 기본으로 HTTP/Security/Controller/DTO → Application Service·객체 의존 → Transaction·외부 I/O → Domain 상태·불변식 → Repository/JPA/Querydsl/SQL → Migration·DB 제약·Lock → 정상/실패/중복 결과 → 보호 테스트까지 연결한다. 필요한 기술은 여러 기능을 가로지르는 수평 분석으로 심화한다. 과거 문제는 증상·가설·실패한 접근·원인·해결·검증·한계를 당시 원본과 최신 코드에 대조한다. 선택적으로 요구사항만 놓고 독립 재설계하거나 격리 재현할 수 있다.

현재 구현은 최신 main 코드·migration·설정·테스트, 의도는 승인 계약·ADR, 역사는 Wiki/PR/Issue/Commit/보고서로 확인한다. 공식 문서·국내외 기술 블로그와 필요 시 도식을 원리 보충에 사용한다. 추정·테스트 존재·실행 성공·운영 검증·사용자 이해를 구분한다. 기존 문서가 충분하면 중복 작성하지 않는다. 일반 개념은 사용자 요청/합의 시 Study, PawCycle 사례는 Project/pawCycle, 확정 결정과 근거는 Wiki에 기록한다.

## 대안과 트레이드오프

- 파일 순차 설명이나 과거 PR 전수 학습은 맥락과 우선순위를 놓칠 수 있어 채택하지 않는다.
- 이론 일괄 이수 후 프로젝트 진입은 연결이 늦고 반복 학습 부담이 크다. 필요한 기초를 충분히 보충하되 별도 커리큘럼은 중복 생성하지 않는다.
- 모든 발견을 즉시 리팩터링하면 AI 주도 구현 반복 및 회귀 위험이 커진다. 분석과 개선 후보는 결합하되 실행 승인은 분리한다.
- 유연한 분석 지도는 고정 일정 대비 진행량을 수치화하기 어렵지만 이해·실제 설계 판단을 우선할 수 있다. 필요에 따라 범위를 조정한다.

## 구현 및 검증 범위와 다음 작업

ChatGPT V11 공통 지침과 실제 소스 파일 `PCC_V11_01_LEARNING.md`, `PCC_V11_02_SYSTEM.md`, `PCC_V11_03_AWS.md`, `PCC_V11_04_ENGINEERING.md`를 확인했다. 이는 이전 PWC-0145의 5개 파일 제안을 보완하는 채팅 프로젝트 지침이며 제품 저장소 파일 적용을 뜻하지 않는다. 기준 PawCycle main은 `0c7dbce70e0164c198f08f208b252d3d4156d59c`로 조회했으나 이번 작업에서 전체 제품 코드·ERD·실행 테스트를 새로 검증하지 않았다.

초기 결정 시점의 다음 작업은 Codex가 이 결정과 최신 저장소 원본을 바탕으로 분석 영역별 실제 경로·핵심 질문·의존성·대표 사례·초기 분석 단위를 포함하는 간결한 Working Roadmap 초안을 반환하는 것이다. 기존 문서와 차이를 표시하고 제품 코드/문서/Issue/PR/운영 변경이나 새 실험은 수행하지 않는다. 세부 로드맵은 사용자 토론을 거쳐 확정하며 이해 완료나 구현 승인을 뜻하지 않는다.

## 합의한 해체 분석 Working Roadmap

2026-11-27 사용자는 앞선 초안을 검토하고 네 가지 역량을 함께 기르는 진행 방식을 채택했다. 코드 이해는 Java 객체와 Spring 호출 흐름을 설명하는 데서, 시스템 설계는 제품 요구를 객체·데이터·시스템 경계에 연결하는 데서 기른다. 문제 해결은 실패의 원인을 증거로 좁히고, 기술적 판단은 현재 설계와 대안 사이에서 선택의 이유를 설명하는 데서 기른다.

### 첫 주제와 네 가지 지도

첫 주제는 **PawCycle Commerce의 전체 제품 요구사항과 핵심 비즈니스 구조**다. 상품 탐색, 회원, 장바구니, 구매, 정기배송, 사후 처리, 추천 및 관리자 운영까지 훑는다. 기존 자료를 다음 관점에서 최신 구현과 대조하고, 필요한 부분만 대화에서 그린다.

| 관점 | 첫 질문 | 출발점 |
| --- | --- | --- |
| 제품 | 고객·관리자에게 어떤 기능을 제공하며 누가 가격·배송·취소 정책을 결정하는가? | `docs/product/current-scope.md`, PS-004/005, 화면과 API 계약 |
| 시스템 | 브라우저 요청과 예약 작업은 어느 프로세스에서 실행되며 어디서 외부 통신이 발생하는가? | `docs/architecture/system-overview.md`, 운영 개요, `infra/production/compose.yaml` |
| 도메인 | 상품·SKU·주문·결제·재고·구독·배송은 누가 생성하고 언제 상태를 바꾸는가? | `docs/data/current-schema.md`, `docs/domain/state-machines.md`, Flyway migration |
| 코드 | 요청과 스케줄 작업의 진입점, 객체의 책임, 패키지 간 호출은 어떻게 연결되는가? | `docs/architecture/backend-architecture-v2.md`, Backend의 `catalog`, `member`, `commerce`, `subscription`, `common` |

전체 맥락을 잡은 뒤 일반 구매와 정기배송의 시작 주체, 주문·결제·배송의 시점, 공통 데이터와 회차 고유의 상태를 비교한다. 첫 수직 추적은 상품 목록 화면에서 `GET /api/products`로 이어지는 정상 조회다. 이어 회원·인증과 장바구니를 거쳐 Checkout·재고·결제·구독을 깊게 읽는다. 기술 비교와 역사 복원은 관련 흐름이 익숙해지는 시점에 끼워 넣는다. 별도 Bottom-up 학습에서 배운 개념은 실제 코드의 판단에 사용한다. 고정 일정·진도율·완료 관문·별도 지도 문서는 두지 않는다.

### 기능을 읽는 깊이와 세 가지 분석 방법

1. **비즈니스** — 고객의 행동과 기대 결과를 한 장면으로 설명한다.
2. **객체와 코드** — DTO, Spring이 주입하는 협력 객체, 호출 중 만들어지는 객체를 구별하고 각 메서드의 책임을 읽는다.
3. **정상 실행** — 입력값 하나가 메서드 호출, 조회·쓰기, 응답 필드로 바뀌는 경로를 따라간다. 실제 SQL 관찰과 코드에서 예상한 SQL을 구별한다.
4. **기술 원리** — 그 경로에서 DI, 트랜잭션 경계, JPA 영속성, DB 제약이 담당하는 부분을 설명한다.
5. **실패와 경합** — 중복 요청, 마지막 재고 경쟁, 외부 승인 뒤 내부 롤백처럼 조건 하나를 바꾸고 남는 상태를 확인한다.
6. **설계 판단** — 유지·단순화·대안 각각이 보장하는 동작과 새로 생기는 비용을 비교한다.

단순 CRUD는 정상 호출을 설명할 만큼만 읽고, 돈·재고·구독 회차처럼 실패 결과가 큰 기능은 깊게 다룬다. 결과 예상이나 독립 설계는 선택 활동이다.

- **수직 분석**은 한 행동을 끝까지 읽는다. 상품 목록에서는 화면 필터 하나를 요청 DTO와 조회 조건, 응답까지 따라가고 계약 테스트가 실제로 단언하는 필드를 확인한다.
- **수평 분석**은 둘 이상의 기능에서 같은 기술의 선택 기준을 비교한다. 객체의 정책 배치, 인터페이스·DI, Request/Command/Response의 변환, 예외의 HTTP 변환, 인증과 자원 소유권을 살핀다. 트랜잭션 선언과 명시적 경계, JPA 매핑·Querydsl·직접 SQL, 잠금·DB 제약, mock·통합·실제 MySQL 테스트도 각 방식이 보호하는 동작과 연결한다.
- **역사적 분석**은 초기 구현 → 관찰된 증상 → 시도와 한계 → 현재 코드와 회귀 테스트를 당시 자료로 복원한다. 멤버십 교착은 ARCH-017, PR #558·#564를 함께 읽는다. 구현해 실패한 시도, ADR에서 검토 후 기각한 대안, 원문이 없어 미확인인 구간을 구분한다.

### 코드 품질과 독립 설계 토론

평소에는 Java 표현과 조건문이 의도를 드러내는지, 이름과 메서드·클래스 책임이 맞는지, 인터페이스·위임·패키지 분리가 실제 호출자에게 이점이 있는지 본다. 방어 코드는 입력 경계와 발생 가능한 데이터로, 과거 호환 코드는 migration과 소비자로, 테스트는 구현을 바꾸어도 지켜야 할 동작으로 판단한다. 예컨대 `ProductDiscoveryReader`를 인라인할 때 호출자가 어떤 의존성을 떠안는지 물으면 단순 위임의 비용과 책임 분리의 이점을 비교할 수 있다. 결론은 단순해서 충분한 구조, 비용을 감수할 이유가 있는 구조, 줄일 근거가 있는 복잡성, 근거 부족 중 어디에 해당하는지 설명한다.

중요한 기능을 이해한 뒤에는 가끔 요구사항만 놓고 독립적으로 대안을 비교한다. 마지막 재고 한 개에 주문 두 건이 경합한다면 조건부 UPDATE, 비관적·낙관적 잠금, Redis 기반 제어의 보장 범위·충돌 빈도·처리량·복구·운영 부담을 비교한다. 이 예시는 현행 구현이나 채택 결정에 대한 주장이 아니다. AI 추천에도 같은 기준을 적용하고 결론을 바꿀 조건을 남긴다. 직접 수정·부하 실험은 별도 승인 후 선택한다.

이번 합의는 분석 방법과 탐색 순서에 관한 것이다. 사용자는 인용된 코드·테스트를 독립 재검증하지 않았다. 프로젝트 요약 문서와 현재 코드 사이의 차이, 실제 SQL·운영 활성 설정은 해당 주제에서 확인한다. 첫 분석은 전체 기능과 주체를 놓고 주문·결제·재고·구독·배송의 관계를 설명하는 대화로 시작한다.
