# Querydsl은 복잡한 mapped read에 한정하고 compiled dependency guard를 유지한다

## Context

동적 query 조합과 raw mapping 은 유지보수 비용이 있었지만 모든 고정 JPQL·vendor SQL 을 Querydsl 로 바꾸는 것은 이득이 불분명했다.

## Decision

T01에서 Querydsl7.7을 facet read 한 곳에 pilot 적용해 clean Q-generation·기존 SQL 결과·단일 SELECT 를 비교한 뒤 scope-limited KEEP 했다. ArchUnit1.5.0의 production bytecode guard 도 KEEP 했다. 명시적 legacy baseline 과 actual 을 양방향 비교해 신규 위반과 해결됐는데 남은 baseline 모두 차단한다. Q-type 은 persistence 구현 안에 두고 generated source 는 commit 하지 않는다.

## Alternatives and interpretation

Querydsl everywhere, API predicate binder 노출, baseline 자동 생성/승인, 모든 legacy 위반을 즉시 없애는 대규모 rewrite 를 제외했다. 단순 고정 read 는 JPQL, MySQL 고유 query 는 근거 있는 native 를 선택한다.

## Consequences and limits

추가 build/annotation processing 비용과 Hibernate/JPA 호환성 검증이 필요하다. explicit alias/createDefaultVariable=false 는 static 초기화 cycle 회피 선택이었다. guard 는 reflection·SQL 의미·transaction 정합성을 증명하지 않는다.

## Implementation and verification

#341은 131 legacy edge freeze 와 실제 MySQL facet parity, clean build/최종 CI 를 확인했다. JAVA_TOOL_OPTIONS 때문에 자식 JVM stderr7 FAIL 후 국소 재검증 7 PASS 를 분리한다. IntelliJ UI 와 성능 benchmark 는 미실행이다. #347은 고정 Order read 에 JPQL 을 선택했고 #349는 실제 optional predicate/join 가치가 있는 Recommendation 에만 확장했다.
