# Phase 9는 resource envelope를 재현한 뒤 단일 변수 후보를 채택·기각한다

local250진단의약2SQL/request·낮은query/acquire/usage·pending0은SQL/index/pool확대를첫최적화로지지하지않았다. AWS와다른640MiB/0.75CPU/PID256envelope를backend에만재현해request/thread/native/resource압력을분리했다.

envelope first-result는1000VU/PID225/565.4MiB와metric불능을보였으나aggregate없음·OOM없음으로partial이다. 동일load는반복하지않고collector보존을보강했다.

Tomcat64는PID/memory압력을줄였으나actual39.5583RPS/drop24256/p5021.241s로성능희생이과도해기각했다. CPU포화가남아worker제한방향은유지하고128을후속단일변수candidate로둔다. local값채택은Production권장/배포승인이아니다. 이후후보/대가도이기록에누적한다.

Tomcat128은64보다낫지만actual71.83RPS/drop20385/p9516.51s로기각했다. CPU0.75→1.5는actual109.06으로개선됐으나640MiB99%·GC/memory재병목,1GiB는actual145.70/p958.136s로더나아져도pendingpeak116과CPU포화가남았다. memory는보조원인이다. 이값들은local인과성실험이지Production권장sizing이아니다. [전체조건·실행댓글](../history/pawcycle-source-ledger/batch-181-190.md).

CPU2 개선은 특정 Java method의 책임을 입증하지 못했다. PH9-011의 불충분한 profiling 뒤에는 CPU/worker 숫자 튜닝이나 추정한 mapping·serialization 최적화를 더하지 않고 [추가 최적화 NO CHANGE](PWC-0077.md)로 Phase 9을 종료했다. 이는 병목 해결이나 과거 실험의 성공 판정이 아니다.
