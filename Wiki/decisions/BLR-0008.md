# Use the end-to-end web request path to integrate OS, networking, and server operations

## Context

A curriculum limited to CLI commands and Nginx installation would miss the relationship between the operating system, network transport, HTTP, the reverse proxy, the JVM and actual failure recovery. Conversely, trying to become an infrastructure specialist across cloud platforms and distributed production systems in this first phase would spread the learning scope too broadly.

## Decision

The **learning spine is the full execution path of a web request on a single Ubuntu host**: Windows client -> names/hosts or DNS -> VM address/route -> TCP listening socket/port and host firewall -> TLS/HTTP at Nginx -> reverse proxy -> embedded Tomcat/Spring Boot Java process -> response. Observe the supporting Linux process, permission, systemd and logging mechanics. Treat this as **understanding a web service's operating environment**, not mastery of all networking, operating systems or infrastructure engineering.

Emphasize three cross-cutting connections alongside the eight curriculum stages:

1. Explain the lifecycle from name lookup and TCP connection through TLS, HTTP, proxying, application processing, and response.
2. Connect Linux sockets, bind addresses and processes to network reachability across the Windows/WSL/VM boundary.
3. Attribute failures to name resolution, network/firewall, web server, application, OS process/configuration or resources using reproducible evidence before making changes.

The user approved recording and proceeding from the revised learning direction on 2026-11-08. The [detailed phase roadmap](../knowledge/BLK-0001.md) is a plan and reference, not completed work.

## Alternatives and trade-offs

- **Pure CLI command syllabus:** insufficient to teach requests and operational diagnosis.
- **Only deploying a Spring application:** hides Linux and transport concepts.
- **Cloud-native/distributed infrastructure in phase one:** deferred (Docker orchestration, Kubernetes, multiple nodes, HA/LB, elaborate VPC, advanced CI/CD, full observability stack).
- **Bounded local Ubuntu lab:** chosen for safe repeatable direct practice, while allowing later expansion.

## Consequences and constraints

Maintain theory + hands-on verification, reasoning before commands, small reversible exercises, and no requirement to memorize all CLI flags. Initial lab is Windows + WSL2; use a distinct Ubuntu Server VM when needing independent boot/network/firewall/SSH behavior. A static page and minimal no-DB Spring Boot API can provide a reusable operational target rather than a new product project.
