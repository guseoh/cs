# 여섯 도메인의 독립 실행 Spring Boot 앱을 하나의 학습용 저장소에 모듈로 관리한다

## 배경

2026-11-19에 처음 논의했던 다중 도메인 Monorepo 제안이 같은 날 사용자의 후속 메시지로 **명시적으로 확정**되었다. 하나의 서비스를 여섯 분야로 확장하는 것이 아니라 **서로 다른 목표를 갖는 여섯 학습 애플리케이션**을 한 GitHub 저장소에서 관리하려는 것이다. 포트폴리오 완성보다 시스템 이해·설계·구현·검증 학습을 우선한다.

## 결정

1. **단일 저장소:** 물류 최적화(`logistics`), 대중교통 경로 검색(`transit-search`), 부동산 실거래가 분석(`real-estate`), 대규모 티켓팅(`ticketing`), 주차장 검색/예약(`parking`), 실시간 이벤트 집계(`event-analytics`)를 한 GitHub 저장소에서 다룬다.
2. **독립 실행 단위:** 각각은 독립적으로 기동·테스트하는 **Spring Boot 애플리케이션**이다. 개별 API, 도메인 모델, 데이터 저장소(물리 DB나 논리 스키마는 후속 결정), 테스트, 런타임 설정을 가진다. 한 애플리케이션 내부의 여섯 패키지가 아니며 **자동적으로 서로 통신하는 MSA도 아니다**.
3. **목표별 차별화:** 물류=재고/출고 정합성·분산 장애, 교통=그래프/최적 경로·검색, 부동산=공공 데이터·배치·SQL 성능, 티켓팅=예약 경쟁·대기열, 주차장=공간 검색·예약/캐시, 이벤트 분석=Kafka·스트림 처리·집계/복구를 우선 학습 대상으로 한다. 각 상세 실험과 기술 도입은 문제 정의 이후 별도 승인한다.
4. **점진적 구성:** 모든 모듈을 동시에 완성하거나 기동하도록 강제하지 않는다. 먼저 물류 분야에서 기존 학습 흐름을 이어가고, 다음 앱은 학습 필요에 따라 추가한다.
5. **빌드 방식:** `Gradle 멀티 프로젝트`와 `apps/*` 배치는 **추천 구현 초안**이다. 최종 빌드 스크립트, JDK/Spring Boot 버전, 모듈 위치는 실제 초기 설정 시 검토·확정한다.
6. **공유 정책:** 빌드/테스트 관례·문서 형식은 공통화 가능하지만 서로 다른 도메인의 엔티티·Repository·비즈니스 로직·DB 테이블을 가짜 공통 API로 묶지 않는다. 실제 반복과 필요성 검증 이후에만 공통 유틸리티를 추출한다.
7. **교재 연계:** 동일 저장소에 시스템 설계 1·2권의 **별도 설계 실습 트랙**을 둔다. 책 내용의 범위와 운영 원칙은 [BSL-0002](BSL-0002.md)에 기록한다.

## 비교한 대안

- **도메인마다 분리된 저장소:** 각 서비스 격리는 단순하지만 학습 진행/설계 기록과 Gradle·CI 관리가 분산된다.
- **하나의 실행 Spring Boot 애플리케이션:** 초기에 코드량은 줄지만 무관한 학습 문제의 배포·데이터·테스트가 뒤섞인다.
- **여섯 서비스의 완전한 MSA 연결:** 메시징·네트워크·배포 비용 때문에 실험 목적을 흐릴 수 있다. 실제 이벤트 통합이 학습 목표로 선택될 때 별도 설계한다.

## 결과와 제약

**사용자가 확정한 것은 저장소 단위와 독립 애플리케이션 여섯 개 및 각각의 학습 목적이다.** 구체적 요구사항·데이터 모델, 모듈별 기술 스택, 순서·완료량, 저장소명, CI·배포 전략, 예시 폴더 위치는 **미확정**이다.

이 결정은 2026-11-19의 이전 **proposed** 검토안을 사용자 승인으로 **accepted**로 승격한 것이다. 이전 논의와 제안·기각 대안의 경위는 월별 이력에 보존한다.

## 구현 및 검증

실제 GitHub 신규 저장소·Wiki·멀티 프로젝트 빌드·Spring Boot 앱·테스트/부하 실험·배포는 아직 **생성 또는 검증되지 않았다**. 도구의 공식 문서는 구현 형태의 참고이며 코드 동작 검증과는 다르다.

## 출처와 결정 경위

같은 날 사용자가 "각각 독립적으로 실행되는 여섯 개의 Spring Boot 학습 애플리케이션을 하나의 저장소에서 관리"하는 목적을 직접 명시하였다. 기록은 공개 가능한 합의 내용만 포함한다.
