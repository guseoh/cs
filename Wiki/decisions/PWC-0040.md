# AUTH-002는 세션 API·CSRF 전달·credential 최소 계약을 제안했다

## Context / status
2026-07-10 #30은 ARCH-006의 DR1~DR3를 메우는 Decision Proposal이다. session/CSRF/HttpOnly/memberId/BCrypt/API JSON은 기존 승인 입력이지만 아래 세부값은 Recommended였으며 #30 병합 자체로 승인되지 않는다. 후속 AUTH-003 승인은 [PWC-0007](PWC-0007.md)에서 별도 추적한다.

## DR1 — API candidate
POST login/email+password → 200 memberId, POST logout → 204, GET me → 200 memberId, GET csrf → 200 token/no-store의 네 경로를 /api/auth 아래 제안했다. INVALID_CREDENTIALS/AUTH_REQUIRED/ACCESS_DENIED/CSRF_INVALID와 입력 VALIDATION_FAILED를 구분했다. 없는 email/틀린 password는 동일 오류, fieldErrors는 비필드 오류에 빈 배열이다. CSRF는 인증 검사보다 먼저 403이 될 수 있다.

대안은 204만 반환(주체 별도 확인), username 복합 로그인(범위 증가), 기본 form redirect(API JSON과 충돌), DELETE session logout(추가 통합 조정)이다. 가입·rate limit·계정 잠금은 미포함이라 공격 방어 완료가 아니다.

## DR2 — CSRF and cookie candidate
HttpSessionCsrfTokenRepository, GET /api/auth/csrf JSON token, X-CSRF-TOKEN header, _csrf parameter, FE 메모리 보관을 추천했다. 전용 JS-readable CSRF cookie 없이 login 전 획득→성공 후 재획득→logout 후 폐기하며 비멱등 POST는 자동 replay하지 않는다.

대안 CookieCsrfTokenRepository는 SPA 연동이 편하지만 cookie/request handler·재발급 비용, 응답 header는 노출/CORS 계약 비용이 든다. CSRF 비활성화는 상위 승인과 충돌한다. 익명 csrf 호출도 session 저장 비용이 들고 새로고침 뒤 재획득이 필요하다.

JSESSIONID/HttpOnly/Lax, HTTPS Secure·local HTTP 예외, host-only·Path /, persistent Max-Age 없음·idle 30m, 로그인 changeSessionId·logout 정리를 후보로 제안했다. same-origin 우선이며 cross-site None+Secure/CORS는 별도 결정이다. 이 cookie 세부값을 ARCH-006의 기존 승인으로 소급하지 않는다.

## DR3 — identity and seed candidate
최종 추천은 ASCII email의 local-part case 보존·domain만 소문자화·ascii_bin unique와 충돌 실패다. 앞뒤 ASCII space/tab만 제거하고 provider alias/점/+tag 통합, Unicode/IDN/SMTPUTF8은 미도입이다. email 254자, password_hash VARCHAR(100) NOT NULL, principal은 Entity 없이 memberId를 제안했다. 100자는 BCrypt와 encoder prefix를 수용하는 여유이며 cost는 측정 전 미확정이다.

대안 CHAR(60)은 prefix/encoder 변경 시 migration 비용, credential 별도 테이블은 join/model 비용, 전체 소문자화는 서로 다른 local-part를 합칠 위험, production V1 고정 회원은 credential/환경 데이터 영구 결합 위험이 있다. test fixture는 격리 DB에서 hash를 만들고 local-only bootstrap은 운영에서 꺼야 한다.

## Review and evidence limits
리뷰 4건 뒤 전체 email 소문자화에서 위 경계로 수정했고, CSRF 성공 전용 body의 token은 허용하되 로그/URL 비노출이라는 예외를 정렬했다. 기존 npm moderate 2건은 next→postcss advisory에 대한 당시 보고로 담당/후속을 연결했으며 현재 취약점 상태를 재판정한 것은 아니다.

최신 조회 main caad5233269f52ccd31f6e93e54c77a464766b36에서도 원본 제목의 Decision Proposal을 확인했다. 실제 cookie/CSRF/DB 통합 검증은 구현 전이라 없었고 로컬 Java25 부재도 보고됐다. [상세 #30](../history/pawcycle-source-ledger/batch-021-030.md)을 따른다.
