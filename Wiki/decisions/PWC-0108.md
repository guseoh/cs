# Checkout capacity는 고정 VU 단계 부하와 workload별 경계로 판정한다

## Context

독립 SKU Checkout 의 20 RPS 실행에서 dropped 가 남았지만, Hikari 증설은 유효한 개선 근거를 만들지 못했다. 요청별 SKU 를 분리한 결과로 인기 SKU 의 동시 구매 비용을 대신 판단할 수도 없었다.

## Decision

120 VU 와 Hikari10을 고정하고 5→10→15→20 RPS 를 각 30초 예열·120초 측정한다. 오류·dropped·deadlock·재시작/OOM·fixture 불일치·actual RPS 98% 미만이면 더 높은 단계를 중단한다. 지연시간에 임의 SLA 를 만들지 않으며 Hikari pending 을 root cause 로 곧바로 귀속하지 않는다. shared-SKU 실험은 같은 runtime 에서 새로운 isolated20 control 을 먼저 통과해야 한다.

## Alternatives and interpretation

VU 상한을 계속 늘리거나 pool 부터 재증설하는 안, 이전 Slice 의 control 재사용, 여러 tuning 동시 적용을 제외했다. 계측만으로 원인을 특정하지 못하면 NO_CHANGE/INCONCLUSIVE 가 정상적인 결과다.

## Consequences and limits

장점은 workload 차이와 원인 후보를 나누는 것이다. 단일 local host·120초 관측은 Production 이나 장시간 용량을 보증하지 않는다. 자원 수집 자체의 실패와 image/source 일치는 별도 gate 가 필요하다.

## Implementation and verification

#334는 독립 SKU 네 단계 stable, 하한 ≥20 RPS·knee 미관측·NO_CHANGE 였다. #334의 후속 리뷰에는 불완전 자원 수집을 stable 로 허용하는 gate, 무제한 monitor join, runtime image/source 결합 지적이 남아 있다. #336은 shared5 stable 뒤 shared10 충돌을 수정하여 After10 성공했지만 상위 15/20은 미측정이다.
