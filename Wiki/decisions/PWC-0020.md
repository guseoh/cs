# AI 호출은 DB 트랜잭션 밖으로 빼고 저장 전에 최신 리뷰를 검증한다

## Context
[Issue #437](https://github.com/guseoh/pawcycle-commerce/issues/437)의 기존 ReviewSummary·ProductComparison은 read-only DB transaction 안에서 느릴 수 있는 외부 AI 호출을 수행했다. readOnly라고 해서 응답 대기 중 transaction이 닫히지 않는다. 또한 리뷰를 읽어 생성한 AI summary가 늦게 돌아와 그사이 변경된 최신 리뷰의 캐시를 덮어쓸 수 있었다.

## Decision
[PR #440](https://github.com/guseoh/pawcycle-commerce/pull/440)은 필요한 리뷰/facts/facets의 짧은 read snapshot transaction을 분리하고 AI invoke 시 실제 DB transaction이 없도록 한다. ReviewSummary의 결과 저장 전에는 **현재 visible review 전체에 대한 locking current read 및 fingerprint 일치 여부**를 검증하고 일치할 때만 atomic upsert한다. 오래된 결과면 stale cache update를 거부해 UNAVAILABLE을 반환한다.

## Rejected alternatives
- 메서드 전체 readOnly transaction 유지: provider 대기 동안 lock/connection·transaction 경계를 유지한다.
- Annotation만 제거하고 AI 결과를 무조건 저장: 데이터 snapshot·stale write 문제는 해결하지 못한다.
- 새 Queue/Redis worker로 해결: 현재 필요한 최소 DB·외부 I/O 경계를 넘어선다.

## Consequences and constraints
최신 fingerprint 확인용 locking read는 DB 부하·잠금 대가를 추가할 수 있다. 같은 snapshot에서 나온 두 AI 요약 중 마지막 저장 문자열은 다를 수 있지만 오래된 리뷰 상태를 최신으로 덮지 않도록 한다. 데이터·API/schema·실제 AI Provider 설정을 바꾸지 않는다.

## Implementation/verification
[PR #440](https://github.com/guseoh/pawcycle-commerce/pull/440)은 2026-10-21 MySQL 8.4.11 회귀에서 AI 호출 중 활성 트랜잭션 없음, AI 대기 중 다른 리뷰 write, stale overwrite 방지 확인 후 병합됐다. [PR #441](https://github.com/guseoh/pawcycle-commerce/pull/441)은 독립 DB CONNECTION_ID와 InnoDB data_locks/data_lock_waits의 실제 대기를 검증하도록 보강했다. 초기 테스트 fixture 오류와 Windows AuthSmoke timeout 이력은 해당 PR에서 기록·분리했다. 외부 AI Production 실행이나 비용 검증은 수행하지 않았다.
