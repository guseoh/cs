# Phase 9은 특정 코드 hotspot을 입증하지 못해 추가 최적화 NO CHANGE로 종료한다

## 당시 판단

[PR #201](https://github.com/guseoh/pawcycle-commerce/pull/201)과 [최종 결론 문서](https://github.com/guseoh/pawcycle-commerce/blob/4be4d17c0a9504e0fa01c0bcc4a01fa63c597eba/docs/performance/PERF-PH9-014-phase9-conclusion.md)는 CPU가 중요한 부분 원인이고 CPU2에서도 포화가 남는다는 사실과, 특정 Java 코드의 책임을 구분했다. PH9-011은 실제 workload 일부가 진행됐지만 정상 aggregate/diagnostic-summary가 없고 JFR Duration 0s·ExecutionSample 0이어서 hotspot attribution에 사용할 수 없었다. 이를 근거로 추가 애플리케이션 최적화는 **NO CHANGE**, profiling은 **Outcome C — evidence insufficient**로 종료했다.

## 검토한 대안과 대가

- Entity snapshot과 최종 DTO의 중복 materialization을 없애면 allocation을 줄일 수 있지만, 짧은 read transaction과 계층 분리를 위해 만든 경계를 다시 결합할 수 있다.
- 반복 loop를 합치는 것은 가능하지만 fixture cardinality와 해당 단계 CPU 비중을 측정하지 않아 잔여 포화의 주요 해법으로 정당화할 수 없다.
- Repository projection·custom serialization은 entity 비용을 줄일 가능성과 query/API/framework 계약 변경 위험이 함께 있다. 유효 stack/allocation 근거가 없어 구현하지 않았다.

잔여 병목이 해결됐다는 뜻도, 과거 모든 Phase 9 코드 변경을 되돌렸다는 뜻도 아니다. 기존 transaction 축소는 유지된 상태에서 마지막 추가 최적화만 하지 않은 결정이다.

## 실패와 후속 조건

300초 startup recording에 대해 helper는 non-empty file만 검사했다. 파일 존재·copy·summary command 성공은 recording 종료와 유효 sample을 증명하지 않는다. 다음에는 completion-aware dump/stop·duration/event coverage·child failure metadata를 먼저 검증해야 한다. 기존 PH9-011 one-shot은 재실행하지 않으며 새 profiling 작업·실행 승인은 별도다. 세부 교훈은 [PWL-0002](../lessons/PWL-0002.md)에 연결한다.

## 검증 수준

원본은 단위 9개 통과와 로컬 통합 7개의 datasource 환경 실패를 보고한다. correction commit은 문서-only CI에서 Backend/MySQL도 skipped됐으므로 이번 PR의 2-query·JSON 통합 계약을 미검증으로 남겼다. 최종 Actions job metadata로 해당 skip을 대조했다. 외부 review collection은 0개이며 CodeRabbit 안내 댓글은 리뷰 미실행 상태다.

이번 Wiki 조사는 공개 문서·commit correction·당시 helper와 reader 코드·CI metadata를 읽은 것이며 JFR/k6·제품 테스트·운영을 재실행하지 않았다. 원시 JFR과 실제 과거 자원 상태는 재검증하지 않았다.

## 연결과 재개

[원본별 처리와 manifest](../history/pawcycle-source-ledger/batch-201-201.md)에 SHA·검증·미확인을 남겼다. #195의 현재 closure는 확인되지만 이 PR과의 직접 종료 원인은 미확인이다. Phase 10의 구체적인 후속 선택은 #202부터 순서대로 확인한다.
