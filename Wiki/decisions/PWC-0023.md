# Backend 일반 Runtime의 직접 JdbcTemplate은 제거하되 Native SQL과 증명된 잠금 의미는 유지한다

## Why the boundary was revisited
PawCycle의 초기 Commerce·Subscription은 명시 SQL, JPA, application transaction, JSON/DTO 구성과 유지보수 경계가 혼재했다. 변경 범위·typed API·테스트 가능성과 raw DB result 노출을 줄이려는 Architecture V2 작업이었지만, SQL을 단지 JPA API로 감싼다고 MySQL의 `FOR UPDATE`, missing-row/gap, unique/CAS, microsecond timestamp, provider I/O의 의미가 같아지는 것은 아니다.

## Approved decision
[Master #339](https://github.com/guseoh/pawcycle-commerce/issues/339)의 **2026-10-08 사용자 승인 수정**은 일반 Runtime(customer, scheduler, admin, operations, recommendation, subscription)의 직접 `JdbcTemplate` owner를 **0**으로 줄이는 것이다. JPA/Spring Data Repository를 기본 영속성 경계로 삼되, MySQL 고유 `UPSERT`, `FOR UPDATE`, conditional UPDATE, lock/ordering·정밀 SQL protocol은 **EntityManager Native SQL 또는 해당 feature persistence로 근거를 남겨 유지**한다. Legacy 직접 JDBC를 Native SQL로 이름만 바꾸는 활동이나 모든 Native SQL 0 목표는 승인하지 않았다.

Maintenance/bootstrap/migration/performance 등 비일반 Runtime 소유자는 실제 profile·caller·실행 경계로 격리하고 별도 허용한다. Package dependency·raw 반환 경계·Transaction owner를 검증하고, 단일 구현에 의미 없는 interface를 강제하지 않는다. Querydsl도 bulk mutation/JPA 영속성 컨텍스트의 stale/flush 차이를 검증하며 도입한다.

## Alternatives and costs
- **전부 JPA Entity CRUD로 일괄 교체:** 잠금 순서·gap/unique/SQLState/INSERT SELECT·JPA flush timing을 바꿀 수 있다.
- **JDBC/Native SQL을 기술 부채라는 이유로 무조건 제거:** 검증된 특수 SQL 형태와 성능/정합성을 잃을 수 있다.
- **Adapter 통합·제거 자체를 성과로 삼기:** 책임 경계가 이미 안정적이면 변경량과 회귀 비용만 늘어난다.
- **Architecture 정적 Guard를 완전한 데이터 흐름 증명으로 해석:** reflection/간접호출·동적 의존성까지 입증하지 않는다.

## Implementation and verification
[PR #382](https://github.com/guseoh/pawcycle-commerce/pull/382)는 Cancellation/Return/Refund/Quick Reorder의 **52 SQL 문장**의 조건·순서·잠금 footprint를 Native 경계에서 보존하며 직접 JDBC owner를 제거했다. 같은 MySQL 8.4에서 frozen JDBC 참조와 statement count, lock wait, UTC/Seoul, rollback을 비교했다. 2026-10-21 [PR #438](https://github.com/guseoh/pawcycle-commerce/pull/438)과 **사용자 공식 Closure 댓글**은 일반 Runtime JdbcTemplate 0, 격리 JDBC owner 9, application→api 0, persistence→api 0, runtime→maintenance 5 intentional KEEP, **21개 PersistenceAdapter 전부 KEEP**를 저장소 범위에서 완료로 판정했다. 추가 MySQL Checkout 만료 2건·Delivery 8건 rollback/경합 테스트 및 physical lock 5/5가 완료됐다.

해당 완료는 **Repository Implemented/Verified/Merged**에 한한다. 네 개의 opt-in diagnostic SKIP을 PASS로 바꾸지 않고, 운영 DB·실제 Provider·Production 데이터 적용과 별개다. 과거 [PWC-0006](PWC-0006.md)의 JDBC Store 선택은 역사 기록으로 유지한다.
