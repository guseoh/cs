# 초기 인증은 사용자 승인 세션·CSRF 계약을 기준으로 구현한다

## Context
구독 생성과 내 구독 조회는 로그인과 소유권 검증을 요구한다. 초기 기술 설계에서는 인증 API, Session cookie, CSRF 전달, 계정·비밀번호 최소 데이터가 미결정이었다. [AUTH-002](https://github.com/guseoh/pawcycle-commerce/blob/main/docs/adr/AUTH-002-session-authentication-contract-proposal.md)는 이를 DR1~DR3 결정 요청으로 제안했으며 [AUTH-003](https://github.com/guseoh/pawcycle-commerce/blob/main/docs/adr/AUTH-003-session-authentication-approved-inputs.md)은 사용자가 2026-07-10 추천 계약을 승인한 입력이다.

## Decision
첫 Backend 인증 구현은 AUTH-003에 승인된 서버 측 Session, CSRF token 전달·검증, Session cookie 경계와 최소 credential 저장 계약을 따른다. 인증 성공 후에는 승인된 Session 전략과 `SecurityContext` 저장·복원 흐름을 사용하고, 보호되는 구독 API와 개별 구독 소유권을 별도로 검증한다. 정확한 HTTP endpoint, cookie 설정값과 예외 응답 의미는 중복 기술하지 않고 AUTH-003에 위임한다.

## Rejected alternatives
- **제안 문서 AUTH-002의 내용을 구현 전에 무승인 확정:** 사용자 승인 전에는 proposal일 뿐이므로 채택하지 않는다.
- **JWT·OAuth2를 기술 목록 목적으로 선도입:** AUTH-003의 초기 승인 범위를 넘어 해당 도입을 이 기록으로 추정하거나 승인하지 않는다.
- **로그인 성공만으로 모든 구독 조회를 허용:** 개인 구독 소유권 계약과 충돌한다.

## Consequences and constraints
브라우저 요청에는 CSRF와 Session·Cookie 운영 책임이 따른다. 로그인 후 복귀는 내부 안전한 GET 경로로 한정하고 외부 URL 또는 이전 POST 자동 재실행을 허용하지 않는 초기 제품 계약과 맞춰야 한다. 후속 `MemberAuthenticationProvider` 책임 분리([ARCH-010](https://github.com/guseoh/pawcycle-commerce/blob/main/docs/adr/ARCH-010-authentication-provider-ownership.md))는 별개 결정이다.

## Implementation/verification
[PR #34](https://github.com/guseoh/pawcycle-commerce/pull/34)은 2026-07-12 병합됐다. 이는 승인된 인증 계약의 저장소 구현 근거이며, 오늘의 Production 로그인/CSRF 정상 동작을 다시 검증했다는 뜻은 아니다.

## #30 최초 세부 제안과 승인 구별

[AUTH-002/PWC-0040](PWC-0040.md)에 DR1 API·DR2 CSRF/cookie·DR3 최소 credential 추천과 대안을 보존했다. #30은 Decision Proposal이며 전체 email 소문자화 추천은 리뷰 후 ASCII local-part case 보존/domain 소문자화로 바뀌었다. 이 초안 correction은 후속 AUTH-003 승인과 별도 사건이며, 당시 [#21–#30 배치](../history/pawcycle-source-ledger/batch-021-030.md)는 #31/#34 심사 전이었으며 아래 새 배치에서 후속 근거를 보강했다.

## #31 승인 → #33 기반 → #34 구현 → #38 조건부 QA

2026-11-04 [번호순 배치](../history/pawcycle-source-ledger/batch-031-040.md)에서 네 원본의 전체 변경파일·공개 review·최종 head CI metadata를 대조했다. #31은 email 거부 조건과 session/email 생명주기 Deferred 누락을 복원했고 AUTH-002의 Proposal 상태는 유지했다. #33의 Security/Flyway 기반에는 실제 인증 endpoint가 없었으며 #34가 session strategy·SecurityContext 명시 저장과 승인 logout을 구현했다.

#34는 기본 /logout 비활성화·최대 email 경계·credential 실패 BCrypt 1회 비교를 보강했다([PWL-0014](../lessons/PWL-0014.md)). email 문법을 승인 밖의 domain label 정책까지 확대하자는 review는 미반영했다. #38의 QA는 안전 응답과 로그 stack trace 테스트가 임의 message의 redaction을 보장하지 못한다는 한계로 **조건부 통과**였다([PWL-0015](../lessons/PWL-0015.md)). 현재 배포 로그 조건이 해소됐다는 근거는 이번 배치에 없다. 최종 head CI 성공은 과거 기록의 조회이며 Production 재검증이 아니다.
