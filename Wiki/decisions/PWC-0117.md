# Cleanup vendor DML과 격리 유지보수 JDBC는 실행 의미로 유지한다

## Context

Cleanup 은 시간 cutoff·bounded repair/delete·transaction·metrics 가 결합돼 있고 유지보수 9도구는 일반 Runtime 과 다른 명시 실행 계약을 가졌다.

## Decision

네 MySQL UPDATE/DELETE 의 predicate·ORDER BY·LIMIT·affected row·repair grace 를 기존 SubscriptionNativeSql/EntityManager 경계로 옮기고 JDBC4.2 LocalDateTime 직접 바인딩을 유지한다. maintenance/bootstrap/migration/performance9 owner 는 실제 caller·Bean/Profile/Property/CLI/Runner/HTTP/Scheduler·opt-in 을 조사해 격리 계약이 유효하면 JDBC KEEP 한다. runtime-maintenance5 edge 는 의도적 실제 연결로 남긴다.

## Alternatives and interpretation

SELECT 후 여러 delete 로 분해, Native SQL0 목표, 도구까지 기계적 JPA 변환, 빈 baseline 을 만들기 위한 caller 이름 변경·blanket 예외를 제외했다.

## Consequences and limits

freeze boolean 은 실제 외부 source-write freeze 의 증명이 아니다. importer/migration/부하를 실행할 권한을 주지 않으며 일반 Runtime0은 T12에서 따로 확인해야 한다.

## Implementation and verification

#370 Runtime16→15/전체 25→24/격리 9. frozen JDBC·batch1/2·microsecond·rollback/metrics·격리회귀·CI/physical5 PASS 를 확인했다. 전체 Seoul suite 와 실제 운영 cleanup 은 미실행이다. #371은 JDBC0 달성 이후에도 Architecture 전체 감사 Gate 를 별도로 유지했다.
