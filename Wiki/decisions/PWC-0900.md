# OCI A1 확보는 조회·알림과 수동 생성으로 분리한다

## Context
OCI Tokyo `VM.Standard.A1.Flex`의 2 OCPU / 12 GiB 용량 부족 상황에서 서버 확보 기회를 놓치지 않으려면 짧은 주기의 용량 확인이 필요하다. 그러나 용량 조회(Compute Capacity Report), 실제 VM 생성(Provisioner), 운영 인프라 변경은 서로 다른 권한·비용·실패 경계를 가진다. 이전 [PWC-0002](PWC-0002.md)와 [PR #496](https://github.com/guseoh/pawcycle-commerce/pull/496)은 보호 장치를 갖춘 Provisioner의 **저장소 구현**을 남겼을 뿐, 활성화·인스턴스 생성의 승인은 아니었다.

## Decision
2026-11-03 승인된 현재 운영 모드는 **report-only / monitor-and-notify**다. 도쿄 A1 용량을 조회하고 실제 `AVAILABLE` 전이에만 기존 Discord·GitHub Issue 알림을 보낸다. 관측 후 VM 생성은 사용자가 콘솔에서 별도로 판단한다. 항상 무료(Always Free) 제약과 Cloud·비용·운영 변경의 별도 승인 게이트를 유지한다. **자동 A1 생성, Provisioner IAM 활성화, systemd Timer 실행, PAYG 전환은 이번 모니터링 작업의 범위가 아니다.**

## Alternatives and trade-offs
- **기존 Python Auto Provisioner 활성화:** 요청을 반복해 확보 기회를 높일 수 있지만 실행 Host, 전용 IAM, 이미지, 비용·중복 생성·복구 게이트가 필요하다. Preflight는 `NOT_RUN`; 활성화하지 않는다.
- **Terraform 반복 apply:** 재현 가능한 인프라 구성 관리에는 적합하지만 분 단위 감시 스케줄러가 아니며 반복 apply의 실행 Host·상태·권한·재시도 위험을 별도로 해결해야 한다. 5분 모니터링 문제의 최소 해결책으로는 선택하지 않는다. 장기 OCI IaC 도입 가능성까지 기각한 것은 아니다.
- **용량 미확보에 매번 알림:** 경보 피로도가 높아진다. 정상적인 `OUT_OF_HOST_CAPACITY` 결과는 조회 성공으로 기록하되 긴급 용량 알림은 보내지 않는다.

## Consequences and constraints
용량 보고의 `AVAILABLE`은 특정 시점의 관측일 뿐 예약·VM 생성 성공 보장이 아니다. 실제 A1을 만들기 전 해당 계정·compartment의 기존 인스턴스, Shape, 이미지 아키텍처, 네트워크, 무료 한도와 비용 조건을 독립 확인해야 한다. 기존 GitHub Actions의 Cron 설정과 모니터링 성공률도 별개의 문제다.

## Implementation / verification
[2026-11-03 기준 Runbook](https://github.com/guseoh/pawcycle-commerce/blob/caad5233269f52ccd31f6e93e54c77a464766b36/docs/runbook/oci-a1-capacity-watch.md)은 수동 생성 정책을 명시한다. [PR #502](https://github.com/guseoh/pawcycle-commerce/pull/502)는 새 스케줄러의 **미병합 Draft / 기본 비활성 구현**이다. 성공한 개별 Actions 실행에서 `OUT_OF_HOST_CAPACITY` 조회는 관찰됐지만, 5분마다 실제 조회가 지속됐거나 Cloudflare 운영 전환이 완료됐다는 증거는 없다. Provisioner Preflight/실행도 이 기록에서 수행하지 않았다.
