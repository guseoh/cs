# 고립된 결제 PROCESSING은 query-only 우선의 단계적 수동 복구로 다룬다

## Context
일반 결제 confirm은 NORMAL/PROCESSING을 먼저 DB에 commit하고 Provider를 트랜잭션 밖에서 호출한 뒤 별도 DB 트랜잭션에서 주문·재고·결제 완료 효과를 확정한다. [Issue #414](https://github.com/guseoh/pawcycle-commerce/issues/414) 및 [PR #415](https://github.com/guseoh/pawcycle-commerce/pull/415)의 disposable MySQL + Fake Provider 중단 실험에서는 Provider 호출 전 중단, Provider 성공 뒤 최종화 실패 시 PROCESSING과 예약이 남을 수 있었다. 이는 실제 Toss/Production 장애 실증은 아니다.

## Decision
[2026-10-22 사용자 승인](https://github.com/guseoh/pawcycle-commerce/issues/417#issuecomment-6333149778): 관리자가 의심 Payment를 명시적으로 고른 뒤 **Provider query-only 조회**를 실행한다. 조회 결과만으로 Payment/Order/Inventory/Cart/Coupon 상태나 예약을 바꾸지 않는다. Provider 주문번호·결제 키·금액 identity가 정확히 일치하는 DONE, 확정 실패, 진행 중, 모호성/조회 불능을 구분한다. 404 등 4xx, 5xx, timeout, 신원 불일치, 미발견은 일괄 FAILED로 간주하지 않는다.

확정 DONE도 활동 중 worker가 없다는 운영 fence, fresh DB 재검증·lock·한 번만 완료되는 원자성 및 **별도 승인된 Phase 2 구현**이 있어야 로컬 finalization 후보가 된다. 자동 재승인, 강제 READY 전환, 단순 경과시간에 의한 orphan 판정은 선택하지 않았다.

## Rejected alternatives
- 조회 오류 즉시 FAILED/예약 해제: 외부 승인이 성공했을 가능성을 제거하지 못한다.
- POST confirm 자동 재시도·재결제: 이중 승인/부작용 위험을 만든다.
- DB 행 잠금만으로 worker fencing 보장: 이미 진행 중인 외부 I/O를 막지 못한다.

## Consequences and constraints
신뢰성 대신 추측으로 완료시키지 않으므로 운영자의 수동 조사와 예약 장기 보존 비용이 남는다. 불명확한 Provider 상태와 운영 fence는 STOP 조건이다.

## Implementation/verification
[PR #450](https://github.com/guseoh/pawcycle-commerce/pull/450)의 query-only·Provider 조회 오류 분류는 2026-10-23 **Repository Implemented/Verified/Merged**이고 Fake Provider/격리 MySQL 회귀가 존재한다. 그러나 NORMAL/PROCESSING 실제 최종화·active worker fencing은 미구현이다. [Issue #417](https://github.com/guseoh/pawcycle-commerce/issues/417)은 Open이며 Phase 2 설계가 곧 실행 승인은 아니다. 실제 Provider, 운영 DB 또는 Cloud 실행은 이번 Wiki 작업에서 하지 않았다.
