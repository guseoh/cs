# 백엔드·인프라 코드는 사용자가 직접 구현하고, 스크립트·문서는 AI가 작성한다

> **대체됨(2026-11-19):** 첫 적용 대상에서 AI가 준 정답 코드의 결함이 드러나([PWL-0057](../lessons/PWL-0057.md)), 사용자가 "AI가 구현하고 사용자는 완성 코드를 검토하며 학습"으로 바꿨다. 현재 기준은 [PWC-0141](PWC-0141.md)이다. 아래는 당시 결정 원문이다.

## Context

같은 날 앞서 정한 [PWC-0137](PWC-0137.md)은 "AI는 측정, 사용자는 해석·개선"이었다. 이후 사용자는 분담을 두 번 다시 조정했다.

1. AI가 측정·설계와 **정답 코드·방법을 보여 주고**, 사용자가 직접 구현한다. 지금까지는 AI가 구현까지 했지만, 프로젝트 이해와 학습, 설계·코드 검증을 위해 사용자가 직접 진행한다.
2. 그중 정답 코드를 보고 직접 구현하는 대상은 **백엔드·인프라 코드로 한정**한다. k6·Python 같은 스크립트와 JS는 AI가 작성한다. 사용자는 Java/Spring 백엔드 개발자 취업 준비생이라 핵심 역량에 집중하는 편이 낫다고 판단했다.

AI가 검토하며 보강을 제안했고 사용자가 받아들였다. 백엔드 테스트와 Flyway migration SQL도 사용자 범위에 넣는다.

## Decision

| 대상 | 구현 | 방식 |
| --- | --- | --- |
| 백엔드 Java/Spring 코드, 백엔드 테스트(JUnit·통합), Flyway migration SQL | 사용자 | AI가 정답 코드와 이유를 **채팅에만** 보여 준다(파일을 만들지 않는다). 사용자 구현 뒤 AI가 diff를 리뷰한다 |
| 인프라 코드(compose, nginx, Dockerfile, 알림 규칙) | 사용자 | 위와 같다. 변경이 작으면 따라 쓰는 수준으로 두고, "왜 이 설정인가" 설명에 무게를 둔다 |
| 스크립트(k6 JS, Python 실행기, PowerShell·bash) | AI | 저장소에 직접 작성 |
| 문서·보고서·Wiki, 측정 실행, 설계, 리뷰 | AI | 직접 작성·실행 |

- 한 PR에 둘이 섞이면 사용자의 백엔드·인프라 커밋과 AI의 스크립트 커밋을 나눠, git 이력에서 작업자가 구분되게 한다.
- 병합 위임, 리뷰 확인, 운영 실행 승인 경계는 기존 규칙 그대로다.

## Rejected alternatives

- [PWC-0137](PWC-0137.md) 그대로(AI는 측정만, 개선은 힌트만 주고 사용자가 처음부터 구현): 사용자가 정답 코드를 보고 이해하는 쪽이 학습과 검증에 낫다고 판단했다.
- 모든 코드를 사용자가 구현: 측정용 스크립트는 면접 핵심 영역이 아니라 효율이 낮다.
- 모든 코드를 AI가 구현(이전 방식): 백엔드 판단 경험이 사용자에게 남지 않는다.

## Consequences and constraints

- 4단계 G-2(k6·실행기·보고서)는 모두 스크립트·문서라 AI가 구현했다([PWK-0007](../knowledge/PWK-0007.md)).
- 처음으로 사용자가 직접 구현하는 코드는 H 측정 이후 5단계 병목 개선(백엔드 코드)부터 나올 가능성이 크다.
- 포트폴리오에서는 "측정 도구는 AI 도움, 백엔드·인프라 구현은 직접"으로 분담을 밝힐 수 있고, git 이력이 이를 뒷받침한다.

## Implementation/verification
