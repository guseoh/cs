# 구독 명령의 행 잠금·버전 CAS·고유 제약을 함께 보존한다

## Context
2026-08-02 [ARCH-007](https://github.com/guseoh/pawcycle-commerce/blob/main/docs/adr/ARCH-007-second-mvp-subscription-consistency.md)은 `If-Match`와 optimistic version·unique 제약을 먼저 검증하며 비관적 DB 잠금은 추가하지 않는 **Proposed 초안**이었다. 이 원안은 Accepted로 승격되지 않았다. 반면 실제 구현은 동일 구독에 비관적 행 잠금을 사용한다. [PR #87](https://github.com/guseoh/pawcycle-commerce/pull/87)의 2026-08-02 신규 `V2SubscriptionService` 코드는 `lockedOwnedSubscription(... FOR UPDATE)`와 `UPDATE subscriptions SET version=version+1 WHERE id=? AND version=?`를 함께 도입했다. 이 PR은 **현재 확인 가능한 최초 구현 근거**이며 당시 Backend/MySQL 회귀와 병합 기록이 있다. 그러나 ARCH-007의 '비관적 lock 추가하지 않음' 초안에서 바꾼 이유를 별도 승인 ADR/대화로 확인하지는 못했다.

## Decision
[Issue #356](https://github.com/guseoh/pawcycle-commerce/issues/356)은 **2026-10-08 사용자 승인** T09 변경에서 기존 동시성·멱등 동작을 그대로 유지하도록 결정했다. [PR #357](https://github.com/guseoh/pawcycle-commerce/pull/357)은 이를 JPA/Native SQL 경계로 수렴했다. 현재 `SubscriptionCommandApplicationService.command()`는 하나의 `@Transactional` 범위에서 소유 구독 잠금, scope 예약과 성공 replay 우선, `If-Match` version 검사, 상태·회차 mutation, expected-version CAS, history·response 저장을 수행한다. `SubscriptionAggregateQueryPersistence.lockOwnedSubscription()`는 `LockModeType.PESSIMISTIC_WRITE`를 사용한다.

비관적 lock은 동시 실행을 직렬화하지만 HTTP stale 명령 처리까지 대체하지 않는다. 버전 조건부 UPDATE/CAS와 scope/date/pending unique는 독립된 마지막 방어선이다. `JOIN/LIMIT FOR UPDATE`, atomic upsert, DB UTC timestamp 같은 SQL은 JPA 전환으로 lock footprint·원자성이 달라지지 않도록 제한된 Native SQL로 남긴다.

## Rejected alternatives
- **ARCH-007 Proposed를 현행 승인 원본으로 승격:** 실제 lock 사용 및 원본 상태와 충돌한다.
- **모든 CAS를 자동 `@Version`·dirty checking으로 치환:** replay precedence, affected-row, flush 시점이 바뀔 수 있어 T09에서 무조건 선택하지 않았다.
- **`ON DUPLICATE KEY UPDATE`나 JOIN/LIMIT lock을 read-then-save로 분해:** DB 원자성·missing-row/gap lock 범위를 보존한다는 증거가 없다.
- **Redis lock/Kafka를 도입하면서 DB 잠금·제약 제거:** 기존 검증된 계약을 바꿀 별도 요구·승인이 없다. 기술을 영구 기각하는 것은 아니다.

## Consequences and constraints
DB 행 잠금은 lock wait·deadlock의 비용을 동반한다. replay는 stale ETag보다 먼저 판정하고, pending snapshot, 미래 Schedule, command history, version 증가 및 idempotency 결과는 같은 transaction의 성공/실패를 따른다. JPA로 변경해도 lock 순서·SQL 결과·rollback·HTTP/ETag가 같아야 한다.

## Implementation/verification
PR #357은 2026-10-08 병합됐고 frozen JDBC 대비 UTC MySQL 회귀 및 lock footprint 비교·경쟁/rollback 테스트를 보고했다. [현재 parity 테스트](https://github.com/guseoh/pawcycle-commerce/blob/540464a9b875f7bc6bdda11ecf499efdea2e2d43/backend/src/test/java/com/pawcycle/backend/subscription/persistence/SubscriptionCommandPersistenceParityIntegrationTests.java)가 기존 SQL 결과를 비교한다. 이번 Wiki 작업에서는 테스트를 새로 실행하거나 운영 동시성을 실측하지 않았다.
