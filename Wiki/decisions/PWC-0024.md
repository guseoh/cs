# Production Catalog는 startup seed 대신 명시적 검증·확인·one-shot apply로 적재한다

## Problem
MVP4 당시 실제 Production `/api/products`는 empty(0개)였고 로컬 Demo Catalog fixture는 `local-integration` profile에서만 자동 bootstrap 됐다([Issue #231](https://github.com/guseoh/pawcycle-commerce/issues/231)). 앱 이미지를 배포한 것과 고객이 탐색할 Product 데이터가 준비됐다는 것은 다른 상태다. Production startup에 fixture를 자동 연결하면 재기동 시 예상치 못한 재고·상품 데이터 변경이 발생할 수 있다.

## Decision and evolution
2026-08-26 병합 [PR #232](https://github.com/guseoh/pawcycle-commerce/pull/232)는 재사용 가능한 manifest importer를 만들고 **Production startup 자동 seed를 금지**했다. Production에서 명시적 one-shot `validate`는 DB 내용 변경 없이 사전 확인, `apply`는 운영자 명시 action과 **이중 confirmation**을 통과해야 한다. Apply는 하나의 DB 트랜잭션, business-key conflict는 fail-closed, 미완료/postflight 실패는 rollback을 원칙으로 한다.

2026-08-30 병합 [PR #259](https://github.com/guseoh/pawcycle-commerce/pull/259)은 Demo와 V3를 독립 복제하지 않고 Canonical Customer Catalog를 공통 데이터 모델로 정리했다. [PR #260](https://github.com/guseoh/pawcycle-commerce/pull/260)은 기존 기본 target `demo`를 유지하면서 **명시적인 `customer` target**을 추가하고, [PR #261](https://github.com/guseoh/pawcycle-commerce/pull/261)은 Production one-shot shell/Runbook을 이 선택에 연결했다. 검증된 데이터 사양은 Product 100·SKU 166·Brand 10·Customer Category 27 규모이며, **이 숫자를 현재 운영 DB row count로 주장하지 않는다.**

## Rejected alternatives
- **Production startup 자동 적재:** 배포·재기동이 데이터 변형의 트리거가 된다.
- **운영 DB에 임의 수동 대량 SQL 실행:** business-key collision/멱등성/재고 snapshot 검증·재현 경로가 사라진다.
- **같은 manifest 재실행마다 중복 row 생성:** import 멱등성과 mutable Inventory 보존을 어긴다.
- **새 Admin UI/CSV/API ingest를 이 작업의 필수조건으로 만들기:** 현재 one-shot의 최소 요구·운영 위험을 넘어선다.

## Consequences, evidence and limits
명시적인 승인과 preflight·postflight가 필요하지만 Release 실행과 영구 데이터 변경을 분리한다. [PR #232/#260/#261](https://github.com/guseoh/pawcycle-commerce/pull/261)은 repository 코드·Shell contract·테스트와 Runbook을 병합했다. 이는 실제 Production `validate/apply`와 공개 Catalog 노출 실증을 뜻하지 않는다. 정확한 Production import 시행 여부는 당시의 **별도 운영 실행 기록**이 필요하며, 이번 조사에서는 해당 실행을 새로 검증하거나 누락을 보완한 것으로 주장하지 않는다. 현재 기존 상품 데이터가 있다면 재적용은 별도 고위험 변경이며 자동 반복하지 않는다.
