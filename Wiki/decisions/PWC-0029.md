# 최초 Backend는 공개 상품·Session 로그인·Flyway V1만 제한 승인했다

## Historical context
처음의 ARCH-001·AUTH-001·API-001·DATA-001/002·FOUNDATION-000은 대다수 **Proposed** 상태였다. [ARCH-005/#28](https://github.com/guseoh/pawcycle-commerce/pull/28)은 후보를 제시했지만 병합만으로 전체 승인이 되는 문서는 아니었다. [ARCH-006/#29](https://github.com/guseoh/pawcycle-commerce/pull/29)은 사용자가 승인한 초기 Backend 범위를 별도로 고정했다. 이후 [AUTH-003/#31](https://github.com/guseoh/pawcycle-commerce/pull/31)에서 DR1~DR3를 추가로 승인했다.

## Approved implementation inputs — ARCH-006
1. **제품 수직 범위:** 공개 상품 목록 GET `/api/products`, 공개 상세 GET `/api/products/{productId}` 및 최소 Session 회원 로그인/로그아웃/현재 회원 식별. 구독 생성·결제·재고·배송은 아직 제외.
2. **필수 기술 의존성:** Spring Data JPA, MySQL JDBC Driver, Flyway, Spring Security, `spring-security-test` 및 Java 25 빌드·MySQL CI. 불필요한 의존성 추가 금지. Testcontainers/OpenAPI 자동화·JWT/OAuth2 라이브러리는 DEFER.
3. **DB:** DATA-001/002에서 `members`·`products`·`skus` 세 테이블과 Product 1:N SKU만 구현 입력으로 선택한다. Flyway 최초 V1 migration과 최소 PK/FK/unique/CHECK/index를 갖추되, 장래 Subscriptions와 가격·재고·배송 데이터는 아직 만들지 않는다.
4. **보안:** 서버 관리 Session·SecurityContext, 인증 성공 시 세션 생성 및 실패 시 인증 세션 금지, CSRF 활성화, 상태 변경 POST 보호, HttpOnly cookie, 최소 memberId principal, BCrypt. JWT/session hybrid·개발용 인증 우회는 미채택.
5. **HTTP·계층:** 공개 상품 GET은 인증 없이 접근, 인증/인가 실패는 `/api/**`에서 401/403 JSON, 공통 `code/message/fieldErrors`. 당시 ARCH-001/ARCH-003 package 경계는 **승인된 일부 구현 입력으로만** 참조했다.
6. **운영/검증:** MySQL 환경 변수는 key/placeholder만 저장하고 Secret 실제 값은 저장소에 기록하지 않는다. CI의 DB·Flyway·Security·API 회귀를 통과해야 한다. 구현 시 논리 설계와 물리 DDL 충돌이 확인되면 STOP하고 별도 승인을 받는다.

## Decision Required and rejected expansion
[ARCH-006](https://github.com/guseoh/pawcycle-commerce/blob/540464a9b875f7bc6bdda11ecf499efdea2e2d43/docs/adr/ARCH-006-first-backend-implementation-approved-inputs.md)은 **DR1 최소 login/logout/me API, DR2 CSRF 전달, DR3 email/password_hash 식별 계약, DR4 실제 SQL/JPA/profile/CI image 세부**를 아직 구현 전 보완 대상으로 남겼다. [AUTH-003](https://github.com/guseoh/pawcycle-commerce/blob/540464a9b875f7bc6bdda11ecf499efdea2e2d43/docs/adr/AUTH-003-session-authentication-approved-inputs.md)은 DR1–DR3 승인 입력을 기록했지만 ARCH-006의 전체 Proposed 문서 전체를 승인한 것은 아니다. 모든 기술 버전을 `FOUNDATION-000` Proposed 표 하나로 영구 확정하거나 처음부터 복잡한 DB/보안 스택을 도입하는 방식은 당시 선택이 아니었다.

## Verification and historical scope
[PR #29](https://github.com/guseoh/pawcycle-commerce/pull/29)과 [PR #31](https://github.com/guseoh/pawcycle-commerce/pull/31)은 **문서 기반 사용자 승인 입력**이며 실제 Flyway/Authentication/API 구현이 아니다. 후속 [PR #33](https://github.com/guseoh/pawcycle-commerce/pull/33), [#34](https://github.com/guseoh/pawcycle-commerce/pull/34), [#36](https://github.com/guseoh/pawcycle-commerce/pull/36), [#42](https://github.com/guseoh/pawcycle-commerce/pull/42)가 구현 시점을 구성한다. 그 구현·QA 결과는 번호 순 조사에서 별도 판정해야 한다. 지금 적용된 Spring Boot·데이터 계약을 7월 최초 후보 그대로라고 가정하지 않는다.
