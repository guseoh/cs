# 현재 API 문서는 Spring 매핑에서 만든 색인 검사와 REST Docs로 관리하고 springdoc은 보류한다

## Context

API 계약이 MVP 단계별 문서 12개(API-001~012)에 흩어져 있었다. 현재 등록된 전체 엔드포인트 목록은 어디에도 없었고, 사람이 쓴 문서는 코드 변경을 따라가지 못했다. 저장소에는 API 문서 도구가 없었다(Controller 50개, 엔드포인트 141개, MockMvc 테스트 35개).

## Decision

사용자가 2026-11-14에 네 가지 방식을 비교한 뒤 다음을 선택했다.

- **엔드포인트 색인과 어긋남 검사:** `ApiEndpointIndexIntegrationTests`가 Spring이 실제로 등록한 매핑을 읽어 `docs/api/current-endpoints.md`와 비교한다. 다르면 실패하고, system property로 다시 생성한다.
- **Spring REST Docs 점진 도입:** 테스트 전용 의존성 `spring-restdocs-mockmvc`(Boot BOM, 4.0.1)를 추가했다. 공개 상품 API 2개부터 응답 필드를 검증하는 스니펫을 만든다.
- **springdoc은 보류:** 나중에 따로 판단한다.

## Rejected alternatives

- **Markdown 직접 작성만 하기:** 기존 12개 문서처럼 코드와 어긋난다.
- **springdoc 지금 도입:** 런타임 의존성, `/v3/api-docs` 공개 여부를 정하는 Security 결정, 빌드·CI 변경이 따라온다. 또 테스트로 검증된 내용이 아니다.

## Consequences and constraints

- Controller 매핑을 바꾸는 PR은 색인도 함께 갱신해야 Backend CI를 통과한다.
- 색인 파일만 고친 PR에서는 Backend lane이 돌지 않아 검사되지 않는다.
- profile로 켜지는 Controller(`/internal/performance/**`)는 `test` profile 기준 색인에 없다.
- Asciidoctor HTML 변환은 아직 없고, 스니펫(.adoc)까지만 만든다.
