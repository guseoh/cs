# Product 목록의 반복 read 비용은 제한된 Redis cache로 우회한다

## Context
2026-08 Phase 9의 `GET /api/products` 측정에서는 CPU 증설로 처리량이 좋아졌지만 CPU 2.0에서도 dropped iteration·긴 tail latency·Hikari pending이 남았다. 관련 SQL은 비교적 저렴했고 Hikari pool 확대는 오히려 성능을 악화시켰다. Java hotspot에 대한 유효한 JFR 귀속도 확보되지 않았다. 따라서 **DB가 느리기 때문에 Redis가 필요하다**고 가정하지 않고, 반복 조회의 JPA 객체화·DTO 조립과 connection 사용을 cache hit로 우회할 수 있는지 시험했다.

## Decision
[ARCH-014](https://github.com/guseoh/pawcycle-commerce/blob/main/docs/adr/ARCH-014-product-list-redis-cache.md)의 선택은 상품 목록의 legacy/no-argument read에만 Redis를 적용하고 MySQL을 authoritative source로 유지하는 것이다. 검색·필터·정렬·pagination의 DB-native reader, 상세 조회, session은 범위 밖이다. 캐시 값은 `ProductListView`의 JSON이며 namespace/format version을 가진다. [PR #203](https://github.com/guseoh/pawcycle-commerce/pull/203)의 초기 기술 설명에는 v1 key가 등장하지만 [PR #219](https://github.com/guseoh/pawcycle-commerce/pull/219) 이후 현재 구현은 `pawcycle:catalog:product-list:v2`다. 과거 key 설명을 현행 값으로 혼동하지 않는다.

일반 cache-aside의 위험은 **stale refill race**다. cache miss가 이전 DB 값을 읽는 사이 관리자의 수정이 commit되고 cache key가 삭제되더라도, 느린 miss가 뒤늦게 과거 값을 Redis에 다시 저장할 수 있다. 그래서 miss 전에 generation을 읽고 Lua conditional set에서 generation이 일치할 때만 저장한다. 쓰기 transaction의 `afterCommit`에서 Lua `INCR generation + DEL data`를 원자 실행하고 rollback에서는 무효화하지 않는다. TTL 기본 5분은 correctness 자체를 보장하는 방법이 아니라 잔여 stale entry의 보조 제한이다.

## Rejected alternatives
- **단순 DEL invalidation:** concurrent miss가 삭제 직후 오래된 값을 다시 채울 수 있다.
- **TTL-only:** 상품 수정 후 TTL까지 공개 상품 상태·가격이 낡을 수 있다.
- **Spring Cache + Java native serialization:** key/value 포맷과 실패 경계의 직접 통제가 어렵고 serialization 호환성·안전성 대가가 있다.
- **Product detail/session까지 확대, distributed lock 추가:** 이 실험의 병목·요구로 정당화되지 않았다.

## Consequences and constraints
Cache hit는 기존 DB/JPA/DTO 경로를 우회하지만 Redis 요청·JSON 처리·무효화 비용이 생긴다. Redis read/write 오류는 cache error metric으로 관측하고 상품 목록은 DB로 fallback한다. 그러나 Redis timeout 중 지연, DB fallback 압력, Redis invalidation 실패 후 TTL까지 남을 수 있는 stale entry는 여전히 비용·위험이다. cache 기본값은 비활성이며 해당 PR의 Production Redis/Secret/비용·배포는 승인 범위 밖이다.

## Implementation/verification
현재 `main` 540464a9b875의 [ProductListCache.java](https://github.com/guseoh/pawcycle-commerce/blob/540464a9b875f7bc6bdda11ecf499efdea2e2d43/backend/src/main/java/com/pawcycle/backend/catalog/product/application/ProductListCache.java)는 두 Lua script, generation 비교, hit/miss/error metric 및 DB fallback을 실제로 구현한다. [ProductListCacheInvalidator.java](https://github.com/guseoh/pawcycle-commerce/blob/540464a9b875f7bc6bdda11ecf499efdea2e2d43/backend/src/main/java/com/pawcycle/backend/catalog/product/application/ProductListCacheInvalidator.java)는 Spring transaction synchronization의 `afterCommit` 사용을 확인한다. [ProductListCacheTests.java](https://github.com/guseoh/pawcycle-commerce/blob/540464a9b875f7bc6bdda11ecf499efdea2e2d43/backend/src/test/java/com/pawcycle/backend/catalog/product/application/ProductListCacheTests.java)에는 refill race, Redis 장애, DB 오류 전파 검증이 있다. 테스트 코드를 확인한 사실과 이번 세션에서 재실행한 사실은 다르다.

[Issue #216](https://github.com/guseoh/pawcycle-commerce/issues/216)과 병합된 [PR #217](https://github.com/guseoh/pawcycle-commerce/pull/217)의 **과거 local/synthetic first-result** 기준 Before는 약 193.49 RPS / dropped 5,808 / p95 6,854.56ms / p99 8,590.75ms, Redis After는 250 RPS / dropped 0 / p95 4.71ms / p99 26.99ms다. Redis는 이 시험의 Read Scale 판단에서 `KEEP`이다. 측정 단위·workload·조건이 제한돼 있으므로 이 수치를 현재 Production 성능, 최대 RPS 또는 SLO 달성으로 사용할 수 없다.
