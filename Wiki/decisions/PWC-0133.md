# 고립 NORMAL/PROCESSING 결제는 결제사 DONE이 확인된 경우에만 유지보수 명령으로 성공 확정한다

## Context

[PWC-0016](PWC-0016.md)은 query-only를 우선하는 단계적 수동 복구 정책이다. 그 Phase 1(#450)은 결제사 조회와 오류·identity 분류를 구현했다. 하지만 결제사 승인 뒤 로컬 확정 전에 멈춘 `NORMAL/PROCESSING` 결제는 여전히 처리 경로가 없었다(재고 예약, `PAYMENT_PENDING` 주문이 그대로 남는다).

## Decision

사용자가 2026-11-15에 상세 설계와 권장안을 승인했다(Phase 2a).

- **범위:** 결제사 조회 결과가 같은 주문 ID·결제 키·금액의 `DONE`일 때만 성공으로 확정한다. 정상 확정의 성공 분기를 `applyNormalSuccess`로 꺼내 같은 효과를 같은 순서로 한 번 적용한다.
- **실행 형태:** property로만 켜지는 단발 유지보수 명령이다. 공개 API는 만들지 않는다. 같은 프로세스에 결제 만료·정기결제·구독 주문·회차 보정 스케줄러가 켜져 있으면 거부하고, 이 프로세스에서는 스케줄링 자체를 끈다.
- **사전 조건:** ADMIN 실행자, NORMAL/PROCESSING, 주문 PAYMENT_PENDING, identity 존재, `expires_at` + 10분 경과, RESERVE 이동 존재와 DEDUCT·RELEASE 이동 없음.
- **운영자 펜싱(결제 유입 중단 확인):** 실행 조건으로 강제하지 않고 Runbook 권고로 둔다. 성공 방향 확정은 결제 행 잠금 뒤 `PROCESSING`일 때만 적용되므로, 동시에 실행돼도 효과가 한 번만 적용된다.

## Rejected alternatives

- **운영자 펜싱을 강제 조건으로 두기:** 성공 확정의 정확성에는 필요하지 않고, 실행 절차만 무거워진다.
- **실패 확정·예약 해제를 함께 구현:** 진행 중인 요청과 구분할 근거(lease·fencing)가 없어서, 잘못 해제하면 초과 판매 위험이 생긴다.
- **범용 finalizer:** BACKEND-505에서 기각된 방향이다. 이번에는 정상 확정 하나의 성공 분기만 재사용한다.

## Consequences and constraints

- 결제사에서 실패로 끝난 고립 결제는 여전히 `PROCESSING`과 재고 예약으로 남는다.
- 실제 Toss 응답으로는 검증하지 않았다. 운영 실행은 별도 승인 대상이다.
- `expires_at`이 없는 결제는 대상이 아니다.

## Implementation/verification

#532 병합(main `d7b4c9f8`, CI 성공).

- 일회용 MySQL과 가짜 결제사로 T1~T10 시나리오를 확인했다: 성공, HTTP 오류, 확정되지 않은 결제사 상태, identity 불일치, 재실행, 조회 중 정상 확정, 동시 복구, 중간 실패 롤백, 대상 거부, 비관리자.
- 독립 리뷰 8건을 반영했다. 그중 Runbook 명령이 `main()`에서 다른 bootstrap에 가로채져 실행되지 않던 결함은 실행 jar로 명령을 돌려 해결을 확인했다.
- 리뷰 수는 CodeRabbit 미실행으로 0건이다. Production 검증은 없다.
