# Learn software architecture through explained Java/Spring cases before independent design

## Context

A previously proposed daily architecture exercise expected the learner to create domain models, APIs, architecture choices and trade-offs independently. The user instead chose a concept-first pathway before open-ended architecture decisions. The public curriculum of an Inflearn software-architecture course is a **topic reference**; there is no purchase or request to reproduce any proprietary lesson content.

## Decision

Use the existing concept-learning project for a six-stage, instructor-led architecture learning course:

1. Architecture definitions, requirements, quality attributes, drivers, tactics and trade-offs.
2. Object-oriented responsibilities, coupling/cohesion, domain modeling, DDD and interfaces.
3. Layered/hexagonal, modular-monolith, microservices and event-driven styles.
4. Java/Spring API, transaction, concurrency, consistency, caching, messaging, resilience, performance and observability.
5. Source-based existing-system reverse engineering, architecture diagrams, ADRs and evaluation.
6. Guided practical system design with a gradual transition to user-led decisions.

Every substantial topic must explain **why the problem occurs**, demonstrate it with concrete Java 21/Spring Boot code and domain/service scenarios, show execution or state transitions visually where helpful, compare a baseline with alternative designs, clarify costs and limits, and give a way to test or measure the conclusion. Use small teaching examples plus realistic order/inventory/payment examples, without claiming unexecuted code was verified.

**Technical reference policy:** proactively search Korean technology and engineering blogs (including Woowa, NAVER D2, Toss and LY Corporation), prioritize source posts containing actual problem context, diagrams, code, constraints and trade-offs, and integrate substantive findings into Korean lessons with direct links. Cross-check vendor claims and version-sensitive details against primary documentation. Do not make reading linked posts mandatory to understand the core lesson.

## Rejected alternatives

- Force independent architecture design or mandatory quizzes before core concepts are understood.
- Present definitions/pattern catalogs without concrete examples, implementation flow or failure modes.
- Treat a company's selected architecture as universally optimal.
- Reproduce commercial course material instead of producing original explanations from public references.
- Replace the existing Board, DevPedia, PawCycle or system-design book tracks.

## Consequences and constraints

The early phase is explanation-and-analysis led, not a graded design interview. Example depth matters more than superficial breadth. Progression is based on understanding and user preference, not a fixed date. Existing project implementation approvals and ownership rules remain unchanged.

## Implementation/verification

User confirmed the study change on 2026-11-06. The public course outline and listed engineering posts were inspected as reference candidates. No study lesson, code execution, project modification, test result or independent system design has been verified by this Wiki record.
