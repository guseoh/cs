# Order read와 Quick Reorder command persistence의 책임을 먼저 분리한다

## Context

OrderPersistenceAdapter 가 조회 projection 과 회원/장바구니 잠금·멱등 응답 저장·수량 변경을 동시에 소유해 변경 경계가 불분명했다.

## Decision

#338에서 QuickReorderPersistenceAdapter 를 분리하고 OrderApplicationService 가 read/command adapter 를 각각 주입받게 했다. 기존 application TransactionTemplate, SQL·잠금 순서·JSON replay 를 유지한 상태에서 책임부터 드러냈다. #351의 typed JDBC row 와 #388의 순수 정책/codec 추출은 이후 별도 단계다.

## Alternatives and interpretation

분리하면서 JDBC→JPA, raw Map 전면 제거, missing-row lock 교정, retry 추가를 함께 하지 않았다. Checkout 과 유사한 위험만으로 Quick Reorder 잠금을 추정 수정하지 않았다.

## Consequences and limits

분리 시점에는 두 adapter 의 JDBC 와 Quick Reorder raw mapping 이 그대로 남는다. 파일 분리 자체를 정합성 개선이나 성능 개선으로 계산하지 않는다.

## Implementation and verification

#338 실제 MySQL targeted3 PASS·compile/build·CI 성공. 전체 로컬 422중 쿠폰 1 FAIL 은 당시 미해결이며 후속 #360/#362의 Seoul 분석과 연결한다. 분리와 원래 lock/rollback 보호를 구분한다.
