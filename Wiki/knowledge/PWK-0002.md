# JVM 워밍업 비용과 CRaC — 330초에서 2~3초로 단축한 운영 사례

## 핵심 주장과 적용 범위

Pulkit Garg의 [원문: JVM Startup Time Story: From 330 Seconds to 3](https://medium.com/engineering-housing/we-stopped-our-jvm-from-ever-booting-cold-again-b5dbd492fe88)(2026년 11월 초 공개)과 [GeekNews 한국어 정리](https://news.hada.io/topic?id=36566)(2026-11-04)를 확인한 **외부 기술 사례 학습 기록**이다. 이는 특정 팀이 발표한 사례이지 일반적인 Java/Spring 성능 보증이나 이 저장소 프로젝트에서 재현한 벤치마크가 아니다.

핵심 문제는 Java 프로세스를 시작하는 시간만이 아니라, 파드가 실제 트래픽을 안정적으로 처리할 수 있도록 JIT 컴파일과 애플리케이션 워밍업을 반복하는 비용이다. **CRaC(Coordinated Restore at Checkpoint)**는 한 번 충분히 워밍업한 JVM의 실행 상태를 체크포인트로 저장하고 새 인스턴스에서 복원해 반복 비용을 낮춘다. 따라서 시작 지연뿐 아니라 롤링 배포, 장애 복구, 오토스케일링, 상시 CPU 여유 용량에도 영향을 줄 수 있다.

## JVM 워밍업과 CRaC의 작동 원리

- JVM은 클래스 로딩·초기화와 함께 바이트코드를 실행한다. HotSpot의 **JIT(Just-In-Time) 컴파일러**는 자주 실행되는 메서드 및 경로를 관찰하고 단계적으로 네이티브 코드를 생성·최적화한다. 초기 요청과 충분히 워밍업한 이후의 요청은 실행 특성이 다를 수 있다.
- 기존 방식에서는 새 파드가 생성될 때마다 애플리케이션 초기화와 JIT 워밍업을 반복한다. 파드가 준비 완료로 표시되는 시점과 성능이 안정되는 시점은 별개일 수 있으며, 원문에서 330초는 이 둘을 포함하는 **트래픽 투입 가능 시점까지의 시간**이다.
- CRaC은 HotSpot JVM의 체크포인트·복원을 지원하는 OpenJDK 프로젝트이며 Linux **CRIU**를 활용한다. CRaC 지원 JDK에서 실제 코드 경로를 워밍업한 뒤 JVM 메모리·최적화 상태를 디스크에 저장하고 여러 JVM 인스턴스가 같은 체크포인트에서 복원할 수 있다. 복원된 JVM에서도 추가 JIT 최적화가 가능하다.
- 체크포인트 전후의 소켓, 파일 디스크립터, DB 연결, 스레드 풀 같은 리소스의 생명주기를 관리해야 한다. Spring Boot는 일부 리소스를 처리하지만 애플리케이션과 의존 라이브러리의 모든 상태를 자동 보장하지 않는다. 예컨대 연결은 재생성하고, 외부 시스템·토큰·시간 의존 상태는 복원 후에도 유효한지 검증해야 한다.

실행 흐름은 **CRaC 지원 JDK로 실행 → 대표 요청으로 워밍업 → 외부 리소스 안전 처리 → Checkpoint 생성 → 새 파드에서 Restore → 연결 재설정·준비 상태 검사 → 트래픽 수용**이다. 이 흐름은 개념적 요약으로, 원문에 없는 구체적인 배포 명령이나 인프라 구성을 확정한 것은 아니다.

## 원문의 보고 수치

| 지표 | 적용 전 | CRaC 적용 후 | 해석 |
| --- | --- | --- | --- |
| 새 파드가 트래픽을 처리할 준비 시간 | 약 330초 | 약 2~3초 | 특정 서비스에서 보고한 값 |
| 전체 롤링 배포 | 약 20분 | 약 4분 | 파드 준비 시간이 배포 병목을 완화 |
| 파드 정상 상태 CPU | 기존 기준 100% | 약 20% | 저자의 주장. 측정 정의와 원시 데이터는 공개되지 않음 |
| 오토스케일링 | 실용적이지 않았음 | 활용 가능해짐 | 새 용량이 실제로 유용해지는 시점이 빨라짐 |

원문은 **애플리케이션 부팅 약 75초 + 워밍업 약 245초**라고 설명하면서 총 준비 시간을 대략 **330초**로 표현한다. 합계는 산술적으로 320초이므로 각각 근삿값으로 읽어야 한다. 특히 '330초 → 3초'를 JVM 프로세스의 순수 부팅 시간만 단축한 결과로 해석하면 안 된다.

CPU 20% 수치는 **독립적으로 검증한 사실이 아니다**. 기존 워밍업 여유 용량, CPU 예약량, 실제 CPU 사용률, 정상 처리량당 CPU 효율은 서로 다른 지표다. 원문에는 구분 가능한 측정 방법·기간·부하·원시 시계열이 없어, 워밍업 제거만으로 일반적인 JVM 정상 상태 CPU가 80% 감소한다고 결론 내릴 수 없다. 비용·스팟 인스턴스·스케일링 개선도 해당 환경의 운영 조건에 따른 효과이다.

## 실제 장애: CPU 기능 불일치와 롤백

CRaC를 운영에 배포한 뒤 여러 파드에서 `cpu.features` 비트맵 불일치가 발생하여 체크포인트 복원이 실패했다. JIT이 체크포인트를 생성한 호스트에서 사용 가능한 CPU 명령어 확장에 맞춰 기계어를 생성했는데, 복원 대상 호스트의 CPU 기능 집합이 달랐던 것이다. 복원 엔진은 호환되지 않는 코드를 실행 중에 실패시키는 대신 JVM 시작 단계에서 거부했다. 이는 **안전 검사에 의한 조기 실패**로 설명된다.

원문 팀은 원인 규명보다 **마지막으로 검증된 비-CRaC 이미지로 즉시 롤백**하는 복구를 우선했다. 이후 동적 오토스케일러가 선택한 노드에서 인스턴스 유형·노드 그룹 레이블이 CPU 명령어 호환성을 보장하지 않는다는 점을 확인했다. 수정은 체크포인트 생성 스크립트가 환경 변수로 **기준 CPU 기능 집합을 고정**하도록 하는 방식이었다. 가능한 최고 성능 일부를 포기하더라도 실제 배치 가능한 호스트에서 복원되는지를 우선한 트레이드오프다.

재사용할 운영 원칙은 다음과 같다.

- **복구와 원인 분석을 분리한다.** 실패한 신규 경로를 계속 재시도하기보다 검증된 구버전의 독립적 실행 경로를 확보한다.
- **레이블과 호환성을 혼동하지 않는다.** 이미지와 노드의 OS/CPU 아키텍처 및 명령어 기능을 실제로 검증한다.
- **Restore 성공과 서비스 정상성은 다르다.** JVM 기동, 소켓/DB 재연결, readiness, 실제 요청 처리를 독립적으로 확인한다.
- **체크포인트를 만들어 둔 시점의 상태를 검토한다.** 외부 연결·시간에 민감한 데이터·인증 상태가 복원 후 그대로 유효하다고 가정하지 않는다.

## 대안과 기술 선택의 경계

| 접근법 | 주된 이점 | 한계 또는 확인할 사항 |
| --- | --- | --- |
| 일반 JVM + 사전 워밍업 | 현행 런타임 유지, 구현 부담 낮음 | 새 파드마다 워밍업 비용이 재발할 수 있음 |
| AppCDS | 클래스 메타데이터 공유로 시작 단계 일부 개선 | JIT 워밍업 전체를 재사용하는 기술은 아님 |
| GraalVM Native Image | AOT 컴파일로 빠른 시작 및 낮은 초기 메모리 목표 | 동적 기능·라이브러리 호환성과 장시간 처리량을 별도 평가. 모든 서비스에 대규모 재작업이 반드시 필요한 것은 아님 |
| CRaC | 워밍업된 JVM 상태의 빠른 복원, HotSpot/JIT 유지 | 체크포인트/복원 생명주기·CPU 호환성·아티팩트 배포·운영 복잡성 |

기술 선택은 시작 시간 수치 하나만으로 하지 않는다. **콜드 스타트 빈도, 워밍업 부하, steady-state 처리량, 배포 토폴로지, 지원 JDK 및 라이브러리 호환성, 롤백 용이성**을 함께 평가해야 한다.

## Java/Spring 및 대규모 시스템 학습에 적용

이 지식은 특정 프로젝트의 CRaC 도입 결정이 아니며, **향후 실험 후보**에 해당한다. 예를 들어 Large-scale Board와 같은 격리된 Java/Spring 실습 환경에서 일반 JVM 기준선과 CRaC 복원을 비교할 수 있다.

1. **측정 대상 분리:** 프로세스 실행 시작, Spring 애플리케이션 준비, 첫 성공 요청, p95/p99 응답 시간이 안정되는 시점, 배포 전체 소요 시간을 각각 기록한다.
2. **부하·리소스 통제:** 동일 코드/데이터/CPU 할당/동시성 조건에서 CPU 사용량, CPU 예약, 메모리, 처리량, GC 및 워밍업 구간을 비교한다.
3. **복원 정확성 확인:** DB 커넥션 풀, 네트워크 소켓, 파일, 스케줄러·스레드, 시간 민감 상태를 확인하고 실제 HTTP 요청까지 검증한다.
4. **장애 실험:** 호환되지 않는 CPU에서의 복원 실패를 안전한 테스트 환경에서 재현하고, CRaC 없이 시작하는 폴백 및 롤백 시간을 측정한다.
5. **판정:** 관측값에 근거해 KEEP/DEFER/REJECT를 결정한다. 위 실험을 실제로 수행했거나 CRaC를 어떤 프로젝트에 도입했다는 의미는 아니다.
