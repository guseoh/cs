# PawCycle 1단계 학습 노트 — 결제·재고·정기배송 정합성

## 이 노트를 읽는 법

로드맵 1단계(2026-11-15)를 되돌아보기 위한 노트다. 각 절은 "무엇이 걱정이었나 → 어떻게 확인했나 → 코드가 왜 그렇게 생겼나 → 무엇이 남았나" 순서다. 구현은 AI(Claude) 비중이 크고, 결정은 사용자가 승인했다. 끝의 질문에 자기 말로 답할 수 있으면 이 단계를 설명할 수 있다.

- 기준 코드: `main` [`375546aa`](https://github.com/guseoh/pawcycle-commerce/commit/375546aa8bc2ee4f8cf7a47fb8ac5d0830f77805)(이후 단계까지 반영된 상태에서 읽은 코드)
- PR: [#530](https://github.com/guseoh/pawcycle-commerce/pull/530)~[#535](https://github.com/guseoh/pawcycle-commerce/pull/535)
- 시간순 기록: [2026-11 journal 1단계 절](../journal/pawcycle/2026-11.md#2026-11-15-pawcycle-1단계-정합성-착수)

## 1. 왜 정합성이 첫 단계였나

고도화 설계(2026-11-14)에서 순서를 "정합성 → 장애 관측 → 배포·보안 → 성능 → 개선"으로 잡았다. 이유는 다음과 같다.

- 커머스에서 가장 비싼 결함은 느린 화면이 아니라 **돈과 재고가 틀리는 것**이다(초과 판매, 중복 결제, 같은 회차 주문 두 번).
- 성능을 개선하려면 잠금·트랜잭션을 건드리게 된다. 그 전에 "지금 정합성이 지켜지고 있다"는 **보호 테스트**가 있어야 개선이 회귀를 만들지 않는다.

1단계에서 다룬 위험은 `docs/architecture/known-risks.md`의 R2(재고 경합), R5(구독 잠금 상태 불명), R6(스케줄러 중복 실행), 그리고 [#417](https://github.com/guseoh/pawcycle-commerce/issues/417)(고립 PROCESSING 결제)이다.

## 2. 문서와 실제 코드를 먼저 맞추기 (#530)

ARCH-007 ADR은 "구독 행 잠금"을 제안 상태로 적고 있었다. 코드를 추적해 보니 구독 행 잠금은 **첫 구현(#87)부터 있었고** ARCH-011이 이미 승인한 상태였다. 그래서 새 코드를 쓰지 않고 문서를 실제 상태로 확정하고 R5를 해소했다.

배운 점: 위험 목록을 받으면 바로 고치지 말고 **지금 코드가 실제로 무엇을 하는지**부터 확인한다. 고칠 것이 없을 수도 있다.

## 3. 특성 테스트로 동시성 고정하기 (#531)

### 3.1 무엇을 확인했나

| 시나리오 | 기대 | 결과 |
| --- | --- | --- |
| 재고 10개 SKU에 30명이 동시에 결제 | 10명 성공, 20명 재고 부족 거절, 재고(가용 0·예약 10), RESERVE 이동 10건 | 통과 |
| 두 SKU를 서로 반대 순서로 담은 장바구니 20개 동시 결제 | 데드락 없이 20건 성공 | 통과 |
| 배송 알림 작업 두 개가 동시에 실행 | 같은 알림 중복 없음 | 통과 |

결제 만료, 정기결제, 재시도, 구독 주문에는 이미 동시 실행 테스트가 있었다. 빠진 것은 배송 알림뿐이었다. 그래서 **분산 잠금(Redis lock 등)을 도입할 근거가 없다**고 결론 냈다. 회차 보정은 구독별 잠금과 version 확인이 있고 기본으로 꺼져 있다.

### 3.2 "특성 테스트"란

특성 테스트(characterization test)는 "이렇게 동작해야 한다"가 아니라 **"지금 이렇게 동작한다"를 고정**하는 테스트다. 나중에 5단계에서 잠금이나 쿼리를 바꿀 때, 이 테스트가 깨지면 정합성 동작이 바뀐 것이다.

### 3.3 동시 시작을 만드는 방법

```java
CountDownLatch ready = new CountDownLatch(buyers.size());
CountDownLatch start = new CountDownLatch(1);
ExecutorService executor = Executors.newFixedThreadPool(buyers.size());
// 각 작업: ready.countDown(); start.await(); checkout(...)
assertThat(ready.await(TIMEOUT_SECONDS, TimeUnit.SECONDS)).isTrue();
start.countDown();   // 모든 스레드가 준비된 뒤 한꺼번에 출발
```

스레드를 그냥 순서대로 제출하면 앞의 요청이 끝난 뒤 다음 요청이 시작될 수 있어 경합이 생기지 않는다. `ready`로 모두 대기 지점에 도착했는지 확인하고, `start` 하나로 동시에 풀어 준다. 실제 MySQL(Testcontainers가 아닌 CI MySQL)에서 돌려야 InnoDB 잠금이 실제로 작동한다.

### 3.4 왜 데드락이 안 나는가 — 코드 읽기

재고 예약은 두 겹으로 보호된다.

```java
// InventoryRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select inventory from InventoryEntity inventory where inventory.skuId = :skuId")
Optional<InventoryEntity> findLockedBySkuId(@Param("skuId") long skuId);

@Query("""
    update InventoryEntity inventory
    set inventory.availableQuantity = inventory.availableQuantity - :quantity,
        inventory.reservedQuantity = inventory.reservedQuantity + :quantity,
        inventory.version = inventory.version + 1
    where inventory.skuId = :skuId and inventory.version = :expectedVersion ...""")
```

- 비관적 잠금(`SELECT ... FOR UPDATE`)으로 같은 SKU 재고 행을 한 트랜잭션만 읽고 바꾸게 한다.
- UPDATE에 version 조건을 한 번 더 걸어, 잠금 없이 들어온 경로가 있어도 덮어쓰지 못하게 한다.

다중 SKU 데드락에 대해서는 **코드에 명시적인 정렬이 없다.** Checkout은 장바구니의 SKU를 `findAllByIdInForUpdate(skuIds)` — 즉 `WHERE id IN (...) FOR UPDATE` **한 문장**으로 먼저 잠근다. InnoDB는 이 문장을 PK 인덱스 순서로 스캔하며 잠그므로, 장바구니에 담은 순서와 관계없이 모든 트랜잭션이 같은 순서로 SKU 행을 잡는다. 그 뒤 재고 예약은 이미 SKU를 쥔 상태에서 진행된다. #531의 반대 순서 테스트가 이 성질을 고정한다.

- 트레이드오프: 코드에 정렬을 명시하면 의도가 드러나지만, 지금 구조로도 안전하다는 것이 테스트로 확인됐다. 이 성질은 "한 문장으로 잠근다"에 기대므로, 나중에 SKU를 하나씩 잠그도록 바꾸면 깨질 수 있다. 그 경우 테스트가 알려 준다.

## 4. 고립 PROCESSING 결제 성공 확정 (#532, #417 Phase 2a)

### 4.1 문제

결제 승인 요청이 결제사에 도착한 직후 서버가 죽으면, 결제사에서는 승인(DONE)됐는데 우리 DB 결제는 PROCESSING으로 남는다. 이 결제는 만료 스케줄러도 건드리지 않는다(만료는 READY만 처리). 고객은 돈을 냈고 재고는 예약된 채로 묶인다.

### 4.2 결정과 범위

[PWC-0133](../decisions/PWC-0133.md): **결제사 DONE이 확인된 경우에만** 유지보수 명령으로 성공 확정한다. 실패 확정과 재고 예약 해제는 범위 밖이다(Phase 2b, [PWC-0134](../decisions/PWC-0134.md)에서 별도 승인 — 작업자 배제가 필요하다).

왜 성공만 먼저인가: 성공 확정은 정상 결제 확정과 같은 효과(결제 SUCCEEDED, 주문 PAID, 예약 DEDUCT)다. 실패 확정은 예약을 풀어 재고를 다시 팔 수 있게 하므로, 그 사이 다른 작업자가 같은 결제를 성공으로 처리하면 **초과 판매**가 된다. 위험이 비대칭이다.

### 4.3 코드 읽기 — 확인, 외부 조회, 재확인

```java
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public Outcome recover(long paymentId, long operatorMemberId) { ... }

private Outcome recoverOnce(long paymentId, long operatorMemberId) {
  // 1) 짧은 트랜잭션: 관리자 확인, 후보 조회(잠금 없음)
  RecoveryCandidate before = transaction.execute(s -> payments.findRecoveryCandidate(paymentId, expiredBefore, false));
  Outcome refusal = eligibility(before);
  if (refusal != null) return refusal;

  // 2) 트랜잭션 밖: 결제사 조회
  observation = reconciliation.queryOnly(paymentId);
  if (!"SUCCEEDED".equals(observation.status())) return Outcome.stopped(observation.status());

  // 3) 새 트랜잭션: 행 잠금 후 다시 확인하고 정상 확정 경로 재사용
  return transaction.execute(s -> {
    RecoveryCandidate locked = payments.findRecoveryCandidate(paymentId, expiredBefore, true);
    if (locked != null && "SUCCEEDED".equals(locked.status())) return Outcome.ALREADY_FINALIZED;
    if (eligibility(locked) != null) return Outcome.CHANGED_DURING_QUERY;
    if (!sameIdentity(before, locked)) return Outcome.CHANGED_DURING_QUERY;
    normalPayments.applyNormalSuccess(paymentId, locked.orderId(), locked.paymentKey());
    audits.append(operatorMemberId, AUDIT_ACTION, "PAYMENT", paymentId);
    return Outcome.RECOVERED;
  });
}
```

읽을 포인트:

- **외부 호출을 트랜잭션 밖에 둔다**(`NOT_SUPPORTED` + `TransactionTemplate`). 결제사 응답을 기다리는 동안 DB 커넥션과 행 잠금을 쥐고 있으면, 결제사가 느릴 때 커넥션 풀이 고갈된다.
- 그 대가로 **조회 사이에 상태가 바뀔 수 있다.** 그래서 3)에서 행을 잠근 뒤 자격 조건(`eligibility`)과 신원(`sameIdentity`: 주문·결제사 주문 ID·paymentKey·금액)을 다시 확인한다. 이것이 "확인 → 외부 → 잠금 후 재확인" 패턴이다.
- **정확히 한 번**은 운영자 잠금이 아니라 "PROCESSING일 때만 효과 적용"이라는 정상 확정 경로의 게이트로 보장한다. 다른 경로가 먼저 확정했으면 `ALREADY_FINALIZED`로 끝난다.
- 자격 조건은 보수적이다: NORMAL 결제, PROCESSING, 주문 PAYMENT_PENDING, 결제사 식별값 존재, **만료 후 10분 경과**, 예약 이동 수 = 주문 항목 수, 이미 정산된 이동 없음. 하나라도 어긋나면 `REFUSED_*`로 아무것도 바꾸지 않는다.
- 결과는 `Outcome` enum으로 모두 이름을 가진다. 운영자가 "왜 안 됐는지"를 결과 코드만으로 안다.
- 결제사 조회 실패는 `STOPPED_PROVIDER_UNKNOWN`으로 멈추고, 실패 분류 지표에 남긴다(2단계의 `ExternalCallFailures`).

### 4.4 진입점에서 막힌 일 — PWL-0051

서비스 테스트는 모두 통과했는데, Runbook대로 명령을 실행하자 아무 일도 일어나지 않았다. `main()`에서 기존 운영 인증 smoke bootstrap이 "웹이 아닌 실행"을 모두 자기 요청으로 보고 먼저 종료했기 때문이다.

```java
if (isProcessingPaymentRecovery(args, System.getProperty(RECOVERY_PROPERTY), System.getenv())) {
  SpringApplication.run(PawcycleBackendApplication.class, args);
  return;
}
int maintenanceExitCode = ProductionAuthSmokeMemberBootstrap.runIfRequested(args);
```

복구 명령을 auth smoke보다 먼저 분기하도록 고치고 라우팅 테스트(`PawcycleBackendApplicationRoutingTests`)를 추가했다. 교훈: 운영 명령은 **실제 진입점으로 한 번은 실행**해 봐야 한다([PWL-0051](../lessons/PWL-0051.md)).

## 5. Toss 테스트 환경 (#533~#535)

- 목표: 로컬 통합 환경에서 실제 Toss 테스트 키로 결제위젯 → 승인(S1) → backend confirm까지 한 번 통과시키기.
- **키 종류 문제(#534):** 결제 화면은 결제위젯(SDK v2 `widgets()`)인데 코드는 API 개별 연동 키(`test_ck_`/`test_sk_`)만 받았다. 결제위젯은 위젯 연동 키(`test_gck_`/`test_gsk_`)를 써야 한다. 끝까지 한 번 실행해 보기 전에는 드러나지 않았다([PWL-0052](../lessons/PWL-0052.md)). 계약 문서 API-006도 함께 고쳤다([PWL-0053](../lessons/PWL-0053.md)).
- **Runbook 첫 실행에서 고친 것(#535):** 명령 기준 경로 혼재, `.env.local`의 UTF-8 BOM 때문에 첫 줄 변수를 못 읽음, 카드 결제가 테스트 키여도 실제 카드사 인증 창으로 이어질 수 있다는 주의.
- **결과: 부분 검증.** 위젯 표시와 결제창 취소(S2)는 확인했다. **S1(실제 승인과 backend confirm)은 미실행**이다. 카드사 인증 창이 떠서 사용자가 중단했다. 알려진 위험 R10으로 남아 있다.
- 보안 경계: 키는 사용자 셸에서만 입력했고(`Read-Host -MaskInput`), 카드 선택과 결제 진행은 사용자가 직접 했다.

## 6. 트레이드오프 정리

| 선택 | 대안 | 왜 이쪽인가 | 대가 |
| --- | --- | --- | --- |
| 분산 잠금 도입 안 함 | Redis lock | 기존 DB 잠금과 동시성 테스트로 중복이 막혀 있었다 | 인스턴스를 여러 대로 늘리면 다시 검토 |
| 성공 확정만 먼저 | 성공·실패 확정 동시 구현 | 실패 확정은 예약 해제로 초과 판매 위험 | 결제사 실패로 끝난 고립 결제는 여전히 수동 대응(#417 Phase 2b) |
| 외부 조회를 트랜잭션 밖에 | 잠금을 쥔 채 조회 | 결제사 지연이 커넥션 고갈로 번지지 않는다 | 잠금 후 재확인 코드가 필요 |
| 유지보수 명령(일회성 프로세스) | 관리자 API | 운영자가 명시적으로 실행하고 감사 로그를 남긴다 | 진입점 라우팅이 복잡해졌다 |

## 8. 되돌아볼 질문

1. 특성 테스트와 일반 회귀 테스트는 무엇이 다른가? 5단계에서 이 테스트들이 왜 중요해지는가?
2. `CountDownLatch` 두 개(`ready`, `start`)를 쓰는 이유는? 하나만 쓰면 무엇이 약해지는가?
3. 다중 SKU 결제에서 데드락이 나지 않는 이유를 InnoDB 잠금 순서로 설명해 보라. 어떤 코드 변경이 이 성질을 깰 수 있나?
4. 재고 예약에 비관적 잠금과 version 조건을 둘 다 쓰는 이유는?
5. 고립 결제 복구에서 결제사 조회를 트랜잭션 밖에 둔 이유와, 그 때문에 추가로 필요해진 확인은?
6. "정확히 한 번"을 운영자 잠금이 아니라 무엇으로 보장했나?
7. 성공 확정과 실패 확정의 위험이 비대칭인 이유는?
