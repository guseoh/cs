# 여섯 도메인과 대규모 시스템 설계 1·2권의 학습 목표·연계 설계안

> **구분:** 교재 1·2권을 같은 저장소에 두는 것은 확정이지만 **교재 학습은 현재 보류·후순위**이며, 당장의 중심 학습은 백엔드·시스템 설계·RAG이다. 여섯 도메인의 독립 실행과 교재 1·2권의 동일 저장소 운영은 사용자 확정. 아래 **세부 장별 적용/모듈 명칭/실험 주제/순서**는 학습용 제안이며 아직 실행되지 않았다. 목차는 출판사 공개 자료를 근거로 했다.

## 1. 저장소의 두 학습 축

### A. 도메인별 실행 앱 (6개)

| 모듈 후보 | 집중할 문제 | 장기 학습 목표 |
| --- | --- | --- |
| `apps/logistics` | 재고 할당·출고 결정, 트랜잭션 경계, 이벤트·복구 | 도메인 모델링·정합성·상태 전이 및 장애 |
| `apps/transit-search` | 교통 데이터 적재, 그래프/최단 경로, 검색 | 알고리즘 복잡도·공간/검색 인덱스·실측 |
| `apps/real-estate` | 공공 거래 데이터 수집·정제·분석 | Spring Batch·파티셔닝·집계 SQL |
| `apps/ticketing` | 좌석 재고, 동시 예약 경쟁, 공정성·대기열 | 동시성 제어·분산/DB 락·부하 |
| `apps/parking` | 위치 검색·예약 상태·만료 | 공간 인덱스·캐싱 정합성·예약 |
| `apps/event-analytics` | 대량 이벤트 수집·집계·Consumer 장애 | Kafka 파티션·멱등성·스트림/배치 처리 |

이 도메인들에 Kafka, Redis, PostgreSQL을 모두 적용하는 것은 목표가 아니다. 실제 문제를 재현하고 필요/비용을 확인한 뒤 선택한다.

### B. 교재 기반 설계·선택적 실험 (별도 앱 아님)

- **Volume 1:** 규모 확장성, 대략적 규모 추정, 설계 면접 접근, 처리율 제한, 안정 해시, 키-값 저장소, 분산 ID, URL 단축, 웹 크롤러, 알림, 뉴스 피드, 채팅, 자동완성, 유튜브, 드라이브. 별도 설계 주제와 재현 가치가 높은 작은 실험을 구분.
- **Volume 2:** 근접성, 주변 친구, 구글 맵, 분산 큐, 모니터링/경보, 클릭 집계, 호텔 예약, 이메일, S3 유사 객체 저장소, 실시간 순위표, 결제, 전자 지갑, 증권 거래소. 각 주제의 요구사항·규모·일관성/가용성·실패 경계를 분석.
- **원칙:** 교재 1·2권 전 장의 1:1 코드 구현 의무 없음. 이해·설계가 충분하면 코드 없이도 해당 장의 학습을 마칠 수 있다.

## 2. 주제별 교차 연계 제안

| 책의 장/주제 | 연결 도메인 후보 | 학습 질문 또는 검증 아이디어 |
| --- | --- | --- |
| 1권: 규모 추정 | 모든 앱 | 특정 RPS·데이터량·QPS를 가정하고 CPU/DB/메모리와 지연 목표의 관계 정의 |
| 1권: 처리율 제한 | 티켓팅, 물류 | 과도한 요청 차단과 실제 대기열의 **역할 차이**, 제한 정책의 공정성 |
| 1권: 안정 해시·분산 ID | 이벤트 분석/물류 | 파티션 결정·키 분배, 식별자 충돌·정렬·단일 노드 대비 이점 |
| 1권: 크롤러·자동완성 | 부동산/교통 | 수집 품질·API 이용 조건, 인덱스/자동완성 성능 (무단 수집 방지) |
| 2권: 근접성/구글 맵 | 주차장/교통 | 위치 검색·좌표 데이터·지도/경로 처리, 공간 질의와 그래프 탐색의 차이 |
| 2권: 분산 메시지 큐 | 이벤트 분석/물류 | Kafka 도입 필요성, 처리 순서·중복·재처리·파티션 |
| 2권: 클릭 이벤트 집계 | 이벤트 분석 | 중복 이벤트·윈도 집계·Consumer 지연·처리량 |
| 2권: 호텔 예약 | 티켓팅/주차장 | 예약 가능 수량·중복 예약·잠금·TTL/만료의 정합성 |
| 2권: 모니터링/경보 | 모든 앱 | 지표, 트레이싱, 오류율·p95/p99·경보 오탐 |
| 2권: 객체 저장소/결제/전자 지갑/증권 거래 | 우선 독립 설계 | 도메인 억지 통합 없이 요구사항·정합성·트레이드오프만 설계 |

위 연결은 책의 정답 구조를 복제한다는 의미가 아니라 **해당 문제에서 선택할 대안과 실험 가설을 찾는 학습 참고**다.

## 3. 설계 실습의 표준 산출물 (가벼운 템플릿)

1. **문제와 범위:** 사용자/기능, 이번 장에서 제외할 것, 현재 합리적 가정
2. **비기능 조건:** 트래픽·데이터 크기·응답 시간·일관성·복구 요구; 임의로 만든 규모 가정과 실제 측정치를 구분
3. **기초 설계:** 단순한 단일 시스템에서 시작한 API·DB·컴포넌트와 주요 데이터 흐름
4. **확장 설계:** 병목 또는 실패 사례를 제시하고 대안의 비용·복잡성을 비교
5. **사용자 결정:** 어떤 방식이 왜 현재 제약에 맞는지 선택하고 다른 대안을 기록
6. **작은 코드 실험(선택):** 실행할 때만 환경·요청·결과·재현 절차 기록
7. **연계와 복습:** 기존 여섯 앱 중 해당하는 이슈/실험과 연결; 억지 코드 통합 금지

책의 공개 목차와 설명에 근거하여 **문제별 설계 훈련**을 권장한다. 책 본문 전체의 정확한 코드/도식 재현이나 전문 복제를 하지 않는다.

## 4. 권장 폴더 및 빌드 관리 (미확정)

```text
apps/                     # 실제 실행하는 독립 Spring Boot 앱
design-studies/
  volume-1/               # 장별 요구사항·설계·ADR
  volume-2/
experiments/              # 정말 필요한 작은 독립 검증 코드
docs/
  decisions/
  experiment-results/
  progress/
```

- `settings.gradle.kts`에는 **실제 코드를 작성한 앱/실험 모듈만 등록**하고, 설계 노트는 Gradle 하위 프로젝트로 등록하지 않는다.
- 공통은 Gradle/JDK 및 테스트 정책 같은 빌드 도구 수준으로 제한한다. 데이터베이스·서비스 구현 간 교차 의존은 기본적으로 금지한다.
- 모듈별 테스트/실행 명령·환경 변수·포트·데이터 저장소를 분리하고, 비용 큰 외부 구성은 실험 시에만 기동한다.
- 학습 주제 간 **독립 실행 여부를 확인**할 때 하나의 앱 변경이 다른 앱의 런타임에 영향을 주지 않도록 검증한다.

## 5. 학습 순서와 검증 방식 제안

- 물류 앱을 첫 주요 개발 도메인으로 유지하고, 시스템 설계·RAG 학습을 병행할 수 있다. **교재 두 권은 당장 진행하지 않으므로 교재의 장별 목표·과제를 현재 진도에 강제하지 않는다.**
- 2권의 분산 큐·집계·예약 문제는 해당 도메인(분산 이벤트/티켓팅/주차장)을 학습할 때 연계하거나 **독립 설계**한다.
- 시간표, 각 장 구현 의무량, 도메인별 완료 비율을 고정하지 않는다. 실측 결과와 이해 수준을 토대로 다음 주제를 선택한다.

## 6. Wiki 기록과 승인 상태

- 사용자 확정: **단일 저장소**, **독립 실행 도메인 앱 6개**, **교재 1·2권의 동일 저장소 후순위 설계 학습**, **백엔드·시스템 설계·RAG 중심**, **AI 채팅 중심·최종 결정 사용자**.
- 제안·미검증: 저장소 가칭, 폴더명, Gradle 설정·Java/Spring 버전, 도메인 모델/ERD/API, 교재별 특정 코드 실험·시험 트래픽·실제 진도, 신규 소스 저장소 및 GitHub Wiki 생성.
- **기록 출처:** 사용자 의사결정과 출판사 도서 소개·목차. 사용자 코드 실행이나 교재 내용을 실제 모두 학습했다고 주장하지 않는다.
