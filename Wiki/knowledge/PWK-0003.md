# PawCycle 4단계 G-1 학습 노트 — 합성 데이터에 backend를 붙이는 규모 측정 환경

## 이 노트를 읽는 법

로드맵이 끝난 뒤 되돌아보며 학습하기 위한 노트다. **무엇을 만들었는지**보다 **왜 그렇게 만들었는지, 다른 선택지는 무엇이었는지, 코드가 왜 그런 모양인지**를 남긴다. 끝의 "되돌아볼 질문"에 답할 수 있으면 이 단계를 자기 말로 설명할 수 있다.

- 기준 코드: `main` [`375546aa`](https://github.com/guseoh/pawcycle-commerce/commit/375546aa8bc2ee4f8cf7a47fb8ac5d0830f77805) ([PR #555](https://github.com/guseoh/pawcycle-commerce/pull/555))
- 구현 주체: 측정 환경은 Claude가 구현했고, 설계 선택은 사용자가 승인했다([PWC-0136](../decisions/PWC-0136.md)). 이후 병목 해석과 개선은 사용자가 맡는다([PWC-0137](../decisions/PWC-0137.md)).
- 이 노트의 수치는 로컬 Windows Docker Desktop 1회 실행 결과다. 운영 용량이 아니다.

## 1. 왜 필요했나

고도화 로드맵 4단계의 목표는 "데이터가 1만 → 10만 → 100만으로 커지면 어디가 먼저 느려지는가"의 **기준선**을 얻는 것이다. 이 기준선이 있어야 다음 두 단계가 진행된다.

- 2단계 알림 임계값 확정(I): 지금 임계값(p95, 오류율, 커넥션 대기)은 실측 없이 정한 임시값이다.
- 5단계 병목 개선: 측정 없이 고치면 "체감상 느린 곳"을 고치게 된다.

4단계는 G(측정 환경) → H(10만·100만 측정) → I(임계값 확정) 순서다. G-1은 그중 **환경을 처음부터 끝까지 만들고 지우는 것**까지다.

## 2. 출발점과 막혀 있던 것

선행 작업 [PR #547](https://github.com/guseoh/pawcycle-commerce/pull/547)(PERF-SCALE-001)에서 합성 데이터 생성기 `perfgen.py`를 만들었다. 회원·상품·SKU·재고 원장·리뷰·주문·결제·배송·구독을 서로 연결해, **같은 seed면 같은 행**이 나오게 만든다(모든 값이 `CRC32(seed:tag:key)`의 함수). 안전장치(guard)로 이름이 `pawcycle-perfgen-*`이고, label이 있고, 익명 volume을 쓰고, port를 열지 않은 MySQL만 받는다.

하지만 이 데이터에 backend를 붙여 요청을 보낼 수는 없었다.

| 막힌 점 | 원인 |
| --- | --- |
| backend 기동 거부 | `perfgen up`이 migration SQL을 직접 적용해 `flyway_schema_history`가 없다. backend의 Flyway는 "기록 없는 비어 있지 않은 schema"로 보고 기동을 멈춘다. |
| 연결할 network 없음 | 생성기 MySQL은 port 없이 `docker exec`로만 접근한다. |
| 로그인 불가 | 합성 회원의 `password_hash`가 `synthetic-no-login`이다. |
| 정기배송 부하 불가 | 모든 구독 회차가 2030년 이후라 처리할 회차(due)가 0건이다. |
| 스케줄러 통제 착시 | 이전 측정 compose(`catalog-isolated`)가 쓰던 `PAWCYCLE_SCHEDULER_ENABLED`는 **코드에 없는 설정**이었다. 그 측정 중에는 결제 만료와 지표 갱신이 실제로 돌았다. |

마지막 항목이 중요하다. "꺼 두었다"고 믿은 설정이 실제로는 아무 효과가 없었다. 그래서 이번에는 **코드의 `@ConditionalOnProperty`를 직접 찾아 실제 이름으로만** 켜고 끈다.

## 3. 설계 선택지와 트레이드오프

### 3.1 backend와 합성 DB를 어떻게 연결하나

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. Flyway가 schema를 만든 뒤 생성 (채택)** | backend를 빈 DB에 한 번 띄워 Flyway가 schema와 history를 만들게 하고, 그다음 perfgen으로 데이터만 넣는다 | 운영과 같은 migration 경로. checksum 검증이 그대로 살아 있다 | backend 기동이 한 번 더 필요(약 50초) |
| B. Flyway baseline | `baselineOnMigrate`로 "이미 최신"이라고 표시 | 가장 간단 | migration 검증을 건너뛰어 schema 차이를 놓칠 수 있다 |
| C. 생성기가 history 행을 직접 씀 | Flyway checksum을 Python으로 계산 | 기동 1회 절약 | Flyway 내부 형식에 의존해 깨지기 쉽다 |

A를 고르면 생성기는 "이 schema가 정말 저장소 최신 migration으로 만들어졌는가"를 확인해야 한다. 그래서 `schema_source()`를 추가했다(6.2절).

### 3.2 로그인 부하용 회원을 어떻게 만드나

| 선택지 | 내용 | 판단 |
| --- | --- | --- |
| **A. 해시 복사 (채택)** | 실제 BCrypt 해시 하나를 만들어 합성 회원 K명(기본 1,000)에 복사 | 로그인 비용(BCrypt 검증)이 실제와 같다. 이 회원들은 주문·구독 이력이 있어 "내 주문" 조회도 실제 규모에서 측정된다 |
| B. 회원가입 API로 새로 만들기 | k6 setup에서 가입 | 이력이 없는 회원이라 조회가 빈 결과다 |
| C. 생성기에서 해시 생성 | Python 표준 라이브러리에 BCrypt가 없다 | 새 dependency 필요 |

**구현 중에 바뀐 점:** 설계에서는 "측정 회원 1명을 회원가입 API로 만들고 그 해시를 복사"하려 했다. 그런데 PawCycle에는 **회원가입 API가 없었다**(`docs/api/current-endpoints.md`에 `POST /api/auth/login`은 있고 가입은 없다). local QA bootstrap이 회원을 만들 수 있지만, 상품·SKU·구독 fixture도 함께 넣어 생성기 manifest(행 수 검사)를 깬다. 그래서 다음처럼 바꿨다.

> 방금 build한 backend jar 안의 Spring Security `BCrypt` 클래스를 꺼내, backend Dockerfile의 build stage와 **같은 pinned JDK 이미지**에서 network 없이 실행해 cost 10 해시를 만든다.

backend의 `SecurityConfig`가 `new BCryptPasswordEncoder()`(기본 cost 10)를 쓰므로 같은 비용이다. 새 이미지나 라이브러리를 추가하지 않았다.

### 3.3 요청 경로: backend 직접 vs nginx 포함

3단계([#549](https://github.com/guseoh/pawcycle-commerce/pull/549))에서 운영 nginx에 IP별 요청 제한을 넣었다. 한 PC에서 부하를 주면 모든 요청이 같은 IP라 바로 429를 받는다. 그러면 backend 성능이 아니라 **nginx 거부를 측정**하게 된다. 그래서 backend에 직접 요청하고, nginx 경로는 "제한이 의도대로 동작하는가"를 보는 별도 항목으로 둔다.

### 3.4 자원 상한

| 대상 | 상한 | 이유 |
| --- | --- | --- |
| backend | `mem_limit 640m`, `cpus 0.75`, `MaxRAMPercentage=65`, read-only root | 운영 compose와 같게. 결과를 운영 backend 한 대와 비교할 수 있게 |
| MySQL | 2 CPU / 2 GiB, binlog 끔 | 운영은 OCI Managed라 사양을 맞출 수 없다. 대신 고정하고 결과와 함께 기록. binlog는 버릴 데이터에 디스크만 쓴다 |

결과는 **같은 PC·같은 상한에서 규모만 바꾼 상대 비교**다. 운영 절대 용량이 아니다.

### 3.5 스케줄러와 fixture

끌 수 있는 작업은 모두 실제 설정 이름으로 끈다.

| 작업 | 설정(환경 변수) | G-1 |
| --- | --- | --- |
| Checkout 결제 만료 | `PAWCYCLE_COMMERCE_CHECKOUT_EXPIRATION_ENABLED` (기본 켜짐) | 끔 |
| 구독 주문 자동화 | `PAWCYCLE_SUBSCRIPTION_AUTOMATION_ENABLED` | 끔 |
| 정기결제 | `PAWCYCLE_COMMERCE_BILLING_ENABLED` | 끔 |
| 회차 보정·배송 알림·멱등성 정리 | 각 `..._ENABLED` | 끔 |
| 지표 갱신 3개 | 끄는 설정 없음 | 켜짐(100만 규모에서 이 조회 비용도 측정 대상) |

**구현 중 발견:** `local-integration` profile에서는 `pawcycle.local-demo-catalog.enabled`가 **기본 켜짐**(`matchIfMissing = true`)이다. 그대로 두면 backend 첫 기동 때 demo 상품이 들어가 생성기가 "schema가 비어 있지 않다"며 멈춘다. 그래서 `PAWCYCLE_LOCAL_DEMO_CATALOG_ENABLED=false`를 명시했다. Spring은 환경 변수의 `_`를 속성 이름의 `.`과 `-` 양쪽으로 맞춰 보므로 이 이름으로 `local-demo-catalog`가 꺼진다.

profile을 `local-integration`으로 둔 이유: 결제·정기결제·환불 adapter가 `@Profile("local-integration")`이면 sandbox 구현이고, 그 밖의 profile은 "사용 불가" 구현이다. G-2의 Checkout 부하에 sandbox 결제가 필요하다. 실제 Toss는 쓰지 않는다.

### 3.6 정기배송 due cohort

`--due-count K`는 id 순서로 **처음 K개 ACTIVE 구독**의 다음 배송일과 회차 날짜를 `--as-of`(기본 2026-11-01)로 옮긴다. 나머지는 2030년 이후다.

- 왜 id 순서인가: 같은 입력이면 같은 K개가 골라져 재현된다.
- 트레이드오프: 회차 날짜가 실행일보다 과거라서, 자동화를 켜면 "지연(overdue)"으로 집계될 수 있다. 오늘 날짜로 두면 실행일마다 데이터가 달라져 재현성이 깨진다. 재현성을 택했고, 해석은 G-2/H에서 시나리오별로 한다.

## 4. 실행 흐름

```text
run-scale.py --scale 10k --seed 42 --due-count 200
  ├─ compose build backend            (infra/local-integration/backend.Dockerfile 재사용)
  ├─ compose up --wait mysql          → perfgen.guard(container)
  ├─ compose up --wait backend        ← Flyway가 V1..V28 + flyway_schema_history 생성
  ├─ compose stop backend
  ├─ perfgen generate                 ← schema_source()가 Flyway 최신 버전 확인
  ├─ perfgen check                    ← 불변식 + manifest
  ├─ cohort()                         ← JDK 컨테이너에서 BCrypt 해시 → members 1..K에 복사
  ├─ compose up --wait backend        → /actuator/health UP
  ├─ login(1, K/2, K) == 200 & /api/auth/me == 200, login(K+1) != 200
  └─ finally: compose down -v → container·network·volume 0개 확인
```

설계 문서는 별도 `schema-bootstrap` 서비스를 두는 안이었다. 구현에서는 **같은 backend 서비스를 두 번 기동**하는 것으로 단순화했다. 서비스가 하나 줄고 설정이 한 곳에만 있다.

## 5. 실행 결과 (10k, seed 42, due 200)

| build | MySQL 기동 | Flyway 첫 기동 | generate | check | cohort | 재기동 | 합계 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 94s | 17s | 52s | 16s | 8s | 13s | 42s | 약 4분 10초 |

- Flyway V28, `schema_source=flyway`, 불변식·manifest 55/55 PASS(due 회차 200개 포함)
- cohort 1,000명. 회원 1·500·1000 로그인과 `/api/auth/me` 200, cohort 밖 1001은 401
- DB 크기 약 44 MB(데이터+인덱스), 정리 후 남은 container·network·volume 0개
- 생성 시간 12.9초. #547 때 1만 규모가 50~85초였던 것보다 짧다. binlog를 끈 영향으로 보이지만 **원인을 분리해 측정하지는 않았다.**

## 6. 코드 읽기

### 6.1 compose: guard 계약을 compose로 옮기기

`infra/performance/scale/compose.yaml`의 MySQL 서비스는 생성기 guard가 요구하는 조건을 그대로 만족하도록 썼다.

```yaml
  mysql:
    image: mysql:8.4.10
    container_name: ${PAWCYCLE_SCALE_DB_CONTAINER:?...}   # pawcycle-perfgen-<run>
    command: [..., --disable-log-bin]
    labels:
      pawcycle.purpose: perf-synthetic-data
    volumes:
      - /var/lib/mysql          # 이름 없는 경로 = 익명 volume
    cpus: 2.0
    mem_limit: 2g
    # ports 없음
```

- `volumes: - /var/lib/mysql`처럼 **이름 없이 경로만** 쓰면 Docker가 64자 hex 이름의 익명 volume을 만든다. guard는 이 이름 형식을 확인해 공유 named volume(`pawcycle-local-integration-*`)을 거부한다.
- `container_name`을 실행 id로 고정해, perfgen이 `docker exec <name>`으로 같은 DB에 접근한다.
- 비밀번호(`MYSQL_ROOT_PASSWORD` 등)는 `${...:?}` 변수로만 받는다. 실행 스크립트가 실행마다 무작위로 만들어 **자식 프로세스 환경 변수로만** 넘긴다. 파일에 쓰지 않는다.

backend는 `127.0.0.1:${PORT}:8080`으로만 연다. 같은 PC 밖에서는 접근할 수 없다.

### 6.2 perfgen: Flyway schema를 받되 확인하고 받기

```python
def schema_source(name, latest):
    present = mysql(name, "... table_name = 'flyway_schema_history'")
    if present == '0':
        return 'raw'                       # perfgen up이 만든 schema
    failed, version = rows(mysql(name, (
        "SELECT SUM(success = 0), MAX(CAST(version AS UNSIGNED)) FROM flyway_schema_history "
        "WHERE version IS NOT NULL")))[0]
    if failed not in ('0', 'NULL') or version != str(latest):
        raise Stop(f'flyway schema is not complete at V{latest} ...')
    return 'flyway'
```

- `CAST(version AS UNSIGNED)`: version은 문자열 컬럼이라 그냥 `MAX`를 쓰면 `'9' > '28'`이 된다. 숫자로 바꿔 비교한다.
- 실패 행이 하나라도 있거나 최신 버전이 저장소의 마지막 migration 번호와 다르면 멈춘다. "다른 branch에서 만든 schema에 지금 생성기 SQL을 붓는" 사고를 막는다.

### 6.3 perfgen: due cohort SQL

```python
def due_cohort_sql(as_of, count):
    due = f"DATE('{as_of}')"
    return (
        "UPDATE subscriptions s JOIN (SELECT id FROM subscriptions WHERE status = 'ACTIVE' "
        f"ORDER BY id LIMIT {int(count)}) d ON d.id = s.id "
        f"SET s.next_order_date = {due}, s.created_date = {due} - INTERVAL s.delivery_cycle_weeks WEEK; "
        "UPDATE subscription_schedules sc JOIN subscriptions s ON s.id = sc.subscription_id "
        "SET sc.scheduled_date = s.next_order_date WHERE sc.scheduled_date <> s.next_order_date;")
```

- MySQL은 `WHERE id IN (SELECT ... LIMIT n)`을 허용하지 않는다. 그래서 `LIMIT`이 있는 subquery를 **derived table로 JOIN**한다.
- 구독과 회차를 같은 날짜로 맞춰야 불변식(열린 회차 규칙)이 깨지지 않는다. 두 번째 UPDATE는 날짜가 달라진 행만 고친다.
- 실행 뒤 "기한이 된 회차 수 = K"를 다시 세어, ACTIVE 구독이 K보다 적으면 멈춘다. manifest 검사도 `manifest_due_schedules_equal_due_count`와 `manifest_no_other_schedule_due`(기한 회차는 모두 ACTIVE 구독의 SCHEDULED 회차)로 바꿨다.

### 6.4 run-scale: jar에서 BCrypt만 꺼내 해시 만들기

```python
def bcrypt_hash(password):
    cid = docker create pawcycle-perf-scale-backend:local
    jar = docker cp {cid}:/app/app.jar -        # tar stream으로 jar를 꺼냄
    script = ('tar -xf - app.jar; '
              'jar xf app.jar $(jar tf app.jar | grep "BOOT-INF/lib/spring-security-crypto-.*\\.jar$"); '
              '... Hash.java: BCrypt.hashpw(System.getenv("PERF_COHORT_PASSWORD"), BCrypt.gensalt(10)) ...'
              'java -cp "$(ls BOOT-INF/lib/spring-security-crypto-*.jar)" Hash.java')
    docker run --rm -i --network none -e PERF_COHORT_PASSWORD <JDK 이미지> sh -c script   (stdin = jar)
```

(위는 흐름을 줄인 의사 코드다. 실제 코드는 `subprocess.run` 호출이다.)

- **왜 JDK 이미지인가:** backend 이미지는 JRE라 `jar` 도구와 소스 직접 실행(`java Hash.java`, 컴파일러 필요)이 없다. Dockerfile build stage와 같은 `eclipse-temurin:25.0.3_9-jdk-noble`이라 새 이미지를 들이지 않는다.
- **왜 `BCrypt` 클래스를 직접 쓰나:** `BCryptPasswordEncoder`는 로깅 라이브러리(commons-logging)에 의존한다. `BCrypt`의 정적 메서드는 crypto jar 하나만으로 실행된다.
- **비밀번호 전달:** `docker run -e PERF_COHORT_PASSWORD`처럼 **값 없이 이름만** 주면, Docker가 호출한 프로세스의 환경 변수에서 값을 가져온다. 그래서 비밀번호가 명령행 인자(프로세스 목록에 보임)에 나타나지 않는다.
- `--network none`: 해시 계산에는 network가 필요 없다.
- 결과는 정규식 `\$2[aby]\$10\$[./0-9A-Za-z]{53}`로 형식을 확인한 뒤에만 DB에 넣는다.

### 6.5 run-scale: 실패하면 반드시 지우기 (Codex P2 반영)

```python
    try:
        ... 생성·검사·로그인 ...
        failed = verification_failures(summary)
        if failed:
            summary['verification_failed'] = failed
    except BaseException as error:
        summary['error'] = ...
        raise
    finally:
        # 검증을 통과한 환경만 남긴다.
        if args.keep and 'error' not in summary and 'verification_failed' not in summary:
            summary['kept'] = True
        else:
            summary['cleanup'] = down(env, project, container)
```

처음 구현에서는 로그인 검증을 `finally` **뒤**에서 했다. `login()`은 실패해도 예외가 아니라 상태 코드를 돌려주므로, `--keep`이면 로그인이 401이어도 환경이 남고 `kept: true`가 출력된 다음에야 종료 코드 3으로 끝났다. Codex 리뷰가 이것을 P2로 지적했다. 판정을 `try` 안으로 옮겨 "검증 실패 = 중단과 같은 취급"으로 바꾸고 `verification_failures()` 단위 테스트를 더했다.

`down()`은 지우기 전에 다시 `perfgen.guard()`를 호출한다. 실행 id를 잘못 줘도 perfgen 규칙에 맞지 않는 container는 지우지 않는다. 지운 뒤에는 compose project label로 container·network를, 기억해 둔 이름으로 익명 volume을 다시 조회해 0개인지 확인한다.

### 6.6 테스트 (Docker 없이)

- `test_perfgen.py` 9개: 기존 guard·결정성 테스트에 더해 due cohort SQL(ACTIVE만, 결정적, DDL 없음)과 Flyway 버전 확인(raw/flyway/버전 불일치/실패 행)을 추가했다.
- `test_run_scale.py` 6개: 실행 id가 perfgen 이름 규칙 안에 들어가는지, MySQL이 guard 계약을 지키는지, backend가 `127.0.0.1`·운영 상한인지, 끌 수 있는 작업이 기본 끔인지, 존재하지 않는 `PAWCYCLE_SCHEDULER_ENABLED`가 없는지, 검증 실패 판정.
- 이 테스트들은 CI workflow에 연결되어 있지 않다(기존 perfgen 테스트도 로컬 실행 전용).

## 7. 리뷰와 CI에서 배운 것

| 사건 | 원인 | 처리 |
| --- | --- | --- |
| Codex P2: 검증 실패한 `--keep` 환경이 남음 | 판정 위치가 `finally` 뒤 | 6.5절처럼 수정, 테스트 추가 |
| CI conventions 실패 1 | PR 본문 `실행 구분: 저장소 변경 (설명)` — 값 뒤에 괄호 설명을 붙임 | 허용 값만 쓰도록 수정 |
| CI conventions 실패 2 | 검증기는 `- 포함 범위: 값`처럼 **같은 줄** 값만 읽는다. 하위 bullet만 있으면 빈 값 | 라벨 뒤에 한 줄 요약 추가 |
| compose lane 실패 | backend 이미지 build 중 Gradle이 plugins.gradle.org에서 Spring Boot 4.1.0 artifact를 찾지 못함(외부 저장소 문제) | 재실행으로 통과 |
| 재실행해도 conventions 실패 | Actions 재실행은 **처음 이벤트의 PR 본문**을 다시 쓴다 | PR을 닫았다 다시 열어(`reopened`) 현재 본문으로 새 실행 → 9 job 통과. [PWL-0054](../lessons/PWL-0054.md) |

CodeRabbit은 이 저장소에서 수동 트리거가 필요해 실행되지 않았고, Codex는 수정 커밋을 다시 리뷰하지 않았다.

## 8. 한계와 다음 단계

- 10만·100만은 아직 실행하지 않았다(H). 100만 생성은 1~2시간이 걸릴 수 있고, 2시간을 넘으면 생성기를 먼저 개선한다.
- 상품 목록 cache(Redis)와 Redis 세션 없이 측정한다. 운영에서 cache를 켜면 탐색 요청 결과가 달라진다.
- due 회차가 과거 날짜라 overdue 집계와 겹친다(3.6절).
- G-2: 혼합 부하 k6(탐색 70 / 로그인 사용자 조회 15 / 쓰기 10 / 로그인 5, 예열 2분 + 정상 10분)와 서버 지표 수집·보고서 형식.
- G-0(선택): `catalog-isolated` compose의 가짜 스케줄러 설정 수정.
