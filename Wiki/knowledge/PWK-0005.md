# PawCycle 2단계 학습 노트 — 장애 관측과 로깅

## 이 노트를 읽는 법

로드맵 2단계(2026-11-15 설계 → 2026-11-17 종료)를 되돌아보기 위한 노트다. 관측은 "지표 → 로그 → 알림 → 리허설" 순서로 쌓았다. 각 절에서 **왜 이 신호가 필요했나, 코드가 왜 이런 모양인가, 리허설에서 무엇이 틀렸나**를 본다.

## 1. 문제: "HTTP는 정상인데 업무가 멈춘 상태"

2단계 시작 시점의 관측 상태는 다음과 같았다.

- 업무 지표는 반품·환불·결제 UNKNOWN을 합친 숫자 하나뿐이었다. 고립 PROCESSING 결제(#417)는 빠져 있었고, 가장 오래된 건이 얼마나 지났는지도 없었다.
- 기한이 지났는데 주문되지 않은 정기배송 회차, 구독 자동화의 마지막 성공 시각이 없었다.
- HTTP·DB 기본 지표는 노출됐지만 알림 규칙이 없었다.

결제 만료 스케줄러가 멈춰도 API는 200을 돌려준다. 고객 결제가 확정되지 않은 채 쌓여도 HTTP 지표는 깨끗하다. 그래서 2단계의 핵심은 **업무 상태를 직접 재는 지표와, 그것이 멈췄을 때 울리는 알림**이었다.

## 2. 사용자가 정한 방향

| 결정 | 선택 | 이유 |
| --- | --- | --- |
| 범위 | 운영 배포가 당장 어려워 **로컬 감지·리허설까지**. 운영 반영은 3단계 | 운영 반영 없이도 감지 설계와 리허설을 검증할 수 있다 |

| 로깅 고도화 | 이번 기회에 함께 진행 | 알림이 울린 뒤 원인을 찾는 단계가 로그다 |
| Sentry | 검토했지만 이번 범위에는 넣지 않음 | 사용자가 로컬 단계에 과한지 물었고, 구조화 로그 + Loki로 대체했다. 오류 그룹화·릴리스 추적 같은 Sentry 고유 기능은 이후 운영 단계에서 다시 볼 수 있다 |

| 임계값 | 잠정값으로 시작, 4단계 기준선 뒤 확정 | 정상 기준선이 아직 없다 |

설계를 한 번 다시 했다: 첫 설계 검토에서 결함이 나와 사용자가 "2단계 자체 설계를 재진행"을 요청했고, 로깅 영역을 따로 깊게 분석한 뒤 구현에 들어갔다.

## 3. 외부 호출 실패 분류 (#536)

### 3.1 왜

결제사·AI 호출이 실패하면 지금까지는 "실패" 하나였다. 그러나 대응이 다르다. 타임아웃·연결 실패·결제사 5xx는 **상대 쪽 장애**이고, 응답을 못 읽는 것(PARSE)이나 그 밖의 예외(INTERNAL)는 **우리 코드 결함**일 가능성이 높다.

### 3.2 코드 읽기

```java
public enum FailureClass {
  TIMEOUT(false), CONNECT(false), PROVIDER_5XX(false), PROVIDER_REJECTED(false),
  PARSE(true),      // 응답은 왔는데 읽지 못함
  INTERNAL(true);   // 그 밖의 모든 것: 우리 코드 결함일 가능성
  public boolean error() { ... }   // true면 ERROR 로그 + stack trace
}

public static FailureClass classify(Throwable failure) {
  for (Throwable current = failure; current != null && seen.add(current); current = current.getCause()) {
    FailureClass known = direct(current);
    if (known != null) return known;
  }
  return FailureClass.INTERNAL;
}

private static FailureClass direct(Throwable failure) {
  if (failure instanceof HttpConnectTimeoutException) return FailureClass.CONNECT;   // ① 먼저
  if (failure instanceof HttpTimeoutException || ...) return FailureClass.TIMEOUT;
  ...
  if (failure instanceof OpenAIInvalidDataException || failure instanceof JacksonException) return FailureClass.PARSE;
  if (failure instanceof IOException) return FailureClass.CONNECT;                   // ② 나중
  return null;
}
```

- **cause chain을 따라간다.** 실제 원인은 여러 겹 감싼 예외 안쪽에 있다. `seen`(identity set)으로 순환 cause를 막는다.
- **검사 순서가 의미다.** ① `HttpConnectTimeoutException`은 `HttpTimeoutException`의 하위 타입이지만 "결제사에 닿지도 못함"이라 CONNECT다. ② JSON 읽기 실패는 `IOException`이기도 해서, PARSE 검사를 IOException보다 먼저 둔다.
- 기본값이 INTERNAL이다. 모르는 예외를 결제사 장애로 보고하지 않는다.
- 분류는 **로그와 지표만** 바꾼다. 결제 상태 전이(예: UNKNOWN 유지)는 그대로다. 관측 작업이 업무 동작을 바꾸지 않게 한 경계다.

### 3.3 메시지를 지운 예외 — `RedactedFailure`

```java
public final class RedactedFailure extends RuntimeException {
  private RedactedFailure(Throwable original, Throwable cause) {
    super(original.getClass().getName() + " (message removed)", cause, false, true);
    setStackTrace(original.getStackTrace());
  }
}
```

예외 메시지에는 결제사 응답 원문(JSON 파서가 예상 못 한 토큰으로 paymentKey를 인용할 수 있다)이나 SQL 값이 들어갈 수 있다. 공통 실패 기록기는 **타입과 stack frame만 남기고 메시지는 지운 복사본**을 로그에 쓴다. cause도 같은 방식으로 최대 16단계까지 복사한다.

## 4. 스케줄 작업 지표 (#537)

```java
static final String JOB_TAG = "job_name";   // "job"이 아니다

public ScheduledJobRunner(MeterRegistry registry, Clock clock) {
  // 미리 등록: 한 번도 성공하지 않은 작업도 시계열이 존재한다
  for (ScheduledJob job : ScheduledJob.values()) meters.put(job, new Meters(registry, job));
}

private int execute(ScheduledJob job, IntSupplier work) {
  MDC.put("jobName", job.tag());
  MDC.put("jobRunId", UUID.randomUUID().toString());
  try {
    int items = work.getAsInt();
    jobMeters.success(items, elapsed, clock.millis());
    return items;
  } catch (RuntimeException failure) {
    jobMeters.failure(elapsed);
    log.error("Scheduled job failed; ...", ..., RedactedFailure.of(failure));
    return 0;                 // 다시 던지지 않는다
  } finally { restore MDC }
}
```

| 설계 | 이유 |
| --- | --- |
| 태그 이름 `job_name` | Prometheus는 `job` label을 scrape 대상 이름으로 쓴다. 같은 이름의 태그는 `exported_job`으로 바뀌어 쿼리가 어긋난다(구현 중 실제로 부딪혔다) |
| 미리 등록 | 처음엔 첫 실행 때 meter를 만들었다. 한 번도 안 돈 작업은 시계열이 없어 "정지" 알림이 울리지 않았다 |
| 마지막 성공 시각이 없으면 `NaN` | 꺼진 작업을 0(= 1970년에 성공)으로 오인하지 않는다 |
| 실패를 다시 던지지 않음 | fixed-delay 스케줄은 예외가 나도 다음 실행이 돈다. 여기서 한 번만 기록하고 로그 중복을 막는다 |
| MDC `jobName`·`jobRunId` | 한 실행의 모든 로그 줄을 한 번에 찾는다 |

## 5. 업무 적체 지표 (#538)

결제·환불·정기배송 적체를 종류별로 나눴다. 기존 방식대로 스케줄 작업이 조회 결과를 캐시에 채우고, Prometheus가 수집할 때는 캐시만 읽는다(수집 때마다 DB를 치지 않는다). 주문·회원 ID는 태그에 넣지 않는다(시계열 폭발 방지).

판단이 필요했던 지점: **일반 PROCESSING 결제의 "경과 시간"을 무엇으로 재나.** `payments`에는 PROCESSING으로 바뀐 시각 컬럼이 없다. Checkout 시각으로 재면, 결제창을 늦게 연 정상 결제도 고립 결제처럼 보인다. 그래서 `expires_at`(결제창 만료) 기준으로 재고, #417 복구 명령의 대상 조건(만료 + 10분)과 같은 정의를 썼다. 지표와 복구 명령이 같은 기준을 써야 "알림이 울린 건 = 복구 대상"이 된다.

## 6. 구조화 로그와 요청 ID (#539, #540)

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class RequestCorrelationFilter extends OncePerRequestFilter {
  private static final Pattern SAFE_REQUEST_ID = Pattern.compile("[A-Za-z0-9._-]{1,64}");
  protected void doFilterInternal(...) {
    String requestId = requestId(request);          // 안전한 X-Request-ID면 재사용, 아니면 UUID
    MDC.put("requestId", requestId);
    response.setHeader("X-Request-ID", requestId);  // 고객이 문의할 때 인용할 수 있게
    try { filterChain.doFilter(request, response); } finally { MDC.remove("requestId"); }
  }
}
```

- **가장 먼저 실행**(`HIGHEST_PRECEDENCE`)한다. Spring Security의 401/403 처리기는 뒤의 필터를 부르지 않고 응답을 쓰므로, 보안 필터보다 뒤에 있으면 인증 실패 로그에 요청 ID가 빠진다.
- 들어온 ID는 **정규식으로 검사한 뒤에만** 쓴다. 헤더 값을 그대로 로그에 넣으면 로그 위조(줄바꿈 삽입)가 가능하다.
- 오류 응답(`ApiErrorResponse`)에도 requestId를 넣었다(#540). 화면의 오류 → 로그 한 줄로 바로 간다.
- 로그 형식은 ECS JSON(`PAWCYCLE_LOG_FORMAT=ecs`). local-integration nginx도 query string 없는 JSON access log로 바꿨다. 운영 nginx·compose는 배포 도구의 **승인 지문 계약** 때문에 2단계에서 바꾸지 않았다(3단계에서 처리).

구현 중 막힌 것: Spring Boot는 테스트 context가 캐시돼 있으면 로깅 시스템을 다시 초기화하지 않는다. 로그 형식 테스트가 다른 테스트 순서에 따라 깨졌다. 그래서 `StructuredLogEncoder`를 직접 만들어 쓰는 격리된 테스트 도구로 바꿨다.

## 7. 업무 이벤트 로그 (#541)

```java
BusinessEvent.of(BusinessEvent.Name.PAYMENT_RECOVERY_FINISHED)
    .with(BusinessEvent.Field.PAYMENT_ID, paymentId)
    .with(BusinessEvent.Field.OUTCOME, outcome.name())
    .log();
```

- 이벤트 이름과 필드 이름이 **enum으로 고정**돼 있다. 자유 문자열을 넣을 방법이 없다. 문자열 값은 `[A-Za-z0-9_.:-]{1,64}`만 통과하고, 나머지는 `INVALID`로 바뀐다. 이름·주소·이메일·결제 키가 실수로 로그에 들어갈 길을 구조적으로 막았다.
- **commit 이후에 기록**한다. 트랜잭션 동기화가 켜져 있으면 `afterCommit`에 등록한다. 롤백된 작업이 "결제 확정 완료"로 로그에 남지 않는다.
- JSON 키를 `event`가 아니라 `businessEvent`로 쓴다. ECS가 `event.*`를 자기 객체로 예약하고 있다.

## 8. 스케줄러 스레드 분리 (#542, O7)

```java
// SchedulerNames
// default scheduler(scheduling-1): DB 업무 작업, 하나씩
// METRICS: 지표 갱신 — 업무 작업이 밀려도 관측은 굶지 않는다
// PROVIDER_CALLS: 결제사를 기다리는 작업(정기결제, 호출당 최대 10초)
```

Spring의 기본 스케줄러는 스레드가 하나다. 정기결제가 결제사 응답을 기다리는 동안 결제 만료와 구독 자동화가 줄을 서고, **지표 갱신까지 멈춰** 정지 알림이 거짓으로 울린다. 설계 문서의 O7 항목에서 "그대로 두기 / 공용 풀 크기 늘리기 / 역할별 전용 스레드"를 비교했고, 사용자가 역할별 분리(C)를 골랐다.

- 공용 풀을 키우면 지금까지 한 스레드에서 차례로 돌던 DB 업무 작업들이 **서로 동시에** 돌기 시작한다. 1단계에서 확인한 동시성 전제가 바뀌고, 느린 작업이 여럿이면 여전히 풀을 다 차지할 수 있다.
- 역할별 전용 스레드는 DB 업무 작업의 실행 방식(하나씩)을 그대로 두면서, 관측(지표)과 외부 대기(결제사)를 떼어 낸다. 대가는 스레드 수가 고정이라 같은 역할 안의 지연은 여전히 줄을 선다는 점이다.

구현 중 막힌 것: 테스트에서 `getPoolSize()`로 스레드 수를 확인했더니 값이 흔들렸다. 이 메서드는 **현재 살아 있는 스레드 수**다. 설정값은 `getCorePoolSize()`로 봐야 한다.

## 9. 로컬 관측 스택 (#543)

```text
backend(ECS JSON 로그, /actuator/prometheus)
  ├─ Alloy → Loki        (로그. label은 service, level만. requestId 등은 JSON 필드로 검색)
  └─ Prometheus → Alertmanager → Discord(critical / warning 채널)
Grafana: 지표 대시보드 + 로그 대시보드
```

- 이미지 버전은 모두 고정(Loki 3.7.9, Alloy v1.21.3, Prometheus v3.13.2, Alertmanager v0.28.1, Grafana 13.1.3).
- **label에는 값이 적은 것만 넣는다**(service, level). requestId를 label로 올리면 요청마다 새 stream이 생겨 Loki가 무거워진다. 검색은 JSON 필드로 한다.
- Discord webhook URL은 파일로만 주입한다. 저장소·채팅·로그에 넣지 않는다.
- `test-observability-config.sh`가 각 도구의 자체 검사기(promtool 규칙 문법·단위 테스트, amtool 설정·라우팅, Loki `-verify-config`, Alloy fmt)로 설정을 검증한다.

## 10. 알림 규칙 읽기

```yaml
- alert: PawCycleStuckProcessingPayment
  expr: pawcycle_payment_stuck{kind="normal_processing"} > 0
  for: 1m
  keep_firing_for: 2m

- alert: PawCycleApiLatencyP95
  expr: |
    histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket{uri=~"/api/.*"}[5m]))) > 1
    and sum(rate(http_server_requests_seconds_count{uri=~"/api/.*"}[5m])) > 0.2
  for: 10m

- alert: PawCycleDbConnectionAcquireFailure
  expr: |
    sum(increase(hikaricp_connections_timeout_total[2m])) > 0
    and max(hikaricp_connections_pending) > 0
  for: 1m
  keep_firing_for: 2m
  labels: { severity: critical }
```

| 장치 | 의미 | 왜 넣었나 |
| --- | --- | --- |
| `for` | 조건이 이 시간 동안 계속돼야 firing | 순간 튐을 거른다 |
| `keep_firing_for: 2m` | 조건이 사라져도 2분 더 firing 유지 | backend 재시작으로 지표가 잠깐 사라지면 원인이 그대로인데 resolved가 갔다(리허설 실측 3건) |
| 요청량 하한 `> 0.2` rps | 요청이 적으면 판정하지 않음 | 분당 몇 건일 때는 느린 요청 하나가 곧 p95다. DB 복구 3분 뒤에 늦게 울렸다 |
| 두 조건 `and` | 시간 초과가 있었고 **지금도** 기다리는 요청이 있음 | 지난 일만으로 critical을 보내지 않는다 |

**억제(inhibit):** backend를 수집할 수 없을 때는 그 밖의 알림이 소음이라 장애 하나만 보낸다. DB 커넥션 획득 실패 중에는 **즉시 풀리는 결과(DB 대기 알림) 하나만** 억제한다. 처음엔 넓게 억제했는데, 시간창 알림(작업 실패 10분, ERROR 급증 5분, p95·5xx 5분)은 복구 뒤에도 창이 남아 firing이라, 억제하면 resolved 직후로 **밀려서** 올 뿐 메시지 수가 줄지 않았다(#546, Codex P2).

## 11. 장애 리허설 (#544)

일회용 compose project에서 실제로 장애를 일으키고 신호를 기록했다. 실제 Toss·AI 호출은 backend에서 해당 호스트를 loopback으로 고정해 막았다.

| 시나리오 | 결과 |
| --- | --- |
| backend 중단 | 57초 뒤 critical, 복구 후 resolved |
| MySQL 중단 | warning만(DB 대기·작업 실패·ERROR 급증). critical 없음 → #546에서 critical 추가, 2분 9초 뒤 수신 |
| 고립 PROCESSING 결제 | 75초 뒤 critical, 복구 명령으로 성공 확정 후 resolved |
| 정기배송 지연 | 30분 뒤 warning, 재개 후 처리 |
| Checkout 만료 지연 | warning, 재개 후 EXPIRED·예약 해제, RESERVE = DEDUCT + RELEASE |
| 외부 호출 실패 | connect 실패 5건, 21초 뒤 warning |
| 외부 호출 INTERNAL | 재현 수단 없음 → SKIP(규칙 테스트만) |

리허설로 드러난 결함(모두 #544에서 수정):

- 로컬 compose가 리팩터링 전 환경 변수 이름을 써서 **회차 보정이 꺼져 있었다.** "설정했다"와 "효과가 있다"는 다르다(4단계 G에서도 같은 일이 반복됐다).
- 장애 기준선 검증 스크립트가 #543 이후 구조 변화로 동작하지 않았다.
- 재시작 시 거짓 resolved → `keep_firing_for`.
- 저트래픽 p95 지연 → 요청량 하한.
- 1시간 주기로 다시 켜진 회차 보정이 10분 정지 규칙에 걸림 → 정지 규칙에서 제외.

정상 기준선: 초당 약 2건 6분, p50 32ms, p95 151ms, 5xx 0, 커넥션 대기 0. 감지·전달·복구를 **따로** 판정했다([PWC-0066](../decisions/PWC-0066.md)의 감지·전달 분리).

## 12. 실제 Discord 전달 (#551)

사용자가 직접 webhook URL을 입력해 critical·warning 시험 알림과 resolved 4건을 Discord에서 확인했다(2026-11-17). 같은 절차를 `verify-discord-delivery.ps1`로 저장소에 넣었다. URL은 화면·로그에 남기지 않는다. 이로써 2단계를 로컬 검증 범위에서 종료했다.

## 13. 남은 것

- MySQL 중단 한 번에 오는 메시지 수는 크게 줄지 않았다(작업 실패 warning이 critical보다 먼저 온다).
- INTERNAL 외부 호출, 5xx 비율, 구독 자동화 실패 알림은 실행 리허설 없이 규칙 테스트만 했다.
- 임계값은 모두 잠정값이다. 4단계 기준선 뒤 사용자가 확정한다(I).
- `keep_firing_for` 2분은 2분 넘는 재시작의 거짓 resolved를 막지 못한다.
