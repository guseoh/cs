# PawCycle 4단계 G-2 학습 노트 — 혼합 부하 측정 도구와 1만 기준선

## 이 노트를 읽는 법

G-1([PWK-0003](PWK-0003.md))이 "합성 데이터 위에 backend를 띄우는 환경"이었다면, G-2는 **그 환경에 실제와 비슷한 혼합 부하를 주고, 서버·DB 지표와 함께 한 번에 기록하는 도구**다. 이 노트는 설계 선택지, 코드가 왜 그런 모양인지, 리뷰 7건과 내가 만든 버그를 어떻게 잡았는지를 남긴다.

- 기준 코드: `main` [`318dfab4`](https://github.com/guseoh/pawcycle-commerce/commit/318dfab4fb1a40fb69236cbec4f7c6a080ab8325) ([#556](https://github.com/guseoh/pawcycle-commerce/pull/556) `a238c796` + [#557](https://github.com/guseoh/pawcycle-commerce/pull/557))
- 구현: G-2는 k6 script·Python 실행기·보고서라 분담상 Claude가 구현했다([PWC-0140](../decisions/PWC-0140.md)).
- 수치는 로컬 Windows Docker Desktop 1회 측정이다. 운영 용량이 아니다.

## 1. 무엇을 만들었나

```text
run-mixed.py --scale 10k --seed 42 --rps 20 --warmup 120 --steady 600
  ├─ run-scale.py --keep                       (G-1 환경: MySQL + Flyway + 생성 + backend)
  ├─ 새 cohort 비밀번호 → 세션 150개 미리 로그인  (VU당 회원 1명)
  ├─ 상품·SKU 표본 준비                          (#557: 측정 구간 밖)
  ├─ k6 예열 실행                               (기록만, 판정하지 않음)
  ├─ 기준점: DB digest 초기화, row lock 상태, /actuator/prometheus
  ├─ k6 측정 실행 + 10초마다 /actuator/prometheus 수집
  ├─ 상위 SQL digest 10개, row lock 증가량, 서버 지표 증가량·최댓값
  ├─ perfgen check --no-manifest                (쓰기 뒤 불변식)
  └─ 판정 → 환경 정리
```

| 묶음 | 비율(iteration) | 요청 |
| --- | --- | --- |
| browse | 70% | 목록 40%, 검색 15%, 카테고리 15%, 상세 30% |
| member | 15% | 내 주문 / 장바구니 / 구독(돌아가며) |
| write | 10% | 장바구니 담기 → 장바구니 조회 → Checkout → sandbox 결제 확인 |
| login | 5% | CSRF → 로그인(BCrypt) |

## 2. 설계 선택지와 트레이드오프

### 2.1 부하 모델: 요청률 고정(open) vs 사용자 수 고정(closed)

| 모델 | 동작 | 문제 |
| --- | --- | --- |
| closed(VU 수 고정, 끝나면 다음 요청) | 서버가 느려지면 요청 간격이 벌어져 **부하가 저절로 줄어든다** | 느려질수록 덜 때리니 병목이 숨는다 |
| **open(`constant-arrival-rate`, 채택)** | 정해진 간격으로 iteration을 시작한다. 서버가 느리면 VU를 더 써서라도 요청률을 지킨다 | VU가 모자라면 시작하지 못한 iteration이 `dropped`로 남는다 → 이것을 판정에 넣는다 |

묶음마다 시나리오를 하나씩 두고 `timeUnit: '1m'`로 계산한다. 20 iteration/s의 5%는 초당 1이지만 RPS가 바뀌면 소수가 될 수 있다. 분 단위면 `20 × 60 × 0.05 = 60`처럼 정수가 된다.

### 2.2 예열과 측정: 한 번 실행 vs 두 번 실행

첫 구현은 한 번의 k6 실행 안에서 "시작 후 2분이 지난 iteration만 기록"하는 방식이었다. 바꾼 이유는 다음과 같다.

- DB digest와 서버 지표는 **k6 밖**에 있다. 한 번 실행이면 "예열이 언제 끝났는지"를 실행기가 정확히 알 수 없다(k6 `setup()`의 세션 로그인 시간만큼 어긋난다).
- 두 번으로 나누면 실행기가 두 실행 사이에 `TRUNCATE performance_schema.events_statements_summary_by_digest`와 지표 기준점을 정확히 찍을 수 있다.
- 대가: 두 실행 사이에 몇 초 공백이 있다. backend JVM은 그대로라 예열 효과는 유지된다.

### 2.3 로그인 세션: k6 setup vs 실행기가 미리

- k6 `setup()`에서 150명을 로그인하면 실행마다 BCrypt 150회가 측정 구간 앞에 붙고, 예열·측정 두 실행에서 두 번 한다.
- 그래서 **실행기(Python)가 한 번 로그인**하고 세션 목록을 k6 두 실행에 같이 넘긴다.
- 넘기는 방법: 처음엔 환경 변수(`SCALE_SESSIONS`)였는데, 세션 150개 JSON이 Windows 환경 변수 한 개 상한(32,767자)에 가까웠다. 시스템 임시 폴더의 파일(`SCALE_SESSIONS_FILE`)로 넘기고 실행 끝에 지운다. 저장소에는 쓰지 않는다.

### 2.4 VU와 회원 매핑

```js
function mySession() {
  return SESSIONS[exec.vu.idInTest - 1];
}
```

- `exec.vu.idInTest`는 **시나리오를 넘어 고유한** VU 번호다. 모든 VU 번호에 회원을 하나씩 주면 두 VU가 같은 장바구니를 쓰지 않는다(같은 장바구니면 cart version 충돌로 쓰기 오류가 섞인다).
- 그래서 세션 수는 모든 시나리오 `maxVUs`의 합(150)이다. browse VU에게도 세션이 배정되지만 쓰지 않는다. 단순함을 택했다.
- login 묶음은 세션에 쓰지 않은 **cohort 뒤쪽 절반**(501~1000)만 쓴다. 세션용 회원과 겹치지 않게 해서, 같은 회원의 반복 로그인이 기존 세션에 영향을 주는지 따로 따질 필요를 없앴다.

### 2.5 판정: 무엇을 실패로 볼까

| 판정(측정 구간) | 이유 |
| --- | --- |
| 묶음별 응답 계약 위반 1% 이상 → k6 종료 99 | 틀린 응답이 빠르면 의미 없다 |
| `dropped` iteration > 0 | 요청률을 지키지 못했다 |
| 시작했지만 끝나지 않은 iteration > 0 (#556 리뷰) | 측정 끝에 잘린 요청은 오류율에도 안 잡힌다 |
| steady k6 종료 코드 ≠ 0 (#556 리뷰) | 외부 신호로 끊긴 k6도 그럴듯한 요약을 남길 수 있다 |
| 쓰기 뒤 불변식 위반 | 부하가 데이터를 깨면 안 된다 |

**지연 기준(탐색 p95 < 300ms 등)은 판정하지 않고 기록만 한다.** 기준 미달은 측정 실패가 아니라 5단계 후보이기 때문이다.

## 3. 코드 읽기

### 3.1 시작·완료 카운터로 중단 세기

```js
function iteration(bundle, body) {
  metrics[bundle].started.add(1);
  body();
  metrics[bundle].finished.add(1);
}
export function write(data) { iteration('write', () => writeOnce(data)); }
```

- gracefulStop에서 잘리거나 예외로 끝난 iteration은 두 번째 `add`에 도달하지 못한다. `started − finished`가 중단 수다.
- `try/finally`를 쓰지 않은 이유: 중단(interrupt)이 finally를 실행하는지 k6 동작에 기대지 않으려고, "정상 경로의 마지막 줄"에만 완료를 둔다. 조기 `return`(오류로 다음 단계를 건너뜀)은 정상 완료로 센다. 오류는 이미 `record()`로 기록됐기 때문이다.

### 3.2 예외를 던지지 않는 JSON 읽기

```js
// A body that is not valid JSON is a contract failure, not an exception.
function jsonOf(response, selector) {
  try {
    // json(undefined) is not json(): k6 treats the argument as a selector path.
    return selector === undefined ? response.json() : response.json(selector);
  } catch (error) {
    return undefined;
  }
}
```

- `response.json()`은 본문이 JSON이 아니면 예외를 던진다. 그러면 `record()`가 실행되지 않아 **오류율에서 빠진다**(CodeRabbit Major).
- 두 번째 줄의 분기는 내가 만든 버그를 고친 흔적이다. 처음엔 `return response.json(selector)` 한 줄이었는데, `jsonOf(checkout)`처럼 selector 없이 부르면 `json(undefined)`가 되고 k6는 이것을 경로로 해석해 `undefined`를 돌려줬다. 결과적으로 **모든 Checkout이 실패**로 기록됐다. 짧은 시험 실행에서 새로 넣은 "steady 종료 코드 ≠ 0" 판정이 바로 잡았다([PWL-0055](../lessons/PWL-0055.md)).

### 3.3 인증 요청에 세션 고정

```js
function authParams(session, name, extraHeaders) {
  return {
    cookies: { JSESSIONID: { value: session.sessionId, replace: true } },
    headers: Object.assign({ 'X-CSRF-TOKEN': session.csrf, 'Content-Type': 'application/json' }, extraHeaders || {}),
    tags: { name },
  };
}
```

k6 VU는 자기 cookie jar를 가진다. login 묶음이 jar에 남긴 다른 세션 쿠키가 섞이면 엉뚱한 회원으로 요청이 간다. `replace: true`로 이 요청의 JSESSIONID를 강제한다.

### 3.4 Checkout 멱등 키

```js
const key = `g2-${data.runTag}-${exec.vu.idInTest}-${exec.scenario.iterationInTest}`;
```

`runTag`는 실행마다 `${PHASE}-${Date.now()}`다. 같은 DB에서 예열·측정을 두 번 돌리면 VU 번호와 iteration 번호가 다시 0부터 시작한다. runTag가 없으면 측정의 Checkout이 예열 때와 같은 키를 다시 쓴다. 그러면 저장된 멱등 결과가 돌아오거나(실제 처리 없이 빨라짐) 요청 내용이 달라 거절된다. 어느 쪽이든 측정이 왜곡된다.

### 3.5 Prometheus 텍스트 파싱(실행기)

```python
def parse_prometheus(text):
    for line in text.splitlines():
        ...
        if value != value:   # NaN
            continue
```

- 마지막 성공 시각 지표는 한 번도 성공하지 않은 작업에서 `NaN`이다(2단계 설계, [PWK-0005](PWK-0005.md)). 이것을 0으로 더하면 "1970년에 성공"이 된다. 파싱 단계에서 버린다.
- `server_summary(before, after, sampled)`: 카운터(타임아웃, GC, 요청 수, 5xx, 작업 실행)는 **측정 전후 차이**, 게이지(Hikari 활성·대기, heap, CPU)는 **10초 표본의 최댓값**이다. 게이지는 순간값이라 차이가 의미 없다.

### 3.6 기존 환경을 지우지 않기(Codex P1)

```python
if subprocess.run(['docker', 'inspect', container], capture_output=True).returncode == 0:
    raise Stop(f'{container} already exists; remove it with run-scale.py --down {run} first')
...
if up.returncode:
    raise Stop(...)          # run-scale은 실패하면 자기가 만든 것을 스스로 지운다
created = True               # 이제야 이 실행이 환경을 소유한다
```

처음엔 `run-scale.py`를 부르기 **전에** `created = True`였다. 같은 `--run` 이름으로 `--keep`해 둔 환경이 있으면 `run-scale`은 생성을 거부하는데, 실행기의 `finally`가 그 기존 환경을 지워 버렸다. "자식의 보호 장치가 부모의 정리 코드 때문에 오히려 삭제를 일으키는" 구조였다.

### 3.7 k6 자체 시험(#557)

`selftest/scale-mixed-selftest.py`는 Python `ThreadingHTTPServer`로 API 흉내를 내는 loopback stub을 띄우고 k6를 두 번 돌린다.

| 모드 | stub의 Checkout | 기대 | 결과 |
| --- | --- | --- | --- |
| ok | 정상 JSON | 종료 0, 쓰기 오류 0, 결제 확인 호출 있음 | 종료 0, 결제 확인 7회 |
| bad-json | 200 + `<html>not json</html>` | 종료 99, Checkout 계약 오류, 결제 확인 0회, 중단 0 | 종료 99, Checkout 오류 6, 결제 확인 0, 중단 0 |

DB나 backend 없이 40초 안에 쓰기 경로의 판정을 증명한다. 수정 전 코드에서 이 시험이 실패하는지는 돌려 보지 않았다.

## 4. 1만 규모 기준선 (20 iteration/s, 예열 2분 + 측정 10분)

| 묶음 | 요청 수 | p50 | p95 | p99 | 오류 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 탐색 | 8,401 | 9.8ms | 26.5ms | 34.1ms | 0 |
| 회원 조회 | 1,801 | 5.0ms | 12.7ms | 20.1ms | 0 |
| 쓰기(요청 단위) | 4,804 | 10.5ms | 18.4ms | 35.9ms | 0 |
| 로그인(POST만) | 601 | 63.9ms | 83.7ms | 151.1ms | 0 |

- 서버: HTTP 16,477건, 5xx 0, Hikari 활성 최대 2·대기 0·획득 시간 초과 0, GC 94회·0.294초, heap 최대 133MiB, CPU 최대 39%.
- DB: row lock 대기 0. 총 실행 시간 1위는 상품 목록 조회 SQL(5,891회, 평균 5.09ms, 읽은 행 514만). 2위 `COMMIT`, 3·4위는 상품 목록 건수 `COUNT(*)`.
- 쓰기 뒤 불변식 25개 PASS. 주문 PAID 1,439 / PAYMENT_PENDING 3.
- 이 측정은 #556 리뷰 반영 전 script로 했다. 측정 구간에서 완료 수가 예정 이상이고 오류가 0이라 중단은 없었다고 본다. 측정 구간에 k6 setup 카탈로그 요청(최대 90건)이 섞여 있었다(#557에서 고침).

**해석은 하지 않는다.** 1위 SQL이 무거운지, 규모가 커지면 무엇이 먼저 느려지는지는 10만·100만(H)을 본 뒤 사용자가 판단한다.

## 5. 리뷰·CI·실행에서 생긴 일

| 출처 | 내용 | 처리 |
| --- | --- | --- |
| PR 본문 검증 | 보고서에 `목적`·`위험과 제한` 섹션이 없고 실행 구분 값에 설명을 붙임 | 섹션 추가, 값 수정. 같은 작업 ID 보고서와 작업 등급이 같아야 한다는 규칙도 #557에서 만남 |
| Codex P1 | 기존 환경 삭제(3.6) | 수정, 회귀 테스트 |
| Codex P2 | 측정 끝에 잘린 iteration 미판정 | 시작·완료 카운터(3.1) |
| CodeRabbit Major | steady k6 종료 코드 미판정 | 판정 추가 |
| CodeRabbit Major | JSON 파싱 예외가 오류율에서 빠짐 | `jsonOf`(3.2), self-test(3.7) |
| CodeRabbit Minor | PENDING 3건 원인을 "끝에서 잘린 iteration"으로 단정 | **틀린 서술이었다.** 수치 대조로 정정([PWL-0056](../lessons/PWL-0056.md)) |
| CodeRabbit Minor | 로그인 요청 수에 CSRF GET이 빠짐 | 의도(BCrypt 비용 희석 방지)를 요약 `notes`·보고서에 명시 |
| CodeRabbit Minor(범위 밖) | k6 `setup()` 카탈로그 요청이 측정 구간에 섞임 | #557에서 실행기가 예열 전 준비 |
| 내 버그 | `json(undefined)`로 모든 Checkout 실패 | 시험 실행에서 종료 코드 판정이 잡음 |
| CI | `auth-lifecycle`·`compose` lane이 Gradle 외부 저장소(Spring Boot 4.1.0 artifact) 조회 실패로 두 번 실패 | 이 변경과 무관. 재실행·다음 push에서 통과 |
| 실행 | 시험 실행 중 Docker Desktop이 멈춰 환경 1개와 임시 세션 파일 1개가 남음 | `run-scale.py --down`과 파일 삭제로 정리. "강제 종료 시 임시 파일이 남을 수 있다"를 PR 위험에 기록 |

#556은 HEAD `aec0ca3e`에서 CI 통과 후 병합했고, 그 시점에 아직 push하지 않은 CodeRabbit 반영분을 #557로 분리했다. CodeRabbit은 #556에서 사용자 계정으로 수동 요청해 실행했고, #557에서는 실행하지 않았다.

## 6. 남은 것

- 반복 측정 편차를 재지 않았다(1만 1회).
- 20 iteration/s는 도구 검증용 기본값이다. 규모 간 비교 요청률과 단계적 증가는 H에서 정한다.
- 예열 중 결제 확인이 실패하는 원인(상태 코드·서버 로그)을 아직 보지 않았다. 시험 실행에서 결제 확인 실패 2건과 PENDING 2건이 일치했다.
- 정기배송 처리 시나리오(`--due-count` + 자동화)는 H에서 추가한다.

## 7. 되돌아볼 질문

1. closed 모델로 측정하면 느린 서버에서 어떤 착시가 생기나? open 모델에서 그 대가로 봐야 하는 지표는?
2. 예열과 측정을 한 번의 k6 실행으로 하면 DB digest 기준점이 왜 어긋나나?
3. 세션을 k6 `setup()`이 아니라 실행기가 만드는 이유 두 가지는? 환경 변수 대신 파일로 넘긴 이유는?
4. `exec.vu.idInTest`로 회원을 고르는 이유와, 로그인 묶음이 뒤쪽 절반 회원만 쓰는 이유는?
5. 지연 기준을 판정에서 뺀 이유는? 그러면 어떤 경우에 실패로 끝나나?
6. 시작·완료 카운터가 잡는 것과 `dropped`가 잡는 것은 어떻게 다른가?
7. `response.json()` 예외를 그대로 두면 오류율이 왜 낮게 나오나? `json(undefined)` 버그는 무엇이 잡았나?
8. Checkout 멱등 키에 `runTag`가 없으면 측정 결과가 어떻게 왜곡되나?
9. 게이지는 최댓값, 카운터는 전후 차이로 요약한 이유는?
10. 기존 환경 삭제 버그에서 "보호 장치가 삭제를 일으킨" 구조를 설명해 보라.
11. PENDING 주문 원인을 처음에 잘못 쓴 이유와, 어떤 수치 대조가 정정 근거가 됐나?
