## 1. 출발점: 무엇이 약했나

| 항목 | 상태 | 운영에서의 결과 |
| --- | --- | --- |
| 세션 | Tomcat 메모리. CSRF 토큰도 세션에 있다 | 배포·재시작마다 **전원 로그아웃** |
| 요청 제한 | nginx가 로그인만 IP당 분당 10회 | 검색·Checkout·결제·AI 호출을 무제한으로 두드릴 수 있다 |
| 로그 | 운영 nginx access log에 query string 포함 | 결제 성공 redirect의 `paymentKey`가 로그에 남는다 |
| 검색 | LIKE의 `%`·`_`를 백슬래시로 이스케이프 | MySQL `NO_BACKSLASH_ESCAPES` 모드에서 리터럴 검색이 깨진다 |
| 운영 알림 | 운영 Prometheus는 있지만 Alertmanager 없음 | 운영에서 critical이 나도 아무도 모른다 |

## 2. 검색 LIKE 이스케이프 (#545)

```java
private static final String LIKE_ESCAPE_CHARACTER = "!";
private static final String LIKE_ESCAPE_CLAUSE = " ESCAPE '" + LIKE_ESCAPE_CHARACTER + "'";

static String escapeLikeLiteral(String value) {
  return value
      .replace("!", "!!")      // 1) 이스케이프 문자 자신을 먼저
      .replace("%", "!%")
      .replace("_", "!_");
}
// ... LOWER(p.name) LIKE :q1 ESCAPE '!'
```

- **왜 백슬래시가 아닌가:** MySQL은 기본적으로 `\`를 LIKE 이스케이프로 쓰지만, `NO_BACKSLASH_ESCAPES` sql_mode가 켜지면 이 암묵적 규칙이 사라진다. SQL 문 안에 `'\\'`를 쓰는 것 자체도 그 모드에 따라 해석이 달라진다. `ESCAPE '!'`를 명시하면 모드와 관계없이 같은 의미다.
- **순서가 중요하다.** `!`를 먼저 `!!`로 바꾸지 않으면, 나중에 넣은 `!%`의 `!`가 다시 바뀌어 의미가 꼬인다.
- 회귀 테스트를 두 sql_mode 모두에서 돌린다. 외부 API·schema 변경은 없다.

## 3. 요청 제한 (#549, R4)

### 3.1 선택지

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. nginx `limit_req` 확장(채택)** | IP 키로 경로별 제한 | 앱 변경 없음, 앱에 도달하기 전에 거른다 | 운영 nginx 지문 계약을 바꿔야 함, 계정 단위 제한 불가 |
| **B. 앱 메모리 버킷(로그인 계정 단위만 채택)** | 계정 이메일 키 | 계정 단위 제한 가능 | 재시작하면 초기화, 인스턴스 간 공유 안 됨 |
| C. 앱 + Redis 카운터 | 공유 카운터 | 인스턴스 간 유지 | 운영 Redis가 더 필요하다 |

선택: **A + 로그인 계정 단위는 B.** 지금 backend는 한 대라 B의 "공유 안 됨"이 문제 되지 않는다.

### 3.2 nginx 코드 읽기

```nginx
limit_req_zone $binary_remote_addr zone=login_per_ip:10m rate=10r/m;
limit_req_zone $binary_remote_addr zone=checkout_per_ip:2m rate=10r/m;
limit_req_zone $pawcycle_search_limit_key zone=search_per_ip:2m rate=60r/m;

# 검색어가 있는 상품 목록 요청만 키를 가진다. 빈 키는 제한하지 않는다.
map $args $pawcycle_search_limit_key {
    "~*(?:^|&)(?:q|%71)=[^&]" $binary_remote_addr;
    default "";
}

location = /api/auth/login {
    limit_req zone=login_per_ip burst=5 nodelay;
    limit_req_status 429;
}
```

- `$binary_remote_addr`: IP를 문자열이 아니라 4바이트(IPv4)로 저장해 zone 메모리를 아낀다.
- **빈 키는 제한하지 않는다**는 nginx 성질을 이용해, 같은 `/api/products` 경로에서 검색어가 있는 요청만 제한한다. 일반 탐색은 영향이 없다. `%71`은 `q`를 URL 인코딩한 형태라 우회를 막는다.
- `burst`·`nodelay`: 순간 몰림을 burst만큼 즉시 통과시키고, 넘치면 429로 거절한다(지연 대기열을 만들지 않는다).
- 임계값(사용자가 2026-11-17 제안값 그대로 확정): csrf 30r/m burst 20, 검색 60/30, checkout 10/10, 결제 10/10, interactions 120/60, AI 30/30.
- 이 제한 때문에 4단계 성능 측정은 nginx를 거치지 않고 backend에 직접 요청한다([PWK-0003](PWK-0003.md)).

### 3.3 로그인 계정 제한 코드 읽기

```java
/** 회원이 존재하든 안 하든 정규화한 이메일로 실패를 센다. */
public void checkAllowed(String normalizedEmail) {   // 회원 데이터를 보지 않는다
  Attempts current = attempts.get(key(normalizedEmail));
  if (current != null && current.lockedAt(now)) throw new LoginRateLimitedException();
}

public void recordFailure(String normalizedEmail) {
  if (!attempts.containsKey(key) && attempts.size() >= maxTrackedAccounts && !makeRoom(now)) {
    log.warn("Login throttle capacity reached; failure not tracked");
    return;   // 모두 잠긴 상태면 기존 잠금을 지우지 않는다
  }
  attempts.compute(key, (ignored, previous) -> next(previous, now));
}

private static String key(String normalizedEmail) {
  return normalizedEmail.toLowerCase(Locale.ROOT);   // MySQL 조회가 대소문자 무시라 예산을 쪼개지 않게
}
```

- **계정 존재 여부를 드러내지 않는다.** 없는 이메일도 같은 방식으로 세고 같은 시점에 잠근다. 잠금 응답의 차이로 "이 이메일은 가입돼 있다"를 알아낼 수 없다.
- **잠긴 동안은 비밀번호 검사 자체를 하지 않는다.** 맞는 비밀번호로도 못 들어온다. 그렇지 않으면 잠금 중에도 정답 여부를 확인할 수 있다.
- **메모리 상한(추적 계정 10,000).** 공격자가 무작위 이메일로 맵을 무한히 키우는 것을 막는다. 공간이 필요하면 만료된 항목 → 잠기지 않은 카운터 순으로 지운다. 모두 잠겨 있으면 새 실패를 세지 않고 경고만 남긴다(기존 잠금을 지워 공격자를 풀어 주지 않는다).
- `ConcurrentHashMap.compute`로 같은 키의 갱신을 원자적으로 한다.
- 대소문자: MySQL 조회는 대소문자를 무시하는데 키가 구분하면 `A@x`와 `a@x`가 예산을 따로 가진다.
- 성공하면 카운터를 지운다. 4단계 성공 로그인 부하에는 영향이 없다.

### 3.4 지문 계약 교착 — Codex P1

운영 배포 도구(`oci-release.py`)는 nginx 설정 파일의 SHA-256 지문이 승인된 값과 같아야 배포를 진행한다(설정이 몰래 바뀌는 것을 막는 계약). 처음 구현은 **새 지문만** 허용했다. 그런데 배포 도구는 먼저 "지금 운영 중인 설정(baseline)"을 검증하는데, 운영은 아직 이전 설정이라 검증에 실패한다. **이전 설정에서 새 설정으로 넘어갈 방법이 없는** 교착이었다.

```python
NGINX_CONTRACT_SHA256 = "0371486e..."
PREVIOUS_NGINX_CONTRACT_SHA256 = frozenset({"dfb93f4f..."})
require(fingerprint == NGINX_CONTRACT_SHA256 or (baseline and fingerprint in PREVIOUS_NGINX_CONTRACT_SHA256), ...)
```

이전 지문은 **운영 중인 baseline 검증·adopt·복구에서만** 허용하고, 새 배포 대상과 rollback 대상은 새 지문만 허용한다. 교훈: 계약 값을 바꾸는 변경은 "옛 값 → 새 값" 전환 경로를 함께 설계해야 한다.

## 4. query 없는 운영 access log (#549, R11)

```nginx
# $uri에는 query string이 없다. 결제 키 같은 값이 로그에 남지 않는다.
log_format pawcycle_json escape=json '{"time":"$time_iso8601","request_id":"$pawcycle_request_id",'
    '"method":"$request_method","uri":"$uri","status":$status, ...}';

map $http_x_request_id $pawcycle_request_id {
    "~^[A-Za-z0-9._-]{1,64}$" $http_x_request_id;
    default $request_id;
}
```

- `$request`(요청 줄 전체)나 `$request_uri`에는 query가 들어간다. `$uri`는 정규화된 경로만이다.
- `escape=json`: 값 안의 따옴표·제어 문자를 이스케이프해 JSON이 깨지지 않게 한다.
- request id는 backend 필터(2단계)와 같은 규칙으로 검사한다. nginx 로그와 backend 로그를 같은 ID로 잇는다.

## 5. 세션 저장소 (#550, R3, AUTH-005)

### 5.1 선택지

| 안 | 장점 | 단점 |
| --- | --- | --- |
| **A. Spring Session Redis(채택)** | 코드 변경이 작다, 재시작에도 세션 유지 | 세션 전용 Redis 운영, Redis 장애 시 인증 불가 |
| B. Spring Session JDBC | 새 인프라 없음 | migration 필요, 요청마다 DB 쓰기 |
| C. JWT | 서버 상태 없음 | 승인된 세션 인증(AUTH-003)을 뒤집는다. 로그아웃·강제 만료가 어렵다 |

### 5.2 코드 읽기

```java
@SpringBootApplication(exclude = SessionDataRedisAutoConfiguration.class)   // 자동 설정 끔

@ConditionalOnProperty(name = "pawcycle.session.store", havingValue = "redis")
@Import(RedisHttpSessionConfiguration.class)
static class RedisSessionStoreConfiguration {
  @Bean(defaultCandidate = false)
  @SpringSessionRedisConnectionFactory
  LettuceConnectionFactory sessionRedisConnectionFactory(...) { ... }

  @Bean
  ApplicationListener<ApplicationReadyEvent> sessionRedisConnectionWarmUp(...) {
    return event -> {
      try (RedisConnection connection = connectionFactory.getConnection()) { connection.ping(); }
      catch (RuntimeException e) { log.warn("Session Redis is not reachable at startup; ..."); }
    };
  }
}
```

- **캐시 Redis와 세션 Redis를 분리한다.** 로컬 캐시 Redis는 `allkeys-lru`라 메모리가 차면 아무 키나 지운다. 세션이 조용히 사라지면 사용자는 이유 없이 로그아웃된다. 세션 Redis는 `noeviction`(가득 차면 쓰기 실패) + AOF다.
- Spring Boot의 Redis 세션 자동 설정은 **연결이 하나라도 있으면 그 연결(=캐시 Redis)에 세션을 묶는다.** 그래서 자동 설정을 빼고 직접 구성한다.
- `defaultCandidate = false` + `@SpringSessionRedisConnectionFactory`: 세션용 연결 팩토리를 Spring Session만 쓰게 한다. 이 bean이 기본 후보가 되면 캐시가 세션 Redis로 붙어 버린다.
- **기동 시 미리 연결(warm-up).** 로컬 실측에서 유휴 뒤 첫 세션 요청이 Redis 연결 초기화 시간 때문에 command timeout(1초)을 넘겨 500이 났다. 준비 완료 시점에 미리 연결해 첫 로그인이 그 비용을 내지 않게 했다. 실패해도 경고만 남기고 기동은 계속한다(익명 조회는 가능해야 하므로).
- 설정값 검증: `memory`나 `redis`가 아니면 기동을 멈춘다. 오타가 조용히 memory로 동작하는 일을 막는다.
- **운영 기본값은 `memory`.** 병합·배포만으로는 운영 동작이 바뀌지 않는다. `redis` 전환은 별도 PR·release로만 하고, 전환 때 1회 전원 로그아웃 공지가 필요하다.
- 로컬에서 backend 재시작 뒤에도 로그인과 CSRF 토큰이 유지되는 것을 실측했다.

## 6. 운영 계약 확장: sibling Compose project (#553, #552)

### 6.1 선택지

운영 앱 release 계약(`oci-release.py`)은 backend·frontend·proxy의 **서비스·volume 집합을 고정**해서 검사한다. 세션 Redis와 Alertmanager를 넣는 방법은 두 가지였다.

| 안 | 장점 | 단점 |
| --- | --- | --- |
| 앱 release 계약을 넓힌다 | 한 번에 배포 | release·rollback 경로 전체가 바뀐다. 앱 배포 실패와 Redis 문제가 얽힌다 |
| **별도 sibling project(채택)** | 앱 release 계약과 rollback 경로를 그대로 둔다. 기존 운영 관측(ARCH-012)과 같은 방식 | sibling의 수명주기를 별도 Runbook으로 관리해야 한다 |

### 6.2 운영 세션 Redis (#553)

- 사양(사용자 결정): `maxmemory 64mb`, `noeviction`, AOF `everysec`, 128m / 0.25 CPU, host port 없음(Docker 내부 network만).
- 배포 도구는 backend가 `redis` 모드일 때만 sibling의 이미지·health·network·port를 **읽기 전용으로** 확인한다.
- **Codex P1:** Redis가 장애일 때 `memory` release로 rollback하려 해도, 현재 release의 Redis 확인에 막혀 rollback이 안 됐다. 복구 수단이 장애 원인에 막히는 구조였다. `memory` 대상 rollback은 Redis 상태를 요구하지 않고, `redis` 대상 배포·rollback만 정상 Redis를 요구하도록 고쳤다. 회귀 테스트를 추가했다.

### 6.3 운영 Alertmanager (#552, ARCH-016)

- observability network에만 두고(host port 없음, 64m / 0.05 CPU), Discord webhook은 파일로만 주입한다.
- 운영 규칙은 critical 4개(scrape 중단, DB 커넥션 획득 실패, 고립 PROCESSING, UNKNOWN 장기화)와 Watchdog이다. Loki는 app01 메모리 여유를 위해 보류했다.
- **로컬 규칙을 그대로 옮기지 않았다.** 운영 수집 간격이 30초라 "지금 대기 중인 요청"(순간 값)을 놓칠 수 있다. DB 커넥션 규칙을 "5분 안 시간 초과 2건 이상"으로 바꿨다. 운영에서 검증되지는 않았다.
- **Codex P2:** webhook 파일을 file bind mount로 넣으면, 파일을 교체해도 실행 중인 컨테이너는 **옛 inode**를 계속 본다. Runbook 교체 순서를 "새 webhook 작성 → 파일 교체 → Alertmanager 재생성 → 새 채널 수신 확인 → 기존 webhook 삭제"로 바꿨다.
- #553 병합 뒤 #552에 `main`을 merge해(rebase·force push 없음) 계약 검사 충돌을 두 검사 모두 유지하도록 풀었다.

| 선택 | 얻은 것 | 내준 것 |
| --- | --- | --- |
| nginx IP 제한 | 앱 앞에서 차단, 앱 변경 없음 | NAT 뒤 여러 사용자가 한 IP를 공유하면 함께 제한될 수 있다. 성능 측정은 nginx를 우회해야 한다 |
| 로그인 계정 제한을 메모리에 | 새 인프라 없음 | 재시작하면 잠금이 풀린다. 인스턴스가 늘면 다시 설계 |
| 세션 Redis(fail-closed) | 배포해도 로그인 유지 | Redis가 멈추면 세션 요청 실패. 응답 코드가 전용 코드가 아니다(쿠키 있는 요청 500, 없는 csrf 401) |
| 운영 기본 `memory` 유지 | 병합이 곧 운영 변경이 아니다 | 실제 효과는 전환 PR 이후 |
| sibling project | 앱 release·rollback 계약 불변 | 수명주기 Runbook이 늘어난다 |

## 8. 남은 것 (운영 미적용)

- 운영 세션 Redis 기동과 `redis` 전환, 운영 Discord 채널·webhook 파일, 운영 관측 재적용과 `amtool` 시험 알림, 외부 dead man's switch 도입 여부 — 모두 #470 승인 대상.
- `redis` 모드의 운영 인증 smoke를 실행해 본 적이 없다. 로그아웃 응답의 쿠키 삭제 헤더가 두 개다.
- 세션 Redis 전용 알림이 없다.
