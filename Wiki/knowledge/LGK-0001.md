# 물류 학습 프로젝트 — 요구사항·설계·구현·실험 로드맵 초안

> **상태:** 전체 로드맵은 논의용 초안이다. 물류 도메인/학습 목적/AI 협업 방식은 사용자 확정, 물류 하위 문제·도메인 엔티티·API·성능 목표·기술 스택은 **미확정 제안**이다. 실제 저장소 생성·구현·실험은 아직 없다.

## 1. 학습 목표

- 물류 업무 문제를 관찰 가능한 사용자·시스템 요구사항으로 해석한다.
- 데이터 불변식과 실패 시나리오를 먼저 정의하고 트랜잭션·동시성 제어를 비교·선택한다.
- 실제 실행 결과를 기준으로 인덱스, 캐싱, 이벤트 처리 및 복구 전략을 검증한다.
- 변경 이유·대안·결과를 기록하여 코드뿐 아니라 설계 경위를 스스로 설명할 수 있게 한다.

## 2. 도메인 문제 후보 (결정 전)

| 후보 | 핵심 질문 | 검증/학습 포인트 |
| --- | --- | --- |
| 출고센터 결정과 재고 할당 (우선 검토) | 어떤 센터에서 주문을 처리해야 하며 동시에 들어오는 주문에 어떻게 재고를 할당할까? | 도메인 정책·락·정합성·선택 알고리즘·성능 |
| 창고 입출고·피킹 | 입고·적재·피킹 작업의 선후 관계와 재고를 어떻게 관리할까? | 재고 원장·상태 전이·작업 배정·중복 처리 |
| 배송 이벤트 추적 | 출고 후 배송 상태가 중복 또는 역순으로 도착하면 어떻게 처리할까? | 이벤트·멱등성·순서·장애 복구 |
| 배송 경로 최적화 | 제한된 차량·배송 시간 안에서 경로를 어떻게 정할까? | 그래프·휴리스틱·성능 실험·데이터 품질 |

단계별 모든 주제를 필수로 구현하는 것은 아니다. 첫 범위는 사용자와 요구사항을 함께 검토한 뒤 결정한다.

## 3. 초기 기능 요구사항 예시 — 출고센터·재고 할당안 (전부 제안)

- FR-01: 주문 요청의 상품 식별자, 수량, 배송 권역을 검증한다.
- FR-02: 상품을 취급하면서 재고·영업/처리 가능 조건을 만족하는 센터 후보를 조회한다.
- FR-03: 거리·우선순위·처리 용량 등 정책에 따라 출고센터를 선택한다. 정확한 정책은 별도 결정한다.
- FR-04: 센터 재고 예약을 생성하고 중복 요청/동시 주문에서도 재고를 초과 배정하지 않는다.
- FR-05: 예약 성공·실패 및 주문/할당 상태를 조회한다.
- FR-06: 예약 취소·타임아웃·중복 요청 시 정합성을 유지한다.
- FR-07(후속 후보): 출고 완료를 이벤트로 전달하고 장애·재처리를 검증한다.

### 논의할 핵심 비기능 요구사항

- **정확성:** 총 예약 수량이 사용 가능 수량을 초과하지 않으며 실패한 요청이 재고를 잘못 점유하지 않는다.
- **멱등성:** 중복 요청·중복 메시지가 데이터 손상 없이 처리되는지 정의한다.
- **지연·처리량:** 데이터 크기·동시 사용자 수·테스트 환경을 먼저 정하고 평균·p95/p99·TPS 및 실패율을 기록한다.
- **복구:** DB 실패, 타임아웃, Consumer 중지, 재시도 이후의 상태를 확인한다.
- **데이터:** 가상 데이터를 사용할지 공개 데이터를 수집할지, 갱신/중복/품질의 검증 방법을 결정한다.
- 목표치와 규모는 **아직 정의되지 않았으며 측정값도 없다**.

## 4. 진행 단계·완료 조건 초안

| 단계 | 함께 논의할 작업 | 검증 증거·완료 조건 예시 |
| --- | --- | --- |
| 00. 요구사항·도메인 선택 | 업무 흐름, 역할, 문제 범위, 대안 | 승인된 문제·주요 시나리오·제외 범위 |
| 01. 모델·API·정합성 설계 | 용어, 엔티티 관계, 불변식, 상태 전이, API | 결정 근거와 핵심 정상/오류 사례 |
| 02. 기본 구현 | Spring 구성, 최소 기능, DB 연동 | 사용자 로컬 실행·테스트 결과 공유 |
| 03. 동시성·트랜잭션 | 경쟁 상태 재현, 락/CAS/제약 비교 | 재현 가능한 실패→수정→회귀 테스트 |
| 04. 데이터·검색 성능 | 데이터 생성/수집·정제, 인덱스, 실행 계획 | 동일 조건 전후 실행 계획·지연 비교 |
| 05. 이벤트·장애 복구 | 이벤트 필요성 검토, Kafka 등 후보 비교 | 중복·유실/지연·재처리 시나리오 검증 |
| 06. 캐시·고급 최적화 | 읽기 병목·캐시 정합성·부하 테스트 | 목표 대비 실측 수치와 도입/기각 결정 |
| 07. 정리·재설계 | 장애·실험 기록 검토, 아키텍처 개선 | 결과 요약·남은 위험·포트폴리오 전환 별도 판단 |

단계는 **의무 기술 목록이 아니다**. 충분한 문제·측정 없이 Kafka/Redis/MSA를 도입하지 않는다.

## 5. 채팅에서 사용할 학습·구현 프로토콜

1. **문제 설명:** 현재 물류 업무 문제, 전제, 성공/실패 조건을 먼저 이해한다.
2. **공동 설계:** 여러 선택지와 이유·비용을 비교한다. 사용자 승인 전에는 확정이라고 표현하지 않는다.
3. **코드 제공:** 초기 설정과 일반 기능은 AI가 채팅에 완전한 파일/코드/명령을 제공하며 사용자가 직접 작성·실행한다. 필요하면 예상 출력도 제공하되 실제 실행 결과와 구분한다.
4. **힌트 우선:** Kafka·장애 복구·파이프라인·캐시·고급 최적화 등 첫 경험 기술은 개념→힌트→사용자 시도→피드백으로 진행한다. 사용자가 원하면 예제 또는 정답 코드를 제시한다.
5. **검증:** 사용자의 실행 결과, 테스트 로그, SQL 실행 계획, 부하 측정값 등 공유된 증거를 검사한다. 직접 실행하지 않은 일은 수행했다고 기록하지 않는다.
6. **기록:** 아래 원칙에 따라 매 의미 있는 작업 후 상태·결정·실험·다음 작업을 두 Wiki에 반영한다(신규 프로젝트 Wiki는 저장소 생성 및 접근 확인 이후).

## 6. Wiki 기록 형식과 진척 상태

- **Decision/ADR:** 문제와 제약, 대안, 선택 이유, 위험, 변경 시점, 검증 여부
- **요구사항/설계:** 업무 시나리오, 상태 전이, 데이터 불변식, API·데이터 모델, 미결 사항
- **실험/실패:** 가설, 환경, 데이터 규모, 실행 명령/방법, 결과·재현 여부, 수정·재검증
- **진행 로그:** 무엇을 논의/작성/실행/검증했고 다음 행동은 무엇인지, GitHub 관련 링크
- **학습 노트:** 처음 접한 개념, 실제 적용 이유, 코드 흐름, 사용 조건, 한계 등 필요한 내용만 선별

상태는 `제안`, `사용자 확정`, `코드 제시`, `로컬 작성 보고`, `실행 검증`, `측정 검증`, `보류/기각`으로 나누며 하나의 단계 완료만으로 다음 단계를 자동 완료 처리하지 않는다.

### 신규 프로젝트 Wiki 생성 시 초기 목차 제안

- `Home`: 목표·범위·현재 상태·최신 결정
- `Requirements`: 업무 흐름·기능 및 비기능 요구사항
- `Domain-and-Architecture`: 용어·엔티티·상태·설계 대안
- `Decisions`: ADR 색인과 개별 확정 결정
- `Experiments`: 동시성·부하·SQL·메시지·장애 재현 근거
- `Progress`: 일자별 완료·미검증·다음 작업

GitHub Wiki가 실제 활성화·연결되는지 확인하기 전에는 위 페이지를 이미 만들었다고 주장하지 않는다. 중앙 `guseoh/cs/Wiki`에는 중요 결정을 ID로 남기고 프로젝트 상세 정본의 링크 및 현재 진행 상태를 유지한다.

## 7. 첫 논의 질문

1. 첫 제품 경계는 **출고센터 결정·재고 할당**으로 잡는 것이 적절한가? 다른 물류 문제와 비교한다.
2. 주문은 외부에서 입력되는 것으로 가정할까, 주문·재고·출고 업무를 모두 이 프로젝트 안에서 모델링할까?
3. 출고센터 선택 기준과 재고 부족/중복 요청 시 허용할 비즈니스 동작은 무엇인가?
4. 최초에는 가상 데이터로 시작할지, 공개 데이터로 시작할지 선택한다.
5. 선택된 문제에 필요한 최소 기능을 정한 뒤 데이터베이스와 API를 설계한다.

## 8. 검증·출처 경계

사용자가 명시적으로 승인한 것은 **물류 선택, 학습 우선, 채팅 기반 코드 제공, 사용자 최종 결정, 어려운 기술의 힌트 우선, 두 Wiki 기록 의도**다. 이 문서의 도메인 후보·기술 단계·FR 번호·데이터 모델 방향은 아직 **제안**이며 공개 데이터 출처·운영 수준·측정 수치에 대한 독립 검증은 없다.
