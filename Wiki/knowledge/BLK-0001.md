# Ubuntu / Linux / web-service operations — phase-one learning roadmap

## Goal, status and scope

**Goal (user-confirmed):** build OS, network, web-server and single-Ubuntu-server literacy for Java/Spring backend work. Explain the end-to-end web request path and investigate/recover failures at the appropriate layer. **Method:** theory -> underlying behavior -> predict the outcome -> execute Ubuntu exercises directly -> inspect evidence -> adapt/recover. Commands are reference tools, not a memorization syllabus.

Phase 1 **completed based on user-provided terminal output**: file creation, search/pipe count, copy/move/find, symlink/stderr, and direct retry of the missing-file `ls` with exit status `2`. Phase 2 **completed based on user-provided terminal output**: `chmod 000` denied reading an owned test file, `chmod 600` restored it; an owned sleeping background process was observed, sent SIGTERM, returned `wait` status `143`, and was absent from final `ps`. Phase 3 system inspection commands have been assigned **but their output is not yet observed**. Phases 4–7 not started. No agent execution or independent machine access is claimed. This is user-provided observation, **not assistant access to the user's computer or independent runtime verification**. Preserve the separate backend-first priority and the existing Large-scale Board roadmap.

**In scope:** Linux shell/files/permissions/processes; packages, systemd, journald, resource observation; basic IP/TCP/ports/DNS/HTTP/TLS; Nginx static serving and reverse proxy; simple Spring Boot executable JAR; SSH/firewall; backup, rollback and safe fault diagnosis.

**Out of phase-one scope:** Kubernetes, multi-host load balancing/HA, advanced cloud topology/VPC, full CI/CD platform, Docker orchestration, database operations, Prometheus/Grafana stack, advanced kernel/JVM tuning.

## Environment, transition and safety

- **Host:** Windows. **Initial Linux:** WSL2 Ubuntu for direct shell/files/process/permissions practice. Keep initial Linux experiments under the Linux home directory rather than a Windows-mounted directory.
- **Server laboratory:** a single Ubuntu Server virtual machine. WSL2 also supports systemd and Nginx, but the VM offers a clearer independent boot, network, SSH and firewall boundary.
- Use the same maintained Ubuntu LTS release where feasible; choose a release when installing, not by assuming one is already present. Initial suggested VM size is 2 vCPU / 4 GiB RAM / 30 GiB disk, adjusted to actual resources.
- Expose the lab only between the Windows host and VM initially. VM NAT/bridged/host-only reachability depends on the hypervisor; never assume localhost and guest address semantics match WSL2 port conveniences.
- Before firewall/SSH changes, retain VM console recovery access. Prefer disposable snapshots before risky exercises; snapshots do not replace file backup-and-restore practice. Reproduce disk-full only on a size-limited disposable filesystem; do not exhaust the host drive.

## Reference request lifecycle

```text
Windows Browser
  -> hosts or DNS name lookup
  -> Ubuntu VM IP / route / transport access
  -> firewall + TCP listener/port
  -> Nginx (HTTP; later HTTPS/TLS)
       |-- static HTML
       `-- reverse proxy -> 127.0.0.1:8080
                           -> Spring Boot embedded Tomcat + Java process
                           -> API handler + HTTP response
  <- HTTP response returns along established connections

Alongside: Linux users/permissions, process & socket, systemd, journal/application logs.
```

Distinguish **name resolution**, **reachability/connectivity**, **TLS identity**, **HTTP status**, **reverse proxy forwarding**, **application processing** and **Linux lifecycle**. Spring Boot's embedded Tomcat can serve HTTP directly; Nginx is included to observe static delivery, TLS termination and proxy responsibilities, not because Spring Boot universally requires it.

**Sequence rationale:** establish Linux file/process/service primitives before network-facing configuration; then add Nginx static serving, simple Spring Boot, TLS/security and finally bounded operational recovery. Do not delay phase transition until every conceivable command is known.

## Small practice workload and milestones

- **Phases 0–3:** no application development project. Use throwaway practice files, simple commands and a tiny service unit as needed.
- **Phase 4:** serve one static HTML page with Nginx. Study browser, curl, network, HTTP response, access and error logs.
- **Phases 5–7:** reuse a *minimal* Spring Boot (Java 21) application: `/api/hello` returning fixed JSON and `/api/status` returning a non-secret test identity. No database, authentication, UI or domain features. The objective is Linux execution/proxy/operations, not application feature delivery.
- **Phase 6:** use a learning-only local CA/certificate with appropriate SAN name and explicitly configure trust. Do not treat a `curl -k` result as TLS validation success.
- **Phase 7:** start with default utilities and evidence collection; no required full Grafana/Prometheus stack. Keep recovery bounded to disposable lab assets.

## Cross-cutting integration exercises

1. **HTTP full path:** before looking at tools, predict DNS/hosts -> TCP -> TLS (once enabled) -> Nginx -> proxy -> Tomcat -> handler -> response. Observe at least one fact per major hop and correct misunderstandings.
2. **OS-network link:** identify the process owning the socket and contrast `127.0.0.1` with guest interface binding, and guest firewall rules with Windows-side reachability.
3. **Layered incident response:** write *symptom -> hypothesis -> evidence to collect -> limited change -> retest*; group faults by OS/permissions, transport/firewall, web server, proxy, Java process/config or TLS/name trust.

Candidate deliberate faults include: missing directory permission, occupied port, wrong environment variable under systemd, killed Java process yielding upstream error, proxy URI mismatch, invalid Nginx config, bad hosts mapping, firewall block, cert SAN/trust error and limited-filesystem exhaustion. A 502 is a **possible** outcome of a broken upstream, not an invariant for all proxy failures. Do not practice host-wide memory exhaustion.
