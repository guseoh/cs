# Obsidian 시작 성능 실측과 안전한 최적화 방법 (2026-11-25)

## 실측 환경과 전체 결과

사용자가 Obsidian 설정의 Start-up time breakdown에서 제공한 단일 측정 결과다.

- Obsidian / Installer: 1.15.1
- 운영체제: Windows 11 Home 10.0.26300
- Vault: 1,286개 파일
- Workspace: 11 tabs, 9 deferred
- 활성 커뮤니티 플러그인: 23개
- 전체 시작 시간: **7,655ms**

| 영역 | 시간 | 전체 비중 |
| --- | ---: | ---: |
| Initialization | 2,699ms | 35.3% |
| Vault | 799ms | 10.4% |
| Workspace | 803ms | 10.5% |
| Core plugins | 152ms | 2.0% |
| Community plugins | 3,202ms | 41.8% |
| **Total** | **7,655ms** | **100%** |

Initialization 2,699ms 중 Boot 2,430ms다. Boot 구성은 Response 115ms, DOM parse 788ms, Workspace snapshot 1,086ms, Script evaluation 441ms다. Vault는 Configuration 29ms, Reading files 574ms, Loading file metadata 188ms, Metadata listeners 9ms다. Workspace는 Components 203ms, Appearance 16ms, Managers 28ms, Layout 544ms, Extra 12ms다.

이 수치에서 Community plugins가 가장 큰 집계 항목인 것은 확인된다. 그러나 Boot의 Workspace snapshot과 DOM parse도 각각 1초 안팎의 큰 비용이다. Vault 파일 처리 799ms만을 원인으로 보고 파일이나 첨부를 정리해서는 안 된다. Workspace snapshot의 시간이 탭 수 때문에 발생했다고 단정할 수도 없다.

Editing Toolbar, Excalidraw, Hover Reveal 상위 3개는 합계 1,574ms로 커뮤니티 플러그인 초기화 시간의 49.2%다. 상위 5개는 2,002ms로 62.5%다. 이 값은 플러그인별 시작 시점의 측정치이며, 번들 크기나 런타임의 지속적인 CPU/RAM 사용량과 혼동하지 않는다.

## 코드 검토로 확인한 최적화 후보

### Editing Toolbar

추적된 설정에서 `ai.enabled=false`임을 확인했다. 그러나 Editing Toolbar 4.1.12의 `main.js`는 플러그인 `onload()`에서 AI Manager를 생성하고 `aiManager.onload()`와 AI Editor Extension 등록을 항상 수행한다.

AI Manager 초기화는 Secret Storage 조회, 로그인 상태 동기화, 사용자 정의 API 키 마이그레이션, 프로토콜 핸들러 등록, Vault/Metadata 이벤트 구독을 포함한다. 특히 로그인 토큰이 존재하고 저장된 사용자 정보가 없으면 `syncLoginState()`가 인증 검증을 시작할 수 있다. 다만 로컬 Secret Storage 값은 원격 저장소에서 읽을 수 없으므로 실제 요청이 발생했는지는 미확인이다.

이는 AI 기능이 비활성인 환경에서 불필요한 초기화를 줄일 수 있는 구체적인 코드 후보지만, 789ms 전체가 AI Manager에서 발생했다는 뜻은 아니다. `commandsManager.registerCommands()`, 툴바 초기화, 커스텀 Prism 편집기 확장도 같은 `onload()` 경로에 존재한다.

AI Manager를 조건부 초기화하려면 다음을 함께 다뤄야 한다.

- 시작 시 AI 비활성 상태에서 Secret Storage/인증/이벤트 등록을 생략한다.
- 사용자가 나중에 AI를 켜면 인증 상태와 프로토콜 핸들러를 초기화한다.
- AI Editor Extension을 현재 열려 있는 편집기에도 정상 등록한다.
- AI 명령, 설정 탭, 로그인/로그아웃, AI 활성화·비활성화 및 플러그인 재시작을 회귀 테스트한다.
- 기존 툴바와 읽기·쓰기 코드 색상 일치 기능을 보존한다.

단독 A/B 결과가 충분한 개선을 보여주기 전에는 번들 코드를 수정하지 않는다.

### 다른 플러그인

- Excalidraw는 `aiEnabled=true`가 확인되었지만 실제 사용 여부가 확인되지 않아 설정을 바꾸지 않는다.
- Hover Reveal은 Markdown Post Processor와 Editor Extension 등을 등록한다. 290ms 내부에서 어느 작업이 주요 원인인지는 아직 모른다.
- Dataview의 화면 갱신 간격을 2.5초에서 5초로 변경한 것은 런타임 재렌더링 빈도 조정이다. 198ms의 시작 초기화 시간을 직접 줄이는 설정은 아니다.
- Obsidian Git의 198ms는 플러그인 초기화 시간이다. 자동 Pull의 네트워크 작업 완료 시간과 동일하지 않으므로 Pull 완료 여부를 별도로 검증한다.

## 안전한 다음 측정

1. Obsidian을 완전히 종료하고 재실행해 시작 시간 보고서를 3회 수집한다. 전체 시간과 각 플러그인별 중앙값을 기록한다.
2. Editing Toolbar만 UI에서 임시 비활성화하여 3회 측정하고, 곧바로 다시 활성화한다. 이 테스트 중에는 기존 툴바와 Prism 색상 기능을 사용할 수 없으므로 작업하지 않는다.
3. 필요할 때 Excalidraw, Hover Reveal, PDF++를 한 번에 하나씩 같은 방식으로 측정한다. 다중 비활성화 결과로 개별 영향을 추정하지 않는다.
4. 11개 탭(9 deferred) 기준과 사용하지 않는 탭을 닫은 임시 기준을 비교한다. Workspace snapshot/Layout 비용이 실제로 변하는지 본 뒤 영구 작업 공간 변경은 별도로 승인한다.
5. Editing Toolbar의 단독 영향이 확인된 경우에만 AI 비활성 상태의 AI Manager 지연 초기화를 구현한다.

## 검증 한계

현재 기준선은 단일 사용자 제공 측정이다. cold/warm 실행 구분, 3회 중앙값, 플러그인 비활성화 A/B, 로컬 Secret Storage, 자동 Pull 완료 시간, 메모리/CPU, 실제 UI 회귀 및 두 번째 PC 결과는 아직 없다. 따라서 최종 병목 원인과 최적화 개선량은 미확정이다.

관련 구현 및 진행은 [Obsidian 성능 최적화 PR #106](https://github.com/guseoh/cs/pull/106)에서 추적한다.
