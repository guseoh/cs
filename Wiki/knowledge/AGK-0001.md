# Java/Spring 백엔드의 AI 활용·AI 도입 경계 — 핵심 Q&A

> **범위:** 2026-11-05 학습 방향 논의에서 재사용 가치가 있는 질문과 답변을 편집하여 정리했다. 질문 문구나 답변은 비공개 대화의 축어록이 아니다. 개인 학습 선택은 **user-confirmed**, 기술적 설명은 일반 원리, 아직 수용되지 않은 변경안은 **proposed**로 구분한다.

## Q1. 시스템 설계 역량은 Java/Spring·CS·운영 기본기의 응용인가?

**확정 학습 관점:** 그렇다. CS·Java/Spring·DB·트랜잭션·동시성·네트워크·운영에 대한 기본기와 **도메인 지식**을 요구사항·제약조건에 맞춰 조합하는 능력으로 설계 역량을 이해한다. 개별 기술의 정의나 원리를 설명할 수 있는 것에 더해, 현재 조건에서 대안을 평가하고 선택한 설계를 구현·검증할 수 있어야 한다.

물류 재고 예약을 예로 들면 동시성 제어와 DB 격리 수준은 기술 기반이지만, 예약 시점·해제 조건·주문과 결제의 상태 전이는 도메인 규칙이다. 설계는 이 둘을 결합해 데이터 정합성, 처리량, 실패 복구와 비용 사이의 트레이드오프를 판단하는 일이다.

## Q2. 시스템 설계 책과 도메인 바이브 코딩의 관계는?

**확정 학습 방향:** 《가상 면접 사례로 배우는 대규모 시스템 설계 기초》 1·2권으로 설계 사고 과정을 공부하고, 물류와 스트리밍 등 논의한 도메인에서 요구사항·데이터 모델·아키텍처를 설계하면서 AI를 활용한 구현·검증 역량도 기른다. 도메인 설계와 AI 활용은 새로운 별도 강의를 추가하는 대신 같은 실전 작업에서 함께 연습한다.

구체 서비스 범위, 최종 단일 도메인 선택, 기술 스택, 구현 일정은 이 기록에서 확정하지 않는다. 기존 [BLR-0004](../decisions/BLR-0004.md)와 [BLR-0005](../decisions/BLR-0005.md)의 범위와 원본 프로젝트 권위를 보존한다.

## Q3. AI 활용 개발 능력과 Agent의 내부 구조 학습은 같은가?

**확정 역할 구분:** 다르다. 코딩 에이전트에게 목표, 코드 맥락, 제약, 완료 기준, 테스트와 검증 조건을 제공하고 결과를 검토하는 역량은 **도메인 개발 트랙**에서 훈련한다. LLM이 어떤 Context를 받고, Tool을 어떻게 호출하며, Spring AI와 Agent Runtime이 무슨 책임을 갖는지 이해하는 학습은 **AgentLab**에서 수행한다. 이 때문에 AgentLab에 바이브 코딩·하네스 커리큘럼을 중복 추가하지 않는다.

## Q4. 'Spring LLM' 또는 'Spring 프로젝트에 AI를 도입했다'는 말은 정확히 무엇인가?

**기술적 구분:** 'Spring LLM'은 정식 프레임워크 명칭으로 쓰기보다 **Spring AI 도입** 또는 **Spring Boot에서 LLM API 연동**이라고 표현하는 편이 명확하다. Spring AI는 모델 학습 자체가 아니라, 외부 또는 로컬 LLM을 Java/Spring 애플리케이션에서 호출하고 결과를 처리할 수 있게 하는 프레임워크다.

AI 도입의 작은 예로는 텍스트 요약·번역·배송 상태 설명이 있다. 좀 더 구조적인 통합으로는 자연어 주문 검색 조건을 Java DTO로 변환하는 Structured Output, 문서 검색 결과를 근거로 응답하는 RAG, 애플리케이션의 조회 기능을 Tool로 연결하는 Tool Calling 등이 있다. **AI를 도입했다고 반드시 Agent를 구축한 것은 아니다.**

예: 배송 상태는 서버가 권한을 확인한 뒤 조회하고, LLM은 실제 조회된 상태만 바탕으로 사용자용 안내문을 생성한다. 비즈니스 규칙과 권한·데이터의 권위는 기존 Spring Service에 남는다.

## Q5. LLM 호출, Tool Calling, Agent는 어떤 차이가 있는가?

**일반 원리:** 단일 LLM 호출은 애플리케이션이 제공한 입력을 바탕으로 텍스트나 구조화된 출력을 생성한다. Tool Calling에서는 모델이 사용 가능한 도구와 인자를 요청할 수 있고 **실제 Java 메서드/API 실행 책임은 애플리케이션 런타임**에 있다. Agent는 작업 결과를 다시 입력으로 활용해 추가 행동을 선택하거나 최종 답변에 도달하도록 조정할 수 있다.

파일이나 DB가 애플리케이션에 존재한다는 사실만으로 모델이 그 내용을 자동으로 아는 것은 아니다. 먼저 애플리케이션이 검색·조회 결과를 제공하거나, 허가된 Tool 실행 결과가 Context에 반영되어야 한다.

## Q6. 실제 백엔드 프로젝트에 AI가 필요한 시점은 언제인가?

**기술적 판단 기준:** 규칙이 명확한 단순 주문 상태 조회·CRUD는 기존 Java/Spring 로직만으로 충분할 수 있다. 반면 자연어에서 조건을 추출하거나, 여러 종류의 문서와 조회 결과를 종합하는 데 모델 능력이 유용할 수 있다. 작업 경로가 고정돼 있으면 우선 일반적인 프로그래밍 흐름을 고려하고, 모델이 다음 도구·작업을 동적으로 선택해야 하는 경우에 Agent 방식을 검토한다.

모델을 통합해도 권한 검사, 입력/출력 검증, 정합성, 외부 API 지연·오류·비용, 관측·감사 책임이 사라지는 것은 아니다. DTO 역직렬화 성공도 비즈니스 규칙 검증을 의미하지 않는다.

## Discussed, not yet accepted

- AgentLab 13단계의 **일부 단계만 더 깊게 실습**하고 Skills/Subagent는 사례 중심으로 축소하는 권장안.
- 기존 로드맵 안에 **Structured Output 및 AI 출력 평가·검증** 실습을 어느 정도 보강할지에 관한 제안.
- 특정 주문/배송 시나리오를 AgentLab의 단일 통합 예제로 채택하는 제안.

위 항목들은 합리적인 후보이지만 **사용자가 로드맵 변경이나 프로젝트 구현을 확정 승인한 기록이 아니다**. 후속 검토 전에는 기존 13단계 로드맵을 유지한다.
