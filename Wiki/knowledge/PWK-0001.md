# PawCycle — code and design reverse-engineering learning guide

## Intent and authority
This is the user-confirmed **learning operating guide**, migrated from [PawCycle Issue #456](https://github.com/guseoh/pawcycle-commerce/issues/456) to AI-retrievable Wiki knowledge. It is **not** evidence that the course has been completed, that every code path was inspected, or that any production changes were approved. The original Issue contains full context; PawCycle source, tests, approved architecture/API contracts and runtime evidence remain authoritative for technical facts.

Goal: independently understand, explain, modify and safely operate the complete AI-assisted PawCycle system. Learn its actual Java/Spring/JPA/SQL, transactions, business invariants, architecture, ERD, processes, tests, deployment and recovery. Optimize for understanding **why** the design was chosen and what trade-offs it creates, not for memorizing every class or producing more AI-generated features.

## Default learning loop
1. **Broad system map (L1).** On the current `main`, map application entry points, packages, DI/configuration, domain boundaries, controllers, security, APIs, data model, Flyway migrations, runtime and tests. Treat historic docs as hypotheses until matched to current implementation.
2. **One vertical feature (L2).** Trace user action → normal/failure states → HTTP/filter/security → Controller/DTO → Service/Transaction → Repository/Entity/JPA → SQL/schema/index → response/exception; identify important calls and ownership boundaries.
3. **Horizontal Java/Spring explanation (L3).** Where the real feature uses DI/IoC, AOP/proxy, MVC, Session/CSRF, JPA persistence context/flush, transactions/propagation/isolation, locks, error handling or Java object design, explain the mechanism with the project code and applicable reference docs. Avoid redundant lectures.
4. **Reconstruct and validate (selective L4).** Explain requirements and invariants in the learner's own words, compare alternatives and trade-offs, and when appropriate make an isolated change/test to validate understanding. AI explanation alone does **not** certify user understanding.
5. **Record the decision chain.** Problem → current source evidence → candidate alternatives → rationale/cost → observed tests/production limits → KEEP/IMPROVE/DEFER. Link existing ADRs and Wiki decisions instead of duplicating them.

Default interaction: **code-first and focused**. No mandatory quiz, no recurring long theory lessons. Explain deeper only when requested or when a concrete design or correctness risk demands it. The learner controls pacing, depth and order.

## Suggested feature progression — flexible, not a completion checklist
| Order | Feature | Focus |
| --- | --- | --- |
| 1 | Member shipping-address CRUD | `MemberAddressController`, application service, entity/repository/DTO, ownership, default address, logical/physical ERD, basic Spring/JPA/transaction flow |
| 2 | Product query and catalog | API/DTO/Entity, Querydsl, SQL, indexes, filters/pagination |
| 3 | Member authentication and authorization | SecurityFilterChain, Session, principal, CSRF, ownership checks; related [PWC-0007](../decisions/PWC-0007.md) |
| 4 | Cart and Wishlist | Persistence, change/version semantics, concurrency |
| 5 | Checkout, Order, Payment, Inventory, cancel/refund | Invariants, idempotency, locking, provider I/O outside transaction, recoverability; unresolved [Issue #417](https://github.com/guseoh/pawcycle-commerce/issues/417) and [PWC-0016](../decisions/PWC-0016.md) |
| 6 | Subscription scheduling | State transitions, retries, duplicate avoidance, command/automation ownership |
| 7 | Recommendations and AI | Candidate validation, Spring AI/client boundary, fallback and quality/cost |
| 8 | Cross-cutting architecture and operations | Runtime/Observability, tests, full ERD/process reconstruction, release and recovery |

At the first feature, relate the address CRUD to Security, JPA and DB as needed; do **not** require the full theory curriculum first.

## Learning coverage and evidence
- **L1:** locate and explain responsibilities across the full backend.
- **L2:** reproduce important request/data/state transitions for core features.
- **L3:** explain critical Java/Spring/DB mechanisms, alternatives, failure boundaries and why they matter.
- **L4:** selectively rebuild, change or verify core behavior independently.
- Preserve source URL/commit, experiment settings, environment, observed results and limitations. Distinguish source inspection, isolated tests, user-provided observations, and independently verified live production state.
- Portfolio-worthy records emphasize consequential decisions, concurrency/consistency, failure/debugging, load testing and real operations. Do not claim an experiment or deployment that did not run.

## Parallel operations and later experiments
OCI operations are a **parallel learning track**, not a prerequisite or automatic mutation: inspect `app01`, Compose/containers, Managed MySQL, network, backup/rollback, monitoring and release evidence under separate access/approval rules.

After sufficient code understanding, isolated exercises may compare transaction/lock order, duplicate payment confirmation, provider success + local DB failure, concurrency races, AOP/async, caching and Spring AI. A successful isolated learning experiment does not authorize adopting it in production.
