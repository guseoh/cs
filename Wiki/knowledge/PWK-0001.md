# PawCycle 전체 시스템 리버스 엔지니어링 — 학습·설계 분석 가이드

## 목적·권위·진행 경계

사용자 확정(2026-11-05): PawCycle은 **단순한 기능/도메인 흐름·코드 해설**이 아니라, 요구사항, 객체지향·DDD 설계, 논리·물리 ERD, Java/Spring/JPA/MySQL 내부 원리, API·보안, 전체 시스템 아키텍처, Frontend 연결, CI/CD·네트워크·인프라·AWS/OCI 운영, 관측·장애·복구, 기술 선택·실패·대안·대가까지 **전체를 해체하여 재구성**하는 학습 대상이다. 최종 목표는 사용자가 독립적으로 시스템을 설계·설명·비판·검증·필요 시 수정할 수 있는 역량이다.

[원본·개정 학습 기준: PawCycle Issue #456](https://github.com/guseoh/pawcycle-commerce/issues/456)을 구체적 질문·범위의 기준으로 삼는다. 이 문서는 AI 검색용 **운영 가이드**이고 실제 코드·도메인 계약·운영 승인 원본의 대체물이 아니다.

**OOP·DDD 백엔드 리팩터링은 이미 별도 계획으로 진행 중이다.** 이를 새로 계획하거나 완료·병합됐다고 추정하지 않는다. 리팩터링 전후의 책임·의존·도메인 모델·불변식·잠금·트랜잭션 변경을 기존 PR/Issue/ADR/테스트로 복원하고, 실제 학습은 작업 시점 최신 `main`을 기준으로 한다. 리팩터링이 진행 중이면 병합된 현재 구현과 미병합 계획을 구분한다. 코드/OCI/Production 변경은 각각 별도 권한과 검증 Gate가 필요하다.

## 네 관점의 교차 검증

| 관점 | 출발점 | 핵심 산출 |
| --- | --- | --- |
| **하향식** | 요구사항·제약 → 시스템·컴포넌트 → 코드 | 구조의 필요성·책임·아키텍처 가설 |
| **상향식** | 실제 클래스·SQL·Migration·설정·테스트 → 관계/경계 | 지금 구현된 구조·데이터·의존 사실 |
| **동적 실행 추적** | Frontend/HTTP/Security → Service/Transaction → JPA/SQL/MySQL·Provider → 응답/실패 | 정상·예외·동시성의 실제 경로와 상태 변화 |
| **역사 복원** | 최초 결정·대안 → 실패/검증 → 후속 변경 | 선택 이유·대가, 현재 유지/보류 판단 |

C4 **System Context/Container/Component/Code**와 필요한 **Dynamic/Deployment** 그림으로 전체를 시각화한다. C4는 표현 방식이고 L1~L4는 학습 깊이이다. 처음에는 **전체 시스템 지도**, 그다음 **주요 기능의 수직 추적 ↔ 관련 기술의 수평 심화**, 이후 **핵심 설계의 독립 재구성/검증**을 반복한다. 네 활동은 필요에 따라 왕복하며, 한 순서를 강제 마일스톤으로 만들지 않는다.

## 전체 분석 인벤토리

1. **요구사항·제품·도메인:** 기능/비기능 요구, 비즈니스 프로세스와 상태 전이, 공통 언어, Bounded Context, 객체 책임·협력·캡슐화, Entity/VO/Aggregate/Domain Service, 스냅숏·불변 조건과 OOP·DDD 리팩터링 전후 판단.
2. **ERD·데이터 모델:** 전체/기능별 논리·물리 ERD, Flyway DDL, PK/FK/Unique/CHECK, Index·조회 모델, SQL·실행계획, 데이터 수명·정합성·보존 전략. DB 테이블을 도메인 Aggregate와 동일시하지 않는다.
3. **전체 아키텍처:** 애플리케이션 실행점, 모듈/패키지·Layer·DI/Bean/Configuration, API·Application·Domain·Persistence·Infrastructure 의존, 외부 Adapter/Provider, 동기/비동기 협력과 대안 구조.
4. **Java/Spring 실행 원리:** Java OOP/예외/컬렉션/스레드/JVM·GC, IoC/DI/Proxy/AOP, Servlet/DispatcherServlet/MVC/Validation, Security Filter/Session/CSRF/인가, Transaction/Propagation/Isolation, JPA 영속성 컨텍스트/Flush/Dirty Checking/연관관계/Lazy/N+1, Querydsl.
5. **MySQL·트랜잭션·성능:** MVCC, InnoDB Lock/Deadlock, CAS/버전·멱등·동시성, 예약 재고·중복 Checkout·Payment/Subscription 경계, 부하 Dataset·관측·최적화 전후 대가.
6. **Frontend/API·보안:** 사용자 행동→HTTP/쿠키/CSRF/오류·Retry→Backend/DB 경계, API/DTO 계약, 권한·소유권, 실패 시 화면과 서버 상태의 정합성. Frontend 디자인 전수 리뉴얼은 기본 목적이 아니다.
7. **인프라·배포·네트워크:** Docker/Linux/Nginx/DNS/TLS, CI/CD·GHCR·Host Pull/release/rollback, OCI Compute/VCN/Managed MySQL/Observability, **과거 AWS** EC2/RDS/EBS/S3/SSM 등과 현재 OCI의 기술·비용·가용성·복구 제약 비교.
8. **관측·장애·복구·테스트:** Unit/MySQL Integration/API Contract/Frontend E2E/CI 보장 범위, Logs/Metrics·진단, Failure Modes·백업/Restore·Rollback·RTO/RPO 및 실제 미검증 영역.
9. **AI 활용 개발·Harness:** 요구/설계 승인→Codex 구현→테스트/독립 Review→사용자 병합, AGENTS·Skill·Runbook의 효과·실패·운영 복잡성·Trade-off.

기능·도메인 대상은 Member/Address/Pet, Catalog/Product/SKU, Cart/Wishlist, Checkout/Order/Payment/Inventory, Subscription/Plan/Schedule/Billing, Delivery/Cancel/Return/Refund, Coupon/Membership, Recommendation/Interaction/AI, Admin/Operations 전체다. 중요도와 위험에 따라 깊이를 다르게 한다.

## L1~L4의 적용 방식

| 깊이 | 목표 | 범위 |
| --- | --- | --- |
| L1 전체 지도 | 책임·실행점·주요 의존·데이터/배포 관계 설명 | 전체 프로젝트에 걸쳐 넓게 |
| L2 기능 수직 추적 | 실제 요청·객체·SQL·데이터·오류·상태 전이 복원 | 핵심 기능별 |
| L3 기술/선택 심화 | 원리, 당시 선택 근거, 대안·비용·동시성·보안·복구 경계 | 고위험/중요 영역 중심 |
| L4 독립 재설계·검증 | 요구·제약으로 새 구조를 설계하고 실제 구현/테스트와 비교 | 핵심 주제 선택적 |

모든 파일을 같은 깊이로 설명하거나 모든 코드를 암기하지 않는다. **AI가 설명을 끝냈다는 이유로 사용자의 이해·실험이 완료된 것으로 기록하지 않는다.** 의무 퀴즈/진도율 체크리스트는 없다.

## 주제별 실무 분석 루프

1. **요구와 질문:** 어떤 사용자 문제·비기능 제약·정상/실패 시나리오/불변 조건을 해결하는가?
2. **실제 구현:** 최신 `main`의 코드, 설정, Migration, 엔티티·SQL, 테스트와 호출·트랜잭션·데이터 흐름으로 검증한다.
3. **내부 원리:** 실제 지점에서 Spring/Java/JPA/MySQL/네트워크 원리가 왜 그렇게 동작하는지 필요 깊이만큼 설명하고, 다른 사용처와 비교한다.
4. **설계 역사:** ADR·Issue·PR·Wiki·승인/실패를 추적한다. 기록 없는 당시 이유는 **추정**으로만 제시한다.
5. **대안 비교:** 객체 모델·DB/SQL·동기화·인프라/아키텍처의 이점과 복잡성, 성능·정합성·보안·운영 대가를 비교한다.
6. **반례/증거:** 기존 테스트·CI·실측과 승인된 격리 MySQL+Fake Provider 실험을 구분하고, 예상·관측·미검증을 명시한다.
7. **판단:** `KEEP / IMPROVE(검증된 최소 수정) / DEFER / REJECT`로 구분한다. 수정이 필요하면 별도 범위·승인·Branch/PR/Review·검증 Gate를 사용한다.

**결제 예시:** 왜 Order/Payment를 분리했는가 → 중복 HTTP 요청·멱등/상태 전이 → Proxy/트랜잭션·DB Lock/Flush·Commit → 외부 Provider 성공·DB 실패/복구 → 단일 트랜잭션 vs Queue/Outbox 대안 → 격리 반례 실험 → 유지/변경 결정. 대안을 사용해야 한다는 결론을 미리 정하지 않는다.

## 권장 착수와 학습 운영

1. **먼저 전체 시스템 지도**: C4, 주요 제품 제약, 데이터/배포·네트워크·보안·운영/CI 경계.
2. 요구사항·도메인·전체/부분 ERD·객체 모델과 현재 의존을 연결한다.
3. Spring Boot 실행/DI/Bean/MVC/공통 설정의 위치를 확인한다.
4. **첫 세부 수직 기능은 기존 승인대로 회원 배송지 CRUD**: `MemberAddressController`, `MemberAddressApplicationService`, `MemberAddress`, `MemberAddressRepository` 및 DTO·테스트, 소유권/기본 배송지, 실제 SQL·JPA·트랜잭션·물리 ERD.
5. 필요에 따라 인증·인가 → 카탈로그/Querydsl → Cart/Wishlist → Checkout/Order/Payment/Inventory/환불 → Subscription/Scheduler/Billing → 추천/AI·운영 기능으로 확장한다.
6. **운영·보안·성능 학습은 항상 병렬**이다. OCI 실상 확인을 코드 전수 완료 뒤로 미루지 않는다. 독립 재설계는 핵심 영역에서 반복한다.

기본 설명은 **구체적 한국어 서술**로 개념→실제 코드→실행 원리→선택 이유·대안→실패·검증을 연결한다. 필요한 diagram·핵심 요약·표를 사용하되 한 줄 메모 나열을 피한다. 공식/한국어 기술 자료를 함께 보되 핵심 설명을 외부 링크로 떠넘기지 않는다.

## 증거·기록·수정·안전

- **승인된 계약 / 현재 코드·Migration 사실 / 실제 테스트·CI / 실제 운영 관측 / 당시 문서 주장 / 미검증 추정**을 구분한다. 과거 AWS 운영 증거와 현재 OCI 운영은 절대 혼동하지 않는다. `Implemented / Verified / Production Verified`는 별도 상태다.
- 학습 중 발견된 유의미한 최소 코드 변경은 진행 중 OOP·DDD 리팩터링과 중복/충돌을 검토한 뒤 별도 승인된 변경으로 처리한다. 실제 운영 DB·Cloud·Secret·유료 리소스·장애 주입·Restore·Rollback은 해당 최신 Runbook Start/Stop/Recovery Gate 없이는 실행하지 않는다.
- [Wiki capture-policy](../capture-policy.md)의 **PawCycle full mode**로 의미 있는 결과와 실패·대안을 출처 중심으로 기록한다. 일반 기술 개념은 `guseoh/cs/Study/**`, PawCycle의 실제 판단·실험은 `guseoh/cs/Project/pawCycle/**` 및 이 Wiki의 기록으로 분리하되 원본 ADR·PR·Issue를 중복 복제하지 않는다.
- 소스 링크·검증 시점·조건·한계·미해결 질문을 유지한다. 공개 Wiki에 비밀값·개인정보·비공개 대화 원문이나 원시 Production 데이터는 기록하지 않는다.
- 이 문서 개정은 **학습 방식이 합의되었다는 증거**이지 리버스 엔지니어링 학습의 완료나 OOP·DDD 리팩터링/운영 복구의 검증 근거가 아니다.
