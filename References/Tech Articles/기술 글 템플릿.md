# 원문 제목

> [!abstract] 한눈에 보는 핵심
> **문제** · 무엇이 병목이고 왜 변경이 필요했는가?
>
> **선택** · 어떤 접근을 채택했고 결정적인 근거는 무엇인가?
>
> **결과** · 원문에서 실제 검증한 변화와 아직 남은 한계는 무엇인가?

| 문서 정보 | 확인된 사실 |
| --- | --- |
| 출처 / 발행일 | 조직·작성자 / YYYY-MM-DD |
| 기술 영역 | 핵심 분류와 관련 기술 |
| 활용 가치 | 어떤 문제를 설계·구현할 때 참고할 수 있는가 |

## 01. 문제의 출발점

해당 기술 글을 읽기 전에 알아야 할 서비스의 상황과 기존 설계를 먼저 설명한다. 무엇이 문제가 되었고, 트래픽·데이터 정합성·운영 비용 등 어떤 제약 때문에 해결하기 어려웠는지 실제 사례로 서술한다.

- **문제의 증상:** 원문에서 언급한 장애·성능 저하·개발 비효율
- **핵심 제약:** 바꿀 수 없는 조건과 기대하는 목표
- **이전 방식:** 가능한 경우 기존 시스템의 처리 흐름

## 02. 접근 방식과 설계 과정

### 처리 흐름과 책임 분리

실제 데이터와 요청이 통과하는 과정을 순서대로 설명한다. 코드나 그림이 있으면 본문에 포함하고, 왜 그 위치에서 책임을 나누었는지 해설한다.

### 주요 기술 선택

기술 이름만 나열하지 않고 **선택 이유 → 동작 원리 → 기대 효과 → 비용**을 설명한다. 코드가 있는 글이라면 필요한 부분에 코드 블록을 넣고, 실행 순서와 핵심 라인을 함께 설명한다.

> [!example] 설계에서 주목할 점
> 기존 방식과 무엇이 달라졌는지, 시스템의 불변식과 장애 경계가 어디인지 구분해서 정리한다.

## 03. 대안과 트레이드오프

*원문에서 비교·검토한 대안이 있는 경우에만 작성한다. 근거가 없다면 소제목을 삭제한다.*

| 검토 기준 | 선택한 접근 | 다른 대안 / 포기한 이점 |
| --- | --- | --- |
| 원문에 언급된 기준 | 실제 채택안 | 실제 검토된 내용 |

## 04. 구현 결과와 검증

**결과를 주장하는 조건과 근거**를 함께 기록한다. 성능·처리량·지연시간 등 수치를 인용할 때는 측정 대상과 비교 기간, 실험 환경을 명확히 한다.

| 관측 항목 | 이전 | 이후 | 해석 및 조건 |
| --- | --- | --- | --- |
| 원문에 있는 지표 | — | — | 확인된 결과만 |

> [!warning] 검증 범위
> 검증 수치가 없거나 비교 조건이 불분명하면 **원문 미제시**라고 쓰고, 추정 효과를 성과처럼 기록하지 않는다.

## 05. 연결되는 개념과 내 프로젝트

실제 Vault에 존재하는 개념 노트만 Wikilink로 연결한다. 글에서 다룬 문제를 Java·Spring 백엔드 관점에서 재현할 수 있는 실험으로 바꿔 본다.

- [ ] 재현할 시나리오와 예상되는 실패 조건 정의
- [ ] 성능·정합성·운영 지표를 비교하는 테스트 수행
- [ ] 트레이드오프를 정리해 ADR 또는 학습 노트에 연결

> [!note] 읽고 남긴 생각
> 원문에서 확인한 **사실**과 나의 **추가 해석·의문**을 분리한다. 아직 검증하지 않은 제안은 검증된 결론처럼 작성하지 않는다.
