# 디자인 컴포넌트 라이브러리를 ‘실제 사용 방식’에 맞게 다시 설계한 이야기

> [!abstract] 한 줄 정리
> 과거의 호환성 요구에 맞춘 UMD·CommonJS 및 28개 패키지 구조가 현재의 단일 사용 방식과 어긋나자, ESM과 명시적 exports로 구조를 단순화해 빌드와 번들 비용을 크게 줄였습니다.

> 컬리 기술 블로그 · 2025-12-23

## 핵심 내용

- **문제:** Kitchen 디자인 시스템은 일부 컴포넌트만 import해도 전체 코드가 번들에 포함됐습니다. 컴포넌트별 패키지 구조를 유지했지만 실제 사용과 배포는 단일 진입점에 집중됐습니다. - **원인:** UMD/CJS 혼합과 kitchen-core의 전체 re-export 때문에 번들러가 의존성을 정적으로 추적하기 어려웠습니다. 레거시 지원을 위한 초기 설계가 현재 사용 방식에서는 제약이 됐습니다. - **접근:** ESM-only와 exports 명시로 트리셰이킹을 지원하고, 28개 컴포넌트 패키지를 단일 kitchen 패키지로 통합했습니다. 공통 디자인 토큰은 foundation으로 분리했습니다.

- **수치:** 빌드 60.93→6.94초(88.6% 단축), Cold 개발 확인 86.34→20.87초(75.82% 단축), 공통 번들 내 Kitchen 코드 1.61MB→162.5KB(89.97% 감소), 코드 약 2만8천 줄 감소를 보고했습니다. - **트레이드오프:** 단일 패키지의 변경 범위와 빌드 부담을 우려했지만 실제 사용 단위와 맞추는 이점을 택했습니다. 번들러 자체 교체는 영향 범위를 고려해 보류했고, 수치는 명시된 측정 환경의 결과입니다.

컴포넌트를 여러 패키지로 나눴다고 애플리케이션 번들이 작아지는 것은 아니다. 소비자가 단일 진입점으로 모든 코드를 가져오고 CJS/UMD 전체 Re-export가 섞이면 번들러의 Tree Shaking이 제한될 수 있다. 원문은 패키지의 개수보다 실제 소비 방식에 맞춰 Entry Point와 Module 형식을 재설계했다.

| 측정 | 이전 | 개선 |
| --- | ---: | ---: |
| 빌드 시간 | 60.93초 | 6.94초 |
| Cold 개발 확인 | 86.34초 | 20.87초 |
| 공통 번들 Kitchen 코드 | 1.61MB | 162.5KB |

28개 컴포넌트 패키지를 단일 `kitchen`으로 합치면서 Foundation 토큰을 분리하고 ESM과 Exports를 명시한 것이 핵심이다. 하나의 패키지로 통합했다는 사실 자체보다 실제 소비 프로젝트의 번들 결과를 측정해야 한다.

## 왜 읽을까

모듈과 패키지를 많이 분리하는 것이 언제나 좋은 설계가 아니라는 것을 수치로 보여줍니다. 사용 방식이 바뀌었는데 과거의 추상화와 배포 경계를 계속 유지할 필요가 있는지 판단하는 기준을 얻을 수 있습니다.
