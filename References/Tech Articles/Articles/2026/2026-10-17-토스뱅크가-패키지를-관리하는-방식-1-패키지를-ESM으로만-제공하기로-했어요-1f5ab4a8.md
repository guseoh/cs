# 토스뱅크가 패키지를 관리하는 방식 #1: 패키지를 ESM으로만 제공하기로 했어요

> [!abstract] 한 줄 정리
> ESM과 CommonJS를 동시에 배포하면 같은 패키지의 상태가 두 벌로 생성될 수 있다. 사용 환경을 통제할 수 있는 사내 패키지라면 호환성 요구를 확인하고 ESM-only로 단순화할 수 있다.

> 토스 기술 블로그 · 토스뱅크 프론트엔드 챕터 · 2026-10-15

## 핵심 내용

같은 패키지를 ESM과 CommonJS(CJS)로 이중 배포하면 `import`와 `require()`가 서로 다른 모듈 인스턴스를 불러와 런타임 상태가 분리될 수 있다. 특히 React Context는 Provider와 Hook이 같은 객체를 참조해야 하므로 서로 다른 빌드를 읽는 Dual package hazard가 사용자에게 직접적인 버그로 드러난다.

토스뱅크는 사내 소비 애플리케이션과 Node.js 실행 환경을 통제할 수 있다는 조건에서 ESM-only로 배포하기로 했다. Node.js 22.12.0 이후의 `require(esm)` 지원을 활용할 수 있지만 ESM의 최상위 `await`가 있다면 동기 `require()`로 불러올 수 없다는 한계가 남는다. 구형 Node.js를 지원해야 하는 외부 공개 라이브러리에는 여전히 CJS 대응이 필요할 수 있으므로 조직의 소비 환경을 확정하지 않고 보편 규칙으로 삼을 수 없다.

```json
// ESM-only 의도를 보여 주는 최소 예시 (원문 설정 그대로가 아님)
{
  "type": "module",
  "exports": {
    ".": "./dist/index.js"
  }
}
```

소비자가 여전히 `require()`를 사용하면 실행 중인 Node 버전과 의존 모듈의 top-level await 유무를 확인해야 한다.

| 배포 전략 | 이득 | 위험·확인 사항 |
| --- | --- | --- |
| ESM + CJS Dual | 구형 Node 및 CJS 소비자 지원 | Provider/Hook 등 상태 모듈의 중복 인스턴스 |
| ESM-only | 빌드/타입/디버깅 경로 단순화 | 지원하지 않는 런타임과 top-level await 제약 |
| 호스트 번들링 | 앱별 타깃 결정 | 타입 및 export 조건 해석 일치 필요 |

타입 선언도 두 모듈 경로로 잘못 분리하면 CJS 경로에서 선언이 누락되어 TypeScript가 부정확한 `any`로 처리할 위험이 있다. 구현과 선언을 한 경로로 관리하면 빌드·버전·디버깅 비용을 줄일 수 있으나 ESM-only 정책의 호환 범위를 테스트해야 한다. 원문에는 빌드 성능 개선의 정량값이 제시되지 않았다.

## 왜 읽을까

호환성을 넓히는 선택이 런타임 상태 분리와 타입 안정성 문제를 만들 수 있다는 사례다. 기술 표준을 도입할 때 실제 소비 환경과 유지보수 비용을 먼저 확인해야 한다.

**프로젝트에 적용 — 공통**

- [ ] 프런트엔드 패키지의 `exports` 조건과 ESM/CJS 혼용 여부를 확인한다.
- [ ] 공유 상태·싱글턴·React Context가 중복 로드될 가능성을 점검한다.
- [ ] 실행 환경을 확인하지 않고 ESM-only로 전환하지 않으며 타입 검사와 실행 테스트를 구분한다.
