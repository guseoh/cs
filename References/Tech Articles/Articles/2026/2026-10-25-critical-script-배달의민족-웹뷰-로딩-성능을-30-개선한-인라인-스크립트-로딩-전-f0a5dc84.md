# critical-script, 배달의민족 웹뷰 로딩 성능을 30% 개선한 인라인 스크립트 로딩 전략 이야기

> [!abstract] 한 줄 정리
> 느린 API나 번들을 각각 더 빠르게 만드는 대신, HTML 파싱 직후 API 호출을 시작해 JavaScript 다운로드·실행과 병렬화하면 로딩의 임계 경로를 단축할 수 있다.

> 우아한형제들 기술블로그 · 추용혁 · 2026-10-21

## 한눈에 보기

첫 화면 표시 시간은 JavaScript 다운로드나 API 호출 하나의 처리 시간을 줄이는 것만으로 개선되지 않을 수 있다. HTML 파싱, 번들 로드, 앱 초기화, API 호출이 직렬로 놓이면 마지막 요청의 시작 시간이 늦어진다. 배달의민족은 HTML 내 작은 스크립트에서 초기 API 호출을 먼저 시작하고 메인 앱이 그 Promise를 이어받게 만들어 요청의 임계 경로를 단축했다.

*그림 2. 실제 사용자 데이터의 LCP 분위수 비교 그래프 — [출처: 원문 기술 블로그](https://techblog.woowahan.com/27864/)*

첫 번째 그림에서 핵심은 API 응답 자체를 단축한 것이 아니라 **요청 시작을 앞당겼다**는 사실이다. Promise를 `window`에 보관하고 Axios 인터셉터가 동일 요청에 대해 그 결과를 재사용함으로써 불필요한 중복 호출을 피한다. 이 최적화는 코드 분리와 런타임 의존성을 늘릴 수 있어 페이지 근처의 `*.critical.ts`와 빌드 플러그인, 약 8KB 기본 상한으로 유지보수 비용도 관리했다.

## 핵심 내용

### 도입 배경과 문제

**문제:** 정적 웹뷰의 HTML 파싱 → 번들 다운로드·실행 → React 실행 → API 호출 → 렌더링이 직렬로 이어져 첫 화면 표시가 늦었다.

### 선택한 구조와 구현

**접근:** 인라인 스크립트가 HTML 파싱 시점에 `fetch`를 시작하고 Promise를 `window` 캐시에 저장한다. 메인 앱은 axios 인터셉터를 통해 같은 요청의 결과를 재사용한다.

**수치:** 초기 갤럭시 S22+·Wi-Fi 측정에서 LCP가 \*\*1,340ms → 847ms(37% 개선)\*\*로 바뀌었다. 실제 사용자 Sentry 데이터에서는 적용 전후 각 1주일을 비교해 LCP p50·p75·p90이 **25~35%** 개선됐다.

### 실행 결과와 한계

**구조:** 첫 구현은 별도 패키지에 코드가 떨어져 있어 유지보수가 어려웠다. `*.critical.ts` 파일을 페이지 옆에 두고 빌드하는 Vite 플러그인을 만들었으며, 의도치 않은 의존성 포함을 막기 위해 인라인 산출물의 기본 상한을 **8KB**로 설정했다. 적용 페이지는 약 **80개**로 확대됐다.

**트레이드오프:** 실제 CPU 실행 시간이나 네트워크 전송 시간이 줄어드는 것은 아니다. 메인 앱과 런타임을 공유하지 못하므로 타입·브라우저 지원 범위·전역 캐시·요청 중복을 별도로 고려해야 한다.

### 설계 선택과 핵심 수치

| 측정 조건 | 적용 전 | 적용 후·변화 |
| --- | ---: | ---: |
| 갤럭시 S22+·Wi-Fi의 실험 LCP | 1,340ms | 847ms(약 37% 개선) |
| 실제 사용자 Sentry RUM | 적용 전 1주일 | 적용 후 1주일, LCP p50/p75/p90 약 25~35% 개선 |
| 적용 페이지 수 | 초기 일부 페이지 | 약 80개로 확대 |
| 중요 인라인 스크립트 크기 | 별도 최적화 필요 | 기본 8KB 상한 설정 |

*실험실의 단일 기기 수치와 실제 사용자 데이터는 서로 다른 측정 집단이다. API 계산이나 네트워크 전송 자체의 시간을 줄였다는 뜻은 아니다.*
