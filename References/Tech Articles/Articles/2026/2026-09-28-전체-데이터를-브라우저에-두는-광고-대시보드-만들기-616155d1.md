# 전체 데이터를 브라우저에 두는 광고 대시보드 만들기

> [!abstract] 한 줄 정리
> 처리 위치는 관습이 아니라 데이터 상한과 사용자 행동을 측정해 결정해야 한다. 서버 작업을 클라이언트로 옮기는 과감한 선택도 전제와 실패 비용을 숫자로 고정하면 합리적인 설계가 될 수 있다.

> Toss Tech · 2026-08-20

## 핵심 내용

관리자용 광고 대시보드에서 필터·정렬·검색·페이지 이동마다 서버를 호출하면 수백 밀리초의 왕복 대기가 쌓이고 요구사항이 바뀔 때마다 백엔드 API를 수정해야 한다. 토스는 전체 데이터가 실제로 최대 약 2만 건이고 설계 상한이 10만 건이라는 사실을 확인한 뒤, 모든 데이터를 브라우저가 가지고 화면 처리를 직접 수행하는 대안을 선택했다.

전체 데이터도 종류에 따라 갱신 주기가 달라서 Metadata와 Performance, 부가 컬럼 API를 분리하고 각각 5분·5초처럼 다른 캐시 수명을 적용했다. 10만 건의 필터·검색·정렬·페이징은 Web Worker에서 수행해 메인 UI 스레드를 막지 않고, 초기 대용량 ArrayBuffer는 Transferable로 넘겨 큰 데이터의 복사 비용을 줄였다. 필요한 테이블 형태로 정규화한 다음 0건 항목도 포함하는 집계나 새로운 정렬 기준을 UI에서 계산할 수 있다.

```js
// 메인 스레드에서 Worker로 버퍼 소유권을 이전하는 예시
worker.postMessage({type: 'LOAD', buffer}, [buffer]);
// 이후 원래 ArrayBuffer는 전송한 쪽에서 사용할 수 없음
```

*실제 원문 Worker 프로토콜 전체를 복제한 코드가 아니라 Transferable의 비용 모델을 설명한다.*

| 데이터 유형 | 변경 특성 | 예시 캐시 기간 |
| --- | --- | --- |
| Metadata | 구조·이름 중심, 비교적 안정 | 5분 |
| Performance | 수치 변화가 빠름 | 5초 |
| 전체 데이터 상한 | 최대 약 2만, 목표 10만 | Worker 약 10ms/연산 |

*수치는 원문의 해당 브라우저·데이터 구조 실험이며 범용 SLA는 아니다.*

원문 기준 10만 건 연산은 약 10ms였지만 초기 전체 다운로드와 메모리 사용량, Worker 재시작 시 원본 데이터 재전송이 비용으로 남는다. 데이터가 계속 증가하거나 개인화 권한이 복잡해질 경우 같은 구조가 성립하지 않을 수 있으므로 브라우저 저장 가능 상한을 테스트로 고정해야 한다. 저장된 데이터의 만료와 실제 광고 성과의 최신성도 별개다.

## 왜 읽을까

‘필터링은 서버에서 해야 한다’ 같은 관습 대신 데이터 규모의 상한부터 측정하고 처리 위치를 결정한다. 선택하지 않은 Virtual Scrolling·IndexedDB까지 이유를 남겨, 좋은 설계가 정답 기술을 고르는 일이 아니라 전제와 비용을 명확히 하는 일임을 보여준다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집글 검색·필터 요구가 생기면 데이터 규모와 사용 패턴부터 측정한 뒤 서버/클라이언트 처리 경계를 정한다.
- [ ] 하나의 무거운 응답에 모든 데이터를 묶기보다 변경 주기와 실패 영향이 다른 데이터는 API·캐시 경계를 분리할 수 있는지 검토한다.
- [ ] 아키텍처 결정 문서에 선택안뿐 아니라 기각한 대안과 다시 검토해야 할 데이터 임계값을 남긴다.
