# 전체 데이터를 브라우저에 두는 광고 대시보드 만들기

> [!abstract] 한 줄 정리
> 처리 위치는 관습이 아니라 데이터 상한과 사용자 행동을 측정해 결정해야 한다. 서버 작업을 클라이언트로 옮기는 과감한 선택도 전제와 실패 비용을 숫자로 고정하면 합리적인 설계가 될 수 있다.

> Toss Tech · 2026-08-20

## 핵심 내용

- **문제:** 필터·정렬·검색·페이지 이동마다 서버를 호출해 수백 ms씩 기다렸고, 전체 데이터가 클라이언트에 없어서 0건 항목 누락·임의 정렬 추가·계층 검증 같은 요구도 매번 서버 변경이 필요했다.
- **수치:** 실제 최대 데이터는 약 2만 건이었고 설계 상한을 10만 건으로 잡았다. 이 상한을 확인한 뒤 전체 데이터를 브라우저에 두는 선택을 했다.
- **구조:** 목록의 뼈대인 Metadata, 자주 바뀌는 Performance, 부가 컬럼 API를 분리하고 각각 5분·5초처럼 다른 캐시 수명을 적용해 점진적으로 화면을 완성한다.
- **성능:** 10만 건의 필터·검색·정렬·페이지네이션은 Web Worker에서 처리하며 한 번의 연산은 약 10ms다. 초기 대용량 데이터는 ArrayBuffer를 Transferable로 넘겨 복사 비용을 피한다.
- **트레이드오프:** 첫 진입 시 전체 데이터를 받아야 하고 클라이언트 메모리와 Worker 장애 복구 비용이 늘어난다. Worker가 죽으면 데이터를 서버에서 다시 받아야 하므로 이 비용을 명시적으로 감수했다.

## 왜 읽을까

‘필터링은 서버에서 해야 한다’ 같은 관습 대신 데이터 규모의 상한부터 측정하고 처리 위치를 결정한다. 선택하지 않은 Virtual Scrolling·IndexedDB까지 이유를 남겨, 좋은 설계가 정답 기술을 고르는 일이 아니라 전제와 비용을 명확히 하는 일임을 보여준다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집글 검색·필터 요구가 생기면 데이터 규모와 사용 패턴부터 측정한 뒤 서버/클라이언트 처리 경계를 정한다.
- [ ] 하나의 무거운 응답에 모든 데이터를 묶기보다 변경 주기와 실패 영향이 다른 데이터는 API·캐시 경계를 분리할 수 있는지 검토한다.
- [ ] 아키텍처 결정 문서에 선택안뿐 아니라 기각한 대안과 다시 검토해야 할 데이터 임계값을 남긴다.
