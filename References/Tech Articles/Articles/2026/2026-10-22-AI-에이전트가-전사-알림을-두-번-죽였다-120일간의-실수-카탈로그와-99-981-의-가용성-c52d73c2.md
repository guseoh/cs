# AI 에이전트가 전사 알림을 두 번 죽였다: 120일간의 실수 카탈로그와 99.981%의 가용성

> [!abstract] 한 줄 정리
> AI를 운영 환경에 투입할 때는 명령 실행 속도보다 부작용을 막고 실제 사고를 재발 방지 규칙으로 전환하는 체계가 중요하다.

> 아임웹 기술블로그 · Yonghyun Kim · 2026-02-28

## 핵심 내용

- **문제:** Datadog Slack 연동에 채널을 추가하려 AI가 문서상 유효한 API를 호출했지만 기존 OAuth 인증이 무효화돼 전사 알림이 3일간 중단됐다. 비슷한 사고가 몇 달 뒤 반복됐다. - **시행착오:** Redis CPU 99.8% 포화의 원인을 배치로 의심했지만 실제로는 운영 Redis를 바라본 OMS 부하 테스트가 원인이었다. Nginx 설정 손상이 프록시 4대로 전파될 위험도 발견했다. - **접근:** 120일간 경험한 AI 관련 사고 15건을 금지 명령, 안전한 대안, 사고 이력을 포함하는 가드레일로 정리했다. 공통 정책과 환경별 지식을 팀에 공유했다.

- **수치:** 작성자는 가용성 99.963% → 99.981%, 모니터 75개 → 191개, Target 5xx 비율 90% 감소를 보고했다. AI 정책만의 독립 효과를 측정한 수치는 아니다. - **주의점:** API 문서에 없는 부작용과 운영 환경의 영향 범위는 AI의 제안만으로 검증되지 않는다. 변경 전 승인과 복구 경로가 필요하다.

에이전트가 사용한 API가 문서에 기술된 정식 API여도 운영 서비스에서 부작용이 없다는 뜻은 아니다. 특히 Datadog과 Slack 같은 외부 통합의 자격 증명을 바꾸는 작업은 기존 알림 채널 전체에 영향을 줄 수 있어 API 호출 성공 여부 외에 **기존 알림이 계속 도착하는지**를 확인해야 한다. 운영 Redis를 대상으로 실행한 부하 테스트 역시 작업 의도와 실제 환경이 어긋난 사례다.

| 위험 유형 | 실행 전 확인 | 실행 후 검증 |
| --- | --- | --- |
| 외부 연동 변경 | 기존 OAuth·토큰·대상 채널 | 테스트 알림의 수신 |
| 부하 테스트 | 대상 클러스터와 계정 | 운영 자원 영향 |
| 프록시 설정 | 설정 Diff·영향 서버 | Syntax Check·헬스 체크 |
| AI 자동 조치 | 권한·승인·Rollback | 감사 로그·복구 절차 |

120일간 발생한 15건을 금지 목록으로만 저장하기보다 **실패를 만드는 조건, 안전한 대체 명령, 최소 검증 절차**를 함께 기록해야 유사 사고를 막을 수 있다. 가용성 99.963%→99.981%는 그 기간 여러 운영 변화가 반영된 결과로, AI 가드레일만의 인과 효과를 뜻하지 않는다.

## 왜 읽을까

운영 사고를 '다음엔 조심하자'로 끝내지 않고 실제 정책과 검증 절차로 바꾸는 과정을 볼 수 있다. 장애 원인을 추측 대신 관측 데이터로 확인하는 습관도 배울 수 있다.
