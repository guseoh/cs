# AI 에이전트가 전사 알림을 두 번 죽였다: 120일간의 실수 카탈로그와 99.981%의 가용성

> [!abstract] 한 줄 정리
> AI를 운영 환경에 투입할 때는 명령 실행 속도보다 부작용을 막고 실제 사고를 재발 방지 규칙으로 전환하는 체계가 중요하다.

> 아임웹 기술블로그 · Yonghyun Kim · 2026-02-28

## 핵심 내용

- **문제:** Datadog Slack 연동에 채널을 추가하려 AI가 문서상 유효한 API를 호출했지만 기존 OAuth 인증이 무효화돼 전사 알림이 3일간 중단됐다. 비슷한 사고가 몇 달 뒤 반복됐다.
- **시행착오:** Redis CPU 99.8% 포화의 원인을 배치로 의심했지만 실제로는 운영 Redis를 바라본 OMS 부하 테스트가 원인이었다. Nginx 설정 손상이 프록시 4대로 전파될 위험도 발견했다.
- **접근:** 120일간 경험한 AI 관련 사고 15건을 금지 명령, 안전한 대안, 사고 이력을 포함하는 가드레일로 정리했다. 공통 정책과 환경별 지식을 팀에 공유했다.
- **수치:** 작성자는 가용성 99.963% → 99.981%, 모니터 75개 → 191개, Target 5xx 비율 90% 감소를 보고했다. AI 정책만의 독립 효과를 측정한 수치는 아니다.
- **주의점:** API 문서에 없는 부작용과 운영 환경의 영향 범위는 AI의 제안만으로 검증되지 않는다. 변경 전 승인과 복구 경로가 필요하다.

## 왜 읽을까

운영 사고를 '다음엔 조심하자'로 끝내지 않고 실제 정책과 검증 절차로 바꾸는 과정을 볼 수 있다. 장애 원인을 추측 대신 관측 데이터로 확인하는 습관도 배울 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] OCI와 Docker의 읽기 전용 점검과 변경 작업을 구분하고 승인 기준을 명시한다.
- [ ] 배포 전 Health, DB 연결 대상, Secret, 롤백 경로를 확인하는 체크리스트를 작성한다.
