# “스케줄이 또 안 돌았어요” — 우리가 Temporal을 선택한 이유

> [!abstract] 한 줄 정리
> 업무상 중요한 스케줄을 cron으로 실행하는 것보다 실패·재시도·진행 상태까지 복구 가능한 워크플로로 모델링하는 편이 필요한 순간이 있다. Temporal을 선택한 이유보다 어떤 실패 비용 때문에 워크플로 엔진이 필요해졌는지가 핵심이다.

> 무신사 테크 블로그 · 2026-02-05

## 핵심 내용

OMS 출고 지시 스케줄이 Jenkins crontab에서 실행되지 않으면 물류센터 작업과 배송까지 지연됐다. 실행 여부를 감시하는 별도 스케줄도 자체적으로 실패할 수 있어 감시 체계 역시 신뢰하기 어려웠다. 실행 상태와 이력을 보존하고 네트워크·일시적 장애를 자동 재시도할 수 있도록 업무 흐름 일부를 Temporal Workflow로 이전했다.

하나의 Workflow가 정책 조회, 중복 여부 확인, wave/batch 생성과 외부 파이프라인 호출 같은 여러 Activity를 조율하고, Activity는 재시도되어도 문제가 없도록 멱등성을 고려한다. 개인정보가 포함된 주문 데이터를 Temporal에 직접 전달하지 않고 Payload ID만 넘기고 실제 데이터는 내부 시스템에 유지하는 경계를 뒀다.

단순 스케줄까지 모두 Workflow Engine으로 옮기면 운영 복잡도가 오히려 커질 수 있다. 실패 복구와 실행 추적이 비즈니스적으로 중요한 흐름부터 제한적으로 도입하는 판단이 필요하다.

Jenkins crontab을 Temporal로 바꾸는 목적은 스케줄 문법이 아니라 **실행 이력을 추적하고 실패한 단계부터 재개하는 의미론**을 확보하는 것이다. Workflow는 순서를 기록하고 Activity가 외부 시스템을 호출하므로, Activity 재시도 시 동일 배치가 두 번 생성되지 않도록 업무별 멱등 키나 상태 검사를 설계해야 한다. 중요한 주문 정보는 내부 저장소에 두고 Payload ID만 넘기는 방식은 워크플로 엔진의 보관 데이터와 개인정보 처리 경계를 분리한다.

```mermaid
flowchart LR
  A["Workflow 시작"] --> B["정책 조회"]
  B --> C["중복 여부 검사"]
  C --> D["Wave/Batch 생성"]
  D --> E["외부 파이프라인 호출"]
  E --> F["실행 상태 기록·재시도"]
```

*자체 재구성. 각 Activity에서 멱등 처리가 별도로 필요하다.*

## 왜 읽을까

cron과 배치는 단순할 때 강력하지만, 재시도·부분 성공·중복 실행·장애 복구 요구가 늘어나면 애플리케이션 코드와 감시 스크립트가 상태 머신처럼 변한다. 이 글은 **언제 스케줄러 문제를 워크플로 문제로 다시 정의해야 하는지** 생각하게 한다.

또 워크플로 엔진을 도입해도 멱등성이나 데이터 경계 문제가 자동으로 해결되는 것은 아니라는 점을 같이 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 정기 작업 중 실패 시 수동 복구가 필요하거나 중복 실행이 위험한 작업을 먼저 구분한다.
- [ ] 각 작업을 재시도했을 때 동일 결과가 보장되는지 멱등성 조건을 문서화한다.
- [ ] 단순 cron으로 충분한 작업과 실행 상태를 영속화할 가치가 있는 업무 흐름을 분리한다.
