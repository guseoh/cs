# 토스뱅크가 패키지를 관리하는 방식 #2: 토스뱅크 패키지의 세 가지 기준

> [!abstract] 한 줄 정리
> 패키지의 안정성, 원본 구조 보존, 디버깅 편의성을 기준으로 제작자와 사용자의 책임을 분리한다.

> 토스 기술 블로그 · 2026-10-16

## 핵심 내용

토스뱅크의 패키지 기준은 코드가 어디서 실행될지 예측 가능해야 한다는 문제에서 출발한다. 패키지와 소비 애플리케이션이 별도의 TypeScript 변환·번들 환경을 가지고 있으면 작성 시점에 지원되던 문법이나 런타임 API가 실제 실행 환경에서는 지원되지 않을 수 있다.

팀은 안정성, 예측 가능성, 디버깅 편의성을 핵심 기준으로 정의하고, 패키지 빌드에서는 타입 제거에 필요한 TypeScript→JavaScript 변환만 수행하도록 경계를 정했다. 모듈의 import/export를 최대한 보존하면 실제 사용자 앱이 자신에게 적합한 타깃으로 트랜스파일·번들할 수 있다. 그러나 트랜스파일러 자체가 다루지 못하는 문법이나 호스트에 없는 런타임 API는 패키지가 일방적으로 해결할 수 없으므로 호스트 지원 범위와 문법 규칙을 맞춰야 한다.

```jsonc
// 설명을 위한 package.json의 모듈 경계 예시
{
  "type": "module",
  "exports": {".": {"types": "./dist/index.d.ts", "default": "./dist/index.js"}},
  "files": ["dist", "src"]
}
```

실제 패키지 설정은 TypeScript 및 소비 애플리케이션의 지원 조건에 맞게 조정해야 한다.

| 기준 | 라이브러리가 보장할 것 | 호스트가 확인할 것 |
| --- | --- | --- |
| 안정성 | 공개 API·타입 선언의 일치 | 지원 런타임과 API |
| 예측 가능성 | 의도치 않은 이중 구현 제거 | 최종 번들·트랜스파일 설정 |
| 디버깅 | 소스맵과 원본 접근 | 오류 위치 매핑과 개발자 도구 |

선언 파일과 declaration sourcemap, 원본 소스를 함께 제공하여 설치된 패키지에서 IDE가 정의를 찾아가고 문제 위치를 정확히 볼 수 있게 했다. 즉 배포 결과물의 JavaScript 용량뿐 아니라 소비자의 디버깅 경로가 패키지 설계의 일부다. 원문은 빌드 시간 개선을 수치로 제시하지 않으므로 변환 단계 감소가 곧바로 성능 향상이라고 단정해서는 안 된다.

## 왜 읽을까

패키지 빌드 방식을 고르기 전에 실행 환경과 원본 코드의 경계를 보존할 계약을 정하는 방법을 배울 수 있다.

**프로젝트에 적용 — 공통**

- [ ] 패키지의 타입 선언과 소스맵, 원본 소스 탐색이 가능한지 확인한다.
- [ ] 프런트엔드 빌드 대상의 문법·API 호환성을 별도로 확인한다.
