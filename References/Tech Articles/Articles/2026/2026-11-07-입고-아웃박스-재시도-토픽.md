# 컬리의 입고 시스템이 외부 인입 데이터를 안전하게 동기화하는 방법

> [!abstract] 한 줄 정리
> 외부 채널에서 입고 예정 정보를 수신할 때 DB 저장과 Kafka 발행은 단일 로컬 트랜잭션으로 원자성을 보장할 수 없다. 컬리는 아웃박스에 발행 의도를 함께 저장하고 비동기 발행·재시도 처리를 분리해 실패 복구 경로를 만들었다.

## 핵심 내용

컬리는 자체 발주 중심의 1P 모델에서 외부 파트너의 물류를 처리하는 3PL 모델로 확장하며 서로 다른 규격의 입고 예정 정보를 받게 됐다. 외부 채널이 직접 API를 호출하거나 컬리가 파트너 API를 주기적으로 조회하면, 수신 데이터는 인터페이스 테이블에 적재되고 Kafka 메시지를 거쳐 내부 입고 예정 정보로 변환된다. 그러나 메시지는 발행됐는데 DB 커밋이 실패하면 두 시스템의 상태가 달라진다. 또한 파트너나 상품의 기준 데이터가 아직 동기화되지 않았다면 컨슈머가 입고 정보를 생성하지 못한다.

발행 측에서는 인터페이스 데이터와 **아웃박스 레코드**를 하나의 DB 트랜잭션으로 저장한다. 이후 별도 폴러가 미발행 레코드를 읽어 Kafka로 보내고 성공 상태를 기록한다. 이는 DB와 Kafka를 하나의 분산 트랜잭션으로 묶는 것이 아니라, DB 내부의 원자적 기록을 바탕으로 발행을 재시도할 수 있게 하는 방식이다. 발행 성공 직후 상태 기록에 실패할 가능성은 남으므로 소비 측 멱등성까지 검토해야 한다.

직접 폴러와 상태 관리를 구현하는 대신 Namastack Outbox for Spring Boot를 채택해 폴링, 상태, 재시도 횟수와 인스턴스 관리를 위임했다. 원문은 `outbox_record`의 `status`, `retry_count`, `next_retry_at`, `aggregate_id` 등의 컬럼과 인덱스를 제시한다. 운영 DB 계정에 DDL 권한이 없어 테이블을 수동 생성한 점도 실제 도입 제약이다.

설정 예시에서는 2초 폴링, 최대 재시도 3회, 지수 백오프와 최대 60초 지연을 사용한다. 이 값은 원문의 구성 예시이지, 보편적인 권장 설정이나 처리량 검증 결과는 아니다. 특히 라이브러리 0.3.0을 기준으로 설명하며 0.4.x의 Spring Boot 호환 범위가 달라진다는 버전 제약을 명시한다.

아웃박스가 해결하는 것은 **발행 의도의 유실 방지**이지 소비자 측 선행 데이터 부족까지 자동으로 없애는 것은 아니다. 원문은 소비자가 파트너·상품 데이터 동기화 지연을 만나 실패할 수 있다는 별도 문제를 다루며 재시도 토픽을 사용해 일시적 실패를 재처리하는 방향을 설명한다. 재시도 가능 오류와 영구 오류를 구분하는 정책은 실제 서비스에 맞게 설계해야 한다.

## 왜 읽을까

트랜잭션 어노테이션이 붙은 메서드 안에서 메시지를 발행했다고 해서 외부 브로커까지 원자성이 확보되는 것은 아니다. DB 커밋 실패와 메시지 중복 발행, 기준 데이터 도착 순서의 차이를 각각 별도 실패 모드로 모델링하는 방법을 배울 수 있다.

**PawCycle 적용 제안(미검증):** 주문·재고 변경 이벤트를 대상으로 DB 커밋 직전 실패, Kafka 발행 후 상태 갱신 실패, 소비자 기준 데이터 누락을 주입하는 테스트를 설계할 수 있다. 다만 현재 시스템의 이벤트 처리 방식과 운영 비용을 먼저 확인한 후 아웃박스 도입 여부를 결정해야 한다.
