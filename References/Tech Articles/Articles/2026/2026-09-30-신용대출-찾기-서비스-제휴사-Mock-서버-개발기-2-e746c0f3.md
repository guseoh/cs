# 신용대출 찾기 서비스 제휴사 Mock 서버 개발기 #2

> [!abstract] 한 줄 정리
> 완전한 E2E 자동화를 당장 도입하기 어려운 상황에서 Docker 기반 Mock 서버와 통합 테스트를 CI에 넣고, 외부 제휴사 DTO 변경에 맞춘 테스트 데이터 갱신까지 자동화한 사례다. 이상적인 테스트보다 현재 조직이 지속해서 유지할 수 있는 검증 루프를 만드는 접근이 핵심이다.

> Toss Tech · 2025-08-27

## 핵심 내용

- **문제:** 제휴사 Mock 서버가 있어도 E2E가 자동화되지 않아 코드 변경 때마다 사람이 직접 검증해야 했고 테스트 누락 위험이 있었다.
- **접근:** Docker에서 Mock 서버를 띄우고 GitHub Actions에서 통합 테스트를 실행했다. 기존 Local/Alpha 환경을 희생하지 않기 위해 `mockServerTest` Multi Profile로 Docker용 인프라 값만 덮어썼다.
- **트레이드오프:** 퍼널 테스트마다 가심사를 반복하면 실행 시간이 N분씩 늘어나므로 테스트 독립성 원칙을 일부 포기했다. 가심사를 한 번 수행하고 원장 데이터를 재사용하며 JUnit Suite로 클래스 간 순서를 명시했다.
- **자동화:** 제휴사 DTO 변경을 감지하고 Kotlin Reflection과 JSON Schema로 명세를 추출해 샘플 데이터를 갱신한다. 기존 데이터 값을 우선 보존하면서 새 프로퍼티만 채우고 `init.sql`까지 생성한다.
- **결과:** feature→develop에서는 통합 테스트 실패를 PR 작성자에게 알리고, develop→master에서는 테스트 결과와 제휴사 코드 변경 여부를 배포 파이프라인에서 노출한다. 테스트 데이터 변경도 자동 PR로 연결했다.

## 왜 읽을까

테스트 피라미드의 이상론보다 외부 시스템 의존성이 큰 실제 서비스에서 어디까지 자동화할지를 보여준다. 테스트 코드뿐 아니라 환경 설정과 Mock 데이터 유지보수까지 자동화 대상이라는 점도 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 회원가입·로그인·세션 유지 같은 핵심 흐름을 Docker DB와 함께 CI 통합 테스트로 고정한다.
- [ ] 테스트용 profile이 운영 설정을 침범하지 않도록 override 범위를 명시한다.
- [ ] 테스트 fixture가 도메인 DTO 변경과 함께 깨지는 경우 스키마 검증이나 fixture 생성 자동화를 검토한다.
