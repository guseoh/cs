# 신용대출 찾기 서비스 제휴사 Mock 서버 개발기 #2

> [!abstract] 한 줄 정리
> 완전한 E2E 자동화를 당장 도입하기 어려운 상황에서 Docker 기반 Mock 서버와 통합 테스트를 CI에 넣고, 외부 제휴사 DTO 변경에 맞춘 테스트 데이터 갱신까지 자동화한 사례다. 이상적인 테스트보다 현재 조직이 지속해서 유지할 수 있는 검증 루프를 만드는 접근이 핵심이다.

> Toss Tech · 2025-08-27

## 핵심 내용

대출 비교 서비스는 금융기관마다 응답 형식과 조건이 달라 제휴사 Mock 서버 없이는 통합 테스트를 반복하기 어렵다. 하지만 Mock 서버 자체만 있어도 테스트를 실행하는 사람이 매번 외부 응답 케이스를 고르면 배포 안전성이 자동으로 확보되지 않는다.

토스의 테스트 환경은 Docker에서 Mock 제휴사를 띄우고 GitHub Actions에서 통합 시나리오를 실행한다. 기존 Local/Alpha 환경을 변경하지 않기 위해 `mockServerTest` Multi Profile로 해당 실행에서만 외부 연결과 설정값을 교체했다. 가심사를 매 테스트마다 반복하면 실행 시간이 너무 길어져 테스트 케이스의 독립성을 일부 포기하고 가심사 원장 데이터를 JUnit Suite가 뒤의 퍼널 테스트에서 재사용하도록 순서를 명시했다.

```yaml
# Spring Profile 전환 의도를 보여 주는 설정 예시
spring:
  config:
    activate:
      on-profile: mockServerTest
partner:
  base-url: http://partner-mock:8080
```

*실제 원문 설정 전체가 아닌 테스트 환경 분리의 개념 예시다.*

| 선택 | 이득 | 확인할 단점 |
| --- | --- | --- |
| Docker Mock | 외부 제휴사 장애와 분리 | 실제 응답 변화 추적 필요 |
| Profile 분리 | 기존 환경 안전 | 시험용 설정의 범위 관리 |
| 가심사 결과 재사용 | 퍼널 테스트 시간 단축 | 테스트 순서/데이터 오염 |
| DTO→JSON Schema 자동 생성 | 샘플 데이터 최신화 | 기존 값 보존·새 필드 의미 확인 |

제휴사 DTO가 변경되면 Kotlin Reflection과 JSON Schema로 새 데이터 필드를 추출해 기존 응답 예시의 값을 보존하면서 추가 필드만 채우고, `init.sql`까지 갱신하는 자동 PR을 생성한다. feature→develop과 develop→master의 검증 목적과 알림도 구분했다. 공유 상태를 쓰는 테스트는 빠르지만 순서 의존과 오염 위험을 만들므로 데이터 준비 실패가 어떤 테스트에 영향을 주는지 추적 가능해야 한다.

## 왜 읽을까

테스트 피라미드의 이상론보다 외부 시스템 의존성이 큰 실제 서비스에서 어디까지 자동화할지를 보여준다. 테스트 코드뿐 아니라 환경 설정과 Mock 데이터 유지보수까지 자동화 대상이라는 점도 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 회원가입·로그인·세션 유지 같은 핵심 흐름을 Docker DB와 함께 CI 통합 테스트로 고정한다.
- [ ] 테스트용 profile이 운영 설정을 침범하지 않도록 override 범위를 명시한다.
- [ ] 테스트 fixture가 도메인 DTO 변경과 함께 깨지는 경우 스키마 검증이나 fixture 생성 자동화를 검토한다.
