# 배송최적화 시스템 구축기 Part 02. 복잡한 비즈니스 로직에 유연한 디자인 패턴 입히기

> [!abstract] 한 줄 정리
> 출고 센터 선택 로직을 조건별 전략과 최종 결정 전략으로 나누고, 실행 순서·중단 조건·룰 활성화를 분리하면 정책 변경과 불필요한 외부 API 호출을 함께 제어할 수 있습니다.

> 올리브영 테크블로그 · 2026-09-04

## 한눈에 보기

출고 센터를 결정하는 로직은 단순히 거리 하나로 순위를 매기는 문제가 아니다. 권역, 재고, 센터 처리 용량과 배송 정책을 통과한 후보를 만든 뒤 그중 하나를 확정해야 한다. 올리브영은 이 두 책임을 나누고 실행 비용에 따라 전략 순서를 조정하여 복잡한 조건과 외부 API 비용을 함께 통제했다.

![올리브영 출고 센터 후보 선택과 최종 결정 플로우](https://oliveyoung.tech/_img/dd2fa8abd15890ec-1024.webp)

*그림 1. 센터 후보 평가 Selection과 최종 센터 확정 Decision을 분리한 원문 그림 — [출처: 원문 기술 블로그](https://oliveyoung.tech/2026-09-04/delivery-optimization-design-pattern/)*

Selection은 배정 가능한 후보의 집합을 좁히는 책임이고 Decision은 복수의 결과 중 최종 정책을 적용하는 책임이다. 후보가 없는 경우처럼 결과가 이미 결정된 때는 `shouldStop`으로 후속 비싼 API 호출을 중단한다. DB에 저장한 룰의 활성화 상태와 실행 우선순위는 코드 구조 외에도 운영 변경의 책임이 된다.

## 핵심 내용

### 문제와 제약

**문제:** 배송 권역·센터 CAPA·재고·택배사 등의 조건을 중첩 if 문으로 결합하면 정책이 추가될수록 테스트 조합과 변경 영향이 급증합니다.

### 선택한 구조와 구현

**구조:** 후보 센터를 평가하는 CenterSelectionStrategy와 최종 하나를 결정하는 DecisionStrategy를 분리하고 CompositeCenterSelectionStrategy로 여러 선택 전략을 조합했습니다.

**운영:** 전략의 활성화 여부를 DB에 보관해 배포 없이 특정 룰을 켜고 끌 수 있도록 했습니다. 다만 설정 변경 자체가 비즈니스 동작을 바꾸므로 변경 이력 관리가 필요합니다.

### 검증 결과와 남은 판단

**성능:** CAPA처럼 저렴한 내부 조회를 먼저 실행하고, 외부 재고 API처럼 비싼 연산은 뒤로 미뤘습니다. 결과에 shouldStop을 두어 이미 배정 불가 또는 확정된 경우 후속 호출을 중단합니다.

**주의점:** 전략 패턴의 기본형 하나로 복합 조건을 해결할 수 없어서 선택과 결정을 별도 책임으로 나눴습니다. 글에는 이 최적화의 정량적인 응답 시간 개선 수치는 제시되지 않습니다.

### 핵심 근거와 비교

| 선택 단계 | 확인 내용 | 실행 비용과 판단 |
| --- | --- | --- |
| 출고 가능 여부 | 센터 CAPA 등 내부 조건 | 내부 조회로 먼저 탈락 후보 제거 |
| 재고 확인 | 다른 시스템의 재고 API | 네트워크 I/O이므로 필요한 경우에만 호출 |
| 복합 조건 통합 | 각 선택 전략의 결과 | 중단 신호를 확인하며 후보 집합 생성 |
| 최종 결정 | 후보·우선 정책 | `DecisionStrategy`에서 단일 센터 확정 |

*원문은 조기 종료 전략의 정량적인 응답 시간 개선 수치를 공개하지 않는다.*

## 왜 읽을까

디자인 패턴을 단순한 if 제거 기법이 아니라 도메인 정책의 변경 단위, 운영 설정, 성능 비용에 연결해 볼 수 있습니다. 특히 후보 평가와 최종 의사결정을 분리하는 관점은 요구사항 분석 실습에 유용합니다.

**프로젝트에 적용 — PawCycle**

- [ ] 배송·재고·주문 상태 판별 로직을 조건 평가와 최종 결정 단계로 나눌 수 있는지 검토합니다.
- [ ] 저렴한 DB 검사와 비싼 외부 API 검사의 실행 순서를 정하고 조기 종료 조건을 테스트합니다.
- [ ] 운영 중 바꿀 수 있는 룰에는 변경 이력과 롤백 기준을 정의합니다.
