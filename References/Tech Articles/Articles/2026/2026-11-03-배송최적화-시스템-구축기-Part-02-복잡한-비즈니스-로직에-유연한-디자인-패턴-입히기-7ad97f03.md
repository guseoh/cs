# 배송최적화 시스템 구축기 Part 02. 복잡한 비즈니스 로직에 유연한 디자인 패턴 입히기

> [!abstract] 한 줄 정리
> 출고 센터 선택 로직을 조건별 전략과 최종 결정 전략으로 나누고, 실행 순서·중단 조건·룰 활성화를 분리하면 정책 변경과 불필요한 외부 API 호출을 함께 제어할 수 있습니다.

> 올리브영 테크블로그 · 2026-09-04

## 핵심 내용

배송 권역, 택배사, 센터 CAPA, 재고 같은 조건을 단일 중첩 if문으로 결합하면 정책 추가 때마다 분기와 테스트 조합이 증가한다. 올리브영은 가능한 센터를 추리는 Selection과 그중 최종 하나를 정하는 Decision을 별도 책임으로 분리했다.

![출고 센터 후보 선택과 최종 결정 원문 구조](https://oliveyoung.tech/_img/dd2fa8abd15890ec-1024.webp)

*그림 1. Selection과 Decision 책임을 분리한 출고 센터 결정 플로우 — [출처: 원문 기술 블로그](https://oliveyoung.tech/2026-09-04/delivery-optimization-design-pattern/)*

원문 Kotlin 구현에서는 `CenterSelectionStrategy`가 후보 결과를 반환하고 `DecisionStrategy`가 복수 선택 결과로 최종 결정을 내린다. `CompositeCenterSelectionStrategy`는 DB에서 활성화된 룰을 필터링하고 우선순위대로 실행한다. 값싼 내부 CAPA 검사 후 외부 재고 API 검사를 수행하며, 결과의 `shouldStop`이 참이면 불필요한 전략 실행을 중단한다.

```kotlin
// 원문 인터페이스의 핵심 계약을 축약해 재구성
interface CenterSelectionStrategy<T> {
    fun select(context: T): CenterSelectionResult
}
interface DecisionStrategy {
    fun decide(results: List<CenterSelectionResult>): CenterSelectionResult
}
```

여기서 선택 전략의 중간 반환값과 최종 센터 확정은 다른 계약이다.

| 선택 단계 | 확인 내용 | 실행 비용과 판단 |
| --- | --- | --- |
| 출고 가능 여부 | 센터 CAPA 등 내부 조건 | 내부 조회로 먼저 탈락 후보 제거 |
| 재고 확인 | 다른 시스템의 재고 API | 네트워크 I/O이므로 필요한 경우에만 호출 |
| 복합 조건 통합 | 각 선택 전략의 결과 | 중단 신호를 확인하며 후보 집합 생성 |
| 최종 결정 | 후보·우선 정책 | `DecisionStrategy`에서 단일 센터 확정 |

*원문은 조기 종료 전략의 정량적인 응답 시간 개선 수치를 공개하지 않는다.*

룰 On/Off를 배포 없이 바꿀 수 있어 운영 정책 변경에 유리하지만, DB 설정 변경 역시 실제 주문 분배에 영향을 미친다. 따라서 룰 변경 이력, 변경자, 복구 정책과 비활성화 시 기본 동작을 함께 설계해야 한다. 원문은 구조와 구현 코드를 공개하지만 정량적인 지연 감소율은 제시하지 않는다.

## 왜 읽을까

디자인 패턴을 단순한 if 제거 기법이 아니라 도메인 정책의 변경 단위, 운영 설정, 성능 비용에 연결해 볼 수 있습니다. 특히 후보 평가와 최종 의사결정을 분리하는 관점은 요구사항 분석 실습에 유용합니다.

**프로젝트에 적용 — PawCycle**

- [ ] 배송·재고·주문 상태 판별 로직을 조건 평가와 최종 결정 단계로 나눌 수 있는지 검토합니다.
- [ ] 저렴한 DB 검사와 비싼 외부 API 검사의 실행 순서를 정하고 조기 종료 조건을 테스트합니다.
- [ ] 운영 중 바꿀 수 있는 룰에는 변경 이력과 롤백 기준을 정의합니다.
