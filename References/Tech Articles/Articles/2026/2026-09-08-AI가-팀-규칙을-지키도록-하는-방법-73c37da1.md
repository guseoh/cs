# AI가 팀 규칙을 지키도록 하는 방법

> [!abstract] 한 줄 정리
> AI에게 팀 규칙을 한 번에 많이 주는 것보다, 코드를 작성한 직후 관련 규칙만 다시 주입하는 피드백 루프가 더 효과적이다. 규칙 역시 로그와 PR 리뷰를 통해 지속적으로 개선해야 한다.

> Toss Tech · 2026-09-08

## 핵심 내용

AI 코딩 에이전트의 `AGENTS.md`에 팀의 모든 규칙을 넣어도 긴 실행 과정에서는 앞부분 지침이 약해지고, 규칙이 많아질수록 작업에 필요 없는 내용이 컨텍스트를 차지한다. 토스의 Stylepack은 코드가 바뀌는 시점에 해당 규칙을 다시 보여주는 Hook 방식으로 이 문제를 풀었다.

 ```mermaid
flowchart LR
 A[파일 작성·변경] --> B[Hook 패턴 검사]
 B --> C[관련 규칙 최대 2개 주입]
 C --> D[에이전트 수정]
 D --> E[최종 git diff 검사·최대 4개]
 E --> F[PR 리뷰 근거·오탐 기록]
 F --> G[중앙 Stylepack 규칙 개선]
```

*원문 근거를 바탕으로 자체 재구성한 가로형 학습 도식이다.*

파일이 생성·수정되면 Hook이 파일명과 코드 패턴을 정규식으로 비교해 관련성 높은 규칙을 최대 두 개만 주입한다. 작업이 끝나기 직전에는 전체 `git diff`를 보고 최대 네 개 규칙을 다시 검사한다. 규칙은 저장소마다 복사하지 않고 중앙 저장소에서 세션 시작에 최신 버전을 가져온다. 관련성을 LLM으로 판정하는 방법은 호출당 약 10초가 추가되어 결정적인 정규식 후보 선별로 바뀌었다.

| 규칙 제공 방식 | 도입 효과 | 검증해야 할 위험 |
| --- | --- | --- |
| 모든 AGENTS.md 상시 주입 | 전체 맥락 제공 | 길이·주의력 희석 |
| 파일 수정 Hook | 최대 2개 관련 규칙 재주입 | 정규식 오탐/미탐 |
| 작업 종료 Hook | git diff 기준 최대 4개 | 검증 시점·코드 수정 반영 |
| LLM 규칙 검색 | 유연한 분류 | 약 10초 추가 지연 |
| Review→규칙 저장 | 반복 실패 방지 | 실제 코드 변화로 효과 측정 |

한 규칙은 21개 세션에서 발동했어도 실제 코드 변경이 0건으로 오탐임을 확인했고, 조건을 수정했다. N+1처럼 문법 패턴만으로 판단하기 어려운 항목은 Hook 규칙보다 상시 Context에 배치했다. 반복되는 PR 리뷰 코멘트를 신규 규칙 후보로 수집하는 피드백 루프도 두었지만, 규칙이 자동 선택됐다는 사실만으로 실제 코드의 설계 적합성이 검증되는 것은 아니다.

## 왜 읽을까

AI 코딩 규칙을 문서에 더 많이 적는 것이 정답이 아니라, **언제 어떤 규칙을 다시 보여줄 것인지**가 중요하다는 관점을 얻을 수 있다. 특히 규칙 시스템 자체의 오탐·미탐을 로그로 측정하고 개선한다는 점이 실무적이다.

**프로젝트에 적용 — DevPedia**

- [ ] Codex가 자주 놓치는 규칙을 전역 지침과 작업 직후 피드백 규칙으로 구분한다.
- [ ] 반복되는 PR 리뷰 지적을 모아 실제로 재발하는 항목만 프로젝트 규칙 후보로 승격한다.
- [ ] 규칙별 발동 횟수와 실제 수정 여부를 기록해 쓸모없는 규칙을 제거한다.
