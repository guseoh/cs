# nginx 설정 없이 우아하게 서비스 점검하기 (上)

> [!abstract] 한 줄 정리
> 운영 중 일부 기능만 안전하게 차단해야 할 때 공지나 인프라 수동 변경에 의존하지 않고, 애플리케이션이 직접 제어할 수 있는 점검 경계를 만들되 그 제어 시스템 자체의 의존성까지 제거해야 한다.

> 컬리 기술 블로그 · 2025-10-10

## 핵심 내용

재고 DB를 점검하던 중에도 센터 작업자가 물건 적치 API를 호출하면 입고 시스템의 비동기 후처리가 실패하고 보상 트랜잭션이 없기 때문에 사람이 재고를 보정해야 했다. nginx 라우팅을 바꾸는 권한이 없는 상황에서 공지만으로 작업을 막을 수 없다는 운영 문제를 해결하려고 애플리케이션의 AccessBlock 기능을 도입했다.

![원문의 access_block·access_block_group ERD: Path와 그룹 Toggle 기반 접근 차단](https://helloworld.kurly.com/_astro/access-block-erd.BgUJN6yT_ZuHlef.webp)

*그림 1. 원문의 access_block·access_block_group ERD: Path와 그룹 Toggle 기반 접근 차단 — [출처: 원문 기술 블로그](https://helloworld.kurly.com/blog/access-block-1/)*

처음에는 MySQL의 `access_block`에 페이지 Path를, `access_block_group`에 그룹과 Toggle 상태를 저장하고 프런트 라우팅마다 차단 여부 API를 호출했다. 필요할 때 그룹을 켜면 점검 안내 화면으로 전환한다. 이후 특정 클러스터만 차단할 요구가 생겨 조건이 확장됐다. 하지만 보호 대상인 RMS/MySQL 자체가 점검되면 차단 정보를 조회할 수 없어 안전장치가 같은 장애 영역에 묶이는 문제가 새로 나타났다.

| 설계 단계 | 장점 | 실패 위험 |
| --- | --- | --- |
| 작업 중지 공지 | 즉시 사용 가능 | 작업자가 공지를 놓침 |
| nginx 차단 | 네트워크 진입 차단 | 팀에 변경 권한 없음 |
| MySQL AccessBlock | 그룹/클러스터 단위 설정 | 점검 DB 장애 시 조회 실패 |
| Redis 캐시 | 차단 조회의 DB 의존 제거 | 새 메타데이터 등록은 RDB 의존 |

접근 차단 메타데이터를 Redis에 캐시하고 Toggle을 별도로 관리해 일반 조회 경로의 RDB 의존을 낮췄다. 다만 신규 차단 메타데이터를 등록하는 부분은 여전히 RDB에 의존해 완전히 독립된 설계는 아니었다. 매 화면 전환마다 API 호출이 하나 추가되는 비용은 감수하지만 운영 중 즉시 차단과 권한·토큰 만료 확인의 이득을 얻었다.

## 왜 읽을까

운영 기능을 추가할 때 정상 경로뿐 아니라 **그 운영 기능이 가장 필요한 장애 순간에도 동작하는가**를 묻게 한다. 단순 점검 페이지 구현기가 아니라 실패 도메인과 제어 평면을 어떻게 분리할지 생각하기 좋은 사례다.

**프로젝트에 적용 — PawCycle**

- [ ] DB 마이그레이션·점검 중 주문/구독처럼 쓰기 위험이 큰 기능만 선택적으로 막아야 하는 시나리오를 정의한다.
- [ ] 점검 제어 상태가 보호하려는 DB와 같은 장애 영역에 묶이지 않는지 확인한다.
- [ ] 공지나 수동 조작보다 시스템 차단과 복구 절차를 우선하고, 대표 API로 실제 차단 여부를 검증한다.
