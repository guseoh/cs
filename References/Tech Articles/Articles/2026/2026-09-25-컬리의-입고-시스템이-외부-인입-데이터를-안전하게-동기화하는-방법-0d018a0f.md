# 컬리의 입고 시스템이 외부 인입 데이터를 안전하게 동기화하는 방법

> [!abstract] 한 줄 정리
> DB 저장과 Kafka 발행 사이의 원자성 문제는 아웃박스 패턴으로 경계를 다시 잡고, 일시적으로 처리할 수 없는 메시지는 재시도 토픽으로 격리해 운영자 개입 없이 회복하도록 설계할 수 있다.

> 컬리 기술 블로그 · 2026-01-12

## 핵심 내용

- **문제:** DB 적재와 Kafka 발행을 한 흐름으로 처리해도 Kafka 발행 뒤 DB 커밋이 실패하면 메시지만 남을 수 있어 두 시스템 사이 원자성이 깨진다.
- **접근:** 비즈니스 데이터와 발행할 이벤트를 같은 DB 트랜잭션에서 아웃박스 테이블에 저장하고, 별도 Poller가 Kafka 발행을 담당하도록 분리했다.
- **주의점:** Kafka 발행 성공 뒤 아웃박스 완료 마킹 전에 인스턴스가 죽으면 같은 메시지가 재발행될 수 있으므로 Consumer의 멱등성은 별도로 보장해야 한다.
- **구조:** 아직 파트너·상품 정보가 준비되지 않은 일시적 실패는 메인 토픽을 막지 않도록 Retry Topic으로 보내고, 10분 간격으로 최대 24시간, 총 144회 재시도한 뒤 DLT로 보낸다.
- **트레이드오프:** 아웃박스와 재시도 토픽은 안정성을 높이는 대신 테이블·Poller·재시도 정책·DLT 운영 비용을 추가한다.

## 왜 읽을까

@Transactional 하나로 DB와 메시지 브로커까지 원자적으로 묶을 수 없다는 문제를 실제 실패 시나리오에서 출발해 설명한다. 패턴 이름보다 실패 경계, 중복 가능성, 재시도 데드라인을 먼저 보는 설계 관점을 얻기 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] 주문·구독 상태 변경과 이벤트 발행이 함께 필요한 경로가 있는지 찾는다.
- [ ] DB 커밋과 Kafka 발행의 성공·실패 조합별 장애 시나리오를 적는다.
- [ ] 재처리를 허용한다면 Consumer의 멱등성 키와 중복 처리 방식을 먼저 정의한다.
