# 컬리의 입고 시스템이 외부 인입 데이터를 안전하게 동기화하는 방법

> [!abstract] 한 줄 정리
> DB 저장과 Kafka 발행 사이의 원자성 문제는 아웃박스 패턴으로 경계를 다시 잡고, 일시적으로 처리할 수 없는 메시지는 재시도 토픽으로 격리해 운영자 개입 없이 회복하도록 설계할 수 있다.

> 컬리 기술 블로그 · 2026-01-12

## 핵심 내용

외부 파트너의 입고 예정 정보는 API 호출 또는 배치 조회로 들어오고, 시스템은 인터페이스 테이블을 적재한 뒤 Kafka 메시지를 발행해야 한다. 컬리는 DB 쓰기와 Kafka 발행을 한 트랜잭션처럼 묶었어도 Kafka에 먼저 성공한 다음 DB Commit이 실패하면 두 저장소 사이에 서로 다른 사실이 남는 원자성 문제가 존재한다는 점을 확인했다.

비즈니스 데이터와 Outbox 이벤트를 같은 DB 트랜잭션에 기록한 뒤 별도 Poller가 Kafka로 발행하도록 구조를 분리했다. Poller가 Kafka 발행 이후 Outbox 완료 기록 전에 중단될 수 있으므로 중복 전송을 전제로 소비자가 이벤트 식별자로 멱등 처리해야 한다. 또한 아직 파트너·상품 정보가 도착하지 않아 처리할 수 없는 이벤트는 메인 토픽을 막지 않고 Retry Topic으로 이동하도록 했다.

| 장애 구간 | 새 구조의 보호 수단 | 여전히 남는 책임 |
| --- | --- | --- |
| DB 커밋↔Kafka 발행 | Outbox 로컬 트랜잭션 | Poller 재시도·중복 발행 |
| 파트너/상품 지연 | Retry Topic | 정상화 뒤 순서·멱등성 |
| 일시적 오류 | 10분×144회(24시간) | 재시도 한도·관측 |
| 영구 오류 | DLT 격리 | 수동 수정·재처리 |

Retry는 10분 간격으로 최대 24시간, 총 144회 수행한 다음에도 해결되지 않으면 DLT에 분리한다. 이 방식은 메시지 유실을 막고 전파된 이벤트를 재처리할 길을 주지만, Outbox 테이블 정리·Poller 장애·Retry 백로그·DLT의 운영 책임을 추가한다. 일시적 데이터 미도착과 영구적인 스키마 오류를 구분해야 무의미한 재시도가 폭주하지 않는다.

## 왜 읽을까

@Transactional 하나로 DB와 메시지 브로커까지 원자적으로 묶을 수 없다는 문제를 실제 실패 시나리오에서 출발해 설명한다. 패턴 이름보다 실패 경계, 중복 가능성, 재시도 데드라인을 먼저 보는 설계 관점을 얻기 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] 주문·구독 상태 변경과 이벤트 발행이 함께 필요한 경로가 있는지 찾는다.
- [ ] DB 커밋과 Kafka 발행의 성공·실패 조합별 장애 시나리오를 적는다.
- [ ] 재처리를 허용한다면 Consumer의 멱등성 키와 중복 처리 방식을 먼저 정의한다.
