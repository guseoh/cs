# 딜리버리 암호화 모듈 개발기

> [!abstract] 한 줄 정리
> 암호화 모듈은 알고리즘 선택만의 문제가 아니라 JPA 생명주기, 키 관리, 저장 포맷, 의존성 호환성, 마이그레이션과 성능까지 함께 설계해야 하는 애플리케이션 인프라다.

> 컬리 기술 블로그 · 2025-06-02

## 핵심 내용

- **문제:** 엔티티 자동 암·복호화를 위해 `@PostLoad`를 쓰자 복호화로 값이 바뀌어 조회만 해도 dirty checking에 의해 UPDATE가 발생했다. Hibernate `PreLoad` 방식은 Spring Boot 3 전환 시 Hibernate 6 버그와 충돌했다.
- **접근:** 최종적으로 JPA `AttributeConverter`를 선택해 리플렉션 없이 타입별 변환을 지원하고, JPQL·QueryDSL projection에서도 복호화가 적용되도록 했다.
- **구조:** 키를 애플리케이션이 직접 장기 보관하지 않는 봉투 암호화를 적용하고, 헤더를 요구사항에 맞게 줄여 암호문 저장 크기를 약 10~30% 절감했다. Base64 대신 DB의 바이트 타입을 사용해 약 33%의 크기 증가와 인코딩 비용도 피했다.
- **테스트:** Property-based test로 무작위·경계 입력을 1,000회 검증하고, 실제 소비 애플리케이션의 Spring Boot dependency management가 모듈 의존성을 바꾸는 상황까지 별도 호환성 테스트로 확인했다.
- **수치:** M1 MacBook Pro 16GB, Xms256m·G1 GC 조건에서 약 300만 개 평문 처리에 암호화 5.58초, 복호화 5.36초가 걸렸으며 JVM warm-up 전 100회는 측정에서 제외했다.

## 왜 읽을까

JPA 기능 하나를 고르는 과정에서 dirty checking과 Hibernate 버전 호환성까지 실제로 부딪힌 기록이라 Java/Spring 백엔드 관점에서 특히 유용하다. 보안 모듈도 API 사용성, 성능, 저장 비용, 소비자 애플리케이션 호환성을 함께 검증해야 한다는 점을 잘 보여준다.

**프로젝트에 적용 — PawCycle**

- [ ] 개인정보 암호화가 필요해질 경우 DB 함수와 애플리케이션 암호화의 책임·키 관리 방식을 먼저 결정한다.
- [ ] JPA Converter를 적용한다면 entity 전체 조회뿐 아니라 projection, dirty checking, bulk 작업 경로도 테스트한다.
- [ ] 암호화 도입 전후 저장 크기와 처리량을 측정하고, Spring Boot/JDK 업그레이드 시 호환성 회귀 테스트를 유지한다.
