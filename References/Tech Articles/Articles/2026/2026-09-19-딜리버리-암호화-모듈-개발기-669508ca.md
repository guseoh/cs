# 딜리버리 암호화 모듈 개발기

> [!abstract] 한 줄 정리
> 암호화 모듈은 알고리즘 선택만의 문제가 아니라 JPA 생명주기, 키 관리, 저장 포맷, 의존성 호환성, 마이그레이션과 성능까지 함께 설계해야 하는 애플리케이션 인프라다.

> 컬리 기술 블로그 · 2025-06-02

## 핵심 내용

배송 데이터 암호화를 JPA 엔티티에서 자동화할 때 `@PostLoad`로 로드 뒤 값을 바꾸면 Hibernate Dirty Checking이 이를 실제 데이터 수정으로 인식해 조회만 해도 UPDATE할 수 있다. 컬리는 Spring Boot 3 전환 과정에서 Hibernate 6의 PreLoad 처리와도 충돌하면서 저장·조회 경계를 다시 검토했다.

최종적으로 `AttributeConverter`를 선택해 애플리케이션의 필드 타입과 DB 값 사이에서 암·복호화를 일관되게 적용하도록 했다. JPQL·Querydsl Projection 조회에도 변환이 적용되고 매 엔티티에 리스너·Transient 필드를 반복 작성할 필요가 줄었다. 키 관리에는 봉투 암호화를 적용해 애플리케이션이 장기 마스터 키를 직접 보유하지 않도록 설계하고, 암호문 헤더의 불필요한 바이트와 Base64 인코딩을 없애 바이너리 컬럼에 저장했다.

```java
// JPA AttributeConverter의 적용 지점을 보여 주는 축약 예시
@Converter
class EncryptedValueConverter implements AttributeConverter<String, byte[]> {
    public byte[] convertToDatabaseColumn(String value) { return encrypt(value); }
    public String convertToEntityAttribute(byte[] raw) { return decrypt(raw); }
}
```

*encrypt/decrypt는 실제 암호화 구현이 아닌 자리 표시자다. 암호모드는 인증된 암호화 방식과 키 회전을 고려해야 한다.*

| 방법 | 문제/효과 | 선택 결과 |
| --- | --- | --- |
| `@PostLoad` | 복호화 변경이 Dirty Checking에 잡힘 | 제외 |
| Hibernate PreLoad | Hibernate 6 호환 문제 | 제외 |
| `AttributeConverter` | 타입별 변환·Projection 처리 | 선택 |
| Base64 문자열 | 저장 크기 약 33% 증가 | 바이너리 저장 |
| 암호문 헤더 축약 | 10~30% 저장 절감 | 요구 범위 검토 후 적용 |

헤더를 줄여 암호문 저장 크기를 약 10~30% 절감했고 Base64의 약 33% 크기 증가도 회피했다. Property-based Test로 무작위·경계값을 1,000회 검증했으며, 약 300만 건의 변환에서 암호화 5.58초·복호화 5.36초(M1 MacBook Pro 16GB, Xms256m, G1GC, JVM 초기 100회 제외)를 관찰했다. 키 회전과 데이터 마이그레이션 등 장기 운영 경계는 별도 검증 대상이다.

## 왜 읽을까

JPA 기능 하나를 고르는 과정에서 dirty checking과 Hibernate 버전 호환성까지 실제로 부딪힌 기록이라 Java/Spring 백엔드 관점에서 특히 유용하다. 보안 모듈도 API 사용성, 성능, 저장 비용, 소비자 애플리케이션 호환성을 함께 검증해야 한다는 점을 잘 보여준다.

**프로젝트에 적용 — PawCycle**

- [ ] 개인정보 암호화가 필요해질 경우 DB 함수와 애플리케이션 암호화의 책임·키 관리 방식을 먼저 결정한다.
- [ ] JPA Converter를 적용한다면 entity 전체 조회뿐 아니라 projection, dirty checking, bulk 작업 경로도 테스트한다.
- [ ] 암호화 도입 전후 저장 크기와 처리량을 측정하고, Spring Boot/JDK 업그레이드 시 호환성 회귀 테스트를 유지한다.
