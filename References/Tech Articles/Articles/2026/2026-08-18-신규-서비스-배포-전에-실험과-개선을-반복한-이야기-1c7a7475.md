# 신규 서비스 배포 전에 실험과 개선을 반복한 이야기

> [!abstract] 한 줄 정리
> 성능 테스트는 마지막 확인 절차가 아니라 설계 오류와 DB 병목을 발견하는 개발 과정입니다. 컬리 VSMS는 데드락과 과도한 DB I/O를 반복 실험으로 찾아 120 TPS 수준에서 최종 1,500 TPS 이상까지 끌어올렸습니다.

> 컬리 기술 블로그 · 2020-09-07

## 핵심 내용

기존 운영 RPS와 향후 물류센터·서비스 성장분을 고려해 Peak 약 300 TPS의 4배인 1,200 TPS를 목표로 잡았습니다. 첫 정식 테스트에서 장바구니 상품의 잠금 순서가 요청마다 달라 `A→B`, `B→A` 형태의 교착 상태가 발생했고, commit 시 DB I/O가 커서 약 120 TPS에 머물렀습니다.

잠금 순서를 일관되게 만들고 여러 건의 DB 처리를 묶어 commit 횟수를 줄였습니다. 성능을 위해 임시로 가독성을 희생한 구현과 리팩터링 버전을 동일 조건에서 반복 비교한 뒤, 성능 차이가 근소함을 확인하고 유지보수 가능한 구조를 선택했습니다. 수량 변경 로그가 RDB 커넥션을 점유하는 것을 APM에서 확인하고, 로그 저장을 MongoDB로 분리해 핵심 재고 처리와 부가 기록의 자원 경쟁을 줄였습니다.

7시간 동안 3,685만 건을 처리하며 1,462 TPS, 이어 4시간 45분 동안 2,476만 건과 1,445 TPS를 기록했고 이후 1,500 TPS 이상을 유지했습니다.

데드락은 단순히 스레드를 더 늘린다고 해결되지 않는다. 같은 장바구니 상품 집합을 처리할 때 잠금 순서가 `A→B`와 `B→A`로 엇갈리면 서로가 가진 락을 기다릴 수 있으므로, 일관된 잠금 순서와 트랜잭션 범위를 먼저 정의해야 한다. 로그 기록을 별도 저장 경로로 분리한 것도 부가 작업이 핵심 재고 변경의 DB 커넥션을 차지하지 않게 하려는 자원 격리다.

| 검증 | 원문 결과 |
| --- | --- |
| 첫 주요 성능 측정 | 약 120 TPS |
| 장기 부하 시험 1 | 7시간, 3,685만 건, 1,462 TPS |
| 장기 부하 시험 2 | 4시간 45분, 2,476만 건, 1,445 TPS |

동작이 같을 때 성능 차이가 근소하면 유지보수 가능한 구현을 택했다는 판단도 코드 품질과 성능을 함께 평가한 좋은 사례다.

## 왜 읽을까

'인덱스 하나 추가' 같은 단일 최적화가 아니라 목표 수립 → 부하 테스트 → 데드락 재현 → DB I/O 축소 → 리팩터링 비교 → 장시간 검증의 전체 과정을 볼 수 있습니다. 특히 성능 때문에 유지보수성을 무조건 버리지 않고 실험으로 두 선택지의 차이를 확인한 과정이 좋습니다.

**프로젝트에 적용 — PawCycle**

- [ ] 실제 운영 지표나 합리적인 가정을 바탕으로 목표 TPS와 p95 기준을 먼저 정합니다.
- [ ] 재고·주문처럼 여러 행을 갱신하는 기능은 동시 요청에서 잠금 획득 순서가 일관적인지 테스트합니다.
- [ ] 부하 테스트 때 애플리케이션 TPS뿐 아니라 DB commit, connection pool, lock wait, I/O를 함께 봅니다.
