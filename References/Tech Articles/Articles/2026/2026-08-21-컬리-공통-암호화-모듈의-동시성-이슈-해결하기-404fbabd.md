# 컬리 공통 암호화 모듈의 동시성 이슈 해결하기

> [!abstract] 한 줄 정리
> 간헐적 오류는 입력값보다 공유 가변 상태를 의심해야 할 때가 있으며, 동시성 문제는 재현 가능한 멀티스레드 테스트로 가설을 검증해야 한다.

> 컬리 기술 블로그 · 2022-09-26

## 핵심 내용

- **문제:** AWS KMS Data Key를 Caffeine에 캐싱해 쓰는 공통 암호화 SDK에서 일부 요청만 `newPosition > limit` ByteBuffer 오류가 발생했다.
- **접근:** 동일한 키로도 오류가 간헐적으로 발생한다는 점에서 동시성 문제를 의심하고, 100개 고정 스레드가 동시에 암호화 로직을 호출하는 테스트로 `position`, `limit`, `length`를 관찰했다.
- **결과:** 정상적으로 0이어야 할 ByteBuffer의 position이 일부 스레드에서 32로 나타나 공유 Buffer가 thread-safe하지 않다는 사실을 재현했다.
- **트레이드오프:** `synchronized`로 직렬화할 수도 있지만 성능 비용이 생기므로, 각 스레드가 독립적인 상태를 갖도록 `duplicate()`를 사용해 문제를 해결했다.
- **주의점:** 공통 SDK나 캐시는 호출 측에서 불변처럼 보여도 내부 객체가 mutable하면 여러 요청이 같은 상태를 공유할 수 있다.

## 왜 읽을까

Java 동시성 문제를 ‘락을 배우는 글’이 아니라 **간헐적 운영 오류 → 코드 추적 → 가설 → 동시성 테스트 → 해결책 비교**의 흐름으로 볼 수 있다. 특히 라이브러리 객체의 thread-safety 계약을 확인하는 습관이 중요하다.

**프로젝트에 적용 — FutMatch**

- [ ] 여러 요청이 동시에 접근하는 공통 객체·캐시·버퍼가 mutable한지 점검한다.
- [ ] 동시성 버그는 단일 테스트가 아니라 여러 스레드로 반복 재현하는 테스트를 만든다.
- [ ] 무조건 synchronized를 붙이기 전에 상태 복제·불변화로 공유 자체를 없앨 수 있는지 검토한다.
