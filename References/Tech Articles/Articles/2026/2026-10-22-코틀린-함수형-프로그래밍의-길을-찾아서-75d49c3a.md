# 코틀린 함수형 프로그래밍의 길을 찾아서

> [!abstract] 한 줄 정리
> 함수형 프로그래밍을 거창한 추상화로 시작하기보다 불변성, 계산과 외부 의존성의 분리, 반복 패턴의 작은 추출부터 적용하면 변경과 테스트가 쉬워진다.

> 카카오페이 기술 블로그 · 스노우 · 2024-11-21

## 핵심 내용

- **문제:** 결제 요청 객체의 금액을 환율 변환·할인·분할 결제 과정에서 계속 변경하면 이전 단계의 상태가 다음 계산에 영향을 미친다. - **사례:** 글의 예시에서는 21,000원 결제에 할인을 중복 적용해 MONEY 10,000원과 POINT 9,000원을 결제한다. 원래 의도는 전체 할인 한 번이었다. - **접근:** 요청 필드를 불변으로 바꾸고 환율은 초기에 한 번 가져온다. 금액별 계산 결과를 KrwPayParams로 분리해 실제 결제 실행과 구분한다.

- **확장:** 예외 처리, 재시도, 배치 같은 반복 패턴은 고차함수로 추출하는 방식을 소개하고 Kotlin Arrow 등의 적용 방향을 검토한다. - **주의점:** 외부 시스템 의존을 모두 제거할 수는 없으며 재시도는 멱등성과 실패 조건을 고려해 사용해야 한다.

결제 금액 계산은 원본 요청 객체를 단계마다 수정하면 순서에 따라 결과가 바뀌기 쉽다. 할인은 한 번만 적용되어야 하는데 환율·분할 결제 로직이 같은 Mutable 상태를 공유하면 중복 적용을 발견하기 어렵다. 원문이 계산 결과를 `KrwPayParams`처럼 별도 값으로 만드는 이유는 계산을 재실행·테스트하기 쉬운 함수 경계로 분리하기 위해서다.

```kotlin
// 개념 설명용 재구성: 입력을 수정하지 않고 계산 결과를 반환
data class PaymentInput(val amountKrw: Long, val discountKrw: Long)
fun payableAmount(input: PaymentInput): Long =
    (input.amountKrw - input.discountKrw).coerceAtLeast(0)
```

불변 입력과 순수 계산만으로 결제의 외부 부작용까지 제거되는 것은 아니다. 환율 조회나 결제 승인 같은 I/O는 바깥 계층으로 분리하고 결과를 입력값으로 전달해야 테스트에서 같은 계산을 재현할 수 있다. 재시도 또한 네트워크 호출이 중복 승인으로 이어지지 않도록 업무 멱등 키를 별도로 설계해야 한다.

## 왜 읽을까

불변성과 순수 함수가 단순한 코드 취향이 아니라 할인 중복 적용 같은 비즈니스 오류를 예방하고 테스트 범위를 줄이는 설계 수단임을 알 수 있다. Kotlin 예제지만 Java에도 적용할 수 있는 원칙이다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집 지원 상태 변경 과정에서 입력 DTO를 계산용으로 변형하지 않는지 확인한다.
- [ ] 상태 전이 판단 규칙을 외부 조회와 분리해 독립적으로 테스트한다.
- [ ] 재시도 추상화 도입 전 중복 처리와 부작용을 검토한다.
