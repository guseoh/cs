# 대AI시대에 일하는 방식의 변화에 대한 고찰

> [!abstract] 한 줄 정리
> 에이전트를 여러 개 실행해도 사람이 검토하고 승인할 수 있는 양은 무한하지 않다. 병렬화의 목표를 창 수가 아닌 판단 가능한 작업 수와 검증 품질에 맞춰야 한다.

> 무신사 기술 블로그 · Sangho Lee · 2026-10-26

## 핵심 내용

- **문제:** git worktree와 tmux로 에이전트의 코드·조사·문서 작업을 병렬화했지만, 네 번째 판단 대기 작업부터 지시 망각·세션 혼동·검토 누락이 나타났다.
- **구조:** 작업별 worktree와 에이전트 세션을 분리하고, 구현 후 테스트·자동 코드 리뷰는 백그라운드에서 수행한다. 사람은 결과를 읽고 승인하는 역할을 맡는다.
- **접근:** 판단이 필요한 코드 작업을 동시에 3개까지만 두고 추가 작업은 대기열로 넘긴다. 반복 규칙과 설계 결정은 지침 문서·메모리 파일에 외부화한다.
- **트레이드오프:** 자동 검증으로 검토 대상을 줄이되 핵심 변경의 최종 승인과 설명 책임은 사람이 유지한다. 개인의 리뷰 병목을 해소해도 팀 동료의 리뷰 대기열로 전가될 수 있다.
- **주의점:** '3개'는 작성자의 체감상 한계이지 측정으로 입증한 보편적인 최적 동시성 값은 아니다.

## 왜 읽을까

에이전트 병렬화에서 코드 생산량이 아니라 검토 가능한 변경량을 병목으로 보는 관점을 얻을 수 있다. 여러 세션을 열어두는 것과 동시에 판단을 요구하는 작업을 늘리는 것을 구분하는 데 유용하다.

**프로젝트에 적용 — 공통**

- [ ] Codex 병렬 작업마다 worktree·목표·검증 조건·변경 범위를 분리한다.
- [ ] 동시에 리뷰/승인을 요구하는 작업 수를 제한하고, 새 작업은 큐로 관리한다.
- [ ] 테스트와 정적 분석은 자동화하되 중요한 도메인·DB·보안 변경은 직접 diff를 검토한다.
- [ ] 작업 종료 시 결정 근거와 재개 지점을 문서에 기록한다.
