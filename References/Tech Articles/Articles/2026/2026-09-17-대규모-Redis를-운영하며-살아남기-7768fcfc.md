# 대규모 Redis를 운영하며 살아남기

> [!abstract] 한 줄 정리
> Redis를 단순한 빠른 캐시로 보는 대신 대규모 운영에서 HA와 리소스 효율, 장애 위험을 함께 관리해야 하는 데이터 시스템으로 바라보게 하는 운영 사례다.

> LY Corporation Tech Blog

## 핵심 내용

서비스마다 Redis를 늘려 온 조직은 한산한 인스턴스에서도 고정된 메모리 자원을 할당하기 때문에 비용과 노드 운영 부담이 함께 증가한다. LY의 대규모 Redis 운영팀은 인스턴스를 무조건 키우는 대신 서비스별 사용량·고가용성·장애 전환 요구를 함께 관찰했다.

Low Usage Project는 메모리와 CPU, 네트워크·명령량이 낮은 Redis 인스턴스를 찾아 리소스를 회수하거나 더 작은 사양으로 조정하는 과정이다. 그러나 평균 메모리만 낮다고 줄이면 큰 키·복제 재동기화·일시적인 피크, 장애 전환 후 단일 노드 처리량을 감당하지 못할 수 있다. 캐시와 영속성 요구가 다른 Redis 사용 사례도 함께 구분해야 한다.

| 점검 요소 | 줄일 수 있는 비용 | 축소 시 위험 |
| --- | --- | --- |
| 평균 메모리/CPU | 과잉 할당 | 피크·리밸런스 |
| 복제본/HA | 무조건 중복된 용량 | Failover 여유 부족 |
| 연결 수/명령 패턴 | 유휴 커넥션·Hot Key | 단일 노드 집중 |
| 워크로드 | 캐시·세션·데이터 저장 | 일관성/내구성 차이 |

운영팀은 Redis 자체 지원과 클라이언트별 접속·Failover 정책도 일관되게 제공하는 책임을 가진다. 비용 절감은 사용률 낮은 인스턴스를 찾아내는 것에서 시작하지만 리사이즈 후 p99, 연결 오류, 복제 지연과 장애 전환 시간을 확인하는 절차까지 포함해야 최종 성공이다. 원문에 인스턴스당 보편적인 비용 절감률은 제시되지 않는다.

## 왜 읽을까

Redis 도입 이유를 `빠르니까`로 끝내지 않고, 규모가 커진 뒤 어떤 운영 책임이 생기는지 생각하게 한다. 캐시나 분산 락처럼 작은 기능으로 시작한 Redis도 결국 별도의 상태 저장 시스템이라는 점을 기억하기 좋은 글이다.

**프로젝트에 적용 — FutMatch**

- [ ] 매칭 상태나 조회 캐시 때문에 Redis가 필요해질 때 먼저 DB만으로 충족하지 못하는 latency·동시성 요구를 측정한다.
- [ ] 도입 시 key 수, 메모리 사용량, TTL/eviction, 장애 시 fallback 동작을 함께 관측한다.
- [ ] 캐시 hit rate가 낮거나 사용량이 작은 데이터는 Redis에 계속 유지할 가치가 있는지 주기적으로 검토한다.
