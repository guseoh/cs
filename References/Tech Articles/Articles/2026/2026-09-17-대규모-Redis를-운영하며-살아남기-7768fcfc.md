# 대규모 Redis를 운영하며 살아남기

> [!abstract] 한 줄 정리
> Redis를 단순한 빠른 캐시로 보는 대신 대규모 운영에서 HA와 리소스 효율, 장애 위험을 함께 관리해야 하는 데이터 시스템으로 바라보게 하는 운영 사례다.

> LY Corporation Tech Blog

## 핵심 내용

- **문제:** LINE 관련 서비스의 Redis 사용 규모가 계속 커지면서 단순 증설만으로는 클라우드 자원 비용과 운영 부담을 감당하기 어려워졌다.
- **구조:** 팀은 서비스 Redis에 대한 기술 지원과 HA 구성을 함께 담당하며, Redis 자체뿐 아니라 장애 전환과 운영 정책을 하나의 시스템으로 관리한다.
- **접근:** 사용량이 낮은 인스턴스를 찾아 리소스를 회수·재배치하는 Low Usage Project를 진행해 무조건적인 증설 대신 실제 사용 패턴을 기준으로 용량을 최적화했다.
- **주의점:** Redis는 메모리 기반이라 빠르지만 메모리 여유, 복제·장애 전환, 데이터 크기와 사용 패턴이 함께 맞지 않으면 비용과 장애 위험이 빠르게 커진다.

## 왜 읽을까

Redis 도입 이유를 `빠르니까`로 끝내지 않고, 규모가 커진 뒤 어떤 운영 책임이 생기는지 생각하게 한다. 캐시나 분산 락처럼 작은 기능으로 시작한 Redis도 결국 별도의 상태 저장 시스템이라는 점을 기억하기 좋은 글이다.

**프로젝트에 적용 — FutMatch**

- [ ] 매칭 상태나 조회 캐시 때문에 Redis가 필요해질 때 먼저 DB만으로 충족하지 못하는 latency·동시성 요구를 측정한다.
- [ ] 도입 시 key 수, 메모리 사용량, TTL/eviction, 장애 시 fallback 동작을 함께 관측한다.
- [ ] 캐시 hit rate가 낮거나 사용량이 작은 데이터는 Redis에 계속 유지할 가치가 있는지 주기적으로 검토한다.
