# 뱅크샐러드가 게임을 만들 때 데이터 정합성을 유지하는 법 (feat. 낙관적 락)

> [!abstract] 한 줄 정리
> 낙관적 락의 적합성은 단순한 충돌 빈도뿐 아니라 실패한 작업을 비즈니스적으로 복구할 수 있는지에 달려 있다. 이 사례는 버전 비교로 갱신 손실을 막고 시간 차분 보상 모델로 즉시 재시도 필요성을 낮췄다.

> 뱅크샐러드 기술 블로그 · 2026-01-16

## 핵심 내용

일해라 김뱅샐의 SAL은 현금으로 전환할 수 있으므로 게임 재화여도 금융 잔액과 같은 정합성 요구를 가진다. 예를 들어 보상 +200과 운영자 지급 +500이 모두 잔액 1,000을 읽은 뒤 독립적으로 저장하면 최종 1,500만 남아 정상 잔액 1,700에 비해 200이 사라질 수 있다. 이것은 같은 레코드에 대한 동시 수정에서 발생하는 Lost Update 문제다.

서비스는 캐릭터의 정적 정보와 자주 바뀌는 `character_state`를 분리하고, `update_version`을 조건으로 하는 CAS(Compare-And-Set) 업데이트를 적용했다. `WHERE character_id = ? AND update_version = ?` 조건이 맞는 행만 잔액과 버전을 함께 바꾸며 영향 행이 0이면 다른 요청이 먼저 수정했다는 뜻으로 판단한다. 비관적 락의 대기와 Redis 기반 분산 락의 운영 부담보다 사용자 단위 데이터 충돌 가능성이 낮다고 평가한 선택이다.

```sql
-- 낙관적 락의 핵심 SQL을 단순화한 학습 예시
UPDATE character_state
SET sal = :newBalance,
    update_version = update_version + 1
WHERE character_id = :characterId
  AND update_version = :expectedVersion;
-- 영향 행 0건이면 충돌: 현재 상태를 다시 조회해 판단
```

원문의 JPA/실제 테이블 구조를 그대로 옮긴 코드는 아니며 SQL 수준의 원자적 조건 갱신을 설명한다.

| 요청 | 서로 같은 최초 잔액 | 버전 검사 없이 저장 | CAS 적용 |
| --- | ---: | --- | --- |
| 사용자 보상 +200 | 1,000 | 1,200 저장 | 선행 요청 성공 시 버전 +1 |
| 운영자 지급 +500 | 1,000 | 1,500 덮어씀 | 이전 버전 조건이 불일치해 감지 |
| 최종 잔액 | — | 1,500(200 유실) | 최신 상태 재계산 시 1,700 |

이 서비스의 시간 경과 보상은 `(현재 시각 - 마지막 정산 시각) × 초당 보상률`로 계산하므로 특정 정산 시도가 CAS 충돌로 실패해도 다음 성공에서 경과 시간이 포함될 수 있다. **따라서 재시도를 생략할 수 있다는 결론은 이 시간 기반 누적 정산에만 적용**되며 선착순 보상이나 계좌 이체에 그대로 사용할 수 없다. 원문은 운영 중 정합성 이슈 0건을 보고했고, 복제 지연으로 오래된 버전을 읽는 문제를 피하려면 중요 경로를 Primary에서 조회하도록 강조한다.

## 왜 읽을까

락 방식은 프레임워크 설정만으로 결정되지 않는다. '충돌하면 무엇을 잃는가', '사용자 경험상 실패를 어떻게 처리하는가', '실패한 보상을 나중에 복원할 수 있는가'를 먼저 정의해야 함을 보여준다. 특히 **재시도 없는 낙관적 락**이 성립하는 특수한 도메인 조건을 구별해 읽을 가치가 있다.

**프로젝트에 적용 — FutMatch**

- [ ] 동일 경기의 마지막 참가 자리를 여러 사용자가 동시에 신청하는 시나리오를 정의한다.
- [ ] 정원 초과·중복 참가·갱신 손실을 동시 요청 테스트로 재현하고 현재 트랜잭션 경계를 확인한다.
- [ ] 참가 확정은 시간 경과로 자동 복구되지 않으므로 이 글의 '재시도 불필요' 결론을 복사하지 않고 낙관적/비관적 락과 충돌 응답을 비교한다.
