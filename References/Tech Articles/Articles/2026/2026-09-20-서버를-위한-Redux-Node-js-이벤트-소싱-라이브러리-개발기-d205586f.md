# 서버를 위한 Redux: Node.js 이벤트 소싱 라이브러리 개발기

> [!abstract] 한 줄 정리
> 승인·감사·롤백처럼 상태가 변한 이유 자체가 중요한 도메인에서는 현재 상태만 저장하는 CRUD보다 변경 이벤트를 원본으로 남기는 이벤트 소싱이 문제를 더 자연스럽게 표현할 수 있다.

> 당근 기술 블로그 · 2026-01-23

## 핵심 내용

- **문제:** 내부 도구에 승인·수정 기록·롤백·알림 요구가 붙으면서 status 컬럼과 히스토리 테이블을 계속 추가하는 CRUD 구조가 복잡해졌고, 현재 상태만으로는 왜 그 상태가 되었는지 추적하기 어려웠다.
- **접근:** 현재 상태 대신 상태를 바꾼 이벤트를 영구 저장하고, Reducer가 이벤트를 순서대로 적용해 현재 상태를 재구성하는 이벤트 소싱을 도입했다. 프론트엔드의 Redux와 유사한 모델로 설명해 팀 간 학습 비용도 낮췄다.
- **구조:** TypeScript 기반 Ventyd를 만들어 Schema·Reducer·Entity·Repository·Adapter를 분리했다. 저장소와 검증 라이브러리를 어댑터로 교체할 수 있고 이벤트 로그를 기반으로 감사·롤백·CQRS 같은 요구를 확장할 수 있다.
- **결과:** 게임 상태 사례에서는 클라이언트가 동일 도메인 로직으로 즉시 상태를 계산하고 서버가 이벤트를 재생해 검증할 수 있어 낙관적 업데이트·오프라인 동작·리플레이·부정행위 검증 같은 요구를 한 모델로 다룰 수 있었다.
- **트레이드오프:** 이벤트 소싱은 단순 CRUD의 기본 대체재가 아니다. 현재 상태만 필요한 도메인에는 과한 복잡성이며, 이벤트 순서·재생·읽기 모델과 저장 어댑터를 별도로 운영해야 하는 비용을 수반한다.

## 왜 읽을까

이벤트 소싱을 추상적인 아키텍처 패턴이 아니라 ‘왜 현재 상태만 저장하면 부족해지는가’에서 출발해 설명한다. CQRS나 이벤트 기반 시스템을 기술 스택으로 먼저 도입하기 전에 어떤 도메인 요구가 실제로 이 복잡성을 정당화하는지 판단하는 기준으로 읽기 좋다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기·매칭 상태에서 단순 현재값보다 변경 이력 자체가 비즈니스 의미를 갖는 상태를 먼저 식별한다.
- [ ] 감사·롤백·재현 요구가 실제로 생기기 전에는 일반 CRUD를 유지한다.
- [ ] 이벤트 소싱이 필요해지면 상태 변경 규칙을 순수 함수에 가깝게 분리해 이벤트 재생 테스트가 가능하도록 설계한다.
