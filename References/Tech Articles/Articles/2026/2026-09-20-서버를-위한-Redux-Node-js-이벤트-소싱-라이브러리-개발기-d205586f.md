# 서버를 위한 Redux: Node.js 이벤트 소싱 라이브러리 개발기

> [!abstract] 한 줄 정리
> 승인·감사·롤백처럼 상태가 변한 이유 자체가 중요한 도메인에서는 현재 상태만 저장하는 CRUD보다 변경 이벤트를 원본으로 남기는 이벤트 소싱이 문제를 더 자연스럽게 표현할 수 있다.

> 당근 기술 블로그 · 2026-01-23

## 핵심 내용

기록·승인·롤백이 중요한 내부 도구에서 현재 상태와 히스토리 컬럼을 계속 추가하면 왜 그 상태가 되었는지 재현하기 어려워진다. 당근은 상태 전이의 사건 자체를 저장하고 Reducer로 현재 상태를 계산하는 이벤트 소싱을 Node.js/TypeScript에서 사용할 수 있도록 Ventyd를 개발했다.

각 Command가 검증된 이벤트를 만들면 이벤트 저장소에 순서대로 기록하고, 읽을 때 Schema·Reducer가 이벤트를 접어 현재 상태를 계산한다. Entity·Repository·Adapter를 분리해 저장소와 검증 라이브러리를 교체할 수 있고, 동일 이벤트 목록을 Client와 Server가 재생하면 같은 상태를 계산할 수 있다. 이 원리는 낙관적 UI 업데이트, 오프라인 리플레이, 부정행위 검증에도 적용 가능하다.

```ts
// Reducer의 상태 재생 원리를 설명하는 예시
function reduce(balance: number, event: {type:string; amount:number}) {
  return event.type === 'credited' ? balance + event.amount : balance;
}
const current = events.reduce(reduce, 0);
```

동일한 이벤트 순서가 유지되어야 재생 결과가 결정적이다.

| 데이터 설계 | 일반 CRUD | 이벤트 소싱 |
| --- | --- | --- |
| 저장 내용 | 현재 상태 | 상태를 바꾼 이벤트 |
| 과거 상태 | 별도 이력 구현 | 이벤트 리플레이 |
| 읽기 성능 | 현재 row 조회 | 프로젝션·스냅샷 가능 |
| 운영 복잡성 | 상대적으로 단순 | 순서·버전·재생·스키마 진화 |

다만 이벤트가 누락·재배열되면 상태를 잘못 복원하므로 이벤트 ID와 버전, 순서, 스냅샷, 읽기 모델의 재구축 정책이 필요하다. 단순한 CRUD에는 이 모든 운영 비용이 과할 수 있으므로 감사·과거 재현·도메인 상태 변경이 실제 요구사항인지 확인한 후 채택하는 것이 맞다.

## 왜 읽을까

이벤트 소싱을 추상적인 아키텍처 패턴이 아니라 ‘왜 현재 상태만 저장하면 부족해지는가’에서 출발해 설명한다. CQRS나 이벤트 기반 시스템을 기술 스택으로 먼저 도입하기 전에 어떤 도메인 요구가 실제로 이 복잡성을 정당화하는지 판단하는 기준으로 읽기 좋다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기·매칭 상태에서 단순 현재값보다 변경 이력 자체가 비즈니스 의미를 갖는 상태를 먼저 식별한다.
- [ ] 감사·롤백·재현 요구가 실제로 생기기 전에는 일반 CRUD를 유지한다.
- [ ] 이벤트 소싱이 필요해지면 상태 변경 규칙을 순수 함수에 가깝게 분리해 이벤트 재생 테스트가 가능하도록 설계한다.
