# BFF 서버에 SSE를 도입한 이유: 전시 서버의 통신 구조 재설계

> [!abstract] 한 줄 정리
> BFF로 클라이언트 복잡도를 줄이면 응답 결합과 가장 느린 의존성에 묶이는 새 병목이 생길 수 있어 스트리밍 같은 다음 설계가 필요할 수 있습니다.

> techblog.woowahan.com

## 핵심 내용

가게목록 화면이 성장하며 클라이언트가 여러 서버를 직접 호출하는 구조를 `1지면 1API` BFF로 통합합니다. 그러나 모든 데이터를 하나의 JSON으로 합치면 응답이 커지고 가장 느린 서버에 전체가 묶이는 문제가 예상돼 완료된 데이터부터 보내는 SSE를 선택했습니다. nginx `proxy_buffering`은 인터넷 조언대로 끄지 않고 Spring Boot MVC·Kotlin·가상 스레드·SseEmitter 환경에서 직접 이벤트 도착 시간을 측정해 ON/OFF 자체에는 의미 있는 차이가 없고 gzip 등 다른 조건이 실제 원인일 수 있음을 확인했습니다.

BFF는 클라이언트가 여러 내부 서버를 이해해야 하는 복잡도를 줄이지만, 모든 구좌의 JSON을 한 번에 반환하면 전체 응답이 가장 느린 구좌에 묶인다. 원문에서는 가게목록 약 280KB와 여러 큐레이션을 합친 한 지면이 약 1.7MB까지 커질 수 있음을 문제로 봤다. 요청은 한 번만 보내되 구좌가 완료되는 순서로 SSE 이벤트를 전달하면 첫 화면 요소를 기다리는 시간을 줄일 수 있다.

```text
# 원문의 SSE 페이로드 예시 일부
event: DISPLAY_GROUP
data: {"sections": ["SUBCATEGORY", "CURATION", "SHOP_LIST"]}

event: SUBCATEGORY
data: {"items": [...]}

event: DONE
```

| 대안 | 검토한 판단 |
| --- | --- |
| 단일 REST 응답 | 마지막 구좌가 끝날 때까지 화면 대기 |
| ResponseBodyEmitter | 일회성 전송에 가볍지만 메시지 경계 직접 구현 |
| WebSocket | 이 조회 흐름에 필요 없는 양방향 복잡도 |
| SSE | 표준 이벤트 형식과 순차 렌더링 때문에 채택 |

원문에서 빠른 서브카테고리는 약 15ms에 먼저 도착하고 무거운 가게목록은 약 300ms 걸리는 사례로 설명한다. `proxy_buffering` ON/OFF 자체를 원인으로 단정하지 않고 gzip 등 측정 조건을 재검토한 점도 설정 최적화보다 실측을 우선한 판단이다.
