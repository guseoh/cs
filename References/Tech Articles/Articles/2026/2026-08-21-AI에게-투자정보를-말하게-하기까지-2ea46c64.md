# AI에게 투자정보를 말하게 하기까지

> [!abstract] 한 줄 정리
> 고객에게 바로 노출되는 AI 서비스에서는 모델의 생성 능력보다 근거 선별, 실행 경로 통제, 평가 가능한 출력 구조가 더 중요하다.

> Toss Tech · 2026-08-13

## 핵심 내용

투자 정보는 적시성·정확성·추적 가능성이 중요하고 시장 분포도 계속 바뀌므로, 자율형 에이전트의 오류가 검색→판단→생성 단계로 전파되기 쉽다. 원천 데이터는 입수 시점에 BERT 기반 분류와 엔티티·임베딩 메타데이터를 붙이고, 검색 단계에서는 넓게 후보를 가져온 뒤 중복 제거·리랭킹·실패 사유 필터링으로 좁힌다.

응답 요건이 명확한 작업은 자율형 ReAct보다 `검색 → 관련성 판단 → 중복 제거 → 근거 구성 → 생성` 절차형 그래프로 고정해 각 단계를 디버깅·평가 지점으로 만들었다. 자연어 답변만 남기지 않고 이벤트 유형·실패 유형 같은 구조화 필드를 함께 생성해 정밀도·재현율·F1 등으로 개선 여부를 측정한다.

운영 실패 사례를 임베딩해 유사한 positive/negative few-shot으로 재사용하자 재현율을 유지하면서 정확도와 정밀도가 크게 개선됐다.

금융 정보 검색은 사실이 맞아도 시점이나 종목이 다르면 위험한 응답이 될 수 있다. 데이터 입수 시점에 엔티티·이벤트 유형 같은 구조화 메타데이터를 부여해 검색 후보를 구성한 뒤, 리랭킹과 중복 제거를 통해 응답에 쓸 근거를 좁히는 흐름이 중요한 이유다. 자유형 ReAct보다 단계가 고정된 그래프를 사용하면 어느 검색·판단 단계에서 오분류가 일어났는지 재현하기 쉽다.

| 품질 단계 | 별도 검증 |
| --- | --- |
| 검색·후보 선별 | Recall·관련성 |
| 이벤트 분류 | Precision·Recall·F1 |
| 최종 설명 | 출처·시점·사실 일치 |

운영 실패 사례를 few-shot으로 재사용할 때도 성공·실패의 판정 기준을 구조화해야 같은 오류를 다시 학습에 섞지 않는다.

## 왜 읽을까

AI 기능을 붙일 때 ‘더 좋은 모델’보다 먼저 **자율성을 어디까지 허용할지, 실패를 어떻게 재현하고 평가할지** 설계해야 한다는 관점을 얻을 수 있다. 특히 운영에서 나온 실패 사례를 다음 평가셋과 프롬프트 개선으로 연결하는 피드백 루프가 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 절차가 명확한 작업은 자유형 에이전트보다 단계가 고정된 워크플로부터 시작한다.
- [ ] 운영 실패 사례를 회귀 평가 데이터로 재사용하는 구조를 만든다.
