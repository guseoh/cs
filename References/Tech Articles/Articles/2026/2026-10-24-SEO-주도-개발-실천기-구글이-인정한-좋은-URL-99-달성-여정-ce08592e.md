# SEO 주도 개발 실천기: 구글이 인정한 ‘좋은 URL’ 99% 달성 여정

> [!abstract] 한 줄 정리
> 웹 성능을 개선할 때 프런트엔드 렌더링만 고치지 말고 HTML 응답, DB 조회, API 호출, 번들, 레이아웃 이동을 지표로 분리해 병목부터 해결해야 한다.

> 원티드랩 기술 블로그 · jpapa · 2025-11-04

## 핵심 내용

- **문제:** 초기 HTML의 90%가 번역키 데이터였고, 로그인 사용자의 세션 조회에는 DB 인덱스가 빠져 있었어. 서버와 브라우저 양쪽에서 로딩 지연이 누적됐어. - **접근:** 번역키 데이터 제거, 세션 테이블 인덱스 추가, 독립적인 SSR API 병렬 호출, 내부 API 전환, CDN 도입을 순차 적용했어. - **수치:** 번역키 제거 후 HTML 크기 66% 감소, 서버 지연 16% 개선, LCP 21% 개선. 세션 인덱스 추가로 TTFB 70%, 독립 API 병렬화로 TTFB 20%, 내부 API 전환으로 호출 지연 32% 개선을 각각 보고했어.

- **클라이언트 개선:** `_app.js`를 759KB에서 489KB로 35% 줄이고 지연 로딩을 적용했어. 이 단계에서 FCP 60%, LCP 31% 개선을 보고했고, 마지막에는 데스크톱 상세 페이지의 CLS를 0.1 미만으로 낮췄어. - **결과·주의점:** Google Search Console 기준 전체 URL의 99% 이상이 ‘좋은 URL’로 분류됐어. 위 백분율은 서로 다른 개선 작업의 개별 측정치이므로 합산해서 전체 효과로 계산하면 안 돼.

Core Web Vitals를 개선할 때는 서버의 응답 시작 시간을 뜻하는 TTFB, 화면의 주요 콘텐츠가 보이는 LCP, 레이아웃 흔들림을 뜻하는 CLS를 서로 다른 증상으로 측정해야 한다. 번역키를 HTML에 과도하게 실어 보낸 구조와 세션 DB 인덱스 누락은 둘 다 느린 페이지를 만들었지만 전자는 전송 크기와 파싱 비용, 후자는 서버에서 첫 바이트를 만들기 전의 대기 시간에 영향을 준다.

| 변경 | 해당 단계의 관측 결과 | 확인할 이유 |
| --- | --- | --- |
| 번역키 제거 | HTML 66% 감소, LCP 21% 개선 | 초기 문서 크기 축소 |
| 세션 인덱스 | TTFB 70% 개선 | 백엔드 조회 병목 |
| API 병렬화 | TTFB 20% 개선 | 독립 요청의 대기 시간 |
| `_app.js` 축소 | 759KB→489KB | JS 전송·실행 비용 |
| 데스크톱 CLS | 0.1 미만 | 레이아웃 안정성 |

각 백분율은 **해당 최적화 단계의 측정치**이므로 서로 더해 전체 속도 개선율을 계산하면 안 된다. Search Console의 좋은 URL 99%라는 결과도 색인·사용자 경험 기준을 포함한 평가이며 단일 지표만으로 검색 노출이 보장되지는 않는다.

## 왜 읽을까

한 지표만 최적화해도 실제 사용 경험은 그대로일 수 있다는 점을 보여줘. 서버 응답과 브라우저 렌더링을 구분하고, 작업마다 측정 근거를 확보해 팀을 설득하는 과정이 특히 유용해.

**프로젝트에 적용 — DevPedia**

- [ ] 공개 모집글 목록·상세 화면의 LCP, CLS, TTFB를 같은 조건에서 기준선으로 기록한다.
- [ ] 로그인/비로그인 요청의 응답 지연을 구분하고 느린 조회가 있다면 SQL 실행 계획을 확인한다.
- [ ] 초기 JS 번들과 불필요한 선로딩 데이터를 조사하고 변경 전후를 동일 환경에서 재측정한다.
