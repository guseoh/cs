# 당근 데이터 지도를 그리다: 컬럼 레벨 리니지 구축기

> [!abstract] 한 줄 정리
> 완벽한 데이터 계보 시스템을 먼저 만들기보다 실제 SQL 실행 기록에서 컬럼 의존성을 추출해 영향도 분석의 시간을 줄인 사례다. 도입 비용이 큰 표준 계측 대신 중앙 수집 가능한 데이터에서 시작한 선택 과정이 특히 좋다.

> 당근 기술 블로그 · 2025-12-04

## 핵심 내용

한 테이블의 파이프라인 장애가 어디까지 전파되는지 찾는 데 몇 시간이 걸렸고, MySQL 컬럼을 삭제할 때도 downstream 영향 범위를 사전에 정확히 알기 어려웠다. 여러 실행 환경에 OpenLineage 계측을 심는 대신 BigQuery `INFORMATION_SCHEMA.JOBS`에 이미 모이는 SQL을 수집해 컬럼 레벨 리니지를 중앙에서 추출했다.

sqlglot으로 SQL AST를 만들고 CTE·서브쿼리·alias 관계를 추적하며, Spark로 대량 병렬 파싱하고 Airflow로 주기 실행한 뒤 BigQuery에 저장한다. 약 2개월의 개발 후 하루 단위로 약 15,000개 테이블과 800,000개의 컬럼 의존성을 추적하며, MCP를 통한 영향도 조회는 수초 안에 가능해졌다.

모든 SQL 문법을 처음부터 완벽하게 지원하지 않고, 사용 빈도가 높고 영향도가 큰 패턴부터 처리해 커버리지를 점진적으로 넓혔다.

테이블 단위 리니지만으로는 '어느 테이블이 의존하는가'까지는 알 수 있어도 '어느 컬럼에 영향이 있는가'를 과대평가하기 쉽다. SQL AST에서 SELECT 항목과 조인·별칭·CTE를 따라가면 특정 필드가 만들어진 계보를 좁힐 수 있다. 수십만 컬럼 연결의 전체 지도를 유지하려면 데이터 생성 위치마다 새로운 계측을 심는 방식보다 중앙 SQL 로그 활용이 운영상 더 저렴할 수 있다.

| 데이터 원천 | 처리 | 결과 |
| --- | --- | --- |
| BigQuery JOBS SQL | sqlglot AST 분석 | 컬럼 의존 관계 |
| 다수 쿼리 | Spark 병렬 처리 | 추출 처리량 확보 |
| Airflow 정기 실행 | BigQuery 저장 | 조회 가능한 Lineage |

파싱할 수 없는 SQL을 임의로 연결하지 않고 미지원 구문과 커버리지를 별도로 관리해야 영향 분석의 신뢰도가 유지된다.

## 왜 읽을까

리니지는 거대한 데이터 플랫폼 조직만의 기능처럼 보이지만, 핵심 문제는 **변경하기 전에 어디가 깨질지 알아내는 것**이다. 이 글은 데이터 인프라를 새로 계측하는 비용과 기존 실행 기록을 재활용하는 비용을 비교해 현실적인 시작점을 고르는 과정을 보여준다.

또 정확도 100%를 기다리지 않고 실제 운영 가치가 큰 구간부터 적용하는 방식은 일반 백엔드의 정적 분석·의존성 분석에도 그대로 가져갈 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 스키마 변경 전 `테이블/컬럼 → Repository → Service/API` 영향 범위를 짧게 기록하는 규칙을 만들어본다.
- [ ] 검색·통계 기능이 늘어나면 어떤 원천 데이터에서 파생됐는지 추적할 최소 메타데이터를 남긴다.
- [ ] 완전한 자동화보다 변경 위험이 큰 핵심 테이블부터 영향도 확인 체계를 적용한다.
