# 당신의 CPU는 열심히 일하고 있나요?

> [!abstract] 한 줄 정리
> 같은 CPU 실험 결과도 런타임과 멀티테넌시 구조가 다르면 최선의 운영 결정은 달라질 수 있습니다.

> techblog.lycorp.co.jp

## 핵심 내용

Kubernetes `cpu.requests`, `cpu.limits`, Linux CFS 스케줄링이 실제 애플리케이션 CPU 사용에 미치는 영향을 Spring과 Node.js 서버에서 실험합니다. 두 환경 모두 CPU limit 제거 시 성능은 좋아졌지만 Spring 싱글 테넌시 서버는 limit 제거를 택했고, Node.js 멀티 테넌시 환경은 TPS 약 13%, 최대 TPS 약 20% 향상에도 성능·설정 일관성과 다른 워크로드 보호를 위해 limit을 유지했습니다.

Kubernetes의 `cpu.requests`는 스케줄링과 자원 보장의 기준이고, `cpu.limits`는 사용할 수 있는 CPU 시간의 상한을 정한다. 특히 CFS quota로 스로틀링이 발생하면 CPU 사용률이 낮게 보여도 요청 지연이 증가할 수 있다. 하지만 Limit 제거를 통해 특정 Pod의 처리량이 좋아지는 것과 노드 전체에서 다른 워크로드를 안전하게 보호하는 것은 다른 목표다.

| 원문에서 비교한 환경 | 선택 | 주된 판단 근거 |
| --- | --- | --- |
| Spring 싱글 테넌시 | CPU Limit 제거 | 격리된 환경에서 처리량 활용 |
| Node.js 멀티 테넌시 | Limit 유지 | 이웃 워크로드 보호와 설정 일관성 |

Node.js 환경에서 원문은 TPS 약 13%, 최대 TPS 약 20%의 향상 가능성을 보고했다. 그럼에도 Limit을 유지한 결정은 수치만이 아니라 공유 인프라의 책임 경계를 고려한 결과다.

## 왜 읽을까

`CPU limit을 없애면 빠르다`가 아니라 실험 결과를 운영 구조와 함께 해석해야 한다는 점이 좋습니다.
