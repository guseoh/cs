# 6개월 만에 연간 수십조를 처리하는 DB CDC 복제 도구 무중단/무장애 교체하기

> [!abstract] 한 줄 정리
> 대규모 CDC 시스템의 교체는 새 도구를 만드는 것보다 복제·검증·복구를 분리하고, 기존 시스템과 중복 실행하며 데이터 정합성을 단계적으로 증명하는 과정이 더 중요하다.

> NAVER D2 · 2025-11-18

## 핵심 내용

- **문제:** 기존 mig-data는 단일 레코드 실패가 전체 복제 지연으로 이어지고, Source/Target 컬럼 추가 순서 제약과 제한적인 장애 복구 절차가 있었다.
- **구조:** Apache Flink + Spring 기반 ergate를 만들고 복제, 검증, 복구를 별도 흐름으로 분리했다. 검증은 Kafka 이벤트를 2분 지연 소비해 Target과 비교하고 실패 건은 DLQ와 상태 DB로 보낸다.
- **목표:** 기존 Write QPS의 10배 이상 처리하고 CDC 이벤트 발행 후 1초 이내 복제를 보장하는 것을 성능 목표로 잡았다.
- **장애 대응:** 복제 실패 건을 전체 흐름을 막지 않고 후속 데이터는 계속 처리하며, 5분 후 자동 복구·장애 배치 복구·수동 복구를 함께 제공했다. Target DB 장애 시 커넥션 대기로 Flink까지 영향을 받는 문제는 서킷 브레이커로 격리했다.
- **전환:** mig-data와 ergate를 서로 모르는 상태로 중복 복제하고, 영향도가 낮은 테이블부터 1차 5개·2차 13개·잔여 테이블 순으로 전환했다. 매 단계에서 동시 복제와 검증을 거친 뒤 기존 복제를 종료했다.

## 왜 읽을까

CDC 자체보다 '운영 중인 데이터 경로를 어떻게 안전하게 교체할 것인가'를 배우기 좋은 글이다. 특히 실패를 전체 스트림 중단으로 처리하지 않고 검증·복구 계층으로 넘기는 설계와, 기존 시스템을 정답지로 일정 기간 유지하는 전환 전략이 인상적이다.

**프로젝트에 적용 — PawCycle**

- [ ] 향후 비동기 데이터 파이프라인을 도입한다면 처리 성공뿐 아니라 검증·복구 경로를 별도로 설계한다.
- [ ] 새 데이터 경로 도입 시 Big Bang 전환보다 기존 경로와 병행해 정합성을 비교한다.
- [ ] 장애 테스트에서 DB 연결 실패가 애플리케이션 스레드·커넥션 풀까지 전파되는지 확인한다.
