# App Router의 장점은 우리에게도 장점일까요?

> [!abstract] 한 줄 정리
> 새 프레임워크의 일반적인 장점을 그대로 믿지 않고 실제 웹뷰·라우팅·캐시·운영 조건에서 검증한 뒤, 얻는 이득보다 전환·유지 비용이 크다는 근거로 App Router 도입을 보류한 사례다.

> Toss Tech · 2026-09-09

## 핵심 내용

Next.js App Router와 React Server Components는 서버에서 데이터 패칭을 정리하고 스트리밍으로 화면 일부를 일찍 보여줄 수 있다는 장점이 있다. 하지만 토스뱅크 웹뷰는 Chromium과 WebKit의 동작 차이, 기존 Pages Router와의 공존, 사용자별 캐시가 만드는 복잡성이 크기 때문에 새로운 라우터의 도입 효과를 직접 시험했다.

1·3·5초 지연을 주는 스트리밍 실험에서 Chromium FCP가 약 64ms였던 반면 WebKit은 약 5,065ms로 늦어졌다. 보이지 않는 SVG를 포함하는 우회 실험에서는 WebKit FCP가 103ms로 줄었지만 이처럼 브라우저별 보정 코드를 유지해야 한다. 스켈레톤 높이를 실제 화면에 맞추면 CLS가 0.138에서 0.036으로 감소했으나 콘텐츠 구성이 바뀔 때마다 로딩 UI도 유지해야 한다. RSC는 번들·데이터 패칭을 단순화하는 대신 Server/Client 컴포넌트와 사용자 캐시 키 관리가 새로운 책임이 된다.

| 검증 항목 | 관측·선택 | 운영상 의미 |
| --- | --- | --- |
| 스트리밍 FCP | Chromium 64ms / WebKit 5,065ms | 웹뷰 엔진별 동작 차이 |
| WebKit 우회 | 숨겨진 SVG 후 103ms | 별도 호환 처리 필요 |
| Skeleton CLS | 0.138 → 0.036 | 높이 유지·UI 관리 비용 |
| 혼합 라우팅 | `/base/base/...` 404 | 점진 이관에도 새로운 오류 |
| 최종 결정 | Pages Router 유지 | 제품별 검증에 기반한 선택 |

기존 Pages Router와 App Router를 점진적으로 섞는 과정에서는 basePath와 동적 라우트가 만나 `/base/base/...`로 이동하는 404 사례도 발생했다. 실제 웹뷰 환경의 사용자 경험과 운영 비용을 비교한 팀은 현재 단계에서 Pages Router를 유지했다. 이는 App Router의 일반적인 성능이 나쁘다는 판단이 아니라 해당 서비스·브라우저에서 전환 이득보다 추가 책임이 크다는 결정이다.

## 왜 읽을까

새 기술을 검토할 때 기능 목록이나 생태계 인기도가 아니라 실제 사용 환경에서 장점이 살아나는지 확인하는 과정을 볼 수 있다. 특히 “도입하지 않음”도 충분히 좋은 기술 결정이 될 수 있으며, 그 결정을 성능 측정과 운영 리스크로 설명하는 방식이 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] Spring·프론트엔드·빌드 도구의 큰 버전 전환 전, 현재 프로젝트에서 기대하는 이득을 먼저 2~3개로 명시한다.
- [ ] PoC에서는 정상 경로뿐 아니라 캐시·라우팅·브라우저/런타임 차이처럼 실제 운영 조건을 재현한다.
- [ ] ‘최신 버전이므로 전환’이 아니라 얻는 이득, 이관 비용, 운영 리스크와 롤백 가능성을 함께 기록해 도입 여부를 결정한다.
