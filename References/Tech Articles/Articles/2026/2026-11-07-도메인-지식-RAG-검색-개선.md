# AI에게 도메인을 가르치다 두 번 갈아엎은 이야기 — LLM Wiki + RAG 혼합기

> [!abstract] 한 줄 정리
> LLM이 내부 도메인 문서를 전부 읽도록 하는 방식은 문서 증가에 따라 토큰 비용과 검색 누락이 커졌다. 컬리는 수동 역색인과 본문 임베딩을 차례로 시도한 후, 짧은 요약의 의미 검색과 원문 FTS5 정확 검색을 결합했다.

## 핵심 내용

배송 도메인의 정책과 진행 과제를 Confluence·Slack에서 모아 Markdown Wiki로 축적했지만, 문서가 30개에서 100개로 늘자 모든 문서를 매번 컨텍스트에 넣는 방식이 비효율적이었다. 첫 시도는 키워드별 역색인 파일을 만들고 해당 문서를 찾아 읽는 구조였다. 그러나 '샛별'과 '새벽배송' 같은 동의어를 색인에 빠뜨리면 검색이 실패하고, '용차'처럼 여러 문서에 공통으로 등장하는 단어는 관련 없는 문서까지 불러왔다.

두 번째는 SQLite의 `sqlite-vec`와 `multilingual-e5-small`을 이용해 본문·별칭·키워드를 임베딩하는 방식이었다. 자연어 표현과 동의어 검색은 개선됐지만 다주제 문서가 하나의 벡터로 평균화되면서 일반어에 끌려 무관한 문서가 상위에 나타났다. 또한 티켓 ID와 사내 약어처럼 정확한 문자열을 찾는 일에는 의미 검색이 약했다.

측정 과정에서 임베딩 모델의 최대 입력이 512토큰이라는 중요한 제약이 드러났다. 약 85%의 문서가 이 길이를 초과했고 가장 긴 문서는 7,396토큰으로 약 93%가 임베딩에 반영되지 않았다. 그럼에도 검색이 일부 동작했던 이유는 각 문서의 앞부분에 요약이 있었기 때문이다. 이는 본문 전체가 아니라 요약이 실제 의미 검색에 기여하고 있었다는 뜻이다.

세 번째 구조는 **한 문서 한 주제**로 정리하고, 사람이 검토한 요약·별칭·키워드 약 100~200토큰만 벡터화했다. 본문 전체는 SQLite FTS5와 BM25로 별도 색인하여 약어와 식별자를 찾는다. 질의 시 벡터 상위 3개와 키워드 상위 2개를 병합하고 중복을 제거하며, 먼저 요약을 보여주어 불필요한 본문 읽기를 줄였다.

| 방식 | 장점 | 실패 또는 제약 |
| --- | --- | --- |
| 역색인 | 정확 키워드 매칭 | 동의어 누락, 색인 유지 부담, 무관한 문서 로딩 |
| 본문 임베딩 | 의미·동의어 검색 | 512토큰 잘림, 다주제 평균화, 식별자 검색 약함 |
| 요약 임베딩 + FTS5 | 의미 검색과 정확 검색 분업 | 요약 품질 편차, 일반어 노이즈 일부 잔존 |

원문은 검색 사례와 호출 횟수 비교를 제시하지만 전체 질의 집합에 대한 정량 정확도 개선률을 제시하지는 않는다. 따라서 이 구조가 모든 도메인에서 우수하다고 단정할 수 없다.

## 왜 읽을까

RAG에서 임베딩 모델을 교체하기 전에 **문서 단위·입력 길이·정확 검색 요구**를 분리해야 한다는 판단 기준을 얻을 수 있다. 검색 실패를 모델 성능 문제로만 해석하면 색인 구조와 데이터 품질의 문제를 놓치기 쉽다.

**PawCycle 적용 제안(미검증):** 설계·운영 Wiki를 주제별로 분리한 뒤, 아키텍처 개념 질의와 커밋 SHA·설정 키·장애 코드 검색을 별도로 테스트해 볼 수 있다. 기존 지식 문서를 수정하기 전에 검색 실패 사례를 기준 데이터로 확보하는 것이 우선이다.
