# 신뢰성 향상을 위한 SLO/SLI 도입 3편 - 서비스 적용 사례

> [!abstract] 한 줄 정리
> 서버가 살아 있는지보다 사용자가 반드시 완료해야 하는 핵심 여정(CUJ)을 먼저 정의하고, 그 여정의 성공률과 지연을 SLI/SLO로 측정해야 신뢰성과 기능 개발 사이의 우선순위를 정할 수 있다.

> LY Corporation 기술 블로그 · 천기철 · 2026-04-22

## 핵심 내용

운영자가 서버가 살아 있는지만 확인하면 사용자가 겪는 실패를 놓칠 수 있다. LY의 SLO/SLI 도입 사례는 메시지 전송·알림·로그인과 같은 핵심 사용자 여정(CUJ)을 먼저 선정하고, 해당 작업이 성공했는지와 얼마나 지연됐는지를 측정 가능한 서비스 수준 지표로 변환했다.

LINE 메시지·채널·인증 서비스에서 사용자 관점의 핵심 여정(CUJ)을 선별한 뒤 대표 API와 관측 위치(게이트웨이·프런트엔드·백엔드)를 정했다.

CUJ별 SLI를 응답 성공률과 응답 지연 퍼센타일 등으로 정의하고, 측정 기간·목표치를 SLO로 설정한 뒤 대시보드로 시각화했다.

![LINE 핵심 사용자 여정을 서비스 품질 지표로 정의한 CUJ 표](https://vos.line-scdn.net/landpress-content-v2-vcfc68aynwenkh3bno0ixfx8/1c088693f3f04c559550e1ae396445f0.png?updatedAt=1776385043000)

*그림 1. 메시지 전송과 알림·친구 조회·가입 같은 실제 사용자 여정을 지표 정의의 출발점으로 둔 원문 표 — [출처: 원문 기술 블로그](https://techblog.lycorp.co.jp/ko/sli-and-slo-for-improving-reliability-3)*

같은 사용자 여정이라도 API 게이트웨이, 프런트엔드, 백엔드 어디에서 지표를 수집하느냐에 따라 실패의 범위와 원인이 달라진다. 성공률에는 오류 응답만 포함할지 타임아웃을 포함할지 계약이 필요하고, 지연 퍼센타일은 합의된 기간과 집계 지점이 정해져야 한다. 그다음 목표치(SLO)를 정하고 기간별 Error Budget을 계산해 기능 출시와 안정화 작업의 우선순위를 조정한다.

```text
# 개념 학습용 오류 예산 예시
관찰 기간 28일, 가용성 목표 99.9%
허용 실패 시간 = 28일 × 24시간 × 60분 × 0.001
              = 약 40.3분
```

이 숫자는 개념 계산이며 원문이 측정한 실제 장애 시간은 아니다.

메시지 전송 SLI를 p99.9 지연 500ms 미만과 성공률 99.999%로 정의하는 예시를 제시했다. 이는 실제 모든 LINE 서비스가 달성했다는 수치가 아닌 설명용 기준이다.

지나치게 높은 SLO는 운영 비용을 늘리고, 낮은 SLO는 사용자 경험을 악화한다. 현실적인 목표와 오류 예산(Error Budget)을 함께 고려해야 한다.

오류 예산 상태에 따라 온콜 알림을 설정하고, 예산이 넉넉하면 기능 개발을 확대하며 소진이 빠르면 안정화 작업에 리소스를 집중하도록 활용했다.

| 구분 | 정의 | 적용 시 질문 |
| --- | --- | --- |
| CUJ | 사용자가 반드시 완수해야 할 핵심 여정 | 메시지 전송·인증 중 어떤 경로가 중요한가 |
| SLI | 실제 측정 가능한 서비스 품질 | 어디에서 성공·실패와 지연을 계측할까 |
| SLO | 일정 기간의 목표 품질 | 운영 비용과 사용자 기대를 어떻게 균형 잡을까 |
| Error Budget | 허용한 실패의 여유분 | 빠르게 소진된다면 배포를 늦출 필요가 있을까 |

*예를 들어 28일 구간에서 가용성 99.9% 목표의 허용 실패 시간은 약 40.3분이다. 이 계산은 개념 이해용 예시로 원문의 실제 운영 측정값이 아니다.*

원문에서는 메시지 전송의 극단적으로 높은 성공률이나 p99.9 지연 목표를 설명용 예시로 제시한다. 이것을 모든 LINE 서비스가 실측으로 달성한 숫자라고 해석해서는 안 된다. Error Budget이 빠르게 소진되면 새로운 기능을 서둘러 출시하기보다 원인을 조사하고 신뢰성을 회복하는 의사결정에 활용할 수 있다는 점이 더 중요하다.

## 왜 읽을까

SLI/SLO를 단순 모니터링 숫자가 아니라 **사용자 여정과 운영 의사결정을 연결하는 계약**으로 이해할 수 있다. 지표의 측정 위치, 실패 판정 기준, 비용과 목표 수준의 균형을 실제 서비스에 적용하는 과정을 참고할 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 상품 조회·로그인·주문 등 핵심 사용자 여정 중 운영상 중요한 2~3개를 선정한다.
- [ ] 각 여정의 대표 API, 실패 판정 조건, p95/p99 지연 기준을 정의한다.
- [ ] 로컬 부하 테스트와 운영 Health/메트릭을 분리해 사용자 관점의 실패율을 관찰한다.
- [ ] 28일 기준 가상의 SLO와 오류 예산을 계산하고, 장애 대응 우선순위에 연결해본다.
