# 실시간 마케팅을 위한 PoC 개발기

> [!abstract] 한 줄 정리
> 일 단위 배치 데이터를 실시간 파이프라인으로 바꾸려면 기술을 먼저 확정하기보다, 실제 마케팅 요구를 만족하는 지연 시간·정합성·운영 복잡도를 PoC로 검증해 아키텍처 선택의 근거를 만들어야 한다.

> 우아한형제들 기술블로그 · 2025-05-20

## 핵심 내용

일 배치로 갱신하는 마케팅 타깃은 사용자가 상품을 보거나 특정 행동을 한 직후 메시지를 보내야 하는 요구를 만족하기 어렵다. 그렇다고 전체 데이터 플랫폼을 바로 스트림 처리 시스템으로 대체하면 실시간성 필요 여부와 기술의 운영 비용을 분리해 판단할 근거가 없다.

```mermaid
flowchart LR
 A[사용자 행동 이벤트] --> B[수집·전송]
 B --> C[실시간 처리]
 C --> D[타깃 상태 갱신]
 D --> E[마케팅 후보]
 E --> F[사용자 접점]
```

*원문을 바탕으로 자체 재구성한 가로형 처리 경계 도식이다.*

우아한형제들의 PoC는 이벤트가 발생하는 지점, 이벤트 전달·처리 계층, 실제 타깃 데이터가 갱신되는 지점으로 흐름을 나누었다. 이벤트 수집→사용자 상태 갱신→세그먼트 판정→메시지 발송 후보 기록까지의 각 단계에서 어떤 데이터가 필요한지와 재처리 시 결과가 중복되지 않을지를 검토하는 방식이다. 일배치와 실시간 파이프라인은 서로 다른 시점에 데이터를 제공하므로 전체 사용자 데이터의 정합성 기준도 함께 정해야 한다.

| 평가 항목 | 배치 접근 | 실시간 PoC에서 확인할 것 |
| --- | --- | --- |
| 갱신 시각 | 일 단위 | 이벤트~타깃 반영 지연 |
| 재처리 | 배치 재실행 | 이벤트 중복·순서 |
| 운영 복잡성 | 정해진 시간 실행 | 상시 스트림·장애 복구 |
| 효과 측정 | 일간 집계 | 행동 후 반응과 캠페인 성과 |

PoC를 평가할 때는 'Kafka로 전송했다'보다 행동 발생부터 실제 타깃 반영까지 걸린 지연의 분포와 누락률, 재처리 안전성, 운영 비용을 기준으로 두는 편이 적절하다. 원문은 기술 방향을 소개하지만 표준화된 지연·비용 Before/After를 공개하지 않았으므로 실시간 전환이 반드시 경제적이라고 단정할 수 없다.

## 왜 읽을까

Kafka나 스트림 처리 기술을 도입했다는 결과보다 PoC를 통해 아키텍처 가정을 먼저 검증하는 과정이 가치 있다. 새로운 분산 구조는 기능 요구를 해결하는 동시에 장애 지점과 운영 비용을 늘리므로, 본 구현 전에 어떤 것을 측정해야 하는지 생각하기 좋다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기 모집·신청·알림 중 즉시성이 실제 필요한 이벤트와 지연을 허용할 수 있는 작업을 먼저 구분한다.
- [ ] 이벤트 기반 구조를 검토할 때 중복 이벤트, 순서 역전, Consumer 재처리 시나리오를 PoC에 포함한다.
- [ ] 단순 동기 호출과 메시징 구조의 복잡도·지연·복구 방식을 비교한 뒤 도입 여부를 결정한다.
