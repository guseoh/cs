# LLM 서빙, 띄우는 것과 잘 띄우는 것 사이

> [!abstract] 한 줄 정리
> LLM 운영에서는 일반 서버 지표만으로 원인을 찾기 어렵다. TTFT, 생성 토큰 처리량, Prefix/KV Cache 같은 모델·서빙 프레임워크 지표를 함께 관찰하고 스트레스 테스트와 빠른 롤백까지 연결해야 한다.

> Toss Tech · 2026-08-21

## 핵심 내용

- **구조:** 처리량을 초당 요청 수가 아닌 초당 생성 토큰 수로, 응답 시간을 전체 완료 시간 대신 TTFT(Time To First Token)로 다시 정의했다. Grafana 메트릭과 Kibana 단건 로그를 중앙화했다.
- **결과:** Prefix Cache가 비활성화된 모델을 찾아 재활성화한 뒤 TTFT가 최대 약 20초 수준에서 약 1/10로 줄었고 Prefix Cache Hit Rate는 90% 이상을 기록했다.
- **결과:** vLLM 버그로 reasoning 종료 토큰이 잘못 처리되던 문제에 워크어라운드를 적용해 에러율을 약 0.2%에서 0.02%로 낮췄다.
- **수치:** 생성 TPS가 약 1,000인데 KV Cache 사용량이 1% 미만인 상황을 확인해 증설 전 동시성 테스트를 했고, 동시성 20까지 허용 가능함을 검증해 자원을 두 배 쓰지 않고 트래픽을 최대 4배까지 받을 힌트를 얻었다.
- **주의점:** 서빙 프레임워크와 모델 버전 변화가 빨라 모든 문제를 미리 예방하기보다 `발견 → 관찰 → 가설·검증 → 반영·롤백`의 운영 루프를 갖추는 쪽을 택했다.

## 왜 읽을까

Observability의 핵심은 지표를 많이 모으는 게 아니라 시스템의 동작 특성에 맞는 지표를 고르는 것이라는 점을 잘 보여준다. 비용이 큰 GPU 증설을 하기 전에 실제 자원 사용률과 동시성 한계를 측정하는 과정도 일반 백엔드 성능 문제와 그대로 연결된다.

**프로젝트에 적용 — 공통**

- [ ] 성능·운영 지표를 기술별 기본 지표에만 맡기지 말고, 실제 처리 모델의 병목을 설명할 지표가 무엇인지 먼저 정의한다.
- [ ] 증설 전 `현재 자원을 정말 다 쓰고 있는가`를 확인하는 검증 절차를 운영 체크리스트에 포함한다.
- [ ] 장애 대응 기록을 `발견 → 관찰 → 가설 → 검증 → 반영/롤백` 흐름으로 남긴다.
