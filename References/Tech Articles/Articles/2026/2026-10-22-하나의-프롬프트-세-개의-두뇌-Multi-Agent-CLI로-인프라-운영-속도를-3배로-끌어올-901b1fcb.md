# 하나의 프롬프트, 세 개의 두뇌: Multi-Agent CLI로 인프라 운영 속도를 3배로 끌어올린 이야기

> [!abstract] 한 줄 정리
> AI 에이전트를 무조건 늘리기보다 작업 위험도에 맞게 속도·정밀도·교차 검증을 선택하고 정책을 한 곳에서 관리해야 한다.

> 아임웹 기술블로그 · Yonghyun Kim · 2026-03-20

## 핵심 내용

- **문제:** 빠른 로그 분석과 고위험 IAM 변경을 하나의 에이전트에 맡기면 검증 부족과 컨텍스트 과부하가 발생한다. - **구조:** Claude 조율자, Gemini 빠른 분석, Codex 정밀 검증의 역할을 분리하고 solo/quick/precise/cross/critical 다섯 모드를 제공한다. 작업별 타임아웃도 다르게 둔다. - **검증:** IAM 정책 작성에서 두 모델을 비교해 S3 ListBucket 조건과 DynamoDB GSI 접근 권한의 차이를 발견했다. 배포 계획은 정밀 검증 → 영향 분석 → 종합 판단 순서로 진행한다.

- **시행착오:** 레거시 PHP 분석에서는 한 모델이 파일 경로를 잘못 파악하고 다른 모델은 원격 접근이 막혀 교차 검증을 중단하고 단일 탐색으로 전환했다. - **결과:** 작성자는 복잡한 작업 처리 속도 3배 향상, 코드 리뷰 품질 체감 40% 개선을 보고했다. 후자는 주관적 평가이며 일반화된 벤치마크는 아니다.

여러 모델을 병렬 호출하는 것의 장점은 의견을 많이 얻는 데 그치지 않고 **작업의 위험도에 따라 검증 비용을 다르게 배분**할 수 있다는 점이다. 로그를 빠르게 분류하는 읽기 전용 작업과 IAM 정책을 수정하는 작업에는 동일한 정확성·승인 기준을 적용할 필요가 없다. 원문에서 S3 ListBucket 조건과 DynamoDB GSI 권한처럼 작은 차이를 교차 점검한 것은 정책 파일이 문법적으로 유효하다고 실제 의도가 보장되지 않기 때문이다.

| 작업 유형 | 적합한 검증 |
| --- | --- |
| 빠른 조사 | 탐색·요약 후 출처 확인 |
| 코드·설정 리뷰 | 독립 분석과 Diff 비교 |
| IAM·운영 변경 | 권한 시뮬레이션·사람 승인 |
| 에이전트 접근 불가 | 실패 보고 및 검증 경로 전환 |

복수 모델이 같은 잘못된 입력을 받아 동일한 오류를 낼 수도 있다. 따라서 합의된 답을 곧 정답으로 보지 않고 **검증 가능한 증거, 재현 가능한 명령, 변경 후 관측 결과**를 최종 판단에 사용해야 한다.

## 왜 읽을까

멀티에이전트의 가치는 모델 개수보다 독립 검증과 실패 시 단순한 방법으로 되돌아갈 수 있는 설계에 있다. 공통 정책 Hub와 에이전트별 Spoke를 분리하는 방법도 참고할 만하다.

**프로젝트에 적용 — PawCycle**

- [ ] 코드 분석·테스트 생성·운영 변경을 위험도별로 구분하고 운영 변경은 사람 승인 뒤에만 수행한다.
- [ ] 중요한 설계는 독립 검토를 거치되 최종 결론은 실제 코드·테스트로 검증한다.
- [ ] 에이전트별 중복 정책 대신 공통 안전 규칙의 단일 출처를 유지한다.
