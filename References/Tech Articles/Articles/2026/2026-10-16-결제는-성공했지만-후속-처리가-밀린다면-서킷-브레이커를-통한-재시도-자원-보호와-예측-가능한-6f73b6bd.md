# 결제는 성공했지만 후속 처리가 밀린다면? 서킷 브레이커를 통한 재시도 자원 보호와 예측 가능한 실패 설계

> [!abstract] 한 줄 정리
> Outbox로 외부 장애를 핵심 트랜잭션에서 분리해도 재시도 워커의 스레드와 네트워크 자원은 고갈될 수 있다. Backoff와 Circuit Breaker로 ‘언제 다시 시도하고 언제 즉시 실패할지’를 통제해야 한다.

> Minseo Kim · Medium 개인 개발 블로그 · 2026-01-27

## 핵심 내용

핵심 결제는 정상적으로 커밋됐는데 외부 티켓 서버가 중단되면 후속 처리 워커가 계속 네트워크 타임아웃을 기다리게 된다. Outbox를 통해 결제와 티켓 발급을 분리했더라도 무제한 재시도는 스레드와 DB 커넥션을 소비하고 회복 직후에도 밀린 요청을 폭발시킬 수 있다.

이 사례는 후속 요청마다 `nextRetryAt`을 저장하고 실패 회수에 따라 5초→30초→2분→10분으로 간격을 늘려 일정 시각 이전에는 실행하지 않는다. Resilience4j Circuit Breaker는 최근 10회 실패율이 50% 이상이면 OPEN으로 전환해 즉시 호출을 막고, 30초 뒤 HALF_OPEN에서 3건을 시험한다. CLOSED의 네트워크 오류와 OPEN의 `CallNotPermittedException`은 같은 실패가 아니므로 로그와 테스트에서 구분해야 한다.

```yaml
# 기사 설정값의 의미를 보여 주는 축약 예시
resilience4j:
  circuitbreaker:
    instances:
      ticketIssue:
        slidingWindowSize: 10
        failureRateThreshold: 50
        waitDurationInOpenState: 30s
        permittedNumberOfCallsInHalfOpenState: 3
```

재시도 일정은 회로 차단 상태와 별도로 저장해야 예약된 건이 조용히 사라지지 않는다.

| 회로 상태 | 외부 네트워크 호출 | 재시도 워커 판단 |
| --- | --- | --- |
| CLOSED | 실제 API 호출 | 실패 시 nextRetryAt 설정 |
| OPEN | 즉시 거절 | 오래 대기하지 않고 다음 시점 예약 |
| HALF_OPEN | 제한된 3건 시험 | 회복 여부 관측 후 상태 전환 |
| 최대 횟수 초과 | 호출 중단 | FAILED 격리·운영 알림 |

최대 재시도 횟수 이후에는 FAILED로 격리해 사람의 개입이나 재처리 정책을 결정할 수 있다. Circuit Breaker를 열면 즉시 실패하므로 사용자 후속 처리 지연을 숨기지 않고 관측·알림 체계를 함께 만들어야 한다. 원문은 예제 설정을 설명한 것으로 실제 Before/After 처리량을 공개하지 않았고 위 숫자들도 범용 튜닝 권장값이 아니다.

## 왜 읽을까

재시도는 항상 안정성을 높이지 않는다. 복구 불가능한 상태에 계속 요청을 보내면 장애가 커지므로, 빠른 실패와 복구 탐색을 별도 상태로 설계하는 이유를 배울 수 있다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기 참가 확정 이후 외부 알림을 보내는 흐름이 생긴다면 외부 API 타임아웃·장애 시 참가 상태가 유지되는지 검증한다.
- [ ] 재시도 간격과 최대 횟수, 실패 상태를 명시하고 중복 알림 방지 조건을 정의한다.
- [ ] 외부 API를 강제로 중단한 테스트에서 워커 스레드 점유와 실패 복구 과정을 확인한다.
