# 결제는 성공했지만 후속 처리가 밀린다면? 서킷 브레이커를 통한 재시도 자원 보호와 예측 가능한 실패 설계

> [!abstract] 한 줄 정리
> Outbox로 외부 장애를 핵심 트랜잭션에서 분리해도 재시도 워커의 스레드와 네트워크 자원은 고갈될 수 있다. Backoff와 Circuit Breaker로 ‘언제 다시 시도하고 언제 즉시 실패할지’를 통제해야 한다.

> Minseo Kim · Medium 개인 개발 블로그 · 2026-01-27

## 핵심 내용

- **문제:** 외부 티켓 서버가 중단되면 Outbox 워커가 매 요청마다 타임아웃을 기다려 스레드가 묶이고, 재시도 큐가 쌓여 서버 복구 후에도 처리 지연이 이어졌다.
- **접근:** `nextRetryAt`으로 재시도 시점을 관리하고 실패 순서에 따라 **5초 → 30초 → 2분 → 10분**으로 대기 간격을 늘렸다. 허용 횟수 초과 시 `FAILED` 상태로 분리한다.
- **설정:** Resilience4j의 횟수 기반 슬라이딩 윈도 10건, 실패율 임계치 50%, OPEN 유지 30초, HALF\_OPEN 허용 호출 3건을 사용했다. 이 값은 해당 예제의 설정이지 보편적 권장값은 아니다.
- **검증:** CLOSED 상태에서는 실제 네트워크 실패인 `ResourceAccessException`, OPEN 상태에서는 호출 없이 `CallNotPermittedException`이 발생함을 테스트 프로필과 로그로 확인했다.
- **트레이드오프:** 외부 장애의 대기 비용을 줄이는 대신 Outbox 테이블, 워커, 차단 임계치와 복구 시도 정책을 계속 운영해야 한다. 정량적인 처리량 Before/After는 공개하지 않았다.

## 왜 읽을까

재시도는 항상 안정성을 높이지 않는다. 복구 불가능한 상태에 계속 요청을 보내면 장애가 커지므로, 빠른 실패와 복구 탐색을 별도 상태로 설계하는 이유를 배울 수 있다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기 참가 확정 이후 외부 알림을 보내는 흐름이 생긴다면 외부 API 타임아웃·장애 시 참가 상태가 유지되는지 검증한다.
- [ ] 재시도 간격과 최대 횟수, 실패 상태를 명시하고 중복 알림 방지 조건을 정의한다.
- [ ] 외부 API를 강제로 중단한 테스트에서 워커 스레드 점유와 실패 복구 과정을 확인한다.
