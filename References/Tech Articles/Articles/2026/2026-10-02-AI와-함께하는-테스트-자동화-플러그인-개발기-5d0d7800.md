# AI와 함께하는 테스트 자동화: 플러그인 개발기

> [!abstract] 한 줄 정리
> AI에게 테스트 코드를 통째로 맡기기보다, IDE가 컴파일 가능한 구조와 정확한 프로젝트 문맥을 제공하고 AI는 구현을 채우도록 역할을 나누면 실제 멀티모듈 환경에서도 자동화의 신뢰도를 크게 높일 수 있다.

> 우아한형제들 기술블로그 · 2025-12-04

## 핵심 내용

AI로 테스트 코드를 자동 생성해도 컴파일조차 되지 않으면 실제 테스트 자산이 아니다. 우아한형제들의 첫 번째 버전은 10개 클래스에 테스트 파일을 모두 생성했지만 컴파일은 단 한 개 클래스만 통과했고, 없는 import와 잘못된 타입, 기존 테스트 덮어쓰기·메서드 누락이 반복됐다.

플러그인은 IDE의 PSI로 실제 클래스·메서드·의존성을 읽고 유효한 테스트 파일의 구조와 팀의 테스트 패턴을 결정적으로 작성한다. AI는 해당 구조 안에서 입력·경계·기대값을 채우도록 역할을 축소했다. 복잡한 업무 시나리오의 테스트 케이스를 그대로 모든 클래스에 복사하는 대신, 클래스별 책임에 따라 단위 테스트가 가능한 검증을 분리한다. '형식 보장'과 '검증 의미 보장'을 서로 다르게 보는 접근이다.

| 단계 | 초기 실패 | 책임 분리 뒤 확인할 기준 |
| --- | --- | --- |
| 코드 구조 | import·타입 불일치 | PSI 기반 결정적 생성 |
| 기존 테스트 | 덮어쓰기·누락 | 변경 범위 검사 |
| 테스트 의미 | 실제 계약 누락 | 클래스별 책임과 TC 대응 |
| 컴파일 성공률 | 1/10 | 약 95% |
| 생성 테스트 실행 통과 | 별도 불안정 | 약 97% |

개선 후 클래스당 작업 시간 10분→3분, 컴파일 성공률 95%, 생성 테스트 실행 통과율 97%를 기록했다. 100개 클래스 기준 약 11.7시간을 절약했다는 추산은 특정 업무 환경의 결과다. 테스트가 컴파일되고 실행된다는 사실만으로 요구사항을 다 검증한다는 뜻은 아니므로 assertion 완전성·거짓 PASS와 기존 테스트 보존을 사람·자동 검증이 함께 확인해야 한다.

## 왜 읽을까

AI 코딩 도구의 데모가 아니라, 실제 멀티모듈 프로젝트에서 자동 생성 테스트가 왜 깨지는지를 수치로 보여주고 실패한 첫 설계를 다시 바꾼 과정이 좋다. 특히 테스트 자동화에서는 생성량보다 컴파일 가능성, 기존 테스트 보존, 책임에 맞는 TC 배치가 먼저라는 판단을 얻을 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 세션 인증·회원 API의 기존 테스트 패턴을 먼저 고정하고 AI가 그 구조를 재사용하게 한다.
- [ ] Codex가 생성한 테스트는 컴파일·전체 테스트 통과뿐 아니라 기존 assertion 삭제·완화 여부도 diff로 검사한다.
- [ ] Service별 책임에 맞춰 테스트 케이스를 분산하고, 통합 테스트가 필요한 시나리오는 억지로 단위 테스트로 만들지 않는다.
