# AI를 전제로 다시 설계하다, Tech-Verse 2026 참관기

> [!abstract] 한 줄 정리
> AI 코딩의 병목은 모델 성능이나 타이핑 속도만이 아니라 작업 간 핸드오프, 컨텍스트 손실, 검증 환경에 있다. AI를 개발 흐름에 넣을수록 공통 하네스와 증거 기반 검증을 함께 설계해야 한다.

> LY Corporation Tech Blog · 2026-09-11

## 핵심 내용

AI 개발 도구를 도입해 개별 작업이 빨라져도 리뷰 대기와 개발 단계의 인수인계가 길면 전체 제품 출시 속도는 크게 바뀌지 않을 수 있다. LY Tech-Verse 2026 참관기는 이 문제를 AI Velocity Paradox로 설명하며 모델 성능보다 에이전트와 조직이 협업하는 계약에 주목했다.

출시 2개월 만에 Agent Builder에는 100개 이상의 워크플로가 생기고 MCP Hub에는 150개 이상의 서버가 연결됐다. 이 규모에서는 도구 스키마 검증·호출 속도 제한·권한과 다섯 종류의 가드레일이 플랫폼 수준에서 제공되어야 한다. 레거시 서비스가 105개 이상인 환경에서는 AI가 기존의 암묵적 설계 규칙을 모르고 코드를 바꿀 수 있기 때문에 명세와 테스트를 사람이 검토하는 단계에만 의존하지 않고 하네스에서 기계적으로 강제해야 한다.

| 관측 사례 | 보고 수치 | 해석 제한 |
| --- | --- | --- |
| Agent Builder | 2개월간 100+ 워크플로 | 도입 규모 |
| MCP Hub | 150+ 서버 | 연결 개수≠품질 |
| 구조화 설계서 | 약 46배 증가 | 문서량≠좋은 결정 |
| 레거시 AI 코드 | 약 20% | 생성 비율≠안전성 |
| LINE Plus 백엔드 | 인당 시간당 9.24배 | 해당 10개월 대상/조건 |
| 코드량 변화 | 약 39% 감소 | 유지보수 품질 검증 필요 |

자료는 AI 사용 환경에서 설계서가 약 46배로 증가하고 레거시 영역의 AI 생성 코드 비중이 약 20%에 도달했으며, LINE Plus 백엔드의 10개월 측정에서 인당 시간당 생산성이 9.24배 증가한 사례를 소개한다. 이 수치들은 각각 측정 대상과 분모가 다르므로 동일한 조직 생산성의 단일 증거로 섞어서는 안 된다. 코드량 39% 감소와 처리 티켓 증가 역시 맥락 개선 이후의 관찰이다.

## 왜 읽을까

AI 활용을 ‘코드를 더 빨리 쓰는 도구’로만 보지 않고 개발 프로세스 전체의 병목을 다시 찾게 해준다. 특히 에이전트의 완료 선언보다 검증 가능한 근거를 남기는 구조가 중요하다는 관점은 AI 기반 개발을 운영 단계까지 가져갈 때 유용하다.
