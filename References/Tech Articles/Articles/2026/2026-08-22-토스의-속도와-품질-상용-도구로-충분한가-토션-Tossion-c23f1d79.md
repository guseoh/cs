# 토스의 속도와 품질, 상용 도구로 충분한가 — 토션(Tossion)

> [!abstract] 한 줄 정리
> QA 데이터를 한곳에 모으는 데서 출발해 PR 위험 분석, AI 테스트 케이스 생성, 실기기 회귀 테스트까지 확장한 플랫폼 사례다. AI 결과를 신뢰하기보다 누락을 잡는 규칙과 독립된 검증 계층을 겹쳐 품질을 만든다.

> Toss Tech · 2026-08-11

## 핵심 내용

- **문제:** 자동화 결과, 수동 테스트 결과, 테스트 케이스와 판단 근거가 서로 다른 도구에 흩어져 과거 검증 결과를 다시 추적하기 어려웠다. 상용 TCM은 조직의 변경 속도에 맞춰 확장하기도 어려웠다.
- **구조:** Project → Suite → Section → Test Case 구조를 두고 Test Run 생성 시 당시 Assignee·Step·Description을 복사해 스냅샷으로 보존한다. 원본 테스트 케이스가 바뀌거나 삭제돼도 과거 검증 근거는 남는다.
- **수치:** 한 릴리즈에 약 400개의 PR이 들어오므로 AI에게 한 번에 맡기지 않고 작은 묶음으로 나눠 병렬 분석한다. 분석이 두 시간 걸릴 때도 묶음 단위로 중간 결과를 저장해 중단 후 이어서 실행할 수 있게 했다.
- **접근:** 모호한 문장, PR 제목 복사, 함수명 노출, 필수 테스트 정보 누락 등을 규칙으로 판정하고 부적합 결과는 재분석한다. 입력 PR 수와 분석 결과 수도 마지막에 대조해 누락을 찾는다.
- **검증:** AI 테스트 케이스는 자기 검토, 결정론적 규칙 검사, 별도 AI가 독립적으로 만든 테스트 계획과의 비교라는 세 겹의 신뢰 장치를 둔다. 구조 변경은 AI가 직접 수행하지 않고 평평한 경로만 받아 시스템 코드가 트리를 구성한다.

## 왜 읽을까

AI 테스트 자동화에서 생성 능력보다 **누락을 어떻게 발견할 것인가**가 더 중요하다는 관점을 준다. 또한 테스트 결과를 단순 성공/실패 리포트가 아니라 특정 테스트 케이스와 당시의 판단 근거에 연결해 보존하는 데이터 모델도 실무적으로 유용하다.

**프로젝트에 적용 — 공통**

- [ ] Codex가 만든 테스트는 개수보다 요구사항·경계값·상태 전이가 빠졌는지 별도 기준으로 검증한다.
- [ ] AI 검증과 결정론적 검증을 분리해, 자동 검사 가능한 규칙은 테스트·CI가 맡도록 한다.
- [ ] 성능·회귀 테스트 결과를 코드 변경 시점의 조건과 함께 보존해 Before/After 근거로 재사용한다.
