# 네이버 통합검색 AIB 도입과 웹 성능 변화 분석

> [!abstract] 한 줄 정리
> 성능 지표는 숫자 자체보다 사용자 경험의 어느 순간을 측정하는지 이해해야 올바르게 해석할 수 있습니다.

> d2.naver.com

## 핵심 내용

네이버 통합검색 AIB 확대 후 LCP p95가 약 3.1초로 관측돼 원인을 분석합니다. 서버 응답과 초기 데이터 전달에서는 큰 변화가 없었고 실제로는 스켈레톤 UI와 어절 단위 텍스트 애니메이션이 LCP 측정 시점을 뒤로 밀고 있었습니다. 채팅처럼 콘텐츠를 점진적으로 보여주는 UI에서는 기존 LCP만으로 체감 속도를 충분히 표현하기 어렵다는 문제도 제기합니다.

LCP(Largest Contentful Paint)는 화면에서 큰 요소가 최종적으로 그려진 시점의 지표이지 모든 애니메이션 UI의 **첫 체감 반응**을 측정하는 지표는 아니다. 스켈레톤과 어절 단위 텍스트 출력을 추가하면 네트워크와 초기 응답이 같아도 큰 콘텐츠가 늦게 확정되어 LCP가 뒤로 밀릴 수 있다. 그러므로 AIB 도입 전후의 서버 응답 시간, 스켈레톤 노출 시점, 콘텐츠 렌더 완료 시점을 각각 분리해 관측하는 것이 중요하다.

원문의 약 **LCP p95 3.1초**는 해당 통합검색 측정 조건의 관측치다. 점진적 인터페이스에서는 지표 악화가 실제 사용자 경험 악화와 항상 일치하는 것은 아니지만, 그렇다고 성능 문제가 없다는 결론을 먼저 내려서는 안 된다.

## 왜 읽을까

성능 지표가 객관적인 숫자처럼 보여도 무엇을 측정하는지에 따라 의미가 달라진다는 좋은 사례입니다. 백엔드의 평균 latency, p95, TPS 해석에도 그대로 연결됩니다.
