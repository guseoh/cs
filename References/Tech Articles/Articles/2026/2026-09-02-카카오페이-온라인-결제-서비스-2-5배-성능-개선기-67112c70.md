# 카카오페이 온라인 결제 서비스 2.5배 성능 개선기

> [!abstract] 한 줄 정리
> 대형 이벤트를 앞두고 DB CPU와 쿼리 구조, 캐시, 트랜잭션 범위를 차례로 좁혀가며 안전 처리량을 157 TPS 수준에서 목표 이상으로 끌어올린 실전 성능 개선 사례다. Redis나 설정 하나를 만능 해법으로 보지 않고 실제 병목을 측정한 뒤 선택을 바꾼 과정이 핵심이다.

> 카카오페이 기술 블로그 · 2023-12-07

## 핵심 내용

자체 성능 테스트에서 안전 허용치는 157 TPS였지만 빼빼로데이 목표는 300 TPS였다. 애플리케이션 CPU에는 여유가 있었고 DB CPU가 주요 제약으로 확인돼 DB 분리보다 기존 구조 개선을 먼저 선택했다. 읽기 비중이 큰 쿼리와 호출 빈도가 높은 API를 추적하고 Redis 캐시, 트랜잭션 범위 축소, 모니터링 보강 등 여러 개선을 단계적으로 적용했다. 임시 Redis 상태 조회는 복잡성을 늘리는 코드라는 점도 인지하고 더 나은 구조가 자리 잡은 뒤 제거 대상으로 봤다.

Spring의 OSIV가 기본값 true로 남아 있어 요청 전 구간에서 DB 커넥션을 오래 점유하고 외부 호출 대기까지 영향을 줄 수 있었다. OSIV를 끄는 대신 Lazy Loading 관련 코드를 정리해야 하는 비용을 감수했다. 성능 테스트 기준 TPS는 170 → 400, QPS는 53K → 80K, DB CPU는 74% → 50%로 개선됐다. 처리량은 약 2.5배 늘면서도 DB CPU는 오히려 낮아졌다.

| 지표 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 테스트 처리량 | 170 TPS | 400 TPS |
| DB QPS | 53K | 80K |
| DB CPU | 74% | 50% |

표에서 핵심은 TPS가 높아진 것뿐 아니라 DB CPU가 내려갔다는 점이다. `OSIV`처럼 편의 기능이 커넥션 보유 시간을 늘리면 요청이 외부 호출을 기다리는 동안 DB 용량을 잠식할 수 있다. DB 분리보다 캐시·트랜잭션 경계·쿼리 호출량부터 줄인 이유를 시스템 전체의 병목 이동 관점에서 이해해야 한다.

## 왜 읽을까

성능 문제를 만나면 캐시나 스케일아웃부터 떠올리기 쉽지만, 이 글은 **현재 병목 자원이 무엇인지 확인한 뒤 가장 작은 변경부터 검증하는 흐름**을 보여준다. 특히 Redis, OSIV, APM 같은 요소를 각각 장단점이 있는 도구로 다룬다는 점이 좋다.

또 큰 개선 수치만 보여주는 데 그치지 않고 임시 해법의 복잡성, Lazy Loading 정리 비용처럼 성능 개선이 새로 만드는 비용도 함께 드러낸다.

**프로젝트에 적용 — PawCycle**

- [ ] k6 기준선에서 TPS·p95뿐 아니라 DB CPU, 쿼리 수, HikariCP 대기 시간을 함께 기록한다.
- [ ] OSIV 사용 여부와 실제 DB 커넥션 점유 범위를 확인하고, 변경 전후를 같은 부하 조건으로 비교한다.
- [ ] 캐시를 넣기 전에 어떤 DB 조회를 줄이려는지 명시하고, 캐시 정합성과 복잡성 증가를 함께 기록한다.
