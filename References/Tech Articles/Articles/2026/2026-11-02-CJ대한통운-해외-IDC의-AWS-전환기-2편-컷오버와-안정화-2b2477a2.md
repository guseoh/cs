# CJ대한통운 해외 IDC의 AWS 전환기 2편: 컷오버와 안정화

> [!abstract] 한 줄 정리
> 클라우드 이전의 성공 기준은 서버 복제 완료가 아니라, 의존 시스템·배치·데이터를 검증하고 실제 전환 이후의 장애까지 통제하는 것입니다. 되돌릴 수 있는 시점과 없는 시점을 구분한 컷오버 설계가 핵심입니다.

> AWS 기술 블로그 · CJ대한통운 · 2026-10-30

## 핵심 내용

CJ대한통운의 해외 IDC 전환은 수십 대의 Windows 서버를 복제하는 문제 이상이었다. SQL Server, Active Directory, 배치 작업, 원격 시스템과의 데이터 연결이 서로 의존하기 때문에 어느 한 서버가 정상적으로 뜨더라도 업무 전체가 준비됐다고 할 수 없었다. 실제 연결 관계를 수집하는 의존성 분석과 표준 컷오버 절차를 별도 산출물로 정의해야 했다.

![환경별 마이그레이션 담당과 검증 절차를 정리한 Migration Order](https://d2908q01vomqb2.cloudfront.net/2a459380709e2fe4ac2dae5733c73225ff6cfee1/2026/10/30/cj-logistics-aws-migration-cutover-stabilization-03-1.png)

*그림 1. 준비·Test·Cutover·Finalize를 환경·담당자·산출물별로 구분한 원문 프레임워크 — [출처: 원문 기술 블로그](https://aws.amazon.com/ko/blogs/tech/cj-logistics-aws-migration-cutover-stabilization-2/)*

원문에서는 사전 준비와 리허설을 통해 SQL Server 데이터 이전, 내부 연결 확인, DNS 변경·사용자 인수 시험(UAT), 안정화 단계를 분리했다. 환경별 준비 문서와 작업 담당자를 Migration Order로 정리하고 Jira로 추적하여 배포 담당자의 기억이 아닌 단계별 완료 기준으로 진행했다. RDS가 기존 SQL Server 기능 일부와 호환되지 않는 제약을 고려해 EC2 직접 운영을 선택한 것도 당시 환경 의존성에 따른 결정이었다.

| 관찰 항목 | 실제 확인 내용 | 해석 |
| --- | --- | --- |
| 사전 리허설 | 5회 | DNS·DB·외부 연계별 실행 단계 점검 |
| 컷오버 목표 | 150분 이내 | 서비스 전환 계획의 한계 시간 |
| 실제 컷오버 | 약 200분 | 계획 대비 약 50분 초과 |
| 원격 쓰기 최적화 | 배치 전체 약 12시간 → 6~7분 | 건별 원격 쓰기를 1,000건 단위로 묶은 결과 |
| 컷오버 후 복구 | 쓰기 트래픽 유입 후 전진 복구 | 데이터 역전 가능성 때문에 즉시 롤백이 불리 |

*배치 시간 단축은 해당 원격 쓰기 병목 해결 사례이며 모든 SQL Server 작업에 보장되는 수치는 아니다.*

리허설을 다섯 차례 수행했지만 컷오버는 계획한 150분을 넘어 약 200분이 걸렸다. 고객 트래픽이 신규 환경으로 들어온 뒤에는 이전 환경으로 단순 복귀할 경우 데이터가 역전될 수 있어 전진 복구가 더 적합했다. 누락된 SQL Server 배치 잡과 IDC에 남은 Linked Server의 건별 원격 쓰기가 운영 장애로 드러났으며, 1,000건 단위 묶음 처리로 배치 전체를 약 12시간에서 6~7분 수준으로 줄였다. 데이터 복제의 성공과 업무 프로세스의 정상화는 다른 검증 항목이다.

## 왜 읽을까

마이그레이션을 인프라 복제가 아닌 의존성 분석·데이터 정합성·운영 절차의 설계 문제로 바라보게 합니다. 특히 코드가 동일해도 네트워크 거리가 달라지면 실행 시간이 급증하고, 데이터 이전만으로 배치·권한·연계가 복구되지 않는다는 점이 실무적입니다.

**프로젝트에 적용 — PawCycle**

- [ ] OCI 대체 배포를 가정해 DB·배치·비밀·DNS·외부 연동 의존성 목록을 작성합니다.
- [ ] 전환 전후 데이터 건수·핵심 API·배치 소요 시간 검증표를 만듭니다.
- [ ] 롤백 가능한 시점, 데이터 쓰기 시작 이후의 복구 방법과 Go/No-Go 기준을 분리합니다.
