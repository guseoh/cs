# CJ대한통운 해외 IDC의 AWS 전환기 2편: 컷오버와 안정화

> [!abstract] 한 줄 정리
> 클라우드 이전의 성공 기준은 서버 복제 완료가 아니라, 의존 시스템·배치·데이터를 검증하고 실제 전환 이후의 장애까지 통제하는 것입니다. 되돌릴 수 있는 시점과 없는 시점을 구분한 컷오버 설계가 핵심입니다.

> AWS 기술 블로그 · CJ대한통운 · 2026-10-30

## 핵심 내용

- **문제:** 수십 대의 Windows/SQL Server와 외부 연계가 얽힌 해외 IDC를 이전해야 했습니다. RDS가 기존 SQL Server 기능 일부를 지원하지 않아 EC2 직접 운영을 선택했습니다.
- **구조:** 5회 리허설을 거쳐 DB 컷오버→내부 연결 검증→DNS 전환·UAT→안정화의 4단계로 분리하고, 단계별 Go/No-Go·완료 조건·롤백 경계를 정했습니다.
- **수치:** 150분 이내 목표였지만 실제 컷오버는 약 200분 걸렸습니다. 고객 트래픽 유입 이후에는 데이터 역전의 위험 때문에 롤백보다 전진 복구를 택했습니다.
- **장애:** DB 백업/복원에서 시스템 DB의 배치 잡이 누락됐고, IDC에 남은 Linked Server의 행 단위 원격 쓰기가 병목이 됐습니다. 전체 배치가 약 12시간으로 늘었다가 1,000건 묶음 처리로 6~7분까지 줄었습니다(문제 스텝 2시간 48분→29초).
- **트레이드오프:** 3년 운영비는 기존 IDC와 거의 같았습니다. 비용 절감보다 재사용 가능한 운영 절차, 글로벌 공통 기반과 자원 조정 가능성을 확보한 사례입니다.

## 왜 읽을까

마이그레이션을 인프라 복제가 아닌 의존성 분석·데이터 정합성·운영 절차의 설계 문제로 바라보게 합니다. 특히 코드가 동일해도 네트워크 거리가 달라지면 실행 시간이 급증하고, 데이터 이전만으로 배치·권한·연계가 복구되지 않는다는 점이 실무적입니다.

**프로젝트에 적용 — PawCycle**

- [ ] OCI 대체 배포를 가정해 DB·배치·비밀·DNS·외부 연동 의존성 목록을 작성합니다.
- [ ] 전환 전후 데이터 건수·핵심 API·배치 소요 시간 검증표를 만듭니다.
- [ ] 롤백 가능한 시점, 데이터 쓰기 시작 이후의 복구 방법과 Go/No-Go 기준을 분리합니다.
