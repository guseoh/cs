# Hexagonal Architecture, 진짜 하실 건가요?

> [!abstract] 한 줄 정리
> 아키텍처는 도메인을 보호할 때 가치가 있다. 외부 API 계약이 이미 변경을 흡수하는 서비스에서는 과도한 Port·Adapter·멀티모듈이 오히려 변경 비용을 키울 수 있다.

> 카카오페이 기술 블로그 · 2025-01-21

## 핵심 내용

헥사고날 아키텍처를 도입했다고 해서 모든 팀에서 Port/Adapter의 수가 줄거나 변경이 쉬워지는 것은 아니다. 카카오페이 홈 서버는 약 24개 연동 서비스와 평균 50회 API 호출을 통해 화면 데이터를 구성하므로, 외부 시스템 변경을 보호하려는 동기가 분명했다. 하지만 연동 팀들과 공통 API 규격을 합의하는 작업이 이미 외부 변경을 흡수하는 역할을 맡고 있었다.

Out Port마다 외부 API 인터페이스를 정의하고 여러 모듈로 계층을 나누자 실제 보호 효과보다 DTO 변환과 파일 이동이 늘어났다. 40개가 넘는 Port를 관리하는 데 비용이 들었지만 독립적인 핵심 도메인 모델은 명확하지 않았다. 결국 외부 계약과 내부 화면 DTO를 구분하는 책임만 유지하면서 단일 모듈·관심사별 패키징으로 돌아왔다.

| 설계 선택 | 예상 이점 | 실제 관찰·판단 |
| --- | --- | --- |
| Hexagonal + 멀티모듈 | 외부 API 변경 격리 | 이미 표준 API 계약으로 일부 격리 |
| 40개+ Out Port | 의존 역전 | DTO 변환과 탐색 비용 증가 |
| 단일 모듈로 복귀 | 사용되는 경계만 유지 | 8,000줄+ 변경/삭제 |
| DTO 경계 유지 | 외부 응답 영향 차단 | 보호 효과가 실제 존재하므로 보존 |

*이 사례는 헥사고날 아키텍처 일반의 실패가 아니라 적용 대상의 도메인 성질과 중복된 보호 계층에 대한 판단이다.*

이 과정에서 PR 기준 8,000줄 이상의 코드를 줄였지만 삭제한 줄 수 자체가 품질 지표는 아니다. 외부 시스템을 교체할 가능성, 비즈니스 규칙의 독립성, 테스트 대역의 필요성, 변경 전파 범위를 기준으로 Port가 실제 값을 만드는지 검토해야 한다. 모델 경계가 분명하지 않은 BFF/집계 시스템에서는 공통화된 외부 API 계약과 명료한 패키징만으로 충분할 수 있다.

## 왜 읽을까

Hexagonal Architecture를 적용할지 결정할 때, '패턴을 구현할 수 있는가'가 아니라 '보호할 코어가 명확한가, 외부 계약이 이미 충분한가, 변경 비용이 줄어드는가'를 먼저 묻게 하는 실전 사례다. 설계의 일부 원칙은 남기고 과도한 구조만 제거한 점도 중요하다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집글·지원서처럼 규칙이 풍부한 도메인과 단순 외부 응답 조합 기능을 구분한다.
- [ ] Port/Adapter를 추가하기 전에 실제로 변경 가능성이 높은 외부 의존성과 테스트 대체 필요성을 적는다.
- [ ] 불필요한 DTO 매핑은 줄이되 외부 API DTO와 사용자에게 노출하는 응답 DTO의 경계는 유지한다.
