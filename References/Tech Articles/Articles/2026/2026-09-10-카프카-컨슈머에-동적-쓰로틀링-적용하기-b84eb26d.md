# 카프카 컨슈머에 동적 쓰로틀링 적용하기

> [!abstract] 한 줄 정리
> Kafka lag을 줄이려고 컨슈머만 늘리면 병목이 DB로 이동할 수 있으므로, 처리량 상한을 다운스트림 자원에 맞춰 동적으로 조절하고 불필요한 리밸런싱을 피하는 제어가 필요하다.

> 우아한형제들 기술블로그 · 2025-01-09

## 핵심 내용

- **문제:** lag을 빠르게 해소하려고 consumer를 늘리자 downstream DB가 병목이 됐고, 실제 운영에서 master DB CPU가 80%를 넘는 알람이 발생했다.
- **접근:** consumer 수를 계속 바꾸는 대신 downstream CPU 지표를 기준으로 delay를 계산해 동적으로 throttling하는 구조를 도입했다.
- **주의점:** 단순 `Thread.sleep`은 처리 스레드를 쉬게 하지만 poll 간격이 길어져 `max.poll.interval.ms`를 넘으면 rebalance가 발생할 수 있다.
- **구조:** `MessageListenerContainer`의 pause/resume은 pause 중에도 poll을 유지해 rebalance를 피할 수 있고, concurrency가 여러 개면 실제 partition을 가진 내부 container 단위로 제어해야 한다.
- **트레이드오프:** Record listener에서는 이미 poll된 batch 때문에 pause 시점이 정밀하지 않고 반복 pause가 생길 수 있어 Batch listener 또는 commit 시점의 ConsumerInterceptor 같은 대안과 AckMode 조건을 함께 검토해야 한다.

## 왜 읽을까

Kafka 성능 문제를 consumer 수만의 문제로 보지 않고 DB·외부 API 같은 downstream의 실제 처리 한계를 기준으로 바라보게 해준다. 처리량을 늘리는 것보다 시스템 전체가 감당 가능한 속도로 흐르게 만드는 backpressure 관점을 익히기 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] Kafka backlog가 생겼을 때 consumer scale-out 전에 DB CPU·connection pool·처리 지연을 함께 측정한다.
- [ ] downstream 포화가 확인되면 lag과 DB 자원을 동시에 관찰하는 throttling 실험을 설계한다.
- [ ] `sleep`과 pause/resume 방식의 rebalance·처리량 차이를 부하 테스트로 비교한다.
