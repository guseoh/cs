# 카프카 컨슈머에 동적 쓰로틀링 적용하기

> [!abstract] 한 줄 정리
> Kafka lag을 줄이려고 컨슈머만 늘리면 병목이 DB로 이동할 수 있으므로, 처리량 상한을 다운스트림 자원에 맞춰 동적으로 조절하고 불필요한 리밸런싱을 피하는 제어가 필요하다.

> 우아한형제들 기술블로그 · 2025-01-09

## 핵심 내용

Kafka Consumer Lag을 줄이려 컨슈머를 늘리면 병목이 사라질 것처럼 보이지만, 처리 결과를 쓰는 DB의 용량은 그대로여서 오히려 Master CPU가 80%를 넘을 수 있다. 우아한형제들은 컨슈머 자체의 처리 속도보다 downstream의 실제 부하를 제어 신호로 삼는 동적 쓰로틀링을 적용했다.

 ```mermaid
flowchart LR
 A[Kafka Lag 증가] --> B[Consumer 처리]
 B --> C[Downstream DB CPU 관측]
 C --> D{CPU 임계 초과?}
 D -- 예 --> E[Container pause·처리량 제한]
 D -- 아니오 --> F[resume·점진 처리]
 E --> C
 F --> B
```

*원문 근거를 바탕으로 자체 재구성한 가로형 학습 도식이다.*

DB CPU를 관측해 허용된 처리 속도를 계산하고 Consumer를 잠시 늦추는 방식이지만, 단순 `Thread.sleep`으로 폴링 사이 시간을 늘리면 `max.poll.interval.ms`를 넘겨 그룹 리밸런싱이 발생할 수 있다. Spring Kafka `MessageListenerContainer`의 `pause/resume`은 일시 중지 중에도 poll을 유지해 그룹 소속을 관리할 수 있다. Concurrency가 여럿일 때는 실제 파티션을 보유한 내부 Container 단위로 제어해야 과도하게 많은 파티션을 동시에 멈추지 않는다.

| 제어 방법 | 기대 효과 | 주의할 실패 |
| --- | --- | --- |
| Consumer 증설 | Lag 해소 | DB CPU 80%+ 부하 전파 |
| Thread.sleep | 단순 지연 | poll 간격 초과·리밸런싱 |
| pause/resume | poll 유지·부하 제어 | 이미 fetch된 배치 처리 |
| 내부 Container 제어 | 실제 파티션별 조절 | Concurrency와 AckMode 고려 |

Record Listener에서는 pause 전에 이미 poll한 레코드가 남기 때문에 제어 효과가 즉시 나타나지 않을 수 있다. Batch Listener로 처리 단위를 바꾸거나 AckMode와 커밋 시점에 맞춘 ConsumerInterceptor를 검토한 이유다. 쓰로틀링은 Lag 회복 속도를 늦추는 대신 원본 DB 가용성을 보호하는 결정이므로 CPU·Lag·처리 지연 세 지표를 함께 운영해야 한다.

## 왜 읽을까

Kafka 성능 문제를 consumer 수만의 문제로 보지 않고 DB·외부 API 같은 downstream의 실제 처리 한계를 기준으로 바라보게 해준다. 처리량을 늘리는 것보다 시스템 전체가 감당 가능한 속도로 흐르게 만드는 backpressure 관점을 익히기 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] Kafka backlog가 생겼을 때 consumer scale-out 전에 DB CPU·connection pool·처리 지연을 함께 측정한다.
- [ ] downstream 포화가 확인되면 lag과 DB 자원을 동시에 관찰하는 throttling 실험을 설계한다.
- [ ] `sleep`과 pause/resume 방식의 rebalance·처리량 차이를 부하 테스트로 비교한다.
