# 주니어 서버 개발자가 유저향 서비스를 개발하며 마주쳤던 이슈와 해결 방안

> [!abstract] 한 줄 정리
> 중복 요청과 동시성 문제는 프론트 방어만 믿지 말고 서버에서 DB 제약, 멱등성, 필요 시 락을 서로 다른 역할로 설계해야 합니다.

> tech.kakaopay.com

## 핵심 내용

카카오페이 혜택 서비스를 개발하며 동시성, DB 성능, 멱등성 문제를 해결한 경험입니다. 중복 클릭으로 리워드가 여러 번 지급될 수 있어 Redis 분산 락을 적용하고 트랜잭션 범위를 조정하며, 외부 시스템 호출 성공 여부를 이력으로 남겨 동일 요청에는 다시 호출하지 않는 방식으로 멱등성을 보장합니다. 프론트 디바운스가 있어도 서버에서 중복 요청을 방어해야 한다는 점을 강조합니다.

중복 클릭을 막는 프런트엔드 디바운스는 사용자 경험 개선이지 결제·리워드 정합성의 최종 방어선이 아니다. 서버 인스턴스가 여러 대라면 같은 사용자에 대한 요청을 서로 다른 서버가 동시에 처리할 수 있으므로 **동일 업무 식별자**, 지급 이력의 유일성, 상태 전이 및 동시 실행 제어를 각각 점검해야 한다. Redis 락이 풀린 뒤 동일 요청이 재전송되는 상황까지 막으려면 락 외에 멱등성 기록과 DB 제약이 필요하다.

| 보호할 위험 | 보완 수단 | 검증할 상황 |
| --- | --- | --- |
| 사용자의 연속 클릭 | 프런트 방어 | 이중 요청 발생 자체는 가정 |
| 동일 리워드의 동시 지급 | 분산 락·원자적 상태 변경 | 서버 여러 대에서 동시 요청 |
| 네트워크 타임아웃 뒤 재시도 | 지급 이력·멱등 키 | 이전 호출의 성공 여부 불확실 |
| 상태 저장 도중 장애 | DB 트랜잭션·제약 | 절반만 처리되는지 확인 |

락을 획득했다는 사실과 외부 시스템에서 지급이 최종 확정되었다는 사실은 같지 않으므로 실패·재시도 시나리오를 별도로 검증해야 한다.

## 왜 읽을까

주니어 백엔드 개발자가 실제 서비스에서 만나기 쉬운 락, 트랜잭션, 멱등성을 한 글에서 서로 다른 문제로 구분해 볼 수 있습니다.
