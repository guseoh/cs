# es-toolkit, 사내 작은 라이브러리가 전세계적인 라이브러리가 되기까지

> [!abstract] 한 줄 정리
> 사내 유틸리티를 오픈소스로 키운 과정에서, 성능·호환성·마이그레이션 비용을 함께 설계해야 실제 생태계 채택이 일어난다는 점을 보여줍니다.

> Toss Tech · 2026-06-22

## 핵심 내용

lodash 계열은 오래된 브라우저 대응과 비효율적 구현, ESM 미지원 등으로 현대 프런트엔드 환경에서 성능·번들 크기 비용이 컸습니다. 핵심 함수는 최소 2배에서 최대 10배 이상 빨라졌고, 일부 함수는 번들 크기가 30배 이상 줄었습니다.

단순 대체를 강요하지 않고 `es-toolkit/compat`를 둬 기존 lodash 코드의 import만 바꿔 점진적으로 옮길 수 있게 했습니다. 모든 edge case를 그대로 지원하면 현대화 이점이 줄고, 호환성을 버리면 채택 비용이 커지므로 호환 레이어와 본체를 분리했습니다.

주간 2천만 회 이상 다운로드되고 Yarn·Recharts 같은 라이브러리에서도 사용되는 수준으로 확장됐습니다.

라이브러리를 빠르게 만드는 것과 생태계에서 채택하게 하는 일은 별도 과제다. `es-toolkit/compat`는 기존 lodash 호출 표면을 유지하는 이행 경로를 제공하고, 새 API는 현대 JavaScript 환경에 맞춰 경량화한다. 이중 경로는 호환성 비용을 명시적으로 격리함으로써 기존 코드 전체를 한 번에 교체하지 않아도 최적화를 시작할 수 있게 한다.

성능 배수는 함수 종류와 입력 크기에 따라 달라지고, bundle 크기 절감도 실제 tree-shaking 조건에 좌우된다. 따라서 모든 함수가 일괄적으로 10배 빨라진다는 식으로 읽지 않고 원문의 개별 벤치마크 조건을 기준으로 판단해야 한다.

## 왜 읽을까

좋은 라이브러리를 만드는 것과 실제로 채택되게 만드는 것은 다른 문제라는 점이 잘 드러납니다. API 호환성, 마이그레이션 경로, 성능 측정, 커뮤니티 피드백을 하나의 제품 설계 문제로 볼 수 있습니다.

**프로젝트에 적용 — 공통**

- [ ] 공통 유틸이나 라이브러리를 만들 때 성능보다 먼저 실제 교체 비용을 확인하기
- [ ] 기존 코드와의 호환 경로가 필요한지 별도 어댑터·compat 계층 검토하기
- [ ] 추상적인 장점보다 Before/After 수치로 도입 근거 남기기
