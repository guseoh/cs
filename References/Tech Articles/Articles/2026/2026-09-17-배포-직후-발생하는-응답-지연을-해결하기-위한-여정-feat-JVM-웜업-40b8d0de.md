# 배포 직후 발생하는 응답 지연을 해결하기 위한 여정 (feat. JVM 웜업)

> [!abstract] 한 줄 정리
> 배포 직후의 DB Connection Timeout을 커넥션 부족으로 단정하지 않고, 설정 변경과 점진 배포 실험을 거쳐 JVM 초기 실행 비용이 커넥션 점유 시간을 늘리는 진짜 병목임을 추적한 사례다.

> 카카오페이 기술 블로그 · 2026-02-25

## 핵심 내용

- **문제:** 새 파드에 트래픽이 들어오는 순간 HikariCP 커넥션 30개가 모두 Active가 되고, 요청은 최대 10초를 기다린 뒤 Timeout이 발생했다.
- **접근:** `maximumPoolSize`를 30→50으로 늘려도 50개가 모두 사용됐고, 안정화 후에는 약 20개만으로 충분했다. 커넥션 수 자체가 근본 원인이 아니라는 가설로 전환했다.
- **접근:** 블루/그린 배포에서 새 파드에 30초마다 20%씩 트래픽을 흘려 일시적으로 완화했지만, 서비스 성장 후 같은 지연이 다시 나타나 근본 해결책이 아님을 확인했다.
- **수치:** 배포 직후 Connection Usage Time은 최대 1~1.5초, Acquire Time은 5~10초까지 증가했다. 안정 상태에서는 각각 약 3~5ms 이하, 1ms 이하였고 DB 쿼리 응답 시간 자체는 평소와 같았다.
- **결과:** JVM의 지연 클래스 로딩·초기 실행 비용이 사용자 요청과 겹치는 구간을 웜업으로 앞당겨 초기 성능 저하를 해결했다. 에러가 발생한 계층과 병목의 원인이 존재하는 계층이 다를 수 있음을 보여준다.

## 왜 읽을까

`Connection Timeout → 풀 크기 증가`처럼 증상에 바로 설정을 대응하지 않고, 실패한 가설도 측정 결과로 폐기하면서 원인을 좁혀가는 과정이 좋다. HikariCP 메트릭과 JVM 런타임 동작을 연결해 보는 실전 트러블슈팅 사례로 다시 볼 가치가 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 배포 직후와 안정화 후의 p95/p99 응답 시간, HikariCP usage/acquire time을 분리해 측정한다.
- [ ] Connection Timeout이 생기면 pool size부터 키우지 않고 DB query latency와 connection hold time을 함께 비교한다.
- [ ] 실제 cold-start 지연이 재현될 때만 warm-up이나 점진 트래픽 전환을 후보로 검증한다.
