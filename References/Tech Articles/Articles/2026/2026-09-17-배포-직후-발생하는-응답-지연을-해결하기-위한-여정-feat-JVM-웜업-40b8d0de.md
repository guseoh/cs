# 배포 직후 발생하는 응답 지연을 해결하기 위한 여정 (feat. JVM 웜업)

> [!abstract] 한 줄 정리
> 배포 직후의 DB Connection Timeout을 커넥션 부족으로 단정하지 않고, 설정 변경과 점진 배포 실험을 거쳐 JVM 초기 실행 비용이 커넥션 점유 시간을 늘리는 진짜 병목임을 추적한 사례다.

> 카카오페이 기술 블로그 · 2026-02-25

## 핵심 내용

새 Pod가 Ready로 판정된 뒤 첫 사용자 요청이 들어오면 HikariCP의 커넥션이 모두 Active가 되고 최대 10초 뒤 Timeout이 났다. 카카오페이는 풀 크기를 30→50으로 늘려도 50개가 모두 사용되고, 안정화 후에는 20개 이하로 충분하다는 현상을 보고 커넥션 부족을 근본 원인으로 단정하지 않았다.

블루/그린 배포에서 30초마다 20%의 트래픽을 흘려보내면 일시적으로 나아졌지만 서비스 성장 후 다시 재발했다. HikariCP의 Connection Usage Time이 배포 직후 1~1.5초(안정 시 3~5ms 이하), Acquire Time은 5~10초(안정 시 1ms 이하)로 증가했지만 DB 쿼리 응답 자체는 정상이라 애플리케이션의 초기 클래스 로딩·JIT 준비가 커넥션 보유 시간을 늘린다고 판단했다.

| 지표/시도 | 배포 직후 | 안정화 후/판단 |
| --- | --- | --- |
| Hikari Pool | 30→50 모두 소진 | 약 20개면 충분 |
| Usage Time | 1~1.5초 | 3~5ms 이하 |
| Acquire Time | 5~10초 | 1ms 이하 |
| 점진 트래픽 | 30초당 +20% | 임시 효과, 성장 뒤 재발 |
| 웜업+startupProbe | 실제 요청 전 초기 실행 | 초반 사용자 지연 완화 |

사용자 트래픽이 들어오기 전에 ApplicationRunner에서 핵심 경로를 미리 호출해 JVM을 웜업하고 startupProbe가 완료 상태를 확인하도록 했다. 실제 초기화가 끝나기 전에는 readiness를 열지 않아 첫 사용자 요청이 JVM의 초기 비용을 대신 부담하지 않게 했다. 웜업 자체도 CPU·DB에 부하를 만들 수 있으므로 더미 요청이 외부 부작용을 발생시키지 않도록 분리해야 한다.

## 왜 읽을까

`Connection Timeout → 풀 크기 증가`처럼 증상에 바로 설정을 대응하지 않고, 실패한 가설도 측정 결과로 폐기하면서 원인을 좁혀가는 과정이 좋다. HikariCP 메트릭과 JVM 런타임 동작을 연결해 보는 실전 트러블슈팅 사례로 다시 볼 가치가 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 배포 직후와 안정화 후의 p95/p99 응답 시간, HikariCP usage/acquire time을 분리해 측정한다.
- [ ] Connection Timeout이 생기면 pool size부터 키우지 않고 DB query latency와 connection hold time을 함께 비교한다.
- [ ] 실제 cold-start 지연이 재현될 때만 warm-up이나 점진 트래픽 전환을 후보로 검증한다.
