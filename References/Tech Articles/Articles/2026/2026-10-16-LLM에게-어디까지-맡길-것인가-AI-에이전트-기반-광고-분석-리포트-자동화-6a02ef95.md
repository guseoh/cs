# LLM에게 어디까지 맡길 것인가: AI 에이전트 기반 광고 분석 리포트 자동화

> [!abstract] 한 줄 정리
> 숫자 계산과 정합성 검증은 결정적 코드에 맡기고, LLM에는 검증된 사실의 해석과 설명을 맡겨야 운영 가능한 자동 리포트를 만들 수 있다. 에이전트가 탐색한 결과도 근거 등급을 매긴 뒤에만 원인으로 채택한다.

> LY Corporation Tech Blog · 2026-09-18

## 핵심 내용

광고 매출 리포트를 하나의 LLM 프롬프트에서 계산부터 해설까지 모두 생성하게 하면 DoD·MoM·YoY 비교와 반올림 결과가 흔들리거나 중요한 기여 항목이 빠질 수 있다. LY는 숫자의 계산 책임을 코드에 맡기고 모델은 확인된 수치의 설명을 담당하도록 분석 파이프라인의 경계를 재설계했다.

상위 KPI와 매출 기여도는 Spark의 사전 집계와 결정적 계산으로 구한 뒤 중요한 원인 후보를 선정한다. 원인 탐색이 꼭 필요할 때만 에이전트가 Trino를 조회하고, 접근할 수 있는 상품·업종·광고주의 관계를 그래프로 제한했다. 무한 분석 반복이나 같은 도구 호출을 줄이기 위해 턴·시간·중복 호출의 제한을 두고, 보고서의 각 섹션은 병렬로 생성하되 실패한 섹션만 재작성한다.

| 단계 | 맡기는 책임 | 자동 검증 기준 |
| --- | --- | --- |
| Spark·코드 | KPI·기여도 계산 | 동일 입력의 결정적 결과 |
| Trino 에이전트 | 부족한 원인 근거 탐색 | 승인된 데이터 관계·호출 한도 |
| LLM 섹션 생성 | 구조화된 결과 설명 | 숫자 변조 금지·근거 상태 표시 |
| 후처리 검증 | 반올림·형식·누락 검사 | 코드 규칙 + 사람 평가 |

*상관관계를 인과관계로 과장하지 않도록 근거의 강도를 구분하는 것이 설계 핵심이다.*

생성된 설명은 매출 변동의 일부와 함께 움직였다는 사실만으로 원인이라고 확정하지 않는다. 원문은 근거를 `driver_eligible`, `caution_only`, `monitoring_signal`로 구분했고, 숫자·형식은 규칙 검사로, 실제 인과 설명과 업무 유용성은 사람과 LLM 평가로 확인했다. Langfuse 추적에는 코드·모델·프롬프트 설정·도구 호출 버전을 연결한다. 공개한 금액 예시는 가상값이며 전체 비용·시간 절감의 검증 수치는 없다.

## 왜 읽을까

생성형 AI로 보고서를 만들 때 ‘숫자가 맞는가’와 ‘설명이 설득력 있는가’를 분리해야 하는 이유가 선명하다. 프롬프트만 고치지 않고 계산, 탐색, 검증, 평가의 책임 경계를 재설계하는 과정이 특히 유용하다.

**프로젝트에 적용 — PawCycle**

- [ ] 기존 부하 테스트나 운영 로그에서 응답시간·오류율·처리량을 코드로 먼저 집계하고 측정 조건을 함께 저장한다.
- [ ] AI로 분석 요약을 생성한다면 원본 측정값을 수정하지 못하게 하고, 추정 원인과 확인된 원인을 구분한다.
- [ ] 리포트의 수치 일치·누락·원인 단정 여부를 검증하는 체크리스트를 만든다.
