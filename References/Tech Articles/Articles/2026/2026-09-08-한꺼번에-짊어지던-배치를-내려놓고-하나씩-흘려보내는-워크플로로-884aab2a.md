# 한꺼번에 짊어지던 배치를 내려놓고, 하나씩 흘려보내는 워크플로로

> [!abstract] 한 줄 정리
> 주기적으로 전체 대상을 훑는 배치를 주문별 durable workflow로 바꾸면 시간 기반 비즈니스 흐름을 코드 한곳에 모으고, 대기 중 리소스 점유와 피크타임 전체 스캔 부담을 줄일 수 있다.

> 우아한형제들 기술블로그 · 2026-09-08

## 핵심 내용

- **문제:** 미접수 주문 알림처럼 몇 분 뒤 처리해야 하는 로직을 배치로 수행하자 비즈니스 흐름이 여러 모듈에 흩어지고, 1분 cron 기준 최대 59초 오차가 생기며, 피크타임에는 한 번에 조회·처리할 대상이 급증했다.
- **트레이드오프:** Temporal은 필요한 기능을 제공하지만 deterministic replay 학습 비용, 별도 클러스터·DB 운영, 엔진 내부 장애 대응, SDK·실행 모델 종속성이 부담이었다. 팀은 필요한 primitive만 가진 자체 라이브러리 `Flowkit`을 만들었다.
- **구조:** `Workflow`, `Activity`, `Signal`, `Scheduler` 네 개 개념으로 구성하고, `await`에서 상태를 DocumentDB에 체크포인트한 뒤 코루틴을 종료한다. 타이머나 Signal이 오면 처음부터 replay하되 이미 끝난 Activity·await 결과는 캐시해 외부 호출을 반복하지 않는다.
- **주의점:** Temporal은 Activity 완료마다 결과를 즉시 영속화하지만 Flowkit은 기본적으로 `await`·완료·실패 시점에 체크포인트한다. 구조는 단순해지지만 크래시 시 Activity 재실행 가능성과 멱등성 설계를 더 신경 써야 한다.
- **결과:** 주문 1건을 워크플로 1개로 표현해 대기 중 스레드와 메모리를 점유하지 않고, 전체 후보를 매번 재스캔하지 않으며, 흐름과 진행 상태를 한 워크플로와 한 인스턴스 문서에서 추적할 수 있게 했다.

## 왜 읽을까

Temporal 같은 정답 기술을 바로 도입하지 않고, **필요한 보장과 감당할 운영 비용을 먼저 분해한 뒤 더 작은 실행 모델을 선택하는 과정**이 잘 드러난다. 배치, 상태 머신, replay, 멱등성, Saga를 하나의 실제 문제에서 연결해 볼 수 있다는 점도 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] 정기배송·주문 후처리 중 `몇 분/몇 시간 뒤 상태를 다시 확인하는` 배치 후보를 먼저 식별한다.
- [ ] 현재 배치의 대상 수, 실행 시간, DB 조회량, 시간 오차를 측정한 뒤 워크플로 전환 필요성을 판단한다.
- [ ] 워크플로를 실험한다면 Activity 단위 멱등성과 크래시 재실행 조건을 먼저 테스트한다.
