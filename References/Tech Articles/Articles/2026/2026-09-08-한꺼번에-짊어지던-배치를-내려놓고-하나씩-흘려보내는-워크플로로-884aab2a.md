# 한꺼번에 짊어지던 배치를 내려놓고, 하나씩 흘려보내는 워크플로로

> [!abstract] 한 줄 정리
> 주기적으로 전체 대상을 훑는 배치를 주문별 durable workflow로 바꾸면 시간 기반 비즈니스 흐름을 코드 한곳에 모으고, 대기 중 리소스 점유와 피크타임 전체 스캔 부담을 줄일 수 있다.

> 우아한형제들 기술블로그 · 2026-09-08

## 핵심 내용

미접수 주문 알림처럼 특정 주문을 몇 분 후 처리해야 하는 작업을 1분 Cron 기반 대형 배치에서 모두 조회하면 최대 약 59초의 시각 오차가 생기고 피크에 조회 대상이 한꺼번에 몰린다. 우아한형제들은 주문 하나를 독립적인 Workflow로 표현해 긴 대기 중에 스레드와 메모리를 계속 점유하지 않도록 바꿨다.

 ```mermaid
flowchart LR
 A[주문별 Workflow 시작] --> B[Activity 실행]
 B --> C[await·DocumentDB 체크포인트]
 C --> D[메모리에서 코루틴 종료]
 E[Timer·Signal 도착] --> F[Workflow Replay]
 F --> G[완료 Activity 결과 재사용]
 G --> H[다음 단계 실행]
```

*원문 근거를 바탕으로 자체 재구성한 가로형 학습 도식이다.*

Temporal은 필요한 기능을 제공했지만 결정적 Replay의 학습 비용, 별도 클러스터·DB 운영과 엔진 종속성이 부담이어서 필요한 개념만 담은 Flowkit을 만들었다. Workflow·Activity·Signal·Scheduler가 핵심이며 Kotlin Coroutine이 `await` 지점에서 상태를 Reactive DocumentDB에 체크포인트한 뒤 실행을 종료한다. Timer나 Signal이 도착하면 Workflow의 코드는 처음부터 다시 실행되지만 완료된 Activity/await 결과는 저장된 상태를 재사용해 외부 효과를 반복하지 않도록 한다.

```kotlin
// Flowkit의 대기·복구 원리를 설명하는 학습용 의사 코드
workflow("order-42") {
    val order = activity("loadOrder") { loadOrder() }
    await("notifyAt", order.deadline)
    activity("notify") { notifyCustomer(order.id) }
}
```

*원문 Flowkit의 실제 API 서명이 아니라 Activity/await 체크포인트 경계를 보여 주는 예시다.*

| 요소 | Flowkit | Temporal과의 차이 |
| --- | --- | --- |
| 대기 | await에서 코루틴 종료 | Workflow 상태 재구성 원리는 유사 |
| 영속화 | await/완료/실패 기본 체크포인트 | Activity 결과 이벤트별 기록 범위 다름 |
| 복구 | 처음부터 Replay·결과 캐시 | 중간 Activity 재실행 가능성 |
| 운영 | 별도 엔진 최소화 | 인프라 단순성 대신 직접 책임 |

다만 Flowkit은 Temporal처럼 Activity 완료마다 결과를 즉시 영속화하지 않고 기본적으로 `await`·완료·실패 시점에 체크포인트한다. 따라서 Activity 성공 직후 체크포인트 전에 프로세스가 죽으면 동일 외부 작업이 다시 수행될 수 있어 멱등성 키와 재실행 가능한 작업 설계가 중요하다. 자체 엔진은 단순함을 얻는 대신 복구 의미와 보존 기간을 직접 운영해야 한다.

## 왜 읽을까

Temporal 같은 정답 기술을 바로 도입하지 않고, **필요한 보장과 감당할 운영 비용을 먼저 분해한 뒤 더 작은 실행 모델을 선택하는 과정**이 잘 드러난다. 배치, 상태 머신, replay, 멱등성, Saga를 하나의 실제 문제에서 연결해 볼 수 있다는 점도 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] 정기배송·주문 후처리 중 `몇 분/몇 시간 뒤 상태를 다시 확인하는` 배치 후보를 먼저 식별한다.
- [ ] 현재 배치의 대상 수, 실행 시간, DB 조회량, 시간 오차를 측정한 뒤 워크플로 전환 필요성을 판단한다.
- [ ] 워크플로를 실험한다면 Activity 단위 멱등성과 크래시 재실행 조건을 먼저 테스트한다.
