# toodoori와 AI

> [!abstract] 한 줄 정리
> AI 코딩으로 구현 속도가 빨라져도 제품 방향과 코드 경계, 비즈니스 규칙의 검증은 사람이 책임져야 한다. 규칙을 문서와 테스트로 고정해야 장기적으로 유지 가능한 프로젝트가 된다.

> 이문기 개인 Medium 개발 블로그 · 2026-02-08

## 핵심 내용

- **배경:** 개인용 칸반 앱을 2025년 10월부터 AI와 개발해 2026년 1월 18일 첫 사용을 시작했다. 초기에는 로그인·회원가입을 1시간 이내에 구현할 만큼 빠르게 진행했다.
- **문제:** 기능이 늘자 버그와 장문의 코드가 증가했다. 일부 페이지는 약 2,000줄에 달해 개발자와 AI 모두 코드 이해 비용이 커졌다.
- **접근:** 서비스 철학·용어·필수 기능을 먼저 문서화하고, FE·BE·Infra 책임을 분리했다. BE가 API 명세를 만들면 FE가 참조하는 협업 방식도 적용했다.
- **검증:** 비즈니스 규칙은 주석보다 테스트로 강제하고, 단위·API E2E·DB 마이그레이션 테스트를 구분했다. Docker의 PostgreSQL과 MinIO로 격리 테스트 환경을 만들었다.
- **주의점:** DB 마이그레이션에서 약 3시간 시행착오를 겪은 후 현재 스키마 재현, dry-run, 실제 적용, 제약조건 확인, 롤백을 로컬에서 검증하도록 했다. AI가 작성한 법률 문서에 대한 모델 간 검토는 전문 법률 검토와 동일하지 않다.

## 왜 읽을까

AI로 개인 프로젝트를 빠르게 시작한 뒤 구조와 품질 문제가 누적되는 과정을 솔직하게 기록했다. 개발 속도보다 변경 가능성과 검증 가능성을 유지하는 편이 장기적으로 더 중요하다는 점을 구체적인 코드 규모와 테스트 절차로 이해할 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 회원·모집글·지원서의 핵심 규칙을 문서와 테스트에 각각 명시한다.
- [ ] FE·BE 책임 경계와 API 계약을 정해 AI가 임의로 구현을 뒤섞지 않도록 한다.
- [ ] DB 스키마 변경은 운영 적용 전에 독립 DB에서 적용·제약조건·복구 가능성을 확인한다.
