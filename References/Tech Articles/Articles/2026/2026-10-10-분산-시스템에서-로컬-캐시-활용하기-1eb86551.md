# 분산 시스템에서 로컬 캐시 활용하기

> [!abstract] 한 줄 정리
> 변경이 드문 조회용 메타데이터는 서버별 로컬 캐시로 빠르게 제공하고, 변경 이벤트로 캐시를 무효화할 수 있다. 다만 Redis Pub/Sub은 메시지 유실 가능성이 있으므로 강한 정합성이 필요한 데이터에 그대로 적용하면 안 된다.

> 카카오페이 기술 블로그 · 2025-01-16

## 핵심 내용

- **문제:** 통신 상품·혜택 같은 메타데이터를 반복해서 DB에서 조회하면 비용이 발생하지만, 서버별 로컬 캐시는 변경 시 데이터가 일시적으로 달라질 수 있다.
- **설계:** 변경이 적고 최종적 일관성을 허용하는 데이터는 로컬 캐시, 세션처럼 공유·변경이 잦은 데이터는 Redis 캐시로 구분하고 CacheManager에서 처리한다.
- **구조:** MongoDB 메타데이터 저장 후 Redis Pub/Sub에 변경 이벤트를 발행하고, 각 서버의 구독자가 해당 키의 로컬 캐시를 evict해 다음 조회에서 DB 값을 다시 읽도록 한다.
- **트레이드오프:** 기본 TTL은 1시간이다. Pub/Sub 알림을 놓치면 만료 전까지 오래된 값이 남을 수 있어, 유실이 치명적인 경우 Redis Streams나 ACK가 있는 메시징 시스템을 고려해야 한다.
- **결과:** 캐시 조회 경로와 무효화 구현 코드를 제시하지만, 실제 응답시간·DB 부하의 Before/After 수치는 공개하지 않았다.

## 왜 읽을까

'Redis를 쓸까, 로컬 캐시를 쓸까'보다 먼저 어떤 데이터의 불일치를 얼마 동안 허용할 수 있는지 결정해야 한다는 관점을 준다. 빠른 조회와 정합성·운영 복잡도의 교환 관계를 코드 수준에서 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 브랜드·카테고리처럼 변경 빈도가 낮은 읽기 데이터와 가격·재고처럼 최신성이 중요한 데이터를 분류한다.
- [ ] 로컬 캐시 도입 전에 허용 가능한 오래된 데이터의 지속 시간과 TTL을 정의한다.
- [ ] 캐시 무효화 이벤트 유실과 서버 재시작 상황을 테스트하고, 캐시 적중률과 DB 조회량을 전후 비교한다.
