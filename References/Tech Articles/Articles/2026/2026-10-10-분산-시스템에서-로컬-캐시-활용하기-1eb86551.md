# 분산 시스템에서 로컬 캐시 활용하기

> [!abstract] 한 줄 정리
> 변경이 드문 조회용 메타데이터는 서버별 로컬 캐시로 빠르게 제공하고, 변경 이벤트로 캐시를 무효화할 수 있다. 다만 Redis Pub/Sub은 메시지 유실 가능성이 있으므로 강한 정합성이 필요한 데이터에 그대로 적용하면 안 된다.

> 카카오페이 기술 블로그 · 2025-01-16

## 핵심 내용

상품·혜택 메타데이터를 조회할 때마다 MongoDB에 접근하면 불필요한 비용이 발생하지만, 서버별로 로컬 캐시를 사용하면 다른 서버에서 업데이트된 사실을 알지 못해 값이 달라질 수 있다. 카카오페이는 변경이 적고 최종 일관성을 허용하는 값과 세션처럼 공유되어야 하는 값의 캐시 저장소를 다르게 선택했다.

![메타데이터 관리자 서버에서 PubSub 채널을 통해 여러 API 서버의 로컬 캐시를 무효화하는 구조](https://tech.kakaopay.com/_astro/messagesystem.Cs0iqaiY_Z1YuE0X.webp)

*그림 1. 원문 로컬 캐시 무효화 구조: DB 변경 이후 Pub/Sub로 각 서버에 키 변경을 알린다 — [출처: 원문 기술 블로그](https://tech.kakaopay.com/post/local-caching-in-distributed-systems/)*

메타데이터는 각 인스턴스 로컬 캐시에서 먼저 조회하고 미스 시 MongoDB를 조회하도록 `MetaService`를 구성했다. 관리 서버에서 데이터를 변경한 뒤 Redis Pub/Sub에 어떤 키가 변경됐는지 통지하면 모든 애플리케이션 인스턴스의 구독자가 해당 키를 evict한다. 이후 첫 요청은 DB에서 새 값을 읽어 로컬 캐시에 채운다. 따라서 이 설계의 중심은 업데이트된 객체 전체를 여러 서버에 즉시 복제하는 것이 아니라 **서버별 오래된 사본의 무효화**에 있다.

| 저장소·동기화 | 적합한 상황 | 데이터 불일치 조건 |
| --- | --- | --- |
| 서버 로컬 캐시 | 변경 적은 메타데이터 | 서버별 값이 다를 수 있음 |
| 공용 Redis 캐시 | 여러 서버의 즉시 공유 필요 | 네트워크 호출·운영 비용 |
| Redis Pub/Sub Evict | 변경 이벤트를 빠르게 전달 | 구독 중단 시 알림 유실 |
| TTL 1시간 | 영구적인 오래된 캐시 방지 | TTL 만료 이전까지는 오염 가능 |

원문 구현의 기본 TTL은 약 1시간이다. Redis Pub/Sub는 구독자가 잠시 연결이 끊겼을 때 이벤트를 다시 전달하지 않으므로 갱신 통지를 놓친 서버에는 TTL 만료 전까지 오래된 값이 남을 수 있다. 가격처럼 잠깐의 불일치도 치명적인 값이라면 실시간 재조회·버전 비교·내구성 있는 스트림과 ACK 등 더 강한 계약이 필요하다. 원문에는 응답 지연이나 DB 부하 감소율의 정량 비교가 없다.

## 왜 읽을까

'Redis를 쓸까, 로컬 캐시를 쓸까'보다 먼저 어떤 데이터의 불일치를 얼마 동안 허용할 수 있는지 결정해야 한다는 관점을 준다. 빠른 조회와 정합성·운영 복잡도의 교환 관계를 코드 수준에서 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 브랜드·카테고리처럼 변경 빈도가 낮은 읽기 데이터와 가격·재고처럼 최신성이 중요한 데이터를 분류한다.
- [ ] 로컬 캐시 도입 전에 허용 가능한 오래된 데이터의 지속 시간과 TTL을 정의한다.
- [ ] 캐시 무효화 이벤트 유실과 서버 재시작 상황을 테스트하고, 캐시 적중률과 DB 조회량을 전후 비교한다.
