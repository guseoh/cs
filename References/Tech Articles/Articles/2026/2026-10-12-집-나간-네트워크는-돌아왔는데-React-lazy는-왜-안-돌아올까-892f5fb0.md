# 집 나간 네트워크는 돌아왔는데 React.lazy는 왜 안 돌아올까

> [!abstract] 한 줄 정리
> 네트워크가 복구돼도 dynamic import 실패가 브라우저의 모듈 맵에 남으면 단순 재시도가 통하지 않는다. 사후 재시도 대신 실패가 캐시되는 경로를 피하도록 로딩 순서를 설계했다.

> 우아한형제들 기술블로그 · 2026-09-15

## 핵심 내용

배민주문접수 웹뷰에서 네트워크가 끊긴 상태로 미로딩 화면에 진입하면 온라인으로 돌아온 뒤에도 `React.lazy`가 오류 상태를 유지했다. 영업 중인 앱이었기 때문에 전체 새로고침으로 상태를 초기화하는 방법은 주문접수 중 작업을 잃게 할 수 있어 사용할 수 없었다.

문제는 두 계층에 있었다. React.lazy는 한 번 Reject된 로딩 결과를 재사용했고 브라우저의 모듈 맵은 실패한 import URL을 document 수명 동안 기억했다. React ErrorBoundary에서 retry 버튼을 누르거나 import URL에 단순 쿼리 파라미터를 더해도 공유 청크의 고정 경로 때문에 실패를 피하기 어려웠다. 출시 전에는 정적 import로 되돌려 안정성을 확보한 다음, 네트워크가 복구되었는지 `fetch(HEAD)`로 먼저 확인하고 주요 화면 청크를 부팅할 때 미리 로딩하는 방식으로 lazy와 코드 분할을 다시 조합했다.

```ts
// import 실패 전에 연결을 검증한다는 설계의 개념 예시
async function ensureConnectivity(url: string) {
  const response = await fetch(url, { method: 'HEAD', cache: 'no-store' });
  if (!response.ok) throw new Error('network unavailable');
}
// 이후 안정적으로 준비된 시점에만 동적 import 수행
```

HEAD 성공만으로 동적 모듈의 가용성을 보장하는 것은 아니므로 자원 호스트와 실제 모듈 경로도 검증해야 한다.

| 해결책 | 검토 결과 | 대가 |
| --- | --- | --- |
| 전체 새로고침 | 주문 작업 상태 소실 | 운영 중 부적합 |
| 정적 import | import 실패 경로 회피 | 초기 번들 176.9kB |
| React.lazy 단독 retry | 브라우저 Module Map의 실패 캐시 | 재호출 실패 가능 |
| 사전 연결 검사+프리로드 | 오프라인 복귀 뒤 화면 진입 | lazy 다운로드 최적성 일부 포기 |

이 설계는 브라우저에서 필요할 때만 청크를 내려받는 장점 일부를 포기하지만, SPA 상태를 보존하면서 네트워크 복구 뒤 새 화면 진입을 가능하게 한다. 적용 후 오프라인→온라인 이동 실패가 재현되지 않았고 메인 번들 gzip 크기는 정적 import 시 176.9kB에서 다시 84.7kB로 줄었다. 팀은 직접 React.lazy 사용을 막는 lint 규칙도 추가했다.

## 왜 읽을까

라이브러리의 에러 처리만 보면 해결되지 않는 문제가 브라우저 표준의 캐시 규칙에서 비롯될 수 있다. 재시도 가능한 fetch와 실패가 기록되는 import의 차이를 이해하고, 제품의 상태 보존 요구에 맞춰 복구 전략을 선택하는 사례다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기 신청·예약 폼 입력 중 네트워크를 끊었다 복구해도 상태가 유지되는지 E2E로 확인한다.
- [ ] 코드 스플리팅된 페이지의 청크 로드 실패와 브라우저 재시도 동작을 실제 빌드에서 재현한다.
- [ ] 전체 새로고침이 필요한 복구 전략을 선택한다면 미저장 폼 데이터의 보존 조건부터 정의한다.
