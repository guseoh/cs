# 집 나간 네트워크는 돌아왔는데 React.lazy는 왜 안 돌아올까

> [!abstract] 한 줄 정리
> 네트워크가 복구돼도 dynamic import 실패가 브라우저의 모듈 맵에 남으면 단순 재시도가 통하지 않는다. 사후 재시도 대신 실패가 캐시되는 경로를 피하도록 로딩 순서를 설계했다.

> 우아한형제들 기술블로그 · 2026-09-15

## 핵심 내용

- **문제:** 배민주문접수 웹뷰에서 오프라인 상태로 미로드 화면에 이동한 뒤 온라인으로 돌아와도 오류 화면이 계속 나타났다. 영업 중인 SPA라 전체 새로고침은 작업 상태 손실 때문에 허용할 수 없었다.
- **원인:** React.lazy는 Rejected 상태를 재호출하지 않으며, 당시 브라우저 모듈 맵도 실패한 import URL을 document 수명 동안 기억했다. React 수준의 retry나 URL 쿼리 변경은 공유 청크의 고정된 import 경로 때문에 실패했다.
- **접근:** 출시 직전에는 정적 import로 회귀해 안정성을 확보했다. 이후 fetch HEAD로 연결을 확인한 뒤에만 import를 실행하고, 부팅 시 주요 화면을 미리 불러오는 방식으로 React.lazy를 복원했다.
- **트레이드오프:** 지연 로딩의 '안 쓰는 화면은 받지 않음' 이점은 포기했지만 코드 스플리팅은 유지했다. Service Worker는 관리 비용, modulepreload는 Chrome 51 지원 하한과의 호환성 때문에 제외했다.
- **결과:** 오프라인→온라인 복귀 시 화면 이동 오류가 재현되지 않았고, 메인 번들 gzip 크기는 정적 import 시 176.9kB에서 84.7kB로 줄었다. 직접 React.lazy를 쓰지 못하게 린트 규칙도 추가했다.

## 왜 읽을까

라이브러리의 에러 처리만 보면 해결되지 않는 문제가 브라우저 표준의 캐시 규칙에서 비롯될 수 있다. 재시도 가능한 fetch와 실패가 기록되는 import의 차이를 이해하고, 제품의 상태 보존 요구에 맞춰 복구 전략을 선택하는 사례다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기 신청·예약 폼 입력 중 네트워크를 끊었다 복구해도 상태가 유지되는지 E2E로 확인한다.
- [ ] 코드 스플리팅된 페이지의 청크 로드 실패와 브라우저 재시도 동작을 실제 빌드에서 재현한다.
- [ ] 전체 새로고침이 필요한 복구 전략을 선택한다면 미저장 폼 데이터의 보존 조건부터 정의한다.
