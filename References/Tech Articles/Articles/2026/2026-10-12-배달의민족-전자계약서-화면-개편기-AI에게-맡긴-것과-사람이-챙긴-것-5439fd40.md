# 배달의민족 전자계약서 화면 개편기: AI에게 맡긴 것과 사람이 챙긴 것

> [!abstract] 한 줄 정리
> AI 코딩의 생산성은 프롬프트보다 코드 경계·명세·테스트·사람의 승인 시점에 좌우된다. 생성 속도 개선과 출시 후 품질은 별도로 측정해야 한다.

> 우아한형제들 기술블로그 · 2026-09-18

## 핵심 내용

- **문제:** 큰 전자계약서 폼에서 props 객체를 직접 수정하고 상위 컴포넌트를 forceUpdate해 상태 변경 경로를 추적하기 어려웠다. 디자인시스템과 함께 전체 화면 구조를 교체했다.
- **구조:** View(표시), Form(입력·검증), Store(상태·동작)로 책임을 나누고 린트·테스트로 경계를 강제했다. 구현 파일마다 명세와 테스트를 짝지어 '명세 승인→테스트 승인→구현' 순서를 지켰다.
- **접근:** AI가 디자인시스템 문서 59개를 참조해 Storybook 스크린샷을 최대 5회 비교·수정하도록 했고, 사람은 컴포넌트 선택·인터랙션·중요한 로직을 검토했다.
- **수치:** 비교한 두 프로젝트에서 생산 로직 작성량은 근무일당 605줄→1,224줄(약 2배), 프로덕션 코드 1줄당 테스트는 0.15줄→1.28줄(약 8.5배)로 늘었다. 서로 다른 작업의 비교이므로 통제된 실험은 아니다.
- **주의점:** 배포 뒤 2주 동작 버그는 비AI 작업 2건, AI 작업 4건이었다. AI로 구현을 빨리 했어도 연결된 코드 흐름을 직접 읽지 않으면 디버깅 시간이 늘어났다.

## 왜 읽을까

AI로 구현한 코드의 구조를 사람이 검증 가능하게 만드는 실전 절차가 구체적이다. 특히 생산성 향상을 코드 줄 수 하나로 단정하지 않고 버그, 명세 유지비, 리뷰 비용까지 함께 보는 판단 기준을 얻을 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집글·지원서 기능에서 API 계약과 상태 전이 명세를 먼저 작성하고 테스트와 연결한다.
- [ ] Codex가 변경하는 핵심 비즈니스 규칙은 명세→테스트→구현 순서로 리뷰한다.
- [ ] AI 작업 전후 개발 시간뿐 아니라 회귀 버그·리뷰 수정 횟수를 함께 기록한다.
