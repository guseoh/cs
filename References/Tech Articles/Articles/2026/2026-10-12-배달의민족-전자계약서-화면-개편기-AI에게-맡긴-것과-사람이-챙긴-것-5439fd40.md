# 배달의민족 전자계약서 화면 개편기: AI에게 맡긴 것과 사람이 챙긴 것

> [!abstract] 한 줄 정리
> AI 코딩의 생산성은 프롬프트보다 코드 경계·명세·테스트·사람의 승인 시점에 좌우된다. 생성 속도 개선과 출시 후 품질은 별도로 측정해야 한다.

> 우아한형제들 기술블로그 · 2026-09-18

## 핵심 내용

전자계약서의 거대한 입력 화면에서 props를 직접 수정하고 부모를 강제로 다시 렌더링하면 어느 입력이 어떤 상태를 바꿨는지 찾기 어렵다. 우아한형제들은 Bootstrap·Ant Design 중심 화면을 사내 디자인시스템으로 바꾸면서 상태 변경의 책임도 View, Form, Store로 분리했다.

View는 표시만 담당하고 Form은 입력·검증, Store는 상태·동작을 맡아 동작을 추적할 수 있도록 했다. AI는 디자인시스템 문서 59개를 읽고 Storybook 스크린샷과 비교해 컴포넌트를 수정하도록 활용했지만, 컴포넌트 선택의 타당성과 실제 입력의 인터랙션 및 중요한 비즈니스 로직은 사람이 검토했다. 파일마다 명세·테스트·구현을 연결해 '명세 승인→테스트 승인→코드 작성' 순서를 적용한 것도 핵심이다.

| 비교 항목 | 비AI 비교 작업 | AI 활용 작업 |
| --- | ---: | ---: |
| 근무일당 생산 로직 | 605줄 | 1,224줄 |
| 프로덕션 코드 1줄당 테스트 | 0.15줄 | 1.28줄 |
| 배포 후 2주 버그 | 2건 | 4건 |

*작업의 난도와 범위가 서로 다르므로 코드 줄 수와 버그 건수만으로 생산성의 인과관계를 확정할 수 없다.*

비교한 두 작업에서 생산 로직 작성량은 근무일당 605줄에서 1,224줄로, 프로덕션 코드 1줄당 테스트 코드는 0.15줄에서 1.28줄로 늘었다. 그러나 배포 2주 내 버그는 비AI 작업 2건, AI 작업 4건이었다. 서로 다른 프로젝트를 비교한 관측값이므로 AI가 작업 속도를 두 배 높였다는 통제 실험 결과는 아니다. 생성 코드의 흐름을 직접 이해하지 않으면 수정과 디버깅 비용이 늘어날 수 있다.

## 왜 읽을까

AI로 구현한 코드의 구조를 사람이 검증 가능하게 만드는 실전 절차가 구체적이다. 특히 생산성 향상을 코드 줄 수 하나로 단정하지 않고 버그, 명세 유지비, 리뷰 비용까지 함께 보는 판단 기준을 얻을 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집글·지원서 기능에서 API 계약과 상태 전이 명세를 먼저 작성하고 테스트와 연결한다.
- [ ] Codex가 변경하는 핵심 비즈니스 규칙은 명세→테스트→구현 순서로 리뷰한다.
- [ ] AI 작업 전후 개발 시간뿐 아니라 회귀 버그·리뷰 수정 횟수를 함께 기록한다.
