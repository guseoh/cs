# 토스의 디바이스 팜 만들기

> [!abstract] 한 줄 정리
> 팀마다 흩어져 있던 실기기 테스트 환경을 API 하나로 추상화한 중앙 플랫폼으로 바꾸고, 범용 Appium 대신 조직의 요구에 맞는 전용 드라이버를 만들어 속도·운영성·보안 기준을 함께 끌어올린 사례다.

> Toss Tech · 2026-07-30

## 핵심 내용

팀마다 맥미니·폰·Appium 환경을 따로 운영하면서 5~10대 수준의 규모 한계, 반복되는 세팅·복구 작업, 보안·컴플라이언스 편차가 생겼다. 클라이언트 → 오케스트레이션 서버 → 호스트 에이전트 → 기기 컨트롤러의 4계층으로 나누고, 테스트 실행은 Kafka로 분산하며 기기 점유는 `occupy · assign · release` 기반 분산 락으로 제어한다.

Android 기준 엘리먼트 클릭 p50은 Appium 702ms 대비 Nebula 52ms로 13.5배, 텍스트 입력은 1,377ms 대비 138ms로 10배 빨랐다. Appium 세션 생성에 매번 15~40초가 들던 구조도 상시 기동된 stateless HTTP 컨트롤러로 없앴다. Appium은 화면 안정화를 기다리는 견고성 우선 철학이고 Nebula는 즉시 실행하는 속도 우선 철학이다. 범용성을 버린 대신 토스 환경에 필요한 입력기·보안 정책·앱센터 연동을 직접 통제할 수 있게 됐다.

15대에서 시작한 팜이 100대를 넘어 수백 대 규모로 확장됐고, SDK·CLI·웹 콘솔·AI 에이전트까지 같은 API를 공유하는 전사 테스트 인프라가 됐다.

| 동작 | Appium | Nebula | 비교 조건 |
| --- | ---: | ---: | --- |
| Android 엘리먼트 클릭 p50 | 702ms | 52ms | 원문 실측 |
| 텍스트 입력 | 1,377ms | 138ms | 원문 실측 |
| 테스트 세션 | 생성에 15~40초 | 상시 컨트롤러 호출 | 실행 모델 차이 |

이는 컨트롤러 한 명령의 속도 비교이지 테스트 전체 성공률을 같은 비율로 향상시킨다는 뜻은 아니다. 분산 락으로 디바이스 점유를 제어하고, 실행 경로를 API로 통일해야 여러 팀이 같은 기기를 안전하게 공유할 수 있다.

## 왜 읽을까

테스트 자동화의 병목이 테스트 코드가 아니라 **테스트 환경을 준비하고 유지하는 비용**일 수 있다는 점을 보여준다. 공통 플랫폼을 만들 때 범용 도구를 계속 확장할지, 조직 특화 계층을 직접 소유할지를 판단하는 기준도 구체적이다.

특히 성능 수치만 제시하지 않고 Appium이 느린 이유가 `waitForIdle`이라는 견고성 정책 때문임을 분리해 설명한다. 따라서 단순한 '직접 만들면 빠르다'가 아니라 어떤 품질 속성을 교환했는지까지 볼 수 있다.

**프로젝트에 적용 — 공통**

- [ ] Codex가 수행하는 테스트에서 환경 준비·실행·정리 절차를 프로젝트별 스크립트로 흩어두지 말고 공통 인터페이스로 묶을 수 있는 부분을 식별한다.
- [ ] 테스트 실행 속도 개선 시 단순 시간만 비교하지 않고 안정성 대기·재시도 등 제거된 안전장치가 무엇인지 함께 기록한다.
- [ ] 장기적으로 E2E 환경이 커지면 `점유 → 실행 → 해제`의 자원 수명주기를 명시하고 중복 실행·고아 자원 복구 조건을 테스트한다.
