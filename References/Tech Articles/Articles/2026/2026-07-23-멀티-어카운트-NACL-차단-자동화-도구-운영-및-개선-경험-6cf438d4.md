# 멀티 어카운트 NACL 차단 자동화 도구 운영 및 개선 경험

> [!abstract] 한 줄 정리
> 보안 자동화는 '한 번 실행하면 된다'가 아니라 상태 불일치·중복 요청·부분 실패를 견디도록 멱등성과 직렬화, 재검증을 설계해야 합니다.

> techblog.woowahan.com

## 핵심 내용

여러 AWS 계정의 NACL 차단을 자동화하면서 실제 NACL 상태와 DynamoDB 상태가 어긋나는 문제, 동시에 들어오는 요청의 경쟁 조건, API throttling 등을 다룹니다. 상태를 다시 맞추는 sync check를 추가하고 Lambda reserved concurrency를 1로 제한해 순차 처리하며 adaptive retry를 적용했습니다.

개선 후 consumer의 메시지 처리 시간은 대략 72초에서 7초 수준으로 줄었고, 이미 처리된 작업을 건너뛰는 멱등 처리와 계정별 결과 보고도 보강했습니다.

멀티 어카운트 NACL 차단은 AWS API 호출을 여러 번 수행하는 자동화처럼 보이지만 각 계정의 실제 규칙과 중앙 상태 저장소의 결과가 일치해야 한다는 **분산 상태 동기화 문제**가 있다. 작업 중 실패하거나 API 요청이 재시도될 때 DynamoDB 기록만 먼저 바뀌면 실제 차단 상태를 잘못 보고할 수 있다. 원문은 Sync Check를 추가하고 Lambda의 Reserved Concurrency를 1로 제한해 경합을 줄이며 Adaptive Retry로 Throttling에 대응했다.

```mermaid
flowchart LR
 A["차단 요청 Queue"] --> B["단일 Lambda Consumer"]
 B --> C["AWS 계정별 NACL 적용"]
 C --> D["실제 규칙 재조회"]
 D --> E["DynamoDB 상태 보정"]
 E --> F["계정별 결과 보고"]
```

*자체 재구성. 제어 상태와 실제 NACL 상태를 일치시키는 검증 경로를 표시한다.*

Consumer 처리 시간이 약 **72초 → 7초**로 줄었다는 관측은 이 구현의 개선 결과이며 순차 처리 방식을 모든 계정과 상황에서 항상 더 빠르다고 일반화할 수 없다.

## 왜 읽을까

운영 자동화에서 가장 중요한 것은 happy path보다 '중간에 실패했을 때 상태를 믿을 수 있는가'라는 점을 잘 보여줍니다.

**프로젝트에 적용**

**PawCycle** — 배포·장애 대응 자동화를 만들 때 같은 명령의 재실행 안전성, 일부 인스턴스 실패, 재시도 이후 최종 상태 검증을 명시적으로 설계해볼 수 있습니다.
