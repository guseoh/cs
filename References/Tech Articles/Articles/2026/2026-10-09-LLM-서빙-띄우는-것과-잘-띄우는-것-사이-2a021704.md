# LLM 서빙, 띄우는 것과 잘 띄우는 것 사이

> [!abstract] 한 줄 정리
> LLM 서빙 장애는 일반적인 요청 수·응답시간만으로 진단하기 어렵다. TTFT, 토큰 처리량, Prefix/KV Cache, finish\_reason을 함께 관찰하고 설정·프레임워크 문제를 실험으로 좁혀야 한다.

> 토스증권 기술 블로그 · 2026-08-21

## 핵심 내용

LLM 서비스를 배포하는 일과 지연·오류를 안정적으로 관리하는 일은 별개다. 토스증권은 약 100건의 타임아웃 알림이 한꺼번에 쌓였을 때 일반 CPU/메모리 지표만으로는 원인을 구별할 수 없어, LLM 특유의 처리 방식에 맞춘 관측 지표로 전환했다.

모델이 한 요청에서 생성하는 토큰 수가 다르므로 HTTP RPS 대신 초당 생성 토큰 수로 처리량을 평가하고, 사용자 체감 응답의 시작은 TTFT(Time To First Token)로 측정했다. vLLM과 SGLang의 Prefix Cache Hit Rate, KV Cache 사용률, `finish_reason`을 로그·메트릭에 연결해 모델별 출력 중단·캐시 미스·메모리 병목을 구분했다. 특정 모델에서 기본 비활성화된 Prefix Cache를 켜자 적중률이 90% 이상으로 오르고 약 20초이던 TTFT 사례가 대략 1/10이 되었다.

| 관측 신호 | 정상적 해석 | 장애 추적 활용 |
| --- | --- | --- |
| 초당 생성 토큰 | 실제 토큰 생성량 중심 처리량 | RPS의 요청 길이 편차 제거 |
| TTFT | 응답 시작까지의 지연 | Prefix Cache 미스·스케줄링 분석 |
| Prefix Cache Hit Rate | 공통 접두부 재사용 비율 | 기본 비활성화 여부 확인 |
| KV Cache 사용률 | 토큰 상태 메모리 점유 | 동시성 확장 여지 |
| finish_reason / 오류율 | 정상 종료 및 비정상 종료 구분 | reasoning 종료 토큰 버그 탐지 |

reasoning 종료 토큰을 잘못 처리하던 vLLM 버그를 우회해 오류율을 약 0.2%→0.02%로 낮추었고, KV Cache 사용률 1% 미만 환경에서 동시성 20을 시험해 GPU Pod 증설 없이 약 네 배 트래픽 수용 가능성을 관찰했다. 하지만 모델 프레임워크 업데이트는 새로운 회귀를 만들 수 있어 같은 출력·긴 요청·취소·동시성 부하를 비교해야 한다. 가용 GPU 메모리가 남았다고 서비스의 외부 API나 토크나이저까지 여유롭다는 뜻은 아니다.

## 왜 읽을까

모델을 바꾸거나 GPU를 증설하기 전에 관측 지표와 로그로 원인을 좁혀야 한다는 실전 사례다. 특히 '설정은 켰지만 실제로 적용됐는가', '자원이 부족한가 아니면 동시성 제한이 과도한가'를 구분하는 관점을 얻을 수 있다.
