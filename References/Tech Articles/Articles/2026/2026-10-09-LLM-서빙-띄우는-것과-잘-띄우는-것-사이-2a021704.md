# LLM 서빙, 띄우는 것과 잘 띄우는 것 사이

> [!abstract] 한 줄 정리
> LLM 서빙 장애는 일반적인 요청 수·응답시간만으로 진단하기 어렵다. TTFT, 토큰 처리량, Prefix/KV Cache, finish\_reason을 함께 관찰하고 설정·프레임워크 문제를 실험으로 좁혀야 한다.

> 토스증권 기술 블로그 · 2026-08-21

## 핵심 내용

- **문제:** 타임아웃 알림이 100건 가까이 몰려도 일반 서버 지표만으로 원인을 찾기 어려웠다. 처리량은 요청 수 대신 초당 생성 토큰, 지연은 TTFT(첫 토큰 시간)를 중점적으로 봤다.
- **접근:** Grafana 메트릭과 Kibana 단건 로그에 vLLM·SGLang의 Prefix Cache Hit Rate, KV Cache 사용률, finish\_reason 등 서빙 특화 신호를 결합했다.
- **결과:** 특정 모델에서 기본 비활성화된 Prefix Cache를 켜자 캐시 적중률이 90% 이상, 20초에 가깝던 TTFT 사례가 약 1/10 수준으로 감소했다.
- **결과:** reasoning 종료 토큰 처리 관련 vLLM 버그를 찾아 우회한 뒤 오류율이 약 0.2%에서 0.02%로 감소했다.
- **트레이드오프:** KV Cache 사용량이 1% 미만인 상황에서 동시성 20까지 검증해, GPU 파드 증설 없이 트래픽을 최대 4배 받을 가능성을 확인했다. 프레임워크 업데이트는 새 회귀 위험이 있어 스트레스 테스트와 롤백이 필요하다.

## 왜 읽을까

모델을 바꾸거나 GPU를 증설하기 전에 관측 지표와 로그로 원인을 좁혀야 한다는 실전 사례다. 특히 '설정은 켰지만 실제로 적용됐는가', '자원이 부족한가 아니면 동시성 제한이 과도한가'를 구분하는 관점을 얻을 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 성능 대시보드에서 요청량·p95/p99 외에 Hikari pending, 실제 DB 사용량, 스레드/CPU 지표를 동일 시간축으로 확인한다.
- [ ] 증설 전 부하 구간별 병목 자원과 미사용 여유 자원을 기록하고, 설정 변경 전후 동일 워크로드로 재측정한다.
- [ ] 설정 변경 시 회귀 감지 지표와 즉시 롤백 조건을 함께 정한다.
