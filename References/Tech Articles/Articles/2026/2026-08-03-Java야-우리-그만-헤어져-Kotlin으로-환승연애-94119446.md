# Java야…, 우리 그만 헤어져. Kotlin으로 환승연애

> [!abstract] 한 줄 정리
> 큰 전환일수록 테스트로 기존 동작을 고정하고 작은 배포 단위로 나누면 운영 위험을 크게 줄일 수 있습니다.

> techblog.woowahan.com

## 핵심 내용

2018년부터 운영한 Java 기반 포인트 시스템을 약 3개월에 걸쳐 Kotlin으로 전환한 기록입니다. 테스트 코드를 먼저 옮기고 운영 코드는 기능·패키지 단위로 나눠 총 10번 점진 배포했으며, 82개 작업 티켓을 처리하는 동안 전환으로 인한 운영 장애가 없었다고 설명합니다. null 처리, Lombok 제거, QueryDSL DTO 매핑, Jackson 역직렬화, Spring 트랜잭션 예외 차이까지 검토했고 코드 스멜은 330개에서 4개, 테스트 커버리지는 61.5%에서 76.7%로 개선됐습니다.

Java에서 Kotlin으로의 전환은 문법을 줄이는 작업처럼 보이지만, 실제 운영의 경계는 **Java 라이브러리와 Kotlin nullability, 역직렬화, Proxy, 빌드 산출물의 호환성**에서 결정된다. 테스트를 먼저 Kotlin으로 옮긴 것은 운영 코드의 이전에 앞서 호환성을 검증하는 방어선이었고, 기능·패키지별 10번의 점진 배포는 이슈가 발생했을 때 영향 범위를 좁히기 위한 선택이다.

| 점검 대상 | Java→Kotlin 전환 위험 |
| --- | --- |
| Nullability | Java Platform Type의 런타임 null |
| Lombok | Kotlin 데이터 클래스·생성자 의미 차이 |
| QueryDSL·Jackson | DTO 생성·역직렬화 계약 |
| Spring AOP·트랜잭션 | 프록시와 예외 처리 차이 |
| 테스트·배포 | Java/Kotlin 혼재 시 회귀 |

원문에서 코드 스멜 **330개 → 4개**, 커버리지 **61.5% → 76.7%**로 개선된 수치는 전환 과정 전체의 결과다. Kotlin 채택만으로 품질이 자동 상승한다는 인과로 읽어서는 안 된다.

## 왜 읽을까

언어 전환 성공담보다 운영 중인 시스템을 어떻게 안전하게 바꾸는지가 중심입니다. 일반적인 리팩터링이나 대규모 구조 변경에도 적용할 수 있는 방식입니다.
