# 평균 CPU는 여유로운데, 커밋은 왜 느릴까?

> [!abstract] 한 줄 정리
> 전체 CPU 평균이 정상이어도 특정 코어의 NIC 인터럽트 경합 때문에 DB 커밋이 지연될 수 있다. 프로세스가 실행된 CPU와 장치 인터럽트 분포를 함께 추적해야 병목을 찾을 수 있다.

> 토스증권 기술 블로그 · 조규범 · 2026-10-19

## 핵심 내용

Oracle에서 커밋하면 redo log를 디스크에 기록하는 LGWR 작업이 완료되어야 트랜잭션이 성공으로 돌아온다. 토스증권은 `log file sync` 대기가 간헐적으로 0.1초를 넘는 문제를 겪었지만 디스크·DB·OS·네트워크의 평균 지표에서는 특이점을 찾지 못했다. 평균 CPU 사용률과 특정 코어·소켓의 인터럽트 경쟁은 다른 지표라는 점이 조사 방향을 바꿨다.

```mermaid
flowchart LR
 A[log file sync 100ms+ 지연] --> B[pidstat: LGWR 실행 CPU 확인]
 B --> C[CPU 28과 지연 상관]
 C --> D[/proc/interrupts 30초 차분]
 D --> E[특정 소켓 NIC IRQ 집중]
 E --> F[NIC 재배치·Active-Active]
 F --> G[IRQ 분산·LGWR 커밋 지연 감소]
```

*원문에서 제시한 단서를 가로 방향으로 자체 재구성한 학습용 흐름도다.*

`pidstat`으로 LGWR가 실행된 CPU를 추적하자 28번 CPU에서 실행될 때만 지연이 나타났다. 4개 소켓·32개 물리 코어(하이퍼스레딩 포함 논리 CPU 64개) 환경에서 `/proc/interrupts`를 30초 간격으로 두 번 읽어 차이를 비교하니 NIC 인터럽트가 특정 소켓의 8개 코어에 집중되어 있었다. 인터럽트가 LGWR의 CPU 시간을 간헐적으로 빼앗는다면 전체 평균 CPU가 낮아도 커밋은 늦어질 수 있다.

```bash
# 원문 진단 접근을 요약한 예시: 동일 간격으로 두 번 비교
pidstat -p <LGWR_PID> -u 1
cat /proc/interrupts > interrupts_before.txt
# 30초 뒤 같은 측정값 수집
cat /proc/interrupts > interrupts_after.txt
```

장치별 누적 카운터의 단순 값이 아니라 측정 구간의 **차분**을 보고 CPU별 인터럽트 집중을 분석해야 한다. 실제 운영 장비에서 NIC 배치를 바꾸기 전에는 하드웨어·복구 경로 검증이 필요하다.

| 관찰 지표 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 초당 1,000회 이상 IRQ를 처리하는 코어 | 8개 | 15개 |
| IRQ 집중도 Gini 계수 | 0.80 | 0.67 |
| 다른 RAC 개장 후 첫 10분 평균 CPU | 약 36.6% | 약 17.4% |
| 비교 대상 동시접속 | 이전 조건 | 변경 후 약 28% 더 많은 조건 |

*다른 RAC의 CPU 수치는 같은 부하에서의 통제 실험이 아니며, 공통 SQL 9건 중 8건의 개선도 데이터·계획 차이 때문에 보조 근거로 읽어야 한다.*

처음에는 `irqbalance`로 인터럽트를 분산하려 했지만 NIC와 장비 매핑 제약 때문에 해결하지 못했고, `taskset`으로 LGWR를 고정하는 방법은 프로세스 재시작과 장애 전환 시 관리 부담이 있었다. 그래서 NIC 2장을 서로 다른 소켓 슬롯에 배치하고 Active–Standby를 Active–Active로 변경했다. 초당 1,000회 이상 인터럽트를 처리하는 물리 코어가 8개에서 15개로 늘고 집중도 Gini 계수는 0.80→0.67로 낮아졌다. 다른 RAC에서 관찰한 CPU 평균 36.6%→17.4%는 변경 후 동시접속자가 약 28% 더 많은 조건이었으므로 엄격한 동일 부하 비교로 단정하지 않는다.

## 왜 읽을까

애플리케이션 쿼리나 인덱스만으로 설명되지 않는 지연을 진단할 때 유용하다. 평균 CPU와 특정 코어의 포화는 다른 문제이며, DB의 대기 이벤트와 OS 인터럽트 지표를 연결해야 원인을 좁힐 수 있다는 판단 관점을 제공한다.

**프로젝트에 적용 — PawCycle**

- [ ] MySQL 성능 이슈가 발생하면 평균 CPU와 함께 DB 대기·슬로 쿼리·컨테이너별 CPU 분포를 같은 시간대에 비교한다.
- [ ] 재현 가능한 지연이 있으면 호스트별 코어 편중과 네트워크 인터럽트까지 조사 범위를 확장하되, OCI 관리형 DB에서 직접 조작할 수 없는 하드웨어 설정은 변경하지 않는다.
- [ ] 개선 전후에는 동일 부하 조건의 p95/p99 지연과 DB 지표를 기록한다.
