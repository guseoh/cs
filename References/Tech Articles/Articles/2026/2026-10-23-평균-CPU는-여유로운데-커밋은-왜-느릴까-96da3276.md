# 평균 CPU는 여유로운데, 커밋은 왜 느릴까?

> [!abstract] 한 줄 정리
> 전체 CPU 평균이 정상이어도 특정 코어의 NIC 인터럽트 경합 때문에 DB 커밋이 지연될 수 있다. 프로세스가 실행된 CPU와 장치 인터럽트 분포를 함께 추적해야 병목을 찾을 수 있다.

> 토스증권 기술 블로그 · 조규범 · 2026-10-19

## 핵심 내용

- **문제:** Oracle의 `log file sync` 대기가 0.1초 이상 반복됐지만 스토리지·네트워크·OS·DB의 평균 지표는 정상으로 보였다.
- **추적:** `pidstat`으로 LGWR가 CPU 28에서 실행될 때만 지연됨을 찾고, `/proc/interrupts`의 30초 차분으로 NIC 인터럽트가 32개 물리 코어 중 8개(한 소켓)에 집중됨을 확인했다.
- **접근:** `irqbalance`는 장비 매핑 제약으로 적용되지 않았고 `taskset` 고정은 재기동마다 관리해야 했다. NIC 2장을 서로 다른 소켓 슬롯에 배치하고 Active-Standby를 Active-Active로 변경했다.
- **수치:** 초당 1,000회 이상 인터럽트를 처리하는 물리 코어가 8→15개, 인터럽트 집중도 Gini 계수가 0.80→0.67로 바뀌었다. 다른 RAC의 개장 후 10분 CPU 평균은 동시접속자가 28% 많은 날에도 36.6%→17.4%였다.
- **주의점:** 공통 SQL 9건 중 8건의 실행 시간이 감소했으나 실행 계획·데이터량 차이가 섞여 있어 보조 지표로만 해석했다. 최초 서버의 0.1초 초과 커밋 대기도 대부분 개선됐다.

## 왜 읽을까

애플리케이션 쿼리나 인덱스만으로 설명되지 않는 지연을 진단할 때 유용하다. 평균 CPU와 특정 코어의 포화는 다른 문제이며, DB의 대기 이벤트와 OS 인터럽트 지표를 연결해야 원인을 좁힐 수 있다는 판단 관점을 제공한다.

**프로젝트에 적용 — PawCycle**

- [ ] MySQL 성능 이슈가 발생하면 평균 CPU와 함께 DB 대기·슬로 쿼리·컨테이너별 CPU 분포를 같은 시간대에 비교한다.
- [ ] 재현 가능한 지연이 있으면 호스트별 코어 편중과 네트워크 인터럽트까지 조사 범위를 확장하되, OCI 관리형 DB에서 직접 조작할 수 없는 하드웨어 설정은 변경하지 않는다.
- [ ] 개선 전후에는 동일 부하 조건의 p95/p99 지연과 DB 지표를 기록한다.
