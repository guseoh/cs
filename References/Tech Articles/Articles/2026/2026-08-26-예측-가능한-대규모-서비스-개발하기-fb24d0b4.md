# 예측 가능한 대규모 서비스 개발하기

> [!abstract] 한 줄 정리
> 대규모 서비스에서 중요한 것은 '빠르다'가 아니라 어느 정도 부하까지 버틸지 예측 가능하게 만드는 것이며, 프로토타입과 성능 테스트를 반복해 병목을 수치로 제거해야 한다.

> 당근 기술 블로그 · 2022-02-07

## 핵심 내용

GeoLocation 서비스의 IP 데이터는 S3에 두고, CentralDogma에서 버전·Hash·업데이트 시각을 관리해 서버가 설정 변경을 감지하면 새 데이터를 받아 무중단으로 반영하도록 했다. Python으로 프로토타입을 먼저 만들어 배포와 성능 테스트까지 전체 사이클을 빠르게 돌린 뒤, 병목이 확인된 부분을 바탕으로 본 구현을 개선했다.

초기 프로토타입에서 ITC는 약 1.3K RPS, CTC는 약 240 RPS였고 실패 케이스가 25% 섞이면 CTC는 약 140 RPS까지 떨어졌다. 두 API 모두 CPU가 병목이었다. CTC는 STRTree 최근접 검색 뒤 Geometry.contains 연산을 수행하면서 CPU Bound가 심하게 발생했다.

최종 버전에서 CTC 성능은 프로토타입 대비 약 66배 향상됐고, 이후 추가 성능이 필요하면 서버 증설이라는 명확한 용량 판단 기준을 갖게 됐다.

프로토타입은 최종 구현보다 성능이 낮아도 병목을 찾는 도구로서는 가치가 있다. 이 사례는 같은 GeoLocation API에서도 ITC와 CTC의 계산 경로가 달라, CTC가 STRTree 검색 뒤 Geometry.contains를 수행하며 훨씬 더 CPU Bound가 될 수 있음을 드러냈다. 실패 입력 비중을 섞어 측정했을 때 처리량이 더 떨어진 것도 데이터 분포 자체가 성능 조건이라는 증거다.

| 테스트 구간 | 프로토타입 처리량 |
| --- | ---: |
| ITC | 약 1,300 RPS |
| CTC | 약 240 RPS |
| CTC, 실패 입력 25% | 약 140 RPS |

최종 CTC의 약 66배 개선은 글의 프로토타입 대비 수치다. 서로 다른 API의 성능이나 모든 입력 분포에서 같은 개선이 난다고 해석하면 안 된다.

## 왜 읽을까

오래된 글이지만 성능 엔지니어링의 기본 흐름이 아주 선명하다. 프로토타입을 실패를 줄이는 도구로 쓰고, 병목을 CPU·알고리즘 수준까지 좁힌 뒤 다시 측정해 '현재 한계와 다음 확장 수단'을 명확히 만든다.

**프로젝트에 적용 — PawCycle**

- [ ] k6 테스트 전에 목표 RPS와 허용 지연을 먼저 정의한다.
- [ ] CPU·DB·네트워크 중 병목 자원을 구분하고, 개선 전후를 같은 조건으로 재측정한다.
- [ ] 최적화 이후 남은 한계를 기록해 코드 최적화와 인프라 증설의 경계를 판단한다.
