# 스케일 다운을 이끈 데이터베이스 최적화 전략

> [!abstract] 한 줄 정리
> 반복되는 DB 장애를 서버 증설로 덮지 않고 SQL 리뷰, 바인드 변수, 인덱스·조회 패턴, 캐시와 UI 중복 요청까지 단계적으로 개선했다. 운영 지표로 효과를 확인한 뒤 DB 인스턴스를 축소했다.

> 미리디 블로그 (이준수) · 2025-05-14

## 핵심 내용

- **문제:** 10년 이상 운영한 비즈하우스의 Oracle DB에서 부하성 장애가 반복됐다. 이전 피크 CPU 80~90%, 평균 50~60%였고 월 1~2회 장애가 있었다고 설명한다.
- **접근:** SQL 리뷰 채널과 배포 전 실행 계획 검토를 도입했다. 실행 빈도가 높은 동적 문자열 결합 SQL을 PreparedStatement·바인드 변수로 바꿔 하드 파싱과 SQL 인젝션 위험을 함께 줄였다.
- **구조:** 날짜·문자열 함수가 적용된 검색 조건을 범위·정규화 비교로 바꾸고, 불필요한 COUNT·JOIN·정렬·힌트를 정리했다. 인덱스는 데이터 분포와 실행 계획으로 판단했으며, 조회가 많은 일부 데이터에는 선택적으로 비정규화와 캐시를 적용했다.
- **결과:** 최고 DB 로드는 1.36→0.14, 평균 CPU는 50~60%→10% 미만, 피크 CPU는 20% 미만으로 내려갔다. 주요 API의 p95는 1초 미만, 개선 뒤 1년 이상 중대한 DB 장애 없이 운영했다고 보고했다.
- **비용·주의점:** RDS 인스턴스를 한 단계 낮춰 월 비용을 절반으로 줄였다고 한다. 사례는 Oracle 기반이므로 SQL 문법·실행 계획·NULL 인덱싱 등 세부 동작을 MySQL에 그대로 일반화하면 안 된다.

## 왜 읽을까

DB 성능을 SQL 한 줄의 마술 같은 튜닝으로 보지 않고, 관측→우선순위→쿼리·스키마·애플리케이션 개선→재측정→용량 조정으로 연결한 사례다. 특히 SQL 작성 규칙과 리뷰 문화가 운영 안정성을 어떻게 뒷받침하는지 확인할 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 느린 API 1개를 정하고 SQL 실행 빈도, 실행 계획, p95 응답시간, DB CPU를 기준선으로 기록한다.
- [ ] 해당 SQL의 문자열 결합, 함수가 걸린 검색 조건, 불필요한 COUNT·JOIN, 인덱스 사용 여부를 확인한다.
- [ ] 쿼리 또는 인덱스를 한 가지씩 수정하고 같은 데이터·부하 조건에서 전후를 재측정한다.
- [ ] 캐시를 고려한다면 데이터 갱신 빈도와 허용 가능한 지연을 먼저 정의한다.
