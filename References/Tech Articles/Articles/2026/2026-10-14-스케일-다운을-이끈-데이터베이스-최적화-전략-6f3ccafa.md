# 스케일 다운을 이끈 데이터베이스 최적화 전략

> [!abstract] 한 줄 정리
> 반복되는 DB 장애를 서버 증설로 덮지 않고 SQL 리뷰, 바인드 변수, 인덱스·조회 패턴, 캐시와 UI 중복 요청까지 단계적으로 개선했다. 운영 지표로 효과를 확인한 뒤 DB 인스턴스를 축소했다.

> 미리디 블로그 (이준수) · 2025-05-14

## 핵심 내용

10년 넘게 운영된 Oracle 기반 비즈하우스의 병목은 특정 SQL 하나만 수정해서 해결할 수 없었다. 미리디는 평균 CPU 50~60%, 피크 80~90%와 월 1~2회 반복되는 DB 부하성 장애를 겪으면서 배포 이전의 SQL 리뷰와 실행 계획 검증을 운영 프로세스로 도입했다.

문자열을 매번 결합하는 동적 SQL은 DB가 서로 다른 문장으로 해석하면 하드 파싱 부담이 증가할 수 있어 바인드 변수와 PreparedStatement를 사용하도록 바꾸었다. 인덱스 컬럼에 날짜·문자열 함수를 적용하는 조건은 인덱스 탐색을 방해할 수 있으므로 가능하면 경계값을 이용한 범위 비교로 재작성했다. 불필요한 COUNT, JOIN, ORDER BY, 힌트를 제거하고 실행 계획과 데이터 분포를 함께 확인했다. 읽기 중심의 일부 데이터는 비정규화와 캐시로 조회 경로를 단축했지만 갱신 책임도 같이 증가한다.

```sql
-- 컬럼에 함수를 적용하는 조건 대신 범위 비교를 사용하는 원리
-- 비권장 예: WHERE TRUNC(created_at) = :day
WHERE created_at >= :dayStart
  AND created_at < :nextDayStart
```

*Oracle 기반 원문에서의 일반적인 범위 비교 원리를 학습용으로 단순화했다. 실제 인덱스 사용 여부는 실행 계획과 데이터 분포로 확인해야 한다.*

| 측정 지표 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 평균 CPU | 50~60% | 10% 미만 |
| 피크 CPU | 80~90% | 20% 미만 |
| 최고 DB Load | 1.36 | 0.14 |
| 중대한 DB 장애 | 월 1~2회 | 개선 뒤 1년+ 큰 장애 없음 |
| 월 DB 비용 | 이전 인스턴스 | 스케일다운 후 약 50% 절감 |

이러한 변경을 합친 후 최고 DB Load 1.36→0.14, 평균 CPU 50~60%→10% 미만, 피크 CPU 20% 미만, 주요 API p95 1초 미만을 보고했다. 안정화 이후 1년 넘게 큰 DB 장애 없이 운영했고 RDS 인스턴스 규모를 한 단계 줄여 월 비용을 절반으로 낮췄다. 여러 SQL·운영 정책·캐시 변경을 동시에 적용한 결과이므로 한 인덱스의 독립 효과로 해석할 수 없다.

## 왜 읽을까

DB 성능을 SQL 한 줄의 마술 같은 튜닝으로 보지 않고, 관측→우선순위→쿼리·스키마·애플리케이션 개선→재측정→용량 조정으로 연결한 사례다. 특히 SQL 작성 규칙과 리뷰 문화가 운영 안정성을 어떻게 뒷받침하는지 확인할 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 느린 API 1개를 정하고 SQL 실행 빈도, 실행 계획, p95 응답시간, DB CPU를 기준선으로 기록한다.
- [ ] 해당 SQL의 문자열 결합, 함수가 걸린 검색 조건, 불필요한 COUNT·JOIN, 인덱스 사용 여부를 확인한다.
- [ ] 쿼리 또는 인덱스를 한 가지씩 수정하고 같은 데이터·부하 조건에서 전후를 재측정한다.
- [ ] 캐시를 고려한다면 데이터 갱신 빈도와 허용 가능한 지연을 먼저 정의한다.
