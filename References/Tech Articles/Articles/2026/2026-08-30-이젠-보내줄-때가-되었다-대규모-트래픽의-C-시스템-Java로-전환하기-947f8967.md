# 이젠 보내줄 때가 되었다. 대규모 트래픽의 C++ 시스템 Java로 전환하기

> [!abstract] 한 줄 정리
> 언어 전환은 단순 재작성 프로젝트가 아닙니다. 기존 성능·메모리 구조·배포 위험을 먼저 수치로 정의하고, 전환 후 GC 같은 새 병목까지 운영 트래픽으로 다시 검증해야 합니다.

> 우아한형제들 기술블로그 · 2025-01-07

## 핵심 내용

기존 C++ 서버는 1대당 2,000 TPS 이상을 10ms 이하로 처리했지만, 팀의 C++ 전문성 부족과 공통 배포·모니터링 체계 미적용으로 유지보수가 어려웠습니다. 구조를 과도하게 바꾸지 않고 약 180MB 데이터를 메모리에 올리는 기존 방식을 유지한 채 Java/Spring Boot로 먼저 전환해 리스크를 줄였습니다.

Java 1차 전환 후 nGrinder 테스트에서 약 3,500 TPS를 확보해 기존 목표인 2,000 TPS 이상을 만족했습니다. 1% → 5% → 20% → 50% → 100%로 트래픽을 늘리는 Canary를 반복하고, ALB Target Group으로 최대 1분 내 롤백 가능하게 했습니다.

운영 후 major GC로 인한 CPU spike를 발견해 primitive 중심 컬렉션으로 개선했고, 최대 TPS는 3,500 → 3,700, 힙 하단은 2GB → 1.13GB로 줄었으며 1,500 TPS 지속 테스트에서 major GC가 사라졌습니다.

| 검증 지점 | 원문 결과 |
| --- | --- |
| 기존 C++ 처리 성능 | 서버 1대당 2,000 TPS 이상, 10ms 이하 |
| Java 1차 전환 | nGrinder 약 3,500 TPS |
| 컬렉션 개선 후 | 최대 약 3,700 TPS |
| 힙 하단 | 약 2GB → 1.13GB |

이번 전환은 C++을 Java로 다시 쓰면 무조건 빨라진다는 사례가 아니다. 기존 인메모리 설계를 상당 부분 유지해 기능 변경과 언어 변경을 분리했고, 카나리 중 부하·GC·롤백 가능성을 확인했다. 운영 중 major GC가 드러난 뒤 primitive 컬렉션을 검토한 과정은 런타임 이전 후에도 GC 프로파일링이 필요하다는 근거다.

## 왜 읽을까

성능 테스트만 통과했다고 끝내지 않고, **Ramp-up 테스트가 놓친 지속 부하의 GC 문제를 운영 지표로 다시 발견**하는 과정이 좋습니다. 기술 교체의 성공 기준을 유지보수성뿐 아니라 성능·롤백·운영성까지 함께 보는 사례입니다.

**프로젝트에 적용 — PawCycle**

- [ ] 성능 테스트를 Ramp-up만 하지 말고 일정 TPS를 오래 유지하는 soak test도 포함합니다.
- [ ] JVM GC, heap, CPU spike를 p95/p99와 함께 기록해 장시간 부하에서만 드러나는 문제를 찾습니다.
- [ ] 큰 구조 변경은 캐시·DB·언어·배포 방식을 한 번에 바꾸지 말고 변경 변수를 최소화한 뒤 단계적으로 검증합니다.
