# AI 코딩 시대, DDD가 더 필요해진 이유

> [!abstract] 한 줄 정리
> 비즈니스 규칙이 핸들러·벤더·유틸 폴더에 흩어져 있으면 사람과 AI 모두 변경 영향 범위를 파악하기 어렵다. 도메인 경계와 의존성 방향을 코드 구조로 강제해야 점진적 리팩터링이 실제 복잡도 감소로 이어진다.

> 뱅크샐러드 기술 블로그 · 2026-10-15

## 핵심 내용

- **문제:** Go 기반 신용 서비스의 핸들러가 인증, 약관, 데이터 조회, 점수 계산, 외부 오류 해석까지 맡았다. 기술·벤더 기준 폴더와 복제된 규칙 때문에 변경 영향과 테스트 범위가 불명확했다.
- **시행착오:** 2025년부터 DDD 폴더를 도입했지만 `supporting/kcb`처럼 데이터 출처 중심으로 코드가 다시 모여, 1년 뒤에도 구조만 바뀌고 복잡도는 남았다.
- **접근:** 무거운 이벤트 소싱 등은 보류하고 비즈니스 개념별 바운디드 컨텍스트, handler/application/domain/infrastructure 4계층, domain 중심의 단방향 의존성이라는 DDD-lite·Clean Architecture 규칙을 정했다.
- **결과:** 2026년 6월 한 달간 **435개 PR**로 서비스를 중단하지 않고 점진적으로 정비했다. `credit-score`에 관련 코드를 모으고 외부 신용평가사 KCB는 infrastructure 어댑터로 이동했다.
- **트레이드오프:** 일관된 경계와 리뷰 기준을 유지하는 데 시간이 들었다. AI의 코드 탐색 범위가 줄었다는 관찰은 있지만, 생산성 향상에 대한 독립적인 정량 벤치마크는 제시하지 않았다.

## 왜 읽을까

DDD를 '폴더 이름 바꾸기'로 오해할 때 생기는 실패를 구체적으로 보여준다. 설계의 가치는 추상적인 계층 수가 아니라 **비즈니스 규칙의 소유 위치**, 의존성 경계, 변경 영향 범위를 쉽게 설명할 수 있는지로 판단해야 한다는 관점을 얻는다.

**프로젝트에 적용 — PawCycle**

- [ ] 기존 코드에서 주문·결제 등 핵심 흐름 하나의 Controller → Service → Repository → 외부 의존성을 추적한다.
- [ ] 도메인 규칙이 어디에 있고 기술/벤더별 코드와 섞여 있는지 기록한다.
- [ ] 구조 변경을 바로 시작하지 말고 테스트와 실제 변경 이력을 근거로 현재 경계의 장단점을 설명한다.
