# AI 코딩 시대, DDD가 더 필요해진 이유

> [!abstract] 한 줄 정리
> 비즈니스 규칙이 핸들러·벤더·유틸 폴더에 흩어져 있으면 사람과 AI 모두 변경 영향 범위를 파악하기 어렵다. 도메인 경계와 의존성 방향을 코드 구조로 강제해야 점진적 리팩터링이 실제 복잡도 감소로 이어진다.

> 뱅크샐러드 기술 블로그 · 2026-10-15

## 핵심 내용

AI가 코드를 빠르게 생성해 주는 환경일수록 도메인 경계가 부정확하면 그 잘못된 구조가 더 빠르게 복제될 수 있다. 뱅크샐러드의 Go 신용 서비스에서는 하나의 handler가 인증·약관·외부 신용평가 호출·점수 계산·오류 해석을 모두 맡았고, 벤더 기준 폴더 구조가 비즈니스 규칙을 여러 곳에 분산시켰다.

처음 DDD 폴더 구조를 도입했어도 `supporting/kcb`처럼 데이터 제공 업체 중심으로 다시 코드가 모였기 때문에 파일 위치만 바뀌고 책임은 여전히 섞였다. 팀은 무거운 이벤트 소싱보다 도메인 개념별 Bounded Context와 `handler/application/domain/infrastructure` 네 계층, 도메인으로 향하는 단방향 의존성 규칙을 우선했다. 신용 점수는 `credit-score` 도메인이 책임지고 KCB는 그 도메인이 사용하는 외부 인프라 어댑터가 되도록 이동했다.

```text
# 학습용 개념 구조: 실제 프로젝트 파일 목록의 복제 아님
credit-score/
  handler/          # HTTP 계약·요청 검증
  application/      # 사용 사례 조율
  domain/           # 신용 점수 규칙과 불변식
  infrastructure/   # KCB 등 외부 벤더 어댑터
```

KCB 공급자 응답이 바뀌어도 도메인 점수 규칙이 벤더 DTO에 직접 의존하지 않도록 계약을 분리한다.

| 구조 | 변경이 전파되던 이유 | 이번 정리의 판단 기준 |
| --- | --- | --- |
| 거대한 Handler | 여러 업무 규칙이 한 진입점에 집중 | HTTP 책임만 남김 |
| 벤더 중심 폴더 | KCB 같은 외부 제공자에 도메인 종속 | 도메인 개념 기준 책임 배치 |
| DDD-lite·Clean | 코드 생성과 변경의 소유권 불명확 | 도메인 단방향 의존과 점진적 PR |

*435개 PR은 리팩터링 과정의 규모 지표로, 품질 향상을 단독으로 증명하지 않는다.*

2026년 6월 한 달에 걸쳐 435개 PR을 사용해 서비스를 중단하지 않고 점진적으로 정리했다. 변경 경계가 분명해지면 AI도 관련 코드 범위를 좁히기 쉽지만 생산성 향상의 독립적 정량 실험은 제시하지 않았다. 설계 품질은 폴더명이 DDD인지보다 도메인 규칙이 어디에 존재하고 외부 공급자를 교체할 때 어느 계층이 수정되는지로 검증해야 한다.

## 왜 읽을까

DDD를 '폴더 이름 바꾸기'로 오해할 때 생기는 실패를 구체적으로 보여준다. 설계의 가치는 추상적인 계층 수가 아니라 **비즈니스 규칙의 소유 위치**, 의존성 경계, 변경 영향 범위를 쉽게 설명할 수 있는지로 판단해야 한다는 관점을 얻는다.

**프로젝트에 적용 — PawCycle**

- [ ] 기존 코드에서 주문·결제 등 핵심 흐름 하나의 Controller → Service → Repository → 외부 의존성을 추적한다.
- [ ] 도메인 규칙이 어디에 있고 기술/벤더별 코드와 섞여 있는지 기록한다.
- [ ] 구조 변경을 바로 시작하지 말고 테스트와 실제 변경 이력을 근거로 현재 경계의 장단점을 설명한다.
