# Nx에서 Bun 더 잘 사용하기: Nx 18 -> 21 마이그레이션

> [!abstract] 한 줄 정리
> 빠른 패키지 설치를 위해 Bun을 먼저 도입했지만 Nx의 lockfile 감지와 외부 의존성 메타데이터 파싱에서 호환 문제가 발생했다. 임시 우회보다 Nx 21.4+와 텍스트 `bun.lock`으로 전환해 유지보수성과 CI 성능을 함께 개선했다.

## 핵심 내용

컬리 핀테크그룹 프런트엔드는 Nx 모노레포에서 Node.js 런타임을 유지하면서 패키지 매니저만 pnpm에서 Bun으로 교체했다. 최초 도입 시 Nx 18은 Bun을 공식 지원하지 않았지만, MacBook Pro M2 Pro·32GB 환경에서 캐시를 삭제한 cold start 10회 평균으로 설치와 `nx build web` 시간이 1분 46초에서 42초로 줄어 약 60% 단축된 것을 확인했다. 이는 이후 Nx 21 업그레이드의 CI 개선 수치와 다른 실험이다.

Nx 18에서 `nx migrate`를 실행하자 Bun 대신 Yarn을 찾는 오류가 발생했다. 구 버전 Nx는 `bun.lockb`를 패키지 매니저 판별에 사용하지 않았고, 호환성 대비용으로 남겨둔 `yarn.lock`을 보고 Yarn을 선택했기 때문이다. 마이그레이션 중에만 보조 `yarn.lock`을 제거하여 npm fallback으로 버전을 올린 후, Bun 공식 지원 범위로 이동했다.

다음 문제는 Nx 19.x·Bun 1.0.33·webpack executor의 `generatePackageJson: true` 조합에서 발생한 `HookWebpackError`였다. 빌드 산출물용 package.json을 생성할 때 Nx가 외부 패키지 의존성 그래프의 메타데이터를 읽는데, 구형 바이너리 `bun.lockb` 해석이 불완전했다. 옵션을 끄거나 커스텀 플러그인을 넣는 우회도 검토했으나 추가 스크립트와 호환성 부채를 피하기 위해 버전 업그레이드를 선택했다.

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| Nx | 18.3.3 | 21.4+ |
| Bun | 1.0.33 | 1.2.x |
| Lockfile | 바이너리 `bun.lockb` 및 `yarn.lock` | 텍스트 `bun.lock` |
| CI 파이프라인 | 13분 30초 | 11분 40초 |
| Artifact 크기 | 330MB | 280MB |

CI 시간과 산출물 크기는 GitLab Runner 5회 평균으로, 각각 약 14%, 15% 개선됐다. 텍스트 lockfile로 변경하면서 PR diff 검토와 Dependabot 호환성도 개선됐다. 그러나 개선 폭은 이 프로젝트의 구성과 측정 조건에 한정되며, 공식 지원이 시작됐다는 사실만으로 모든 조합의 안정성을 보장하지는 않는다.

## 왜 읽을까

도구의 공식 지원 여부보다 실제 lockfile 형식, executor 옵션, 의존성 그래프 해석과 같은 **구체적인 통합 계약**이 더 중요할 수 있음을 보여준다. 임시 우회로 당장 빌드를 통과시키는 것과 장기 유지보수 비용을 낮추는 업그레이드 중 무엇을 선택할지 비교하는 좋은 사례다.

**일반적인 적용 제안(미검증):** 프로젝트별 빌드 도구를 올릴 때 lockfile diff, clean build, CI 실행 시간, 산출물 크기, 롤백 경로를 같은 조건에서 기록하는 체크리스트를 만들어볼 수 있다. 특정 사용자 프로젝트가 Nx·Bun을 사용한다는 전제는 두지 않는다.
