# 실전! Spring Boot 3 마이그레이션

> [!abstract] 한 줄 정리
> Spring Boot 메이저 업그레이드는 버전 숫자만 바꾸는 일이 아니라 Java·Jakarta EE·Security·Batch·JPA·Tracing·Flyway·테스트 생태계의 계약을 함께 옮기는 작업이다. 큰 점프보다 공식 변경점을 분해하고 단계적으로 이관하는 방식이 안전하다.

> LY Corporation Tech Blog · 2023-11-08

## 핵심 내용

Spring Boot 3 이관은 의존성 한 줄을 바꾸는 작업이 아니라 Java 17 이상, Jakarta EE 네임스페이스, Spring Security 6, Batch 5, Observability 스택을 함께 조정하는 호환성 변경이다. LY는 기존 서비스를 한 번에 최신 버전으로 올리기보다 공식 Migration Guide와 각 중간 릴리스 변경사항을 확인하는 순서를 택했다.

`javax.*` 기반 코드를 `jakarta.*`로 옮기는 컴파일 단계의 변경과 런타임 호환성 문제를 분리해야 한다. Spring Security는 `WebSecurityConfigurerAdapter` 대신 Bean 기반 `SecurityFilterChain`을, 관측은 Sleuth 대신 Micrometer Tracing을 사용한다. Spring Batch 5에서는 Job/Step Builder와 JobParameter 직렬화·저장 형식까지 바뀔 수 있으므로 기존 배치의 재시작 가능성도 확인해야 한다.

```java
// Spring Security 6 구성 원리를 보여 주는 예시
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .build();
}
```

*원문의 실제 보안 정책이 아닌 구조 변화 설명용 예시다. 기존 엔드포인트별 인가 계약은 별도로 옮겨야 한다.*

| 변경 범위 | 기존 형태 | Boot 3 대응에서 확인할 점 |
| --- | --- | --- |
| Java/EE API | Java 8/11, `javax.*` | Java 17+, `jakarta.*` |
| 보안 | `WebSecurityConfigurerAdapter` | `SecurityFilterChain` Bean |
| 분산 추적 | Spring Cloud Sleuth | Micrometer Tracing |
| 배치 | Spring Batch 4 | Batch 5 빌더·파라미터·재시작 |
| 외부 인프라 | MySQL 5.7/Flyway 등 | DB·마이그레이션 도구 호환성 |

MySQL 5.7처럼 인프라 버전이 최신 생태계의 지원 범위 밖에 있으면 Flyway 자동 설정을 포기하거나 별도 관리해야 한다. Mockito 5의 varargs 매칭 변화처럼 테스트 의존성의 불일치도 이관 실패를 만들 수 있다. 따라서 컴파일 성공→테스트→배치 재시작→배포 환경·DB 확인→점진적 운영 전환 순서로 증거를 확보하는 것이 중요하며 이 사례의 정량적인 개선율은 일반화할 수 없다.

## 왜 읽을까

오래된 글이지만 Spring 메이저 버전 전환을 “컴파일 오류를 고치는 작업”이 아니라 의존 생태계의 계약 변경으로 보는 방식은 여전히 유효하다. Spring Security·Batch·JPA처럼 평소 따로 배우는 기술이 버전 전환에서 어떻게 한꺼번에 연결되는지도 보기 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] Spring/Security 메이저 업그레이드 전에 현재 의존성·설정·deprecated API 목록을 먼저 인벤토리화한다.
- [ ] 인증 흐름은 회원가입→로그인→세션 유지→인가→로그아웃을 통합 테스트로 고정해 Security 설정 변경의 회귀를 잡는다.
- [ ] 버전 변경과 기능 리팩터링을 가능한 한 분리해 문제가 생겼을 때 원인을 좁힐 수 있게 한다.
