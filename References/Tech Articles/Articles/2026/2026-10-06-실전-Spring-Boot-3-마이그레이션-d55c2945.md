# 실전! Spring Boot 3 마이그레이션

> [!abstract] 한 줄 정리
> Spring Boot 메이저 업그레이드는 버전 숫자만 바꾸는 일이 아니라 Java·Jakarta EE·Security·Batch·JPA·Tracing·Flyway·테스트 생태계의 계약을 함께 옮기는 작업이다. 큰 점프보다 공식 변경점을 분해하고 단계적으로 이관하는 방식이 안전하다.

> LY Corporation Tech Blog · 2023-11-08

## 핵심 내용

- **접근:** 공식 Migration Guide와 Release Note를 먼저 읽고, 오래된 Boot 버전이라면 한 번에 3으로 뛰기보다 중간 버전을 거쳐 변경점을 단계적으로 흡수할 것을 권한다.
- **구조:** Java 17+, Jakarta EE 전환과 함께 Spring Cloud Sleuth→Micrometer Tracing, Spring Batch 5, Spring Security 6 등 연관 프로젝트 변경을 각각 분리해 대응한다.
- **주의점:** Spring Batch 5에서는 Job/Step 빌더 구성과 잡 파라미터 방식 등이 바뀌고, Spring Security 6에서는 WebSecurityConfigurerAdapter 대신 SecurityFilterChain 등 Bean 기반 구성이 중심이 된다.
- **트레이드오프:** MySQL 5.7처럼 최신 Spring 생태계와 지원 범위가 어긋나는 기존 인프라를 유지하면 Flyway 자동 설정 같은 편의 기능을 포기하고 별도 설정을 책임져야 한다.
- **검증:** Mockito 5의 varargs 매칭처럼 프레임워크 외곽의 테스트 라이브러리 변경도 기존 테스트를 깨뜨릴 수 있어, 메이저 업그레이드 범위를 애플리케이션 코드에만 한정하면 안 된다.

## 왜 읽을까

오래된 글이지만 Spring 메이저 버전 전환을 “컴파일 오류를 고치는 작업”이 아니라 의존 생태계의 계약 변경으로 보는 방식은 여전히 유효하다. Spring Security·Batch·JPA처럼 평소 따로 배우는 기술이 버전 전환에서 어떻게 한꺼번에 연결되는지도 보기 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] Spring/Security 메이저 업그레이드 전에 현재 의존성·설정·deprecated API 목록을 먼저 인벤토리화한다.
- [ ] 인증 흐름은 회원가입→로그인→세션 유지→인가→로그아웃을 통합 테스트로 고정해 Security 설정 변경의 회귀를 잡는다.
- [ ] 버전 변경과 기능 리팩터링을 가능한 한 분리해 문제가 생겼을 때 원인을 좁힐 수 있게 한다.
