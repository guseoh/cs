# Flutter + Kiwi 한국어 형태소 분석 플러그인 개발기: 온디바이스 구현, 코드 예제, 벤치마크까지

> [!abstract] 한 줄 정리
> 온디바이스 한국어 형태소 분석은 서버 호출을 줄이지만 네이티브 브리지, 모델 파일 배포, 초기화 비용이 생긴다. 선택은 단순 처리량보다 배포·운영·프라이버시까지 포함해 판단해야 한다.

> 개인 Medium 블로그 · Dreamwalker(박제창) · 2026-02-17

## 핵심 내용

- **문제:** Flutter에서 Kiwi 형태소 분석을 플랫폼마다 따로 연결해야 했고, 모델 경로·초기화·배포 실패가 실제 사용을 막았어. - **구조:** 네이티브에서는 FFI, 웹에서는 WASM을 사용하되 앱에는 동일한 `KiwiAnalyzer` API를 제공한다. 모델은 명시 경로 → 번들 에셋 → 다운로드·캐시 순서로 찾는 fallback을 설계했다. - **접근:** 분석기를 UI에서 직접 다루지 않고 서비스 계층에 격리해 초기화·종료·오류를 한곳에서 관리해. 런타임 사용자 사전과 플랫폼별 빌드 준비 스크립트도 제공한다.

- **수치:** 2026-02-17 macOS arm64, release 모드, 40문장, warmup 3회·measure 15회·topN 1 조건에서 Flutter 플러그인은 초당 2,408.41회·평균 0.42ms, Python `kiwipiepy`는 3,666.54회·0.27ms였어. - **트레이드오프:** Flutter 측은 FFI 경계와 직렬화·초기화 비용이 있고 토큰 수에도 9,660 대 9,645의 차이가 있었어. 더 느린 절대 수치에도 오프라인 동작, 공통 API, 개인정보 외부 전송 감소라는 이점을 선택 근거로 제시해.

Flutter 앱이 Kiwi를 직접 호출하는 API를 플랫폼별로 다르게 노출하면 화면 로직이 데스크톱·모바일·웹을 각각 알아야 한다. `KiwiAnalyzer`로 통합하고 하부에서 네이티브 FFI와 WASM을 선택하면 실행 위치 차이를 감출 수 있지만, 모델 파일의 탐색 경로와 초기화 실패 처리까지 동일한 계약으로 정의해야 한다. 명시 경로 → 번들 에셋 → 다운로드·캐시의 Fallback은 네트워크가 끊기거나 앱 패키징 방식이 달라졌을 때의 복원력을 높인다.

| 비교할 비용 | 네이티브 FFI | 웹 WASM |
| --- | --- | --- |
| 실행 경로 | 플랫폼 라이브러리 로딩 | WASM 초기화·브라우저 제약 |
| 모델 배포 | OS·아키텍처별 파일 | 번들 크기·캐시 |
| 호출 오버헤드 | Dart↔Native 경계 | JS↔WASM 경계 |
| 개인정보 | 로컬 분석 가능 | 로컬 실행 가능 |

제시된 2,408.41회/초와 3,666.54회/초는 특정 macOS arm64 환경·40문장·워밍업 및 측정 조건의 결과다. 분석 결과의 토큰 차이도 존재했으므로 단순 처리량만이 아니라 정확도·초기화 비용·오프라인 요구를 함께 평가해야 한다.
