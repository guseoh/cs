# 모두가 데이터를 다루는 AI 시대, 지난 1년간 데이터 팀은 어떻게 달라졌을까?

> [!abstract] 한 줄 정리
> 자연어로 데이터를 쉽게 조회하게 만드는 것보다 더 중요한 것은 AI가 신뢰할 수 있는 지표 정의·리니지·권한·최신성·검증 체계를 플랫폼의 기본 동작으로 만드는 것이다.

> 당근 기술 블로그 · 2026-04-22

## 핵심 내용

AI가 SQL 초안과 데이터 품질 영향 범위 분석, 파이프라인 장애 원인 탐색을 보조하게 되면 데이터 엔지니어의 역할은 쿼리 하나를 잘 작성하는 것에서 지표·권한·리니지·갱신 정책을 설계하고 검증하는 쪽으로 이동한다. 당근은 데이터 도구를 각각 AI에 연결하는 대신 공통 `data-mcp` 인터페이스를 두었다.

 ```mermaid
flowchart LR
 A[데이터 분석가·AI Agent] --> B[data-mcp 공통 진입]
 B --> C[BigQuery·Superset]
 B --> D[KarrotMetrics·Event·Experiment]
 B --> E[Lineage·권한·최신성]
 E --> F[출처 포함 결과·승인 경계]
```

*원문 근거를 바탕으로 자체 재구성한 가로형 학습 도식이다.*

`data-mcp`는 BigQuery, 데이터 Lineage, KarrotMetrics, Superset, Event, Experiment와 연결되어 질문에 필요한 데이터 소스를 선택한다. AI가 지표를 계산하려면 KarrotMetrics의 코드로 버전 관리된 정의와 컬럼 레벨 리니지를 함께 확인해야 서로 다른 팀의 '매출'을 같은 지표로 오인하지 않는다. 소스·테이블 권한은 사용자에게 있는 그대로 적용하고 문서의 소유자와 최신성을 같이 전달해야 한다.

| 자산 | Agent에 제공할 것 | 신뢰를 위한 제약 |
| --- | --- | --- |
| BigQuery | 데이터 조회 | 사용자 권한·비용 |
| KarrotMetrics | 지표 정의 | 버전·정본 의미 |
| Column Lineage | 상하위 데이터 관계 | 최신성·영향 범위 |
| Experiment/Event | 실험·행동 근거 | 세그먼트·분모 구분 |
| MCP 라우팅 | 도구 선택과 결과 | 쓰기·관리 작업 승인 |

사용자가 자연어만으로 데이터에 접근하기 쉬워져도 잘못된 지표나 무단 접근까지 안전해진 것은 아니다. 읽기 질의와 메타데이터 설명은 넓혀도 쓰기·스키마 변경·권한 요청은 별도 승인 경계가 있어야 한다. 원문은 팀 역할의 변화와 실제 도구 구성을 소개하지만 검증 가능한 시간 절감률 하나로 효과를 정량화하지는 않는다.

## 왜 읽을까

AI를 데이터 조직의 생산성 도구로만 보는 대신 **데이터 거버넌스와 플랫폼 설계 문제**로 확장해 볼 수 있다. 특히 “답이 없는 것이 틀린 답보다 안전하다”는 기준은 AI가 사내 데이터에 접근할 때 좋은 안전 원칙이 된다.

**프로젝트에 적용 — DevPedia**

- [ ] AI가 사용하는 프로젝트 지표·통계를 코드 또는 명시적 정의에서만 가져오도록 근거 소스를 고정한다.
- [ ] 통계 응답에 정의, 계산 기준, 최신 시점 같은 메타데이터를 함께 제공할 수 있는지 검토한다.
- [ ] AI가 접근할 수 없는 정보는 추론으로 채우지 않고 명시적으로 실패하도록 권한 경계를 둔다.
