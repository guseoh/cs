# 응? 이게 왜 롤백되는거지?

> [!abstract] 한 줄 정리
> Spring 트랜잭션의 롤백 여부는 코드 모양보다 실제 트랜잭션 경계와 예외 전파 방식에 따라 결정됩니다.

> techblog.woowahan.com

## 핵심 내용

서비스 코드에서 예상과 다르게 트랜잭션이 rollback-only 상태가 되는 상황을 통해 Spring의 트랜잭션 경계와 예외 처리 동작을 설명합니다. 내부에서 예외를 잡았다고 해서 이미 트랜잭션 인프라가 기록한 롤백 상태까지 되돌아가는 것은 아니라는 점이 핵심입니다.

Spring 트랜잭션은 내부 메서드에서 예외를 `catch`했다고 해서 이미 기록된 **rollback-only** 상태가 지워지는 구조가 아니다. 트랜잭션 경계 내부에서 예외가 발생해 프록시가 해당 트랜잭션을 롤백 대상으로 표시했다면 바깥 계층이 예외를 잡고 정상적으로 반환하더라도 최종 커밋 시점에 `UnexpectedRollbackException`이 발생할 수 있다.

```java
// 개념 설명용 재구성: 내부의 롤백 표시를 바깥 catch가 취소하지 못함
@Transactional
void placeOrder() {
    try {
        paymentService.reserve(); // 같은 트랜잭션에 참여한 내부 호출
    } catch (PaymentException ignored) {
        // 예외를 처리해도 rollback-only 상태는 유지될 수 있음
    }
}
```

| 확인할 경계 | 핵심 질문 |
| --- | --- |
| 프록시 호출 | 실제 `@Transactional` 적용 대상인가? |
| Propagation | 같은 트랜잭션에 참여하는가? |
| 롤백 규칙 | Checked/Unchecked 예외 정책은? |
| 최종 Commit | rollback-only 표시가 남았는가? |

독립적으로 반드시 저장해야 할 실패 이력은 별도 트랜잭션과 도메인 복구 설계를 검토할 수 있지만, 단순히 예외를 삼키는 해결책은 정합성을 보장하지 못한다.

## 왜 읽을까

`@Transactional`을 붙이는 문법보다 예외가 어느 레이어를 지나고 어떤 트랜잭션에 참여하는지를 추적하는 습관을 만들기 좋은 고전적인 사례입니다.
