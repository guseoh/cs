# \[카카오테크 캠퍼스\] 2025년 회고

> [!abstract] 한 줄 정리
> AI와 멘토링을 많이 활용할수록 결과를 받아들이는 것보다 자신의 판단 근거를 만들고 설명하는 훈련이 더 중요해집니다.

> ezilog.dev

## 핵심 내용

카카오테크 캠퍼스 활동을 돌아보며 학습, 코드 리뷰, TIL, 멘토 피드백을 통해 구현 결과보다 '왜 이렇게 설계했는가'를 설명하는 능력을 키운 과정을 정리합니다. 특히 AI에 의존해 답을 빠르게 얻는 방식에서 벗어나 자신의 생각을 먼저 세우는 태도를 강조합니다.

멘토링과 코드 리뷰를 학습 기록으로 남기는 목적은 구현 결과를 자랑하기보다 **어떤 가정이 틀렸고 무엇을 검증했는지 재사용**할 수 있게 하는 것이다. 특히 AI에게 즉시 정답을 요청하면 코드가 동작하더라도 자신이 선택한 대안의 이유를 말하지 못할 수 있다. 먼저 도메인 제약과 자신의 가설을 쓰고, 실제 테스트나 멘토 피드백으로 수정하는 학습 방식이 설계 능력 향상에 유리하다.

| 학습 단계 | 남겨야 할 증거 |
| --- | --- |
| 요구사항 이해 | 제한조건·모호한 입력 |
| 설계 결정 | 대안과 선택 이유 |
| 구현·테스트 | 작동한 범위·실패 사례 |
| 코드 리뷰 | 수정 요청의 근거 |
| 회고 | 다음에 바꿀 판단 방식 |

이는 특정 기술의 벤치마크가 아니라 개인 경험 기반의 회고이므로 생산성 향상 수치를 임의로 만들어 넣지 않고 학습 방법의 변화에 집중해야 한다.

## 왜 읽을까

기술 하나를 깊게 설명하는 글은 아니지만, 프로젝트 중심 학습에서 피드백과 기록을 어떻게 자기 실력으로 바꿀지 생각해보기 좋습니다.

**프로젝트에 적용**

**DevPedia·PawCycle·FutMatch 공통** — AI가 만든 구현을 승인할 때 `왜 이 구조인가`, `다른 선택지는 무엇인가`, `어떻게 검증했는가`를 짧게라도 직접 기록하는 습관으로 연결할 수 있습니다.
