# 우리 팀만의 vLLM 플러그인 만들기 1편 - 검색 AI 모델 서빙 성능 극대화하기

> [!abstract] 한 줄 정리
> 모델 자체를 바꾸지 않고도 런타임과 요청 경로를 재설계하면 서빙 성능이 크게 달라질 수 있다. 성능 숫자가 너무 좋을 때는 자료형·배치·캐시 같은 숨은 변수를 다시 의심해야 한다.

> NAVER D2 · 2026-08-10

## 핵심 내용

검색·추천 스코어링 모델은 한 요청에서 후보 수십~수백 개를 평가해야 하는데, 전처리·토큰화·모델 서버·후처리가 분리돼 네트워크 왕복과 직렬화 비용이 누적됐다. 모델을 vLLM 풀링 런타임의 사용자 정의 모델로 옮기고, IO Processor 안으로 전후처리를 통합해 요청 경로를 줄였다. vLLM 자체는 포크하지 않고 외부 플러그인 패키지로 배포했다.

0.6B 재순위화 모델은 63.85 QPS에서 397.21 QPS로 약 6.2배, ABSA 모델 p50은 101.22ms에서 16.43ms로 83.8% 감소했다. 이미지 랭킹은 3.76 img/s에서 62.2 img/s로 누적 16.5배 향상됐다. 처음 나온 13.1배 개선은 vLLM의 자동 FP16 변환 효과가 섞인 값이었다. FP32로 조건을 맞추자 순수 런타임 개선 폭은 4.05배였고, 이후 자료형을 명시적으로 고정하는 규칙을 만들었다.

전후처리를 GPU 파드 내부로 옮기면 CPU 비용도 함께 들어온다. 이미지 디코딩처럼 무거운 CPU 작업은 오히려 GPU 대기를 늘릴 수 있어 병렬성과 입력 최적화를 별도로 측정해야 한다.

| 대상 | 기존 측정 | 변경 후 | 읽는 법 |
| --- | ---: | ---: | --- |
| 재순위화 0.6B 모델 | 63.85 QPS | 397.21 QPS | 동일 모델 경로 비교 |
| ABSA p50 | 101.22ms | 16.43ms | 단건 지연 비교 |
| 이미지 랭킹 | 3.76 img/s | 62.2 img/s | 이미지 처리량 비교 |

처음 관측한 13.1배 수치를 그대로 런타임 효과라고 발표하지 않고 FP16 자동 변환 효과를 분리해 4.05배로 재평가한 과정이 중요하다. 모델 정밀도가 달라지면 추론 성능과 품질이 모두 영향을 받으므로 코드 최적화, 자료형, 배치 크기의 실험 조건을 분리해야 재현 가능한 성능 개선이 된다.

## 왜 읽을까

프레임워크를 바꿔서 빨라졌다는 결과보다, 어디에서 시간이 새는지 네트워크·직렬화·GPU 커널까지 내려가 확인하는 과정이 좋다. Before/After 숫자를 그대로 믿지 않고 조건을 맞춰 다시 측정하는 태도도 성능 실험의 좋은 기준이 된다.

**프로젝트에 적용 — PawCycle**

- [ ] 큰 개선 폭이 나오면 설정·캐시·자료형·테스트 데이터 차이가 섞이지 않았는지 동일 조건으로 재측정한다.
