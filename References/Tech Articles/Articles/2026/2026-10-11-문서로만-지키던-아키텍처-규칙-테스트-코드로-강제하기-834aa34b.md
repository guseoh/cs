# 문서로만 지키던 아키텍처 규칙, 테스트 코드로 강제하기

> [!abstract] 한 줄 정리
> 아키텍처 규칙을 위키나 AI 지침에만 두면 리뷰 누락과 에이전트의 규칙 위반을 막기 어렵다. ArchUnit 테스트와 CI로 신규 위반을 차단하면서 기존 레거시는 동결해 점진적으로 줄일 수 있다.

> 우아한형제들 기술블로그 · 2026-09-07

## 핵심 내용

아키텍처 규칙을 위키와 AI 에이전트 지침으로만 공유하면 사람이 코드 리뷰에서 위반을 계속 찾아야 하고 세션마다 AI가 다른 구조를 생성할 수 있다. 우아한형제들은 도메인 레이어의 의존 방향, 필드 주입 금지, 네이밍 같은 규칙을 ArchUnit 테스트와 CI에 연결해 코드 수준에서 강제했다.

![ArchUnit FreezingArchRule의 기존 위반 동결 및 신규 위반 검증 흐름](https://techblog.woowahan.com/wp-content/uploads/2026/08/8-freezing-archrule-flow.svg)

*그림 1. 원문 FreezingArchRule 흐름도: 기존 위반을 기준으로 관리하고 신규 위반은 실패 처리 — [출처: 원문 기술 블로그](https://techblog.woowahan.com/26835/)*

ArchUnit 1.3.0과 JUnit 테스트를 독립 모듈로 두고, 위반이 거의 없는 의존 규칙부터 CI에서 차단했다. 기존 코드에 수천 개의 위반이 있을 때 한 번에 모든 코드를 고치는 대신 `FreezingArchRule`로 기존 위반 목록을 Git 파일에 동결했다. 동결 목록에 없는 새로운 위반은 빌드를 실패시키고, 기존 위반을 수정하면 동결 목록이 감소해 리팩터링 진행 상태를 볼 수 있다. 반대로 동결 파일이 늘어나는 PR은 신규 위반을 우회했을 가능성이 있어 반드시 리뷰해야 한다.

```java
// 도메인 계층의 인프라 의존을 금지하는 ArchUnit 규칙의 학습 예시
ArchRule domainMustNotDependOnInfrastructure = noClasses()
    .that().resideInAPackage("..domain..")
    .should().dependOnClassesThat()
    .resideInAPackage("..infrastructure..");
```

실제 패키지 규칙은 프로젝트의 아키텍처 계약과 Kotlin/Java 클래스 경계에 맞춰 검증해야 한다.

정책을 코드로 표현해도 그 규칙 자체가 제품의 실제 설계 목적에 맞는지 검토하는 역할은 남는다. 지나치게 일반적인 패키지 패턴은 도메인 패키지를 잘못 분류할 수 있고 동결 파일을 허용 없이 증가시키면 테스트를 무력화할 수 있다. 원문의 단계별 도입은 '규칙이 맞는가'와 '기존의 위반을 한 번에 없앨 수 있는가'를 분리한 실무 전략이다.

## 왜 읽을까

‘아키텍처를 문서화했다’와 ‘아키텍처가 유지된다’ 사이의 차이를 보여준다. 코드 리뷰어의 기억과 AI 프롬프트에 의존하는 규칙을 실행 가능한 회귀 테스트로 옮기면서도 기존 코드 전체를 즉시 수정하지 않는 현실적인 도입 전략을 얻을 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 현재 패키지·모듈 의존성 규칙(Controller→Service→Repository 등) 중 실제 지켜야 할 것만 명문화한다.
- [ ] ArchUnit으로 도메인 계층이 웹·인프라 구현에 직접 의존하지 않는지 테스트하고 CI에 연결한다.
- [ ] 기존 위반은 필요 시 baseline으로 동결하되 신규 위반 0건을 유지하고 동결 목록의 증가를 리뷰한다.
