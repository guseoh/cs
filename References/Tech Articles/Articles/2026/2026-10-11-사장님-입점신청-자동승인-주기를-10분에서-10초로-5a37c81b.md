# 사장님 입점신청 자동승인 주기를 10분에서 10초로

> [!abstract] 한 줄 정리
> 스케줄러 주기만 줄이지 않고 후보 조회·재시도·중복 선점의 책임을 분리해 승인 시작 대기를 최대 12분 59초에서 10초 이내로 줄였다. 상태 재조정이 필요한 업무에서는 이벤트보다 폴링이 더 안전하고 단순할 수 있다.

> 우아한형제들 기술블로그 · 2026-09-23

## 핵심 내용

입점 신청 자동승인은 원래 요청을 후보 큐에 넣는 enqueue와 실제 처리하는 process가 10분 간격으로 움직였기 때문에 시작까지 최소 3분에서 최대 12분 59초가 걸렸다. 단순히 Cron을 10초로 줄이면 대량 후보 조회와 외부 API 호출이 같은 비율로 늘어나 운영 부담이 커질 수 있었다.

 ```mermaid
flowchart LR
 A[신규 신청·RETRY_WAITING] --> B[상태·nextRetryTime 조회]
 B --> C[10초 폴링 신규 건 / 기존 재시도 간격]
 C --> D[Redis 요청별 선점 락]
 D --> E[Writer DB 상태 재확인]
 E --> F[외부 승인 API]
 F --> G[성공·재시도·실패 상태 기록]
```

*원문 책임 분리를 바탕으로 재구성한 가로형 흐름이다. Redis 락이 있다고 DB의 최종 상태 검사가 불필요해지는 것은 아니다.*

auto_approve_outbox 큐를 없애고 원본 신청과 `auto_approve_state`를 직접 조회하면서 신규 신청과 RETRY_WAITING 상태를 분리했다. 신규 건은 10초 폴링을 적용하지만 재시도 건에는 `nextRetryTime`을 두어 기존 10분 간격 정책을 유지했다. 여러 워커가 동시에 같은 요청을 찾더라도 Redis 락으로 먼저 선점하고 실제 쓰기 DB에서 상태를 다시 확인해 읽기 Replica 지연과 락 만료에 따른 중복을 줄인다. 처리 중 죽어 IN_PROGRESS에 남은 건은 클렌징 스케줄러가 회수한다.

| 판단 | 측정·조건 | 선택 이유 |
| --- | --- | --- |
| 기존 시작 대기 | 3분~12분 59초 | enqueue/process 10분 주기 |
| 신규 신청 조회 | 10초 주기 | 사용자 체감 대기 단축 |
| 기존 재시도 | 10분 간격 유지 | 외부 시스템 부하 억제 |
| SKIP LOCKED 실험 | 20건 선점 중 394행 락 | 요청 테이블 경합 회피 |
| 워커 실패 | IN_PROGRESS 잔여 | 별도 클렌징 처리 |

조건부 UPDATE나 SKIP LOCKED는 DB만으로 선점할 수 있지만, 테스트에서 20건을 가져오는 동안 394행을 잠그는 부작용이 확인되어 부담이 컸다. Redis 락은 DB 락 경합을 줄이는 대신 락 저장소와 상태 DB 사이의 일관성 계약을 만들어야 한다. 입력량이 처리 능력을 넘지 않는다는 전제에서 신규 건의 처리 시작 대기는 최대 12분 59초에서 10초 이내로 줄었다.

## 왜 읽을까

주기를 60배 빠르게 바꾸는 것보다 발견 주기와 재시도 주기를 분리하는 설계가 핵심이다. ‘이벤트가 왔는가’보다 ‘지금 승인 가능한 상태인가’를 반복 확인하는 reconciliation 모델을 배울 수 있다.

락을 Redis, 조건부 UPDATE, SKIP LOCKED 중에서 선택할 때 기능 가능 여부만이 아니라 잠금 범위, 복제 지연, 실패한 선점 비용을 실제 실행 계획과 두 세션 실험으로 판단한 과정도 유용하다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기 참가 승인·대기자 승격에서 ‘새 신청 발견 주기’와 ‘실패 재시도 주기’를 별도 상태와 정책으로 정의한다.
- [ ] 동일 신청을 워커 두 개가 동시에 처리하는 테스트를 만들고 중복 승인·중복 알림이 없는지 확인한다.
- [ ] DB 조건부 UPDATE와 Redis 락 중 실제 처리량·DB 쓰기 부하를 측정한 뒤 단순한 방식을 우선 선택한다.
