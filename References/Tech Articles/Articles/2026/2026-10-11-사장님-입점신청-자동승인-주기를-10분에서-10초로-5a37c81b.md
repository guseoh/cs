# 사장님 입점신청 자동승인 주기를 10분에서 10초로

> [!abstract] 한 줄 정리
> 스케줄러 주기만 줄이지 않고 후보 조회·재시도·중복 선점의 책임을 분리해 승인 시작 대기를 최대 12분 59초에서 10초 이내로 줄였다. 상태 재조정이 필요한 업무에서는 이벤트보다 폴링이 더 안전하고 단순할 수 있다.

> 우아한형제들 기술블로그 · 2026-09-23

## 핵심 내용

- **문제:** 후보를 DB 작업 큐에 넣는 enqueue와 처리하는 process가 10분 주기로 분리돼 자동승인 시작까지 최소 3분, 최대 12분 59초가 걸렸다. 무거운 후보 조회와 건별 외부 API 호출 때문에 주기만 단축할 수 없었다.
- **구조:** 큐 역할의 auto\_approve\_outbox를 제거하고 요청 테이블과 auto\_approve\_state를 함께 조회한다. 신규 건과 RETRY\_WAITING 건을 구분하고 nextRetryTime을 상태에 기록해 10초 폴링과 기존 10분 재시도를 분리했다.
- **동시성:** N대 워커가 모두 폴링하되 요청 단위 Redis 락으로 선점한다. 쓰기 DB에서 상태를 재확인해 Replica Lag과 락 만료로 인한 중복을 막고, 서버 중단 후 IN\_PROGRESS에 남은 건은 별도 클렌징 스케줄러로 복구한다.
- **트레이드오프:** 조건부 UPDATE는 단순하지만 실패한 선점도 쓰기 DB에 도달한다. SKIP LOCKED 실험은 20건을 선점하면서 394행이 잠겨 요청 테이블의 다른 쓰기를 방해했다. Redis 락은 DB 부담을 줄이지만 두 저장소 간 선점·상태 기록 경계가 복잡해진다.
- **결과:** 유입량이 처리 용량을 넘지 않는다는 전제에서 처리 시작 대기가 최대 12분 59초에서 10초 이내로 줄었다. 재시도 간격은 유지하고 외부 시스템 호출 부하는 늘리지 않았다.

## 왜 읽을까

주기를 60배 빠르게 바꾸는 것보다 발견 주기와 재시도 주기를 분리하는 설계가 핵심이다. ‘이벤트가 왔는가’보다 ‘지금 승인 가능한 상태인가’를 반복 확인하는 reconciliation 모델을 배울 수 있다.

락을 Redis, 조건부 UPDATE, SKIP LOCKED 중에서 선택할 때 기능 가능 여부만이 아니라 잠금 범위, 복제 지연, 실패한 선점 비용을 실제 실행 계획과 두 세션 실험으로 판단한 과정도 유용하다.

**프로젝트에 적용 — FutMatch**

- [ ] 경기 참가 승인·대기자 승격에서 ‘새 신청 발견 주기’와 ‘실패 재시도 주기’를 별도 상태와 정책으로 정의한다.
- [ ] 동일 신청을 워커 두 개가 동시에 처리하는 테스트를 만들고 중복 승인·중복 알림이 없는지 확인한다.
- [ ] DB 조건부 UPDATE와 Redis 락 중 실제 처리량·DB 쓰기 부하를 측정한 뒤 단순한 방식을 우선 선택한다.
