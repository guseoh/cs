# 모노리포 희망편, 절망의 리포가 희망의 리포로 부활하기까지 걸린 1년

> [!abstract] 한 줄 정리
> 모노리포 자체보다 중요한 것은 공통 의존성의 버전과 업그레이드 경로를 플랫폼 정책으로 관리하는 일입니다. 표준을 강제하되 새 버전은 점진적으로 검증하고 자동 마이그레이션 경로까지 제공해야 규모가 커져도 일관성을 유지할 수 있습니다.

> Toss Tech · 2026-08-10

## 핵심 내용

- **문제:** 100명이 넘는 프론트엔드 엔지니어가 하나의 모노리포를 쓰지만 서비스마다 React·TypeScript 등 핵심 의존성 버전이 달라 설치 시간, 개발 경험, 공통 라이브러리 검증 비용이 커졌습니다.
- **접근:** 핵심 라이브러리 버전을 `Catalog`로 정의하고 신규 서비스는 기본적으로 해당 카탈로그를 참조하게 했으며, 직접 다른 버전을 설치하는 실수는 CI에서 차단했습니다.
- **결과:** Yarn PnP의 `.pnp.cjs`가 96MB에서 15MB로 약 84% 감소했고, 개발 서버 기동은 26.7초→20.3초로 약 23%, 전체 의존성 설치는 528.4초→249.9초로 약 52% 개선됐습니다.
- **구조:** 기존 카탈로그의 파괴적 변경은 금지하고 새 카탈로그를 발행해 일부 서비스에서 먼저 검증한 뒤 이동하도록 했습니다. 월 최대 한 번 새 카탈로그를 발행하고, 코드 변환 스크립트와 CLI·AI Skill로 업그레이드 비용을 낮췄습니다.
- **트레이드오프:** 표준화가 개발자의 자유도를 일부 줄이지만, 서비스별 임의 선택보다 검증 가능한 공통 기반과 예측 가능한 마이그레이션 경로를 우선했습니다.

## 왜 읽을까

'모노리포를 쓰면 코드 공유가 쉽다'는 수준을 넘어, **규모가 커진 뒤 표준화를 어떻게 운영 정책과 자동화로 유지하는지**를 보여줍니다. 라이브러리 버전 업그레이드를 개인의 숙제가 아니라 플랫폼의 책임으로 보는 관점이 좋습니다.

**프로젝트에 적용 — 공통**

- [ ] 여러 프로젝트에서 반복 사용하는 Java·Spring·Gradle·Node 도구 버전 중 반드시 통일할 것과 프로젝트별 선택으로 남길 것을 구분하기
- [ ] 공통 버전 변경 시 한 번에 올리지 않고 테스트 프로젝트 또는 한 서비스에서 먼저 검증하는 경로 만들기
- [ ] 버전 업그레이드 과정에서 반복되는 수정은 문서보다 스크립트나 Codex Skill 후보로 추출하기
