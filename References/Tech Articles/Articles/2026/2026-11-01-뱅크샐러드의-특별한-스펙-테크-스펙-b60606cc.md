# 뱅크샐러드의 특별한 스펙, '테크 스펙'

> [!abstract] 한 줄 정리
> 기능 구현 전에 목표·제외 범위·기술적 선택·마일스톤을 공유 문서로 합의하면, 코드 리뷰 때 설계 의도를 재설명하고 요구 변경을 뒤늦게 발견하는 비용을 줄일 수 있습니다.

> 뱅크샐러드 기술 블로그 · 2020-10-26

## 핵심 내용

코드를 작성한 뒤 리뷰 과정에서 설계 배경을 처음 설명하면 이미 구현에 비용을 지출한 상태라 방향을 바꾸기 어렵다. 뱅크샐러드는 기능의 목표와 하지 않을 일, 대안, API 및 데이터 흐름, 마일스톤을 구현 전에 기술 스펙으로 정리해 팀이 같은 문제를 보고 판단하도록 했다.

테크 스펙의 핵심은 긴 문서를 쓰는 데 있지 않다. 요구사항을 검토하는 사람에게 현재의 제약, 설계가 지키는 계약, 의도적으로 제외한 기능, 선택하지 않은 대안과 그 이유를 명확히 전달하는 것이 목적이다. 필요한 경우 시퀀스 다이어그램과 ERD, 요청·응답 예시를 사용하지만 모든 섹션을 기계적으로 같은 깊이로 채우지는 않는다.

```markdown
<!-- 원문 항목을 바탕으로 재구성한 최소 테크 스펙 예시 -->
**목표:** 모집 승인 상태의 일관성 확보
**Non-Goals:** 알림 플랫폼 교체 제외
**계약:** 승인 시 지원 상태는 한 번만 전이
**검증:** 중복 승인·동시 요청 통합 테스트
```

이처럼 문서 한 장에서 왜 선택했는지와 어떻게 검증할지를 연결하는 것이 중요하다.

| 테크 스펙 항목 | 답해야 할 설계 질문 |
| --- | --- |
| 배경·목표 | 어떤 사용자·운영 문제가 있고 성공 기준은 무엇인가 |
| Non-Goals | 이번 구현에서 의도적으로 제외할 범위는 무엇인가 |
| 대안과 트레이드오프 | 어떤 제약 때문에 선택하거나 기각했는가 |
| API·데이터·오류 계약 | 호출자와 저장소에 무엇을 보장하는가 |
| 마일스톤·검증 | 완료를 어떤 테스트·관측으로 입증하는가 |

*원문은 작성과 합의의 실제 과정을 소개하지만 문서화로 줄어든 시간을 정량 측정하지는 않았다.*

리뷰어가 문서를 통해 설계 의도를 사전에 검토하면 PR에서는 이미 합의한 계약을 구현했는지 평가할 수 있다. 범위가 바뀌거나 트레이드오프 판단이 달라지면 스펙과 결정 이력도 갱신해야 이후 담당자가 같은 논쟁을 반복하지 않는다. 원문은 문서 작성의 실무 가치를 제시하지만 정량적인 시간 절감 수치는 제공하지 않는다.

## 왜 읽을까

설계 문서를 단순한 산출물이 아니라 의사결정과 작업 분할의 입력으로 다루는 글입니다. AI가 코드를 작성하는 환경에서도 사람의 요구 정의·Trade-off·완료 조건을 먼저 확정하는 실무 습관을 만드는 데 직접적입니다.

**프로젝트에 적용 — DevPedia**

- [ ] DB·API 설계 대안과 채택·기각 이유를 남깁니다.
