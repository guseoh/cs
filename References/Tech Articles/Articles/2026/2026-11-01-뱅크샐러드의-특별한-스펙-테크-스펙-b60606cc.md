# 뱅크샐러드의 특별한 스펙, '테크 스펙'

> [!abstract] 한 줄 정리
> 기능 구현 전에 목표·제외 범위·기술적 선택·마일스톤을 공유 문서로 합의하면, 코드 리뷰 때 설계 의도를 재설명하고 요구 변경을 뒤늦게 발견하는 비용을 줄일 수 있습니다.

> 뱅크샐러드 기술 블로그 · 2020-10-26

## 한눈에 보기

코드가 작성된 뒤 PR에서 설계 이유를 처음 논의하면 비용이 이미 발생한 상태여서 변경 방향을 수정하기 어렵다. 뱅크샐러드의 테크 스펙은 목적·비목표·대안·API 계약·계획을 구현 전에 공유해 판단의 근거를 남기는 장치다. 설계 문서가 길수록 좋은 것이 아니라 검토자가 중요한 제약과 완료 기준을 찾을 수 있어야 한다.

```mermaid
flowchart LR
  A[배경·문제 정의] --> B[목표·Non-Goals]
  B --> C[대안·트레이드오프]
  C --> D[API·DB·시퀀스 설계]
  D --> E[팀 리뷰·범위 합의]
  E --> F[작은 PR·테스트·마일스톤]
  F --> G[결정 문서 갱신]
```

*원문 내용을 바탕으로 자체 재구성한 개략 흐름도다.*

테크 스펙에는 기능 목표뿐 아니라 의도적으로 하지 않을 일과 결정이 나중에 바뀔 수 있는 조건이 함께 있어야 한다. API 요청·응답, 오류 계약, 데이터 모델과 의존 관계는 팀의 합의 수준에 맞게 상세도를 정한다. 구현 후 문서를 방치하면 다시 구두 설명에 의존하게 되므로 변경 이력과 문서 갱신 책임도 생각해야 한다.

## 핵심 내용

### 문제와 제약

**문제:** PR과 구두 설명에만 설계 배경이 남아 작성자가 바뀌면 의도를 찾기 어렵고, 기능 요구가 변할 때 작업 범위와 일정이 흔들렸습니다.

### 설계 선택과 실제 구현

**접근:** 개발 전에 테크 스펙을 작성해 배경, 목표, Non-Goals, 구현 계획, 대안, 마일스톤을 명시하고 전체 기술 구성원의 리뷰를 받습니다.

**구조:** 계획에는 API 요청·응답·오류 계약, 데이터 흐름, 시퀀스 다이어그램, ERD 등을 필요한 깊이로 포함합니다. 선택하지 않은 대안도 이유와 함께 기록합니다.

### 결과·한계·운영 판단

**결과:** 문서를 PR과 작업 계획의 공통 맥락으로 사용해 중복 설명과 범위 확장을 줄이려 했습니다. 글에는 이 방식의 정량적인 시간 절감 측정은 없습니다.

### 주요 비교와 확인 기준

| 테크 스펙 항목 | 답해야 할 설계 질문 |
| --- | --- |
| 배경·목표 | 어떤 사용자·운영 문제가 있고 성공 기준은 무엇인가 |
| Non-Goals | 이번 구현에서 의도적으로 제외할 범위는 무엇인가 |
| 대안과 트레이드오프 | 어떤 제약 때문에 선택하거나 기각했는가 |
| API·데이터·오류 계약 | 호출자와 저장소에 무엇을 보장하는가 |
| 마일스톤·검증 | 완료를 어떤 테스트·관측으로 입증하는가 |

*원문은 작성과 합의의 실제 과정을 소개하지만 문서화로 줄어든 시간을 정량 측정하지는 않았다.*

## 왜 읽을까

설계 문서를 단순한 산출물이 아니라 의사결정과 작업 분할의 입력으로 다루는 글입니다. AI가 코드를 작성하는 환경에서도 사람의 요구 정의·Trade-off·완료 조건을 먼저 확정하는 실무 습관을 만드는 데 직접적입니다.
