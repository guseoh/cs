# 뱅크샐러드의 특별한 스펙, '테크 스펙'

> [!abstract] 한 줄 정리
> 기능 구현 전에 목표·제외 범위·기술적 선택·마일스톤을 공유 문서로 합의하면, 코드 리뷰 때 설계 의도를 재설명하고 요구 변경을 뒤늦게 발견하는 비용을 줄일 수 있습니다.

> 뱅크샐러드 기술 블로그 · 2020-10-26

## 핵심 내용

- **문제:** PR과 구두 설명에만 설계 배경이 남아 작성자가 바뀌면 의도를 찾기 어렵고, 기능 요구가 변할 때 작업 범위와 일정이 흔들렸습니다.
- **접근:** 개발 전에 테크 스펙을 작성해 배경, 목표, Non-Goals, 구현 계획, 대안, 마일스톤을 명시하고 전체 기술 구성원의 리뷰를 받습니다.
- **구조:** 계획에는 API 요청·응답·오류 계약, 데이터 흐름, 시퀀스 다이어그램, ERD 등을 필요한 깊이로 포함합니다. 선택하지 않은 대안도 이유와 함께 기록합니다.
- **결과:** 문서를 PR과 작업 계획의 공통 맥락으로 사용해 중복 설명과 범위 확장을 줄이려 했습니다. 글에는 이 방식의 정량적인 시간 절감 측정은 없습니다.

## 왜 읽을까

설계 문서를 단순한 산출물이 아니라 의사결정과 작업 분할의 입력으로 다루는 글입니다. AI가 코드를 작성하는 환경에서도 사람의 요구 정의·Trade-off·완료 조건을 먼저 확정하는 실무 습관을 만드는 데 직접적입니다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집·지원·승인 기능 구현 전에 배경·목표·Non-Goals·핵심 불변식을 한 문서에 정리합니다.
- [ ] DB·API 설계 대안과 채택·기각 이유를 남깁니다.
- [ ] 테크 스펙에서 테스트 기준과 PR 단위 마일스톤을 추출해 Codex 작업 계약으로 사용합니다.
