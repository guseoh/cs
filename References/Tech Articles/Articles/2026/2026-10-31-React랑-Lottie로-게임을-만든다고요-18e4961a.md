# React랑 Lottie로 게임을 만든다고요?

> [!abstract] 한 줄 정리
> 웹뷰의 캐릭터 게임을 별도 게임 엔진 없이 React·DOM·Lottie로 구현했습니다. 도구 선택은 기능 요구뿐 아니라 학습 비용과 일정에 맞추고, 렌더링 문제는 레이어·리플로·상태 범위를 분리해 해결한 사례입니다.

> 뱅크샐러드 기술 블로그 · 2026-01-15

## 핵심 내용

- **문제:** 웹뷰에서 캐릭터의 머리·옷·안경을 조합해야 했지만 모든 조합마다 애니메이션을 제작하면 파일과 디자인 작업량이 커졌습니다. - **접근:** Phaser.js·Pixi.js 도입 대신 익숙한 React와 DOM을 선택하고, Lottie JSON의 `assets` 이미지 경로를 런타임에 바꿔 하나의 애니메이션으로 다양한 조합을 표현했습니다. 디자이너와 레이어 이름 규칙을 맞추는 것이 전제였습니다. - **트러블슈팅:** 일부 iOS 웹뷰에서 절대 배치된 여러 `img` 레이어를 교체할 때 깜빡임·버벅거림이 발생했습니다. 이미지를 여러 장 겹치는 대신 CSS `background-image` 레이어로 변경해 현상을 해소했습니다.

- **성능:** 글자 타이핑 효과에서 글자를 순차 추가하면 반복적인 레이아웃 계산이 발생해, 전체 글자를 미리 배치하고 `opacity`만 바꾸도록 수정했습니다. 반복 애니메이션은 CSS로 구현하고 자주 변하는 코인 상태는 별도 컴포넌트로 분리했습니다. - **주의점:** 저자는 발열·배터리 소모를 설계 제약으로 다뤘지만 FPS, 배터리 사용량, 개선 전후 처리 시간 등 정량적 벤치마크는 공개하지 않았습니다. 복잡한 3D·물리 시뮬레이션에는 같은 선택이 적합하지 않을 수 있습니다.

애니메이션이 많은 웹뷰라도 모든 화면을 게임 엔진으로 만들 필요는 없다. React·DOM은 기존 팀의 디버깅 경험을 유지하고 Lottie JSON의 이미지 Asset 경로를 바꾸면 머리·옷·안경 조합마다 별도 애니메이션을 제작하지 않아도 된다. 디자이너가 만든 레이어 이름과 Asset 규칙이 바뀌면 교체 코드가 깨질 수 있으므로 명시적인 디자인-개발 계약이 중요하다.

| 문제 | 개선 방식 |
| --- | --- |
| 조합별 애니메이션 파일 증가 | 공통 Lottie + 동적 Asset |
| iOS 이미지 깜빡임 | 중첩 `img` 대신 CSS 배경 레이어 |
| 타이핑 효과의 반복 레이아웃 | 미리 배치하고 `opacity`만 변경 |
| 잦은 코인 상태 갱신 | 독립 컴포넌트로 리렌더 범위 축소 |

발열·배터리는 설계 제약이지만 FPS나 배터리의 정량 수치가 공개되지 않았으므로 임의의 개선율을 추정하지 않고 실제 기기에서 프로파일링해야 한다.

## 왜 읽을까

라이브러리 도입 여부를 유행이 아니라 요구사항·팀 역량·개발 기간으로 결정한 과정이 유용합니다. 특히 iOS 웹뷰에서만 발생한 현상을 렌더링 방식의 문제로 좁혀 해결한 사례를 통해, UI 최적화에서도 실제 환경의 재현과 검증이 중요하다는 관점을 얻을 수 있습니다.

**프로젝트에 적용 — PawCycle**

- [ ] 상품 옵션을 시각적으로 미리 보여 주는 UI가 필요해질 경우, 조합마다 이미지를 생성할지 레이어를 재사용할지 먼저 비교합니다.
- [ ] 옵션 변경 시 리렌더링 범위를 분리하고 Chrome·iOS Safari 등에서 화면 깜빡임과 레이아웃 변화를 확인합니다.
- [ ] 애니메이션을 추가하기 전 사용자의 동작 감소 설정과 저사양 기기 동작을 검증합니다.
