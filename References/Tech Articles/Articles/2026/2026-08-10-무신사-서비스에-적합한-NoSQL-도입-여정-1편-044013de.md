# 무신사 서비스에 적합한 NoSQL 도입 여정 — 1편

> [!abstract] 한 줄 정리
> 새로운 DB는 유행이나 벤치마크 순위가 아니라 현재 비용과 워크로드 요구사항을 정의한 뒤 후보를 실제 장애 조건까지 검증해서 선택해야 합니다.

> techblog.musinsa.com

## 핵심 내용

AWS DocumentDB 운영에서 예상보다 스토리지와 I/O 비용이 늘어난 문제를 출발점으로 MongoDB, Cassandra, Couchbase를 운영성, 검색 방식, 비용, 가용성 관점에서 비교합니다. 10만 건 Insert·조회·집계·삭제를 비교하고 운영 존 장애를 가정해 별도 존에서 읽기·쓰기가 가능한지도 검증합니다. 리액티브 구현에서는 Couchbase Insert가 658초에서 53초로 줄어드는 등 처리량 차이도 측정했습니다.

새 NoSQL을 선정할 때 Insert가 가장 빠른 후보만 고르면 운영 중 가장 많이 발생하는 조회·집계·장애 복구 요구를 놓칠 수 있다. DocumentDB의 비용 구조를 확인한 뒤 MongoDB, Cassandra, Couchbase를 비교한 것처럼 현재 서비스의 읽기/쓰기 분포, 데이터 모델, 인덱스, 운영 가능한 팀 역량을 먼저 제약조건으로 세우는 순서가 중요하다.

| 평가 기준 | 검증해야 할 내용 |
| --- | --- |
| 기능 적합성 | 조회·집계·삭제와 데이터 모델 |
| 처리 성능 | 동일한 10만 건 워크로드·드라이버 방식 |
| 장애 대응 | 가용 영역 하나가 내려간 뒤 읽기·쓰기 |
| 비용 | 저장량 외 I/O·복제·운영 관리 |
| 이행 비용 | 기존 데이터 이전·검증·되돌리기 |

본문의 **Couchbase Insert 658초 → 53초**는 리액티브 구현 전후에 관측된 사례다. DB 제품 간 모든 환경에서 동일한 배수로 차이가 난다고 일반화할 수 없으며, 동일 조건 비교와 애플리케이션 접근 방식 변경을 분리해야 한다.

## 왜 읽을까

NoSQL 중 무엇이 최고냐가 아니라 현재 문제가 무엇인지, 후보를 어떤 기준으로 줄이고 실제 워크로드로 어떻게 검증하는지를 보여줍니다.
