# 기획서 없이 내재화하기: 검증 로직으로 동일함을 증명하다

> [!abstract] 한 줄 정리
> 대규모 리팩터링과 내재화의 성공은 새 코드가 완성됐는지가 아니라 기존 시스템과 결과가 동일한지를 자동으로 증명할 수 있느냐에 달려 있습니다.

> techblog.lycorp.co.jp

## 핵심 내용

기획서와 기존 코드까지 확인하기 어려운 외부 시스템을 내재화하면서 동일 입력을 기존·신규 시스템에 주입하고 API 응답, DB 변경 결과, 전체 처리 건수를 비교하는 검증 파이프라인을 만들었습니다. 수천만 건 카탈로그와 수억 건 상품을 수작업으로 확인할 수 없어 CDC와 Kafka를 이용해 실시간 비교했고, 비동기 시간차로 생기는 일시적 불일치는 재시도 후에도 다를 때만 실제 차이로 판정했습니다.

블랙박스 시스템의 사양을 추측해 새로 구현하는 대신 **동일 입력에서 관찰 가능한 행동이 같은가**를 검증 기준으로 삼았다. 원문은 CDC가 변경을 감지하면 기존·신규 API에 같은 입력을 보내고, 조회 결과뿐 아니라 업데이트 상태·처리 건수까지 비교한다. 두 시스템의 비동기 반영 시점이 다를 수 있으므로 첫 불일치를 바로 오류로 취급하지 않고 일정한 재확인과 비교 기준을 둔다.

| 비교 유형 | 필요한 동일성 |
| --- | --- |
| API 조회 | 결과 필드·순서·정규화 기준 |
| 통계 업데이트 | SKU·`merchantUpdateDate` 시점의 결과 |
| 데이터 수신 | 원천 URL별 성공·오류·처리 건수 |
| 비동기 처리 | 시간차 해소 후에도 남는 불일치 |

'원본과 결과가 같다'는 것은 관찰한 범위에서의 동등성이지 모든 미지의 입력에 대한 형식적 증명은 아니다. 그래서 지속적으로 변경 이벤트를 수집하고 비교 대상을 늘리는 운영 루프가 필요하다.

## 왜 읽을까

마이그레이션을 테스트 코드만의 문제가 아니라 운영 데이터와 비동기 흐름까지 포함한 결과 비교 문제로 바라보게 해줍니다.
