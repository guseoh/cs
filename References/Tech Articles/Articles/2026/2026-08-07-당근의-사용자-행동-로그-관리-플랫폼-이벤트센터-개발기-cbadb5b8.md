# 당근의 사용자 행동 로그 관리 플랫폼: 이벤트센터 개발기

> [!abstract] 한 줄 정리
> 행동 로그도 여러 생산자와 소비자가 공유하는 데이터 계약이므로 정의·검증·배포를 코드 밖에서 체계적으로 관리할 필요가 있습니다.

> medium.com

## 핵심 내용

사용자 행동 로그를 Git과 코드로 관리하다 로그가 늘면서 명세 불일치, 변경 검토 어려움, 반복 수작업이 커졌고 UI 기반 이벤트센터로 전환합니다. 이벤트 정의, 검증, 배포를 한곳에서 관리해 로그 이름과 속성 변경도 생산자·소비자 간 호환성 문제로 다룹니다.

행동 로그는 화면 개발자가 만들어서 분석팀이 나중에 읽는 부수 데이터가 아니라 생산자와 소비자가 공유하는 **이벤트 계약**이다. 이벤트 이름이 바뀌거나 필수 속성이 제거되면 애플리케이션 기능이 정상이어도 기존 대시보드와 실험 지표가 깨질 수 있다. 이벤트센터로 정의·승인·배포 이력을 묶는 이유는 단순한 입력 UI 편의가 아니라 데이터 스키마를 팀 간에 동기화하기 위해서다.

| 계약 요소 | 변경 시 검사할 대상 |
| --- | --- |
| 이벤트 이름·발생 조건 | 데이터 파이프라인·리포트 집계 |
| 필수 속성·자료형 | 클라이언트 SDK·Consumer |
| 버전·deprecated 여부 | 이전 앱 버전과의 호환 |
| 검증·배포 상태 | 수집 전후의 차이·누락 |

이벤트 스키마를 중앙에 저장하더라도 실제 코드가 해당 계약대로 전송하는지 확인하는 빌드·런타임 검증이 별도로 필요하다.

## 왜 읽을까

분석 로그를 부가 데이터가 아니라 계약으로 보는 관점이 좋습니다. 데이터가 쌓인 뒤 이름을 바꾸는 비용과 책임을 생각하게 합니다.
