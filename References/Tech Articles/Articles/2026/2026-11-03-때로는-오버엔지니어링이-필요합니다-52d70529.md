# 때로는 오버엔지니어링이 필요합니다

> [!abstract] 한 줄 정리
> 평균 초당 1건 미만의 문자 발송에도 CDC·Kafka를 도입한 이유는 처리량이 아니라 레거시 전환 중 누락·중복·관측 불가 위험을 통제하기 위해서입니다. 과도기 구조에는 제거 조건까지 있어야 합니다.

> 올리브영 테크블로그 · 2026-09-23

## 핵심 내용

- **문제:** 수십 개 서비스가 발송 대상 DB 테이블에 INSERT하고 단일 데몬이 폴링·발송했습니다. 데몬은 WAS와 자원을 공유했고, 모니터링이 부족하며 다중 실행 시 중복 발송 위험이 있었습니다.
- **선택:** 모든 서비스를 한꺼번에 API 호출로 바꾸는 대신 기존 INSERT를 CDC로 포착해 Kafka → 별도 워커 → 통합 메시지 API로 연결했습니다. 큐에는 메시지 ID만 싣고 원본은 DB에서 조회하는 Claim Check 구조를 택했습니다.
- **정합성:** 발송은 되돌릴 수 없으므로 발송 후 이력을 기록하고, 발송 이력 저장·원본 삭제는 한 트랜잭션으로 묶었습니다. Kafka의 at-least-once 재수신과 API 실패 종류에 따른 재시도 정책을 별도로 다뤘습니다.
- **수치:** 평소 발송량은 초당 1건 미만이지만 10분간 1만 건 이상 몰린 사례가 있었습니다. 워커 한 대의 평균 처리 시간은 67ms, 피크 시 약 120ms로, 대략 초당 10건을 처리했습니다.
- **트레이드오프:** 실패 메시지는 큐 전체를 막지 않도록 offset을 확정하고 제한적으로만 재시도합니다. 과도기 파이프라인은 발송 대상 테이블 INSERT가 0건이 되면 제거하도록 정했습니다.

## 왜 읽을까

트래픽이 작다는 이유만으로 단순한 배치가 최선은 아니라는 점을 배울 수 있습니다. 시스템 전환 위험, 복구 가능성, 관측성, 임시 구조의 수명까지 설계 의사결정에 포함하는 좋은 사례입니다.

**프로젝트에 적용 — PawCycle**

- [ ] 주문·알림 발송 경로에서 DB 저장과 외부 호출의 성공·실패 순서를 시퀀스 다이어그램으로 정리합니다.
- [ ] 알림 중복 수신, 타임아웃, 4xx·5xx, 재시작 후 재처리 시나리오를 테스트합니다.
- [ ] 현행 경로를 점진적으로 바꿀 때 기능 플래그, 관측 지표, 기존 경로 제거 조건을 명시합니다.
