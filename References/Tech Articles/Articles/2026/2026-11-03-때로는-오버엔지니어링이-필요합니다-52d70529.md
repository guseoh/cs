# 때로는 오버엔지니어링이 필요합니다

> [!abstract] 한 줄 정리
> 평균 초당 1건 미만의 문자 발송에도 CDC·Kafka를 도입한 이유는 처리량이 아니라 레거시 전환 중 누락·중복·관측 불가 위험을 통제하기 위해서입니다. 과도기 구조에는 제거 조건까지 있어야 합니다.

> 올리브영 테크블로그 · 2026-09-23

## 한눈에 보기

트래픽만 보면 주기적인 발송 데몬으로도 충분한 문자 발송 시스템에 CDC와 Kafka를 도입했다는 점이 역설적이다. 그러나 새 API 방식으로 모든 호출자를 한 번에 바꿀 수 없고, 장애가 나면 누락·중복 발송이 생길 수 있다는 전환 위험이 더 중요했다. 이 구조는 영구 표준이 아니라 기존 INSERT 연동이 사라질 때 철거할 과도기 파이프라인으로 설계됐다.

*그림 2. 기존 호출자의 INSERT를 유지한 채 CDC에서 새 발송 경로로 연결한 과도기 구성 — [출처: 원문 기술 블로그](https://oliveyoung.tech/2026-09-23/overengineering-message-system/)*

외부 서비스의 계약을 한꺼번에 변경하지 않고도 발송 데몬을 새 경로로 대체한다. Kafka에는 메시지 원문 전체 대신 ID를 전달하고, 워커가 원본 DB를 조회하는 Claim Check 방식으로 전환 이력을 유지한다. 외부 발송은 되돌릴 수 없는 부작용이므로 ACK, 중복 처리, 재시도 한계와 기록 트랜잭션을 구분해야 한다.

## 핵심 내용

### 문제와 제약

**문제:** 수십 개 서비스가 발송 대상 DB 테이블에 INSERT하고 단일 데몬이 폴링·발송했습니다. 데몬은 WAS와 자원을 공유했고, 모니터링이 부족하며 다중 실행 시 중복 발송 위험이 있었습니다.

### 선택한 구조와 구현

**선택:** 모든 서비스를 한꺼번에 API 호출로 바꾸는 대신 기존 INSERT를 CDC로 포착해 Kafka → 별도 워커 → 통합 메시지 API로 연결했습니다. 큐에는 메시지 ID만 싣고 원본은 DB에서 조회하는 Claim Check 구조를 택했습니다.

**정합성:** 발송은 되돌릴 수 없으므로 발송 후 이력을 기록하고, 발송 이력 저장·원본 삭제는 한 트랜잭션으로 묶었습니다. Kafka의 at-least-once 재수신과 API 실패 종류에 따른 재시도 정책을 별도로 다뤘습니다.

### 검증 결과와 남은 판단

**수치:** 평소 발송량은 초당 1건 미만이지만 10분간 1만 건 이상 몰린 사례가 있었습니다. 워커 한 대의 평균 처리 시간은 67ms, 피크 시 약 120ms로, 대략 초당 10건을 처리했습니다.

**트레이드오프:** 실패 메시지는 큐 전체를 막지 않도록 offset을 확정하고 제한적으로만 재시도합니다. 과도기 파이프라인은 발송 대상 테이블 INSERT가 0건이 되면 제거하도록 정했습니다.

### 핵심 근거와 비교

| 판단 항목 | 실제 조건 | 설계에 미친 영향 |
| --- | --- | --- |
| 평균 발송량 | 초당 1건 미만 | 평상시 성능만 보면 단순 배치 가능 |
| 일시적 집중 | 10분간 1만 건 이상 사례 | 피크 대응과 버퍼링 필요 |
| Kafka 재수신 | 적어도 한 번 전달 가능성 | 발송 상태·중복 처리 정책 필요 |
| 철거 조건 | 레거시 테이블 INSERT가 0건 | 전환 완료 후 CDC 파이프라인 제거 |

*복잡성의 정당화 기준은 TPS가 아니라 전환 위험 및 종료 조건이다.*
