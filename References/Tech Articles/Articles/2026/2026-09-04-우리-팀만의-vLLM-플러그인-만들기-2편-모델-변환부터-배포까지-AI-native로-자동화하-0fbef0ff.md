# 우리 팀만의 vLLM 플러그인 만들기 2편 - 모델 변환부터 배포까지 AI-native로 자동화하기

> [!abstract] 한 줄 정리
> 반복되는 모델 변환 절차를 AI에게 매번 새로 설명하는 대신, 승인 게이트와 검증 단계가 있는 재사용 가능한 Skill·지식 구조로 바꾸면 자동화의 범위와 품질을 함께 키울 수 있다.

> NAVER D2 · 2026-08-10

## 핵심 내용

- **문제:** Hugging Face 모델을 vLLM으로 옮길 때 모델별 변환, IO Processor 구현, 테스트·벤치마크, 배포 준비가 반복되고 vLLM 자체 변화까지 계속 따라가야 했다.
- **접근:** 변환 절차를 Claude Code Skill로 만들고 환경 준비 → 모델 변환 → IO Processor 개발 → 테스트·벤치마크 → publish의 단계로 고정했다. 계획을 먼저 검토하는 승인 게이트와 별도 컨텍스트 검증을 둬 AI가 곧바로 변경을 확정하지 않게 했다.
- **결과:** 서로 다른 7개 모델 유형을 같은 절차로 변환해 운영에 적용했고, 과정에서 발견한 주의 사항 45개를 재사용 가능한 지식으로 축적했다.
- **수치:** 매 호출마다 전체 지식을 넣던 방식을 필요한 지식만 가져오는 구조로 바꾸면서 지식 전달 토큰을 약 6,900개에서 170개로 줄였다. 약 97% 감소다.
- **구조:** 최종적으로 GitHub Issue를 시작점으로 변환부터 배포까지 이어지는 E2E 자동화로 확장해, AI 자동화와 Git 기반 검토·운영 흐름을 연결했다.

## 왜 읽을까

AI 코딩 자동화에서 중요한 것은 프롬프트를 길게 만드는 게 아니라 반복되는 시행착오를 검증 가능한 지식과 절차로 바꾸는 일이라는 점을 보여준다. 특히 사람의 승인 지점과 독립 검증을 남겨두면서 자동화 범위를 넓히는 방식이 실무적이다.

**프로젝트에 적용 — DevPedia**

- [ ] Codex가 반복해서 수행하는 탐색·변환·검증 절차를 프로젝트 Skill 또는 명시적 작업 단계로 분리한다.
- [ ] 과거 트러블슈팅과 규칙을 전부 프롬프트에 넣지 말고 작업 종류에 따라 필요한 컨텍스트만 불러오는 구조를 검토한다.
- [ ] 큰 자동화에는 `Plan 승인 → 구현 → 독립 검증 → PR` 같은 사람의 검토 경계를 남긴다.
