# 일 41TB, 200억 건의 로그를 ClickStack으로 실시간 처리하기 - 호그와트 도서관 프로젝트

> [!abstract] 한 줄 정리
> 로그가 폭증한 뒤 저장소 하나만 교체한 것이 아니라 수집·Kafka·처리·저장·장기 보관·조회 UI를 병목 순서대로 재설계했다. Observability도 결국 데이터의 수집률, 압축률, 보관 계층, 조회 패턴을 함께 설계하는 데이터 플랫폼 문제임을 보여준다.

> 카카오페이 기술 블로그 · 2026-02-23

## 핵심 내용

카카오페이증권의 로그는 하루 약 100GB에서 41TB·200억 건 이상으로 늘어났고 OpenSearch 조회가 5분 이상 지연되거나 최신 로그가 늦게 들어오는 문제가 나타났다. 수집·전송·저장·검색 전 과정을 그대로 확장하면 비용이 로그 증가 속도에 비례해 급증하므로 역할별로 병목을 제거했다.

*그림 2. ClickStack·Kafka·ssak3·S3 기반 최근 로그와 장기 로그 저장 분리 — [출처: 원문 기술 블로그](https://tech.kakaopay.com/post/pallas-v2-log-platform/)*

기존 Filebeat→Kafka→Fluentd→OpenSearch 경로에서 OpenTelemetry Collector→Kafka→OpenTelemetry Collector→ClickHouse로 변경하고 개발자가 조회하는 화면은 HyperDX에 맡겼다. 최근 9일 로그는 IDC ClickHouse에서 직접 조회한다. 그 이후 로그는 자체 `ssak3`가 S3 Parquet로 아카이빙하고, 조회 요청이 드물어 상시 운영할 필요가 없는 AWS ClickHouse를 요구 시에만 실행한다. Kafka Topic도 300개에서 18개로 통합했다.

| 지표 | 기존 | 변경 후 |
| --- | ---: | ---: |
| 하루 로그량 | 100GB 수준에서 성장 | 41TB·200억 건+ |
| Core당 수집량 | 약 150건/초(Fluentd) | 약 4,000건/초(OTel) |
| 로그 도착 지연 | 수 분~수 시간 | 20초 이내 |
| 저장 비용 | 100% | 14.4%(85.6% 감소) |
| Kafka Topic 수 | 약 300 | 18 |
| 최근/장기 보관 | 단일 운영 부담 | IDC 9일 + S3 Parquet |

원문은 Fluentd가 Core당 초당 약 150건을 처리하던 것과 OpenTelemetry Collector의 4,000건/초를 비교해 약 26배 처리량 향상을 보고했다. ZSTD와 컬럼 저장으로 약 90% 용량을 줄이고 로그 유입 지연을 수 분~수 시간에서 20초 이내, 비용은 기존 대비 14.4%로 낮췄다. 다만 수집 경로·저장 형식·보관 계층을 모두 변경한 결과이므로 한 컴포넌트의 독립 효과로 나누어 계산할 수 없다.

## 왜 읽을까

Observability를 “로그를 많이 모으는 것”으로 보지 않고 처리량·압축·보관 기간·조회 빈도·비용을 하나의 시스템으로 설계하는 사례다. 병목을 앞단부터 하나씩 걷어내고 각 단계의 수치를 남긴 점도 성능·운영 개선을 기록하는 좋은 참고가 된다.

**프로젝트에 적용 — PawCycle**

- [ ] 현재 필요한 운영 로그와 메트릭을 장애 진단 질문 기준으로 정하고 불필요한 고카디널리티 데이터를 줄인다.
- [ ] OCI 이전 후 로그 보관 기간과 조회 빈도를 측정해 hot/cold 보관을 나눌 필요가 있는지 판단한다.
- [ ] 성능 실험에서는 요청 지표뿐 아니라 DB·Nginx·애플리케이션 로그를 같은 시간축에서 추적할 수 있게 만든다.
