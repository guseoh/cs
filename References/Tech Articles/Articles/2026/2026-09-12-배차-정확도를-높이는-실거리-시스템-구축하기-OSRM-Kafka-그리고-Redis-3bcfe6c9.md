# 배차 정확도를 높이는 실거리 시스템 구축하기: OSRM, Kafka, 그리고 Redis

> [!abstract] 한 줄 정리
> 배차 계산에 필요한 거리를 실경로 기반으로 바꾸면서, 계산을 요청 시점에 몰아넣지 않고 이벤트 기반으로 미리 계산·갱신하고 Redis 자료구조와 수명 정책까지 함께 최적화한 사례다.

> 우아한형제들 기술블로그 · 2025-06-26

## 핵심 내용

- **문제:** 배달 5만 건과 라이더 5만 명을 단순 조합하면 25억 건의 거리 계산 후보가 생기므로, 배차 사이클마다 실거리 계산을 동기적으로 수행하는 방식은 현실적으로 감당하기 어렵다.
- **구조:** OSRM으로 실거리를 계산하고 Kafka 기반 이벤트 흐름으로 필요한 거리 데이터를 갱신해, 배차 시점에는 계산 결과를 빠르게 조회할 수 있는 구조를 선택했다.
- **접근:** Redis에 지역별 데이터를 단일 압축 String으로 저장하던 방식에서 지역 ID를 Key로 하는 Hash 구조로 전환해 필요한 필드만 읽고 쓰도록 했다. 다중 필드 접근으로 네트워크 왕복을 줄이되, 명령의 O(N) 특성과 ElastiCache의 요청당 인자 제한을 고려해 청크 처리했다.
- **트레이드오프:** 초기에는 모든 HMSET에 6시간 EXPIRE를 함께 적용했지만, 배달 완료 시간을 고정값으로 가정하기 어렵고 TTL 갱신 자체가 네트워크·복제 쓰기 비용을 만들었다. 이후 완료·취소 시 더 이상 필요하지 않은 데이터만 명시적으로 삭제하는 방식으로 바꿨다.
- **결과:** Redis Hash와 명시적 삭제, 클러스터 모드를 조합해 불필요한 전체 데이터 송수신과 TTL 갱신을 줄이고 쓰기 트래픽을 여러 샤드에 분산할 수 있는 구조를 만들었다.

## 왜 읽을까

이 글은 Redis를 단순히 "캐시를 붙였다"고 끝내지 않고, 어떤 자료구조를 쓰는지와 데이터의 수명을 어떻게 정의하는지가 네트워크·CPU·메모리·복제 비용까지 바꾼다는 점을 보여준다.

또한 실시간 계산을 호출 경로에 둘지, 이벤트 기반으로 선계산할지처럼 성능 문제를 아키텍처 경계의 문제로 바라보는 관점을 얻을 수 있다.

**프로젝트에 적용 — FutMatch**

- [ ] 향후 매칭에 경기장까지의 거리나 이동 시간이 실제 조건으로 필요해질 때만 실거리 계산 필요성을 검증한다.
- [ ] 매칭 후보 조합마다 외부 경로 계산을 호출하지 않고, 실제 병목이 확인되면 선계산·캐시 구조와 동기 계산 구조를 부하 테스트로 비교한다.
- [ ] 캐시를 도입한다면 임의의 TTL부터 정하지 말고 도메인 이벤트상 데이터가 더 이상 필요 없어지는 시점을 먼저 정의한다.
