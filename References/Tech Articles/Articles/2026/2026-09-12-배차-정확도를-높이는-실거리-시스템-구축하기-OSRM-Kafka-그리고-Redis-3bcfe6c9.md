# 배차 정확도를 높이는 실거리 시스템 구축하기: OSRM, Kafka, 그리고 Redis

> [!abstract] 한 줄 정리
> 배차 계산에 필요한 거리를 실경로 기반으로 바꾸면서, 계산을 요청 시점에 몰아넣지 않고 이벤트 기반으로 미리 계산·갱신하고 Redis 자료구조와 수명 정책까지 함께 최적화한 사례다.

> 우아한형제들 기술블로그 · 2025-06-26

## 핵심 내용

라이더 5만 명과 배달 5만 건을 전부 조합하면 25억 거리 계산 후보가 생겨 배차 주기마다 모두 계산할 수 없다. 우아한형제들은 단순 직선 거리 대신 OSRM 기반 실제 이동 거리 정보를 활용하면서도 매번 계산하지 않고 필요한 값을 미리 갱신·저장하는 구조로 만들었다.

```mermaid
flowchart LR
 A[배달·라이더 이벤트] --> B[Kafka]
 B --> C[OSRM 실거리 계산]
 C --> D[Redis Hash·청크 갱신]
 D --> E[배차 최적화 읽기]
 F[배달 완료·취소] --> G[해당 키 삭제]
 G --> D
```

*원문 내용을 바탕으로 자체 재구성한 가로형 기술 흐름도다.*

주문과 라이더의 상태 변화는 Kafka 이벤트로 전달하고 OSRM이 계산한 거리와 경로 정보를 Redis에 두어 배차 때 읽는다. 초기에는 지역별로 압축된 큰 String 하나에 데이터를 넣었으나 필드 일부를 바꿀 때 전체 데이터를 다시 송수신해야 해 Redis Hash로 전환했다. 요청 크기와 단일 명령의 O(N) 비용, ElastiCache의 인자 수 제한을 고려해 HMGET/HMSET을 청크로 실행했다.

| 저장 방식 | 기존 | 변경 후 |
| --- | --- | --- |
| 지역별 데이터 | 큰 압축 String | Redis Hash 필드별 읽기 |
| 일부 필드 갱신 | 전체 String 재전송 | 해당 필드/청크 갱신 |
| 데이터 만료 | 모든 HMSET에 EXPIRE 6시간 | 완료·취소 시 명시적 삭제 |
| 확장 | 일부 키 집중 | Cluster 샤드 분산 |

처음에는 매 쓰기마다 6시간 EXPIRE를 갱신했지만 배달 완료 시각이 일정하지 않고 TTL 업데이트 자체가 쓰기·복제 부담을 만들었다. 완료·취소 이벤트가 올 때 필요한 키를 명시적으로 삭제하는 쪽으로 변경했다. 이는 모든 데이터를 영구 보존하자는 뜻이 아니라 수명 종료 신호가 있는 데이터는 일률적인 TTL 갱신보다 정확한 이벤트 기반 삭제가 적합할 수 있다는 판단이다.

## 왜 읽을까

이 글은 Redis를 단순히 "캐시를 붙였다"고 끝내지 않고, 어떤 자료구조를 쓰는지와 데이터의 수명을 어떻게 정의하는지가 네트워크·CPU·메모리·복제 비용까지 바꾼다는 점을 보여준다.

또한 실시간 계산을 호출 경로에 둘지, 이벤트 기반으로 선계산할지처럼 성능 문제를 아키텍처 경계의 문제로 바라보는 관점을 얻을 수 있다.

**프로젝트에 적용 — FutMatch**

- [ ] 향후 매칭에 경기장까지의 거리나 이동 시간이 실제 조건으로 필요해질 때만 실거리 계산 필요성을 검증한다.
- [ ] 매칭 후보 조합마다 외부 경로 계산을 호출하지 않고, 실제 병목이 확인되면 선계산·캐시 구조와 동기 계산 구조를 부하 테스트로 비교한다.
- [ ] 캐시를 도입한다면 임의의 TTL부터 정하지 말고 도메인 이벤트상 데이터가 더 이상 필요 없어지는 시점을 먼저 정의한다.
