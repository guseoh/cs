# AI 시대의 개발 능력은 검증력으로 결정된다, Flava API Gateway 개발 중 배운 빠른 검증과 로컬 환경 구성 전략

> [!abstract] 한 줄 정리
> AI 코딩의 생산성은 생성 속도보다 검증 피드백 루프의 속도와 신뢰성에 달려 있다. 스펙을 먼저 고정하고 테스트·린터·로컬 환경을 빠르게 만들어야 에이전트가 스스로 오류를 수정할 수 있다.

> LY Corporation Tech Blog · 2026-06-25

## 핵심 내용

- **문제:** 에이전트가 컴파일되지 않는 코드나 존재하지 않는 API를 만들고, 설계가 정해지지 않은 부분을 임의로 결정했다. CI 왕복과 반나절짜리 환경 프로비저닝은 에이전트의 빠른 반복 속도에 비해 큰 병목이었다.
- **접근:** OpenAPI로 계약을 먼저 정하고 OpenSpec의 제안·설계·델타 스펙·작업 목록을 통해 구현 전에 모호함을 줄였다. 테스트와 린터는 실패를 즉시 드러내 에이전트가 다음 반복에서 직접 수정하도록 했다.
- **구조:** 단위·통합·E2E를 합쳐 2,754개 테스트를 구성했고, PostgreSQL 실제 제약·트랜잭션부터 Athenz 인증·Kong 데이터 플레인·멀티테넌트 격리까지 검증한다. 통합 테스트의 HTTP 응답은 OpenAPI 스펙과도 자동 대조한다.
- **수치:** 전체 테스트를 개발자 기기에서 약 15초 안에 실행한다. 테스트별 PostgreSQL 스키마 격리와 병렬화를 통해 에이전트가 매 반복마다 전체 검증을 부담 없이 돌릴 수 있게 했다.
- **트레이드오프:** 빠른 검증에는 초기 투자 비용이 든다. Nix 기반 Devenv로 PostgreSQL·Athenz·린터·코드 생성기까지 로컬에서 재현 가능하게 만든 이유도 검증 루프가 환경 설정 비용 때문에 생략되지 않게 하기 위해서다.

## 왜 읽을까

AI 코딩에서 프롬프트를 더 길게 만드는 것보다 실패를 빠르게 드러내는 테스트와 명시적인 계약이 더 강력한 제어 장치가 될 수 있음을 보여준다. 특히 스펙·테스트·로컬 환경이 각각 따로 존재하는 게 아니라 하나의 짧은 피드백 루프로 연결돼야 한다는 관점이 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] AI가 수정한 뒤 별도 지시 없이도 실행할 수 있는 검증 명령 세트를 하나로 묶는다.
- [ ] CI에서만 가능한 검증을 줄이고 핵심 통합 테스트를 로컬에서도 재현할 수 있게 한다.
- [ ] 완료 기준을 코드 생성이나 PR 생성이 아니라 스펙·테스트·회귀 검증 통과로 둔다.
