# 로그 수집기가 왜 자꾸 OOM으로 죽었나 - 누적 드롭 8.9억 건을 기록한 로그 파이프라인을 고친 이야기

> [!abstract] 한 줄 정리
> 로그 수집기 OOM은 메모리 부족만의 문제가 아니라 중복 수집·재수집과 높은 레이블 카디널리티가 겹친 구조적 문제였다. 수집 경로와 상태 보존, 레이블·청크·캐시를 함께 개선해 증설 없이 안정성과 조회 성능을 높였다.

> 카카오페이손해보험 기술 블로그 · 2026-10-27

## 한눈에 보기

로그 수집기 Alloy의 메모리 부족은 단순한 limit 부족이 아니라 노드마다 클러스터 전체 로그를 중복 수집하는 경로와 재시작 후 오래된 로그를 재수집하는 상태 관리가 겹친 결과였다. 카카오페이손해보험은 노드 로컬 파일 수집·position 영속화로 입력을 조정하고 레이블·청크·캐시도 함께 튜닝했다. 여러 변경이 합쳐진 측정 결과라는 점을 구분해야 한다.

![Pod Alloy Loki Grafana 데이터 경계 파이프라인](https://tech.kakaopay.com/_astro/pipeline-overview.TQdBtvao_26nG73.svg)

*그림 1. Alloy 수집과 Loki 적재·조회 경계를 설명하는 원문 구조도 — [출처: 원문 기술 블로그](https://tech.kakaopay.com/post/no-more-oom-log-pipeline/)*

기존 Kubernetes API 로그 접근은 수집 에이전트가 노드별로 실행될 때 같은 Pod 로그를 중복 요청할 수 있었다. 실제 파일 소유 노드에서 읽고 읽기 위치를 디스크에 남기면 중복 수집과 재시작 문제를 분리할 수 있다. 스트림 수를 늘리는 고카디널리티 레이블과 청크·캐시 설정도 조회 지연에 큰 영향을 준다.

## 핵심 내용

### 배경과 문제

**문제:** EKS에서 Alloy 메모리가 2Gi 제한의 약 95%까지 증가하며 OOM 재시작을 반복했고, 전송 실패·드롭이 누적됐다. 하루 로그량은 약 1.3TB였으며 누적 드롭은 8.9억 건 규모였다.

### 구조와 설계 선택

**원인:** 노드마다 실행되는 Alloy가 Kubernetes API 방식으로 클러스터 전체 Pod 로그를 중복 수집했다. 노드가 20개면 동일 로그를 최대 20번 요청하는 구조였고, 오래된 로그 재수집으로 Loki의 'entry too far behind' 거부도 발생했다.

**접근:** clustering 활성화, Kubernetes API 로그 스트림에서 노드 로컬 파일 수집으로 전환, 읽기 위치(position)의 hostPath 영속화를 함께 적용했다. 이후 높은 레이블 카디널리티와 청크·캐시 설정도 조정했다.

### 결과와 제약

**수치:** 샌드박스에서 활성 스트림 4,024→899(-78%), Loki CPU 16.9→0.37 cores(-98%), 쿼리 P99 0.245→0.025초(-90%), 24시간 범위 쿼리 12.6→0.56초(-96%)로 개선됐다.

**주의점:** 위 성능 개선은 수집 방식·레이블·청크·캐시 변경이 함께 반영된 결과다. 재수집과 OOM의 정확한 단일 인과관계 및 개별 변경의 기여도는 확정되지 않았다.

### 핵심 수치·비교

| 지표(샌드박스) | 변경 전 | 변경 후 | 변화 |
| --- | ---: | ---: | ---: |
| 활성 스트림 | 4,024 | 899 | -78% |
| Loki CPU | 16.9 cores | 0.37 cores | -98% |
| 쿼리 P99 | 0.245초 | 0.025초 | -90% |
| 24시간 조회 | 12.6초 | 0.56초 | -96% |

*수집 경로·레이블·청크·캐시 변경의 합산 효과이며 개별 설정의 기여율은 검증되지 않았다.*

## 왜 읽을까

모니터링 시스템 자체가 운영 장애의 원인이 될 수 있다는 사례다. 리소스를 증설하기 전에 로그 수집의 소유권, 재시작 시 읽기 위치, 인덱스 카디널리티를 확인해야 한다는 진단 순서를 배울 수 있다. 개선 수치가 측정된 환경과 여러 변경의 합산 효과를 구분해 보고한 점도 중요하다.

**프로젝트에 적용 — PawCycle**

- [ ] OCI 배포 환경에서 로그 수집 경로와 로그 중복 발생 가능성을 먼저 확인한다.
- [ ] 수집기 재시작·배포 시 읽기 위치와 로그 유실/중복 가능성을 점검한다.
- [ ] 로그량, 수집 실패율, 수집기 메모리, 조회 p95/p99를 기준선으로 기록한다.
- [ ] 운영 설정을 바꾸기 전 격리 환경에서 변경 전후를 비교한다.
