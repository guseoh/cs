# ELK와 Grafana를 이용해 테스트 자동화 시각화하기

> [!abstract] 한 줄 정리
> 테스트를 자동으로 실행하는 것만으로는 품질 관리가 완성되지 않습니다. 실행 과정·결과를 표준 이벤트로 수집하고 누구나 상태를 확인할 수 있게 해야 테스트 자동화가 지속적으로 사용됩니다.

> LINE Engineering · 2023-07-14

## 한눈에 보기

테스트 실행 자동화만 구축하면 테스트 실패와 완료 시점을 담당자가 메일이나 테스트 솔루션에 들어가 찾아야 하는 문제가 남는다. LINE은 각 테스트 노드에서 나온 이벤트를 통합 저장하고 Grafana에서 진행률과 실패 근거를 보여주도록 관측 경계를 추가했다. 실행 자동화와 모니터링·알림을 분리해야 팀이 테스트를 운영할 수 있다.

```mermaid
flowchart LR
  A[신규 앱 빌드·Jenkins] --> B[테스트 노드 자동 실행]
  B --> C[공통 실행 이벤트 로그]
  C --> D[Filebeat]
  D --> E[Logstash]
  E --> F[Elasticsearch]
  F --> G[Grafana 진행률·실패 현황]
  G --> H[Slack 알림·원인 조사]
```

*원문 내용을 바탕으로 자체 재구성한 개략 흐름도다.*

Heimdall 파이프라인은 테스트 도구가 제각각인 환경에서 로그 필드를 공통 언어로 만드는 역할을 한다. 로그 스키마에는 애플리케이션·테스트 케이스·기기·실행 이벤트 등 약 20개의 항목이 포함된다. 성공 건수만 합산하는 방식과 달리 특정 빌드에서 어떤 기기의 어떤 케이스가 실패했는지 추적할 수 있도록 하는 것이 설계 목표다.

## 핵심 내용

### 문제와 제약

**문제:** 서비스마다 여러 회귀·퀵 테스트 잡이 돌았지만 결과 메일이 쌓이고, 테스트 진행률·완료 시점·실패 원인을 한눈에 파악하기 어려웠습니다.

### 설계 선택과 실제 구현

**구조:** 여러 테스트 노드의 로그를 Filebeat→Logstash→Elasticsearch로 적재하는 Heimdall 파이프라인을 구축하고 Grafana로 시각화했습니다.

**데이터:** 애플리케이션·테스트 케이스·기기·이벤트 정보를 담은 약 20개의 로그 필드를 정의하고, 솔루션에 부족했던 로깅을 ActionLog.Script로 보완했습니다.

### 결과·한계·운영 판단

**자동화:** Jenkins가 신규 앱 빌드를 확인해 다운로드·설치·회귀 테스트 실행을 이어 주고, Grafana 대시보드와 Slack 알림으로 진행 상태를 공유했습니다.

**결과:** 수동 리포트 메일 작성 부담을 줄이고 테스트 상태를 실시간으로 볼 수 있게 됐습니다. 정량적인 시간 절감 수치는 공개하지 않았습니다.

### 주요 비교와 확인 기준

| 구성 요소 | 담당 책임 | 검증 관점 |
| --- | --- | --- |
| Jenkins | 빌드 감지·테스트 실행 | 빌드 SHA와 실행 이력 연결 |
| Filebeat / Logstash | 노드별 이벤트 수집·가공 | 공통 필드·시간·실패 정보 정규화 |
| Elasticsearch | 테스트 이벤트 조회 | 테스트 ID·케이스·실행 시점 기반 검색 |
| Grafana | 진행률·결과 공유 | 실시간 상태 및 원인 추적 |
| Slack | 운영 알림 | 담당자가 조사할 링크 제공 |

*원문은 결과 공유·가시성 개선을 설명하지만 정량적인 시간 절감률은 제시하지 않는다.*

## 왜 읽을까

테스트 성공률만 보는 대시보드가 아니라 테스트를 '운영 가능한 시스템'으로 만드는 설계 관점을 배울 수 있습니다. 핵심은 ELK 자체보다 공통 이벤트 스키마, 실패 추적, 빌드부터 결과 공유까지 이어지는 실행 흐름입니다.
