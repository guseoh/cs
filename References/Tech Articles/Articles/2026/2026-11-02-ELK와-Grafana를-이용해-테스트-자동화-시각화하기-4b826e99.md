# ELK와 Grafana를 이용해 테스트 자동화 시각화하기

> [!abstract] 한 줄 정리
> 테스트를 자동으로 실행하는 것만으로는 품질 관리가 완성되지 않습니다. 실행 과정·결과를 표준 이벤트로 수집하고 누구나 상태를 확인할 수 있게 해야 테스트 자동화가 지속적으로 사용됩니다.

> LINE Engineering · 2023-07-14

## 핵심 내용

자동 테스트가 실행되고 있어도 완료 시점과 어떤 케이스가 실패했는지 제때 파악하지 못하면 운영 효율이 높다고 할 수 없다. LINE은 다양한 테스트 솔루션의 로그를 같은 이벤트 형식으로 수집한 뒤 Grafana에 연결해 실행 진행률과 실패 근거를 공유하도록 테스트 모니터링을 개선했다.

 ```mermaid
flowchart LR
 A[신규 앱 빌드·Jenkins] --> B[테스트 노드]
 B --> C[공통 실행 이벤트]
 C --> D[Filebeat·Logstash]
 D --> E[Elasticsearch]
 E --> F[Grafana 진행률·실패]
 F --> G[Slack 알림·원인 조사]
```

*원문 근거를 토대로 가로 방향으로 자체 재구성한 학습용 흐름도다.*

Jenkins가 신규 앱 빌드를 감지하고 테스트 실행을 시작한다. 각 테스트 노드에서는 애플리케이션·케이스·기기·이벤트 등 약 20개의 로그 필드를 공통 규약으로 남긴다. Filebeat가 이를 전송하고 Logstash에서 가공한 뒤 Elasticsearch에 적재하며, Grafana에서 여러 잡의 결과를 모니터링한다. 원래 테스트 도구가 제공하지 않던 일부 이벤트는 ActionLog.Script로 보완하여 구조화된 로그에 포함했다.

```json
// 학습용 로그 스키마 예시: 원문의 약 20개 필드를 간추림
{"buildSha":"...","testCase":"login","device":"windows","result":"FAILED"}
```

이런 구조의 식별자가 있어야 같은 테스트의 이전 실행과 실패 원인을 연결해 추적할 수 있다.

| 구성 요소 | 담당 책임 | 검증 관점 |
| --- | --- | --- |
| Jenkins | 빌드 감지·테스트 실행 | 빌드 SHA와 실행 이력 연결 |
| Filebeat / Logstash | 노드별 이벤트 수집·가공 | 공통 필드·시간·실패 정보 정규화 |
| Elasticsearch | 테스트 이벤트 조회 | 테스트 ID·케이스·실행 시점 기반 검색 |
| Grafana | 진행률·결과 공유 | 실시간 상태 및 원인 추적 |
| Slack | 운영 알림 | 담당자가 조사할 링크 제공 |

*원문은 결과 공유·가시성 개선을 설명하지만 정량적인 시간 절감률은 제시하지 않는다.*

이 설계는 대시보드 화면만 만드는 작업이 아니라 CI의 특정 빌드와 테스트 케이스·기기·실패 이벤트 사이에 추적 가능한 식별자를 만드는 일이다. Slack 알림이 원인 로그·Grafana 화면으로 이어져야 실패를 조사할 수 있고, 단순 성공/실패 메일보다 다양한 테스트를 한 화면에 보여줄 수 있다. 원문은 효율의 개선을 설명하지만 시간 절감률은 정량적으로 발표하지 않았다.

## 왜 읽을까

테스트 성공률만 보는 대시보드가 아니라 테스트를 '운영 가능한 시스템'으로 만드는 설계 관점을 배울 수 있습니다. 핵심은 ELK 자체보다 공통 이벤트 스키마, 실패 추적, 빌드부터 결과 공유까지 이어지는 실행 흐름입니다.

- [ ] PR 검증 결과를 요약해 실패 원인과 이전 실행 대비 변화를 추적합니다.
- [ ] 테스트가 실패한 경우 담당자가 원인 로그까지 빠르게 접근하는 링크를 제공합니다.
