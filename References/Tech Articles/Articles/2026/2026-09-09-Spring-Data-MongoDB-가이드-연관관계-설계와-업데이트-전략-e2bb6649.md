# Spring Data MongoDB 가이드: 연관관계 설계와 업데이트 전략

> [!abstract] 한 줄 정리
> MongoDB 연관관계 매핑의 편의보다 조회 패턴과 애그리거트 경계를 먼저 두고, 변경은 전체 `save()`보다 필요한 필드만 명시적으로 갱신하는 편이 예측 가능하다.

> 카카오페이 기술 블로그 · 2026-09-09

## 핵심 내용

- **문제:** `@DBRef`로 문서 연관관계를 편하게 표현할 수 있지만, 목록 조회 뒤 연관 객체에 접근하면 N+1 쿼리가 발생할 수 있고 지연 로딩도 직렬화나 필드 접근 시점에 결국 추가 조회를 유발한다.
- **수치:** 글의 벤치마크에서는 Author를 함께 사용하는 1,000개 Post 조회가 N+1 영향으로 약 1,000ms까지 늘었고, `$lookup`을 이용한 조인 방식이 더 효율적인 대안으로 비교됐다.
- **접근:** `author_id`처럼 식별자만 저장하면 자동 객체 로딩을 포기하는 대신 의도하지 않은 객체 그래프 조회를 막을 수 있고, 필요한 경우 `$lookup` 등으로 조회를 명시한다.
- **구조:** 객체 참조를 강하게 걸면 애그리거트 간 결합과 일관성 경계가 흐려질 수 있다. ID 참조는 서로 다른 애그리거트의 독립적인 변경 경계를 더 분명하게 만들고 향후 컬렉션·서비스 분리에도 유리하다.
- **주의점:** 문서 전체를 다시 저장하는 방식은 동시 변경이나 의도하지 않은 필드 덮어쓰기 위험이 있다. 필요한 필드만 부분 업데이트하고 대량 변경은 `bulkOps`처럼 목적이 드러나는 연산을 쓰는 전략을 함께 다룬다.

## 왜 읽을까

MongoDB의 `@DBRef` 사용법만 설명하는 글이 아니라, 편리한 매핑이 실제 조회 비용과 도메인 경계에 어떤 영향을 주는지 연결해서 볼 수 있다. 특히 ORM·ODM의 편의 기능을 도입하기 전에 “이 관계가 같은 일관성 경계인가, 조회 시 실제로 함께 필요한가”를 먼저 묻는 기준을 얻기 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 엔티티 관계를 설계할 때 객체 참조가 편하다는 이유보다 실제 조회 시나리오와 일관성 경계를 먼저 적는다.
- [ ] 목록 API에서 연관 데이터 접근 시 쿼리 수와 응답 시간을 측정하는 검증 항목을 둔다.
- [ ] 전체 객체 저장보다 변경 의도가 명확한 부분 업데이트가 필요한 지점을 구분한다.

MongoDB 전용 기법을 그대로 가져오기보다, **연관관계 표현 방식이 조회 비용과 경계를 동시에 바꾼다**는 판단 기준을 적용하는 편이 맞다.
