# Spring Data MongoDB 가이드: 연관관계 설계와 업데이트 전략

> [!abstract] 한 줄 정리
> MongoDB 연관관계 매핑의 편의보다 조회 패턴과 애그리거트 경계를 먼저 두고, 변경은 전체 `save()`보다 필요한 필드만 명시적으로 갱신하는 편이 예측 가능하다.

> 카카오페이 기술 블로그 · 2026-09-09

## 핵심 내용

MongoDB에서 다른 컬렉션의 객체를 `@DBRef`로 직접 참조하면 코드는 편리하지만 목록 조회 후 참조 대상에 접근할 때 N+1 요청이 발생할 수 있다. 지연 로딩으로 설정해도 실제 필드 접근이나 JSON 직렬화가 추가 조회를 유발할 수 있으므로 컬렉션과 애그리거트 사이의 변경 경계를 다시 정해야 한다.

카카오페이는 `Post.author` 객체를 매핑하는 대신 필요할 때 `authorId`만 저장해 참조 대상을 명시하고, 한 번에 Author 정보가 필요한 조회는 MongoDB `$lookup` 등 명시적인 집계 쿼리로 처리하는 방식을 비교했다. 서로 다른 애그리거트의 ID 참조는 저장된 문서 그래프를 무조건 자동 로딩하지 않고 독립적인 변경 책임을 유지하는 장점도 있다.

```javascript
// Author를 명시적으로 조인하는 집계의 핵심 예시
{ $lookup: {
  from: 'author', localField: 'authorId',
  foreignField: '_id', as: 'author'
}}
// 부분 갱신: { $set: { status: 'PUBLISHED' } }
```

*컬렉션과 필드 이름은 설계 원리의 설명 예시이며 실제 원문 데이터 스키마와 다를 수 있다.*

| 연관 설계 | 읽기·쓰기 특성 | 검증 경계 |
| --- | --- | --- |
| @DBRef | 편리한 객체 참조 | 목록+참조 N+1 |
| ID 참조 | 필요할 때 명시 조회 | 독립 애그리거트 유지 |
| `$lookup` | 필요한 정보 묶어 조회 | 인덱스·조인 결과 크기 |
| `save` 문서 전체 | 단순한 전체 치환 | 동시 필드 덮어쓰기 |
| `$set`·bulkOps | 목적 필드/집합만 수정 | 조건 갱신·트랜잭션 |

원문의 벤치마크에서는 1,000개 Post의 Author를 읽는 경우 N+1 경로가 약 1,000ms까지 늘었고 `$lookup`을 활용한 경로가 더 효율적이었다. 쓰기에서도 전체 문서를 `save`하면 동시 수정 중 다른 필드를 덮어쓸 수 있어 필요한 필드의 `$set`만 수행하고 다량 갱신은 `bulkOps`로 의도를 명확히 했다. `$lookup` 자체도 무한정 빠른 것은 아니므로 대상 인덱스와 실제 결과 크기를 측정해야 한다.

## 왜 읽을까

MongoDB의 `@DBRef` 사용법만 설명하는 글이 아니라, 편리한 매핑이 실제 조회 비용과 도메인 경계에 어떤 영향을 주는지 연결해서 볼 수 있다. 특히 ORM·ODM의 편의 기능을 도입하기 전에 “이 관계가 같은 일관성 경계인가, 조회 시 실제로 함께 필요한가”를 먼저 묻는 기준을 얻기 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 엔티티 관계를 설계할 때 객체 참조가 편하다는 이유보다 실제 조회 시나리오와 일관성 경계를 먼저 적는다.
- [ ] 목록 API에서 연관 데이터 접근 시 쿼리 수와 응답 시간을 측정하는 검증 항목을 둔다.
- [ ] 전체 객체 저장보다 변경 의도가 명확한 부분 업데이트가 필요한 지점을 구분한다.

MongoDB 전용 기법을 그대로 가져오기보다, **연관관계 표현 방식이 조회 비용과 경계를 동시에 바꾼다**는 판단 기준을 적용하는 편이 맞다.
