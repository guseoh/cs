# OMS의 최적화된 마이크로서비스 아키텍처 디자인

> [!abstract] 한 줄 정리
> 마이크로서비스의 경계를 도메인 이름만 보고 나누지 않고 기능·변화 가능성·관리 비용으로 판단하며, 분리된 구조가 팀의 개발·리뷰 방식까지 어떻게 바꾸는지 보여준다.

> 컬리 기술 블로그 · 2025-05-09

## 핵심 내용

- **구조:** OMS는 판매처의 결제완료 주문을 풀필먼트가 이해할 수 있는 형태로 변환하고 주문 라우팅과 이행 정보를 제공하는 경계 시스템으로 동작한다.
- **접근:** 특정 판매처에 강하게 결합되지 않도록 풀필먼트에 꼭 필요한 데이터만 동기화하고, 판매처별 표현은 내부 공통 의미로 재가공해 서빙한다.
- **트레이드오프:** 상품이라는 별도 도메인이 있어도 현재 관리 비용이 낮고 주문 기능 안에서 충분히 다룰 수 있다면 별도 MSA로 분리하지 않는다. 향후 재고 등 독립 기능이 커져 관리 비용이 높아질 때 분리를 검토한다.
- **구조:** 판매처의 트래픽·데이터 특성에 따라 서비스별 기술 선택을 달리하며 Spring MVC와 WebFlux를 혼용한다. 동일한 기술을 일괄 적용하기보다 워크로드 특성을 경계 설계에 반영한다.
- **주의점:** 작은 팀이 여러 MSA를 운영하면 모든 엔지니어가 전체 컨텍스트를 유지해야 하는 비용이 생긴다. 이를 완화하기 위해 기능을 작은 티켓으로 나누고 데이터 저장과 서빙 구현을 서로 다른 엔지니어가 이어서 맡는 방식도 사용한다.

## 왜 읽을까

“MSA니까 도메인마다 서비스를 쪼갠다”는 식의 기계적인 설계를 피하게 해준다. 서비스 분리는 독립 이름의 존재보다 변경 이유와 운영 비용이 충분히 커졌는지로 판단해야 한다는 기준을 얻을 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] Recruitment의 Position·TechStack을 별도 서비스로 분리하기보다 현재처럼 같은 애플리케이션 안의 명확한 도메인 경계로 유지한다.
- [ ] 도메인 분리 판단 시 `독립 변경 빈도 / 별도 데이터 소유 필요성 / 독립 배포 필요성 / 운영 비용`을 기준으로 기록한다.
- [ ] 기능이 커져도 곧바로 MSA로 전환하지 않고 모듈·패키지 경계를 먼저 명확히 해 실제 분리 필요성이 생기는지 관찰한다.
