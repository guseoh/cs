# OMS의 최적화된 마이크로서비스 아키텍처 디자인

> [!abstract] 한 줄 정리
> 마이크로서비스의 경계를 도메인 이름만 보고 나누지 않고 기능·변화 가능성·관리 비용으로 판단하며, 분리된 구조가 팀의 개발·리뷰 방식까지 어떻게 바꾸는지 보여준다.

> 컬리 기술 블로그 · 2025-05-09

## 핵심 내용

OMS는 판매처의 결제완료 주문을 풀필먼트가 처리할 수 있는 의미로 변환하고 배송 가능 시간·주문 이행 계획 정보를 다시 판매처에 제공한다. 컬리는 컬리몰도 여러 판매처 가운데 하나로 취급해 특정 쇼핑몰의 필드와 정책이 물류 도메인의 중심 모델을 오염시키지 않도록 했다.

![컬리 OMS의 주문·권역·이행 계획·트래킹과 공용 캐시 경계를 나타낸 원문 아키텍처](https://helloworld.kurly.com/_astro/oms-architecture-overview.COp0orch_okgj2.webp)

*그림 1. 컬리 OMS의 주문·권역·이행 계획·트래킹과 공용 캐시 경계를 나타낸 원문 아키텍처 — [출처: 원문 기술 블로그](https://helloworld.kurly.com/blog/oms-msa-architecture-1/)*

판매처에서 받은 데이터는 주문 라우팅에 꼭 필요한 필드만 동기화하고, 나머지는 필요할 때 다른 도메인 서비스에서 조회한다. 여러 내부 도메인의 데이터가 합쳐지는 곳이 OMS지만 도메인 이름을 무조건 독립 MSA로 나누지는 않는다. 예를 들어 상품 매핑만 담당하고 독립 재고 정책이 없는 상품 정보는 주문 도메인 안에 두되 이후 관리 비용이 높아질 때 분리할 수 있다. 판매처별 트래픽 특성에 따라 Spring MVC와 WebFlux를 함께 사용했다.

| 모듈 경계 | 현재 판단 | 분리 기준 |
| --- | --- | --- |
| 판매처 인터페이스 | 공통 의미로 변환 | 외부 계약 격리 |
| 주문 관리 | 상품 매핑 일부 포함 | 기능 독립성·관리 비용 |
| 권역·이행 계획 | 별도 책임 | 데이터·확장 요구 |
| API 기술 선택 | MVC/WebFlux 혼용 | 워크로드 특성 |
| MSA 전체 | 최소 동기화·재가공 서빙 | 작은 팀 운영 복잡성 |

MSA 수가 많아질수록 작은 팀이 전체 흐름을 이해하고 장애를 추적하는 운영 비용도 커진다. OMS는 기능 변경·관리 비용·독립 스케일링 필요성이 실제로 커질 때 경계를 나누는 방식을 택했다. 현재 API 지연이나 배포 횟수에 대한 통제된 비교 수치는 제공하지 않으므로 아키텍처 이름 자체를 성능 향상 근거로 삼지 않는다.

## 왜 읽을까

“MSA니까 도메인마다 서비스를 쪼갠다”는 식의 기계적인 설계를 피하게 해준다. 서비스 분리는 독립 이름의 존재보다 변경 이유와 운영 비용이 충분히 커졌는지로 판단해야 한다는 기준을 얻을 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] Recruitment의 Position·TechStack을 별도 서비스로 분리하기보다 현재처럼 같은 애플리케이션 안의 명확한 도메인 경계로 유지한다.
- [ ] 도메인 분리 판단 시 `독립 변경 빈도 / 별도 데이터 소유 필요성 / 독립 배포 필요성 / 운영 비용`을 기준으로 기록한다.
- [ ] 기능이 커져도 곧바로 MSA로 전환하지 않고 모듈·패키지 경계를 먼저 명확히 해 실제 분리 필요성이 생기는지 관찰한다.
