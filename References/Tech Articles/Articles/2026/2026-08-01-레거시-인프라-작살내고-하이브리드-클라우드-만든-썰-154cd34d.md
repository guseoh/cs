# 레거시 인프라 작살내고 하이브리드 클라우드 만든 썰

> [!abstract] 한 줄 정리
> 하이브리드 클라우드는 클라우드를 많이 쓰는 구조가 아니라 장애 영역·비용·통제권·데이터 이동 비용을 명시적으로 나누는 설계 문제입니다.

> toss.tech

## 핵심 내용

오래된 인프라를 정리하면서 OpenStack 기반 private cloud와 AWS를 Active-Active 형태로 운영하는 과정을 다룹니다. 네 개 live region과 두 cloud를 운영하며 로그만 해도 초당 10만~30만 건 규모여서, cloud 사이 네트워크 병목을 피하기 위해 Elasticsearch cluster도 양쪽에 분리하는 선택을 합니다.

하이브리드 클라우드에서 Active-Active를 구축했다는 표현만으로 모든 저장소와 로그를 클라우드 간 실시간으로 공유해야 한다는 뜻은 아니다. 로그만 초당 10만~30만 건이 들어오는 환경에서 Elasticsearch를 하나의 원격 클러스터로 합치면 클라우드 간 전송과 장애 전파가 병목이 된다. 원문은 클라우드별 로그 클러스터를 분리해 네트워크 비용과 조회 지연, 독립 장애 대응을 고려했다.

| 설계 문제 | 분리 선택의 이유 |
| --- | --- |
| 애플리케이션 Active-Active | 리전·클라우드 장애 때 트래픽 우회 |
| 로그 검색 클러스터 | 클라우드 간 대용량 로그 전송 경감 |
| 공통 운영 자동화 | 리소스 생성·설정 편차 감소 |
| DR 검증 | 한쪽 클라우드가 중단된 상태의 기능 유지 |

클라우드가 네 곳의 리전과 두 사업자에 분산돼도 결제 상태나 데이터의 소유권은 별도로 정의해야 한다. 가용성과 일관성은 서로 다른 검증 항목이다.

## 왜 읽을까

public cloud가 언제나 정답이라는 식이 아니라 비용·통제·장애 격리의 트레이드오프를 실제 운영 구조로 보여줍니다.

**프로젝트에 적용**

**PawCycle** — 규모를 따라할 필요는 없지만, EC2/RDS 같은 구성 요소마다 `이 장애가 어디까지 퍼지는가`, `AWS 의존성이 끊기면 무엇이 남는가`를 아키텍처 설명에 포함할 수 있습니다.
