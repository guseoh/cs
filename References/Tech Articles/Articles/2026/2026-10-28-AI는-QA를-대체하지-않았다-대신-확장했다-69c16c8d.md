# AI는 QA를 대체하지 않았다, 대신 확장했다

> [!abstract] 한 줄 정리
> AI로 테스트 초안을 빠르게 만드는 것보다, 이슈·PR·테스트·사용자 피드백이 발생하는 순간 품질 정보를 수집·분석하는 워크플로에 AI를 통합하는 편이 QA의 판단 범위를 넓힌다.

> LY Corporation 기술 블로그 · 채수광 · 2026-05-14

## 핵심 내용

- **문제:** 기획·Slack·Jira·PR·테스트·사용자 리뷰가 분산돼 QA가 AI에 전달할 맥락부터 수작업으로 수집해야 했다. 개별 챗봇 사용만으로는 팀의 품질 운영 구조를 바꾸기 어려웠다.
- **구조:** 스케줄 기반 분석(정기 리뷰·테스트 요약)과 웹훅 기반 분석(PR 병합·이슈 변경·테스트 결과 업로드)을 분리해 품질 이벤트에 반응하도록 설계했다.
- **수치:** LINE Album QA는 30개 이상의 자동화 워크플로를 운영하며, 2026년 기준 테스트 케이스 약 90%의 **초안**을 AI가 생성한다. 이는 90%가 자동 승인된다는 뜻이 아니다.
- **접근:** API/UI 자동화 결과를 Jira와 Slack으로 전달하고 실패 분석, PR 변경 영향 요약, 사용자 리뷰 분석을 자동 실행한다. QA는 리스크 판단과 최종 의사결정을 담당한다.
- **트레이드오프:** 자동화는 정보 정리와 초기 분석을 가속하지만 도메인 맥락, 위험 평가, 최종 품질 승인은 사람이 책임진다.

## 왜 읽을까

AI 활용 성과를 생성 코드량이나 테스트 케이스 수만으로 평가하지 않고, **품질 신호를 모으고 검토하는 전체 흐름**으로 평가하는 관점을 얻을 수 있다. 특히 이벤트 기반 분석과 정기 분석을 나누는 기준이 실무적이다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집·지원·승인 상태 전이별 필수 테스트를 먼저 사람이 명시한다.
- [ ] PR이 생성되면 Codex가 변경 파일과 영향을 받는 도메인 규칙을 요약하도록 실험한다.
- [ ] AI 생성 테스트는 실제 실패 조건·검증 assertion을 확인한 후 반영한다.
- [ ] CI 실패 시 테스트 결과를 요약하되 병합 판정은 테스트와 검토 결과에 근거하도록 한다.
