# 수천 개의 API/BATCH 서버를 하나의 설정 체계로 관리하기

> [!abstract] 한 줄 정리
> 설정도 복사해 두는 문자열이 아니라 중복을 줄이고 테스트할 수 있는 소프트웨어로 다루면, 수천 개 서버의 운영 실수를 구조적으로 줄일 수 있다.

> Toss Tech · 2026-01-09

## 핵심 내용

- **문제:** API·배치 서버가 수천 개로 늘면서 비슷한 YAML과 JVM 설정을 복사해 관리했고, 작은 오타 하나가 50억 규모 정산 배치 같은 중요 작업에도 들어갈 수 있었다.
- **구조:** API 설정은 `global → cluster → phase → app` 계층을 겹치는 오버레이 구조와 템플릿을 결합해 공통값은 한 번 정의하고 필요한 값만 하위 계층에서 덮어쓴다.
- **접근:** 배치 쪽은 Jenkins Job DSL을 한 번 더 감싼 선언형 빌더를 만들어 Java 버전·JVM 옵션·모니터링·프로파일러 같은 운영 설정을 한 인터페이스로 제공한다.
- **결과:** 설정이 Groovy 코드가 되면서 STAGING 장비에 LIVE 배치를 할당하는 식의 업무 규칙 위반을 배포 전에 테스트로 차단할 수 있게 됐다.
- **트레이드오프:** 복잡한 새 플랫폼을 택하기보다 기존 Jenkins를 유지하되, 메모리 경합은 작업마다 전용 노드를 동적으로 프로비저닝하고 유휴 노드는 종료하는 방식으로 풀었다.

## 왜 읽을까

설정 파일을 코드보다 덜 중요한 부속물로 보는 습관을 깨준다. 중복 제거, 추상화, 타입에 가까운 인터페이스, 자동 테스트 같은 소프트웨어 설계 원칙을 운영 설정에도 그대로 적용하는 과정을 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 배포 환경별로 중복된 JVM·Spring·Docker 설정이 있다면 공통값과 환경별 override를 분리한다.
- [ ] CI에서 필수 환경변수, 허용 프로파일, 메모리 범위 같은 설정 계약을 자동 검증한다.
- [ ] 설정 변경도 코드 변경처럼 diff와 테스트 결과를 남겨 배포 Evidence에 포함한다.
