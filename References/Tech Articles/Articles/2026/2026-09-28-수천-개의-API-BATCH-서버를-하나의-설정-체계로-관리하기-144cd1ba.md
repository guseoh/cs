# 수천 개의 API/BATCH 서버를 하나의 설정 체계로 관리하기

> [!abstract] 한 줄 정리
> 설정도 복사해 두는 문자열이 아니라 중복을 줄이고 테스트할 수 있는 소프트웨어로 다루면, 수천 개 서버의 운영 실수를 구조적으로 줄일 수 있다.

> Toss Tech · 2026-01-09

## 핵심 내용

API·배치 서버가 수천 개에 이르면 서버별로 복사한 YAML·JVM 옵션에 작은 오타가 들어가도 중요한 정산 배치까지 영향을 미칠 수 있다. 토스는 모든 서버 설정을 새 플랫폼으로 이전하기보다 공통 설정과 차이를 구조적으로 표현하는 선언형 체계를 도입했다.

API 서비스는 `global → cluster → phase → app`의 오버레이 계층으로 기본값을 정의하고 하위 환경에서 꼭 필요한 설정만 덮어쓰도록 했다. 배치에는 Jenkins Job DSL 위에 더 작은 선언형 빌더를 만들어 Java 버전·모니터링·프로파일러·JVM 플래그와 실행 환경을 공통 함수에서 설정하도록 했다. 설정을 Groovy 코드로 표현하니 STAGING의 작업을 LIVE 노드에 배정하는 식의 정책 위반을 단위 테스트로 배포 전에 발견할 수 있었다.

```yaml
# 설정 오버레이를 설명하는 가상 구조
# global.yml -> cluster.yml -> phase.yml -> app.yml
jvm:
  heap: 2g
monitoring:
  enabled: true
```

*원문의 정확한 운영 설정과 달리 합성 규칙의 예시다. 실제 오버레이 우선순위는 테스트로 고정해야 한다.*

| 관리 대상 | 구조화 방법 | 검증 항목 |
| --- | --- | --- |
| API YAML | global→cluster→phase→app | 덮어쓰기 우선순위·충돌 |
| Batch Job | Jenkins DSL 추상화 | Java/JVM·프로파일·노드 정책 |
| 서버 자원 | 작업별 임시 노드 | 메모리 경합·유휴 비용 |
| 배포 안전 | 선언형 Groovy 테스트 | STAGING→LIVE 잘못된 지정 차단 |

공유된 디폴트가 바뀌면 여러 서비스가 동시에 영향을 받는다는 위험도 있다. 따라서 최종 합성된 설정을 diff하고 변경 범위를 검토해야 하며, 수많은 배치가 같은 노드의 메모리를 경합하지 않도록 작업 단위로 노드를 동적 프로비저닝한 뒤 유휴 시 종료했다. 선언형 설정의 가치는 파일 수 감소보다 **중앙 정책의 기계적 검증 가능성**에 있다.

## 왜 읽을까

설정 파일을 코드보다 덜 중요한 부속물로 보는 습관을 깨준다. 중복 제거, 추상화, 타입에 가까운 인터페이스, 자동 테스트 같은 소프트웨어 설계 원칙을 운영 설정에도 그대로 적용하는 과정을 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 배포 환경별로 중복된 JVM·Spring·Docker 설정이 있다면 공통값과 환경별 override를 분리한다.
- [ ] CI에서 필수 환경변수, 허용 프로파일, 메모리 범위 같은 설정 계약을 자동 검증한다.
- [ ] 설정 변경도 코드 변경처럼 diff와 테스트 결과를 남겨 배포 Evidence에 포함한다.
