# pnpm 모노레포에서 React 19 마이그레이션하기: 숨겨진 호이스팅 레이어가 만든 타입 충돌 트러블슈팅

> [!abstract] 한 줄 정리
> 의존성 업그레이드 문제는 버전 숫자보다 실제 dependency graph와 hoisting이 어떤 타입을 노출하는지 추적해야 풀립니다.

> techblog.woowahan.com

## 핵심 내용

pnpm 모노레포에서 React 19를 점진적으로 적용하는 과정에서 third-party dependency와 hoisting 때문에 서로 다른 React 타입이 섞이는 충돌을 추적합니다. catalogs를 이용해 버전을 관리하고, `paths`나 별도 lockfile 같은 대안의 유지보수 비용을 비교한 뒤 `packageExtensions`를 사용해 문제를 보정합니다.

pnpm에서 의존성이 서로 다른 버전을 사용한다고 해서 런타임 파일만 충돌하는 것은 아니다. React 19 이전 과정에서 `@types/react` 버전과 라이브러리의 peerDependency, 숨은 호이스팅 경로가 서로 다른 타입 정의를 동시에 참조하면 TypeScript가 같은 React 요소를 호환되지 않는 타입으로 판단할 수 있다.

| 대안 | 해결 방식 | 남는 부담 |
| --- | --- | --- |
| `tsconfig paths` | 컴파일러 경로 강제 | 실제 런타임 의존성과 괴리 |
| lockfile 분리 | 각 패키지 의존성 격리 | 관리·빌드 복잡도 |
| `pnpm catalogs` | 공통 의존성 버전 정의 | 선언되지 않은 peer 조건 존재 |
| `packageExtensions` | 패키지 메타데이터 보완 | 업스트림 변경 추적 |

원문은 의존성 그래프를 확인한 뒤 metadata 보정을 채택했다. `skipLibCheck`처럼 진단을 숨기는 처방보다 실제 타입 소스가 어디서 분기되는지 추적하는 것이 근본 해결에 가깝다.

## 왜 읽을까

'타입 에러가 나니 tsconfig를 고친다'가 아니라 패키지 관리자의 의존성 해석 구조까지 내려가 원인을 찾는 트러블슈팅 과정이 좋습니다.

**프로젝트에 적용**

**PawCycle** — Spring Boot·Security·프론트 의존성 업그레이드 때 증상만 맞추는 설정 패치보다 dependency tree와 transitive dependency를 먼저 확인하는 업그레이드 절차로 활용할 수 있습니다.
