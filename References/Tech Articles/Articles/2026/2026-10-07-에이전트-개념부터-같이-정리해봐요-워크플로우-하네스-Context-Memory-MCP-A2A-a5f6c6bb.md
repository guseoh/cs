# 에이전트, 개념부터 같이 정리해봐요 - 워크플로우 · 하네스 · Context/Memory · MCP/A2A

> [!abstract] 한 줄 정리
> 에이전트·워크플로우·하네스·Context/Memory·MCP/A2A처럼 자주 섞여 쓰이는 개념을 원문 스펙과 실제 구현을 기준으로 다시 구분한다. AI 도구를 많이 붙이는 것보다 각 구성요소가 맡는 책임과 경계를 먼저 합의하는 데 도움이 된다.

> NAVER D2 · 2026-09-30

## 핵심 내용

AI Agent라는 이름만으로 서비스의 제어 구조가 정해지는 것은 아니다. NAVER D2의 용어 정리 글은 Workflow와 Agent, Harness와 모델, Context와 Memory, MCP와 A2A를 구분해 팀이 같은 설계 논의를 하도록 돕는다.

Workflow는 미리 정한 순서와 분기를 따라 도구를 호출하는 반면 Agent는 목표를 달성하기 위해 실행 중 다음 단계를 동적으로 결정할 수 있다. Harness는 모델에 제공하는 도구, 권한, 실행 제한, 검증·관측과 실패 복구를 담당하는 실행 환경이다. Context는 한 번의 모델 호출에 실제 들어가는 정보이고 Memory는 세션을 넘어 다시 사용할 근거를 보존하는 저장 구조다. MCP는 도구·리소스의 호출 인터페이스를 표준화하며, A2A는 서로 독립적인 에이전트의 작업 요청과 결과 전달을 대상으로 한다.

| 개념 | 담당 책임 | 혼동하지 말 것 |
| --- | --- | --- |
| Workflow | 정해진 경로·분기 실행 | Agent의 자율적 계획과 차이 |
| Agent | 실행 중 목표에 맞는 후속 작업 결정 | 모든 작업의 무제한 권한 아님 |
| Harness | 격리·계약·도구·검증 | LLM 모델 파라미터와 별개 |
| Context | 현재 호출에 주입된 정보 | 영구 Memory와 다름 |
| Memory | 세션을 넘어 보존하는 근거 | 매번 전량 주입하지 않음 |
| MCP / A2A | 도구 연결 / 에이전트 간 통신 | 보안·승인 책임 자동 해결 아님 |

이 구분은 표준 프로토콜의 이름을 붙이면 신뢰성·권한 통제까지 자동으로 해결된다고 착각하지 않기 위한 기준이다. 에이전트 개발에서 가장 먼저 질문해야 할 것은 어떤 작업을 모델이 선택하게 하고, 어떤 경계를 시스템이 강제하고, 누가 결과를 검증할 것인가이다. 원문은 개념을 설명하는 기술 자료로 독립적인 처리량·비용 개선 수치를 제공하지 않는다.

## 왜 읽을까

AI 에이전트를 실제 개발 워크플로에 쓰기 시작하면 제품 이름보다 개념 경계가 중요해진다. 특히 Codex 같은 코딩 에이전트를 여러 도구와 연결할 때 “Context를 더 넣자”와 “지속 Memory가 필요하다”, “MCP가 필요하다”는 전혀 다른 설계 결정임을 구분하는 기준점으로 쓰기 좋다.

**프로젝트에 적용 — 공통**

- [ ] Codex 작업 지침, 프로젝트 문서, 일회성 작업 Context를 같은 저장소에 무작정 섞지 않고 수명과 책임별로 분리한다.
- [ ] 외부 도구 연동은 MCP 도입 자체를 목표로 하지 않고 기존 CLI/API 대비 어떤 계약과 발견 가능성을 얻는지 먼저 적는다.
- [ ] 에이전트가 여러 단계 작업을 수행할 때 결정론적 Workflow와 모델 판단이 필요한 Agent 구간을 구분한다.
