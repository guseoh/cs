# Spring JDBC 성능 문제, 네트워크 분석으로 파악하기

> [!abstract] 한 줄 정리
> 애플리케이션 로그만으로 보이지 않던 JDBC 배치 INSERT 지연을 TCP 패킷과 Spring JDBC·Oracle 드라이버 내부까지 추적해, null 파라미터 타입 명시만으로 100만 건 INSERT 시간을 18분에서 2분으로 줄인 사례다.

> Toss Tech · 2024-01-17

## 핵심 내용

- **문제:** Spring Batch의 `ItemWriter`에서 `batchUpdate`로 객체 5,000개를 저장하는 데 1분 이상 걸렸지만 애플리케이션 로그에는 INSERT 외의 원인이 드러나지 않았다.
- **접근:** Wireshark로 TCP 패킷을 확인해 실제 INSERT 전에 다수의 SELECT가 발생함을 찾고, 디버깅으로 `setNull()`에서 `getParameterMetaData()`가 호출되는 흐름까지 추적했다.
- **구조:** Oracle JDBC 드라이버는 null 파라미터의 타입을 알아내기 위해 메타데이터 질의를 DB로 보내는 반면, MySQL 드라이버는 같은 메타데이터를 재사용하는 차이가 있었다.
- **트레이드오프:** 전역 옵션 `spring.jdbc.getParameterType.ignore=true`도 가능했지만 시스템 전체에 영향을 주기 때문에, 문제가 발생한 파라미터에 SQL 타입을 명시하는 국소적인 해결을 선택했다.
- **결과:** 약 100만 건의 거래 내역 INSERT 시간이 약 18분에서 2분으로 줄었다.

## 왜 읽을까

성능 문제를 SQL이나 인덱스에서만 찾지 않고 프레임워크, JDBC 드라이버, 네트워크 왕복까지 계층을 내려가며 증거를 좁히는 과정을 볼 수 있다. 같은 Spring JDBC 코드라도 DB 드라이버 구현에 따라 비용이 달라질 수 있다는 점도 실무적으로 중요하다.

또 전역 설정으로 빠르게 우회하는 방법과 영향 범위를 좁힌 수정 사이에서 무엇을 선택할지 보여줘, 성능 개선과 변경 리스크를 함께 판단하는 연습이 된다.

**프로젝트에 적용 — PawCycle**

- [ ] 대량 JDBC 저장이 필요한 지점에서 nullable 파라미터 유무에 따른 배치 처리 시간을 비교한다.
- [ ] 테스트 시 전체 시간뿐 아니라 SQL 횟수와 DB 왕복 횟수를 함께 확인한다.
- [ ] 개선 전후를 동일한 데이터량으로 재측정하고, 전역 설정보다 영향 범위가 작은 해결책을 우선 검토한다.
