# CPU 뼛속까지 써먹고, Milvus 사이징 기준을 만들기까지

> [!abstract] 한 줄 정리
> CPU 사용률이 높아도 계산이 아니라 원격 메모리 접근을 기다리고 있을 수 있다. 검색 품질을 고정한 뒤 인덱스·NUMA 배치·하드웨어 카운터를 함께 측정하자 같은 서버에서 처리량을 41% 높일 수 있었다.

> 토스 기술 블로그 · 토스증권 Data Infra팀 · 2026-10-12

## 핵심 내용

Milvus 기반 벡터 검색 서버를 사이징할 때 QPS만 높이면 검색 품질이 떨어지는 인덱스를 과대평가하기 쉽다. 토스증권은 LAION-100M의 768차원 벡터와 서버 3대를 고정하고 `recall@10 ≥ 0.95` 조건을 만족하는 인덱스·서버 자원을 비교했다.

HNSW와 압축된 HNSW_SQ8의 메모리 사용량, 검색 시 후보 범위를 나타내는 `ef` 값을 함께 측정했다. HNSW_SQ8의 ef48은 recall 0.954에 316 QPS, 약 114GB/replica였지만 비압축 HNSW는 약 335GB를 사용하고도 같은 비교 조건의 처리량 목표를 달성하지 못했다. 이후 CPU IPC가 0.37에 머무르고 원격 DRAM 읽기가 노드별 약 49%인 점에 주목했다. 이는 CPU 코어 수가 충분해도 다른 NUMA 소켓의 메모리를 읽느라 실행이 느려질 수 있음을 의미한다.

| 실험 조건 | 값 | 의미 |
| --- | --- | --- |
| HNSW_SQ8 ef48 | recall 0.954, 316 QPS, 114GB | 품질 하한 충족·압축 메모리 |
| NUMA 조정 전/후 | 원격 DRAM 약 50% → 0.8% | 메모리 지역성 개선 |
| 동일 recall 검색 | 405 → 572 QPS | 약 41% 처리량 증가 |
| 검색 품질 선택 | ef48 190 QPS / ef128 99 QPS | 더 높은 recall은 처리량 비용 |

*모든 수치는 원문 하드웨어·데이터셋에서 측정된 값이며 별도 행의 실험 조건을 혼합해 계산해서는 안 된다.*

Kubernetes CPU Manager·Memory Manager·Topology Manager로 CPU와 메모리를 같은 NUMA node에 배치하자 원격 DRAM 접근 약 50%→0.8%, IPC 0.37→0.55로 개선되었다. 동일 recall 0.9541 기준 처리량이 405→572 QPS로 41% 증가했고 p99 측정 구간 최댓값은 3.94→2.04초였다. 반면 ef128은 recall 0.962로 조금 좋아져도 QPS가 190→99로 감소한다는 측정이 있어 검색 정확도와 지연의 교환 비용을 명확히 보여준다.

## 왜 읽을까

성능 개선에서 지표를 하나만 최적화하면 잘못된 결론에 도달할 수 있음을 보여준다. ANN 검색은 QPS와 recall을 함께 봐야 하고, CPU 병목도 사용률뿐 아니라 IPC·NUMA·메모리 접근 경로를 확인해야 한다.

인덱스와 서버 수를 먼저 늘리기보다 현재 자원이 왜 기다리는지 설명할 수 있는 측정 근거를 쌓는 접근이 특히 유용하다.
