# CPU 뼛속까지 써먹고, Milvus 사이징 기준을 만들기까지

> [!abstract] 한 줄 정리
> CPU 사용률이 높아도 계산이 아니라 원격 메모리 접근을 기다리고 있을 수 있다. 검색 품질을 고정한 뒤 인덱스·NUMA 배치·하드웨어 카운터를 함께 측정하자 같은 서버에서 처리량을 41% 높일 수 있었다.

> 토스 기술 블로그 · 토스증권 Data Infra팀 · 2026-10-12

## 핵심 내용

- **문제·기준:** 1억 건 벡터 검색의 서버 대수를 정해야 했고, 단순 QPS 비교는 검색 품질을 숨길 수 있었다. LAION-100M(768차원)과 서버 3대로 `recall@10 ≥ 0.95`를 만족하는 구성의 처리량·지연시간을 비교했다.
- **인덱스:** HNSW\_SQ8·ef48은 recall 0.954, 316 QPS를 기록했고 replica당 메모리는 약 114GB였다. 압축하지 않은 HNSW는 약 335GB를 사용하면서 같은 비교의 처리량 목표 300 QPS를 충족하지 못했다.
- **진단:** 검색 중 IPC는 약 0.37이었고, 세 노드의 원격 DRAM 읽기 비율은 48.9%·49.5%·49.6%였다. CPU 사용률만으로는 다른 소켓 메모리 접근 대기를 구분하기 어려웠다.
- **개선 수치:** CPU Manager·Memory Manager·Topology Manager로 CPU와 메모리를 같은 NUMA node에 배치한 뒤 원격 DRAM 비율 약 50%→0.8%, IPC 0.37→0.55, 동일 recall(0.9541)에서 405→572 QPS(+41%)를 측정했다. 검색 p99 측정 구간 최댓값은 3.94초→2.04초였다.
- **트레이드오프:** ef48은 노드당 190 QPS·recall 0.954, ef128은 99 QPS·recall 0.962로 품질과 처리량을 맞바꿨다. 서버 수·벡터 차원·메모리 요구량을 함께 계산하되, 실제 서비스 데이터와 장애 여유 용량으로 재검증해야 한다.

## 왜 읽을까

성능 개선에서 지표를 하나만 최적화하면 잘못된 결론에 도달할 수 있음을 보여준다. ANN 검색은 QPS와 recall을 함께 봐야 하고, CPU 병목도 사용률뿐 아니라 IPC·NUMA·메모리 접근 경로를 확인해야 한다.

인덱스와 서버 수를 먼저 늘리기보다 현재 자원이 왜 기다리는지 설명할 수 있는 측정 근거를 쌓는 접근이 특히 유용하다.
