# 대용량 AI 실시간 임베딩 데이터를 효율적으로 다루기

> [!abstract] 한 줄 정리
> 대량의 실시간 데이터 제공에서는 DB의 단건 조회 속도만이 아니라 다건 접근 패턴, 네트워크 전송량, 압축 CPU 비용, 테스트 부하 발생기까지 함께 설계해야 한다.

> LY Corporation Tech Blog · 박찬우, 양유성 · 2024-06-28

## 핵심 내용

- **문제:** 임베딩은 데이터 한 건의 크기가 크고 모델이 여러 건을 동시에 조회하므로, TPS가 아주 높지 않아도 네트워크와 DB I/O가 병목이 될 수 있다.
- **접근:** 키·서브키 기반 다건 조회, 네이티브 샤딩, QPS 대비 비용, Reactive 드라이버를 기준으로 DB를 비교해 Redis Cluster를 주 저장소로 채택했다. 별도 DB 이중 쓰기로 손실 위험을 낮추는 방안을 설명한다.
- **구조:** 키 분산과 Big Key를 고려해 Redis hashes와 hmget을 선택했다. 서브키별 TTL을 설정할 수 없는 제약은 이 서비스의 요구사항에서는 허용했다.
- **트레이드오프:** 데이터 압축은 전송량을 줄이지만 압축·해제에 CPU를 사용한다. 데이터 표현 방식과 압축 방식을 조합해 손익분기점을 넘는지 검증하고, 이득이 없으면 압축하지 않는다.
- **검증:** JMH 로컬 벤치마크로 후보를 좁힌 후 실제 성능 테스트 플랫폼에서 TPS·지연·자원 사용을 검증했다. 부하 발생 서버 자체가 병목이 되어 클러스터를 증설한 사례도 있다. 정량적인 최종 TPS와 비용 절감 수치는 공개하지 않았다.

## 왜 읽을까

Redis를 캐시로만 써야 한다는 고정관념 대신 데이터 접근 패턴과 실패 비용으로 저장소를 선택하는 과정을 볼 수 있다. 로컬 마이크로벤치마크와 실제 부하 테스트를 구분하는 이유도 명확하다.

**프로젝트에 적용 — PawCycle**

- [ ] 상품 추천 또는 검색에서 큰 응답 데이터를 다건 조회하는 경로가 있는지 먼저 확인한다.
- [ ] 조회 건수·응답 바이트·p95 지연을 기준선으로 측정하고, 압축 유무의 네트워크 절감과 CPU 비용을 비교한다.
- [ ] 로컬 벤치마크 결과를 운영 성능으로 단정하지 않고 독립된 부하 환경에서 재검증한다.
