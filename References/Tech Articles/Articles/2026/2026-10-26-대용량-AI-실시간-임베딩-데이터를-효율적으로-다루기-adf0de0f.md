# 대용량 AI 실시간 임베딩 데이터를 효율적으로 다루기

> [!abstract] 한 줄 정리
> 대량의 실시간 데이터 제공에서는 DB의 단건 조회 속도만이 아니라 다건 접근 패턴, 네트워크 전송량, 압축 CPU 비용, 테스트 부하 발생기까지 함께 설계해야 한다.

> LY Corporation Tech Blog · 박찬우, 양유성 · 2024-06-28

## 핵심 내용

대량의 AI 임베딩을 실시간으로 제공할 때 한 요청의 TPS가 아주 높지 않아도 임베딩 자체가 크고 한 번에 여러 건을 조회하므로 네트워크와 DB I/O가 병목이 될 수 있다. LY는 DB 제품의 명성보다 데이터의 키·서브키 접근 패턴, 샤딩, 한 요청의 바이트 수와 비용을 기준으로 저장소를 비교했다.

![Redis Hash 한 키 아래 여러 종류의 임베딩 서브키를 저장하는 구조](https://vos.line-scdn.net/landpress-content-v2-vcfc68aynwenkh3bno0ixfx8/1719201575847.png?updatedAt=1719201577000)

*그림 1. HMGET에 적합하도록 주요 키와 임베딩 유형별 하위 필드를 나눈 원문 구조도 — [출처: 원문 기술 블로그](https://techblog.lycorp.co.jp/ko/how-to-efficiently-handle-massive-ai-real-time-embedding)*

Redis Cluster의 Hash 자료구조를 선택한 이유는 하나의 주요 키 아래 여러 유형의 임베딩 서브키를 묶고 `HMGET`으로 필요한 부분 집합을 한 번에 조회할 수 있기 때문이다. 임베딩 유형별 별도 키를 증가시키는 MGET 방식에 비해 논리적 관리가 쉽지만 Hash의 필드별 독립 TTL을 설정할 수 없다는 제약도 받아들였다. 샤딩에서는 일부 키에 데이터·요청이 편중되거나 Big Key가 발생하지 않도록 분산을 검토해야 한다.

```redis
# 원문의 Hash/HMGET 접근 패턴을 설명하는 예시
HSET user:42 vector_m "..." vector_d "..."
HMGET user:42 vector_m vector_d
```

압축된 벡터의 표현과 만료 정책은 서비스의 데이터 갱신 계약에 맞게 별도로 정해야 한다.

| 선택 항목 | 기대 효과 | 주의할 비용·제약 |
| --- | --- | --- |
| Redis Cluster | 키 분산과 다건 조회 지원 | 샤드 분포 및 Big Key |
| Redis Hash + HMGET | 필요한 서브키 집합만 조회 | Hash 하위 필드별 TTL 부재 |
| 압축 전송 | 응답 네트워크 바이트 감소 | CPU 압축·해제 부담 |
| JMH 로컬 벤치마크 | 자료 구조 후보 비교 | 네트워크·부하 발생기 병목 반영 불가 |
| 클러스터 부하 시험 | TPS·지연·자원 함께 검증 | 부하 발생 서버를 별도 튜닝·증설해야 할 수 있음 |

*원문은 최종 TPS 또는 비용 절감률의 일률적인 수치를 공개하지 않았다.*

전송량을 줄이기 위해 압축을 적용하면 네트워크 부담은 줄지만 압축·복원 CPU와 GC 비용이 늘 수 있다. 따라서 압축률만 보고 선택할 수 없으며 JMH로 후보 표현을 비교한 뒤 실제 네트워크와 부하 발생기를 포함하는 환경에서 TPS·지연·자원을 재측정해야 한다. 원문에서는 성능 실험을 수행하는 부하 발생 서버 자체가 병목이 되어 증설한 경험도 공개했다.

## 왜 읽을까

Redis를 캐시로만 써야 한다는 고정관념 대신 데이터 접근 패턴과 실패 비용으로 저장소를 선택하는 과정을 볼 수 있다. 로컬 마이크로벤치마크와 실제 부하 테스트를 구분하는 이유도 명확하다.

**프로젝트에 적용 — PawCycle**

- [ ] 상품 추천 또는 검색에서 큰 응답 데이터를 다건 조회하는 경로가 있는지 먼저 확인한다.
- [ ] 조회 건수·응답 바이트·p95 지연을 기준선으로 측정하고, 압축 유무의 네트워크 절감과 CPU 비용을 비교한다.
- [ ] 로컬 벤치마크 결과를 운영 성능으로 단정하지 않고 독립된 부하 환경에서 재검증한다.
