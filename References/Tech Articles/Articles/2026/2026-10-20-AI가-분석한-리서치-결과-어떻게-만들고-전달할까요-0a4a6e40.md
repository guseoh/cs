# AI가 분석한 리서치 결과, 어떻게 만들고 전달할까요?

> [!abstract] 한 줄 정리
> AI 리서치 기능의 사용자 경험은 답변 내용뿐 아니라 결과를 안정적으로 생성하고 기다리는 동안 진행 상황을 전달하는 방식에도 달려 있다. 프롬프트 구성과 비동기 결과 전달을 하나의 제품 문제로 바라본다.

> 우아한형제들 기술블로그 · 2026-08-31

## 핵심 내용

리서치 결과를 생성하는 AI 기능에서는 모델이 분석을 끝내는 시점과 사용자가 그 결과를 받아들이는 경험을 별도로 설계해야 한다. 응답이 오래 걸리는 작업에 단순한 로딩 스피너만 표시하면 사용자는 실제로 진행 중인지, 언제 결과가 도착할지 판단하기 어렵다.

우아한형제들 사례는 LLM이 리서치 질의를 분석할 때 지켜야 할 프롬프트 규칙과 결과 전달 인터페이스를 함께 검토한다. 생성 작업을 한 번의 거대한 응답으로 반환하는 대신 SSE를 통해 처리 단계와 생성된 결과를 점진적으로 안내하면 채팅 UI가 상태를 표현할 수 있다. 다만 SSE 연결 성공이 분석 결과의 정합성을 보장하지는 않으며, 구독이 끊긴 뒤 재접속 시 어떤 결과를 복구할지는 애플리케이션 계약으로 정의해야 한다.

```text
# 긴 AI 분석 작업의 상태 전달을 설명하는 SSE 이벤트 예시 (자체 재구성)
event: progress
data: {"stage":"retrieval","status":"running"}

event: result
data: {"section":"summary","status":"completed"}
```

이는 실제 원문 API 규격을 인용한 것이 아니라 단계별 전달과 완성 이벤트를 분리하는 설계 예시다.

| 책임 | 확인해야 할 실패 | 사용자에게 보일 정보 |
| --- | --- | --- |
| LLM 분석 | 작업 오류·잘못된 응답 | 실패·재시도 가능성 |
| SSE 연결 | 네트워크 끊김·이벤트 순서 | 현재 단계·재접속 상태 |
| 채팅 UI | 중복 렌더링·미완성 결과 | 메시지 단위 완료 여부 |
| 알림 | 도착 시점이 불명확 | 결과 완성·확인 가능 상태 |

화면 구성에서는 채팅 메시지 구조와 알림음의 역할도 함께 고려했다. 새 텍스트를 매 토큰 단위로 보여주는 것과 완성된 분석 단위를 전달하는 것은 가독성과 인지 부담이 다르므로 실제 사용자 흐름에 맞춘 경계가 필요하다. 원문 요약에서 확인되는 범위에는 응답 시간을 얼마나 단축했는지에 대한 정량적 Before/After가 없으므로, 스트리밍 도입만으로 분석이 빨라졌다고 주장할 수 없다.

## 왜 읽을까

AI 기능을 '모델 호출 API'로만 보면 생성 시간 동안의 상태 전달과 사용자 피드백을 놓치기 쉽다. AI 분석의 안정성과 비동기 UX를 함께 검토할 때 참고할 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] AI 분석이 필요한 화면을 도입할 경우, 즉시 응답할 정보와 나중에 도착하는 결과를 구분한다.
- [ ] 긴 처리 시간을 가정해 진행 중·완료·실패 상태를 화면에서 어떻게 알릴지 정의한다.
- [ ] 프롬프트 변경에 따른 결과 품질과 UI 전달 방식의 동작을 별도 기준으로 검증한다.
