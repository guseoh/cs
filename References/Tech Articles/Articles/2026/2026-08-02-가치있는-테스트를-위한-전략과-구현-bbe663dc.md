# 가치있는 테스트를 위한 전략과 구현

> [!abstract] 한 줄 정리
> 테스트 수를 늘리는 것보다 변경될 수 있는 구현 세부사항과 반드시 보호해야 하는 사용자·도메인 행동을 구분해야 테스트가 개발 속도를 지켜줍니다.

> toss.tech

## 핵심 내용

테스트 코드가 지나치게 구현 세부사항에 결합되면 작은 리팩터링에도 대량으로 깨져 오히려 변경을 방해하는 문제를 다룹니다. 테스트가 보호해야 할 계약과 도메인 행동을 먼저 정하고 unit/integration 등 각 레벨의 비용과 가치를 고려해 테스트 전략을 구성합니다.

테스트의 가치는 검증 개수보다 **보호하는 계약이 얼마나 오래 유지되는가**에 달려 있다. 내부 메서드 호출 횟수나 테스트 더블의 구현 세부사항에 강하게 의존하면 정상적인 리팩터링도 실패로 기록돼 개발자가 테스트를 신뢰하지 못하게 된다. 도메인 관점에서는 주문 생성 이후 결제 가능 상태가 유지되는지 같은 관찰 가능한 행동을 기준으로 테스트를 설계하는 편이 변경에 강하다.

| 테스트 레벨 | 잘 잡는 위험 | 주의할 비용 |
| --- | --- | --- |
| 단위 테스트 | 도메인 분기·계산·불변식 | 내부 구현과 과한 결합 |
| 통합 테스트 | DB 제약·트랜잭션·외부 계약 | 실행 시간·환경 관리 |
| E2E 테스트 | 사용자 여정 연결 | 느린 실행·불안정성 |

모든 시나리오를 E2E로 올리거나 모든 협력을 Mock으로 바꾸기보다 결함의 발생 가능성과 회귀 영향에 맞춰 검증 경계를 배치하는 것이 핵심이다.

## 왜 읽을까

'테스트가 많을수록 좋다'가 아니라 유지보수 가능한 회귀 보호 장치를 만드는 기준을 생각하게 합니다.

**프로젝트에 적용**

**DevPedia** — 서비스 메서드 내부 호출 순서를 Mock으로 고정하기보다 인증/인가, 모집 상태 변경, DB 제약처럼 깨지면 실제 사용자에게 영향을 주는 동작을 우선 테스트할 수 있습니다.
