# 함수형 프로그래밍과 Effect System을 이용한 의도가 명확한 코드 작성하기

> [!abstract] 한 줄 정리
> 네트워크·DB·Kafka처럼 실행 결과가 외부 상태에 의존하는 사이드 이펙트를 코드의 타입과 구조에 드러내면, 실행 시점과 실패 가능성을 더 명시적으로 다루고 테스트·추론 가능한 영역을 넓힐 수 있습니다.

> 카카오페이 기술 블로그 · 2025-03-18

## 핵심 내용

`sendEvent()`라는 메서드명만으로는 네트워크 호출·예외·시간 초과·메트릭 기록 같은 숨은 부수효과를 알 수 없다. 카카오페이는 특히 결제와 FDS의 중요한 로직에서 외부 효과를 순수한 계산과 구분해야 코드를 읽을 때 지역적으로 동작을 추론할 수 있다고 설명한다.

함수형 프로그래밍에서는 순수 함수가 입력에 따라 일관된 결과를 만들고, 외부 서비스와 상호작용하는 부분은 IO 같은 Effect 값으로 묘사해 실행 시점을 별도 런타임에서 관리할 수 있다. 이렇게 하면 Timeout, 오류 복구, 병렬 실행을 값을 조합하는 방식으로 선언할 수 있다. 카카오페이 FDS는 Cats Effect와 ZIO 등을 이용해 수백 개 Rule을 수십 밀리초 내에 평가하는 시스템을 운영한 경험을 제시한다.

```scala
// IO의 지연 실행 개념을 보여주는 의사 코드
val action = IO.delay(sendNetworkRequest()) // 선언 시 실행하지 않음
val limited = action.timeout(2.seconds)       // 오류·시간 정책 조합
// 실제 런타임에서 action 실행
```

*원문의 실제 서비스 구현 코드를 옮긴 것이 아니라 Effect 값과 실행의 분리를 보여준다.*

| 접근 | 장점 | 도입 비용 |
| --- | --- | --- |
| 순수 함수 | 테스트·재현·추론 용이 | 외부 효과 분리 설계 필요 |
| IO/Effect | 실행·오류·시간 정책 조합 | 런타임·스케줄링 이해 |
| Tagless Final | 구현 교체 유연성 | 추상화 난도 |
| Kotlin suspend | 언어 수준 비동기 표현 | 예외·컨텍스트 관리 |

Effect System을 사용하면 명시적인 경계를 확보하지만 IO가 여러 층에서 합성될 때 실제 실행 순서가 직관적이지 않거나 Fiber 스케줄러와 동시성 정책을 추가로 학습해야 한다. Tagless Final이나 Kotlin suspend, Algebraic Effects는 장단점이 다른 대안이므로 '무조건 Effect를 쓴다'보다 순수 계산/외부 효과/실패 재시도 책임을 어떻게 분리할지부터 정하는 것이 중요하다.

## 왜 읽을까

함수형 프로그래밍 문법 소개보다 ‘왜 사이드 이펙트가 유지보수와 운영을 어렵게 만드는가’를 실서비스 문제와 연결해서 설명합니다. 메서드 이름만으로는 보이지 않는 네트워크·예외·지연을 설계 수준에서 어떻게 드러낼지 생각해볼 수 있습니다.

또한 장점만 소개하지 않고 Effect System의 러닝커브와 디버깅 비용까지 다뤄, 새로운 추상화를 도입할 때 얻는 명시성과 떠안는 복잡도를 함께 비교하기 좋습니다.

**프로젝트에 적용 — PawCycle**

- [ ] 주문·결제·외부 API 호출 로직에서 순수한 도메인 계산과 DB·네트워크·메시지 발행 같은 사이드 이펙트를 구분해 봅니다.
- [ ] 사이드 이펙트가 있는 메서드는 실패, timeout, 재시도 정책이 호출부에서 보이는지 점검합니다.
- [ ] Effect System을 바로 도입하기보다 현재 코드에서 외부 상호작용을 국소화하는 것만으로 테스트와 추론성이 얼마나 좋아지는지 먼저 확인합니다.
