# 함수형 프로그래밍과 Effect System을 이용한 의도가 명확한 코드 작성하기

> [!abstract] 한 줄 정리
> 네트워크·DB·Kafka처럼 실행 결과가 외부 상태에 의존하는 사이드 이펙트를 코드의 타입과 구조에 드러내면, 실행 시점과 실패 가능성을 더 명시적으로 다루고 테스트·추론 가능한 영역을 넓힐 수 있습니다.

> 카카오페이 기술 블로그 · 2025-03-18

## 핵심 내용

- **문제:** `sendEvent()` 같은 메서드는 시그니처만으로 RPC 호출, 예외, 지연, 메트릭 출력 같은 숨은 사이드 이펙트를 알기 어렵고, 크리티컬한 결제 흐름에서는 이런 불확실성이 운영 위험으로 이어질 수 있습니다.
- **접근:** 외부 상호작용을 가능한 한 국소화하고 순수 계산과 분리해 Local Reasoning이 가능한 코드를 만든 뒤, Effect System에서는 사이드 이펙트를 IO 같은 값으로 묘사해 실행 시점을 분리합니다.
- **구조:** IO로 실행을 지연시키면 timeout, 오류 처리, 병렬 실행 같은 정책을 조합할 수 있습니다. 카카오페이 FDS에서는 Cats Effect와 ZIO를 활용해 수백 개의 룰을 수십 밀리초 내에 실행하는 구조를 운영하고 있습니다.
- **트레이드오프:** IO 합성이 많아지면 디버깅과 실행 흐름 추론이 어려워지고, 별도 런타임과 Fiber 기반 비동기 실행 자체가 새로운 복잡도가 됩니다. 이를 줄이기 위한 Tagless Final, Kotlin `suspend`, Algebraic Effects 같은 대안도 함께 비교합니다.
- **주의점:** Effect System 자체가 목적이 아니라, 외부 상호작용의 존재와 실패 가능성을 코드에서 숨기지 않고 어디에서 실행할지를 통제하는 것이 핵심입니다.

## 왜 읽을까

함수형 프로그래밍 문법 소개보다 ‘왜 사이드 이펙트가 유지보수와 운영을 어렵게 만드는가’를 실서비스 문제와 연결해서 설명합니다. 메서드 이름만으로는 보이지 않는 네트워크·예외·지연을 설계 수준에서 어떻게 드러낼지 생각해볼 수 있습니다.

또한 장점만 소개하지 않고 Effect System의 러닝커브와 디버깅 비용까지 다뤄, 새로운 추상화를 도입할 때 얻는 명시성과 떠안는 복잡도를 함께 비교하기 좋습니다.

**프로젝트에 적용 — PawCycle**

- [ ] 주문·결제·외부 API 호출 로직에서 순수한 도메인 계산과 DB·네트워크·메시지 발행 같은 사이드 이펙트를 구분해 봅니다.
- [ ] 사이드 이펙트가 있는 메서드는 실패, timeout, 재시도 정책이 호출부에서 보이는지 점검합니다.
- [ ] Effect System을 바로 도입하기보다 현재 코드에서 외부 상호작용을 국소화하는 것만으로 테스트와 추론성이 얼마나 좋아지는지 먼저 확인합니다.
