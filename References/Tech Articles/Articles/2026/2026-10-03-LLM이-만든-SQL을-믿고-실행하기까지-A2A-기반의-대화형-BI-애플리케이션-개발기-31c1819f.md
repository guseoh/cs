# LLM이 만든 SQL을 믿고 실행하기까지: A2A 기반의 대화형 BI 애플리케이션 개발기

> [!abstract] 한 줄 정리
> LLM이 SQL을 그럴듯하게 생성하는 것만으로는 운영 신뢰를 만들 수 없다. 의미를 책임지는 에이전트·근거를 공급하는 온톨로지 RAG·실행을 강제 통제하는 Query Guardrail을 분리해 정확성과 안전을 시스템 구조로 만든 사례다.

> LY Corporation Tech Blog · 2026-10-02

## 핵심 내용

- **문제:** 스키마와 컬럼 설명만으로는 조직의 지표 정의·예외 규칙·JOIN 관례를 전달하기 어려워, 문법적으로 정상인 SQL도 그럴듯한 오답을 만들었다.
- **구조:** Domain·Retrieval·SQL·Guardrail/Policy·Report Agent로 전문성 경계를 나누고 A2A 계약으로 입출력·실패 유형·근거 전달을 표준화했다.
- **접근:** Tableau·OpenMetadata 등의 정의와 관계를 공통 스키마로 정규화한 온톨로지 기반 RAG로 질문에 빠진 기간·대상·KPI 조건과 해석 근거를 공급한다.
- **보안:** SQL 실행 직전에 독립 Query Guardrail이 RLS와 CLS를 검증한다. SQL을 파싱해 실제 접근 리소스와 최종 노출 컬럼을 계산하므로 프롬프트나 문자열 매칭에 안전을 맡기지 않는다.
- **트레이드오프:** 관계 모델이 충분히 검증되지 않은 초기에는 Graph DB 대신 Vector DB로 빠르게 시작했지만, 2~3홉 간접 관계의 정확도 한계를 확인해 향후 그래프 모델의 기준으로 삼았다.

## 왜 읽을까

AI 기능의 신뢰성을 모델 성능이 아니라 책임 분리와 강제 가능한 정책으로 만드는 과정을 볼 수 있다. 특히 ‘정확한 답 생성’과 ‘안전한 실행’은 성질이 다른 문제이므로 하나의 프롬프트에 몰아넣지 않아야 한다는 설계 관점이 좋다.
