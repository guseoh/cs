# LLM이 만든 SQL을 믿고 실행하기까지: A2A 기반의 대화형 BI 애플리케이션 개발기

> [!abstract] 한 줄 정리
> LLM이 SQL을 그럴듯하게 생성하는 것만으로는 운영 신뢰를 만들 수 없다. 의미를 책임지는 에이전트·근거를 공급하는 온톨로지 RAG·실행을 강제 통제하는 Query Guardrail을 분리해 정확성과 안전을 시스템 구조로 만든 사례다.

> LY Corporation Tech Blog · 2026-10-02

## 핵심 내용

LLM이 만든 SQL이 문법적으로 유효하다는 사실은 그 SQL이 조직에서 합의한 KPI를 정확히 계산하거나 실행 권한을 지킨다는 뜻이 아니다. LY의 대화형 BI 프로젝트는 테이블 스키마 이외의 비즈니스 지표·제외 조건·조인 관계를 검색할 수 있는 온톨로지 기반 RAG와, 독립적으로 SQL 접근을 검사하는 Guardrail이 필요하다고 보았다.

```mermaid
flowchart LR
 A[사용자 분석 질문] --> B[Domain·Retrieval Agent]
 B --> C[온톨로지 RAG]
 C --> D[SQL 생성]
 D --> E[AST 기반 RLS·CLS Guardrail]
 E --> F[승인된 SQL만 실행]
 F --> G[Report Agent·근거 반환]
```

*원문을 근거로 자체 재구성한 가로형 학습 도식이다.*

Domain Agent는 질문의 지표·기간·대상을 해석하고 Retrieval Agent는 Tableau·OpenMetadata 등 정의를 정규화한 온톨로지에서 필요한 근거를 찾는다. SQL Agent가 쿼리를 만들면 별도 Guardrail/Policy Agent가 SQL AST를 파싱해 실제 참조 리소스와 최종 출력 컬럼을 조사하고 Row-Level/Column-Level Security 정책을 확인한다. 마지막 Report Agent가 결과와 근거를 사용자에게 전달한다. 이들 에이전트는 A2A 계약으로 입력·출력과 실패 유형을 교환한다.

| 검증 대상 | 필요한 근거 | 실패 시 처리 |
| --- | --- | --- |
| KPI 의미 | 정의·기간·예외 조건 | 모호하면 사용자에게 확인 |
| JOIN 경로 | 온톨로지·실제 관계 | 잘못된 조인 차단 |
| Row Level Security | 사용자·테넌트 범위 | 쿼리 실행 거절 |
| Column Level Security | 출력 컬럼·민감 필드 | 허용되지 않은 노출 차단 |
| 결과 해석 | SQL·데이터 출처 | 근거 없는 결론 제거 |

초기에는 그래프 모델이 충분히 검증되지 않아 Vector DB로 구현해 빠르게 시험했다. 그러나 2~3홉 간접 관계에서는 검색 정확도 한계가 나타났고 이후 그래프 모델 도입을 검토하게 됐다. 무엇보다 SQL을 실행하기 전에 서버 쪽에서 권한 검사를 강제해야 하며 프롬프트에 '개인정보를 보지 마'라고 적는 것만으로 RLS/CLS를 구현할 수 없다.

## 왜 읽을까

AI 기능의 신뢰성을 모델 성능이 아니라 책임 분리와 강제 가능한 정책으로 만드는 과정을 볼 수 있다. 특히 ‘정확한 답 생성’과 ‘안전한 실행’은 성질이 다른 문제이므로 하나의 프롬프트에 몰아넣지 않아야 한다는 설계 관점이 좋다.

- [ ] AI가 만든 쿼리·명령은 허용된 리소스와 필드만 접근하는지 코드 기반 정책으로 검사한다.
