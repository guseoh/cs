# BULK 처리 Write에 집중해서 개선해보기

> [!abstract] 한 줄 정리
> 대량 쓰기 성능은 쿼리 한 개의 속도보다 batch 크기·트랜잭션·실행 시간대와 시스템 전체 자원 사용량을 같이 봐야 개선할 수 있습니다.

> helloworld.kurly.com

## 핵심 내용

BULK write가 순간적으로 많은 DB·애플리케이션 자원을 사용하는 문제를 두고 실행 시간 조정, 애플리케이션 수준 tuning, 구조적 개선 등 여러 선택지를 비교합니다. Testcontainers를 활용한 성능 검증도 함께 다루며 변경 전후를 실제 환경에 가깝게 측정하려고 합니다.

BULK 쓰기의 병목은 단순히 한 번에 더 많은 row를 보낸다고 해결되는 것은 아니다. Chunk 크기를 키우면 DB 왕복이 줄 수 있지만 애플리케이션 메모리·락 점유·WAL/Redo 생성량과 실패 시 재처리 범위가 함께 증가한다. 따라서 배치 실행 시간 변경, SQL/JDBC Batch 조정, 파이프라인 자체의 재설계를 서로 다른 선택지로 구분해야 한다.

| 대안 | 이점 | 검증할 위험 |
| --- | --- | --- |
| 저부하 시간대로 이동 | 사용자 요청과 경합 완화 | 전체 실행 시간 개선은 아님 |
| JDBC Batch·Bulk Write | 네트워크 왕복 감소 | 큰 트랜잭션·락·메모리 |
| 처리 단위 분리 | 부분 실패 재처리 가능 | 멱등 키·작업 상태 관리 |
| 인프라 증설 | 즉시 처리량 확보 | 비용·근본 병목 유지 |

Testcontainers 기반 검증은 실제 DB 기능과 쿼리 실행을 확인하는 데 유리하지만 운영 데이터 분포와 하드웨어까지 완전히 재현한 측정이라고 가정해서는 안 된다.

## 왜 읽을까

대량 처리를 단순 `saveAll()` 최적화가 아니라 workload 특성과 운영 시간, 자원 사용량까지 포함한 문제로 보게 합니다.

**프로젝트에 적용**

**DevPedia·PawCycle 공통** — 관리자 일괄 등록이나 데이터 migration이 생기면 batch size를 바꿔가며 DB connection, commit 시간, 메모리, p95를 측정하고 온라인 요청에 영향을 주는지 확인할 수 있습니다.
