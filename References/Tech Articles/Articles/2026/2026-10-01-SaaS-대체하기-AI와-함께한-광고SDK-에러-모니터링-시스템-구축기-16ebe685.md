# SaaS 대체하기: AI와 함께한 광고SDK 에러 모니터링 시스템 구축기

> [!abstract] 한 줄 정리
> 서드파티 광고 SDK라는 특수한 실행 환경에서 범용 오류 모니터링 SaaS의 구조적 한계를 확인하고, 필요한 관측 기능을 직접 구축한 사례다. AI Agent는 제품 선택을 대신하기보다 구현 속도를 높이는 도구로 사용된다.

> NAVER D2 · 2026-06-16

## 핵심 내용

광고 SDK의 오류는 브라우저·앱의 실행 환경과 광고 화면의 생명주기, 외부 연동 상태에 영향을 받는다. 범용 SaaS 오류 모니터링이 필요한 맥락을 수집하지 못하거나 운영 정책과 맞지 않으면 단순 설정을 추가하는 방식만으로 분석 품질을 확보하기 어렵다.

```mermaid
flowchart LR
 A[광고 SDK 런타임 오류] --> B[이벤트 수집·정규화]
 B --> C[전용 수집 API]
 C --> D[저장·집계]
 D --> E[검색·알림]
 E --> F[원인 재현·수정]
```

*원문을 바탕으로 자체 재구성한 가로형 처리 경계 도식이다.*

NAVER D2 사례는 오류 수집·저장·검색·알림의 모든 기능을 새로 만들기보다 광고 SDK에 실제로 필요한 에러 종류와 실행 환경 식별자, 발생 시점의 광고 지면 정보를 우선 정의해 전용 모니터링 구조를 만들었다. AI Agent는 기존 구현 패턴 탐색과 빠른 코드 작성에 활용하되 오류 데이터의 정합성, 개인정보 노출 방지, 재현 가능성은 별도 검증해야 하는 계약이다. SaaS와의 비교는 제품 기능 목록이 아니라 오류를 얼마나 정확하게 재현·분류할 수 있는지로 평가해야 한다.

| 직접 관리할 계약 | 필요한 결정 | 남는 운영 책임 |
| --- | --- | --- |
| 오류 스키마 | SDK·광고 지면·버전 | 필드 누락·민감정보 |
| 수집량 | 폭주 시 샘플링/제한 | 비용과 정보 유실 |
| 알림 | 사용자 영향도·임계값 | 오탐·피로도 |
| 보관·조회 | 검색과 보존 기간 | 인프라·접근 권한 |

내재화를 통해 수집 필드를 제어하고 사내 도구와 연결할 수 있지만 스토리지 비용, 에러 급증 시 수집량 제한, 알림 오탐, 운영 당직 등의 책임이 팀으로 이동한다. 원문에 정량적인 비용 절감이나 오류 탐지율 개선이 제시되지 않으므로 근거 없이 주장하지 않는다. 어떤 오류와 지표가 진짜 사용자의 실패를 의미하는지도 검증 필요하다.

## 왜 읽을까

도구가 유명하거나 기능이 많다는 이유만으로 현재 문제에 맞는 것은 아니다. SaaS를 계속 커스터마이징할 비용과 작은 전용 시스템을 소유할 비용을 비교하는 판단 과정을 생각해 보기 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] Observability 도구를 추가하기 전에 실제로 답해야 하는 운영 질문을 먼저 목록화한다.
- [ ] 외부 SaaS의 제약을 발견하면 즉시 교체하지 말고 우회 비용·자체 구축 범위·장기 운영 비용을 비교한다.
- [ ] AI로 운영 도구를 만들더라도 수집 누락·오탐·장애 시 fallback은 사람이 검증 가능한 형태로 남긴다.
