# 수백만의 스냅샷 데이터를 효율적으로 관리하기 : 자동저장글 개선 (feat.MongoDB)

> [!abstract] 한 줄 정리
> 짧게 살아야 할 자동저장 스냅샷을 영구 게시글과 같은 관계형 테이블에 섞자 JOIN 오염과 인덱스·스토리지 비용이 누적됐다. 데이터의 수명과 접근 패턴에 맞춰 별도 저장소와 TTL을 선택한 사례다.

> 월부 테크 블로그 · 2025-07-28

## 핵심 내용

임시 자동저장 글을 영구 게시글과 같은 RDB 테이블에 `is_auto_save` 플래그로 보관하면 게시글을 조회하는 JOIN마다 임시글을 제외해야 한다. 월부의 경우 일부 쿼리에서 조건을 빠뜨려 UI에 임시 글이 섞이고, 짧은 수명의 임시 데이터를 영구 데이터와 같은 보관 정책으로 관리하는 문제가 나타났다.

자동저장은 보통 5~10초 간격으로 발생하고 작성 시간 20분 동안 사용자당 수백 건의 쓰기를 생성할 수 있다. 이 데이터는 수정 빈도가 높고 만료 시각이 명확하며 게시글·댓글 같은 관계형 조인에 참여할 필요가 없으므로 문서 DB에 별도로 저장하도록 분리했다. MongoDB의 TTL Index를 이용하면 마지막 수정 시점이나 정해진 만료 시각을 기준으로 임시 스냅샷을 정리할 수 있다. 다만 TTL 정리 작업은 정확히 그 초에 삭제됨을 보장하지 않으므로 사용 시점의 만료 판정도 필요할 수 있다.

```javascript
// MongoDB TTL Index 사용 원리의 예시. 보관 기간은 서비스 정책에 따라 결정
// db.drafts.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });
```

위 형식은 문서의 `expiresAt`에 만료 시각을 저장하는 일반적인 정책 예시이며 원문 구현의 정확한 인덱스 설정값은 아니다.

| 데이터 종류 | 영구 게시글 | 자동저장 스냅샷 |
| --- | --- | --- |
| 수명 | 사용자 삭제 전까지 | 짧고 만료 가능 |
| 관계 | 댓글·과제·검색 JOIN | 본문 임시 복원 중심 |
| 쓰기 | 사용자 제출 시 | 5~10초 주기 반복 |
| 선택 | RDB 정합성 관리 | MongoDB 문서·TTL 분리 |

기존 RDB에는 월평균 15만 건 이상의 임시글 데이터가 쌓였으며, 2025년 4월 개선 이후 자동저장 관련 고객 문의가 더 이상 접수되지 않았다고 보고했다. DB 접근 부하나 API 지연의 정량적인 Before/After는 공개되지 않았으므로 추정치를 만들지 않는다. 영구 게시글로 확정할 때 임시 저장소에서 본문을 읽어 전환하는 경계와 임시글 유실 시 사용자에게 보여 줄 복구 안내도 중요하다.

## 왜 읽을까

정규화와 NoSQL 중 어느 쪽이 무조건 낫다는 글이 아니다. 데이터의 수명, 쓰기 빈도, 조회 관계가 다르면 같은 도메인처럼 보여도 저장 경계를 달리해야 한다는 설계 기준을 보여준다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집글 작성 중 임시저장 기능이 필요해질 경우 완성된 모집글과 초안의 수명·조회·정합성 요구를 구분한다.
- [ ] 초안을 본 게시글 테이블에 플래그로 섞었을 때 목록·검색·JOIN에 미치는 영향을 통합 테스트로 확인한다.
- [ ] 초기에는 별도 RDB 초안 테이블과 만료 정리 작업부터 검토하고, 쓰기 부하가 확인될 때 문서 저장소 도입을 판단한다.
