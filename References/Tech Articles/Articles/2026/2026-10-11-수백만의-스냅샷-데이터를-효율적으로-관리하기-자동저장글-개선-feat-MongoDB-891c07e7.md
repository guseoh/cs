# 수백만의 스냅샷 데이터를 효율적으로 관리하기 : 자동저장글 개선 (feat.MongoDB)

> [!abstract] 한 줄 정리
> 짧게 살아야 할 자동저장 스냅샷을 영구 게시글과 같은 관계형 테이블에 섞자 JOIN 오염과 인덱스·스토리지 비용이 누적됐다. 데이터의 수명과 접근 패턴에 맞춰 별도 저장소와 TTL을 선택한 사례다.

> 월부 테크 블로그 · 2025-07-28

## 핵심 내용

- **문제:** 초기에는 기존 게시글 테이블에 is\_auto\_save 플래그를 추가했다. 임시 데이터가 댓글·과제 등 JOIN 결과에 섞여 조건 누락과 UI 오류가 발생했고, 여러 MyBatis XML·서비스에 예외 분기가 퍼졌다.
- **특성:** 자동저장은 사용자당 5~10초마다 발생하고 평균 20분 작성 동안 수백 번 쓰인다. 동시 사용자가 수백~수천 명일 수 있어 읽기보다 짧은 수명의 쓰기 작업이 많은 데이터다.
- **접근:** 자동저장 스냅샷을 영구 게시글과 분리해 MongoDB 계열 문서 저장소로 옮겼다. 유연한 문서 구조와 TTL Index 기반 자동 만료를 이용해 임시 데이터 수명에 맞게 관리한다.
- **수치:** 기존 RDB에는 월평균 15만 건 이상 자동저장 데이터가 만들어지고 있었다. 글은 2025년 4월 구조 개선 이후 자동저장 관련 고객 문의가 더 이상 접수되지 않았다고 보고한다.
- **트레이드오프:** 저장소 분리로 JOIN 오염과 RDB 비용을 줄이는 대신 운영할 데이터 저장소가 늘어난다. 응답시간·DB 부하의 구체적인 Before/After 수치는 공개하지 않았다.

## 왜 읽을까

정규화와 NoSQL 중 어느 쪽이 무조건 낫다는 글이 아니다. 데이터의 수명, 쓰기 빈도, 조회 관계가 다르면 같은 도메인처럼 보여도 저장 경계를 달리해야 한다는 설계 기준을 보여준다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집글 작성 중 임시저장 기능이 필요해질 경우 완성된 모집글과 초안의 수명·조회·정합성 요구를 구분한다.
- [ ] 초안을 본 게시글 테이블에 플래그로 섞었을 때 목록·검색·JOIN에 미치는 영향을 통합 테스트로 확인한다.
- [ ] 초기에는 별도 RDB 초안 테이블과 만료 정리 작업부터 검토하고, 쓰기 부하가 확인될 때 문서 저장소 도입을 판단한다.
