# 총 용량 1EB 초과! 서로 역사가 다른 두 HDFS를 어떻게 연결할까? 데이터 플랫폼 연계 중 직면한 과제와 설계 결정

> [!abstract] 한 줄 정리
> 대규모 시스템 통합은 기술적으로 연결하는 것만으로 끝나지 않는다. 서로 다른 확장 방식, 권한 모델, 운영 책임을 보존하면서 실제 병목을 측정해 점진적으로 연결하는 설계가 필요하다.

> LY Corporation Tech Blog

## 핵심 내용

두 조직의 HDFS 플랫폼을 연결할 때 단순히 파일 복사만 하면 되는 것이 아니라 접근 권한·Namespace와 라우팅 정책이 서로 다를 수 있다. LY의 구 LINE과 구 Yahoo Japan 주요 HDFS 총 용량은 1EB 이상이었고 한쪽은 ViewFS와 DB/테이블 역할 기반 권한, 다른 쪽은 RBF와 Path 기반 권한으로 발전해 왔다.

NameNode의 파일·블록 메타데이터가 늘수록 힙과 GC 부담이 증가하고 DataNode 확장·축소에는 Balancer의 대량 트래픽이 발생한다. 작은 파일 병합을 통해 메타데이터 개수를 줄이는 것이 우선이었으며, 한쪽 환경에서 Router CallQueue 증가를 보고 Router만 증설했지만 개선이 작았다. 실제로는 Observer NameNode 경로에서 발생하는 과도한 `msync` 호출이 Active NameNode를 압박하는 문제였다.

| 요소 | 구 LINE | 구 Yahoo Japan |
| --- | --- | --- |
| Namespace | ViewFS | RBF |
| 권한 기준 | DB·테이블 역할 | HDFS Path |
| 확장 부담 | NameNode 메타데이터·GC | Router/Observer·msync 병목 |
| 통합 전략 | 기존 운영 정책 보존 | 권한·전송부터 점진적 연계 |

읽기 결과의 최신성 요구를 해치지 않는 범위에서 `msync` 빈도를 조정해 Active NameNode 부하를 완화했다. 두 플랫폼의 권한과 데이터 위치를 단번에 통일하면 전환 비용이 크므로 기존 구조를 유지하면서 데이터 전송과 권한을 먼저 연결하는 점진적 전략을 택했다. 지연 지표 하나의 발생 지점이 실제 병목의 소유자와 다를 수 있다는 사례다.

## 왜 읽을까

규모가 커졌을 때 단순 스케일 아웃이 왜 근본 해결이 아닐 수 있는지, 그리고 조직·플랫폼 통합에서 기술 구조와 권한·운영 모델이 어떻게 함께 움직이는지를 한 사례에서 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 병목이 생기면 CPU나 DB처럼 겉으로 막힌 컴포넌트만 늘리지 말고 요청 경로의 실제 대기 원인을 측정한다.
- [ ] 향후 시스템 경계를 분리하거나 통합할 때 기존 데이터·권한·운영 흐름의 전환 비용을 먼저 기록한다.
- [ ] 전면 교체와 점진적 연계 두 안을 비교하고 롤백 가능한 작은 단계부터 검증한다.
