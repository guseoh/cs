# 총 용량 1EB 초과! 서로 역사가 다른 두 HDFS를 어떻게 연결할까? 데이터 플랫폼 연계 중 직면한 과제와 설계 결정

> [!abstract] 한 줄 정리
> 대규모 시스템 통합은 기술적으로 연결하는 것만으로 끝나지 않는다. 서로 다른 확장 방식, 권한 모델, 운영 책임을 보존하면서 실제 병목을 측정해 점진적으로 연결하는 설계가 필요하다.

> LY Corporation Tech Blog

## 핵심 내용

- **구조:** 구 LINE과 구 Yahoo Japan의 주요 HDFS를 합친 총 용량은 1EB를 넘지만, 전자는 ViewFS와 DB/테이블 중심 역할 기반 권한을, 후자는 RBF와 HDFS Path 기반 권한을 사용해 발전 경로와 운영 철학이 달랐다.
- **문제:** 파일·블록 수가 늘면서 NameNode 힙과 GC 부담이 커지고, DataNode 증감 시 블록 재배치와 Balancer가 대규모 네트워크 트래픽을 만들었다. 스몰 파일 병합으로 메타데이터와 조작 요청 수를 함께 줄였다.
- **접근:** 구 Yahoo Japan 측에서는 Router CallQueue가 병목처럼 보여 Router를 확충했지만 기대만큼 개선되지 않았다. 조사 결과 Observer NameNode 사용 시 발생하는 대량의 `msync`가 Active NameNode를 압박하는 실제 병목이었다.
- **결과:** 읽기 결과에 영향을 주지 않는 범위에서 `msync` 빈도를 재조정해 Active NameNode 부하와 HDFS 전체 지연을 개선했다. 표면적인 대기 지점과 근본 병목이 다를 수 있음을 보여준다.
- **트레이드오프:** 두 플랫폼을 즉시 하나로 합치면 전환 비용이 너무 커서, 기존 특성을 유지하면서 권한 관리와 데이터 전송을 먼저 연계하는 점진적 방식을 택했다.

## 왜 읽을까

규모가 커졌을 때 단순 스케일 아웃이 왜 근본 해결이 아닐 수 있는지, 그리고 조직·플랫폼 통합에서 기술 구조와 권한·운영 모델이 어떻게 함께 움직이는지를 한 사례에서 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 향후 시스템 경계를 분리하거나 통합할 때 기존 데이터·권한·운영 흐름의 전환 비용을 먼저 기록한다.
