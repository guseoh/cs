# Hive에서 Iceberg로: 데이터 반영 속도 12배 향상의 비밀

> [!abstract] 한 줄 정리
> 전체 재처리 대신 증분 처리로 전환하려면 속도뿐 아니라 최신성, 중복·유실, 장애 복구까지 함께 설계해야 합니다.

> techblog.lycorp.co.jp

## 핵심 내용

수억 건 상품 데이터를 변경 때마다 전체 재작성하던 Hive 기반 ETL을 Apache Iceberg와 Flink 기반 증분 처리 구조로 바꾼 사례입니다. 기존 60분 주기의 반영을 5분으로 줄였고, 늦게 도착한 과거 데이터가 최신 데이터를 덮지 않도록 이벤트 시각을 상태로 관리했습니다. 체크포인트와 2단계 커밋으로 Iceberg 저장과 Kafka 상태 메시지 사이 부분 성공도 방지했습니다.

Hive 테이블 전체를 재작성하던 구조는 상품 수가 커질수록 실제 변경량과 무관하게 동일한 대규모 작업을 반복한다. 원문은 MongoDB의 CDC와 **최신 전체 문서 보정 스트림**을 분리해서 받아 Flink의 상품 ID 기준 KeyedStream에 합친 뒤, 과거 `updateDate`가 최신 스냅샷을 덮어쓰지 않게 했다. 이런 시점 비교가 없으면 늦게 도착한 보정 이벤트가 오히려 데이터 최신성을 훼손할 수 있다.

![원문의 MongoDB CDC·보정 파이프라인과 Flink·Iceberg 저장 아키텍처](https://vos.line-scdn.net/landpress-content-v2-vcfc68aynwenkh3bno0ixfx8/5a166b89bbf94d5997ceee451c83cc81.jpg?updatedAt=1774862941000)

*그림 1. 보정 데이터 생성과 최신 데이터 반영을 분리한 스트리밍 ETL — [출처: LY Corporation Tech Blog](https://techblog.lycorp.co.jp/ko/from-hive-to-iceberg-12x-faster-data-updates)*

```text
# 개념 설명용 재구성: 상품 ID별 최신 시각 보호
if incoming.updateDate < state.lastProcessedUpdateDate:
    drop
else:
    update_state_and_merge_into_iceberg
```

**60분 → 5분**은 원문이 보고한 반영 주기 개선이다. Iceberg Sink와 상태 메시지의 부분 성공까지 고려해 체크포인트와 커밋 경계를 조정한 점이 단순 저장 형식 변경과 구별된다.

## 왜 읽을까

기술이 빠르다는 설명보다 데이터 최신성·중복·유실·장애 복구 요구사항을 먼저 정의하고 Spark와 Flink를 비교한 과정이 좋습니다. 운영 복잡도와 러닝 커브 증가도 비용으로 인정합니다.
