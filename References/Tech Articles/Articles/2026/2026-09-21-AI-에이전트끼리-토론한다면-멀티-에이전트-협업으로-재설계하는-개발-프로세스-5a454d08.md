# AI 에이전트끼리 토론한다면? 멀티 에이전트 협업으로 재설계하는 개발 프로세스

> [!abstract] 한 줄 정리
> 코드 생성 자체보다 스펙·검증·리뷰·전달 사이의 사람 조율이 병목이 되자, 제안자와 도전자 에이전트를 분리하고 근거 기반 상태 머신으로 개발 프로세스를 재설계했다. 자동화의 목표는 사람의 판단을 없애는 것이 아니라 판단 전에 필요한 증거를 자동으로 준비하는 것이다.

> LY Corporation Tech Blog

## 핵심 내용

AI 에이전트 하나가 구현을 빠르게 하더라도 사람이 스펙을 전달하고 코드 리뷰·테스트·PR 정리를 계속 연결한다면 조율 비용이 그대로 남는다. LY의 멀티 에이전트 프로세스는 작업을 스펙→구현→전달로 나누고, 제안과 반론을 주고받도록 역할을 구성했다.

 ```mermaid
flowchart LR
 A[Spec 제안·반론] --> B[검증 가능한 계약 확정]
 B --> C[Build 구현·테스트]
 C --> D{테스트·위험 확인}
 D -- 실패 --> E[수정 또는 사람 리뷰]
 D -- 통과 --> F[PR·검증 근거 전달]
```

*원문 내용을 토대로 가로형으로 자체 재구성한 도식이다.*

제안자는 스펙·코드를 발전시키고 도전자는 모호한 요구, 누락된 테스트, 보안·성능, 배포 준비 상태를 반박한다. 조율자는 증거가 있는 지적만 반영하고 다음 단계로 넘길지 결정한다. 빌드 전에 테스트·검증 명령을 스펙에 포함하면 코드를 작성한 뒤 사후적으로 검증 범위를 상상할 필요가 없다. 전달 단계에서는 diff뿐 아니라 검사 결과, 알려진 위험과 리뷰어가 먼저 볼 파일도 PR에 포함한다.

| 단계 | 제안자/도전자 역할 | 다음 단계 통과 조건 |
| --- | --- | --- |
| Spec | 제약·대안·테스트 도출 | 모호한 계약 해결 |
| Build | 코드·검증 반복 | 컴파일·테스트·보안 근거 |
| Delivery | PR 설명·위험 정리 | 사람 리뷰 우선순위 제공 |
| 진동 감지 | 반복 실패 기록 | 자동 루프 중단·설계 재검토 |

A→B→A처럼 같은 실패가 여러 번 돌아오는 경우에는 자동 수정 루프를 중단하고 설계 리뷰로 올린다. 모든 작업을 토론 구조에 넣으면 단일 에이전트보다 비용과 지연이 커지므로 고위험·비동기 CI 업무에 선택적으로 사용한다. 에이전트 사이의 합의 자체가 올바름의 증거가 아니며 실제 실행 로그·컴파일·테스트 결과가 근거다.

## 왜 읽을까

멀티 에이전트를 “에이전트를 많이 띄우기”로 설명하지 않고 책임 분리, 수렴 조건, 증거, 중단 규칙으로 설계한다. AI 코딩에서 품질을 높이려면 더 긴 프롬프트보다 어떤 단계에서 어떤 증거를 남기게 할지 설계해야 한다는 관점을 얻기 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 콘텐츠·코드 대규모 검토에서 작성/수정 Agent와 반대 관점의 QA Agent 역할을 분리한다.
- [ ] 영역별 작업 전에 범위·금지사항·완료 조건을 짧은 스펙으로 고정하고, 최종 보고서는 테스트·diff·검증 결과를 근거로 작성하게 한다.
- [ ] 동일 실패가 반복되면 자동 수정 횟수를 늘리지 말고 원인 재분석 단계로 전환하는 stop rule을 둔다.
