# AI 에이전트끼리 토론한다면? 멀티 에이전트 협업으로 재설계하는 개발 프로세스

> [!abstract] 한 줄 정리
> 코드 생성 자체보다 스펙·검증·리뷰·전달 사이의 사람 조율이 병목이 되자, 제안자와 도전자 에이전트를 분리하고 근거 기반 상태 머신으로 개발 프로세스를 재설계했다. 자동화의 목표는 사람의 판단을 없애는 것이 아니라 판단 전에 필요한 증거를 자동으로 준비하는 것이다.

> LY Corporation Tech Blog

## 핵심 내용

- **문제:** AI가 각 단계는 빠르게 처리해도 사람이 스펙 작성, 결과 복사, 테스트 재실행, diff 검토, PR 설명 요청을 계속 연결해야 해 조율 계층이 병목으로 남았다.
- **구조:** `스펙 → 빌드 → 전달`을 별도 단계로 나누고, 제안자는 산출물을 발전시키고 도전자는 모호성·테스트·보안·성능·준비 상태를 반박한다. 조율자가 수정·상위 보고·다음 단계 진행 여부를 결정한다.
- **접근:** 빌드 전에 스펙에서 테스트와 검증 명령을 도출하고, 전달 단계에서는 변경 요약뿐 아니라 통과한 검사·남은 리스크·리뷰 우선순위까지 PR 패키지로 만든다. 에이전트의 이의 제기와 거부도 실행 로그·컴파일·테스트 같은 구체적 증거를 요구한다.
- **주의점:** A→B→A처럼 실패가 되돌아오는 진동을 감지하면 자가 수정 루프를 중단하고 재설계 리뷰로 올린다. 모든 작업에 동일한 토론 비용을 쓰지 않고 리스크에 따라 리뷰 강도를 조절한다.
- **트레이드오프:** 단일 에이전트보다 토큰 비용이 크고 작업당 수 분이 걸릴 수 있어 비동기 CI 작업에 적합하다. 불명확한 제품 결정이나 검증 가능한 정답이 없는 작업은 사람의 판단을 유지해야 한다.

## 왜 읽을까

멀티 에이전트를 “에이전트를 많이 띄우기”로 설명하지 않고 책임 분리, 수렴 조건, 증거, 중단 규칙으로 설계한다. AI 코딩에서 품질을 높이려면 더 긴 프롬프트보다 어떤 단계에서 어떤 증거를 남기게 할지 설계해야 한다는 관점을 얻기 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 콘텐츠·코드 대규모 검토에서 작성/수정 Agent와 반대 관점의 QA Agent 역할을 분리한다.
- [ ] 영역별 작업 전에 범위·금지사항·완료 조건을 짧은 스펙으로 고정하고, 최종 보고서는 테스트·diff·검증 결과를 근거로 작성하게 한다.
- [ ] 동일 실패가 반복되면 자동 수정 횟수를 늘리지 말고 원인 재분석 단계로 전환하는 stop rule을 둔다.
