# nginx 설정 없이 우아하게 서비스 점검하기 (下)

> [!abstract] 한 줄 정리
> 점검 기능도 인프라 제약과 운영 사용자를 고려하면 단순 nginx 설정이 아니라 메타데이터와 실행 상태를 분리한 애플리케이션 기능으로 설계할 수 있다.

> 컬리 기술 블로그 · 2025-10-10

## 핵심 내용

- **문제:** nginx가 모든 요청을 받는 구조가 아니고 설정도 인프라팀 소유라서, 개발자 외 운영자까지 쉽게 사용할 수 있는 점검·접근 차단 기능이 필요했다.
- **구조:** 차단할 path를 정의하는 **메타데이터**와 ‘언제·누구를 차단할지’를 나타내는 **실행데이터**를 분리했다. 실행데이터에는 cluster·warehouse·제외 권한을 포함한다.
- **접근:** 메타데이터는 Google Sheet→BigQuery로 관리하되 BigQuery 직접 조회 지연을 피하기 위해 Redis에 캐시하고 정확히 3분마다 동기화한다.
- **구조:** 즉시 반영이 필요한 실행데이터는 Redis에 직접 등록·삭제하며, 프론트는 Vue Router에서 화면을 차단하고 백엔드는 Spring AOP로 RestController 요청을 선처리한다.
- **주의점:** 모든 차단 로직을 하나의 저장소나 관심사에 섞지 않고, 예외 경로와 특정 권한 우회 조건을 별도 정책으로 관리해 운영 중 점검 자체가 막히는 상황을 피한다.

## 왜 읽을까

운영 기능을 만들 때 ‘가장 표준적인 기술’보다 **현재 인프라의 소유권, 데이터 특성, 반영 속도, 실제 운영자의 사용 방식**을 함께 봐야 한다는 좋은 사례다. 작은 기능도 경계를 잘 나누면 운영 리스크를 크게 줄일 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 배포·DB 작업 시 사용할 maintenance mode의 차단 범위와 예외 경로를 정의한다.
- [ ] 즉시 반영해야 하는 실행 상태와 천천히 갱신 가능한 설정 정보를 분리한다.
- [ ] 운영자·관리자 우회 경로가 실제 장애 상황에서도 동작하는지 테스트한다.
