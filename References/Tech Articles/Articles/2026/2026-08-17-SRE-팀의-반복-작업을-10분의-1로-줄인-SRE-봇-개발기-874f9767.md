# SRE 팀의 반복 작업을 10분의 1로 줄인 SRE 봇 개발기

> [!abstract] 한 줄 정리
> 운영 자동화는 봇을 만드는 것보다 먼저 반복 작업의 시간과 실수 비용을 측정하고, 가치가 큰 작업부터 줄이는 게 핵심입니다.

> LY Corporation Tech Blog · 2026-03-24

## 핵심 내용

LINE Home DevOps 팀은 배포와 인프라 요청을 처리하면서 Slack → Confluence → Jira를 반복해서 오갔고, 일주일 측정 결과 배포 요청과 일반 문의 처리에 **주당 약 15시간**이 들었습니다. Slack을 요청 진입점으로 두고 Jira 티켓 생성, 버전·스프린트 설정, Confluence 체크리스트 연결 등을 자동화했습니다.

외부 API 호출은 비동기로 처리하고, Slack-Jira 매핑은 Redis+TTL로 관리했습니다. 동시 클릭 문제에는 Redis Transaction을 사용했고, Slack·Jira·Confluence·Redis 의존성은 포트와 어댑터로 격리했습니다. 실제 배포 요청 시 SRE가 직접 처리하던 작업 시간이 **약 30분에서 1분 이내**로 줄었습니다.

Slack 봇은 사람에게 메시지를 대신 보내는 기능이 아니라 반복적인 배포 요청을 **구조화된 업무 절차**로 바꾸는 인터페이스다. Redis TTL이 있는 Slack-Jira 매핑을 쓰면 같은 요청의 후속 처리를 추적하기 쉬워지지만 중복 클릭과 외부 API 실패가 분리된 경합 조건이 된다. 포트와 어댑터로 외부 서비스 호출을 감싸면 Slack·Jira·Confluence의 응답 형식 변화가 도메인 흐름 전체에 전파되는 것을 줄일 수 있다.

| 원문 측정 | 도입 전 | 도입 후 |
| --- | --- | --- |
| 배포 요청의 SRE 직접 처리 | 약 30분 | 1분 이내 |
| 전체 배포·문의 반복 업무 | 주당 약 15시간 | 자동화 대상 식별 |

전후 수치는 담당자 손으로 수행하는 작업 시간 비교이며 모든 배포의 총 소요 시간이 1분으로 줄었다는 뜻은 아니다.

## 왜 읽을까

“운영 자동화 봇을 만들었다”는 결과보다 **자동화할 가치가 있는지 먼저 시간을 측정했다**는 점이 좋습니다. 자동화 과정에서도 비동기 처리, 상태 저장, 동시성, 외부 시스템 격리 같은 백엔드 설계 문제가 그대로 드러납니다.

**프로젝트에 적용 — PawCycle**

자동화할 작업을 고를 때 먼저 아래 값을 기록해볼 수 있습니다.

- 작업 빈도
- 한 번 처리 시간
- 실수 발생 시 비용

`작업 빈도 × 처리 시간 × 실수 비용`이 큰 수작업부터 자동화하고, 전후 시간을 다시 측정하면 **어떤 운영 비용을 얼마나 줄였는지** 근거로 남길 수 있습니다.
