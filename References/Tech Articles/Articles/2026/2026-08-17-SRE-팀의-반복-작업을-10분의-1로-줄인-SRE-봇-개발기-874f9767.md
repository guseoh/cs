# SRE 팀의 반복 작업을 10분의 1로 줄인 SRE 봇 개발기

> [!abstract] 한 줄 정리
> 운영 자동화는 봇을 만드는 것보다 먼저 반복 작업의 시간과 실수 비용을 측정하고, 가치가 큰 작업부터 줄이는 게 핵심입니다.

> LY Corporation Tech Blog · 2026-03-24

## 핵심 내용

- **문제:** LINE Home DevOps 팀은 배포와 인프라 요청을 처리하면서 Slack → Confluence → Jira를 반복해서 오갔고, 일주일 측정 결과 배포 요청과 일반 문의 처리에 **주당 약 15시간**이 들었습니다.
- **자동화 범위:** Slack을 요청 진입점으로 두고 Jira 티켓 생성, 버전·스프린트 설정, Confluence 체크리스트 연결 등을 자동화했습니다.
- **백엔드 설계:** 외부 API 호출은 비동기로 처리하고, Slack-Jira 매핑은 Redis+TTL로 관리했습니다. 동시 클릭 문제에는 Redis Transaction을 사용했고, Slack·Jira·Confluence·Redis 의존성은 포트와 어댑터로 격리했습니다.
- **결과:** 실제 배포 요청 시 SRE가 직접 처리하던 작업 시간이 **약 30분에서 1분 이내**로 줄었습니다.

## 왜 읽을까

“운영 자동화 봇을 만들었다”는 결과보다 **자동화할 가치가 있는지 먼저 시간을 측정했다**는 점이 좋습니다. 자동화 과정에서도 비동기 처리, 상태 저장, 동시성, 외부 시스템 격리 같은 백엔드 설계 문제가 그대로 드러납니다.

**프로젝트에 적용 — PawCycle**

자동화할 작업을 고를 때 먼저 아래 값을 기록해볼 수 있습니다.

- 작업 빈도
- 한 번 처리 시간
- 실수 발생 시 비용

`작업 빈도 × 처리 시간 × 실수 비용`이 큰 수작업부터 자동화하고, 전후 시간을 다시 측정하면 **어떤 운영 비용을 얼마나 줄였는지** 근거로 남길 수 있습니다.
