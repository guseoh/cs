# 월부 신입 백엔드 개발자가 받은 첫 과업은 무엇일까?

> [!abstract] 한 줄 정리
> 140만 건 구매 이력을 처리하는 배치의 병목은 계산보다 반복적인 DB 접근에 있었다. 벌크 연산, 인덱스, No-Offset 읽기와 메모리 캐시를 순차적으로 적용해 실행 시간을 28시간에서 4분 32초로 줄였다.

> 월부 테크 블로그 · 한성현 로덕 · 2025-02-08

## 핵심 내용

140만 건 구매 이력을 분석해 상품을 함께 구매한 순서쌍과 사용자의 마지막 구매 상품을 계산하는 배치를 작성했을 때, 거래 1건마다 최소 다섯 번의 DB 접근이 필요했다. 이 때문에 Historical Batch는 최초 약 28시간이 걸렸으며, 알고리즘의 반복 횟수뿐 아니라 데이터 읽기·쓰기 방식과 인덱스가 전체 수행 시간을 결정했다.

집계 결과를 `product_pairs`에, 사용자별 최근 구매를 `last_purchased_products`에 분리했다. JPA 영속성 컨텍스트와 JPQL 벌크 작업을 조정해 반복 DB 접근을 줄인 뒤, 정렬·범위 조회에 맞는 복합 인덱스를 구성했다. Reader에서는 OFFSET이 커질수록 이전 행을 스캔하는 문제를 피하려고 마지막으로 처리한 키를 커서로 사용하는 No-Offset 방식으로 바꿨다. 이 방식은 인덱스 정렬이 안정적이고 중복 키를 구분할 수 있다는 조건이 필요하다.

```sql
-- No-Offset Reader 핵심 원리: 원문 구현을 설명하기 위한 예시
SELECT id, user_id, product_id
FROM purchase_history
WHERE id > :lastProcessedId
ORDER BY id
LIMIT :batchSize;
```

이전 페이지의 마지막 키를 다음 조회 조건에 전달하면 큰 OFFSET을 건너뛰는 비용을 피할 수 있다. 원문 쿼리와 동일한 SQL이라고 가정하지 않는다.

| 최적화 단계 | 측정 값 | 분모/영향 범위 |
| --- | --- | --- |
| 초기 Historical Batch | 약 28시간 | 전체 최초 이력 처리 |
| 영속성·벌크 연산 정리 | 약 6시간 | 전체 배치 |
| 복합 인덱스 적용 | 약 3시간 | 전체 배치 |
| No-Offset Reader | 32분 → 1분 30초 | 140만 건 읽기 구간 |
| 인메모리 최근 구매 집계 등 | 최종 4분 32초 | 전체 배치 |

No-Offset Reader로 140만 건 읽기 시간이 32분에서 1분 30초로 줄었다. 사용자 약 19만 명의 마지막 구매 상태는 약 20MB 인메모리 캐시로 관리하였고 전체 배치는 최종 4분 32초에 끝났다. 조회와 집계의 어느 단계를 측정한 숫자인지 구분해야 하며, 28시간에서 4분 32초로의 차이는 여러 단계의 리팩터링을 합친 결과이지 단일 SQL 힌트의 효과가 아니다.

## 왜 읽을까

개선 순서마다 실제 실행 시간을 남겨 병목 가설과 측정 결과를 비교하는 사례다. JPA·인덱스·페이지네이션·캐시가 각각 어느 비용을 줄였는지 분리해서 볼 수 있다. 특히 신입 개발자가 기술 선택의 근거와 PR 크기까지 회고한 점이 유용하다.
