# LLM Wiki: 코드 기준으로 자동 최신화되는 도메인 지식 SSOT 만들기

> [!abstract] 한 줄 정리
> MSA에서 흩어진 정책과 문서를 매번 AI에 다시 주입하는 대신, 실제 코드를 가장 강한 근거로 삼아 raw와 knowledge 두 층의 SSOT를 만들고 PR 병합마다 최신화한다. AI가 문서를 만들더라도 모호한 결정과 변경 승인에는 사람 검증을 남긴다.

> LY Corporation Tech Blog · 2026-08-28

## 핵심 내용

- **문제:** 여러 서비스와 문서에 비즈니스 정책이 흩어진 MSA 환경에서는 AI가 오래된 문서나 부족한 맥락을 추론으로 보완하면서 잘못된 스펙을 만들 수 있었다.
- **구조:** 코드에서 현재 동작을 추출한 `raw`에는 원본 근거와 변경 이력을 누적하고, `knowledge`에는 현시점에 유효한 정책·수치·흐름만 정리한다. 코드는 무엇이 동작하는지, ADR·주석·문서는 왜 그렇게 결정됐는지를 보완한다.
- **접근:** baseline 생성 이후 PR마다 제목·본문·리뷰·diff·주변 코드를 분석해 변경 스펙을 만들고, GitHub Actions가 `추출 → 사람 리뷰 → ingest → 주기적 lint` 흐름을 실행한다.
- **주의점:** API 엔드포인트, Kafka 토픽, DB 컬렉션, enum 같은 식별자는 한 글자만 달라져도 추적이 깨지므로 원문 그대로 유지하고, lint로 raw와 knowledge의 식별자 무결성·최신성·링크 정합성을 검사한다.
- **트레이드오프:** 완전 자동화를 택하지 않았다. baseline의 모호한 지점과 PR 단위 스펙 변경은 아직 사람이 검증하며, 신뢰가 쌓인 부분부터 자동화 범위를 넓힌다.

## 왜 읽을까

AI 개발에서 컨텍스트를 많이 넣는 것보다 **무엇을 기준 정보로 삼고 어떻게 최신성을 보장할지**가 더 중요하다는 관점을 얻을 수 있다. 특히 코드와 문서를 별도 진실로 두지 않고, 코드 사실과 결정 배경을 분리해 같은 지식 체계로 연결하는 방식이 실용적이다.

**프로젝트에 적용 — DevPedia**

- [ ] Entity·Validator·Service·설정에서 현재 정책과 예외를 역추출해 가벼운 baseline 문서를 만든다.
- [ ] ADR에는 코드만으로 알 수 없는 선택 이유와 제외 범위만 남기고 구현 사실을 중복 기록하지 않는다.
- [ ] PR merge 시 변경된 정책·API·DB 계약만 추출해 문서 갱신 후보를 만들고 사람이 검토하는 흐름을 실험한다.
- [ ] 문서 최신성보다 먼저 `코드 사실과 문서가 충돌하는지`를 검증하는 lint 규칙을 정의한다.
