# 쉼 없이 도는 테스트, 사람이 어디까지 돌봐야 할까요? - 토스닥터(Toss Doctor)

> [!abstract] 한 줄 정리
> 테스트 자동화의 병목을 실행 자체가 아니라 작성·요소 탐색·실패 진단·복구까지 포함한 전체 유지보수 루프로 보고, AI는 실패한 순간에 필요한 만큼만 개입하도록 설계한 사례다.

> Toss Tech · 2026-09-22

## 핵심 내용

- **문제:** 토스 앱은 플랫폼별로 5~7개의 RC 빌드가 쌓이고 빌드마다 스모크 테스트가 필요했지만, V1은 테스트 작성 비용과 UI 변경에 따른 깨짐, 실패 원인 분석 비용이 계속 커졌다.
- **접근:** 사람은 Gherkin의 Given-When-Then으로 검증 의도만 작성하고, LLM과 Appium MCP가 실제 디바이스를 보며 실행 코드를 생성한다. 요소 탐색도 스크린샷·노출 요소 → 전체 XML → 사람 질문 순으로 비용을 단계화했다.
- **주의점:** 검증 단계에서는 유사 요소 매칭을 금지했다. 실제로 잘못된 유사 매칭 때문에 5개 스텝이 연속으로 거짓 성공한 사례가 있어, 복구 편의보다 검증 신뢰성을 우선했다.
- **구조:** 실패 시 시나리오·코드·에러·직전 화면들을 모아 recoverable 여부를 판정하고, 고칠 수 있는 문제만 재현 → 실제 화면 확인 → 코드 수정 → 재실행 → 학습 기록 순으로 자동 복구한다.
- **결과:** 세 명의 테스터가 이틀 동안 수행하던 배포 전 회귀 테스트 영역으로 확장했고, 1,375개 테스트 케이스를 기존 업무와 병행하며 3주 만에 자동화했다.

## 왜 읽을까

AI 테스트 자동화를 단순히 ‘테스트 코드를 생성한다’로 축소하지 않는다. 자동화가 오래 살아남으려면 실패를 어디까지 스스로 복구해도 되는지, 어디서부터 사람에게 넘겨야 하는지, 그리고 거짓 성공을 어떻게 막을지를 함께 설계해야 한다는 점이 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 회원가입 → 로그인 → `/me` → 로그아웃 같은 핵심 인증 흐름을 먼저 실행 가능한 시나리오로 고정한다.
- [ ] AI가 테스트를 수정하더라도 assertion이나 기대 결과를 임의 완화하지 못하도록 검증 규칙을 둔다.
- [ ] 실패 결과를 `환경 문제 / 코드로 복구 가능 / 사람 판단 필요`로 분류해 반복되는 조사 비용을 줄인다.
