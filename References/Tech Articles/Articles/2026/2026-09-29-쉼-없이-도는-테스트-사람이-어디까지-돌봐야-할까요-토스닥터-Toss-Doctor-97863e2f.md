# 쉼 없이 도는 테스트, 사람이 어디까지 돌봐야 할까요? - 토스닥터(Toss Doctor)

> [!abstract] 한 줄 정리
> 테스트 자동화의 병목을 실행 자체가 아니라 작성·요소 탐색·실패 진단·복구까지 포함한 전체 유지보수 루프로 보고, AI는 실패한 순간에 필요한 만큼만 개입하도록 설계한 사례다.

> Toss Tech · 2026-09-22

## 핵심 내용

모바일 앱의 릴리스 후보(RC)가 플랫폼별로 5~7개 쌓이는 환경에서는 매 빌드마다 회귀 검증을 사람이 반복하기 어렵다. 그렇다고 AI가 화면을 보고 클릭하는 방식만 채택하면 유사한 요소를 잘못 선택해 테스트가 PASS가 되는 위양성이 발생할 수 있다.

Toss Doctor는 사람이 Gherkin Given-When-Then으로 검증 의도를 작성하고 LLM과 Appium MCP가 디바이스를 탐색해 테스트 코드를 실행한다. Locator 탐색 비용을 화면의 스크린샷·노출 요소→전체 XML→사람에게 질문하는 순서로 나누었다. 검증 단계에서는 유사 요소를 자동 매칭하지 않는 규칙을 두었는데, 과거 잘못된 유사 매칭이 연속 다섯 스텝을 거짓 성공시킨 사례가 있었기 때문이다.

| 단계 | AI 자동화 범위 | 사람·규칙의 통제 |
| --- | --- | --- |
| 요구사항 | Gherkin 코드화 | 검증 의도 승인 |
| 요소 탐색 | 화면→XML 순차 검색 | 모호한 경우 질문 |
| PASS 판정 | assertion 실행 | 유사 요소 강제 매칭 금지 |
| 오류 복구 | recoverable만 재생성 | 실제 제품 버그와 테스트 버그 구분 |
| 성과 | 3주간 1,375 TC 자동화 | 위양성·유지보수 지속 검증 |

실패한 테스트는 시나리오와 실행 코드·오류·직전 화면을 모아 자동 복구 가능 여부를 판단한 뒤 재현→화면 확인→수정→재실행→학습 기록 순서로 처리한다. 1,375개 테스트 케이스를 3주 동안 자동화해 세 명의 테스터가 이틀 수행하던 수동 회귀 영역을 대체할 범위를 확보했다. 단순히 자동 실행 건수가 많아진 것보다 검증 의도를 보존하고 잘못된 PASS를 차단한 계약이 신뢰성의 핵심이다.

## 왜 읽을까

AI 테스트 자동화를 단순히 ‘테스트 코드를 생성한다’로 축소하지 않는다. 자동화가 오래 살아남으려면 실패를 어디까지 스스로 복구해도 되는지, 어디서부터 사람에게 넘겨야 하는지, 그리고 거짓 성공을 어떻게 막을지를 함께 설계해야 한다는 점이 좋다.

**프로젝트에 적용 — DevPedia**

- [ ] 회원가입 → 로그인 → `/me` → 로그아웃 같은 핵심 인증 흐름을 먼저 실행 가능한 시나리오로 고정한다.
- [ ] AI가 테스트를 수정하더라도 assertion이나 기대 결과를 임의 완화하지 못하도록 검증 규칙을 둔다.
- [ ] 실패 결과를 `환경 문제 / 코드로 복구 가능 / 사람 판단 필요`로 분류해 반복되는 조사 비용을 줄인다.
