# 킹덤 서버! 튜토리얼

> [!abstract] 한 줄 정리
> 낯선 코드베이스에 합류할 때는 문법을 전부 외운 뒤 개발하는 것이 아니라, 팀의 핵심 모델을 학습하고 테스트·작은 버그 수정·리뷰를 거쳐 실제 동작을 이해하는 과정이 효과적이다.

> 데브시스터즈 DEVTECH · 2026-06-02

## 핵심 내용

- **온보딩 구조:** Scala·함수형 프로그래밍 기초 학습 레포지토리 → ZPure(순수 상태 계산)와 ZIO(외부 효과 관리) 이해 → 유닛/시나리오 테스트 → 작은 버그 수정 → 콘텐츠 구현으로 단계를 나눴다.
- **설계:** ZPure는 기존 상태를 직접 바꾸지 않고 새 상태를 계산하며, DB·네트워크 등 부수 효과는 ZIO 계층에서 관리한다. 테스트는 개별 규칙과 여러 기능이 이어지는 사용자 시나리오를 구분한다.
- **버그 사례:** 클라이언트가 아무 젤리도 처치하지 않은 경우 `0`을 보내면 서버에 존재하지 않는 0번 젤리 조회로 오류가 났다. 미참여를 `None`으로 표현하고 기본 참여 보상만 지급하도록 수정했다.
- **시행착오:** 불변 컬렉션의 `shuffle` 결과를 버려 카드가 실제로 섞이지 않았고, 즉시 평가되는 난수와 실행 시점에 생성되는 난수의 차이도 코드 리뷰에서 발견했다.
- **운영 관점:** 기능 배포 뒤에도 QA에서 놓친 오류를 모니터링하고, 보상 지급 오류처럼 이미 발생한 상태 변경의 후속 처리까지 기획팀과 논의한다.

## 왜 읽을까

학습과 구현을 분리한 긴 준비 기간보다, 테스트로 현재 동작을 확인하고 작은 변경을 직접 완결하는 과정이 코드베이스 이해에 도움이 된다는 실제 사례다.

특히 `0`과 `None`의 차이, 불변 값의 반환, 난수 평가 시점처럼 사소해 보이는 모델링 선택이 실제 버그로 연결되는 과정을 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 기존 핵심 흐름 하나를 골라 요청부터 DB 변경까지 직접 추적하고 상태 전이를 기록한다.
- [ ] 정상 경로와 예외 경로의 테스트를 먼저 읽고, 누락된 경계 조건 하나를 보강한다.
- [ ] 작은 버그 수정 또는 리팩터링 한 건을 직접 구현해 변경 이유·테스트 결과·회고를 남긴다.
