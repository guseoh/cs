# 킹덤 서버! 튜토리얼

> [!abstract] 한 줄 정리
> 낯선 코드베이스에 합류할 때는 문법을 전부 외운 뒤 개발하는 것이 아니라, 팀의 핵심 모델을 학습하고 테스트·작은 버그 수정·리뷰를 거쳐 실제 동작을 이해하는 과정이 효과적이다.

> 데브시스터즈 DEVTECH · 2026-06-02

## 핵심 내용

쿠키런: 킹덤의 서버 코드베이스는 Scala 함수형 프로그래밍, ZPure 및 ZIO처럼 상태 변화와 외부 효과를 구분하는 모델을 사용한다. 신규 엔지니어가 처음부터 큰 콘텐츠를 수정하면 도메인 규칙과 부수 효과, 테스트 경계를 동시에 이해해야 해 오류 위험이 커진다.

![ZPure ZSTM ZIO 층으로 정리된 Tri-Z 아키텍처](https://tech.devsisters.com/static/acaca24ce41e8f5bc581d0cc397e0981/25946/tri-z.png)

*그림 1. 원문 Tri-Z 아키텍처: 순수 계산을 중심에 두고 상태 원자성·외부 효과를 바깥 계층으로 분리 — [출처: 원문 기술 블로그](https://tech.devsisters.com/posts/ck-server-tutorial/)*

온보딩에서는 먼저 언어·FP 기본을 학습하고 작은 유닛 테스트로 순수 상태 계산을 확인한다. ZPure가 주어진 기존 상태에서 새 상태를 계산하면 ZIO는 DB 기록과 네트워크 등 실패 가능한 외부 작업을 조율한다. 이후 여러 기능이 연결되는 시나리오 테스트와 작은 운영 버그 수정으로 범위를 넓힌다. 실제로 클라이언트가 '아무 젤리도 처치하지 않음'을 0으로 보냈을 때 서버가 존재하지 않는 0번 객체를 조회하던 문제를 `None`으로 표현해 수정했다.

```scala
// 순수 상태 변환과 외부 효과의 분리를 보여 주는 의사 코드
val nextState = pureGameLogic(currentState, action)
val persisted = saveToDatabase(nextState) // 실제 효과 경계
```

학습용 의사 코드이며 원문의 실제 ZPure/ZIO API 서명을 옮긴 것은 아니다.

불변 컬렉션의 `shuffle` 결과를 버리면 컬렉션이 실제로 바뀌지 않는 점이나, 즉시 실행된 난수와 실행 시점 난수의 차이처럼 함수형 환경의 오해도 코드 리뷰에서 발견했다. 성공적인 온보딩은 문법 암기가 아니라 **순수 계산→외부 효과→시나리오 결과**를 분리하고 예외 상황을 코드와 테스트로 설명할 수 있는 상태다. 원문은 수치화된 팀 전체 생산성 향상률을 제시하지 않았다.

## 왜 읽을까

학습과 구현을 분리한 긴 준비 기간보다, 테스트로 현재 동작을 확인하고 작은 변경을 직접 완결하는 과정이 코드베이스 이해에 도움이 된다는 실제 사례다.

특히 `0`과 `None`의 차이, 불변 값의 반환, 난수 평가 시점처럼 사소해 보이는 모델링 선택이 실제 버그로 연결되는 과정을 볼 수 있다.

**프로젝트에 적용 — PawCycle**

- [ ] 기존 핵심 흐름 하나를 골라 요청부터 DB 변경까지 직접 추적하고 상태 전이를 기록한다.
- [ ] 정상 경로와 예외 경로의 테스트를 먼저 읽고, 누락된 경계 조건 하나를 보강한다.
- [ ] 작은 버그 수정 또는 리팩터링 한 건을 직접 구현해 변경 이유·테스트 결과·회고를 남긴다.
