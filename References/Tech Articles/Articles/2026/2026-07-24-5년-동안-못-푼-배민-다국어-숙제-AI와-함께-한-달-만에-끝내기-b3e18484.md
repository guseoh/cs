# 5년 동안 못 푼 배민 다국어 숙제, AI와 함께 한 달 만에 끝내기

> [!abstract] 한 줄 정리
> AI 도입의 가치는 기존에 너무 비싸서 못 풀던 문제의 비용 구조를 바꿀 때 커지며, 그래도 성공은 작은 PoC와 범위 통제에서 시작합니다.

> techblog.woowahan.com

## 핵심 내용

배민의 다국어 지원은 수년간 시스템 전체와 방대한 메뉴 데이터를 건드려야 하는 비용 때문에 해결하기 어려웠습니다. FDH와 LLM을 활용하면서 번역 파이프라인과 BFF 응답 경로를 분리하고, 앱 전체를 갈아엎지 않는 방식으로 핵심 범위를 좁혀 약 한 달 만에 구현했습니다.

처음부터 완성형을 설계하기보다 PoC로 가능성을 빠르게 확인하고 MVP에 필요한 부분만 남긴 의사결정이 중요합니다.

다국어 제공을 위해 전체 앱의 문자열과 데이터 모델을 한꺼번에 바꾸면 화면, 검색, 메뉴 데이터, 고객 서비스의 변경 범위가 폭발한다. 원문은 FDH·LLM 기반 번역 파이프라인과 BFF 응답 조합을 분리해 **변경이 필요한 최소 경계**에서 다국어를 제공하는 방법을 검토했다. 번역 생성 품질뿐 아니라 언어별 누락, 원문 변경 후 최신성, 비동기 번역 실패 시 폴백이 중요하다.

| 단계 | 검증해야 할 계약 |
| --- | --- |
| 원문 데이터 수집 | 상품·메뉴·메타데이터 식별 |
| LLM 번역·검수 | 번역 품질·금칙어·일관성 |
| 번역 데이터 저장 | 원문 버전·언어 매핑 |
| BFF 응답 구성 | 언어 선택·미번역 폴백 |
| 점진 릴리스 | 이용자 화면의 혼합 언어·오류 |

약 한 달이라는 기간은 해당 범위의 MVP 구현 과정이며 원문 조직의 조건과 같은 결과를 모든 서비스에서 재현할 수 있다는 의미는 아니다.

## 왜 읽을까

AI가 기존 기술을 대체한다기보다 문제의 경제성을 바꾸는 도구가 될 수 있다는 사례입니다. 동시에 범위를 크게 잡으면 여전히 실패한다는 점도 보여줍니다.

**프로젝트에 적용**
