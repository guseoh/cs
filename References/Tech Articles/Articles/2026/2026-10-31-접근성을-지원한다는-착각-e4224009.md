# 접근성을 지원한다는 착각

> [!abstract] 한 줄 정리
> 접근성 속성은 스크린리더를 위한 부가 작업에 그치지 않습니다. UI의 역할과 상태를 기계가 해석할 수 있는 텍스트 인터페이스로 표현하면 사용자 요구사항을 직접 검증하는 테스트도 더 명확해집니다.

> 뱅크샐러드 기술 블로그 · 2025-07-16

## 핵심 내용

- **문제:** UI를 이미지처럼 취급하면 버튼·섹션의 의미와 상태를 자동 테스트에서 확인하기 어려워, 비즈니스 로직만 별도 함수로 떼어 테스트하거나 취약한 이미지 스냅샷에 의존하게 됩니다. - **접근:** 화면 요소에 역할과 이름을 부여하고 `aria-expanded` 같은 상태를 노출해 스크린리더와 테스트 코드가 동일한 의미 정보를 활용하도록 했습니다. - **구조:** '첫 섹션은 접혀 있어야 한다'는 요구사항을 별도 테스트 전용 상태 함수가 아니라 `getByRole`과 접힘 상태 assertion으로 실제 렌더링 결과에서 확인하는 예시를 보여 줍니다.

- **확장:** iOS에서도 접근성 트리를 텍스트로 표현하는 AXSnapshot 사례를 소개해, 접근 가능한 UI 구조를 문서화·검증 가능한 인터페이스로 활용하는 방식을 설명합니다. - **주의점:** 글은 접근성과 테스트 가능성의 설계 관점을 설명하는 글이며 접근성 점수 개선율이나 테스트 시간 절감률을 실측한 보고서는 아닙니다. 의미 기반 테스트도 실제 사용자 보조 기술 검증을 완전히 대체하지는 않습니다.

접근성 정보는 스크린리더를 위한 배려이면서 **화면이 무엇을 의미하는지 기계가 확인할 수 있는 계약**이다. 클래스 이름이나 DOM 구조에 의존하는 테스트는 마크업 변경에 쉽게 깨지지만, 역할·이름·상태를 사용하면 사용자가 실제로 인지하는 동작을 검증할 수 있다.

```tsx
// 개념 설명용 재구성: 의미 있는 상태 노출
<button aria-expanded={open} onClick={() => setOpen(!open)}>
  주문 상세
</button>
```

```typescript
// 구조보다 사용자 의미를 검사
expect(screen.getByRole("button", { name: "주문 상세" }))
  .toHaveAttribute("aria-expanded", "false");
```

자동 테스트 통과가 실제 키보드 탐색, 포커스 이동, 스크린리더 사용성을 모두 보장하지는 않는다. 접근성 트리 기반 자동 검사와 실제 보조 기술 사용성 검증은 보완 관계다.

## 왜 읽을까

UI 테스트를 CSS 선택자나 스크린샷의 문제로만 보지 않고 '사용자에게 어떤 의미와 상태가 전달되는가'를 검증하는 문제로 재정의합니다. 접근성 설계와 회귀 테스트 유지보수성이 서로 강화될 수 있다는 점이 핵심입니다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집글 작성·지원·승인 화면의 버튼, 입력 필드, 상태 메시지에 의미 있는 접근성 이름과 역할을 부여합니다.
- [ ] E2E 테스트는 가능한 경우 `getByRole`·레이블 기반으로 작성하고, 지원 상태 변경 후 실제 UI에 노출되는 의미를 assertion으로 검증합니다.
- [ ] 키보드 탐색과 스크린리더로 주요 신청 흐름을 점검해 자동 테스트만으로 놓치는 문제를 확인합니다.
