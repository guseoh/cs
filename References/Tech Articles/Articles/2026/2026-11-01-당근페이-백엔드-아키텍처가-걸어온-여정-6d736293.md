# 당근페이 백엔드 아키텍처가 걸어온 여정

> [!abstract] 한 줄 정리
> 빠른 출시를 위한 계층형 구조가 성장 뒤 강결합을 만들었고, 헥사고날 구조도 공통 어댑터 집중과 불필요한 동반 배포라는 새 문제를 낳았습니다. 최종 구조는 도메인별 모듈과 독립 배포 경계를 기준으로 재설계했습니다.

> 당근 기술 블로그 · 2026-01-15

## 핵심 내용

당근페이의 아키텍처 변화는 Layered → Hexagonal → Clean이라는 이름의 유행을 따라간 과정이 아니다. 빠른 서비스 출시에는 Controller·Service·Repository 계층형 구조가 적합했지만 도메인 간 순환 참조와 중복 로직, 특정 스프링 구현에 대한 의존이 누적되자 변경 영향 범위가 커졌다. 해결하려던 문제의 종류가 달라지면서 구조도 다시 검토됐다.

초기 Controller–Service–Repository 구조는 출시에는 적합했지만 도메인 확장 뒤 서비스 간 순환 참조·중복 로직·Spring 기술 의존이 늘어났습니다.

도메인·유스케이스·어댑터로 나눈 헥사고날 아키텍처로 의존성을 제어했지만, 여러 도메인이 공통 Adapter에 모이고 한 서비스 수정이 무관한 서비스 배포까지 유발했습니다.

 ```mermaid
flowchart LR
 A[Layered: 빠른 초기 개발] -->|순환 참조·도메인 결합| B[Hexagonal]
 B -->|공통 Adapter·동반 배포| C[Clean + Monorepo]
 C --> D[도메인별 core·usecase]
 D --> E[선택적 모듈 조합·배포]
```

*원문 근거를 토대로 가로 방향으로 자체 재구성한 학습용 흐름도다.*

헥사고날 구조에서 도메인·유스케이스·어댑터 책임을 분리한 것은 진전이었지만 여러 도메인의 코드를 공통 Adapter에 계속 넣으면 경계가 다시 흐려졌다. 또한 한 도메인 수정이 무관한 서비스 배포까지 유발했다. 이 문제를 줄이기 위해 bootstrap, core, infrastructure, library, platform, usecase 같은 모듈 구성을 도메인별로 정하고 필요한 모듈만 조합하여 배포하는 방향으로 바꾸었다.

```text
# 원문의 모듈 분리 기준을 축약한 개념 예시
bootstrap / core / infrastructure
library   / platform / usecase
```

각 이름을 그대로 복사하는 대신 프로젝트의 도메인 규칙과 배포 경계를 먼저 정의해야 한다.

Clean Architecture와 모노레포로 전환하면서 bootstrap, core, infrastructure, library, platform, usecase의 여섯 모듈 영역을 정하고 도메인별 구현과 배포 조합을 분리했습니다.

money 유스케이스 변경이 다른 배너·포인트 서비스의 배포로 번지지 않도록 경계를 만들었습니다. 모노레포의 빌드 속도와 인지 부하라는 새 비용은 남았습니다.

| 단계 | 해결하려던 문제 | 새로 생겼거나 남은 문제 |
| --- | --- | --- |
| Layered | 초기 개발 속도 확보 | 서비스 간 순환 참조·도메인 규칙 결합 |
| Hexagonal | 유스케이스·어댑터 의존 역전 | 공통 Adapter에 구현 집중, 동반 배포 |
| Clean + Monorepo | 도메인별 모듈과 배포 경계 재설계 | 빌드 시간·인지 부하 관리 필요 |

*모든 프로젝트가 이 순서로 구조를 바꿔야 한다는 뜻이 아니라 조직과 변경 패턴에 따라 선택지가 달라진다는 사례다.*

의존성 방향과 배포 단위는 함께 검토해야 한다. 도메인 코드만 분리하고 빌드·실행 구성이 모든 도메인을 묶는다면 독립적인 변경으로 연결되기 어렵다. 반대로 모노레포·멀티모듈을 도입하면 빌드 시간과 의존 관계의 인지 비용도 생긴다. 따라서 설계 패턴 이름이 아니라 변경 이유·변경의 전파 범위·테스트 격리 효과가 판단 기준이 된다.

## 왜 읽을까

패턴의 이름보다 어떤 변경이 다른 도메인과 배포에 영향을 주는지를 기준으로 구조를 평가하는 실제 사례입니다. 계층형→헥사고날→클린 아키텍처를 정답의 순서로 보지 않고, 단계마다 새로 드러난 문제와 선택 비용을 비교할 수 있습니다.
