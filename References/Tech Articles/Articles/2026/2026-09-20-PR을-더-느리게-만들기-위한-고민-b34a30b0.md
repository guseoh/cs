# PR을 더 느리게 만들기 위한 고민

> [!abstract] 한 줄 정리
> AI가 구현 속도를 높이자 병목은 코드 작성에서 사람의 이해와 리뷰로 이동했다. 리뷰 자체를 무작정 빠르게 하기보다 작은 PR과 의사결정 문서, AI 사전 리뷰로 사람이 판단해야 할 범위를 줄이는 접근이 핵심이다.

> 카카오페이 기술 블로그 · 2026-06-12

## 핵심 내용

- **문제:** AI 사용 프로젝트는 1인당 일평균 PR이 0.8건에서 1.7건으로 늘었지만 PR 생성부터 머지까지 중앙값은 5시간 24분이었다. 첫 사람 리뷰까지 2시간 50분, 이후 머지까지 2시간 40분이 걸려 사람의 가용성이 병목이 됐다.
- **접근:** 구현 전에 설계 문서를 만들고 Task → JIRA subtask → PR로 분해했다. PR 변경 라인 중앙값은 246줄에서 158줄, 변경 파일은 14개에서 5개로 줄었고 200줄 이하 PR 비율은 37%에서 60%로 증가했다.
- **구조:** PR 템플릿을 체크리스트가 아니라 문제·선택 이유·트레이드오프·영향 범위·실패 시나리오·대안·위험 리뷰 포인트를 담는 의사결정 문서로 바꿨다.
- **결과:** AI 리뷰어는 약 2분 안에 구조적 품질을 먼저 스캔했다. 분석한 188개 코멘트 중 30건(16%)이 코드 수정으로 이어졌고, AI는 예외 처리·null-safety 같은 기계적 검토를 넓게 맡는 반면 사람은 비즈니스 판단과 토론에 집중했다.
- **주의점:** AI 리뷰가 머지 시간을 직접 줄인 것은 아니다. 리네임·포맷팅 같은 확인 문제와 비즈니스 로직·새 패턴·트레이드오프처럼 사람의 판단이 필요한 문제를 구분하는 것이 더 중요했다.

## 왜 읽을까

AI 생산성이 높아졌는데 왜 팀 전체 속도는 그대로인지 설명하는 좋은 사례다. 코드 생산량이 아니라 리뷰 가능성, PR 크기, 의사결정 기록이라는 지표로 병목을 다시 정의한다는 점이 특히 유용하다.

**프로젝트에 적용 — DevPedia**

- [ ] Codex가 한 번에 큰 변경을 만들기보다 학습영역·검증 책임별로 독립 리뷰 가능한 PR 단위로 분해한다.
- [ ] PR 본문에 선택 이유·트레이드오프·실패 시나리오·집중 리뷰 지점을 남긴다.
- [ ] 기계적 검사는 AI와 자동 검증에 맡기고 사람 검토는 콘텐츠 품질·도메인 판단·설계 결정에 집중한다.
