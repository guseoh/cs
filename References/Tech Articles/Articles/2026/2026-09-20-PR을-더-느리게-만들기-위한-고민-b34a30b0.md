# PR을 더 느리게 만들기 위한 고민

> [!abstract] 한 줄 정리
> AI가 구현 속도를 높이자 병목은 코드 작성에서 사람의 이해와 리뷰로 이동했다. 리뷰 자체를 무작정 빠르게 하기보다 작은 PR과 의사결정 문서, AI 사전 리뷰로 사람이 판단해야 할 범위를 줄이는 접근이 핵심이다.

> 카카오페이 기술 블로그 · 2026-06-12

## 핵심 내용

AI로 구현 속도가 빨라지면 PR 생성량이 늘지만 사람의 코드 이해 속도까지 자동으로 빨라지는 것은 아니다. 카카오페이손해보험은 일평균 PR 0.8→1.7건의 변화 속에서도 PR 생성~병합 중앙값이 5시간 24분으로 남아 있었고 첫 리뷰 2시간 50분이 병목임을 관찰했다.

팀은 PR을 무작정 빨리 합치는 대신 구현 전 설계를 확정하고 Task→JIRA subtask→PR 단위로 변경을 분할했다. PR의 변경 라인 중앙값이 246→158줄, 파일 수가 14→5개로 줄고 200줄 이하 PR 비율은 37→60%로 증가했다. PR 템플릿에는 문제·선택 근거·대안·트레이드오프·실패 시나리오와 리뷰 우선 위치를 기록해 코드 외의 판단 맥락도 제공했다.

| PR 운영 지표 | 이전 | 변경 후 |
| --- | ---: | ---: |
| 1인 일평균 PR | 0.8건 | 1.7건 |
| 변경 라인 중앙값 | 246줄 | 158줄 |
| 변경 파일 | 14개 | 5개 |
| 200줄 이하 PR | 37% | 60% |
| 생성→병합 중앙값 | — | 5시간 24분 |
| AI 코멘트 → 실제 수정 | — | 30/188건(16%) |

AI 리뷰는 약 2분 안에 구조적 문제를 찾았지만 분석된 188개 코멘트 중 실제 코드 수정으로 이어진 건은 30건(16%)이었다. AI 리뷰가 병합시간을 직접 단축했다는 의미는 아니며 기계적으로 검증 가능한 null·예외·정적 규칙은 자동화하고 도메인·리스크 판단을 사람에게 남기는 역할 구분이 중요하다.

## 왜 읽을까

AI 생산성이 높아졌는데 왜 팀 전체 속도는 그대로인지 설명하는 좋은 사례다. 코드 생산량이 아니라 리뷰 가능성, PR 크기, 의사결정 기록이라는 지표로 병목을 다시 정의한다는 점이 특히 유용하다.

**프로젝트에 적용 — DevPedia**

- [ ] Codex가 한 번에 큰 변경을 만들기보다 학습영역·검증 책임별로 독립 리뷰 가능한 PR 단위로 분해한다.
- [ ] PR 본문에 선택 이유·트레이드오프·실패 시나리오·집중 리뷰 지점을 남긴다.
- [ ] 기계적 검사는 AI와 자동 검증에 맡기고 사람 검토는 콘텐츠 품질·도메인 판단·설계 결정에 집중한다.
