# 기술이 없던 곳에 기술 더하기: 사내 해커톤 플랫폼 만들기

> [!abstract] 한 줄 정리
> AI가 빠르게 만든 코드라도 실제 운영 환경의 세션·DB·권한·배포 제약을 통과하지 못하면 제품이 되지 않습니다.

> techblog.woowahan.com

## 핵심 내용

사내 해커톤 플랫폼을 빠르게 구현하면서 AI를 활용했지만, 초기 구현의 SQLite, 공유 세션, AWS 권한과 배포 환경, Bedrock 연동 같은 실제 시스템 제약을 차례로 마주친 사례입니다. 생성된 코드를 그대로 믿기보다 운영 환경에 맞는 저장소와 상태 관리, 권한 구조로 다시 검증하고 수정합니다.

해커톤에서 AI가 만들어 준 화면과 서버 코드가 빠르게 동작해도 실제 행사에서는 로그인 세션의 소유권, SQLite의 동시 쓰기, 클라우드 IAM, 배포 비밀과 같은 제약이 드러난다. 짧은 개발 기간에는 기능 수보다 **행사 핵심 흐름이 고장 났을 때 복구할 수 있는가**에 우선순위를 둬야 한다.

| 처음 구현이 쉬운 선택 | 실제 운영에서 확인할 점 |
| --- | --- |
| SQLite | 동시 접속·백업·쓰기 경합 |
| 단순 공유 세션 | 사용자 식별·세션 만료·권한 분리 |
| 넓은 AWS 권한 | 최소 권한·비밀 관리 |
| Bedrock 연동 | 요청 실패·비용·타임아웃 |
| 빠른 자동 배포 | 릴리스 확인·롤백 |

AI 생성 코드를 빠른 실험 도구로 활용하되 실제 운영 안전성까지 자동 완성된 것으로 취급하지 않는 것이 이 프로젝트에서 얻을 수 있는 교훈이다.

## 왜 읽을까

AI 개발 생산성과 운영 가능성 사이의 간극을 구체적으로 볼 수 있습니다. 빠른 프로토타입과 운영 시스템의 기준이 다르다는 점이 잘 드러납니다.

**프로젝트에 적용**

**PawCycle** — Codex가 구현한 기능도 로컬 테스트 통과에서 끝내지 않고 다중 인스턴스, 세션 저장, AWS 권한, 배포 후 health check까지 실제 운영 조건으로 검증하는 체크리스트를 만들 수 있습니다.
