# AI로 E2E 회귀 테스트 자동화하기: ‘딸깍’을 파이프라인으로 바꾸기까지

> [!abstract] 한 줄 정리
> AI가 테스트 코드를 실행 가능하게 만들었다고 해서 의도한 동작까지 검증한 것은 아니다. 원본 기대 결과를 고정하고, 누락·위양성·모호함을 별도 게이트로 검사해야 신뢰할 수 있는 자동화가 된다.

> LY Corporation 기술 블로그 · LINE Plus · 2026-10-16

## 핵심 내용

AI가 Playwright 테스트 코드를 생성해 실행이 PASS가 되더라도 실제 테스트 명세를 충족했다고 단정할 수 없다. LY의 초기 파이프라인은 중복된 요소에서 무조건 첫 locator를 고르거나 여섯 항목 중 하나만 검사하고도 전체 테스트 성공으로 기록했다. 따라서 코드 생성과 별개로 **원래 기대 결과가 생성된 assertion에 모두 반영됐는지** 검증하는 추적 계약이 필요했다.

초기 v1의 케이스 파싱→locator 검증→코드 생성→실행→리포트 절차를 v2에서 `raw_expected`, `expected_items`, `assertions`, `covers`로 연결했다. 사람의 판단이 필요한 모호한 locator나 기대 결과는 `gaps`에 남겨 자동 진행을 중단한다. 또한 `test.only`, `test.skip`, `waitForTimeout`처럼 테스트가 실행됐지만 실제 검증을 건너뛰거나 타이밍에 기대는 코드는 실행 전에 정적 검사로 차단한다.

```json
{
  "raw_expected": "카드 3개가 표시된다",
  "expected_items": ["카드 수=3"],
  "assertions": ["cardCount === 3"],
  "covers": ["카드 수=3"],
  "gaps": []
}
```

*기대 결과의 전 범위가 assertion에 매핑되는 방식을 보여주는 학습용 간소화 예시다. 실제 테스트 ID와 JSON 구조는 원문의 명세에 따라 달라질 수 있다.*

| 단계 | v1에서 발생한 문제 | v2 검증 경계 |
| --- | --- | --- |
| locator 선택 | 동일 요소 중 첫 번째를 임의 선택 | 모호하면 gaps로 사람 승인 |
| assertion 생성 | 6개 기대값 중 1개만 확인 | covers로 전수 대응 관계 확인 |
| 실행 전 검사 | skip/only 등 우회 가능 | 위험 패턴 거절 |
| PASS 판정 | 실제로 틀려도 PASS | 기대값 변조 후 반드시 FAIL 확인 |

원문의 핵심 검증은 기대값을 3에서 4로 바꿔 기존 생성 테스트가 반드시 실패하는지 확인하는 위양성 탐지 실험이다. 테스트 코드가 컴파일되고 브라우저가 열리는 것만으로는 오류를 잡지 못하기 때문이다. 98개 수동 회귀 케이스를 자동화하고 총 196개·11개 영역으로 확대했지만, 파이프라인 설계에는 수개월이 들었고 사람의 locator·버그 판별 역할도 남았다.

## 왜 읽을까

AI로 생성한 테스트가 초록색으로 통과하는 상황에서도 회귀 검증의 공백이 생길 수 있음을 실제 사례로 보여준다. 자동화율보다 **요구사항과 assertion의 추적성**, 모호할 때 멈추는 설계, 사람이 확인해야 할 증거의 품질을 평가하는 관점을 얻을 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집·지원·승인 중 하나의 핵심 사용자 흐름을 고르고 기대 결과를 최소 검증 단위로 나눈다.
- [ ] E2E 테스트의 assertion이 각 기대 결과를 실제로 검증하는지 매핑한다.
- [ ] 의도적으로 기댓값을 바꿨을 때 실패하는지 확인하고, 애매한 UI locator는 화면 근거로 검토한다.
