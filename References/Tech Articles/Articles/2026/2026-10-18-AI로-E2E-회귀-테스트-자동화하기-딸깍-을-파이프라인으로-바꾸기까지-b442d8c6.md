# AI로 E2E 회귀 테스트 자동화하기: ‘딸깍’을 파이프라인으로 바꾸기까지

> [!abstract] 한 줄 정리
> AI가 테스트 코드를 실행 가능하게 만들었다고 해서 의도한 동작까지 검증한 것은 아니다. 원본 기대 결과를 고정하고, 누락·위양성·모호함을 별도 게이트로 검사해야 신뢰할 수 있는 자동화가 된다.

> LY Corporation 기술 블로그 · LINE Plus · 2026-10-16

## 핵심 내용

- **문제:** 초기 파이프라인은 중복된 화면 요소에서 무조건 첫 번째 locator를 선택하거나, 6개 항목 중 1개만 검증하고도 테스트를 PASS 처리했다. 실행 성공과 테스트 의도 충족은 달랐다.
- **구조:** v1은 케이스 파싱 → locator 검증 → 코드 생성 → 실행 → 리포팅의 5단계였다. v2는 원본 기대 결과를 `raw_expected`·`expected_items`·`assertions`·`covers`로 연결하고, 판단이 모호하면 `gaps`에서 사람의 답을 기다리도록 바꿨다.
- **검증:** 명세 형식, assertion 누락, `test.only`·`test.skip`·`waitForTimeout` 등 위험 패턴을 실행 전 검사한다. 기대값 3을 4로 바꿔 테스트가 실제 실패하는지 확인하는 위양성 검증과 스크린샷 기반 리뷰 패킷도 추가했다.
- **수치:** 기존 수동 회귀 케이스 98개를 모두 자동화하고 총 196개·11개 영역으로 확대했다. 파이프라인 설계·개선에는 수개월이 들었지만 완성 후 실제 테스트 코드 구축은 약 한 달이었다.
- **트레이드오프:** 구축·유지 비용이 있으며 단순 노출 여부 등 일부 assertion은 자동 위양성 검증이 어렵다. 사람은 locator의 실제 의미와 제품 버그 여부를 계속 판단해야 한다.

## 왜 읽을까

AI로 생성한 테스트가 초록색으로 통과하는 상황에서도 회귀 검증의 공백이 생길 수 있음을 실제 사례로 보여준다. 자동화율보다 **요구사항과 assertion의 추적성**, 모호할 때 멈추는 설계, 사람이 확인해야 할 증거의 품질을 평가하는 관점을 얻을 수 있다.

**프로젝트에 적용 — DevPedia**

- [ ] 모집·지원·승인 중 하나의 핵심 사용자 흐름을 고르고 기대 결과를 최소 검증 단위로 나눈다.
- [ ] E2E 테스트의 assertion이 각 기대 결과를 실제로 검증하는지 매핑한다.
- [ ] 의도적으로 기댓값을 바꿨을 때 실패하는지 확인하고, 애매한 UI locator는 화면 근거로 검토한다.
