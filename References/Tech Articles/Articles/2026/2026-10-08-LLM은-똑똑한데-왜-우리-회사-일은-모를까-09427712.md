# LLM은 똑똑한데, 왜 우리 회사 일은 모를까

> [!abstract] 한 줄 정리
> 검색 결과를 많이 가져오는 것만으로는 사내 지식의 정확성과 최신성을 보장할 수 없다. 문서·코드·대화의 출처, 변경 상태, 충돌 여부를 별도의 컨텍스트 계층에서 관리해야 한다.

> 토스 기술 블로그 · 2026-07-30

## 핵심 내용

- **문제:** 운영 문서의 재시도 정책, 회의에서 결정한 정책, 실제 코드가 서로 다를 수 있다. 검색 결과의 관련성만으로 무엇이 현재 사실인지 판단하기 어렵다.
- **구조:** 문서는 제목 계층을 유지한 섹션, 메신저는 전체 스레드, 코드는 파서가 추출한 심볼과 코드 근거를 포함한 semantic card로 나눠 `ContentUnit`에 정규화한다.
- **접근:** Granularity·Faithfulness·Staleness·Canonicality·Consistency·Coverage의 여섯 축을 분리해 검증한다. 모호한 별칭 병합과 근거 충돌은 사람의 승인 대상으로 남긴다.
- **최신성:** content hash와 코드의 commit/span hash로 변경 여부를 먼저 판단한다. 바뀌지 않은 근거는 재사용하고 달라진 코드 근거만 의미 검증을 다시 수행한다.
- **결과:** `trusted`, `disputed`, `stale_risk`, `insufficient_evidence` 등 상태와 원문 근거를 함께 제공한다. 모든 품질 문제가 자동 해결된 것은 아니며 특히 누락된 정보의 Coverage 판단에는 한계가 있다.

## 왜 읽을까

AI가 만든 설명을 신뢰할지 판단할 때 검색 순위보다 **출처·버전·실제 구현과의 일치**가 더 중요하다는 기준을 얻는다. 문서와 코드가 불일치할 때 어느 쪽이 정답인지 자동 단정하지 않는 설계가 특히 유용하다.

**프로젝트에 적용 — DevPedia**

- [ ] API/인증 설계 문서마다 관련 구현 경로와 검증한 commit SHA를 연결한다.
- [ ] 로그인·세션·인가 계약을 문서와 통합 테스트 결과로 교차 확인한다.
- [ ] 문서와 구현이 다르면 즉시 덮어쓰지 않고 `검증 필요/구현 변경 중` 상태로 기록한다.
