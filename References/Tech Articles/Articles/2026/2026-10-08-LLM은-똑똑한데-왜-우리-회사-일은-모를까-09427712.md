# LLM은 똑똑한데, 왜 우리 회사 일은 모를까

> [!abstract] 한 줄 정리
> 검색 결과를 많이 가져오는 것만으로는 사내 지식의 정확성과 최신성을 보장할 수 없다. 문서·코드·대화의 출처, 변경 상태, 충돌 여부를 별도의 컨텍스트 계층에서 관리해야 한다.

> 토스 기술 블로그 · 2026-07-30

## 핵심 내용

사내 문서, 회의 기록, 코드가 같은 정책에 대해 서로 다른 내용을 담을 때 RAG 검색 상위에 뜬 문장을 그대로 현재 사실로 취급하면 위험하다. 토스의 지식 검색 설계는 벡터 유사도만 높이는 문제보다 어떤 근거가 최신·공식·충분한지 판정할 책임을 먼저 분리했다.

문서는 제목 계층을 유지한 섹션으로, 메신저는 스레드 전체로, 코드는 파서가 추출한 심볼과 근거 위치를 포함한 Semantic Card로 나눠 `ContentUnit`에 정규화한다. 근거의 단위를 적절히 유지하는 Granularity, 출처에 충실한 Faithfulness, Staleness, Canonicality, Consistency, Coverage를 서로 다른 품질 축으로 검증한다. 콘텐츠 hash와 코드 commit/span hash를 비교해 바뀌지 않은 자료는 재사용하고 변경된 근거만 다시 의미 검증하도록 설계했다.

| 품질 축 | 핵심 질문 | 실패 예시 |
| --- | --- | --- |
| Granularity | 필요한 의미 단위를 잘랐는가 | 문맥이 사라진 문서 청크 |
| Faithfulness | 근거를 벗어나지 않았는가 | 코드에 없는 동작 주장 |
| Staleness | 현재 버전의 자료인가 | 오래된 설계문서 |
| Canonicality | 승인된 정본인가 | 미승인 회의 아이디어 |
| Consistency | 자료끼리 충돌하는가 | 문서·코드의 재시도 조건 상이 |
| Coverage | 답할 자료가 충분한가 | 누락된 정책을 그럴듯하게 생성 |

신뢰 상태를 `trusted`, `disputed`, `stale_risk`, `insufficient_evidence`처럼 나눠 결과에 원문과 위치를 함께 제공한다. 특히 최신 코드와 과거 결정 문서가 충돌하면 어느 쪽이 권위 있는 자료인지 사람이 판단해야 한다. 문서에 없는 결정을 AI가 추론해서 채우면 커버리지 부족이 숨겨지므로 '증거가 불충분함'을 명시하는 것이 올바른 결과일 수 있다.

## 왜 읽을까

AI가 만든 설명을 신뢰할지 판단할 때 검색 순위보다 **출처·버전·실제 구현과의 일치**가 더 중요하다는 기준을 얻는다. 문서와 코드가 불일치할 때 어느 쪽이 정답인지 자동 단정하지 않는 설계가 특히 유용하다.

**프로젝트에 적용 — DevPedia**

- [ ] API/인증 설계 문서마다 관련 구현 경로와 검증한 commit SHA를 연결한다.
- [ ] 로그인·세션·인가 계약을 문서와 통합 테스트 결과로 교차 확인한다.
- [ ] 문서와 구현이 다르면 즉시 덮어쓰지 않고 `검증 필요/구현 변경 중` 상태로 기록한다.
