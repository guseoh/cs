# 토스의 디바이스 팜 만들기

> [!abstract] 한 줄 정리
> 테스트 인프라의 목표는 도구를 늘리는 것이 아니라 검증 환경을 싸고 빠르게 제공해 팀의 테스트 빈도를 높이는 것입니다.

> toss.tech

## 핵심 내용

각 팀이 맥미니와 스마트폰을 따로 관리하며 Appium 설정, 기기 장애, 보안 정책을 반복 처리하던 문제를 중앙 디바이스 팜 Nebula로 통합했습니다. 기기 15대와 개발자 한 명에서 시작해 100대 이상으로 확장했고 기기 점유와 테스트 실행을 API로 추상화했습니다. 자체 Driver는 주요 클릭 52ms 대 Appium 702ms, 텍스트 입력 138ms 대 1,377ms처럼 토스 사용 패턴에서 큰 성능 차이를 측정한 뒤 선택했으며 직접 유지보수 비용을 감수합니다. 자동 검수 시간도 30~40분에서 10분 이내로 줄었습니다.

분산 디바이스 팜은 장비 수를 늘리는 것뿐 아니라 테스트할 기기가 **누구에게 점유되어 있고 언제 반환되는지**를 일관되게 관리해야 한다. 각 팀의 맥미니와 앱 드라이버를 독립 운영하면 환경 차이로 인해 테스트 실패가 코드 문제인지 인프라 문제인지 분리하기 어려워진다. Nebula는 중앙 제어 API로 점유와 실행을 추상화해 자동화 장치와 내부 보안 기준을 한곳에 모았다.

| Android 동작 | Appium | 자체 Driver |
| --- | ---: | ---: |
| 클릭 | 702ms | 52ms |
| 텍스트 입력 | 1,377ms | 138ms |

이 비교는 해당 조직의 주요 테스트 패턴과 구현 조건에 한정된다. 자체 Driver가 빨라진 대신 범용 Appium이 맡던 호환성·유지보수 책임을 직접 부담한다.

## 왜 읽을까

기존 솔루션을 왜 버렸는지를 실제 측정과 요구사항으로 설명하고, 테스트 인프라가 개발 생산성에 미치는 영향을 볼 수 있습니다.
