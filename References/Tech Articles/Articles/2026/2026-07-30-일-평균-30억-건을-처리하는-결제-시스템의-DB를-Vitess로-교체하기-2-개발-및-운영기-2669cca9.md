# 일 평균 30억 건을 처리하는 결제 시스템의 DB를 Vitess로 교체하기 - 2. 개발 및 운영기

> [!abstract] 한 줄 정리
> 대규모 DB 플랫폼 선택에서도 공식 권장 방식보다 실제 프로토콜 오류·DDL 운영·failover 책임을 측정하고 조직에 맞는 경로를 고르는 것이 중요합니다.

> techblog.lycorp.co.jp

## 핵심 내용

일 평균 약 30억 건을 처리하는 결제 시스템 DB를 Vitess로 옮기는 과정에서 gRPC를 시험했지만 `http2: frame too large`와 CPU 문제를 겪고 MySQL protocol로 전환합니다. Online DDL도 장점만 보고 채택하지 않고 운영 중단 가능성과 DBA 역할을 고려해 직접 MySQL DDL을 실행하는 방식을 선택합니다.

VTOrc를 통한 topology 감시와 장애 복구 등 운영 시나리오도 함께 검증합니다.

Vitess를 도입하면서 기존 MySQL 애플리케이션과 동등하게 동작할 것이라고 가정하면 샤딩 키, 트랜잭션 격리 수준, SQL 지원 범위에서 예상하지 못한 문제가 생길 수 있다. 원문은 애플리케이션이 샤딩 키를 전달하고 VTGate가 실제 서비스 샤드를 찾아 쿼리를 전달하는 흐름을 설명하며, 통신 방식에서 gRPC 오류와 CPU 문제를 겪은 뒤 MySQL Protocol을 채택했다.

| 운영 쟁점 | 원문의 판단 |
| --- | --- |
| gRPC 통신 | `http2: frame too large`와 CPU 부담 확인 |
| MySQL Protocol | 애플리케이션 호환 경로로 선택 |
| 단일 샤드 트랜잭션 | MySQL `REPEATABLE READ` |
| 다중 샤드 트랜잭션 | `READ COMMITTED` |
| Failover | VTOrc 장애 감지·승격 검증 |

프라이머리 종료 테스트에서 약 **10초 내외**의 애플리케이션 장애 후 복구를 관찰했다는 결과는 실험 조건의 관측치다. 장애 상황마다 동일한 복구 시간이 보장된다는 의미는 아니다.

## 왜 읽을까

새 기술의 대표 기능을 그대로 쓰지 않고 자신의 트래픽·운영 조직·장애 책임에 맞춰 선택을 바꾸는 실제 사례입니다.

**프로젝트에 적용**

**PawCycle** — DB나 인프라 기술을 바꿀 때 벤치마크뿐 아니라 backup/restore, failover, schema 변경, rollback 주체까지 검증 항목에 포함하는 기준으로 활용할 수 있습니다.
