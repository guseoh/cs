# 이커머스 플랫폼의 주문 DB 마이그레이션 경험기

> [!abstract] 한 줄 정리
> Oracle→MySQL 이관을 단순 DB 교체로 끝내지 않고 데이터 모델, JPA 영속성 경계, ID 생성, 동시성, 무중단 전환까지 함께 재설계했다. 핵심은 새 DB에 복사하는 것이 아니라 새 구조가 더 빠르고 정합하며 되돌릴 수 있음을 단계적으로 증명한 것이다.

> LY Corporation Tech Blog · 2024-03-07

## 핵심 내용

기존 주문 조회에서 17개 테이블을 조인하고 상품 약 100개인 주문의 조회가 최대 5초 이상 걸리자 LY는 Oracle 기반의 데이터 모델을 MySQL로 옮기면서 조회 모델을 다시 설계했다. 단순 DB 제품 이전이 아니라 **검색에 유리한 정규화 모델**과 **빠른 상세 조회를 위한 비정규화 모델**의 비용을 비교한 작업이다.

![LY 이커머스 주문 DB의 정규화 모델과 JSON 조회 모델 두 설계안](https://vos.line-scdn.net/landpress-content-v2-vcfc68aynwenkh3bno0ixfx8/1708672587997.png?updatedAt=1708672588000)

*그림 1. 원문 두 저장 모델 비교: 전체 JSON 저장과 정규화+비정규화 병행 구조 — [출처: 원문 기술 블로그](https://techblog.lycorp.co.jp/ko/experience-in-migrating-order-db-on-ecommerce-platform)*

![Oracle에서 MySQL로 이관하는 다섯 단계 읽기 쓰기 경로 전환](https://vos.line-scdn.net/landpress-content-v2-vcfc68aynwenkh3bno0ixfx8/1708673455657.png?updatedAt=1708673457000)

*그림 2. 원문 5단계 이관 도식: 이중 쓰기와 읽기 전환을 별도로 승인 — [출처: 원문 기술 블로그](https://techblog.lycorp.co.jp/ko/experience-in-migrating-order-db-on-ecommerce-platform)*

하나의 주문을 JSON으로만 저장하는 첫 방안은 검색의 유연성이 부족하고 Jackson 직렬화·JPA 변경 감지가 많은 비용을 차지했다. 두 번째 방안은 정규화된 여러 테이블과 주문 JSON 스냅샷을 함께 유지하고, 쓰기 변경 명세 객체로 정규화 테이블을 수정한 뒤 비정규화 조회 모델을 재구성했다. 통합 테스트에서 두 저장 모델의 상태가 같음을 확인하도록 했다. JPA Batch Insert와 Auto Increment의 마찰은 시간·인스턴스·시퀀스를 조합한 자체 18자리 ID로 해결했다.

| 작업 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 주문 단일 조회 | 약 60ms | 약 4ms |
| 주문 목록 | 약 150ms | 약 51ms |
| 검색 | 약 300ms | 약 60ms |
| 주문 수정 | 약 400ms | 약 17ms |

*네트워크 지연을 제외한 원문 실험 수치다. 마이그레이션 과정의 동시 쓰기·분산 락 경계를 검증하지 않으면 조회 속도만 개선하고 정합성을 잃을 수 있다.*

하지만 주문의 두 상품이 동시에 배송 상태를 바꾸면 정규화 테이블의 각 행은 정상인데 주문 전체 JSON을 치환하는 비정규화 테이블에서는 한쪽 수정이 덮어써지는 Lost Update가 발생했다. 기존 Redis 분산 락은 재진입을 지원하지 않아 Oracle/MySQL 프록시·서비스가 중첩 호출될 때 교착을 만들었고 재진입 가능한 락 구현으로 해결했다. 이관은 비동기 적재·검증→이중 쓰기→MySQL 읽기 전환→Oracle 수정 제거→Oracle 쓰기 제거의 다섯 단계로 수행했다.

## 왜 읽을까

JPA와 DB 모델링, 성능, 동시성, 무중단 마이그레이션이 한 사례 안에서 연결된다. 특히 “비정규화하면 빠르다” 같은 단순 규칙 대신 실제 직렬화 비용과 정합성 비용을 측정하고, 전환 단계마다 롤백 가능성을 남기는 과정이 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] 주문 조회 경로의 조인 수와 SQL 실행 계획을 기준선으로 남기고, 조회 모델 분리가 필요한 임계점을 측정한다.
- [ ] 읽기 최적화를 위해 비정규화 데이터를 추가한다면 원본과 조회 모델의 일관성을 검증하는 통합 테스트를 함께 만든다.
- [ ] 큰 데이터 구조 변경은 dual-write/비교 검증처럼 구·신 구조를 동시에 관찰할 수 있는 전환 단계를 설계한다.
