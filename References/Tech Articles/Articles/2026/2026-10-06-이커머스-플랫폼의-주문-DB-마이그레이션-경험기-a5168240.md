# 이커머스 플랫폼의 주문 DB 마이그레이션 경험기

> [!abstract] 한 줄 정리
> Oracle→MySQL 이관을 단순 DB 교체로 끝내지 않고 데이터 모델, JPA 영속성 경계, ID 생성, 동시성, 무중단 전환까지 함께 재설계했다. 핵심은 새 DB에 복사하는 것이 아니라 새 구조가 더 빠르고 정합하며 되돌릴 수 있음을 단계적으로 증명한 것이다.

> LY Corporation Tech Blog · 2024-03-07

## 핵심 내용

- **문제:** 기존 주문 조회는 17개 테이블 조인이 필요했고, 상품 약 100개 주문은 최대 5초 이상 걸렸다.
- **접근:** 검색에 유연한 정규화 모델과 빠른 조회를 위한 비정규화 모델을 함께 운영했다. JPA 변경 감지와 Jackson 직렬화 비용까지 Pinpoint로 측정해 대안을 선택했다.
- **구조:** 업데이트 명세 객체와 변경 단위 애그리게이션을 사용해 전체 그래프 로딩을 피하고, 정규화/비정규화 데이터 일관성은 통합 테스트로 검증했다.
- **주의점:** 주문 전체 JSON을 치환하는 비정규화 테이블에서 동시 업데이트가 서로를 덮어쓰는 문제가 발생해 Redis 분산 락을 도입했고, 기존 락의 재진입 한계 때문에 재진입 가능한 구현까지 필요했다.
- **결과:** 네트워크 지연을 제외하면 단일 조회 약 60ms→4ms, 주문 목록 약 150ms→51ms, 검색 약 300ms→60ms, 주문 수정 약 400ms→17ms로 개선됐다. 전환은 비동기 적재·검증 → 이중 쓰기 → MySQL 읽기 → Oracle 수정 제거 → Oracle 쓰기 제거의 5단계로 진행했다.

## 왜 읽을까

JPA와 DB 모델링, 성능, 동시성, 무중단 마이그레이션이 한 사례 안에서 연결된다. 특히 “비정규화하면 빠르다” 같은 단순 규칙 대신 실제 직렬화 비용과 정합성 비용을 측정하고, 전환 단계마다 롤백 가능성을 남기는 과정이 좋다.

**프로젝트에 적용 — PawCycle**

- [ ] 주문 조회 경로의 조인 수와 SQL 실행 계획을 기준선으로 남기고, 조회 모델 분리가 필요한 임계점을 측정한다.
- [ ] 읽기 최적화를 위해 비정규화 데이터를 추가한다면 원본과 조회 모델의 일관성을 검증하는 통합 테스트를 함께 만든다.
- [ ] 큰 데이터 구조 변경은 dual-write/비교 검증처럼 구·신 구조를 동시에 관찰할 수 있는 전환 단계를 설계한다.
